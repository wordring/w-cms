# 【一覧】語彙

w-cms のページ本文（HTML）で使える**語彙**のリファレンス。**何が書けるのか**と、
**どの形式がどのDBテーブルへ入るのか**だけを書きます。

> **分担**——**「いま何があるか」＝本ファイル**（正本は
> [internal/cms/vocab.go](../internal/cms/vocab.go) の `vocabRegistry`）。
> ⚠ **「なぜその形か・いつ変わったか」は書きません**——決定と理由は
> [【考察】語彙モデル.md](【考察】語彙モデル.md)（§9 決定ログ・§11）、経緯は
> [変更履歴.md](変更履歴.md) が正本です。
> 安全性の規則は [本文サニタイズ設計.md](本文サニタイズ設計.md) §5、計算プラグインの作り方は
> [【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md)。

> **形式を決めるのは「見える言葉」です。** `<section><h2>表示名</h2>…</section>` と書けば、
> **その見出しの言葉が形式を宣言**します（解決は `vocabTypeOf`。表は `<caption>` が同じ役目）。
> ⚠ **`data-type` は機械の名前**——属性があれば属性が勝ちますが、**書かなくてよい**のが普通の形です。
> ⚠ **属性が必須なのは可変タグ（`tags`）と、配線を属性に持つ形式**（`file-view`・`file`）だけ。
>
> ⚠ **未実装の形式は載せません**（設計中のものは各 `【考察】`・`【要求】` へ）。
> ⚠ **通信記録ページと参照は新しい形式ではなく可変タグで表します**（§4。参照の値は `ページID-ブロックID`）。

## 1. 本文の語彙は3つの層でできている

**①語彙レジストリ／②汎用索引／③計算プラグインの3層モデルは
[【考察】語彙モデル.md](【考察】語彙モデル.md) §4 が正本**。本ファイルが写すのは①の中身（§2）と、
それが②③のどこへ流れるか（§3）。運用上おさえるのは次の2点。

- **安全性の門はサニタイザだけで、レジストリは関与しない**。`data-type` の**値は検査されない**ので、
  レジストリに無い値も保存を通り、②汎用索引にも載る（保存応答の `unknown_types` で告知するだけ。
  [【一覧】API.md](【一覧】API.md)）。レジストリが担うのは編集支援（スラッシュメニュー・挿入骨格・
  型検証）と、鍵・型を解決するための語彙だけ。
- **エディタは語彙を手書きで持たない**。要素リストも形式リストも `GET /api/tag-schema` から受け取る
  （応答は `elements` / `void` / `block_id` / `vocab` / `vocabulary` / `column_types` / `extensions` の7キー。
  `extensions` は載っている拡張の名簿で、画面が拡張のボタンを出し分けるのに使い、
  `column_types` は `th[data-type]` に書ける列型の一覧）。
  `assets/index.html` に手書きで残るスラッシュメニュー項目は `h1`（見出し）・`p`（段落）・画像（レジストリの
  形式ではなく添付＋`<img>` の挿入操作）の3つだけで、残りは `populateSlashMenuVocab` がレジストリから生成する。

### 1.1 `data-*` マーカーの許可範囲

**許可範囲（どの属性をどの要素へ許すか・値を検査するか）の正本は
[本文サニタイズ設計.md](本文サニタイズ設計.md) §5.4**（実装は
[internal/cms/htmldoc/sanitize.go](../internal/cms/htmldoc/sanitize.go)）。本文の語彙マーカーは
**`data-type`（型名）・`data-src`（出所アドレス）・`data-ref`（ファイル表示の配線・
`section` 限定）の3つだけ**で、`data-id`（保存の単位）と
`id`（リンクの宛先）は全要素共通の別枠（この2つを分ける理由は
[【考察】語彙モデル.md](【考察】語彙モデル.md) §9）。語彙側の固有事情だけをここに書く。

- **`th[data-type]` だけは意味が違う**——形式名ではなく**列型**を明示する。使えるのは
  **9つ**（`validColumnTypes`・[vocab.go](../internal/cms/vocab.go)）: `text` / `code` /
  `number` / `date` / `datetime` / `enum` / `image` / `ref` / `email`。
  `datetime`（時刻を含む日時。`date` は日付だけ）・`ref`（他ページや
  その中のブロックへの参照）・`email`（メールの相手。値は `名前 <アドレス>` で、
  畳んだ値がアドレスだけ）——は、**タグの型としても名前から決まります**（§4）。
- **列型の決定順序は `th` の `data-type` 明示 > レジストリ宣言 > 見出し語の辞書 > `text`**
  （サーバーは `vocab_index.go` の `resolveColumnType`、エディタは同じ辞書を `/api/tag-schema` の
  `vocabulary` で受け取るので、索引と画面の判定が食い違わない）。
  **辞書の正本は `config/settings.json` の `vocabulary`**（1語につき `{"type": …, "values": [...]}` の
  1件で、型と選択肢を一緒に持つ）。
  ⚠ **Goコードに既定値は無く、ファイルが唯一の正本**（運用者がファイルへ足して
  DB再構築すれば効く）。
- **鍵（フィールド名）は見出しの表示文字**（`th` / `dt` のテキスト）ただ1つ。「見える文字がすべて」。
  ③計算形式では、その表示文字がレジストリ宣言の**ラベル**に一致することで機械キー
  （`Field`。§2.2）へ解決される。**機械キーを本文へ書き出す属性はない。**

> **見出しを改名すると、その列は③計算プラグインに読まれなくなる**（部材手配計算などの
> 型付きテーブルへ入らない）。黙って止まらないよう、解決できなくなった列は保存応答の
> `unresolved_fields` で告知する（拒否はしない。[【一覧】API.md](【一覧】API.md)）。

### 2.2 列と列型

⚠ **形式ごとの列の一覧は、ここには置きません。**
レジストリの `Columns` が決めるのは**2つだけ**で、**本文に何が書けるかではありません**:

1. **挿入の骨格**——スラッシュメニューから挿したとき最初に並ぶ見出し
2. **③計算が読む鍵**——見出しの表示文字が `Label` に一致したとき解決される機械キー（`Field`）

⚠ **本文の鍵は、書いた人が見出しに書いた言葉です。** 宣言に無い列を足しても索引には入り、
宣言どおりの列でも**見出しを改名すれば③計算からは外れます**（保存応答の `unresolved_fields`）。
**だから宣言を写した表は「本文の現実」にはなりません。**

**いまの宣言を見たいときは正本を見ます**——[internal/cms/vocab.go](../internal/cms/vocab.go) の
`vocabRegistry`、動いているサーバーなら `GET /api/tag-schema` の `vocab`
（拡張・設定から足した形式も入る）。

> ⚠ **`備考` の列だけが画面で折り返します**（`app.js` の `WRAP_COLUMNS`）。
> ほかの列は1行に保ち、表は自分の中で横スクロールします。
> ⚠ **`状態` の `完了` だけは「もう受注残に出さない」の宣言**です（`納品済` は出したという事実で、
> 残数があればまだ出る）。`材料発注`・`納品書発行`・`請求書発行` は人が付ける `済` の印
> （⚠ 「材料発注が終わった」の事実は手配状況リストの残要手配数 0 が答えで、印と事実を二重に持たない
> ——[【考察】製造という軸.md](【考察】製造という軸.md)）。

補足：

- **数値は正規化して読む**。`¥8,000` や全角の `８０００` は `8000` として解釈される
  （`NormalizeValue`）。正規化値は**併記**であり、生テキストが常に正本。
- **`quantity` の空セルは 1** として扱う（手で書く表で「1個」をいちいち書かせないため）。
- **型の不一致は拒否せず赤印で通知するだけ**。「自由な記述をシステムが認識する」というコンセプトを
  壊さないため（[【考察】語彙モデル.md](【考察】語彙モデル.md) §5.1）。
- `date` 型は `YYYY-MM-DD` へ正規化する（`YYYY/M/D`・`YYYY年M月D日` も受ける）。
- **`text` と `code` は「畳む強さ」だけが違う**。見た目も入力補助も同じで、
  索引の併記値（`norm_value`）の作り方が変わる:
  - `text` …… 軽く畳む（全角英数→半角・半角カナ→全角・濁点の合成・前後の空白）。
    **長音 `ー` には触らない**——`ひかりレーザー` を壊さないため。
  - `code` …… 強く畳む（軽い正規化＋空白の除去・ハイフン類/長音/`_`→`-`・英字は大文字）。
    図面番号・発注書番号のような**符牒**に付ける。**区切りの有無は畳まない**
    （`R520-M070` と `R520M070` は別扱い——別の部品を1つにしないため）。

  引くときは `PagesByTag`（生の完全一致）と `PagesByTagLoose`（畳んだ一致）を**呼ぶ側が選ぶ**。
  正本は [【考察】テキストの正規化.md](【考察】テキストの正規化.md)。
- **`enum` は `text` と同じに畳む。** 中の空白は畳みません（それは `code` だけ）。
  ⚠ **正規化しない列型は `image` だけ**です。
- **`image` 列の入力補助**は、セルにキャレットを置くと出る「🖼 画像を選ぶ」ボタンと、セルへの画像ドロップ
  （どちらも `insertImageIntoCell`。`/api/upload-image` へ送って `<img>` を入れる。[【要求】添付.md](【要求】添付.md)）。

### 2.3 形式の外形（HTMLの実例）

**いまの形**（1文書＝1ページ）。ヘッダは**ページの可変タグ**、原本は `<details>` で
畳んだ**ファイル表示**と「読んだまま」の写し、明細は **`<caption>` で形式を名乗る表**。
🤖 解析が受注ページに書く形がこれです（[ext/subcon/analyze_pdf.go](../ext/subcon/analyze_pdf.go) の
`buildOrderPageHTML`）。並びは**原本（PDF）→ 読んだまま → 弊社の明細**＝確かさの順。

```html
<h1>250715-304 みなと商店</h1>
<dl data-type="tags">
  <dt>発注書番号</dt><dd>250715-304</dd>
  <dt>発注元</dt><dd>みなと商店</dd>
  <dt>発注日</dt><dd>2026-07-15</dd>
  <dt>納期</dt><dd>2026-08-20</dd>
  <dt>小計</dt><dd>80000</dd>
  <dt>消費税</dt><dd>8000</dd>
  <dt>合計金額</dt><dd>88000</dd>
```

**業務データが入る表は2つだけ**です（コアテーブルは `pages` と `page_perms`。

（[【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md) §8）。

## 6. 本文はすべて標準HTML

**本文に独自の要素は1つも無い。** 語彙は**標準HTMLの担い手**（`table` / `dl` / `section` / `th`）に
見出しの表示文字（と、例外だけ `data-type`）で意味を載せる形だけです。
番人は `vocabulary_test.go` の `TestNoCustomElementVocabulary`——`AllowedVocabulary()` に
ハイフンを含む要素名が現れたら落ちます。

許可リストに無い要素は**アンラップされます**（要素は捨てられ、中身のテキストは残る）ので、
独自要素の混じった本文が入ってきても文字は失われません。
