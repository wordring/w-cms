# 【一覧】語彙

w-cms のページ本文（HTML）で使える**語彙**の実装済みリファレンス。何が書けるのか、どの形式がどのDBテーブルへ同期されるのかをまとめる。

> **分担**——**「いま何があるか」＝本ファイル**（形式の一覧・列・同期先。定義の実体は
> [internal/cms/vocab.go](../internal/cms/vocab.go) の `vocabRegistry`）。
> **「なぜその形か」＝[【考察】語彙モデル.md](【考察】語彙モデル.md)**（3層モデル・設計判断・決定ログ）。
> 安全性の規則は [本文サニタイズ設計.md](本文サニタイズ設計.md) §5、計算プラグインの作り方は
> [【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md)、ユースケースは
> [【ユースケース】受注から利益まで.md](【ユースケース】受注から利益まで.md)。

> **このファイルは現行実装の鏡（手書き）**。`vocabRegistry` を増減したら本ファイルも更新すること。
> **カスタム要素（`<m-*>`）は全廃済み**（2026-08-20）。新しい語彙はレジストリへ宣言1件を足す（§5）。
> 設計中の未実装形式（納品レコード等）は本ファイルには載せない
> （[【考察】通信記録処理.md](【考察】通信記録処理.md) を参照）。通信記録ページと参照は新しい形式では
> なく**可変タグ**で表す（§4。参照の値は `ページID-ブロックID`・D-4）。

> **`data-type` の位置づけは 2026-08-25 に変わった**——役割は階層と名前が主で、`data-type` は
> **機械が数えるための副**（[コンセプト.md](コンセプト.md) §1②）。さらに形式名を `data-type` 値から
> **セクションの見出しの言葉**へ移す**機能見出し**が 2026-08-31 に実装された（D-2・
> [【考察】語彙モデル.md](【考察】語彙モデル.md) §11）。`<section><h2>表示名</h2>…</section>` と書けば
> `data-type` 無しでその形式になり（解決は `vocabTypeOf`。属性があれば属性が勝つ）、エディタの
> スラッシュメニューもこの形で挿す。本ファイルの `data-type` 表記は属性形の名前で、機能見出し形の
> 実例は §2.3。

## 1. 本文の語彙は3つの層でできている

**①語彙レジストリ／②汎用索引／③計算プラグインの3層モデルは
[【考察】語彙モデル.md](【考察】語彙モデル.md) §4 が正本**。本ファイルが写すのは①の中身（§2）と、
それが②③のどこへ流れるか（§3）。運用上おさえるのは次の2点。

- **安全性の門はサニタイザだけで、レジストリは関与しない**。`data-type` の**値は検査されない**ので、
  レジストリに無い値も保存を通り、②汎用索引にも載る（保存応答の `unknown_types` で告知するだけ。
  [【一覧】API.md](【一覧】API.md)）。レジストリが担うのは編集支援（スラッシュメニュー・挿入骨格・
  型検証）と、鍵・型を解決するための語彙だけ。
- **エディタは語彙を手書きで持たない**。要素リストも形式リストも `GET /api/tag-schema` から受け取る
  （応答は `elements` / `void` / `block_id` / `vocab` / `type_inference` の5キー）。
  `assets/index.html` に手書きで残るスラッシュメニュー項目は `h1`（見出し）・`p`（段落）・画像（レジストリの
  形式ではなく添付＋`<img>` の挿入操作）の3つだけで、残りは `populateSlashMenuVocab` がレジストリから生成する。

### 1.1 `data-*` マーカーの許可範囲

**許可範囲（どの属性をどの要素へ許すか・値を検査するか）の正本は
[本文サニタイズ設計.md](本文サニタイズ設計.md) §5.4**（実装は
[internal/cms/htmldoc/sanitize.go](../internal/cms/htmldoc/sanitize.go)）。本文の語彙マーカーは
**`data-type`（型名）と `data-src`（出所アドレス）の2つだけ**で、`data-id`（保存の単位）と
`id`（リンクの宛先）は全要素共通の別枠（この2つを分ける理由は
[【考察】語彙モデル.md](【考察】語彙モデル.md) §9）。語彙側の固有事情だけをここに書く。

- **`th[data-type]` だけは意味が違う**——形式名ではなく**列型**（`text` / `number` / `date` /
  `enum` / `image`）を明示する。
- **列型の決定順序は `th` の `data-type` 明示 > レジストリ宣言 > 語→型推論辞書 > `text`**
  （サーバーは `vocab_index.go` の `resolveColumnType`、エディタは同じ辞書を `/api/tag-schema` の
  `type_inference` で受け取るので、索引と画面の判定が食い違わない）。
  **推論辞書の正本は `data/settings.json`**（Goコード内の値は既定値。運用者がファイルへ足して
  DB再構築すれば効く——2026-08-30）。
- **鍵（フィールド名）は見出しの表示文字**（`th` / `dt` のテキスト）ただ1つ。「見える文字がすべて」。
  ③計算形式では、その表示文字がレジストリ宣言の**ラベル**に一致することで機械キー
  （`Field`。§2.2）へ解決される。機械キーを本文へ書き出す `data-field` は 2026-08-20 に撤去した。

> **見出しを改名すると、その列は③計算プラグインに読まれなくなる**（部材手配計算などの
> 型付きテーブルへ入らない）。黙って止まらないよう、解決できなくなった列は保存応答の
> `unresolved_fields` で告知する（拒否はしない。[【一覧】API.md](【一覧】API.md)）。

## 2. 語彙レジストリ（12形式）

`internal/cms/vocab.go` の `vocabRegistry` の全件。`data-type` は kebab-case でレジストリ全体で一意。

### 2.1 形式の一覧

|---|---|---|---|---|---|
| `tags` | 🏷️ 可変タグ | メタ | `dl` | `vocab_index` | 鍵は `dt` の表示文字（自由語）。**タグ1つ＝名前：値の1対**（2026-08-26 決定。1つの `dt` に複数 `dd` は形式外・同名は対の繰り返しで）。見た目はチップ（左に名前・右に値の角丸）。骨格は1項目だけ生成し、項目操作UIで増やす |
| `part-materials` | 🔩 部材定義 | 業務 | `table` | `vocab_index` | 部材手配計算が読む③計算形式。**RequiresTag**=`部品番号`（鍵はページの可変タグにある。§4） |

> `section` の素の `dl`／`table`**（`vocab_index.go` の `OnElement`／`syncVocabSection`。2026-08-31）。
> `section` 自身は行を持たず、ヘッダの `<dl>`（`data-type` を持たない。§2.3）は包む `section` の
> 形式名で、素の `<table>` は `Items` の形式名（`client-order-items` 等）で載る。ファイル容器・
> 計算ビューは索引に無い。保存時の未知形式の告知（`UnknownVocabTypes`）は `table`／`dl`／`section` の
> `data-type` を見る（見出し語は未登録でも告知しない——普通の見出しへの誤検知を避けるため）。

- **数値は正規化して読む**。`¥8,000` や全角の `８０００` は `8000` として解釈される
  （`NormalizeValue`）。正規化値は**併記**であり、生テキストが常に正本。

- **型の不一致は拒否せず赤印で通知するだけ**。「自由な記述をシステムが認識する」というコンセプトを

  （どちらも `insertImageIntoCell`。`/api/upload-image` へ送って `<img>` を入れる。[要件定義書.md](要件定義書.md) §2.6）。

### 2.3 形式の外形（HTMLの実例）

**業務文書ブロック**（`section` がヘッダ `dl` と明細 `table` を包む。論点A・案1）。
下は**旧形**（file 容器で包む。2026-08-31 までの挿入形。既存本文は互換で動く）。

```html
<section data-type="file" data-src="PO-A100.pdf">
  <p>📎 <a href="/data/master/00/000012/PO-A100.pdf">顧客発注書.pdf</a></p>
  <section data-type="client-order">
    <dl>
      <dt>発注書番号</dt><dd>PO-A100</dd>
      <dt>発注元</dt><dd>トーア</dd>
      <dt>発注日</dt><dd>2026-06-18</dd>
    </dl>
    <table data-type="client-order-items">
      <tbody>
        <tr><th>品番</th><th>品名</th><th>単価</th><th>数量</th><th>状態</th></tr>
        <tr><td>SHAFT-01</td><td>シャフトA</td><td>8000</td><td>10</td><td>未着手</td></tr>
      </tbody>
    </table>
  </section>
</section>
```

- **ヘッダの `<dl>` に `data-type` は付けない**。`section` が形式を決め、`dt` の表示文字が鍵を運ぶ。
- **明細表は最初の `tr` が見出し行**（列の鍵と型を運ぶ＝文書自身がスキーマを携帯する）。
- ファイル名リンクは**可視の中身**で、正本に保存される（閲覧ゼロJSでもPDFを開ける）。
  PDFプレビュー・ドロップゾーン・AI解析ボタンはエンハンサ（`enhanceFileSections`）が `File` 宣言の
  形式ブロック自身（互換で `file` 容器にも）へ挿す `.vocab-chrome` で、**保存されない**。

**機能見出し形**（D-2・2026-08-31 以降の挿入形。エディタの `buildVocabSkeleton` がこの形で挿す）。
`data-type` を書かず、`section` の最初の見出しの言葉（レジストリの表示名）が形式を宣言する。
PDFは容器で包まず、可視のファイル名リンクを `section` の先頭に置く（href は `/<ページID>/<生成ID>.pdf`）。

```html
<section>
  <h2>顧客の発注書</h2>
  <p data-id="m2k3x1">📎 <a href="/000012/m2k3x1.pdf" download="顧客発注書.pdf">顧客発注書.pdf</a></p>
  <dl>
    <dt>発注書番号</dt><dd>PO-A100</dd>
    <dt>発注元</dt><dd>トーア</dd>
    <dt>発注日</dt><dd>2026-06-18</dd>
  </dl>
  <table>
    <tbody>
      <tr><th>品番</th><th>品名</th><th>単価</th><th>数量</th><th>状態</th></tr>
      <tr><td>SHAFT-01</td><td>シャフトA</td><td>8000</td><td>10</td><td>未着手</td></tr>
    </tbody>
  </table>
</section>
```

- 素の `dl` はヘッダ（形式自身の列）、素の `table` は明細（`Items` 宣言の形式 `client-order-items` の列）として
  索引に載る（`syncVocabSection`）。`inspection-record` のような単独の表も `<section><h2>検査記録</h2><table>…` で書ける。
- 見出し語がレジストリに無ければ静かにただのセクション（告知なし）。`data-type` があればそちらが勝つ。

**名前:値**（`dl`）と**繰り返し明細**（`table`）の単独形式。

```html
<dl data-type="tags"><dt>発注元</dt><dd>株式会社トーア</dd><dt>部品番号</dt><dd>SHAFT-01</dd></dl>

<table data-type="inspection-record">
  <tbody>
    <tr><th>品番</th><th>判定</th><th>検査写真</th><th>検査日</th></tr>
    <tr><td>SHAFT-01</td><td>合格</td><td></td><td>2026-08-17</td></tr>
  </tbody>
</table>
```

**計算ビュー**（表示専用）。本文に保存されるのは空のマーカーだけで、中身は
`view_render.go` がページを返すたびに `<div class="vocab-chrome">` として埋める
（仕組みは [アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.4）。

```html
<section data-type="child-list"></section>
<section data-type="required-materials"></section>
```

## 3. 形式 → テーブルの早見

**テーブルは1つだけです**。D-1（硬いドメイン表の全廃・2026-08-31）で、形式ごとの
専用テーブル8つと所有プラグイン4本を削除しました。

| テーブル | 由来する形式 | 担当 |
|---|---|---|
| `vocab_index` | **すべての** `table[data-type]` / `dl[data-type]` に加え、業務文書ブロック（`section[data-type]` または機能見出しの `section`）の**素の `<dl>`（ヘッダ）と素の `<table>`（明細）**（`data-type` を持たない。`section` の側から拾う） | [vocab_index.go](../internal/cms/vocab_index.go) |

索引での区別は `data_type` 列です——ヘッダは包む `section` の形式名（`client-order`）、
明細は表自身の `data-type`、素の表なら包む形式の `Items`（どちらも `client-order-items`）で載ります。
読む側の入口は [vocab_query.go](../internal/cms/vocab_query.go) の3つ（`vocabTableRowsOf`・`vocabBlocksOf`・`pagesByTag`）。③計算（部材手配計算）は
この索引だけを読みます（[【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md) §8）。

`file` / `child-list` / `required-materials` は索引にも載りません（順に、配線だけの容器・
表示専用×2）。

**コアテーブルは `pages` と `page_perms` だけ**で、業務データは `vocab_index` に載ります
（[internal/database/sqlite.go](../internal/database/sqlite.go)）。

受発注のPDFパスは形式自身ではなく**祖先のファイル容器** `section[data-type="file"]` の
`data-src` にあります。**索引はしません**（配線＝属性であって表示される値ではなく、
読む者もいなかったため。D-1・2026-08-31）——本文には残るので情報は失われません。

## 4. 可変タグ（`dl[data-type="tags"]`）の既知の名前

`tags` の鍵（`dt` の表示文字）は自由語で、すべて `vocab_index` に `(field, value)` として入る
（専用テーブル `page_tags` は 2026-08-30 に吸収・廃止）。
**同じ名前を同一ページに複数置いてよい**（担当者が2人、関連部品番号が複数といった多値属性。
**対の繰り返し**で表す——1つの `dt` に複数 `dd` は形式外だが、来れば鍵の繰り返しとして寛容に読む）。
単一値として読む用途は `cms.TagValue` が先頭を採る。
特別扱いされる名前のみ以下：

| 名前 | 用途 |
|---|---|

## 5. 語彙の増やし方

**既定の増やし方は「レジストリへ宣言を1件足す」**。カスタム要素は作らない（§6）。

1. [internal/cms/vocab.go](../internal/cms/vocab.go) の `vocabRegistry` へ `VocabDef` を1件足す
   （`Type` は kebab-case・一意、`Element` は `table` / `dl` / `section` のいずれか）。
2. 再起動すると `GET /api/tag-schema` の `vocab` に現れ、**スラッシュメニューに自動で並ぶ**
   （`Hidden: true` なら並ばない）。挿入骨格・列型の検証・②汎用索引への同期もそのまま通る。
3. 本ファイル §2 の表を更新する。
4. **Goのコードは1行も書かない**。集計API・型付きテーブル・取り込み変換のいずれかが要るときだけ
   ③計算プラグインを追加する（[【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md) 冒頭の振り分け）。

> **サニタイザは変更不要**。`data-type` は許可済みの属性名で、**値は検査されない**ので、
> 新しい形式名を足しても許可リストに触る必要はない（`table` / `dl` / `section` / `th` を担い手にする限り）。
> 新しい**要素**や**属性**が要る場合だけ `structuralElements` を直す
> （[本文サニタイズ設計.md](本文サニタイズ設計.md) §5・§7）。

> **手書きの写経は件数が増えれば破綻する**。正本がレジストリという1テーブルへ集約されたので当面は
> 本ファイルが鏡でよいが、`vocab` からの自動生成は引き続き課題
> （[要件定義書.md](要件定義書.md) §5「語彙一覧の生成化」。経緯は [変更履歴.md](変更履歴.md)）。
