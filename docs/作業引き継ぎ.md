## 直近のセッションでやったこと（2026-08-05・その2）

**添付アップロードの脆弱性を修正**した（[変更履歴.md](変更履歴.md) 2026-08-05 の節が詳細）。
`POST /api/upload-pdf` が任意の名前・種類を受け付けており、保存先にはページの本文と
**権限の正本であるサイドカーが同居している**ため、write 権限だけの利用者が

1. `<id>.meta.json` を上書きして**所有者の奪取・匿名公開・mode の書き換え**（権限昇格）
2. `evil.html` を置いて `/data/master/...` から**同一オリジンのHTMLとして配信**（保存型XSS。
   本文の二層サニタイズを完全に迂回し、中間版CSPの `'unsafe-inline'` では防げない）

を実行できた。入口（`.pdf` のみ・先頭 `%PDF-` 必須・32MiB上限・ファイル名の正規化）と
出口（`nosniff`／PDF以外はダウンロード扱い／本文とサイドカーは配信しない）の両方を塞ぎ、
[upload_test.go](../internal/cms/upload_test.go) で固定した（**修正前のコードでは落ちる**ことを確認済み）。

**この監査で見た範囲**: 認証（セッション・Cookie・ロックアウト）、CSRF（Origin検証）、CSP、
本文サニタイザ、認可（`RequirePageWrite`／`RequirePageReadOrPublic`／admin API）、パス組み立て
（`GetPageDir`・`DataFileHandler`）、SQLの組み立て（すべてプレースホルダ）。**上記以外に
成立する脆弱性は見つからなかった**。残る既知の弱点は「未着手」の節を参照。

## その前（2026-08-05・その1）

**カスタム要素の Shadow DOM 方針を統一**した（[コンセプト.md](コンセプト.md)「既知の課題」の最優先項目）。
着手して分かったのは、これが見た目の不統一ではなく**編集機能が壊れていた**話だったこと。

- `<m-child-list>` だけが Shadow DOM で描画しており、その残骸 `getRootNode().host` が Light DOM の
  テンプレートに残っていた。**Light DOM では `.host` が `undefined`** なので、`<m-tag>` の値編集・
  `<m-item>` の項目編集と削除ボタンは `TypeError` で**動いていなかった**（ハーネスで再現確認）。
- **基底クラス `MElement` を導入**して全要素が継承。描画先を Light DOM に統一し、ホストへの
  書き戻しは **`data-attr`／`data-remove` に一本化**（インライン `on*=` を除去）。
- **自己更新では再描画しない**ようにした（`updateAttr`）。従来は1文字打つごとに入力欄が作り直され、
  フォーカスが飛んで実質1文字しか入力できなかった。
- `applyMode` の再描画対象が固定の要素名リストで、業務要素（`m-client-order` 等）が漏れていたのも修正。
- 確定仕様は [エディタ仕様.md](エディタ仕様.md) §0.1、経緯は [変更履歴.md](変更履歴.md)（2026-08-05）。
- **検証**: `/assets/` が認証不要なことを利用し、一時ハーネスHTMLを置いて実ブラウザで
  修正前後を確認（修正前＝3種の `TypeError`、修正後＝値の書き戻し・打鍵中のフォーカス保持・
  親子で属性が混ざらないこと・削除・閲覧モードの描画・CSS移設をすべて確認）。ハーネスは削除済み。
  **Goのテストは全パス（フロントのみの変更で影響なし）。**

### 前半：許可タグ・属性の拡張

本文で扱えるHTMLの語彙を広げ、**エディタとサニタイザを1つの宣言から導く**構造にした。
経緯は [【考察】許可タグと属性.md](【考察】許可タグと属性.md)、決定の正本は
[本文サニタイズ設計.md](本文サニタイズ設計.md) §5、まとめは
[変更履歴.md](変更履歴.md)（2026-08-04 の節）。

- **語彙の一元化**: `GET /api/tag-schema` が構造HTMLとカスタム要素の**両方**を返すようにし
  （`elements` / `void` / `block_id`）、エディタは手書きの `TEXT_BLOCK_TAGS` を捨てて
  DOMを辿る汎用シリアライザ（`serializeBlock` / `serializeNode`）に置き換えた。
  以後は `structuralElements` を直すだけでエディタが追随する。
- **許可リストの拡張**: `h1`〜`h6`・`dl`/`dt`/`dd`・ルビ・`section` 等・`details`/`summary`・
  `ins`/`del`・表の一族・`video`/`audio` などを追加（方針「タグは寛容・属性は厳格」）。
- **URL規則を2種類に分離**: リンク（`href`・`cite`）は外部可、埋め込み（`src`・`srcset`・`poster`）は
  **相対のみ**。あわせて**プロトコル相対URL `//host/…` が素通りしていた穴を塞いだ**。
- **`document.execCommand` を廃止**: Range 操作で常に `<strong>`/`<em>`/`<u>` を出す
  `toggleInlineFormat` に置き換え、`tidyInline` で空要素・入れ子・隣接・入れ子順序を正規化。

**着手前に判明していた要点**: サニタイザが許可していても、エディタのシリアライザが知らない
要素は**保存時に黙って捨てられる**（`h4`・`ul`・`table` が「画面に出るのに消える」状態だった）。
許可リストを広げる前に語彙の一元化が必要、という順序がこのセッションの肝。

**検証方法のメモ**: エディタ側のロジックは、`assets/index.html` から関数を名前で抜き出して
ハーネスHTMLを生成し、実ブラウザで動かして確認した（本体をコピペしないので実装と乖離しない）。
サーバー側はGoのテストで、**エディタの出力が無変更でサニタイザを通ること**まで含めて固定した。

（このセッションでは `docs/` 配下の通信記録処理の設計検討には触れていない。その内容は
[【考察】通信記録処理.md](【考察】通信記録処理.md) が正本のまま、下記「残課題」に引き続き残っている。）

  [本文サニタイズ設計.md](本文サニタイズ設計.md) §5、経緯は [【考察】許可タグと属性.md](【考察】許可タグと属性.md)。

## 開発環境の再現（自宅などで再開する手順）

```bash
# 1. 最新を取得
git pull

# 2. 依存取得
go mod tidy

# 3. 初回のみ管理者を作成して起動（ローカルHTTP検証なので Secure Cookie 無効）
#    ローカル開発の管理者は user=a / password=a に統一する（環境間で揃えるため。2026-07-04 決定）。
WCMS_ADMIN_USER=a WCMS_ADMIN_PASSWORD='a' WCMS_SECURE_COOKIES=0 \
  go run cmd/w-cms/main.go
# 2回目以降は環境変数なしで go run cmd/w-cms/main.go
# → http://localhost:8080 （/login にリダイレクト。a / a でログイン）

# 4. テスト
go test ./...
```

注意:
- **ローカル開発のログイン**: `a` / `a`（**ローカル検証専用**。本番では使わないこと）。
  古い環境には `admin` / `Admin` で作られた `auth.db` が残っている場合がある（2026-07-04 に `a`/`a` へ変更）。
  入れないときは下の再設定手順で揃える。
- `data/`（`cms.db` と `master/`、`auth.db`）は `.gitignore` 対象でコミットされない。**環境ごとに独立**するため、
  別環境（自宅など）では初回起動時に上記の環境変数で管理者が新規作成される。`auth.db` は同期されないので、
  「家でログインできない」は data/ が無い＝初回の管理者未作成か、別の認証情報で作成済みのいずれか。
- **既存 `data/auth.db` の認証情報を忘れた／揃えたいとき**は、サーバーを止めてから以下で揃えられる:
  ```bash
  # 一時パッケージで internal/auth を呼ぶ（ルートに別の package main があるためサブdirで実行）
  # 既存ユーザーなら SetPassword、未作成なら CreateUser を使う。
  mkdir -p _resetpw && cat > _resetpw/main.go <<'GO'
  package main
  import ("fmt"; "w-cms/internal/auth"; "w-cms/internal/database")
  func main(){ database.InitAuthDB(); defer database.AuthDB.Close()
    if err := auth.SetPassword("a", "a"); err != nil {
      if err2 := auth.CreateUser("a", "a", true, ""); err2 != nil { fmt.Println(err, err2); return }
    }
    fmt.Println("ローカル管理者 a / a を用意しました") }
  GO
  go run ./_resetpw && rm -rf _resetpw
  ```
- ローカル実行・プレビュー用に `.claude/launch.json`（`go run` 起動設定）を用意済み。
  プレビュー（http://localhost）でCookieが付くよう **`env: { "WCMS_SECURE_COOKIES": "0" }`** を設定してある。

   `updateAttr`／`bindEditFields` の1箇所で足りる）と、**属性変更ごとの全体再描画**（自己更新は
   抑止済みなので、残るのは外から属性が変わる経路のみ）。
   道具で一掃するなら `lit` が第一候補（[エディタ仕様.md](エディタ仕様.md) §0 に判断軸）。
1. **`<aside>` サイドパネルの本レイアウト作り込み**: 現状はカードを縦に並べた素直な構成。表示の磨き込み
   （アイコン・余白・折りたたみ既定状態など）は後追いで可能。
1.5 **CSP を strict へ格上げ（前提リファクタ）**: 中間版CSPは付与済み。strict（`'unsafe-inline'` なし）に
   するには、フロントの全インライン（`index.html` の script2つ・`<style>`・`on*=`11個・`style=`12個、
   `web-components.js` の `innerHTML`＋動的 `style=`、`templates/*.html` 12ファイルの `on*=`/`style=`）を
   外部化・addEventListener化・CSSOM化する必要がある。FOUC head スクリプトは per-request nonce で残す方針。
   詳細チェックリストは正本 [【考察】CSP強化.md](【考察】CSP強化.md) §4。
1.6 **監査で見つけた「脆弱性ではないが直す価値のある」点**（2026-08-05 の監査。いずれも未着手）:
   - **JSONボディにサイズ上限が無い**: `/api/save`・`/api/save-block` などは `json.NewDecoder(r.Body)` を
     直接使っており、認証済み利用者が巨大なボディでメモリを圧迫できる。添付と同じく
     `http.MaxBytesReader` を通すのが素直（添付は 2026-08-05 に対応済み）。
   - **ページIDの正規化漏れ**: 保存APIは `page_id` を `strconv.Atoi` で権限判定しつつ、
     ファイルパスには**受け取った文字列のまま**使う（`GetPageDir`）。`"0012"` や `"+12"` でも
     権限判定は通り、`data/master/00/0012/` のような別ディレクトリができる。トラバーサルには
     ならない（`.` や `/` は `Atoi` を通らない）が、正本の名前が揺れる。ゼロ詰め6桁へ正規化すべき。
   - **`/assets/` にキャッシュ制御が無い**: ブラウザのヒューリスティックキャッシュが効くため、
     デプロイ後に古いフロント（`web-components.js`・テンプレート）が残りうる。検証時は
     ハードリロードが要る。長期的にはハッシュ付きURLか `Cache-Control` の指定を検討。
2. **既存データの移行**: 旧 `<m-page-info>` 方式で作られたHTML（属性がHTML内にある）が実環境に存在する場合、
   サイドカーへ移す一度きりの移行が要る。本リポジトリの `data/` はローカル限定のため通常は不要。
   ローカル検証で作った旧テストページ（`000001` 等）が気になる場合は管理コンソールの「DB再構築」で整理可能。
3. **CSS変数のさらなる移行**: トップレベルとサイドパネルはトークン化済み。スラッシュメニュー・ブロック操作・
   スイッチ等のウィジェット内部配色は据え置き。段階的に移行可能。
4. **`updated_at` の表記ゆれ**: サイドカー由来は RFC3339、フォールバックは SQLite の `CURRENT_TIMESTAMP`。
   表示は `formatDateTime` が吸収するが、必要なら保存時に正規化を検討。
5. **同時編集の競合対策（Phase 1+2＋エディタ内操作の直列化まで実装完了・運用中。一部の設計判断のみ未決）**:
   旧来の last-write-wins による lost update は悲観ロック＋SSEで解消済み。さらに権限変更・所有者変更・
   親付け替えも本文保存と同じロックで直列化済み（共通ゲート `RequireEditLock`／フロント `lockedFetch`）。
   経緯メモは [【考察】同時編集の競合対策.md](【考察】同時編集の競合対策.md) §9 決定ログに集約。
   **残る未決**（§8「今後の再検討候補」参照）: 複数待機者の順序（FIFO 等）、任意の安全TTL、ロック多重化時の
   共有ストア化、将来の CRDT 化。いずれも現状の単一プロセス・揮発的ロックで運用上の支障は出ていない。
