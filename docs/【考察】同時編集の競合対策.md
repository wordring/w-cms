## 0. 目的

複数人が同時に編集・操作した場合の w-cms の挙動を整理し、どこまで・どの順で対策するかを合意する。

## 1. 背景：現状の挙動（コード根拠つき）

w-cms の保存は **「最後の保存が勝つ（last-write-wins）」** で、同時編集に対する保護は実質ありません。

- エディタは変更を **1.5秒デバウンスで全文HTMLを自動保存**します（`assets/index.html` の `triggerAutoSave` → `saveToServer`）。
- 保存API（[`SaveAPIHandler`](../internal/cms/handler.go)）は受け取った**全文HTMLを上書き**するだけで、バージョン照合をしません。`updated_at` を持っているのに**保存時の競合検出に使っていません**（楽観ロック無し）。
- エディタは**ページ読み込み時にしか本文を取得しない**ため、他人の保存に気づけません（再読込するまで）。
- ページ属性はサイドカー `<id>.meta.json` が正本で、`BumpUpdatedAt` / `SetSidecarParent` / chmod / chown は **ReadSidecar→変更→WriteSidecar をロック無し**で行い、毎回**構造体全体を書き戻します**。
- DB接続（[`sqlite.go`](../internal/database/sqlite.go)）は `sql.Open` のみで **busy_timeout も WAL も未設定**。
- 新規ID採番 `GenerateNextID` は **`SELECT MAX(id)+1` で非原子的**（一方「＋子ページを作成」の `NewPageAPIHandler` は `INSERT` 自動採番で原子的）。

## 2. 競合シナリオと深刻度

| # | シナリオ | 深刻度 | 内容 |
|---|---|---|---|
| A | 同じページを2人が同時編集 | 🔴 高 | 後勝ちで相手の編集を黙って上書き（lost update）。全文置換のため部分マージもされない。 |
| E | save 経由の新規ID衝突 | 🟠 中 | 同時に「空IDで保存」すると `MAX(id)+1` が同一IDを採番しファイル衝突。子ページ作成ボタン経由は安全。 |
| C | サイドカー属性の競合 | 🟡 中 | 並行する別フィールド変更（例: 親変更とchmod）が read-modify-write で互いを失う。 |
| B | ファイル非原子書き込み | 🟡 中 | `os.WriteFile` は truncate→write で非原子。同時書き込みで torn write / 共有違反の恐れ。 |
| D | DBロック | 🟢 低 | 並行 `SyncIndex` で `database is locked` が出うる。DBはファイルから再生成可能なので回復可。 |

## 3. 対策の選択肢（軽 → 重）

1. **楽観ロック**: ロード時の `updated_at` を保持し、保存時に「期待 updated_at」を送る。サーバーは現在値と不一致なら **409 Conflict** を返し、フロントは「他の人が更新しました。再読込してください」を表示（ETag/`If-Match` 相当）。→ A を**検出**できる（防止ではなく検出＋再読込導線）。
2. **採番の原子化**: save の新規パスも `INSERT` 自動採番へ統一し、`GenerateNextID` の MAX+1 を廃止。→ E を解消。
3. **書き込みの原子化＋直列化**: HTML/サイドカー保存を **temp file + rename** に。サイドカーの read-modify-write を**プロセス内 mutex** で直列化。→ B・C を解消。
4. **DB堅牢化**: `busy_timeout`（例 5s）+ **WAL** を有効化、書き込み接続に `SetMaxOpenConns(1)` も検討。→ D を実質回避。
5. **編集ロック／プレゼンス（任意）**: ページ単位の「編集中」表示・悲観ロック。実装やや重め。
6. **リアルタイム共同編集（CRDT/OT + WebSocket）**: 大規模改修。「標準ライブラリ優先・外部依存最小」「ファイルが正本」という[開発方針](開発方針.md)と相性が悪く、現時点では過剰。

## 4. 推奨ロードマップ（暫定）

- **第一弾（費用対効果・高）**: 1. 楽観ロック ＋ 2. 採番の原子化。最悪の「黙って lost update」と「ID衝突」を塞ぐ。
- **第二弾（堅牢性）**: 3. 原子的書き込み・サイドカー直列化 ＋ 4. DB堅牢化（WAL/busy_timeout）。
- **第三弾（要件次第）**: 5 / 6 は、同時編集が常態化する場合のみ検討。

現規模（社内・少人数・ファイルが正本）なら、**第一弾＋第四弾**で実用上の同時編集耐性はかなり上がる、というのが暫定の見立て。

## 5. 編集ロック方式の詳細設計（検討）

方針：**悲観ロック（ページ単位）**。提案どおり「編集モード移行時にロック取得＋最新版ロード → 定期保存」。
有効期間は固定TTLではなく、**競合トリガー方式**を採る（下記）。

- **取得**: 編集モードへ移行したら `POST /api/lock?id=`。空き、または自分が保持中なら付与し、**ロックトークン＋最新HTML**を返す（古い版で上書きしないよう必ず再ロードしてから編集開始）。他者が保持中なら **423 Locked / 409** ＋保持者名（と猶予の残り時間）を返す。閲覧は可。
- **有効期間：競合トリガー方式【2026-06-21 ユーザー合意】**: ロックは**誰も要求しない限り無期限**（保持者は考え込んでも追い出されない。ロック維持のための定期ハートビートも不要）。**他者が編集を要求した時点から 2 分の猶予**を開始し、猶予満了で保持者はロックを明け渡す（独占防止）。
  - 猶予は**最初の要求**で deadline = now + 2分 に固定し、保持者の編集活動では延長しない（これが公平性の保証）。
  - 既存のオートセーブ（1.5秒）により猶予中も保存され続けるため、明け渡し時に失う差分はほぼ無い。
  - **要求者の離脱で猶予をキャンセル**: 要求者がいなくなったら猶予を取り消し、保持者はロックを保持し続ける（誰も待っていないのに追い出さない）。要求者は関心の継続をポーリング／SSE で知らせる。
  - 任意のハートビートは「保持者の死活検知」にのみ使い（要求発生時に保持者が既に切断済みなら 2 分を待たず即解放）、ロック延命には使わない。
- **保存の安全網**: `/api/save` は**ロックトークンを検証**し、現在の保持者でなければ 409/423 で拒否する（明け渡し後の古いクライアントが新しい保持者の編集を上書きしないため）。＝楽観ロック（3章の1）の役割を**ロックトークンが兼ねる**ので、両方は不要。
- **解放**: 閲覧モードへ戻る／タブを閉じる時に `POST /api/unlock`（タブ離脱は `navigator.sendBeacon` でベストエフォート送信）。明け渡しは「猶予満了」または「明示解放」で起きる。
- **ロックの保存場所**: ロックは**ephemeral（揮発的）なランタイム状態**であり、サイドカー（正本）にもHTMLにも入れない。**プロセス内の mutex 付き map**（例 `map[pageID]{user, token, waiter, graceDeadline}`。`graceDeadline` は競合発生時のみ設定）が最小・無依存で、「DBは使い捨てキャッシュ（ファイルから再生成可能）」という不変条件（8章）とも整合する（再起動で全ロックが消えるのは許容＝ロックは元々揮発的）。
  - **注意（前提）**: これは**単一プロセス前提**。将来、複数プロセス/インスタンスで負荷分散する場合は共有ストア（DB/Redis 等）が必要になる。現状の w-cms は単一バイナリなので問題なし。
- **管理者の強制解除**: 保持者が落ちている等でスタックした場合に備え、admin がロックを破棄できる導線。
- **編集モードトグルの常時表示【2026-06-21 ユーザー要件】**: ロックは編集モードに紐づき、ユーザーは編集モードの ON/OFF を頻繁に行う（＝ロックの取得・解放を意識的に切り替える主要操作になる）。そのため**編集モード切替トグルを画面内に常時表示**する（長いページでもスクロールで隠れないよう、ヘッダーを sticky にするか、フローティングのトグルを置く）。現状はトグルが `<header class="header">` 内にあり、スクロールで画面外へ出てしまう。
- **UX**:
  - 取得失敗時：「○○さんが編集中です。あと約N分で取得できます。閲覧のみ可能です」＋**「再試行」ボタン**（残り時間も表示）。あわせて**時間制限つきの待機ポーリング**（8秒間隔・上限約2.5分）を開始し、空き次第で**自動的に編集へ入る**（最新版を再ロード）。上限を超えたら停止して「再試行」ボタンを残す（**無期限ポーリングはしない**＝放置時に背景タブが延々と保持者を脅かさない）。
  - 保持者：通常は残り時間表示なし（無期限）。誰かが要求したら「○○さんが編集を待っています。あと N分で編集権が移ります」を表示し、保存を促す（7章のトースト/プッシュ）。
  - 保存がロック喪失で拒否されたら：「編集権が他の人に移りました。変更を退避して再読込してください」＋現HTMLのクリップボード退避。

**メリット**: 設計が単純で「lost update を構造的に防ぐ」。同一ページ同時編集が稀な w-cms の用途に合う。
**限界**: 真の同時共同編集はできない（直列化）。粒度はページ全体（章ごとの並行編集は不可）。

## 6. リアルタイム通知（WebSocket / SSE）の考察

- **ロックだけなら WS/SSE は不要**: 空き確認は数秒間隔の **HTTP ポーリング**、ロック更新は **HTTP ハートビート**で足りる（最小・無依存）。まずはこれで成立する。
- **WS/SSE が効く場面**:
  1. プレゼンス/通知の即時化（「○○が編集を開始」「ロックが空いた」を push）。ポーリングより滑らか。
  2. **切断の即時検知**: 接続が切れたらサーバーが離脱を即座に把握し、**TTLを待たずロック解放**できる（HTTPハートビート＋sendBeacon より確実）。
  3. 真のリアルタイム共同編集（CRDT/OT）。← これは別物で重い（3章の6）。
- **依存方針との整合**:
  - Go の標準ライブラリに **WebSocket サーバーは無い**。`golang.org/x/net/websocket`（凍結・非推奨）か外部（gorilla / nhooyr 等）が必要。
  - **【方針・2026-06-21 ユーザー合意】WebSocket が必要になった場合は外部ライブラリの追加を許容する**（[開発方針](開発方針.md) §1 の「外部依存最小」に対する条件付きの例外。実際に WS 採用を確定する時点で、採用ライブラリを開発方針の承認済みリストへ明記する）。
  - 代替の **SSE（Server-Sent Events）は純 `net/http` だけで実装可能**（`text/event-stream` のストリーミング応答）。サーバー→クライアントの一方向で、「ロック状態変化」通知やプレゼンスには十分。クライアント→サーバーは通常のHTTP（ハートビート/解放）でよい。
  - → **判断軸**: 通知が一方向（プレゼンス／空き通知）で足りるなら、無依存で済む **SSE が第一候補**。双方向の密な通信や、確実な切断検知・将来の共同編集まで見据えるなら **WebSocket を採用**（外部ライブラリ可）。
- **推奨段階**:
  - **Phase 1**: 悲観ロック＋TTL を**純HTTP**（取得/更新/解放＋保存時のトークン検証）＋空き確認ポーリングで実装。新規依存なし。
  - **Phase 2（任意）**: 即時プレゼンス／確実な切断検知が必要になったら、**SSE（無依存）または WebSocket（外部ライブラリ可）** を追加。一方向通知で足りるか、双方向が要るかで選ぶ。
  - **CRDT/OT（真の同時共同編集）**: さらに将来。導入する場合は WebSocket 前提。

## 7. アプリ内通知（トースト/スナックバー）と通知エリア

ロック関連のフィードバックを、専用の**アプリ内通知エリア**（トースト／スナックバーのホスト）に集約する。「何が起きたか（イベント）」と「どう見せるか（描画）」を分離し、将来の通知（保存エラー・競合・システム連絡）も同じ場所に出せるようにする。

- **通知エリアの設計**: 画面固定のトーストコンテナを1つ置き、任意のコードから `notify(message, {type, duration, action})` で出せる小さなAPIにする。種類（info / warn / error / success）と任意のアクションボタン（例:「保存して解放」「再読込」）を持てる。まずは一過性のトーストで開始し、必要になれば永続の「通知センター（ベル／受信箱）」へ拡張可能。
- **ロック取得失敗の通知（編集しようとした人へ・同期）**: B が編集モードにしようとして A が保持中なら、`POST /api/lock` の **423 応答をそのままトースト表示**：「○○さんが編集中です（残り N分）。閲覧のみ可能です」。サーバープッシュ不要（自分の操作への即時応答）＝**Phase 1 で実装可能**。
- **「誰かが編集を待っている」通知（保持者へ・プッシュ）**: A が保持中に B が編集を試みたことを **A の画面へ push** してトースト表示：「○○さんが編集を待っています」。A は自分で操作していないので、**サーバー→クライアントのプッシュが必要＝Phase 2**。
  - これは push チャネルの**具体的で強い用途**。かつ一方向（サーバー→A）で足りるので **SSE で実現可能**（WebSocket 必須ではない）。＝6章の「通知が一方向なら SSE」を裏づける。
  - 任意で、保持者のトーストに「保存して解放」アクションを付け、待っている人へ素早く譲れるようにする（独占防止のソフトな後押し）。
- **その他の通知候補（同じエリアに集約）**: 保存エラー（現状は `#save-status` のテキスト）、ロック喪失による保存拒否（「変更を退避して再読込」）、他者がページを更新した旨（「このページは更新されました。再読込してください」＝push）。

→ **評価**: 通知エリアの新設は良い基盤。**ロック失敗トーストは Phase 1、保持者への「編集待機中」通知は Phase 2（SSE で可）**に置くのが自然。push チャネルの用途が「一方向通知」に寄るため、SSE で足りる見込みが強まる（WS は将来の共同編集まで踏み込む場合）。

- ~~Phase 2 の通知方式（SSE か WebSocket か）~~ → **決定**: **SSE を採用**（一方向通知で足り、純 `net/http` で無依存）。WebSocket は将来の共同編集まで踏み込む場合の選択肢として留保。
- ~~ロックの保存~~ → **決定**: プロセス内 mutex 付き map（単一プロセス前提・揮発的）で確定。
- ~~編集モードトグルの常時表示の方式~~ → **決定**: ヘッダーを sticky 化。
- ~~管理者の強制解除~~ → **実装済み**: `POST /api/lock/force`（admin 限定・`auth.Audit` に `lock.force` 記録）。

**今後の設計変更で再検討しうる項目（本メモを生かす理由）**
- **複数の待機者の順序**: 現状は「解放後の早い者勝ち」。公平性が問題になれば **FIFO（先着の要求者優先）** をサーバー側キューで導入する余地。
- **安全TTL（任意）**: 無競合のまま保持者が死んだロックは現状 `holderConnectGrace` と SSE 切断検知で解放されるが、想定外のスタック対策に長め TTL（例 15〜30分）を別途設けるかは未決。
- **多重化（複数プロセス/インスタンス）対応**: 現状の mutex map は単一プロセス前提。負荷分散する場合は共有ストア（DB/Redis 等）が必要になる。スケール要件が出たら再設計。
- **真のリアルタイム共同編集（CRDT/OT + WebSocket）**: ページ全体の悲観ロックでは章ごとの並行編集ができない。同時編集が常態化したら検討（重い改修・WebSocket 前提）。
- **残る軽微な競合（B 非原子書き込み・C サイドカー read-modify-write）**: 悲観ロックでは直接解消しないため、3章の 3 を**別途いつ入れるか**（D DBロック・E 採番は Phase 1 で対処済み）。
- **デバウンス間隔**（現1.5秒）の見直し。ロックで衝突は防げるので、保存頻度はUX観点で別途調整可。
- **通知の発展**: 一過性トーストのみか、永続の通知センター（受信箱／ベル）も設けるか。`#save-status` を通知エリアへ統合するか。
- 想定する**同時実行規模**（最大同時編集者数・同一ページ同時編集の頻度）。上記の優先度を左右する。

- 2026-06-21: **ロックの有効期間を「競合トリガー方式（猶予2分）」に決定**（ユーザー合意・5章）。無競合なら無期限（ハートビートでの延命不要・保持者を追い出さない）、他者が編集を要求した時点から **2分**の固定猶予で明け渡す。固定TTL＋常時ハートビート案は撤回。残課題：要求者の離脱検知・複数待機者の順序・任意の安全TTL（8章）。
- 2026-06-21: **Phase 1 のロック挙動を最終確定**（ユーザー合意）。8章の主要な未決を以下で決着し、これで Phase 1（純HTTP）の仕様が固まった。
  - **待機者管理はクライアント側・サーバーはキューを持たない**: 非保持者の `POST /api/lock` には **423＋保持者名＋残り時間**を返すだけ。待機者は**自動ポーリングせず**、busyトーストの**「再試行」ボタン**で明示的に取得を試みる（押した時だけ presence が立つ）。複数待機者の順序は**解放後の早い者勝ち**（次に再試行した待機者が取得）。
  - **要求者の離脱検知＝再試行の途絶**: サーバーは最後の要求（＝再試行クリック）時刻だけ覚え、**約30秒**新たな再試行が無ければ要求者は去ったとみなし**猶予をキャンセル**。専用の離脱APIは不要。手動再試行にしたことで「背景タブが押し続けて保持者を追い出す」誤作動が起きない。
  - **保持者への「編集待機中」通知も Phase 1 で純HTTP**: 保持者も同じ状態取得を **10秒ポーリング**（`GET /api/lock-status?id=` を保持者・待機者で共用）し、「待機者あり＋残り時間」をトースト表示。SSE による即時プッシュは Phase 2 の任意拡張。
  - **保持者の死活検知はポーリングに流用**: 保持者の10秒ポーリングを死活信号とし、**待機者がいて保持者が約30秒ポーリングを止めていたら、2分を待たず即解放**。死活専用ハートビートは入れない。
  - **安全TTLは設けない**: 無競合で席を立った保持者は **admin の強制解除**で対応（競合時は2分で明け渡るため固定TTL不要）。必要なら将来「長時間ポーリング途絶で自動解放」を追加可能。
  - **ロックの保存はプロセス内 mutex 付き map で確定**（単一プロセス前提・揮発的）。当面の多重化予定なし。
  - **編集モードトグルは常時表示＝ヘッダーを sticky にする**（独立フローティング案は不採用）。ロックの残り時間表示もヘッダーに併設。
  - **採番の原子化を第一弾に同梱**: `/api/save` の空ID経路も `INSERT` 自動採番へ統一し `GenerateNextID` の `MAX(id)+1` を廃止（シナリオE解消）。
  - 第一弾に同梱するか別途かは任意だが、**DB堅牢化（WAL＋busy_timeout）は安価なので同梱を推奨**（シナリオD緩和）。原子的ファイル書き込み・サイドカーの read-modify-write 直列化（B・C）は本ロックとは独立の堅牢化として別途。
- 2026-06-21: **Phase 1 を実装完了**（純HTTP・新規依存なし）。確定仕様は [エディタ仕様.md](エディタ仕様.md) 10章・[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.3 へ反映。
  - 堅牢化（独立）: DSNの `_pragma` で WAL＋busy_timeout＋foreign_keys を全接続に適用（シナリオD）。採番を `reserveNewPageID` の `INSERT` 自動採番へ統一し `GenerateNextID`(MAX+1) を廃止（シナリオE）。
  - ロック: `internal/cms/lock.go`（プロセス内 mutex map・競合トリガー方式・遅延評価）と `lock_handler.go`（`/api/lock`・`/api/lock-status`・`/api/unlock`・`/api/lock/force`）。`SaveAPIHandler` がトークン検証（他者保持/失効は409、ロック無しは許可）。

- 2026-06-21: **busy 時の自動ポーリングを廃止し「再試行」ボタンへ変更**（ユーザー提案・推奨案A）。背景タブの待機ポーリングが `waiterLastSeen` を更新し続け、保持者を不当に2分で追い出す問題（レビュー指摘1）を解消。サーバーの `reap()` は変更不要で、フロントの `startWaiterPolling` を「再試行」アクション付きトーストへ置換（`acquireLock` の423経路）。
- 2026-06-21: **「再試行」だけでは編集権の移動が両エディタに反映されない不具合を修正**。原因＝純手動だと待機者の presence が約30秒で切れ猶予がキャンセルされるため、2分の自動移譲自体が発火せず、空いても待機者は自動入室しなかった（保持者側も本文を再読込しなかった）。対応：(1) 再試行クリック後に**時間制限つき待機ポーリング**（8秒間隔・上限約2.5分）を回し、空き次第で**自動入室**（最新版再ロード）→上限超過で停止し「再試行」ボタンを残す（無期限ではない）。(2) 保持者は `lost` 検知時に **`reloadContent` で最新本文を自動再読込**して他者の編集を反映。(3) クリップボード退避の成否で文言を出し分け。プレビューで「A保持→B待機→A解放→Bが自動入室」「保持者の強制明け渡し→閲覧復帰＋本文再読込」を確認（コンソールエラー無し）。
