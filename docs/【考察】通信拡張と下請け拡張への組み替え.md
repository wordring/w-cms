## 1. なぜこの形か

### 1.1 アドレス帳を通信の範疇に入れても、09-11 の判定と矛盾しない

09-11 に「アドレス帳は**メール**の持ち物ではない」と判定した4つの根拠
（[【考察】アドレス帳の作り直し.md](【考察】アドレス帳の作り直し.md) §5b）は、**相手がメールだったから**
成り立っていた。範疇が「通信」に広がると半分が裏返る:

- 根拠4「FAXだけ・電話だけの客先にはメールアドレスが無い」→ 通信なら全部含む。むしろ入れる理由になる
- 根拠1「メール拡張は使っていない」→ FAX番号も電話番号も**相手を言い当てる手掛かり**で、3つの通信路が
  すべてアドレス帳を引く

> ⚠ **下の段落の理由は 2026-09-15 のうちに取り下げた**（§4.3）。「下請けは入れたが通信箱は無い」
> ビルドは**最初から存在しない**（作れるのは全部入り／`nomail`／`minimal` の3つで、通信箱はコアに
> あった）ので、守ろうとした組み合わせが無かった。アドレス帳は別パッケージのまま置くが、
> 理由は整理のためで、ビルドタグのためではない。

**残るのは根拠3（ビルドタグ）だけ**で、これは**別パッケージにすれば解ける**。タグは
`cmd/w-cms/ext_*.go` の import 行に付くので、`subcon` が直接 import した `ext/comm/contacts` だけが入り、
通信箱（`ext/comm` 本体）は連れてこられない。**同じパッケージに入れると `init()` の連鎖で通信箱ごと
入り、「通信を外す」が効かなくなる**——ここが唯一の注意点。

### 1.2 板金拡張は、中身がもう下請け業務だった

`ext/sheetmetal`（5,177行）のうち板金に寄った語が出るのは**コード中2行**（DXF表題欄の項目名の並びと、
部材表の列見出し `材質`）。登録している14形式も図面を受け取って部品を作る下請けに共通。
**唯一の業種の前提は整理の木** `取引先／社名／段／装置名称／図面名称`（部品は顧客の装置に属する）で、
機械部品の下請け（板金・切削・溶接・塗装）には当てはまる。範囲は「**製造の下請け**」。

### 1.3 FAXサーバーと同居すると、機械の口の認証が軽くなる

作業引き継ぎで「FAXサーバーと共通の未解決」としていた**機械の口の認証**が、ネットワーク越しの認証では
なく「**同じ機械の中からしか届かない口**」（ループバック限定の口か、決まったフォルダへの投函）で足りる。
設計は `ext/comm/fax` に着手するときに詰める。**人の手ドロップと機械の投函を同じ口で受けない**
（09-05 の決定・PDFを `チャネル：FAX` と決めつけた事故）はそのまま守る。

## 4. 3の前に決めること

### 4.1 拡張の画面をどう持つか

§3.5 のとおり、画面は外れていない。案は2つ:

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| A. **載っている拡張をサーバーが知らせる** | `/api/tag-schema` か `/api/me` に `extensions: ["comm","mail",…]` を足し、`app.js` の各入口が見て出し分ける | 小さい。ファイルは1つのまま | コアの JS が拡張の画面を持ち続ける（語彙がコアに残る） |
| B. **拡張が自分の JS を配る** | `ext/*/assets/*.js` を `embed` し、載っている拡張だけ `<script>` を出す（CSP strict は self なので通る） | 外せば画面ごと消える。コアの JS から業務語が消える | `app.js` の内部関数（`tagValue`・`placeFloating`・`notify` 等）を公開する口が要る |

**推しは A から B へ**——3では A で出し分けだけ直し、B は通信・下請けそれぞれの画面を触る機会に1つずつ。

### 4.2 拡張の設定をどこに置くか

`machine_stages`（subcon だけが使う）・`vocabulary` の通信の語・`webdav_readonly` の `通信箱` がコアの
設定ファイル1本に同居している。`DisallowUnknownFields` があるので、**型をコアから外すだけで起動が止まる**。
拡張が自分の設定の節を登録する口（例 `cms.RegisterSettingsSection("subcon", &cfg)`）が要る。
**語彙（`vocabulary`）は分けない**のが自然——型は名前で決まり、辞書は1つのほうが衝突に気づける。

### 4.3 決定（ユーザー 2026-09-15）

| 論点 | 決定 |
|---|---|
| 拡張の画面（§4.1） | **A→B と段階で**。3段目では A（サーバーが載っている拡張を知らせ、`app.js` が出し分ける）。B（拡張が自分の JS を配る）は画面を触る機会に1つずつ |
| 拡張の設定（§4.2） | **拡張が自分の節を登録する**。`config/settings.json` は1本のまま、語彙（`vocabulary`）は分けない |
| 通信記録の語の参照（3d） | **アドレス帳と下請けは `ext/comm` を import する**（相手のタグ名 `差出人`・`宛先`・`CC`・`返信先` などを定数で通す）。依存は import で表す。`ext/comm` 本体はメールと違いタグを持たず `!minimal`——`nomail` でも通信箱（手で作る記録・電話）は残る。§1.1 の「別パッケージにすれば通信箱を連れてこない」は取り下げ（その組み合わせは作れなかった） |

### 4.4 画面の出し分けが要るのは「JSが自分で作るクローム」だけ（2026-09-16・実測）

3d-4 の着手時、段取り表は**4つ**（スレッド・未処理一覧・記録する・電話）を出し分ける予定でした。
測ったところ、**実際に要ったのは2つだけ**です。

| 画面 | 出し分け | なぜ |
|---|---|---|
| 通信記録のクローム（`refreshMailChrome`） | **要る**（箱ごと） | 中の「🧵 やりとりの前後」「📨 この記録への返信」が `/api/thread`・`/api/replies` を叩く。通信が無いと**通信記録ページを開くたびに404が2本**（どちらも失敗を黙って飲むので、画面には何も出ないまま要求だけ飛ぶ） |
| 電話の「記録を作る」 | **要る**（チェックだけ） | `/api/intake/memo` を叩く。**既定でオン**なので、掛けるたびに「発信の記録を作れませんでした」の通知が出る。⚠ `tel:` のリンクは残す——**掛けることは通信拡張の持ち物ではない** |
| 未処理一覧（`wireUnhandledActions`・`markHandled`） | **要らない** | 押す相手（`.unhandled-mark`・まとめて片付け）は**サーバーが描いたもの**。通信が無ければ `unhandled-intake` は語彙レジストリに載らず、**鏡の引き金が立たない**——本文に `<section data-type="unhandled-intake">` が書いてあっても空のまま出るので、配線は何も見つけずに帰る |
| 「＋ 記録する」（`wireNewRecord`） | **要らない** | 同じビューが描いているため（上と同じ理由） |
| 機械向けタグを畳む（`foldMachineTags`） | **要らない** | 本文のDOMを畳むだけで、口を叩かない |

**一般則**: 出し分けが要るのは **JS が自分で作るクローム**だけです。サーバーが描いたものは、
拡張が無ければそもそも描かれません。**「拡張の画面」を数えるのではなく、「口を叩くところ」を
数えること**——前者で数えると、要らない分岐を4つ足して、次の人がそれを維持することになります。
理由は `wireUnhandledActions` の直前にコメントとして書き残しました。

番人は `e2e/probe-extension-gating.js`（期待値を `/api/tag-schema` から導くので、
**3つのビルドどれに当てても通る**）。出し分けを外すと `-tags minimal` で404が2本出ることを
確認済みです。
