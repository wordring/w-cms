# Notion風ブロックエディタ UI/UX 実装仕様

w-cms のフロントエンドエディタは、モダンでインタラクティブなNotionライクなブロックエディタとして実装されています。このドキュメントでは、そのUIとイベント制御の仕組みについて解説します。

**ファイルの分担（2026-08-06 以降）**: `assets/index.html` は**殻の markup だけ**（198行）で、
操作ロジックは [assets/app.js](../assets/app.js)、スタイルは [assets/app.css](../assets/app.css) にあります。
以下で「エディタ」と書いたときの実装は `app.js` を指します（インラインを外部化した経緯は
[【考察】CSP強化.md](【考察】CSP強化.md) §4）。

## 0. なぜフレームワークを使わないのか（バニラJS）

エディタは**バニラJS**で書かれています。React/Vue のような汎用UIフレームワークは
このエディタには**不向き**、というのが結論です（2026-06-28 の設計検討）。理由は3つで、いずれも
この設計に固有かつ強いものです。

1. **保存形式＝DOM（決定打）**。編集中のDOMがそのまま保存HTML（＝正本）になり、Goの `x/net/html` が
   同じタグを読みます（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §1）。仮想DOMを挟むと
   「コンポーネント木 → 保存用クリーンHTML」への変換層が要り、**HTMLをDBとする設計の最大の利点を失います**。
2. **ビルド工程ゼロ**。`/assets/` のファイルをそのまま配信します。多くの
   フレームワークは npm＋バンドラを連れてきて、[開発方針.md](開発方針.md) §1 の「単一バイナリ・外部依存最小・
   ポータビリティ」と衝突します。
3. **`contenteditable` × 仮想DOM は難所**。ブラウザとユーザーがフレームワークの外でDOMを変えるため
   相性が悪く、本格的なエディタが専用ライブラリ（ProseMirror/Lexical）を使うのはこのためです。

**Web Components（カスタム要素）は廃止を決定した（2026-08-17・[【考察】語彙モデル.md](【考察】語彙モデル.md) §9）。**
上の3本柱はカスタム要素固有の性質ではなく、語彙は標準HTML＋`data-*` マーカーへ完全統一する。
動的な振る舞いは**編集モードのクローム**と**閲覧ビューのエンハンサ**（マーカー要素に配線する
バニラJS）が担い、DOM生成は殻の `<template>`＋`cloneNode`＋`textContent` 代入で行う
（文字列置換＋`innerHTML` のテンプレート機構は持ち込まない）。これに伴い:

- **新しいカスタム要素は作らない**（即時発効）。
- **`lit` の再評価は打ち切り**（対象のカスタム要素が消滅するため。かつての評価——Light DOM
  統一との衝突・CDN不可——は [変更履歴.md](変更履歴.md) に残る）。
- **ProseMirror / Lexical** だけは将来の再検討対象に残る: 堅牢な選択範囲管理・共同編集が
  必須要件になったとき（いまのアンドゥは自前スナップショットで釣り合っている。
  [【考察】アンドゥ・リドゥ.md](【考察】アンドゥ・リドゥ.md)）。React/Vue は引き続き非推奨。

### 0.1. カスタム要素の作法（Light DOM・`data-attr`・基底クラス `MElement`）

> **本節は移行完了までの現行実装の作法**（廃止決定済み・上記 §0）。現行のカスタム要素
> 10種に手を入れる場合はこの作法に従う。新規カスタム要素は作らない。

`assets/web-components.js` のカスタム要素は、次の3点を**全要素で統一**する（2026-08-05 確定）。
共通部分は基底クラス **`MElement`** が持ち、各要素は `render()` と `observedAttributes` だけを書く。

1.  **描画先は Light DOM（`this.innerHTML`）。Shadow DOM は使わない。**
    *   **保存はDOM走査で行う**（§8 の `serializeCustomElement`）。Shadow に隠すと入れ子の
        `<m-item>` が走査から外れ、保存される本文とサーバーの語彙がずれる。
    *   **配色は `assets/components.css`（外部スタイルシート）に置ける**。Shadow だと要素ごとに
        `<style>` を複製することになり、CSPのstrict化（[【考察】CSP強化.md](【考察】CSP強化.md)）とも噛み合わない。
    *   **`contenteditable` と同じツリーに乗る**ので、選択・キャレットの扱いが素直。
    *   コンポーネントが描いた `<div>` や `<ul>` が本文に混ざる心配は要らない。シリアライザが
        書き出すのは**カスタム要素の属性と、入れ子のカスタム要素**だけである。
2.  **ホストへの書き戻しは `data-attr` に一本化する。テンプレートにインライン `on*=` を書かない。**
    *   `data-attr="item-name"` … その入力欄の値を要素の属性へ書き戻す（`select` は `change`、他は `input`）。
    *   `data-remove` … 押すとその要素自身を本文から取り除く。
    *   配線は `render()` の最後に `this.bindEditFields()` を呼ぶだけ。対象は**自分が描いたUIに限られる**
        （入れ子の `<m-item>` も同じ `data-attr` を使うため、直近のカスタム要素の祖先が自分かで線を引く）。
3.  **自分のUI操作による属性変更では再描画しない**（`MElement.updateAttr`）。
    素の `setAttribute` だと `attributeChangedCallback` → `render()` で入力欄が作り直され、
    **1文字打つたびにフォーカスが飛ぶ**。外から属性が変わったとき（読み込み・PDF解析の反映など）は
    従来どおり描き直す。

> **経緯**: かつて `<m-child-list>` だけが Shadow DOM で描画しており、その名残の Shadow 前提API
> `getRootNode().host` が Light DOM のテンプレートに残っていた。Light DOM では `getRootNode()` は
> `document` を返し `.host` は `undefined` なので、`<m-tag>` の値編集・`<m-item>` の項目編集と
> 削除は `TypeError` で動いていなかった。ホストの取得方法も `getRootNode().host` / `closest()` /
> 直接 `setAttribute` の3通りに割れていたため、上記の1本の作法へ統一した。

## 1. ブロックラッパーのDOM構造

エディタ内のすべての要素（見出し、段落、発注書コンポーネントなど）は、プレーンなHTMLのままではなく、JavaScriptによって動的に `.editor-block` というラッパー要素で包まれます。

```html
<!-- DOM上の実際の構造 -->
<div class="editor-block" draggable="true">
    <!-- ホバー時に表示されるコントロール（＋ と ドラッグハンドル） -->
    <div class="block-controls">
        <button class="add-btn">＋</button>
        <div class="drag-handle">⠿</div>
    </div>
    <!-- 実際のコンテンツ -->
    <div class="block-content" contenteditable="true">
        <p>ここにテキストを入力します...</p>
    </div>
</div>
```

*   **自動ラップ (`wrapInBlock` 関数)**: エディタの初期化時や、新しい要素が挿入された際に、対象の要素を `.block-content` の中に入れ、左側に `.block-controls` を付与します。
*   **シリアライズ (`updateHtmlPreview` 関数)**: データベースに保存（送信）する際は、ラッパー要素を除去し、中身の `<p>` や `<m-file>` だけを抽出してクリーンなHTMLに戻します。

## 2. ドラッグ＆ドロップ (Drag & Drop)

*   `draggable="true"` 属性は `.editor-block` 自体に付与されますが、実際にドラッグを開始できるのは `.drag-handle` (`⠿`) を掴んだ時だけになるようにイベントを制御しています。
*   ドラッグ中は `.dragging` クラスが付与され、ドロップ先の要素には `.drag-over` クラスが付与されて青い境界線（視覚的フィードバック）が表示されます。
*   ドロップされた際、`insertBefore` または `insertAfter` のロジックを用いてブロックのDOMノードを並び替えます。

## 3. スラッシュコマンド (`/`) メニュー

テキストブロックで `/` を入力した際、または `＋` ボタンを押した際に、フローティングの「ブロック種別選択メニュー（`.slash-menu`）」が表示されます。

*   **表示トリガー**: `keyup` イベントを監視し、中身が `/` 1文字だけになったブロックを検知すると `showSlashMenu(targetBlock)` を呼び出します。
*   **キーボードナビゲーション**: メニュー表示中は、`ArrowUp`, `ArrowDown` で選択項目のハイライト（`.selected` クラス）を移動し、`Enter` で確定します。
*   **確定時の処理 (`replaceBlockWithComponent`)**: 選択したブロック種別（`m-file-client` など）の要素を新しく生成し、`/` が入力されていたトリガー元のブロックをその新しい要素で置換（Replace）します。

### 3.2 汎用表エディタ v1（2026-08-17 実装）

`data-type` 付きの表・定義リストの編集は、**型の数に対して不変の汎用実装**
（[【考察】語彙モデル.md](【考察】語彙モデル.md) §5.2）。型ごとの JavaScript は書かない。

*   **セル編集**: ブロックの contenteditable がそのまま担う（値＝中身＝表示される文字）。
    専用の入力欄や属性への書き戻しは無い。
*   **行操作**: キャレットが本文中の表の行にあるとき、**行操作ツールバー**
    （`#table-toolbar`: 行を下に追加・上下移動・削除）が行の横に表示される。
    クロームは本文DOMの**外**（シェル直下）に置く——ボタンを表の中へ挿すと
    シリアライザが中身を本文として拾ってしまうため。**見出し行**（最初の `tr`＝
    列の鍵と型を運ぶ）は削除・移動の対象外。カスタム要素が描画する表では出さない。
*   **機械属性のハイライト**: `th[data-field]`・`th[data-type]`・`dd[data-field]` は
    編集モードで背景をハイライトし、見えている文字が鍵・型として使われていないことを
    示す（CSS属性セレクタ。閲覧・公開ページには出さない）。
*   **未実装（段階的に足す）**: 列型に応じた入力補助（`number`/`date`/`enum`
    ドロップダウン/`image`）、列設定UI（ポップオーバ＝属性の編集口）、
    列操作（追加・削除・並べ替え）、dl の項目追加・削除、型不一致の通知。

## 4. コンテキストツールバー (Contextual Toolbar)

対象のブロックを選択・フォーカスした際に、そのブロック専用のツールバーがブロック上部に表示されます。

*   **表示トリガー**: `selectionchange` イベントおよび `click` イベントを監視し、現在カーソルがあるノード（`activeBlock`）を特定します。
*   **動的生成**: 対象のブロックが `<m-client-order>`（容器 `<m-file>` の中でも可）の場合は、ツールバーの中に「＋ 部品を追加」ボタンを動的に生成します。
*   **コンポーネント内への挿入**: ボタンがクリックされると、該当の業務要素の中（`.m-block-items`）に `<m-item>` コンポーネントを DOM として `appendChild` し、シリアライズ処理（`updateHtmlPreview`）をトリガーします。
*   **装飾ボタン（B / I / U）**: ブロックが構造HTML（カスタム要素でない）なら太字・斜体・下線のボタンを出します。見出しと段落だけでなく、リストや引用の中の文字にも効きます。実装は下の 4.1。

### 4.1. インライン装飾（太字・斜体・下線）

`document.execCommand` は使いません（`toggleInlineFormat`）。

*   **なぜ独自実装か**: `execCommand` は仕様上 deprecated で、**生成されるHTMLがブラウザによって違います**（`<b>` か `<strong>` か、あるいは `style="font-weight:bold"` か）。`style` 属性はサニタイザが落とすため、**装飾が保存後に消える**という食い違いが実際に起きえます。
*   **出力**: 常に `<strong>` / `<em>` / `<u>`。いずれも許可リストにあります。
*   **判定**: 選択範囲が**すべて**その装飾なら外し、そうでなければ（一部だけの場合も含め）付けます。一般的なワープロと同じで、「まだ掛かっていない所に揃える」方が直感に合うためです。
*   **範囲の一部だけ外す**: `<strong>あいうえお</strong>` の「いう」だけ外す場合、装飾要素を前後で分割して `<strong>あ</strong>いう<strong>えお</strong>` にします（`splitAround` / `liftOutOf`）。
*   **整理（`tidyInline`）**: 操作のたびに、空になった装飾の除去・同じ装飾の入れ子の解消・**入れ子順序の正規化**・隣接する同装飾の統合・テキストノードの `normalize()` を行います。これをしないと付け外しのたびに `<strong></strong>` や `<strong>A</strong><strong>B</strong>` が積もり、保存HTMLが操作履歴に依存して膨らみます。順序の正規化により、太字→斜体と斜体→太字は**同じHTML**になります。
*   **キーバインド**: `Ctrl+B` / `Ctrl+I` / `Ctrl+U` を横取りします（`preventDefault()` しないとブラウザ標準の `execCommand` が走ってしまいます）。
*   **アンドゥとの関係**: 本文HTMLのスナップショット方式なので、この操作も `updateHtmlPreview()` 経由でそのまま履歴に載ります（特別扱いは不要）。

## 5. Web Components との親和性・イベント伝播制御

`<m-file>` や `<m-item>` といった Web Components の内部には、ユーザーが文字を入力するための `<input>` タグが含まれています。

ブロックエディタは通常、`Enter` キーを押すと「新しいブロックを下に追加」し、`Backspace` で「ブロックを削除」するグローバルなイベントリスナーを持っています。しかし、コンポーネント内の `<input>` で `Enter` を押した際に勝手に新しいブロックが作られてしまうと致命的なバグになります。

この問題を回避するため、コンポーネント内部の入力欄では、キーボードイベントが親の `.editor-block` までバブリングしないよう、適切に `event.stopPropagation()` を呼び出してイベントをせき止める設計としています（コンポーネントは Light DOM に描くため、イベントは素通しで親まで上がる。§0.1 参照）。

## 6. オートセーブ（Debounce）とロード処理

Notionのようなシームレスな編集体験を実現するため、エディタはバックエンドのAPI（`/api/save`, `/api/load`）と非同期で連携します。

### 6.1. オートセーブの実装（Debounce処理）
ユーザーが文字を入力したり、ブロックを移動したりするたびにサーバーへ保存リクエストを送ると負荷が高くなるため、「デバウンス（Debounce）」処理を挟みます。

*   **検知トリガー**: エディタ内での `input` イベント、またはD&Dの `drop` イベントなど、DOMツリーやコンテンツに変更が生じたタイミング。
*   **タイマー制御**: 変更を検知すると `setTimeout` で1〜2秒後の保存処理（`saveToServer()`）を予約します。予約時間内に再度変更が検知された場合は、前のタイマーを `clearTimeout` でキャンセルし、新しく予約し直します。
*   **ブロック離脱時の即時保存**: 上記のデバウンスに加え、`#editor-content` の `focusout`（＝そのブロックの編集が終わった時点）でも保存します。デバウンスは、ひとつのブロックを編集し続けている間の保険として働きます。
*   **送信の絞り込み（ブロック単位保存）**: 直近に保存した状態と比較して、送る内容を決めます。

    | 判定 | 送信先 | 送る内容 |
    |---|---|---|
    | 変更なし | — | **何も送らない**（ブロック間を移動しただけ等） |
    | 1ブロックの内容だけ変化（IDあり） | `POST /api/save-block` | そのブロックだけ |
    | 追加・削除・並べ替え・ID未採番・複数変更 | `POST /api/save` | 本文全体 |

    ブロックは `data-id` で識別しますが、**この属性は任意**です。付いていない本文
    （手で書いたHTML等）は全文保存で動きます。編集モードへ入るときに未採番のブロックへ
    IDを振り、その回の全文保存で正本へ永続化します。サーバーがブロックを見つけられない・
    IDが重複する場合は 409 を返し、クライアントは全文保存へフォールバックします。
*   **シリアライズと送信**: `updateHtmlPreview()` によって生成されたクリーンなHTMLを抽出し、`fetch('/api/save')` で POST します。属性値・テキストは `esc()` でエスケープされます（値に `"` や `<` を含めても生成HTMLが壊れないように）。詳細は 6.1.1。

#### 6.1.1. シリアライザ（語彙はサーバーから受け取る）

保存するHTMLは `innerHTML` をそのまま送るのではなく、DOMを辿って**語彙にある要素と属性だけ**を書き出して作ります（`serializeBlock`）。ブラウザが編集中に挿す一時的な属性（`contenteditable`・`spellcheck` 等）や、貼り付けで紛れ込んだ未許可の要素・`style` を落とすためです。落とさないと保存のたびにサーバーが除去し、エコーバックでブロックが差し替わってキャレットが飛びます。

*   **語彙の出どころ**: `GET /api/tag-schema`。**構造HTMLとカスタム要素の両方**が同じ形で返り、中身はサニタイザの許可リストそのものです（[本文サニタイズ設計.md](本文サニタイズ設計.md) §7）。エディタ側に手書きの要素リストは持ちません。
*   **2種類の書き出し方**: 名前にハイフンを含む要素は必ずカスタム要素なので、一覧を持たずに判別できます（`isCustomTag`）。

    | 種類 | 値の在りか | 書き出し方 |
    |---|---|---|
    | カスタム要素（`<m-*>`） | **属性** | 語彙にある属性だけを書き、子孫のカスタム要素を再帰（`serializeCustomElement`）。描画時に挟まる `<div>` 等のクロームは無視 |
    | 構造HTML（`p`・`ul`・`strong` …） | **中身そのもの** | DOMを辿って要素・属性・テキストを書き出す（`serializeNode`）。未知の要素は**アンラップ**して中身だけ残す（サニタイザと同じ扱い） |

*   **字下げ**: 空白が表示に影響しない要素（`ul`・`table`・`tr` 等、`WHITESPACE_INSENSITIVE`）だけ子を1行ずつ字下げします。`p` や `li` の中で改行すると空白として描画されてしまうためです。
*   **空要素**: `void`（`br`・`img`・`hr` 等）は終了タグを書きません。この一覧も `/api/tag-schema` から受け取ります。
*   **編集可能にする範囲**: `.block-content` 直下のうちカスタム要素でないものすべてを `contenteditable` にします（カスタム要素は自前のUIで編集するため対象外）。

> **かつての不具合**: エディタ側に `TEXT_BLOCK_TAGS = ['h1','h2','h3','p']` という手書きの表があり、サニタイザが許可している `h4`〜`h6`・`ul`・`table`・`blockquote` が**画面には出るのに保存すると消えていました**。語彙をサーバーの1箇所へ寄せたことで、この種のズレは構造的に起きなくなっています。
*   **サニタイズ結果の反映（エコーバック）**: サーバーは保存時に本文をサニタイズし、結果と `sanitized` フラグを返します。除去が起きたときだけ、差分のあったブロックを差し替えて通知します（フォーカス中のブロックはキャレット保持のため据え置き）。編集者は画面上の変化で何が落ちたかを把握できます。詳細は [本文サニタイズ設計.md](本文サニタイズ設計.md) §3。

### 6.2. ページIDの確定と新規作成フロー
*   **新規作成時**: ユーザーが「＋ 子ページを作成」をクリックすると、フロントエンドは `/api/new-page?parent={親ページID}` を呼び出します。
*   **サーバー処理とリダイレクト**: サーバーはアトミックにDBにレコードを挿入して新しいページID（例: `000001`）を確定させ、対応する初期HTMLファイルを生成したあと、そのアドレス（例: `/000001?edit=true`）へ302リダイレクトします。
*   **上書き保存**: 初回作成がサーバー側で完了しているため、フロントエンドは遷移直後から確定した `page_id` を使用して、通常の `POST /api/save` による上書き保存（Update）を行います。

### 6.3. ヘッダーの保存状況インジケーター
エディタの画面右上には、現在の状態を示すインジケーターを配置します。
*   `未保存`（または非表示）: 変更がない状態。
*   `保存中...`: `saveToServer()` が発火し、APIのレスポンスを待っている状態。
*   `保存済`: APIから正常にレスポンスが返ってきた状態。

### 6.4. データロード機構（サーバー合成方式）
`/000001` のようなURLにアクセスすると、サーバーが **`assets/index.html` に本文を埋め込んだ完成HTML** を返します（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.2.1）。初期表示で `/api/load` は呼びません。
*   **初期化フロー**: ページロード時（`window.onload`）、URLのパスからID（`000001`）を抽出し、`window.currentPageId` に設定します。
*   **展開**: 本文は既に `#editor-content` に入っているため、そのまま `initBlocks()`・`buildToc()` を呼んでブロック化します。初期表示のチラつきが無く、JSを実行しないクローラでも本文が読めます。
*   **本文はサニタイズ済み**: 埋め込まれる本文はサーバーが許可リスト方式でサニタイズしたものです（[本文サニタイズ設計.md](本文サニタイズ設計.md)）。**編集時は生HTMLを使う**ため、編集モードへ入る際に `/api/lock` の応答で載せ替えます（6.5）。
*   **エラーハンドリング**: 権限不足・不存在はサーバーが応答で解決します（認証済みで read 不可＝403、匿名で非公開＝`/login` へ302、不存在＝404）。フロント側のエラー表示は不要になりました。

### 6.5. `/api/load` が使われる場面
初期表示から外れたため、`/api/load`（生HTML）を使うのは**編集ロック起点の載せ替え**だけです。
*   **編集モードへ入るとき**: `acquireLock()` が `POST /api/lock` の応答に同梱される最新HTMLで載せ替えます。
*   **編集権を失ったとき**: `reloadContent()` が `/api/load` から取り直します（`handleLockLost()` 経由）。

この「閲覧＝サニタイズ済み／編集＝生」という非対称により、サニタイズで欠けた内容が保存されて正本を壊すことがありません（根拠は [本文サニタイズ設計.md](本文サニタイズ設計.md) §4）。

## 6.6. アンドゥ・リドゥ（Ctrl+Z / Ctrl+Y）

編集中の操作を取り消せます。設計の経緯と決定は [【考察】アンドゥ・リドゥ.md](【考察】アンドゥ・リドゥ.md) §3 が正本。

*   **なぜ独自実装か**: ブラウザ標準の undo は `execCommand` とネイティブ入力しか捕捉しません。
    このエディタはブロックの挿入・並べ替え・置換、明細の追加、カスタム要素の再描画といった
    **プログラム的DOM操作**を多用するため、標準undoではそれらを戻せず不整合になります。
*   **方式**: 本文HTMLの**スナップショット**を積む独自スタック（上限100）。復元は `populateEditor()`
    でまるごと再描画する既存経路を再利用します。
*   **粒度**: 1キーストロークごとではなく、**変更が確定した単位**＝保存が走る単位
    （既存の1.5秒デバウンス）。専用の変更検知は持たず `saveToServer` の差分判定に相乗りします。
*   **キーバインド**: Undo = `Ctrl+Z` / `Cmd+Z`、Redo = `Ctrl+Y` / `Ctrl+Shift+Z`。
    **必ず `preventDefault()`** して標準undoとの二重スタックを防ぎます。カスタム要素内の
    入力欄からも効くよう、ブロック絞り込みより前で処理します。
*   **キャレット復元**: 各スナップショットに `{data-id, 文字オフセット}` を添えて復元します。
    アンドゥ時は「戻した先の状態が作られたときの位置」ではなく**取り消した編集があった位置**へ
    置きます（一般的なエディタの挙動）。
*   **履歴の寿命**: 編集モードに入るとき初期化し、抜けるときに破棄します。
    **編集権を失ったとき（`handleLockLost`）も破棄**します——本文がサーバーの最新版に
    置き換わり手元の編集も失われているため、戻せない状態へのアンドゥを防ぎます。
    通常のブロック離脱では履歴は消えません。
*   **サニタイズとの関係**: 除去が起きたときは除去後の状態を積み直すので、
    アンドゥで危険な内容へ戻ることはありません。

> **保存済み文書の版管理（リビジョン／リバート）は別機能で未実装**です。過去の保存状態へ戻す
> 機能は [【考察】アンドゥ・リドゥ.md](【考察】アンドゥ・リドゥ.md) §4・§5 に設計だけがあります。

## 7. PDF連携（D&D、プレビュー, 自動解析）のフロー

ファイル容器 `<m-file>` コンポーネントには、PDFを扱うためのリッチなUXが組み込まれています。

### 7.1. アップロードフロー
*   **ドロップゾーン**: `<m-file>` 内に `.pdf-drop-zone` が配置されており、`dragover`, `drop` イベントを監視します。
*   **APIコール**: PDFがドロップされると、`FormData` を構築し `POST /api/upload-pdf` を呼び出します（この際、`window.currentPageId` が必要になるため、初回の自動保存が済んでいることが前提です）。
*   **属性の更新**: アップロード成功後、APIから返却されたファイル名を `<m-file src="...">` として設定し、コンポーネントを再レンダリングします。

### 7.2. インラインプレビュー
*   `<m-file>` の `render()` 処理内で、`src` 属性が `.pdf` で終わっているかを判定します。
*   該当する場合、`<embed src="/data/master/{prefix}/{pageId}/{src}" type="application/pdf">`（`prefix`＝pageId先頭2桁。例: `/data/master/00/000002/sample.pdf`）タグを動的に生成し、コンポーネントの枠内にPDFの中身を直接プレビュー表示させます。

### 7.3. 自動解析と明細追加（Gemini API連携）
*   **推測APIのコール**: アップロード完了直後に、続けて `POST /api/parse-pdf` を呼び出します。
*   **Geminiによる超高精度解析**: バックエンドでは受け取ったPDFをそのままGemini 3.5 Flashモデルに丸投げし、視覚的なレイアウトや表構造を加味して明細を抽出させます。
*   **DOMへの自動挿入**: バックエンドからパース済みのJSONデータ（`items`）が返却されると、フロントエンドはそれをループ処理し、自動で複数の `<m-item>` タグを生成してDOMに挿入します。
*   **エラーハンドリングの強化**: もしAPIキー未設定やGemini側の制限エラーが発生した場合、バックエンドは `success: false` と共に詳細な `message` を返却します。フロントエンドはこれを受け取り、「バックエンドエラー：〇〇」という形で画面上に詳細なアラートを表示し、握りつぶさないようにしています。
*   **自動保存連携**: 明細が挿入された後、`window.updateHtmlPreview()` と `window.triggerAutoSave()` を呼び出すことで、ユーザーの操作なしにデータが自動保存されるゼロクリックUXを実現しています。

## 8. Web Components のテンプレート外部化

`<m-tag>`, `<m-file>`, `<m-item>`, `<m-material>`, `<m-required-materials>` 等のデザイン（HTML構造）は、JavaScriptコード内にハードコードせず、`assets/templates/` 配下の個別HTMLファイルに分離されています。

*   **閲覧用・編集用の分離**: 各コンポーネントは閲覧モード用（例: `m-file-view.html`）と編集モード用（例: `m-file-edit.html`）の2種類のテンプレートを持ちます。
*   **非同期ロードとキャッシュ**: `assets/web-components.js` 内の共通関数 `fetchTemplate(name)` が、テンプレートを `fetch` で取得します。取得結果はメモリ上の `templateCache` に保存され、2回目以降の描画では再リクエストなしに即座に再利用されます。
*   **レンダリング処理**: 各コンポーネントの `render()` メソッドは `async/await` 化されており、ロードしたテンプレート文字列内のプレースホルダー（`${name}` 等）を現在の属性値で置換した上で `this.innerHTML` に流し込みます。

## 9. ページ情報サイドパネルと画面構成

UNIXに倣い、ページの**属性**（親ページID・作成日時・作成者・更新日時・権限）は本文HTMLではなく**サイドカー `<id>.meta.json`（正本）**に保存します（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 2・4章）。HTML本文は純粋な「内容」です。属性の表示・編集や子ページナビは、文書とは分離した**クローム側の独立サイドパネル `<aside class="rail">`** が担います。

### 9.1. 画面構成（レール＋文書）

> **各部分の呼び名と範囲は [画面構成と用語.md](画面構成と用語.md) が正本**（レイアウト図つき）。
> 本節は挙動の仕様を扱います。

役割を物理的に分離するため、画面は次の構成になります。作業領域は `flex` の4カラム
（左レール｜目次レール｜文書｜右レール）です。

| 層 | DOM | 役割 | ファイルに保存 |
|---|---|---|---|
| ヘッダー | `<header class="header">` | アプリのクローム（タイトル・モード切替・⚙管理・ログアウト） | ✗ |
| 作業領域 | `<div class="work-area">`（flex） | 左=階層ナビ、目次、中=文書、右=ページ情報 | — |
| └ 左レール | `<aside class="rail rail-left">` | **ページ階層**に対する情報と操作（親ページリンク、子ページナビ、＋子ページを作成） | ✗ |
| └ 目次レール | `<aside class="rail rail-toc">` | 本文の見出し（`h1`〜`h6`）から生成した目次 | ✗ |
| └ 文書 | `.doc-column > #editor-content` | ページの*内容*（タイトル・本文・`<m-tag>` 等） | ✓ |
| └ 右レール | `<aside class="rail rail-right">` | **このページ**に対する情報と操作（属性の表示・編集、権限） | ✗ |
| フッター帯 | `<footer class="site-footer">` | 現状は仮表示のみ | ✗ |

各レールの役割は「対象（左＝ページ階層／右＝このページ）に対する**情報と、それに紐づく操作**をまとめる」という基準で統一しています。汎用的な操作（検索・コマンドパレットなど特定のページ／階層に紐づかないもの）はこの基準に当てはまらないため、レールではなくヘッダーや別のオーバーレイUIに置く方針です。

かつてヘッダーと文書の間にあった**ページ操作バー（`<nav class="page-actions">`）は廃止**しました。そこに同居していた「＋ 子ページを作成」は**左レール最下部**（親ページリンク・子ページカードの下）へ、左右レールの開閉トグルは**各レール脇に固定した常時表示のつまみ**（§9.1.1）へ振り分けています。

作業領域は **`@media (max-width: 760px)`** で挙動が切り替わります。広い画面では文書の左右にレールを置き、狭い画面では文書を1カラム全幅にしてレールを**ドロワー化**します（§9.1.1）。

### 9.1.1. レールの開閉・ドロワー・永続化
左右レールは、各レール脇の**画面端に固定した常時表示のトグル**（`<button class="rail-toggle" id="toggle-left|toggle-right">`、`toggleRail('left'|'right')`）で開閉します。トグルは `position: fixed`・縦中央配置なので**ページをスクロールしても常に見え**、ページ操作バーに依存しません（縦書きラベル＋アイコンのつまみ。開いている側は `is-on` でアクセント色）。トグルは**画面幅でモードが変わります**。

*   **広い画面（`> 760px`）**: レールを文書の脇に**インライン表示**し、トグルで畳む／開く。開閉状態は**サーバー非依存のUI設定**なので **UI 設定ストア（`localStorage` の単一キー `wcms.ui` の `rails` セクション）に保存**し、全ページで共有します（クッキー不使用＝毎リクエスト送信の無駄を避ける。§9.1.2）。`<head>` のインラインスクリプトが body 描画前に状態を読んで `<html>` にクラス（`left-collapsed` / `right-collapsed`）を付けるため、チラつき（FOUC）が起きません。
*   **狭い画面（`≤ 760px`）**: レールを **`position: fixed` のオフキャンバス・ドロワー**にし、トグルで左右からスライドイン／アウトします（`toggleDrawer`。`<html>` の `left-drawer-open` / `right-drawer-open`）。**左右は同時に1つだけ**開き、**半透明バックドロップ**を表示。バックドロップ click・**Escape**・**デスクトップ復帰（`matchMedia` change）**で自動的に閉じます（`closeDrawers`）。ドロワー状態は**永続化せず既定は閉**（狭幅では `collapsed` 設定は無視）。ドロワーは全高で `overflow-y: auto` ＋ `overscroll-behavior: contain` により**単独でスクロール**し、表示中は `<html>` を `overflow: hidden` にして**背景（window）スクロールをロック**します（モーダル相当。閉じれば位置は保たれる）。
*   ドロワーをビューポート基準で固定するため、`.container` の `container-type` は外し、レイアウト分岐はコンテナクエリからビューポート `@media` へ移行しています（`prefers-reduced-motion` 尊重）。

### 9.1.2. UI 設定ストア（`wcms.ui`）
レール開閉のような**サーバー非依存のクライアントUI設定**は、`localStorage` の**単一ルートキー `wcms.ui`** に**階層化した JSON** で一元管理します。キーを散らかさず、設定が増えても**セクションを足すだけ**で済むようにするための仕組みです。

*   **API**: 本体スクリプト先頭の `UI` ヘルパが `UI.get('rails.left', 既定値)` / `UI.set('rails.left', 値)` のドットパスで読み書きし、`set` で自動的に永続化します。
*   **バージョン管理**: `_v` を持ち、スキーマ変更時は `migrate` を1本足すだけで移行できます。初版（`_v: 1`）で旧 `wcms.rails`（単発キー）を `wcms.ui.rails` へ取り込み、旧キーは掃除します。
*   **構造（例）**: `{ "_v": 1, "rails": { "left": true, "right": true } }`。将来は `theme`（配色）・`cards`（`<details>` 開閉）・`editor`（プレビュー表示）等のセクションや、必要ならページ別の `pages.<id>.*` を同じストアに足せます。
*   **FOUC 防止**: `<head>` のインラインスクリプトは本体読込前なので `UI` に依らず `wcms.ui`（無ければ旧 `wcms.rails`）を直接読み、レール初期クラスを付けます。
*   **置き場所**: エディタの本体スクリプト（[assets/app.js](../assets/app.js)）内に実装。管理画面など他ページでも使うようになったら共有JSへ抽出します（現状は不要）。

### 9.2. サイドパネルのカード（`<aside class="rail">`）
各レールは複数のカード（`<details>` で折りたたみ可能）を縦に並べたものです。カードはクロームであり、ファイルには保存されません。

*   **親ページリンク（左・最上部）**: 親があれば「↑ 親ページ」リンクを左レールの**最上部**（子ページカードの外）に表示します（「親＝上／子＝下」の階層感。子ページカードを畳んでも常に見える）。`loadPageMeta()` が描画し、トップページなど親が無いときは表示しません。
*   **子ページカード（左）**: `loadChildNav()` が `GET /api/children?parent_id=` で子ページ一覧を描画。本文に子ページ一覧を埋め込みたい場合は、従来どおり `<m-child-list>` をスラッシュメニューから挿入できます（既定テンプレートには含めません）。
*   **子ページを作成（左・最下部）**: 「＋ 子ページを作成」ボタン（`.page-action-btn`、`createSubpage()`）は、子ページ階層に対する操作なので左レールに置きます。親ページリンク・子ページカードの**下（レール最下部）**に配置（試験的な配置。最上部から変更）。レール幅いっぱいの主ボタン。
*   **ページ情報カード（右）**: ページID・親ページID・作成日時・作成者・更新日時を表示。`loadPageMeta()` が `GET /api/page-meta?id=` で取得して描画します。日時は `formatDateTime()` で日本語整形。ページIDは常にURL/DBを正とします。
*   **権限カード（右）**: owner / group / mode の表示と chmod / chgrp / chown。旧 `perms-panel` をここへ畳み込みました（`loadPerms()` が読み込み時に `GET /api/page-perms` で取得）。権限はこのカードに常設のため、ヘッダーにあった「🔒 権限」ボタンは廃止しました。
    *   **編集は編集モード（＝ロック保持中）でのみ可能**。閲覧モードでは値を読み取り専用で表示し、入力欄を無効化・「保存」「所有者変更」を隠して「編集モードに切り替えてください」と促します（`refreshPermsEditable()` が `body[edit-mode]` とサーバーの `can_chmod`/`can_chown` の両方で可否を判定。`applyMode()` から再評価）。これにより権限変更も本文編集と同じロックで直列化され、他者との競合を避けます（親ページIDの編集と同じ方針）。
    *   **UIゲートに加えサーバーでも検証**: `savePerms()`/`chownPage()`/`applyParent()` は共通ラッパ **`lockedFetch()`** 経由で送信し、現在のロックトークンを `X-Lock-Token` ヘッダに載せます。サーバーは共通ゲート `RequireEditLock` で検証し、他者保持中なら **409**（→ `handleLockLost` で退避＋再読込）。直接API経由の競合も防げます（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.3）。将来のエディタ内操作（画像/PDFの保存・削除など）は、UIに `.edit-only` を付け、送信を `lockedFetch`、サーバーを `RequireEditLock` に通すだけで同じロックを共有できます。
*   **編集できる属性は編集モードでのみ**。親ページIDは編集モードで入力欄＋「適用」ボタンを表示し、`applyParent()` が `POST /api/set-parent?id=&parent=` でサイドカーへ反映します（成功で更新日時表示も更新）。作成日時・作成者・更新日時・ページIDはサーバー管理の読み取り専用です。

### 9.3. 親ページIDの入力検証
「適用」を押すと `POST /api/set-parent` がサーバー側で検証してから反映します。検証は実在・自己参照/循環の防止・新しい親への write 権限を確認します。**親なし（トップレベル）化はトップページ（`000000`）自身のみ可能で、他のページは admin でも親なしにはできません**（子ページ作成時も同様に `parent` は常に必須）。不正ならカード内に赤字エラーを表示して**反映しません**。即時フィードバック専用の `GET /api/validate-parent` も同じ検証ロジック（`validateParentChange`）を共有します。

## 10. 編集ロックのライフサイクル（同時編集の競合対策）

同一ページの同時編集による lost update を防ぐため、フロントは**編集モードに悲観ロックを紐づけ**ます。バックエンドのAPIと方式は [アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.3、設計の経緯は [【考察】同時編集の競合対策.md](【考察】同時編集の競合対策.md) を参照。`toggleMode` は **`applyMode`（表示/編集のDOM切替）** と **`onModeToggle`（ロックの取得・解放の入口）** に分離されています。

*   **取得（編集モードに入る）**: `onModeToggle` が `POST /api/lock` を呼ぶ。ロックは**エディタ個体（トークン）単位**で、同じユーザーが別タブで開いた場合も競合として扱う。
    *   成功 → 返ってきた**最新HTMLで再ロード**してから（`populateEditor`）編集モードを適用。古い版で他者の編集を上書きしないため必ず再ロードする。
    *   **423 busy** → 閲覧モードのまま、**「待機をやめる」ボタン付きトースト**を出す（応答の `same_user` で「別のタブ／ウィンドウで編集中」と「『○○』さんが編集中」を出し分け、`grace_remaining_sec` で残り時間も表示）。同時に**待機者として SSE を購読**（`openWaiterEvents`）し、空き次第でサーバーから push される `available` を受けて**自動的に編集へ入る**（最新HTMLで再ロード）＝**取得は自動なので操作不要**。トーストの**「待機をやめる」**を押すと購読を閉じて待機を取りやめ（サーバー側は待機者の離脱として猶予をキャンセル）、トーストも消える（`cancelWaiting`）。これにより「要求 → 約2分後に自動移譲 → 待機者が自動で編集開始」が成立する。
*   **状態変化の受信（SSEプッシュ）**: ポーリングはせず、**`EventSource('/api/lock-events')`** を購読する。保持者は `role=holder`、待機者は `role=waiter`。**接続の生存＝presence**（タブを閉じれば即座に離脱が検知される）。
    *   保持者が受ける `waiter` → 「編集を待っている人がいます（残り約N分）」トースト。「**今すぐ編集権を渡す**」アクションで、2分を待たず即座に譲れる（直前の内容を保存してから解放するので失われない）。`holding`（待機者なし）でトーストを消す。
    *   保持者が受ける `lost`（猶予満了・強制明け渡し・保持者切断による移譲）→ `handleLockLost`：自分の変更をクリップボードへ退避し、閲覧モードへ戻したうえで**最新の内容を再読込**（`reloadContent`）して他の人の編集を反映する。
*   **保存**: `/api/save` に**ロックトークンを同梱**。**409**（編集権喪失）なら `handleLockLost` と同じ退避処理。
*   **解放**: 閲覧モードへ戻ると `POST /api/unlock` ＋ SSE 切断。タブ離脱・ページ遷移時は `pagehide` で `navigator.sendBeacon('/api/unlock')`（ベストエフォート。SSE 切断でもサーバーは presence 喪失を検知）。
*   **ヘッダーの出し入れ（headroom 型）**: ヘッダーは `position: sticky` のまま、**下スクロールで隠れ・上スクロール／上端付近（〜80px）で再表示**する（`initHeadroom`／`.header--hidden` で `translateY(-100%)`。`requestAnimationFrame` スロットル＋`passive` リスナー、`prefers-reduced-motion` 尊重）。sticky のまま transform で隠すのでレイアウトはガタつかない。モードトグルが常駐しなくなる分、**モードの気付きはトーストで補う**（§10.1）。
*   **モバイル（狭幅）対応**: ヘッダー（`.header`／`.switch-container`）は `flex-wrap` で右側コントロール群を下段へ折り返し、横スクロールを防ぐ。`@media (max-width: 480px)` で `body`/`.container` の余白を詰めて表示幅を確保し、タイトル縮小・`#save-status` の固定幅解除・`.page-actions` の折り返しを行う。折り返しでヘッダーが多段になっても headroom は高さ100%基準なので完全に隠れる。

### 10.1. アプリ内通知（トースト）
ロック関連のフィードバックは、画面右下固定の**トースト通知エリア**（`#toast-host`）へ集約します。`notify(message, {type, duration, id, action})` で出し、種類（info/warn/error/success）・自動消去時間（`0` で消えない）・同一 `id` の置換・任意のアクションボタンに対応します。保存エラーなど将来の通知も同じ仕組みに集約できます。

*   **モード移行の明示（緑トースト）**: ヘッダーが headroom 型でモードトグルが常駐しないため、モード移行をトーストで知らせる。編集モード移行時に **緑（success）の「編集権を取得しました。編集モードです。」**（3秒）を出す（待機後の `available` 自動入室経路でも通るので「権限が回ってきた」気付きにもなる）。閲覧モードへ戻ると **「閲覧モードに戻りました。」**（info・2.5秒）。両者は `id:'mode'` で互いに置換する。
