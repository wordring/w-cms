# ページ情報欄の統合（検討中）

> 本ドキュメントは実装前の設計議論メモです。合意が取れた内容を確定仕様として
> [エディタ仕様.md](エディタ仕様.md) 等へ反映したら、本ファイルは削除またはアーカイブしてください。

## 1. 課題

現在のエディタ画面 (`assets/index.html`) には、**親ページIDの入力欄が2か所**存在する。

1. **ヘッダー部分**（`assets/index.html:317-319`）
   - `ページID: <strong id="display-page-id">` （表示のみ）
   - `親ページID: <input id="parent-id-input">` （編集可能）
2. **文書本文中の `<m-tag name="親ページID">` ブロック**（`assets/web-components.js` の `MTag` コンポーネント）
   - 編集モードでは `m-tag-edit.html` テンプレートにより、本文中にインライン入力欄として表示される。

両者は `updateParentIDTag()` (`assets/index.html:492-514`) と、読込時の逆方向同期 (`assets/index.html:1241-1245`) によって値を一致させているが、

- 同じ情報を異なる場所で2回編集できる UI は分かりにくい。
- 本文中の `m-tag` は他の可変タグ（自由記述のメタデータ）と見た目が同じため、「これはシステム上特別な意味を持つ親子関係のタグだ」と気づきにくい。
- ヘッダー側は「ページID／親ページID」のみで、作成日時・更新日時・作成者などのページ管理情報は表示されていない。

## 2. 提案する変更

### 2.1 方針

- **ヘッダーの簡易表示（`display-page-id` + `parent-id-input` の行）を廃止する。**
- 代わりに、**文書編集欄（`#editor-content` 等のコンテンツ領域）の最上部**に「ページ情報パネル」を新設し、そこに集約する。
- パネル内の項目は、編集可能なものは入力欄（input）で、不可なものはラベル＋値のテキストで表示する。

### 2.2 表示項目（案）

| 項目 | 編集可否 | データソース（現状） | 備考 |
|---|---|---|---|
| ページID | 不可 | `pages.id` | 新規作成後に確定するため、新規作成中は空欄表示 |
| 親ページID | **可** | 本文中 `m-tag[name="親ページID"]` の `value`、DB側は `pages.parent_id` | 唯一の編集導線とする。本文中の `m-tag-parent` 要素は内部表現として残すか、廃止するかは 3.1 で要検討 |
| 作成日時 | 不可 | **未実装**（`pages` テーブルに `created_at` 列が無い） | 2.4・3.2 参照。ファイルに記録しないと再構築で失われる |
| 更新日時 | 不可 | `pages.updated_at` | ただし再構築のたびに「今」で上書きされ、真の更新履歴は残っていない（2.4 参照） |
| 作成者 | 不可 | **未実装**（`page_perms.owner` はあるが chown 可能なため「作成者」ではなく「現在の所有者」） | 2.4・3.2 参照。作成者を恒久的に残すにはファイル（または meta.json）に記録が必要 |

### 2.3 配置イメージ（イメージのみ・実装はまだしない）

```
┌ 文書編集欄 ─────────────────────────────────┐
│ [ページ情報パネル]                              │
│  ページID: 000123    親ページID: [ 000010 ]    │
│  作成日時: 2026-05-01 10:00  作成者: admin     │
│  更新日時: 2026-06-20 19:03                    │
├──────────────────────────────────────────┤
│ （以降、通常のブロックエディタ本文）              │
│  # 見出し...                                   │
└──────────────────────────────────────────┘
```

### 2.4 「ページ情報はファイルに保存する」案の評価（重要）

> ユーザー方針: ページ情報は文書の内容ではなく**属性**だが、文書の一部ではあるので、
> **ページ内（HTMLファイル）に記録して保存したい**。

これは w-cms のアーキテクチャ（「**ファイルが正・DBは派生インデックス**」）と完全に整合しており、
単に「自己記述的で移植しやすい」という以上に、**そうしないと一部の情報がそもそも恒久的に残らない**という
実装上の根拠がある。

**根拠: DB再構築でメタデータは失われる。**
管理コンソールの「DB再構築」ボタンが呼ぶ `RebuildDatabase()` は、`data/master` 配下のHTMLファイル群を
正としてDBを丸ごと作り直す（[internal/cms/sync.go:92](../internal/cms/sync.go)）。このとき：

- `updated_at` は INSERT/UPSERT 時に `CURRENT_TIMESTAMP`（=再構築した瞬間）で上書きされる
  （[internal/cms/sync.go:60](../internal/cms/sync.go)）。**真の最終更新日時は保持されていない。**
- `created_at` 列・作成者列は**そもそも存在しない**。
- 作成者は新規作成時に `EnsureSidecar()` がサイドカー `<id>.meta.json` の owner として記録するが
  （[internal/cms/handler.go:262](../internal/cms/handler.go)）、owner は chown で変わるため「作成者」とは別物。

つまり「ファイルに書く」を採らない限り、作成日時・作成者・正確な更新日時は再構築で消える。
**結論: ユーザー案（ファイルに記録）を採用する。** 表示専用パネルではなく、HTMLに永続化する設計とする。

**ただしフィールドごとに「誰が書く権限を持つか」を分ける必要がある（自己記述 ≠ 何でもクライアント編集可）。**

| フィールド | 書き込み主体 | ルール |
|---|---|---|
| 親ページID | ユーザー（クライアント） | パネルの入力欄で編集 → HTMLに反映 → 同期 |
| 作成日時 / 作成者 | サーバー（生成時に1回だけ） | 新規作成HTML（`NewPageAPIHandler`）に埋め込む。以後クライアントが書き換えても保存時にサーバーが無視・復元する（改竄防止） |
| 更新日時 | サーバー（保存のたび） | 保存時にサーバーがHTMLへ注入。クライアント値は信用しない |
| ページID | サーバー（採番） | DBの自動採番が正。ファイルへ埋めるのは表示・自己記述用の冗長コピーに留める（移動・再採番で陳腐化しうる点に注意） |

**実装上の含意:**

- 保存API (`SaveAPIHandler`) は、受け取ったHTMLの「サーバー権限フィールド」を**サーバー側の値で上書きしてから**保存する責務を負う（クライアントを信用しない）。
- これらを束ねる専用ブロック（例: `<m-page-info>` Webコンポーネント）を導入し、文書編集欄の先頭に1つだけ置く案が素直。既存の `<m-tag name="親ページID">` はこのブロックの中に内包させる（現行の親ページIDタグ方式＝3.1案Aをそのまま活かせる）。
- 永続化するため、`pages` テーブルに `created_at` / `created_by` 列を追加し、`SyncIndex` / `RebuildDatabase` がHTML（またはサイドカー）から読み取って入れる必要がある（3.2）。

### 2.5 「＋子ページを作成」ボタンの行方 ＝ 「ページ操作バー」の新設

現状このボタンは親ページID入力欄と同じ行にあり、混乱の一因になっている。**機能の性質を整理すると、これはページの「属性」ではなく「アクション」**である：`createSubpage()` は `currentPageId` を親として **新しい別ページを作る**導線（[assets/index.html:416](../assets/index.html)）。`<m-child-list>`（子ページ一覧）は単なる便利表示に過ぎず、ここへ併設するのも適切ではない。

→ **方針: ヘッダーと文書の間に「ページ操作バー」を新設し、このページに対するアクションをそこへ集約する。**

これにより役割が次の3層にきれいに分離される：

| 層 | 役割 | ファイルに保存されるか |
|---|---|---|
| **ヘッダー** | アプリのクローム（タイトル・モード切替・🔒権限・⚙管理・ログアウト） | ✗ |
| **ページ操作バー**（新設・ヘッダと文書の間） | このページに対する*アクション*（＋子ページを作成。将来: 複製・PDF出力など） | ✗ |
| **文書（ページ情報パネル＋本文）** | ページの*属性*（`<m-page-info>`）と*内容* | ✓（HTMLに保存） |

- **利点**: 「保存されないアクション」と「保存される属性」が物理的に分離され混同しない。将来アクションが増えてもこの帯に集約でき拡張性が高い。
- **注意**: この帯は文書（ページ情報パネル）のすぐ上に来るため、**見た目を「文書の一部」に見せない**こと。帯はクローム色、ページ情報パネルは文書の“紙”の中、という視覚的対比をつける。

## 3. 未確定事項・要相談ポイント

### 3.1 本文中の `m-tag[name="親ページID"]` をどうするか

現状、親ページIDは「本文タグとして保存されるメタデータ」という設計になっている（`docs/アーキテクチャとDBスキーマ.md` 参照、HTML内のカスタムタグからDBへ同期する仕組み）。選択肢:

- **(A) 本文中のタグ表現は内部実装として維持し、UI上の編集導線だけパネルに一本化する。**
  パネルの入力欄が `m-tag` の `value` 属性を裏で更新する（現行の `updateParentIDTag()` に近い実装）。本文中には可視のインライン入力は出さない（`m-tag-parent` 専用の非表示テンプレート、または本文走査時にスキップする等）。
- **(B) 親ページIDをタグ方式から脱却し、ページ情報パネル専用のサイドデータ（例: 保存APIのトップレベルフィールド）に変更する。**
  `docs/アーキテクチャとDBスキーマ.md` の同期ロジック（`internal/cms/parser.go` / `sync.go`）に影響するため変更範囲が大きい。

→ **(A) を採用**（2.4 の方針と整合）。既存の同期機構（HTML→DB）をそのまま使え、変更範囲を抑えられる。親ページIDタグは新設の `<m-page-info>` ブロック内に内包する。

### 3.2 作成日時・作成者の永続化方法 ＝ HTML本文へ（確定）

2.4 で「ファイルに記録する」方針は確定。記録先は **(ア) HTML本文**で確定（ユーザー合意済み）：

- `<m-page-info>` ブロックに属性として保持（例: `<m-page-info created-at="2026-05-01T10:00:00Z" created-by="admin" ...>`）。自己記述的でファイル単体で完結。
- クライアントから見える／書き換えられるが、**保存API (`SaveAPIHandler`) がサーバー権限フィールドを保存前にサーバー値で上書き**して改竄を防ぐ。新規作成時の作成者はサーバーが取得済み（[internal/cms/handler.go:225,262](../internal/cms/handler.go)）。
- `pages` テーブルへ `created_at` / `created_by` 列を追加し、同期 (`SyncIndex` / `RebuildDatabase`) がHTMLから読み込んで反映する。

### 3.3 新規ページ作成時（ページIDが未確定の状態）の表示

新規作成はサーバーが採番してからリダイレクトするフロー（`docs/エディタ仕様.md` 6.2節）なので、エディタが開く時点で既にIDは確定している。よって「ID未確定の編集画面」は基本的に発生しない想定でよいが、念のためパネル側はID空時に「未保存」表示でフォールバックする。

## 4. 確定した方針（まとめ）

- ページ情報は**HTMLファイルに永続化**する（DB再構築で失わないため）。表示専用にはしない。
- 文書編集欄の先頭に専用ブロック `<m-page-info>` を1つ置き、ページ情報を集約。既存の親ページIDタグはこの中に内包（3.1案A）。
- 作成日時・作成者の記録先は **(ア) HTML本文**（`<m-page-info>` の属性）で確定（3.2）。
- フィールドごとに書き込み主体を分離（ユーザー＝親ページID／サーバー＝作成日時・作成者・更新日時・ID）。保存APIがサーバー権限フィールドを保護する。
- ヘッダーの簡易表示（`display-page-id` + `parent-id-input` の行）は廃止。
- 「＋子ページを作成」はアクションなので、**ヘッダーと文書の間に「ページ操作バー」を新設**してそこへ集約（2.5）。`m-child-list` への併設はしない。
- UIは3層構成（ヘッダー／ページ操作バー／文書）。操作バーは見た目をクローム側に寄せ、文書と視覚的に区別する。
- **ページIDのHTMLへの冗長コピーはしない**（確定）。ページIDの表示は常にURL/DBを正とする。`<m-page-info>` にIDは埋め込まない。
- **`<m-page-info>` の表示レイアウト詳細は後で決める。** 当面は項目を縦/横に並べただけの**仮レイアウト**で実装を進め、見た目は後から詰める。

## 5. HTML/CSS のモダン化（あわせて実施）

現状の `assets/index.html` は構造・スタイルが古い：

- セマンティックタグ **0個**（`<header>` `<nav>` `<main>` `<section>` 等を使わず、すべて `<div>`。計23個の div）。
- インラインスタイルが **24か所**に散在。`<style>` ブロックはあるが CSS変数（デザイントークン）は未使用で、色（`#f1f5f9` `#1e293b` など）がリテラルで重複。

今回のUI再編（3層化）に合わせて、無理のない範囲で次を行う：

1. **セマンティックHTML化**: トップ枠を `<header>`（クローム）／ページ操作バーを `<nav>` または `<div role="toolbar">`／文書本体を `<main>` に置き換える。ページ情報パネルは `<section>`。
2. **CSS変数の導入**: 色・角丸・影・余白などを `:root` のカスタムプロパティに集約し、リテラル重複を解消する。
3. **インラインスタイルの削減**: 繰り返し使うものはクラス化して `<style>` 側へ寄せる。一度きりの微調整は残してよい（過剰なリファクタは避ける）。

> 注意（開発方針 4章）: 既存の無関係なコメント・構造は勝手に削らない。モダン化は「ページ情報統合」とは目的が異なるため、可能なら**別コミットに分ける**。

## 6. 次のステップ（実装順・各ステップ別コミット）

1. **DBスキーマ拡張＋同期**: `pages` に `created_at` / `created_by` 列を追加し、`SyncIndex` / `RebuildDatabase` がHTML（`<m-page-info>`）から読み込んで反映。新規作成 (`NewPageAPIHandler`) で初期値を刻む。
2. **保存APIの保護**: `SaveAPIHandler` がサーバー権限フィールド（作成日時・作成者・更新日時）を保存前にサーバー値で上書き。
3. **フロント（機能）**: `<m-page-info>` Webコンポーネント＋テンプレート追加（**仮レイアウト**）。本文先頭に配置し、親ページIDタグを内包。ヘッダー簡易表示の削除と「ページ操作バー」新設（＋子ページを作成を移設）。
4. **HTML/CSSモダン化**（5章）: セマンティックタグ化・CSS変数導入・インラインstyle削減。**別コミット**。
5. **ドキュメント反映**: `docs/エディタ仕様.md`・`docs/アーキテクチャとDBスキーマ.md` に確定仕様を反映。本ファイルは役目を終えたらアーカイブ/削除。
