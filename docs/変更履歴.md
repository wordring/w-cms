## メールアドレスを表示名と別のタグにする（2026-09-03）

ユーザー指摘:「**メールの差出人、宛先などは、メールアドレス単体でDBに入れるほうが
検索漏れが無くなって良いと思います**」。そのとおりで、実データがまさに踏んでいた——

```
宛先 = ㈱東邦金属工業所 南　様 (minami@i-toho.co.jp) <minami@i-toho.co.jp>
```

索引の逆引き（`PagesByTag`）は**完全一致**なので、この形では `minami@i-toho.co.jp` で
検索しても1件も出ない。しかも表示名の中にもアドレスが紛れており、部分一致に寄せるのは
筋が悪い（誤爆する・索引が効かない）。**値を原子的にする**のが正しい直し方。

- `.eml` 取り込みが `差出人`／`差出人アドレス`、`宛先`／`宛先アドレス`、
  `CC`／`CCアドレス` の**別々のタグ**を書く（`writeAddressTags`）。
  表示名の `=?ISO-2022-JP?B?…?=` は従来どおり復号する
- **宛先が複数なら対を繰り返す**（多値は対の繰り返し・[【一覧】語彙.md](【一覧】語彙.md) §4）。
  表示名の無いアドレスはアドレスのタグだけになる
- **解析できないヘッダは原文のまま1つのタグに落とす**——記録を落とすより、
  検索しにくい形でも残すほうがよい（受信箱は不変アーカイブ）
- `Cc` も拾うようにした（ユーザーの「など」に含めた。同じ経路で3行）
- 既存の実データ1ページも保存API経由で新しい形へ揃えた（版が残る）

**この形にしたのは、ユーザーが同時に述べた原則のため**——「利用者が、『名前：値』の
タグは見た目のままにDBに入れられると信じるためには、実際にそうである必要があります」。
検索の都合で**裏に隠れた正規化**（`差出人` は全体のまま見せ、`norm_value` にだけ
アドレスを入れる）を選ぶと、見た目とDBが乖離して、利用者は自分が書いた文字が何に
なるか予測できなくなる。**画面に出るタグを増やす**ほうを採った。

あわせて原則そのものを回帰テストで固定した（`TestTagValueIsIndexedExactlyAsDisplayed`）
——メールアドレス入りのヘッダ形・緩い日付・単位つきの数・全角と ㈱・要エスケープの記号を
並べ、**どれも書き換えずに** `value` へ入ることを見る。実データ（本文の dt/dd と
`vocab_index` の突き合わせ）でも不一致ゼロを確認済み。

テスト3本（分離とアドレス単体の逆引き・解析できないヘッダの保全・見た目のままの索引）。

**残る筋**: アドレスの大小文字の畳み込みは、次の「テキストの正規化」
（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §9・D-3残）で
`norm_value` 側の仕事として扱う——生テキストが正本、という原則は動かさない。

## コンパイル時に選べる拡張——板金部の既定セットを ext/sheetmetal へ（2026-09-03）

ユーザー:「**コンパイル時にプラグインを選択できるようにしたい**」。「w-cms は他社にも
使っていただきたいので、拡張として存在するものという立て付けにしたい」（2026-09-01）の
続き。文書には既に「他社デプロイでは外す・差し替える前提」と書いてあったが、
**外す機構が無かった**。

```bash
go build ./cmd/w-cms                 # 板金部の既定セット入り（既定）
go build -tags minimal ./cmd/w-cms   # 素の w-cms（他社へ配る形）
```

方式は **blank import**（`database/sql` のドライバ型）。`cmd/w-cms/ext_sheetmetal.go` が
唯一の取り付け口で、拡張が `init()` で自分の語彙・プラグイン・計算ビュー・ルートを
登録する。コアには登録の口を2つ足した（`RegisterVocab`・`RegisterView`。どちらも
二重登録はその場で落とす——黙って後勝ちにすると、どちらの宣言が効いているのか
画面から分からない）。

**既定を「入り」にしたのは、忘れて機能が静かに消えるほうが危ないから。** タグを
付け忘れたビルドは受注ページ生成も部材計算も業務語彙も無いまま**普通に起動して
しまい**、気づくのは「発注書を解析しても何も起きない」とき。外すのは他社へ配ると
いう意識的な行為なので、そちら側にタグを要求した。何が入っているかは**起動ログ**に
出す（`拡張セット: …`）——ビルドタグの付け外しは目に見えないので、画面から
確かめられるようにしておく。

**ルートも拡張と一緒に外れる。** `/api/analyze-attachment` は `main.go` への直書きを
やめ、プラグインの `Routes()` へ寄せた（直書きのままだと `-tags minimal` で
コンパイルが通らない）。

### 移したもの

PDF解析（`analyze_pdf.go`）・部材手配計算（`materials.go`）・手配状況リストの描画・
業務語彙8形式（受発注4・見積2・部材・手配ビュー）。**手配ビューの宣言も一緒に
出した**——宣言だけコアに残すと、素のビルドで「この形式の中身を作る処理が
まだ用意されていません」が永久に表示される。

コアに残した公開名: `CreateChildPage`・`GeminiGenerate`・`SafeAttachmentName`・
`DecodeJSONBody`（8MiB上限という方針を持つので複製しない）・`JSONFail`・
`StripJSONFence`・`DecodeZipName`・`ErrNoGeminiKey`・`MaxUploadBytes`・
`PagesByTag`・`VocabTableRowsOf`・`VocabBlocksOf`・`VocabNumber`・`VocabQuantity`。
最後の2つは語彙の一般規則（数量の空セルは1）なのでコアの持ち物。

### テストの置き場

コアのテストは業務語彙を**道具として**使う（サニタイザ・配送係・ブロック・
テンプレートの検査に現実的な形の表が要る）ので、写しを
`internal/cms/vocab_fixture_test.go` に置いた。**ずれても構わない**——試している
のはコアの機構であって板金部の列定義ではない。**宣言そのものの検証は拡張側**
（`ext/sheetmetal/vocab_test.go`）が受け持つ。

集計・解析のテスト11本は ext へ移し、種まきは**実本文を `SyncIndex` へ通す形**へ
書き換えた（索引への直接書き込みヘルパはコアの非公開）。経路が長いぶん本番に近く、
サイドカーが無いと権限が引き直せないことも実地で踏んだ（`addPage` に正本の
書き込みを足した）。

実測: 素のビルドは語彙が **12→4形式**（`tags`・`file`・`inspection-record`・
`child-list`）、`/api/required-materials` は **404**、起動ログは
「拡張セット: なし（素の w-cms）」。`go test ./...` は両ビルドで全通過。

## 取り込みの重複検知（source_ref・2026-09-02）

同じメールを受信箱へ2度落としても、記録が二重にならないようにした
（[【考察】通信記録処理.md](【考察】通信記録処理.md) §8・§10-2）。再ドロップは
**普通に起きる**——送り直し・取りこぼしの確認。黙って2枚できると、どちらが正かを
人が見分けられず、しかも参照タグ `受信元` の指す先が2つに割れる。

**鍵は本文の可変タグ `メッセージID`**（Message-ID）。専用テーブルは作っていない
——D-1 でドメイン表を全廃したので、鍵の置き場は**見える文字**しかなく、
判定は `vocab_index` の逆引き（`pagesByTag`）1回で済む。「見える文字がデータの
手掛かり」（コンセプト §2）がそのまま重複検知になった形で、**新しい仕組みは
1つも要らなかった**。

**分担は「鍵の取り出しは取り込み係・照合はコア」。** 何が鍵かは形式ごとに違う
（メールなら Message-ID、FAX なら受信機の通番）のでコアには決められない。逆に
「その鍵を持つページが既にあるか」は形式に依らない。任意実装の
`SourceRefFinder` を足し、コアが `ExistingIntakePage` で照合する。実装しない
取り込み係は従来どおり動く。

**判定に使うのは通信記録ページの存在だけ**（§2.7 の決定）。「このメールから受注
ページを作ったか」は使わない——使うと、受注ページを取り消したあとに再実行できなく
なり、可逆性が失われる。

**鍵を持たないファイルは異常ではない**（手で組んだメール・一部のFAXゲートウェイ）。
`ok=false` を返すだけで取り込みは止めない——重複検知が効かないより、記録が残らない
ほうが困る。

重複時の応答は `{"duplicate": true, "page_id": …}`。ただし**読めない相手には
`page_id` を返さない**（匿名の404統一と同じ規律）——「取り込み済み」という事実だけは
返す。でないと「なぜ入らないのか」が分からなくなる。

Goテスト3本（鍵が本文に書かれ索引から引ける／2度目が重複として検出される／
Message-ID が無くても取り込める）を先に赤で確認してから実装。実サーバーでも
同じ `.eml` を2回投げ、1回目は新ページ・2回目は `duplicate` で子ページが1つの
ままであることを実測した。

## PDF解析をボタン起動へ一本化——ZIP内PDFも解析できる（2026-09-01）

テストは Go 6本（生成・ZIP内取り出し・非発注書・API障害・write関門・エスケープ）

## 添付のクリック展開——PDFのインライン表示とZIPの目録（2026-09-01）

「PDFのインライン表示は可能ですか？」「ZIPの中身が見れるようにはなりませんか？」
（【考察】添付ファイルの表示と操作.md §2 の続き）。方式は**クリックで展開**を
ユーザーが選択——外来ファイルを自動では開かず、開く判断を人に残す。

- 閲覧モードで、きれいなURL（`/<ページID>/<生成ID>.pdf|.zip`）への📎リンクの横に
  **▶ボタン**が出る。PDFは押すと `<embed>`（ブラウザ内蔵ビューア・箱の中で自分で
  スクロールするので多ページでも本文の背丈は伸びない）、ZIPは**中身の目録**
  （名前とサイズ）。もう一度押すと閉じる
- **埋め込みは本文マークアップでは書けないまま**（サニタイザは `embed`/`iframe` を
  落とし続ける）。表示はクロームが担い、宛先は**リンクの href がきれいなURLの形に
  一致するときだけ導出**する——リンクの宛先はサニタイザが制限していないので、
  任意の href を embed に流してはならない（「本文で許す＝データをコードにする／
  クロームで出す＝コードがデータを読む」の線。app.js `refreshAttachmentPreviews`）
- ZIPの目録は `GET /api/zip-list`（[zip_list.go](../internal/cms/zip_list.go)）。
  標準ライブラリ `archive/zip` の**セントラルディレクトリ読みだけ**で展開はしない
  （ZIP爆弾を踏まない）。Windows の右クリック圧縮の Shift_JIS 名は x/text で復号。
  名前の検査は `safeAttachmentName` の同じ関門、認可は添付配信と同じ
  `RequirePageReadOrPublic`（OptionalAuth・route_guard_test に固定）
- 個々のファイルの取り出しは未実装（展開は攻撃面が別枠で増えるため、要望が出たら設計）

テストは Go 4本（目録・SJIS復号・名前の関門・閲覧関門）＋ **E2E 新スイート
verify-preview.js（13項目）**——展開・閉じる・正本を汚さないこと・CSP違反なしまで実測。
`go test` 全パス。

  （UTC の Z 表記は人が読み違える。指す時刻は同じ・ISO 8601 のまま。
  [intake_eml.go](../internal/cms/intake_eml.go)）。テストは実行機のタイムゾーンに

## 添付PDFの判定→受注ページ生成——板金部の既定セット（2026-09-01）

通信記録の2つ目の縦切り。受信箱へ `.eml` を落とすと、添付PDFを Gemini が
**「顧客が発行した発注書か」判定し、発注書なら受注ページを自動生成**する。

**コアに足したのは「取り込み観察係」の回覧1段**（[intake.go](../internal/cms/intake.go)

## 表の折り返し制御——短い値は折らず、長い文は折る（2026-09-01）

## リンクの挿入とプロパティ欄（2026-09-01）

[【考察】添付ファイルの表示と操作.md](【考察】添付ファイルの表示と操作.md) §4 の実装。
コンテキストツールバーの **🔗** が選択した文字を `<a href="">` で包み、キャレットが
リンク上にあるあいだプロパティ欄（`#w-link-popover`）が近傍に出る。

**モーダルは出さない。** ユーザーの経験則（2026-08-31）:「**編集するのにダイアログが
出るのは使いにくかった。プロパティ欄があるものが使いやすかった**」。列設定ポップオーバ
とまったく同じ形——値（表示される文字）は contenteditable、配線（href・表示されない）は
この欄。打つそばから本文へ反映し、「適用」ボタンは置かない。

**スラッシュメニューには載せなかった。** 設計文書は「スラッシュメニューに『リンク』
（または選択文字列をリンク化する操作）」と2案を挙げていたが、**前者は成立しない**
——スラッシュメニューは `/` で始まる段落を**ブロックごと**差し替える口で、文中の
インライン要素は入らない。リンクは B/I/U と同じ「選択した文字への操作」なので、
装飾の並びに置いた（文書側にも理由を残した）。

実装中に1つ踏んだ: **本文の中を押しても欄が閉じなかった**。`href` の欄にフォーカスが
ある間 `selectionchange` は早期 return する作り（列設定と同じ理由で、打っている最中に
キャレットが本文から出たと誤認して閉じるのを防ぐため）なので、キャレットが本文へ
戻ったことに気づけない。mousedown 側で「リンク以外を押したら閉じる」を持たせて解決。

宛先は**制限しない**（サニタイザの既定どおり。2026-08-21 決定——埋め込みの `/data/`
制限はリンクには掛けない）。ページ内・ページ間リンクの**補完**（`#見出し名` や `000123`
の入力補助）は未実装で、参照タグのリンク描画と同じ土台に乗るため一緒にやる。

`verify-stage2.js` に11項目追加（ボタンが出る／選択がリンクになる／欄が開く／欄は本文の
外のクローム／href が即時反映／保存に残りクロームは漏れない／リンクの外で閉じる／既存
リンクで開き直す／いまの href が入る／外すと a が消えて文字は残る）。E2E 9本・246項目通過。

## 添付のURLをきれいに——/<ページID>/<生成ID> と3役の一致（2026-08-31）

ユーザー決定の連なり:

> 添付ファイルのURLが「…/data/master/01/010152/files/….png」のようになりますが、
> 「…/010152/….png」のようにしたいです。実際に保存される場所を推測されたくないですし、
> 見た目もすっきりさせたいです。さらに、ファイル名も元のファイル名ではなく、
> 生成したものを使いたいです

> ファイル名とdata-id、IDを一致させるアイデアはどうですか？

> 一致させるとダウンロードで困るでしょうか？拡張子があるので区別できるかも

実装:

- **配信URLは `/<ページID>/<生成名>`**——ページURLの下の未使用名前空間。認可は旧口と
  同じ（read／実効公開・無ければ404）。物理配置（data/master/…/files/）はURLに出ない。
  旧URLは互換で配信継続
- **生成IDは3役を兼ねる**（`GeneratedAttachmentID`・時刻ミリ秒の base36）——
  保存名・URLの名前・**リンクブロックの data-id**。同じ文字列なので、参照
  `ページID-ID` が**ブロックとしても添付としても同じものに届く**（§9.3-3 の答え）。
  拡張子の有無でファイルとブロックを区別できる（ユーザーの見立てどおり）
- **ダウンロードの保存名は元の名前**——リンクの `download` 属性が運ぶ（サニタイザへ
  `a[download]` を許可。サーバーに状態を持たない）。表示文字も元の名前のまま
- **生成名の副産物: 添付の上書き破壊が設計ごと消えた**——同じ元名を再アップロード
  しても別ファイルとして増える（`TestAttachmentUploadsAreAuditedAndNeverDestroy`）
- サニタイザの埋め込み許可へきれいなURL形（`^/[0-9]{6}/[^/]+$`）を追加
- 移行ツールは全添付URLをきれいな形へ書き換える段まで拡張（実行済み・28ファイル
  15ページ。残る /data/master/ 参照は実在しないファイルへのテスト用リンク8件のみ）

## 添付の置き場を正本から分離——files/ サブフォルダへ（2026-08-31）

## 版のコアレッシングを「捨てる」から「置き換える」へ（2026-08-31）

ユーザー指摘「版の履歴が細かすぎます」。原因は窓（10分）の中の保存を**捨てる**方式にあった
——1セッションが〈最初の保存＝ほぼ編集前の内容〉と〈ロック解放時のチェックポイント＝
最終状態〉の**ほぼ同じ2版**を残す。短いセッションを重ねる実運用では、数分おきの
対の版が一覧を埋めていた。

**窓の中は最新の内容へ置き換える**方式に変更（[version.go](../internal/cms/version.go)）:

- 同じ編集者・窓内の保存は、直近の版の**中身を最新へ進める**（版IDは据え置き＝窓の起点、
  At は実際の内容の時刻へ前進）。窓の起点を At でなくIDにしたのは、置き換えのたびに
  窓が滑って永遠に1版へ畳まれるのを防ぐため——「10分ごとに次の版」の粒度は保たれる
- チェックポイント（ロック解放）は常に同内容になるため**自然に消える**——結果、
  **1セッション＝1版**
- `force` は**リバート専用の区切り**になった——「直前の退避」と「戻した記録」が

  **要らない語は消せる**

加えました（[【ガイド】デプロイ・運用.md](【ガイド】デプロイ・運用.md) §4.1）——`data/master`・

## DBスキーマ設計し直しの骨格が決まった（2026-08-30）

判断待ち.md からは消しました（同文書の「片付け方」の規約どおり）。

到達点は **コア2テーブル（`pages`・`page_perms`）＋汎用索引1本（`vocab_index`）＋
設定ファイル1本（`data/settings.json`）**——**ドメイン語彙を持つテーブルは1つも残りません**。
硬いドメイン表8つ（受注・受注明細・発注・発注明細・販売見積・購入見積・部材・タグ）は全廃し、
索引の「形式」列は `data-type` の値から**見出しの言葉**へ移ります（機能見出し＝本丸）。
**いずれも設計の確定のみで、実装は全部これから。**

### `page_refs` を作らないことにした（D-4・この日の一番大きな転換）

参照線（「この発注書はどのメールで届いたか」「この図面の1つ前の版はどれか」）を、
**専用テーブルではなく本文の「名前：値」タグ**で表すことにしました。

```
原発注書 : 000002-12
```

ユーザーの言葉:

> 由来への参照は必須ですが、DBに書き込むというより、文書に書き込みます。なんなら、
> **機械的に「名前：値」のタグを入れたって良い**のです。（…）そうすると、DBにも
> 「名前:値」のレコードが入りますから、あとから検索できるはずです。

> **page_refs は正本の座から降ろしてください。この方式にする理由は、AIが柔軟な操作を
> してくれると信じているからです。必ずその時代が来るはずです。**

**同じ日の午前には D-4 は「`page_refs` を今回の設計に含める」へ格上げされていた**ので、
これは方針の反転です。反転の決め手は**正本の置き場**でした——`page_refs` に参照線を持たせると、
それは本文から再生成できない唯一のデータになり、「DBはファイルから再生成できるものしか
持たない」（§8.1）を破ります。本文のタグなら正本はファイルのまま、索引は洗い替えで戻ります。
結果として**新しいテーブルが1つも要らなくなり**、D-1 で8テーブルを畳んだ流れの延長線に乗りました。

**代償は承知の上**——これは参照整合性のある関係ではなく**ラベル一致**なので、宙ぶらりん
（指す先が無い）と多重ヒットが起きえます。ただし「項目の鍵は見出しの表示文字」で
既に同じ賭けをしているので、設計としては一貫しています。

**この決定は前提条件を2つ要求します**（どちらも未実装）。とくに1つ目は机上の心配ではなく、
**議論で示された参照番号の例そのものが、ASCIIハイフン（`U+002D`）ではなく
半角カタカナの長音記号（`U+FF70`）を区切りに使っていました**。`toHalfWidth` が畳むのは
`－`(U+FF0D)・`ー`(U+30FC)・`−`(U+2212) の3つだけなので、いま実装するとこの参照は引けません。
**w-cms を作る動機（「ワンノートがハイフン区切りの図面名称を検索できない」）が、
参照の形で再来した**ことになります。

> **この段落は同日夕に一部が覆りました**——参照値は業務番号ではなく `ページID-ブロックID` と
> いう**文法を持つ**ので、正規化ではなく構文解析で扱えます。ハイフンの揺れが本当に効くのは
> **一般のタグ値（図面番号など）**のほうでした。下の「参照の値は業務番号ではなく…」を参照。

1. **テキストの正規化**——`NormalizeValue` は number と date しか正規化せず、text は素通し
2. **`(field, norm_value)` の索引**——いまの索引は `(page_id)` と `(data_type, field)` だけで、
   参照の逆引きが全表走査になる

`page_refs` が戻るとしたら、タグ値を解決した**派生のキャッシュ**としてだけです（洗い替えで
再生成できるので不変条件は壊れない）。現在の規模では自己JOINで足りるため、いまは作りません。

全編が `page_refs` 前提で書かれている [【考察】通信記録処理.md](【考察】通信記録処理.md) には、
冒頭に読み替え表つきの ⚠ を入れました（`plugin_quote.go` は不要・`ref_type` 列はタグの名前そのもの・
**参照追従集計そのものは残る**・§4.6 の「前版は新→旧の後ろ向き」も維持）。

### 参照の値は業務番号ではなく「ページID-ブロックID」だった（同日夕・D-7〜D-10）

**上の記述には、この日のうちに訂正が入りました。** 参照の値を「業務番号（発注書番号・図面番号）を
使い、ページIDは使わない」と書いていましたが、ユーザーの意図は逆でした:

> `000002` はページ番号、`12` はページ内のIDという意味で書きました。**URLのリンクみたいな
> 感じです**。したがって、PDFや表を文書に貼り付けると、IDが付く必要があるのかもしれません。

つまり値は業務番号ではなく**所在地**——`/000002#12` に相当します。ここから3つ出ました。

**押せば飛べる。しかも実装は既にある。** `RenderAnchors`（[anchor.go](../internal/cms/anchor.go)）が
ページ描画時に `data-id` を `id` へ合成するので、`#<ブロックID>` は今日のページでもう解決できます。
ユーザー:「**値はページとIDを指すので、クリックすれば移動すらできるのでは？**」——できます。

**D-7（番号の揺れ）はほぼ解消した。** 値が `<6桁のページID>-<ブロックID>` という文法を持つので、
生の文字列一致ではなく構文解析で引けます。ハイフンの種類の揺れは畳んでよく、
**先頭のゼロだけは絶対に畳めません**（ページIDのゼロ埋め6桁）。
ただし**一般のタグ値の揺れは別問題として残ります**——図面番号のような文法を持たない値は
ハイフン類・全角半角・英字の大小の判断が要り、これは **w-cms を作る動機そのもの**なので
**サイト内検索に着手するときに必ず戻ってきます**。

**ブロックIDの穴が2つ見つかった**（実測）。`data-id` は4桁の base36 ランダムで、
採番されるのは**トップレベルのブロックだけ**です。したがって **`<section>` の中の明細表には
IDが付かず**、参照で指せません（`vocab_index.block_id` が入れ子で空なのも同じ原因で、
**参照の解決に使う列がそこ**）。ユーザーの「PDFや表を貼り付けるとIDが付く必要がある」は、
**入れ子の要素で満たされていない**——実装前に埋める穴として §9.3 に書きました。
もう1つは、ページ間コピーで重複したとき `ensureBlockIds` が**振り直す**こと
——参照先が単独で存在する限り安定ですが、**恒久的な識別子ではありません**。

## 日付形式と数詞の調査（2026-08-30）

ユーザー指示「SQLiteが扱える日付形式や各国の一般的な日付形式を調査して文書化してください。
数値の後に付く数詞についても同様に」。D-3（取り込み時の正規化）の設計材料として
[【一覧】日付形式と数詞.md](【一覧】日付形式と数詞.md) を新設した。
SQLite の受理形式は本番と同じドライバ（`modernc.org/sqlite`・SQLite 3.51.2）で**実測**——
主要な発見: ①日本の業務文書の日付形式は**ほぼ1つも直接通らない**（`2026/06/15` も
`2026年6月15日` も、桁詰めなしの `2026-6-15` すら NULL）②数字だけの文字列は
**ユリウス日として解釈される罠**がある ③ゼロ詰めISOなら文字列比較＝時系列順で
`BETWEEN` が効く（正規化の出力形式はこれ一択）。各国形式・和暦換算・助数詞と単位は
実データ（板金部）の観測例つきで整理し、現行実装（`normalizeDate`・`typeInference` 5語・
`vocabNumber`）が読める形／読めない形の対応表で締めた。
同日、続く問答から2件——①空白区切りの日時（`2026-06-15 14:30`）は ISO 8601 ではなく
SQL リテラルの流儀（ユーザー指摘で表を訂正）②比較の三分類（文字列・数値・時間）は
意味の分類として正しく、格納クラス2つの上に乗る（数値だけは TEXT 格納だと壊れるのが
スキーマ設計の必須項目）。そして**決定**——「**時刻は ISO-8601 とします。w-cms 全域で
使用しますが、利用者がプラグインなどで別表記に対応するのを妨げるものではありません**」
（[要件定義書.md](要件定義書.md) §3 へ記録）。`updated_at` の表記ゆれ（小粒な残り）の
解消方向もこれで決まった。
