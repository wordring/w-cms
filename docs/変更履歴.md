## 表の折り返しは見出しで決める・検算の合格は薄い緑（2026-09-21 夜）

ユーザー:「備考欄以外は改行しないようにして、テーブルが横に大きくなりますから、
テーブルだけスクロールに出来ますか？」「検算に合格の色は緑系統が良いのでは？」

### 折り返してよいのは自由文の列だけ

番号・名前・数・日付・状態は、途中で折ると読みにくく**行の高さも揃いません**。
横へ伸びるぶんは**表自身が横スクロール**して受けます（ページは揺らさない）。

- 判定を**見出しの表示文字**（`WRAP_COLUMNS = ['備考']`）へ移しました。
  ⚠ **列の順番には依存しません**——列を足しても並べ替えてもずれません。
- ⚠ **2026-09-01 からは「長さ20字」のしきい値でした**（ワンノートの実測・
  品名 p95=19字・図面番号 p95=18字から採った値）。**しきい値は「その値が自由文か
  どうか」を当てにいく代理**でしかなく、実データで品名が20字を超え、
  **同じ列の中で折れる行と折れない行が混ざりました**。
- 表の横スクロールを `@media (max-width: 760px)` の中から**全幅へ**出しました。
  ⚠ それまで**狭い画面では表が自分でスクロールし、広い画面ではページごと横へ
  伸びて**いました。媒体クエリに重なっていた同じ宣言2つは畳みました。
- ⚠ **備考には幅の下限が要ります**（`min-width: 14em`）。ほかの列が折り返さないので、
  表は**備考だけを細らせて**収めようとします——実測（760px）で **69px まで細り、
  1つの備考が高さ417pxの短冊**になりました。下限を置けば、潰す代わりに横へ流れます。

### ⚠ 元から在った不具合——セルの印が、閲覧モードでは一度も付いていなかった

`validateTypedTables` は**編集モードに入るときだけ**呼ばれていました。CSS には
「編集・閲覧の両モードで効かせる（読みやすさはモードに依らない）」と書いてあったのに、
**閲覧で開き直すと印が消え、表が全部折り返して**いました。**一度編集へ入ると直る**ので、
「たまに直っている」という気づきにくい形です。本文DOMの変化で巡る
`decorateVocabBlocks` に相乗りさせました（変化が無ければDOMを触らないので、
観測→保存の輪にはなりません）。

番人は `e2e/verify-table-wrap.js`（自分で当て先を作り、最後に消す）。1280／760／390px の
**閲覧モード**で5点を見ます。変異試験でこの呼び出しを外すと6件 NG になり、
そのとき品名は `normal`・備考は 69px・21行——**報告された壊れ方と同じ**でした。

### 検算の合格は薄い緑（＋ 行頭の `✓`）

それまで合格は**灰色の文字だけ**で、「検算して合った」と「ただの注記」（検算
できません・飛ばした行があります）が**同じ見え方**でした。色の規約に3色目が増えます:

  薄い青 … 機械が読む　　薄い赤 … 疑わしい・未定義　　薄い緑 … 確かめて合った

⚠ **色だけに頼りません。** 赤と緑は赤緑色覚で**いちばん近づく組み合わせ**です——
`e2e/probe-phone.js` と同じ計算で ΔE は:

| 組み合わせ | 正常視 | 2型（緑） | 1型（赤） |
|---|---|---|---|
| 薄赤 × **薄緑** | 24.4 | **11.1** | **9.5** |
| 薄赤 × 薄青（`ref-missing`） | 18.3 | 17.4 | 20.7 |
| 薄赤 × 白（**それまでの合格**） | 12.9 | 8.5 | 9.5 |

同スクリプトの物差し（10以上で「別の色」・2以下でほぼ同じ）の**ちょうど境目**です。
⚠ **とはいえ後退ではありません**——それまでの白地＋灰文字のほうが低い（8.5／9.5）。
それでも境目なので、`⚠` と `✓` の対を最後の見分けにします——**印の形は色覚にも
白黒印刷にも影響されません**。

⚠ **自前で書いた ΔE の計算と、repo が持っていた `probe-phone.js` で数字が
食い違いました**（自前は2型 3.3・1型 4.4）。シミュレーションの行列が違うためです。
**repo の道具のほうを正**にしました——次に測る人が走らせるのはそちらなので。

## 受注ページに原本のPDF・品名の正規化・品番を Gemini に選ばせる（2026-09-21 夜）

ユーザー:「顧客の発注書（読んだまま）の上にPDFを表示できるようにします（通常は
折りたたむ）。品名が半角カナになっているので、正規化します。半角カナ以外も
正規化します」「品番には入りそうなものを入れます。…図番が多いですが、そうとも
限りません。これはGeminiに尋ねてはどうでしょう？」

3つとも**実データを開いて出てきた**注文です。09-20 に入れた原本の写しを実際に
読んでみて、足りないものが見えた形になります。

### ① 原本のPDFを、写しの上に畳んで置く

受注ページの並びが **原本（PDF）→ 読んだまま（機械の読み取り）→ 弊社の明細** に
なりました。**確かさの順**です——入れ替わると、人は読み取りの結果を原本だと思って
見ることになります。

- **畳んだ状態で始めます**（`open` を付けない）。毎日見るのは弊社の明細で、PDFは
  **食い違いを疑ったときに開くもの**です。開きっぱなしだと明細が画面の下へ
  押し出されます。
- **素のHTMLだけで畳めます**（`<details>`）——CSP strict の下でも、公開ページの
  ゼロJSでも動きます。原本の写しと同じ作法です。
- 書くのは**ファイル表示のマーカー1つだけ**で、開くのはコアの機能です
  （`section[data-type="file-view" data-ref]`）——この拡張はPDFの出し方を知りません。
  人が消せば出なくなり、`受信元` のタグ（出所の記録）は残ります。
- ⚠ **写しが読めなくてもPDFは出します。** 写しは機械の読み取りなので失敗しえますが、
  **PDFは在ります**。読めなかったときこそ人は原本を開きたいので、一緒に消えると
  **いちばん要るときに無い**ことになります。
- ⚠ **コア側に番人を1本足しました**（`TestFileViewOpensInsideDetails`）。配送係が
  `<details>` の中へ降りなくなった日に、**PDFが黙って出なくなります**——畳んで
  あるので、人は「閉じているだけ」と思って開き、空を見ます。気づきにくい壊れ方です。

### ② 弊社の表は正規形で書き起こす（原本の写しは読んだまま）

実データの品名が `ﾌﾞﾗｹｯﾄ` の形で届いていました。

⚠ **半角カナのままだと、同じ品物が2つの綴りで並びます**——`ブラケット` と `ﾌﾞﾗｹｯﾄ` は
**画面では似て見えるのに、検索では別物**です。索引の畳んだ値（`norm_value`）は NFKC を
通るので引くほうは当たりますが、**人が読む値**（`value`・表の見た目）は半角のまま残り、
目で見比べる人が揺れます。

通すのは `NormalizeNameForIngest`（NFKC＋空白の詰め）で、`NormalizeCode` では
ありません——長音を潰すと `レーザー` が `レ-ザ-` になります。

- **品番・品名・単位**を畳みます。⚠ **単位を落とすと** `ｾｯﾄ` が選択肢（`個`／`セット`）の
  どちらにも当たらず、画面が「見慣れない単位」として色を付けます。**まれにしか出ない
  単位ほど、揺れたまま気づかれません**。
- ⚠ **行の納期もページのタグと同じ作法**（`CanonicalForIngest`）を通します。それまで
  **ここだけ生で書いていた**ので、先方が `2026/10/15` と書くと**ページのタグは
  `2026-10-15`、行は `2026/10/15`** と食い違いました。日付として読めない値
  （「最短納期」）はそのまま残ります——**取り込みは情報を捨てない**（D-3）。
- ⚠ **原本の写しは畳みません。** 畳むと「読んだまま」が名前どおりでなくなります。

⚠ **これは「機械は text を書き換えない」の例外です**（[normalize_ingest.go](../internal/cms/normalize_ingest.go)）。根拠は
図面名称のときと同じで、**原本がページに出ているから**——食い違えば、すぐ上の
「読んだまま」の表と、**その上のPDF**で見比べられます。①を入れた日に②が成り立つ、
という順番です。

### ③ 品番に何を入れるかは、書面を読まないと決まらない

実データは**品番が7行とも空**でした。先方の表に「品番」という見出しの列が無かった
ためです。**品番を持たず図番を品番として送ってくる客先**があり、一方で**図番とは別に
品番を持つ客先**もあります——機械にも人にも、表を見ないと決められません。

そこで**選ぶのを Gemini に頼み、選んだ根拠も返させます**（`item_no_source`）。

- 頼み文の規則: 「品番」の列があればそれ、無ければ**図番・図面番号・部品番号・型式**など
  **その品物を一意に指している列**。番号にあたる列が無ければ空。
  ⚠ **品名を入れさせません**——同じ名前の別の品物がありえます。
- ⚠ **言い換えたときは本文に1行残します**（「解析は、先方の『図面番号』を弊社の
  『品番』に入れました」）。**0c の積み残し**でした——それまで**元の見出しは返り値の
  どこにも残らず**、原本と見比べない限り気づけませんでした。
  - ⚠ **言い換えていなければ黙ります**（毎回出る注意書きは読まれなくなる——
    未処理一覧で一度学んだこと）。
  - ⚠ **行ごとに違う列から採っていたら黙ります**。様式を読めていない印で、
    **1行で言えないことを1行で言うと嘘になります**。そのときは原本の写しが手掛かり。
- ⚠ **鏡型ではなく本文に書きます。** 検算の ⚠ は**いまの数字**についての判断なので
  人が直したら消えねばなりませんが、これは**解析がそのとき何をしたか**という出来事で、
  あとから品番を打ち直しても真のままです。

**頼み文を関数の外の定数へ出しました**（`orderJudgePrompt`）——番人が読めるように。
⚠ **`TestPromptMentionsEveryJSONKey`** が、頼み文とGoの構造体のずれを見ます。
**片方だけ直すと、その項目はエラーにならず常に空**になります——応答に入っていない
だけなので `json.Unmarshal` は何も言いません。気づくのは「あれ、単位が入っていない」と
誰かが思ったときです。

### ⚠ 途中で1つ踏んだ——パッケージ変数の初期化は `init()` より先

列の見出しを `var itemNoLabel = labelOf(...)` で引いたところ、**語彙が登録される前に
走って常に空**になりました。空だと比較が素通りして、**言い換えていないときも**
「先方の『品番』を弊社の『』に入れました」と出ます。関数にして直しました。
番人（`...SilentWhenSame`）が捕まえることを変異試験で確かめています。

### ⚠ 「最短納期」は、並べると先頭・絞ると消える（実測・未対応）

ユーザーの問い:「納期に最短納期と入っている場合、検索で一番納期が短いものとして
出てくるでしょうか？」——SQLite で実測しました。

`最短納期` は `date` として畳めないので `page_tags.norm_value` は **NULL** です
（生の値は正本として残る）。**いまはどこにも出てきません**——納期で並べる／範囲で
引く口がまだ無いからです。⚠ **作るときが危ない**:

| 書き方 | `最短納期` の行 |
|---|---|
| `ORDER BY norm_value` | **先頭に来る**（SQLite は NULL を最小として並べる） |
| `WHERE norm_value <= ?` | **黙って消える**（NULL の比較は偽） |

**正反対の振る舞いが同じ列から出ます。** 並べたときに先頭へ来るのは意味としては
合っていますが、`都度`・`未定` も同じ場所に来るので**たまたま**です。口を作るときは
`norm_value IS NOT NULL` を明示し、**畳めなかった納期は別枠で必ず見せる**こと。

## 発注書の検算——数どうしの辻褄で OCR を確かめる（2026-09-20 夜）

ユーザー:「顧客の発注書に数量と単価があって、金額や総額もあるなら、**検算が出来ると
思います**」。

**これは、外の正解なしに読み取りを確かめられる、たぶん唯一の手段です。** 他の検査は
すべて「人が紙と見比べる」に帰着します——原本の写しを残したのも（同日・下の節）
「人が見比べられるように」でした。**数どうしの辻褄なら、機械が自分で見られます。**

### 検算は3本あり、捕まえるものが違う

| 検算 | 式 | これだけが捕まえるもの |
|---|---|---|
| 行 | 数量 × 単価 = 金額 | その行の数の読み違い |
| 小計 | Σ金額 = **小計** | ⚠ **行の落丁** |
| 合計 | 小計 + 消費税 = 合計 | 小計・消費税そのものの読み違い |

⚠ **行の検算だけでは落丁に気づけません。** 1行まるごと落ちても、**残った行は互いに
辻褄が合ったまま**だからです。小計との突き合わせが唯一の手段になります。

⚠ **3本目に税率を使いません。** `小計 × 税率 = 消費税` と書くと 10%／8%（軽減）を
当てにいくことになりますが、`小計 + 消費税 = 合計` なら**税率を知らずに済みます**。
軽減税率の発注書で ⚠ が出ない、というのがこの式を選んだ理由です。

### ⚠ 検算を Gemini にやらせない

**この判断がいちばん大事です。** 自分の読みを自分で検算させると、LLM は**数字を合う
ように書き直します**——誤りが消えるのではなく、**見えなくなります**。検算の意味が
そこで失われる。

- Gemini に頼むのは `subtotal`・`tax`・`total` を**書かれているまま**返すことだけで、
  プロンプトに「**足し算・掛け算をして求めないでください**」と明示しました。
- 掛け算と足し算は Go（[ext/subcon/checksum.go](../ext/subcon/checksum.go)）でやります。

### 小計・消費税・合計金額はページのタグ

ユーザー:「変形した表になっていて、**表の右下の方に、小計、消費税、合計金額が
飛び出しています**」。書面のヘッダ（表の外）にある値なので、納期と同じく**ページの
タグ**にしました（`小計`・`消費税`・`合計金額`・いずれも `number`）。受注額として
それ自体見たい数でもあります。⚠ **`config/settings.json` に3語足したので DB再構築が要ります。**

⚠ **飛び出しているので、Gemini はそれらを明細の行としても返してきます。** そのまま
足すと**小計を二重に数え**、必ず ⚠ が出ます（狼少年になる）。**数量・単価・金額が
3つとも揃う行だけ**を足すことで自然に外れますが、**外した行数は黙らずに知らせます**。

### 見せ方は鏡型——弊社の明細の足元に

- ⚠ **本文には書きません。** 焼き込むと、人が数字を直しても ⚠ が残り、逆に直した結果が
  間違っていても ⚠ が出ません。**鏡型なら毎回数え直すので、直せば消えます。**
  そもそも `class` はサニタイズで落ちるので、印は鏡でしか付けられません
  （`ref-missing` の薄赤・`row-obsolete` と同じ作り）。
- ⚠ **引き金は弊社の受注明細で、原本ではありません。** 原本は `<details>` で畳まれて
  いるので、そちらに出すと**開くまで読まれない警告**になります。
- ⚠ **表の中へ `<p>`・`<div>` を足すと、HTMLパーサが表の外（手前）へ追い出します。**
  足元の行は **`<tfoot>` の `<tr>`** として足します。
- ⚠ **合っているときも黙りません。** 黙ると「検算して合った」と「そもそも検算して
  いない」が見分けられません（E2E が前提の無い項目を「飛ばす」と言うのと同じ理由）。
  ただし文面は控えめに——**辻褄が合うことは、正しいことを意味しません**。揃えて
  読み違えることはありえます。**合わないときに疑える、それだけの道具です。**

### 当て推量をしない

⚠ 見出しから `数量`・`単価`・`金額` の列が見つからなければ**検算しません**。当て推量で
別の列を掛け算すると、**正しい発注書に ⚠ を出します**——狼少年になると本物の ⚠ も
読まれなくなります。⚠ **部分一致も採りません**（`合計金額` が `金額` に当たって
小計を明細として足してしまう）。**様式ページ**（`取引先／社名／発注書の様式`）が
入ったら、そちらが見出しの対応の正本になります。

**変異試験12件**（検算6・鏡6）で、守りを外すとすべて番人が落ちることを確認しました。

ユーザー:「加工製品のページには、加工データを作るためのCADファイルが必要です。

`PUT` が届き、前の中身が版に残り、OLE の容器も壊れず、**引いた線が往復した**

```
    （75秒、何も届かない）
22:32:01  PUT         ← RootPro CAD を閉じた
```

## 添付の目録 `files/meta.json`（2026-09-17）

ユーザー:「各ページのFilesフォルダには、meta.jsonファイルがあって、元のファイル名や
保存日時等が書き込まれていると良いと思います」。

添付の保存名はサーバー採番のID（`kokl.pdf`）で、**元の名前を知っているのは本文のリンク文字
だけ**でした。`files/` を見ても WebDAV の一覧を見ても何のファイルか分からない。
`files/meta.json` に**保存した時点の事実**を書き留めます——届いたときの名前・保存日時・
利用者・大きさ・SHA-256・由来（`upload`／`mail:<受信原本>`／`zip:<ZIP>/<中のパス>`／`dav`）。

**本文との棲み分け**: 本文のリンク文字は「表示名」（人が書き換えてよい）、目録は「届いた事実」
（機械が書き、人は触らない）。問いが違うので正本が2つになりません。

- 書き手は保存の作法1か所（`cms.SaveAttachmentFrom`・[attachment_meta.go](../internal/cms/attachment_meta.go)）
  と WebDAV の上書き。取り込みの `IntakeContext.SaveAttachment` は自前の書き込みをやめてコアへ委譲。
- 読み手: **WebDAV の一覧が届いたときの名前で出る**（`Z:\…\補強ストッパー.dxf`。同じ名前が
  2つあれば保存名を添える。**保存名でも引ける**ので割り当て済みのショートカットは切れない）。
  ファイル表示の見出しも届いた名前に。目録が無い古い添付は保存名のまま。
- 守り: `.json` は添付にならない拡張子なので衝突しない。配信の口2つ（きれいなURL・旧URL）と
  WebDAV は `.json` を配らない。目録が壊れていれば上書きしない（空として読む）。目録が書けなくても
  保存は失敗にしない（監査 `attach.meta-failed`）——押し直しで同じファイルが2つになるほうが害。
- DB には載せない（ドメイン表ゼロ）。既存データの穴埋めもしない（開発中。次の入れ直しで全件が持つ）。

## メール添付の ZIP は取り込みで展開する（2026-09-17）

ユーザー:「メール添付のZIPから作った部品ページはPDFが表示されません」。

### 何が起きていたか

ZIP の中の PDF を解析すると、部品ページの配線は **ZIP そのもの**を指していました
（`data-ref="000059-bb7p"`・`bb7p` は `.zip`）。ZIP の中のファイルには本文のブロックが無く、
参照（`ページID-添付ID`）が ZIP を指すしかなかったためです。ファイル表示は拡張子で
開き方を決めるので、ZIP は「ブラウザでは開けない形式」の枝に入り、📎 の保存リンクだけを
出していました。「どの中身か」を伝える `元ファイル` タグは、ファイル表示には届きません。

### 決定——取り込みの時点で ZIP を展開する

ユーザー:「**ZIP本体がEMLの中に存在するのであれば、ZIPを展開しても良いと思います**」
「展開することによってセキュリティ問題が発生するかもしれないので、検討してください」
「現在は開発中で実運用していないので、残すべきデータはありません。設定のみ残してください。
思いっきりやってください」。

2026-09-01 の目録（`/api/zip-list`）は「展開はしない」を原則にし、取り出しは「要望が出たら
設計する」と保留していました。その要望が出たので設計しました。**展開してよい根拠は、
受信原本（.eml）が ZIP を丸ごと持っていること**——複製が増えても正本は増えません。
だから**人が手で落とした ZIP は展開しません**（原本が無い）。

- **コア** `internal/cms/zip_expand.go`——`ExpandZip`（上限つき・飛ばしたものは理由つきで返す）と
  `AttachmentExtAccepted`（PDF・画像・`attachment_extensions` のどれかが受けるか）。
- **メール取り込み**（`saveMailAttachments`）——ZIP 本体を保存したうえで中身を1つずつ添付にする。
  リンク文字は**フォルダを含む中のパス**（`↳ Q055-…図面/R310-….PDF`。フォルダ名が装置名称を
  含むため）、保存名（`download`）はファイル名だけ。`添付` タグは保存したブロックの数。
- **解析** `ext/subcon`——ZIP の枝を撤去（`entry` 引数・`loadPDFForAnalysis` の ZIP 分岐・
  `matchDXFInZip`・`元ファイル`・`対応DXFファイル`）。解析が見るのは常に自分のブロックIDを
  持つ PDF なので、部品ページの配線はその PDF を指し、ファイル表示が開きます。
  ⚠ 同日の朝に「`元ファイル` をファイル名だけにする」（`578f83f`）を入れましたが、
  タグごと無くなったので**その変更は消えました**（ユーザー:「ZIPを展開して保存する場合、
  先ほど言った元ファイルタグはPDFファイル名だけで良いというのは間違いかもしれません」）。
- **画面**——ZIP の目録から「🤖 解析」を外した（目録は読むだけ）。

### セキュリティの検討（8点）

| 面 | 蓋 |
|---|---|
| ZIP爆弾 | 1件は添付上限、件数200、合計4×添付上限。実読みは `LimitReader` で打ち切る（申告サイズは信じない） |
| Zip Slip（`../`） | **構造的に効かない**——保存名はサーバー採番のID。中の名前は本文のリンク文字にしか使わない |
| 中の ZIP | 再帰しない（1段だけ）。名前だけ本文に残す |
| シンボリックリンク | モードを見て飛ばす（中身がパス文字列の偽ファイルになるため） |
| 拡張子 | 人が落とす口と同じ許可リスト。外れたもの（`.exe`・`.html`）は ZIP の中に残す |
| 中身 | `GuardUploadContent`（PDF のマジックナンバー・画像の種別一致と EXIF 除去） |
| 暗号化・破損 | その1件を飛ばす。ZIP 全体が開けなければ展開を諦めて ZIP を残す |
| 配信 | 変わらない（未知の種別は `octet-stream`＋`attachment`＋`nosniff`）。新しい配信経路は増えていない |

### 見つかった既存の穴を2つ塞いだ

- **メール取り込みは添付を検査せずに保存していました**——拡張子の許可リストも中身の検査も
  通らず、`.exe` でも `.html` でも届いたまま `files/` へ。配信側の守りで実害は無かったが、
  人が落とす口との非対称。いまは同じ検査を通し、通らないものは**保存せず名前と理由を本文に
  残す**（受信原本が持っているので失うものは無い）。
- **和文の添付名が化けていました**——`P220-DC装置Dノック昇降　図面　20240913.zip` が
  `XkxMISEbKEIyMDI0MDkx?= 3.zip` に。原因は Go 標準の `Part.FileName()` が RFC 2047 の
  復号**前**に `filepath.Base` を掛けること（base64 の `/` で切れる）。`partFileName` で
  復号してから区切りを落とす形に。実データ5本の ZIP 名がすべて正しく出るようになった。

### 文字化けの調査

実データの ZIP 4本・82件は全件が正しく復号（Windows 製 Shift_JIS 3本・Mac/Unix 製 UTF-8 1本）。
CP932 特有の文字（①㈱№℡・髙﨑・～－￢∵・半角ｶﾅ・全角空白）も往復一致。穴は
**UTF-8 なのに UTF-8 フラグが無い名前**（古い Linux/Java 製）だけで、`DecodeZipName` に
「フラグ無しでも正しい UTF-8 で非ASCIIを含むなら UTF-8 のまま」を足した。

### 実データで確認

職場のデータを入れ直し（初期化→置き場→メール50通）、ZIP 5本・中身68件が添付になり、
展開された PDF を解析して作った部品ページ（`000062`）で `<embed src="/000052/kokl.pdf">` が
出ることを確認。E2E は `verify-preview` の期待値を1つ直して（目録に解析ボタンは出ない）
関係6本が全部通る。

## 拡張が要る置き場を、管理画面のボタンで作れるようにする（2026-09-16）

ユーザー:「**拡張プラグインが必要とするフォルダなどは、管理画面でボタンを押して
作成する仕組みにしてはどうでしょう？**」

### なぜ要ったか——「登録しないと作業面が出ず、作業面が無いと登録できない」

w-cms には**名前で機能が決まるトップ直下のページ**が4つあります。ところが
**誰が作るかがばらばら**でした:

| 置き場 | それまで誰が作っていたか |
|---|---|
| テンプレート | 誰も作らない（人が手で） |
| 通信箱 | 誰も作らない（人が手で。「意図して置く」という 09-05 の決定） |
| 取引先 | 連絡先の登録の口と整理だけ |
| 受注 | 整理のときだけ |

同日のデータ一掃で、**取引先が行き止まり**になりました。取引先ページを作るのは
`EnsurePartnerBox` で、その呼び手は登録の口と整理の2つだけ。ところが
**登録の画面（未登録の連絡先）は取引先ページの上に載っている**ので、
登録しないと作業面が出ず、作業面が無いと登録できません。手で1枚作って抜けました。

これは 2026-09-11 に踏んだ「**機械が作るページは行き止まりにしない**」の再発です
——あのときは取引先が見出しだけで作られ、**アドレス帳の作業面がどこにも存在しないまま
実メール100通が過ぎました**。

### 形

新しいフック **`cms.RegisterRequiredPage`**。各拡張が `init()` で自分の置き場を
名乗ります（名簿・設定の節・アップロードの受け口と同じ流儀）。管理画面
（`/assets/admin.html`）に「置き場」の表と「足りない置き場を作る」ボタン
（`GET`／`POST /api/admin/pages`・admin限定）。

**載っている拡張のぶんだけ出ます**——`-tags minimal` の素の w-cms ではコアの
テンプレート置き場1件だけ（実測）。

### 決めたこと

- **起動時に自動で作りません。** **人が押したことが、そのページを置く意図です**
  ——通信箱は「そこへ落とすと取り込みが走る」機能の入口なので、機械が勝手に置いて
  よいものではありません（09-05 の決定）。ボタンなら**その線を保ったまま**、
  「どこに何を作ればいいのか分からない」だけを解けます。起動のたびに黙ってページが
  増える形は、無人生成の歯止めにも反します。
- **冪等。** 既にあるものは触りません。足りないものが無ければ**ボタン自体が
  押せなくなります**（「押したのに何も起きない」を画面で防ぐ）。
- **本文は作業面込み。** 見出しだけの箱を作るとまた行き止まりになるので、
  `Body` を宣言した置き場は `<section data-type=…>` を含むことを試験で固定しました。
  ⚠ **受注だけは例外**——納期・受注残を見るビューが未実装なので、実装したら
  `Body` を足すこと。
- **宣言と現状を分けました。** `RequiredPages`（何が要るか・DBを引かない）と
  `RequiredPageStatuses`（いま在るか・引く）。別の問いです。

### 実データで確かめた

一掃直後の状態で押すと、未作成だった受注が作られ、ボタンが「足りない置き場は
ありません」に変わりました。その後 E2E を一式流してトップ直下にゴミが45枚積もった
ので、**ゴミ箱へ移してから置き場をボタンで作り直し**、通信箱＋実メール50通＋
置き場4つの **63ページ**に落ち着いています。

⚠ **`取引先` が一時2枚になりました**（E2Eが作ったものと手で作ったもの）。
「相手のページは1枚・箱も1枚」の前提が崩れるので、片付けのときに1枚へ戻しました。

### 同じ題が2枚あることを、画面が知らせる（同日・ユーザー「必要そうですね」）

**題が機能を決める**ので、同じ題のトップ直下ページが2枚あると `TopLevelPageByTitle` は
**片方しか返さず、もう片方は誰からも見えないまま残ります**。空のうちは害がありませんが、
**見えないほうに書き込むと、書いた内容がどこへ行ったのか分からなくなります**。

**防げません**（題は人が自由に付けられる）。だから**知らせます**——管理画面の「置き場」の
状態欄に `⚠ 同じ題がほかに1枚: 000108（使われるのは 000107 だけです）` と出し、
余りのページへも飛べるようにしました（中身を移してから消せるように）。

あわせて **`TopLevelPageByTitle` に `ORDER BY id` を足しました**。それまで `LIMIT 1` だけで、
**2枚あるとどちらが返るかは決まっていませんでした**——原理上は問い合わせのたびに別の
ページが「通信箱」になりえます。いまは**いちばん古いほうが勝ちます**。

番人は `TestRequiredPageStatusReportsDuplicates`（2通りの壊し方で落ちることを確認）と
`probe-required-pages`（**重複が無ければ警告を出さない**ことも見る——普通の状態で
警告が出ると、見る人が慣れて無視するようになります）。

## PDF解析の口を下請けへ寄せる——コアから業務語が消えた（2026-09-16）

ユーザー:「**PDF解析は業務に密着せざるを得ないので、ext/subcon ではないでしょうか？

プロンプトが分かれていくのは前者**です。

`filepath.Base` だけだったころ、**本文 `<id>.html` と権限サイドカー `<id>.meta.json` を

## コードのリファクタリング——重複の併合と、そこで見つかった不具合4件（2026-09-14）

ユーザー:「コードのリファクタリングをお願いします」。

**先に測りました。** 全パッケージで一度も通らない関数が154個、80行超の関数が25本、
`contacts.go` は1,217行。そのうえで**網のあるところだけ**触っています。

### 見つかった不具合4件——**元から在ったもの**

リファクタリングで生んだのではなく、重複を寄せる過程で**見えた**ものです。

**① 機械の本文書き換えが、編集ロックを取っていませんでした**（6箇所）。
`append_page.go` は「**ロックは呼ぶ側が取ります**」と宣言しているのに、
`RewriteBody`/`SetPageH1` の呼び手（連絡先の登録・「対応：不要」・整理の実行）が
誰も取っていませんでした。`RewriteBody` は**読んで・変えて・書く**ので、
誰かがエディタを開いていると**オートセーブと黙って上書きし合います**。

⚠ **`RequireEditLock` は使えません。** これらは一覧画面のボタンで、エディタを
開いていないのでトークンを持てず、付けると全部409になります。要ったのは
「**誰かが開いていたら断る**」という別の判定でした（`EditorOpen`）。

作りながら気づいた罠が2つ:

- **自分が開いていても断ります。** 手元のエディタは書き換え前の本文を持って
  いるので、そのまま保存すれば機械の変更が消えます——「自分だから安全」ではない。
- **保持者が居なくなったロックは無視します。** `tick` がロックを消すのは
  **待機者が居るときだけ**なので、ブラウザを閉じただけの人のロックは残り続けます。
  それを「開いている」と数えると、**機械の書き込みが永久に止まります**。

**② `PageChownHandler` にメソッド関門がありませんでした**——状態を変える
ハンドラで唯一の例外。GETで状態が変わらないのは `DecodeJSONBody` が空ボディで
落ちるという**偶然**に依っていました。

**③ `handler_replies` と `handler_thread` もメソッド確認が抜けていました**
——同じ16行の前置きを7箇所に写した結果です。**写した回数だけ抜ける機会があった**。

**④ 失敗の理由が画面に届いていませんでした。**

```
サーバー: 400  この拡張子は添付として受け付けていません（許可リストは…）
画面    : 400                          ← 理由が消えていた
```

`res.json()` が落ちると `catch(() => ({}))` が空を返します。しかも退避のつもりの
`|| await res.text()` は**本体を使い切ったあと**なので**永久に空文字**でした。
本体を1回だけ読む形（`readResult`）に直すと、**共通の関門が返す `text/plain`**
（「認証が必要です」等）にも効きます。

### 試験が穴を見逃していました

`TestStateChangingRoutesRejectGET` は `buildHandler()` へ流すので、
**`RequireAuth` が先に401を返し、ハンドラ自身のメソッド確認が一度も走りません**。
「401か405なら合格」だったので、確認を丸ごと外しても緑のまま——②を一度も
知らせませんでした。**ハンドラを直接呼ぶ**形に変え、外すと落ちることを確かめています。

## ファイル表示のマーカーと、セキュリティ設計書の新設（2026-09-14）

> ⚠ **この節の本文の形は翌日（2026-09-15）に変わりました**——配線が中の参照タグから
> 属性 `data-ref` へ移り、「タグの名前は書く人が決める」も無くなっています
> （理由は上の 09-15 の節）。**当時の記録としてそのまま残します。**

ユーザーの問いから始まりました:「部品ページの図面項目のHTMLに図面の埋め込みタグが

### 調べて分かったこと

**埋め込み表示できる形式を全部数えたら、答えが変わりました。**

| 形式 | 本文に直接書けるか |
|---|---|
| 画像（png/jpg/webp/gif）・**svg** | ✅ `<img>` が許可済み |
| **mp4・音声** | ✅ `<video>`・`<audio>` が許可済み |
| **pdf** | ❌ `embed`・`object`・`iframe` は**3つとも禁止** |

**仕組みが要るのは PDF だけ**でした。「PDFを出す仕組み」を作る前にこの表を見ること
——正本は [セキュリティ設計.md](セキュリティ設計.md) §3 の判定手順です。

### コアから板金の語彙を抜いた

ユーザー:「いまPDFを埋め込んでいるのは、どの拡張でしょうか？**私としてはPDFを
埋め込み表示するのはコア機能で、タグを見て表示するのが素直に思うのです**」。

**拡張ではなく、コアでした**（拡張はJSを1行も配っていません）。しかも
`<section><h2>図面</h2>` という**板金の語彙でコアが分岐**していました——
「コアが `通信箱` を名前で特別扱いすると、仕組みの側に語彙が漏れます」
（2026-09-07 の決定）と同じ漏れ方です。数えたら、コアが業務語で分岐していたのは
3か所で、うち2か所がこの関数でした。

### `section[data-type="file-view"]`——意図で名づける

ユーザー:「PDFを表示するタグが必要に思います」「**表示するという意図を伝える名前が
良いと思います。ほかに編集するという意図も出てくると思います**」。

`pdf-view` にしなかったのは、控えている「編集する」（WebDAV でローカルアプリへ渡す）が
`pdf-edit` になると**PDFを編集する意味**になってしまうためです。対象（file）と
意図（view）で名づければ、形式が増えても名前は変わりません。

```html
<section data-type="file-view">
  <dl data-type="tags"><dt>受信元</dt><dd>010272-c3p7</dd></dl>
</section>
```

本文に残るのはこれだけで、**消せば出なくなります**。タグの名前は書く人が決めます
——`参考図` でも `構成部品` でも、語彙に宣言していない名前でも効きます。

- **計算ビューではなく鏡型にしました。** 計算ビュー（`View: true`）は**中身を全消しする**ので、
  マーカーの中に書いた参照タグが画面から消えます。それでは「HTMLに在るものが見えている」
  になりません。鏡型なら人の書いたものは残り、枠をその下へ足せます。
- **拡張はPDFの出し方を知りません**——`ext/sheetmetal` は `<section data-type="file-view">` と
  書くだけです。

### サーバー側へ移して、消える不具合が直った

**編集モードを出入りすると図面が黙って消えていました。** 旧実装は `a.ref-link` に
頼っていましたが、これを作る `RenderReferenceLinks` は **`/api/load` を通りません**
（ページ描画の経路だけ）。サーバー側の鏡は両方の経路で走るので、この穴ごと塞がりました。
**公開ページ（匿名・ゼロJS）でも出るようになります。**

### ほかのページへ出す入口——「🔗 参照」

ユーザー:「PDFがほかの部品の一部で、部品ページを作らず、**ほかのページに埋め込む場合**は
どうしますか？」

**もう動いていました**（無関係なページに、宣言していないタグ名で出せます）。

[セキュリティ設計.md](セキュリティ設計.md) を新設しました。セキュリティの正本が

## 語彙の設定を1つに畳んだ——名前と型と選択肢を1件で登録する（2026-09-14）

ユーザー:「語彙の設定に名前と型をセットで登録しては？」

**1語の情報が2つの表に割れていた。** `config/settings.json` には語→型の
`type_inference` と語→選択肢の `tag_enums` があり、`在籍` と `取引` は
**選択肢だけあって型が無い**状態だった——既定の `text` 扱いで、選択肢を持つのに
`enum` ではない。一方、業務ブロックの列は最初から `VocabColumn{Label, Type, Enum}` と
セットで宣言している。**タグ側だけが割れていた**ので、そちらへ揃えた。

```json
"vocabulary": {
  "数量": { "type": "number" },
  "差出人": { "type": "email" },
  "在籍": { "type": "enum", "values": ["在籍", "休職", "出向", "退社"] }
}
```

- **`/api/tag-schema` の応答も1つに**（`type_inference` + `tag_enums` → `vocabulary`）。
  エディタ側の `typeInferenceDict` / `tagEnumDict` も `vocabWords` の1つになった。
  Go の `TypeInferenceDict()` / `TagEnumDict()` は `VocabularyDict()` に置き換えた。
- **`enum` を `text` と同じに畳むようにした**（`NormalizeValue`）。それまでの不変条件は
  「enum は正規化しない」だったが、`在籍` が text から enum に変わると**畳んだ値が
  黙って空になる**（索引の後退）。選択肢から選んだ値でも、打てば末尾の空白や全角は
  混ざる。中の空白は畳まない（畳むのは `code` だけ）。
- **検証を増やした**——選択肢を持てるのは `enum` だけ／`enum` なのに選択肢が無いのは誤り。
  **黙って無視しない**のは、書いた人が効くつもりでいるから。`text` に `values` を
  書いて色分けが出ない、という気づけない失敗を塞ぐ。

**設定を変えたので DB 再構築が要る**（`POST /api/rebuild-db`）——`enum` の畳んだ値は
再構築ではじめて入る。職場環境では実施済み（31ページ）。

## 受信を IMAP へ移し、Microsoft Graph を完全撤去（2026-09-05）

ユーザー:「MS Graphの完全撤去をお願いします。コードからも文書からも撤去します」
「**メールサーバーはレンタルに移すことが決まりました**」「移すまでの間、MS365を
使い続けます」。

**移設が決まったことで、Graph は費用に変わった。** 受信だけが Graph（HTTP API）で、
送信は既に SMTP。このまま移設すると**受信を丸ごと書き直す**ことになる——IMAP なら
借りたサーバーでもそのまま通る。パッケージも `ext/mailgraph` → `ext/mail` へ改名した。

- **IMAP4rev1 を必要な分だけ自前で書いた**（`ext/mail/imap.go`）。使うコマンドは5つ
  （AUTHENTICATE／EXAMINE／UID SEARCH／UID FETCH／LOGOUT）で、標準ライブラリだけ
  （`net`・`crypto/tls`・`bufio`）。**外部依存は増えていない**。
- **既読にしない**——`EXAMINE`（読み取り専用の SELECT）＋ `BODY.PEEK[]` の2枚重ね。
  w-cms が取り込んだせいで Outlook 側の未読が消えると、人の作業の目印が壊れる。
- **接続先は環境変数**（`WCMS_MAIL_IMAP_HOST` / `WCMS_MAIL_SMTP_HOST`・既定は M365）。
  移設で書き換わるのは接続先と認証方式だけ、という形にした。パスワード認証は
  **移設先が決まってから**足す（ホストも分からないうちに書いても確かめようがない）。
- **トークンが1つになった**——IMAP も SMTP も同じ Exchange Online なので、
  `AADSTS70011`（Graph と Exchange を1回の要求に混ぜられない）という罠ごと消えた。
- 自分のアドレスは Graph の `/me` から **`id_token` の claim** へ。IMAP も SMTP も
  「あなたは誰か」を教えてくれないため。

**踏んだバグ**: 新しい権限（IMAP）の同意が無いと `AADSTS65001` が返るが、それは
`invalid_grant` の形で来る。コードはそれを「失効した」とみなして**保存済みの
サインインをその場で消した**——コメント自身が「権限が足りないだけのときに保管を
捨てない」と書いていたのに、判定が `invalid_grant` しか見ていなかった。
**保管は自動で捨てないことにした**（古いトークンは無害で、サインインし直せば
上書きされる。理由はそのまま画面へ出す）。

## リファクタリング——メールの口を実際に使う形へ、死んだコードの撤去（2026-09-05）

`deadcode` で本体の未到達を洗い、1件ずつ「本当に死んでいるか」を確かめてから
片付けた。**確かめる価値があった**——9件のうち4件は偽陽性（テスト補助が
15箇所から使われていた）、1件は同一パッケージ内から呼ばれており
（`auth.RequireAdmin`）、コンパイラに止められて気づいた。

### メール送信の抽象が迂回されていた

`cms.SendMail` / `CurrentMailer` は**呼び手ゼロ**だった。`mail.go` の設計
（「使う側はコアに尋ねる … `CurrentMailer()`」）に反して、mailgraph が自前の
`SendAndReturnID` を使っていたため。

**理由は明白で、抽象の形が用途に合っていなかった。** `In-Reply-To` を立てるには
送信で得た Message-ID が要るのに、`Send` は `error` しか返さない。SMTP へ移った
（2026-09-03）ときに要求が変わり、口のほうが取り残された。

そこで **`Mailer.Send` と `SendMail` が Message-ID を返す形へ直し**、mailgraph の
別口（`SendAndReturnID`）を畳んで、返信ハンドラをコアの口経由に戻した。これで
「メールを送りたい側は `cms.SendMail` だけを見る」が実際に成立する——**他の拡張が
mailgraph を import せずに送れる**という、口を置いた本来の狙いが効く。

### 同じ仕事が2つあって、しかも動作が違った

`writeTag`（「名前：値」のタグを1対書く）が取り込み係と mailgraph に別々にあり、
**mailgraph だけが値を trim していた**。どちらの経路で作られたページかで値が変わる、
という形の静かな食い違い。

trim する側が正しい——索引の逆引き（`PagesByTag`）は生テキストの完全一致で引くので、
空白付きで書かれた値は空白無しの鍵では見つからない。**取り込みの重複検知
（`メッセージID`）がまさにこの経路**。コアの `WriteTag` 1つに寄せ、回帰テストを足した。

  機能は動く）。2026-09-02 に `VocabDLFields` ほかを「呼び出し元ゼロのまま残すのを
  やめ」て撤去したのと同じ扱い。必要になったら1行で戻せる
