## 発注書を送る——メール・FAX・手渡しと、行ごとの発注済みの印（2026-09-22）

ユーザー:「発注書ページで**送信方法を選んで**、メールの場合は**メールを書くボックス**が
出て送信します。FAXの場合は、FAXのページを揃えて送信します。（**FAXサーバーはまだ
つくっていないので、人間が送ったボタンを押すかもしれません**）」
「**発注書の表の一品ずつに発注済みの印**をつけます。…**メールの送信など自明な時は、
自動で印をつければ良い**し、発注書を印刷して手渡しするような場合は、**人間が発注済みの
印をつける**と思います。大事なことは、**発注の取り消しもある**ということです」。

**設計の正本は [【考察】製造という軸.md](【考察】製造という軸.md) §7k**。

### 印は行に付く

発注明細の `状態` が **`未発注／発注済／納品済／取消`** になりました
（[ext/subcon/order_status.go](../ext/subcon/order_status.go)）。

⚠ **ページのタグにしませんでした**——1枚の紙の中でも**行ごとに事情が違います**
（1品だけ取り消す・1品だけ先に納まる）。ページに1つの印では、そのどれも表せません。

⚠ **既定が `未納品` から `未発注` に変わりました。** それまでは「**紙を作る＝発注した**」
と読む形で、**出す前の紙と出した紙が見分けられません**でした。
⚠ **09-22 より前の紙の `未納品` は `発注済` と同じに読みます**——`未発注` に読むと、
**既に出した発注書が全部「まだ出していない」に化けます**。

### 読み手が変わった2か所

| 読み手 | 変わったこと | なぜ |
|---|---|---|
| 未手配の一覧の引き算（`orderedByProduct`） | ⚠ **`取消` の行を数えない** | 数えると**取り消した材料が一覧から消えたまま**になり、**誰も買わないまま納期が来ます**（エラーは出ません）。⚠ **`未発注` は数えます**——紙はできているので、二重に発注しないため |
| 最新単価（`latestMaterialPrices`） | ⚠ **`未発注` の単価を出さない** | こちらが書いただけで、**仕入先はまだ何も承諾していません**。出すと、**自分で書いた希望額を相場として見積もる**ことになります |

### 送る

発注明細の足元に **[📠 FAXで送った] [🤝 手渡した] [📧 メールで送る]** が出ます
（[ext/subcon/order_send.go](../ext/subcon/order_send.go)）。

⚠ **送信の口は作っていません。** メールは `POST /api/mail/send` が**既に在り**、
添付つきで送れて**通信箱に控えが残ります**——足したのは**下ごしらえ**（`仕入先` の題で
連絡帳を引いた**宛先の候補**・発注書番号入りの件名・`メールの署名` を入れた本文）と、
**出たあとに印を付ける口**（`/api/our-order/sent`）だけです。

⚠ **メールとFAXで「送った」の意味が違います。** メールは**送信の成功がその事実**なので
自動で印が付き、FAX・手渡しは**人が押したことがその事実**です。FAXサーバーができたら
そちらの成功に付け替えます（**画面は変わりません**）。

⚠ **いちばん困るのは「送れたのに印が付かなかった」**なので、画面はそこで黙りません
——「メールは送りました**が**、発注済みの印を付けられませんでした」と言います。
黙ると**もう一度送ってしまいます**。

### 「まだ発注していません」が消える

発注ページに残る発注書へのリンクが**鏡になりました**
（[ext/subcon/order_link_mirror.go](../ext/subcon/order_link_mirror.go)）。

⚠ **それまでは本文に焼き込んでいました。** **出したら消えなければならない文**なので、
焼き込むと**発注書を出したあとも古いまま**残ります——直すには2か所を書き換えることに
なり、片方は必ず忘れられます。いまは**本文に残すのはリンクと行数だけ**（変わらないもの）で、
**進み具合は毎回発注書ページから読み直します**（材料の参考単価と同じ形）。

⚠ **鏡の引き金は発注明細の表そのもの**です（器を本文に置く形ではありません）
——**09-21 までに作った紙にも、今日から送信の欄が付きます**。

### 取り消す——どの段からも、ただし重さは2通り

ユーザー:「**発注した後でも取り消す場合があり得ます**。この場合、電話などで材料屋に
取り消しを依頼して、**OKが出たら**取り消しボタンを押します。**発注前なら単純に
取り消します**。**発注後に材料屋から取り扱いが無いと連絡が来てキャンセルになることも
あります**」。

| 段 | 取消の意味 | 画面 |
|---|---|---|
| `未発注` | 紙はまだ出ていない——こちらの都合だけ | **確認なし** |
| `発注済` | 相手との合意が要る／先方から「取り扱いが無い」 | ⚠ **確認を出す** |
| `納品済` | 現物を返す話 | ⚠ **確認を出す** |

⚠ **紙が外へ出たあとの取消は、押しただけでは終わりません**——確かめずに押せる形にすると
「押したから片付いた」と読まれ、**材料屋には注文が残ったまま**になります。⚠ **逆に、
発注前にまで確認を出してはいけません**——**読まれない確認は、本当に要るときにも
読まれません**。

⚠ **`納品済` からも直に取り消せます。** 「2手かければ戻せる」では、現物が届いたあとの
取消が**在ることに気づけません**。

⚠ **取り消した行を紙に刷らない穴を、同日に直しました。** `readOrderDoc` は全行を読んで
いたので、**取り消した行がPDFに刷られ、合計金額にも入って**いました——**取り消した
ものの代金を請求される紙**を自分で作る形です。行そのものは本文に残します（一度は注文
しようとした事実で、**発注済みから取り消した行は相手も知っています**）。
⚠ **全部取り消したときは「全部取り消されています（n行）」と言います**——「中身のある
行がありません」だと、**書き忘れたのか取り消したのか**が読む人に分かりません。

⚠ **取り消すとその部材は未手配の一覧へ戻ります**（引き算が `取消` を数えないため）。
**確認の文にその行き先を書いてあります**——無いと、人は**もう一度どこかで発注し直す**
必要があると思います。

### 見積は同じ表に混ぜません（ユーザーの問いへの答え）

ユーザー:「今考えたのは、**見積もりの印をつければ見積も同じDBを使うことが出来ます**が、
そうするべきか否かということです」。

⚠ **筆者の答えは「同じDBを使います。同じ表は使いません」**（§7k に詳しく）。
`取消` は**同じものの状態**ですが、`見積` は**別の種類の文書**です——状態の列に混ぜると
**読み手すべてが「見積を外す」ことを覚える**ことになり、**1か所忘れた日に見積が
手配済みに化けます**。⚠ **決定的なのは相見積もり**で、1つの材料に**複数社が並ぶ**ので、
混ぜると**買ってもいない会社の値段**が「最新単価」を上書きします。
**列の宣言を共有して形式を分ける**——`orderItemColumns()` が既にその形です。

### 番人

13本（`order_send_test.go`）。⚠ **8つの変異すべてで落ちる**ことを確かめました——
取消の引き算・未発注の単価・まとめ書きの取消除外・2つの鏡の登録・**紙から取消の行を
落とすこと**・**確認を出す属性**・**納品済からの取消**。
リンクの鏡は**「まだ」と「✓」の両方**を見ます（⚠ 片方だけだと、鏡が一度も走って
いなくても通ります）。⚠ **PDFの番人は合計金額まで見ます**——行が消えても合計に
残っていたら、紙の上では**取り消したものの代金を請求されます**。

## 発注部材表と未手配の一覧を、往復できるようにした（2026-09-22・3段目）

ユーザー:「**発注部材表から未手配の一覧へ戻す方法がありません**」

⚠ **調べたら、それ以前の穴が出ました**——**発注部材表に入れても、未手配の一覧から
消えていませんでした**（実データで確認）。ユーザーの構想（§7d）の「**すると元の表からは
それらの行が消えます**」を、1段目の実装が落としていたのです。

⚠ **これは実害のある穴です**——**同じものを2回発注しかねません。**

### 入れたら消える

未手配の一覧の引き算に、**発注部材表に入っている数**を足しました（`draftedQty`）。

```
残要手配数 = 必要数 − 発注済み（発注書）− **いま発注部材表に入っている分**
```

⚠ **鍵は `orderedByProduct` と同じ**（`procKey`＝加工製品ページ × 材料の3つ組／品名）
——発注書と発注部材表で別の束ね方をすると、**引き算が合いません**。
⚠ **弊社品番の無い行**（消耗品など）は引きません——**そもそも一覧に出ないもの**なので。

### 戻す＝外す

各行の末尾に **`↩ 戻す`** が出ます（鏡）。押すと `/api/our-order/draft/remove` が
**その行を本文から外し**、一覧に戻ります。

⚠ **戻す先へ何かを書く必要はありません**——一覧は**毎回計算される鏡**なので、
発注部材表から消えれば**自動的に戻ってきます**。
⚠ **閲覧モードから押せることが肝**です。本文の表なのでエディタでも消せますが、
**一覧を見ながら出し入れする**のに、いちいち編集モードへ入るのは道が遠すぎます。

### 実データで往復

| | 未手配 |
|---|---|
| はじめ | **4行** |
| 1行を発注部材表へ入れる | **3行**（減った） |
| `↩ 戻す` を押す | **4行**（戻った） |

### ⚠ 「1枚目へ足す」が効いていませんでした——画面が値を送っていなかった

ユーザー:「**一枚目の発注部材表に入れるを選択しても別の部材表が出来ます**」

⚠ **サーバーの口は正しく、画面が `into` を送っていませんでした。** 結果を表示する行
（`d.into ? …`）だけ足して、**送信側を書き損ねていた**のです。

⚠ **これは気づきにくい壊れ方です**——Go の試験は全部緑、`/api/our-order/draft` を直に
叩く確認も通っていました。**画面が値を送っているかは、画面からしか確かめられません。**

だから **E2E を1本足しました**（`e2e/verify-order-draft.js`）——ブラウザで
「新しく作る」「1枚目へ足す」「全部戻す」を実際に押して、**表の枚数**を見ます。

```
✓ 新しく作る → 表が1枚増えた
✓ 1枚目へ足す → 表は増えない（行が足される）   ← ここが壊れていた
✓ 全部戻す → 空の表は残らない（0 枚）
```

⚠ **同じ形の欠落が他に無いかも照合しました**——発注書を作る口が送る8つの鍵
（`supplier`・`order_at`・`due`・`note`・`signer`・`lines`・`draft_page`・`draft_index`）は
サーバー側と**全部一致**していました。

### ⚠ 最後の1行を外したら、表ごと消します

ユーザー:「**戻しても部材表から消えません**」

⚠ **行は消えていましたが、見出しだけの表が残っていました。** 実データで確かめたところ
**空の発注部材表が3枚**溜まっていて、しかも**「何枚目へ足すか」の選択肢に並ぶ**ので
**押し間違いの元**になります。

いまは**最後の1行を外すと、表ごと消えます**（実データで確認: 2行 → 1行 → **0枚**）。
⚠ **他の表は消しません**（同時に進めていた別の業者ぶんが失われるので）。
⚠ **空の表を作る道は残します**（何も選ばずに「発注部材表へ入れる」）——**人が意図して
作った空の表**と、**外して空になった表**は別のことです。

⚠ **原因を追うのに、ブラウザで実際に押しました**（Playwright）。サーバーの口も、
画面の配線も**正しく動いていました**——**残っていたのは「表の骨」だけ**で、
**API を叩くだけの確認では気づけない**ものでした。

### 番人（3つの変異で落ちることを確かめました）

`order_draft_test.go` に1本（計8本）、`unordered_test.go` に1本（計6本）。
当てた変異: 行番号が1つずれる／引き算をしない／鍵をずらす（発注書と別の束ね方）。

⚠ **最初に当てた変異が空振りしました**——`if i == 0 { i++; continue }` を
`if false { i++; continue }` にしても、**`i++` が残るので結果が同じ**でした。
**変異は「振る舞いを変えたか」まで見ること**（8通り目の空振りの形）。


## 発注部材表の3点を直した——ボタンの位置・複数枚・リンク化（2026-09-22・2段目）

ユーザーの訂正3点を実装しました。⚠ **3つとも私の設計が違っていました。**

### ① 「発注書を作る」は発注部材表の下へ

> 「**発注部材表から発注書を作るので「発注書を作る」ボタンは発注部材表の下にあるはずです**」

⚠ **最初の実装は、未発注の表のフォームに両方のボタンを置いていました**——「表作成」と
「発注書作成」が並んでいて、**どちらの表から発注書ができるのか**が画面から読み取れません
でした。**ボタンは、その相手の隣にあるべき**です。

いまは**鏡**（`order_draft_mirror.go`）が、**表ごとに**足元へ欄を出します——仕入先・
差出人・発注日・納期・備考と「発注書を作る」。⚠ **表が2枚あれば2つ**出ます。
⚠ **仕入先と差出人もここで決めます**——**1枚＝1社**が決まるのは、表を作り終えたときだから。

### ② 発注部材表は何枚あってもよい

> 「**発注部材表は複数できて良いはずで、新規に作るのか、どれかに足すのか聞くべきです**」

⚠ **最初の実装は2枚目を 409 で断っていました。実務が回りません**——**1枚＝1社**なので、
**業者ごとに同時に進める**のが普通の形です。

いまは未発注の表に**「入れる先」**が出ます（`新しく作る` ／ `1枚目へ足す` ／ …）。
⚠ **既定は「新しく作る」**——**黙って既存の表へ混ぜるほうが危ない**（別の業者の行が
1つの紙に混ざり、**紙にしてから気づきます**）。

### ③ 発注書ができたら、発注部材表はリンクに化ける

> 「**発注書ページが出来て、実際に発注するまで発注ページに発注書ページへのリンクが
> 残れば良いのでは？**」

```
📄 発注書 000145　みなと商店（2行・まだ発注していません）
```

⚠ **表は消してリンクを残します**——中身は発注書ページへ移ったので、**残すと古い写しに
なり、次の発注のときに混ざります**。⚠ **他の表は消しません**（同時に進めていた別の
業者ぶんの作業が丸ごと失われるので）。
⚠ **リンク化に失敗しても発注書は取り消しません**——**紙のほうが重い**ので、
「表が残ってしまった」は人が消せば済みます。理由を `draft_note` に添えるだけです。

### ⚠ 実データで踏んだ穴——0件のときフォームごと消えていました

未手配が0件のとき、一覧は「ありません」の1文で**早期に戻っていました**。
⚠ **それでは「何も選ばずに空の表から始める」道が、画面から消えます**——
**加工製品ページに無い部材（消耗品・治具）だけを買うときに、いちばん要る道**です。
**0件のときこそフォームを出します。**

| **2枚目も作る**（空） | ✓ **409 になりません** |

| 足元の「発注書を作る」 | **2個**（表2枚ぶん）。未発注の表には**ありません** |
| 1枚目から発注書を作る | `000145` ができ、**1枚目だけが**リンクに化けました（2枚目はそのまま） |

### 番人（3つの変異すべてで落ちることを確かめました）

`order_draft_test.go` に2本追加（計7本）。当てた変異: 足す先を常に1枚目にする／
無い枚数でも足す／置き換えで他の表も消す。

## 発注部材表——未発注の表と発注書のあいだに、人が足し引きする表（2026-09-22・1段目）

ユーザーが流れを具体化しました:

> 「候補の表は**発注ページの未発注の表の下**で良いのでは？未発注の表のチェックボックスを
> クリックして（**必要なければ何もクリックしなくても**）**表作成ボタン**をクリックすると
> **発注部材表**が開き、そこを編集して**発注書作成**をクリックすると、**発注書ページ**が
> でき、発注書ページで**送信方法**を選んでクリックすると**メール編集ボックス**が開き…」

```
発注（ページ）
  ├ 未発注の表     … 鏡（毎回計算・読み取り専用）
  │    ↓ チェック（何もクリックしなくてもよい）→ [発注部材表を作る]
  ├ 発注部材表     … **本文の表**（人が足し引きする）        ← 本日ここまで
  │    ↓ 編集して → [発注書作成]                             ← 次
  └ 2026年／09月／発注 みなと商店
         ↓ 送信方法を選ぶ → メール編集ボックス               ← その次
```

### ⚠ なぜ本文に書いてよいのか

**人が足し引きした結果は「推測」ではなく「事実」だから**です。
「**今回は**自社加工する」「この消耗品も一緒に頼む」は**機械には導けません**——だから
「印と事実を二重に持たない」（[【考察】製造という軸.md](【考察】製造という軸.md) §9）と
ぶつかりません。**未手配の一覧（鏡）は候補、発注部材表は人が決めた結果**です。

### 決めたこと

- **形式は `order-draft`（発注部材表）**。⚠ **列は発注明細と同じ12列**
  （`orderItemColumns` を共有）——**そのまま発注書へ移せる**ようにするため。違うのは
  「まだ紙になっていない」ことだけなので、形を変える理由がありません。
  ⚠ 片方だけ列を足すと**移すときに落ち、しかもエラーが出ません**（索引は見出しの
  表示文字で引くので黙ってずれる）。番人は `TestOrderDraftSharesColumnsWithOrderItems`。
- ⚠ **行が0でも作ります**（ユーザー:「必要なければ何もクリックしなくても」）——

  ときの道です。空のときは**書き足す取っ掛かりとして空の行を1つ**置きます。

- ⚠ **状態（`未納品`）は書きません**——まだ発注していないのに書くと、**もう注文した
  ように見えます**。紙のほうには書きます。
- ⚠ **`品名` を落とす規則は共有します**（`itemNameOf`）——同じ規則を2か所に書くと、
  **片方だけ直した日に、表と紙で品名が違います**。

未手配の配線（`wireUnorderedOrder`）は**トップレベルの IIFE** に居て、
`currentPageId` は別のスコープです。**サーバーが描いた属性から取ります**
（`data-unorder-page`）——受注残表の書き戻しが `data-order-page` でやっているのと同じ手です。

- **[発注書作成]**——発注部材表を読んで発注書ページを作る。いまの `/api/our-order/new` は

## 発注書の検算——数どうしの辻褄で OCR を確かめる（2026-09-20 夜）

ユーザー:「顧客の発注書に数量と単価があって、金額や総額もあるなら、**検算が出来ると
思います**」。

**これは、外の正解なしに読み取りを確かめられる、たぶん唯一の手段です。** 他の検査は
すべて「人が紙と見比べる」に帰着します——原本の写しを残したのも（同日・下の節）
「人が見比べられるように」でした。**数どうしの辻褄なら、機械が自分で見られます。**

### 検算は3本あり、捕まえるものが違う

| 検算 | 式 | これだけが捕まえるもの |
|---|---|---|
| 行 | 数量 × 単価 = 金額 | その行の数の読み違い |
| 小計 | Σ金額 = **小計** | ⚠ **行の落丁** |
| 合計 | 小計 + 消費税 = 合計 | 小計・消費税そのものの読み違い |

⚠ **行の検算だけでは落丁に気づけません。** 1行まるごと落ちても、**残った行は互いに
辻褄が合ったまま**だからです。小計との突き合わせが唯一の手段になります。

⚠ **3本目に税率を使いません。** `小計 × 税率 = 消費税` と書くと 10%／8%（軽減）を
当てにいくことになりますが、`小計 + 消費税 = 合計` なら**税率を知らずに済みます**。
軽減税率の発注書で ⚠ が出ない、というのがこの式を選んだ理由です。

### ⚠ 検算を Gemini にやらせない

**この判断がいちばん大事です。** 自分の読みを自分で検算させると、LLM は**数字を合う
ように書き直します**——誤りが消えるのではなく、**見えなくなります**。検算の意味が
そこで失われる。

- Gemini に頼むのは `subtotal`・`tax`・`total` を**書かれているまま**返すことだけで、
  プロンプトに「**足し算・掛け算をして求めないでください**」と明示しました。
- 掛け算と足し算は Go（[ext/subcon/checksum.go](../ext/subcon/checksum.go)）でやります。

### 小計・消費税・合計金額はページのタグ

ユーザー:「変形した表になっていて、**表の右下の方に、小計、消費税、合計金額が
飛び出しています**」。書面のヘッダ（表の外）にある値なので、納期と同じく**ページの
タグ**にしました（`小計`・`消費税`・`合計金額`・いずれも `number`）。受注額として
それ自体見たい数でもあります。⚠ **`config/settings.json` に3語足したので DB再構築が要ります。**

⚠ **飛び出しているので、Gemini はそれらを明細の行としても返してきます。** そのまま
足すと**小計を二重に数え**、必ず ⚠ が出ます（狼少年になる）。**数量・単価・金額が
3つとも揃う行だけ**を足すことで自然に外れますが、**外した行数は黙らずに知らせます**。

### 見せ方は鏡型——弊社の明細の足元に

- ⚠ **本文には書きません。** 焼き込むと、人が数字を直しても ⚠ が残り、逆に直した結果が
  間違っていても ⚠ が出ません。**鏡型なら毎回数え直すので、直せば消えます。**
  そもそも `class` はサニタイズで落ちるので、印は鏡でしか付けられません
  （`ref-missing` の薄赤・`row-obsolete` と同じ作り）。
- ⚠ **引き金は弊社の受注明細で、原本ではありません。** 原本は `<details>` で畳まれて
  いるので、そちらに出すと**開くまで読まれない警告**になります。
- ⚠ **表の中へ `<p>`・`<div>` を足すと、HTMLパーサが表の外（手前）へ追い出します。**
  足元の行は **`<tfoot>` の `<tr>`** として足します。
- ⚠ **合っているときも黙りません。** 黙ると「検算して合った」と「そもそも検算して
  いない」が見分けられません（E2E が前提の無い項目を「飛ばす」と言うのと同じ理由）。
  ただし文面は控えめに——**辻褄が合うことは、正しいことを意味しません**。揃えて
  読み違えることはありえます。**合わないときに疑える、それだけの道具です。**

### 当て推量をしない

⚠ 見出しから `数量`・`単価`・`金額` の列が見つからなければ**検算しません**。当て推量で
別の列を掛け算すると、**正しい発注書に ⚠ を出します**——狼少年になると本物の ⚠ も
読まれなくなります。⚠ **部分一致も採りません**（`合計金額` が `金額` に当たって
小計を明細として足してしまう）。**様式ページ**（`取引先／社名／発注書の様式`）が
入ったら、そちらが見出しの対応の正本になります。

**変異試験12件**（検算6・鏡6）で、守りを外すとすべて番人が落ちることを確認しました。

## 原本が読めないだけで解析を丸ごと落としていた（2026-09-20 夜）

ユーザー:「解析に失敗したと出ます」。原因は `source_table` を**構造に直接当てて

## WebDAV の Ctrl+S が届かなかった——PROPPATCH と「開いただけで消える」（2026-09-18）

ユーザー:「加工製品のページには、加工データを作るためのCADファイルが必要です。
このファイルそのものは、テンプレートのコピーで良いのですが、加工屋に送る時には
適切なファイル名が必要です」「これをw-cmsでもできるようにしたい。**しかも自動で**」。

いま RootPro CAD で図面を展開し（立体の板金形状をレーザー加工用の平面へ）、その
`.rpcd` をワンノートの加工製品ページに貼り、**ファイル名を手で図面名称に打ち替えて**
いる。その手作業を無くしたい、という要望。

**実装の前に、輪が閉じるかを実物で確かめた**——ここが今日の本体になった。

### 実データで測ったこと

的は `000047`（`取引先／南北スポーツ機械／現行／設置アームマシン／
保持ブラケット2`・整理済み・`図面名称` タグつき）。いただいた空の雛形
（`Scratch.rpcd`・**OLE複合ドキュメント**・27,136バイト）を
`展開　保持ブラケット2.rpcd` の名前で添付し、`Z:` から開いた。

1. **開けた。** WebDAV 越しに読んだバイトは原本と完全一致（`3d247880…`）。
2. **保存できなかった。**「DocFileが壊れています（0x80030109）」→「ファイルの保存に
   失敗しました」。⚠ **ファイルは壊れていない**——壊れていたのは保存の経路。
3. **ログに犯人が写っていた**: `GET` → `LOCK` → **`PROPPATCH`** で終わり、
   **`PUT` が1度も来ていない**。`PROPPATCH` は塞いでいた5つの1つだった。

### 直したこと（2つで1組・片方だけでは壊れる）

- **`davWriteFile.Close` は、一時ファイルが空なら差し替えない。** `x/net/webdav` は
  PROPPATCH でも `O_RDWR` で開くので、この守りが無いと**1バイトも書かないまま添付が
  0バイトになる**。⚠ **これは今日まで空いていた穴**で、変異試験で実際に踏んだ
  （`10 バイト → 0 バイト`）。
- **`PROPPATCH` を `davBlockedMethods` から外した。** 中身を変えない要求で、消す・
  動かすと一緒に括ったのが行き過ぎだった。`DELETE` `MOVE` `COPY` `MKCOL` はそのまま。

### 結果——輪は閉じた

`PUT` が届き、前の中身が版に残り、OLE の容器も壊れず、**引いた線が往復した**
（ユーザー:「線は引かれています」）。目録は届いたときの名前を保ち、`source` が `dav` に。

### ⚠ ただし Ctrl+S では届かない

```
22:30:47  PROPPATCH   ← Ctrl+S を押した
    （75秒、何も届かない）
22:32:01  PUT         ← RootPro CAD を閉じた
```

Windows の WebDAV（`WebClient` サービス）が**手元に溜めて、最後のハンドルが閉じたときに
書き戻す**ため。**サーバー側では直せない。** ユーザー:「アプリを閉じないと書き込みされ
ないのは困った挙動ですね」。打てる手は2つで、どちらも未実装:

- **①「いま開かれています」を画面に出す**（小）。⚠ **w-cms は既に知っている**——
  `LOCK`／`UNLOCK` が届いている。`webdav.NewMemLS()` を薄く包んで道を控えるだけ。
  挙動は直らないが、**嘘をつかれなくなる**（この日、作者も筆者も1度騙された）。
- **② 常駐ヘルパー（`w-cms://`）**（本命・[【考察】添付をローカルアプリで編集する.md](【考察】添付をローカルアプリで編集する.md) の案B）。
  ⚠ **位置づけが変わった**——09-07 は「Aが駄目だったときの控え」だったが、いまや
  **Ctrl+S を通す唯一の道**。加えて `Z:` の割り当てが要らなくなり、**社外公開では
  WebDAV を出さない決定**があるので、外から開ける道もこれだけになる。

### 配布の検討（Microsoft Store）

ユーザー:「Microsoftstoreでヘルパーを配布するのはどうですか？」。
**2025-09-10 から個人開発者の登録は無料**（筆者が挙げた `$19/$99` は古い情報だった）。

**決まった**:

  リンク文字は**フォルダを含む中のパス**（`↳ Q055-…図面/R310-….PDF`。フォルダ名が装置名称を
  含むため）、保存名（`download`）はファイル名だけ。`添付` タグは保存したブロックの数。
- **解析** `ext/subcon`——ZIP の枝を撤去（`entry` 引数・`loadPDFForAnalysis` の ZIP 分岐・
  `matchDXFInZip`・`元ファイル`・`対応DXFファイル`）。解析が見るのは常に自分のブロックIDを
  持つ PDF なので、部品ページの配線はその PDF を指し、ファイル表示が開きます。
  ⚠ 同日の朝に「`元ファイル` をファイル名だけにする」（`a74b1f7`）を入れましたが、
  タグごと無くなったので**その変更は消えました**（ユーザー:「ZIPを展開して保存する場合、
  先ほど言った元ファイルタグはPDFファイル名だけで良いというのは間違いかもしれません」）。
- **画面**——ZIP の目録から「🤖 解析」を外した（目録は読むだけ）。

### セキュリティの検討（8点）

| 面 | 蓋 |
|---|---|
| ZIP爆弾 | 1件は添付上限、件数200、合計4×添付上限。実読みは `LimitReader` で打ち切る（申告サイズは信じない） |
| Zip Slip（`../`） | **構造的に効かない**——保存名はサーバー採番のID。中の名前は本文のリンク文字にしか使わない |
| 中の ZIP | 再帰しない（1段だけ）。名前だけ本文に残す |
| シンボリックリンク | モードを見て飛ばす（中身がパス文字列の偽ファイルになるため） |
| 拡張子 | 人が落とす口と同じ許可リスト。外れたもの（`.exe`・`.html`）は ZIP の中に残す |
| 中身 | `GuardUploadContent`（PDF のマジックナンバー・画像の種別一致と EXIF 除去） |
| 暗号化・破損 | その1件を飛ばす。ZIP 全体が開けなければ展開を諦めて ZIP を残す |
| 配信 | 変わらない（未知の種別は `octet-stream`＋`attachment`＋`nosniff`）。新しい配信経路は増えていない |

### 見つかった既存の穴を2つ塞いだ

- **メール取り込みは添付を検査せずに保存していました**——拡張子の許可リストも中身の検査も
  通らず、`.exe` でも `.html` でも届いたまま `files/` へ。配信側の守りで実害は無かったが、
  人が落とす口との非対称。いまは同じ検査を通し、通らないものは**保存せず名前と理由を本文に
  残す**（受信原本が持っているので失うものは無い）。
- **和文の添付名が化けていました**——`P220-DC装置Dノック昇降　図面　20240913.zip` が
  `XkxMISEbKEIyMDI0MDkx?= 3.zip` に。原因は Go 標準の `Part.FileName()` が RFC 2047 の
  復号**前**に `filepath.Base` を掛けること（base64 の `/` で切れる）。`partFileName` で
  復号してから区切りを落とす形に。実データ5本の ZIP 名がすべて正しく出るようになった。

### 文字化けの調査

実データの ZIP 4本・82件は全件が正しく復号（Windows 製 Shift_JIS 3本・Mac/Unix 製 UTF-8 1本）。
CP932 特有の文字（①㈱№℡・髙﨑・～－￢∵・半角ｶﾅ・全角空白）も往復一致。穴は
**UTF-8 なのに UTF-8 フラグが無い名前**（古い Linux/Java 製）だけで、`DecodeZipName` に
「フラグ無しでも正しい UTF-8 で非ASCIIを含むなら UTF-8 のまま」を足した。

### 実データで確認

職場のデータを入れ直し（初期化→置き場→メール50通）、ZIP 5本・中身68件が添付になり、
展開された PDF を解析して作った部品ページ（`000062`）で `<embed src="/000052/kokl.pdf">` が
出ることを確認。E2E は `verify-preview` の期待値を1つ直して（目録に解析ボタンは出ない）
関係6本が全部通る。

## 拡張が要る置き場を、管理画面のボタンで作れるようにする（2026-09-16）

ユーザー:「**拡張プラグインが必要とするフォルダなどは、管理画面でボタンを押して
作成する仕組みにしてはどうでしょう？**」

### なぜ要ったか——「登録しないと作業面が出ず、作業面が無いと登録できない」

w-cms には**名前で機能が決まるトップ直下のページ**が4つあります。ところが
**誰が作るかがばらばら**でした:

| 置き場 | それまで誰が作っていたか |
|---|---|
| テンプレート | 誰も作らない（人が手で） |
| 通信箱 | 誰も作らない（人が手で。「意図して置く」という 09-05 の決定） |
| 取引先 | 連絡先の登録の口と整理だけ |
| 受注 | 整理のときだけ |

同日のデータ一掃で、**取引先が行き止まり**になりました。取引先ページを作るのは
`EnsurePartnerBox` で、その呼び手は登録の口と整理の2つだけ。ところが
**登録の画面（未登録の連絡先）は取引先ページの上に載っている**ので、
登録しないと作業面が出ず、作業面が無いと登録できません。手で1枚作って抜けました。

これは 2026-09-11 に踏んだ「**機械が作るページは行き止まりにしない**」の再発です
——あのときは取引先が見出しだけで作られ、**アドレス帳の作業面がどこにも存在しないまま
実メール100通が過ぎました**。

### 形

新しいフック **`cms.RegisterRequiredPage`**。各拡張が `init()` で自分の置き場を
名乗ります（名簿・設定の節・アップロードの受け口と同じ流儀）。管理画面
（`/assets/admin.html`）に「置き場」の表と「足りない置き場を作る」ボタン
（`GET`／`POST /api/admin/pages`・admin限定）。

**載っている拡張のぶんだけ出ます**——`-tags minimal` の素の w-cms ではコアの
テンプレート置き場1件だけ（実測）。

### 決めたこと

- **起動時に自動で作りません。** **人が押したことが、そのページを置く意図です**
  ——通信箱は「そこへ落とすと取り込みが走る」機能の入口なので、機械が勝手に置いて
  よいものではありません（09-05 の決定）。ボタンなら**その線を保ったまま**、
  「どこに何を作ればいいのか分からない」だけを解けます。起動のたびに黙ってページが
  増える形は、無人生成の歯止めにも反します。
- **冪等。** 既にあるものは触りません。足りないものが無ければ**ボタン自体が
  押せなくなります**（「押したのに何も起きない」を画面で防ぐ）。
- **本文は作業面込み。** 見出しだけの箱を作るとまた行き止まりになるので、
  `Body` を宣言した置き場は `<section data-type=…>` を含むことを試験で固定しました。
  ⚠ **受注だけは例外**——納期・受注残を見るビューが未実装なので、実装したら
  `Body` を足すこと。
- **宣言と現状を分けました。** `RequiredPages`（何が要るか・DBを引かない）と
  `RequiredPageStatuses`（いま在るか・引く）。別の問いです。

### 実データで確かめた

一掃直後の状態で押すと、未作成だった受注が作られ、ボタンが「足りない置き場は
ありません」に変わりました。その後 E2E を一式流してトップ直下にゴミが45枚積もった
ので、**ゴミ箱へ移してから置き場をボタンで作り直し**、通信箱＋実メール50通＋
置き場4つの **63ページ**に落ち着いています。

⚠ **`取引先` が一時2枚になりました**（E2Eが作ったものと手で作ったもの）。
「相手のページは1枚・箱も1枚」の前提が崩れるので、片付けのときに1枚へ戻しました。

### 同じ題が2枚あることを、画面が知らせる（同日・ユーザー「必要そうですね」）

**題が機能を決める**ので、同じ題のトップ直下ページが2枚あると `TopLevelPageByTitle` は
**片方しか返さず、もう片方は誰からも見えないまま残ります**。空のうちは害がありませんが、
**見えないほうに書き込むと、書いた内容がどこへ行ったのか分からなくなります**。

**防げません**（題は人が自由に付けられる）。だから**知らせます**——管理画面の「置き場」の
状態欄に `⚠ 同じ題がほかに1枚: 000108（使われるのは 000107 だけです）` と出し、
余りのページへも飛べるようにしました（中身を移してから消せるように）。

あわせて **`TopLevelPageByTitle` に `ORDER BY id` を足しました**。それまで `LIMIT 1` だけで、
**2枚あるとどちらが返るかは決まっていませんでした**——原理上は問い合わせのたびに別の
ページが「通信箱」になりえます。いまは**いちばん古いほうが勝ちます**。

番人は `TestRequiredPageStatusReportsDuplicates`（2通りの壊し方で落ちることを確認）と
`probe-required-pages`（**重複が無ければ警告を出さない**ことも見る——普通の状態で
警告が出ると、見る人が慣れて無視するようになります）。

## 拡張どうしを結んでいた生の文字列を定数へ通す（2026-09-16）

### 通した先

| どこ | 何 |
|---|---|
| アドレス帳 → 通信 | `addressFields` が `comm.FromTag`・`ToTag`・`CcTag`・`ReplyToTag` を使う（`ext/comm/contacts` が `ext/comm` を import する初めの1本） |

| 通信の中 | 読み手の SQL 5か所（未処理一覧・返信の一覧・やりとりの前後）。**読む側も書く側と同じ定数を通る** |
| 下請けの中 | `受信元` を `SourceRefTag` へ（書き手2か所と、合流の重複検知の正規表現） |

### 新しく作った定数

- **`comm.ChannelMail` / `ChannelFax` / `ChannelPhone` / `ChannelMemo`**（チャネルの値）。

- **`comm.SentOutAtTag`（`発信日時`）**。`送信日時`（`SentAtTag`）とは**別の欄**です

定数へ通す作業は**取り違えてもコンパイルが通ります**。そこで、置き換えた先をわざと壊して
試験が気づくか確かめました——**2か所は気づきませんでした**。

### ファイル表示の配線を属性へ出す（`c7efe53`）

ユーザー:「embedタグと同じようにリソースを指定して表示するだけのタグにしてはどうでしょう」
「PDFに限らず表示できるほうが良い」。前日に作ったばかりの形を、1日で作り直しました。

```html
<!-- 旧（09-14） -->
<section data-type="file-view"><dl data-type="tags"><dt>受信元</dt><dd>010272-c3p7</dd></dl></section>
<!-- 新（09-15） -->
<section data-type="file-view" data-ref="010272-c3p7"></section>
```

やめた理由は3つです:

- **同じ値が2つの意味で並ぶ。** 解析が書く本文では、図面ブロックの `受信元`（＝どのメールで
  届いたかの記録＝実データ）と、表示先を指す配線とが、同じ `010272-c3p7` として2行出ていました。
- **タグの名前に意味が無い。** `受信元` でも `あ` でも同じに動くので、読む人はどちらが配線か
  見分けられません（前日は「タグの名前は書く人が決める」を利点として書いていました）。
- **当てずっぽう。**「最初の `dl` の最初の参照」なので、2つ書くと2つ目が黙って無視されます。

**URL（`data-src="/010272/c3p7.pdf"`）にはしません。** `<embed src>` に一番近く、サニタイザの
許可も検査も既にありますが、**URLは派生**です——ページIDと添付IDと拡張子から組めるもので、
配信のアドレスは一度変わっています（`/data/` → きれいなURL・08-31）。**本文は正本**なので、
次に変えた日に全部が古くなる書き方は選びません。

**安全の性質は変わりません。** 書く人が選べるのはページIDと添付IDだけで、URLは機械が組み、
配信は `page.CanView` を通ります（[セキュリティ設計.md](セキュリティ設計.md) §4）。
サニタイザは `data-ref` を **`section` 限定**で通し、値は検査しません——URLではないので
`safeEmbedURL` を通す意味がないためです（検査で守っているのではない、という §4 の要点がここでも効きます）。

**PDF以外も開くようにしました。** ブラウザが素で描ける形式（画像・動画・音声。~~テキスト~~は
同日のコードレビューで**描けない**と分かり外した）は
その場に開き、描けないもの（DXF・Excel・ZIP）は**開く口を出します**——前は「見つかりません」と
言っていましたが、ファイルは在るのですから嘘でした。

**代償は「配線が見えなくなる」ことです。** 空の `section` はクリックもキャレット移動も

### 見つかった不具合4件——**元から在ったもの**

リファクタリングで生んだのではなく、重複を寄せる過程で**見えた**ものです。

**① 機械の本文書き換えが、編集ロックを取っていませんでした**（6箇所）。
`append_page.go` は「**ロックは呼ぶ側が取ります**」と宣言しているのに、
`RewriteBody`/`SetPageH1` の呼び手（連絡先の登録・「対応：不要」・整理の実行）が
誰も取っていませんでした。`RewriteBody` は**読んで・変えて・書く**ので、
誰かがエディタを開いていると**オートセーブと黙って上書きし合います**。

⚠ **`RequireEditLock` は使えません。** これらは一覧画面のボタンで、エディタを
開いていないのでトークンを持てず、付けると全部409になります。要ったのは
「**誰かが開いていたら断る**」という別の判定でした（`EditorOpen`）。

作りながら気づいた罠が2つ:

- **自分が開いていても断ります。** 手元のエディタは書き換え前の本文を持って
  いるので、そのまま保存すれば機械の変更が消えます——「自分だから安全」ではない。
- **保持者が居なくなったロックは無視します。** `tick` がロックを消すのは
  **待機者が居るときだけ**なので、ブラウザを閉じただけの人のロックは残り続けます。
  それを「開いている」と数えると、**機械の書き込みが永久に止まります**。

**② `PageChownHandler` にメソッド関門がありませんでした**——状態を変える
ハンドラで唯一の例外。GETで状態が変わらないのは `DecodeJSONBody` が空ボディで
落ちるという**偶然**に依っていました。

**③ `handler_replies` と `handler_thread` もメソッド確認が抜けていました**
——同じ16行の前置きを7箇所に写した結果です。**写した回数だけ抜ける機会があった**。

**④ 失敗の理由が画面に届いていませんでした。**

```
サーバー: 400  この拡張子は添付として受け付けていません（許可リストは…）

```

`res.json()` が落ちると `catch(() => ({}))` が空を返します。しかも退避のつもりの
`|| await res.text()` は**本体を使い切ったあと**なので**永久に空文字**でした。
本体を1回だけ読む形（`readResult`）に直すと、**共通の関門が返す `text/plain`**
（「認証が必要です」等）にも効きます。

ユーザー:「PDFを表示するタグが必要に思います」「**表示するという意図を伝える名前が
良いと思います。ほかに編集するという意図も出てくると思います**」。

意図（view）で名づければ、形式が増えても名前は変わりません。

```html
<section data-type="file-view">
  <dl data-type="tags"><dt>受信元</dt><dd>010272-c3p7</dd></dl>
</section>
```

  マーカーの中に書いた参照タグが画面から消えます。それでは「HTMLに在るものが見えている」
  になりません。鏡型なら人の書いたものは残り、枠をその下へ足せます。
- **拡張はPDFの出し方を知りません**——`ext/sheetmetal` は `<section data-type="file-view">` と
  書くだけです。

## 語彙の設定を1つに畳んだ——名前と型と選択肢を1件で登録する（2026-09-14）

ユーザー:「語彙の設定に名前と型をセットで登録しては？」

**1語の情報が2つの表に割れていた。** `config/settings.json` には語→型の
`type_inference` と語→選択肢の `tag_enums` があり、`在籍` と `取引` は
**選択肢だけあって型が無い**状態だった——既定の `text` 扱いで、選択肢を持つのに
`enum` ではない。一方、業務ブロックの列は最初から `VocabColumn{Label, Type, Enum}` と
セットで宣言している。**タグ側だけが割れていた**ので、そちらへ揃えた。

```json
"vocabulary": {
  "数量": { "type": "number" },
  "差出人": { "type": "email" },
  "在籍": { "type": "enum", "values": ["在籍", "休職", "出向", "退社"] }
}
```

- **`/api/tag-schema` の応答も1つに**（`type_inference` + `tag_enums` → `vocabulary`）。
  エディタ側の `typeInferenceDict` / `tagEnumDict` も `vocabWords` の1つになった。
  Go の `TypeInferenceDict()` / `TagEnumDict()` は `VocabularyDict()` に置き換えた。
- **`enum` を `text` と同じに畳むようにした**（`NormalizeValue`）。それまでの不変条件は
  「enum は正規化しない」だったが、`在籍` が text から enum に変わると**畳んだ値が
  黙って空になる**（索引の後退）。選択肢から選んだ値でも、打てば末尾の空白や全角は
  混ざる。中の空白は畳まない（畳むのは `code` だけ）。
- **検証を増やした**——選択肢を持てるのは `enum` だけ／`enum` なのに選択肢が無いのは誤り。
  **黙って無視しない**のは、書いた人が効くつもりでいるから。`text` に `values` を
  書いて色分けが出ない、という気づけない失敗を塞ぐ。

**設定を変えたので DB 再構築が要る**（`POST /api/rebuild-db`）——`enum` の畳んだ値は
再構築ではじめて入る。職場環境では実施済み（31ページ）。

  - 「向き：送信＝済み」→ **崩れた**。「かけた電話で受注することもあるので、処理は
    すんでいません。やはり、人間がチェックするべきでは」
  - 「子ページがある＝手を付けた」→ **崩れた**。「一つのメールに複数の案件が含まれる
    こともあるので、処理済みの判断は作業者自身がした方が良いと思います」

  規則は **「通信箱の下で、`対応` の印が無いもの」** の1つになった。もともとは
  **同じ方の 2026-09-03 の判断**（「メールを読んだ時点で受注ページが作られるので問題ない」）
  で、**実データで運用の形が見えたことで本人が撤回した**。推し量りはたいてい合っているので、
  外れたときに気づけない——だから残す側（人の印）へ寄せた。
- **年・月フォルダは題で見分ける**（`IsDateFolderTitle`）。作る側の隣に置いたので、
  形を変えるなら両方を同時に直すことになる。

**踏んだバグ**: 一覧の時刻が UTC で出ていた。保存は UTC（`…Z`）で正しく、**表示側が
文字列を切り出していた**のが誤り。受信日時のタグは `+09:00` を持つので気づかず、
**タグの無い記録（メモ・社内案件）だけが9時間ずれていた**（ユーザー指摘）。

## リファクタリング——メールの口を実際に使う形へ、死んだコードの撤去（2026-09-05）

`deadcode` で本体の未到達を洗い、1件ずつ「本当に死んでいるか」を確かめてから
片付けた。**確かめる価値があった**——9件のうち4件は偽陽性（テスト補助が
15箇所から使われていた）、1件は同一パッケージ内から呼ばれており
（`auth.RequireAdmin`）、コンパイラに止められて気づいた。

### メール送信の抽象が迂回されていた

`cms.SendMail` / `CurrentMailer` は**呼び手ゼロ**だった。`mail.go` の設計
（「使う側はコアに尋ねる … `CurrentMailer()`」）に反して、mailgraph が自前の
`SendAndReturnID` を使っていたため。

**理由は明白で、抽象の形が用途に合っていなかった。** `In-Reply-To` を立てるには
送信で得た Message-ID が要るのに、`Send` は `error` しか返さない。SMTP へ移った
（2026-09-03）ときに要求が変わり、口のほうが取り残された。

そこで **`Mailer.Send` と `SendMail` が Message-ID を返す形へ直し**、mailgraph の
別口（`SendAndReturnID`）を畳んで、返信ハンドラをコアの口経由に戻した。これで
「メールを送りたい側は `cms.SendMail` だけを見る」が実際に成立する——**他の拡張が
mailgraph を import せずに送れる**という、口を置いた本来の狙いが効く。

### 同じ仕事が2つあって、しかも動作が違った

`writeTag`（「名前：値」のタグを1対書く）が取り込み係と mailgraph に別々にあり、
**mailgraph だけが値を trim していた**。どちらの経路で作られたページかで値が変わる、
という形の静かな食い違い。

trim する側が正しい——索引の逆引き（`PagesByTag`）は生テキストの完全一致で引くので、
空白付きで書かれた値は空白無しの鍵では見つからない。**取り込みの重複検知
（`メッセージID`）がまさにこの経路**。コアの `WriteTag` 1つに寄せ、回帰テストを足した。
