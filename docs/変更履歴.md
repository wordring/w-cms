## エディタヘッダーを headroom 型に＋モード移行を緑トーストで明示（2026-06-25）

エディタ上部の sticky ヘッダーを、**下スクロールで隠れ・上スクロール／上端付近で再表示**する
headroom 型に変更（`initHeadroom`／`.header--hidden`）。本文を広く使えるようにした。sticky の
まま `transform` で隠すのでレイアウトのガタつきは無し。`prefers-reduced-motion` 尊重。

ヘッダーのモードトグルが常駐しなくなる分、**モードの気付きをトーストで補強**：編集モード移行時に
緑（success）の「編集権を取得しました」、閲覧復帰時に「閲覧モードに戻りました」を表示
（`id:'mode'` で置換）。フロントのみ（`assets/index.html`）。確定仕様は
[エディタ仕様.md](エディタ仕様.md) 10章・10.1。

## エディタ内の変更操作を編集ロックで直列化（共通化）（2026-06-22）

権限変更・所有者変更・親付け替えを、本文保存と同じ編集ロックで直列化する共通の仕組みを導入。
今後増えるエディタ内操作（画像/PDF等のリソース保存・削除）も最小の追加で同じロックに乗せられる。

*   **バックエンド**: 共通ゲート `RequireEditLock(w, r, id)` を新設（`lock_handler.go`）。`X-Lock-Token`
    ヘッダ（無ければ `token` クエリ）を `pageLocks.Validate` で検証し、他者保持/失効なら 409、ロック
    無しは許可（保存と同一規約）。`PagePermsHandler`(POST)・`PageChownHandler`・`SetParentAPIHandler`
    が権限チェックの後にこれを通す。
*   **フロント**: 共通ラッパ `lockedFetch()` を新設。ロックトークンを自動同梱し、409 を `handleLockLost`
    （退避＋閲覧復帰＋再読込）に集約。`savePerms`/`chownPage`/`applyParent` を移行。
*   **UI規約**: 編集モードでのみ表示する汎用クラス `.edit-only` / `.view-only` を追加。
*   **テスト**: chmod/chown/set-parent の他者ロック中 409・保持者の成功を `TestEditLockVerification` で追加。
*   確定仕様は [エディタ仕様.md](エディタ仕様.md) 9.2・[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.3。

## 権限カードの編集を編集モード限定に（競合回避）（2026-06-22）

右サイドパネルの「🔒 権限」カード（owner/group/mode の chmod/chgrp/chown）を、これまで編集モードと
無関係に常時変更可能だったのを、**編集モード（＝ロック保持中）でのみ編集可能**に変更（親ページIDの編集と
同じ方針）。閲覧モードでは読み取り専用表示にし、入力無効化・保存/所有者変更を非表示にして編集モードへ
誘導する。`refreshPermsEditable()` が `body[edit-mode]` とサーバーの `can_chmod`/`can_chown` の両方で
可否を判定し、`applyMode()` から再評価する。これで権限変更も本文編集と同じロックで直列化され競合を避ける。
フロントのみ（`assets/index.html`）。確定仕様は [エディタ仕様.md](エディタ仕様.md) 9.2。

## 編集ロック：busyトーストを「再試行」から「待機をやめる（自動取得＋キャンセル）」へ（2026-06-22）

SSE移行で待機者は `available` を受けて**自動的に編集へ入る**ようになっており、busyトーストの
「再試行」ボタンは happy path では不要だった（押さなくても取得できる）。そこで取得は自動である旨を
明示し、ボタンを**「待機をやめる」**に変更。押下で待機者購読を閉じ（サーバー側は待機者離脱として
猶予をキャンセル）、トーストも消す（`cancelWaiting`）。あわせて、編集権を失った時（`handleLockLost`）と
通常離脱時に「待機者あり」トーストを消し、「編集権が他の人に移りました」トーストは10秒で自動消去に変更。
確定仕様は [エディタ仕様.md](エディタ仕様.md) 10章。フロントのみの変更（`assets/index.html`）。

## 同時編集ロック：プッシュ通知（SSE）へ移行（Phase 2）（2026-06-22）

ロック状態の同期をポーリングから **SSE プッシュ**へ移行した。`GET /api/lock-events`
（`text/event-stream`）を新設し、**presence を SSE 接続の有無で判定**（保持者の切断で即明け渡し、
待機者の切断で猶予キャンセル）。`GET /api/lock-status`（ポーリング）は廃止。確定仕様は
[エディタ仕様.md](エディタ仕様.md) 10章・[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.3。

*   サーバー: `lock.go` を接続ベース presence ＋ broadcast へ刷新。待機者の接続で2分猶予を起動し、
    猶予満了は `StartLockReaper`（1秒ティッカー、`main` から起動）で評価。`lock_test.go` を新APIへ書き換え。
*   フロント: ポーリング関数を撤去し `EventSource`（holder/waiter ロール）へ置換。待機者は `available` で
    自動入室、保持者は `lost` で閲覧復帰＋本文自動再読込。ヘッダーの「編集権の移行まで約N分」表示は撤去。
*   検証: 単体テスト＋プレビュー実機で双方向のハンドオーバーを確認（コンソールエラー無し）。

## 同時編集の競合対策 Phase 1（悲観ロック・純HTTP）（2026-06-21）

同一ページ同時編集の lost update を防ぐため、ページ単位の悲観ロック（競合トリガー方式）を純HTTPで実装した。合意の経緯は [同時編集の競合対策（検討中）.md](同時編集の競合対策（検討中）.md)、確定仕様は [エディタ仕様.md](エディタ仕様.md) 10章・[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.3。

*   **堅牢化（ロックと独立）**: `database/sqlite.go` をDSNの `_pragma` で開き、全接続に `busy_timeout`・`foreign_keys`、DBに `journal_mode=WAL` を適用（シナリオD）。`reserveNewPageID` の `INSERT` 自動採番に統一し、非原子的な `GenerateNextID`(MAX+1) を廃止（シナリオE）。`TestReserveNewPageID` で並行一意性を検証。
*   **ロック基盤**（`cms/lock.go`）: プロセス内 mutex 付き map。無競合は無期限、他者要求から2分の猶予で強制明け渡し。待機キューは持たず（busy を返すのみ）、要求者のポーリング途絶（約30秒）で猶予キャンセル、保持者のポーリング途絶（約30秒）で待機者がいれば即解放。判定はアクセス時に遅延評価（常駐ゴルーチン不要）。時刻は引数注入で決定的にテスト可能。
*   **エンドポイント**（`cms/lock_handler.go`）: `POST /api/lock`（取得＝待機リトライ、成功時に最新HTML同梱）・`GET /api/lock-status`（死活更新＋待機者通知）・`POST /api/unlock`（sendBeacon 想定）・`POST /api/lock/force`（admin、`auth.Audit` 記録）。`SaveAPIHandler` がロックトークンを検証し、他者保持/失効は 409、ロック無しは許可。
*   **フロント**（`assets/index.html`）: 編集モード移行でロック取得＋最新版再ロード、busy 時の10秒空き待ち（空き次第で自動編集）、保持中の status 10秒ポーリング、`lost`/409 でクリップボード退避＋閲覧モード復帰。アプリ内通知エリア（トースト）新設、編集トグルが常に見えるようヘッダーを sticky 化。`toggleMode` を `applyMode`＋`onModeToggle` に分離。
*   **検証**: ロックの単体テスト（取得・強制明け渡し・死活奪取・離脱キャンセル・トークン検証・解放/強制解除/待機者通知）。実機（Claude in Chrome）で lock取得→status polling→save(token)→強制解除でlost検知→トースト＋閲覧モード切替まで確認、コンソールエラーなし。
*   **未実装**: Phase 2 の即時通知（SSE/WebSocket）、軽微な競合 B（原子的ファイル書き込み）・C（サイドカー直列化）。

## ページ属性のサイドカー化と独立サイドパネル（2026-06-21）

直前の `<m-page-info>`（HTML本文に属性を埋め込む方式）を見直し、UNIXに倣って
**「内容＝HTML本体／属性＝サイドカー `<id>.meta.json`」** に分離した。あわせてページ情報の
表示・編集を文書から切り離し、クローム側の**独立サイドパネル `<aside class="rail">`** へ集約した（Plan B）。
詳細仕様は [エディタ仕様.md](エディタ仕様.md) 9章・[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 2・4・8章。

*   **動機**: 親ページID・作成日時・作成者・更新日時は文書の「内容」ではなく「属性」であり、
    サイドカー（既に owner/group/mode を持つ正本）へ寄せる方が概念的に整合し、保存APIのHTML属性
    注入・改竄復元（`setPageInfoAttrs`）という一群の処理が不要になる。DB再構築で属性が失われない点は
    HTML埋め込み方式と同等に担保される（サイドカーもファイル＝正本のため）。
*   **サイドカー（`PageMeta`）**: `parent_id` / `created_by` を追加（`created_at` / `updated_at` は既存）。
    `WriteSidecar` は `updated_at` を空のときだけ補完し、本文保存は `BumpUpdatedAt`、親付け替えは
    `SetSidecarParent` が更新日時を進める（所有権の変更は chmod/chown 経由のみ＝自己認可を防止）。
*   **パーサ／同期**: `ParseCore` は属性抽出を廃しタイトル・タグのみ抽出（旧「親ページID」タグはスキップ）。
    `SyncIndex` は親・作成情報・更新日時をサイドカーから読む。
*   **API**: 保存（`SaveAPIHandler`）と新規作成（`NewPageAPIHandler`）を簡素化（HTMLは内容のみ）。
    親付け替え `POST /api/set-parent`、属性取得 `GET /api/page-meta` を新設。`GET /api/validate-parent` は存続。
*   **フロント**: 文書内の `<m-page-info>` コンポーネント・テンプレートを撤去。`<aside class="rail">` に
    「ページ情報」カードと「権限」カード（旧 perms-panel を畳み込み）を新設。画面を2カラムグリッド化し、
    コンテナクエリで狭いときは1カラムに畳む。親ページIDは `/api/set-parent` で変更。
*   **リファクタ（別コミット）**: サイドカー構造体 `PagePerms` を `PageMeta` に改名（一覧用の旧 `PageMeta` は
    `PageSummary` に）。
*   テスト: `<m-page-info>` 関連テストを、サイドカーからの属性同期（`TestSidecarAttributesSync`）と
    ミューテータの権限保持（`TestSidecarMutators`）に置き換え。

## ページ情報欄の統合（`<m-page-info>` 新設）（2026-06-20）

エディタで親ページIDの入力欄が2か所あった状態を解消し、ページの属性（ページID・親ページID・作成日時・作成者・更新日時）を文書先頭の `<m-page-info>` パネル1か所に集約した。あわせて画面を3層（ヘッダー／ページ操作バー／文書）に再編し、HTML/CSSを保守的にモダン化した。詳細仕様は [エディタ仕様.md](エディタ仕様.md) 9章・[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 2・4章。

*   **DBスキーマ＋同期**: `pages` に `created_at` / `created_by` を追加（既存DB向けに冪等な `ALTER TABLE` マイグレーションも用意）。`ParseCore` が `<m-page-info>` の created-at / created-by / updated-at を抽出し、`SyncIndex` が反映。作成情報は空なら `COALESCE` で既存値を保持、`updated_at` はHTML値があれば採用（DB再構築でも真の値が残る）。
*   **保存APIの保護**: `SaveAPIHandler` が `<m-page-info>` のサーバー権限フィールド（作成日時・作成者・更新日時）を保存前にサーバー値で上書き（`setPageInfoAttrs`）。応答に `updated_at` を返す。新規ページHTMLは `NewPageAPIHandler` が `<m-page-info>` に親ページIDタグを内包して生成。
*   **親ページIDの検証**: 親を付け替える保存に限り、実在・自己参照/循環の防止・新しい親への write 権限（トップレベル化は admin）を検証（`validateParentChange`）。即時フィードバック用に `GET /api/validate-parent` を追加。親が変わらない通常保存は検証対象外。
*   **フロント**: `<m-page-info>` Webコンポーネント（Shadow DOM）とテンプレート `m-page-info-view/-edit` を新設。ヘッダーの簡易表示（ページID・親ID入力）を廃止し、「＋子ページを作成」を新設の `<nav class="page-actions">` へ移設。読込時に旧形式の親IDタグをパネルへ移行。
*   **HTML/CSSモダン化**（別コミット）: コンテナを `<main>`・クロームを `<header>` にセマンティック化し、`:root` のCSS変数（デザイントークン）をトップレベルのレイアウトに導入。ウィジェット内部配色は過剰なリファクタを避けて据え置き。
*   テスト追加: `<m-page-info>` の抽出・同期・COALESCE保持、`setPageInfoAttrs` の改竄上書き、`updated-at` の永続化、親ページ検証（実在・循環・権限・トップレベル）。

## 認可（フェーズ2）の実装（2026-06-20）

[認証認可設計.md](認証認可設計.md) のフェーズ2を実装。ページ単位の read/write 権限を Unix風（owner/group/other、グループ対応、admin=root）で強制するようにした。

*   `internal/cms/perms.go`（新規）: 権限の中核。
    *   サイドカー `<id>.meta.json`（owner/group/mode）の読み書き。本文保存パスからは触れず、新規ページ作成・権限操作のみが書き込む（自己認可問題の回避）。
    *   `mode` は3桁（各桁 r=2 / w=1 / rw=3）。`effectiveClass` で owner/group/other を判定し、`CanRead`/`CanWrite`（adminはバイパス）。
    *   `GetPerms` は権限レコードの無いページを「admin所有・other不可」でフェイルクローズ。
    *   `RequirePageRead`/`RequirePageWrite`/`RequireAdmin` のHTTP強制ヘルパー、`DataFileHandler`（`/data` 配信時にread権限を確認、トラバーサル対策込み）。
*   `database/sqlite.go`: コアテーブルに `page_perms`（サイドカーから再生成される派生インデックス）を追加。
*   `sync.go`: `SyncIndex` がサイドカー → `page_perms` を同期（プラグインではなくコア扱い）。
*   各APIに権限チェックを組み込み: `/api/load`・`/data`=read、`/api/save`・`/api/upload-pdf`・`/api/parse-pdf`=write、`/api/new-page`=親のwrite（トップレベルはadmin）、`/api/children`=親のread＋子をフィルタ、`/api/required-materials`=read、`/api/rebuild-db`=admin。
*   新規ページ既定mode `"330"`（owner/group rw, other なし）。トップ `000000` は `"302"`（other read）で全員閲覧可・admin（owner）のみ書込可。
*   テスト追加（mode判定・other可読・サイドカー往復と `page_perms` 同期・フェイルクローズ）。

## 認証基盤（フェーズ1）の実装（2026-06-20）

[認証認可設計.md](認証認可設計.md) のフェーズ1（認証基盤）を実装。インターネット公開を前提としたアプリ単体のパスワード認証を導入した。この段階では「ログインすれば全機能利用可」で、ページ単位の認可はフェーズ2で実装する。

*   `internal/database/auth.go`: 認証用の独立DB `data/auth.db`（`users` / `groups` / `group_members` / `sessions` / `login_attempts`）。`cms.db` とは別接続で、全再構築の対象外。
*   `internal/auth`（新パッケージ）:
    *   `password.go`: argon2id（m=64MiB, t=3, p=1）でハッシュ化し、PHC string形式で保存・検証。
    *   `session.go`: 256bitトークンのサーバ側セッション（絶対8時間／アイドル30分、トークンはハッシュ化して保存）。
    *   `users.go`: 認証・グループ解決・ユーザー作成・初期管理者ブートストラップ（環境変数）・ログイン失敗のロックアウト（5回／15分）。
    *   `middleware.go`: `RequireAuth`（未認証は `/login` へ、APIは401）、`CSRFProtect`（状態変更系のオリジン検証）、`HttpOnly`/`Secure`/`SameSite=Lax` Cookie。
    *   `handlers.go`: ログイン画面・`/api/login`・`/api/logout`・`/api/me`（argon2idの同時実行をセマフォで制限しメモリピークを抑制）。
*   `cmd/w-cms/main.go`: 公開ルート（`/login`・`/api/login`・`/assets`）と保護ルート（その他すべて）を分離し、CSRFを全体に適用。起動時に `auth.db` 初期化と管理者発番。
*   依存追加: パスワードハッシュ用に `golang.org/x/crypto`（承認済み）。
*   運用: 初期管理者は `WCMS_ADMIN_USER` / `WCMS_ADMIN_PASSWORD` で作成。ローカルHTTP検証時のみ `WCMS_SECURE_COOKIES=0` でSecure属性を無効化可能。バックアップ対象に `data/auth.db` を追加（[デプロイ・運用マニュアル.md](デプロイ・運用マニュアル.md) 4・6章）。

## DB全再構築の全テーブルDROP方式化と起動時自動リビルド（2026-06-20）

「`data/master` のファイルが正本、`cms.db` は使い捨て可能な派生インデックス」という方針（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 8章）を実装に反映した。設計の文書化を先行し、その後コードを実装。

*   `RebuildDatabase` を、全行DELETE方式から**全テーブルDROP方式**へ変更（`sqlite_master` を列挙して全テーブルをDROP → コア＋全プラグインのスキーマを再作成 → `data/master` の全HTMLを再同期）。廃止プラグインの残存テーブルなどスキーマのdriftも一掃できる。DBファイルは削除せず接続を維持したまま実行（Windowsのファイルロック・同時実行を回避）。
*   起動時フック `RebuildIfEmpty` を追加。`pages` が空かつ `data/master` にHTMLがある場合に自動再構築するため、バックアップからファイルを戻して起動するだけで復元が完了する。
*   `Plugin.Tables()` の役割を「再構築の削除リスト」から「所有テーブルの自己文書化・整合性検証用」に変更（全テーブルDROP方式により、記載漏れが再構築バグを起こさなくなった）。
*   テスト追加: `TestRebuildDatabase`（drift除去・孤児ページ一掃・ファイルからの再同期）、`TestRebuildIfEmpty`（空DBで自動再構築／既存DBで無処理）、`TestPluginTablesConsistency`（Schema/Tablesの整合）。
