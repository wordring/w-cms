# 【要求】w-cms とは

w-cms が**何のためのソフトウェアか**をまとめた要求仕様です。
はじめて w-cms に触れる方は、ここから読んでください。

## 1. 目的

AI利用を前提とした、文書システムと帳票システムの融合です。

### 文書を書く

- w-cms はワンノートのような、自動的に保存されるリッチなメモ帳です。
- ワンノートのように、構造化された文書を書くことが出来ます。
- ページの下に子ページを作り、階層にしていくことが出来ます。
- 帳票のような画面や紙は、文書の上に作ります。ページの種類をコードや DB に固定しません。
  すべてのページは同じ構造で、役割は階層・ページ名・テンプレートで決まります。

### 自動的に DB に格納される

- 「名前:値」のタグと、キャプション（表の題）の付いた表は、保存したときにデータベースへ格納されます。
  あとで検索や集計に使えます。
- キャプションの名前が DB のテーブルの名前になり、表の列の名前がテーブルの列の名前になります。
  文書に書いた言葉がそのまま DB に入り、見たままに扱えることが特徴です。
- 単語には型を結び付けて、型に合った正規化（表記の揺れをそろえること）も行います。

### 特定用途向けに拡張できる

- w-cms をコア（土台）として、様々な用途に拡張することが出来ます。
- AI が拡張のプログラムを書けるように、文書を整備していきます。
- w-cms は、開発元以外の事業者も設置して使います。語彙と拡張は、設置した人が足せます。
  開発元の業務の拡張も、そうした拡張の1つです。

⚠ **いま**: 語彙は、設定のファイル（`config/settings.json`）に運用者が書いて、サーバーを起動し直せば足せます。
拡張は Go のプログラムで、`cmd/w-cms/ext_*.go` に1つ足して組み直します。
開発元の業務の拡張（東邦）もこの形で入っていて、組むときに `-tags minimal` を付ければ外せます。

以上の機能によって、小規模事業者向けの業務システムを作ることが出来ます。
ただし、それぞれの用途のために拡張する必要があります。

## 2. 用途は2つ

1. 業務システム
2. ウェブサイト

- 同じソフトウェアを、どちらの用途にも使えます。
- 業務システムとウェブサイトを、同じインスタンスで共用はしません。独立した別のサーバーで運用します。

「インスタンス」は、動いている w-cms の1つ1つのことです。

| インスタンス | 用途 | 主な利用者 | 中心になる要求 |
|---|---|---|---|
| **業務** | 社内の業務システム | ログインした利用者だけ | 業務の記録と集計（中身は、使う側が拡張で作ります） |
| **サイト** | 一般に公開するウェブサイト | ログインしていない訪問者と、編集する人 | 公開ページを読み取り専用で届けること |

## 3. 利用者

| 利用者 | できること |
|---|---|
| ログインした利用者（認証済み） | ページごとの権限の範囲で、閲覧と編集ができます。権限は「読む」「書く」の2つで、Unix のファイルの権限に似た形です |
| グループ | 利用者をまとめる単位です。ページの権限は「所有者・グループ・それ以外」の3つに分けて付けるので、その「グループ」に当たります。**グループの中にグループは作れません**（入れ子なし） |
| 管理者（admin） | すべてを行える利用者です（Unix の root に当たります）。ページの権限に関わらず全部を扱え、利用者とグループの管理・DB の再構築・ロックの強制解除ができます |
| ログインしていない訪問者（匿名） | **公開されているページ**を読むことだけができます |

「公開されているページ」とは、そのページ自身と、親をたどった先のページのすべてが公開になっているページのことです
（これを「実効公開」と呼びます）。詳しくは [【要求】権限.md](【要求】権限.md) にあります。

## 4. 公開範囲と脅威モデル

どこまでを誰に見せるか、何から守るかの決まりです。

- **どちらのインスタンスも、インターネットに公開して使うことを前提にします。**
  そのため、次の4つは**必須**です。
  - 強固な認証
  - HTTPS
  - レート制限（短い時間に何度も試す操作を止める仕組み）
  - CSRF 対策（ほかのサイトから、ログイン中の人に勝手な操作をさせない仕組み）
- **業務インスタンスは、ログインしていない人に何も見せません。**
  すべてのページを非公開のまま運用します（`public` を使いません）。
  ページが在るかどうかも教えません。読めないページにも、存在しないページにも、同じ「ありません」（404）を返します
  （[【要求】権限.md](【要求】権限.md) の404統一）。
- **サイトインスタンスでは、ログインしていない訪問者が読みに来るのが、ふだんの主な使われ方です。**
  ログインせずに届く範囲は、公開ページの本文・子ページの一覧・親ページへのリンク・添付ファイルの配信です。
  ここは「**はじめは非公開。人がはっきり公開の操作をしたものだけを公開する**」という形で守ります
  （迷ったら閉じる側に倒す考え方で、フェイルクローズと呼びます）。
  下書き（非公開のページ）が在ることも、訪問者には漏らしません。

## 5. 実装の制約（守ってほしいこと）

- **Go の標準ライブラリを優先します。**
  外部のパッケージを新しく足すことは原則として禁止で、足すときは事前の承認が要ります。
  承認済みのものの一覧は [開発方針.md](開発方針.md) §1 が正本です。
- **CGO なしでビルドできること。**
  CGO は、Go から C 言語のプログラムを呼ぶ仕組みです。これに頼らなければ、Windows でも C コンパイラなしで動かせます。
- **画面（フロントエンド）は、素の JavaScript だけで書きます。**
  ビルドの工程は置かず、ライブラリも足しません。
- **実行ファイル1つと、その横に置く2つのフォルダだけで、配布して起動できること。**
  フォルダは `assets/`（画面の HTML・JS・CSS）と `config/`（運用者が育てる設定）です。
- **語彙の数が増えても、実装の量が増えないこと。**
  語彙の種類ごとに JavaScript を書かない、語彙を増やすたびに画面の HTML を手で足さない、ということです。
- **語彙が百種の規模になっても破綻しないこと。**
  語彙を増やす・一覧を保守する・エディタから選ぶ、のどの道もです。

⚠ **いま**:

- 画面のファイル（`assets/`）は、サーバーが毎回ディスクから読みます。画面を直したときは、組み直さなくても効きます。
- 表の種類は、表のキャプションで決まります。列の型と選択肢は、設定の語彙（`config/settings.json`）に書きます。
- 語彙を足す道は2つです。設定に書くか、拡張がプログラムで登録するか（`cms.RegisterVocab`）。
- エディタのスラッシュメニューは、この登録から自動で組み立てます。語彙ごとの画面のコードはありません。

利用者の言葉:「そもそもがワンノートに検索や集計機能を付けたようなものです」「ワンノートでの運用そのものは変えたくない」。

### 2. 文書が主、データベースが副

検索と集計はあとから足した機能です。文書の書き方を縛る理由にはしません。

- 出どころ: コンセプト.md:33-35（2026-08-21）
- 入れる場所の案: §1

### 3. コアは業務の語彙を知らない

表のキャプションや `data-type` の値は、コアにとっては中身を問わない、ただの名前です。業務の決まりは拡張が持ちます。

- 出どころ: アーキテクチャとDBスキーマ.md:50-52・634・806-807
- 入れる場所の案: §1 か §5
- ⚠ 開発方針 §0 には書いてありますが、【要求】にはまだありません。
