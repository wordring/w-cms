# 【要求】w-cms とは

**何のためのソフトウェアか**の要求仕様です。

> **書くのは利用者**、**矛盾を指摘するのがエージェント**（開発方針 §2）。


⚠ **2種類のことが書いてあります。** （印なし）＝**要求**（利用者が直す）、
⚠ **いま**＝**実装の現状**（エージェントが直す）。
**なぜそうなったか**は `【考察】` が正本です。

---

## 1. 目的

AI利用を前提とした、文書システムと帳票システムの融合

**文書を書く**

- w-cmsはワンノートのような自動的に保存されるリッチなメモ帳です。
- ワンノートのように構造化された文書を書くことが出来ます。
- w-cmsはページの下に子ページを作り階層化していくことが出来ます。
- 帳票のような画面や紙は、文書の上に作ります。ページの種類をコードやDBに固定せず、すべてのページは同じ構造で、
  役割は階層・ページ名・テンプレートで決まります。  
  （2026-10-01 利用者が選んだ言い換え——09-27 の書き直しで消えた「固定のページ種別を持たない」を「融合」に合わせて戻した）

**自動的にDBに格納される**

- 「名前:値」のタグとキャプションの付いた表が保存時にデータベースへ格納され、後で検索や集計に利用されます。
- キャプションの名前がDBのテーブルの名前となったり、表の列名がDBのTableの列名になるなど、
  文書に書いた言葉がそのままDBに入り、見たままに扱えることが特徴です。  
  ※単語に型を紐づけ相応の正規化も行います。

**特定用途向けに拡張できる**

- w-cmsをコアとして様々な用途に拡張することが出来ます。
- AIが拡張プログラムを書けるように、文書を整備していきます。
- w-cms は開発元以外の事業者も設置して使います。語彙と拡張は設置した人が足せます。開発元の業務の拡張も、そうした拡張の1つです。  
  （2026-10-01 利用者が選んだ言い換え——09-27 の書き直しで消えた「設置者は開発元に限らない」〔2026-08-26 利用者
  「…**利用者は私のみではありません**」〕を戻した）

⚠ **いま**: 語彙は設定のファイル（`config/settings.json`）に運用者が書いて再起動すれば足せます。拡張は Go のプログラムで、
`cmd/w-cms/ext_*.go` に1つ足して組み直します（組み直しが要る）。開発元の業務の拡張（東邦）もこの形で、`-tags minimal` で外せます。

以上の機能によって小規模事業者向けの業務システムを作ることが出来ます。  
※それぞれの用途のために拡張する必要があります。

## 2. 用途は2つ

1. 業務システム
2. ウェブサイト

- 業務システム用途とウェブサイト用途を同じインスタンスで共用はしません。
  独立した別のサーバーで運用します。
- 同じソフトウェアで2用途に使えます。

| インスタンス | 用途 | 主な利用者 | 中心の要求 |
|---|---|---|---|
| **業務** | 社内の業務システム | 認証済みの利用者だけ | 業務の記録と集計（中身は利用者側が拡張で作ります） |
| **サイト** | 一般公開のウェブサイト | 匿名の訪問者＋編集者 | 公開ページの読み取り専用配信 |

## 3. 利用者

| 利用者 | できること |
|---|---|
| 認証済みの利用者 | ページ権限（Unix風 read/write）の範囲で閲覧・編集 |
| グループ | ページの group クラス権限の単位（**フラット・入れ子なし**） |
| admin | root 相当。全権限バイパス・利用者/グループ管理・DB再構築・ロック強制解除 |
| 匿名の訪問者 | **実効公開ページだけ** read 専用 |

## 4. 公開範囲と脅威モデル

- ⚠ **どちらのインスタンスもインターネット公開を前提**とします。強固な認証・HTTPS・
  レート制限・CSRF 対策は**必須**です。
- **業務インスタンスは匿名に何も見せません。** 全ページ非公開（`public` を使わない運用）とし、
  匿名には**存在情報も返しません**（[【要求】権限.md](【要求】権限.md) の404統一）。
- **サイトインスタンスでは匿名アクセスが常時の主要動線**です。未認証で到達できる面
  （公開ページの本文・子ページ一覧・親リンク・添付配信）は、**既定非公開＋明示的な公開操作**という
  **フェイルクローズ**で守ります。⚠ **下書き（非公開ページ）の存在も匿名には漏らしません。**

## 5. 実装の制約（守ってほしいこと）

- **標準ライブラリ優先。** 外部パッケージの新規追加は**原則禁止・事前承認制**。
  ⚠ 承認済みの直接依存の一覧は [開発方針.md](開発方針.md) §1 が正本です。
- ⚠ **CGO 不要**でビルドできること（Windows でも C コンパイラなしで動く）。
- **フロントエンドはバニラJS・ビルド工程ゼロ・追加ライブラリなし。**
- **単一バイナリ**で配布・起動できること。
- ⚠ **実装量が語彙数に対して不変であること。** 型ごとの JavaScript を書かない、
  語彙を増やすたびにフロントの markup を手で足さない。
- 語彙が百種規模になっても、増やす・一覧を保守する・エディタから選ぶ道が破綻しないこと。  
  （2026-10-01 利用者が選んだ——09-27 の書き直しで消えた旧 §4「業務の対象領域」のうち、コアの要求をここへ戻した。業種と役割語は
  [【要求】東邦拡張.md](拡張/東邦/【要求】東邦拡張.md) §16 へ）

⚠ **いま**: 表の種類はキャプションで名乗り、列の型と選択肢は設定の語彙（`config/settings.json`）——語を足すのは設定と、
拡張の登録（`cms.RegisterVocab`）。スラッシュメニューは登録から組む（語ごとの画面のコードは無い）。
