# 【要求】添付

**ページにファイルを添えること**の要求仕様です。

> **この文書の読み方**
>
> - 印の無い文は**要求**です（こうあってほしい、という決まり）。書くのは利用者で、
>   エージェント（AI）は矛盾を見つけたら指摘します（[開発方針.md](開発方針.md) §2）。
> - 「⚠ **いま**」で始まる段落は**実装の現状**です。こちらはエージェントが実装に合わせて直します。
> - 末尾の「下書き」は、エージェントが旧文書から抜き出して置いたものです。
>   利用者が読んで、直したり採ったりします。
> - いつ・なぜその形になったかは、末尾の「この文書の経緯」と、`考察/` フォルダの【考察】にあります。

この文書は、2026-09-23 に [要件定義書.md](旧文書/要件定義書.md) の §2.6 から抜き出して作りました。

## 1. 何を添えられるか

| 種類 | 入口 | 配信 |
|---|---|---|
| **PDF** | ドロップ／ファイル選択 | **インライン表示** |
| **画像**（png・jpeg・webp・gif・svg） | ドロップ／選択／**カメラ撮影** | **インライン表示**（⚠ SVGは別扱い・§3） |
| **その他**（CAD・Office・ZIP など） | 本文へのドロップ | **ダウンロード扱い** |

「インライン表示」は、ブラウザの中でそのまま見せることです。
「ダウンロード扱い」は、その場では開かずに、ファイルとして保存させることです。

- **許す拡張子は、設定で決めます**（運用者が増やせます）。ただし、`.json` は書けません。
- ⚠ **添付は `files/` サブフォルダに置き、正本の2ファイルと同じ場所に置かないこと。**
  正本の2ファイルは、本文と、属性のファイル（サイドカー）です。
  こうしておくと、添付の名前で正本を上書きしてしまう穴が、構造として無くなります。

> 2026-10-01 利用者:「画像をペーストできるようにしたい」「画像とPDFの違いを自動判定して、画像をはる、PDFをはるというわけかたをなくせませんか」

⚠ **いま**（2026-10-01）:

上の表の「入口」の列は、2026-10-01 より前の分け方です。
いまは、PDF・画像・その他のどれも、次の4つの入口から入ります。

- **入口は4つです。どれも同じ処理を通り、種類は選ばせません。**
  - 書式の帯の 📎（書式の帯は、ブロックを触ると出る、太字などのボタンの帯です）
  - スラッシュメニュー（`/` を打つと出る一覧）の「📎 画像・ファイル」
  - 本文へのドロップ
  - 貼り付け（Ctrl+V）
- **貼り付けは、文字が一緒に載っていないときだけ扱います。**
  Excel のセルなどは文字が載るので、文字のまま貼られます。
- 切り取りの画像の名前（`image.png`）は、貼った日時の名前（`貼り付け 2026-10-01 13.40.13.png`）に付け替えます。
- 表の画像の列のセルでは、「🖼 画像を選ぶ」が残ります（そのセルに入るのは画像だけです）。
- 入る場所は、**キャレット（落とした所）のすぐ後ろ**です。キャレットは、文字を打つ位置の印です。
  節・折りたたみの中なら、中のまま入ります。
- 入り方は、種類で分かれます。
  - **画像は、本文の中の絵**（`<img>`）として入ります。
  - **それ以外（PDF・CAD・Office など）は、ファイル表示**として入ります（ファイル表示は §5）。
    PDF は開く枠、描けない形式は開く案内になります。

  > 利用者:「イメージと添付ファイルは扱いが違って当然ですね」

- 写真は、マウスを載せると右上に「⋯」が出ます。
  📝（ローカルのアプリで編集）は、その中にあります（§5「形式に合った操作」）。
  タッチ端末と、ログインしていない人には出ません。
- カメラは、スマホのファイル選択の画面から選べます（独自のカメラ画面はありません）。

## 2. 入口で守ること

ファイルを受け取る入口では、次のことを守ります。

- **リクエスト上限**（1回に送れる大きさの上限）を置くこと。既定は 32MiB で、設定で変えられます。
- **中身を見ること。拡張子だけを信じないこと。**
  - PDF は、先頭が `%PDF-` であることを確かめます。
  - ラスタ画像（点の集まりでできた画像。SVG 以外の画像です）は、**マジックナンバー**を確かめます。
    マジックナンバーは、ファイルの先頭にある、形式ごとに決まった印です。
- **ファイル名を正規化すること**（決まった形にそろえること）。
  - パスの要素（フォルダの区切りなど）や制御文字（画面に出ない特殊な文字）は拒否します。
  - 本文・サイドカーと同じ名前は拒否します。
- **名前の検査は、すべてのアップロードの入口が、同じ関数を通ること。**
- ⚠ **外部へ送る側（AI への送信など）も、同じ関門を通すこと。**
  「**置く側は守られ、送る側だけ素通し**」という非対称（片方だけ守られていない状態）が、過去に実際にありました。

### ⚠ EXIF は保存時にサーバーで除去する

EXIF は、カメラが写真のファイルに埋め込む、付属の情報です。
カメラの写真には、**撮影位置（GPS）・撮影日時・機材**が埋まっています。
そのまま公開サイトに載ると、**撮影者の所在が漏れます**。

- **除去は、アップロードの経路で一律に行うこと。** 公開するときに選んで落とす方式にはしません。
  迷ったら閉じる側に倒す考え方（フェイルクローズ）です。
- **回転の情報を捨てるなら、画素の向きを補正してから保存すること。** 表示が横倒しにならないようにするためです。

⚠ **帰結**: 撮影日時・撮影場所を、**業務データとして使う設計にはできません**。
必要なら、アップロードを受け付けた時刻をサーバーが記録するか、利用者が表の `date` 列へ入力します。

## 3. SVG は「不活性な画像」として許す

SVG は、図を文字で書き表す画像の形式です。**スクリプト（プログラム）を中に含められる、文書の形式**でもあります。

中身を完全にサニタイズする（危ない部分を取り除く）ことはしません。
**埋め込み方と配信の二層で、無害にします。**
下の表の①と②が、その二層です。③は、その上に重ねる網です。

| 層 | 何をするか |
|---|---|
| ① 埋め込み | 本文からの表示は **`<img src="x.svg">` 経由のみ**。⚠ **画像コンテキストではブラウザ仕様としてスクリプトが実行されません**。インライン `<svg>` はサニタイザが部分木ごと削除 |
| ② 配信 | `Content-Type: image/svg+xml` ＋ `Content-Disposition: attachment`（**直接開くと描画せずダウンロード**）＋このレスポンス限定の `Content-Security-Policy: sandbox; default-src 'none'` |
| ③ 入口 | well-formed XML でルートが `<svg>` か検査し、`<script>`・`<foreignObject>`・`on*=`・`javascript:` を含むものを拒否 |

表の言葉を説明します。

- 「画像コンテキスト」は、`<img>` で画像として読み込まれる場面のことです。
- 「インライン `<svg>`」は、本文の HTML の中に直接書いた SVG のことです。
  「部分木ごと削除」は、その要素を、中身ごと取り除くことです。
- `Content-Disposition: attachment` は、「その場で開かずに保存させる」という指示です。
- `Content-Security-Policy: sandbox; default-src 'none'` は、
  「この応答の中では、スクリプトを動かさず、ほかの物も読み込ませない」という指示です。
- 「well-formed XML」は、文法の崩れていない XML のことです。

この3つについて、次のことを覚えておきます。

- **安全性の本体は、②の配信側です。** ③は、守りを重ねるための網です（多層防御）。
- **代償として、SVG の中の対話性（押すと動く、などの仕掛け）は動きません。**
  ロゴや図版の用途を想定しています。

## 4. 配信

添付をブラウザへ届けるときの決まりです。

- ⚠ **静的配信ではなく、ページの read 権限を要求する保護ハンドラにすること。**
  静的配信は、置いてあるファイルを、誰にでもそのまま渡す形です。
  保護ハンドラは、ページを読む権限（read）を確かめてから渡す入口です。
- `nosniff` を付けること。
  `nosniff` は、ブラウザに「中身から種類を推し量らず、サーバーの伝えた種類に従うこと」と伝える指示です。
- **許可した種別のほかは、ダウンロード扱いにすること。**
- ⚠ **本文とサイドカーは配信しないこと。**

**「描ける形式」の表は、配信側の帰結です。独立した判断ではありません。**

- 配信が `inline`（その場に表示してよい、という指定）で返す形式は、PDF・ラスタ画像です。
- SVG は、ダウンロード扱いで返します。それでも、`<img>` 経由なら描けます（§3 の①②）。
- その場に描けるのは、この3つだけです。
- それ以外は、「描ける」と宣言しても、**ブラウザは描きません**。

⚠ **いま**: 動画・音声（`.mp4`・`.m4a`・`.mp3`）は、ダウンロード扱いで配ります。

- ファイル表示は、これを `<video>`・`<audio>` の要素で出します（§5「PDF 以外も開きます」）。
- 実際に再生できるかは、まだ確かめていません。
- 形式ごとの出し方は、`internal/cms/file_view.go` の `fileViewKinds` にあります。

### ブラウザの手元に残す

> 2026-10-27 利用者:「単なるトンネルではなく、画像のキャッシュなどはできますか」
> （VPS に貯めず、ブラウザの手元に残す案を聞いて）「作ってください」

⚠ **いま**（2026-10-27）:

- 住所の `?v=`（版の印＝書いた時刻）が今のものと合えば、その人のブラウザが、確かめずに手元の写しを使ってよい（`private, max-age=31536000, immutable`）。
- 印が無い・古い住所は、使う前に毎回「変わったか」を聞かせます（`private, no-cache`）。変わっていなければ、中身は送りません（304）。上書きしたあとに、古い中身を見せ続けないためです。
- どちらも `private` で、途中の中継（VPS）には残させません。添付は、読める人だけに配るものだからです。
- 印を添えるのは、ファイル表示の埋め込みと、閲覧の描き方の本文の写真です（`internal/cms/attachment_cache.go`）。書くための本文の口には添えません（本文として保存されてしまうため）。
- 2026-09 の総点検で「添付の配信にキャッシュ抑止は足さない」と決めています（共用の PC も個人のログインで使う前提）。この形は手元に残すほうへ寄せたもので、その決めごとと食い違いません。
- 実装: `internal/cms/page/perms.go` の `setAttachmentCache`・`AttachmentVersion`。

## 5. 本文から開く

本文に **`<section data-type="file-view" data-ref="ページID-添付ID">`** と書くと、
**サーバーが、その添付を開く枠を足します**。この形を「ファイル表示」と呼びます。

足される枠は「鏡」です。
鏡は、本文には印（マーカー）だけを置いて、中身はサーバーが表示のたびに描く部分のことです。

- **本文に在るのは、マーカーと、短縮ファイル名の名札だけです。**
  - 中身（PDF の枠など）は、ページを返すたびに描きます。
    `.vocab-chrome`（保存しない部分の印）に包むので、**保存されません**。
  - 名札は、保存のたびにサーバーが書きます。
  - ⚠ いま: 枠が埋め込む住所（PDF・画像・動画・音声）には、ファイルを書いた時刻を `?v=` で添えます（2026-10-23）。同じ添付を上書きしたとき（部材発注書の「PDF作成」・📝 ローカル編集など）に、ブラウザが前の中身を出し続けないためです。配信のキャッシュの扱いは変えていません（変わっていなければ手元の写しが使えます）。
    名前は、保存した人の権限で引きます。読めない添付の名前を漏らさないためです。
  - 名札は、表示のときには消します。
  - 保存された HTML を読めば、何を表示しているかが分かります。

  > 2026-09-27 利用者:「保存時は…短縮ファイル名</section> としておいて、表示するときに消せば良いのでは？」

- ⚠ **`<embed>` を本文に書かせないのが、この形の要点です。**
  `<embed>` は、ほかのファイルをページの中に埋め込んで見せる要素です。
  - 危ないのは、要素そのものではありません。**`src`（埋め込む先のアドレス）を、書いた人が決めること**です。
  - 本文へ `<img src="/api/logout">` を1つ保存すると、**全員が無音でログアウト**した、という事故が実際にありました。
  - マーカー方式なら、**書く人が選べるのは、ページ ID と添付 ID だけ**です。URL は機械が組みます。
- **PDF 以外も開きます**（画像・動画・音声）。
  表に無い形式には、**開くためのリンク**を出します。
  「見つかりません」と言って黙るのは、嘘でした。ファイルは在るのですから。

> 2026-10-01 利用者:「メール送信にファイル添付が無いです。PDFや画像の表示にIDが在ると思いますが、それをクリック程度で簡単にクリップボードへコピーできると、ほかの場所にスラッシュメニューから貼りつけたり、メールに添付できるのでは」

⚠ **いま**:

- ファイル表示の頭の行と、写真（マウスを載せたとき）の「⋯」のメニューに、「🔗 ID を写す」があります。
  押すと、ID（`ページID-添付ID`）を写します（「⋯」は、下の「形式に合った操作」にあります）。
- 貼り先は2つです。
  - スラッシュメニューで挿したファイル表示（挿すと、参照の欄がすぐ開きます）
  - 拡張の画面の欄（例: 通信の拡張の送る欄。[【要求】通信拡張.md](拡張/通信/【要求】通信拡張.md) §5）
- ID から添付を引く API は、`GET /api/file-ref` です。
  読める添付だけを返します。添付の住所（`/ページID/添付ID.拡張子`）も受けます。
- 描けない形式の頭の行は、ID の文字の代わりに、「出どころ」のリンクにしました。
  同じ ID が2つ並ばないようにするためです。
- 頭の行は、ファイル名だけです。

  > 2026-10-01 利用者:「を開いていますは冗長です。ファイル名だけで分かります」

### 形式に合った操作（「⋯」）

> 2026-10-01 利用者:「ドロップやファイルダイアログで追加された画像やファイル等は形式を判定して、ファイル形式にあったボタンなりクリックメニューを搭載してはどうでしょう？」

出し方を聞いて、「⋯」1つにまとめることなどが決まりました。

- **本文に入れたファイル（ファイル表示）と写真には、形式に合った操作を出すこと。**
  出し方は「⋯」1つです。押すと、形式に合った項目だけが並びます。
- 拡張が足す項目をどのページに出すかは、拡張の【要求】へ移しました（東邦）。

⚠ **いま**: 形式は、拡張子で決めます。

| 形式 | 項目 |
|---|---|
| どれも | 🔗 ID を写す・⬇ 保存（届いたときの名前で） |
| PDF | ＋📝 ローカル編集・拡張の項目（下の注） |
| 画像 | ＋🔍 原寸で開く・📝 ローカル編集・🗜 写真を小さくする（JPEG だけ・§6a） |
| Excel（`.xlsx`） | ＋📝 Excel で開く・拡張の項目（同上） |
| CAD（DXF・STEP・rpcd・dwg・igs・x_t・slddrw） | ＋📝 CAD で開く |
| ZIP | ＋🗂 中身を見る・拡張の項目（同上） |
| 動画・音声 | 共通の2つだけ |
| ほか | ＋📝 ローカル編集 |

- 表の「拡張の項目」は、コアではなく拡張が足しています（例: 東邦の拡張の 🤖。2026-10-20 から。`window.wcms.onFileMenu`・`ext/toho/assets/toho.js`）。
  その拡張を外して組むと、その項目は出ません。
  どの形式に何を足すかは、拡張の【要求】へ移しました（東邦）。
- 拡張は、置き場所に応じて、ほかの項目も足します。
  例: 東邦の拡張が足す、改定の項目（📐。[【要求】東邦拡張.md](拡張/東邦/【要求】東邦拡張.md) §19）。
- ファイル表示の頭の行の住所と名前は、サーバーが画面の部品（クローム）の属性（`data-file-url`・`data-file-name`）で渡します。
  画面の部品は、保存しない、画面の飾り付けのことです。この属性も保存されません。
- 本文の 📎 リンク（例: 通信の拡張が取り込んだ本文の、添付へのリンク）の横の札は、▶ 表示（ZIP は ▶ 中身）と 🔗 参照です。閲覧モードだけに出ます。
  拡張のボタン（例: 東邦の 🤖）は、2026-10-20 から、リンクの横ではなく、拡張の鏡の中の添付の一覧に出ます
  （例: 通信の拡張の「記録の箱」。本文の印 `<section data-mirror="記録の箱">` にサーバーが描く鏡です。くわしくは [【要求】通信拡張.md](拡張/通信/【要求】通信拡張.md) §6）。
- 実装: `assets/app.js` の `openFileMenu`・`fileMenuItems`。形式を決めるのは `fileKindOf` です。
  📎 リンクの横の札は `refreshAttachmentPreviews` です。

## 6. 版と目録

- ⚠ **添付に版はありません。** 上書きすると、前のものは戻せません。
  だから、監査（誰が何をしたかの記録）では、**上書きを別の名前で記録**します。
- ⚠ いま: 「📝 ローカル編集」で上書きしたときだけは、前の中身が版に残ります（`files/.versions/`）。
- **目録 `files/meta.json`** に、届いたときの名前・保存日時・利用者・大きさ・SHA-256・由来を残します。
  SHA-256 は、中身から計算する、ファイルの指紋のような値です。
- **本文のリンク文字は表示名、目録は届いた事実**です。役割が違うので、**正本は2つになりません**。

## 6a. 写真を小さくする

> 2026-10-27 利用者:「では、添付の中で容量を取るファイル形式を調べ、ワンクリックで容量を小さくする方法を考えましょう」

- 写真（JPEG）を、長い辺が決めた大きさになるまで縮められます。
- 置き場は3つです（利用者の答え）。管理画面でまとめて・写真ごとの「⋯」・これから上げる写真は自動で。
- 大きさは長い辺 2000 px です（利用者の答え）。

⚠ **いま**（2026-10-27）:

- 大きさは設定 `photo_shrink`（`long_side`・`quality`）です。設定が無ければ縮めません。
- 縮めるのは、書き換えてよい写真だけです（ページへの書き込み権限があり、設定 `attachment_readonly` の範囲の外）。届いた添付は、届いた事実の証拠なので縮めません。
- ⚠ 縮める前の写真は、w-cms の中には残しません（残すと容量が減らないため）。元の写真は、夜の控えと社外の控えにあります。
- 目録 `files/meta.json` に、縮める前の大きさ・SHA-256・画素を `shrunk_from` で残します。中身の指紋で同じ写真かを確かめる道具が、縮めた写真を元の写真と見分けられるようにするためです。
- 「📝 ローカル編集」で上書きした写真は縮めません（人がわざと大きく置いたものかもしれないため）。
- PNG は縮めません。図や画面の写しが多く、JPEG にすると名前（拡張子＝住所）が変わるためです。
- 実装: `internal/cms/photo_shrink.go`（1枚・上げたとき）・`photo_shrink_all.go`（まとめて）・`assets/app.js` の `shrinkPhoto`・`assets/admin.js` の `loadPhotoShrink`。

## 8. ZIP の展開

ZIP の展開は、ZIP の中のファイルを取り出すことです。

- **ZIP を展開するのは、受信原本が ZIP を持っている取り込みの経路だけです。**
  受信原本は、届いたままの元のファイルのことです。どの経路かは、拡張の【要求】にあります。
- **人が手で落とした ZIP は、展開しません。**
- ⚠ **展開の処理を別の経路へ足すときは、同じ根拠が立つかを、先に確かめること。**
- **上限は3つです**（1件の大きさ・件数・合計）。ZIP 爆弾への対策です。
  ZIP 爆弾は、展開すると桁違いに大きくなるように作られた、悪意のある ZIP のことです。
