# 【考察】許可タグと属性

> 状態: **決定・実装ともに完了（2026-08-04）**。本文HTMLで「何を許可し、何を落とすか」の
> 判断基準と、現行リストの棚卸しをまとめた考察メモ。
> **決定した許可・拒否リストと理由の正本は [本文サニタイズ設計.md](本文サニタイズ設計.md) §5**。
> 本ファイルは「なぜそう決めたか」の検討過程を残すもの。
> 関連: [コンセプト.md](コンセプト.md) / [【考察】タグ設計.md](【考察】タグ設計.md) / [開発方針.md](開発方針.md)

## 0. 決定（2026-08-04）

**タグは寛容・属性は厳格**。要素は危険でなければ許可し、属性は必要なものだけ許可する。

| 論点 | 決定 |
|---|---|
| `span` | **残す**（`div` も残す） |
| `dl`/`dt`/`dd` 等 | **残す**。危険が無い限り落とさない |
| `b`/`i` の `strong`/`em` への正規化 | **行わない**（貼り付けた表現をそのまま保つ） |
| 見出し | **`h1`〜`h6` を使う**（目次・サニタイザ・エディタで統一） |
| `img` の外部URL | **不正**（相対URLのみ） |
| `video`/`audio`/`picture`/`source`/`track` | **含める。ただしURLは相対のみ** |
| ルビ `ruby`/`rt`/`rp` | 日本語の振り仮名のため**追加** |
| プロトコル相対URL `//host/…` | **拒否**（§3 ①の修正） |

**実装済み**。§3 の4件の不整合と、下記「実装上の含意」はすべて解消した。

### 実装上の含意（重要）— 解消済み

**着手前の状態**: エディタが保存できるのは `h1`/`h2`/`h3`/`p` とカスタム要素だけで、
`serializeBlock` がそれ以外に空文字を返して**破棄**していた。つまりサニタイザが許可している
`ul`・`table`・`blockquote`・`pre`・`hr`・`h4`〜`h6` は、**画面に出ても次の保存で消えていた**。

**やったこと**: 手書きの `TEXT_BLOCK_TAGS` を廃し、カスタム要素で既に確立していた
「宣言は1つ、両者がそれに従う」形（`/api/tag-schema`）へ寄せた。同APIは構造HTMLと
カスタム要素の**両方**を返すようになり、エディタはDOMを辿る汎用シリアライザで書き出す。
サニタイザ側の `structuralElements` を直すだけでエディタが追随する。

インライン装飾も `document.execCommand` をやめ、Range を直接操作して常に
`<strong>`/`<em>`/`<u>` を出す実装に置き換えた（[エディタ仕様.md](エディタ仕様.md) 4.1）。

実装の対応先:

| 決定 | 実装 |
|---|---|
| 許可リストの拡張 | [internal/cms/sanitize.go](../internal/cms/sanitize.go) `structuralElements` |
| リンクは外部可・埋め込みは相対のみ | 同 `linkURLAttributes` / `embedURLAttributes`・`safeLinkURL` / `safeEmbedURL` |
| 語彙の一元化 | `AllowedVocabulary()` → `GET /api/tag-schema`（`elements` / `void` / `block_id`） |
| 汎用シリアライザ | [assets/index.html](../assets/index.html) `serializeBlock` / `serializeNode` |
| `execCommand` 廃止 | 同 `toggleInlineFormat` / `tidyInline` |

## 1. なぜいま考えるか

インライン装飾（太字・斜体・下線）を**保存できるようにする**にあたり、許可リストが実際に効いてくる。
着手前は B/I/U ボタンが押せて画面上も変わるが、エディタのシリアライザが `innerText` しか出さないため
**保存されず、再描画で消えていた**（＝ボタンが事実上機能していなかった）。

同時に、現行の許可リストを棚卸ししたところ**4件の不整合**が見つかった（§3、いずれも実証済み）。
装飾対応と合わせて整理する。

## 2. 判断の物差し

既存の設計原則から、5つの基準を導く。

| # | 基準 | 由来 |
|---|---|---|
| **A** | **自己説明的か**——正本HTMLを読んだ人に意味が伝わるか。意味も属性も持たない入れ子はノイズ | [コンセプト.md](コンセプト.md)「HTMLが正本」「grep/diffが効く」 |
| **B** | **役割は属性・見える値は中身**か | [【考察】タグ設計.md](【考察】タグ設計.md) §2 |
| **C** | **安全か**——実行・外部通信・UI乗っ取りの経路にならないか | [本文サニタイズ設計.md](本文サニタイズ設計.md) |
| **D** | **往復で安定するか**——シリアライズ⇄サニタイズが冪等か。同じ見た目に2表現があると差分判定が揺れる | ブロック単位保存・アンドゥのスナップショット比較が壊れるため |
| **E** | **カスタム要素と役割が重複しないか** | `<m-tag>`/`<m-field>`/`<m-table>` が担う領域は素のHTMLで二重に持たない |

**Dは今回とくに重い。** 「変更が無ければ保存しない」判定とアンドゥのスナップショット比較は、
どちらもシリアライズ結果の文字列一致に依存している。表現が揺れると無駄な保存や誤ったアンドゥを招く。

## 3. 現状の棚卸しで見つかった不整合（実証済み → **すべて解消済み**）

> 解消の内訳: ①は `isRelativeURL` がプロトコル相対を拒否。②は `TEXT_BLOCK_TAGS` 廃止＋
> `/api/tag-schema` からの語彙取得。③は「タグは寛容」の方針で**残す**と決定（構造の境界として
> 意味がある、が結論。§4.4 参照）。④も同じく**両方残す**（貼り付けた表現を保つ）と決定し、
> エディタは常に `strong`/`em` を出すことで揺れを断つ（[エディタ仕様.md](エディタ仕様.md) 4.1）。

| # | 問題 | 基準 | 実証 |
|---|---|---|---|
| ① | **プロトコル相対URL `//evil.example/x` が通る** | C | `<img src="//evil.example/beacon.png">` が素通り。`safeURL` がスキーム空を「相対」と判定するため |
| ② | **`h4`〜`h6` が三者で食い違う** | D | 目次は h1〜h6 を拾い、サニタイザも通すが、**エディタの `TEXT_BLOCK_TAGS` が h1〜h3 のみ**。貼り付けた h4 は目次に出るのに次の保存で消える |
| ③ | **`div`/`span` が意味も属性も無いまま残る** | A | `<div><span>x</span></div>` がそのまま通る。`class`/`id`/`style` は落とすので、残っても情報量ゼロ |
| ④ | **`b`/`i` と `strong`/`em` が二重に許可** | D | 同じ見た目に2表現。エディタが片方を出し、貼り付けがもう片方を持ち込むと差分が揺れる |

①は**外部への情報漏れ**（閲覧者のIPと閲覧時刻が第三者に渡るトラッキングビーコン）になりうる。
中間版CSP `default-src 'self'` が実行時にブロックするが、二層防御の趣旨からは許可リストでも弾くべき。

## 4. 分類ごとの考察

### 4.1 ブロック構造

- **`h1`〜`h6`**: 目次が既に h1〜h6 対応なので、**エディタ側を h1〜h6 へ揃える**のが素直（②の解消）。
  スラッシュメニューは現状 h1 のみだが、`h2`/`h3` は日常的に使うので出す価値がある。
  h4以降は貼り付け由来で保持できれば十分。
- **`p` `br` `hr`**: 維持。`<br>` は現在 `innerText` 経由で改行文字に潰れているが、インライン対応で保持できる。
- **`ul` `ol` `li`**: 維持。`ol[start]` は使用頻度が低いが害もない。
- **`blockquote`**: 維持。ただし将来の **`<m-quote>`（他ページの引用）と紛らわしい**——前者はテキストの引用、
  後者はページ参照。[【一覧】カスタムタグ.md](【一覧】カスタムタグ.md) に書き分けを明記したい。
- **`pre` `code`**: 型番・寸法・識別子を等幅で見せる用途があるので維持。
- **`div`**: 落とすとブロック境界が消えて行が繋がる実害があるため**維持**。
- **`span`**: インライン装飾は `strong`/`em`/`u`/`s` が担うので、**属性を失った `span` は情報量ゼロ**。
  アンラップ（中身は残す）を提案（③の解消）。
- **`dl` `dt` `dd`**: **不採用**。「名前:値」は `<m-tag>`／`<m-field>` の領域（基準E）。

### 4.2 インライン装飾

- **`strong` `em` `u` `s` `code` に統一し、`b`→`strong`・`i`→`em` へ正規化する**（④の解消）。
  落とすのではなく**言い換える**のが要点——貼り付けた `<b>` の意図（強調）を保ったまま表現を一本化でき、
  往復が安定する（基準D）。正規化は「表現の統一」なのでサニタイザの責務として自然。
- **`u`**: リンクと紛らわしいが、ボタンがあるので維持。
- **`s`**: 打ち消し線。なお**ページの「取消」状態は `<m-tag name="状態">` が表す**（[タグ設計 §6](【考察】タグ設計.md)）。
  `s` は純粋な視覚表現として使う、と役割を分ける（基準E）。
- **追加候補 `sub` `sup`**: 単位・化学式（m³ 等）。製造業の文書では出番がある。
- **追加候補 `mark`**: ハイライト。無くても困らない。

### 4.3 リンクと画像

- **`a[href]`**: 相対・`http`・`https`・`mailto` を許可。**プロトコル相対を弾く**（①の解消）。
  - `target`/`rel` は**追加しない**。同一タブのままなら reverse tabnabbing の心配が無く、属性も増えない。
  - 追加候補 `tel:`（連絡先）。
- **`img[src]`**: **相対URLのみに限定する**ことを提案。
  - 外部画像はトラッキングビーコンになりうる（①と同じ懸念）。
  - しかも CSP `default-src 'self'` が実行時にブロックするので、**許可しても「壊れた画像」が出るだけで利益がない**。
  - `alt` は維持（アクセシビリティ）。`width`/`height` は表示に必要な指定として維持。

### 4.4 表

- **`table` `thead` `tbody` `tr` `th` `td`**: 維持。`th`/`td` の `colspan`/`rowspan` も維持。
- **生の `<table>` と将来の `<m-table>` は役割が違う**（基準E）。
  生 table＝貼り付けた資料としての表（意味づけ無し）、`<m-table>`＝業務明細（列に役割 `data-field`）。
  両立してよい。`<m-table>` はプラグインが `Tags()` で宣言するので**コアの許可リストは無変更**で済む。
- 追加候補 `caption`、`th[scope]`（アクセシビリティ）。優先度は低い。

### 4.5 グローバル属性

- **`data-id`**: 維持（ブロック識別）。
- **`class` `id` `style`**: **引き続き禁止**。`id` はシェルの要素を乗っ取れる（[本文サニタイズ設計.md](本文サニタイズ設計.md) §5.4）、
  `style` は CSP strict 化の方針に反する、`class` はクロームのCSSと衝突する。
- **`title`**: 情報が hover に隠れて自己説明性を損なう（基準A）ので、`a`/`img` 以外へは広げない。
- **`lang` `dir` `aria-*` `role`**: 現状用途が無いので不採用。必要になってから足す。

### 4.6 危険要素（現状維持でよい）

`script` `style` `iframe` `object` `embed` `form` `input` `button` `textarea` `select` `link` `meta`
`base` `svg` `math` `template` `noscript` `frame(set)` `applet` は部分木ごと削除のまま。
とくに **`base`**（相対URLの解決先を書き換えられる）と **`svg`**（中にスクリプトを書ける）は重要。

> `<m-file>` の PDF プレビューは `<embed>` を使うが、これは**コンポーネントが描画時に生成するクローム**であり
> 本文ではないので、サニタイズの対象外。整合している。

## 5. 提案する許可リスト（差分のみ）

| 変更 | 内容 | 基準 |
|---|---|---|
| **修正** | プロトコル相対URL（`//host/…`）を弾く | C |
| **修正** | `img[src]` を相対URLのみに限定 | C |
| **修正** | エディタを `h1`〜`h6` 対応にする（サニタイザ・目次と揃える） | D |
| **修正** | `b`→`strong`、`i`→`em` へ正規化 | D |
| **削除** | `span` をアンラップ | A |
| **追加候補** | `sub` `sup`、`mark`、`caption`、`th[scope]`、`tel:` | — |

## 6. 決定の記録と、残る検討事項

§0 のとおり決着した。提案のうち**採らなかったもの**とその理由:

- **`span` のアンラップ**（§4.1 で提案）→ **不採用**。「危険が無い限り残す」方針を採ったため。
  情報量ゼロという指摘は妥当だが、貼り付けた内容の構造を保つ利益を優先した。
- **`b`→`strong`・`i`→`em` の正規化**（§4.2 で提案）→ **不採用**。同じ方針による。
  なお正規化しなくても**往復の安定性（基準D）は保たれる**——シリアライザが DOM の内容を
  忠実に出力する限り、表現が2種類あっても文字列は一意に定まるため。
  正規化はあくまで表現統一の「あったら良い」であって、正しさの要件ではなかった。

**残る検討事項**

- スラッシュメニューに `h2`/`h3`（さらにリスト・表）を出すか。現状は `h1` のみで、
  他の見出しは貼り付けか手動でしか作れない。UIの作り込みの話なので別途。
- `<m-table>`（[【考察】タグ設計.md](【考察】タグ設計.md) §7）が入った後、生の `<table>` との
  使い分けをどう案内するか。役割は分かれている（資料の表 / 業務明細）が、編集UI上の導線は未設計。
