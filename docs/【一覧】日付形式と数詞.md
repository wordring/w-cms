# 【一覧】日付形式と数詞

DBスキーマ設計し直し（判断待ち D-3「**正規化はPDF取り込み時に行い、認識できた形式は
背景色で示す**」）の設計材料。**取り込み時の正規化と、語→型辞書・単位込み数量の設計**が
この一覧を参照する。

- 調査日: 2026-08-30。SQLite の受理形式は**実測**（SQLite **3.51.2**・`modernc.org/sqlite`
  ＝本番と同じドライバ。`SELECT date(?)` へ各形式を渡して確認）。各国の形式と数詞は
  一般知識の整理（2026-08 時点）。
- **決定（2026-08-30）: 日時の表記は ISO 8601 を w-cms 全域の正とする**（日付のみ
  `YYYY-MM-DD`・時刻付きは `T` 区切り）。利用者がプラグイン等で別表記に対応するのは自由。
  正本は [要件定義書.md](要件定義書.md) §3。
- 現行実装の対応状況は §4 にまとめた（`normalizeDate`・語→型辞書 `type_inference`・`vocabNumber`）。

## 1. SQLite が扱える日付形式（実測）

SQLite に日付**型**は無い。TEXT / REAL / INTEGER のどれかで持ち、日付**関数**
（`date()`・`datetime()`・`strftime()` 等）が特定の書式だけを解釈する。

| 入力 | `date()` の結果 | 備考 |
|---|---|---|
| `2026-06-15` | ✅ `2026-06-15` | **ゼロ詰め必須の ISO-8601** |
| `2026-06-15T14:30:05` | ✅ | **ISO 8601 準拠の時刻付き**（区切りは `T`。`:SS`・`.SSS` も可） |
| `2026-06-15 14:30` | ✅ | ⚠ **空白区切りは ISO 8601 ではない**（規格の区切りは `T`）。これは **SQL 標準の TIMESTAMP リテラル**の流儀で、SQLite はどちらも受ける |
| `2026-06-15T14:30:05Z` / `+09:00` | ✅ | タイムゾーン接尾辞も可 |
| `now` | ✅ 現在日 | `'localtime'`／`'utc'` 修飾子と併用 |
| `2461847.5`（数字列） | ⚠ `2028-03-17` | **ユリウス日として解釈される**（下の罠） |
| `1780000000` ＋ `'unixepoch'` | ✅ | UNIX秒は修飾子が要る |
| `2026-6-15`（桁詰めなし） | ❌ NULL | **1桁の月日は通らない** |
| `2026/06/15` | ❌ NULL | スラッシュ不可 |
| `2026.06.15` / `15.06.2026` | ❌ NULL | ドット不可 |
| `20260615` | ❌ NULL | 区切りなし不可 |
| `06/15/2026`（米式） | ❌ NULL | |
| `2026年6月15日` / `R8.6.15` | ❌ NULL | 和文・和暦不可 |

**要点**:

1. **日本の業務文書に現れる形は、ほぼ1つも直接は通らない**。取り込み時の正規化が必須
   （D-3 の決定「入り口で揃える」はこの実測と整合する）。
2. **正規化の出力はゼロ詰め `YYYY-MM-DD` 一択**——SQLite の関数がそのまま食え、
   **TEXT の辞書順比較＝時系列順**になる（`BETWEEN '2026-01-01' AND '2026-12-31'` が
   効くことを実測済み）。人が読め・grep が効くのも「文書が主」と同じ精神。
3. **罠: 数字だけの文字列を日付関数へ渡すとユリウス日になる**（`"2461847.5"` →
   2028-03-17）。「日付らしき値」を未検証のまま SQLite の日付関数へ渡してはいけない——
   **正規化済みの値だけを日付として扱う**こと。
4. 扱える範囲は `0000-01-01`〜`9999-12-31`。うるう秒なし・グレゴリオ暦を過去へも外挿。

## 2. 各国の一般的な日付形式

| 方式 | 例 | 主な使用地域 | 備考 |
|---|---|---|---|
| ISO 8601 | `2026-06-15` | 国際規格・技術文書 | w-cms の正規形 |
| 年月日（和文） | `2026年6月15日` | 日本・中国 | 中国は `2026年6月15日` も `2026-06-15` も |
| 年/月/日 | `2026/06/15`・`2026/6/15` | 日本 | **年が先頭なら曖昧性なし** |
| 和暦 | `令和8年6月15日`・`R8.6.15` | 日本（役所・帳票） | 換算表は下 |
| 月/日/年 | `06/15/2026`・`6/15/26` | 米国 | |
| 日/月/年 | `15/06/2026` | 英国・仏・豪ほか多数 | |
| 日.月.年 | `15.06.2026` | 独・露・北欧ほか | |
| 年. 月. 日 | `2026. 6. 15.` | 韓国 | `2026년 6월 15일` も |

**曖昧性の核心は「01/02/03 問題」**——米式なら2003年1月2日、欧式なら2003年2月1日、
ISO短縮なら2001年2月3日。判定規則として使えるのは:

- **先頭が4桁なら年**（`2026/6/15` は Y/M/D と断定できる）——日本のスラッシュ形は
  ほぼ常にこの形なので、実務上の曖昧性は低い。
- 2桁始まり（`6/15`・`15/06/2026`）は**文脈（地域・書き手）が無いと決められない**。
  日本の社内文書の `6/15` は月/日＋年省略が通例。

**和暦の換算**（元年＝1年）:

| 元号 | 記号 | 西暦の始まり | 換算 |
|---|---|---|---|
| 明治 | M | 1868 | 明治N年 = 1867+N |
| 大正 | T | 1912 | 大正N年 = 1911+N |
| 昭和 | S | 1926 | 昭和N年 = 1925+N |
| 平成 | H | 1989 | 平成N年 = 1988+N |
| 令和 | R | 2019 | 令和N年 = **2018+N** |

**実データ（板金部ノート）で観測された形**: `2026-06-15`（自由文中・ISO準拠！）・
`2024-08-20`・`2024-09-XX`（**日未定**の月表記・セクション名）・`2025-10-27`。
納期には「9月末」「上旬・中旬」のような**範囲語**も来うる（希望納期タグは自由記入）——
これらは単一日付へ正規化できないので、**正規化不能として原文のまま**が正しい扱い
（値の正本は常に原文・`norm_value` は併記、という既存の決定と整合）。

## 3. 数値の後に付く数詞（と、前に付く記号）

### 3.1 助数詞（個数を数える語）

製造・受発注で現れる主なもの:

| 助数詞 | 数えるもの | 備考 |
|---|---|---|
| 個 | 汎用（部品） | 最頻。実測: `5個`・`60個単位` |
| 本 | 細長い物（丸棒・パイプ・ボルト） | |
| 枚 | 薄い物（**板**・シート） | 板金業の主役 |
| 台 | 機械・装置 | 実測: `一台15分程度` |
| 組・対・セット | 組み合わせ | |
| **式** | 一式（まとめて1つ） | **見積の単位として頻出**（`一式` は数量1の意味） |
| 点・件 | 品目・案件 | |
| 束・巻・箱・袋・缶 | 荷姿 | |
| 基・脚・面・丁 | 据え付け物・脚物ほか | |
| ロット | 製造単位 | 実測: `ロット20`（**列名にも埋まる**） |
| 球 | 製品固有（ボール数） | 実測: `170球`——**運用者固有の助数詞は無限にある**という実例 |

### 3.2 単位（計量・通貨）

| 分類 | 単位 | 備考 |
|---|---|---|
| 通貨 | 円・万円・千円 | `3,500円`・`1.2万円`。**単位なしの円も多い**（実測: `3500`・`1172` が円） |
| 長さ | mm・cm・m | **図面は mm が既定で単位省略が普通**（実測: `t9*44*360` ＝板厚×幅×長さ・全部mm） |
| 重さ | g・kg・t（トン） | ⚠ 板金の `t` は**板厚**が優勢（下の前置記号） |
| 面積・体積 | mm²・m²・L・cc | |
| 時間 | 分・時間・日・週・ヶ月・年 | 実測: `30時間`・`90分` |
| 率・角度 | %・割・度 | |
| 回転数など | rpm | 実測: `892rpm` |

### 3.3 前置の記号（数値の**前**に付く）

| 記号 | 意味 | 実測例 |
|---|---|---|
| ¥ | 円 | `¥8,000`（`vocabNumber` が対応済み） |
| Φ・φ | 径 | `Φ410`・`Φ50.5` |
| **t** | **板厚**（mm） | `t2.3`・`t4.5`・`t9*44*360` |
| R | 半径・（文脈により）曲げR | |
| M | ねじの呼び径 | `M8`・`M10` |
| l= | 長さ | `PS-314-3(l=884)` |
| No. | 番号 | 明細表の列 |

**前置記号の値は「数量」ではなく「仕様値」**——Φ410 は個数でなく寸法の属性。数値としての
抽出はできるが、意味は列見出し（見える文字）が決める。ここでも「鍵は見出し」の原則が効く。

### 3.4 パースを難しくする表記（正規化の敵リスト)

- **桁区切り**: `3,500` ／ **全角数字**: `５個` ／ **漢数字**: `五個`（表では稀）
- **万・千の混在**: `1万2000円`・`1.2万円`
- **範囲**: `5〜10個`・`5-10個` ／ **約**: `約20`・`20程度`・`20くらい`（実測: `深さ8.5程度`）
- **複合単位**: `円/個`（単価）・`個/台`（員数）
- **数値と単位の複合語**: `60個単位`（「60個ずつ買う」＝数量ではなく条件）

## 4. 現行実装の対応状況と、取り込み正規化への含意

| 実装 | いま読める形 | 読めない形（この一覧が埋める穴） |
|---|---|---|
| `normalizeDate`（[vocab.go](../internal/cms/vocab.go)） | `2026-06-15`・`2026/6/15`・`2026年6月15日`（→ゼロ詰めISOへ） | 和暦・ドット区切り・年省略（`6/15`）・月まで（`2024-09`）・範囲語（`9月末`） |
| 語→型辞書 | 既定値は date が `納期`・`日付`・`検査日`・`発注日`・`納品日` の**5語** | `加工日`・`出荷日`・`受注日`・`見積日` 等。**辞書は `data/settings.json` へ移したので、運用者がファイルへ足してDB再構築すれば増えます**（2026-08-30 実装） |
| `vocabNumber`／`normalizeNumber`（[vocab.go](../internal/cms/vocab.go)） | `¥8,000` → 8000・`3500円` → 3500（`¥`・桁区切り・全角・末尾の「円」を吸収） | **`5個` のような助数詞込み**（「円」以外の単位・助数詞を剥がす処理が無い） |

**D-3 の決定への接続**——「正規化はPDF取り込み時に行う」ので、この一覧の主戦場は
**取り込み側の変換辞書**になる（和暦→西暦・単位剥がし・全角→半角・桁区切り除去）。
手書きページには引き続き `normalizeDate`／語→型辞書が効くため、**辞書を増やせること**が要る。
ユーザーの決定（2026-08-30）:「**運用中に増やしてDB再構築します**」——これを受けて辞書は
Goコード内の map から **`data/settings.json`** へ移した（同日実装）。Goコード内の値は
**既定値**として残り、ファイルが無いときの初期内容として書き出される。
「認識できた形式は背景色で示す」は、この一覧の**どの形が認識されたか**を書き手へ返す
仕組みとして設計する。

## 5. 比較の三分類（2026-08-30 ユーザー確認）

> 「SQLiteに格納する場合、文字列として比較、数値として比較、時間として比較の
> 三分類で良いでしょうか」——**意味の分類としては3つで正しい**。SQLite に日付型は
> 無いので、格納クラスは実質2つ（TEXT と数値）に落ち、意味の型3つがその上に乗る。

| 分類 | 格納 | 注意 |
|---|---|---|
| 文字列 | TEXT | 比較はバイト順（BINARY 照合）。等値・前方一致は十分だが**五十音順にはならない**。全角/半角は比較前に正規化（取り込みの担当） |
| 数値 | **INTEGER / REAL** | **TEXT に入れると壊れる**（`"8000" < "900"`）。number 型は `norm_num REAL` へ分けて格納する（**2026-08-30 実装**・下の (b) 案）。`norm_value`（TEXT）は date の時系列比較と表示用に残る。`CAST` は非数値→0.0 の罠があり不採用 |
| 時間 | TEXT（ゼロ詰めISO） | 正規化済みなら**文字列比較に畳める**（`BETWEEN` 実測済み）。分類として独立させる価値は比較でなく**検証・正規化規則・UI**の側 |

三分類に乗るもの: enum（状態）＝文字列の等値・進行順は業務知識なのでDBへ持ち込まない／
真偽＝enumの特殊形／期間・工数（90分）＝**数値**（時点ではない）／仕様値（Φ410）＝数値。
**採らない4つ目**: 自然順（Rev.2 < Rev.10。文字列比較では逆転する）——この規模で必要に
なる根拠が無いので明示的に不採用。

数値を数値クラスで持つ実装は (a) `norm_value` 1列に混在（SQLite の柔軟型付けでは正当・
数値は常にテキストより前に整列）(b) `norm_num REAL` の分離、の2案。**内部判断**として
設計時に決める（分離が自己文書的で有力）→ **(b) を採用・実装済み**（2026-08-30。
[vocab_index.go](../internal/cms/vocab_index.go) の `vocab_index.norm_num REAL`）。
