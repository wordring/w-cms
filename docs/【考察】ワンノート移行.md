# 【考察】ワンノート移行

現在ワンノートで回している業務を w-cms へ移すために、**実物のノートを読み取って
「w-cms 側に必要な受け皿（スキーマ的な条件）」を洗い出した**調査の記録です。
移行スクリプトの設計はまだしません——ここに書くのは**実測値と、そこから決まる条件**だけです。

- 調査日: 2026-08-25。OneNote デスクトップ版の COM（`GetHierarchy` / `GetPageContent`）を
  **読み取り専用**で使用（ワンノート側への書き込み・削除は一切なし）。
- 対象: 全4ノート1,522ページを取得したうえで、**現在運用中の「板金部」ノートに絞って分析**
  （2026-08-25 ユーザー確認:「今運用しているのは板金部というノートのみです」）。
- 実行できること自体は 2026-08 中旬に確認済み（4ノート・当時1,514ページの列挙と本文取得）。
  実施は**運用開始後・画像アップロード実装後**の予定。

## 2. 事実上のスキーマ（発見された定型）

紙の帳票が無いだけで、実質は帳票運用だった。頻度順に:

**① 部材表（横持ち・1行目が鍵）——471件**

```
材質 | 形状 | 寸法 | 個数 | 単価（ロット） | 単価（ロット1）倉橋 | 単価（ロット1）杉田 | 備考
```

**列名がデータを運んでいる**のが要点——業者名（倉橋・杉田）とロット数が列名に埋め込まれ、
ページごとに変わる（ロット1・5・6・7・15・20・40・100 の変種を確認）。

**② 工程表（縦持ち・第1列が鍵）——497件（変種計）**

```
工程   | 数 | 単位 | 備考          ← 1行目
ロット |    | 個   |               ← 鍵は第1列にある
材料   |    | 円   |
ブランク・ドリル・ブレーキ・組み立て …
```

`工程|工数|備考`（102件）や、列側にロットを並べる `工程|ロット6|ロット7|ロット20|備考` の変種もある。

**③ 発注明細表——22件**: `No.|部品番号|品名|サイズ|図面番号|数量|単位|単価|金額`。
w-cms の受注明細（`client-order-items`）とほぼ同型。

**④ 図面番号はハイフン連結の複合キー**: `W120-P211-86-03`・`Q090-01-05（架台）`・
`KHT-NKH-0032-BARI` など。**ワンノートがこれを検索できないことが w-cms の動機の1つ**
（[要件定義書.md](要件定義書.md) §4.4 の検索）。

## 3. スキーマ的な条件（w-cms 側に必要な受け皿・重い順）

1. **画像アップロードが移行の絶対前提**——4,825枚・86%のページ。規模が判明したことで、
   [要件定義書.md](要件定義書.md) §2.6（未実装・作業引き継ぎ9番）の優先度の根拠になる。
   印刷イメージ1,120枚は原本PDFが添付されていれば移行対象から外せる（XPSの裏ファイル972個も同様）。
2. **OCRテキストの受け皿**——移行で捨てると、図面画像の中の文字（図面番号など）が
   引けなくなり**「検索を付けたワンノート」なのに検索が後退する**。画像に付随する
   検索可能テキストの置き場（索引に載る形）が要る。形式は未決（`figcaption` か、
   画像コンテナ内の本文テキストか）。**鍵は「見える文字がすべて」との整合**——
   隠しテキストにすると原則が破れる点に注意。
3. **縦持ち表（第1列が鍵）の語彙**——現行の表語彙は**1行目を見出し行として読む**だけ
   （[vocab_index.go](../internal/cms/vocab_index.go) `syncVocabTable`）。2番目に多い定型
   （工程表497件）が索引に載らない。「鍵は第1列」型を語彙へ足すか、移行時に横持ちへ
   転置するかの決定が要る（3値［数・単位・備考］を持つため `dl`（名前：値）では潰れる）。
4. **添付の許可拡張子**——現行は **`.pdf` のみ**（[pdf_handler.go](../internal/cms/pdf_handler.go)
   `allowedAttachmentExts`）。実データは `.dxf`(389)・`.rpcd`(251)・`.xlsx`(175)・`.zip`(54)・
   `.docx`(42)・`.dwg`・`.step`・`.x_t`・`.slddrw`・`.igs`・`.eml`・`.pub`・`.lbx`・`.mp4` の計15種で、
   **約950件のCADデータ等が今の w-cms には入らない**。拡張子を絞る設計意図（サイドカー
   `<id>.meta.json` の上書き防止＝権限昇格の遮断）は、`.json` を許可リストへ入れない限り
   拡張しても保てる。
5. **可変列名は汎用索引でしか受からない**——`単価（ロット20）倉橋` のような列名は
   硬い列スキーマ（`price INTEGER`）では表現できず、`vocab_index`（ページID・表のID・
   名前・値）なら**そのまま入って、そのまま引ける**。スキーマ設計し直し（作業引き継ぎ13番）で
   検討中の「名前：値」汎用索引への一本化案を、実データが裏付けた形。業者名もロット数も
   **見えるところに書いてある**——「見える文字がすべて」と同じ向き。

## 4. 楽観できる材料（「無い」と確認できたもの）

- **ページ間リンクの書き換え問題は実質存在しない**（`onenote:` リンク2件のみ）。
  外部リンクは `a[href]` でそのまま通る。
- **自由配置の線形化はほぼ自明**——1ページ1アウトライン（本文枠）が基本で、
  複数枠のページはごく少数（位置でソートすれば足りる）。サブページも0。
- **階層は `parent_id` ツリーでそのまま受かる**（最大7段）。セクショングループ／
  セクションは本文の無い「分類ページ」になる——**葉だけがテンプレート**という判定
  （[【考察】ページテンプレート.md](【考察】ページテンプレート.md)）とも整合。
- **手書きインク（3ページ）は画像化で足り、ワンノートのタグ機能（6個）は無視できる規模**。
- **「テンプレート」という名前のページは存在しない**——テンプレート置き場の名前駆動判定と
  衝突しない。
- タイトルの重複（全ノート横断で208種。「まとめ」×73・「印刷イメージ」×33 など）は、
  w-cms がページを数字IDで識別するため問題にならない。

## 5. 未決（移行設計を始めるときに決める）

1. **OCRテキストの置き場の形式**（条件2）——「見える文字がすべて」と両立する形。
2. **縦持ち表を語彙で受けるか、転置するか**（条件3）。
3. **セクショングループ／セクションを分類ページへ写すときの本文**——空にするか、
   子ページ一覧（`child-list`）を1つ置くか。
4. **印刷イメージの扱い**——原本PDFありは再生成・なしは画像として取り込み、の切り分け。
5. **ごみ箱25ページ**は移行対象外でよいか。

## 6. 再調査の手順（生データは残していない）

取得した生XMLはセッションの一時領域にしか無いが、**同じ調査は読み取り専用でいつでも再実行できる**:
PowerShell から `New-Object -ComObject OneNote.Application` を作り、`GetHierarchy("", 4, [ref]$xml)`
で階層、ページごとに `GetPageContent($id, [ref]$c, 0)` で本文XMLを得る（全1,522ページで約3.5分）。
**`UpdatePageContent` 等の書き込み系は使わないこと。**
