# 【要求】権限

**認証・認可・公開・監査**の要求仕様です。

> **書くのは利用者**、**矛盾を指摘するのがエージェント**（開発方針 §2）。
> 本書は **2026-09-23 に [要件定義書.md](旧文書/要件定義書.md) の §2.3・§4.1 から抜き出したもの**です
> ——⚠ **利用者が読んで直すための下書き**です。

⚠ **2種類のことが書いてあります。** （印なし）＝**要求**（利用者が直す）、
⚠ **いま**＝**実装の現状**（エージェントが直す）。
**なぜそうしたか**は [認証認可設計.md](旧文書/認証認可設計.md) が正本。

---

## 1. 認証

- **アプリ単体で管理**します（SSOへ委譲しない）。⚠ 将来の委譲（MFA・SSO/OIDC）は
  接合点だけ予約してあります。
- パスワードは **argon2id** でハッシュ。
- **総当たり対策**（バックオフ／ロックアウト）と、**利用者の列挙対策**
  （⚠ **存在しない利用者でも同じ計算量を消費する**）を備えること。
- セッションは **256bit トークン**（DB側はハッシュ保存）、Cookie は
  `HttpOnly`/`Secure`/`SameSite=Lax`。
- **「最後の操作から8時間」で失効**すること（アイドル基準へ一本化）。
  ⚠ **失効の数分前に画面で告知すること**——⚠ **いま**は**どちらも未実装**（2026-08-21 決定）。実装は旧来の
  **「ログインから8時間の絶対期限」＋「30分操作が無ければ失効」**のまま（`internal/auth/session.go` の
  `sessionAbsoluteTTL`・`sessionIdleTTL`。Cookie の寿命も絶対期限の8時間で、ログイン時に1度だけ発行する）
  ——操作していても**ログインから8時間で切れ**、30分席を離れても切れる。直し方は [認証認可設計.md](旧文書/認証認可設計.md) §2.2a。
- **初期管理者**は環境変数で、**利用者が空のときだけ**作ること。

⚠ **パスワード変更で既存セッションは切りません**（ユーザー:「書きかけが保存できないほうが
困ります」）。締め出しは「利用停止」が受け持ちます。

## 2. 認可——ページ単位の Unix 風モデル

- **read/write の2ビット × owner/group/other の3クラス**（mode は `"330"` のような3桁文字列）。
- **子ページの作成には親ページの write を要求**します（ディレクトリ書き込み相当）。
- chmod/chgrp は **owner または admin**、chown は **admin のみ**。

### ⚠ 権限の正本はサイドカー

権限の正本は **`<id>.meta.json`** で、**書き込めるのは権限変更の口とページ新規作成だけ**です。

⚠ **本文保存の口は権限に一切触れないこと**——**自己認可の構造的な防止**です
（本文を保存する操作で自分の権限を書き換えられてはいけません）。

⚠ **いま**: 認可の**読み口はサイドカーではなく `cms.db`（派生）**です。
ずれたら認可は索引に従います。⚠ **派生から正本へは書き戻しません**
（サイドカーが読めなければ止まる）。

## 3. 匿名公開

- **mode と独立した `public` フラグ**で制御します。
- **実効公開＝自分の public ∧ 全先祖の public**（パスゲート）。
  ⚠ **ルート `000000` の非公開化が、サイト全体のキルスイッチ**になること。
- **新しいページの `public` は常に false**（フェイルクローズ）。
- 匿名は **read 専用**。
- ⚠ **匿名には「読めない」と「存在しない」を区別させない**
  （[【要求】ページとエディタ.md](【要求】ページとエディタ.md) §1）。
- 戻り先は**同一サイト内の絶対パスだけ**に絞ること。

## 4. 監査

**書き込み・権限変更を記録し、admin が閲覧できること。**

**認証イベント（ログインの成功・失敗・ログアウト）も記録対象**です。

> 2026-08-21 ユーザー:「**誰が事務所の外から入ってきたか知る必要があると思います。**」

- 「どこから」を満たすため、認証イベントには**接続元アドレス**も残します。
- ⚠ **詐称できないようにすること。** 本番はリバースプロキシの背後なので `X-Forwarded-For` を
  見ますが、⚠ **前段がプロキシ（ループバック／私設アドレス）のときだけ採用し、
  末尾＝直近のプロキシが足した値**を使います。
- 記録するもの: 本文の保存・権限変更・**ページの新規作成**・**添付の保存と上書き**
  （⚠ **上書きは別の名前で記録します**——添付の上書きは復元できないため）・**索引の全再構築**。

⚠ **監査ログで「5年遡れること」は満たせません**（[【要求】ページとエディタ.md](【要求】ページとエディタ.md) §4）。

## 5. 本文の安全

### サニタイズは二層

**保存時＋描画時**の許可リスト方式で、**サニタイザは冪等**であること
（`Sanitize(Sanitize(x)) == Sanitize(x)`）。

⚠ **保存時は除去結果をエディタへエコーバックして利用者に通知すること**
——黙って消すと、書いたものが消えたことに気づけません。

### 「タグは寛容・属性は厳格」

| | 方針 |
|---|---|
| **要素** | 構造HTML（h1〜h6・リスト・ルビ・表・`details`・`video`/`audio`）は**広く許可** |
| | `script`/`style`/`iframe`/`form` 系は**部分木ごと削除** |
| **属性** | `on*`・`style`・`id`・`class` は**常に拒否**（例外は `data-id`・`data-type`・`data-ref`） |

⚠ **`input`・`button`・`select` も削除対象**です（入力欄の偽装）
——**本文に偽のログインフォームを書ける穴**を塞ぐため。
⚠ **だからチェックボックスは本文に書けません**（[【要求】タグと表.md](【要求】タグと表.md) §10）。

⚠ **`data-type` は属性名だけを要素限定で許可し、値は検査しません。**
**レジストリは編集支援と検証の語彙であって、安全性の門ではありません**
——この分離があるから、将来レジストリを実行時に編集できるようにしても危険な要素は増えません。

### URLの規則

| どこ | 許す形 |
|---|---|
| リンク（`href`・`cite`） | 相対・http・https・mailto・tel |
| **埋め込み**（`img src` 等） | ⚠ **`/data/` 配下ときれいなURLに限る** |

⚠ **リンクは制限していないので、クロームがリンクから埋め込みを導出するときは形を必ず検査すること。**

### そのほか

- **CSP を全レスポンスへ付与**すること。⚠ **いま**は **strict 版**（`'unsafe-inline'` なし）で、
  インラインの `script`/`style`/`on*=` は**書けません**。
- **CSRF は Origin/Referer とリクエストホストの一致検証**（GET/HEAD/OPTIONS 以外）。
  ⚠ **ヘッダが無ければ拒否**（フェイルクローズ）。
- ⚠ **フロントのDOM生成は `createElement`＋`textContent`。**
  **値を文字列連結して `innerHTML` へ入れないこと**——`escapeAttr` 頼みの保存型XSSが
  **実際に発火した過去があります**。
- ⚠ **サニタイズ後にHTMLを足す関数は、自前でエスケープ責任を負います**
  （`RenderComputedViews`・`RenderAnchors`・`RenderPageShell`・`RenderReferenceLinks`）。
  **破れると保存型XSS**です。
- **本番は TLS/HTTPS 必須**（リバースプロキシで終端）。
  ⚠ **Secure Cookie の無効化は、ローカル検証のときだけ。**

**認証**（→ §1）

- **利用停止は次のリクエストで即座に効く**——パスワード変更でセッションを切らない以上、盗まれた Cookie を止める手段はこれだけ
  （認証認可設計.md:142-150・381-387）。
- **セッションの失効——利用者の元の言葉**「操作が8時間無ければログアウトにしては？ログアウト数分前に告知するのも良いと思います。」
  （認証認可設計.md:86）。決めた理由: 共用の端末で8時間生き続けることを承知のうえで、「勝手に切れて作業を失う」ほうを重く見た。
  未決: 告知の「数分」の値・失効時間を設定で変えられるようにするか（同:94・125・127-133）。→ 理由は【考察】へ
- **ログインの同時実行を制限する**（argon2id は1件 64MiB——同時4件で約 256MiB）。本番に入る前に、実機で反復回数を較正する
  （1件 0.3〜0.5秒）（認証認可設計.md:63-72）。⚠ いま: 同時実行の制限は実装済み（4件）・較正はまだ。
- **認可はログインの方式に依存しない**（内部の利用者＝名前＋グループ）。後から SSO を足しても認可は直さずに済み、ローカルの認証と
  併存できる（認証認可設計.md:177-192）。⚠ いま: 備えのうち実装にあるのは `password_hash` の NULL 許容と `GroupsFor` だけ
  （`Authenticator` のインターフェースと `user_identities` の表は無い）。
- **プロキシ由来のヘッダ（X-Forwarded-For／-Proto／-Host）は、前段がプロキシのときだけ信じる。** 監査の接続元と公開ページの
  基底URLで同じ判定を使う（ずれると片方だけ詐称できる）（認証認可設計.md:155-156・189・419-427）。→ §4 を一般化
- （低）ログアウトと期限切れでは、サーバー側でセッションを消す（認証認可設計.md:79-81）。

**認可と公開**（→ §2・§3）

- **新しいページの既定**（2026-06-20 確定）——owner＝作成者・group＝作成者の主グループ・mode は既定 `330`（other＝なし——明示して
  共有しない限り、無関係な利用者には見せない）・子ページは group と mode を親から継承する（setgid 相当）
  （認証認可設計.md:224-229・344-345・470-479）。⚠ いま: 既定の mode を設定で変えるのは未実装。
- **ページ単位の見せ分けを使い、集計から読めない行を落としたことは知らせない（C案）。** 利用者「Cでお願いします。」（2026-08-21・
  選択肢は A＝社内は全員見てよい／B＝見せ分けは使うが欠けを明記／C＝見せ分けは使い今のまま）。代償は、表の数字が人によって違い、
  それが本人に分からないこと（認証認可設計.md:362・370-375）。→ §2（または【要求】タグと表 §14 の隣）
- **認証済みの read/write はページごとに独立で、先祖を辿らない**（辿るのは匿名公開だけ——意図した非対称）。付随して、権限の無い
  上位ページの名前が見えている件は未対処（認証認可設計.md:540-544・375-376）。
- **公開の切り替え**——切り替えられるのは owner か admin。公開フラグは非破壊・可逆（親を非公開にしても子のフラグは書き換えない）。
  親が非公開のまま公開しようとしたら断り、理由を言う。親を非公開にするときは「配下 N ページが実効非公開になります」と見せて
  確かめる。切り替えは owner/admin にだけ見せ、編集モードで操作する。ページ自身のフラグと実効値を出し分ける
  （認証認可設計.md:455-468・エディタ仕様.md:795）。⚠ いま: 最後の確認は未実装・断る側は実装済み。
- （低）実効権限の判定は admin → owner → group → other の順で、当たった最初のクラスの桁だけで決める（認証認可設計.md:217-222）。
- （低）サイドカーが無いページは、読むとき admin 所有・既定の mode として扱う（フェイルクローズ）。書く操作は止める
  （認証認可設計.md:257・333）。

**監査**（→ §4）

- **監査の規律**——記録に失敗しても本処理は止めない・閲覧は記録しない（要るようになってから）・ログインに失敗したとき、入力された
  パスワードは残さない（認証認可設計.md:348・394-396・430-431）。
- **記録するものの列挙に、ページの削除・版の書き戻し・親の付け替え・利用者とグループの管理が無い**（総則「書き込み・権限変更」には
  含まれる・認証認可設計.md:398-413）。⚠ いま: コードはさらに多くを記録している（`dav.write`・`data.reset`・`local-edit.*` など）。

**本文の安全**（→ §5）

- **本文に書ける文字は「表示」以上の力を持たない**（不変条件）——スクリプト・外部への通信（画像1枚も含む）・アプリの口を叩く・
  画面を覆う・入力欄を偽装する・他人の権限で読む、のどれも起こせないこと。いちばん大きな相手は「本文を書ける全利用者」
  （コピペ1回で事故になる）（セキュリティ設計.md:21-33・39-49）。→ §5 の冒頭
- **三枚重ね**——サニタイズ・配信ヘッダ・CSP は独立した層で、どれか1枚が破れても止まること。サニタイズは CSP の代わりにならず
  （偽のログイン欄・`dialog`・`id` の乗っ取りは CSP では止まらない）、逆も同じ。本文に `style=` を通す例外を作らない（作れば
  `style-src` を緩めることになる）（セキュリティ設計.md:53-63・本文サニタイズ設計.md:3-10・36-39・65-70・381-385）。
- **保存と描画のほかに、本文の取得（`/api/load`）と版の取り出し・書き戻しもサニタイズを通す。無検査で正本へ書く入口を作らない**
  （2026-08-20・発端は `id="w-…"` で殻の要素を乗っ取れたこと・本文サニタイズ設計.md:45-63・セキュリティ設計.md:190）。
- **本文の生のHTMLを返す口は `text/plain`＋`nosniff`**（URL を直接開いても実行させない・アーキテクチャとDBスキーマ.md:287）。
- **状態を変える口は GET で受けない**——CSRF の検証は GET を見ないので、GET で状態が変わる口があると、本文の
  `<img src="/api/logout">` 1つで全員がログアウトした（2026-08-21 の事故）・`<img src="/api/new-page?…">` で閲覧者にページを
  作らせられた（認証認可設計.md:161-164・セキュリティ設計.md:35-37・アーキテクチャとDBスキーマ.md:550・エディタ仕様.md:501-505・
  解体前 l.444-448）。→ CSRF の行。⚠ いま: 実装済み（`method_guard_test.go`・`route_guard_test.go`）。
- **未知の要素はアンラップする**（要素は捨て、子と文字は残す——知らないタグで本文が消えない）（本文サニタイズ設計.md:125-127・
  206-208・エディタ仕様.md:481）。→「タグは寛容」の表
- **削除する要素の全体と理由**——`base`（相対URLの解決先の乗っ取り）・`link`・`meta`（外部の読み込み・refresh での飛ばし）・
  `template`（走査から外れる）・`dialog`（画面を覆う）・`noscript`・`frame` 類・`object`・`embed`・`applet`・`svg`・`math`・
  `textarea`・`option`（本文サニタイズ設計.md:148-160）。⚠ 【一覧】語彙 §1.1 は許可範囲の正本を本文サニタイズ設計 §5.4 と
  している——旧文書を消すなら、この表の置き場が要る。
- **利用者に見える許可属性の決め**——動画・音声の `autoplay` は許さない（勝手に再生させない）・`a` の `target`/`rel` は許さない
  （同じタブで開く）・`a[download]` は許す・貼り付けた `b`/`i` を `strong`/`em` に直さない・`div`/`span` は属性を失っても残す・
  `title` は `a`/`img` だけ（本文サニタイズ設計.md:169・173・184・186・457-466）。
- **本文の `id` は全要素で許す**（ページ内リンクが書ける）。殻の接頭辞 `w-` は無くなるまで繰り返し剥がし、剥がしたら保存の応答で
  告知する（拒否はしない）。空になったら属性ごと落とす（2026-08-20・本文サニタイズ設計.md:241-254・269）。
  ⚠ 上の §5 の表「`id` は常に拒否」と食い違う。
- **マーカー属性**——`data-src` の値は参照先だけ（状態の値を入れない・検査は埋め込みと同じURLの規則）。`data-mirror` は値を検査
  しないが、登録されていない名前は描かない（本文サニタイズ設計.md:287-302）。→ 例外の列
- **URL を取る属性を足すときは「リンク（外部可）」か「埋め込み（この w-cms の中だけ）」かを必ず決める**——埋め込みを外部可に
  しない（トラッキングの目印になる）。マーカー属性は要素限定を崩さない（本文サニタイズ設計.md:294-297・409-412）。→「URLの規則」
- **本文に貼る画像は、この w-cms へアップロードしたものだけ。** 問い「本文に貼る画像は、この w-cms へアップロードしたものだけで
  足りますか」に利用者「限ってよいです」（2026-08-21・本文サニタイズ設計.md:314-335）。帰結: 外部サイトの画像は本文に埋め込めない。
  →「URLの規則」の埋め込みの行の理由
- **「これを画面に出したい」の判定の手順**——①ブラウザが素で描けるか ②本文に書ける要素か ③書けなければマーカー方式
  ④宛先URLは機械が組み、書き手には ID だけ選ばせる ⑤配信の口が読み手の権限を見ているか（セキュリティ設計.md:71-99・139-149）。
  手順そのものは【ガイド】向きかもしれない。
- **CSP の目的**——外部への送信・読み込みを塞ぐ（`default-src 'self'`）・他サイトの枠に入れさせない（`frame-ancestors`）・
  nonce を使わずヘッダを定数に保つ（公開キャッシュと両立させるため）（本文サニタイズ設計.md:360-379・482-494）。
  ⚠ 上の「いまは strict 版」は 2026-08-20 の決定で、開発方針 §4 の規則——「⚠ いま」から要求へ上げるか。
- **サニタイザを拡張で広げさせない**（安全性の門が破れる）。拡張はコンパイル時に組み込まれ、コアと同じ信頼水準だが、拡張が描く
