## 0. 総評

**骨格は健全で、破れているのは末端です。** 3層の語彙モデル・一方向依存（htmldoc がドメインを知らない）・
サニタイズの二層化・決定ログの文化は、いずれも文書が主張するとおり実装として成立していました。
文書と実装の乖離を探しに行って、**見つかったのは文書の誤りではなく文書が触れていない領域**
（メソッドガード・キャッシュヘッダ・派生索引の認可）ばかりだった、というのが調査の結論です。

一方で、**「黙って壊れる」経路が想定より多い**ことが分かりました。「見える文字がすべて」の代償が
告知機構で十分に補われておらず、いくつかは実測で再現しました。以下はその一覧です。

## 1. 検証済み（再現を確認した5件）

### ① 派生索引が正本を書き戻し、親ページIDを失わせる 【高】

`readMetaOrPerms`（[page/perms.go](../internal/cms/page/perms.go):116-124）は**サイドカーが読めないと
DB の `page_perms` へ落ち**、`BumpUpdatedAt`（同:128-136）がその値を `WriteSidecar`（同:75-94）で
**正本へ書き戻します**。`GetPerms` が返すのは owner/group/mode/public だけなので、
`ParentID`・`CreatedAt`・`CreatedBy` は空のまま書かれます。

**実測**: サイドカーを切り詰めた子ページを1回保存すると、owner/group/mode は DB 由来で復活する一方
`ParentID` が空になり、`pages.parent_id` が NULL、**親から見た子ページ一覧が空**になりました。
`created_at` は「今」に打ち直されます。

**訂正（検証者による）**: 親・作成者が失われるのはサイドカーが読めなくなった時点で、書き戻しが
消しているのではありません。書き戻しの罪は**復元できないのに見た目が健全なサイドカーを新造して
欠損を隠蔽すること**です。また親の最後の1コピーを潰しているのは perms.go ではなく
[sync.go](../internal/cms/sync.go):75 の `parent_id = excluded.parent_id`——`created_at`/`created_by` は
COALESCE で守られているのに `parent_id` だけ無条件上書きです。**修正の第一候補はここ**。

補足: `WriteSidecar` は `os.WriteFile`（O_TRUNC）で、リポジトリ全体で一時ファイル＋rename を
使っていません（`os.Rename` は handler_delete.go の ゴミ箱移動のみ）。**この経路自身が前提条件
（切り詰め破損）を作れます**。

### ② 索引に載るかがトップ直下ページの h1 で決まる 【高】

テンプレート判定（[template.go](../internal/cms/template.go)）は「サイドカーの親が `000000`」かつ
「本文の最初の h1 が定数 `"テンプレート"`」の2条件で、これが**部分木まるごとの②索引・③計算への
登録可否**を切り替えます（[sync.go](../internal/cms/sync.go):103-113）。

**実測**: ルートの h1 を「テンプレート」→「テンプレート集」に直しただけで、配下の再同期時に
`client_orders` が 0→1 行、`vocab_index` が 0→5 行。逆向きも再現。告知は一切出ません
（`UnknownVocabTypes`・`UnresolvedVocabFields` はどちらも `data-type` を持つ table/dl しか見ない）。

**訂正**: 反転は即時ではなく各ページの次の保存か DB 再構築で効きます。また完全な無症状ではなく、
`/api/templates` が空になり**テンプレートメニューが消える**という可視の副作用が同時に起きます。

これは自分（2026-08-20 の実装）が作った面なので、対処案は考察文書に既に書いた
**サイドカー属性 `template_root: true` への昇格**が素直です。

### ③ `order_no` の UNIQUE がページ横断で受注を奪う 【高】

`client_orders.order_no` / `our_orders.order_no` は UNIQUE で、Sync が
`ON CONFLICT(order_no) DO UPDATE SET page_id = excluded.page_id` を使うため、
**発注書番号がページを跨ぐグローバル主キー**になっています。しかも `orderNo` は `NullableString` を
通さないので、空値は NULL でなく `''` として衝突します。

**実測**: 発注書番号を空にした2ページを順に同期すると、`RequiredMaterials(51)` が `[]` になり、
`RequiredMaterials(52)` に**ページ51由来の部材**が現れました。例外もログも出ません。

**訂正**: 発火経路は「PDF取り込み・見出し改名」ではなく実質「人が番号欄を空にする／手で重複させる」
の1経路です（PDF取り込みは `order_no` に触れません）。エディタとテンプレートの再採番は
この衝突を避けるための**回避策**であって、根治ではありません。

### ④ `parse-pdf` が本文と権限サイドカーを外部へ送れる 【高】

`ParsePDFHandler`（[pdf_handler.go](../internal/cms/pdf_handler.go):183-184）は
`filepath.Join(pageDir, filepath.Base(req.FileName))` だけで、**拡張子も名前も検証しません**。
読んだバイト列はそのまま Gemini へ送られます。`file_name` に `<id>.html` や `<id>.meta.json` を
指定すれば、本文と権限サイドカーが外部LLMへ渡ります。

**防御の非対称が本質**です——アップロード側（同:65-72）は拡張子許可リスト＋本文名・サイドカー名の
名指し拒否、配信側 `DataFileHandler`（[page/perms.go](../internal/cms/page/perms.go):403-407）も
名指しで404にするのに、**読み出し側だけが素通し**。

**訂正**: 応答にファイルのバイト列は含まれないので「本文の取得口が増えた」わけではなく、
**外部への一方向の egress** です。パストラバーサルも不可（対象は自ページのディレクトリ内）。
修正は pdf_handler.go:184 の直後に名指し検査を1つ置くだけで、対応するテストもありません。

### ⑤ 改名の告知は3類型のうち1つしか拾わない 【高】

「見える文字がすべて」は改名を告知で補う設計ですが、`UnresolvedVocabFields` が捕まえるのは
「どの宣言列にも当たらない見出しがある（stray）」場合だけです。

- **類型①（同一形式の別の宣言済みラベルへ改名）**: `client-order-items` の「品名」→「品番」で
  告知は `nil`、`VocabTableRows` が同じ機械キーへ後勝ちで代入し、**実測で `item-id` が
  "SHAFT-01" から "軸" へ、`item-name` が空**になりました。
- **類型②（Field を持たない形式の改名）**: `tags` の dt「部品番号」→「部品No」で `part_id` が空になり、
  部材手配計算が丸ごと空になるのに**告知はゼロ**。`部品番号` は
  [plugin_materials.go](../internal/cms/plugin_materials.go):64 に直書きされた**日本語の魔法文字列**で、
  レジストリにもエディタ補助にも現れません。

**訂正**: 類型②は実装バグではなく**明文化された設計判断**（vocab.go:430-432＋
vocab_unresolved_test.go が挙動を固定）。したがって問題は「告知が仕様どおり動いていない」ではなく、
**その設計判断の根拠が `plugin_materials.go:64` の1行によって反証されている**ことです。
「Field を持たない列は改名しても壊れない」が `部品番号` だけ成り立ちません。
**修正は `tags` に `{Field:"part-id", Label:"部品番号"}` を宣言するだけ**で足ります。

なお本文の**見出し重複を検出するコードはリポジトリに存在しません**。

## 2. 未検証（根拠はあるが裏取りが要る）

着手前に必ず自分で確かめてください。深刻度は報告者の自己申告です。

### 安全性・認可

- **`/api/new-page` にメソッドガードが無く GET でページが作られる**【高】。`CSRFProtect` は
  GET を素通しし（[middleware.go](../internal/auth/middleware.go):127-133）、Cookie は SameSite=Lax なので
  トップレベルGETナビゲーションでは送られる。フロント自身が `window.open` で GET 遷移として
  使っているため、**意図的なGET設計と CSRF 防御モデルが正面衝突**している。
  `/api/logout`・`/api/page-chown` も同様にガード無し。
- **派生索引にページ単位認可が及んでいない**【高】。`RequiredMaterials` は `part_materials` を
  `part_id` だけで引き、**定義元ページの read を見ない**。しかも API は匿名を401で拒否するのに
  SSR の計算ビューは匿名に描画するので、**公開ページに `required-materials` マーカーを1つ置くと
  非公開ページ由来の仕入先・原価が外部に出る**可能性がある。
- **`/api/page-meta` が親のタイトルを親の read を確認せずに返す**【中】。
- **`/api/upload-pdf` と `/api/parse-pdf` だけ編集ロックを通らない**【中】。画像アップロードを
  実装するとこの穴がそのまま広がる。
- **保存2本のロック検証が `u != nil && !Validate(...)` でフェイルオープン**【中】。
  現状 RequireAuth 配下なので実害は無いが、共通ゲート `RequireEditLock` は逆に u==nil で401。
- **ルートの保護レベルを固定するテストが1本も無く、`CSRFProtect` のテストもゼロ**【高】。
  CSP は `csp_test.go` が後戻りを検出するのに、同じ最外周の CSRF とルート表は無防備。
- **認可付き応答のキャッシュ制御が画面だけ**【中】。`/api/load` と `/data/` にヘッダが無く、
  `/data/` は `http.ServeFile` の Last-Modified でヒューリスティックキャッシュの対象になりうる。
  **公開キャッシュを検討する前にここの切り分けが要る**。

### 語彙モデル

- **`View: true` の語彙は「宣言1件」では動かない**【中】。`RenderComputedViews` が
  child-list / required-materials を文字列で決め打ち。3つ目を足すと**無言の空白**になる
  （JS側は `def.view` を汎用に読むので非対称）。
- **`section[data-type]` の未知形式は告知されない**【中】。`UnknownVocabTypes` が table/dl しか
  見ないので、`<section data-type="cliet-order">` のようなタイポが完全に無症状。
  **業務文書ブロックは section が担い手なので、最も壊れやすい形式が告知対象外**。
- **業務ブロックのヘッダ dl が②に載らない**【中】。ヘッダは `data-type` を持たない裸の dl なので、
  発注書番号・発注元・発注日は③にしか存在しない。将来の横断検索で業務文書だけ穴が空く。
- **派生9テーブルのうち本番コードが読むのは5つだけ**【高】。`vocab_index`・`page_tags`・
  `our_estimates`・`supplier_estimates` は**書き込み専用**で、`SELECT` が1つも無い。
  読み手は `RequiredMaterials` ただ1関数。②の設計判断は実地で検証されないまま溜まり続けている。
- **①と③で読み取りロジックが重複**【中】。`plugin_materials` が `VocabTableRows` とほぼ同じ処理を
  自前で持つ。
- **エディタに語彙知識が残っている**【中】。`parsePDFIntoSection` が client-order / our-order と
  機械キーを決め打ちするので、新しい受発注系形式を足しても**AI解析だけ効かない**。

### エディタ・その他

- **`MutationObserver` の `attributeFilter` が旧カスタム要素時代の属性名のまま**【中】。
  `data-type`/`data-src`/`data-id` が無く、属性変更で自動保存が走る経路が事実上死んでいる。
  `applyColType` の明示的な `triggerAutoSave` はその個別回避。
- **`insideCustomElement` の停止条件が接頭辞リネーム前の id (`editor-content`) を参照**【低】。
  いま実害は無いが、殻の DOM を変えた瞬間に誤判定へ変わる。
- **保存時の通知文が実在しない機能を約束している**【低】。「検索の索引にも載ります」
  （app.js:632-634）だが検索機能は無い。
- **公開サイト未実装のコストが HTTP 境界に直接出ている**【高】。匿名読者にもエディタの殻が
  配信され、**隠しているのは JS が付ける `body.anonymous` の CSS だけ**——JS 無効の匿名読者には
  ログアウトボタン・編集スイッチ・「保存されるHTML」が見える。`robots.txt`/`sitemap.xml` は
  `.` を含むパスが404に落ちて到達不可。
- **18MB の Linux バイナリ `w-cms` が git に追跡されている**【中】。`.gitignore` は `*.exe` だけ。
- **ルートに孤立した `list_models.go`（package main）が残っている**【低】。これが原因で
  「サブdirで実行」という回避策が引き継ぎに恒久手順として書かれている。

### 文書・テスト

- **コードリファレンスの行数主張20件中11件が実測とずれ、対象コミットが26コミット古い**【高】。
  直近5ファイル（anchor.go・handler_delete.go・template.go・template_new.go・handler_template.go）が
  全体地図に1件も載っていない。**この文書群は現在まるごと疑わしい**。
- **E2E の正本がリポジトリ外（OneDrive）にあり CI も無い**【高】。最も価値の高い安全網が
  git 管理外でレビュー不能・引き継ぎ不能。
- **往復契約テストに語彙形式が1つも無い**【中】。`TestSanitizeAcceptsEditorOutput` の fixture は
  素のブロック10種だけで `data-type` がゼロ。**エディタが最も多く吐く形式でエコーバックが
  起きても検出されない**。
- **`.claude/worktrees/` に移行前のコードが丸ごと残っている**【中】。`web-components.js` と
  `assets/templates/` の `style=` 属性が**ちょうど75個**——「撤去した」と記録された当のもの。
  追跡下の HEAD では「カスタム要素0種」「インライン style ゼロ」は真だが、
  **作業ディレクトリを grep すると偽になる**。grep に頼る調査（特にAIエージェント）が誤結論を出す。

## 3. 着手するなら（優先順の私案）

1. **⑤の `tags` へ `{Field:"part-id", Label:"部品番号"}` を1行**——最も安く、最も鋭い穴が塞がる。
2. **④の `parse-pdf` に名指し検査**——数行＋テスト1本。外部送信という性質上、先に潰す価値がある。
3. **①の `sync.go:75` を `parent_id` も COALESCE に**——正本を失う唯一の経路。
4. **`/api/new-page` の POST 化**——ただし `window.open` を使う UI の作り直しを伴う。
5. **ルート保護レベルの固定テスト**——CSP と同じ流儀で、退行を機械に検出させる。
6. **E2E をリポジトリへ取り込む**——引き継ぎ可能性の問題であり、いま最も安く効く。

**②③は運用開始前に**。テンプレートの h1 依存（②）は属性への昇格で、
`order_no` の全域UNIQUE（③）は `(page_id, order_no)` への変更で解けますが、
後者は③計算の JOIN も併せて直す必要があります。
