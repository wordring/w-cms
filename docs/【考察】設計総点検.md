## 0. 総評

**骨格は健全で、破れていたのは末端でした。** 3層の語彙モデル・一方向依存（htmldoc がドメインを知らない）・
サニタイズの二層化・決定ログの文化は、いずれも文書が主張するとおり実装として成立していました。文書と実装の
乖離を探しに行って、**見つかったのは文書の誤りではなく文書が触れていない領域**（メソッドガード・キャッシュ
ヘッダ・派生索引の認可）ばかりだった、というのが結論です。一方で **「黙って壊れる」経路が想定より多い**こと
が分かりました——「見える文字がすべて」の代償が、告知機構で十分に補われていません。

## 1. この調査から得た教訓

個別の指摘は対処か判断で片付きますが、下の8点は残ります。

1. **未検証の指摘は、着手前に必ず反証してから使う。** 全件を反証側から検証して**原文のまま通った指摘は
   1件もありませんでした**（判定が覆ったもの7件、成立するが範囲・深刻度・原因の訂正が要るもの10件、
   残りは新規発見）。誇張・因果の取り違え・深刻度の付け間違いが体系的に混じるので、**指摘を読んで
   そのままコードを直すと、存在しない欠陥を「修正」してしまう**。
   > 実例——「保存2本のロック検証がフェイルオープン」→ `u == nil` は `RequirePageWrite` とルート表の
   > `RequireAuth` で二重に到達不能＝**不成立**。「`robots.txt` が `.` を含むパスで404」→ **因果が誤り**で
   > そもそもハンドラ未登録。「`/api/load` がヒューリスティックキャッシュされうる」→ 検証子が無く再利用
   > されないので**起きない**（実害は `/data/` だけ）。「往復契約テストに語彙形式が無い」→ **結論が誤り**で、
   > `save_sanitize_test.go` が3形式にバイト一致の往復契約を与えている（残る課題は12形式中8形式が未カバー）。
2. **テストは「値」だけでなく「配線」も固定する。** [csp_test.go](../internal/auth/csp_test.go) が固定して
   いたのはポリシー文字列だけで `main.go` の組み込みは見ておらず、**`CSPProtect` を丸ごと外しても緑**
   でした。`buildHandler()` を切り出して [route_guard_test.go](../cmd/w-cms/route_guard_test.go) が
   ルートごとの保護レベルと CSRF・CSP の**配線**を固定するようにしたのは、この発見によります
   （配線を変異させてテストが落ちることを確認済み）。
3. **E2E だけが守っている不変条件がある。** `serializeChildren` の `.vocab-chrome` 除外には Go テストが
   無く、破れを検出できるのは E2E だけでした。E2E がリポジトリ外にあることの本当の重さは
   「レビュー不能」より**この一点**で、`e2e/` の取り込みはそのために優先しています。
4. **正本と索引がズレたら、認可は索引に従う。** `GetPerms` も `EffectivePublic` の親チェーンも読むのは
   `cms.db`（派生）であってサイドカー（正本）ではありません。「サイドカーが壊れて `parent_id` を失う」は
   データ整合の問題ではなく、**そのまま公開範囲の問題**になります（データモデルと安全性の2体が独立に
   同じ結節点を指しました）。
5. **サニタイズの後にHTMLを足す関数が3つある**（`RenderComputedViews`・`RenderAnchors`・
   `RenderPageShell`）。それぞれが自前でエスケープ責任を負っており、規律が破れた時点で保存型XSSです
   （[本文サニタイズ設計.md](本文サニタイズ設計.md) §2 の二層の**外側**）。
6. **`.vocab-chrome` の不変条件は「型」ではなく「規律」。** 本文DOMを走査する箇所は**29ある**のに明示除外は
   4つだけで、残りは「クロームが入れ子」「クロームが `data-type` を持たない」という現時点の偶然に
   依存しています。レジストリへ `View: true` を1件足すと5箇所が一斉に誤爆します。
7. **手で書いた写像は、実装と同じ速度で陳腐化する。** コードリファレンスは行数主張30件中16件が誤り、
   `app.js` を指す `file:line` は7件中6件が誤り、殻の `id` 参照は7件すべてが `w-` 未追随でした。
   **一方で腐っていなかったのは**依存の向き・ミドルウェア入れ子・ルート表・サニタイズ二層・不変条件・
   テスト地図——**構造は生き、座標は死ぬ**。文書を畳んだ判断はこの非対称に基づきます。
8. **「黙って壊れる」を告知で補うと決めたなら、告知の網羅を測る。** 改名の告知は3類型のうち1つしか拾って
   おらず、`section[data-type]` のタイポは完全に無症状、部材手配が読む `部品番号` は Go コードに直書き
   された**日本語の魔法文字列**でレジストリにもエディタ補助にも現れませんでした（どちらも対処済み）。

## 2. 対処（2026-08-21）

11件を修正しました。いずれも `upload_test.go` の流儀で、**修正前に落ちるテストを先に書いて**います。
**内容とコミットの一覧は [変更履歴.md](変更履歴.md) 2026-08-21 が正本**。ここには、そちらに書かない
**採らなかった判断**と、他文書から参照される**実測値**だけを残します。

### 2.1 採らなかったもの

- **`tags` へ `{Field:"part-id", Label:"部品番号"}` を1行足す**（当初の最優先案）→ **採れない**。`tags` は
  自由語なので列として宣言すると、担当者しか書いていないページでも「部品番号が無い」と鳴り、**全ページで
  誤検知**になります。代わりに「部材表があり、タグを実際に使っており、それでも鍵が引けない」ときだけ
  報告する形（レジストリ宣言 `RequiresTag`）にしました。
- **テンプレート判定をサイドカー属性 `template_root` へ昇格し、右レールにトグルを出す** → **取り消し**
  （2026-08-21 に一度は決定したが着手前に中止）。**h1（ページ名）で決まるまま**とし、置き場を改名すると
  配下が丸ごと②索引・③計算から出入りする（告知は出ない）リスクは**受け入れます**。**決定とその根拠
  （ユーザーの言葉）の正本は [【考察】ページテンプレート.md](【考察】ページテンプレート.md) §9**、
  受け入れたリスクは同 §3.3。なお「テンプレートという名前を設定で変えられる方が良いかもしれない」は**未決**。

### 2.2 起動時のDB再構築の決着（実測値の正本）

`f2458a9` が入れた「起動時にスキーマのずれを見つけたらファイルから全再構築する」処理
（[main.go](../cmd/w-cms/main.go)）について所要時間を実測し、ユーザーの判断を得ました。

**実測**: **1500ページ = 7.0秒**／**3000ページ = 15.8秒**。**1ページあたり約5ミリ秒でページ数に比例**し、
本文の分量には比例しません（同じ1500ページで本文を4倍にしても7.4秒）。再構築が終わるまでサーバーは
受け付けを始めません。**心配していたほど長くはありませんでした。**
**ユーザーの判断**: **1日以内で終わるなら、ファイルから作り直す方式で行く**。外挿すると100万ページで
約1時間半——楽観値で実際はもっと掛かりますが、いずれにせよ1日以内なので**方式は維持**します。

**残る穴（未対処）**: 再構築が途中で止まると（強制終了・停電）、**次の起動は何事もなく成功し、取り込めなかった
ページは開いても「ありません」のまま**になります。`RebuildIfEmpty`（[sync.go](../internal/cms/sync.go)）は
`pages` が**空かどうか**しか見ないため、途中まで入ったDBは「再構築済み」と見分けが付きません（スキーマずれの
経路も同じで、DROP と CREATE を終えた時点でずれは消えるので2回目以降は走りません）。ユーザーは下の3点に同意
済みで、**やることは決まっていて未実装**です——①再構築を**始めた印**を残す ②起動時にその印が残っていたら
**必ずやり直す** ③終わったら**件数と所要時間**を記録に残す。

## 3. 未対処（行き先つき）

**この節がこの文書で唯一「生きている」部分です。** 深刻度は反証検証後の値。

### 3.1 安全性・認可

- **匿名がページIDを列挙できる**【高】——`/` だけが認可より先に `pages` を引くため、404（不存在）と
  302（非公開）の差が出る。→ [要件定義書.md](要件定義書.md) §2.1、着手順は
  [作業引き継ぎ.md](作業引き継ぎ.md)「次にやること」。
- **派生索引に最初の読み手を足す瞬間の認可**【高】——手配集計の越境は `af5c032` で塞いだが、根は
  「派生索引にページ単位の認可が及ばない」こと。読み手ゼロの4テーブル（`vocab_index`・`page_tags`・
  `our_estimates`・`supplier_estimates`）に最初の `SELECT` を書くときは同じ穴を作らないこと
  （**バグではなく未使用の投資**で、`vocab_index` は②＝検索・単純集計の先行実装）。
  → [アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md)。
- **`/api/page-meta` が親のタイトルを親の read を確認せずに返す**【中】——匿名には漏れず（パスゲートで
  構造的に不可能）1階層だけだが、タイトルは**本文の最初の `<h1>` そのもの**＝read 権の無いページの中身の
  1行。`/api/children` は同じ `pages.title` を1件ずつ `CanRead` で絞っており**内部規約と非対称**。
  → [認証認可設計.md](認証認可設計.md)。
- **監査ログの空白域**【中】——ログイン成功/失敗・ログアウト・`new-page`・`rebuild-db` が一切記録されない
  （索引を全DROPする `rebuild-db` が無記録なのが重い）。→ [認証認可設計.md](認証認可設計.md)。
- **パスワード変更でセッションが失効しない**【中】——漏洩後にリセットしても盗まれた Cookie が最大8時間
  有効。→ [認証認可設計.md](認証認可設計.md)。
- **認可付き応答のキャッシュ制御**【中】——実害があるのは **`/data/` だけ**（`Last-Modified` のみ＝経過
  時間の約10%が鮮度期間）。**公開キャッシュを検討する前にここの切り分けが要る**。
  → [要件定義書.md](要件定義書.md) §4.4。

### 3.2 語彙モデル・計算

- **`View: true` は「宣言1件」では動かない**【低〜中】——`RenderComputedViews` が child-list／
  required-materials を文字列で決め打ちしており、3つ目を足すと**無言の空白**になる（ビルドも `go vet` も
  テストも通る。実測で再現）。現在 `View: true` は2件で決め打ち側と完全一致＝**現時点の実害ゼロ**。追加
  手順は [【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md) に明記済みだが、
  [【ユースケース】受注から利益まで.md](【ユースケース】受注から利益まで.md) は分岐追加に触れていないので**次の計算
  ビューで踏む**。
- **業務文書ブロックが②索引に載らない**【低】——ヘッダ dl だけの話ではなく `section[data-type]` 系すべてで、
  文書としての同一性が②に丸ごと無い。ただし決定済み・文書済みの帰結
  （[【考察】語彙モデル.md](【考察】語彙モデル.md) §9・[【一覧】語彙.md](【一覧】語彙.md)）なので
  「黙って壊れる」類ではない。
- **①と③で読み取りロジックが逐語コピー**【低〜中】——`plugin_materials` と `VocabTableRows` の実質的な差は
  `make` の容量ヒント（4 vs 8）とコメントだけ。原因も特定済み——`VocabTableRows` は移行第3段で生まれ
  materials の移行は第2段だったため、**共有ヘルパが後から生まれて materials だけ取り残された**。

### 3.3 エディタ（殻の `w-` 接頭辞化への追随漏れを含む）

- **エディタとサーバーの両方に語彙の決め打ちが残る**【中】——主犯は `parsePDFIntoSection` ではなく
  **`enhanceFileSections`**（解析ボタンを出す門）。天井はサーバー側にあり、`ParsePDFItem` とプロンプトが
  3キー固定なので**既存形式でも品番と状態は永久に空セル**。→ [エディタ仕様.md](エディタ仕様.md)。
- **レール開閉ボタンの状態が支援技術へ通知されない**【低】——`syncRailToggleButtons` が
  `getElementById('toggle-' + side)`（[app.js](../assets/app.js):253）で引くのに実体は `w-toggle-left`／
  `w-toggle-toc`／`w-toggle-right`。`if (!btn) return` で毎回抜けるため `is-on` も `aria-pressed` も
  マークアップの初期値に固定される。`shell_id_test.go` は HTML 側しか見ないので**永久に緑**。
- **`insideCustomElement` が常に false を返す**【要実測】——[app.js](../assets/app.js):1855 の停止条件が
  `p.id !== 'editor-content'`（実体は `w-editor-content`。上と同じ追随漏れ）で、一致条件（タグ名にハイフン）も
  カスタム要素0種で成立しない。**当初は原因を「カスタム要素が0種になったため」とだけ書いたが、正しくは
  接頭辞への追随漏れとの2点。** 本来の目的（計算ビューの表では表ツールバーを出さない）が果たされておらず、
  SSRの手配集計は `.vocab-chrome` 内に `<table>` を描くので**行を足しても保存されず黙って消える**経路が
  疑われる。原文の【低】「いま実害は無い」は誤りの可能性が高い。**実測が要る。**
- **`MutationObserver` の `attributeFilter` が旧カスタム要素時代の属性名のまま**【中】——
  [app.js](../assets/app.js):975 は `order-no`・`item-id` 等を並べたままで `data-type`／`data-src`／`data-id`
  が無く、**属性変更で自動保存が走る経路が事実上死んでいる**。`applyColType` の明示的な `triggerAutoSave`
  （同:2106 のコメント）はその個別回避。

### 3.4 公開サイト

いずれも行き先は [要件定義書.md](要件定義書.md) §4.4（公開専用ビュー）。

- **匿名訪問者が毎回FOUCを見る**【中】——認可境界は無傷でマークアップ経由の漏洩はゼロ（textarea も権限欄も空）
  だが、`anonymous` クラスを付けるのが `window.onload` なので**JS有効の匿名訪問者全員が毎回、編集用の殻を
  ちらつきとして見る**。`RootHandler` は既に `CurrentUser(r)` を持つので `<body class="anonymous">` をサーバーで

  いない**こと。Go 1.25 の ServeMux は具体パターン優先なので1行足せば届く。
