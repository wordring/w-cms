## 1. 目的・スコープ

> 顧客から発注書を頂いたときに行う作業を受注処理と言います。メール、FAX、対話（電話等）で受注します。電話や口頭で受注する場合は発注書が無い場合もあります。発注書がない場合、同等の項目を作業者が書き留めることとなります。
> この文書は、受注処理に必要な文書やタグ、データベーススキーマを考察します。
※メール、FAX、電話等は通信記録としてページが保存されています。

## 2. 受注の単位とデータ

[通信記録の取り込み §2.5/§4.5](【考察】通信記録処理.md) も参照
- **1発注書＝1文書ページ**。中身の構造化要素で表現する——単一項目（発注書番号・客先・受注日など）は `<m-field>`、繰り返し明細は `<m-table>`（[タグ設計 §6/§7](【考察】タグ設計.md)。値はセルの中身）。
- 受注データ：`order-no`・客先・受注日・PDF原本、明細（部品・**数量**・単価・status・**納期＝部品単位**）。
- 顧客から頂く発注書のデータには、発注番号、顧客社名、顧客担当者名、希望納期などが載る。

### 2.1 発注書ごとに項目が違う問題：汎用name/value表現

各社の発注書は形式がまちまちで、載る項目（列）も会社ごとに異なる。これを固定スキーマで先取りせず、**「役割名：値」の汎用タグ**（[タグ設計](【考察】タグ設計.md) の `<m-field name="役割">値</m-field>`）で表現し、DBも `(page_id, name, value)` の名前・値索引（既存の `page_tags` と同じEAVパターン）で検索できるようにする。これにより新しい項目名が来ても**スキーマ変更なしに**受け取れる。

表形式の明細（品番・品名・数量・単価…複数行）も同じ発想で、**セル単位のトリプル（行ID・列キー・値）**として索引化できる。ただし行を束ねる**行ID**が無いと「商品名＝ブラケット かつ 数量＝10」のような同一行内の複数条件検索ができないため、実際には最低でも `(文書ID, 表ID, 行ID, 列キー, 値)` の四つ組が要る（[タグ設計 §7](【考察】タグ設計.md) の `<m-table>`＝自己記述ヘッダ `data-field` の考え方と対応）。

### 2.2 型付き既知列 vs 汎用索引の切り分け

全項目を汎用トリプルにすると値がすべてテキストになり、受注残・原価計算のような数量×単価の集計にCASTや自己結合が増えて重くなる（[原価と利益 §3](【ユースケース】原価と利益.md) の集計ロジック参照）。そこで**「数値演算（合計・引き算・掛け算）に使うか」「JOIN/GROUP BYのキーになるか」「日付比較に使うか」**のいずれかに該当する項目だけを型付き既知列にし、それ以外は汎用name/value索引に落とす。

| 列 | 型 | 使われる計算 |
|---|---|---|
| **quantity**（受注数量） | 数値 | 残＝受注数−Σ納品済数、売上＝Σ(price×quantity) |
| **納品済数量**（分納実績） | 数値 | 同上（残の計算） |
| **price**（売価単価） | 数値 | 確定売上＝Σ(price×quantity) |
| **cost**（原価単価） | 数値 | 確定原価＝Σ(cost×quantity) |
| **item_id / item_name**（品番・品名） | テキスト（完全一致キー） | 見積・受注・発注・部材を名寄せするJOINキー |
| **order_no**（発注書番号） | テキスト（完全一致キー） | 明細行を親の発注書（文書ページ）に紐づけるキー（現行実装では `<m-item>` のFK） |
| **納期**（部品単位） | 日付 | 納期ビュー・受注残ビューでの期限判定・ソート |
| **status**（進捗） | enum（将来は数量から導出） | 進捗ボードのフィルタ・集計軸 |
| **client_name / supplier_name** | テキスト（正規化推奨） | 取引先別集計のグルーピング軸（表記ゆれ対策が要る） |

発注元担当者名・支払条件・希望納品場所・備考など、**表示はされるが集計・結合に使わない**項目は既知列を増やさず汎用索引に落とす。

## 3. 受注のライフサイクル（作成・変更・取消）

合意済みの土台（[通信記録の取り込み §2.6](【考察】通信記録処理.md)）：
- 受注は通信記録から**独立した長命エンティティ**。別メールで**変更・取消**され得る。
- **取消は削除でなく状態フラグ**（ページ状態タグ `<m-tag name="状態">取消</m-tag>`・書式は[タグ設計 §6](【考察】タグ設計.md)）。過去参照・集計整合のため受注ページは残す。
- 受注数の変更は「ページを編集するだけ」（文書ベースの柔軟性。残は計算で追従）。
