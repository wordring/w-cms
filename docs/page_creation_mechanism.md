# ページID生成と子ページ作成のメカニズム

w-cmsにおけるページIDの生成アルゴリズムと、子ページ作成時のトラブルシューティングについての詳細ドキュメントです。

## 1. ページIDの生成アルゴリズム

ページIDは、常に一意かつ連続した6桁のゼロ埋め文字列（例: `000001`）として管理されます。フロントエンドが新しいページを作成しようとする際、バックエンドの `/api/new-id` を呼び出すことでIDが発行されます。

### バックエンドの実装 (`GenerateNextID`)
IDの生成は、SQLiteの `pages` テーブルの主キー（`id` カラム）を利用して行われます。
1. **最大IDの取得**: `SELECT id FROM pages ORDER BY id DESC LIMIT 1` を実行し、データベースに登録されている最大の整数IDを取得します。
2. **インクリメント**: 取得した最大IDに `+1` を加算します。テーブルが空の場合は `0` を基準とし、次のIDは `1` になります。
3. **ゼロ埋めフォーマット**: 計算された整数を `%06d` フォーマットで6桁の文字列（例: `000001`）に変換し、フロントエンドへ返却します。

> [!NOTE]
> 以前は `id` が TEXT 型であったため、辞書順ソートによる不具合（`"9"` が `"10"` より大きくなる等）がありましたが、現在は `INTEGER PRIMARY KEY` に移行したことで安全かつ正確に最大値が取得できるようになっています。

## 2. 子ページ作成フロー

フロントエンド（`test.html`）での「子ページを作成」の動作は以下の流れで行われます。

1. 現在のページID（`currentPageId`）を取得し、新しいページの**親**として設定します。
2. バックエンドから `/api/new-id` を取得します。この際、ブラウザの強力なキャッシュ機能を回避するため、URLパラメータにタイムスタンプを付与します（例: `?t=1718712345678`）。
3. `window.open('/[新しいID]?edit=true&parent=[現在のページID]')` で新規タブを開きます。
4. 新規タブでは、既存のページが存在しないため `/api/load` がエラーとなり `.catch` ブロックに入ります。
5. エディタ内を空のテンプレート（ダミーデータを含まないクリーンな状態）に初期化し、親ページIDのタグ（`<m-tag name="親ページID" value="...">`）を挿入します。
6. すぐに `saveToServer()` が呼ばれ、新しいページの実体がHTMLファイルおよびデータベースに保存されます。

## 3. 過去に発生したトラブルと解決策

### トラブル1: IDが更新されず、ページが上書きされ続ける
**症状**: 子ページを1つ作成した後、2つ目を作ろうとしても同じID（例: `000001`）が返ってきてしまい、別のページが作れない。

**原因**: 
ブラウザ（特にWindows環境のChrome/Edge）が、GETリクエストである `/api/new-id` の結果をキャッシュしていました。そのため、2回目以降のボタンクリック時にサーバーへ問い合わせが行かず、記憶していた同じIDが使い回されていました。

**解決策**:
* フロントエンド側で `fetch('/api/new-id?t=' + Date.now())` のように毎ミリ秒変化するクエリパラメータを付加。
* バックエンド側で `Cache-Control: no-store, no-cache, must-revalidate` ヘッダを付与し、キャッシュを明示的に禁止しました。

### トラブル2: 3つ目以降の子ページが作れない（UNIQUE制約違反）
**症状**: 1つ目、2つ目のページは作れるように見えたが、3つ目以降が作れない。またはデータベース再構築後にファイルがあるのにDBに登録されない。

**原因**:
新規ページ作成時、当初はテスト用のハードコードされたダミーHTML（`PO-2026-001` という架空の発注書番号が含まれる `<m-file>`）がそのまま使われていました。
データベースの `client_orders.order_no` は **UNIQUE 制約** が設定されているため、2つ目のページで同じ `PO-2026-001` を保存しようとするとSQLiteがエラーを吐き、**トランザクションがロールバック**されていました。
DBにページが保存されないため、最大IDが進まず、一生同じIDを再発行し続ける「上書きループ」に陥っていました。

**解決策**:
1. **エディタのクリア**: 新規ページ作成時、ダミーデータを含まないクリーンな状態（`<h1>新しいページ</h1>...`）で初期化するように修正しました。
2. **UPSERTの導入**: 万が一、ユーザーが手動で発注書番号をコピペして重複させた場合でもシステムがクラッシュしないよう、`INSERT INTO ... ON CONFLICT(order_no) DO UPDATE SET ...` を用いて、エラーを無視して最新のページに紐付けを移動させる柔軟な仕様に変更しました。
3. **エラーの可視化**: `SyncIndex` のエラーを握り潰さず、エラー時は HTTP 500 を返し、フロントエンドのステータスに赤字で「保存失敗」と表示されるようにしました。
