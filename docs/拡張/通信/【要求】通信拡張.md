# 【要求】通信拡張

**通信拡張**（`ext/comm`）の要求仕様です。通信拡張の受け持つ範囲は、次のとおりです。

- メールの送受信
- FAXの送受信（FAXサーバーとの連携）
- 電話の着信記録・発信と記録（ICT装置との連携）
- 通信箱
- 連絡帳

> **この文書の読み方**
>
> - 印の無い文は**要求**です（こうあってほしい、こういう決まりにする、ということ）。書くのは利用者で、
>   エージェント（AI）は矛盾点・問題点を見つけたら指摘します（[開発方針.md](../../開発方針.md) §2）。
> - 「⚠ **いま**」で始まる段落は**実装の現状**です（実装がいまこうなっている、という事実）。
>   こちらはエージェントが実装に合わせて直します。
> - 要求と「⚠ いま」の2種類を、混ぜないでください。
> - 「（下書き）」と付いた見出しは、利用者の言葉をもとにエージェントが置いた下書きです。
>   利用者が読んで、直したり採ったりします。
> - 「**未決**」と付いた項目は、まだ決まっていないことです。
> - いつ・なぜその形になったかは、末尾の「この文書の経緯」と、`考察/` フォルダの【考察】にあります。

この文書は、2026-09-27 に、コアの【要求】（添付・運用）から通信の決まりを抜き出して置いたのが始まりです
（§1 は【要求】添付 §8 から、§2 は【要求】運用 §3 から移しました）。
業務の決まりを拡張へ分ける方針によるものです（[開発方針.md](../../開発方針.md) §0）。

## メールの保存

- メールは「/通信箱/年/月/メールの件名」にページとして保存されます。（日付等不明のメールは取り込んだ日）
- ページの見出しは「メールの件名」と同じです。（件名が無い場合は「件名なし」）
- メールの属性を DB（データベース）に入れて検索可能とするために、w-cms のタグ機能を使います。
  タグは、「名前：値」の形で本文に書く項目です。

⚠ **いま**（2026-10-09）: 上の要求と実装が食い違っている所が、2つあります。
エージェントからの矛盾の指摘です。**どちらに合わせるかは、利用者が決めます。**

- **日付の読めないメールは、年・月のフォルダを作らず通信箱の直下**に入ります。
  上の「（日付等不明のメールは取り込んだ日）」と食い違っています。
  - 実装: `ext/comm/intake.go` の `arrivalParent`（コメントは「分からない時期を捏造しない」）。
- 件名の無いメールの題は「**（件名なし）**」です（全角の括弧つき）。上は「件名なし」です。
  - 実装: `ext/comm/intake_eml.go`。

## ページに入れるタグ

メールに対する返信が電話やFAXの場合もあります。
ページには、次のタグを入れます。

- 送信受信の「向き」
- メール・FAX・電話などの「チャネル」
- 差出人
- 宛先
- 返信先
- 受信日時/送信日時
- 通信記録の親子関係を表す「親ページID」
- 「In-Reply-To」などの通信路由来の生メッセージヘッダ

「ヘッダ」は、メールの頭に付いている、差出人・宛先・識別の番号などの情報のことです。
`Message-ID` はメール1通ごとの識別の番号で、`In-Reply-To` は「どのメールへの返信か」を表すヘッダです。

> 2026-10-09 利用者:「メール関連のタグはメールヘッダそのままIn-Reply-toなどとして記録し、
> それとは別に親子関係を表すタグとして『親ページID』タグを付けるのはどうでしょう？もちろん、通信記録の前後をたどるには、基本的に
> 『親ページID』を検索します」

⚠ **いま**（2026-10-09）:

- **メールの取り込みが書くタグ**
  - `向き`・`チャネル`・`差出人`・`宛先`・`CC`・`返信先`・`受信日時`／`送信日時`・`Message-ID`・
    `In-Reply-To`・`親ページID`・`添付`（添付の数）です。
  - 値の無いタグは書きません（添付の無いメールに `添付` は付きません。`CC`・`返信先`・`In-Reply-To`・`親ページID` も同じです）。
  - 自分が出したメール（送信の記録）には、`対応：不要` も書きます。
  - 上の要求の一覧に無いものは、`CC`・`添付`・`対応` です（`Message-ID` は「など」に入ると読みました）。
  - 実装: `ext/comm/intake_eml.go`。
- **w-cms から送ったメールの控えが書くタグ**
  - `向き`（送信）・`チャネル`・`対応`（不要）・`差出人`・`宛先`・`CC`・`送信日時`・`Message-ID`・`添付`・
    `In-Reply-To`・`親ページID` です。`返信先` は書きません。
  - 実装: `ext/comm/mail/reply.go` の `sentRecordBody`。
- **そのほかの記録が書くタグ**（上の要求の一覧に無いもの）
  - メールの下書き: `下書き`（用件の名前）・`下書きの元`（`ext/comm/mail/compose.go`）。
  - 「＋ 記録する」と ☎ の発信の記録: `電話番号`・`相手`・`発信日時`（`ext/comm/handler_memo.go`）。
- **生のヘッダの名前で写すのは `Message-ID`・`In-Reply-To` の2つだけ**です
  （2026-10-09 利用者の答え「Message-ID・In-Reply-To だけ」）。
  - 差出人・宛先などは、FAX・電話の記録と共通の、日本語の名前のままです。
  - 閲覧モードでは、2つとも「▸ 詳細」に畳みます（人が読む値ではないためです）。
    書ける形（ページを開いて、そのまま書ける状態）では、畳まずにそのまま見せます。
- **`親ページID`** は、参照（ほかのページを指す値）のタグです。値は、親の記録のページIDです。
  - **書くところ**
    - メールの取り込み: `In-Reply-To` と同じ `Message-ID` の記録が在れば、その記録を親として書きます。
    - w-cms から送った返信の控え: 返信元のページを書きます。
      Message-ID の無い FAX・電話・メモの記録への返信でも書きます。
  - **親があとから取り込まれたら、既にある子に書き足します**（利用者の答え「書き足す」）。
    - 書き足すのは、メールの読み込みの仕事の前と後に、1回ずつです。
    - 人が画面で開いて書いている記録にも、書き足します（2026-10-12 から。画面は編集ロックを取りません）。
      本文は `cms.RewriteBody` を通して書くので、人の保存と重なっても消えません。
      同じブロックがぶつかれば、画面が両方の版を並べます。
    - 飛ばして次の回に回すのは、道具が編集ロック（`/api/lock`）を握っている記録だけです。
    - 古い名前のタグも、ここで新しい名前へ直ります（古い名前は、末尾の「この文書の経緯」にあります）。
    - 実装: `ext/comm/parent_link.go` の `FixRecordTags`。
  - **たどるのは `親ページID` です。** たどる所は3つあります。
    - やりとりの前後（🧵・`/api/thread`）
    - この記録への返信（📨・`/api/replies`。こちらが送ったものだけ）
    - メール一覧の木（`assets/mails.js`）
  - `In-Reply-To` があって `親ページID` の無い記録は、親のメールが w-cms に無いものです
    （取り込む前の古いメールへの返信など）。職場の本物では18通です。

## 1. ZIP の展開

[【要求】添付.md](../../【要求】添付.md) §8 から移した決まりです。

**メールの取り込みだけが ZIP を展開します。**
展開してよい根拠は、**受信原本（`.eml`）が ZIP を持っていること**です。
`.eml` は、届いたメールそのもののファイルです。
だから、**人が手で落とした ZIP は展開しません。**

⚠ **いま**: 展開そのものは、コアの `cms.ExpandZip` が持ちます。
上限は3つあります（1件の大きさ・件数・合計）。詳しくは [【要求】添付.md](../../【要求】添付.md) §8 にあります。

### ZIP の中の PDF をまとめて解析する

> 2026-09-30 利用者:「添付ファイルのPDFについて、ZIPの場合まとめて解析するオプションが欲しいです」

⚠ **いま**:

- 東邦の拡張が載っていれば、メールの ZIP の隣に「🤖 中のPDFをまとめて解析（N件）」が出ます。
  出るのは閲覧モードです（添付の隣のボタンは、閲覧モードの表示です）。
- 中のPDFを、中のパスの順に1つずつ解析します（1件ずつの「🤖 解析」と同じです）。
  最後に、1つの知らせにまとめます。
- 解析済みのものは飛ばします。解析し直すのは、1件ずつの「🤖 再解析」で行います。
- どれがどの ZIP から出たかは、添付の目録（`cms.ZipMembersOf`）が持ちます。

## 5b. パソコンのファイルを添える（下書き）

> 2026-10-04 利用者:「新しいメールを作成するときに、ローカルコンピュータから添付したいです。返信などの時も同様です」

- 新しいメールでも、返信などでも、送る欄から**手元のパソコンのファイル**を添えられます。

⚠ **いま**:

- **添え方**
  - 送る欄の「📎 添付」の下に、「💻 パソコンから添付」があります（いくつでも選べます）。
  - **送る欄へのドロップでも**足せます（本文へのドロップ＝ページの添付にはなりません）。
  - どの用件の送る欄にも出ます（返信・新規・見積書・発注書・見積依頼書）。
- **置き場は下書きのページ**です。
  - まだ下書きでなければ、先に下書きを保存します（通信箱の未処理に並びます）。
  - そこへ添付として置き、印つきで並べ、下書きにも書き留めます（開き直しても並びます）。
- **送れる種類と大きさ**
  - 送れる種類は、ID で足す添付と同じです（PDF・画像・設定の `attachment_extensions`・`.eml`）。
  - PDF の先頭・画像の種別と位置情報は、添付の口と同じに確かめます。
  - 1つ `max_upload_mib` までです。送るときは、合計 25MB までです（今までどおり）。
- **送ったあと**
  - 送ると、下書きはごみ箱へ行きます。
    そのため、**下書きに置いたファイルを送信の控えのページへ写し**、控えのリンクを写した先へ付け替えます
    （w-cms の中のほかのファイルは、今までどおり元のページを指します）。
  - 写せなかったら、下書きを残し、送れたことと一緒に知らせます。
- 実装: `assets/mail-compose.js`・`POST /api/mail/attach`・`ext/comm/mail/compose_attach.go`。

## 6. メールから作るページを選ぶ（下書き）

> 2026-10-01 利用者:「メールから作るボタンは「受注ページ作成」「加工製品ページ作成」「返信」ページのタイプは増える可能性があるので「受注ページ」
> 「加工製品ページ」をコンボボックスで選択して「作成」ボタンを押せばいいかも」

- メールの記録から作るページの種類は、選ぶ欄で選んで「作成」で作ります（種類は増えていきます）。

⚠ **いま**:

- 通信記録のページに、「作るページ [選ぶ] [作成]」が出ます。
  閲覧モードでも、書ける形でも出ます（2026-10-12 から。それまでは閲覧モードだけでした）。
- 選べる種類は、**拡張が登録します**。通信は、種類の名前も作り方も知りません。
- 東邦の拡張が載っていれば、受信のメールに次の3つが出ます。
  - 「受注ページ」（🤖 本文を読む）
  - 「加工製品ページ」（テンプレートから空のページを作って、書ける形で開きます。Gemini は呼びません）
  - 「見積依頼の返事ページ」（🤖 本文を読む。2026-10-05 から。[【要求】見積依頼.md](../東邦/【要求】部材見積依頼.md) §3）
- 送信の控え・下書きには出ません。
- 書けない人には、選ぶ欄を出しません。もう作ったページの印（✓ 受注・✓ 加工製品）だけを出します。
- 「✉️ 返信」はページを作らないので、選ぶ欄に入れず、別のボタンのままです。
- 実装: `comm.RegisterRecordMaker`・`GET /api/record-makers`・`POST /api/record-make`。

「テンプレート」は、ページを作るときの雛形になるページです。「Gemini」は、文書を読ませている AI のサービスです。

## 7. 新しいメールの読み込みはページを閉じても続く（下書き）

> 2026-10-09 利用者:「新しいメールの読み込みは、ページを閉じても継続するようにしてください」

- 通信箱の「📥 新しいメールを読み込む」で始めた読み込みは、**ページを閉じても続きます**。

⚠ **いま**:

- **読み込み**
  - 押すと、サーバーが裏で読み込みを始めます。
  - **受信と送信の箱を、新しいメールが尽きるまで**、50通ずつ取り込みます（重複は Message-ID で弾きます。既読にしません）。
  - 全体の上限は30分です。超えたら、理由を出して止めます。押し直せば、続きを読みます。
- **画面**
  - 画面は、様子を見に行くだけです。
  - 読み込みのあいだ、ボタンは「📥 読み込み中…（N 通）」になり、押せません。
  - 終わると、「受信 N 通・送信 M 通を読み込みました」と知らせます。
  - **開いたときに読み込みが動いていれば、押さなくてもその続きを見ます**。
  - 読み込みは、利用者ごとに1つです（動いているあいだに押しても、二つ目は始めません）。
  - サインインしていなければ、理由を知らせます。
- ⚠ 様子はサーバーの覚えだけです。**サーバーを入れ替えると、動いていた読み込みはそこで止まります**
  （取り込んだ分は残ります。押し直せば、続きを読みます）。
- 起動は、人が押したときだけです。自動で回し続けません
  （[【考察】通信記録処理.md](../../考察/【考察】通信記録処理.md) の人間ゲート型）。
- 実装: `ext/comm/mail/fetch_job.go`・`POST /api/mail/fetch-new`・`GET /api/mail/fetch-new/status`。
  画面は `assets/app.js` の `fetchNewMail`・`watchMailFetch`・`resumeMailFetch`。

### 3. メールのリフレッシュトークンは、ログにも応答にも出さない

ファイルの権限 0600 は、Windows では効きません（実測 666）。
そのため、本番機は OS のアカウントの分離で守ります。

- 出どころ: セキュリティ設計.md:175-177
- 入れる場所の案: §2 の隣
