# w-cms ソフトウェアコンセプト・設計仕様書

このドキュメントでは、**w-cms** の基本コンセプトである「HTMLファイルとデータベースの双方向連携」および、具体的なユースケース（部材価格の推移、製造プロセスの記録、写真付きマニュアル等）の仕様について定義します。

---

## 1. コア・コンセプト：Wikiライクな双方向データ連携

w-cms は、単なる静的ファイルの保存システムではなく、**「Wiki（HTMLファイル）への書き込みが自動でデータベースに反映され、逆にデータベースのデータが各ページに動的に反映される」**という、Wikiを起点とした双方向連携システムです。

```mermaid
graph LR
    Wiki[Wikiページ (HTML)<br>発注書/作業日報/マニュアル等] -- 1. ページ記述から反映 (Write) --> DB[(SQLite DB)]
    DB -- 2. ページ内へ過去データを反映 (Read) --> WikiDetail[Wikiページ (詳細画面)]
```

### ① Wikiへの書き込みがデータベースへ反映される（インプット）
ユーザーがWikiページを編集するようにHTMLファイル（発注書、作業日報、マニュアルなど）を作成してアップロード（保存）すると、その中に含まれるデータ（部材価格、作業時間、使用機械など）が自動的に解析され、データベースへ即座に反映（蓄積）されます。
*   特別なデータベース入力フォームを使わずに、ドキュメントを書く感覚でデータを蓄積できます。

### ② 各ページにデータベースのデータが反映される（アウトプット）
特定のWikiページを表示する際、そのページ自身に記載された静的な内容だけでなく、**データベースに蓄積された過去のすべての記録（統計データや価格推移など）が自動でページ内に読み込まれ、動的に反映（表示）されます**。
*   **例**: 「ボルトAの製品Wikiページ」を開くと、過去に他のWikiページ（納品書など）から登録された価格推移や製造履歴が、そのページ内に最新情報として動的に埋め込まれます。

## 2. 具体的なユースケース

### 2.1. 部材の価格推移管理
仕入れた部材の価格推移を自動でトラッキングし、仕入れ価格の変動を可視化します。
*   **ページからDBへ**: 納品書のWikiページを記述して保存すると、部材価格が自動でDBへ登録されます。
*   **DBからページへ**: 部材のWiki詳細ページを開くと、DBに蓄積された過去の価格推移リストやグラフがページ内に反映されます。

### 2.2. 製造プロセスの記録と見積もり算出への活用
製造時の「設備・加工内容・所要時間」を記録し、将来の製品見積もり（コスト計算）の精度向上や自動化に役立てます。
*   **ページからDBへ**: 日々の「作業日報Wiki」に `<m-process>` タグなどを用いて加工データを書き込むと、製造ログがDBへ保存されます。
*   **DBからページへ**: 製品のWiki詳細ページを開くと、過去の全作業日報DBから集計された「平均加工時間」や「自動計算された見積もり参考価格」がページ内に反映されます。

### 2.3. 写真付き製造マニュアルとしての活用
製造現場での工程ごとの作業内容やコツを、写真付きの「製造マニュアル」としてWeb上で一元管理・共有します。
*   **ページからDBへ**: マニュアル工程ごとの写真と説明文をWikiに書き込むと、画像ファイルのパスとテキストがDBにインデックス登録されます。
*   **DBからページへ**: 部材名や製品名で検索すると、写真がステップ順に並んだ最新の「Web製造マニュアル」がDBからデータを取得してページ上に自動構成されます。

## 3. 実装に向けたデータモデル設計（案）

これらのユースケースを実現するために、今後拡張が想定されるデータベーステーブルの構造案です。

### ① `items` テーブル（部材マスタ）
*   `id` (TEXT, PRIMARY KEY): 部材・製品コード
*   `name` (TEXT): 部材・製品名
*   `spec` (TEXT): 仕様・規格

### ② `price_history` テーブル（価格履歴）
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT)
*   `item_id` (TEXT, FOREIGN KEY): 部材ID
*   `price` (INTEGER): 単価
*   `source_page_id` (TEXT, FOREIGN KEY): 抽出元WikiのページID
*   `recorded_at` (DATE): 発注日・納品日

### ③ `manufacturing_logs` テーブル（製造プロセスログ）
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT)
*   `item_id` (TEXT, FOREIGN KEY): 対象の製品ID
*   `machine_name` (TEXT): 使用した機械（例: 「旋盤A」「マシニングセンタB」）
*   `process_method` (TEXT): 加工方法（例: 「外径削り」「穴あけ」）
*   `duration_minutes` (INTEGER): 加工時間（分）
*   `operator_name` (TEXT): 作業者名
*   `source_page_id` (TEXT, FOREIGN KEY): 抽出元の日報WikiページID
*   `recorded_at` (DATE): 作業日

### ④ `process_photos` テーブル（マニュアル用画像情報）
*   `id` (INTEGER, PRIMARY KEY AUTOINCREMENT)
*   `item_id` (TEXT, FOREIGN KEY): 製品ID
*   `step_number` (INTEGER): 工程順序 (例: 1, 2, 3...)
*   `image_path` (TEXT): 画像ファイルの物理保存パス (例: `data/master/xx/xxxxx/step1.jpg`)
*   `description` (TEXT): その工程の説明・注意点
*   `source_page_id` (TEXT, FOREIGN KEY): 抽出元のマニュアルWikiID

## 4. 今後の開発ロードマップ

1.  **HTML解析機能（parser.go）の拡張**:
    *   Wikiページ内のカスタムタグ（部材価格、製造プロセス情報、画像など）をパースし、DBに自動反映する処理を強化。
2.  **データベース（sqlite.go）の拡張**:
    *   上記の各種テーブルの自動生成処理を追加。
3.  **データ同期ロジック（sync.go）の拡張**:
    *   Wikiアップロード時に、各種データをDBテーブルに正確に反映（同期）するロジックを実装。
4.  **UI/動的反映機能（handler.go / テンプレート）の拡張**:
    *   閲覧対象のWikiページを表示する際、関連するDBデータを引き出してHTML内に埋め込んで描画する「双方向のデータ反映」を実装。
