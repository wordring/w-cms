# 【ガイド】デプロイ・運用

このドキュメントでは、**w-cms** をサーバー上で運用・デプロイする際の手順と、ディレクトリ構成の動作仕様について説明します。

---

## 1. サーバー実行時のディレクトリ構成と動作仕様（対策Aの採用）

w-cms は、データ保存用ディレクトリ（`data`）へのパスがソースコード内で**相対パス**で実装されています。
そのため、実行時の挙動は以下のようになります。

*   **動作仕様**: `data` ディレクトリは、**「実行可能ファイルを実行した時のカレントディレクトリ（作業ディレクトリ）」の直下**に生成されます。
*   **本番サーバーでの運用方法**: 実行可能ファイルの配置場所に関わらず、サービス起動時に作業ディレクトリ（WorkingDirectory）を明示的に指定して実行します。

---

## 2. サーバー（Linux / systemd）へのデプロイ手順

本番サーバーで常時実行（デーモン化）させるための手順です。

### ステップ 1: アプリケーションのビルド
開発環境でターゲットサーバーのOS（例: Linux）に合わせてビルドを行い、バイナリを生成します。

```bash
# Linux（AMD64環境）向けにクロスビルドする場合
$Env:GOOS="linux"
$Env:GOARCH="amd64"
go build -o w-cms cmd/w-cms/main.go
```

### ステップ 2: サーバーへの配置
生成された `w-cms` バイナリを、サーバーの任意のパスに転送します。
*   **バイナリ配置先例**: `/usr/local/bin/w-cms`
*   **データ格納先ディレクトリ例**: `/var/www/w-cms` （ここを作業ディレクトリとします）

サーバー上でデータ格納先ディレクトリを作成し、適切な権限を付与しておきます。
```bash
# サーバー側で実行
mkdir -p /var/www/w-cms
chown -R www-data:www-data /var/www/w-cms
```

### ステップ 3: systemd サービスファイルの作成
`/etc/systemd/system/w-cms.service` を作成し、以下のように定義します。

```ini
[Unit]
Description=w-cms Content Management System
After=network.target

[Service]
Type=simple
User=www-data
Group=www-data
# ★重要: dataフォルダを作成・参照する基準ディレクトリを指定します
WorkingDirectory=/var/www/w-cms
# 実行バイナリのパス
ExecStart=/usr/local/bin/w-cms
Restart=always

[Install]
WantedBy=multi-user.target
```

> **秘密・環境依存の設定は環境変数で渡します**（2026-08-16 決定「設定は環境変数のみ」。
> [【要求】運用.md](【要求】運用.md) §3 の一覧表が正本）。コマンドラインフラグはありません。
> ただし **運用者が育てる設定は `config/settings.json`** に置きます（2026-08-30 に追加——
> 見出し語の辞書 `vocabulary`（1語につき型と選択肢を1件で持つ）・添付1件の上限 `max_upload_mib`（既定32）・汎用添付の
> 拡張子 `attachment_extensions`。**Git管理の必須ファイル**で、Goコードに既定値はありません
> （2026-09-07）——起動時に**無ければ、壊れていれば、どちらも起動が止まる**。
> §4.1・§5 参照）。
> 環境変数を一覧できる場所が欲しい場合は、systemd の `EnvironmentFile=` を使います:
>
> ```ini
> [Service]
> EnvironmentFile=/etc/w-cms/prod.env
> ```
>
> ```bash
> # /etc/w-cms/prod.env（root:root 0600 で保護すること。GEMINI_API_KEY 等の秘密が載る）
> GEMINI_API_KEY=xxxx
> ```
>
> **`GEMINI_API_KEY` に置けるのは、課金が有効な（＝有料枠の）キーだけです**——無料枠は
> 送った書類が学習に使われ、この機能の許可条件（2026-08-21 決定）に反します。
> 理由と根拠、および「使わない」選択肢は **§7**。
>
> **2インスタンス運用**（業務用／サイト用。要件定義書 §1.1）では、ユニットと環境ファイルを
> 1組ずつ用意します（`w-cms-gyomu.service` ＋ `/etc/w-cms/gyomu.env`、`w-cms-site.service` ＋
> `/etc/w-cms/site.env`）。別サーバーが基本ですが、同一ホストに同居させる場合は
> `WCMS_ADDR`・`WCMS_DATA_DIR`（未実装・要件定義書 §5）で待受とデータ置き場を分けます。

### ステップ 4: サービスの起動と有効化
```bash
# 設定の再読み込み
sudo systemctl daemon-reload

# サービスの起動
sudo systemctl start w-cms

# サーバー起動時の自動起動を有効化
sudo systemctl enable w-cms

# ステータスの確認
sudo systemctl status w-cms
```

この設定により、`data/cms.db` や `data/master/` は常に `/var/www/w-cms/data/` 配下に作成・保存され、安全に運用できます。

## 3. 開発環境（会社・自宅）での注意点

*   **ローカル実行時**: §1 と同じで、`go run ./cmd/w-cms` を実行したカレントディレクトリ（通常はプロジェクトルート）直下に `data` が作られます。
*   **Gitの除外設定**:
    ローカルで作成されたデータベースやアップロード画像などの実データは、`.gitignore` によってGitの管理対象外に設定されているため、会社と自宅の間で勝手に上書き同期されることはありません（ソースコードのみが同期されます）。

## 4. バックアップと復元（ファイルベース）

w-cms は **「`data/master/` 配下のファイル群（HTML本体・権限サイドカー・`versions/` の版・`files/` の添付）が唯一の正データであり、`data/cms.db`（SQLite）は派生インデックスにすぎない」** という設計です。データベースはいつでもファイルから再生成できるため、バックアップ・復元はファイルのみを対象にすればよく、DBファイルは対象に含める必要がありません。

> [!IMPORTANT]
> **不変条件**: データベースには「ファイルから再生成できないデータ」を一切持たせてはいけません。新しいプラグインを追加する際も、DBの全カラムが `data/master` のHTMLから `SyncIndex` で再生成可能であることを必ず保証してください。この不変条件が、ファイルのみのバックアップ戦略の前提です。

### 4.1. バックアップ手順
*   **対象（必須）**:
    *   `data/master/` ディレクトリ全体（HTML本体・権限サイドカー・`versions/` の版・`files/` の添付＝PDF・画像・汎用ファイル）。正データ。
    *   **`data/auth.db`**（ユーザー・グループ・セッション・監査ログ等の認証情報）。**ファイルから再生成できないため必ずバックアップする**。
    *   **`config/settings.json`**（設定の正本。住人は7つ——見出し語の辞書 `vocabulary`・添付上限 `max_upload_mib`・汎用添付の拡張子 `attachment_extensions`・文字の置き換え `char_folding`・WebDAV の `webdav_hidden` と `webdav_readonly`・**拡張の節 `extensions`**（いまは下請けの装置の段 `extensions.subcon.machine_stages`。2026-09-15 にトップから移した））。**ファイルから再生成できないため必ずバックアップする**——DBに置かないのはまさにこのため（`cms.db` は再構築で全テーブルが消える）。**無ければ起動が止まります**（Goコードに既定値は無く、埋める材料が無いため。2026-09-07）——ただしGit管理の必須ファイルなので、`git checkout` で**リポジトリの状態までは戻ります**。戻らないのは**運用者がこの環境で足した語・変えた値**だけです。
*   **対象（推奨）**: **`data/trash/`**——削除したページの唯一の写し（削除は物理削除ではなくここへの移動。復元UIは未実装で、手で `data/master` へ戻して再構築する）。失うと削除の取り消しができなくなる。
*   **対象外**: `data/cms.db`（派生インデックス。バックアップしてもよいが必須ではない。復元時は再生成される）。
*   稼働中でも `data/master` 配下のファイルは追記・上書きのみで参照整合が壊れないため、ファイルコピーやrsyncでそのまま取得できます。`auth.db` はSQLiteなので、整合の取れたコピーが必要なら停止中に取得するか `VACUUM INTO` 等を使います。

```bash
# 例: 正データと認証DBをまとめてバックアップ
tar czf wcms-backup-$(date +%Y%m%d).tar.gz data/master data/auth.db config/settings.json
```

### 4.2. 復元手順
1.  バックアップした `data/master/` を元の場所へ展開する。
2.  アプリケーションを起動する。
3.  **起動時の自動リビルド**: `pages` テーブルが空（DBが無い・新規作成された状態）で、かつ `data/master` にHTMLファイルが存在する場合、w-cms は起動時に自動でデータベースを全再構築します（`RebuildIfNeeded`。前回の再構築が途中で止まった印 `rebuild_state` が残っている場合も、`pages` が空でなくてもやり直します）。したがって復元は「ファイルを戻してアプリを起動するだけ」で完了します。
4.  自動リビルドが走らない状況（既存DBがある場合など）で手動再構築したいときは、`POST /api/rebuild-db` を呼び出します。

## 5. データベースの全再構築（リビルド）

`RebuildDatabase`（`POST /api/rebuild-db` から呼ばれる）は、ファイル群を正としてデータベースを完全に作り直す処理です。

### 5.1. 動作（全テーブルDROP方式）
1.  現在DBに存在する全テーブルを `sqlite_master` から列挙し、すべて `DROP TABLE` する（廃止されたプラグインの残存テーブルなど、スキーマのdriftも含めて完全に消去する。例外は再構築の進行状況を残す1行テーブル `rebuild_state` だけ——再構築の最中に自分を消せないため）。
2.  コアテーブル（`pages` / `page_perms`）と、登録済み全プラグインのテーブルを作り直す（`CreateCoreTables` ＋ `ApplySchema`）。汎用索引もプラグインとして登録されているのでここで作り直されます——いまその1プラグイン（`vocabIndexPlugin`）が **`vocab_index` と `page_tags` の2つ**を持ちます（`Tables()`）。可変タグは `page_tags`、業務ブロック（表・機能見出し）は `vocab_index` です。⚠ **`page_tags` は 2026-09-13 に復活しました**——2026-08-30（D-1）にいったん `vocab_index` へ吸収しましたが、アドレス帳でタグが索引の84%を占め、「読む側で `data_type='tags'` を足す」規律が守られなかったため、ユーザー決定で分離し直しています（正本は [【考察】タグ表と業務ブロック表の分離.md](【考察】タグ表と業務ブロック表の分離.md) §8）。**振り分けは書き手1か所**（`insertVocabEntry`）なので、読む側は表を選ぶだけです。
3.  `data/master` 配下のすべての `.html` を走査し、`SyncIndex` で再同期する。

> [!NOTE]
> **再構築の先頭で `config/settings.json` を読み直します。** 語→型の推論辞書がそこにあるため、
> 「辞書へ語を足して再構築する」が**再起動なしで反映される**のはこの読み直しのおかげです
> （ユーザー決定 2026-08-30:「運用中に増やしてDB再構築します」）。設定が**壊れていると**
> **再構築はエラーで止まります**——既定値で黙って続けると、足した語が消えたまま索引だけが
> 作り直されるためです。
>
> ⚠ **ただし「ファイルが無い」ときは止めません。** 読み込み済みの設定のまま続けます
> （`LoadSettings` が `os.ErrNotExist` と「既に読み込み済みか」で見分けます）。起動時とは
> **扱いが違う**のは、再構築が運用中に走るからです——ここで語彙を空にすると索引が静かに
> 痩せます。設定を消したことより、**集計が黙って変わるほうが害が大きい**、という判断です。

> [!NOTE]
> DBファイル自体は削除しません。SQLiteの接続を開いたまま全テーブルをDROP・再作成することで、Windowsでのファイルロック（オープン中のファイルは削除できない）や、リビルド中の他リクエストとの競合を避けています。リビルドは冪等なので、途中失敗した場合は再実行すれば回復します（正データはファイル側にあるため失われません）。

## 6. 認証の運用

設計は [認証認可設計.md](認証認可設計.md)。ページ単位の認可（Unix風 read/write・owner/group/other）と
匿名公開（`public`＋パスゲート）まで実装済み。

### 6.1. 初期管理者の作成
初回起動時、`users` が空のときだけ環境変数から管理者を作成します。作成後は環境変数を外してください。

```bash
WCMS_ADMIN_USER=admin WCMS_ADMIN_PASSWORD='強いパスワード' ./w-cms
```

systemd で運用する場合は、`[Service]` に一時的に `Environment=` を記述して初回起動 → 作成ログを確認 → 該当行を削除して `daemon-reload` ＆再起動、という手順が安全です。

### 6.2. HTTPS（必須）とリバースプロキシ
インターネット公開のため **TLS/HTTPS は必須**です。Caddy / nginx 等のリバースプロキシでTLS終端・レート制限を行い、その背後で w-cms（`:8080`）を動かす構成を推奨します。

*   セッションCookieは既定で `Secure` 属性付き（HTTPSでのみ送信）。プロキシTLS終端でアプリへはHTTPで届く構成でも、ブラウザ↔プロキシ間がHTTPSなら問題ありません。
*   ローカルでHTTP（`http://localhost:8080`）のまま動作確認したいときだけ、`WCMS_SECURE_COOKIES=0` で `Secure` 属性を外せます。**本番では設定しないでください。**

> **プロキシ側で CSP を上書き・除去しないこと**（2026-08-19 に strict 化）。アプリは全レスポンスへ
> `default-src 'self'; script-src 'self'; style-src 'self'; object-src 'self'; base-uri 'self'; frame-ancestors 'self'`
> を付けます（[middleware.go](../internal/auth/middleware.go) の `CSPProtect`）。`'unsafe-inline'` を
> 含まないため、**プロキシやWAFがインラインの `<script>`／`<style>` を注入する機能（エラーページの
> 差し込み・計測タグ・デバッグバナー等）を有効にすると、そのスクリプトはブラウザでブロックされます**。
> アプリ本体は外部リソースを一切使わないので、素の構成なら追加設定は不要です。
> 方針の経緯は [本文サニタイズ設計.md §6](本文サニタイズ設計.md)。

### 6.2a. アプリ自身で TLS 終端する（LAN内・自己署名）と WebDAV
社外へ出さず LAN 内で使うときは、リバースプロキシ無しで **アプリ自身が HTTPS を話せます**（2026-09-07）。

```bash
go run ./cmd/w-cms -gencert      # 自己署名の証明書と鍵を data/tls/ に作る（1度だけ）
export WCMS_TLS_CERT=data/tls/cert.pem WCMS_TLS_KEY=data/tls/key.pem
go run ./cmd/w-cms               # → https://localhost:8443（:8080 は開かない）
```

*   証明書は**各PCの信頼ストアへ1度だけ入れます**（Windows は管理者 PowerShell で `Import-Certificate`）。
    ⚠ `-gencert` を走らせるたびに別の証明書ができるので、**信頼させたものとサーバーが出しているものの指紋が
    一致しているか**を照らし合わせること（`data/tls/` を作り直すと全PCで入れ直し）。
*   **WebDAV は `WCMS_DAV=1` で開きます**（既定は閉じる）。HTTPS が前提——Windows の `WebClient` は平文の
    Basic 認証を送りません。エクスプローラで `https://<ホスト>:8443/dav/` をドライブに割り当てると、
    ページの木がそのまま見えます。**社外へは出さない**（プロキシ経由の要求は既定で 404。
    逃げ道は `WCMS_DAV_ALLOW_FORWARDED=1`）。
*   詳細と罠（Ctrl+S が届くのはアプリを閉じたとき、`PROPPATCH` の扱い、指紋の照合）は
    [【考察】添付をローカルアプリで編集する.md](【考察】添付をローカルアプリで編集する.md)、
    社外公開時の構成は [【考察】社外公開とHTTPSの構成.md](【考察】社外公開とHTTPSの構成.md)。
*   メール送受信を使うなら `WCMS_MAIL_CLIENT_ID`・`WCMS_MAIL_TENANT_ID` も要ります（無いと起動はするが
    「メール送受信: 設定待ち」）。環境変数の一覧は [【要求】運用.md](【要求】運用.md) §3。

### 6.3. 復元時の注意
復元の対象と手順は §4.1・§4.2 のとおり。`auth.db` を戻し忘れるとユーザー・セッションが失われ、初期管理者の再作成（§6.1）が必要になる。

## 7. 発注書PDFの外部AI送信（Gemini）と `GEMINI_API_KEY` の運用条件

発注書PDFの明細抽出（[【要求】表とDB.md](【要求】表とDB.md)、[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 5章）と、
添付PDFの発注書判定→受注ページ生成（2026-09-01。[【考察】通信記録処理.md](【考察】通信記録処理.md)）は、
**PDFそのものを社外＝Google の Gemini へ送信する**機能です。送ってよいかは 2026-08-21 に決着し、
**条件つきで可**となりました。その条件はコードでは守れないため、運用条件としてここに置きます。

> [!WARNING]
> **`GEMINI_API_KEY` には、課金が有効な（＝有料枠の）APIキーだけを設定してください。**
>
> *   **Gemini API の無料枠は、送った入力データを Google の製品改善（モデルの改良）に使います。** 使わせないためには、課金が有効なキーで呼ぶ必要があります。
> *   この機能は「**学習に使用されないという条件で**」使うものとして許可されました（2026-08-21 決定・決定者はユーザー）。原文:
>     > GoogleやMicrosoftにはすでに書類が置いてあるので、大丈夫です。
>     > 学習に使用されないという条件で使用しています
>
>     「無料枠だと学習に使われる」旨の追加確認に対する回答は「**有料枠で使います**」。
>     つまり**課金の有効化はこの許可の前提条件**であり、無料枠のキーを挿せば取引先の書類が学習に使われ、**合意違反になります**。
> *   **コードからは判定できません。** Gemini の呼び出しは [gemini.go](../internal/cms/gemini.go) の `geminiGenerate` に1本化されており、環境変数を読んで、そのキーで送るだけです（`os.Getenv("GEMINI_API_KEY")`＝38行目、`option.WithAPIKey(apiKey)`＝45行目）。有料か無料かはアプリからは見えないので、**運用で担保するしかありません**——キーの発行・差し替え・環境ファイル更新のたびに、課金が有効なプロジェクトのキーであることを確かめてください。

### 7.1 何が、いつ社外へ出るか

> **2026-09-16 に、この節の行番号を関数名へ置き換えました。** app.js の番号が実際より
> 400行ずれており（2873 → 3265）、**数字が古いことに気づく手立てが読む側にありません**。
> 関数名なら grep で当たります。同日に `/api/parse-pdf` の実装が
> `internal/cms/pdf_handler.go` から **`ext/subcon/parse_pdf.go`** へ移りました。

*   **引き金はエディタのボタン2つだけ**です（どちらも人の操作の直後にだけ送る＝人間ゲート型）: 受発注ブロックの「🤖 PDFから明細を解析」（[app.js](../assets/app.js) の `.parse-pdf-btn` を作る枝 → `parsePDFIntoSection` が `POST /api/parse-pdf`）と、📎添付に出る「🤖 解析」（同 `makeAnalyzeButton` → `POST /api/analyze-attachment`。PDF添付とZIP内PDFで共用。2026-09-01）。**PDFを添付（ドロップ）しただけでは送信されません**——`/api/upload-pdf`・`/api/upload-file` はサーバー内の `files/` へ保存するだけです（[pdf_handler.go](../internal/cms/pdf_handler.go) の `UploadPDFHandler`）。**通信箱への `.eml` ドロップ（取り込み）も Gemini を呼びません**（[ext/comm/intake.go](../ext/comm/intake.go) の `serveIntake` 末尾のコメント——添付PDFの解釈はボタンからだけ。当初あった到着時の自動判定は同日にボタン起動へ一本化）。
*   **送られるのはPDFの中身全体**です。ファイルを丸ごと読み（`/api/parse-pdf` は [ext/subcon/parse_pdf.go](../ext/subcon/parse_pdf.go) の `os.ReadFile`、`/api/analyze-attachment` は [ext/subcon/analyze_pdf.go](../ext/subcon/analyze_pdf.go) の `loadPDFForAnalysis`）、`application/pdf` の Blob として、それぞれのプロンプト（明細抽出＝`parse_pdf.go` の `prompt :=`、発注書判定＋ヘッダ・明細抽出＝`analyze_pdf.go` の `prompt :=`）とともに `gemini-3.5-flash`（[gemini.go](../internal/cms/gemini.go) の `geminiModelName`）へ渡します。取引先名・品番・単価・数量が載った書類そのものが社外へ出ます。**どちらの口も `ext/subcon`（下請け業務）の持ち物**なので、`-tags minimal` のビルドでは**社外へ出る経路そのものがありません**（2026-09-16）。
*   **出せるのは `.pdf` の添付**（`/api/parse-pdf`。`cms.SafeAttachmentName` に `.pdf` だけを渡す）**と、`.zip` 添付の中の1件のPDF**（`/api/analyze-attachment`。同じ関門へ `.pdf`／`.zip` を渡す。取り出しは `max_upload_mib` を上限に打ち切る）だけです。**名前の関門はコアの1箇所**（[pdf_handler.go](../internal/cms/pdf_handler.go) の `SafeAttachmentName`）で、置く側と送る側が同じものを通ります——本文 `<id>.html`・権限サイドカー `<id>.meta.json` の名指し拒否がそのまま効きます（添付の置き場が `files/` に分離された今は構造上も届きません）。⚠ **送る側が自前の名前検査を書くと、かつての非対称**（置く側は守られ、送る側だけ素通し）**が復活します**。
*   `/api/parse-pdf` の応答（抽出された明細行）はエディタの表へ追加されるだけで、正データへの反映は利用者の保存操作（`/api/save`）を待ちます。**`/api/analyze-attachment` は違います**——「顧客の発注書」と判定されると**その場で受注ページ（子ページ）が作られます**（保存操作を待たない。取り消しはページ削除＝ゴミ箱への移動）。

### 7.2 この機能を使わない選択肢

*   **`GEMINI_API_KEY` を設定しなければ、PDFは一切送信されません。** `geminiGenerate` はキーが空なら Gemini クライアントを作る前に `errNoGeminiKey` で戻ります（[gemini.go](../internal/cms/gemini.go) 38〜41行目）。**PDFのファイル読み込み自体はその前に済んでいます**（2026-09-01 の切り出しで順序が変わった。サーバー内のメモリに載るだけで外へは出ない）。
*   ただし**解析ボタン自体は消えません**（サーバーはキーの有無を配らないので、画面には知りようがない）。押すと「サーバーに GEMINI_API_KEY 環境変数が設定されていません」という内容がトーストで表示されるだけです（[app.js](../assets/app.js) 3287行目の解析失敗表示。「🤖 解析」側は同 2934行目——文面は「…設定してから起動し直してください」）。機能ごと隠す・無効化するスイッチは**未実装**です。
*   明細表は通常のエディタ操作で手入力できるため、キーを配らないまま受発注ブロックを運用できます（AI解析は入力の補助にすぎません）。
*   キーを配る場合、`GEMINI_API_KEY` は秘密情報です。§2 ステップ3 のとおり `EnvironmentFile=`（`root:root 0600`）へ置き、ユニットファイルやリポジトリへ直書きしないでください。
