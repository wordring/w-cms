# 【ガイド】デプロイ・運用

このドキュメントでは、**w-cms** をサーバー上で運用・デプロイする際の手順と、ディレクトリ構成の動作仕様について説明します。

---

## 1. サーバー実行時のディレクトリ構成と動作仕様（対策Aの採用）

w-cms は、データ保存用ディレクトリ（`data`）へのパスがソースコード内で**相対パス**で実装されています。
そのため、実行時の挙動は以下のようになります。

*   **動作仕様**: `data` ディレクトリは、**「実行可能ファイルを実行した時のカレントディレクトリ（作業ディレクトリ）」の直下**に生成されます。
*   **本番サーバーでの運用方法**: 実行可能ファイルの配置場所に関わらず、サービス起動時に作業ディレクトリ（WorkingDirectory）を明示的に指定して実行します。

---

## 2. サーバー（Linux / systemd）へのデプロイ手順

本番サーバーで常時実行（デーモン化）させるための手順です。

### ステップ 1: アプリケーションのビルド
開発環境でターゲットサーバーのOS（例: Linux）に合わせてビルドを行い、バイナリを生成します。

```bash
# Linux（AMD64環境）向けにクロスビルドする場合
$Env:GOOS="linux"
$Env:GOARCH="amd64"
go build -o w-cms cmd/w-cms/main.go
```

### ステップ 2: サーバーへの配置
生成された `w-cms` バイナリを、サーバーの任意のパスに転送します。
*   **バイナリ配置先例**: `/usr/local/bin/w-cms`
*   **データ格納先ディレクトリ例**: `/var/www/w-cms` （ここを作業ディレクトリとします）

サーバー上でデータ格納先ディレクトリを作成し、適切な権限を付与しておきます。
```bash
# サーバー側で実行
mkdir -p /var/www/w-cms
chown -R www-data:www-data /var/www/w-cms
```

### ステップ 3: systemd サービスファイルの作成
`/etc/systemd/system/w-cms.service` を作成し、以下のように定義します。

```ini
[Unit]
Description=w-cms Content Management System
After=network.target

[Service]
Type=simple
User=www-data
Group=www-data
# ★重要: dataフォルダを作成・参照する基準ディレクトリを指定します
WorkingDirectory=/var/www/w-cms
# 実行バイナリのパス
ExecStart=/usr/local/bin/w-cms
Restart=always

[Install]
WantedBy=multi-user.target
```

> **設定は環境変数のみで渡します**（2026-08-16 決定。[要件定義書.md](要件定義書.md) §4.3 の
> 一覧表が正本）。アプリは設定ファイルもコマンドラインフラグも持ちません。
> 設定を一覧できる場所が欲しい場合は、systemd の `EnvironmentFile=` を使います:
>
> ```ini
> [Service]
> EnvironmentFile=/etc/w-cms/prod.env
> ```
>
> ```bash
> # /etc/w-cms/prod.env（root:root 0600 で保護すること。GEMINI_API_KEY 等の秘密が載る）
> GEMINI_API_KEY=xxxx
> ```
>
> **2インスタンス運用**（業務用／サイト用。要件定義書 §1.1）では、ユニットと環境ファイルを
> 1組ずつ用意します（`w-cms-gyomu.service` ＋ `/etc/w-cms/gyomu.env`、`w-cms-site.service` ＋
> `/etc/w-cms/site.env`）。別サーバーが基本ですが、同一ホストに同居させる場合は
> `WCMS_ADDR`・`WCMS_DATA_DIR`（未実装・要件定義書 §5）で待受とデータ置き場を分けます。

### ステップ 4: サービスの起動と有効化
```bash
# 設定の再読み込み
sudo systemctl daemon-reload

# サービスの起動
sudo systemctl start w-cms

# サーバー起動時の自動起動を有効化
sudo systemctl enable w-cms

# ステータスの確認
sudo systemctl status w-cms
```

この設定により、`data/cms.db` や `data/master/` は常に `/var/www/w-cms/data/` 配下に作成・保存され、安全に運用できます。

---

## 3. 開発環境（会社・自宅）での注意点

複数環境で開発を行う際、`git pull` 後にローカル環境で動かす場合も同様の考え方が適用されます。

*   **ローカル実行時**:
    プロジェクトルート（`C:\Users\kouic\source\repos\w-cms`）で `go run cmd/w-cms/main.go` を実行した場合、データは `C:\Users\kouic\source\repos\w-cms\data` に作成されます。
*   **Gitの除外設定**:
    ローカルで作成されたデータベースやアップロード画像などの実データは、`.gitignore` によってGitの管理対象外に設定されているため、会社と自宅の間で勝手に上書き同期されることはありません（ソースコードのみが同期されます）。

## 4. バックアップと復元（ファイルベース）

w-cms は **「`data/master/` 配下のファイル群（HTML本体とアップロードPDF）が唯一の正データであり、`data/cms.db`（SQLite）は派生インデックスにすぎない」** という設計です。データベースはいつでもファイルから再生成できるため、バックアップ・復元はファイルのみを対象にすればよく、DBファイルは対象に含める必要がありません。

> [!IMPORTANT]
> **不変条件**: データベースには「ファイルから再生成できないデータ」を一切持たせてはいけません。新しいプラグインを追加する際も、DBの全カラムが `data/master` のHTMLから `SyncIndex` で再生成可能であることを必ず保証してください。この不変条件が、ファイルのみのバックアップ戦略の前提です。

### 4.1. バックアップ手順
*   **対象（必須）**:
    *   `data/master/` ディレクトリ全体（HTML本体・PDF・権限サイドカー）。正データ。
    *   **`data/auth.db`**（ユーザー・グループ・セッション等の認証情報）。**ファイルから再生成できないため必ずバックアップする**。
*   **対象外**: `data/cms.db`（派生インデックス。バックアップしてもよいが必須ではない。復元時は再生成される）。
*   稼働中でも `data/master` 配下のファイルは追記・上書きのみで参照整合が壊れないため、ファイルコピーやrsyncでそのまま取得できます。`auth.db` はSQLiteなので、整合の取れたコピーが必要なら停止中に取得するか `VACUUM INTO` 等を使います。

```bash
# 例: 正データと認証DBをまとめてバックアップ
tar czf wcms-backup-$(date +%Y%m%d).tar.gz data/master data/auth.db
```

### 4.2. 復元手順
1.  バックアップした `data/master/` を元の場所へ展開する。
2.  アプリケーションを起動する。
3.  **起動時の自動リビルド**: `pages` テーブルが空（DBが無い・新規作成された状態）で、かつ `data/master` にHTMLファイルが存在する場合、w-cms は起動時に自動でデータベースを全再構築します。したがって復元は「ファイルを戻してアプリを起動するだけ」で完了します。
4.  自動リビルドが走らない状況（既存DBがある場合など）で手動再構築したいときは、`POST /api/rebuild-db` を呼び出します。

---

## 5. データベースの全再構築（リビルド）

`RebuildDatabase`（`POST /api/rebuild-db` から呼ばれる）は、ファイル群を正としてデータベースを完全に作り直す処理です。

### 5.1. 動作（全テーブルDROP方式）
1.  現在DBに存在する全テーブルを `sqlite_master` から列挙し、すべて `DROP TABLE` する（廃止されたプラグインの残存テーブルなど、スキーマのdriftも含めて完全に消去する）。
2.  コアテーブル（`pages` / `page_perms`）と、登録済み全プラグインのテーブルを作り直す（`CreateCoreTables` ＋ `ApplySchema`）。`page_tags` と汎用索引 `vocab_index` もプラグインとして登録されているのでここで作り直されます。
3.  `data/master` 配下のすべての `.html` を走査し、`SyncIndex` で再同期する。

> [!NOTE]
> DBファイル自体は削除しません。SQLiteの接続を開いたまま全テーブルをDROP・再作成することで、Windowsでのファイルロック（オープン中のファイルは削除できない）や、リビルド中の他リクエストとの競合を避けています。リビルドは冪等なので、途中失敗した場合は再実行すれば回復します（正データはファイル側にあるため失われません）。

## 6. 認証の運用

設計は [認証認可設計.md](認証認可設計.md)。ページ単位の認可（Unix風 read/write・owner/group/other）と
匿名公開（`public`＋パスゲート）まで実装済み。

### 6.1. 初期管理者の作成
初回起動時、`users` が空のときだけ環境変数から管理者を作成します。作成後は環境変数を外してください。

```bash
WCMS_ADMIN_USER=admin WCMS_ADMIN_PASSWORD='強いパスワード' ./w-cms
```

systemd で運用する場合は、`[Service]` に一時的に `Environment=` を記述して初回起動 → 作成ログを確認 → 該当行を削除して `daemon-reload` ＆再起動、という手順が安全です。

### 6.2. HTTPS（必須）とリバースプロキシ
インターネット公開のため **TLS/HTTPS は必須**です。Caddy / nginx 等のリバースプロキシでTLS終端・レート制限を行い、その背後で w-cms（`:8080`）を動かす構成を推奨します。

*   セッションCookieは既定で `Secure` 属性付き（HTTPSでのみ送信）。プロキシTLS終端でアプリへはHTTPで届く構成でも、ブラウザ↔プロキシ間がHTTPSなら問題ありません。
*   ローカルでHTTP（`http://localhost:8080`）のまま動作確認したいときだけ、`WCMS_SECURE_COOKIES=0` で `Secure` 属性を外せます。**本番では設定しないでください。**

> **プロキシ側で CSP を上書き・除去しないこと**（2026-08-19 に strict 化）。アプリは全レスポンスへ
> `default-src 'self'; script-src 'self'; style-src 'self'; object-src 'self'; base-uri 'self'; frame-ancestors 'self'`
> を付けます（[middleware.go](../internal/auth/middleware.go) の `CSPProtect`）。`'unsafe-inline'` を
> 含まないため、**プロキシやWAFがインラインの `<script>`／`<style>` を注入する機能（エラーページの
> 差し込み・計測タグ・デバッグバナー等）を有効にすると、そのスクリプトはブラウザでブロックされます**。
> アプリ本体は外部リソースを一切使わないので、素の構成なら追加設定は不要です。
> 方針の経緯は [【考察】CSP強化.md](【考察】CSP強化.md)。

### 6.3. 復元時の注意
バックアップから復元する場合、`data/master`（正データ）に加えて **`data/auth.db`（認証情報）も戻して**ください。`auth.db` を戻さないとユーザー・セッションが失われ、初期管理者の再作成が必要になります。
