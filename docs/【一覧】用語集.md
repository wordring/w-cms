# 【一覧】用語集

w-cms で使う用語の正本です。**業務の用語**（受注／発注・納品・部材…）と**画面の用語**
（レール・クローム・ブロック…）の両方をここに集めます。設計・実装・ドキュメント・
コミットメッセージ、そして会話で**用語を統一**するために使ってください。

- **§1 業務の用語** ——「何を扱っているか」。受発注・ものづくり・納品・通信記録。
- **§2 画面の用語** ——「どこの話をしているか」。「左のパネル」「サイドバー」「メニュー」
  のような曖昧な指し方を避けるために用意しました。実装は
  [assets/index.html](../assets/index.html)、挙動の詳細は [エディタ仕様.md](エディタ仕様.md) §9 が正本です。
- **§3 基盤の用語** —— 両者にまたがる土台（ページ・正本性・語彙・計算ビュー）。

> **本文で使える形式（`data-type`）の一覧**は [【一覧】語彙.md](【一覧】語彙.md)（語彙レジストリの鏡）が正本です。
> ここには個々の形式は載せません。
>
> 2026-08-21 に「画面構成と用語.md」を本ファイルの §2 へ統合しました
> （用語の正本が業務用と画面用の2冊に分かれていて、どちらを引けばよいか分からなかったため）。

## 1. 業務の用語

> 方針メモ:
> - **「発注書」という裸の語は視点で意味が変わり曖昧**（顧客が出す発注書＝こちらは受け取る側）。視点に依らない**役割語**で呼ぶ。
> - 受け取る側／出す側の対は、標準的で曖昧のない **`受注` ／ `発注`** を採用する（`注文` 案は実在の「注文書」に根ざすが、`受注` の教科書的対義語である `発注` を選んだ。2026-06-27 決定）。
> - 見積の2種は、取引の性質で **`販売見積` ／ `購入見積`** とする（`売上/原価見積` 案は「原価見積＝社内原価積算」と紛れるため避けた。2026-06-27 決定）。
> - 「状態」欄が **実装済み** の語は現行コードに対応がある。**設計中** の語は [【考察】通信記録処理.md](【考察】通信記録処理.md) 等で検討中で未実装。

### 1.1 受発注・取引の中核

| 用語 | 意味 | 実装・状態 |
|---|---|---|
| **受注** | **顧客から届いた発注書**（こちらが受け取る側）。売上側。通信記録（メール）から独立した長命エンティティで、別メールにより**変更・取消**され得る（取消は削除でなく状態フラグ）。 | 実装済み：`<section data-type="client-order">`＋明細 `<table data-type="client-order-items">`。エディタは**機能見出し形** `<section><h2>顧客の発注書</h2>…` で挿す（D-2・2026-08-31。属性形も引き続き読む）（呼称は順次 `受注` へ統一） |
| **発注** | **加工業者・材料屋へ送る発注書**（こちらが出す側）。仕入側。 | 実装済み：`<section data-type="our-order">`＋明細 `<table data-type="our-order-items">`。エディタは見出し形 `<section><h2>自社の発注書</h2>…` で挿す（呼称は順次 `発注` へ統一） |
| **同時受注** | **同時に届いた複数の受注の束**（1通のメール／同日受信などの塊）。複数の受注を束ねる**参照ハブ**の一種。 | 設計中（[通信記録メモ §4.3](【考察】通信記録処理.md) のグルーピング軸の一つ） |
| **案件** | 受注・発注・部材・見積を突き合わせる**業務単位（ジョブ）**。「1文書＝1ページ」採用後は、文書ページを**参照マーカー**で束ねる**参照ハブページ**として表す。 | 設計中（[通信記録メモ §2.5](【考察】通信記録処理.md)）。現行は `page_id` 単位の集計 |
| **販売見積** | 弊社が顧客へ提示する見積（売上予定）。確定すると**受注**になる。 | 実装済み：`<dl data-type="our-estimate">`。エディタは見出し形 `<section><h2>弊社の見積もり</h2><dl>…` で挿す（呼称は順次 `販売見積` へ統一） |
| **購入見積** | 仕入先（材料屋・加工業者）が弊社へ提示する見積（原価予定）。確定すると**発注**になる。 | 実装済み：`<dl data-type="supplier-estimate">`。エディタは見出し形 `<section><h2>材料屋の見積もり</h2><dl>…` で挿す（呼称は順次 `購入見積` へ統一） |

**受発注の2×2（予定→確定）**:

| 段階 | 売上側（顧客と） | 原価側（仕入先と） |
|---|---|---|
| 予定（見積） | **販売見積** | **購入見積** |
| 確定（発注書類） | **受注** | **発注** |

```
販売見積 ─(確定)→ 受注      （顧客と・売上側）
購入見積 ─(確定)→ 発注      （仕入先と・原価側）
```

### 1.2 ものづくりの対象

| 用語 | 意味 | 実装・状態 |
|---|---|---|
| **部品** | 製造・加工の対象。`item_id`（製品コード／図面番号）で識別。 | 実装済み：明細表の「品番」列（見出しがレジストリの機械キー `item-id` へ解決される）、および `<dl data-type="tags">` の「部品番号」項目（[受注から利益まで §5](【ユースケース】受注から利益まで.md)） |
| **図面** | 部品の仕様図（PDF/画像/DWG等）。部品とは**多対多**（1図面で1部品／1部品が複数図面）。 | 設計中（[通信記録メモ §4.2](【考察】通信記録処理.md)）。現状は資料添付 |
| **部材** | 1部品あたりに必要な材料。 | 実装済み：`<table data-type="part-materials">`（行そのものには部品番号が無く、ページ横断メタの「部品番号」タグがページ全体の鍵になる＝レジストリの `RequiresTag`） |

### 1.3 納品・進捗

| 用語 | 意味 | 実装・状態 |
|---|---|---|
| **納品** | 受注に対して品物を納めるイベント（◯月◯日に N 個）。 | 設計中（[通信記録メモ §4.3](【考察】通信記録処理.md)） |
| **分納** | 1つの受注を**複数回に分けて納品**すること。充足は `受注数 − Σ納品済数 = 残` で集計。 | 設計中 |
| **進捗（status）** | 部品ごとの状態。現行は単一enum（受注明細＝未着手/加工中/検査中/納品済、発注明細＝未納品/納品済）。分納対応で数量ベース化を検討。 | 実装済み（enum）：明細表の「状態」列（機械キー `status` へ解決）。選択肢は語彙レジストリ（`vocab.go`）が持つ。数量ベース化は設計中 |
| **受注残** | まだ納品し切っていない受注の残数（`現在の受注数 − Σ納品済数`）。**納品では受注数を書き換えず**残が計算で減る。一方**受注変更では受注数そのものを改訂**できる（文書ベースゆえの柔軟性）。**計算ビュー**（§3）として集計表示する（保存せずDBから導出）。 | 設計中（[通信記録メモ §2.6・§4.3](【考察】通信記録処理.md)） |
| **納期** | 納品の期限。**部品（明細）単位**で持つ（受注全体でなく明細行ごと）。現状は `<dl data-type="tags">` の自由記入タグ「希望納期」、明細単位化（列の追加）は設計中。 | 設計中（[通信記録メモ §4.3](【考察】通信記録処理.md)） |
| **納期ビュー（生産スケジュール）** | 残のある明細を納期昇順に並べた計算ビュー（受注残×納期）。製造の優先順位付けに使う。 | 設計中（[通信記録メモ §2.6](【考察】通信記録処理.md)） |

### 1.4 通信記録まわり（受信箱・`.eml` 取り込み・🤖解析は 2026-09-01 に実装。残りは設計中）

> **形の注記**: 未実装のものも含め、下表の形はすべて **`data-type` マーカー付きの標準HTML**
> （語彙レジストリへ1件足す）で作る。独自の要素は作らない。

| 用語 | 意味 |
|---|---|
| **通信記録** | メール・FAX・電話で外部から届いた受信の記録。実装形（2026-09-01・`intake_eml.go`）は `<h1>件名</h1>`＋可変タグ（差出人・宛先・受信日時・メッセージID）＋本文＋📎添付リンクの通信記録ページ。 |
| **受信箱（intake）ページ** | 取り込みの着地ページ。ここへ `.eml` 等をドロップすると取り込み係が子ページを作る（**実装済み**・2026-09-01。トップ直下の「受信箱」ページ——名前が機能。`intake.go`。[§3.2](【考察】通信記録処理.md)）。 |
| **文書ページ** | 1発注書／1図面／1見積など**1文書＝1ページ**の原本＋構造化データ（[§2.5](【考察】通信記録処理.md)）。 |
| **参照ハブ（案件／同時受注 等）ページ** | 文書ページを**参照タグ**（名前：値・値は `ページID-ブロックID`）で引いて束ね、集計する側のページ（[§2.5・§4.4](【考察】通信記録処理.md)）。 |
| **受信元（由来参照）** | 文書ページ（受注など）が持つ、由来となった通信記録ページのページID。自己完結した文書から受信原本（`.eml`）へ戻るための後ろ向きポインタ（実装は `<dl data-type="tags">` の「受信元」項目——🤖解析が作る受注ページに `ページID-添付ID` の参照タグとして書く。`analyze_pdf.go`）。[§9.1](【考察】通信記録処理.md)。 |

## 2. 画面の用語

会話・Issue・コミットメッセージで画面上の位置を指すときは、ここの呼び名を使ってください。

### 2.1 全体レイアウト

```
┌─────────────────────────────────────────────────────────────────┐
│ ヘッダー  .header                                                │  ← クローム
│  タイトル領域 .title-area        モード切替 / ⚙管理 / ログアウト  │
├──────────┬───────────────────────────────────┬──────────────────┤
│          │                                   │                  │
│ 左レール │           文書                    │   右レール       │
│ .rail    │        .doc-column                │   .rail          │
│ -left    │                                   │   -right         │
│ ┌──────┐ │  ┌─────────────────────────────┐  │                  │
│ │ 目次 │ │  │     #w-editor-content       │  │  ┌────────────┐  │
│ └──────┘ │  │      （本文＝正本）          │  │  │ ページ情報 │  │
│ ┌──────┐ │  └─────────────────────────────┘  │  └────────────┘  │
│ │子ページ│ │  ┌─────────────────────────────┐  │  ┌────────────┐  │
│ └──────┘ │  │      HTMLプレビュー          │  │  │ 🔒 権限    │  │
│ ＋子ページ│  │      #w-html-preview        │  │  └────────────┘  │
│  を作成  │  └─────────────────────────────┘  │                  │
├──────────┴───────────────────────────────────┴──────────────────┤
│ フッター帯  .site-footer                                         │
└─────────────────────────────────────────────────────────────────┘
   ↑つまみ .rail-toggle                              つまみ↑
```

作業領域 `.work-area` は **flex の3カラム**（左レール｜文書｜右レール）です。狭幅では2段階
（1100px で右レール、760px で左レールも）で**ドロワー**になり、レールはあふれたら自分の中でスクロールします。
挙動の仕様（ブレークポイント・バックドロップ・レール内スクロール・目次の置き場の経緯）は
[エディタ仕様.md](エディタ仕様.md) §9.1・§9.1.1 が正本です。

### 2.2 殻の各部（クローム）

| 呼び名 | DOM | 範囲・役割 | 本文に保存 |
|---|---|---|---|
| **ヘッダー** | `<header class="header">` | 画面最上部の帯。ページ名、編集モードのスイッチ、⚙管理、ログアウト。下スクロールで隠れ上スクロールで戻る（headroom 型。`.header--hidden`） | ✗ |
| **作業領域** | `.work-area` | ヘッダーとフッターに挟まれた本体。レールと文書を並べる器 | — |
| **レール** | `<aside class="rail …">` | 文書の左右に立つ縦長のパネルの**総称**。**2本**（左・右）。あふれたらレールの中でスクロールする | ✗ |
| └ **左レール** | `.rail-left` | **目次**（`#w-toc-list`。本文の見出し `h1`〜`h6` から生成）と、**ページ階層**に対する情報と操作。親ページへのリンク、子ページカード、「＋ 子ページを作成」（`#w-create-subpage-btn`）、「🗑 このページを削除」（`#w-delete-page-btn`。どちらも編集モードのときだけ出る。削除はさらにトップページ以外） | ✗ |
| └ **右レール** | `.rail-right` | **このページ**に対する情報と操作。ページ情報カード、権限カード、版の履歴カード（`#w-vh-list`） | ✗ |
| **カード** | `<section class="rail-card">` | レールの中の1区画。`<details>` で折りたためる。見出しは `<summary>` | ✗ |
| **つまみ** | `.rail-toggle` | 各レール脇に固定された開閉ボタン。レールを閉じても残る（`.rail-toggle-group` に束ねる） | ✗ |
| **文書** | `.doc-column` | 中央のカラム。本文とHTMLプレビューを縦に並べる | — |
| └ **本文** | `#w-editor-content` | **ページの内容そのもの**。ここだけがファイルへ保存される | **✓** |
| └ **HTMLプレビュー** | `#w-html-preview` | 保存される正本HTMLをそのまま映す読み取り専用テキストエリア | ✗ |
| **フッター帯** | `<footer class="site-footer">` | 画面最下部の帯。現状は「w-cms」の仮表示のみ | ✗ |
| **ドロワー** | （`.rail` の狭幅時の姿） | 狭い画面でレールが文書に重なって出入りする形態（§2.1） | ✗ |

**クローム**＝本文以外のUI全般（ヘッダー・レール・カード・つまみ・フッター帯）を指す総称。
「クロームは保存されない」が本プロジェクトの一貫した原則です。

> **殻の `id` はすべて接頭辞 `w-` を持ちます**（[assets/index.html](../assets/index.html) の全70個・2026-09-02 時点）。
> 殻が接頭辞を独占し本文の `id` は自由、という分担の理由と後戻りの検出は [本文サニタイズ設計.md](本文サニタイズ設計.md) §5.4 が正本。

### 2.3 本文の中の用語

本文（`#w-editor-content`）の中は、エディタが動的にラッパーを被せます。

| 呼び名 | DOM | 説明 |
|---|---|---|
| **ブロック** | `.editor-block` | 本文の最小単位。見出し・段落・表・業務文書ブロックそれぞれを包む |
| └ **ブロック操作** | `.block-controls`・`.add-btn` | ブロック左脇のドラッグハンドル `⠿` と削除 `🗑`（`.block-controls`）。「＋」（`.add-btn`）は `.block-controls` の外で、ブロック**下端の境界の中央**に出る（2026-08-31）。どちらも編集モードでホバー時に出る |
| └ **ブロック本体** | `.block-content` | 実際の要素（`<h1>`・`<p>`・`<section data-type="file">` 等）を入れる器 |
| **スラッシュメニュー** | `#w-slash-menu` | 段落で `/` を打つと出る挿入メニュー（続けて打つ文字で絞り込み）。**手書きは3項目**（H1 見出し・P 段落・🖼 画像）、JS が足す汎用の「表」「定義リスト」（骨組みの下書き）、残りは語彙レジストリから動的生成（12形式のうち `Hidden` の明細表2形式を除く10項目。機能見出し形で挿す） |
| **テンプレートメニュー** | `#w-template-menu` | 「＋ 子ページを作成」で出る小さなメニュー。先頭が「空のページ」、以下が `/api/templates` から得たテンプレートのツリー（枝＝分類の見出し、葉＝テンプレート。[【考察】ページテンプレート.md](【考察】ページテンプレート.md)） |
| **コンテキストツールバー** | `#w-context-toolbar` | ブロックにフォーカスすると上に浮く小さなバー（B/I/U/🔗。タッチ端末では画面下のドック `.is-docked`） |
| **表ツールバー** | `#w-table-toolbar` | 本文中の表のセルにキャレットがあると出る行・列操作（＋行/↑/↓/✕行・＋列/←/→/✕列/⚙）。`data-type` の有無を問わない（計算ビューの中は除く） |
| **dlツールバー** | `#w-dl-toolbar` | 本文中の `dl` の項目にキャレットがあると出る項目操作（＋項目/＋値/↑/↓/✕項目）。`data-type` の有無を問わない |
| **列設定ポップオーバ** | `#w-col-popover` | 表ツールバーの ⚙ で開く。列型の明示（`th` の `data-type`）＝属性側の編集口 |
| **リンクのプロパティ欄** | `#w-link-popover` | キャレットがリンク上にあると出る宛先の入力欄＋「リンクを外す」。ダイアログは出さない（[エディタ仕様.md](エディタ仕様.md) §3.2） |
| **選択肢メニュー** | `#w-enum-menu` | enum 列のセルにキャレットがあると出る、レジストリ宣言の選択肢一覧 |
| **トースト** | `#w-toast-host` の子 | 画面隅に出る一時的な通知（保存結果・ロック状態など） |
| **形式の枠** | `body[edit-mode] … [data-type]` | 編集モードだけに出る破線の枠。「**w-cms がこの要素を見る**」ことを示す（形式ブロック・ファイル容器・計算ビュー）。ページタイトルになる最初の `h1` にも同じ枠が出る（実行時クラス `is-page-title`。属性にしないのは位置で決まるため） |
| **認識の背景色** | `.vocab-word`・`dl[data-type="tags"] dt`・`.cell-known` ／ `.is-vocab-unknown`・`.cell-invalid` | 編集モードの識別は背景色3値（薄い青＝機械が読む／薄い赤＝未定義・型不一致／無印＝素の本文）。正本は [エディタ仕様.md](エディタ仕様.md) §3.2 |
| **語彙クローム** | `.vocab-chrome` | 本文の中に**混ざって見えるが保存されない**DOM。①計算ビューの中身（サーバー事前描画が埋める）②エンハンサが付ける付帯UI（PDFプレビュー・ドロップゾーン・AI明細解析ボタン）③閲覧モードの添付クローム（📎リンク横の「▶ 表示」「▶ 中身」「🤖 解析」と展開したプレビュー・目録）の3用途 |

`.editor-block` と `.block-content` は**エディタが挿す枠であって本文ではありません**。
保存時のシリアライザはこれらを剥がします（[エディタ仕様.md](エディタ仕様.md) 6.1.1）。
`.vocab-chrome` も同様に、シリアライザが読み飛ばすので正本HTMLには入りません
（本文に残るのは空のマーカー `<section data-type="child-list">` 等だけ）。
**本文DOMを走査する新しいコードは、`.vocab-chrome` を除外したか必ず確かめること**——
本文の `class` はサニタイザが必ず落とすので、この判定が誤爆することはありません。

### 2.4 表示モードによる差

| モード | 条件 | 見え方 |
|---|---|---|
| **閲覧モード** | 既定 | 本文は読み取り専用。ブロック操作・スラッシュメニューは出ない |
| **編集モード** | `body[edit-mode]` | 編集ロックを取得済み。本文が `contenteditable` になり、クロームの操作系が有効 |
| **匿名** | `body.anonymous` | 未ログインで実効公開ページを見ている状態。右レールと書き込み系UIはCSSごと隠れる |

**計算ビューはどのモードでも同じ**です。中身はサーバーがページを返すときに埋めるので、
閲覧モード・匿名でもJavaScriptなしで表が見えます（[view_render.go](../internal/cms/view_render.go)）。
編集モードでも中身は `contenteditable` になりません（エディタの持ち物ではないため）。
そのぶん**編集中の変化は自動反映されません**——子ページを作っても、子ページ一覧のビューに
現れるのは再読み込み後です（描画ロジックをGoとJSの2箇所に持たないための割り切り）。

## 3. 基盤の用語（業務と画面にまたがる土台）

| 用語 | 意味 | 出典 |
|---|---|---|
| **ページ** | w-cms の文書の単位。親子の木構造を成し、本文HTML（内容）＋サイドカー（属性）で構成。通信記録・文書・案件（参照ハブ）等もすべてページ。 | [アーキテクチャ §1-2](アーキテクチャとDBスキーマ.md) |
| **ページID** | ページの一意な識別子。**6桁ゼロ埋めの数値文字列**（例: `000001`、トップページは `000000`）。`pages.id`（`INTEGER PRIMARY KEY`）の採番値を桁埋めしたもので、URLパス（`/000001`）や保存フォルダ `data/master/{先頭2桁}/{id}/` の基底になる。 | [アーキテクチャ §6](アーキテクチャとDBスキーマ.md) |
| **正本性** | `data/master` のファイル群が唯一の正データ。DB（`cms.db`）は再生成可能な派生インデックス。 | [アーキテクチャ §8](アーキテクチャとDBスキーマ.md) |
| **受信原本** | 受信したまま改変しない証跡（生 `.eml`／スキャン元）。`.eml` は添付を内包する完全アーカイブ。 | [通信記録メモ §9.1](【考察】通信記録処理.md) |
| **自己完結性** | 各文書ページが業務用の実ファイルを自分のフォルダに所有し、単体で意味が保てること。 | [通信記録メモ §9.1](【考察】通信記録処理.md) |
| **サイドカー** | ページの属性（親ID・所有/権限・作成/更新情報）を持つ `<id>.meta.json`（正本）。本文HTMLは「内容」。 | [アーキテクチャ §2](アーキテクチャとDBスキーマ.md)・[エディタ仕様 §9](エディタ仕様.md) |
| **版管理（リビジョン）** | 多くの取引から参照される定義（部品仕様・図面）の改訂方式。**旧版を消さず保持・新版を追加・現行を状態フラグでマーク**し、参照は使った版を固定（ピン）する。受注のような「その場編集（現在状態）」と区別し、過去取引を遡及改変しない。 | [通信記録メモ §4.6](【考察】通信記録処理.md)・[アーキテクチャ §7](アーキテクチャとDBスキーマ.md) |
| **プラグイン** | 1ユースケース＝1ファイル（`internal/cms/plugin_*.go`）。本文HTML→テーブルの同期を自己登録する。3層モデルでは**③計算プラグイン**（計算が要る場合だけの手段）。**本文の語彙は持たない**（`Tags()` は 2026-08-20 に機構ごと撤去）。 | [【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md) |
| **マーカー付き標準HTML** | 集計・索引の手掛かりを**見える文字**が運ぶ標準HTML——繰り返し明細＝`<table data-type>`、名前:値＝`<dl data-type>`、業務文書ブロック＝`<section data-type>`。項目の鍵は見出し（`th`／`dt`）の**表示文字**が運び、機械キーは本文に現れない（`data-field` は 2026-08-20 に撤去。形式名は**機能見出し**（セクション最初の見出しの言葉）でも宣言でき、エディタはこの形で挿す——D-2・2026-08-31 実装。`data-type` は明示の正として残る＝[語彙モデル §11](【考察】語彙モデル.md)）。**語彙はこの形だけ**——本文に独自の要素は存在しない。 | [語彙モデル §2-§5](【考察】語彙モデル.md) |
| **語彙レジストリ** | 3層モデルの①。形式（`data-type`）の宣言データ（表示名・列・型・enum）。v1 はGoコード内の宣言テーブル（`vocab.go` の `vocabRegistry`。現在**12形式**）。**安全性の門ではない**（未知の `data-type` も通る）。 | [語彙モデル §4](【考察】語彙モデル.md) |
| **汎用索引** | 3層モデルの②。全 `table/dl[data-type]` と、機能見出しを持つセクションの素の `dl`/`table` を縦持ちで同期する `vocab_index` テーブル（コアに1実装。形式が増えてもスキーマ不変）。 | [語彙モデル §4](【考察】語彙モデル.md)・[アーキテクチャ §2](アーキテクチャとDBスキーマ.md) |
