# 【ユースケース】受注から利益まで

見積 → 受注 → 部材手配 → 製造・進捗 → 納品 → 原価と利益。町工場の業務のこの一本の流れを、
w-cms が本文（機能見出し形の標準HTML。旧 `data-type` 属性形も読める）でどう記録し、どこまで自動で計算するかを定めます。

> 旧 `【ユースケース】受注と進捗管理.md`（記録と進捗の面）と `【ユースケース】原価と利益.md`
> （金額の面）を統合した文書です。同じ業務・同じ語彙・同じテーブルを2つの文書が別々に説明していて、
> 「いま何が動いているのか」が読み取りにくくなっていたため、流れを1本にまとめました。

---

## 1. 業務の流れと実装状況（2026-09-02 時点）

本文からDBへの**記録（同期）は全段階で実装済み**です。動いていないのは**読み出す側＝集計と表示**で、
現在まともに集計しているのは**部材手配の1つだけ**です。

| 業務 | 使う形式（`data-type`） | 本文 → DB の同期 | 集計・表示 |
|---|---|---|---|
| 顧客へ見積を出す＝売上**予定**（§3.1） | `our-estimate` | **済**（②汎用索引） | **無い**。書き出すだけで読み出す機能が無く「あの部品は前いくらで出したか」を引けない。横断比較は要件化済み・未実装（[要件定義書.md](要件定義書.md) §5） |
| 業者から見積をもらう＝原価**予定**（§3.2） | `supplier-estimate` | **済**（②汎用索引） | 同上 |
| 顧客から発注書が届く＝売上**確定**（§4） | `client-order` ＋ `client-order-items` | **済**（②汎用索引）。発注書PDFからのAI明細抽出も**済**。受信箱の通信記録（`.eml`）の添付PDFから受注ページを生成する取り込みも**済**（2026-09-01・[【考察】通信記録処理.md](【考察】通信記録処理.md)） | — |
| 部品に要る部材を定義する＝BOM（§5） | `part-materials` ＋ ページ横断メタの「部品番号」 | **済**（②汎用索引） | — |
| 要手配数を出し、足りない分を発注する＝原価**確定**（§6） | `our-order` ＋ `our-order-items` ／ `required-materials` | **済**（②汎用索引） | **実装済み**。計算ビュー（サーバー事前描画）と `/api/required-materials`。集計の実体は `RequiredMaterials`（[plugin_materials.go](../internal/cms/plugin_materials.go)）で、**これがシステム唯一の集計** |
| 製造・加工・検査・納品の進捗を追う（§7） | 明細表の「状態」列 | **済**（`status` 列がDBへ同期される） | **未実装**（発注書ベースの進捗ボードは構想。§7.2） |
| 売上と原価を突き合わせて粗利を見る（§8） | （形式なし） | **済**（上の4テーブルが揃っている） | **未実装**。粗利を出す集計も、それを表示するビューも存在しない |

> **読み方**——未実装と書いた節は、「〜します」という書き方でも**未来形**（こう作りたい、の設計）です。
> 未実装のビューを実装するときに必要な手順は §9 にまとめてあります。

## 2. 記録の共通ルール

- **値は属性ではなく要素の中身**にあります（`dd` ／ `td` のテキスト）。項目の鍵も
  `dt` の項目名・`th` の見出しという**見える文字そのもの**です。だから閲覧側は
  JavaScript なしで読め、印刷してもそのまま意味が通ります。
  （なぜこの形かは [【考察】語彙モデル.md](【考察】語彙モデル.md)。使える形式の一覧は
  [【一覧】語彙.md](【一覧】語彙.md)、定義の実体は [vocab.go](../internal/cms/vocab.go)。）
- **PDF原本があるときは、業務文書ブロック自身が可視のファイル名リンク（`📎 <a href>`）を持ちます。**
  レジストリの `File` 宣言（[vocab.go](../internal/cms/vocab.go)）を持つのは**顧客の発注書（`client-order`）だけ**で、
  エディタはそのセクションへドロップ域・プレビュー・明細AI解析を配線します（自社の発注書に `File` は付けない——
  「表を基にw-cmsがPDFを作るのです」・2026-08-31 ユーザー訂正。見積2形式にも無い）。かつての容器
  `<section data-type="file" data-src="…">` は 2026-08-31 に廃止——互換で読み続けますが、
  索引はPDFの所在を持ちません（`pdf_path` 列と `ClosestFileSrc` は D-1 で消えました）。
  **ファイルは任意**なので、ファイルの無い記録は業務文書ブロックだけを置けば構いません。
- **金額は `¥8,000` のような表記で書いても、同期時に数値へ正規化されます**（`¥`・桁区切り・全角を吸収）。
  **数量の空セルは 1** として扱います（旧 `<m-material>` の既定を引き継いだ値）。
- **見出しを改名すると③計算に読まれなくなります。** 列の鍵はレジストリ宣言の `Label`（表示文字）から
  機械キー `Field` へ解決されるため、「単価」を「単価（税抜）」に変えるとその列は読まれません。
  ただし**黙っては壊れず**、保存時に `unresolved_fields` で告知されます（拒否はしません）。

> **本書の例は機能見出し形で書いてあります**（D-2・2026-08-31 以降にエディタが挿し、取り込みが生成する形。
> [【考察】語彙モデル.md](【考察】語彙モデル.md) §11・書式は [【一覧】語彙.md](【一覧】語彙.md) §2.3）。
> 見出し語はレジストリの表示名で、`data-type` の値と1対1に対応します（`顧客の発注書`＝`client-order`・
> `自社の発注書`＝`our-order`・`弊社の見積もり`＝`our-estimate`・`材料屋の見積もり`＝`supplier-estimate`）。
> 旧 `data-type` 属性形（`<section data-type="client-order">`＋`<table data-type="client-order-items">`・
> file 容器で包む形）も互換で読めます。

## 3. 見積を記録する（売上予定・原価予定）

見積は明細を持たないフラットな1件なので、要素は `<dl>` です（見出し語が形式を宣言する。下の例の `📎` リンクはただの内容——見積2形式に `File` 宣言は無く、ドロップ域や解析の配線は付かない・§2）。

### 3.1 弊社の見積もり（`our-estimate`）

顧客に対して提示した見積金額＝売上予定。

```html
<section>
    <h2>弊社の見積もり</h2>
    <p>📎 <a href="/000002/m2k3x1.pdf" download="見積書_EST-2026-001.pdf">見積書_EST-2026-001.pdf</a></p>
    <dl>
        <dt>品番</dt><dd>SHAFT-01</dd>
        <dt>顧客</dt><dd>トーア</dd>
        <dt>見積金額</dt><dd>10000</dd>
        <dt>見積日</dt><dd>2026-06-15</dd>
    </dl>
</section>
```

### 3.2 材料屋・加工業者の見積もり（`supplier-estimate`）

外注や材料発注にあたり、業者から受領した見積もり＝原価予定。

```html
<section>
    <h2>材料屋の見積もり</h2>
    <p>📎 <a href="/000002/m2k3x2.pdf" download="材料見積_SUP-EST-501.pdf">材料見積_SUP-EST-501.pdf</a></p>
    <dl>
        <dt>部材名</dt><dd>特殊鋼材</dd>
        <dt>仕入先</dt><dd>東邦金属工業</dd>
        <dt>見積金額</dt><dd>2500</dd>
        <dt>見積日</dt><dd>2026-06-16</dd>
    </dl>
</section>
```

> **見積は保存されるだけで、まだ引き出せません。** 値は②汎用索引に載りますが、
> 読み出す経路（横断比較のビューやAPI）はコードのどこにもありません
> （専用テーブル `our_estimates` / `supplier_estimates` は**読む者が1人もいなかった**ため
> D-1・2026-08-31 で廃止。書き込み専用テーブルだったことが、この空白の裏返しです）。
> 「同じ材料を3社に聞いたうちどこが安かったか」を見比べる機能は要件化済み・未実装です
> （[要件定義書.md](要件定義書.md) §5）。

## 4. 受注を記録する（売上確定）

受注の記録は、顧客から発注書が届いたタイミングで作成されます。

### 4.1 1ページに複数の発注書を記録する

顧客は一度の取引で複数枚の発注書を発行することがあるため、**1つの受注記録ページ（ページIDを持つHTML）の中に、
複数枚の発注書PDF（原本）と、それぞれに紐づく複数の部品（図面）情報**を記録できるようにします。
1つのHTMLファイル内に `<section><h2>顧客の発注書</h2>…</section>` ブロックを自由に並べてください。

### 4.2 明細は発注書にぶら下がる

発注書に記載されている部品は、業務文書ブロックの直下に置く明細表（素の `<table>`。`Items` 宣言により
`client-order-items` の列として解釈される）の各行として記述します。索引はヘッダと明細を
**別々の `data_type`**（`client-order` と `client-order-items`）で載せ、両者は
**`block_no`（形式ごとの文書順連番）で対**になります——1つの `section` がヘッダ1つと
明細表1つを持つ限り、同じ番号どうしが対応します。**発注書番号は突き合わせに使いません**——
ページ内の識別子であって、サイト全体の主キーではない（かつて明細行に親の `order_no` を書き写して
`(page_id, order_no)` を UNIQUE にしていた経緯は [変更履歴.md](変更履歴.md)「硬いドメイン表7つを廃して…」2026-08-31）。

```html
<!-- 顧客発注書1 (発注書番号: PO-A100) -->
<section>
    <h2>顧客の発注書</h2>
    <p data-id="m2k3x1">📎 <a href="/000002/m2k3x1.pdf" download="発注書_PO-A100.pdf">発注書_PO-A100.pdf</a></p>
    <dl>
        <dt>発注書番号</dt><dd>PO-A100</dd>
        <dt>発注元</dt><dd>トーア</dd>
        <dt>発注日</dt><dd>2026-06-18</dd>
    </dl>
    <!-- 部品が発注書番号 PO-A100 にぶら下がる -->
    <table>
        <tbody>
            <tr><th>品番</th><th>品名</th><th>単価</th><th>数量</th><th>状態</th></tr>
            <tr><td>SHAFT-01</td><td>シャフトA</td><td>8000</td><td>10</td><td>未着手</td></tr>
            <tr><td>SHAFT-02</td><td>シャフトB</td><td>12000</td><td>5</td><td>加工中</td></tr>
        </tbody>
    </table>
</section>

<!-- 顧客発注書2 (発注書番号: PO-A200、同じページに記録) -->
<section>
    <h2>顧客の発注書</h2>
    <p data-id="m2k3x3">📎 <a href="/000002/m2k3x3.pdf" download="発注書_PO-A200.pdf">発注書_PO-A200.pdf</a></p>
    <dl>
        <dt>発注書番号</dt><dd>PO-A200</dd>
        <dt>発注元</dt><dd>トーア</dd>
        <dt>発注日</dt><dd>2026-06-18</dd>
    </dl>
    <table>
        <tbody>
            <tr><th>品番</th><th>品名</th><th>単価</th><th>数量</th><th>状態</th></tr>
            <tr><td>GEAR-01</td><td>ギヤA</td><td>15000</td><td>2</td><td>検査中</td></tr>
        </tbody>
    </table>
</section>
```

### 4.3 発注書PDFからのAI明細抽出（実装済み）

受発注ブロック（`File` 宣言の形式。旧 file 容器も互換）へPDFをドロップすると `/api/upload-pdf` が
`files/` へ保存し、ブロック内に `📎` のファイル名リンク（`/<ページID>/<生成ID>.pdf`）を書きます
（旧 file 容器では `data-src` を張り替える）。
「🤖 PDFから明細を解析」ボタン（PDFがあり、ブロック自身または容器の中身が受発注のときだけ出る）で `/api/parse-pdf` が
Gemini にPDFを渡し、抽出された品名・単価・数量が明細表へ行として追加されます
（[pdf_handler.go](../internal/cms/pdf_handler.go)・[app.js](../assets/app.js) の
`uploadPDFToSection` ／ `parsePDFIntoSection`）。動作には `GEMINI_API_KEY` が要ります。
受信箱へ取り込んだ通信記録ページの添付は別経路で、閲覧モードの「🤖 解析」（`/api/analyze-attachment`・
2026-09-01）が発注書かを判定し、発注書なら受注ページを子として生成します
（[【考察】通信記録処理.md](【考察】通信記録処理.md) §4.2）。
列の対応は明細表の見出しからレジストリ経由で解決されるため、**AI応答の鍵と本文の見出しは独立**しています。
抽出結果は検証されないので、内容の確認は人が行う前提です（UIも「内容を確認してください」と告げます）。

## 5. 部材を定義する（BOM）

部品1個あたりに要る部材を、部品のページ側で部材表（`part-materials`。列は 部材名・単価・仕入先・数量）として宣言します。

```html
<dl data-type="tags"><dt>部品番号</dt><dd>SHAFT-01</dd></dl>

<section>
    <h2>部材定義</h2>
    <table>
        <tbody>
            <tr><th>部材名</th><th>単価</th><th>仕入先</th><th>数量</th></tr>
            <tr><td>特殊鋼材</td><td>2500</td><td>東邦金属工業</td><td>1</td></tr>
        </tbody>
    </table>
</section>
```

**部材の行そのものは部品番号を持ちません。** ページ横断メタ `<dl data-type="tags">` の
**「部品番号」タグ**がページ全体の鍵になり、集計は**タグの逆引き**（`pagesByTag`）で
「その部品番号を持つページ」を見つけてから、そのページの部材表を読みます。
鍵の名前はレジストリの `RequiresTag` が持ちます
（[plugin_materials.go](../internal/cms/plugin_materials.go) の `RequiredMaterials`）。
鍵の名前をコードへ直書きせずレジストリから引くのは、見出しを改名したときに
**告知する側と読む側がずれる**のを防ぐためです（かつて同期時に `part_materials.part_id` として
全行へ注入していた経緯は [変更履歴.md](変更履歴.md)「硬いドメイン表7つを廃して…」2026-08-31）。

## 6. 部材手配を集計する（**実装済み**——唯一の計算ビュー）

弊社が発行した注文（材料購入や外注加工＝確定原価）は、顧客発注書と**同じ形**で書きます。
見出し語が「自社の発注書」（`our-order` ／ 明細は `our-order-items`）に変わり、ヘッダの「発注元」が「**発注先**」に、
状態の選択肢は `未納品` / `納品済` の2つになります。

```html
<section>
    <h2>自社の発注書</h2>
    <dl>
        <dt>発注書番号</dt><dd>PO-OUR-001</dd>
        <dt>発注先</dt><dd>東邦金属工業</dd>
        <dt>発注日</dt><dd>2026-06-18</dd>
    </dl>
    <table>
        <tbody>
            <tr><th>品名</th><th>単価</th><th>数量</th><th>状態</th></tr>
            <tr><td>特殊鋼材</td><td>2300</td><td>10</td><td>未納品</td></tr>
        </tbody>
    </table>
</section>
```

受注ページに `<section><h2>手配状況リスト</h2></section>`（旧形 `<section data-type="required-materials">`）を置くと、そのページの受注明細（§4）と
部材定義（§5）と自社発注（本節）から、**必要総数・発注済数・残要手配数**が表になって描かれます。

- 集計は `RequiredMaterials`（[plugin_materials.go](../internal/cms/plugin_materials.go)）——
  受注明細の品番から部材定義（`part-materials`）を引いて `部材の数量 × 受注数量` を積み、
  同ページの発注明細（`our-order-items`）の数量を発注済として差し引きます（残がマイナスなら0に丸めます）。
- 表示は**サーバー事前描画**です（[view_render.go](../internal/cms/view_render.go) の
  `requiredMaterialsViewHTML`）。本文に保存されるのは空のマーカーだけで、中身は返すたびに埋め直され、
  `.vocab-chrome` に包まれるのでシリアライザが保存しません。**閲覧はゼロJS**で完結します。
- 同じ集計関数を `/api/required-materials` も使います（表示とAPIでロジックを二重に持たないため）。
- **権限で絞られます**——部材の**定義元ページを読めない相手には、その定義を集計へ混ぜません**。
  集計対象ページの read だけでは足りないからです。品番は本文へ自由に書けるので、自分のページに
  任意の品番を1行置けば、読めない部品定義ページの部材名・仕入先・原価を引けてしまっていました。

## 7. 進捗を追う

### 7.1 明細の「状態」列（同期は実装済み）

部品ごとの進捗は明細表の `状態` 列（機械キー `status`）で持ちます。値は
`未着手`（初期状態）／`加工中`／`検査中`／`納品済` の4つです
（弊社発注書は `未納品`／`納品済` の2つ）。

選択肢は語彙レジストリ（[vocab.go](../internal/cms/vocab.go) の `client-order-items`）が持ち、
エディタは enum 列としてセルに選択肢メニュー（`#w-enum-menu`）を出します。
**一覧に無い値も拒否せず保存されます**（メニューは入力補助であって検査ではありません。
編集中に赤く印が付く `.cell-invalid` は number / date 列だけなので、enum 列の想定外の値には
印も付きません——[app.js](../assets/app.js) の `validateCell`）。

保存すると明細の「状態」が②汎用索引へ同期されます。**ここまでは実装済み**です。

### 7.2 仮想進捗管理ページでの可視化（**構想・未実装**）

同期された `status` を元に、「仮想的な進捗管理ページ」で進捗状況を俯瞰表示する構想です。

```
【受注進捗管理ボード】
----------------------------------------------------------------------
発注書番号: PO-A100 (顧客: トーア, 受注日: 2026-06-18, ページID: 000002)
 ├─ [未着手] シャフトA (SHAFT-01) × 10個
 └─ [加工中] シャフトB (SHAFT-02) × 5個

発注書番号: PO-A200 (顧客: トーア, 受注日: 2026-06-18, ページID: 000002)
 └─ [検査中] ギヤA (GEAR-01) × 2個
----------------------------------------------------------------------
```

これにより、ユーザーは各図面（部品）のページから進捗を更新するだけで、発注書ベースの進捗ボードが
自動的に最新に保たれ、部品単位でどの発注書に紐づいているかも一目で判別できるようになります。

**この進捗ボードはまだ作られていません。** 実装済みの計算ビューは子ページ一覧（`child-list`）と
部材手配集計（`required-materials`）の2種だけです（[view_render.go](../internal/cms/view_render.go)）。
作るときは §9 の手順に乗ります。

## 8. 原価と利益を出す（**未実装・設計のみ**）

> **本節は「こう算出したい」という設計であって、動く機能の説明ではありません。**
> 本文のパース・索引への同期（`our-estimate`・`supplier-estimate`・`client-order-items`・
> `our-order-items` の抽出）は実装済みですが、**これらを名寄せして利益を出す集計も、
> それを表示するビューも存在しません**（Go 側に粗利を計算するコードは1行もありません）。

データベースは、`item_id`（製品コード／図面番号。無ければ `item_name`）をキーとして、
同一案件・同一部品ごとの売上高と原価高を紐づけて算出**する予定です**。見積と発注が非同期に
（別の日・別のページで）登録されても、この名寄せで1本につながることが狙いです。

### 8.1 売上（収入）の算出
1. **確定売上**: `client_order_items` の `price * quantity` の合計。
2. **予定売上**: 顧客からの発注書がまだない場合、販売見積（`our-estimate`）の見積金額を売上予定
   （数量1と仮定、または見積情報）として参照する。

### 8.2 原価（支出）の算出
1. **確定原価**: `our_order_items` の `cost * quantity` の合計。
2. **予定原価**: 弊社からの発注書がまだない場合、購入見積（`supplier-estimate`）の見積金額を原価予定として参照する。

### 8.3 利益計算

$$利益 (粗利) = 売上 - 原価$$
$$利益率 = \frac{利益}{売上} \times 100\%$$

## 9. 未実装のビューを足すときの手順（§7.2・§8 共通）

進捗ボードも利益ビューも、先行する部材手配集計（§6）と同じ形——**サーバー事前描画**
（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §4.4）——に乗せます。

1. 語彙レジストリ（[vocab.go](../internal/cms/vocab.go)）へ `View: true` の形式を1件足す。
   本文には空のマーカー `<section data-type="…">` だけが保存される。
2. **`viewRenderers`（[view_render.go](../internal/cms/view_render.go)）へ描画関数を1件足す。**
   引き金と早道（`hasViewMarker`）はレジストリの `View: true` 宣言から作られるので名指しのリストは無いが、
   中身を作る関数だけは Go で書いて `viewRenderers` に登録する必要がある。
   **レジストリへ1件足すだけでは中身は出ません。** ただし足し忘れは `missingViewHTML` が
   「この形式の中身を作る処理がまだ用意されていません」と**画面に出す**——かつては `strings.Contains` の
   決め打ちが2箇所あり、ビルドも `go vet` もテストも通ったまま**無言の空白**になった
   （[【考察】設計総点検.md](【考察】設計総点検.md) §3.2 で実測再現済み。その後、振り分けをレジストリ駆動へ改めた）。
   「新しい語彙はレジストリへ宣言1件」という原則の、**唯一の例外**がこれです。
3. 集計SQL自体は計算プラグイン側（[【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md)）へ置き、
   ビューとAPIで同じ関数を共用する。閲覧者（匿名は `nil`）を受け取り、**定義元ページの read で絞る**
   ——§6 と同じ理由で、渡し忘れると非公開ページ由来の情報が公開ページへ出ます。

**新しいカスタム要素は作りません**（当初案の `<m-profit-calculator>` は廃止。理由は
[【考察】語彙モデル.md](【考察】語彙モデル.md) §9 の決定ログ）。サーバー事前描画を選ぶことで、
**閲覧はゼロJS**で完結し、公開ページのSEO要件とも整合します。
