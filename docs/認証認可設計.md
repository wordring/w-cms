# 認証・認可 設計書

w-cms の認証（authN: 本人確認）と認可（authZ: 権限制御）の設計書であり、**現行仕様の正本**です。

> [!NOTE]
> **本設計は実装済みです（2026-06-20 に着手、以降追補）。** 実装は
> [internal/auth/](../internal/auth/)（認証・セッション・ミドルウェア・ユーザー/グループ管理）と
> [internal/cms/page/perms.go](../internal/cms/page/perms.go)（ページ単位の認可）にあります。
> 以下の本文は設計＝現行仕様として読んでください。設計時から変えた点は §0.1 に記録しています。

### 0.1 設計から変えた点（実装時の判断）

| 項目 | 設計 | 実装 | 理由 |
|---|---|---|---|
| CSRF対策 | 二重送信Cookie方式のトークン | **Origin（無ければ Referer）とリクエストホストの一致検証**（`CSRFProtect`・`sameOrigin`） | トークンの発行・埋め込み・更新が不要で、`SameSite=Lax` との併用で同等の防御になる。どちらのヘッダも無い場合は安全側に倒して拒否する |
| ユーザー列挙対策 | （設計に記載なし） | **`decoyHash` を追加**。存在しないユーザーでも argon2id と同じ計算量を消費する | 応答時間の差から利用者名の存在を推測されるのを防ぐ（タイミング攻撃） |
| CSP | （設計に記載なし） | **`CSPProtect` を全レスポンスへ適用**（strict 版＝`'unsafe-inline'` なし） | 多層防御。正本は [本文サニタイズ設計.md §6](本文サニタイズ設計.md) |

実装状況の一覧は §9 を参照してください。

## 0. 前提と方針（確定事項）

| 項目 | 決定 |
|---|---|
| 公開範囲・脅威モデル | **インターネット公開**（強固な認証・HTTPS・レート制限・CSRF対策が必須） |
| 認証方式 | **アプリ単体で管理**（SSO委譲はしない）。資格情報は `cms.db` と分離して保管 |
| パスワードハッシュ | **argon2id**（`golang.org/x/crypto/argon2`） |
| 認可モデル | **Unix風**：ファイル（ページ）単位の read / write を owner・group・other の3クラスで制御。グループ対応。admin=root相当 |
| ページ権限の保管 | **サイドカーファイル方式**（各ページの `<id>.meta.json`） |
| 本番環境 | VPS / 2 CPU / 2GB RAM / Linux（systemd） |

### 開発方針との関係
[開発方針.md](開発方針.md) の「外部依存は事前承認」に基づき、パスワードハッシュ用の **`golang.org/x/crypto`（argon2id）を承認済みの依存**として追加する。セッション・Cookie・CSRF・乱数生成は標準ライブラリ（`crypto/rand`, `crypto/subtle`, `net/http`）で実装し、新たな依存は増やさない。

## 1. データの保管（3層に分離）

| データ | 保管先 | 再生成可否 | バックアップ |
|---|---|---|---|
| **本人確認**: users / groups / group_members / sessions / login_attempts（＋監査ログ audit_log・§9.4） | **`data/auth.db`（独立SQLite）** | ファイルから再生成**不可** | 必須（`data/auth.db` を対象に追加） |
| **ページの所有権・権限**: owner / group / mode | **サイドカー** `data/master/xx/<id>/<id>.meta.json` | （正本そのもの） | `data/master` に含まれる（既存方針のまま） |
| **権限の検索インデックス**: page_perms | `cms.db` の `page_perms` テーブル | サイドカーから**再生成可** | 不要（`cms.db` は使い捨て） |

### 不変条件・バックアップへの影響
- 先に確定した「`cms.db` は `data/master` から再生成可能な使い捨てインデックス」という不変条件（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 8章）は維持される。ページ権限はサイドカー（＝`data/master` 配下のファイル）が正本で、`cms.db.page_perms` はそこから再生成される派生インデックスにすぎない。
- **新たに `data/auth.db` がバックアップ対象に加わる**。これは本人確認情報でファイルから再生成できないため、`data/master` とは別に確実にバックアップする。[【ガイド】デプロイ・運用.md](【ガイド】デプロイ・運用.md) のバックアップ手順を実装時に更新すること。

### 自己認可問題の回避
ページ権限を**ページ本文HTMLの中に書かない**ことが要点。権限はサイドカー（後述のchmod/chown APIだけが書き込む）に置き、本文保存パス（`/api/save`）からは一切書き換えられない。これにより「本文を編集できる人が自分の権限を昇格させる」攻撃を構造的に防ぐ。

## 2. 認証（Authentication）

### 2.1. パスワードハッシュ（argon2id）
- 形式は PHC string（例 `$argon2id$v=19$m=65536,t=3,p=1$<salt>$<hash>`）で `users.password_hash` に保存する。
- 塩は `crypto/rand` で16バイト生成。鍵長32バイト。
- 検証は `crypto/subtle.ConstantTimeCompare` で定数時間比較する。

#### VPS（2 CPU / 2GB RAM）向けの初期パラメータ
| パラメータ | 値 | 備考 |
|---|---|---|
| memory | 64 MiB（65536 KiB） | メモリハード性を確保しつつRAMを圧迫しすぎない値 |
| time（反復回数） | 3 | 実機で1ハッシュ ≈ 0.3〜0.5秒になるよう調整する |
| parallelism | 1 | 予測しやすさ優先。必要なら2（CPU数）まで |
| salt長 / key長 | 16 / 32 バイト | |

> [!NOTE]
> **ログインの同時実行を制限する**。argon2idは1ハッシュあたり64MiBを使うため、`64MiB × 同時ハッシュ数` がピークメモリになる。ログイン処理にセマフォ（例: 同時4件まで）を設け、ピークを約256MiBに抑える。これで2GBのうち約1.7GBをアプリ本体・SQLite・OSに残せる。本番投入前に実機で `time` を較正すること。

### 2.2. セッション管理
- ログイン成功時に `crypto/rand` で256bitのセッショントークンを生成し、`auth.db` の `sessions` に保存（ハッシュ化して保存し、平文はCookieのみ）。
- Cookie属性: `HttpOnly` / `Secure` / `SameSite=Lax`（状態変更APIはCSRF対策を併用、後述）。
  **実装ではCSRFトークンではなく Origin/Referer 検証を採用**（§1 の差分表・`CSRFProtect`）。
  `Secure` はローカルHTTP検証用に `WCMS_SECURE_COOKIES=0` で無効化できる（既定は付与）。
- 有効期限と失効前の告知は **§2.2a が正本**（2026-08-21 決定「最後の操作から8時間」＋事前告知・
  **未実装**。現在の実装は絶対8時間／アイドル30分）。期限切れはサーバ側で無効化。
- ログアウトでセッション行を削除。

### 2.2a. セッションの失効条件【決定 2026-08-21】

> **決定（ユーザー・2026-08-21）**
> 「操作が8時間無ければログアウトにしては？ログアウト数分前に告知するのも良いと思います。」

2026-06-20 に確定した **「絶対8時間／アイドル30分」を上書きする**決定です（旧決定は §9.1 の表に
そのまま残し、上書きされた旨を注記しました）。変わるのは次の2点。

| 項目 | 旧（2026-06-20 決定・**現在の実装**） | 新（2026-08-21 決定・**未実装**） |
|---|---|---|
| 失効条件 | **絶対8時間**（ログイン時刻から。操作しても延びない）**かつ** アイドル30分 | **「最後の操作から8時間」のみ**（操作があるかぎり延びる。絶対期限は無し） |
| 失効前の告知 | 無し | **失効の数分前に画面で告知する**（「数分」の具体値は未定） |

#### 現在の実装（2026-08-21 時点。本決定はまだ反映していない）

- [session.go:14-18](../internal/auth/session.go) が `sessionAbsoluteTTL = 8 * time.Hour` と
  `sessionIdleTTL = 30 * time.Minute` を**コンパイル時の定数**として持つ。
  旧記述（2026-06-20 以来の §2.2・§9.1）が添えていた「（設定可能）」は**実装されていない**
  ——環境変数も設定ファイルも無い。
- [session.go:38](../internal/auth/session.go) がセッション作成時に `expires_at = now + 8時間` を
  書き込み、以後**一度も更新しない**（＝ログインからの絶対期限）。
- [session.go:64](../internal/auth/session.go) の判定は
  `now.After(expiresAt) || now.Sub(lastSeen) > sessionIdleTTL`。直後の
  [session.go:71](../internal/auth/session.go) が毎リクエストで `last_seen` を更新するので、
  **延びるのはアイドル30分の側だけ**。
- **失効前の告知はどこにも無い。** `GET /api/me` が返すのは `authenticated` / `username` /
  `is_admin` / `primary_group` / `groups` だけで（[handlers.go:142-160](../internal/auth/handlers.go)）、
  残り時間をフロントへ渡す口が存在しない。`assets/` 側にも失効を扱うコードは無い。

#### 実装時に必要になること（未着手）

1. **アイドル8時間へ一本化する**。`sessionAbsoluteTTL` による打ち切りをやめ、
   `sessionIdleTTL` を8時間にする（または `expires_at` を操作のたびに前へ延ばす）。
2. **Cookie の寿命も同時に直す。** [middleware.go:33](../internal/auth/middleware.go) の
   `MaxAge` は `sessionAbsoluteTTL`（8時間）で、しかも Cookie を発行するのは
   **ログイン時ただ一度**（[handlers.go:109](../internal/auth/handlers.go) の `setSessionCookie`。
   これが唯一の呼び出し）。サーバー側だけアイドル基準にしても、ブラウザの Cookie が
   ログインから8時間で消えるため、**結局ログインから8時間で切れる**。操作のたびに
   Cookie を再発行して寿命を押し延ばす必要がある。
3. **残り時間をフロントへ渡す**（`GET /api/me` に失効時刻を足す等）。告知は画面の作り込みが要る。
   CSP は strict なのでインラインの `script`/`style` は書けない——スクリプトは `/assets/` 配下の
   外部ファイルへ置くこと（[開発方針.md](開発方針.md) §4）。
4. 「（設定可能）」を実現するのか、定数のままにするのかを決める（上記のとおり現状は未実装）。

#### 含意（このトレードオフを承知の上での決定）

アイドル8時間に延ばすと、**席を離れた端末のログインが従来の30分から8時間まで生き続ける**——
共用端末を開いたまま帰れば、翌朝までそのまま使える状態が残る。その代わり
**長時間の編集がセッション切れで壊される問題（旧 C-5）は解消する**——編集中は操作が続くので
セッションが延び、保存が 401 になって編集ロックまで失う事態が起きなくなる。
「勝手に切れて作業を失う」ほうを重く見た判断であり、失効前の告知はこの見張りを補うもの。

> [!NOTE]
> **参考（旧仕様で何が起きていたか）**: `/api/save` も `/api/lock-events` も `RequireAuth` 配下で
> （[main.go:222](../cmd/w-cms/main.go)）、セッションが切れると保存は 401 になり、SSE も
> いったん切れると再接続できない。編集ロックは SSE の presence で判定するため
> （[lock.go:9-11](../internal/cms/editlock/lock.go)）、presence を失うと待機者が現れた時点で
> `lockGraceDuration`（2分）の猶予後に明け渡される。

> [!NOTE]
> **失効が長くなる分、強制ログアウトの手段の重みが増す。** 利用停止（`disabled`）は
> 次のリクエストで即座に効く（`RequireAuth` が毎回 `LookupUser` を引き、
> [users.go:93-95](../internal/auth/users.go) が無効ユーザーを拒否する）。一方
> **パスワード変更ではセッションが切れない**——`SetPassword` は `users` を更新するだけで
> `sessions` に触れない（[admin.go:37-51](../internal/auth/admin.go)）。旧仕様では「盗まれた
> Cookie も最長8時間で自然に死ぬ」ことが暗黙の歯止めになっていたが、**本決定でその歯止めは
> 無くなる**（操作が続くかぎり無期限）。パスワード変更時のセッション失効は別途詰めること
> （[【考察】設計総点検.md](【考察】設計総点検.md) の指摘4。**未対処**）。

本決定は [要件定義書.md](要件定義書.md) の非機能要件（セッション）にも波及する。

### 2.3. インターネット公開のための必須対策
- **TLS/HTTPS必須**: リバースプロキシ（Caddy/nginx）でTLS終端・自動証明書・レート制限を行う構成を推奨。アプリは `X-Forwarded-Proto` を信頼し（プロキシからのみ）、`Secure` Cookieを発行する。
  （実装では `Secure` 属性は `X-Forwarded-Proto` を見ず **`WCMS_SECURE_COOKIES` だけで決まる**（既定は付与・`secureCookies`）。`X-Forwarded-Proto`/`-Host` を使うのは公開ビューの基底URL `requestBaseURL` だけで、採用は前段がプロキシのとき（`auth.IsFromTrustedProxy`）に限る）
- **CSRF対策**: 状態変更系に対策を要求。`SameSite=Lax` と併用。
  当初案は二重送信Cookie方式のCSRFトークンだったが、**実装は Origin（無ければ Referer）と
  リクエストホストの一致検証**（`CSRFProtect`・`sameOrigin`。どちらのヘッダも無ければ拒否）。
  採用理由は §1 の差分表を参照。
- **総当たり対策**: `login_attempts` に失敗回数・最終失敗時刻を記録し、しきい値超過でロックアウト。
  **実装値は「5回連続失敗で15分」**（`maxFailBeforeLock` / `lockoutDuration`。アカウント単位で、
  IP単位・指数的遅延は未実装）。
- **ユーザー列挙対策**: ログイン失敗時のメッセージ・応答時間を一様にし、ユーザー名の存在有無を漏らさない。
- **セキュリティヘッダ**: `Content-Security-Policy`、`X-Content-Type-Options: nosniff` 等を付与。

### 2.4. エンドポイント（認証）
認証の口は `GET /login`・`POST /api/login`・`POST /api/logout`・`GET /api/me` の4つ。
パス・メソッド・応答の一覧は [【一覧】API.md](【一覧】API.md) §5 が正本（ここでは二重管理しない）。
認可の関門だけ記すと、ログイン画面と `/api/login` は認証不要、`/api/logout` は要認証（POST限定）、
`/api/me` は任意認証（未認証は `{authenticated:false}`）。

### 2.5. 将来の外部認証（SSO/IdP委譲）への拡張余地
v1はアプリ単体のパスワード認証（argon2id）だが、**後から外部委託（会社のSSO/IdP）を追加できる**よう、最初から認証と認可を疎結合に保つ。認可（[3章](#3-認可authorization--unix風パーミッション)）はページの `owner`/`group`/`mode` と「内部ユーザー＝username＋所属グループ」だけに依存し、**どの方式でログインしたかには依存しない**。したがって認証層だけを差し替え・追加すればよい。

#### 追加経路（どちらも本設計の接合点に乗る）
- **リバースプロキシ/フォワード認証**: 前段の oauth2-proxy・Authelia 等で認証し、アプリは信頼ヘッダ（例 `X-Forwarded-User`）を内部ユーザーに対応づける。**最も低コスト**。
- **アプリ内OIDC**: Microsoft Entra・Google 等へコールバックフローで委譲する。実装は多めだが、同じ「身元解決」の接合点に差し込める。

#### 後の移行を不要にするため、v1の時点で入れておく備え（コストはほぼゼロ）
1. **`users.password_hash` を NULL 許容**にする。外部認証のみのユーザー（ローカルパスワードを持たない）を表現できるようにする。
2. **認証を `Authenticator` インターフェースの背後に置く**。v1はローカルパスワード実装1つ。後でSSO/プロキシ実装を足すだけで済むようにし、出口（＝内部ユーザーを確定してセッションを発行する処理）を共通化する。
3. **グループ解決を関数 `GroupsFor(user)` に抽象化**する。v1はローカル `group_members` を読むだけだが、後でIdPクレーム由来のグループをマージできる余地を残す。
4. **外部subject紐付け用テーブルを予約**する。`user_identities(user_id, provider, subject)`（例 `provider='oidc:entra'`, `subject='<sub claim>'`）でIdPアカウントとローカルユーザーを後で結びつけられるようにする（v1では未使用でよい）。
5. **プロキシ由来ヘッダは前段プロキシからのみ信頼**する。送信元IP制限や共有シークレットでヘッダ詐称を防ぐ。フォワード認証を追加する際の必須の注意点。

> [!NOTE]
> 重要なのは「内部ユーザー（username＋グループ）」を認証方式から独立した安定した概念として扱うこと。パスワードハッシュはユーザーに紐づく**認証手段の一つ**にすぎず、外部IdPは**別の認証手段**として同じ内部ユーザーに紐づく、という構図にしておけば、ローカル認証とSSOを併存させることもできる。

## 3. 認可（Authorization） — Unix風パーミッション

### 3.1. モデル
実行(x)は不要なので **read(r) / write(w) の2ビット × owner / group / other の3クラス**とする。

- 1クラスの権限を 0〜3 の数字で表す: `r=2`, `w=1`, `rw=3`, `なし=0`。
- modeは3桁文字列 `"<owner><group><other>"`。
  - 例: `"330"` = owner:rw, group:rw, other:なし
  - 例: `"320"` = owner:rw, group:r, other:なし
  - 例: `"322"` = owner:rw, group:r, other:r
- **admin（root相当）はすべてのチェックをバイパス**する。

### 3.2. 操作と必要権限
| 操作 | 必要権限 |
|---|---|
| ページ閲覧 `GET /{id}`・`GET /api/load` | 対象ページの **read** |
| ページ保存 `POST /api/save` | 対象ページの **write** |
| 子ページ作成 `POST /api/new-page`（GETは405。[【一覧】API.md](【一覧】API.md) §2） | **親ページの write**（Unixの「ディレクトリへの書き込み」に相当） |
| 権限変更（chmod）・所有者変更（chown）・グループ変更（chgrp） | そのページの **owner** または admin |
| 全再構築 `POST /api/rebuild-db`・ユーザー/グループ管理 | **admin** のみ |

### 3.3. 実効権限の判定
あるユーザー u がページ p に対して操作するとき：
1. u が admin → 許可。
2. `p.owner == u` → owner クラスのビットで判定。
3. `p.group ∈ u の所属グループ集合` → group クラスのビットで判定。
4. それ以外 → other クラスのビットで判定。

### 3.4. 新規ページの既定権限（umask相当）
- 作成時: `owner = 作成者`, `group = 作成者の主グループ`, `mode = 既定値`。
- **既定modeは `"330"`**（owner=rw, group=rw, **other=なし**）で確定。設定で変更可能。【確定】
  （「設定で変更可能」は**未実装**——実装は `page.DefaultMode` のコンパイル時定数で、`data/settings.json` にも項目は無い。2026-09-02 確認）
- **other（その他）は既定で「なし」**とする。インターネット公開のため、明示的に共有しない限り無関係な認証済みユーザーには見せない（安全側）。【確定】
- **【§10 の設計どおり実装済み】** 子ページ作成時の既定: `group` は**親ページから継承**（setgid相当・常時オン）、`mode` は親から継承、`owner` は作成者のまま、匿名公開フラグ `public` は**常に false**（フェイルクローズ）。実装は `NewPageAPIHandler`（親の `GetPerms` から `inheritGroup`/`inheritMode` を渡す）＋ `page.EnsureSidecar`。詳細は §10.4。

### 3.5. 管理API（chmod/chown/グループ）
認可の関門だけをここに記す（パス・応答の一覧は [【一覧】API.md](【一覧】API.md) §4・§6 が正本）:

- `POST /api/page-perms`（mode / group / public の変更＝chmod・chgrp・公開切替 §10.3）は **owner または admin**。編集ロックも要る。
- `POST /api/page-chown`（owner の変更＝chown）は **admin**。編集ロックも要る。

## 4. サイドカーファイル仕様（`<id>.meta.json`）

各ページのディレクトリ（`data/master/xx/<id>/`）に、本文 `<id>.html` と並べて権限メタデータを置く。Unixの「inodeメタデータ」に相当する。

```json
{
  "owner": "alice",
  "group": "sales",
  "mode": "330",
  "created_at": "2026-06-20T10:00:00Z",
  "updated_at": "2026-06-20T10:00:00Z"
}
```

- 実装のサイドカー（`page.PageMeta`）は上の例に **`public`**（§10.6）・**`parent_id`**・**`created_by`** を加えた形。親ページIDもここが正本（`pages.parent_id` は派生）。
- **書き込み主体**: chmod/chown/chgrp API と、ページ新規作成処理のみ。**本文保存（`/api/save`）はこのファイルに触れない**（自己認可防止）。
  （実装では本文保存も `updated_at` だけは進める＝`BumpUpdatedAt`。権限フィールドには触れない）
- **欠落時のフォールバック**: サイドカーが無いページ（認証導入前の既存ページなど）は、`owner=admin`・既定mode として扱う。移行時に一括でサイドカーを生成するスクリプトを用意する。

## 5. cms.db の派生インデックス `page_perms`

高速な権限判定のため、サイドカーの内容を `cms.db` にインデックス化する。これは派生データなので、サイドカー（正本）からいつでも再生成できる。

```sql
CREATE TABLE IF NOT EXISTS page_perms (
    page_id INTEGER PRIMARY KEY,
    owner   TEXT,
    grp     TEXT,
    mode    TEXT,
    FOREIGN KEY (page_id) REFERENCES pages(id) ON DELETE CASCADE
);
```

- **同期タイミング**: ページ保存時・chmod等の実行時に、対象ページのサイドカーを読んで `page_perms` をupsertする。
- **全再構築との統合**: `RebuildDatabase` / `SyncIndex` がHTML本文を同期する際、同じページのサイドカーも読んで `page_perms` を再生成する。これは「サイドカー（ファイル）→ cms.db（派生）」なので不変条件を保つ。
- **プラグインにしない理由**: 既存のプラグインは `Sync(tx, pageID, root *html.Node)` でHTML本文を解析する仕組みだが、`page_perms` はHTMLではなくサイドカーJSONを読むため、プラグイン機構ではなく**コアの同期処理に組み込む**（`page_tags` と同じコア扱い）。

> [!IMPORTANT]
> **サイドカーが読めないときに `page_perms` から書き戻して自動修復することはしない**
> （2026-08-21 決定・**実装済み**——`page.requireSidecar` と権限API（`/api/page-perms`・`/api/page-chown`）は
> サイドカーが読めなければ**書かずに止める**（保存は500・権限変更は409）。`page_perms` からサイドカーを
> 書く経路はコード上に無い。2026-09-02 確認）。向きは常に
> 「サイドカー（正本）→ `page_perms`（派生）」の一方向で、逆流させてよいのは集計など
> 必要な場合に限る。決定と根拠は
> [アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §8.4。

## 6. リクエスト処理フロー（ミドルウェア）

実装順の図（`buildHandler`＝`CSPProtect(CSRFProtect(root))`。設計時の図は「認証→CSRF→認可」の順だったが、
実装では **CSRF が認証の外側**にある）:

```
リクエスト
  │
  ├─ CSPProtect …… 全レスポンスへ Content-Security-Policy を付与
  │
  ├─ CSRFProtect …… GET/HEAD/OPTIONS 以外は Origin（無ければ Referer）とホストの一致を要求。全ルート共通の1段
  │
  ├─ ルートごとの認証

  │     （/assets は認証不要）
  │
  └─ 各ハンドラの認可
        page.RequirePageRead / Write / ReadOrPublic / Admin が page_perms(cms.db) を引き §3.3 で判定
        admin はバイパス。認証済み×不可は 403、匿名×非公開は 404（§10.5）
```

#### 上の4件の含意（承知のうえでの決定）

- **見せ分けを使う**ので、手配集計から読めないページ由来の行を落とす絞り込み
  （2026-08-21 の認可越境の修正。判定を `page.CanView` へ集約）は**維持**する。
  代償は「**表の数字が人によって違い、しかもそれが分からない**」状態が続くこと——権限の無い人には、
  材料が何種類か少ない手配表が「これで全部」の顔で表示される。利用者が全員 admin か同一グループの
  あいだは絞り込みが一度も発動しないため、実害が出るのは利益計算に着手してからになる。
  この判断は「**見る権限の無い上位ページの名前が見えている**」件（未対処）にもそのまま効く。
- **匿名の404統一には「ログイン後に元のページへ戻す」が付いてくる**。かつてはログインしても
  必ずトップページへ戻されたため、404 だけを足すと、社員どうしでページのアドレスを共有する
  使い方がかえって不便になる。**2026-08-22 に両方まとめて実装**——404画面が
  `/login?next=...` を持ち、ログインフォームが `next` を運び、成功時にそこへ戻す
  （認証に失敗しても戻り先は保つ）。戻り先の検証は `safeNextPath`。
- **パスワード変更でセッションが切れない**帰結として、**盗まれた Cookie を止める手段は
  「利用停止」（`disabled`）だけ**になる。利用停止は次のリクエストで即座に効く
  （[users.go](../internal/auth/users.go) の `LookupUser` が無効ユーザーを拒否）。
  失効が「最後の操作から8時間」へ延びる（上の1行目）ぶんこの非対称は強まるが、
  **§2.2a の [!NOTE] が「別途詰めること」としていた論点は、本決定で「切らない」に決着**した。
  理由は書き手の側の実害の比較——古いログインが生き続けることより、作業中に突然
  「ログインし直してください」となって書きかけが保存できなくなるほうが困る、という判断。
- **添付の `no-store` を足さない**帰結は、次にやる画像アップロードで**本文の画像にも
  同じ扱いが広がる**こと。前提（共用PCでも個人IDでログインする）が崩れたら再検討する。


### 9.4. 監査ログが記録するもの【2026-08-25 実装】

記録先は `auth.db` の `audit_log`（`ts` / `username` / `action` / `target`）。書き込みは
`auth.Audit()` の1関数だけで、**失敗しても本処理は止めません**（記録が取れないことを理由に
仕事を止めるほうが害が大きい、という判断）。admin は `/api/admin/audit` から新しい順に読めます。

| action | 記録される場面 | `target` |
|---|---|---|
| `login` / `login.fail` / `logout` | 認証イベント（§9.3 の決定） | 接続元アドレス |
| `save` / `save-block` | 本文の保存（全文／1ブロック） | ページID |
| `new-page` | ページの新規作成 | `<新ID> under <親ID>`（テンプレート由来ならその旨も） |
| `attach` / `attach.overwrite` | 添付の保存／**上書き** | `<ページID>/<ファイル名>` |
| `delete-page` | ページの削除（ゴミ箱へ移動） | 移動元→移動先 |
| `revert` | 版の書き戻し（リビジョン） | `<ページID> -> <版ID>` |
| `set-parent` | 親の付け替え | `<ID>-><新親>` |
| `chmod` / `chown` / `chgrp` / `publish` / `unpublish` | 権限の変更（公開切替を含む。1回の `/api/page-perms` で複数指定なら先勝ち＝`chmod` > `chgrp` > `publish`/`unpublish`） | ページIDと新しい値 |
| `lock.force` | 編集ロックの強制解除 | ページID |
| `rebuild-db` | 派生索引の**全再構築** | 取り込み件数と所要時間 |
| `user.*` / `group.*` | ユーザー・グループ管理（`user.create`/`user.password`/`user.enable`/`user.disable`・`group.create`/`group.add`/`group.remove`） | 対象の利用者名／グループ名 |
| `intake.create` / `intake.duplicate` | 受信箱への取り込み（ページ作成／重複検知で作らなかった。2026-09-01・02） | `<新ID> under <受信箱ID>` ／ `<既存ID> (鍵名=値)` |
| `analyze-pdf` | 添付PDFの判定→受注ページ生成（2026-09-01） | `<新ID> from <ページID>/<添付名>`（ZIP内なら `!<中のパス>`） |
| `migrate-headings` / `migrate-attachments` | 一括移行API（2026-08-31 導入・両環境適用後 2026-09-02 撤去。経緯は [変更履歴.md](変更履歴.md)）。過去の記録にだけ残る | 変換・移動の件数 |

**添付だけ `attach` と `attach.overwrite` を分けている**のは、添付にリビジョンもゴミ箱も無く、
上書きすると前の中身が復元できないためです。「増えた」のか「消えた」のかが記録から読めないと、
あとで追いかけようがありません。

**接続元アドレスの決め方**（`clientIP`・`internal/auth/handlers.go`）: 本番はリバースプロキシの
背後で動く（[【ガイド】デプロイ・運用.md](【ガイド】デプロイ・運用.md) §6.2）ので `RemoteAddr` は
常にプロキシ自身になり、そのままでは「誰が事務所の外から入ってきたか」に答えられません。そこで
`X-Forwarded-For` を見ますが、**無条件に信じると記録される接続元を利用者が自由に詐称できる**ため、

- リクエストの `RemoteAddr` がループバック／私設／リンクローカルのとき**だけ**採用する（＝前段にプロキシが居る）、
- 値は**末尾**を採る（直近のプロキシが足した1つ。利用者が先頭へ何を書いても、その後ろに真の接続元が積まれる）

という二段の絞りを掛けています。直結の構成では `RemoteAddr` がそのまま残ります。
規則は [audit_login_test.go](../internal/auth/audit_login_test.go) の `TestClientIPTrustsProxyOnlyFromLocal` が固定します。

**記録しないもの**: 閲覧（read）は記録しません（§9.2 の「閲覧監査ログは必要時」のまま）。
ログイン失敗に**入力されたパスワードは残しません**——記録そのものが漏洩経路になるためです。
なお**帳票の5年保持は監査ログでは満たしません**（[要件定義書.md](要件定義書.md) §3。
実データでは監査記録の90%が編集中の自動保存で、文書の版管理が担うべき役目です）。

## 10. 匿名公開（ログイン不要の閲覧）【実装済み 2026-06-26】

> 本章の設計どおり実装済み。バックエンド（`page_perms.public`・`EffectivePublic`・
> `RequirePageReadOrPublic`・公開API・`OptionalAuth`・子作成の継承）とフロント
> （匿名読み取り専用ビュー・🌐公開トグル・`can_write` による編集スイッチの出し分け）まで反映。

インターネット公開のCMSとして「ログインしなくても閲覧できるページ」を持てるようにする。
現状の認可では未認証リクエストは mode を見る前に 401 になり（`requireUser`）、`other` は
「ログイン済みだが owner/group に属さない第三者」を指すため、**未認証の世界（匿名）を表す席が無い**。
この章で匿名公開を独立した次元として加える。

### 10.1. モデル — mode は3桁のまま、`public` を独立フラグに

- **mode（owner/group/other）は3桁のまま無改造**。`other` の意味も従来どおり「ログイン済みの第三者」。
- ページごとに **`public: bool`（既定 false）** を追加する。匿名は「公開されていれば読める／されていなければ読めない」だけなので、表現したい情報は本質的に1ビット。
- **匿名は read 専用**。匿名の write は仕様で禁止する。
- **4桁mode（anon桁の追加）を採らない理由**: 匿名が read 専用である以上、anon桁は `0`（なし）か `2`（r）しか取らず、`1`（w）・`3`（rw）は「存在しない匿名書き込み」を表してしまい紛らわしい。1ビットのフラグの方が実態に忠実で、mode文字列の移行も不要。【確定】

### 10.2. 実効公開（パスゲート）

- **実効公開 = own.public ∧ 先祖すべての public ∧ root.public**。ルートから対象まで「公開の道」が
  繋がって初めて公開とする（Unixで `/a/b/c` を読むには途中ディレクトリの通り抜け権 x が要るのと同じ考え方）。
- **ルート（`000000`）を鎖に含める**。ルートを非公開にすれば配下すべてが実効非公開になる＝**サイト全体のキルスイッチ**。【確定】
- **フラグは非破壊・可逆**。親を非公開にしても子の `public` フラグは書き換えない。親を再公開すれば、
  自分で公開を望んでいた子だけが自然に復活する（Unixでディレクトリの x を落としても配下ファイルの perm を変えないのと同じ）。
- 親が非公開のページで公開しようとした操作は**ブロック**し、「親が非公開のため公開できません。先に親を
  公開するか、公開可能な親へ移動してください。」と明示する。親を非公開にする操作時は「配下 N ページが
  実効非公開になります」と影響範囲を見せて確認する。

### 10.3. 公開を切り替えられる主体

- **owner または admin**（chmod と同じ権限線）。owner は既に `other` を chmod で操作できるため、`public` も owner が触れるのは一貫している。【確定】

### 10.4. 既定値・子ページ作成時の継承（umask の調整）

§3.4 の umask を次のように調整する（このうち匿名公開に直接関わるのは `public`）。

| 次元 | 子ページ作成時 | 理由 |
|---|---|---|
| `owner` | **作成者**（継承しない） | Unixでも新規ファイルの所有者は作成者であり、親ディレクトリの所有者ではない。 |
| `group` | **親から継承**（setgid相当・常時オン） | 「このセクション配下は同じチームの物」になり、毎回 chgrp する手間が消える。階層型CMSと相性が良い。 |
| `mode` | 親から継承（または既定維持） | 同じ枝で r/w の共有範囲が揃う。固定既定 `330` のままでも実害は小さく、ここは設定で選べる。 |
| `public` | **常に false**（継承しない） | フェイルクローズ。公開は明示的な行為。公開セクションの下で下書きを書くのは普通なので、親が公開でも子を自動公開しない。パスゲートにより「親が非公開なら子は公開不可」は別途保証される。 |

### 10.5. 認可フローへの組み込み

- **read 系**（`GET /{id}`・`GET /api/load`・保護された `/data/master/<id>/...`）で未認証リクエストが来たとき、
  対象ページの**実効公開が true なら read を許可**する。そうでなければ拒否するが、**応答の形は経路で分ける**（実装済み）:
  | 経路 | 未認証×非公開 | 認証済み×read不可 |
  |---|---|---|
  | 画面 `GET /{id}`（`requirePageViewable`） | **404**（不存在と同じ。ただしトップページ `000000` だけは 302 `/login`） | **403** |
  | API `GET /api/load`・`/api/page-meta`・`/api/children`・`/api/zip-list`・`/data/`・添付のきれいなURL `/<ページID>/<ファイル名>`（`RequirePageReadOrPublic`） | **404** | **403** |

  **匿名には「読めない」と「存在しない」を区別させない**（2026-08-16 決定・2026-08-22 実装）。
  かつては画面 302／API 401 で、不存在の 404 と応答が分かれていた。狙いは**列挙対策ではなく**
  ——ユーザーの判断は「（数が数えられるのは）気にしません」「（権限が無いときは）ありませんと
  出るほうが良いです」——**権限の無い書類を開いた社員が迷わないこと**。
  認証済みユーザーへの 403（存在は分かるが読めない）は Unix の作法どおり維持する。

  例外は**トップページ**（`/` の飛び先＝`/000000`）だけで、従来どおり `/login` へ誘導する
  ——ここまで404にすると、サイトを閉じたときに誰も入口へ辿り着けなくなる。

  **404画面はログインへの戻り先つきリンクを持つ**（`/login?next=/000123`）。これが無いと、
  社員どうしでページのアドレスを共有する使い方が「ありません」で行き止まりになる
  ——だから404統一と戻り先の復元は同時に入れた。戻り先は `safeNextPath`
  （[handlers.go](../internal/auth/handlers.go)）が**同一サイト内の絶対パスだけ**に絞る
  （`//host`・`/\host`・スキーム付き・制御文字は "/" へ倒す＝開かれたリダイレクトの遮断）。
  不存在ページも同じ画面を返すので、これで存在が分かることはない。
- **write 系**（`/api/save`・chmod/chown/set-parent 等）は `public` の影響を一切受けず、**常にログイン必須**。公開＝読めるだけ。
- **フロント（実装済み）**: `/api/page-perms` が `can_write` を返し（[perms_admin.go](../internal/cms/perms_admin.go)）、
  フロントの `applyEditToggleVisibility()` が編集トグルを出し分ける。匿名は `body.anonymous` のCSSで
  編集・権限系UIごと隠れる。
- **公開ページのレンダリング**【2026-08-26 実装】: 匿名の要求には**公開専用ビュー**を返す
  （`assets/public.html` ＋ `assets/public.css`。編集用クロームは配信そのものをしない）。
  認証済みには従来どおり編集できる殻（`assets/index.html`）を返す。**分岐は認証済みかどうかの1点だけ**で、
  実効公開の判定は手前の認可（`requirePageViewable`）が済ませている。
  一般公開ウェブサイトの用途は**別サーバー・別ドメインのサイトインスタンス**が担い
  （業務用とデータ・認証は完全独立。[要件定義書.md](要件定義書.md) §1.1）、そこでは匿名アクセスが
  **主要動線**になるため必須の要件だった（同 §4.4）。
- **キャッシュの切り分け**【2026-08-26 実装】: キャッシュ可能にするのは
  **匿名 × 実効公開のページ応答だけ**（`public, max-age=600` ＋ `Vary: Cookie` ＋ `ETag`）。
  次はすべて `no-store` のままである——**この線引きが認可の一部**であり、崩れると共有キャッシュが
  他人の応答を配る:
  | 応答 | 扱い |
  |---|---|
  | 匿名 × 実効公開のページ | `public, max-age=600` ＋ `Vary: Cookie` ＋ `ETag`（`If-None-Match` 一致で304） |
  | 認証済みのページ | `no-store` |
  | 匿名 × 読めないページ（404） | `no-store` |
  | 要認証API（`/api/` の RequireAuth 配下） | `no-store`（**入口で一律**。ハンドラごとに付けるとどれか1本が漏れる） |
  | `/api/me` | `no-store`（OptionalAuth 配下なので入口の一律が掛からない。自前で付ける） |
  | 添付の配信（`/data/`） | 従来どおり指定しない（2026-08-21 ユーザー決定「共用PCでも個人IDでログインする前提」） |

  **公開→非公開の即時反映は原理的に作れない**（いったん配った応答は取り消せない）。許容遅延10分は
  ユーザー決定（[要件定義書.md](要件定義書.md) §4.4）で、値は `publicCacheSeconds` の1箇所。
  サーバー側の状態は即時なので、キャッシュを持たない相手（初回訪問者・クローラ・`sitemap.xml`）には
  非公開化がその場で効く。

### 10.6. サイドカー／派生インデックスへの影響

- サイドカー `<id>.meta.json` に `"public": false` を追加する（欠落時は false 扱い＝フェイルクローズ。既存ページは移行不要）。
- 派生インデックス `page_perms` に `public` カラムを追加（サイドカーから再生成可能な派生データ。§5 と同じ扱い）。
  パスゲートの判定が重ければ、実効公開を `effective_public` として非正規化する余地もある（公開・親付け替え時に更新）。

### 10.7. 認証ユーザー権限との非対称性（明記）

現行の mode（owner/group/other）は**ページ独立で先祖を辿らない**。本章の匿名公開だけが先祖ゲート（§10.2）を
持つため、ここに非対称が生まれる。これは、外向き・高リスクな匿名公開にだけ封じ込め保証を効かせるための
**意図的な設計判断**である（全 read 権限をパス・ゲート化するのは本プロジェクトが選んだフラットな per-page 方針から外れる大改修になるため、匿名公開次元に限定する）。
