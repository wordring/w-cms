# 認証・認可 設計書

w-cms の認証（authN: 本人確認）と認可（authZ: 権限制御）の設計書であり、**現行仕様の正本**です。

> [!NOTE]
> **本設計は実装済みです（2026-06-20 に着手、以降追補）。** 実装は
> [internal/auth/](../internal/auth/)（認証・セッション・ミドルウェア・ユーザー/グループ管理）と
> [internal/cms/perms.go](../internal/cms/perms.go)（ページ単位の認可）にあります。
> 以下の本文は設計＝現行仕様として読んでください。設計時から変えた点は §0.1 に記録しています。

### 0.1 設計から変えた点（実装時の判断）

| 項目 | 設計 | 実装 | 理由 |
|---|---|---|---|
| CSRF対策 | 二重送信Cookie方式のトークン | **Origin（無ければ Referer）とリクエストホストの一致検証**（`CSRFProtect`・`sameOrigin`） | トークンの発行・埋め込み・更新が不要で、`SameSite=Lax` との併用で同等の防御になる。どちらのヘッダも無い場合は安全側に倒して拒否する |
| ユーザー列挙対策 | （設計に記載なし） | **`decoyHash` を追加**。存在しないユーザーでも argon2id と同じ計算量を消費する | 応答時間の差から利用者名の存在を推測されるのを防ぐ（タイミング攻撃） |
| CSP | （設計に記載なし） | **`CSPProtect` を全レスポンスへ適用**（中間版） | 多層防御。正本は [【考察】CSP強化.md](【考察】CSP強化.md) |

実装状況の一覧は §9 を参照してください。

## 0. 前提と方針（確定事項）

| 項目 | 決定 |
|---|---|
| 公開範囲・脅威モデル | **インターネット公開**（強固な認証・HTTPS・レート制限・CSRF対策が必須） |
| 認証方式 | **アプリ単体で管理**（SSO委譲はしない）。資格情報は `cms.db` と分離して保管 |
| パスワードハッシュ | **argon2id**（`golang.org/x/crypto/argon2`） |
| 認可モデル | **Unix風**：ファイル（ページ）単位の read / write を owner・group・other の3クラスで制御。グループ対応。admin=root相当 |
| ページ権限の保管 | **サイドカーファイル方式**（各ページの `<id>.meta.json`） |
| 本番環境 | VPS / 2 CPU / 2GB RAM / Linux（systemd） |

### 開発方針との関係
[開発方針.md](開発方針.md) の「外部依存は事前承認」に基づき、パスワードハッシュ用の **`golang.org/x/crypto`（argon2id）を承認済みの依存**として追加する。セッション・Cookie・CSRF・乱数生成は標準ライブラリ（`crypto/rand`, `crypto/subtle`, `net/http`）で実装し、新たな依存は増やさない。

## 1. データの保管（3層に分離）

| データ | 保管先 | 再生成可否 | バックアップ |
|---|---|---|---|
| **本人確認**: users / groups / group_members / sessions / login_attempts | **`data/auth.db`（独立SQLite）** | ファイルから再生成**不可** | 必須（`data/auth.db` を対象に追加） |
| **ページの所有権・権限**: owner / group / mode | **サイドカー** `data/master/xx/<id>/<id>.meta.json` | （正本そのもの） | `data/master` に含まれる（既存方針のまま） |
| **権限の検索インデックス**: page_perms | `cms.db` の `page_perms` テーブル | サイドカーから**再生成可** | 不要（`cms.db` は使い捨て） |

### 不変条件・バックアップへの影響
- 先に確定した「`cms.db` は `data/master` から再生成可能な使い捨てインデックス」という不変条件（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 8章）は維持される。ページ権限はサイドカー（＝`data/master` 配下のファイル）が正本で、`cms.db.page_perms` はそこから再生成される派生インデックスにすぎない。
- **新たに `data/auth.db` がバックアップ対象に加わる**。これは本人確認情報でファイルから再生成できないため、`data/master` とは別に確実にバックアップする。[【ガイド】デプロイ・運用.md](【ガイド】デプロイ・運用.md) のバックアップ手順を実装時に更新すること。

### 自己認可問題の回避
ページ権限を**ページ本文HTMLの中に書かない**ことが要点。権限はサイドカー（後述のchmod/chown APIだけが書き込む）に置き、本文保存パス（`/api/save`）からは一切書き換えられない。これにより「本文を編集できる人が自分の権限を昇格させる」攻撃を構造的に防ぐ。

## 2. 認証（Authentication）

### 2.1. パスワードハッシュ（argon2id）
- 形式は PHC string（例 `$argon2id$v=19$m=65536,t=3,p=1$<salt>$<hash>`）で `users.password_hash` に保存する。
- 塩は `crypto/rand` で16バイト生成。鍵長32バイト。
- 検証は `crypto/subtle.ConstantTimeCompare` で定数時間比較する。

#### VPS（2 CPU / 2GB RAM）向けの初期パラメータ
| パラメータ | 値 | 備考 |
|---|---|---|
| memory | 64 MiB（65536 KiB） | メモリハード性を確保しつつRAMを圧迫しすぎない値 |
| time（反復回数） | 3 | 実機で1ハッシュ ≈ 0.3〜0.5秒になるよう調整する |
| parallelism | 1 | 予測しやすさ優先。必要なら2（CPU数）まで |
| salt長 / key長 | 16 / 32 バイト | |

> [!NOTE]
> **ログインの同時実行を制限する**。argon2idは1ハッシュあたり64MiBを使うため、`64MiB × 同時ハッシュ数` がピークメモリになる。ログイン処理にセマフォ（例: 同時4件まで）を設け、ピークを約256MiBに抑える。これで2GBのうち約1.7GBをアプリ本体・SQLite・OSに残せる。本番投入前に実機で `time` を較正すること。

### 2.2. セッション管理
- ログイン成功時に `crypto/rand` で256bitのセッショントークンを生成し、`auth.db` の `sessions` に保存（ハッシュ化して保存し、平文はCookieのみ）。
- Cookie属性: `HttpOnly` / `Secure` / `SameSite=Lax`（状態変更APIはCSRFトークン併用、後述）。
- 有効期限は **絶対8時間／アイドル30分**（設定可能）。期限切れはサーバ側で無効化。【確定】
- ログアウトでセッション行を削除。

### 2.3. インターネット公開のための必須対策
- **TLS/HTTPS必須**: リバースプロキシ（Caddy/nginx）でTLS終端・自動証明書・レート制限を行う構成を推奨。アプリは `X-Forwarded-Proto` を信頼し（プロキシからのみ）、`Secure` Cookieを発行する。
- **CSRF対策**: 状態変更系（POST/PUT/DELETE）に二重送信Cookie方式のCSRFトークンを要求。`SameSite=Lax` と併用。
- **総当たり対策**: `login_attempts` に失敗回数・最終失敗時刻を記録し、しきい値超過でアカウント/IP単位にバックオフ（指数的遅延）またはロックアウト。
- **ユーザー列挙対策**: ログイン失敗時のメッセージ・応答時間を一様にし、ユーザー名の存在有無を漏らさない。
- **セキュリティヘッダ**: `Content-Security-Policy`、`X-Content-Type-Options: nosniff` 等を付与。

### 2.4. エンドポイント（認証）
| エンドポイント | 内容 |
|---|---|
| `GET /login` | ログインフォーム |
| `POST /api/login` | 認証・セッション発行 |
| `POST /api/logout` | セッション破棄 |
| `GET /api/me` | 現在のユーザー・所属グループ・権限を返す（フロント表示用） |

### 2.5. 将来の外部認証（SSO/IdP委譲）への拡張余地
v1はアプリ単体のパスワード認証（argon2id）だが、**後から外部委託（会社のSSO/IdP）を追加できる**よう、最初から認証と認可を疎結合に保つ。認可（[3章](#3-認可authorization--unix風パーミッション)）はページの `owner`/`group`/`mode` と「内部ユーザー＝username＋所属グループ」だけに依存し、**どの方式でログインしたかには依存しない**。したがって認証層だけを差し替え・追加すればよい。

#### 追加経路（どちらも本設計の接合点に乗る）
- **リバースプロキシ/フォワード認証**: 前段の oauth2-proxy・Authelia 等で認証し、アプリは信頼ヘッダ（例 `X-Forwarded-User`）を内部ユーザーに対応づける。**最も低コスト**。
- **アプリ内OIDC**: Microsoft Entra・Google 等へコールバックフローで委譲する。実装は多めだが、同じ「身元解決」の接合点に差し込める。

#### 後の移行を不要にするため、v1の時点で入れておく備え（コストはほぼゼロ）
1. **`users.password_hash` を NULL 許容**にする。外部認証のみのユーザー（ローカルパスワードを持たない）を表現できるようにする。
2. **認証を `Authenticator` インターフェースの背後に置く**。v1はローカルパスワード実装1つ。後でSSO/プロキシ実装を足すだけで済むようにし、出口（＝内部ユーザーを確定してセッションを発行する処理）を共通化する。
3. **グループ解決を関数 `GroupsFor(user)` に抽象化**する。v1はローカル `group_members` を読むだけだが、後でIdPクレーム由来のグループをマージできる余地を残す。
4. **外部subject紐付け用テーブルを予約**する。`user_identities(user_id, provider, subject)`（例 `provider='oidc:entra'`, `subject='<sub claim>'`）でIdPアカウントとローカルユーザーを後で結びつけられるようにする（v1では未使用でよい）。
5. **プロキシ由来ヘッダは前段プロキシからのみ信頼**する。送信元IP制限や共有シークレットでヘッダ詐称を防ぐ。フォワード認証を追加する際の必須の注意点。

> [!NOTE]
> 重要なのは「内部ユーザー（username＋グループ）」を認証方式から独立した安定した概念として扱うこと。パスワードハッシュはユーザーに紐づく**認証手段の一つ**にすぎず、外部IdPは**別の認証手段**として同じ内部ユーザーに紐づく、という構図にしておけば、ローカル認証とSSOを併存させることもできる。

## 3. 認可（Authorization） — Unix風パーミッション

### 3.1. モデル
実行(x)は不要なので **read(r) / write(w) の2ビット × owner / group / other の3クラス**とする。

- 1クラスの権限を 0〜3 の数字で表す: `r=2`, `w=1`, `rw=3`, `なし=0`。
- modeは3桁文字列 `"<owner><group><other>"`。
  - 例: `"330"` = owner:rw, group:rw, other:なし
  - 例: `"320"` = owner:rw, group:r, other:なし
  - 例: `"322"` = owner:rw, group:r, other:r
- **admin（root相当）はすべてのチェックをバイパス**する。

### 3.2. 操作と必要権限
| 操作 | 必要権限 |
|---|---|
| ページ閲覧 `GET /{id}`・`GET /api/load` | 対象ページの **read** |
| ページ保存 `POST /api/save` | 対象ページの **write** |
| 子ページ作成 `GET /api/new-page` | **親ページの write**（Unixの「ディレクトリへの書き込み」に相当） |
| 権限変更（chmod）・所有者変更（chown）・グループ変更（chgrp） | そのページの **owner** または admin |
| 全再構築 `POST /api/rebuild-db`・ユーザー/グループ管理 | **admin** のみ |

### 3.3. 実効権限の判定
あるユーザー u がページ p に対して操作するとき：
1. u が admin → 許可。
2. `p.owner == u` → owner クラスのビットで判定。
3. `p.group ∈ u の所属グループ集合` → group クラスのビットで判定。
4. それ以外 → other クラスのビットで判定。

### 3.4. 新規ページの既定権限（umask相当）
- 作成時: `owner = 作成者`, `group = 作成者の主グループ`, `mode = 既定値`。
- **既定modeは `"330"`**（owner=rw, group=rw, **other=なし**）で確定。設定で変更可能。【確定】
- **other（その他）は既定で「なし」**とする。インターネット公開のため、明示的に共有しない限り無関係な認証済みユーザーには見せない（安全側）。【確定】
- **【今後の変更（§10 で設計合意・未実装）】** 子ページ作成時の既定を次のように調整する予定: `group` は**親ページから継承**（setgid相当・常時オン）、`mode` は親から継承（または既定維持）、`owner` は作成者のまま、匿名公開フラグ `public` は**常に false**（フェイルクローズ）。詳細は §10.4。

### 3.5. 管理API（chmod/chown/グループ）
| エンドポイント | 権限 | 内容 |
|---|---|---|
| `POST /api/page-perms?id=<id>` | owner または admin | mode / group の変更（chmod・chgrp） |
| `POST /api/page-chown?id=<id>` | admin | owner の変更（chown） |
| `POST /api/users` ほか | admin | ユーザー作成・無効化・パスワード設定 |
| `POST /api/groups` ほか | admin | グループ作成・メンバー追加削除 |

## 4. サイドカーファイル仕様（`<id>.meta.json`）

各ページのディレクトリ（`data/master/xx/<id>/`）に、本文 `<id>.html` と並べて権限メタデータを置く。Unixの「inodeメタデータ」に相当する。

```json
{
  "owner": "alice",
  "group": "sales",
  "mode": "330",
  "created_at": "2026-06-20T10:00:00Z",
  "updated_at": "2026-06-20T10:00:00Z"
}
```

- **書き込み主体**: chmod/chown/chgrp API と、ページ新規作成処理のみ。**本文保存（`/api/save`）はこのファイルに触れない**（自己認可防止）。
- **欠落時のフォールバック**: サイドカーが無いページ（認証導入前の既存ページなど）は、`owner=admin`・既定mode として扱う。移行時に一括でサイドカーを生成するスクリプトを用意する。

## 5. cms.db の派生インデックス `page_perms`

高速な権限判定のため、サイドカーの内容を `cms.db` にインデックス化する。これは派生データなので、サイドカー（正本）からいつでも再生成できる。

```sql
CREATE TABLE IF NOT EXISTS page_perms (
    page_id INTEGER PRIMARY KEY,
    owner   TEXT,
    grp     TEXT,
    mode    TEXT,
    FOREIGN KEY (page_id) REFERENCES pages(id) ON DELETE CASCADE
);
```

- **同期タイミング**: ページ保存時・chmod等の実行時に、対象ページのサイドカーを読んで `page_perms` をupsertする。
- **全再構築との統合**: `RebuildDatabase` / `SyncIndex` がHTML本文を同期する際、同じページのサイドカーも読んで `page_perms` を再生成する。これは「サイドカー（ファイル）→ cms.db（派生）」なので不変条件を保つ。
- **プラグインにしない理由**: 既存のプラグインは `Sync(tx, pageID, root *html.Node)` でHTML本文を解析する仕組みだが、`page_perms` はHTMLではなくサイドカーJSONを読むため、プラグイン機構ではなく**コアの同期処理に組み込む**（`page_tags` と同じコア扱い）。

## 6. リクエスト処理フロー（ミドルウェア）

```
リクエスト
  │
  ├─ 静的ファイル(/assets, /data) … 認証要否は設定で（/data はPDF等なので原則要認証）
  │
  ├─ 認証ミドルウェア
  │     セッションCookie → sessions(auth.db) → user + 所属グループ を解決
  │     未認証なら /login へ（API は 401）
  │
  ├─ CSRFミドルウェア（状態変更系のみ）
  │
  └─ 認可チェック
        対象ページの page_perms(cms.db) を引き、§3.3 で read/write を判定
        admin はバイパス
        不可なら 403
```

## 7. アーキテクチャへの影響

- **2つ目のDB接続**: `internal/database` に `AuthDB`（`data/auth.db`）を追加する。`cms.db`（`DB`）とは別接続・別ライフサイクル。`RebuildDatabase` は `AuthDB` を一切触らない。
- **新規ファイル構成（案）**:
  - `internal/auth/`（新パッケージ）: パスワードハッシュ（argon2id）・セッション・ユーザー/グループ・ミドルウェア。
  - `internal/cms/perms.go`: サイドカーの読み書きと `page_perms` 同期、実効権限判定。
  - `cmd/w-cms/main.go`: 認証・CSRF・認可ミドルウェアでルートを包む。
- **初期adminのブートストラップ**: 起動時に `users` が空なら、環境変数 `WCMS_ADMIN_USER` / `WCMS_ADMIN_PASSWORD` から最初のadminを作成する（**環境変数方式で確定**。systemd運用と相性がよく画面実装も不要。作成後は環境変数を外す運用）。【確定】

| 監査ログ | フェーズ3で「書き込み・権限変更」のみ記録から開始（閲覧ログは必要時） |
| パスワードリセット | フェーズ3。当面はadminによる再設定で代替 |

### 9.2. 将来拡張（初期スコープ外）
- **MFA**: インターネット公開のため中期的に検討する価値あり。初期スコープ外。
- **外部認証（SSO/IdP委譲）**: 後から追加可能。そのための備えは[2.5節](#25-将来の外部認証ssoidp委譲への拡張余地)に記載済み（v1の時点でスキーマと接合点だけ用意しておく）。
- **閲覧監査ログ・グループ階層化**: 必要が生じた時点で追加。
- **匿名公開（ログイン不要の閲覧）**: 実装済み（2026-06-26）。詳細は §10。

## 10. 匿名公開（ログイン不要の閲覧）【実装済み 2026-06-26】

> 本章の設計どおり実装済み。バックエンド（`page_perms.public`・`EffectivePublic`・
> `RequirePageReadOrPublic`・公開API・`OptionalAuth`・子作成の継承）とフロント
> （匿名読み取り専用ビュー・🌐公開トグル・`can_write` による編集スイッチの出し分け）まで反映。

インターネット公開のCMSとして「ログインしなくても閲覧できるページ」を持てるようにする。
現状の認可では未認証リクエストは mode を見る前に 401 になり（`requireUser`）、`other` は
「ログイン済みだが owner/group に属さない第三者」を指すため、**未認証の世界（匿名）を表す席が無い**。
この章で匿名公開を独立した次元として加える。

### 10.1. モデル — mode は3桁のまま、`public` を独立フラグに

- **mode（owner/group/other）は3桁のまま無改造**。`other` の意味も従来どおり「ログイン済みの第三者」。
- ページごとに **`public: bool`（既定 false）** を追加する。匿名は「公開されていれば読める／されていなければ読めない」だけなので、表現したい情報は本質的に1ビット。
- **匿名は read 専用**。匿名の write は仕様で禁止する。
- **4桁mode（anon桁の追加）を採らない理由**: 匿名が read 専用である以上、anon桁は `0`（なし）か `2`（r）しか取らず、`1`（w）・`3`（rw）は「存在しない匿名書き込み」を表してしまい紛らわしい。1ビットのフラグの方が実態に忠実で、mode文字列の移行も不要。【確定】

### 10.2. 実効公開（パスゲート）

- **実効公開 = own.public ∧ 先祖すべての public ∧ root.public**。ルートから対象まで「公開の道」が
  繋がって初めて公開とする（Unixで `/a/b/c` を読むには途中ディレクトリの通り抜け権 x が要るのと同じ考え方）。
- **ルート（`000000`）を鎖に含める**。ルートを非公開にすれば配下すべてが実効非公開になる＝**サイト全体のキルスイッチ**。【確定】
- **フラグは非破壊・可逆**。親を非公開にしても子の `public` フラグは書き換えない。親を再公開すれば、
  自分で公開を望んでいた子だけが自然に復活する（Unixでディレクトリの x を落としても配下ファイルの perm を変えないのと同じ）。
- 親が非公開のページで公開しようとした操作は**ブロック**し、「親が非公開のため公開できません。先に親を
  公開するか、公開可能な親へ移動してください。」と明示する。親を非公開にする操作時は「配下 N ページが
  実効非公開になります」と影響範囲を見せて確認する。

### 10.3. 公開を切り替えられる主体

- **owner または admin**（chmod と同じ権限線）。owner は既に `other` を chmod で操作できるため、`public` も owner が触れるのは一貫している。【確定】

### 10.4. 既定値・子ページ作成時の継承（umask の調整）

§3.4 の umask を次のように調整する（このうち匿名公開に直接関わるのは `public`）。

| 次元 | 子ページ作成時 | 理由 |
|---|---|---|
| `owner` | **作成者**（継承しない） | Unixでも新規ファイルの所有者は作成者であり、親ディレクトリの所有者ではない。 |
| `group` | **親から継承**（setgid相当・常時オン） | 「このセクション配下は同じチームの物」になり、毎回 chgrp する手間が消える。階層型CMSと相性が良い。 |
| `mode` | 親から継承（または既定維持） | 同じ枝で r/w の共有範囲が揃う。固定既定 `330` のままでも実害は小さく、ここは設定で選べる。 |
| `public` | **常に false**（継承しない） | フェイルクローズ。公開は明示的な行為。公開セクションの下で下書きを書くのは普通なので、親が公開でも子を自動公開しない。パスゲートにより「親が非公開なら子は公開不可」は別途保証される。 |

### 10.5. 認可フローへの組み込み

- **read 系**（`GET /{id}`・`GET /api/load`・保護された `/data/master/<id>/...`）で未認証リクエストが来たとき、
  対象ページの**実効公開が true なら read を許可**する。そうでなければ拒否するが、**応答の形は経路で分ける**（実装済み）:
  | 経路 | 未認証×非公開 | 認証済み×read不可 |
  |---|---|---|
  | 画面 `GET /{id}`（`requirePageViewable`） | **302 `/login`**（ログインへ誘導） | **403** |
  | API `GET /api/load`・`/data/`（`RequirePageReadOrPublic`） | **401** | **403** |

  画面はリダイレクトが自然で、APIはステータスで判断させたいという違い。`RequireAuth` の
  「APIは401・画面は `/login`」という既存の作法に合わせている。
- **write 系**（`/api/save`・chmod/chown/set-parent 等）は `public` の影響を一切受けず、**常にログイン必須**。公開＝読めるだけ。
- **フロント（実装済み）**: `/api/page-perms` が `can_write` を返し（[perms_admin.go](../internal/cms/perms_admin.go)）、
  フロントの `applyEditToggleVisibility()` が編集トグルを出し分ける。匿名は `body.anonymous` のCSSで
  編集・権限系UIごと隠れる。
- **公開ページのレンダリング（現状）**: 専用ビューは設けず、編集用テンプレートのクロームをCSSで隠す方式。
  本文はサーバー合成で埋め込まれ、匿名には**サニタイズ済みの読み取り専用**として届く。
  SEO・OGP・キャッシュまで本格対応するなら軽量な公開専用ビューを別途用意する案がある（未着手）。

### 10.6. サイドカー／派生インデックスへの影響

- サイドカー `<id>.meta.json` に `"public": false` を追加する（欠落時は false 扱い＝フェイルクローズ。既存ページは移行不要）。
- 派生インデックス `page_perms` に `public` カラムを追加（サイドカーから再生成可能な派生データ。§5 と同じ扱い）。
  パスゲートの判定が重ければ、実効公開を `effective_public` として非正規化する余地もある（公開・親付け替え時に更新）。

### 10.7. 認証ユーザー権限との非対称性（明記）

現行の mode（owner/group/other）は**ページ独立で先祖を辿らない**。本章の匿名公開だけが先祖ゲート（§10.2）を
持つため、ここに非対称が生まれる。これは、外向き・高リスクな匿名公開にだけ封じ込め保証を効かせるための
**意図的な設計判断**である（全 read 権限をパス・ゲート化するのは本プロジェクトが選んだフラットな per-page 方針から外れる大改修になるため、匿名公開次元に限定する）。
