## 2. パッケージと依存の向き

`go list -f '{{join .Imports "\n"}}'` の実測。**循環はありません。**

```
cmd/w-cms
  └→ ext/comm/contacts, ext/comm/mail, ext/subcon（ext_*.go のブランク import だけ）
  └→ internal/auth, internal/cms, internal/cms/editlock, internal/cms/page, internal/database

ext/comm/mail               →  internal/auth, internal/cms, internal/cms/page, internal/database
ext/subcon         →  ext/comm/contacts, internal/auth, internal/cms, internal/cms/editlock,
                          internal/cms/page, internal/database
ext/comm/contacts           →  internal/auth, internal/cms, internal/cms/editlock, internal/cms/page,
                          internal/database

internal/cms
  └→ internal/auth, internal/cms/editlock, internal/cms/htmldoc, internal/cms/page, internal/database

internal/cms/editlock  →  internal/auth, internal/cms/page
internal/cms/page      →  internal/auth, internal/database
internal/auth          →  internal/database
internal/cms/htmldoc   →  （w-cms の依存なし）
internal/database      →  （w-cms の依存なし）
```

**守るべき向きが4つ**あります。

- **`cms` は `ext/` を import しない。** 拡張は `init()` で自分をコアの登録表へ
  足すだけで、コアは拡張の存在を知りません（`Register`・`RegisterVocab`・
  `RegisterIntake`・`RegisterView`・`RegisterMailer`・`RegisterMirror`・`RegisterSeeder`・
  **`RegisterContactResolver`**）。**コアが口（interface）を宣言し、
  拡張が実装を差し込み、使う側はコアに尋ねる**——`cms.Mailer` がその形の見本です
  （`mail.go` が口、`ext/comm/mail` が実装、返信の記録はコアの `SendMail` を呼ぶ）。
  取り込むかどうかは `cmd/w-cms/ext_*.go` のビルドタグ（`!minimal` / `!nomail`）が決めます。

- **拡張どうしの import は「使う側が連れてくる」1本だけ**——`ext/subcon → ext/comm/contacts`
  （2026-09-15 に解禁。それまで `ext/` 間の import はゼロ）。整理が取引先ページの器
  （`EnsurePartnerBox`・`PartnerBoxPageID`）と社名の解決（`PartnerTitleForAddress`）を
  借ります（`filing.go` の1ファイル・6箇所）。**`ext/comm/contacts` にビルドタグはありません**
  ——タグを付けると「板金は入れたがアドレス帳は外した」という組み合わせが作れてしまい、
  整理が取引先ページを作れずに黙って壊れるため。`cmd/w-cms/ext_contacts.go` は
  **起動ログに名前を出すためだけ**の1枚で、消しても機能は消えません。
  **逆向き（`ext/comm/contacts → ext/subcon`・`ext/comm/mail`）は無い**——アドレス帳は
  「メールが供給する連絡先」ではなく「業務側が使う同一性」なので、供給側にも
  使う側にも依りません（理由の正本は `go doc ./ext/comm/contacts`）。

- **コアがアドレス帳から受ける3つのフックは、どれも任意**（不変条件）——語彙
  （`RegisterVocab`）・計算ビュー（`RegisterView`）・アドレス→ページの解決
  （`RegisterContactResolver`）。積まなければ素の w-cms がそのまま動き、`email` 型の
  タグは**素のテキストで出るだけ**（`linkEmailDD` は解決係が nil なら何もしない）。
  **重複登録は3つとも `panic`**——2つの解決係が別々の答えを返すと、同じアドレスが
  描くたびに違うページへ飛ぶ、という説明のつかない壊れ方をするためです。

- **`htmldoc` は誰も import しない。** 本文の語彙（許可要素・属性）の唯一の正本で、
  アプリのドメイン（レジストリ・プラグイン）を知りません。**`htmldoc` から `cms` を
  import しないこと。**
- **`editlock` は `cms` を import しない。** 版のチェックポイントを打つために
  「ロックを手放した」という出来事だけが必要なので、関数変数 `editlock.OnRelease` で
  受けます（設定するのは `cms/version.go` の `init`）。これで一方向のままになります。

外部の直接依存は6つ（`go.mod` の実測）: `modernc.org/sqlite`・`golang.org/x/crypto`・
`golang.org/x/net`・`golang.org/x/text`（`intake_eml.go`・`zip_list.go`・`normalize_text.go`・
`ext/subcon/dxf.go` が直接利用）・`github.com/google/generative-ai-go`・`google.golang.org/api`。
[../開発方針.md](../開発方針.md) §1 の一覧と一致しています。

> **メール送受信は外部依存を1つも増やしていません**。受信は IMAP4rev1 を必要な分だけ
> 自前で書き（`net`・`crypto/tls`・`bufio`）、送信は SMTP＋XOAUTH2（`net/smtp`・`mime`・
> `mime/multipart`）——すべて標準ライブラリです。当初「IMAPライブラリを承認する」と
> 決めましたが、**使うコマンドが5つしかない**ので自前で足りました。

派生に関する規律:

- **`cms.db` は使い捨て**。`data/master` から丸ごと作り直せます（`RebuildDatabase`）。
  ファイルから再生成できない値をここへ持たせてはいけません。テーブルは
  `pages`・`page_perms`（コア）＋ `vocab_index`・`page_tags`（どちらも唯一の観察係
  `vocabIndexPlugin` の持ち物）＋ `rebuild_state`（再構築の進行印・
  `dropAllTables` の対象外）の**5つ**だけです。
- **⚠ 認可の読み口は正本ではなく派生**——`page.GetPerms` も `page.EffectivePublic` も
  `cms.db` を読みます。**ずれたら認可は索引に従う**ので、`parent_id` の喪失は
  そのまま公開範囲の問題になります。
- **派生（DB）から正本（サイドカー）へは書き戻さない**（2026-08-21 決定）。
  サイドカーが読めなければ `requireSidecar` がエラーを返し、本文保存・親の付け替え・
  権限変更が**止まります**（運用者が手で直す）。
- **正本を書く経路は `page.WriteFileAtomic`**（一時ファイル＋rename）。本文・サイドカー・
  添付・版・メールのトークンの書き込み**9ファイル・14箇所**がこれを通ります
  （宣言元 `page/storage.go` を除く。`os.WriteFile` の呼び出しは残っていません）。
  **添付の3経路は 2026-09-14 に `attachment_save.go` の1箇所へ畳みました**。
- **重複検知に専用テーブルは無い**——取り込み済みかは、通信記録ページの可変タグ
  `メッセージID` を `page_tags` から逆引き（`PagesByTag`）して決めます。
  **やりとりの前後（`/api/thread`）も同じ逆引き**で、`返信元メッセージID` ⇄ `メッセージID`
  を2回引くだけです（専用テーブルも仕掛けもありません）。
- **`:memory:` DBは接続ごとに別のDB**。行を読みながら中で別のクエリを投げると
  カーソルが接続を握ったままなので**空の別DBに当たり、絞り込みが静かに全部落ちます**
  （2026-09-03 に本番コードで踏んだ）。`view_unhandled.go` と `ref_scope.go` は
  **先に読み切ってから絞る**形にしてあります。

| `login.css` | 21 | ログイン画面・404/403 画面 |

> **読み込み順と実行順**: `index.html` の `boot.js`（11行目）は `<head>` の**同期**スクリプト
> （`defer` なし）なので、`</body>` 直前の `app.js`（274行目）より先に実行されます。
> どちらにも `defer` は付いていません。

## 5. 既知のねじれ・注意点

- **`RequireAdmin` が2つある**——`auth.RequireAdmin`（`admin_handlers.go` から6箇所）と
  `page.RequireAdmin`（`editlock/handler.go`・`handler_meta.go`・`perms_admin.go` から）。
  同名で同じ意味ですが、パッケージが違うだけです。
- **添付の配信口が2つある**——旧形 `/data/master/…`（`page.DataFileHandler`・互換）と
  きれいなURL `/<ページID>/<名前>`（`RootHandler` → `page.ServeCleanAttachment`・`files/` だけを読む）。
  応答ヘッダの規律は `setAttachmentHeaders` を共有。埋め込み（`<img src>`）のサニタイザ許可も
  両方の形（`htmldoc.safeEmbedURL`）。
- **`Sanitize` は薄い委譲**——`cms.Sanitize` は `htmldoc` の `Sanitizer` を呼ぶだけ。
  許可リストを直すときは `htmldoc/sanitize.go` を見ます。
- **プラグインテーブルにマイグレーションが無い**——`ApplySchema` は
  `CREATE TABLE IF NOT EXISTS` を流すだけ。起動時のずれ検出（`DriftedSchemaTables`）＋
  自動再構築が入っているので、**スキーマを変えたら起動時に1度だけ再構築が走ります**。
- **コアテーブルには手書きのマイグレーションがある**——`database/sqlite.go` の
  `coreMigrations`（`ALTER TABLE ... ADD COLUMN`。重複列のエラーは無視）。
- **観察係は1人だけ**（`vocabIndexPlugin`）。拡張の `materialsPlugin`・`mailPlugin`・
  `contactsPlugin` も `Register` を通りますが `Observer` を実装しておらず
  （`Schema`/`Tables` は nil）、`RouteProvider` としてAPIを足すだけです。**業務データの行き先はその観察係が持つ2つの表**
  ——可変タグは `page_tags`、業務ブロックは `vocab_index`（2026-09-13 に分離。**観察係は
  1人のまま**です）。
- **`WalkElements` を回すファイルは7つ**（grep の実測・定義と再帰呼び出しを除く）——
  `anchor.go`・`parser.go`・`plugin.go`（`TagValue`）・`ref_render.go`・`sanitize.go`
  （`ShellPrefixedIDs`）・`shell_public.go`（`ExtractDescription`）・`vocab_notify.go`。
  いずれも索引・計算のための走査ではありません。本文を走査する新しいコードを書いたら、
  たいてい配送係（`walk.go`）を使うべき場面です。
- **dt/dd の対を読む処理は `eachDLPair`（`vocab_index.go`）の1つだけ**——呼び手は6ファイル
  （`file_view.go`・`plugin.go`・`ref_render.go`・`template_new.go`・`vocab_index.go`・
  `vocab_notify.go`。`file_view.go` は 2026-09-14 に加わった）。
  入れ子 `section` へ降りるかは引数 `skipSection` で分かれます。
- **section の素の中身を拾う切り分けは `eachPlainVocabChild` の1つだけ**——索引・種まき・
  改名告知の3者が共有。ここが割れると「索引には載るのに告知されない」ずれが生まれます。
- **`walkState.Ancestors` / `Closest` と `SeedContext.SetText` に使い手がいない**
  （テスト以外の呼び出し0件・2026-09-14 に再確認）。前2つはファイル容器
  （`data-type="file"`）を親から拾う用途で作られ、容器の廃止（2026-08-31）で空きました。
  **3つとも残してあります**——どれも文書が指している公開APIだからです
  （`Ancestors`/`Closest` は [【ガイド】プラグイン開発.md](../【ガイド】プラグイン開発.md) の
  段別コンテキスト、`SetText` は [パーサとプラグイン.md](../パーサとプラグイン.md)）。
  2026-09-14 に**「残す理由」をコード側のコメントへ書きました**——理由の書いていない
  死んだコードは、次の掃除で消されます。
  同じ日に**本当に死んでいた2つは撤去**しました（`IntakeContext.CreatePage` は
  2026-09-05 に `CreateDatedPage` へ取って代わられた／`MirrorContext.ReplaceChildren` は
  「計算ビューのように使う」とコメントしていたが、計算ビューは `fillViewMarker` が自前でやっていた）。
- **`Locks.Validate` を直に呼ぶのは保存の2口だけ**（`SaveAPIHandler`・`SaveBlockAPIHandler`。
  トークンは JSON 本文の `token`）。他の変更操作は `editlock.RequireEditLock`
  （ヘッダ `X-Lock-Token` か `token` クエリ）を通ります。
- **編集ロックを要求しない書き込みがある**——取り込み（`serveIntake`）・🤖 解析
  （`AnalyzeAttachmentAPIHandler`）・メール取り込み（`MailImportAPIHandler`）・
  返信（`MailSendAPIHandler`）。いずれも**人が編集中の本文を奪わない**（子ページを
  作る・別ページへ足す）ので、`RequirePageWrite` だけで通します。
- **既存ページの本文を機械が書き換える口には、別の関門がある**（`editlock.RefuseWhileEditing`・
  2026-09-14）。`RewriteBody` / `SetPageH1` は**読んで・変えて・書く**ので、エディタが
  開いているとオートセーブと上書きし合います。かといって `RequireEditLock` は使えません
  ——これらは**一覧画面のボタン**でエディタを開いておらず、編集トークンを持てないので
  必ず409になります。**自分が開いていても断ります**（手元のエディタは書き換え前の本文を
  持っているので、保存すれば機械の変更が消える）。**保持者が居なくなったロックは無視します**
  （`tick` がロックを消すのは待機者が居るときだけなので、ブラウザを閉じただけの人の
  ロックで機械の書き込みが永久に止まる。判定は明け渡しと同じ `holderPresent`）。
  **断り方は口の流儀に合わせてあります**——連絡先の登録／未分類へ戻す（1ページだけ触る）は
  ハンドラで409、まとめて「対応：不要」は1件ずつ飛ばす、整理の実行は**行ごとに** `skipped`
  （複数のページへ書くので、1枚が編集中でも残りは片付けられるほうがよい）。
  理屈と決定の経緯は [【考察】同時編集の競合対策.md](../【考察】同時編集の競合対策.md) §9。
- **参照の文法を持つ場所は2つ、規則は1つ**——描画（`ref_render.go` の `parseRefValue`）と
  集計スコープ（`ref_scope.go`）。後者が前者を呼びます。**別々に持たせないこと**
  ——「画面ではリンクなのに集計には乗らない」という食い違いが生まれます。
- **正規化の規則も1つに寄せてある**——`cms.NormalizeCode` を拡張の
  `normalizeDrawingNo`（PDFとDXFの突き合わせ）が呼びます。索引の `norm_value` と
  突き合わせが同じ規則で畳まれる、という保証がこれです。
- **`page_tags.norm_value` は宣言型を持たない**（2026-09-15）。SQLite は宣言の無い列で
  値ごとの格納クラスを保つので、number のタグは数として入り `"8000" < "900"` の事故が
  起きません。**代償は「型を取り違えると、エラーにならず0件」**——だから束ねる形は
  `tagNormBind`（`vocab.go`）1か所で、書き手 `insertVocabEntry` と読み手
  `PagesByTagLoose`（→ `tagLookupBind`）が同じ関数を通ります。**この列を述語に使う
  裸の SQL を書かないこと**。`vocab_index.norm_num`（REAL）は別で、読み手が実在するため
  （`vocabRows` の集計）統合は別途です。
- **ページIDを文字列にする所は `page.FormatID` を通す**（2026-09-15）。`%06d` の直書き4箇所と
  `%0*d, IDLength` 15箇所（宣言元 `storage.go` 自身を除く・`279ee62` で実測）が散っていたのを寄せました（いま本体で **15ファイル・21箇所**
  ——`handler_tree.go` の5箇所が最多）。桁を変える日にどちらかを取りこぼすと、
  同じページに2つのIDが生まれます。
