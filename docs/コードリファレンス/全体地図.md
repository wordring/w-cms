# 全体地図

**対象コミット: `ce995b5`（2026-09-16 測り直し）**

`docs/コードリファレンス/` は**実装の現状を写した文書群**です。設計の「なぜ」は各設計書が持ち、
ここは「いま何がどうなっているか」だけを扱います。

> **`go doc` が第一の窓口です。** 各パッケージには冒頭コメントを置いてあるので、
> まずそちらを読んでください——本ファイルはパッケージを**横断する**話（依存の向き・
> 正本性・ねじれ）を担当します。
>
> ```bash
> go doc ./internal/cms          # パッケージの概説＋公開APIの一覧
> go doc ./internal/cms Observer # 特定の型・関数の詳説
> go doc ./ext/comm              # 通信（通信箱・取り込み係・メールの口）
> go doc -all ./internal/cms/page  # そのパッケージの全公開APIをコメントごと
> ```

> ## ⚠ この文書群は一度畳まれています（2026-08-21）
>
> 手書きの「現状の写像」は実装と同じ速度で陳腐化し、**行数主張30件中16件が誤り・

> という理由で全部消しています。2026-08-27 に作り直し、2026-08-30・2026-09-02・

>
> - **説明の本体は `go doc`（＝コードの中）へ置く。** パッケージの冒頭コメントは
>   コードと同じファイルにあるので、実装を変える人の目に入ります。この文書群が担うのは

>   時点の値で、各文書に**数え直すコマンド**を添えてあります。合わないときは
>   コードが正しく、文書が古いのです。
> - **古くなったら直すのではなく作り直す**（スキル `/code-reference`）。
>   直し続けるより安い、というのが 2026-08-21 の判断でした。

## 2. パッケージと依存の向き

`grep -rn '"w-cms/' --include='*.go'` の実測（テストを除く）。**循環はありません。**

```
cmd/w-cms
  └→ ext/comm, ext/comm/contacts, ext/comm/mail, ext/subcon（ext_*.go のブランク import だけ）
  └→ internal/auth, internal/cms, internal/cms/editlock, internal/cms/page, internal/database

ext/subcon         →  ext/comm, ext/comm/contacts,
                      internal/auth, internal/cms, internal/cms/editlock,
                      internal/cms/page, internal/database
ext/comm/contacts  →  ext/comm,
                      internal/auth, internal/cms, internal/cms/editlock,
                      internal/cms/page, internal/database
ext/comm/mail      →  ext/comm,
                      internal/auth, internal/cms, internal/cms/page, internal/database
ext/comm           →  internal/auth, internal/cms, internal/cms/editlock,
                      internal/cms/page, internal/database   ← **ext/ を1つも import しない**

internal/cms
  └→ internal/auth, internal/cms/editlock, internal/cms/htmldoc, internal/cms/page, internal/database

internal/cms/editlock  →  internal/auth, internal/cms/page
internal/cms/page      →  internal/auth, internal/database
internal/auth          →  internal/database
internal/cms/htmldoc   →  （w-cms の依存なし）
internal/database      →  （w-cms の依存なし）
```

**守るべき向きが5つ**あります。

- **`cms` は `ext/` を import しない。** 拡張は `init()` で自分をコアの登録表へ
  足すだけで、コアは拡張の存在を知りません。**コアが宣言する登録の口は9つ**
  （`grep '^func Register' internal/cms` の実測）——`Register`（プラグイン）・
  `RegisterVocab`・`RegisterView`・`RegisterMirror`・`RegisterSeeder`・
  `RegisterContactResolver`・`RegisterUploadInterceptor`・`RegisterSettingsSection`・
  `RegisterExtension`。**コアが口（interface）を宣言し、拡張が実装を差し込み、
  使う側はコアに尋ねる**という形です。取り込むかどうかは `cmd/w-cms/ext_*.go` の
  ビルドタグが決めます（§2a）。

  > ⚠ **`RegisterIntake` と `RegisterMailer` はもうコアにありません**（2026-09-15）。
  > 取り込み係の口は `ext/comm/intake.go`、メールの口は `ext/comm/mail.go` に移りました
  > ——どちらも「通信」という業務の概念だからです。素の w-cms は**通信箱を知りません**。

- **拡張どうしの import は「通信へ向かう」一方通行**（2026-09-15 に解禁。それまでは
  `ext/` 間の import はゼロ）。実測は**7ファイル・8行**（`ext/subcon/filing.go` だけが2本）:

  | import する側 | import 先 | 借りているもの |
  |---|---|---|
  | `ext/subcon/filing.go` | `ext/comm`・`ext/comm/contacts` | `comm.FromTag`（1）と、取引先ページの器・社名の解決（`contacts.*` が6箇所） |
  | `ext/comm/contacts/contacts_unknown.go` | `ext/comm` | タグ名の定数4つ（`差出人`・`宛先`・`CC`・`返信先`） |
  | `ext/comm/mail/{plugin,attach,import,reply,smtp}.go` | `ext/comm` | `Mailer` の口・通信箱・取り込みの芯・タグ名の定数 |

  **`ext/comm` は他の拡張を1つも import しません**——通信は「供給する側」で、
  アドレス帳（同一性）も下請け（業務）も、通信に依るが通信は誰にも依らない、という形です。
  **この向きが逆になったら設計の誤りです**（メールがアドレス帳を名指しし始めると、
  `-tags nomail` でアドレス帳が壊れます）。

- **`ext/comm`・`ext/comm/contacts`・`ext/comm/mail`・`ext/subcon` にビルドタグはありません。**
  タグは**取り付け口の側**（`cmd/w-cms/ext_*.go`）にだけあります。パッケージにタグを付けると
  「下請けは入れたがアドレス帳は外した」という組み合わせが作れてしまい、整理が取引先ページを
  作れずに黙って壊れます。**依存は import で表す**、という規律です。

- **`htmldoc` は誰も import しない。** 本文の語彙（許可要素・属性）の唯一の正本で、
  アプリのドメイン（レジストリ・プラグイン）を知りません。**`htmldoc` から `cms` を
  import しないこと。**

- **`editlock` は `cms` を import しない。** 版のチェックポイントを打つために
  「ロックを手放した」という出来事だけが必要なので、関数変数 `editlock.OnRelease` で
  受けます（設定するのは `cms/version.go` の `init`）。これで一方向のままになります。

外部の直接依存は6つ（`go.mod` の実測・**移設で増減なし**）: `modernc.org/sqlite`・
`golang.org/x/crypto`・`golang.org/x/net`・`golang.org/x/text`（`normalize_text.go`・
`zip_list.go`・`ext/comm/intake_eml.go`・`ext/subcon/dxf.go` が直接利用）・
`github.com/google/generative-ai-go`・`google.golang.org/api`。
[../開発方針.md](../開発方針.md) §1 の一覧と一致しています。

> **メール送受信は外部依存を1つも増やしていません**。受信は IMAP4rev1 を必要な分だけ
> 自前で書き（`net`・`crypto/tls`・`bufio`）、送信は SMTP＋XOAUTH2（`net/smtp`・`mime`・
> `mime/multipart`）——すべて標準ライブラリです。

### 2a. 作れる組は3つ（ビルドタグ）

タグは `cmd/w-cms/ext_*.go` の import 行にあります（`//go:build` の実測）。

| ファイル | タグ | import |
|---|---|---|
| `ext_comm.go` | `!minimal` | `w-cms/ext/comm` |
| `ext_contacts.go` | `!minimal` | `w-cms/ext/comm/contacts` |
| `ext_subcon.go` | `!minimal` | `w-cms/ext/subcon` |
| `ext_mail.go` | `!minimal && !nomail` | `w-cms/ext/comm/mail` |

| 組 | 載る拡張 | 語彙の形式 | 拡張が足すルート |
|---|---|---:|---:|
| 通常（`go build ./cmd/w-cms`） | comm, comm/contacts, comm/mail, subcon | 21 | 15（通信4・アドレス帳2・メール4・下請け5） |
| `-tags nomail` | comm, comm/contacts, subcon | 21 | 11（メールの4本だけ落ちる） |
| `-tags minimal` | なし（素の w-cms） | 5 | 0 |

（実測。コアの語彙は5形式＝`tags`・`file`・`inspection-record`・`child-list`（`vocab.go` の
リテラル4つ）＋ `file-view`（`file_view.go` の `init`）。そこへ `ext/subcon` が14、
`ext/comm` が1（`unhandled-intake`）、`ext/comm/contacts` が1（`unknown-contacts`）を足します。
**メール拡張は語彙を1つも持ちません**——だから `nomail` でも21のままです。）

> **`ext_contacts.go` と `ext_comm.go` は「取り付け口を明示するための1枚」**です。
> `ext/subcon` が `ext/comm/contacts` を、それが `ext/comm` を import しているので、
> **この2枚を消しても何も消えません**——2026-09-15 に名乗りが拡張自身へ移った
> （`cms.RegisterExtension`）ので、起動ログの行すら変わりません。
> 逆に **`ext_subcon.go` を消すと下請けは丸ごと落ちます**（誰も import していない）。

### 2b. 載っている拡張を「知らせる」（2026-09-15）

ビルドタグの付け外しは目に見えません。そこで**拡張が自分で名簿に名乗ります**
（`cms.RegisterExtension(id, name)`・`internal/cms/extensions.go`）。

| ID | 名前 | 名乗る場所 |
|---|---|---|
| `comm` | 通信 | `ext/comm/comm_routes.go` の `init` |
| `comm/contacts` | アドレス帳 | `ext/comm/contacts/plugin.go` の `init` |
| `comm/mail` | メール送受信・IMAP／SMTP | `ext/comm/mail/plugin.go` の `init` |
| `subcon` | 下請け業務 | `ext/subcon/materials.go` の `init` |

名簿の行き先は2つです。

1. **起動ログ**——`main.go` が `cms.Extensions()` を読んで「拡張セット: …」の1行を出します。
2. **画面の出し分け**——`/api/tag-schema` の `extensions`（`cms.ExtensionIDs()`。
   **空でも `[]`**）を `assets/app.js` の `hasExtension(id)` が見ます。

> ⚠ **`hasExtension` は「知らされていなければ true」**です（`loadedExtensions === null`）。
> `/api/tag-schema` の取得に失敗したときは出し分けをせず全部出します——出ないより、
> 押して断られるほうが原因に気づけるためです。
>
> ⚠ **名乗るのは拡張自身で、取り付け口ではありません。** だから import の連鎖で
> 入った拡張（`subcon` が連れてくる `comm/contacts`）も名簿から漏れません。
> **載せ忘れると画面のボタンが消えます。**

## 3. 何が正本か（不変条件）

**この節がこの文書群のいちばんの価値です。** 破ると静かに壊れる約束が並びます。

| 対象 | 正本 | 派生 | 破ったときに起きること |
|---|---|---|---|
| ページの**内容** | `data/master/<先頭2桁>/<id>/<id>.html` | `pages.title`・`vocab_index` | — |
| ページの**属性**（所有者・グループ・mode・公開・親・作成/更新） | サイドカー `<id>.meta.json` | `pages.parent_id` 等・`page_perms` | 派生から正本へ書き戻すと、欠損が派生の内容で埋まって「見た目は健全なのに中身が違う」状態になる |
| **添付** | `<id>/files/<生成ID>.<拡張子>`（2026-08-31 以前の添付はページフォルダ直下に残る） | — | 生成IDは保存名＝URL＝リンクブロックの `data-id` の3役（`GeneratedAttachmentID`。**ブロックIDと同じ4桁の base36**）。参照 `ページID-ID` の飛び先は常に本文のブロックなので、採番をブロックと揃えてある——**一意にすべき範囲は `files/` の中（拡張子を問わず）と本文の data-id の2つ** |
| **本人確認**（利用者・グループ・セッション・監査記録） | `data/auth.db` | — | **ファイルから再生成できない**。`data/master` とは別に必ずバックアップ |
| 本文の**語彙**（許可要素・属性） | `htmldoc` の `structuralElements` | `/api/tag-schema` の応答 | エディタとサーバーで許可がずれ、保存のたびに値が消える |
| **形式**の宣言（`data-type` と機能見出しの意味） | `vocab.go` の `vocabRegistry` ＋ 各拡張の `RegisterVocab` | スラッシュメニュー・挿入骨格・型推論・鏡型/種まきの担当判定 | 表示名（`DisplayName`）を変えると、その言葉を見出しに持つ既存セクションが形式なしになる（告知は出ない） |
| **設定**（見出し語の辞書・添付上限・汎用添付の拡張子・WebDAV の見せ方） | `config/settings.json`（`settings.go`） | `/api/tag-schema` の `vocabulary`・②索引の型解決 | 在るのに読めない・不正なら**起動を止める**——既定値で黙って上書きすると運用者が足した語が消えるため |
| **拡張の設定**（`extensions.<名前>`） | 同じ `config/settings.json`。**読み方と検査は拡張が持つ**（`RegisterSettingsSection`・2026-09-15） | — | 載っていない拡張の節は**止めずに読み飛ばす**（同じファイルを `-tags minimal` でも使うため）。打ち間違えた節名も同じ道へ落ちるので、黙らずログへ出す |
| 版 | `versions/<版ID>.html.gz` ＋ `.json` | — | 対象は本文HTMLだけ。リバートで権限・所有者・親は巻き戻らない |
| **業務データ** | 本文の見える文字（`th`／`dt` の表示文字が鍵） | **索引2つ**——可変タグは `page_tags`、業務ブロックは `vocab_index`（2026-09-13 に分離） | ドメイン表は無い。振り分けは書き手1か所（`insertVocabEntry`）。③計算（部材手配）は `vocab_query.go` 経由で索引を読む。**`page_tags.norm_value` は宣言型を持たない**（number のタグは数の格納クラスで入る）——束ねる形は `tagNormBind` 1か所で、書き手（`insertVocabEntry`）と読み手（`PagesByTagLoose` → `tagLookupBind`）が同じ関数を通る。**割れると number のタグはエラーにならず0件** |
| **ページ間の参照** | 本文の「名前：値」タグ（値は `ページID-ブロックID`） | **`page_tags` の1行**（タグなので） | 参照専用テーブル（`page_refs`）は**無い**・D-4。描画（`ref_render.go`）と集計スコープ（`ref_scope.go`）が**同じ文法**（`parseRefValue`）を使う——別に持つと「画面ではリンクなのに集計に乗らない」食い違いが出る |
| **ファイル表示の配線** | 本文の属性 `section[data-ref]`（定数 `cms.FileRefAttr`） | 描かれる枠（`.vocab-chrome` なので保存されない） | **URLは正本ではありません**——配信のアドレスは一度変わっている（`/data/` → きれいなURL）ので、本文には参照ID（`ページID-添付ID`）を置き、URLはサーバーが組む |
| **メールの資格情報** | `data/mail/<利用者>.json`（リフレッシュトークンだけ） | — | アクセストークンは記憶の中だけ。**ログにも応答にも出さない**。権限は 0600 を指定するが **Windows では効かない**（実測 666）ので、本番機はOSのアクセス制御が実質の守り |

派生に関する規律:

- **`cms.db` は使い捨て**。`data/master` から丸ごと作り直せます（`RebuildDatabase`）。
  ファイルから再生成できない値をここへ持たせてはいけません。テーブルは
  `pages`・`page_perms`（コア）＋ `vocab_index`・`page_tags`（どちらも唯一の観察係
  `vocabIndexPlugin` の持ち物）＋ `rebuild_state`（再構築の進行印・
  `dropAllTables` の対象外）の**5つ**だけです。**拡張は1つもテーブルを持ちません**
  （`Schema()`／`Tables()` がすべて nil）。
- **⚠ 認可の読み口は正本ではなく派生**——`page.GetPerms` も `page.EffectivePublic` も
  `cms.db` を読みます。**ずれたら認可は索引に従う**ので、`parent_id` の喪失は
  そのまま公開範囲の問題になります。
- **派生（DB）から正本（サイドカー）へは書き戻さない**（2026-08-21 決定）。
  サイドカーが読めなければ `requireSidecar` がエラーを返し、本文保存・親の付け替え・
  権限変更が**止まります**（運用者が手で直す）。
- **正本を書く経路は `page.WriteFileAtomic`**（一時ファイル＋rename）。本文・サイドカー・
  添付・版・メールのトークンの書き込み**10ファイル・14箇所**がこれを通ります
  （`os.WriteFile` の呼び出しは本体に残っていません）。
- **重複検知に専用テーブルは無い**——取り込み済みかは、通信記録ページの可変タグ
  `メッセージID` を `page_tags` から逆引き（`cms.PagesByTag`）して決めます。
  **やりとりの前後（`/api/thread`）も同じ逆引き**で、`返信元メッセージID` ⇄ `メッセージID`
  を2回引くだけです（専用テーブルも仕掛けもありません）。
- **`:memory:` DBは接続ごとに別のDB**。行を読みながら中で別のクエリを投げると
  カーソルが接続を握ったままなので**空の別DBに当たり、絞り込みが静かに全部落ちます**
  （2026-09-03 に本番コードで踏んだ）。`ext/comm/view_unhandled.go` と
  `internal/cms/ref_scope.go` は**先に読み切ってから絞る**形にしてあります。

## 5. 既知のねじれ・注意点

- **`RequireAdmin` が2つある**——`auth.RequireAdmin`（`admin_handlers.go` から6箇所）と
  `page.RequireAdmin`（`editlock/handler.go`・`handler_meta.go`・`perms_admin.go` から各1）。
  同名で同じ意味ですが、パッケージが違うだけです。
- ~~**`/api/parse-pdf` はコアに残った業務の口です。**~~ → **2026-09-16 に `ext/subcon` へ
  移しました**（`ext/subcon/parse_pdf.go`・ユーザー判断）。**これでコアのコード
  （コメントを除く）に業務の語は1つもありません**（`発注書`・`見積書`・`受注`・`図面`・
  `取引先`・`仕入先`・`通信箱`・`チャネル` で引いて0件）。移設前は画面のボタンが
  `File: true` を宣言する形式（`ext/subcon` の語彙）が在るときだけ出るため、
  `-tags minimal` では**口は生きているが押す手段が無い**状態でした。
- **添付の配信口が2つある**——旧形 `/data/master/…`（`page.DataFileHandler`・互換）と
  きれいなURL `/<ページID>/<名前>`（`RootHandler` → `page.ServeCleanAttachment`・`files/` だけを読む）。
  応答ヘッダの規律は `setAttachmentHeaders` を共有。
- **⚠ ファイル表示の「開ける形式」は配信側の帰結です。** `fileViewKinds`
  （`.pdf`／`.png`・`.jpg`・`.jpeg`・`.webp`・`.gif`・`.svg`／`.mp4`／`.m4a`・`.mp3`）に
  無い拡張子は `kindOther`＝**開く口（リンク）を出す**だけになります。配信が `inline` で
  返さない形式を「描ける」と宣言しても**ブラウザは描きません**——2026-09-15 に
  `.txt` 等でそれをやりました。**足すときは `page.setAttachmentHeaders` を先に。**
- **`Sanitize` は薄い委譲**——`cms.Sanitize` は `htmldoc` の `Sanitizer` を呼ぶだけ。
  許可リストを直すときは `htmldoc/sanitize.go` を見ます。**`section` に許す `data-*` は
  3つ**（`data-type`・`data-src`・`data-ref`）。
- **プラグインテーブルにマイグレーションが無い**——`ApplySchema` は
  `CREATE TABLE IF NOT EXISTS` を流すだけ。起動時のずれ検出（`DriftedSchemaTables`）＋
  自動再構築が入っているので、**スキーマを変えたら起動時に1度だけ再構築が走ります**。
- **コアテーブルには手書きのマイグレーションがある**——`database/sqlite.go` の
  `coreMigrations`（`ALTER TABLE ... ADD COLUMN`。重複列のエラーは無視）。
- **観察係は1人だけ**（`vocabIndexPlugin`）。`Register` を通るプラグインは
  **既定のビルドで5つ**——コアの `vocabIndexPlugin` と、拡張の `commPlugin`・
  `contactsPlugin`・`mailPlugin`・`materialsPlugin`。後の4つは `Observer` を実装しておらず
  （`Schema`/`Tables` は nil）、`RouteProvider` としてAPIを足すだけです。
- **`WalkElements` を回すファイルは7つ**（grep の実測・定義と再帰呼び出しを除く）——
  `anchor.go`（2）・`parser.go`・`plugin.go`（`TagValue`）・`ref_render.go`・`sanitize.go`
  （`ShellPrefixedIDs`）・`shell_public.go`（`ExtractDescription`）・`vocab_notify.go`（3）。
  いずれも索引・計算のための走査ではありません。本文を走査する新しいコードを書いたら、
  たいてい配送係（`walk.go`）を使うべき場面です。
- **dt/dd の対を読む処理は `eachDLPair`（`vocab_index.go`）の1つだけ**——呼び手は5ファイル
  （`file_view.go` は 2026-09-15 の作り直しで**呼ばなくなりました**。配線が属性へ移り、
  中の参照タグを読まなくなったためです。いまは `plugin.go`・`ref_render.go`・
  `template_new.go`・`vocab_index.go`・`vocab_notify.go`）。
- **section の素の中身を拾う切り分けは `eachPlainVocabChild` の1つだけ**——索引・種まき・
  改名告知の3者が共有。ここが割れると「索引には載るのに告知されない」ずれが生まれます。
- **`walkState.Ancestors` / `Closest` と `SeedContext.SetText` に使い手がいない**
  （テスト以外の呼び出し0件）。**3つとも残してあります**——どれも文書が指している
  公開APIだからです（`Ancestors`/`Closest` は
  [【ガイド】プラグイン開発.md](../【ガイド】プラグイン開発.md) の段別コンテキスト、
  `SetText` は [パーサとプラグイン.md](../パーサとプラグイン.md)）。
  **「残す理由」はコード側のコメントにあります**——理由の書いていない死んだコードは、
  次の掃除で消されます。
- **`Locks.Validate` を直に呼ぶのは保存の2口だけ**（`SaveAPIHandler`・`SaveBlockAPIHandler`。
  トークンは JSON 本文の `token`）。他の変更操作は `editlock.RequireEditLock`
  （ヘッダ `X-Lock-Token` か `token` クエリ）を通ります。
- **編集ロックを要求しない書き込みがある**——取り込み（`ext/comm` の `intakeUpload`）・
  🤖 解析（`AnalyzeAttachmentAPIHandler`）・メール取り込み（`MailImportAPIHandler`）・
  返信（`MailSendAPIHandler`）・手で記録を作る（`NewMemoAPIHandler`）。いずれも
  **人が編集中の本文を奪わない**（子ページを作る・別ページへ足す）ので、
  `RequirePageWrite` だけで通します。
- **既存ページの本文を機械が書き換える口には、別の関門がある**（`editlock.RefuseWhileEditing`）。
  `RewriteBody` / `SetPageH1` は**読んで・変えて・書く**ので、エディタが開いていると
  オートセーブと上書きし合います。かといって `RequireEditLock` は使えません
  ——これらは**一覧画面のボタン**でエディタを開いておらず、編集トークンを持てないので
  必ず409になります。**自分が開いていても断ります**／**保持者が居なくなったロックは
  無視します**。**断り方は口の流儀に合わせてあります**——連絡先の登録／未分類へ戻す
  （1ページだけ触る）はハンドラで409、まとめて「対応：不要」は1件ずつ飛ばす、
  整理の実行は**行ごとに** `skipped`。
  理屈と決定の経緯は [【考察】同時編集の競合対策.md](../【考察】同時編集の競合対策.md) §9。
- **参照の文法を持つ場所は3つ、規則は1つ**——描画（`ref_render.go` の `parseRefValue`）と
  集計スコープ（`ref_scope.go`）とファイル表示（`file_view.go`）。後の2つが前者を呼びます。
  **別々に持たせないこと**——「画面ではリンクなのに集計には乗らない」という食い違いが
  生まれます。
- **正規化の規則も1つに寄せてある**——`cms.NormalizeCode` を拡張の
  `normalizeDrawingNo`（PDFとDXFの突き合わせ）が呼びます。索引の `norm_value` と
  突き合わせが同じ規則で畳まれる、という保証がこれです。
- **`page_tags.norm_value` は宣言型を持たない**。SQLite は宣言の無い列で
  値ごとの格納クラスを保つので、number のタグは数として入り `"8000" < "900"` の事故が
  起きません。**代償は「型を取り違えると、エラーにならず0件」**——だから束ねる形は
  `tagNormBind`（`vocab.go`）1か所で、書き手 `insertVocabEntry` と読み手
  `PagesByTagLoose`（→ `tagLookupBind`）が同じ関数を通ります。**この列を述語に使う
  裸の SQL を書かないこと**。
- **ページIDを文字列にする所は `page.FormatID` を通す**（本体で **15ファイル・21箇所**。
  うち `page/storage.go` の `NormalizeID` が1）。桁を変える日にどちらかを取りこぼすと、
  同じページに2つのIDが生まれます。
