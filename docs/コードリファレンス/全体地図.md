## 2. パッケージと依存の向き

`grep -rn '"w-cms/' --include='*.go'` の実測（テストを除く）。**循環はありません。**

```
cmd/w-cms
  └→ ext/comm, ext/comm/contacts, ext/comm/mail, ext/subcon（ext_*.go のブランク import だけ）
  └→ internal/auth, internal/cms, internal/cms/editlock, internal/cms/page, internal/database

ext/subcon         →  ext/comm, ext/comm/contacts,
                      internal/auth, internal/cms, internal/cms/editlock,
                      internal/cms/htmldoc, internal/cms/page, internal/database
ext/comm/contacts  →  ext/comm,
                      internal/auth, internal/cms, internal/cms/editlock,
                      internal/cms/page, internal/database
ext/comm/mail      →  ext/comm,
                      internal/auth, internal/cms, internal/cms/page, internal/database
ext/comm           →  internal/auth, internal/cms, internal/cms/editlock,
                      internal/cms/page, internal/database   ← **ext/ を1つも import しない**

internal/cms
  └→ internal/auth, internal/cms/editlock, internal/cms/htmldoc, internal/cms/page, internal/database

internal/cms/editlock  →  internal/auth, internal/cms/page
internal/cms/page      →  internal/auth, internal/database
internal/auth          →  internal/database
internal/cms/htmldoc   →  （w-cms の依存なし）
internal/database      →  （w-cms の依存なし）
```

**守るべき向きが5つ**あります。

- **`cms` は `ext/` を import しない。** 拡張は `init()` で自分をコアの登録表へ
  足すだけで、コアは拡張の存在を知りません。**コアが宣言する登録の口は11**
  （`grep '^func Register' internal/cms` の実測）——`Register`（プラグイン）・
  `RegisterVocab`・`RegisterView`・`RegisterMirror`・`RegisterSeeder`・
  `RegisterContactResolver`・`RegisterUploadInterceptor`・`RegisterSettingsSection`・
  `RegisterExtension`・**`RegisterRequiredPage`**（2026-09-16）・
  **`RegisterSuggestSource`**（2026-09-21）。**コアが口（interface）を宣言し、拡張が実装を
  差し込み、使う側はコアに尋ねる**という形です。取り込むかどうかは `cmd/w-cms/ext_*.go` の
  ビルドタグが決めます（§2a）。

  > ⚠ **`RegisterIntake` と `RegisterMailer` はコアにありません**（2026-09-15 に移設）。
  > 取り込み係の口は `ext/comm/intake.go`、メールの口は `ext/comm/mail.go` にあります
  > ——どちらも「通信」という業務の概念だからです。素の w-cms は**通信箱を知りません**。

- **拡張どうしの import は「通信へ向かう」一方通行**（2026-09-15 に解禁）。実測は
  **10ファイル・11行**（前版は7ファイル・8行——下請けが連絡帳を使う口が3つ増えた）:

  | import する側 | import 先 | 借りているもの |
  |---|---|---|
  | `ext/subcon/filing.go` | `ext/comm`・`ext/comm/contacts` | `comm.FromTag`（1箇所）と、`contacts.PartnerTitleForAddress`・`OrgNameForPage`・`PartnerByTitle`・`ContactsRefTag`（`contacts.` が6箇所） |
  | `ext/subcon/analyze_pdf.go` | `ext/comm/contacts` | `contacts.OrgNameForPage`（3箇所。解析が書く `発注元`・`客先` を書く前に揃える） |
  | `ext/subcon/filing_order.go` | `ext/comm/contacts` | `contacts.OrgNameForPage`（1。受注の整理の `発注元` の初期値） |
  | `ext/subcon/unlinked.go` | `ext/comm/contacts` | `contacts.ContactsRefTag`（2。「連絡帳と未接続の相手」の判定） |
  | `ext/comm/contacts/contacts_unknown.go` | `ext/comm` | タグ名の定数4つ（`FromTag`・`ToTag`・`CcTag`・`ReplyToTag`） |
  | `ext/comm/mail/{plugin,attach,import,reply,smtp}.go` | `ext/comm` | `Mailer` の口・通信箱・取り込みの芯 `IntakeFile`・`ErrNoMailBox`・タグ名の定数 |

  **`ext/comm` は他の拡張を1つも import しません**——通信は「供給する側」で、
  アドレス帳（同一性）も下請け（業務）も、通信に依るが通信は誰にも依らない、という形です。
  **この向きが逆になったら設計の誤りです**（メールがアドレス帳を名指しし始めると、
  `-tags nomail` でアドレス帳が壊れます）。

- **`ext/comm`・`ext/comm/contacts`・`ext/comm/mail`・`ext/subcon` にビルドタグはありません。**
  タグは**取り付け口の側**（`cmd/w-cms/ext_*.go`）にだけあります。パッケージにタグを付けると
  「下請けは入れたがアドレス帳は外した」という組み合わせが作れてしまい、整理が連絡帳を
  引けずに黙って壊れます。**依存は import で表す**、という規律です。

- **`htmldoc` は w-cms の何も import しない。** 本文の語彙（許可要素・属性）の唯一の正本で、
  アプリのドメイン（レジストリ・プラグイン）を知りません。**`htmldoc` から `cms` を
  import しないこと。** ⚠ 逆向きに使う側は増えました——`ext/subcon` が
  `htmldoc.ParseFragment`／`Render` を直接呼びます（`link_item.go`・`order_edit.go`・
  `order_pdf.go`。本文を木にして1セルだけ書き換えるため）。向きは崩れていません。

- **`editlock` は `cms` を import しない。** 版のチェックポイントを打つために
  「ロックを手放した」という出来事だけが必要なので、関数変数 `editlock.OnRelease` で
  受けます（設定するのは `cms/version.go` の `init`）。これで一方向のままになります。

外部の直接依存は**7つ**（`go.mod` の実測）: `modernc.org/sqlite`・`golang.org/x/crypto`・
`golang.org/x/net`・`golang.org/x/text`・`github.com/google/generative-ai-go`・
`google.golang.org/api`・**`github.com/signintech/gopdf`**（2026-09-21・発注書のPDF発行。
その依存 `github.com/phpdave11/gofpdi` は indirect）。
[../開発方針.md](../開発方針.md) §1 の一覧と一致しています。

> **メール送受信は外部依存を1つも増やしていません**。受信は IMAP4rev1 を必要な分だけ
> 自前で書き（`net`・`crypto/tls`・`bufio`）、送信は SMTP＋XOAUTH2（`net/smtp`・`mime`・
> `mime/multipart`）——すべて標準ライブラリです。**PDFだけが例外**で、日本語の埋め込みを
> 自前で書く理由が無いと判断しました（経緯は
> [../【考察】発注書のPDF発行.md](../【考察】発注書のPDF発行.md)）。

### 2b. 載っている拡張を「知らせる」（2026-09-15）

ビルドタグの付け外しは目に見えません。そこで**拡張が自分で名簿に名乗ります**
（`cms.RegisterExtension(id, name)`・`internal/cms/extensions.go`）。

| ID | 名前 | 名乗る場所 |
|---|---|---|
| `comm` | 通信 | `ext/comm/comm_routes.go` の `init` |
| `comm/contacts` | アドレス帳 | `ext/comm/contacts/plugin.go` の `init` |
| `comm/mail` | メール送受信・IMAP／SMTP | `ext/comm/mail/plugin.go` の `init` |
| `subcon` | 下請け業務 | `ext/subcon/materials.go` の `init` |

名簿の行き先は2つです。

1. **起動ログ**——`main.go` が `cms.Extensions()` を読んで「拡張セット: …」の1行を出します。
2. **画面の出し分け**——`/api/tag-schema` の `extensions`（`cms.ExtensionIDs()`。
   **空でも `[]`**）を `assets/app.js` の `hasExtension(id)` が見ます。呼び手は
   `hasExtension('comm')` が3・`'subcon'` が3・`'comm/contacts'` が1・`'comm/mail'` が1
   （実測）。

> ⚠ **`hasExtension` は「知らされていなければ true」**です（`loadedExtensions === null`）。
> `/api/tag-schema` の取得に失敗したときは出し分けをせず全部出します——出ないより、
> 押して断られるほうが原因に気づけるためです。
>
> ⚠ **名乗るのは拡張自身で、取り付け口ではありません。** だから import の連鎖で
> 入った拡張（`subcon` が連れてくる `comm/contacts`）も名簿から漏れません。
> **載せ忘れると画面のボタンが消えます。**

### 2c. 置き場は「拡張が名乗り、人が押して作る」（2026-09-16）

トップ直下の**名前で機能が決まるページ**は、`cms.RegisterRequiredPage`
（`internal/cms/required_pages.go`）で拡張が名乗り、**管理画面（`/assets/admin.html`）の
「置き場」ボタン**（`GET/POST /api/admin/pages`・admin 限定）で足りないものだけを作ります。
**起動時には作りません**——人が押したことが、そのページを置く意図です。

| 題 | 持ち主 | 名乗る場所 | 初期本文（作業面） |
|---|---|---|---|
| `テンプレート` | コア | `internal/cms/template.go` の `init` | 見出しだけ |
| `通信箱` | `comm` | `ext/comm/intake.go` の `init` | `unhandled-intake`（未処理の受信） |
| `連絡帳` | `comm/contacts` | `ext/comm/contacts/contacts.go` の `init` | `unknown-contacts`（未登録の連絡先） |
| `取引先` | `subcon` | `ext/subcon/materials.go` の `init` | `unlinked-customers`（連絡帳と未接続の相手） |
| `受注` | `subcon` | 同上 | 見出しだけ（⚠ 受注残表 `order-backlog` は人が貼る） |
| `発注` | `subcon` | 同上 | 見出しだけ |

**同じ題は登録できません**（`panic`）。そして **2026-09-21 から、トップ直下に同じ題の
置き場を2枚作ることは保存の時点で 409 になります**（`handler_save.go` の
`refuseDuplicateBoxTitle`——題が名簿に在るときだけ効く。深いところの同題は止めない）。

### 2d. 入力の候補は「名前で引く」（2026-09-21）

列の宣言に `Suggest: "<出どころの名前>"` と書くと（`VocabColumn.Suggest`）、エディタが
`GET /api/suggest?source=…&q=…`（認証必須・上限30件）で候補を引きます。出どころは
拡張が `cms.RegisterSuggestSource(name, fn)`（`internal/cms/suggest.go`）で持ち込み、
**コアは名前しか知りません**。いま登録されているのは `subcon.partners`
（`ext/subcon/suggest_partner.go`・`取引先` 直下の社名ページの題）の1つで、
`外注加工` の `推奨業者` と未手配の一覧の `仕入先` が使います。**知らない出どころは
404 ではなく空**——拡張を外したビルドでは候補が出ないだけ、が正しい振る舞いです。

派生に関する規律:

- **`cms.db` は使い捨て**。`data/master` から丸ごと作り直せます（`RebuildDatabase`）。
  ファイルから再生成できない値をここへ持たせてはいけません。テーブルは
  `pages`・`page_perms`（コア）＋ `vocab_index`・`page_tags`（観察係 `vocabIndexPlugin`）＋
  **`material_dimensions`（観察係 `dimensionPlugin`・`ext/subcon`）**＋ `rebuild_state`
  （再構築の進行印・`dropAllTables` の対象外）の**6つ**です。
  ⚠ **「拡張は1つもテーブルを持たない」は 2026-09-21 で終わりました**——`Register` を通る
  6つのプラグインのうち `dimensionPlugin` だけが `Tables()`／`Schema()` を持ちます
  （`vocab_index` の `block_no` とは揃えず、材質・形状・寸法を自分の表に持つ）。
- **⚠ 認可の読み口は正本ではなく派生**——`page.GetPerms` も `page.EffectivePublic` も
  `cms.db` を読みます。**ずれたら認可は索引に従う**ので、`parent_id` の喪失は
  そのまま公開範囲の問題になります。
- **派生（DB）から正本（サイドカー）へは書き戻さない**（2026-08-21 決定）。
  サイドカーが読めなければ `requireSidecar` がエラーを返し、本文保存・親の付け替え・
  権限変更が**止まります**（運用者が手で直す）。サイドカーの一部更新は `touchSidecar`
  1か所（`BumpUpdatedAt`・`SetSidecarParent`）。
- **正本を書く経路は `page.WriteFileAtomic`**（一時ファイル＋rename）。本文・サイドカー・
  添付・目録・版・メールのトークンの書き込み**10ファイル・12箇所**（＋`page/perms.go` 内に1）
  がこれを通ります（`os.WriteFile` の呼び出しは本体に残っていません）。
- **重複検知に専用テーブルは無い**——取り込み済みかは、通信記録ページの可変タグ
  `メッセージID` を `page_tags` から逆引き（`cms.PagesByTag`）して決めます。
  **やりとりの前後（`/api/thread`）も同じ逆引き**で、`返信元メッセージID` ⇄ `メッセージID`
  を2回引くだけです。**解析済みの印も、弊社品番の結びも同じ流儀**——状態を別に持たず、
  本文のタグ（`受信元`・`弊社品番`）から逆に引きます。
- **`:memory:` DBは接続ごとに別のDB**。行を読みながら中で別のクエリを投げると
  カーソルが接続を握ったままなので**空の別DBに当たり、絞り込みが静かに全部落ちます**
  （2026-09-03 に本番コードで踏んだ）。**読み切ってから返す口をコアに寄せました**
  （2026-09-21）——`cms.TagRowsNamed`・`cms.ChildPages`・`cms.VocabRowsOfType`・
  `cms.TagsOfPage`。行を読みながら `page.CanView` を呼ぶ形を**新しく書かないこと**。
- **⚠ 表示専用クローム（`.vocab-chrome`）は本文へ入る手前で落とします**
  （`cms.StripChrome`・`Sanitize`／`SanitizeReport` の冒頭・2026-09-21）。`/api/load` は
  鏡を埋めて返すので、外から `/api/save` へ書き戻すと鏡が焼き付きます——実際に6枚で起きました。
  **順序がこの守りの全部**（サニタイズは `class` を落とすので、後では印が無い）。
  入口ごとには置いていません（保存の口は `/api/save`・`/api/save-block`・`RewriteBody`・
  `CreateChildPage`・`IntakeContext.UpdatePage` の5つ）。

## 5. 既知のねじれ・注意点

- **`RequireAdmin` が2つある**——ただし **`page.RequireAdmin` は `auth.RequireAdmin` への
  委譲になりました**（2026-09-21）。呼び手は `auth.` 側が `admin_handlers.go` の6箇所
  （同一パッケージ）、`page.` 側が `editlock/handler.go`・`handler_meta.go`・
  `handler_required_pages.go`・`handler_reset_data.go`・`perms_admin.go` の5箇所。
  同名で同じ意味、実体は1つです。
- **観察係は2人になりました**（2026-09-21）。`vocabIndexPlugin`（引き金 `*`・コア）と
  **`dimensionPlugin`**（引き金 `part-materials`・`our-order-items`・`ext/subcon`）。
  `Register` を通るプラグインは**既定のビルドで6つ**——コアの `vocabIndexPlugin` と、拡張の
  `commPlugin`・`contactsPlugin`・`mailPlugin`・`materialsPlugin`・`dimensionPlugin`。
  **`dimensionPlugin` だけが `Tables()`／`Schema()` を持ちます**（`material_dimensions`）。
  だから **`descend` を OR で畳む**（`walk_equiv_test.go` の
  `TestObserversSeeNestedItemsTable`）ことが、いま初めて実際に効いています——
  `dimensionPlugin` は表を届けられたら降りない（false）が、`vocabIndexPlugin` は降りる。
- **拡張の表は `vocab_index` と揃えていません。** `material_dimensions.block_no` は
  自分で数えた連番（`ctx.Counter(dimensionTable+":"+dataType)`）で、コアの `block_no` と
  **一致しません**。結合しない前提で、材質・形状・寸法を自分の表に持っています。
- **`/api/parse-pdf` はコアに無い**（2026-09-16 に `ext/subcon/parse_pdf.go` へ）。**コアの
  コード（コメントを除く）に業務の語は1つもありません**——業務語はすべて `ext/` の定数
  （`analyzed.go`・`filing_order.go`・`customer_box.go`・`contacts.go`・`intake.go`）。
- **添付の配信口が2つある**——旧形 `/data/master/…`（`page.DataFileHandler`・互換）と
  きれいなURL `/<ページID>/<名前>`（`RootHandler` → `page.ServeCleanAttachment`・`files/` だけ）。
  応答ヘッダの規律は `setAttachmentHeaders` を共有。**どちらも `.json` は配らない**
  （サイドカーと目録）。
- **⚠ ファイル表示の「開ける形式」は配信側の帰結です。** `fileViewKinds`
  （`.pdf`／`.png`・`.jpg`・`.jpeg`・`.webp`・`.gif`・`.svg`／`.mp4`／`.m4a`・`.mp3`）に
  無い拡張子は `kindOther`＝**開く口（リンク）を出す**だけになります。配信が `inline` で
  返さない形式を「描ける」と宣言しても**ブラウザは描きません**。**足すときは
  `page.setAttachmentHeaders` を先に。**
- **`Sanitize` は薄い委譲＋クローム落とし**——`cms.Sanitize` は `StripChrome` を通してから
  `htmldoc` の `Sanitizer` を呼びます。許可リストを直すときは `htmldoc/sanitize.go` を見ます。
  **`section` に許す `data-*` は3つ**（`data-type`・`data-src`・`data-ref`）。
- **プラグインテーブルにマイグレーションが無い**——`ApplySchema` は
  `CREATE TABLE IF NOT EXISTS` を流すだけ。起動時のずれ検出（`DriftedSchemaTables`）＋
  自動再構築が入っているので、**スキーマを変えたら起動時に1度だけ再構築が走ります**。
  `material_dimensions` が足された環境でも同じ道で入ります。
- **コアテーブルには手書きのマイグレーションがある**——`database/sqlite.go` の
  `coreMigrations`（`ALTER TABLE ... ADD COLUMN`。重複列のエラーは無視）。
- **`WalkElements` を回すファイルは7つ・10箇所**（grep の実測・定義と再帰呼び出しを除く）——
  `anchor.go`（2）・`parser.go`・`plugin.go`（`TagValue`）・`ref_render.go`・`sanitize.go`
  （`ShellPrefixedIDs`）・`shell_public.go`（`ExtractDescription`）・`vocab_notify.go`（3）。
  いずれも索引・計算のための走査ではありません。本文を走査する新しいコードを書いたら、
  たいてい配送係（`walk.go`）を使うべき場面です。⚠ **`ext/subcon` は自前の走査を持ちます**
  （`rowsOf`・`tablesOfType`・`eachSection`）——本文を木や文字列として1か所だけ書き換える
  ためで、索引の走査ではありません。
- **dt/dd の対を読む処理は `eachDLPair`（`vocab_index.go`）の1つだけ**——呼び手は5ファイル
  （`plugin.go`・`ref_render.go`・`template_new.go`・`vocab_index.go`・`vocab_notify.go`）。
- **section の素の中身を拾う切り分けは `eachPlainVocabTable` の1つだけ**（前版の
  `eachPlainVocabChild` から改名——**素の `dl` はもう拾わない**）——索引・種まき・
  改名告知の3者が共有。ここが割れると「索引には載るのに告知されない」ずれが生まれます。
- **`walkState.Ancestors` / `Closest` と `SeedContext.SetText` に使い手がいない**
  （テスト以外の呼び出し0件・前版から変わらず）。**3つとも残してあります**——どれも文書が
  指している公開APIだからです（`Ancestors`/`Closest` は
  [【ガイド】プラグイン開発.md](../【ガイド】プラグイン開発.md) の段別コンテキスト、
  `SetText` は [パーサとプラグイン.md](../パーサとプラグイン.md)）。
- **呼び手ゼロの公開関数がほかに2つ**（この版で実測）——`cms.EnsureChildByTitle`
  （`page_lookup.go`・2026-09-21 に寄せたが誰も呼ばない。連絡帳は自前の
  `ensureChildByTitle`、整理は `ensureChildPage` を持つ）と `cms.VocabBlocksOf`
  （`vocab_query.go`・ヘッダだけの形式を廃した 2026-09-18 から読む相手が無い）。
  **どちらもコード側に「残す理由」の注記はありません**——消すか使うかはユーザーの判断。
- **`Locks.Validate` を直に呼ぶのは `editlock/handler.go` の `RequireLockToken` だけ**
  （2026-09-21 に寄せた）。保存の2口（`SaveAPIHandler`・`SaveBlockAPIHandler`）は
  `gateSave` → `RequireLockToken`（トークンは JSON 本文の `token`）、他の変更操作は
  `RequireEditLock`（ヘッダ `X-Lock-Token` か `token` クエリ）→ `RequireLockToken` を通ります。
- **編集ロックを要求しない書き込みがある**——取り込み（`ext/comm` の `intakeUpload`）・
  🤖 解析（`AnalyzeAttachmentAPIHandler`）・メール取り込み・返信・手で記録を作る・
  **発注書を作る**（`NewOurOrderAPIHandler`）・**PDF発行**（`OrderPDFAPIHandler`・添付を足すだけ）・
  **整理の実行**（`FileDrawingsAPIHandler`）。いずれも**人が編集中の本文を奪わない**
  （子ページを作る・別ページへ足す）ので `RequirePageWrite` だけで通します。
- **既存ページの本文を機械が書き換える口には、別の関門がある**（`editlock.RefuseWhileEditing`
  ＝呼び手は `contacts_handler.go`（3）・`order_edit.go`、または行ごとの
  `editlock.Locks.EditorOpen`＝呼び手は `handler_handled.go`・`filing.go`（2）・
  `filing_order.go`・`link_item.go`）。`RewriteBody` は**読んで・変えて・書く**ので、エディタが
  開いているとオートセーブと上書きし合います。**自分が開いていても断ります**／
  **保持者が居なくなったロックは無視します**。理屈は
  [【考察】同時編集の競合対策.md](../【考察】同時編集の競合対策.md) §9。
- **⚠ 計算ビューで初めての「書ける鏡」**——受注残表（`backlog.go`）の `<select>`／`<input>`
  は `/api/order-item`（`order_edit.go`）で**別のページ（受注ページ）の本文**を書き換えます。
  歯止めは4つ（行番号＋`品番` の照合・compare-and-swap・`RefuseWhileEditing`・書ける列の宣言）。
  鏡が本文を書く口はこれ1つです——増やすときは同じ4つを通すこと。
- **手配の集計が2本ある**——古い `RequiredMaterials`（`/api/required-materials`・材料名で
  受注ページ全体を合算・`RelatedPages` のスコープ）と、新しい `ProcurementByProduct`
  （`required-materials` ビューの描画・加工製品ごと・全社の発注明細を `弊社品番` で束ねる）。
  古いほうは API を叩く相手（E2E）が居るので残っています。**画面が出すのは新しいほう**。
- **参照の文法を持つ場所は3つ、規則は1つ**——描画（`ref_render.go` の `parseRefValue`。
  タグと表の両方）と集計スコープ（`ref_scope.go`）とファイル表示（`file_view.go`）。
  後の2つが前者を呼びます。**別々に持たせないこと**。
- **社名を機械が書く口は4つ、揃える口は1つ**——`contacts.OrgNameForPage`。解析の `発注元`・
  `客先`／受注の整理／加工製品の整理／連絡帳の初期値。1つでも生の名前を書くと
  `株式会社○○` のページが生まれ、**完全一致で結ぶ2つの木が黙って結ばれません**
  （`linkPartner` → `PartnerByTitle`）。
- **改訂履歴の表を文字列で探す口は2つ、実体は1つ**——`InsertRevisionRow` と `linkRevisionRow`
  はどちらも `revisionTableAt`（属性でも caption でも探す）を通ります。⚠ **`InsertRevisionRow` は
  `analyze_pdf.go` に居て、呼び手は `revision.go` だけ**——置き場と呼び手が別ファイルです。
- **`page_tags.norm_value` は宣言型を持たない**。SQLite は宣言の無い列で
  値ごとの格納クラスを保つので、number のタグは数として入り `"8000" < "900"` の事故が
  起きません。**代償は「型を取り違えると、エラーにならず0件」**——だから束ねる形は
  `tagNormBind`（`vocab.go`）1か所で、書き手 `insertVocabEntry` と読み手
  `PagesByTagLoose`（→ `tagLookupBind`）が同じ関数を通ります。`material_dimensions.num` も
  同じ判断（整数は整数の格納クラスへ）。**この列を述語に使う裸の SQL を書かないこと。**
- **ページIDを文字列にする所は `page.FormatID` を通す**（本体で **20ファイル・38箇所**。
  うち `page/storage.go` の `NormalizeID` が1）。桁を変える日にどちらかを取りこぼすと、
  同じページに2つのIDが生まれます。
- **⚠ `MatchDXFAttachments`（PDFとDXFの突き合わせ）は試験から一度も呼ばれていません**
  （`grep -rl MatchDXFAttachments --include='*_test.go' ext` が空）。`dxf_test.go`（7本）は
  表題欄の読み取りまでで、突き合わせは解析の経路でだけ動きます。
- **`ext/subcon` にメソッド確認の番人がありません**——`internal/cms/method_guard_test.go`
  と `ext/comm/method_guard_test.go` はそれぞれ自分のパッケージのハンドラしか見ません。
  下請けの11本のうち `GateJSONPost`／`GateJSONPageRead`（メソッドを見る）を通るのは7本、
  `RequiredMaterialsAPIHandler`・`AnalyzeAttachmentAPIHandler`・`ParsePDFHandler` は自前で
  見ています。⚠ **`FilingTargetAPIHandler`（GET・読むだけ）はメソッドを見ていません**
  ——状態は変えないので実害は無いが、**固定する試験はどれにも無い**。

## 7. 数え直す（この文書を疑うとき）

```bash
# 規模（**ext/ を必ず含めること**）
find internal cmd ext -name '*.go' -not -name '*_test.go' | xargs wc -l | sort -rn | head -16
find internal cmd ext -name '*_test.go' | xargs cat | wc -l
grep -rh '^func Test' --include='*_test.go' internal cmd ext | wc -l
wc -l assets/*.js assets/*.css assets/*.html
ls e2e/verify-*.js | wc -l; ls e2e/probe-*.js | wc -l; cat e2e/verify-*.js e2e/probe-*.js | wc -l

# パッケージ依存の向き（1行ずつ・拡張も含める）
grep -rn '"w-cms/' --include='*.go' internal cmd ext | grep -v '_test.go' |
  sed 's/:[0-9]*:.*"\(w-cms[^"]*\)".*/ -> \1/' | sed 's#^\(.*\)/[^/]*\.go #\1 #' | sort -u
# 拡張どうしの import（向きは必ず「拡張 → 通信」）
grep -rn '"w-cms/ext/' --include='*.go' ext | grep -v _test.go

# ビルドタグ（パッケージ側には無い＝取り付け口だけ）
grep -rn '^//go:build' --include='*.go' cmd ext internal

# ルート表（コアと、拡張が足す分）
grep -nE 'Handle(Func)?\(' cmd/w-cms/main.go
grep -rn 'Pattern:' --include='*.go' ext/ | grep -v _test

# コアが宣言する登録の口と、拡張からの登録
grep -rn '^func Register' --include='*.go' internal/cms | grep -v _test
grep -rn 'cms\.Register[A-Za-z]*(' --include='*.go' ext | grep -v _test

# 表を持つプラグイン（nil でないもの）
grep -rn 'func (.*) Tables()' --include='*.go' internal ext | grep -v _test

# 語彙の形式・ビュー・ルート・置き場の本数は、組ごとに実際に数えるのがいちばん確か
#   （小さな main を書いて cms.VocabDefs() / cms.PluginRoutes() / cms.ExtensionIDs() /
#    cms.RequiredPages() を出す。`_measure/` のような `_` 始まりのディレクトリなら
#    `./...` に拾われない。終わったら消すこと）
go build ./... && go build -tags nomail ./... && go build -tags minimal ./...
```

**`gofmt -l` は判断材料にしないこと**——このリポジトリでは CRLF のため全ファイルが挙がります。
整形の確認は `go build` / `go vet` / `go test` で行います。
