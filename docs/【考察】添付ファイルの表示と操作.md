## 1. 提案の原文（2026-08-31）

> fileは表示できる画像などは表示し、全体を表示できない多ページPDFなどはサムネイル、
> バイナリファイルなどもサムネイル表示でクリックするとアプリで表示かダウンロードに
> なるのでは？

> 表示されているファイルに対するコンテキストメニューにOCRや編集があるのは良いと思います。

> エディタにリンクを挿入があっても良いかもしれませんね。HTML編集ソフトはリンクを
> 編集するのにプロパティ欄があるものが使いやすかったです。編集するのにダイアログが
> 出るのは使いにくかった

## 2. 種類別の表示（提案1）

**ファイルは種類に応じた最適な見た目で本文に現れる**、という原則。

| 種類 | 表示 | 現状 | 埋める距離 |
|---|---|---|---|
| 画像（PNG/JPEG/GIF/SVG） | **そのまま表示**（インライン `<img>`） | **実装済み**（画像アップロード・2026-08-26） | なし |
| PDF | **クリックで展開**（▶を押すと `<embed>`・ビューア内スクロールで多ページも背丈が伸びない） | **実装済み**（2026-09-01・閲覧モードのクローム。サムネイル案は取りやめ——生成に外部依存が要る一方、埋め込みはゼロ依存で内部スクロールが場所の問題も解く） | なし |
| ZIP | **クリックで中身の目録**（名前とサイズ。`archive/zip` の目録読みで展開はしない・SJIS名も復号） | **実装済み**（2026-09-01・`GET /api/zip-list`）。個々のファイルの取り出しは未実装（要望が出たら設計） | 取り出し |
| その他のバイナリ（CAD・Office 等） | **アイコン＋クリックでアプリ表示かダウンロード** | 📎 リンク＋`download` 配信（受け皿は 2026-08-31 実装済み） | サムネイル等の飾り |

設計の観察:

- **ワンノート移行の受け皿6条件の1つがまさに「添付15拡張子」**（[【考察】ワンノート移行.md](【考察】ワンノート移行.md)）。
  この提案は移行の前提条件を先に一般化した形になっている。
  **添付の置き場は 2026-08-31 に `files/` サブフォルダへ分離済み**——正本と同居しないので
  「添付の名前がサイドカーを上書きする」穴は構造的に消え、**拡張子リストは安全の門ではなく
  運用の方針**になった（ユーザー指摘「.json禁止は、アップロードファイルとjsonが同じ
  フォルダにあることが原因では？」——そのとおりだった）。`safeAttachmentName` の一本化は
  引き続き維持（文字種・トラバーサルの正規化）。
- **PDFサムネイルの生成手段**は当初の論点だったが（標準ライブラリにPDFレンダラは無く外部依存は原則禁止。
  ①`<embed>` の埋め込み／②Gemini で画像化／③アイコンのみ）、①を採用して「クリックで展開」へ発展し決着した（§5 の 2）。
- バイナリの「クリックでアプリ表示かダウンロード」は配信側の `Content-Disposition` の
  仕事で、**SVG の sandbox CSP と同じく配信ヘッダが安全の本体**（作業引き継ぎの罠と同じ）。

### 2.1. 置く場所が増えた——`section[data-type="file-view"]`（2026-09-14 実装）

上の表はすべて**添付そのものの隣**での見せ方だった。2026-09-14 に、**添付を別の場所で
開く**口ができた（ユーザー:「PDFがほかの部品の一部で、部品ページを作らず、ほかのページに
埋め込む場合はどうしますか？」「表示するという意図を伝える名前が良いと思います。ほかに
編集するという意図も出てくると思います」）。

本文へマーカーを置き、その中に参照を1つ書く。正本は
[internal/cms/file_view.go](../internal/cms/file_view.go)。

```html
<section data-type="file-view">
  <dl data-type="tags"><dt>受信元</dt><dd>010272-c3p7</dd></dl>
</section>
```

- **中身を描くのはサーバー**（鏡型・`renderFileView`）。`.vocab-chrome` に包むので
  シリアライザは保存せず、正本に残るのは**マーカーと参照タグだけ**。
  **計算ビュー（`View: true`）ではなく鏡型**なのは、計算ビューが中身を全部消して描き直す
  ため——それだと人が書いた参照タグが画面から消えてしまう。
- **開ける形式は `fileViewKinds` の表**: `.pdf` は `<embed>`／`.png` `.jpg` `.jpeg`
  `.webp` `.gif` `.svg` は `<img>`／`.mp4` は `<video>`／`.m4a` `.mp3` は `<audio>`。
  **表に無い形式は開かず、理由を画面に出す**（CADもOfficeもブラウザは素で描けない）。
  増やす基準は「ブラウザが**素で**描けるか」だけ——描画ライブラリを連れてくるのは
  開発方針 §1（外部依存の最小化）に触れる。
- **タグの名前は書く人が決める**。`受信元` でも `参考図` でも、語彙に宣言していない名前でも
  効く（コアは名前を知らない）。マーカーの中に限っては**素の `dl` も参照として読む**
  ——普段の「参照と読むのは可変タグの中だけ」の例外で、ここはページ全体を走査しないため
  番号が参照に化ける相手が居ない（`firstRefInTags`）。
- **値を書くための入口が「🔗 参照」**（`makeCopyRefButton`・[エディタ仕様.md](エディタ仕様.md) §7.4）。
  埋め込み自体は前からできたが、`010272-c3p7` は添付IDを手で調べないと書けなかった。
  手順は**添付で「🔗 参照」→ 行き先のページで 📄 ファイル表示 を挿す → 貼る**。
- **なぜ `<embed>` を本文に書かせず、マーカーにしたのか**——理由の正本は
  [セキュリティ設計.md](セキュリティ設計.md) §4。
- 名前を `pdf-view` にしなかったのは、**同じ場所に別の意図が並ぶ**から。「編集する」
  （WebDAV でローカルアプリへ渡す。§3・[【考察】添付をローカルアプリで編集する.md](【考察】添付をローカルアプリで編集する.md)）が
  控えており、`pdf-edit` では「PDFを編集する」意味になってしまう。対象（file）と
  意図（view）で名づければ、扱える形式が増えても名前が変わらない。

## 3. コンテキストメニュー: OCR・編集（提案2）

表示されているファイルの上での右クリック（またはホバーのメニュー）に**そのファイルへの
操作**を出す。

| 操作 | 中身 | 既存の土台 |
|---|---|---|
| **OCR** | 画像・スキャンPDFから文字を取り出し、本文へ貼れる形で返す | Gemini 連携（明細AI解析と同じ経路・有料枠の運用条件も同じ）。ワンノートの実データはOCRテキストを持っており（616ページ・325kトークン）、移行後の再OCRにも使える |
| **編集** | 回転・切り抜き・注記 | 将来要件として記録済み（[要件定義書.md](要件定義書.md) §5「保存した画像の編集」）。**添付には版が無い**ので編集結果は別ファイル保存（原本残置）が本命 |

- メニューは `.vocab-chrome`（保存されない編集クローム）として、対象ファイルの近傍に出す。
  CSP strict のため `on*=` は書けない——`addEventListener` で配線する（いつもの規律）。
- OCR結果の置き場は未決——本文へ挿す（見える文字になり索引に載る）か、
  折りたたみの引用ブロックか。**見える文字にすれば検索に載る**ので前者が有力。

## 4. リンクの挿入と編集（提案3）

- スラッシュメニューに**「リンク」**（または選択文字列をリンク化する操作）。
- 編集は**プロパティ欄方式**——ユーザーの経験則:「プロパティ欄があるものが使いやすかった。
  編集するのにダイアログが出るのは使いにくかった」。
- **既存の先例がそのまま使える**: 列設定ポップオーバ（[エディタ仕様.md](エディタ仕様.md)・
  「値は中身・役割や配線は属性の編集口で」）。キャレットがリンク上にあるとき、
  近傍に href の欄を出す——列型の明示（th の data-type）とまったく同じ形。
- 宛先の検査はサニタイザの既存規則のまま（`a[href]` は制限しない決定・2026-08-21。
  埋め込みの `/data/` 制限とは別扱い）。
- ページ内・ページ間リンクの補完（`#見出し名` や `000123` の入力補助）は、参照タグ
  （`ページID-ブロックID`・[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §9.1）の
  リンク描画と同じ土台に乗る——**着手するならそちらと一緒に**。

## 5. 順序の見立て

1. ~~**リンク挿入＋プロパティ欄**（§4）~~ **実装済み**（2026-09-01）——コンテキスト
   ツールバーの 🔗 で選択文字をリンクにし、キャレットがリンク上にある間だけ
   プロパティ欄が出る（[エディタ仕様.md](エディタ仕様.md) §3）。**スラッシュメニューには
   載せていない**——あちらはブロックを差し替える口で、文中のリンクは入らない。
   ページ内・ページ間リンクの**補完**は未実装で、参照タグのリンク描画と一緒にやる
2. ~~**PDFの小さな表示**~~ **実装済み**（2026-09-01・クリックで展開へ発展）——
   「クロームで出す（コードがデータを読む）vs 本文で許す（データをコードにする）」の
   危険性の違いを説明した上でユーザーが「clickで展開」を決定。埋め込みは閲覧モードの
   クロームで、宛先はきれいなURLの形に一致するリンクからのみ導出（app.js
   `refreshAttachmentPreviews`）。ZIPの目録も同じ形（`/api/zip-list`）
3. **コンテキストメニューの器＋OCR**（§3）——Gemini 経路の一般化
4. ~~**バイナリ添付の受け皿**~~ **実装済み**（2026-08-31・`POST /api/upload-file`。
   拡張子は設定 `attachment_extensions`・上限は `max_upload_mib`・本文ドロップが入口。
   残るは種類別の**表示**（§2 の表のとおり、いまは 📎 リンク＋ダウンロード配信））

いずれも**ユーザーの決定が要る細部**（サムネイルの方式・OCR結果の置き場・
バイナリの拡張子リスト）を含むため、着手時にこの文書から再確認すること。
