# 【ガイド】プラグイン開発

新しい**計算ユースケース**（DBテーブル＋同期＋集計API）を追加するための手順書です。

> **2026-08-26 に回覧型（イベントハンドラ＋段別コンテキスト）へ移行済み**です
> （設計の正本は [パーサとプラグイン.md](パーサとプラグイン.md)）。本ガイドはその形で書いてあります。
> なお `data-type` の位置づけは「機械が数えるための副」へ変わり
> （[コンセプト.md](コンセプト.md) §1②）、形式名を見出しの言葉へ移す提案は**検討中**
> （[【考察】語彙モデル.md](【考察】語彙モデル.md) §11）——採用されても差し替わるのは
> 引き金の解決（`triggerOf`）1点だけで、プラグインの書き方は変わりません。

## まず振り分ける — 本当にプラグインが要るか

**プラグインは「計算が要る場合だけ」の手段です。** 新しい語彙を足したいときは、まず次で
振り分けます（①語彙レジストリ／②汎用索引／③計算プラグインという3層モデルの全体像と、
なぜこの分離なのかは [【考察】語彙モデル.md](【考察】語彙モデル.md) §4 が正本）。

1. **記録・表示だけでよい**（語彙100種構想の大半。例: 検査記録・仕様一覧）
   → **プラグインは不要。Goのコードは1行も書きません。** 標準HTML（`<table data-type>`／
   `<dl data-type>`／`<section data-type>`）＋**語彙レジストリ（[vocab.go](../internal/cms/vocab.go) の
   `vocabRegistry`）への宣言1件**で、スラッシュメニュー・挿入骨格・保存・②汎用索引
   （`vocab_index`）・型検証まで自動で通ります（手順は [【一覧】語彙.md](【一覧】語彙.md) §5、
   エディタ側の対応は [エディタ仕様.md](エディタ仕様.md) §3.2）。
2. **集計API・型付きテーブル・取り込み変換のいずれかが要る**（例: 部材手配計算・PDF解析）
   → 本ガイドの手順でプラグインを作ります（③計算プラグイン）。この場合も**語彙の宣言は 1. と同じく
   レジストリ**で行い、プラグインは「マーカー付き標準HTMLを読んで自分のテーブルへ同期する」役だけを担います。

**カスタム要素（`<m-*>`）は作りません**（理由は [【考察】語彙モデル.md](【考察】語彙モデル.md) §9 の
決定ログ、現況は [【一覧】語彙.md](【一覧】語彙.md) §6）。プラグインが語彙を宣言する機構——
`Tags()`・`PluginTags()`・`TagSpec`・`htmldoc.New()` への注入——も撤去済みです（§2.1）。
動的な表示（集計ビュー等）はマーカー付き標準HTML＋エンハンサ／サーバー事前描画で設計します。

**人間にもAIエージェントにも、このガイドだけで作業が完結する**ことを目指して書いています。

> このガイドの背景・設計判断（なぜプラグイン化したか）は [変更履歴.md](変更履歴.md) の「プラグイン機構の導入（2026-06-20）」を参照してください。

## 1. アーキテクチャの全体像

w-cms は「HTMLに書かれた**マーカー付き標準HTML**」を「SQLiteのテーブル」に同期するCMSです。
1つの計算ユースケースは1つの**プラグイン**として表現されます。

保存されたHTMLは、コアの `parser.go`（タイトル・親IDの抽出）と `sync.go` の `SyncIndex` を通ります。
`SyncIndex` は `pages` を同期したあと、登録済み観察係の `OnPageStart` を呼び、**コアの配送係が
本文を1回だけ歩いて**引き金に当たった要素を各観察係の `OnElement` へ届けます（同じトランザクション内。
プラグインは `init()` で `Register()` に自己登録する）。**プラグインを足してもコアは無変更**です。
**プラグインは本文の語彙を持ちません**（§2.1）。

### 関係するファイル

## 2. `Plugin` / `Observer` インターフェース

```go
// テーブルの所有だけを宣言する。
type Plugin interface {
    Name() string      // 識別子（ログ用）
    Schema() []string  // CREATE TABLE IF NOT EXISTS ...
    Tables() []string  // 所有テーブル名（自己文書化・整合性検証用）
}

// 本文を読んで自分のテーブルを洗い替える（＝観察係）。
type Observer interface {
    Plugin
    Triggers() []string                       // 担当する data-type（"*" で全マーカー）
    OnPageStart(ctx *ObserveContext) error    // 自テーブルの当該ページ分を DELETE
    OnElement(ctx *ObserveContext, el *html.Node) (descend bool, err error)
}
```

**6メソッド**です。集計APIを足したい場合は追加で `RouteProvider` を、要素を配り終えた
あとの確定処理が要る場合は `PageFinisher`（`OnPageEnd`）を実装します（どちらも任意）。

```go
type RouteProvider interface { Routes() []Route }        // []Route{{Pattern, Handler}}
type PageFinisher  interface { OnPageEnd(ctx *ObserveContext) error }
```

> **2026-08-26 に `Sync(tx, pageID, root)` は無くなりました。** かつては木を丸ごと受け取って
> **各プラグインが自前で走査**していましたが、同じ木をプラグインの数だけ歩くうえ、除外規則
> （`.vocab-chrome` の中を読まない等）を各自が覚えている必要がありました。いまは**コアの
> 配送係が1回だけ歩き**、引き金に当たった要素だけを `OnElement` へ届けます
> （設計の正本は [パーサとプラグイン.md](パーサとプラグイン.md)）。
>
> 実務上の違いは3つです。
> - **走査コードを書かない**（`WalkElements` を自分で回さない）。
> - **除外を覚えなくてよい**——クロームの中へは配送係が入らないので、そこは観測できない。
> - **DELETE は `OnPageStart` へ**。これでテンプレート領域の除外が定義から成立します
>   （`OnPageStart` は呼ぶが要素イベントを1つも発火しない＝古い行は消えて新しい行は入らない）。

### 2.1 プラグインは本文の語彙を持たない

本文の語彙（許可される要素・属性）は `htmldoc/sanitize.go` の1箇所が正本で、形式（`data-type`）の
宣言は `vocab.go` のレジストリが持ちます。**この役割分担の図と、かつて必須メソッド `Tags()` で
プラグインが語彙を注入していた機構を撤去した経緯（2026-08-20）は
[本文サニタイズ設計.md](本文サニタイズ設計.md) §5.3 が正本です。**

プラグインを書くうえで効いてくるのは次の3点です。

- **サニタイザは `data-type` の値を検査しません。** 新しい形式名を足しても許可リストは無変更です。
  逆に、新しい**要素**や**属性**が要るときだけ `structuralElements` を直します
  （[本文サニタイズ設計.md](本文サニタイズ設計.md) §5・§7）。
- **`OnElement()` が読む鍵は必ずレジストリの `Field`／`Label` に載せる**。載せ忘れると
  文書の見出しから機械キーへ解決できず、値が黙って落ちます（`columnFor` が解決に失敗すると
  その列は読まれません）。かつて `Tags()` の属性宣言漏れで `item-name` が消えて原価集計が壊れた
  のと、症状は同じです。
- 形式の宣言と読み取りが別ファイル（`vocab.go` と `plugin_xxx.go`）に分かれるのは v1 の割り切りです。
  ③計算形式の語彙宣言をプラグイン側へ寄せる案は将来課題（`vocab.go` 冒頭のコメント参照）。

### 2.2 使えるヘルパー

| ヘルパー | 定義 | 用途 |
|---|---|---|
| `Attr(n, "key")` | `plugin.go` | 要素 n の属性値（無ければ ""） |
| `WalkElements(root, fn)` | 〃 | 全要素ノードを先行順で走査 |
| `AtoiSafe(s)` | 〃 | 文字列→int（失敗時 0） |
| `ctx.Tag("部品番号")` | `walk.go` | 可変タグ（`<dl data-type="tags">`）から名前で値を引く（多値は先頭）。**木は渡されない**ので、ページ全体を見る用途はこの口から |
| `ctx.Ancestors()` / `ctx.Closest(fn)` | 〃 | 祖先を辿る（容器の `data-src` を拾う等） |
| `ctx.Counter("鍵")` | 〃 | 1周のあいだの通し番号（同じ形式が複数あるときの区別） |
| `NullableString(s)` | 〃 | "" を SQL NULL に変換（日付列など） |
| `VocabDLFields(dl, def)` | `vocab_index.go` | `dl` の項目を**機械キー→値**の表として返す |
| `VocabTableRows(table, def)` | 〃 | 表のデータ行を**機械キー→値**の並びとして返す（見出し行から鍵を解決） |
| `FirstVocabChild(root, "table", "client-order-items")` | 〃 | 直下から最初の `element[data-type]` を探す（入れ子の `section` へは降りない） |
| `ClosestFileSrc(n)` | 〃 | 祖先のファイル容器 `section[data-type="file"]` の `data-src`（PDFパス）を取る |
| `VocabDefByType("part-materials")` | `vocab.go` | 形式定義を引く（`VocabDLFields`／`VocabTableRows` に渡す） |
| `vocabNumber(raw)` | `plugin_materials.go` | セルの数値を正規化して int で返す（`¥8,000` → 8000。解釈不能なら 0） |

> **鍵の解決規則**（`VocabDLFields`／`VocabTableRows` が内側でやっていること）: 鍵は
> **見出しの表示文字**（`th`／`dt`）ただ1つで、レジストリ宣言の `Label` を通じて機械キー（`Field`）へ
> 解決されます。**見出しを「単価（税抜）」等へ改名すると解決できなくなり、その列は読まれません**——
> 黙って止まらないよう、保存時に `unresolved_fields` で告知されます（拒否はしません）。
> 詳しい仕様は [【一覧】語彙.md](【一覧】語彙.md) §1.1。

> **削除済みのヘルパー**: `ClosestAttr(n, "m-file", "src")` と `Quantity(n)` は旧カスタム要素専用
> だったため撤去されました（2026-08-19）。前者の後継は `ClosestFileSrc(n)`、後者は
> 「空セルなら 1」を呼び出し側で書きます（いまは読み取り側の `vocabQuantity` が当てます）。

## 3. 追加手順（チェックリスト）

1. **DBの形を決める**: 1テーブルか、ヘッダ＋明細（1:N）か、複数テーブルか。
2. **形式（`data-type`）を決めて [vocab.go](../internal/cms/vocab.go) の `vocabRegistry` へ宣言する**:
   `Type`（kebab-case・一意）・`DisplayName`・`Category`・`Icon`・`Element`（`table`／`dl`／`section`）と
   `Columns`（`Field` = `OnElement()` が読む機械キー・`Label` = 見出しの表示文字・`Type` = 列型）。
   ヘッダ＋明細なら親に `Items`（明細表の形式名）、ファイル容器の中に生むなら `Container: "file"`、
   単独で挿入しない形式には `Hidden: true` を付けます。
3. `internal/cms/plugin_<usecase>.go` を新規作成し、§4のテンプレートを埋める。
4. （集計APIが要るなら）`RouteProvider` を実装。
5. （挿入直後の振る舞いや専用UIが要るなら）`assets/app.js` に**エンハンサ**を足す。
   挿す要素は必ず `class="vocab-chrome"` にして**保存されない編集クローム**にします
   （実例は `enhanceFileSections`。呼び出しは `applyMode`／`populateEditor`／挿入直後の3点で、
   作り直し方式なので冪等）。
6. **検証**: `go build ./... && go test ./...`。必要なら新しいテストを追加。
7. ドキュメント追記（[【一覧】語彙.md](【一覧】語彙.md) §2 の形式一覧、[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) のテーブル一覧、[変更履歴.md](変更履歴.md)）。

> ⚠️ **鍵の一致**: レジストリの `Columns[].Field` と、プラグインが `VocabDLFields`／`VocabTableRows`
> の結果から引くキー（`row["item-name"]` の `"item-name"`）は**完全一致**させる必要があります。
> ここがズレると値が空で入り、同期は「成功したのに中身が無い」状態になります。

> ⚠️ **カスタム要素は作りません**（2026-08-17 決定・移行完了済み）。動的な表示が要るときは
> ①エンハンサ（編集時の補助UI。`.vocab-chrome`）か、②サーバー事前描画
> （[view_render.go](../internal/cms/view_render.go)。`View: true` の計算ビュー）のどちらかを選びます。
> **公開ページの閲覧をゼロJSに保つ**なら②です。理由と全体像は
> [【考察】語彙モデル.md](【考察】語彙モデル.md) §9・[エディタ仕様.md](エディタ仕様.md) §0 を参照してください。

> ⚠️ **インラインを書かない**: CSP は strict 化済み（`'unsafe-inline'` なし）です。
> `<script>`・`<style>`・`style=`・`on*=` は使えません。スタイルは `/assets/` の外部CSSへ置き、
> イベントは `addEventListener`、動的スタイルは `element.style.x = y` で当てます（開発方針 4）。

> ⚠️ **正本性の不変条件**: プラグインのテーブルに入れる全データは、`data/master` のHTML（マーカー付き標準HTML）から観察係で**再生成可能**でなければなりません。DBは使い捨て可能な派生インデックスであり、`data/master` のファイルのみがバックアップ対象です。ファイルから再生成できないデータ（外部から取得して保存するだけの値など）をDBに持たせてはいけません（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 8章参照）。

## 4. コピペ用テンプレート

### パターンA: フラットな1テーブル（明細なし）

**① まずレジストリへ形式を宣言する**（`vocab.go` の `vocabRegistry` へ1件追記）。

```go
{
	Type:        "memo",
	DisplayName: "メモ",
	Category:    "記録",
	Icon:        "📝",
	Element:     "dl",
	Columns: []VocabColumn{
		{Field: "title", Label: "件名", Type: ColText},
		{Field: "body", Label: "内容", Type: ColText},
	},
},
```

本文にはこの形で入ります（鍵は `dt` の表示文字。機械キーは本文に書き出しません）。

```html
<dl data-type="memo">
  <dt>件名</dt><dd>在庫確認</dd>
  <dt>内容</dt><dd>丸鋼材の在庫を来週確認する</dd>
</dl>
```

**② プラグインを書く**（`internal/cms/plugin_memo.go`）。

```go
package cms

import (
	"database/sql"

	"golang.org/x/net/html"
)

func init() { Register(memoPlugin{}) }

type memoPlugin struct{}

func (memoPlugin) Name() string { return "memo" }

func (memoPlugin) Schema() []string {
	return []string{
		`CREATE TABLE IF NOT EXISTS memos (
			id INTEGER PRIMARY KEY AUTOINCREMENT,
			title TEXT,
			body TEXT,
			page_id INTEGER,
			FOREIGN KEY (page_id) REFERENCES pages(id) ON DELETE CASCADE
		);`,
	}
}

func (memoPlugin) Tables() []string { return []string{"memos"} }

// Triggers は担当する形式（data-type の値）を宣言します。
// **走査は書きません**——コアの配送係が、この引き金に当たった要素だけを届けます。
func (memoPlugin) Triggers() []string { return []string{"memo"} }

// OnPageStart は当該ページの既存行を消します（洗い替えの前半）。
func (memoPlugin) OnPageStart(ctx *ObserveContext) error {
	_, err := ctx.Tx.Exec(`DELETE FROM memos WHERE page_id = ?`, ctx.PageID)
	return err
}

// OnElement は担当の要素ごとに呼ばれます。el の部分木は自由に読んで構いません。
// 戻り値 descend=false は「この部分木は自分が読み切った」という意思表示です。
func (memoPlugin) OnElement(ctx *ObserveContext, el *html.Node) (bool, error) {
	if el.Data != "dl" { // 引き金は同じでも要素が違うことがある（念のため）
		return true, nil
	}
	def, _ := VocabDefByType("memo") // 見出し → 機械キーの解決に使う
	f := VocabDLFields(el, def)      // {"title": "在庫確認", "body": "..."}
	_, err := ctx.Tx.Exec(
		`INSERT INTO memos (title, body, page_id) VALUES (?, ?, ?)`,
		f["title"], f["body"], ctx.PageID)
	return false, err
}
```

> **`descend` の意味**（2026-08-26）——**既定は true**（降りる）で、`false` を返してよいのは
> 「その部分木を自分が読み切った」ときだけです。ただし観察係どうしは独立なので、
> 配送係は「**全員**が降りないと言ったときだけ降りない」（OR）という規約で動きます
> ——受注の観察係が明細表を丸ごと読んでも、②汎用索引は同じ明細表を自分でも索引します。

> **実物の例はもうありません**——`plugin_estimates.go`（`our-estimate` / `supplier-estimate` の
> 2形式・2テーブル）は D-1 で削除されました。見積もりは語彙レジストリの宣言だけで
> ②汎用索引へ載っています（＝そもそもプラグインが要らない側の例）。

### パターンB: ヘッダ＋明細（1:N）
**雛形にできる実物はもうありません**（`plugin_client_order.go` は D-1 で削除）。この形の
読み取りは②汎用索引が引き受けており、③計算は索引側から読みます（§8）。それでも自前の
テーブルが要ると判断したときの要点：
- 本文の形は `<section data-type="親">` が**ヘッダ `<dl>`（`data-type` は付けない）**と
  **明細 `<table data-type="子">`** を包む形（論点A・案1。[【一覧】語彙.md](【一覧】語彙.md) §2.3）。
  読み出しは `FirstVocabChild(n, "dl", "")` と `FirstVocabChild(n, "table", "子")`。
- レジストリでは親に `Items: "子"` を宣言し、子には `Hidden: true` を付ける（単独では挿入しない）。
- `Tables()` は所有する全テーブルを列挙する（慣習として子→親の順で書く）。`Schema()` で定義したテーブルはすべてここにも列挙する（テストで整合性を検証する）。
- **引き金は親だけ**（`Triggers() []string{"親"}`）。明細表は `OnElement` の中から
  `FirstVocabChild` で自分で読み、`descend=false` を返す。
- 洗い替えは `OnPageStart` で行う。明細テーブルにも `page_id` を持たせてあるので、
  子→親の順に直接消す（`order_no` のサブクエリだと、番号が重複したときに他ページの
  明細まで巻き込む。2026-08-21 修正）：
  ```go
  ctx.Tx.Exec(`DELETE FROM <子> WHERE page_id = ?`, ctx.PageID)
  ctx.Tx.Exec(`DELETE FROM <親> WHERE page_id = ?`, ctx.PageID)
  ```
- 親は `order_no` などの自然キーに `ON CONFLICT(page_id, order_no) DO UPDATE` を付ける。
- PDFの原本パスが要るなら `ClosestFileSrc(el)` で祖先の容器から拾う（容器は任意なので、
  ファイルの無い受注でも空文字列が返るだけで壊れない）。`ctx.Ancestors()` / `ctx.Closest()` でも
  祖先を辿れる。

### パターンC: 集計API付き
[plugin_materials.go](../internal/cms/plugin_materials.go) を雛形にしてください。`RouteProvider` を実装し、`Routes()` で `(パス, ハンドラ)` を返すと、`main.go` が自動でルート登録します（コア無変更）。
集計本体は**エクスポートした関数に切り出す**と、計算ビューのサーバー事前描画から共用できます
（`RequiredMaterials` を `/api/required-materials` と [view_render.go](../internal/cms/view_render.go) が共用している）。

### 特殊: ページ全体のタグを各行に注入したい
可変タグ `部品番号` のような「ページに1つ、全行に効く値」は **`ctx.Tag("部品番号")`** で取得し、
各 INSERT に渡します（[plugin_materials.go](../internal/cms/plugin_materials.go) 参照。読む形式は
`<dl data-type="tags">`）。

**木そのものは渡されません。** `ctx.Tag` はコアが用意する口で、タグが表より後ろにあっても
引けます（文書順の回覧では拾えないため）。木を渡すと「各自が自前で歩く」形へ逆戻りし、
除外規則の一元化（`.vocab-chrome` の中を歩かない等）を失うので、そうしていません。

### 特殊: 表示専用の計算ビューを足したい
本文には**空のマーカー**だけを保存し、中身はサーバーが描く形にします。**ここだけは
「レジストリへ宣言1件」では動かない例外**で、手順は2つです。

1. レジストリで `Element: "section"` ＋ `View: true`（列は持たない）を宣言する。
2. **[view_render.go](../internal/cms/view_render.go) の `viewRenderers` へ描画関数を1件登録する**
   ——`map[string]func(user *auth.User, pageIDInt int) string` に形式名で足すだけです。
   早期リターンの判定も対象の収集も**レジストリの `View: true` から作られる**ので、
   触るのはこの1箇所になりました（2026-08-25 の整理）。
   足し忘れても**無言の空白にはならず**、「この形式（○○）の中身を作る処理がまだ
   用意されていません」と画面に出ます（`missingViewHTML`）。以前は3箇所へ形式名を
   足す必要があり、どれか1つでも漏らすと中身が描かれないまま何も起きませんでした。

中身は `<div class="vocab-chrome" contenteditable="false">` に包まれ、エディタのシリアライザが
`.vocab-chrome` を保存しないので、保存往復ではマーカーだけが残ります。
**タイトル等の利用者入力は必ず `html.EscapeString` を通すこと**（サーバー側で文字列連結するため）。
実例は `child-list`（子ページ一覧）と `required-materials`（手配集計）。仕組みの全体像は
[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.4。

## 5. 動作の仕組み（なぜコアを触らなくてよいか）

- **スキーマ作成**: 起動時に `main.go` が `cms.ApplySchema(db)` を呼び、全プラグインの `Schema()` を実行します。テストは `database.CreateCoreTables(db)` ＋ `cms.ApplySchema(db)` で本番と同じスキーマを再現します。
- **同期**: `SyncIndex` がコア（`pages` の upsert → サイドカー由来の `page_perms`）を同期した後、各観察係の `OnPageStart` を呼び、**配送係が本文を1回だけ歩いて** `OnElement` を配ります（すべて1つのトランザクション内）。可変タグの行き先は②汎用索引 `vocab_index` です（専用テーブル `page_tags` は 2026-08-30 に吸収）。
- **全再構築**: `RebuildDatabase` は `sqlite_master` から**全テーブルをDROP**してスキーマごと作り直し、`data/master` の全HTMLを再同期します（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 8章）。全テーブルをDROPするため、`Tables()` の記載漏れが再構築バグを起こすことはありません。ただし `Schema()` と `Tables()` の整合性はテスト（`TestPluginTablesConsistency`）で検証されるので、所有テーブルは `Tables()` に列挙してください。
- **正本性**: プラグインのテーブルは `data/master` のHTMLから再生成可能でなければなりません（§3の不変条件）。これにより `cms.db` は使い捨て可能で、バックアップはファイルのみで済みます。
- **ルーティング**: `main.go` が `cms.PluginRoutes()` を走査し、`RouteProvider` を実装するプラグインのルートを登録します。

## 7. AIエージェント向けの厳密手順

このセクションは、AIがこのガイドだけで作業する際の決定論的な手順です。

0. **計算が要るかを先に判定する**。集計API・型付きテーブル・取り込み変換のどれも要らないなら、
   **`vocab.go` の `vocabRegistry` へ1件足して終わり**。プラグインは作らない（冒頭の振り分け）。
1. **絶対に編集しないファイル**: `internal/cms/plugin.go`, `internal/cms/parser.go`, `internal/cms/sync.go`, `internal/cms/walk.go`, `internal/cms/vocab_index.go`, `internal/cms/htmldoc/sanitize.go`, `internal/database/sqlite.go`, `cmd/w-cms/main.go`。これらを編集しようとしたら設計を間違えている。
2. **編集するのは2ファイル**: `internal/cms/vocab.go`（`vocabRegistry` へ形式を1件追記）と、新規作成する `internal/cms/plugin_<usecase>.go`。後者は §4 から最も近いパターン（A/B/C）をコピーして名前を置換する。
   **唯一の例外**: `View: true` の**計算ビュー**を足すときだけ、3ファイル目として
   `internal/cms/view_render.go` の `viewRenderers` へ描画関数を1件登録する（§4「特殊: 表示専用の
   計算ビューを足したい」。足し忘れても無言の空白にはならず、理由が画面に出る）。
3. **`Observer` の6メソッド**（`Name` / `Schema` / `Tables` / `Triggers` / `OnPageStart` / `OnElement`）を必ず実装し、ファイル冒頭に `func init() { Register(<plugin>{}) }` を書く。**`Sync()` も `Tags()` も存在しない**（前者は 2026-08-26、後者は 2026-08-20 に撤去）。
4. **`Tables()` は `Schema()` で作るテーブルをすべて列挙**（慣習として子→親順）。整合性は `TestPluginTablesConsistency`（[storage_test.go](../internal/cms/storage_test.go)）が検証する。
5. **洗い替えの DELETE は `OnPageStart` へ**、INSERT は `OnElement` へ置く。明細テーブルも `page_id` を持つので、子→親の順に直接消す。
6. **走査は書かない**。担当は `Triggers()` の宣言で決まり、`OnElement` には当たった要素だけが来る（要素名だけ念のため確かめる）。値の取り出しは `VocabDLFields`／`VocabTableRows` を使い、生の `Attr(el, "...")` で業務値を読まない（値は属性ではなく**中身のテキスト**にある）。
7. **鍵の一致を確認**: `f["item-name"]` の `"item-name"` が、レジストリの `Columns[].Field` と一致しているか。
8. **集計APIが要るときだけ** `RouteProvider` を実装する。`main.go` には触らない。
9. **検証**: `go build ./... && go vet ./... && go test ./...` がすべて通ること。スキーマを使うテストは §6 の定型で用意する。
10. **ドキュメント更新**: [【一覧】語彙.md](【一覧】語彙.md) §2 に形式を、[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) の「2. データベーススキーマ設計」に新テーブルを追記し、[変更履歴.md](変更履歴.md) に1行追記する。

|---|---|---|

### 索引を読む（③計算の書き方）

集計は `vocab_query.go` の層を通します。**この層の仕事は鍵の変換**です——索引の
`field` に入っているのは本文の見出しの表示文字（`品番`・`数量`）で、③計算が使いたいのは
機械キー（`item-id`・`quantity`）。対応表は①語彙レジストリの `Label` ↔ `Field` が唯一の
正本なので、ここで一度だけ引き当てます。**集計コードへ日本語の魔法文字列を直書きしない
こと**——見出しを改名したときに、告知する側（`UnresolvedVocabFields`）と読む側がずれます。

| 関数 | 何を返すか |
|---|---|
| `vocabTableRowsOf(db, pageID, dataType)` | 表形式の行（1データ行＝1件）。`row.Values["item-id"]`・`row.Num("cost")` |
| `vocabBlocksOf(db, pageID, dataType)` | 名前：値形式（1ブロック＝1件）。業務文書ブロックのヘッダもこれ |
| `pagesByTag(db, name, value)` | 可変タグの逆引き（「部品番号が X のページ」）。**ページ横断の突き合わせはこの形**になる |

> **ヘッダと明細の対応づけは `block_no`** です。索引のブロック番号は形式ごとの文書順
> 連番なので、1つの `section` がヘッダ1つと明細表1つを持つ限り、同じ番号どうしが対に
> なります（発注書番号で結ぶと、番号が重複したときに仕入先が入れ替わりえました）。

### プラグインは自前のテーブルを持てるか

**機構としては残っています**（`Schema()` / `Tables()` は健在で、`ApplySchema` が流します）。
ただし**コアのプラグインはもう1つも持っていません**。新しく持たせる前に、
「その計算は索引から Go で束ねられないか」を必ず確かめてください——D-1 で8テーブルを
畳んだのは、**可変列名（`単価（ロット20）倉橋`）が横持ちでは受からない**という実データの
結論からで（[【考察】ワンノート移行.md](【考察】ワンノート移行.md) §3-5）、同じ理由が
新しいテーブルにも当てはまります。

以下の DOM ヘルパは**プラグイン作者向けに残していますが、いまの呼び出し元は0**です
（自前テーブルへ同期していたプラグインが使っていたもの）: `VocabDLFields`・
`VocabTableRows`・`ClosestFileSrc`・`NullableString`。
