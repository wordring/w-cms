# 【ガイド】プラグイン開発

新しいユースケース（新しいカスタムタグ＋DBテーブル＋集計）を追加するための手順書です。

**プラグインは「計算が要る場合だけ」の手段です。** 新しい語彙を足したいときは、まず次で
振り分けます（3層モデル: [【考察】語彙モデル.md](【考察】語彙モデル.md) §4）。

1. **集計API・型付きテーブル・取り込み変換のいずれかが要る**（例: 部材手配計算・PDF解析）
   → 本ガイドの手順でプラグインを作る（③計算プラグイン）。
2. **記録・表示だけでよい**（語彙100種構想の大半。例: 検査記録・仕様一覧）
   → プラグインは不要。標準HTML（`<table data-type>`／`<dl data-type>`）＋
   **語彙レジストリへの宣言1件**で足りる。
   ※ レジストリ（[vocab.go](../internal/cms/vocab.go) の `vocabRegistry`）と汎用索引
   （`vocab_index` テーブル）は **2026-08-17 に実装済み**。宣言を1件足すだけで
   スラッシュメニュー・挿入骨格・保存・索引・型検証まで自動で通る
   （サンプルは「検査記録」。エディタ側の対応は [エディタ仕様.md](エディタ仕様.md) §3.2）。

なお **Web Components（カスタム要素 `<m-*>`）は廃止決定**（2026-08-17・
[【考察】語彙モデル.md](【考察】語彙モデル.md) §9）。③のプラグインでも**新しい `<m-*>` は
作らない**——動的な表示（集計ビュー等）はマーカー付き標準HTML＋エンハンサ／サーバー
事前描画で設計する。本ガイドの `Tags()` まわりの記述は、現行カスタム要素10種を移行完了まで
保守するためのもの。

**人間にもAIエージェントにも、このガイドだけで作業が完結する**ことを目指して書いています。

> このガイドの背景・設計判断（なぜプラグイン化したか）は [変更履歴.md](変更履歴.md) の「プラグイン機構の導入（2026-06-20）」を参照してください。

## 0. 3行サマリー

1. `internal/cms/plugin_xxx.go` を1ファイル新規作成し、`Plugin` インターフェースを実装して `init()` で `Register()` する。
2. （フロントが必要なら）`assets/web-components.js` にカスタム要素を足し、`assets/templates/` にテンプレートを置く。
3. **コアファイル（parser.go / sync.go / main.go / database/sqlite.go）は編集しない。** プラグインが自動的に走査・登録される。

## 1. アーキテクチャの全体像

w-cms は「HTMLに書かれたカスタムタグ」を「SQLiteのテーブル」に同期するCMSです。1つのユースケースは1つの**プラグイン**として表現されます。

```
                ┌─────────────────── コア（編集しない） ───────────────────┐
HTMLページ ──▶  parser.go(ParseCore)        sync.go(SyncIndex)
                  │ タイトル・タグを抽出        │ pages/page_tagsを同期
                  │                            │ 登録済みプラグインを走査 ──┐
                └────────────────────────────────────────────────────────┘ │
                                                                            ▼
        ┌──────────── プラグイン（ここを増やす） ────────────┐
        │ plugin_client_order.go   plugin_estimates.go        │
        │ plugin_our_order.go      plugin_materials.go(+API)  │
        │   各々が Schema()/Tables()/Sync() を提供し           │
        │   init() で Register() に自己登録する                │
        └─────────────────────────────────────────────────────┘
```

コアは「登録されたプラグインのリスト」を走査するだけなので、プラグインを足してもコアは無変更です。

### 関係するファイル
| ファイル | 役割 | 新ユースケースで編集するか |
|---|---|---|
| `internal/cms/plugin.go` | レジストリ・`Plugin`インターフェース・DOMヘルパー | ❌ しない |
| `internal/cms/parser.go` | コア情報（タイトル・親ID・タグ）の抽出 | ❌ しない |
| `internal/cms/sync.go` | `SyncIndex`（コア同期＋プラグイン走査） | ❌ しない |
| `internal/database/sqlite.go` | コアテーブル（pages/page_tags）の作成 | ❌ しない |
| `cmd/w-cms/main.go` | 起動・ルーティング | ❌ しない |
| **`internal/cms/plugin_xxx.go`** | **あなたのユースケース** | ✅ **新規作成** |
| `assets/web-components.js` | カスタム要素（フロント） | △ 必要なら |
| `assets/templates/` | 表示テンプレート（フロント） | △ 必要なら |

## 2. `Plugin` インターフェース

```go
type Plugin interface {
    Name() string                                      // 識別子（ログ用）
    Schema() []string                                  // CREATE TABLE IF NOT EXISTS ...
    Tables() []string                                  // 所有テーブル名（自己文書化・整合性検証用）
    Tags() []TagSpec                                   // 所有するカスタム要素と属性契約
    Sync(tx *sql.Tx, pageID int, root *html.Node) error // 当該ページ分を洗い替え
}
```

集計APIを足したい場合は、追加で `RouteProvider` を実装します（任意）。

```go
type RouteProvider interface {
    Routes() []Route   // []Route{{Pattern: "/api/...", Handler: ...}}
}
```

### `Tags()` — カスタムタグはすべてプラグインが所有する

**コアはカスタム要素（`<m-*>`）を一切知りません。** サニタイザ（`internal/cms/htmldoc`）が
知るのは構造HTMLの安全性だけで、語彙は各プラグインの `Tags()` が唯一の正本です
（cms 側の `sanitize.go` が `PluginTags()` を集めて `htmldoc.New()` へ注入する）。

```go
func (myPlugin) Tags() []TagSpec {
    return []TagSpec{
        {Element: "m-memo", Attributes: []string{"title", "body"}},
    }
}
```

`Tags()` は**任意インターフェースではなく必須メソッド**です。宣言せずに属性を読むプラグインを
コンパイラに書かせないためです。扱うカスタム要素が無ければ `nil` を返します。

この1つの宣言が3つの用途を賄います（個別の実装は不要）:

```
各プラグインの Tags() ──► PluginTags()（要素ごとの和集合）─┬─► サニタイズ許可リスト
                                                          ├─► /api/tag-schema（エディタのシリアライザ）
                                                          └─► docs/【一覧】カスタムタグ.md
```

- **`Attributes` は「読む属性」ではなく「その要素に許される属性の全体」**。誰も同期しないが
  保存には要る属性（`<m-file>` の `src`/`name`、`<m-required-materials>` の `page-id`）も含めます。
- **`Sync()` が読む属性は必ず載せる**。載せ忘れると保存のたびに黙って除去され、集計が壊れます
  （実際に `item-name` の漏れでこの不具合が起きました）。
- 同じ要素を複数のプラグインが宣言してもよく、属性は**和集合**になります
  （`<m-item>` は顧客の発注書と弊社の発注書の双方が使う）。

### 使えるヘルパー（`plugin.go` 定義）
| ヘルパー | 用途 |
|---|---|
| `Attr(n, "key")` | 要素 n の属性値（無ければ ""） |
| `ClosestAttr(n, "m-file", "src")` | 祖先方向へ要素を探して属性値を取る（容器から値を拾う） |
| `AtoiSafe(s)` | 文字列→int（失敗時 0） |
| `Quantity(n)` | quantity属性（未指定なら 1） |
| `WalkElements(root, fn)` | 全要素ノードを先行順で走査 |
| `TagValue(root, "部品番号")` | `<m-tag name="部品番号" value="..">` の値 |
| `NullableString(s)` | "" を SQL NULL に変換（日付列など） |

## 3. 追加手順（チェックリスト）

1. **DBの形を決める**: 1テーブルか、ヘッダ＋明細（1:N）か、複数テーブルか。
2. **タグの形を決める**: どのカスタムタグ・属性名にするか（フロントと一致させる）。
3. `internal/cms/plugin_<usecase>.go` を新規作成し、§4のテンプレートを埋める。
4. （集計APIが要るなら）`RouteProvider` を実装。
5. （フロントが要るなら）`assets/web-components.js` に要素を追加、`assets/templates/` にテンプレートを追加。
6. **検証**: `go build ./... && go test ./...`。必要なら新しいテストを追加。
7. ドキュメント追記（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) のテーブル一覧、[変更履歴.md](変更履歴.md)）。

> ⚠️ **属性名の一致**: フロントの属性（`web-components.js` の `observedAttributes` とテンプレート）と、プラグインの `Attr(n, "...")` で読む属性名は**完全一致**させる必要があります。ここがズレると同期されません。

> ⚠️ **フロントの作法**: カスタム要素は基底クラス **`MElement` を継承**し、`render()` と `observedAttributes` だけを書きます。**描画先は Light DOM（`this.innerHTML`）で、Shadow DOM は使いません。** 入力欄からホストの属性への書き戻しは `data-attr="<属性名>"`（削除ボタンは `data-remove`）を付け、`render()` の最後に `this.bindEditFields()` を呼ぶだけです。テンプレートにインラインの `on*=` は書きません。理由と全体像は [エディタ仕様.md](エディタ仕様.md) §0.1 を参照してください。

> ⚠️ **正本性の不変条件**: プラグインのテーブルに入れる全データは、`data/master` のHTML（カスタムタグ）から `Sync()` で**再生成可能**でなければなりません。DBは使い捨て可能な派生インデックスであり、`data/master` のファイルのみがバックアップ対象です。ファイルから再生成できないデータ（外部から取得して保存するだけの値など）をDBに持たせてはいけません（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 8章参照）。

## 4. コピペ用テンプレート

### パターンA: フラットな1テーブル（明細なし）

```go
package cms

import (
	"database/sql"

	"golang.org/x/net/html"
)

func init() { Register(memoPlugin{}) }

type memoPlugin struct{}

func (memoPlugin) Name() string { return "memo" }

func (memoPlugin) Schema() []string {
	return []string{
		`CREATE TABLE IF NOT EXISTS memos (
			id INTEGER PRIMARY KEY AUTOINCREMENT,
			body TEXT,
			page_id INTEGER,
			FOREIGN KEY (page_id) REFERENCES pages(id) ON DELETE CASCADE
		);`,
	}
}

func (memoPlugin) Tables() []string { return []string{"memos"} }

func (memoPlugin) Sync(tx *sql.Tx, pageID int, root *html.Node) error {
	// 当該ページの既存行を消してから入れ直す（洗い替え）
	if _, err := tx.Exec(`DELETE FROM memos WHERE page_id = ?`, pageID); err != nil {
		return err
	}
	var firstErr error
	WalkElements(root, func(n *html.Node) {
		if firstErr != nil || n.Data != "m-memo" {
			return
		}
		if _, err := tx.Exec(
			`INSERT INTO memos (body, page_id) VALUES (?, ?)`,
			Attr(n, "body"), pageID); err != nil {
			firstErr = err
		}
	})
	return firstErr
}
```

### パターンB: ヘッダ＋明細（1:N）
[plugin_client_order.go](../internal/cms/plugin_client_order.go) を雛形にしてください。要点：
- `Tables()` は所有する全テーブルを列挙する（例: `{"client_order_items", "client_orders"}`）。慣習として子→親の順で書く。`Schema()` で定義したテーブルはすべてここにも列挙する（テストで整合性を検証する）。
- 明細テーブルには `page_id` 列が無いので、洗い替えの削除は**子をサブクエリで先に消す**：
  ```go
  tx.Exec(`DELETE FROM <子> WHERE order_no IN (SELECT order_no FROM <親> WHERE page_id = ?)`, pageID)
  tx.Exec(`DELETE FROM <親> WHERE page_id = ?`, pageID)
  ```
- 親は `order_no` などの自然キーに `ON CONFLICT(...) DO UPDATE` を付ける。

### パターンC: 集計API付き
[plugin_materials.go](../internal/cms/plugin_materials.go) を雛形にしてください。`RouteProvider` を実装し、`Routes()` で `(パス, ハンドラ)` を返すと、`main.go` が自動でルート登録します（コア無変更）。

### 特殊: ページ全体のタグを各行に注入したい
`<m-tag name="部品番号" value="..">` のような「ページに1つ、全行に効く値」は `TagValue(root, "部品番号")` で取得し、各 INSERT に渡します（[plugin_materials.go](../internal/cms/plugin_materials.go) 参照）。

## 5. 動作の仕組み（なぜコアを触らなくてよいか）

- **スキーマ作成**: 起動時に `main.go` が `cms.ApplySchema(db)` を呼び、全プラグインの `Schema()` を実行します。テストは `database.CreateCoreTables(db)` ＋ `cms.ApplySchema(db)` で本番と同じスキーマを再現します。
- **同期**: `SyncIndex` がコア（pages/page_tags）を同期した後、`for _, p := range Plugins()` で各プラグインの `Sync()` を1つのトランザクション内で呼びます。
- **全再構築**: `RebuildDatabase` は `sqlite_master` から**全テーブルをDROP**してスキーマごと作り直し、`data/master` の全HTMLを再同期します（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 8章）。全テーブルをDROPするため、`Tables()` の記載漏れが再構築バグを起こすことはありません。ただし `Schema()` と `Tables()` の整合性はテスト（`TestPluginTablesConsistency`）で検証されるので、所有テーブルは `Tables()` に列挙してください。
- **正本性**: プラグインのテーブルは `data/master` のHTMLから再生成可能でなければなりません（§3の不変条件）。これにより `cms.db` は使い捨て可能で、バックアップはファイルのみで済みます。
- **ルーティング**: `main.go` が `cms.PluginRoutes()` を走査し、`RouteProvider` を実装するプラグインのルートを登録します。

## 6. 検証方法

```bash
go build ./...      # コンパイル（プラグインの init() 登録漏れもここで気付ける）
go vet ./...
go test ./...       # 既存テスト＋自作テスト
```

テストでスキーマを用意する定型（`internal/cms/storage_test.go` 参照）：

```go
database.DB = db
if err := database.CreateCoreTables(db); err != nil { t.Fatal(err) }
if err := ApplySchema(db); err != nil { t.Fatal(err) }
```

手動確認（任意）：サーバを起動し、`/` でページを編集・保存 → 起動ログに `プラグインAPI登録: ...`（API付きの場合）が出る → `data/cms.db` に行が入る。

## 7. AIエージェント向けの厳密手順

このセクションは、AIがこのガイドだけで作業する際の決定論的な手順です。

1. **絶対に編集しないファイル**: `internal/cms/plugin.go`, `internal/cms/parser.go`, `internal/cms/sync.go`, `internal/database/sqlite.go`, `cmd/w-cms/main.go`。これらを編集しようとしたら設計を間違えている。
2. **作るファイルは1つ**: `internal/cms/plugin_<usecase>.go`。§4から最も近いパターン（A/B/C）をコピーして名前を置換する。
3. **`Plugin` の4メソッドを必ず実装**し、ファイル冒頭に `func init() { Register(<plugin>{}) }` を書く。
4. **`Tables()` は `Schema()` で作るテーブルをすべて列挙**（慣習として子→親順）。整合性は `TestPluginTablesConsistency` が検証する。
5. **`Sync()` は必ず「当該ページ分をDELETEしてからINSERT」**（洗い替え）。明細テーブルは `page_id` 列が無い前提で、親のサブクエリ経由で削除する。
6. **属性名の一致を確認**: `Attr(n, "X")` の `X` が、フロント（`web-components.js` の `observedAttributes` とテンプレートのプレースホルダ）と一致しているか。
7. **集計APIが要るときだけ** `RouteProvider` を実装する。`main.go` には触らない。
8. **検証**: `go build ./... && go vet ./... && go test ./...` がすべて通ること。スキーマを使うテストは §6 の定型で用意する。
9. **ドキュメント更新**: [アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) の「2. データベーススキーマ設計」に新テーブルを追記し、[変更履歴.md](変更履歴.md) に1行追記する。
