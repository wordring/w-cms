# 【ガイド】デプロイ・運用

**w-cms** をサーバーに置いて動かす人（運用者）のための手順書です。
設置（デプロイ）の手順と、データを置くディレクトリ（フォルダ）の動作仕様を説明します。

> **この文書の読み方**
>
> - 番号の付いた手順は、上から順に行います。1つの番号に、1つの操作を書いてあります。
> - 「⚠」は、知らないとデータを壊す・失う所です。その手順のすぐ下に置いてあります。
> - 日付（2026-09-07 など）は、その決まりを決めた日や、仕組みを変えた日です。

| やりたいこと | 読む節 |

## 1. サーバー実行時のディレクトリ構成と動作仕様（対策Aの採用）

w-cms は、データを `data` というディレクトリに保存します。
ソースコードの中では、この `data` への道を**相対パス**で書いてあります。
相対パスは、「いまいる場所から見た道」のことです。
そのため、動かしたときの挙動は次のようになります。

- **動作仕様**: `data` ディレクトリは、
  **「実行可能ファイルを実行した時のカレントディレクトリ（作業ディレクトリ）」の直下**に作られます。
  カレントディレクトリは、プログラムを動かすときに「いまいる場所」として扱われるディレクトリです。
- **本番サーバーでの運用方法**: 実行可能ファイルをどこに置いたかに関わらず、
  サービスを起動するときに、作業ディレクトリ（WorkingDirectory）をはっきり指定して動かします。

## 2. サーバー（Linux / systemd）へのデプロイ手順

本番サーバーで w-cms を常時実行（デーモン化）させるための手順です。
systemd は、Linux でプログラムをいつも動かしておくための仕組みです。

### ステップ 1: アプリケーションのビルド

ビルドは、ソースコードから実行ファイル（バイナリ）を作ることです。

1. 開発環境で、動かす先のサーバーの OS（例: Linux）に合わせてビルドし、バイナリを作ります。

   ```bash
   # Linux（AMD64環境）向けにクロスビルドする場合（bash。リポジトリの根で実行します）
   GOOS=linux GOARCH=amd64 go build -o w-cms ./cmd/w-cms
   ```

   PowerShell では、次のように書きます。

   ```powershell
   $Env:GOOS="linux"
   $Env:GOARCH="amd64"
   go build -o w-cms ./cmd/w-cms
   ```

   ⚠ **ファイルを名指し（`cmd/w-cms/main.go`）してビルドしないこと。**
   `main.go` は、同じフォルダの `tls.go`・`listen.go`・`cert_reload.go`・`startup_line.go` などの関数を呼びます。
   拡張の取り付け口 `ext_*_gen.go` も、同じフォルダにあります（取り付け口は、拡張を実行ファイルへ組み込む blank import の1行のファイルです）。
   名指しでは、これらが入りません（2026-09-05 には、拡張が1つも載らないまま起動しました）。
   フォルダ（`./cmd/w-cms`）を指します。

   拡張のフォルダ（`ext/` の下）を足したり外したりしたときは、組み立てる前に `go generate ./cmd/w-cms` を流します（2026-10-20）。
   取り付け口が作り直されます。流し忘れると、試験 `TestExtensionMountsAreGenerated` が落ちます。
   外すのを組み立てのときに選ぶなら、`-tags nomail`（メールだけ外す）・`-tags minimal`（業務の拡張を全部外す）を付けます（[【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md) §9）。

### ステップ 2: サーバーへの配置

1. できた `w-cms` バイナリを、サーバーの任意のパスへ転送します。
   - **バイナリ配置先例**: `/usr/local/bin/w-cms`
   - **データ格納先ディレクトリ例**: `/var/www/w-cms` （ここを作業ディレクトリとします）
2. リポジトリの `assets/` と `config/` と、拡張の画面のファイル `ext/<拡張>/assets/` を、**作業ディレクトリの直下**へ、同じ形のまま転送します
   （例: `/var/www/w-cms/assets/`・`/var/www/w-cms/config/settings.json`・`/var/www/w-cms/ext/toho/assets/`）。
   - w-cms は、画面のファイル（`assets/`）と設定（`config/settings.json`）も、`data` と同じく相対パスで読みます。
   - 拡張の画面のファイル（JS・CSS・HTML）も、作業ディレクトリの `ext/<拡張>/assets/` から読んで配ります（2026-10-20。`internal/cms/ext_scripts.go`）。
     いまあるのは、`ext/comm/assets/`・`ext/comm/contacts/assets/`・`ext/comm/mail/assets/`・`ext/toho/assets/` の4つです。
     ⚠ 転送し忘れても、起動は止まりません。拡張の画面の働き（ボタン・メールの一覧など）が、黙って出なくなります。
   - ⚠ `config/settings.json` が無いと、起動が止まります（ステップ3の「設定の置き場は2つあります」）。
   - 紙（PDF）の書体は、設定 `extensions.toho.pdf_font` に、候補の場所を並べてあります。いちばん前の、在るものを使います
     （2026-10-19 から並べられます。Windows の書体のあとに、Ubuntu の書体の場所も書いてあります）。
     サーバーに日本語の書体が無ければ、入れるか、在る場所を並びに足します。
3. サーバーの上で、データ格納先ディレクトリを作り、適切な権限を付けます。

   ```bash
   # サーバー側で実行
   mkdir -p /var/www/w-cms
   chown -R www-data:www-data /var/www/w-cms
   ```

### ステップ 3: systemd サービスファイルの作成

1. `/etc/systemd/system/w-cms.service` を作り、次のように定義します。

   ```ini
   [Unit]
   Description=w-cms Content Management System
   After=network.target

   [Service]
   Type=simple
   User=www-data
   Group=www-data
   # ★重要: dataフォルダを作成・参照する基準ディレクトリを指定します
   WorkingDirectory=/var/www/w-cms
   # 実行バイナリのパス
   ExecStart=/usr/local/bin/w-cms
   Restart=always

   [Install]
   WantedBy=multi-user.target
   ```

このステップで知っておくことを、4つに分けて書きます。

**設定の置き場は2つあります**

- **秘密・環境依存の設定は環境変数で渡します。**
  環境変数は、プログラムを起動するときに外から渡す、名前の付いた値です。
  - 2026-08-16 に「設定は環境変数のみ」と決めました。設定のためのコマンドラインフラグはありません。
    例外は、証明書を作る `-gencert` だけです（§6.2a。設定ではなく、1度だけの操作です）。
  - 環境変数の一覧表は、[【要求】運用.md](../【要求】運用.md) §3 が正本です。
- ただし、**運用者が育てる設定は `config/settings.json`** に置きます（2026-08-30 に追加）。
  - 置くのは、見出し語の辞書 `vocabulary`（1語につき型と選択肢を1件で持ちます）、
    添付1件の上限 `max_upload_mib`（既定32）、汎用添付の拡張子 `attachment_extensions` などです。
    鍵の全部は、§4.1 に並べてあります。
  - **Git管理の必須ファイル**です。Goコードに既定値はありません（2026-09-07）。
  - ⚠ 起動時に**無ければ、壊れていれば、どちらも起動が止まります**。
  - 詳しくは §4.1・§5 を見てください。

**環境変数を1か所にまとめる**

環境変数を一覧できる場所が欲しい場合は、systemd の `EnvironmentFile=` を使います。

```ini
[Service]
EnvironmentFile=/etc/w-cms/prod.env
```

```bash
# /etc/w-cms/prod.env（root:root 0600 で保護すること。GEMINI_API_KEY 等の秘密が載る）
GEMINI_API_KEY=xxxx
```

**`GEMINI_API_KEY` に置けるキー**

⚠ **`GEMINI_API_KEY` に置けるのは、課金が有効な（＝有料枠の）キーだけです。**

- 無料枠では、送った書類が学習に使われます。
  これは、この機能の許可条件（2026-08-21 決定）に反します。
- 理由と根拠、および「使わない」選択肢は **§7** にあります。

**2インスタンス運用**

業務用とサイト用の2つの w-cms を動かす運用です
（[【要求】w-cmsとは.md](../【要求】w-cmsとは.md) §2・[【要求】運用.md](../【要求】運用.md) §4）。
「インスタンス」は、動いている w-cms の1つ1つのことです。

- ユニット（systemd のサービスの定義ファイル）と環境ファイルを、1組ずつ用意します。
  - `w-cms-gyomu.service` ＋ `/etc/w-cms/gyomu.env`
  - `w-cms-site.service` ＋ `/etc/w-cms/site.env`
- 別サーバーに置くのが基本です。
- 同一ホストに同居させる場合は、`WCMS_ADDR`・`WCMS_DATA_DIR` で、待受とデータ置き場を分けます。
  この2つは、2026-10-14 に実装しました（[【要求】運用.md](../【要求】運用.md) §3 の環境変数の表・§7）。
  - `WCMS_ADDR` は、待受のアドレスです（例 `127.0.0.1:8081`）。
    渡さなければ、いままでと同じです。平文は `:8080`、TLS のとき（証明書と鍵がそろったとき）は `:8443` です。
    渡したら、TLS のときもその値で待ち受けます（`cmd/w-cms/listen.go`）。
  - `WCMS_DATA_DIR` は、`data` の場所です。渡さなければ、作業ディレクトリの `data` です（`internal/database/datadir.go`）。
    本文・ゴミ箱・3つのDB・証明書・メールの保管は、どれもここの下に置きます。
  - 同居させるときは、2つのインスタンスに、違う `WCMS_ADDR` と違う `WCMS_DATA_DIR` を渡します。
  - 効いている値は、起動ログの「有効な設定」の1行に出ます（「待ち受け …」「データ …/」）。

### ステップ 4: サービスの起動と有効化

1. systemd に、設定を読み込み直させます。

   ```bash
   # 設定の再読み込み
   sudo systemctl daemon-reload
   ```

2. サービスを起動します。

   ```bash
   # サービスの起動
   sudo systemctl start w-cms
   ```

3. サーバーを起動したときに、自動で起動するようにします。

   ```bash
   # サーバー起動時の自動起動を有効化
   sudo systemctl enable w-cms
   ```

4. 動いているかを確かめます。

   ```bash
   # ステータスの確認
   sudo systemctl status w-cms
   ```

この設定により、`data/cms.db` や `data/master/` は、常に `/var/www/w-cms/data/` 配下に作成・保存されます。
そのため、安全に運用できます。

## 3. 開発環境（会社・自宅）での注意点

- **ローカル実行時**: §1 と同じです。
  `go run ./cmd/w-cms` を実行したカレントディレクトリ（通常はプロジェクトルート）の直下に、`data` が作られます。
- **Gitの除外設定**:
  ローカルで作られたデータベースやアップロード画像などの実データは、`.gitignore` で Git の管理対象外にしてあります。
  そのため、会社と自宅の間で、勝手に上書き同期されることはありません。同期されるのはソースコードだけです。

## 4. バックアップと復元（ファイルベース）

w-cms は、次の設計です。

**「`data/master/` 配下のファイル群（HTML本体・権限サイドカー・`versions/` の版・`files/` の添付）が唯一の正データであり、`data/cms.db`（SQLite）は派生インデックスにすぎない」**

言葉の説明です。

- 正データは、これが本物（正本）だ、というデータです。
- 権限サイドカーは、本文の横に置く、権限などの属性のファイルです。
- 派生インデックスは、正データから作り直せる、検索用の索引です。

データベースは、いつでもファイルから再生成できます。
そのため、バックアップと復元はファイルだけを対象にすればよく、DBファイルを対象に含める必要はありません。

> [!IMPORTANT]
> **不変条件**: データベースには「ファイルから再生成できないデータ」を一切持たせてはいけません。
> 新しいプラグインを追加する際も、DBの全カラムが `data/master` のHTMLから `SyncIndex` で再生成可能であることを、
> 必ず保証してください。
> この不変条件が、ファイルのみのバックアップ戦略の前提です。

### 4.1. バックアップ手順

**対象（必須）**

- `data/master/` ディレクトリ全体。正データです。
  中身は、HTML本体・権限サイドカー・`versions/` の版・`files/` の添付（PDF・画像・汎用ファイル）です。
- **`data/auth.db`**（ユーザー・グループ・セッション・監査ログ等の認証情報）。
  ⚠ **ファイルから再生成できないため、必ずバックアップします。**
- **`config/settings.json`**（設定の正本）。
  ⚠ **ファイルから再生成できないため、必ずバックアップします。**
  - 住人（書ける設定の鍵）は10個です。`internal/cms/settings.go` の `Settings` 型で数えました。
    1. 見出し語の辞書 `vocabulary`
    2. 表ごとの例外 `table_vocabulary`（2026-09-25）
    3. 運用者が足す表の形式 `vocab_formats`（2026-09-20）
    4. 添付上限 `max_upload_mib`
    5. 汎用添付の拡張子 `attachment_extensions`
    6. 文字の置き換え `char_folding`
    7. 社名から落とす法人格の表 `company_forms`（2026-09-20）
    8. 添付を書き換えられないページの題 `attachment_readonly`
       - 「📝 ローカル編集」で上書きさせない所です。
       - もとの名前は `webdav_readonly` です。
    9. オートコンプリートの数え方 `autocomplete`（2026-10-19）
       - 鍵は `min_value_count`・`min_share`・`min_rows`・`max_values`・`idle_minutes`・`skip_types` です。
       - 無ければ、候補を数えません。
       - 数えた結果は、派生のデータ `data/autocomplete.json` に置きます。
    10. **拡張の節 `extensions`**（2026-09-15 にトップから移しました）。
        - いまは、東邦の業務の `extensions.toho` です。
        - 番号のタグ・PDFのフォント・会社の情報（差出人）・部材の種類・紙の見出しと列・見積の利益率とタグ・税率などが入ります。
          鍵は `ext/toho/settings.go` にあります。
        - 装置の段 `machine_stages` は、2026-09-29 に無くなりました。
  - いまのリポジトリの `config/settings.json` には、`vocab_formats` を除く9つが書いてあります。
  - DB に置かないのは、まさにこのためです。`cms.db` は、再構築で全テーブルが消えます。
  - ⚠ **無ければ起動が止まります。** Goコードに既定値は無く、埋める材料が無いためです（2026-09-07）。
  - ただし、Git管理の必須ファイルなので、`git checkout` で**リポジトリの状態までは戻ります**。
    戻らないのは、**運用者がこの環境で足した語・変えた値**だけです。

**対象（推奨）**

- **`data/trash/`**。削除したページの唯一の写しです。
  - 削除は物理削除ではなく、ここへの移動です。
  - 復元UIは未実装です。戻すときは、手で `data/master` へ戻して再構築します。
  - ⚠ 失うと、削除の取り消しができなくなります。

**対象外**

- `data/cms.db`（派生インデックス）。
  バックアップしてもかまいませんが、必須ではありません。復元時は再生成されます。
- **`data/tables.db`**（2026-09-25 から）。
  本文の表を、キャプションの名前の表として写したものです。
  これも派生で、再構築で作り直されます（[【考察】DBの日本語化.md](../考察/【考察】DBの日本語化.md)）。

**取り方**

- `data/master` 配下のファイルは、稼働中でも、ファイルコピーや rsync でそのまま取得できます。
  追記・上書きのみで、参照整合が壊れないためです。
- `auth.db` は SQLite です。整合の取れたコピーが必要なら、停止中に取得するか、`VACUUM INTO` 等を使います。

```bash
# 例: 正データと認証DBをまとめてバックアップ
tar czf wcms-backup-$(date +%Y%m%d).tar.gz data/master data/auth.db config/settings.json
```

### 4.2. 復元手順

1. バックアップしたものを、元の場所へ展開します。
   - `data/master/`（正データ）
   - `data/auth.db`。戻さないと、ユーザー・セッションが失われます（§6.3）。
   - `config/settings.json`。無いと、起動が止まります。
     リポジトリの版でよければ、`git checkout` でも戻ります。
   - `data/trash/`（取ってあれば）
2. アプリケーションを起動します。
3. **起動時の自動リビルド**: 何もしなくても、w-cms が起動時にデータベースを全再構築します（`RebuildIfNeeded`）。
   - 自動で走るのは、`pages` テーブルが空で、かつ `data/master` に HTML ファイルが存在する場合です。
     `pages` が空なのは、DB が無い・新規作成された状態のときです。
   - 前回の再構築が途中で止まった印 `rebuild_state` が残っている場合も、やり直します（`pages` が空でなくてもです）。
   - 表の写し `data/tables.db` が今の作り方で作られていない場合も、やり直します。
   - これとは別に、テーブルの定義がコードの宣言とずれているときも、起動時に再構築します
     （`cmd/w-cms/main.go` の `DriftedSchemaTables`）。
   - したがって、復元は「ファイルを戻してアプリを起動するだけ」で完了します。
4. 自動リビルドが走らない状況（既存DBがある場合など）で、手動で再構築したいときは、
   `POST /api/rebuild-db` を呼び出します。

## 5. データベースの全再構築（リビルド）

`RebuildDatabase`（`POST /api/rebuild-db` から呼ばれる）は、ファイル群を正として、
データベースを完全に作り直す処理です。

### 5.1. 動作（全テーブルDROP方式）

1. 現在DBに存在する全テーブルを `sqlite_master` から列挙し、すべて `DROP TABLE` します。
   - 廃止されたプラグインの残存テーブルなど、スキーマのdrift（コードと DB の形のずれ）も含めて、完全に消去します。
   - 例外は、再構築の進行状況を残す1行テーブル `rebuild_state` だけです。
     再構築の最中に、自分を消せないためです。
   - 表の写し `data/tables.db` も、ここで空にします（`ResetTablesDB`）。ページを入れ直すときに、作り直されます。
2. コアテーブル（`pages` / `page_perms`）と、登録済み全プラグインのテーブルを作り直します
   （`CreateCoreTables` ＋ `ApplySchema`）。
   - 汎用索引もプラグインとして登録されているので、ここで作り直されます。
   - いま、その1プラグイン（`vocabIndexPlugin`）が **`vocab_index` と `page_tags` の2つ**を持ちます（`Tables()`）。
     可変タグは `page_tags`、業務ブロック（表・機能見出し）は `vocab_index` です。
   - **振り分けは書き手1か所**（`insertVocabEntry`）です。読む側は、表を選ぶだけです。
   - 経緯: **`page_tags` は 2026-09-13 に復活しました。**
     2026-08-30（D-1 の第一歩）に、いったん `vocab_index` へ吸収しました。
     D-1 は、硬いドメイン表の全廃です。全廃が済んだのは、翌 08-31 です。
     しかし、アドレス帳でタグが索引の84%を占め、「読む側で `data_type='tags'` を足す」規律が守られませんでした。
     そのため、利用者の決定で分離し直しています
     （正本は [【考察】タグ表と業務ブロック表の分離.md](../考察/【考察】タグ表と業務ブロック表の分離.md) §8）。
3. `data/master` 配下のすべての `.html` を走査し、`SyncIndex` で再同期します。

> [!NOTE]
> **再構築の先頭で `config/settings.json` を読み直します。**
> 語→型の推論辞書（見出しの言葉から型を決める辞書）が、そこにあるためです。
> 「辞書へ語を足して再構築する」が**再起動なしで反映される**のは、この読み直しのおかげです。
>
> 2026-08-30 利用者:「運用中に増やしてDB再構築します」
>
> - 設定が**壊れていると**、**再構築はエラーで止まります**。
>   既定値で黙って続けると、足した語が消えたまま、索引だけが作り直されるためです。
> - **ただし「ファイルが無い」ときは止めません。** 読み込み済みの設定のまま続けます
>   （`LoadSettings` が `os.ErrNotExist` と「既に読み込み済みか」で見分けます）。
> - 起動時とは**扱いが違う**のは、再構築が運用中に走るからです。
>   ここで語彙を空にすると、索引が静かに痩せます。
>   設定を消したことより、**集計が黙って変わるほうが害が大きい**、という判断です。

> [!NOTE]
> DBファイル自体は削除しません。
> SQLite の接続を開いたまま、全テーブルを DROP・再作成します。
> こうすることで、次の2つを避けています。
>
> - Windows でのファイルロック（オープン中のファイルは削除できない）
> - リビルド中の、他リクエストとの競合
>
> リビルドは冪等です（何度やっても同じ結果になります）。
> 途中で失敗した場合は、再実行すれば回復します。正データはファイル側にあるので、失われません。

## 6. 認証の運用

設計は [認証認可設計.md](../旧文書/認証認可設計.md) にあります。
ページ単位の認可（Unix風 read/write・owner/group/other）と、
匿名公開（`public`＋パスゲート）まで実装済みです。

### 6.1. 初期管理者の作成

初回起動時、`users` が空のときだけ、環境変数から管理者を作成します。
作成したあとは、環境変数を外してください。

```bash
WCMS_ADMIN_USER=admin WCMS_ADMIN_PASSWORD='強いパスワード' ./w-cms
```

systemd で運用する場合は、次の手順が安全です。

1. `[Service]` に、一時的に `Environment=` を記述します。
2. 初回起動します。
3. 作成ログを確認します。
4. 該当行を削除します。
5. `daemon-reload` して、再起動します。

### 6.2. HTTPS（必須）とリバースプロキシ

インターネット公開のため、**TLS/HTTPS は必須**です。

リバースプロキシは、w-cms の手前に置いて、外からの通信を受けて w-cms へ渡すサーバーです。
Caddy / nginx 等のリバースプロキシで TLS終端（HTTPS の暗号を解く役）とレート制限を行い、
その背後で w-cms（`:8080`）を動かす構成を推奨します。

- セッションCookie は、既定で `Secure` 属性付きです（HTTPS でのみ送信されます）。
  プロキシで TLS終端して、アプリへは HTTP で届く構成でも、ブラウザ↔プロキシ間が HTTPS なら問題ありません。
- ローカルで HTTP（`http://localhost:8080`）のまま動作確認したいときだけ、
  `WCMS_SECURE_COOKIES=0` で `Secure` 属性を外せます。
  ⚠ **本番では設定しないでください。**

⚠ **プロキシ側で CSP を上書き・除去しないこと**（2026-08-19 に strict 化）。

CSP（Content-Security-Policy）は、ページが読み込んでよいスクリプトやスタイルを、ブラウザへ伝えるヘッダです。

- アプリは、全レスポンスへ次の CSP を付けます
  （[middleware.go](../../internal/auth/middleware.go) の `CSPProtect`）。

  `default-src 'self'; script-src 'self'; style-src 'self'; object-src 'self'; base-uri 'self'; frame-ancestors 'self'`

- この CSP は `'unsafe-inline'` を含みません。
  そのため、**プロキシやWAFがインラインの `<script>`／`<style>` を注入する機能
  （エラーページの差し込み・計測タグ・デバッグバナー等）を有効にすると、そのスクリプトはブラウザでブロックされます**。
- アプリ本体は、外部リソースを一切使いません。素の構成なら、追加設定は不要です。
- 方針の経緯は [本文サニタイズ設計.md §6](../旧文書/本文サニタイズ設計.md) にあります。

### 6.2a. アプリ自身で TLS 終端する（LAN内・自己署名）

社外へ出さず LAN 内で使うときは、リバースプロキシ無しで、**アプリ自身が HTTPS を話せます**（2026-09-07）。

**HTTPS で起動する手順**

1. 自己署名の証明書と鍵を作ります。

   ```bash
   go run ./cmd/w-cms -gencert      # 自己署名の証明書と鍵を data/tls/ に作る（1度だけ）
   ```

   ⚠ `data/tls/` を作り直すと、全PCで証明書の入れ直しになります（手順4）。

2. 証明書と鍵の場所を、環境変数で渡します。

   ```bash
   export WCMS_TLS_CERT=data/tls/cert.pem WCMS_TLS_KEY=data/tls/key.pem
   ```

3. 起動します。

   ```bash
   go run ./cmd/w-cms               # → https://localhost:8443（:8080 は開かない）
   ```

4. 証明書を、**各PCの信頼ストアへ1度だけ入れます**
   （Windows は、管理者 PowerShell で `Import-Certificate`）。

   ⚠ `-gencert` を走らせるたびに別の証明書ができるので、
   **信頼させたものとサーバーが出しているものの指紋が一致しているか**を、照らし合わせること。
   指紋は、証明書を見分けるための短い印です。

証明書と鍵のファイルを差し替えたときは、起こし直さなくても、次の接続から新しいものを使います（2026-10-19・`cmd/w-cms/cert_reload.go`）。
ファイルの更新時刻を見るのは、多くても10秒に1回です。証明書と鍵の組が合わないあいだ（写している途中など）は、古いものを使い続けます。

**メール**

- メール送受信を使うなら、`WCMS_MAIL_CLIENT_ID`・`WCMS_MAIL_TENANT_ID` も要ります。
  無いと、起動はしますが、「メール送受信: 設定待ち」になります。
- 環境変数の一覧は [【要求】運用.md](../【要求】運用.md) §3 にあります。

**詳しい説明のある文書**

- 指紋の照合の詳細は、
  [【考察】添付をローカルアプリで編集する.md](../考察/【考察】添付をローカルアプリで編集する.md) にあります。
- 社外公開時の構成は、[【考察】社外公開とHTTPSの構成.md](../考察/【考察】社外公開とHTTPSの構成.md) にあります。

### 6.2b. 添付をローカルのアプリで編集する（常駐ヘルパー w-cms-edit・2026-09-29）

常駐ヘルパーは、各 PC に入れておく小さなプログラムです。
ファイル表示の「📝 ローカル編集」を押すと、このヘルパーが次のことをします。

- そのファイルを手元へ落として、既定のアプリで開きます。
- **保存（Ctrl+S）するたびに数秒で w-cms へ入れます**（前の中身は版に残ります）。

この形に決めた経緯は、[【考察】添付をローカルアプリで編集する.md](../考察/【考察】添付をローカルアプリで編集する.md) にあります。

**入れる手順**

1. **組み立て**（開発の機械で1回）:
   `go build -ldflags "-H=windowsgui" -o w-cms-edit.exe ./cmd/w-cms-edit`
   - 黒い窓を出さない組み立てです（Windows だけ）。
   - 組み立てたものは、デスクトップの `w-cms\道具\w-cms-edit\` に置いてあります。
2. **各 PC で1回**: `w-cms-edit.exe -install https://<w-cms のホスト>:8443`
   - アドレスは、**ブラウザで開いているのと同じアドレス**にします。カンマで区切ると、複数書けます。
   - 利用者ごとの登録（HKCU）なので、管理者は要りません。
   - 消すときは `-uninstall` です。

   ⚠ **exe を別の場所へ動かしたら登録し直します**（登録が exe の場所を覚えるためです）。

   ⚠ **登録するアドレスは証明書の名前に入っているもの**にします。
   - 入っている名前は、`localhost`・ホスト名などです。
     `certutil -dump data\tls\cert.pem` の「DNS Name」「IP Address」で見られます。
   - 入っていない IP で開いた画面から押すと、ブラウザは警告を越えて開けても、ヘルパーは証明書の確かめで落ちて繋がりません。
     記録.log に「w-cms に繋がりません」と出ます。

**前提**

- その PC で、w-cms の証明書を信頼していること（§6.2a）。
- 初めて押すと、ブラウザが「w-cms-edit を開きますか」と聞きます。

**うまく動かないとき**

- ⚠ **押しても何も起きない＝その PC に登録が無い**、ということです。
  ブラウザは、知らないリンクを黙って捨てます。
  - w-cms 側には、監査（誰が何をしたかの記録）の `local-edit.start` だけが残ります。
  - ヘルパーがファイルを落としに来れば、`local-edit.write`（保存のたび）が続きます。
  - 2026-10-04 に、09-29 から6回押されて、一度も開いていなかったのが分かりました。
- **書けない所**（通信箱の下・権限の無いページ）のファイルは、読み取り専用で開きます。
- **ほかの人が先に書き換えていたら、上げずに止まります。** 手元のファイルの場所を知らせます
  （`%LOCALAPPDATA%\w-cms-edit\…`・7日で片付きます）。
- 記録は `%LOCALAPPDATA%\w-cms-edit\記録.log` にあります。
- 鍵は12時間で切れます。w-cms を再起動しても切れます。そのときは、画面から開き直します。

### 6.3. 復元時の注意

復元の対象と手順は、§4.1・§4.2 のとおりです。

⚠ `auth.db` を戻し忘れると、ユーザー・セッションが失われます。
その場合は、初期管理者の再作成（§6.1）が必要になります。

## 7. 発注書PDFの外部AI送信（Gemini）と `GEMINI_API_KEY` の運用条件

w-cms には、**書類そのものを社外＝Google の Gemini へ送信する**機能があります。
いまの送るきっかけは5つで、§7.1 に並べてあります。もとになった機能は、次の2つです。

- 発注書PDFの明細抽出
  （[【要求】タグと表.md](../【要求】タグと表.md)、[アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) 5章）。
  この API（`/api/parse-pdf`）は、2026-10-01 に片付けました。いまはありません。
- 添付PDFの発注書判定→案件ページ生成
  （2026-09-01。[【考察】通信記録処理.md](../考察/【考察】通信記録処理.md)）。
  いまの「🤖 解析」です。

送ってよいかは 2026-08-21 に決着し、**条件つきで可**となりました。
その条件はコードでは守れないため、運用条件としてここに置きます。

> [!WARNING]
> **`GEMINI_API_KEY` には、課金が有効な（＝有料枠の）APIキーだけを設定してください。**

理由は次のとおりです。

- **Gemini API の無料枠は、送った入力データを Google の製品改善（モデルの改良）に使います。**
  使わせないためには、課金が有効なキーで呼ぶ必要があります。
- この機能は「**学習に使用されないという条件で**」使うものとして許可されました
  （2026-08-21 決定・決定者は利用者）。原文は次のとおりです。

  > 2026-08-21 利用者:「GoogleやMicrosoftにはすでに書類が置いてあるので、大丈夫です。
  > 学習に使用されないという条件で使用しています」

  「無料枠だと学習に使われる」旨の追加確認に対する回答は、「**有料枠で使います**」でした。
- つまり、**課金の有効化はこの許可の前提条件**です。
  無料枠のキーを挿せば、取引先の書類が学習に使われ、**合意違反になります**。
- **コードからは判定できません。**
  - Gemini の呼び出しは、[gemini.go](../../internal/cms/gemini.go) の `GeminiGenerateBlobs` に1本化されています
    （`GeminiGenerate` もこれを呼びます）。
  - この関数は、環境変数を読んで、そのキーで送るだけです
    （`os.Getenv("GEMINI_API_KEY")`・`option.WithAPIKey(apiKey)`。2026-10-01 に行番号をやめました）。
  - 有料か無料かは、アプリからは見えません。**運用で担保するしかありません**。
  - キーの発行・差し替え・環境ファイル更新のたびに、課金が有効なプロジェクトのキーであることを確かめてください。

### 7.1 何が、いつ社外へ出るか

**送るきっかけは人の操作だけ**です。
どれも、押した直後にだけ送ります（人間ゲート型＝人の操作を関門にする形）。

1. 📎添付の「🤖 解析」と、ZIP の「🤖 中のPDFをまとめて解析」。
   - 送るもの: PDF と表計算（`.xlsx` は文字にして送ります）。
   - 実装: ボタンは、通信記録の「記録の箱」の中に、サーバーが描きます（2026-10-20 夕から。`ext/toho/record_sections.go` の `analyzeSectionHTML`）。
     押すと、[ext/toho/assets/toho.js](../../ext/toho/assets/toho.js) の `runAnalyze`・`analyzeOne` → `POST /api/analyze-attachment` と進みます。
2. メールの記録の「作るページ」で「案件ページ」か「部材見積依頼の返事ページ」。
   - 送るもの: **メールの件名・差出人・日付・本文**。
   - 同じ欄の「加工製品ページ」「見積依頼ページ」「部材見積依頼の返事ページ（手で書く）」は、Gemini を呼びません
     （後の2つは 2026-10-19 に足しました。`ext/toho/quote_case.go`・`rfq_reply_page.go` の `makeRFQReplyByHand`）。
   - 実装: 欄は「記録の箱」の中に、サーバーが描きます（`ext/comm/record_box.go` の `recordMakeHTML`）。
     押すと、[ext/comm/assets/comm.js](../../ext/comm/assets/comm.js) の `makeFromRecord` → `POST /api/record-make`、
     [ext/toho/analyze_mail.go](../../ext/toho/analyze_mail.go) の `mailForJudgment`。
     部材見積依頼の返事は、`ext/toho/rfq_reply_page.go` の `judgeRFQReplyMail` です（2026-10-05）。
3. 整理の「🤖 中身を比べる」。
   - 送るもの: 2つの図面のPDF。
   - 実装: `POST /api/compare-drawings`、[ext/toho/filing_duplicate.go](../../ext/toho/filing_duplicate.go)
4. 部材見積依頼書ページの「🤖 返事を読む」（2026-10-05）。
   - 送るもの: 選んだ返事のファイル（PDF・画像。18MB まで）か、返事のメールの本文。
     部材見積依頼明細表の行の一覧（何の値段か）も、指示の文に入れて送ります。
   - 実装: `POST /api/rfq/read-reply`、`ext/toho/rfq_reply.go` の `RFQReadReplyAPIHandler`
5. ワンノートの移植の道具（`tools/onenote/build`）。職場で人が流します。
   - 送るもの: 図面のPDF・画像。

**送信されないもの**

- **PDFを添付（ドロップ）しただけでは送信されません。**
  `/api/upload-pdf`・`/api/upload-file` は、サーバー内の `files/` へ保存するだけです
  （[pdf_handler.go](../../internal/cms/pdf_handler.go) の `UploadPDFHandler`）。
- **通信箱への `.eml` の取り込みも Gemini を呼びません**（[ext/comm/intake.go](../../ext/comm/intake.go)）。
  添付の解釈は、ボタンからだけです。
  当初あった到着時の自動判定は、2026-09-01 にボタン起動へ一本化しました。

**送られる中身**

- **送られるのは中身全体**です。
  - PDF は、ファイルを丸ごと読みます（`analyze_pdf.go` の `loadPDFForAnalysis`）。
    `application/pdf` の Blob（ひとかたまりのデータ）として渡します。
  - 表計算とメールは、文字にして渡します。
  - どれも、それぞれのプロンプト（AI への指示の文）とともに、
    `gemini-3.5-flash`（[gemini.go](../../internal/cms/gemini.go) の `geminiModelName`）へ渡します。
  - 取引先名・品番・単価・数量が載った書類そのものが、社外へ出ます。
- **どの API も `ext/toho` の持ち物**です。
  そのため、`-tags minimal` のビルドでは、**社外へ出る経路そのものがありません**。

**出せる添付**

- **出せる添付は名前の関門を通ったものだけ**です。
  - `/api/analyze-attachment` は、`cms.SafeAttachmentName` に `.pdf`・`.xlsx` を渡します。
    ZIP の中身は、取り込みのときに1つずつ添付になっています。
  - **名前の関門はコアの1箇所**です
    （[pdf_handler.go](../../internal/cms/pdf_handler.go) の `SafeAttachmentName`）。
    置く側と送る側が、同じものを通ります。
  - そのため、本文 `<id>.html`・権限サイドカー `<id>.meta.json` の名指し拒否が、そのまま効きます。
  - ⚠ **送る側が自前の名前検査を書くと、かつての非対称**（置く側は守られ、送る側だけ素通し）**が復活します**。
    見張りの試験（後戻りを見つける試験）は `ext/toho/analyze_name_guard_test.go` です。
- 「🤖 中身を比べる」が送るのは、図面ブロックのファイル表示が指す添付で、見る人が読めるものだけです。
- 「🤖 返事を読む」が送るのは、見る人が読めるページの添付（PDF・画像）か、そのページのメールの本文だけです。

**ページが作られる時機**

- **`/api/analyze-attachment` と、メールの「案件ページ」「部材見積依頼の返事ページ」は、その場でページを作ります。**
  保存操作を待ちません。取り消しは、ページ削除（ゴミ箱への移動）です。
- 「🤖 中身を比べる」は、答えを見せるだけです。
- 「🤖 返事を読む」は、単価の案を表で見せるだけです。書き込むのは、人が案を直して押したときです。

**この節を直した記録**

- **2026-09-16 に、この節の行番号を関数名へ置き換えました。**
  - app.js の番号が実際より400行ずれていました（2873 → 3265）。
    **数字が古いことに気づく手立てが、読む側にありません**。関数名なら、grep で当たります。
  - 同日に、`/api/parse-pdf` の実装が `internal/cms/pdf_handler.go` から **`ext/toho/parse_pdf.go`** へ移りました。
- **2026-10-01**: 受発注ブロックの「🤖 PDFから明細を解析」（`/api/parse-pdf`）は、**API ごと片付けました**。
  - ボタンを出す形式（`File` を宣言する形式）が無くなり、押す道が無かったためです。
  - 上の一覧は、この日に今の形へ書き直しました。

### 7.2 この機能を使わない選択肢

- **`GEMINI_API_KEY` を設定しなければ、PDFは一切送信されません。**
  - `GeminiGenerateBlobs` は、キーが空なら、Gemini クライアントを作る前に `ErrNoGeminiKey` で戻ります
    （[gemini.go](../../internal/cms/gemini.go)）。
  - **PDFのファイル読み込み自体はその前に済んでいます**（2026-09-01 の切り出しで順序が変わりました）。
    サーバー内のメモリに載るだけで、外へは出ません。
- ただし、**解析ボタン自体は消えません**。
  サーバーはキーの有無を配らないので、画面には知りようがないためです。
  - 押すと、「サーバーに GEMINI_API_KEY 環境変数が設定されていません。設定してから起動し直してください。」という内容が、
    トースト（画面に短く出る知らせ）で表示されるだけです。
  - 実装: 知らせの文は `ext/toho/handler_gate.go` が返します。画面で出すのは、[ext/toho/assets/toho.js](../../ext/toho/assets/toho.js) の `analyzeOne` と、[ext/comm/assets/comm.js](../../ext/comm/assets/comm.js) の `makeFromRecord` です
    （2026-10-01 に行番号を関数名へ直しました。2026-10-20 に、どちらも `assets/app.js` から拡張の JS へ移りました）。
  - 機能ごと隠す・無効化するスイッチは、**未実装**です。
- 明細表は、通常のエディタ操作で手入力できます。
  そのため、キーを配らないまま、受発注ブロックを運用できます（AI解析は入力の補助にすぎません）。
- キーを配る場合、`GEMINI_API_KEY` は秘密情報です。
  §2 ステップ3 のとおり、`EnvironmentFile=`（`root:root 0600`）へ置きます。
  ユニットファイルやリポジトリへ直書きしないでください。

## 8. 運用を始めたあとにコードを直すとき（2026-09-28）

> 利用者:「実際にサーバーで運用を始めてから、データを保護しながらコードの改良を進めることは出来ますか？」

できます。

- 正本は、`data/master/`（本文のファイル・版・添付）と `data/auth.db`・`config/settings.json` だけです。
- DB は派生です（§4・§5）。
- そのため、**コードを入れ替えてもデータはそのまま**です。

守るのは、次の5つです。

1. **本番と開発を分ける。**
   - 本番は運用の機械（FAX＋APサーバー機）、開発は職場・自宅の機械です。
   - 開発で試すときは、**本番の写し**（`data/master`・`data/auth.db`・`config/settings.json`）を、
     開発の機械へ持ってきて使います。

   ⚠ **E2E は本番に向けて流さない。**
   E2E は、画面を自動で操作して、端から端まで確かめる試験です。
   多くの E2E は、本物の置き場（部材発注・受注など）の上で動き、ページを作って消します。
   2026-09-28 に、職場の開発データで、臨時部材表に試験の行が残るのを何度も踏みました。

2. **入れ替える前にバックアップ**（§4.1）。手順は次のとおりです。
   1. バックアップします。
   2. 止めます。
   3. 実行ファイルを入れ替えます。
   4. 起動します。
   5. **起動時刻と実行ファイルの更新時刻を突き合わせます。**
   6. 画面で確かめます。

   戻すときは、前の実行ファイルへ戻します。
   本文の形を変える変更だったら、バックアップのデータも一緒に戻します。

3. **本文を書き換える変更は、写しで下見してから本番へ。**
   - 本文の形を変える（表を節で包む・キャプションを外す など）ときは、道具で一度に移します（下見 → 適用）。
   - **版が残る道**を通します。
     - Go の中から書くときは、`cms.RewriteBody` です。
       ページごとの書き込みのロック（`cms.LockPageBody`）の中で、読んで・変えて・書きます。
     - 外の道具から書くときは、`/api/lock` → `/api/save` → `/api/unlock` です
       （手本は `tools/templates.js`）。
       この3つの API は、道具のために残してあります。画面は、2026-10-12 から使いません。
   - ⚠ **本文のファイルを、直に書き換えません。**
     ロックの外で書くと、人の保存（`POST /api/sync`）と重なったときに、片方が消えます。版も残りません。

   **人が開いているページについて**（2026-10-12 から）

   - 2026-10-12 に、編集モード（ページ単位の編集ロック）をやめました。
     画面は編集権を握らないので、「人が編集中かどうか」を、ロックでは見分けられません。
   - 人が開いているページへ `cms.RewriteBody` で書いても、人の書きかけは消えません。
     その人の画面には、知らせが出ます。
     同じブロックを書きかけていれば、そのブロックの上に、両方の版が並びます。
   - 道具が `/api/lock` で編集権を握っているあいだだけは、鏡のボタンなどの機械の書き込みが断られます（`editlock.RefuseWhileEditing`）。
     道具が握るのは、保存の一瞬です。
   - 2026-09-28 の手直しは、ロックを取れたときだけ書きました。当時は、画面が編集ロックを握っていました。

4. **DB の形を変えるのは気にしなくてよい。**
   - `cms.db`・`tables.db` は、再構築で作り直せます（起動時に、必要なら自動で走ります）。
   - 気にするのは、正本（本文のHTMLの形・サイドカー・設定の鍵）だけです。

5. **設定（`config/settings.json`）を本番で変えたら、リポジトリにも入れる。**
   Git 管理の必須ファイルなので、入れずに `git pull` すると食い違います。

「データの初期化」（管理画面の開発メニュー）は、2026-10-14 に外しました（API `/api/admin/reset` も消しました）。
2026-09-16 に、押した覚えのない初期化が起きています（引き継ぎの罠の節）。

## 9. パソコンで実運用を始め、あとでサーバー機へ移す（2026-09-29）

> 利用者:「吸い出したワンノートの情報を当面パソコンで実運用し、そのデータをサーバーでの実運用に持ち越すことはできますか？」

できます。

- w-cms の正本は、`data\` の中のファイルだけです（§4）。
  **止めて写して、同じ版で起動するだけ**です。
- **ページ番号は変わりません。** 次のものが、そのまま使えます。
  - 弊社品番（＝ページ番号）
  - 参照（`ページ番号-ブロックID`）
  - 版の履歴
  - ワンノート移行の `製造の記録.json`（ワンノートのページ → w-cms のページ番号）

### 9.1 何が移るか

| 置き場 | 中身 | 移すか |
|---|---|---|
| `data\master\` | 本文・版・添付・権限サイドカー（**正本**） | **必ず** |
| `data\auth.db` | 利用者・グループ・セッション・監査ログ | **必ず**（再生成できない） |
| `data\trash\` | 削除したページ（唯一の写し） | 移す |
| `data\mail\` | メールのサインイン（トークン） | 移す（使えなければサーバー機でサインインし直す） |
| `data\tls\` | この機械の名前で作った証明書 | **移さない**。サーバー機で作り直す（9.3） |
| `data\cms.db`・`data\tables.db` | 検索用の索引（派生） | 移さなくてよい。起動時に本文から作り直される（§4.2） |
| `config\settings.json` | 設定（Git 管理） | リポジトリと同じ版で届く。**本番で変えた値はリポジトリにも入れておく**（§8-5） |
| 秘密の設定（`w-cms.env` の中身） | メールのアプリの ID・Gemini のキーなど | サーバー機にも置く（リポジトリには入れない・値をチャットに出さない） |

### 9.2 パソコンで実運用するあいだ守ること

1. **データを消さない。** 管理画面の「データの初期化」は、2026-10-14 に外しました（§8 の末尾）。
2. **E2E を実運用のデータに向けて流さない**（§8-1）。
   - E2E はページを作って消し、本物の置き場（部材発注・受注など）も触ります。
   - 試すのは、開発の機械（家のパソコン）か、**写したデータで動かす別の w-cms** です。
3. **毎日 `data\` の控えを取る**（§4.1）。止めて写すのが確実です。

   ⚠ 置き場には、客先の情報が入ります。控えの置き場所は、運用者が決めます。

4. **コードを直すときは §8 の手順**で行います
   （バックアップ → 止める → 入れ替える → 起動 → 起動時刻と実行ファイルの時刻を突き合わせる）。
5. 使う人がいるあいだは、**パソコンを止めない**（スリープさせない）。
   ブラウザと、ローカル編集のヘルパーの登録（§6.2b）は、**このパソコンのアドレス**を指します。

### 9.3 移す手順

1. **サーバー機を用意する。** パソコンと**同じ版**（同じコミット）の w-cms を置きます。
   - 要るのは、実行ファイル・`assets\`・`config\`・拡張の画面のファイル `ext\<拡張>\assets\` です（§2 ステップ2）。
   - リポジトリを取ってきて組み立てるのが確実です:
     `git clone` → `git checkout <パソコンと同じコミット>` → `go build -o w-cms.exe ./cmd/w-cms`
   - 秘密の設定を置きます。
2. **証明書を作る。** サーバー機で `w-cms.exe -gencert` を実行します（`data\tls\` に作られます）。
   - 使う PC すべてに入れます。
   - **指紋を照らし合わせます**（§6.2a）。
3. **移す日**:
   1. 使う人に知らせます。
   2. **パソコンの w-cms を止めます。**
   3. `data\master`・`data\auth.db`・`data\trash`・`data\mail` を、サーバー機の `data\` へ写します。
      `data\tls` は、サーバー機で作ったものを使います。
4. **サーバー機で起動する。**
   `cms.db` を写していなければ、起動時に本文から索引を作り直します（§4.2・ページ数に応じて時間がかかります）。
5. **確かめる**:
   - ページ数（管理画面）
   - 検索
   - 添付が開けるか
   - 案件残と必要部材表が出るか
   - メールのサインイン（使えなければ、画面からサインインし直します）
6. **アドレスを付け替える。** 各 PC のブックマークと、ローカル編集のヘルパーの登録（§6.2b の `-install`）を、サーバー機へ向けます。

   ⚠ ブラウザに憶えた見え方（折りたたみの開閉・ファイル表示の縦横比。`wcms.view`）は、アドレスごとです。
   一から憶え直しになります。
   開いたときの形（書ける形か閲覧モードか。`wcms.mode`）も、同じです。

7. **パソコン側は止めたまま控えとして残す。**

   ⚠ **2台に同時に書かない**（どちらが正か分からなくなります）。

   - サーバー機で問題が出たら、サーバー機に**まだ誰も書いていない**うちなら、止めてパソコン側を起動し直せば戻ります。
   - 書いたあとなら、サーバー機の `data\` を正とします。

### 9.4 移行の道具（ワンノート・メール）

- **ワンノートの製造**（`go run ./tools/onenote/build`）は、本文を**その機械の `data\`** から読みます。
  - 移したあとは、**サーバー機で動かします**（リポジトリと Go が要ります）。
  - `製造の記録.json`（デスクトップの `w-cms\ワンノート\…`）のページ番号は、そのまま効きます。
- **メールを通信箱へ上げる**（`go run ./tools/mail/push`）は、`WCMS_BASE` で上げ先を指します
  （既定は `https://localhost:8443`）。
  上げ直しても、重複は弾かれます（Message-ID）。
- 吸い出したデータ（デスクトップの `w-cms\ワンノート\`・`w-cms\メール\`）は、
  移したあとも、製造をやり直すために残します。
