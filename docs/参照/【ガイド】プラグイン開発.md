# 【ガイド】プラグイン開発

新しい**計算ユースケース**（DBテーブル＋同期＋集計API）を追加するための手順書です。
プラグインや拡張（`ext/`）を書く開発者と、AIエージェントが読みます。

**人間にもAIエージェントにも、このガイドだけで作業が完結する**ことを目指して書いています。

> **この文書の読み方**
>
> - 先に「まず振り分ける」を読みます。語彙の大半は、プラグインが要りません。
> - 「⚠」は、知らないとデータや集計を壊す所です。
> - 日付の付いた注記は、いつ・なぜその形になったかの記録です。消さずに残してあります。

この文書でよく使う言葉です。

| 言葉 | 意味 |
|---|---|
| プラグイン | 1つの計算ユースケースを受け持つ、プログラムの部品です |
| 拡張 | 業務に固有のものを入れる、`ext/` の下の別パッケージです（§9） |
| 形式 | 本文に書く表（`table`）・名前と値の並び（`dl`）・節（`section`）の種類です。この文書では「形式（`data-type`）」と書きます。いまは、表は `<caption>` で名乗ります（下の「いまの形」） |
| レジストリ | 形式の宣言を並べた登録簿です（`vocab.go` の `vocabRegistry`） |
| 汎用索引 | 宣言された形式を、種類を問わず DB に入れる索引です（`vocab_index`） |
| 観察係 | 本文を読んで、自分のテーブルを洗い替えるプラグインです（`Observer`） |
| 配送係 | 本文を1回だけ歩いて、要素を観察係へ届けるコアの部品です（`walk.go`） |
| 引き金 | 観察係が担当する形式名です（`Triggers()`） |
| 洗い替え | そのページの分を `DELETE` してから、`INSERT` し直すことです |
| 機械キー | プログラムが使う鍵です（例: `item-id`）。本文には書き出しません |
| クローム | 本文に足して見せる、補助の部品です。保存されません（`.vocab-chrome`） |

## まず振り分ける — 本当にプラグインが要るか

**プラグインは「計算が要る場合だけ」の手段です。**
新しい語彙（本文に書く形式）を足したいときは、まず次の 1〜3 のどれに当たるかを見ます。

w-cms は、語彙を3つの層に分けて扱います（3層モデル）。
①語彙レジストリ、②汎用索引、③計算プラグインの3つです。
全体像と、なぜこの分離なのかは、[【考察】語彙モデル.md](../考察/【考察】語彙モデル.md) §4 が正本です。

1. **記録・表示だけでよい**（語彙100種構想の大半。例: 検査記録・仕様一覧）
   → **プラグインは不要です。**
   - 要るのは、標準HTML（キャプションのある表 `<table><caption>表示名</caption>`、または `<dl data-type>`）と、
     **形式の宣言1件**だけです。
   - 宣言の置き場は、3つあります。
     - 業務の形式は、拡張の `init()` から `cms.RegisterVocab(…)` で登録します（§9）。
     - どの業種でも使う形式は、語彙レジストリ（[vocab.go](../../internal/cms/vocab.go) の `vocabRegistry`）へ足します。
     - 運用者が足す表の形式は、設定 `config/settings.json` の `vocab_formats` に書きます。
       これだけは、Go のコードを1行も書きません。
   - これで、スラッシュメニュー・挿入骨格・保存・②汎用索引（`vocab_index`）・型検証まで、自動で通ります。
   - 例の「検査記録」は、もう本番の登録にありません。
     2026-09-27 に、試験用の登録（`internal/cms/vocab_fixture_test.go`）へ移しました。
   - 手順は [【一覧】語彙.md](【一覧】語彙.md) §5 にあります。
     エディタ側の対応は [エディタ仕様.md](../旧文書/エディタ仕様.md) §3.2 にあります。
2. **集計API・型付きテーブル・取り込み変換のいずれかが要る**（例: 部材手配計算・PDF解析）
   → 本ガイドの手順で、プラグインを作ります（③計算プラグイン）。
   - この場合も、**語彙の宣言は 1. と同じくレジストリ**で行います。
   - プラグインは、「マーカー付き標準HTMLを読んで自分のテーブルへ同期する」役だけを担います。
   - 業務の計算は、拡張（`ext/<拡張>/`）に書きます（[開発方針.md](../開発方針.md) §0）。
3. **通信箱へ届いたファイルを解釈してページを作りたい**（例: `.eml` → 通信記録ページ）
   → 本ガイドのプラグインではなく、**取り込み係**を書きます（回覧機構の4つ目の段・2026-09-01）。
   - **口はコアではなく通信拡張にあります**（2026-09-15 に `internal/cms` から移設）。
   - [ext/comm/intake.go](../../ext/comm/intake.go) の `IntakeHandler`（`Name` / `Extensions` / `OnFile`）を、
     `init()` で `comm.RegisterIntake` に登録します。
   - 仕事は、渡される `IntakeContext` だけで行います。
     `IntakeContext` にあるのは、通信箱／年／月の下へ `CreateDatedPage`・`SaveAttachment`・
     作った直後の `UpdatePage` です。
   - 重複検知の鍵を出せるなら、任意の `SourceRefFinder` も実装します。
   - 実物は [ext/comm/intake_eml.go](../../ext/comm/intake_eml.go) です。
     正本は [【考察】通信記録処理.md](../考察/【考察】通信記録処理.md) です。

**カスタム要素（`<m-*>`）は作りません。**

- 理由は、[【考察】語彙モデル.md](../考察/【考察】語彙モデル.md) §9 の決定ログにあります。
  現況は、[【一覧】語彙.md](【一覧】語彙.md) §6 にあります。
- プラグインが語彙を宣言する機構も、撤去済みです（§2.1）。
  撤去したのは、`Tags()`・`PluginTags()`・`TagSpec`・`htmldoc.New()` への注入です。
- 動的な表示（集計ビュー等）は、マーカー付き標準HTML＋エンハンサ／サーバー事前描画で設計します。

## 1. アーキテクチャの全体像

w-cms は、「HTMLに書かれた**マーカー付き標準HTML**」を「SQLiteのテーブル」に同期するCMSです。
マーカー付き標準HTML は、`data-type` などの印（マーカー）を付けた、ふつうの HTML です。
1つの計算ユースケースは、1つの**プラグイン**として表現されます。

保存された HTML は、コアの `parser.go` と、`sync.go` の `SyncIndex` を通ります。

- `parser.go` は、コア情報を抽出します（タイトルの抽出 `PageTitle`）。親ID は、サイドカーが正本です。
  サイドカーは、本文の横に置く、属性のファイルです。
- `SyncIndex` は、次の順に動きます。どれも、同じトランザクション（ひとまとまりの DB の書き込み）の中です。
  1. `pages` を同期します。
  2. 登録済みの観察係の `OnPageStart` を呼びます。
  3. **コアの配送係が本文を1回だけ歩いて**、引き金に当たった要素を、各観察係の `OnElement` へ届けます。

プラグインは、`init()` で `Register()` に自己登録します。
**プラグインを足してもコアは無変更**です。
**プラグインは本文の語彙を持ちません**（§2.1）。

## 2. `Plugin` / `Observer` インターフェース

```go
// テーブルの所有だけを宣言する。
type Plugin interface {
    Name() string      // 識別子（ログ用）
    Schema() []string  // CREATE TABLE IF NOT EXISTS ...
    Tables() []string  // 所有テーブル名（自己文書化・整合性検証用）
}

// 本文を読んで自分のテーブルを洗い替える（＝観察係）。
type Observer interface {
    Plugin
    Triggers() []string                       // 担当する data-type（"*" で全マーカー）
    OnPageStart(ctx *ObserveContext) error    // 自テーブルの当該ページ分を DELETE
    OnElement(ctx *ObserveContext, el *html.Node) (descend bool, err error)
}
```

`Observer` は、`Plugin` の3つと合わせて、**6メソッド**です。
次の2つは、要るときだけ追加で実装します（どちらも任意）。

- 集計APIを足したい場合: `RouteProvider`
- 要素を配り終えたあとの確定処理が要る場合: `PageFinisher`（`OnPageEnd`）

```go
type RouteProvider interface { Routes() []Route }        // []Route{{Pattern, Handler}}
type PageFinisher  interface { OnPageEnd(ctx *ObserveContext) error }
```

> **2026-08-26 に `Sync(tx, pageID, root)` は無くなりました。**
>
> - かつては、木（本文の HTML を解析した木）を丸ごと受け取って、**各プラグインが自前で走査**していました。
> - その形には、困る点が2つありました。
>   - 同じ木を、プラグインの数だけ歩いていました。
>   - 除外規則（`.vocab-chrome` の中を読まない等）を、各自が覚えている必要がありました。
> - いまは、**コアの配送係が1回だけ歩き**、引き金に当たった要素だけを `OnElement` へ届けます
>   （設計の正本は [パーサとプラグイン.md](../旧文書/パーサとプラグイン.md)）。
>
> 実務上の違いは3つです。
>
> - **走査コードを書かない**（`WalkElements` を自分で回しません）。
> - **除外を覚えなくてよい。** クロームの中へは配送係が入らないので、そこは観測できません。
> - **DELETE は `OnPageStart` へ。** これで、テンプレート領域の除外が、定義から成立します。
>   テンプレート領域では、`OnPageStart` は呼びますが、要素イベントを1つも発火しません。
>   つまり、古い行は消えて、新しい行は入りません。

### 2.1 プラグインは本文の語彙を持たない

役割は、次のように分かれています。

- 本文の語彙（許可される要素・属性）は、`htmldoc/sanitize.go` の1箇所が正本です。
- 形式（`data-type`）の宣言は、`vocab.go` のレジストリが持ちます。

**次の2つは、[本文サニタイズ設計.md](../旧文書/本文サニタイズ設計.md) §5.3 が正本です。**

- この役割分担の図
- かつて必須メソッド `Tags()` でプラグインが語彙を注入していた機構を、撤去した経緯（2026-08-20）

プラグインを書くうえで効いてくるのは、次の3点です。

- **サニタイザは `data-type` の値を検査しません。**
  サニタイザは、保存する本文から、許可されていない要素や属性を落とす部品です。
  - 新しい形式名を足しても、許可リストは無変更です。
  - 逆に、新しい**要素**や**属性**が要るときだけ、`structuralElements` を直します
    （[本文サニタイズ設計.md](../旧文書/本文サニタイズ設計.md) §5・§7）。
- **`OnElement()` が読む鍵は必ずレジストリの `Field`／`Label` に載せる**こと。
  - ⚠ 載せ忘れると、文書の見出しから機械キーへ解決できず、値が黙って落ちます
    （`columnFor` が解決に失敗すると、その列は読まれません）。
  - かつて、`Tags()` の属性宣言漏れで `item-name` が消えて、原価集計が壊れました。症状は、それと同じです。
- 形式の宣言と読み取りが、別ファイル（`vocab.go` と `plugin_xxx.go`）に分かれます。
  これは v1 の割り切りです。
  ③計算形式の語彙宣言をプラグイン側へ寄せる案は、将来課題です（`vocab.go` 冒頭のコメント参照）。

### 2.2 使えるヘルパー

| ヘルパー | 定義 | 用途 |
|---|---|---|
| `Attr(n, "key")` | `plugin.go` | 要素 n の属性値（無ければ ""） |
| `WalkElements(root, fn)` | 〃 | 全要素ノードを先行順で走査 |
| `AtoiSafe(s)` | 〃 | 文字列→int（失敗時 0） |
| `ctx.Tag("部品番号")` | `walk.go` | 可変タグ（`<dl data-type="tags">`）から名前で値を引く（多値は先頭）。**木は渡されない**ので、ページ全体を見る用途はこの口から。**いまは、本体に使い手がいません**（2026-10-14 に数えました） |
| `ctx.Ancestors()` / `ctx.Closest(fn)` | 〃 | 祖先を辿る（容器の `data-src` を拾う等）。**いまは使い手ゼロです**（下の注記） |

## 3. 追加手順（チェックリスト）

1. **DBの形を決める**: 1テーブルか、ヘッダ＋明細（1:N）か、複数テーブルか。
2. **形式（`data-type`）を決めて [vocab.go](../../internal/cms/vocab.go) の `vocabRegistry` へ宣言する**。
   業務の形式は、拡張の `init()` から `cms.RegisterVocab(…)` で登録します（手本は `ext/toho/vocab.go`）。
   宣言に書くのは、次のものです。
   - `Type`（kebab-case・一意）・`DisplayName`・`Category`・`Icon`・`Element`（`table`／`dl`／`section`）
   - `Columns`
     （`Field` = `OnElement()` が読む機械キー・`Label` = 見出しの表示文字・`Type` = 列型）
   - ヘッダ＋明細なら、親に `Items`（明細表の形式名）
   - PDF原本を伴う形式なら、`File: true`。
     エディタが、ドロップゾーン・プレビュー・解析ボタンを、その `section` 自身へ付けます
     （`Container` 機構は 2026-08-31 に廃止）。
     ⚠ いま、本番の登録に `File: true` の形式はありません（宣言しているのは、試験用の登録だけです）。
     解析の口 `/api/parse-pdf` も、2026-10-01 に片付けました。
     PDF は、どのページにも添付でき、「ファイル表示」で開きます。新しい形式では、使いません。
   - 単独で挿入しない形式には、`Hidden: true`
   - 鍵がページのタグにあるなら、`RequiresTag`
3. `internal/cms/plugin_<usecase>.go` を新規作成し、§4のテンプレートを埋める。
   業務の計算は、`ext/<拡張>/` にファイルを作ります。
4. （集計APIが要るなら）`RouteProvider` を実装。
5. （挿入直後の振る舞いや専用UIが要るなら）`assets/app.js` に**エンハンサ**を足す。
   エンハンサは、画面へ補助の部品を足す JavaScript です。
   - 挿す要素は、必ず `class="vocab-chrome"` にして、**保存されない編集クローム**にします。
     ⚠ 付け忘れると、本文として保存されます。
     2026-10-12 から、ページは最初から書ける形で開くので、飾り付けは書ける形でも出ます。
   - 実例は `enhanceFileSections` です。
   - 呼び出しは、次の7箇所です（2026-10-14 に数えました）。作り直し方式なので、冪等です（何度呼んでも、同じ結果になります）。
     - `applyMode`（書ける形と閲覧モードを切り替えたとき）
     - `populateEditor`

     - 挿入直後の `replaceBlockWithComponent`
     - 挿入直後の `applyNestedChoice`

7. ドキュメント追記（[【一覧】語彙.md](【一覧】語彙.md) §2 の形式一覧、

> - ファイルから再生成できないデータ（外部から取得して保存するだけの値など）を、DB に持たせてはいけません

## 4. コピペ用テンプレート

### パターンA: フラットな1テーブル（明細なし）

**① まずレジストリへ形式を宣言する**（`vocab.go` の `vocabRegistry` へ1件追記）。

```go
{
	Type:        "memo",
	DisplayName: "メモ",
	Category:    "記録",
	Icon:        "📝",
	Element:     "dl",
	Columns: []VocabColumn{
		{Field: "title", Label: "件名", Type: ColText},
		{Field: "body", Label: "内容", Type: ColText},
	},
},
```

本文には、この形で入ります（鍵は `dt` の表示文字。機械キーは本文に書き出しません）。

```html
<dl data-type="memo">
  <dt>件名</dt><dd>在庫確認</dd>
  <dt>内容</dt><dd>丸鋼材の在庫を来週確認する</dd>
</dl>
```

**② ここで終わりです。プラグインは要りません。**

- 宣言した瞬間から、`<dl data-type="memo">` は、
  ②汎用索引 `vocab_index` に、`field='件名'`／`'内容'` の行として載ります。
- ⚠ `<section><h2>メモ</h2><dl>…` の形（節の見出しで名乗り、中に素の `dl` を書く形）は、もう索引に載りません。
  素の `dl` は 2026-09-18 に索引から外し、節の見出しで名乗る読み方は 2026-09-29 に廃止しました。
- 繰り返しのある記録なら、`Element: "table"` で宣言して、キャプションのある表で書きます
  （`<table><caption>表示名</caption>…`）。読むのは `VocabTableRowsOf` です。
  受注明細表・部材発注明細表などの業務の表が、この形です（`ext/toho/vocab.go`）。
- 計算が要るときだけ③を書き、索引から読みます（§8。読む鍵は機械キー `title`／`body`）。

```go
// メモの件名を集める③計算の断片。テーブルは持たない（Schema/Tables は nil）。
func memoTitles(db ReadOnlyDB, pageID int) ([]string, error) {
	blocks, err := VocabBlocksOf(db, pageID, "memo") // 1ブロック＝1件
	if err != nil {
		return nil, err
	}
	var out []string
	for _, b := range blocks {
		out = append(out, b.Values["title"]) // 索引の「件名」を機械キーで引く
	}
	return out, nil
}
```

観察係（`Observer`）を自分で書くのは、**索引に載らない形の情報を自前テーブルへ写したいとき**だけです
（§8「プラグインは自前のテーブルを持てるか」）。
そのときの雛形は、本ガイド §2 のインターフェース定義そのものです。

- `OnPageStart` で、当該ページ分を `DELETE` します。
- `OnElement` で、`el` の部分木を読んで `INSERT` します。
- 読み切ったら、`descend=false` を返します。

> **`descend` の意味**（2026-08-26）
>
> - **既定は true**（降りる）です。
>   `false` を返してよいのは、「その部分木を自分が読み切った」ときだけです。
> - ただし、観察係どうしは独立です。
>   配送係は、「**全員**が降りないと言ったときだけ降りない」（OR）という規約で動きます。
> - たとえば、受注の観察係が明細表を丸ごと読んでも、②汎用索引は、同じ明細表を自分でも索引します。

### 特殊: 表示専用の計算ビューを足したい

本文には**鏡の印** `<section data-mirror="表示名"></section>` だけを保存します（2026-09-27 午後から）。
中身は、サーバーが描く形にします。

**ここだけは「レジストリへ宣言1件」では動かない例外**で、手順は2つです。

1. レジストリで `Element: "section"` ＋ `View: true`（列は持たない）を宣言する。
2. **[view_render.go](../../internal/cms/view_render.go) の `viewRenderers` へ描画関数を1件登録する**
   - `map[string]func(user *auth.User, pageIDInt int) string` に、形式名で足すだけです。
   - map は非公開です。
     **拡張からは `init()` で `cms.RegisterView(形式名, 描画関数)` を呼びます**（§9）。
   - 早期リターンの判定も、対象の収集も、**レジストリの `View: true` から作られます**。
     そのため、触るのはこの1箇所になりました（2026-08-25 の整理）。
   - 足し忘れても、**無言の空白にはなりません**。
     「この形式（○○）の中身を作る処理がまだ用意されていません」と画面に出ます（`missingViewHTML`）。
   - 以前は、3箇所へ形式名を足す必要がありました。
     どれか1つでも漏らすと、中身が描かれないまま、何も起きませんでした。

⚠ **鏡の中にボタンを出して、表示しているページへ書き込む口を作るなら、テンプレートの中を断ること**（2026-09-27）。

- 書き込む前に、`cms.RefuseTemplateArea(w, pageID)` を通します。
  置く場所は、権限の関門の**後**です（東邦拡張は `requireWritableIdle` が通します）。
  - `requireWritableIdle`（`ext/toho/handler_gate.go`）は、3つを順に確かめます。
    書く権限（`page.RequirePageWrite`）、テンプレートの中でないこと、誰も編集権を握っていないこと
    （`editlock.RefuseWhileEditing`）です。
  - ⚠ 3つ目は、2026-10-12 から、ほぼ素通りです。
    編集モード（ページ単位の編集ロック）をやめたので、画面は編集権を握りません。
    効くのは、道具が `/api/lock` → `/api/save` で一瞬握っているあいだだけです。
    名前の「Idle」は、昔のままです。
- なぜか: テンプレートの上で押されると、書いたものが**そこから作るページ全部へコピーされます**。
  コピーは索引に入って、本物の集計を動かします。
- テンプレート以下では鏡を描かないので、画面にボタンは出ません。
  それでも、口を直に叩けば届きます。
- 受け皿として、`cms.RewriteBody` も `cms.ErrTemplateArea` で断ります。

⚠ **本文を書くときは、必ず `cms.RewriteBody` を通すこと**（2026-10-12 から）。

2026-10-12 に、編集モードをやめました。ページは最初から書ける形で開き、人の保存（`POST /api/sync`）がいつでも来ます。
そのため、機械が本文を書く道は、次の決まりで守ります。

- `cms.RewriteBody(pageID, author, 書き換える関数)` は、ページごとの書き込みの錠（`cms.LockPageBody`）の中で、
  読んで・変えて・書きます。人の保存と重なっても、片方が消えません。
  サニタイズ・更新日時・版・索引・開いている人への知らせも、ここが済ませます。
  東邦拡張は、`rewriteBodyOrFail`（失敗を 500 で返す包み）を通します。
- ⚠ **本文のファイルへ、直に `page.WriteFileAtomic` しません。** 錠の外で書くと、人の保存と重なって、片方が消えます。
- ⚠ **錠を取ったまま、同じページの本文を書く関数を呼びません。** 錠は再入できないので、止まります。
  `RewriteBody` に渡す関数の中から、同じページの `RewriteBody` を呼ばない、ということです。
- 機械は「ほかの書き手の1人」です。人の書きかけと同じブロックがぶつかれば、画面が両方の版を並べます。
  サーバーが断ることは、しません。
- 画面のボタンは、`app.js` の `postJSON` で送ります。
  `postJSON` は、送る前に書きかけを保存します（`window.wcmsFlushSave`）。
  そのため、鏡のボタンは、書ける形でも押せます。ボタンが読む本文には、直したばかりの中身が入っています。
- 口の前口上は、コアの `cms.GateJSONPost` と `cms.PageIDOrFail` を使います
  （東邦拡張は、`gateWritablePage` が `PageIDOrFail` と `requireWritableIdle` を続けて通します）。
  新しい口を書く前に、既にある入口を見ます。

**コードが印を書くときは `cms.ViewMarkerHTML(形式名)` を通します**（試験の置き場のテンプレートなど・2026-09-27）。
置き場の本文は、もうコードに無く、テンプレートが持ちます。

- 返るのは、`<section data-mirror="表示名"></section>` です。属性名は、定数 `cms.MirrorAttr` です。
- 表示名をレジストリから引くので、コードに言葉を焼きません。スラッシュメニューが挿す形と、同じになります。
- `View: true` でない形式（ファイル表示など）を渡すと、その場で panic します。
- ⚠ **`<section data-type="形式名"></section>` と書いても鏡は描かれません。**
  名前の見えない属性の印は、2026-09-27 に廃止しました（`vocabTypeOf` が、計算ビューの `data-type` を読みません）。
- 手で書いた `data-mirror` の名前が、鏡として登録されていなければ、やはり描かれません。
  保存時に、`unknown_types` で告げられます。

**中身の包み方**

- 中身は、`<div class="vocab-chrome" contenteditable="false">` に包まれます。
- エディタのシリアライザ（本文を保存の形へ直す部品）は、`.vocab-chrome` を保存しません。
  そのため、保存往復では、印（と印の中に人が書いたもの）だけが残ります。
- ⚠ **タイトル等の利用者入力は必ず `html.EscapeString` を通すこと**（サーバー側で文字列連結するためです）。
- 実例は、`child-list`（子ページ一覧）と `required-materials`（手配状況リスト）です。
- 仕組みの全体像は、[アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) 4.4 にあります。

## 5. 動作の仕組み（なぜコアを触らなくてよいか）

- **スキーマ作成**:
  - 起動時に、`main.go` が `cms.ApplySchema(db)` を呼び、全プラグインの `Schema()` を実行します。
  - テストは、`database.CreateCoreTables(db)` ＋ `cms.ApplySchema(db)` で、本番と同じスキーマを再現します。
- **同期**:
  - `SyncIndex` が、コア（`pages` の upsert → サイドカー由来の `page_perms`）を同期します。
  - そのあと、各観察係の `OnPageStart` を呼びます。
  - **配送係が本文を1回だけ歩いて**、`OnElement` を配ります（すべて、1つのトランザクション内です）。
  - 可変タグの行き先は **`page_tags`**、業務ブロックは②汎用索引 `vocab_index` です。
    振り分けは、書き手1か所 `insertVocabEntry` です。
  - `page_tags` は、2026-08-30 にいったん吸収しましたが、**2026-09-13 に分離し直しました**。
- **全再構築**:
  - `RebuildDatabase` は、`sqlite_master` から**全テーブルをDROP**して、スキーマごと作り直します。
    そして、`data/master` の全HTMLを再同期します
    （[アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) 8章）。
  - 全テーブルをDROPするため、`Tables()` の記載漏れが再構築バグを起こすことはありません。
  - ただし、`Schema()` と `Tables()` の整合性は、テスト（`TestPluginTablesConsistency`）で検証されます。
    所有テーブルは、`Tables()` に列挙してください。
- **正本性**:
  - プラグインのテーブルは、`data/master` のHTMLから再生成可能でなければなりません（§3の不変条件）。
  - これにより、`cms.db` は使い捨て可能で、バックアップはファイルのみで済みます。
- **ルーティング**:
  `main.go` が `cms.PluginRoutes()` を走査し、`RouteProvider` を実装するプラグインのルートを登録します。

## 7. AIエージェント向けの厳密手順

このセクションは、AIがこのガイドだけで作業する際の、決定論的な手順です。

0. **計算が要るかを先に判定する**。
   集計API・型付きテーブル・取り込み変換のどれも要らないなら、
   **`vocab.go` の `vocabRegistry` へ1件足して終わり**です。プラグインは作りません（冒頭の振り分け）。
1. **絶対に編集しないファイル**:
   `internal/cms/plugin.go`, `internal/cms/parser.go`, `internal/cms/sync.go`, `internal/cms/walk.go`,
   `internal/cms/vocab_index.go`, `internal/cms/htmldoc/sanitize.go`, `internal/database/sqlite.go`,
   `cmd/w-cms/main.go`。
   これらを編集しようとしたら、設計を間違えています。
2. **編集するのは2ファイル**:
   - `internal/cms/vocab.go`（`vocabRegistry` へ形式を1件追記）
   - 新規作成する `internal/cms/plugin_<usecase>.go`。
     §4 から最も近いパターン（A/B/C）をコピーして、名前を置換します。

   ⚠ **業務のもの（別の業種では要らないもの）は、この2ファイルではなく、拡張に置きます**
   （[開発方針.md](../開発方針.md) §0）。
   - 形式は、拡張の `init()` から `cms.RegisterVocab(…)` で登録します。
   - プラグインは、`ext/<拡張>/` のファイルに書いて、`cms.Register(…)` で登録します。
   - 計算ビューは、`cms.RegisterView(…)` で登録します（`view_render.go` は編集しません）。
   - コアのファイルは、1つも編集しません。迷ったら、置き場所を利用者に聞きます。

   **唯一の例外**: `View: true` の**計算ビュー**を足すときだけ、3ファイル目として、
   `internal/cms/view_render.go` の `viewRenderers` へ描画関数を1件登録します
   （§4「特殊: 表示専用の計算ビューを足したい」。足し忘れても無言の空白にはならず、理由が画面に出ます）。
3. **`Observer` の6メソッド**（`Name` / `Schema` / `Tables` / `Triggers` / `OnPageStart` / `OnElement`）を、
   必ず実装します。
   ファイル冒頭に、`func init() { Register(<plugin>{}) }` を書きます。
   **`Sync()` も `Tags()` も存在しません**（前者は 2026-08-26、後者は 2026-08-20 に撤去）。
4. **`Tables()` は `Schema()` で作るテーブルをすべて列挙**します（慣習として子→親順）。
   整合性は、`TestPluginTablesConsistency`（[storage_test.go](../../internal/cms/storage_test.go)）が検証します。
   東邦拡張のプラグインは、同じ名前の試験が `ext/toho/aggregate_test.go` にあります。
5. **洗い替えの DELETE は `OnPageStart` へ**、INSERT は `OnElement` へ置きます。
   明細テーブルも `page_id` を持つので、子→親の順に、直接消します。
6. **走査は書かない**。
   - 担当は、`Triggers()` の宣言で決まります。
     `OnElement` には、当たった要素だけが来ます（要素名だけ、念のため確かめます）。
   - ③計算の値の取り出しは、`vocab_query.go` の3関数です（§8）。
   - 生の `Attr(el, "...")` で、業務値を読みません（値は、属性ではなく**中身のテキスト**にあります）。
7. **鍵の一致を確認**:
   `row.Values["item-name"]` の `"item-name"` が、レジストリの `Columns[].Field` と一致しているか。
8. **集計APIが要るときだけ**、`RouteProvider` を実装します。`main.go` には触りません。
9. **検証**: `go build ./... && go vet ./... && go test ./...` が、すべて通ること。
   スキーマを使うテストは、§6 の定型で用意します。
10. **ドキュメント更新**:
    - [【一覧】語彙.md](【一覧】語彙.md) §2 に、形式を追記します。
    - [アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) の
      「2. データベーススキーマ設計」に、新テーブルを追記します。

### 索引を読む（③計算の書き方）

集計は、`vocab_query.go` の層を通します。**この層の仕事は鍵の変換**です。

- 索引の `field` に入っているのは、本文の見出しの表示文字です（`品番`・`数量`）。
- ③計算が使いたいのは、機械キーです（`item-id`・`quantity`）。
- 対応表は、①語彙レジストリの `Label` ↔ `Field` が唯一の正本です。
  そのため、ここで一度だけ引き当てます。
- ⚠ **集計コードへ日本語の魔法文字列を直書きしないこと。**
  見出しを改名したときに、告知する側（`UnresolvedVocabFields`）と読む側が、ずれます。

| 関数 | 何を返すか |
|---|---|
| `VocabTableRowsOf(db, pageID, dataType)` | 表形式の行（1データ行＝1件）。`row.Values["item-id"]`・`row.Num("cost")` |
| `VocabBlocksOf(db, pageID, dataType)` | 名前：値形式（1ブロック＝1件）。業務文書ブロックのヘッダもこれ |
| `PagesByTag(db, name, value)` | 可変タグの逆引き（「部品番号が X のページ」）。**ページ横断の突き合わせはこの形**になる。畳んだ一致で引く `PagesByTagLoose` も同じファイルにある（本体の呼び手は4か所。2026-10-14 に数えました）。符牒や名前で探すときは、こちらを通す |

> **ヘッダと明細の対応づけは `block_no`** です。
>
> - 索引のブロック番号は、形式ごとの、文書順の連番です。
> - そのため、1つの `section` がヘッダ1つと明細表1つを持つ限り、同じ番号どうしが対になります。
> - 発注書番号で結ぶと、番号が重複したときに、仕入先が入れ替わりえました。

たとえば、解決係が居なければ、`email` 型のタグは素のテキストで出ます（`-tags minimal` の素の w-cms が、そうです）。
**コアは業務語を知らない**、が線です。

表の登録について、知っておくことを、4つ書きます。

**取り込み係とメールの口は `ext/comm` にあります**

⚠ **`comm.` で始まる口は `cms.` ではありません。** 取り込み係とメールの送受信から下の6つです。

- 通信箱・取り込み係・Mailer の口は、2026-09-15 に `internal/cms` から `ext/comm` へ出ました。
  `cms.RegisterIntake` も `cms.RegisterMailer` も、**もう存在しません**。
- 取り込み係やメール実装を足す拡張は、`w-cms/ext/comm` を import します
  （実測: `ext/comm/mail`・`ext/comm/contacts`・`ext/toho` の3つが、そうしています）。
- `ext/comm` のパッケージ自体に、ビルドタグはありません。
  外れるのは、取り付け口 `cmd/w-cms/ext_comm.go` が `!minimal` だからです。
  `-tags minimal` では、誰も import しなくなり、取り込み係の機構ごと消えます。

**拡張が要る置き場（`RegisterRequiredPage`）**

`RegisterRequiredPage` は、**名前で機能が決まるトップ直下のページ**を宣言する口です
（通信箱・製造・受注・テンプレート置き場）。

- 管理画面の「置き場」に並び、**人がボタンを押したときだけ**作られます。
- 起動時に自動で作らないのは、「人が押したことが、そのページを置く意図」だからです
  （通信箱の 09-05 の決定を保ちます）。

⚠ **置き場の本文はコードに書きません**（2026-09-27 に `RequiredPage.Body` を消しました）。

> 利用者:「コードにハードコーディングせず、テンプレート駆動にしたい」「テンプレートが無ければ作れないまで行きます」

- 拡張が宣言するのは、**題（Title）と説明（Why）だけ**です。
- 置き場は、**テンプレート置き場の下の、同じ題のテンプレート（葉）**を、純粋にコピーして作ります。
- **テンプレートが無ければ作りません**
  （`cms.ErrNoBoxTemplate`・管理画面の「置き場」に「テンプレートがありません」と出ます）。
- 途中で置き場を作る口も、同じ道を通ります
  （`cms.EnsureTopLevelBox`・連絡帳の `EnsureContactsBox`・製造の置き場の `EnsureCustomerBox`）。

⚠ **作業面（鏡の印）はテンプレートに入れること。**

- 見出しだけの箱は、**そのページで何をすればよいのかが画面に出ず、行き止まりになります**
  （2026-09-11 と 09-16 に、実際に起きました）。
- 印は、`<section data-mirror="表示名"></section>` です（スラッシュメニューで入ります）。

⚠ **試験で置き場を作るなら、準備でテンプレートを置くこと**
（`ext/toho` の `seedBoxTemplates`・`ext/comm/contacts` の `seedContactsBoxTemplate`）。

- テンプレートは、環境ごとのデータです。
  別の環境へは、`tools/templates.js`（書き出し・取り込み）で運びます。
- 正本は、[required_pages.go](../../internal/cms/required_pages.go)・
  [box_template.go](../../internal/cms/box_template.go) です。

**機械が作るページのテンプレート（`RegisterPageTemplate`）**

**機械が作るページも、テンプレートを写して印を埋めます。**

> 2026-09-27 夕 利用者:「Dの分についても、テンプレート駆動にしたいです」「テンプレートにはスラッシュメニューから表などの印を置き、コードはそれを埋めてはどうでしょう？」

**本文をコードで組まないこと。** 手順は、次のとおりです。

1. `cms.DraftFromTemplate(題)` で、写しを取ります。
2. 次の口で、値を入れます。
   - `SetTitle`
   - `SetTag(名前, 値...)`（同じ名前を繰り返す）
   - `FillTable(キャプション, 列, 行)`（見出しの言葉で列を合わせ、行を要るだけ作る）
   - `SetFileView(参照)`
   - `Container(見出し).SetContent(HTML)`（見出しの節・畳める枠の中身）
3. `HTML()` を、`cms.CreateChildPage` へ渡します。

**形はテンプレート、値と数は機械**です。

- テンプレートに無いタグ・列は、値があれば足されます。
- 値を入れる器（表・節）が無ければ、`cms.TemplateSlotError` で断ります。
  ⚠ **作る前に**確かめること（有料の問い合わせ・送信・仮のページの前に）。
- 使うテンプレートは、`cms.RegisterPageTemplate` で登録します。
  登録すると、管理画面に、在る／無い／2枚あるが出ます。
- 試験は、本物の口を通すために、**テンプレートの見本**を用意します
  （`ext/toho/templates_test.go`・`ext/comm/setup_test.go` の `seedCommTemplates`）。
- 正本は、[page_template.go](../../internal/cms/page_template.go) です。

**アップロードの受け口（`RegisterUploadInterceptor`）は 2026-09-30 に無くしました**

- 使い手は、通信箱へ落とした `.eml` を記録にする取り込み係だけでした。

  > 利用者:「通信箱ページのファイルをドロップすると子ページが作られる機能はもはや必要ないでしょう　ページを作るボタンが新設されたからです」

- どのページへ上げても、添付になります。
- `.eml` を記録にするのは、通信の口 `/api/intake/eml` です。

### 9.1 拡張どうしの import（2026-09-15 に解禁）

それまで、`ext/` 間の import はゼロでした。
アドレス帳を `ext/comm/contacts` へ出したとき、`ext/toho`（整理が取引先ページを作る）から呼ぶ必要が出ました。
そこで、**案B として解禁**しました
（[【考察】アドレス帳の作り直し.md](../考察/【考察】アドレス帳の作り直し.md) §5b・§8）。

いまの向きは、次のとおりです（2026-10-14 に、各パッケージの import 行で確かめました。試験のファイルは除きます）。

- `ext/comm/mail` → `ext/comm` と `ext/comm/contacts`
  （2026-09-16 の実測では、`ext/comm` だけでした。いまは、メールの署名を連絡帳から読みます。`ext/comm/mail/compose.go`）
- `ext/comm/contacts` → `ext/comm`
- `ext/toho` → `ext/comm` と `ext/comm/contacts`

**`ext/comm` は誰も import し返しません**（通信が土台）。規則は2つです。

- **import される側にビルドタグを付けない。**
  - ⚠ `ext/comm/contacts` にタグを付けると、「板金は入れたがアドレス帳は外した」という組み合わせが作れてしまいます。
    すると、整理が取引先ページを作れずに、黙って壊れます。
  - **依存は import で表します。** 使う側が連れてきます。
- **拡張は `init()` で自分を名簿に載せる**
  （`cms.RegisterExtension("toho", "東邦の業務")`・2026-09-15。
  正本は [extensions.go](../../internal/cms/extensions.go)）。
  - 名簿は、起動ログと、`/api/tag-schema` の `extensions` に出ます。
    **画面は名簿を見てその拡張のボタンを出し分けます**（`app.js` の `hasExtension(id)`）。
  - import の連鎖で入った拡張も、自分で名乗るので、漏れません。
  - ⚠ 載せ忘れると、**画面からその拡張のボタンが消えます**
    （サーバーの口は動いているのに、押す場所が無い）。新しい拡張を作ったら、必ず呼ぶこと。
  - **ID はパッケージのパスに揃えます。**
    現在の4つは、`comm`（`ext/comm`）・`comm/contacts`・`comm/mail`・`toho` です。
  - 同じ ID を2度登録すると、取り付けの誤りとして `panic` します。
  - `ExtensionIDs()` は、**空でも `[]`** を返します。
    `null` を返すと、画面が「知らされていない」と取り違えるためです
    （`hasExtension` は、知らされていなければ true）。
  - 取り付け口の `ext_*.go` は、import 行だけです。
    `ext_contacts.go` は、「既定の組にアドレス帳が入っている」ことを明示するために、残してあります
    （消しても、機能は消えません）。

**ルートも拡張と一緒に外します。**

- `main.go` へ直書きすると、`-tags minimal` でコンパイルが通らなくなります。
- `RouteProvider` の `Routes()` で返してください
  （`/api/analyze-attachment` は、2026-09-03 に、直書きからこちらへ移しました）。

> **既定は「入り」です。**
>
> - タグを付け忘れたビルドは、受注ページ生成も部材計算も業務語彙も無いまま、**普通に起動してしまいます**。
>   気づくのは、「発注書を解析しても何も起きない」ときになります。
> - 外すのは、他社へ配るという意識的な行為です。そのため、そちら側にタグを要求しました。
>
> 何が入っているかは、**起動ログに出ます**（ID順。名前は、各拡張の `cms.RegisterExtension` の2つ目の引数です）。
>
> - 既定 … `拡張セット: comm（通信）, comm/contacts（アドレス帳）, comm/mail（メール送受信・IMAP／SMTP）, toho（東邦の業務）`
> - `-tags nomail` … `拡張セット: comm（通信）, comm/contacts（アドレス帳）, toho（東邦の業務）`
> - `-tags minimal` … `拡張セット: なし（素の w-cms）`

**コアの何を使えるか**

- 使えるのは、公開名だけです
  （`cms.CreateChildPage`・`cms.GeminiGenerate`・`cms.VocabTableRowsOf`・`cms.PagesByTag` など）。
- 非公開のヘルパが要ると分かったら、それはコアが持つべき仕事かどうかを、先に考えてください。
- `VocabNumber`・`VocabQuantity`（数量の空セルは1）は、語彙の一般規則なので、コアに残しました。

**テストの置き場も分かれます。**

- コアのテストは、業務語彙を**道具として**使います。
  そのため、写しを [internal/cms/vocab_fixture_test.go](../../internal/cms/vocab_fixture_test.go) に置いてあります。
- 試しているのは、コアの機構です。板金部の列定義ではありません。
  だから、写しは**ずれても構いません**。
- **宣言そのものの検証は拡張側**（[ext/toho/vocab_test.go](../../ext/toho/vocab_test.go)）が受け持ちます。

### 9.2 拡張の設定は「節」で持つ（2026-09-15）

拡張だけが使う設定は、**コアの `Settings` 型に足さず**、
`config/settings.json` の `extensions.<拡張の名前>` の節に置きます。
コアは、「節がある」ことしか知りません。

```jsonc
"extensions": {
  "toho": { "product_code_tags": ["図面番号", "品番"] }
}
```

（2026-09-29 までは、この例が装置の段 `machine_stages` でした。
段は加工製品ページのタグ `区分` になり、選択肢は語彙へ移ったので、節から消えています。）

```go
func init() {
	cms.RegisterSettingsSection("toho", parseSettings)
}

// 節を読んで検査し、効かせる関数を返す（raw は節が無ければ nil）。
func parseSettings(raw json.RawMessage) (func(), error) { … }
```

守ることは3つです（手本は [ext/toho/settings.go](../../ext/toho/settings.go)）。

- **検査と反映を分ける。**
  - 返した関数は、ファイル全体（ほかの拡張の節も含む）の検査が通ってから、呼ばれます。
  - ⚠ 検査の中で自分の変数を書き換えると、別の節が壊れていたときに、**半端な設定で動きます**
    （DB再構築の読み直しでは、止まらずに走り続けます）。
- **節が無ければ（raw が nil）空を効かせる。**
  運用者が節を消した意図どおり、古い値を残しません。
- **打ち間違えたキーで止める**（`DisallowUnknownFields`）。
  コアの設定と同じ流儀です。

そのほかの決まりです。

- 載っていない拡張の節は、コアが**止めずに読み飛ばし、ログへ1行**出します。
  同じ設定ファイルを、`-tags minimal` でも使えるようにするためです。
- **語彙（`vocabulary`）は節に分けません。**
  型は名前で決まります。辞書は1つのほうが、衝突に気づけます。
