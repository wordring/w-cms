# 【一覧】用語集

w-cms で使う用語の正本（いちばん正しいとする元の一覧）です。
利用者と開発者が、同じ言葉で話すために使います。

**業務の用語**（受注／発注・納品・部材…）と、**画面の用語**（レール・クローム・ブロック…）の両方を、ここに集めます。
設計・実装・ドキュメント・コミットメッセージ、そして会話で、**用語を統一**するために使ってください。

この文書は、3つの節でできています。

- **§1 業務の用語**: 「何を扱っているか」を指す言葉です。受発注・ものづくり・納品・通信記録を扱います。
- **§2 画面の用語**: 「どこの話をしているか」を指す言葉です。
  「左のパネル」「サイドバー」「メニュー」のような、曖昧な指し方を避けるために用意しました。
  実装は [assets/index.html](../../assets/index.html)、挙動の詳細は [エディタ仕様.md](../旧文書/エディタ仕様.md) §9 が正本です。
- **§3 基盤の用語**: 両者にまたがる土台の言葉です（ページ・正本性・語彙・計算ビュー）。

> **本文で使える形式（`data-type`）の一覧**は、[【一覧】語彙.md](【一覧】語彙.md) が正本です。
> 形式とは、表やブロックの種類のことです。【一覧】語彙は、語彙レジストリ（使える形式の登録簿）の鏡です。
> ここには、個々の形式は載せません。
>
> 2026-08-21 に、「画面構成と用語.md」を本ファイルの §2 へ統合しました。
> 用語の正本が業務用と画面用の2冊に分かれていて、どちらを引けばよいか分からなかったためです。

表の中には、`<table data-type="…">` のような HTML の書き方や、プログラムの中の名前も出てきます。
これらは開発者のための手掛かりです。言葉の意味を知りたいだけなら、「意味」や「説明」の欄を読めば足ります。

## 1. 業務の用語

この節の用語は、次の方針で決めています。

- **「発注書」という言葉だけでは、誰の立場で言うかによって意味が変わり、曖昧です。**
  たとえば顧客が出す発注書は、こちらから見れば、受け取る側の書類です。
  そこで、立場に依らない**役割語**（役割で呼ぶ言葉）で呼びます。
- **受け取る側と出す側の対は、`受注` ／ `発注` と呼びます**（2026-06-27 決定）。
  標準的で、曖昧さの無い言葉です。
  `注文` という案もありました。実在の「注文書」に根ざした言葉ですが、`受注` の教科書的な対義語である `発注` を選びました。
- **見積の2種は、`見積` ／ `見積依頼` と呼びます**（2026-10-02 に改めました）。
  - `見積` は弊社が顧客へ出すもの、`見積依頼` は弊社が業者へ出すものです。

    > 利用者:「弊社の見積もりを見積もり、業者への見積依頼の場合、見積依頼と明確に言葉を分けます」

  - 置き場も、トップ直下の「見積」と「見積依頼」に分かれます
    （[【要求】見積.md](../拡張/東邦/【要求】見積.md)・[【要求】見積依頼.md](../拡張/東邦/【要求】見積依頼.md)）。
  - それまでは、取引の性質で **`販売見積` ／ `購入見積`** と呼んでいました（2026-06-27 決定）。
    `売上/原価見積` という案は、「原価見積＝社内原価積算」と紛れるので避けました。
- **表の「実装・状態」欄の読み方**:
  **実装済み** とある語は、いまのコードに対応するものがあります。
  **設計中** とある語は、[【考察】通信記録処理.md](../考察/【考察】通信記録処理.md) などで検討中で、まだ実装していません。

### 1.1 受発注・取引の中核

| 用語 | 意味 | 実装・状態 |
|---|---|---|
| **受注** | **顧客から届いた発注書**です（こちらが受け取る側。売上側）。通信記録（メール）から独立した、長く生きる記録（長命エンティティ）です。あとから別のメールで**変更・取消**されることがあります。取消は、削除ではなく、状態の印（状態フラグ）で表します。 | 実装済み：**受注ページ**です（`受注／年／月` の下。1文書＝1ページ）。ヘッダ（`発注書番号`・`発注元`・`発注日`・`納期`・`小計`…）は**ページの可変タグ**に書きます。明細は `<table data-type="client-order-items">` です（`<caption>受注明細</caption>` で名乗ります）。🤖 解析が、通信記録の添付PDFから作ります。形式 `client-order`（`section` で包む形）は、2026-09-18 にレジストリから消えました（[【一覧】語彙.md](【一覧】語彙.md) §2.3） |

| **案件** | 受注・発注・部材・見積を突き合わせる**業務単位（ジョブ）**です。「1文書＝1ページ」を採ってからは、文書ページを**参照マーカー**で束ねる**参照ハブページ**として表します。 | 設計中（[通信記録メモ §2.5](../考察/【考察】通信記録処理.md)）。いまは `page_id` 単位の集計です |

| **見積依頼** | 弊社が業者（材料屋・加工業者）へ値段を聞くものです。業者の返事の単価（原価予定）も、そこに記録します。確定すると**発注**になります。2026-10-02 までの名は `購入見積` でした（業者が出す見積の側から呼んでいました）。 | **未実装**です。形は [【要求】見積依頼.md](../拡張/東邦/【要求】見積依頼.md) にあります（トップ直下の「見積依頼」。`見積依頼／年／月` に、業者ごとに1枚の**見積依頼書ページ**。紙も**見積依頼書**）。いま原価の側は、加工製品ページの見積計算表と、発注書から引く**最新単価**（[【考察】材料の単価と価格の履歴.md](../考察/【考察】材料の単価と価格の履歴.md)）が担っています。旧形式 `supplier-estimate` も、2026-09-18 に消えました |

**受発注の2×2（予定→確定）**:

| 段階 | 売上側（顧客と） | 原価側（仕入先と） |
|---|---|---|
| 予定（見積） | **見積** | **見積依頼**（業者の返事の単価） |
| 確定（発注書類） | **受注** | **発注** |

```
見積     ─(確定)→ 受注      （顧客と・売上側）
見積依頼 ─(確定)→ 発注      （仕入先と・原価側）
```

### 1.3 納品・進捗

| 用語 | 意味 | 実装・状態 |
|---|---|---|
| **納品** | 受注に対して品物を納める出来事（イベント）です（◯月◯日に N 個）。 | 設計中（[通信記録メモ §4.3](../考察/【考察】通信記録処理.md)） |
| **分納** | 1つの受注を、**複数回に分けて納品**することです。充足（どこまで納めたか）は、`受注数 − Σ納品済数 = 残` で集計します。 | 設計中 |
| **進捗（status）** | 部品ごとの状態です。いまは、決まった選択肢から1つを選ぶ形（単一enum）です。選択肢は、受注明細＝未着手/加工中/検査中/納品済、発注明細＝未納品/納品済 です。分納に対応するため、数量で持つ形（数量ベース化）を検討しています。 | 実装済み（enum）：明細表の「状態」列です（機械キー `status` へ解決されます）。選択肢は、語彙レジストリ（`vocab.go`）が持ちます。数量ベース化は設計中です |
| **受注残** | まだ納品し切っていない受注の残数です（`現在の受注数 − Σ納品済数`）。**納品では受注数を書き換えず**、残が計算で減ります。一方、**受注変更では受注数そのものを改訂**できます（文書ベースゆえの柔軟性です）。**計算ビュー**（§3）として集計して見せます（保存はせず、DBから導き出します）。 | 設計中（[通信記録メモ §2.6・§4.3](../考察/【考察】通信記録処理.md)） |
| **納期** | 納品の期限です。**部品（明細）単位**で持ちます（受注全体ではなく、明細の行ごとです）。いまは、`<dl data-type="tags">` の自由記入タグ「希望納期」に書いています。明細単位にすること（列の追加）は設計中です。 | 設計中（[通信記録メモ §4.3](../考察/【考察】通信記録処理.md)） |
| **納期ビュー（生産スケジュール）** | 残のある明細を、納期の早い順（昇順）に並べた計算ビューです（受注残×納期）。製造の優先順位を付けるのに使います。 | 設計中（[通信記録メモ §2.6](../考察/【考察】通信記録処理.md)） |

## 2. 画面の用語

会話・Issue・コミットメッセージで、画面の上の位置を指すときは、ここの呼び名を使ってください。

### 2.1 全体レイアウト

```
┌─────────────────────────────────────────────────────────────────┐
│ ヘッダー  .header                                                │  ← クローム
│  タイトル領域 .title-area        モード切替 / ⚙管理 / ログアウト  │
├──────────┬───────────────────────────────────┬──────────────────┤
│          │                                   │                  │
│ 左レール │           文書                    │   右レール       │
│ .rail    │        .doc-column                │   .rail          │
│ -left    │                                   │   -right         │
│ ┌──────┐ │  ┌─────────────────────────────┐  │                  │
│ │ 目次 │ │  │     #w-editor-content       │  │  ┌────────────┐  │
│ └──────┘ │  │      （本文＝正本）          │  │  │ ページ情報 │  │
│ ┌──────┐ │  └─────────────────────────────┘  │  └────────────┘  │
│ │子ページ│ │  ┌─────────────────────────────┐  │  ┌────────────┐  │
│ └──────┘ │  │      HTMLプレビュー          │  │  │ 🔒 権限    │  │
│ ＋子ページ│  │      #w-html-preview        │  │  └────────────┘  │
│  を作成  │  └─────────────────────────────┘  │                  │
├──────────┴───────────────────────────────────┴──────────────────┤
│ フッター帯  .site-footer                                         │
└─────────────────────────────────────────────────────────────────┘
   ↑つまみ .rail-toggle                              つまみ↑
```

作業領域 `.work-area` は、**flex の3カラム**です（左レール｜文書｜右レール の3列を、横に並べます）。

狭い画面では、レールが2段階で**ドロワー**になります。
ドロワーは、文書に重なって、引き出しのように出し入れする形です。

- 幅 1100px で、右レールがドロワーになります。
- 幅 760px で、左レールもドロワーになります。

レールは、中身があふれたら、自分の中でスクロールします。

挙動の仕様（ブレークポイント・バックドロップ・レール内スクロール・目次の置き場の経緯）は、
[エディタ仕様.md](../旧文書/エディタ仕様.md) §9.1・§9.1.1 が正本です。

`.editor-block` と `.block-content` は、**エディタが挿す枠であって本文ではありません**。
保存するときに、シリアライザ（画面の内容を保存用の HTML に直す処理）が、これらを剥がします
（[エディタ仕様.md](../旧文書/エディタ仕様.md) 6.1.1）。

`.vocab-chrome` も同じです。シリアライザが読み飛ばすので、正本HTMLには入りません。
計算ビューなら、本文に残るのは、鏡の印 `<section data-mirror="子ページ一覧"></section>` 等と、印の中に人が書いたものだけです。

**本文DOMを走査する新しいコードは、`.vocab-chrome` を除外したか必ず確かめること。**
本文の `class` は、サニタイザ（保存の前に危険な HTML を取り除く処理）が必ず落とします。
だから、この判定が誤って当たること（誤爆）はありません。

### 2.4 表示モードによる差

| モード | 条件 | 見え方 |
|---|---|---|
| **閲覧モード** | 既定 | 本文は読み取り専用。ブロック操作・スラッシュメニューは出ない |
| **編集モード** | `body[edit-mode]` | 編集ロックを取得済み。本文が `contenteditable` になり、クロームの操作系が有効 |
| **匿名** | `body.anonymous` | 未ログインで実効公開ページを見ている状態。右レールと書き込み系UIはCSSごと隠れる |

**計算ビューは、どのモードでも同じ**です。

- 中身は、サーバーがページを返すときに埋めます。
  だから、閲覧モードでも匿名でも、JavaScript なしで表が見えます（[view_render.go](../../internal/cms/view_render.go)）。
- 編集モードでも、中身は `contenteditable`（その場で書き換えられる状態）になりません。エディタの持ち物ではないためです。
- そのぶん、**編集中の変化は自動では反映されません**。
  子ページを作っても、子ページ一覧のビューに現れるのは、再読み込みのあとです。
  描画ロジックを Go と JS の2箇所に持たないための割り切りです。
