# 【一覧】用語集

w-cms で使う用語の正本（いちばん正しいとする元の一覧）です。
利用者と開発者が、同じ言葉で話すために使います。

**業務の用語**（受注／発注・納品・部材…）と、**画面の用語**（レール・クローム・ブロック…）の両方を、ここに集めます。
設計・実装・ドキュメント・コミットメッセージ、そして会話で、**用語を統一**するために使ってください。

この文書は、3つの節でできています。

- **§1 業務の用語**: 「何を扱っているか」を指す言葉です。受発注・ものづくり・納品・通信記録を扱います。
- **§2 画面の用語**: 「どこの話をしているか」を指す言葉です。
  「左のパネル」「サイドバー」「メニュー」のような、曖昧な指し方を避けるために用意しました。
  実装は [assets/index.html](../../assets/index.html)、挙動の詳細は [エディタ仕様.md](../旧文書/エディタ仕様.md) §9 が正本です。
- **§3 基盤の用語**: 両者にまたがる土台の言葉です（ページ・正本性・語彙・計算ビュー）。

> **本文で使える形式（`data-type`）の一覧**は、[【一覧】語彙.md](【一覧】語彙.md) が正本です。
> 形式とは、表やブロックの種類のことです。【一覧】語彙は、語彙レジストリ（使える形式の登録簿）の鏡です。
> ここには、個々の形式は載せません。
>
> 2026-08-21 に、「画面構成と用語.md」を本ファイルの §2 へ統合しました。
> 用語の正本が業務用と画面用の2冊に分かれていて、どちらを引けばよいか分からなかったためです。

表の中には、`<table data-type="…">` のような HTML の書き方や、プログラムの中の名前も出てきます。
これらは開発者のための手掛かりです。言葉の意味を知りたいだけなら、「意味」や「説明」の欄を読めば足ります。

## 1. 業務の用語

この節の用語は、次の方針で決めています。

- **「発注書」という言葉だけでは、誰の立場で言うかによって意味が変わり、曖昧です。**
  たとえば顧客が出す発注書は、こちらから見れば、受け取る側の書類です。
  そこで、立場に依らない**役割語**（役割で呼ぶ言葉）で呼びます。
- **受け取る側と出す側の対は、`受注` ／ `発注` と呼びます**（2026-06-27 決定）。
  標準的で、曖昧さの無い言葉です。
  `注文` という案もありました。実在の「注文書」に根ざした言葉ですが、`受注` の教科書的な対義語である `発注` を選びました。
- **見積の2種は、`見積` ／ `見積依頼` と呼びます**（2026-10-02 に改めました）。
  - `見積` は弊社が顧客へ出すもの、`見積依頼` は弊社が業者へ出すものです。

    > 利用者:「弊社の見積もりを見積もり、業者への見積依頼の場合、見積依頼と明確に言葉を分けます」

  - 置き場も、トップ直下の「見積」と「見積依頼」に分かれます
    （[【要求】見積.md](../拡張/東邦/【要求】見積.md)・[【要求】見積依頼.md](../拡張/東邦/【要求】見積依頼.md)）。
  - それまでは、取引の性質で **`販売見積` ／ `購入見積`** と呼んでいました（2026-06-27 決定）。
    `売上/原価見積` という案は、「原価見積＝社内原価積算」と紛れるので避けました。
- **表の「実装・状態」欄の読み方**:
  **実装済み** とある語は、いまのコードに対応するものがあります。
  **設計中** とある語は、[【考察】通信記録処理.md](../考察/【考察】通信記録処理.md) などで検討中で、まだ実装していません。

|---|---|---|

| **見積依頼** | 弊社が業者（材料屋・加工業者）へ値段を聞くものです。業者の返事の単価（原価予定）も、そこに記録します。確定すると**発注**になります。2026-10-02 までの名は `購入見積` でした（業者が出す見積の側から呼んでいました）。 | 実装済み（2026-10-03〜10-05）：置き場は、トップ直下の「見積依頼」です。**見積依頼必要部材表**（`rfq-needs`）→ **見積依頼部材表**（`rfq-draft`）→ 業者ごとに1枚の**見積依頼書ページ**（`見積依頼／年／月`）と進みます。明細は**見積依頼明細**の表です（`rfq-items`。状態は 未回答／回答あり／辞退）。紙も**見積依頼書**（PDF）です。業者の返事の単価は、見積依頼明細の単価の列に記録します（「✓ 回答を記録」「🤖 返事を読む」）。貰った単価は、加工製品ページの「💴 見積回答」に並びます。材料表の**最新単価**（[【考察】材料の単価と価格の履歴.md](../考察/【考察】材料の単価と価格の履歴.md)）にも、買った記録の無い行にだけ「見積」の印つきで出ます。正本は [【要求】見積依頼.md](../拡張/東邦/【要求】見積依頼.md) です。顧客からの見積もりを起点にする入口は、まだありません。旧形式 `supplier-estimate` も、2026-09-18 に消えました |

**受発注の2×2（予定→確定）**:

| 段階 | 売上側（顧客と） | 原価側（仕入先と） |
|---|---|---|
| 予定（見積） | **見積** | **見積依頼**（業者の返事の単価） |
| 確定（発注書類） | **受注** | **発注** |

```
見積     ─(確定)→ 受注      （顧客と・売上側）
見積依頼 ─(確定)→ 発注      （仕入先と・原価側）
```

### 1.2 ものづくりの対象

| 用語 | 意味 | 実装・状態 |
|---|---|---|
| **加工製品** | **当社が図面をいただいて加工し、納めるもの**です（2026-09-17 利用者決定）。単品も組立品（Assy）も含みます。`item_id`（製品コード／図面番号）で見分けます。**`加工業者`（＝こちらが発注する外注先）から来たもの、という意味ではありません。** `外注加工` は、工程の一部を他社へ出したものです。`購入品`・`支給品` とともに、**加工製品の入力**です。 | 実装済み：次の3つです。①解析が作る**加工製品ページ**（`取引先／社名／加工製品／装置名称／図面名称`。2026-09-29 に段をやめ、試作・見積・旧型はタグ `区分` で表します）。②明細表の「品番」列（見出しが、レジストリの機械キー `item-id` へ解決されます）。③加工製品ページの可変タグ（`<dl data-type="tags">`）の `図面番号`・`品番`・`部品番号`。品番で加工製品ページを探すときは、この3つを見ます（設定 `product_code_tags`。[受注から利益まで §5](../旧文書/【ユースケース】受注から利益まで.md)） |
| **弊社品番** | **弊社の中では、これが正しいキー**（品物を1つに決める番号）です。2026-09-21 利用者:「品番でも弊社品番でも検索して紐づけられると思いますが、**弊社の中では品番ではなく弊社品番が正しいキー**という意味です」。値は**加工製品ページのページ番号**です。**`品番`（お客様の言葉）とは別の列**です。`品番` は、**結びつけるための手掛かり**にすぎません。お客様ごとに付け方が違い（図番を品番として送ってくる客先もあります）、**同じ番号で別の加工製品**もありえます。⚠ だから、**機械が結ぶのは候補まで**で、`弊社品番` を書くのは人です。 | 実装済み：受注明細・発注明細の `弊社品番`（`ref` 型）、`品番` からの自動埋め（`LinkProductsToOrder`）、手配集計の突き合わせ（`ProcurementByProduct`） |
| **部品** | **お客様の装置の中での位置づけ**を指す言葉です。同じものが、当社から見れば加工製品、お客様から見れば装置の部品です（「顧客 ＞ 完成品機種 ＞ 部品」。[コンセプト.md](../旧文書/コンセプト.md)）。`構成部品`（材料・購入部品・外注加工）は、**加工製品を作るための入力**です。これも部品と呼びます。 | 用語として維持しています。ページの肩書は、2026-09-17 に**加工製品ページ**へ改めました。単品も組立品も収まり、当社が売るものだと読めるためです |

### 1.3 納品・進捗

| 用語 | 意味 | 実装・状態 |
|---|---|---|
| **納品** | 受注に対して品物を納める出来事（イベント）です（◯月◯日に N 個）。 | 設計中（[通信記録メモ §4.3](../考察/【考察】通信記録処理.md)・[【要求】納品フォルダ.md](../拡張/東邦/【要求】納品フォルダ.md)）。納品の出来事を1件ずつ記録する仕組みと、納品書は、まだありません。いま在るのは、受注明細の `出荷済み` の列（納めた数の合計を人が書きます）と、「納品書発行」の印だけです |
| **分納** | 1つの受注を、**複数回に分けて納品**することです。充足（どこまで納めたか）は、`受注数 − Σ納品済数 = 残` で集計します。 | 一部実装：残は、受注明細の `数量 − 出荷済み` で計算します（受注残表）。何回目にいくつ納めたか、という回ごとの記録は設計中です |
| **進捗（status）** | 部品ごとの状態です。決まった選択肢から1つを選ぶ形（単一enum）です。選択肢は、受注明細＝未着手/加工中/検査中/納品済/完了、発注明細＝未発注/発注済/納品済/取消 です。受注明細の `完了` は、「もう受注残に出さない」という人の宣言です。どこまで納めたかは、状態ではなく、数（`出荷済み` の列）で持ちます。 | 実装済み（enum）：明細表の「状態」列です（機械キー `status` へ解決されます）。選択肢の正本は、設定 [config/settings.json](../../config/settings.json) です（`vocabulary` の `状態` が既定で、発注明細は `table_vocabulary` の例外です。2026-09-25）。語彙レジストリ（`ext/toho/vocab.go`）にも同じ選択肢があり、試験が食い違いを見張ります |
| **受注残** | まだ納品し切っていない受注の残数です（`現在の受注数 − Σ納品済数`）。**納品では受注数を書き換えず**、残が計算で減ります。一方、**受注変更では受注数そのものを改訂**できます（文書ベースゆえの柔軟性です）。**計算ビュー**（§3）として集計して見せます（保存はせず、DBから導き出します）。 | 実装済み（2026-09-21）：計算ビュー**受注残**（`order-backlog`。画面では「受注残表」）です。受注フォルダのトップに置きます。残っている行（`数量 − 出荷済み > 0`。状態が `完了` の行は除きます）を、顧客×納期ごとに1枚の表にします（`ext/toho/backlog.go`） |
| **納期** | 納品の期限です。**部品（明細）単位**で持ちます（受注全体ではなく、明細の行ごとです）。 | 実装済み：受注明細の `納期` の列です（行ごと）。受注ページ・発注書ページのタグにも `納期` があります。型は text です（2026-09-23 の決定）。日付として読めない書き方（「9月末」など）も書けます。そのかわり、索引では日付として並べ替え・範囲検索できません。受注残表は、プログラムの中で日付に直してから並べます |
| **納期ビュー（生産スケジュール）** | 残のある明細を、納期の早い順（昇順）に並べた計算ビューです（受注残×納期）。製造の優先順位を付けるのに使います。 | 実装済み：受注残表が、この役目を担います（顧客×納期ごとの表を、納期の早い順に並べます。日付として読めない納期は、先頭にまとめます。`sortBacklogGroups`）。「納期ビュー」という名前の、別の計算ビューはありません |

### 1.4 通信記録まわり（通信箱・`.eml` 取り込み・🤖解析は 2026-09-01 に実装。残りは設計中）

- 幅 760px で、左レールもドロワーになります。

[エディタ仕様.md](../旧文書/エディタ仕様.md) §9.1・§9.1.1 が正本です。
ブレークポイントは、形が切り替わる画面の幅のことです。バックドロップは、ドロワーの後ろに敷く幕のことです。

| **語彙クローム** | `.vocab-chrome` | 本文の中に**混ざって見えるが保存されない**DOM（画面の部品）です。用途は3つです。①計算ビューと鏡の中身（サーバー事前描画が埋めます。業務のボタンもここに入ります）。②エンハンサが付ける付帯UI（PDFプレビュー・ドロップゾーン など）。③閲覧モードの添付クローム（📎リンク横の「▶ 表示」「▶ 中身」「🔗 参照」「🤖 解析」と、展開したプレビュー・目録）。本文の直下へ飾り付けを足すコードは、必ず `.vocab-chrome` を付けます。付けないと、本文として保存されます |

`.editor-block` と `.block-content` は、**エディタが挿す枠であって本文ではありません**。
保存するときに、シリアライザ（画面の内容を保存用の HTML に直す処理）が、これらを剥がします
（[エディタ仕様.md](../旧文書/エディタ仕様.md) 6.1.1）。

`.vocab-chrome` も同じです。シリアライザが読み飛ばすので、正本HTMLには入りません。
計算ビューなら、本文に残るのは、鏡の印 `<section data-mirror="子ページ一覧"></section>` 等と、印の中に人が書いたものだけです。

**本文DOMを走査する新しいコードは、`.vocab-chrome` を除外したか必ず確かめること。**
本文の `class` は、サニタイザ（保存の前に危険な HTML を取り除く処理）が必ず落とします。
だから、この判定が誤って当たること（誤爆）はありません。

### 2.4 表示モードによる差

| モード | 条件 | 見え方 |
|---|---|---|
| **書ける形** | `body[edit-mode]`（スイッチ「閲覧」がオフ） | ページを開くと、最初から書けます（書く権限のある人が、パソコンで開いたときの既定です）。本文が `contenteditable` になり、ブロック操作・ツールバー・スラッシュメニューが使えます。画面は、編集権（ページ単位のロック）を取りません。保存は `POST /api/sync` で、ブロック単位です。保存するのは、ブロックを去る・タブを隠す・ページを去るときです。同じブロックを2人が同時に書くと、そのブロックの上に枠が出て、両方の版が並びます。違うブロックは、黙って合わさります。業務のボタン（鏡のボタン）も押せます。押す前に、書きかけを保存します |
| **閲覧モード** | `body` に `edit-mode` が無い（スイッチ「閲覧」がオン） | 読むだけです。本文は打てません。ブロック操作・ツールバー・スラッシュメニューは出ません。閲覧モードだけの働きは、表の並べ替え・見出しで畳む・カルーセル・画像の拡大・機械向けのタグを畳む・添付のクリック展開・表の印刷です。スマホは、初めは閲覧モードです。書く権限の無い人は、いつも閲覧モードです（スイッチも出ません） |
| **編集モード** | （2026-10-12 までの呼び名） | 2026-10-12 までは、ページ単位で編集権（編集ロック）を取ってから書く形でした。1人だけが書けました。同日にやめて、いまの「書ける形」になりました。CSS と JavaScript の `edit-mode` という属性の名前は、昔のまま残っています。古い文書と変更履歴に出てくる「編集モード」は、この形のことです |
| **匿名** | `body.public`（[assets/public.html](../../assets/public.html)） | 未ログインで実効公開ページを見ている状態です。サーバーが、編集用の殻ではなく、**公開専用ビュー**を返します（`RenderPublicShell`）。レールも書き込み系のUIも JavaScript も、配りません。編集用の殻の CSS にある `body.anonymous` は、その前の方式の名残です（殻が匿名に届いたときの備えとして残っています） |

どちらの形で開くかは、スイッチ「閲覧」を押した形を、その端末に憶えます（ブラウザの `localStorage` の `wcms.mode`）。
決定の経緯は [【考察】編集モードの再考.md](../考察/【考察】編集モードの再考.md) §6〜§8、要求は [【要求】ページとエディタ.md](../【要求】ページとエディタ.md) §3 にあります。

編集ロックの口（`/api/lock`・`/api/unlock`・`/api/lock/force`・`/api/save`・`/api/save-block`）は、道具のために残っています（ワンノートの製造・テンプレートの取り込み・E2E）。画面は使いません。

**計算ビューは、どのモードでも同じ**です。

- 中身は、サーバーがページを返すときに埋めます。
  だから、閲覧モードでも匿名でも、JavaScript なしで表が見えます（[view_render.go](../../internal/cms/view_render.go)）。
- 書ける形でも、中身は `contenteditable`（その場で書き換えられる状態）になりません。エディタの持ち物ではないためです。
- そのぶん、**書いている最中の変化は自動では反映されません**。
  子ページを作っても、子ページ一覧のビューに現れるのは、再読み込みのあとです。
  描画ロジックを Go と JS の2箇所に持たないための割り切りです。
