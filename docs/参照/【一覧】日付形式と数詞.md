# 【一覧】日付形式と数詞

日付の書き方と、数の後ろ（や前）に付く言葉や記号を、調べてまとめた一覧です。
取り込んだ文書の表記をそろえる（正規化する）ときの、設計の材料にします。

この一覧は、DBスキーマ設計し直しの設計材料として作りました。
もとになったのは、D-3「**正規化はPDF取り込み時に行い、認識できた形式は背景色で示す**」です。
D-3 は、この一覧を作った 2026-08-30 には判断待ちでした。そのあと決定になり、実装も済んでいます
（背景色は 2026-09-01、取り込み時の正規化は 2026-09-04。[アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) §9。いまの対応は §4）。
**取り込み時の正規化と、語→型辞書・単位込み数量の設計**が、この一覧を参照します。
語→型辞書は、見出しの言葉から、その列の型（日付・数値など）を決める辞書のことです。

- **調査日**: 2026-08-30。
  - SQLite の受理形式（受け付ける形式）は、**実測**しました。
    SQLite **3.51.2**（`modernc.org/sqlite`＝本番と同じドライバ）で、`SELECT date(?)` へ各形式を渡して確認しています。
  - 各国の形式と数詞は、一般知識を整理したものです（2026-08 時点）。
- **決定（2026-08-30）: 日時の表記は ISO 8601 を w-cms 全域の正とする。**
  日付のみなら `YYYY-MM-DD`、時刻付きなら `T` 区切りです。
  利用者がプラグイン等で別の表記に対応するのは自由です。
  正本は [【要求】運用.md](../【要求】運用.md) §1〜§2 です。
- いまの実装がどこまで対応しているかは、§4 にまとめました（`normalizeDate`・見出し語の辞書 `vocabulary`・`normalizeNumber`）。

## 1. SQLite が扱える日付形式（実測）

SQLite は、w-cms が使っているデータベースです。

SQLite に、日付の**型**はありません。
日付は、TEXT（文字）/ REAL（小数）/ INTEGER（整数）のどれかで持ちます。
日付の**関数**（`date()`・`datetime()`・`strftime()` 等）が、特定の書式だけを日付として解釈します。

| 入力 | `date()` の結果 | 備考 |
|---|---|---|
| `2026-06-15` | ✅ `2026-06-15` | **ゼロ詰め必須の ISO-8601** |
| `2026-06-15T14:30:05` | ✅ | **ISO 8601 準拠の時刻付き**（区切りは `T`。`:SS`・`.SSS` も可） |
| `2026-06-15 14:30` | ✅ | ⚠ **空白区切りは ISO 8601 ではない**（規格の区切りは `T`）。これは **SQL 標準の TIMESTAMP リテラル**の流儀で、SQLite はどちらも受ける |
| `2026-06-15T14:30:05Z` / `+09:00` | ✅ | タイムゾーン接尾辞も可 |
| `now` | ✅ 現在日 | `'localtime'`／`'utc'` 修飾子と併用 |
| `2461847.5`（数字列） | ⚠ `2028-03-17` | **ユリウス日として解釈される**（下の罠） |
| `1780000000` ＋ `'unixepoch'` | ✅ | UNIX秒は修飾子が要る |
| `2026-6-15`（桁詰めなし） | ❌ NULL | **1桁の月日は通らない** |
| `2026/06/15` | ❌ NULL | スラッシュ不可 |
| `2026.06.15` / `15.06.2026` | ❌ NULL | ドット不可 |
| `20260615` | ❌ NULL | 区切りなし不可 |
| `06/15/2026`（米式） | ❌ NULL | |
| `2026年6月15日` / `R8.6.15` | ❌ NULL | 和文・和暦不可 |

**要点**:

1. **日本の業務文書に現れる形は、ほぼ1つも直接は通りません。**
   取り込み時の正規化が必須です。
   D-3 の決定「入り口で揃える」は、この実測と合っています。
2. **正規化の出力は、ゼロ詰め `YYYY-MM-DD` 一択です。**
   - SQLite の関数が、そのまま読めます。
   - **TEXT の辞書順比較＝時系列順**になります（文字として比べた順が、日付の順と同じになります）。
     `BETWEEN '2026-01-01' AND '2026-12-31'` が効くことを、実測で確かめました。
   - 人が読めて、grep（文字の検索）も効きます。「文書が主」と同じ考え方です。
3. **罠: 数字だけの文字列を日付関数へ渡すと、ユリウス日になります**（`"2461847.5"` → 2028-03-17）。
   ユリウス日は、天文学などで使う、日数の通し番号です。
   「日付らしき値」を、未検証のまま SQLite の日付関数へ渡してはいけません。
   **正規化済みの値だけを日付として扱う**こと。
4. 扱える範囲は、`0000-01-01`〜`9999-12-31` です。
   うるう秒はありません。グレゴリオ暦（いまの暦）を、過去へも外挿します（そのまま当てはめます）。

## 2. 各国の一般的な日付形式

| 方式 | 例 | 主な使用地域 | 備考 |
|---|---|---|---|
| ISO 8601 | `2026-06-15` | 国際規格・技術文書 | w-cms の正規形 |
| 年月日（和文） | `2026年6月15日` | 日本・中国 | 中国は `2026年6月15日` も `2026-06-15` も |
| 年/月/日 | `2026/06/15`・`2026/6/15` | 日本 | **年が先頭なら曖昧性なし** |
| 和暦 | `令和8年6月15日`・`R8.6.15` | 日本（役所・帳票） | 換算表は下 |
| 月/日/年 | `06/15/2026`・`6/15/26` | 米国 | |
| 日/月/年 | `15/06/2026` | 英国・仏・豪ほか多数 | |
| 日.月.年 | `15.06.2026` | 独・露・北欧ほか | |
| 年. 月. 日 | `2026. 6. 15.` | 韓国 | `2026년 6월 15일` も |

**曖昧性の核心は「01/02/03 問題」です。**
同じ書き方が、米式なら2003年1月2日、欧式なら2003年2月1日、ISO短縮なら2001年2月3日と読めます。
判定規則として使えるのは、次の2つです。

- **先頭が4桁なら年です**（`2026/6/15` は Y/M/D と断定できます）。
  日本のスラッシュ形は、ほぼ常にこの形です。だから、実務上の曖昧性は低いです。
- 2桁始まり（`6/15`・`15/06/2026`）は、**文脈（地域・書き手）が無いと決められません**。
  日本の社内文書の `6/15` は、月/日＋年省略が通例です。

**和暦の換算**（元年＝1年）:

| 元号 | 記号 | 西暦の始まり | 換算 |
|---|---|---|---|
| 明治 | M | 1868 | 明治N年 = 1867+N |
| 大正 | T | 1912 | 大正N年 = 1911+N |
| 昭和 | S | 1926 | 昭和N年 = 1925+N |
| 平成 | H | 1989 | 平成N年 = 1988+N |
| 令和 | R | 2019 | 令和N年 = **2018+N** |

**実データ（板金部ノート）で観測された形**は、次のとおりです。

- `2026-06-15`（自由文中・ISO準拠！）
- `2024-08-20`
- `2024-09-XX`（**日未定**の月表記・セクション名）
- `2025-10-27`

納期には、「9月末」「上旬・中旬」のような**範囲語**（幅のある言い方）も来ることがあります（希望納期タグは自由記入です）。
これらは、単一の日付へ正規化できません。
だから、**正規化不能として原文のまま**にするのが、正しい扱いです。
値の正本は常に原文で、`norm_value`（正規化した値）は併記する、という既存の決定とも合います。

## 3. 数値の後に付く数詞（と、前に付く記号）

### 3.1 助数詞（個数を数える語）

製造・受発注で現れる、主なものです。

| 助数詞 | 数えるもの | 備考 |
|---|---|---|
| 個 | 汎用（部品） | 最頻。実測: `5個`・`60個単位` |
| 本 | 細長い物（丸棒・パイプ・ボルト） | |
| 枚 | 薄い物（**板**・シート） | 板金業の主役 |
| 台 | 機械・装置 | 実測: `一台15分程度` |
| 組・対・セット | 組み合わせ | |
| **式** | 一式（まとめて1つ） | **見積の単位として頻出**（`一式` は数量1の意味） |
| 点・件 | 品目・案件 | |
| 束・巻・箱・袋・缶 | 荷姿 | |
| 基・脚・面・丁 | 据え付け物・脚物ほか | |
| ロット | 製造単位 | 実測: `ロット20`（**列名にも埋まる**） |
| ~~球~~ | — | ⚠ **誤りだった**。`170球` は**図面名称の一部**（品名）で、数量の助数詞ではない（2026-09-04 ユーザー指摘）。「運用者固有の助数詞は無限にある」の実例として挙げていたが、**この根拠は無い** |

### 3.2 単位（計量・通貨）

| 分類 | 単位 | 備考 |
|---|---|---|
| 通貨 | 円・万円・千円 | `3,500円`・`1.2万円`。**単位なしの円も多い**（実測: `3500`・`1172` が円） |
| 長さ | mm・cm・m | **図面は mm が既定で単位省略が普通**（実測: `t9*44*360` ＝板厚×幅×長さ・全部mm） |
| 重さ | g・kg・t（トン） | ⚠ 板金の `t` は**板厚**が優勢（下の前置記号） |
| 面積・体積 | mm²・m²・L・cc | |
| 時間 | 分・時間・日・週・ヶ月・年 | 実測: `30時間`・`90分` |
| 率・角度 | %・割・度 | |
| 回転数など | rpm | 実測: `892rpm` |

### 3.3 前置の記号（数値の**前**に付く）

| 記号 | 意味 | 実測例 |
|---|---|---|
| ¥ | 円 | `¥8,000`（`normalizeNumber` が対応済み） |
| Φ・φ | 径 | `Φ410`・`Φ50.5` |
| **t** | **板厚**（mm） | `t2.3`・`t4.5`・`t9*44*360` |
| R | 半径・（文脈により）曲げR | |
| M | ねじの呼び径 | `M8`・`M10` |
| l= | 長さ | `PS-314-3(l=884)` |
| No. | 番号 | 明細表の列 |

**前置記号の値は、「数量」ではなく「仕様値」です。**
Φ410 は、個数ではなく、寸法の属性です。
数値として抽出することはできますが、意味は列見出し（見える文字）が決めます。
ここでも、「鍵は見出し」の原則が効きます。

### 3.4 パースを難しくする表記（正規化の敵リスト)

パースは、文字を読み取って、数や日付として解釈することです。

- **桁区切り**: `3,500` ／ **全角数字**: `５個` ／ **漢数字**: `五個`（表では稀）
- **万・千の混在**: `1万2000円`・`1.2万円`
- **範囲**: `5〜10個`・`5-10個` ／ **約**: `約20`・`20程度`・`20くらい`（実測: `深さ8.5程度`）
- **複合単位**: `円/個`（単価）・`個/台`（員数）
- **数値と単位の複合語**: `60個単位`（「60個ずつ買う」＝数量ではなく条件）

## 5. 比較の三分類（2026-08-30 ユーザー確認）

> 2026-08-30 利用者:「SQLiteに格納する場合、文字列として比較、数値として比較、時間として比較の三分類で良いでしょうか」

答えは、**意味の分類としては3つで正しい**、です。
SQLite に日付型は無いので、格納クラス（値をしまうときの種類）は、実質2つ（TEXT と数値）に落ちます。
意味の型3つは、その上に乗ります。

| 分類 | 格納 | 注意 |
|---|---|---|
| 文字列 | TEXT | 比較はバイト順（BINARY 照合）。等値・前方一致は十分だが**五十音順にはならない**。全角/半角は比較前に正規化（取り込みの担当） |
| 数値 | **INTEGER / REAL** | **TEXT に入れると壊れる**（`"8000" < "900"`）。格納の仕方は**表によって違います**。`vocab_index` は `norm_num REAL` へ分離（2026-08-30・下の (b) 案）。**`page_tags` は `norm_value` の宣言型を外して1列に混在**（2026-09-15・下の (a) 案）。`CAST` は非数値→0.0 の罠があり不採用 |
| 時間 | TEXT（ゼロ詰めISO） | 正規化済みなら**文字列比較に畳める**（`BETWEEN` 実測済み）。分類として独立させる価値は比較でなく**検証・正規化規則・UI**の側 |

ほかの種類の値も、この三分類に乗ります。

- enum（状態）: 文字列の等値で比べます。進行順は業務知識なので、DBへ持ち込みません。
- 真偽: enum の特殊形です。
- 期間・工数（90分）: **数値**です（時点ではありません）。
- 仕様値（Φ410）: 数値です。

**採らない4つ目**: 自然順です（Rev.2 < Rev.10 と並べる順。文字列比較では逆転します）。
この規模で必要になる根拠が無いので、明示的に不採用としました。

数値を数値クラスで持つ実装には、2つの案がありました。

- (a) `norm_value` 1列に混在させる案です。
  SQLite の柔軟型付けでは正当な形で、数値は常にテキストより前に整列します。
- (b) `norm_num REAL` へ分離する案です。

これは**内部判断**として、設計時に決めることにしていました。分離のほうが自己文書的（見れば意味が分かる形）で、有力でした。
結果は、**(b) を採用・実装済み**です
（2026-08-30。[vocab_index.go](../../internal/cms/vocab_index.go) の `vocab_index.norm_num REAL`）。

**2026-09-15 に `page_tags` だけ (a) へ移しました**（利用者の決定です）。

> 利用者:「norm_value は文字列、数値、時刻のような種類が考えられます」

同じ表で2つの案が並ぶのは気持ちが悪いようですが、**2つの表は形が違います**。

- `vocab_index` の `norm_num` には、読み手が実在します（`vocabRows` の集計が、列ごとに数を取ります）。
- `page_tags` には、読み手が居ませんでした。

タグは「名前が型を決める」ので、**1つの問いの中では型が揃い**、混在が問題になりません。

(a) で確かめたこと（実測・`modernc.org/sqlite`）:

| | 並び | 範囲を数で | 範囲を文字列で | 索引 |
|---|---|---|---|---|
| 宣言 `TEXT` | `12.5, 8000.0, 900.0, abc` **←壊れている** | 2件 | 2件 | 効く |
| **宣言なし** | `12.5, 900, 8000, abc` | 2件 | **0件**（静かに） | 効く |

⚠ **(a) の代償は右から2列目**です。**型を取り違えると、エラーにならず0件**になります。

だから、束ねる形（SQL へ値を渡すときの型）の判断は、`tagNormBind` の1か所に閉じています。
書き手と読み手が、同じ関数を通ります
（[page_tags_norm_type_test.go](../../internal/cms/page_tags_norm_type_test.go) という試験が、これを固定しています）。

**`vocab_index.norm_num` の統合は別途**です。読み手が実在するので、移すなら集計の側から進めます。
