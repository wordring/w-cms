## 可変タグは名前：値の1対と決める（2026-08-26）

ユーザー決定:「**名前：値のタグは、値を複数持てません。値を複数持てるのは、また別の
形式だと思います**」。従来のコメントは「1つの dt に複数 dd を並べてよい」と逆の設計を
明文化していたため、決定へ揃えた——タグ1つ＝名前1つ＋値1つ。同名が要るときは
**対の繰り返し**（各タグは1値のまま）。複数値を持つ情報は別の形式（将来）。
エディタは元から対単位でしか作らないため実装コストはゼロで、手書きの複数 dd は
拒否せず名前の繰り返しとして寛容に読む（エコーバックの流儀）。
インラインの配置（チップが横に流れて折り返す）はチップ表示が既にその形。
**文章の行内に置く**インラインタグは dl では表せないため、必要になれば別形式として設計する。

## 可変タグをチップ表示にする（2026-08-26）

実機確認中のユーザー要望「定義リストそのままというより、名前：値の一つのタグとして
扱いたい。左に名前、右に値で、タグとわかるように角丸四角形で囲ってあるような見た目」。
`dl[data-type="tags"]` **専用**のCSSで、dt（名前・薄い地）と dd（値・白地）の隣接する
2要素を角丸で1つのチップに見せる。**マークアップは dt/dd のまま**——見える文字＝鍵の
原則・サニタイザ・索引はすべて無変更で、見た目だけの変換。編集側（app.css）と
公開ビュー（public.css）の両方に入れた。見積もり系の dl はリスト表示のまま。
編集操作は元から対（dt＋dd）単位なので、概念の変更もこれで見た目と揃った。

## スラッシュメニューの到達性——絞り込み・分類・頻度順（2026-08-26）

[エディタ仕様.md](エディタ仕様.md) §3.1 に残っていた最後の1点。語彙は最終的に100種規模になる
（[要件定義書.md](要件定義書.md) §1.2）ので、全項目を1列に並べる形では選べない。

- **絞り込み**——`/` に続けて打った文字がそのまま検索語になる（`/部材` のように打つ）。
  表示名・形式名（kebab-case）・分類のどれかに部分一致すれば残る。形式名でも引けるのは、
  日本語入力へ切り替える前にローマ字で打ち始める使い方を拾うため。
  **入力欄は置かなかった**——フォーカスを移すと `contenteditable` のキャレットが失われ、
  選んだあとの挿入先を見失うからで、ブロックの文字をそのまま検索語にするほうが素直だった。
- **分類**——レジストリの `category` で束ねて見出しを出す。**分類の並びは宣言順で固定**し、
  動くのは分類の中だけにした。分類ごと動かすと「昨日と場所が違う」状態になり、
  覚えて選ぶ使い方ができなくなる。
- **使用頻度順**——使った回数を UI ストア（`wcms.ui.slashUse`）に貯め、その分類の先頭へ寄せる。
- 選んだときは**絞り込みに打った文字を本文から消す**。置き換え型の項目では自然に消えるが、
  画像のように「後ろへ挿す」項目では `/画像` が本文に残ってしまう。

罠を1つ書き留めた——**項目の click / mouseenter は項目を作るたびに配線する**こと。
絞り込みのたびにメニューを組み直すので、初期化で一度だけ配線すると外れる。

## パーサとプラグインの回覧化（2026-08-26）

本文HTMLを処理する3経路（保存時の索引・表示時の計算ビュー・新規作成時のテンプレート新規化）を
**1つの回覧機構**へ寄せた。設計は 2026-08-25 に委嘱された [パーサとプラグイン.md](パーサとプラグイン.md)
で、その §9 の実装順どおり6段すべて完了（実装完了に伴い `【考察】` を外した）。

**何が変わったか**——各プラグインが木を丸ごと受け取って自前で走査していたのをやめ、
**コアの配送係が1回だけ歩き**、引き金（いまは `data-type`）に当たった要素だけを担当へ届ける。
`p` や `h2` のような大半のタグでは誰も呼ばれず、引き金のある要素でも呼ばれるのは表引きで
当たった担当だけ。プラグインから DOM 走査コードが消えた。

- `Plugin` インターフェースから `Sync(tx, pageID, root)` が消え、テーブルの所有だけを宣言する。
  本文の読み取りは `Observer`（`Triggers` / `OnPageStart` / `OnElement`）が担う。
- **除外が規約から事実へ**——`.vocab-chrome` の中は配送係がそもそも歩かないので、各ハンドラが
  「クロームを飛ばす」ことを覚えている必要が無い。作業引き継ぎの勘所に「必ず確かめること」と
  書かれていた罠が構造ごと消えた。
- **テンプレート領域の除外が定義から正しくなった**——従来は「空の本文を渡す」工夫で
  「DELETE だけ走って新規挿入なし」を作っていたが、いまは `OnPageStart` は呼んで**要素イベントを
  1つも発火しない**だけで同じ意味になる。
- **最小権限を型で表した**——観察係の `ObserveContext` に `Replace` は無く、鏡型の `MirrorContext` に
  書き込みDBは無い（`ReadOnlyDB` インターフェース）。「派生→正本の逆流」（2026-08-21 に一度踏んだ）が
  コンパイル時に不可能になる。設計は単一の `Handler` を描いていたが、この意図は段ごとに別の
  受け口を持たないと表現できないので、そこだけ設計から変えた。
- **引き金の解決は `triggerOf` の1関数に隔離**。機能見出し（語彙モデル §11・未決定）が採用された
  ときに差し替わるのはそこだけで、本機構は決定を待たずに動く。

**未決だった2点はこう決めた**（どちらも設計の推奨どおり）:

- **`descend` の既定は true**。ただし配送係は「**全員**が降りないと言ったときだけ降りない」（OR）。
  観察係どうしは独立で書く先も別テーブルなので、受注の観察係が明細表を丸ごと読んでも
  ②汎用索引は同じ明細表を自分でも索引する必要がある。**AND にすると索引が静かに欠ける**ため、
  `TestObserversSeeNestedItemsTable` で固定した。
- **観察係のエラーは保存を止める**（現行維持）。索引の欠けは「黙って壊れる」の芽なので、
  書き手にその場で知らせる。

**ページ全体を見る用途には `ctx.Tag(name)`** を用意した（部材の `part_id`。タグが表より後ろに
あってもよいので文書順の回覧では拾えない）。**木そのものは渡さない**——渡すと「各自が自前で歩く」
形へ逆戻りし、除外規則の一元化を失うため。

**意図的に変えた挙動が1つ**——旧走査は `.vocab-chrome` の中も索引していた（各自が除外を覚える
方式だったので、②汎用索引は覚えていなかった）。新方式では索引されない。**修正であって退行ではない**
ので、同値性テストでそこだけ期待を分けている。

検証は設計 §8 の流儀どおり: 同値性テスト（②汎用索引が旧走査と同じ行を書くことを7通りの本文で
確認）・配送係そのもののテスト・既存の固定資産（`go test ./...` と E2E 9本）。
[【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md) も新しい書き方へ全面更新した。

## 形式ごとの視覚的区別——形式名の札（2026-08-26）

[【考察】語彙モデル.md](【考察】語彙モデル.md) §10 の未実装項目。2026-08-21 の決定
「**`data-type` の改名を許す**」（§9）は**見た目で形式を区別できること**を前提条件にしていたが、
実際に出ていたのは全形式共通の破線枠だけで、**改名しても見た目が変わらなかった**
——前提が成り立っていなかった。

各形式ブロックの直前に、レジストリから引いた**形式名の札**を出すようにした
（`decorateVocabBlocks`）。宣言の無い形式は**赤い「⚠ 未定義の形式「○○」」**になり、枠の破線も
赤へ変わる。ユーザーの言葉「区別できるなら、変更者は壊れることを理解できる」に対する答えは
**名前を出すこと**で、保存時の赤いトースト（2026-08-25）と同じ事実を**起きた場所で**示す。

- **色分けは形式ごとではなく「既知／未定義」の2値**にした。100種規模で色を配ると見分けが
  付かなくなるうえ、色と形式の対応を覚える必要が出る。改名の検知という目的にも名前のほうが直接効く。
- 出すのは**編集モードだけ**（閲覧・公開ページには出さない）。札は `.vocab-chrome` なので保存に漏れない。

実装で2つ踏んだ罠を、仕様として書き留めた（[エディタ仕様.md](エディタ仕様.md) §3.2）:

- **トップレベルの札を `.block-content` の中へ入れてはいけない**。安全化のエコーバック
  （`applySanitizedHtml`）が `content.firstElementChild` を「そのブロックの実体」とみなすので、
  札が先頭に来ると**札を本文と取り違えて差し替え、ページ全体が編集不能になる**
  ——2026-08-21 に直した不具合の再来で、`verify-editor-loss.js` が実際に検出した。
  トップレベルの札は `.editor-block` の中・`.block-content` の外へ置く。
- **変化が無ければDOMを触らない**こと。本文DOMの変化は MutationObserver → 自動保存 →
  `buildToc` → 札の付け直し、と巡ってくるので、毎回作り直すと輪が止まらない。

## 保存済み文書の版管理（リビジョン／リバート）（2026-08-26）

[【考察】アンドゥ・リドゥ.md](【考察】アンドゥ・リドゥ.md) §4・§5 の設計案をそのまま実装した。
2026-08-21 に**帳票の5年保持**を引き受けた要件でもある（監査ログでは「その時点の中身」を
持てないため）。

置き場は正本と同じファイル層（`data/master/<prefix>/<id>/versions/`）。**正本＝ファイル／DBは派生**
なので、**リバートは「古いHTMLをもう一度保存する」だけ**で済み、`Sync` が派生を作り直す。
悲観ロックで1ページ＝単一書き手なので履歴は線形（マージ不要）。

**未決だった5点はこう決めた**（詳細と理由は [【考察】アンドゥ・リドゥ.md](【考察】アンドゥ・リドゥ.md) §4 の表）:

- **コアレッシング**——同じ編集者の連続保存は**10分ひとまとめ**。編集者が変わったら必ず切る。
  加えて**ロック解放時に明示チェックポイント**を打つ（窓の内側で編集を終えた人の最終形を残すため）。
- **プルーニング**——**5年より古い版を消す**。年限だけで切り、世代数の上限は設けない。
  うるう年で目減りしないよう 366 日で数え、端数は必ず**長い側**へ倒す。
- **実装**——標準ライブラリ（`compress/gzip`）。各版は `<版ID>.html.gz` ＋ `<版ID>.json` の
  2ファイルで**自己完結**し、1つ壊れても他へ波及しない。版IDは時刻由来で、**利用者名は
  ファイル名に入れない**（w-cms は利用者名に文字種の制限を掛けていないため）。
- **リバートUI**——右レールの「🕘 版の履歴」。編集モードでのみ「この版に戻す」が出る。
  一覧は**開いたときに取り直す**（オートセーブのたびに取りに行くと1〜2秒ごとの余計な往復になる）。
- **5年保持の対象**——**全ページ一律**。帳票だけに絞るには「どれが帳票か」の判定が要り、
  その判定がずれると保持義務のほうが破れる。

**対象は本文HTMLだけ**（設計 §5）。サイドカー（親・所有者・権限・公開）と添付バイナリは対象外で、
これは容量の都合ではなく**安全のための線引き**——リバートで過去の権限や親が復活しないこと＝
「古い版に戻す」が権限昇格やページ移動の抜け道にならないことを構造的に保証する。

細かいが効く判断:

- **重複した版は作らない**（内容の SHA-256 が最新版と同じなら何もしない）。明示チェックポイントが
  重なっても無駄に増えない。
- **リバートの前に「いまの内容」を必ず残す**ので、リバートそのものも取り消せる。
- **書き戻す本文もいまの許可リストでサニタイズし直す**。過去の版は当時の許可で通ったものなので、
  素通しにはしない。版の取得API（`/api/version`）も `text/plain` ＋ `nosniff` ＋サニタイズで返す。
- **版IDは時刻由来の形しか受け付けない**（`/`・`\`・`.` を含むものは拒否）。APIの引数として
  外から来るので、ページのフォルダの外を指させないため。
- 派生索引の再構築は `versions/` へ**降りない**。いまの版は `.html.gz` なので `.html` の判定には
  掛からないが、手で置かれた `versions/foo.html` が「ページ」として索引に載らないよう明示的に閉じた。
- 版の記録に失敗しても**保存そのものは止めない**（履歴が取れないことを理由に書けなくするほうが
  害が大きい。監査記録と同じ判断）。

**まだ無いもの**: 表示用の diff（版どうしの差分表示）、容量の実測。添付の実体は戻らない（設計どおり）。

検証は Go テスト（`version_test.go`）と E2E（`e2e/verify-version.js`・17項目）。

## 公開ウェブサイトとしての体裁——公開専用ビュー（2026-08-26）

[要件定義書.md](要件定義書.md) §4.4 の「公開ページ専用レンダリング」を実装した。
**匿名の要求には編集用クロームを一切含まない殻**（`assets/public.html` ＋ `assets/public.css`）を返し、
認証済みには従来どおり編集できる殻（`assets/index.html`）を返す。分岐は**認証済みかどうかの1点だけ**で、
実効公開の判定は手前の認可（`requirePageViewable`）が済ませている。

- **公開専用の殻はスクリプトを読み込まない**。閲覧はゼロJSで完結する（本文は標準HTML、計算ビューは
  サーバー事前描画）ので、訪問者へ配る理由が無い。後戻りは `TestPublicShellShipsNoScript` が検出する。
- 前日（2026-08-25）に入れた応急処置——匿名なら殻へ `<body class="anonymous">` を刻む——は、この分岐で
  **到達不能になったので撤去**した。当時から「本筋は公開専用ビュー」と書いてあったとおり。
  JS 側の `body.anonymous` 付与は残してある（編集中にセッションが切れる経路がまだ生きているため）。
- **SEO/SNS共有**: `description` は**本文の最初の段落**から作る（120字で切る。見出しは題名と重複するので
  使わない）。OGP（`og:title`/`og:description`/`og:type`/`og:url`/`og:site_name`）と canonical も出す。
  埋める値はすべて `html.EscapeString` を通す——ここは**サニタイズ後に文字列を連結する4つ目の経路**で、
  規律が破れると保存型XSSになる（`RenderComputedViews`・`RenderAnchors`・`RenderPageShell` と同じ責任）。
- **`sitemap.xml` / `robots.txt`**: 載せるのは実効公開のページだけで、判定は認可と同じ
  `page.EffectivePublic` を通す——独自の判定を書くと、認可とずれた瞬間に**非公開ページのアドレスを
  sitemap が外へ配る**。`robots.txt` は**サイト全体が非公開なら `Disallow: /`** を返す（トップの実効公開で
  判定。パスゲートにより「サイトが閉じているか」と同義）。索引が使えないときも閉じている扱いにする。
- **キャッシュの切り分け**: キャッシュ可能にするのは**匿名 × 実効公開のページ応答だけ**
  （`public, max-age=600` ＋ `Vary: Cookie` ＋ `ETag`。`If-None-Match` 一致で 304）。
  認証済みのページ応答・匿名の404・**要認証API**・`/api/me` は `no-store`。API は
  `RequireAuth` の**入口で一律に**付けた——ハンドラごとに付けるとどれか1本が漏れるため。
  添付（`/data/`）は 2026-08-21 のユーザー決定どおり従来のまま。
  > **「公開→非公開だけ即時失効」は採れない**（要件 §4.4 が実装時の判断に委ねていた点への回答）。
  > いったん配った応答は取り消せないので、原理的に作れない仕組み。即時性が要るなら
  > `publicCacheSeconds` を 0 にして毎回再検証（ETag で 304）へ倒すのが現実的な選択肢で、それでも
  > 帯域は節約できる。なお**サーバー側の状態は即時**なので、キャッシュを持たない相手（初回訪問者・
  > クローラ・`sitemap.xml`）には非公開化がその場で効く。
- **絶対URLの基底**は `WCMS_BASE_URL`（新設）を最優先し、無ければリクエストから組み立てる。
  `X-Forwarded-Proto`/`-Host` は**前段がプロキシのときだけ**採用する——判定は監査記録の接続元と共有し
  （`auth.IsFromTrustedProxy`）、規則がずれると片方だけ詐称できる穴になる。
- **403 の画面**を 404 と同じ体裁にした（理由と次の手を出す）。403 を見るのは**ログイン済みの利用者だけ**
  （匿名は 404 へ統一済み）。

検証は Go テスト（`public_view_test.go`・`route_guard_test.go`）と E2E（`e2e/verify-public.js`・29項目）。
E2E は実データの公開フラグを立てるので、`finally` で必ず戻す作りにしてある。

## 画像の添付と表示（2026-08-26）

公開サイトで画像を出す経路が**ゼロ**だったのを実装した（[要件定義書.md](要件定義書.md) §2.6 の未実装分。
ワンノート移行では画像4,825枚が絶対前提でもある）。入口 `POST /api/upload-image` と出口 `/data/` の二層。

- **中身で種別を決める**（`SniffImageKind`）。拡張子は名乗りにすぎず、`.png` という名前のHTMLを
  置かれると配信側の判定を欺けるため、名乗りと中身が食い違うファイルは拒否する。
- **EXIF は保存前に落とす**（`StripImageMetadata`）。カメラ写真のGPSが公開サイトへ載る事故を、
  公開時の選別ではなく**経路の一律処理**で防ぐ（フェイルクローズ）。JPEG は向きを画素へ反映して
  から再符号化する——捨てるだけだと表示が横倒しになるため。PNG / WebP は容器の塊を歩いて
  メタデータの器だけ落とす。**外部パッケージは使っていない**（開発方針 §1。標準の `image/jpeg` と
  自前のチャンク走査・最小の EXIF 読み取りで足りた）。
- **SVG は「不活性な画像」**として通す。入口では整形式・ルートが `svg`・`<script>`/`<foreignObject>`/
  `on*=`/`javascript:` 無しを確認し、**安全性の本体は配信側**——`attachment` ＋ この応答限定の
  `Content-Security-Policy: sandbox; default-src 'none'` で、直接開いても描画させない。
  `<img>` のサブリソース読み込みは両ヘッダを無視するので、本文での表示は影響を受けない。
- **HEIC / AVIF / TIFF / BMP は形式ごとの理由**を返す。「許可リスト外です」だけでは、iOS のカメラ
  写真が入らない人が次に何をすればよいか分からない。
- 本文が持つのは**絶対パス**（`/data/master/00/000012/写真.png`）。ページのアドレス（`/000012`）からの
  相対名はページの隣ではなくサイトのルートを指してしまうため。サニタイザが埋め込みの絶対パスを
  `/data/` 配下に限って許可している（2026-08-21 決定）ので、この形はその許可範囲そのもの。
- エディタの入口は3つ（スラッシュメニューの「🖼 画像」・本文へのドロップ・`image` 列のセル）で、
  いずれも同じ関数を通る。モバイルは `accept="image/*"` により OS 標準のカメラUIが選べる
  （独自のカメラ画面は持たない）。**レジストリの `image` 列の入力補助もこれで開通した**。
- 名前の検査は `safeAttachmentName` の1箇所へ寄せ、PDF の口と共有した——口を増やすたびに
  「サイドカーを上書きできる穴」が復活しないように。

検証は Go テスト（`image_test.go`・`upload_image_test.go`）と E2E（`e2e/verify-image.js`・21項目）。

## 引き継ぎの「決定済みで小さいもの」5件を実装（2026-08-25）

1. **監査記録の取りこぼしを埋めた**——ページの新規作成・添付の保存と上書き・索引の全再構築、および
   認証イベント（ログインの成功・失敗・ログアウト）。添付だけ `attach` と `attach.overwrite` を
   分けている——添付にはリビジョンもゴミ箱も無く、上書きすると前の中身が復元できないので、
   「増えた」のか「消えた」のかが記録から読めないと後から追えないため。認証イベントには
   **接続元アドレス**も残す（ユーザー判断「誰が事務所の外から入ってきたか知る必要がある」）。
   本番はリバースプロキシの背後なので `X-Forwarded-For` を見るが、無条件に信じると接続元を
   詐称できるため、**前段がループバック／私設アドレスのときだけ採用し、末尾＝直近のプロキシが
   足した値**を使う。一覧は [認証認可設計.md](認証認可設計.md) §9.4。
2. **自動集計の表を触れなくした**（a案）——手配集計表のセルをクリックすると行・列ツールバーが開き、
   行の追加や列の削除が**実際に通っていた**（実測で再現）。入れた内容はシリアライザが
   `.vocab-chrome` を保存しないので消える。判定関数を `isServerOwned` へ改め、`.vocab-chrome` の
   中なら真を返すようにした——この1関数を行・列ツールバー／dl 項目ツールバー／enum メニュー／
   列型の検証の**4箇所が共有**しているので、編集の手掛かりがまとめて出なくなる。
3. **未定義の種別の告知を目立たせた**——`data-type="cliet-order"` のような綴り違いは保存こそ通るが
   その塊は③計算から静かに外れる。他と同じ控えめなトーストで8秒後に消えていたのを、赤地・太字の
   `alert` 型にし、**時間では消さない**（閉じるまで残る）。ユーザー要望「赤色背景などで告知して
   ください」。
4. **公開ページのちらつきを消した**——未ログインで公開ページを開くと編集スイッチ等が一瞬映って
   いた。隠すのは CSS（`body.anonymous`）だが、印を付けるのが `/api/me` の応答後だったため最初の
   描画に間に合っていなかった。匿名かどうかは**サーバーが知っている**情報なので、
   `RenderPageShell` が `<body class="anonymous">` を返すようにした。**本筋は公開専用ビュー**
   （クローム自体を配信しない）で、これはその前の応急処置。
5. **小さな整理2件**——部材表を読む処理の逐語コピーを `VocabTableRows` へ寄せた（鍵の決め方が
   変わったときに片方だけ直る危険を消すため）／計算ビューの振り分けを名指しの分岐から
   **レジストリの `View` 宣言**へ移し、描画関数は `viewRenderers` へ1件登録するだけにした。
   登録が無い形式は**空白ではなく理由**を画面に出す（`missingViewHTML`）——以前は3箇所へ形式名を
   足す必要があり、どれか1つ漏らすとマーカーだけ保存されて中身が描かれず、テストも通っていた。

## ページテンプレートを実装する（2026-08-20）

同日に設計した [【考察】ページテンプレート.md](【考察】ページテンプレート.md) を3段に分けて実装した。
設計時にコードを読んで見つけていた穴2つも、実装しながら塞いだ。

**第1段: テンプレート領域を②索引・③計算から除外**（[template.go](../internal/cms/template.go)）。
テンプレートに書いた仮の発注書が `client_orders` に入り、手配集計・利益計算へ出てくるのを防ぐ。
除外は**「飛ばす」ではなく「空の本文を渡す」**——全プラグインの `Sync` は冒頭で当該ページの行を
`DELETE` する洗い替えなので、空を渡せば「古い行は消える・新しい行は入らない」となり、
**普通のページをテンプレートへ移したときに古い行が残らない**（飛ばすと残る）。
`PurgePageIndex` と同じ流儀に揃った。

**穴①: サイドカーにタイトルが無かった。** 設計では「先祖辿りはサイドカーで」と書いたが、
`PageMeta` は owner/group/mode/public/parent_id/日時だけで、「その先祖が『テンプレート』という
名前か」が分からない。**先に親を見て「トップの直下」で弾く**ことにした——その条件を満たす先祖は
鎖の中にただ1つなので、本文HTMLをディスクから読むのは1回の辿りで高々1ページ分で済み、
順序非依存という肝心の性質も保たれる。

**穴②: 親の付け替えが索引を張り直していなかった。** `SetParentAPIHandler` は
`UPDATE pages SET parent_id` とサイドカー更新だけで `SyncIndex` を呼ばない。上記の
「空の本文を渡す」方式のおかげで、**張り直しさえすれば古い行は自動で消える**。
テストで往復（テンプレートへ入れる→出す）を固定した。

**第2段: コピーと新規化パス**（[template_new.go](../internal/cms/template_new.go)）。
`/api/new-page` に `template=` を足した。規則は「空欄は列型の既定値で埋める・書いてある値は
そのまま保つ」ただ1つ。`order_no` は UNIQUE 制約があるので再採番が必須で、番号は
`PO-<新ページID>` とした（エディタの時刻下6桁より衝突しにくく、由来ページも辿れる）。
検証は**採番より前**に行う——後に失敗するとファイルの無いページ行が `pages` に残るため。

**第3段: 一覧の読み口とメニュー**（[handler_template.go](../internal/cms/handler_template.go)・
`createSubpage`）。`GET /api/templates` がツリーを返し、枝は見出し・葉は選択肢として描く。
テンプレートが1つも無ければ従来どおり即作成。

### テストで見つけた `:memory:` の落とし穴

一覧のテストだけ**ファイルDB**を使う。`visibleChildren` は行を回しながら1件ずつ
`page.GetPerms` を引くが、入れ子のクエリはプールの**別接続**で走り、`:memory:` では
接続ごとに別の空DBになるため権限がフェイルクローズして子が1件も見えなくなる。
本番（`data/cms.db`）はファイルなので同じ問題は起きない。

検証: go test 全パス（除外を外すと第1段の3件が落ちることを確認）。
E2E は既存の stage2（48）／stage3（20）／stage4（25）／delete（9）に加え、
**新設の verify-template（15）** が実機で全通過。

## ページテンプレートを設計する（2026-08-20・設計のみ）

新規ページ作成時に、形式の決まった文書を雛形から起こしたい（ユーザー提起）。
考察を [【考察】ページテンプレート.md](【考察】ページテンプレート.md) へ新設した。**実装は未着手**。

到達点は「**テンプレートも普通のWikiページ**」で、置き場所と見分け方が主な論点だった。
当初はタイトル接頭辞 `【テンプレート】` を提案したが、**ユーザー案「テンプレート用フォルダの
子孫」へ差し替えた**——接頭辞はコピー先のタイトルへ漏れる（`【テンプレート】受注ページ` を
コピーすると同名になり、剥がす魔法か毎回の改名が要る）のに対し、フォルダ方式なら
**テンプレートのタイトルがそのままコピー先の正しいタイトル**になる。加えて分類が階層でタダで手に入り、
group/mode の継承（setgid 相当）がテンプレート共有をそのまま解く。

深さの扱いはさらにユーザーが絞り込み、**葉だけがテンプレート・枝は分類**に決まった。
「子孫はすべてテンプレート」だと分類の階層とテンプレートの階層が混ざるが、葉に限れば
**ページは必ずどちらか一方**になる。副産物として分類ページは誤ってコピーされ得なくなり、
その本文が「このカテゴリの使い方」の説明場所として空く（分類ページはコピーされないため）。

ルート自身は**トップの子でタイトルが「テンプレート」**という約束で見分ける。名前を持つのが
1ページだけなので接頭辞案の欠点が当てはまらず、スキーマもUIも増えない。

コード側で見つけた実装上の必須事項が2つ:

- **テンプレート配下はプラグイン同期から除外する。** `SyncIndex` は保存のたびに全プラグインの
  `Sync` を回すので、`client-order` を含むテンプレートを保存すると仮の発注書が `client_orders` に
  入り、手配集計・利益計算に出てくる。
- **その先祖辿りはサイドカーで行う。** `EffectivePublic` と同じく `pages` テーブルから
  `parent_id` を読むと**DB再構築で壊れる**——空のDBへ1ページずつ同期する過程で、先祖がまだ
  `pages` に無い順序だと「テンプレートではない」と誤判定し、静かに索引が汚れる。
  親の正本はサイドカーなので `ReadSidecar` なら順序に依存しない。
  なお**葉の判定はメニュー表示時（DBが揃っている場面）にしか要らない**ので、この罠は及ばない。

書き込み（日付・一意番号）は既存の `defaultFieldValue` と同じ「**空欄を列型の既定値で埋める**」
規則をサーバー側へ移す。`order_no` には UNIQUE 制約があるため再採番は必須で、
**テンプレート機能を作るなら新規化パスは省けない**。プレースホルダ（`{{今日}}`）と
対話的な入力フォームは v1 では作らない（新規ページは編集モードで開くので、ページ自体が入力フォーム）。

## 「w-cms が見る要素」の視覚ヒントを広げる（2026-08-20）

**DBに入るもの／入らないものが見た目で区別できる必要がある**（ユーザー指摘）。
既に `table`/`dl[data-type]` には編集モードの破線枠があったが、**`section[data-type]` が抜けていた**
——`section[data-type="client-order"]` は型付きテーブルへ直接入る最も重要な業務ブロックなのに
印が出ていなかった。ファイル容器・計算ビューも同様。

**印の規則は `data-type` の有無ただ1つ**とした。「w-cms がその要素を見て何かするなら `data-type` を
付ける」という決定（[【考察】語彙モデル.md](【考察】語彙モデル.md) §9）の当然の帰結で、
形式ブロック（DBへ入る）・ファイル容器（配線）・計算ビュー（表示専用）はどれも `data-type` を持ち、
素の文書は持たない。**基準を1つ決めておくと派生が自動的に決まる**、という例になった。

### ページタイトルの h1 に `data-type` を付ける案は見送った

DBに入る（`pages.title`）のに `data-type` を持たない唯一の例外なので、付ける案を検討したが**見送り**。

- タイトルは「**文書順で最初の h1**」という**位置**で決まる（[parser.go](../internal/cms/parser.go) の
  `ParseCore`）。属性にすると上に見出しを足した瞬間ずれ、並べ替え・挿入のたびに同期させる機構が要る
  ——**位置が既に持つ情報を属性が二重に持つ形で、撤去したばかりの `data-field` と同じ構造**になる。
- 値の意味も決まらない（`data-type="title"` は列も同期プラグインも骨格も持たず、
  レジストリの形式とは性質が違う）。既存ページには属性が無いので抽出規則は「最初の h1」のまま残り、
  **正本が2つ**になる。

かわりに**実行時クラス**（`is-page-title`）で印だけ付け、位置から毎回計算し直す。
class はサニタイザもシリアライザも通さないので保存に漏れない（`.cell-invalid` と同じ流儀）。
計算し直す契機は目次（`buildToc`）とまったく同じなのでそこへ相乗りさせた。

なお「タイトルを書き手が明示的に選べるべきか」も検討したが、**最初の h1 でよい**と決まった
（選べるようにするなら属性が正しい機構になるが、それは印の話ではなく仕様変更）。

検証: go test 全パス。E2E stage2（48・タイトルの印3件を追加。**上に見出しを足すと印が移る**＝
属性ならずれる箇所を固定）／stage3（20・`section` の枠2件を追加）／stage4（25）／delete（9）全通過。

## ページ削除（ゴミ箱への移動）を実装する（2026-08-20）

[【考察】通信記録処理.md](【考察】通信記録処理.md) §2.7④「自動判定してよい。ただし常に
取り消せること」の**前提**として必要だったが、**登録ルートに削除に相当するものが1つも無かった**。
`data/master/<prefix>/<id>/` を手で消して「DB再構築」する以外に手段がなく、管理者権限と
サーバーのファイルシステムへのアクセスが要るため通常運用では取り消しができない状態だった。

- **物理削除ではなく `data/trash` への移動**。削除自体も取り返しがつくようにする（「常に柔軟性」）。
  DB再構築は `data/master` だけを走査するので、移すだけで索引からも消える。
  同じIDが既にゴミ箱にあるとき（削除→復元→再削除）は連番を付けて上書きを避ける。
- 守りは3つ——**トップページは不可**（親を持てない唯一のページで、消すと復旧導線が無くなる）／
  **子ページを持つページは不可**（再帰削除は「取り消せる範囲」を一気に広げるので採らず、
  409＋件数で先に移すか消すよう促す）／**編集ロックが要る**（chmod・chown・set-parent と同じ直列化）。
- `PurgePageIndex`——プラグインの `Sync` はどれも「`page_id` の行を削除してから入れ直す」形なので、
  **空の本文で同期を走らせる**と型付きテーブルが洗い流される。そのあとコアテーブルを消す
  （`SyncIndex` が `pages` を upsert するため、順序はこの通りでなければならない）。
- UIは左レール最下部。**編集モードでトップページ以外のときだけ**表示し、色を分けて confirm を挟む。
  削除後は親（無ければトップ）へ遷移する。

**やらなかったこと**: ゴミ箱からの**復元UI**（戻すには手でフォルダを `data/master` へ移して
DB再構築する）。ゴミ箱の自動整理（保持期間）。§4.4 の「N件から引用されています」警告は
`page_refs` の実装後。

検証: go test 全パス（ゴミ箱への移動・トップページ拒否・子あり409・他者ロック中409）。
E2E: `verify-delete.js` を新設（9項目）。stage2（45）／stage3（18）／stage4（23）も全通過。

## 本文に `id` を書けるようにする——殻の id を接頭辞 `w-` で隔離する（2026-08-20）

**規律の向きを反転させた。** 「本文の書き手が接頭辞を守る」のではなく、**殻の側が接頭辞を独占する**。
守るべき対象が無数の書き手から1つの殻へ移り、本文でページ内リンクが普通に書けるようになった。
設計の正本は [本文サニタイズ設計.md](本文サニタイズ設計.md) 5.3。

### なぜ `id` を拒否していたのか（2026-08-02 の判断）

本文は殻 `assets/index.html` と同じDOMへ合成され、id の名前空間を共有する。
`getElementById` は文書順で最初の要素を返し、**本文の挿入点より後ろに権限UIの入力欄が並ぶ**
（`pi-parent-input`・`pp-owner-input`・`pp-group`・`pp-mode`・`pp-public`）。したがって本文に
`<input id="pp-mode" value="777">` を仕込むと、**そのページを開いた人の権限パネルが
攻撃者の値を読む**——管理者が開いて保存を押せば意図しない権限が送信される。

### 何をしたか

- 殻の**62個の id を `w-` つきへ一括改名**（`index.html`／`app.js`／`app.css`／E2E 3本）。
  本文が合成されるのは `index.html` だけなので `admin.html` は対象外。
- **ガードテスト** `TestShellIDsAreNamespaced`——接頭辞なしの id を殻へ足すと落ちる。
  規律をコードで固定した（CSPの後戻りを `csp_test.go` が検出しているのと同じ流儀）。
- サニタイザは `id` を全要素で許可し、**殻の接頭辞だけを剥がして**通す（拒否ではなく告知）。
  剥がすのは**無くなるまで繰り返す**——1回だけだと `w-w-x` で冪等性が崩れ、
  保存時エコーバックが収束しない。剥がした結果が空なら属性ごと落とす。
- 剥がしたことは保存応答の **`stripped_ids`** で告知し、エディタが警告を出す。
- `AllowedVocabulary` へ全要素共通の属性（`data-id`・`id`）を含めた。含めないと
  「サーバーは通すのにエディタのシリアライザが落とす」非対称ができ、保存のたびに id が消える。
  あわせて `serializeBlock` の `data-id` 二重出力を解消した。

### 副産物：保存状態の退行を1件発見・修正

サーバーが本文を書き換えて返す（`sanitized`）と、`applySanitizedHtml` のDOM変更を
MutationObserver が拾って「未保存」を立て、その後のデバウンス保存が `decideSaveStrategy` の
'none' で早期returnするため**表示が「未保存」のまま戻らなかった**。データは保存されているのに
未保存に見える。通常の保存で `sanitized` が真になる経路が実質無かったため表面化していなかったが、
今回「接頭辞を剥がす」で日常的に踏むようになり、E2E が検出した。

### `data-id` は廃止しない（検討して見送り）

「`id` が使えるなら `data-id` を廃止できないか」を検討し、**残す**と決めた。2つは
**別の情報**（保存の単位／リンクの宛先）を運ぶので、統合は冗長性の除去でなく概念の混同になる。
統合するとアンカー名の変更でブロック同一性が壊れ、`id` の一意制約により人が付けた名前を
`ensureBlockIds` が振り直し、貼り付けた `id` がブロック識別子として解釈される。
理由の詳細は [本文サニタイズ設計.md](本文サニタイズ設計.md) 5.3 の注記、
決定ログは [【考察】語彙モデル.md](【考察】語彙モデル.md) §9。

### 残る課題

書き手が `id` を付けていないページにはアンカーが無く、目次のページ内移動も
JSの `scrollIntoView` のままなので**公開ページではアンカーが効かない**。
次の一手は「**保存形式を変えず、描画時にサーバーが `id` を合成する**」
（見出しとブロックへ自動付与。既存の全ページが遡って恩恵を受ける）。

検証: go test 全パス。E2E stage2（45・id の挙動4件を新規追加）／stage3（18）／stage4（19）全通過。

## 受注・進捗・添付の設計を詰める（2026-08-20・設計のみ）

「1つの受注が複数の発注書から出来る」というユーザーの指摘を起点に、通信記録の取り込み周りの
設計を詰めた。**コードの変更は無く、文書のみ**。決定の正本は
[【考察】通信記録処理.md](【考察】通信記録処理.md) §2.7（新設）。

### 決定5件

1. **添付の実体はすべて通信記録ページのフォルダ**——発注書PDF・図面・ZIP・`.eml` 原本を問わない。
   文書ページは実体を持たずアドレスで指す。§9.1 の「自己完結性＝文書ページが実ファイルを所有」を改定。
2. **変更発注書は「追記」**——既存の明細を書き換えず、受注ブロックをページに足す。
   **人が付けた進捗が失われない**のが理由で、マージUI・差分適用UIは不要。
   **帰結: ファイル容器の入れ子は維持**（1受注ブロック＝1発注書PDF が保たれる）。
   検討途中で「入れ子をやめる」と判断したが誤読によるもので撤回した。
3. **進捗マークの正本は受注ページの `status`**——計算ビューの中身は保存されない（`.vocab-chrome`）ので
   進捗ページには書き込めない。進捗ページは表示に徹する。
4. **自動判定してよい。ただし常に取り消せること**——要件は精度ではなく可逆性。
   通信記録が不変アーカイブだから何度でもやり直せる、というのが根拠。
5. **`data-src` は汎用の「出所アドレス」**——`000200` ／ `000200#<ブロックID>` ／ `000200/<ファイル名>`。
   解釈は `data-type`（型）が決める。**進捗ページのソースはファイルでなく受注ページにしかなりえない**
   ことが一般化の動機。サニタイザは変更不要。決定ログは
   [【考察】語彙モデル.md](【考察】語彙モデル.md) §9 にも記載。

### 判明した欠落

- **ページ削除の機能が無い**——登録ルートを確認したところ、削除に相当するものが1つも無い。
  いまは `data/master/<prefix>/<id>/` を手で消して「DB再構築」する以外に手段がなく、
  通常運用では取り消しができない。決定4の前提なので、独立した作業項目として立てた。
- **保存済み文書のリバートが要件へ格上げ**——決定2のブロック追記を取り消す手段が
  ページ削除では代替できない（消すと元の受注と進捗まで失われる）。

### ページ内アンカーの再考察

`id` を落としているため `#fragment` が効かず、目次すらJSの `scrollIntoView` に頼っている
（公開ページでは機能しない）。`id` を許可へ戻す案は採らない——本文の挿入点
（`assets/index.html` 151行目）より**後ろ**に権限UIの入力欄があり
（`pi-parent-input` 173／`pp-owner-input` 197／`pp-group` 202／`pp-mode` 203／`pp-public` 215）、
`getElementById` が文書順で最初を返すため、本文に仕込んだ偽の入力欄が**必ず勝つ**。
管理者がそのページを開いて保存すると意図しない権限が送信される。

採る案は「**保存形式に `id` を入れず、描画時にサーバーが合成する**」
（`id="h-<見出し>"`／`id="b-<ブロックID>"`、`href="#発注書A"` も同時に変換）。
接頭辞の名前空間をサーバーが独占するので衝突が原理的に起きず、拒否リストは不変のまま。
既存の全ページが遡ってアンカーを持ち、目次も標準リンクへ乗り換えられる。
詳細は [本文サニタイズ設計.md](本文サニタイズ設計.md) 5.3。

## `data-type` を「型名」と定め、`data-field`（機械キー）を撤去する（2026-08-20）

ユーザー提案「w-cms が機能を提供するタグ全般に `data-type` を付けてはどうか（プログラミングの
型名のようなもの）」を受けた設計判断と、その延長で見つかった `data-field` の冗長性の解消。
決定の正本は [【考察】語彙モデル.md](【考察】語彙モデル.md) §9（新規2行）。

### 決定1: `data-type` は型名

**w-cms がその要素を見て何かする（DB保存・描画・配線・入力補助）なら `data-type` を付ける。
何もしないなら付けない。** `data-type` が型名で、他の `data-*`（`data-src`）はその型のフィールド。
`th[data-type]`（列型 text/number/date/enum/image）は**プリミティブ型**で、レジストリの
形式名（複合型）と同じ型宇宙に属する——という読み方で既存のマーカー体系が全部説明できる。

サニタイザの許可は**要素限定のまま**とし、機能を足すときにその要素へ都度広げる
（規約と実装のギャップがそのまま未実装の可視化になる）。この決定は、移行で唯一残った
**参照マーカー**（`受信元`・`前版`）に `<a data-type="…" href>` という素直な置き場を与える
——`dl` は「見える名前:値」の形式なので配線を移せず行き詰まっていた。

### 決定2: 項目の鍵は見出しの表示文字ただ1つ（`data-field` の撤去）

鍵の解決は元々 `columnFor`（`Field` でも `Label` でも引ける）を通っており、`data-field` は
**すでに冗長**だった（`inspection-record` は1つも持たずに動いていた）。唯一の仕事は
「見出しの改名耐性」だけだったので、それを告知へ移して属性ごと撤去した。

- **告知を先に追加**（`UnresolvedVocabFields`）——保存応答の `unresolved_fields` と
  エディタの警告トースト。報告するのは**機械キーを持つ列だけ**で、かつ**改名の徴候**
  （解決されなかった宣言列がある **かつ** どの宣言列にも当たらない見出しがある）が
  あるときに限る。列の削除だけ・独自列の追加だけでは黙る。仕様は
  [【一覧】API.md](【一覧】API.md) 2章の注記。
- **撤去**——サニタイザの許可リストから外し（`dd` の許可属性は**空**になった）、
  ②汎用索引・`VocabDLFields`／`VocabTableRows`・部材表・可変タグの読み取りからも
  分岐を削除。**属性が残っていても読まない**ので、サニタイズを通った本文と通っていない
  本文で `Sync` の結果が変わらなくなった（保存経路の有無に結果が依存しない）。
- **エディタ**——骨格生成が書き出すのをやめ、AI明細の列対応と列型の解決はレジストリ経由の
  共通ヘルパ `findVocabColumn`（サーバーの `columnFor` と同じ規則）へ。編集モードの
  機械属性ハイライトは `th[data-type]`（型の明示）だけになった。
- `VocabDef.Field` は**残す**——③計算プラグインが使う内部の機械キーで、本文には現れない。

**本文のマーカーは `data-type`（型名）と `data-src`（配線）だけ**になり、
「見える文字がすべて」（語彙モデル §2）が鍵について例外なく成立した。

**副作用**: ②汎用索引の鍵が機械キーから表示文字へ変わる（`order-no`→`発注書番号`）。
`vocab_index` を読むコードはまだ無く、形式ごとにばらついていた鍵（`inspection-record` は
元から表示文字）が揃うため、今のうちに変えた。

**検証**: go test 全パス。**実データ68ページを `UnresolvedVocabFields` で走査して未解決ゼロ**
（撤去で壊れるページが無いことを確認）。E2E は stage2（41）／stage3（18・「見出しの改名を
保存時に告知する」を新規追加）／stage4（19）全通過。

**文書**: 語彙モデル §2・§4・§5.1・§5.3・§8.2・§9・§10、本文サニタイズ設計 §5、
【一覧】語彙 §1.1・§2.2・§2.3、【一覧】API 2章、要件定義書 §2.5、アーキテクチャとDBスキーマ、

## スマホ幅の表示崩れ（表による横スクロール）を修正する（2026-08-19）

375px 等の狭い画面で、本文に幅の広い表が1つあるだけでページ全体が横スクロールに
なっていた（ユーザー報告）。原因は2段:

1. 縦積みレイアウト（`@media (max-width: 760px)` の `.work-area { flex-direction: column }`）は
   `align-items: flex-start` のため、flex アイテムの横幅が fit-content になる。
   **fit-content の下限は min-content** なので、min-content 以下に縮められない表が
   あると文書列（`.doc-column`）ごと押し広がる。
2. 表はセルの内容幅（min-content）以下に縮まない。

対処（[app.css](../assets/app.css) の 760px メディアクエリ内）:

- `.doc-column { align-self: stretch }` — 文書列は常に親幅いっぱいに固定
- `#editor-content table { display: block; max-width: 100%; overflow-x: auto }` —
  幅の広い表は**表自身の中で横スクロール**させる（`display: block` は行内容を
  無名テーブルボックスが包む標準的なレスポンシブ対処。セルの罫線・contenteditable・
  行操作ツールバーには影響しない）。`pre` にも同じ横スクロールを付与
- デスクトップ幅（>760px）は無変更

検証: Playwright で 375px の実測（`scrollWidth` 552→375、管理コンソールも 375 で
横はみ出しなし）と、デスクトップ幅の E2E 回帰（verify-stage2.js 41項目＋
verify-migration2.js 16項目）全通過。
なお画面端のレール開閉タブ（ページ階層・目次・ページ情報のつまみ）が本文に重なって
見えるのは狭幅用の設計どおりのクローム（[【一覧】用語集.md](【一覧】用語集.md)）で、
本修正の対象外。

- **JSONボディのサイズ上限**: `/api/save` 等は `json.NewDecoder(r.Body)` を直接使って

## 要件定義書を語彙モデル（3層）で書き直す（2026-08-16）

「標準HTML＋`data-*` マーカー」路線（下の節）を起点に検討を進め、**語彙と拡張の全体像**が
見えたため、[要件定義書.md](要件定義書.md) を書き直した。**章番号は他文書からの参照を壊さない
よう維持**し、§2.5 を「語彙モデルと業務機能」として全面改訂、§2.2・§4.5 等を追随させた。
3層モデル・挿入経路の設計記述は、【考察】文書への展開までは要件定義書 §2.5 が記録の置き場。

### 検討で得た構造（チャットでの検討を文書化）

- **挿入経路の列挙**: 構造化ブロックが本文へ入る経路は、明示挿入／貼り付け変換／
  ファイル取り込み変換（PDF→表は実装済み）／デバイス起点（カメラ・バーコード）／
  他ページ参照／計算ビュー（保存されない派生）／雛形・複製／エディタ外生成（fan-out・
  外部投入・移行）に分類できる。**不変条件は「どの経路でも出口は同じ」**——同じ語彙・
  同じ保存時サニタイズ/検証・同じ編集ロックを通り、語彙の単一正本を迂回する経路を作らない。
- **3層モデル**: ①語彙レジストリ（宣言データ・再デプロイ不要が目標。`data-type` の定義＝
  表示名・分類・列・雛形）②汎用索引（コアに1実装。全 `table[data-type]`/`dl[data-type]` を
  汎用テーブルへ同期＝`page_tags` の一般化）③計算プラグイン（Goコード・少数。型付き
  テーブル＋計算・取り込み変換・集計API）。**100種の大半が①のデータ1件になり、開発者が
  ボトルネックにならない**。プラグインは「1計算ユースケース＝1プラグイン」へ意味が狭まる。
- **エディタの形式知識は3場面で異なる**: 挿入時＝レジストリから受信（骨格はヘッダ定義から
  機械生成）／編集時＝**自己記述ヘッダだけで自立**（レジストリ無しでも既存文書は編集可能）／
  入力補助・検証＝レジストリがあれば向上。エディタ実装は汎用表エディタ1つ
  （列型 `text`/`number`/`date`/`enum`/`image`）で、**型の数に対して不変**。
- **カメラ写真はモデルの検証例**: 素の写真＝コア＋標準HTML（`<img>`）で完結し、どの層にも
  載らない。意味を持つ場面で合流する——表の写真列＝①の列型 `image`（データ1行）、
  撮影画像→明細表＝③の取り込み変換、写真への注記＝将来のSVG編集アプリ。
  EXIF一律除去の帰結として**撮影日時を業務データにするならEXIFに頼れない**
  （受付時刻のサーバー記録 or `date` 列へ入力）ことも §2.6 に明記。
- **サニタイザとレジストリの分離**: 許可リスト（要素・属性名）は従来どおりコードで固定し、
  `data-type`/`data-field` は属性名だけ許可して**値は不活性**。レジストリを安全性の門に
  しないことで、将来レジストリを実行時編集可能（管理UI・語彙定義ページ）にしても危険な
  要素は増やせない。
- **`lit` 再評価の位置づけを更新**: 語彙モデルで表・定義リストが標準HTML化し、カスタム要素は
  少数（計算ビュー系）に戻るため、再評価の緊急度は下がった（§4.5）。
- **未決点3つ**を §2.5 (5) に記録: ①未知 `data-type` の扱い（通す＋通知を推奨・未確定）
  ②レジストリの置き場（コード内→管理UI→語彙定義ページの段階論）③既存プラグインの移行の段取り。

## タグ設計を「標準HTML＋data-* マーカー」路線へ転換する（2026-08-16）

ユーザーから「受注表などは HTML の `table` を使い、class 指定で用途や挙動を決めては」との
提案があり、検討の結果**方向として採用**した（マーカーは `class` でなく `data-*` に修正）。

正本は [【考察】タグ設計.md](【考察】語彙モデル.md) §7 冒頭の注記と §9。

- **繰り返し明細**: `<m-table>` で包む従来案（2026-08-02 決定）を再々検討し、
  **生の `<table data-type="…">`（ヘッダ `data-field` で列役割を自己記述）を第一候補**へ。
  決め手は公開ウェブサイト用途の追加——カスタム要素は表示に `web-components.js` が要るが、

- **マーカーを `class` にしない理由**: ①サニタイザの `class` 全面拒否（本文はシェルと同一DOM）に
  例外を作らない——`data-*` には `data-id` の前例と `globalAttributes` の仕組みがある
  ②見た目のフックと機械可読の役割の分離（改名がデータ破壊にならない）③シェルとの衝突ゼロ。

- **名前:値 → 定義リスト**: `<dl data-type="tags"><dt>名前</dt><dd>値</dd></dl>` 方式。
  名前も値も表示される実テキストになり原則に最も忠実。多値は `dt` 繰り返し／複数 `dd`。

  プラグイン語彙宣言の `data-*` マーカー対応拡張）を §9 に記録。
- 要件定義書 §2.5 にも「標準HTML＋`data-*` マーカーを第一候補、カスタム要素は標準HTMLで
  表せないものに限る」を追記。**カスタム要素の総数が減るため100種問題の緩和にも効く**。

## サーバー側の構造を分ける（handler.go の分割・page / editlock パッケージ）（2026-08-06）

`internal/cms` が18ファイル・単一パッケージで、HTTPハンドラ・認可・ロック・サニタイズ・
プラグインが同居していた。依存の向きが規約でしか守られていない状態を、**型で守られる境界**へ
段階的に移す。振る舞いは変えていない（純粋な移動と修飾の付け替え）。

### 1. `handler.go`（32KB・779行）を関心ごとに4分割

| ファイル | 担当 |
|---|---|
| `handler_save.go` | 保存API（全文・ブロック単位） |
| `handler_view.go` | 画面（サーバー合成）とページ本文API |

`storage.go`（保存パス）と `perms.go`（サイドカー・認可・`/data/` 配信ゲート）を移した。

### 3. `internal/cms/editlock` パッケージを切り出し

`lock.go`（ロック状態）・`lock_handler.go` → `handler.go`（HTTP/SSE）・`lock_test.go` を移した。

`editlock` → `page` の一方向依存で、ロック検証（`RequireEditLock`）もこのパッケージが持つ。

### やらなかったこと（次の判断が要る）

**サニタイザ（`sanitize.go`）の切り出しは見送った。** `sanitize.go` は `PluginTags()`
（プラグインレジストリ）を呼び、ハンドラ（`cms`）は `Sanitize` を呼ぶため、素直に
`htmldoc` パッケージを作ると **`cms → htmldoc → cms` の循環参照**になる。解くには

- **(a) レジストリごと `plugin` パッケージへ出す**: 全 `plugin_*.go` で `Attr`/`TagValue` 等の

  「1ファイル足すだけ」という [【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md) の約束が崩れる）。
- **(b) 依存を反転させる**: サニタイザを純粋なHTML部品にし、カスタム要素の語彙は
  アプリ側から注入する（`htmldoc.SetCustomElements(...)`）。設計としては素直だが、
  `TagSpec` 型の置き場所と初期化順序を決める必要がある。

どちらも設計判断を伴うため、独立した作業として残す。

> **2026-08-17 追記**: (b) を実施して解消した（本履歴の 2026-08-17 の節）。

ロックテストも含む）。ファイル移動は `git mv` で行い、履歴を保っている。

## 殻（index.html・admin.html）からインラインを外へ出す（2026-08-06）

CSP を strict（`'unsafe-inline'` なし）へ格上げするための前提リファクタ
（[本文サニタイズ設計.md §6](本文サニタイズ設計.md) §4 の (1)(3)、および (4) の殻ぶん）。
振る舞いは変えず、置き場所と結び方だけを変えた。

### 何をしたか

| ファイル | 変更前 | 変更後 |
|---|---|---|
| `assets/index.html` | 3015行（`<style>` 696行＋本体 `<script>` 2105行を内包） | **215行**（markup のみ） |
| `assets/admin.html` | 195行（`<style>`＋`<script>` を内包） | **72行**（markup のみ） |
| 新設 | — | `assets/app.css`・`assets/app.js`・`assets/admin.css`・`assets/admin.js` |

- **`on*=` はリポジトリ全体でゼロになった**。`index.html` の11個は `bindChromeActions()`、

- 本体スクリプトは **`defer` を付けずに** `</body>` 直前へ置いた。付けると

## 添付アップロードの脆弱性を修正（権限昇格・保存型XSS）（2026-08-05）

`POST /api/upload-pdf` が**任意の名前・任意の種類**のファイルを受け付けていた。保存先は
ページのディレクトリ `data/master/<prefix>/<id>/` で、そこには**本文 `<id>.html` と
属性サイドカー `<id>.meta.json` が同居している**。これにより、対象ページの write 権限しか
持たない利用者に次の2つが成立していた（実機コードで確認し、テストで再現させた）。

### 1. 権限昇格（サイドカーの上書き）

`<id>.meta.json` という名前でアップロードすれば、**権限の正本であるサイドカーを丸ごと
差し替え**られた。`{"owner":"攻撃者","mode":"333","public":true}` を置いてから本文を保存すると、
`SyncIndex` → `syncPageMeta` が `page_perms` へ反映するため、

- **所有者の奪取**（本来 admin 限定の chown 相当）
- **匿名公開の有効化**（本来は所有者/admin のみ、かつパスゲートの検証つき）
- mode の書き換え

が権限チェックを一切通さずに実現できた。サイドカーを「これらのAPIのみが書き換える」
（`perms_admin.go` 冒頭）という前提が、添付の書き込みによって破れていた。

### 2. 保存型XSS（同一オリジンのHTML配信）

`evil.html` を置き `/data/master/00/<id>/evil.html` を開かせると、`DataFileHandler` の
`http.ServeFile` が拡張子から `text/html` を推定して**同一オリジンの文書として**返していた。
本文の二層サニタイズ（[本文サニタイズ設計.md](本文サニタイズ設計.md)）は本文しか見ないので完全に迂回でき、
中間版CSPの `script-src 'unsafe-inline'` はインラインを許すため防げない。ページが匿名公開なら
未ログインの閲覧者にも届く。`.svg` でも同じ。

### 修正

**入口**（[pdf_handler.go](../internal/cms/pdf_handler.go)）:

- リクエスト全体を **32MiB** に制限（`http.MaxBytesReader`）。従来は `io.ReadAll` で無制限に
  メモリへ読み込んでいた。
- ファイル名を正規化（`attachmentFileName`）。`/` `\` の両方でパス要素を落とし、空・`.`・`..`・
  ドット始まり・制御文字を拒否。**拡張子は `.pdf` のみ**、本文・サイドカーと同名は明示的に拒否。
- 中身の先頭が **`%PDF-`** であることを確認（拡張子は名乗りにすぎない）。

**出口**（`DataFileHandler`・[page/perms.go](../internal/cms/page/perms.go)）— 過去に置かれたファイルや
バックアップ復元に備えた多層防御:

- 本文 `<id>.html` と サイドカー `<id>.meta.json` は**配信しない**（それぞれ画面／APIが認可のもとで返す）。
- `X-Content-Type-Options: nosniff` を常時付与。`.pdf` は `application/pdf` でインライン（`<embed>` 表示は従来どおり）、

## カスタム要素を Light DOM へ統一（Shadow DOM の残骸を除去）（2026-08-05）

[コンセプト.md](コンセプト.md) の「既知の課題」に**優先で手当てすること**として挙がっていた
「Shadow DOM方針の不統一」を解消した。着手して分かったのは、これが見た目の不統一ではなく
**編集機能が壊れていた**という話だった点である。

### 何が壊れていたか

`<m-child-list>` だけが Shadow DOM で描画しており、その時代のAPI `getRootNode().host` が
Light DOM で描かれる他要素のテンプレート（`m-tag-edit`・`m-item-edit-client`・`m-item-edit-our`）に
残っていた。**Light DOM では `getRootNode()` は `document` を返し、`document.host` は `undefined`** なので、

- `<m-tag>` の値の編集
- `<m-item>` の項目（部品コード・部品名・単価・数量・ステータス）の編集
- `<m-item>` の削除ボタン

はいずれも `TypeError: Cannot read properties of undefined (reading 'setAttribute')` で
**何も起きない**状態だった。ハーネス（`/assets/` は認証不要なので、そこへ一時HTMLを置いて実ブラウザで
実行する方法）で再現・確認した。

さらに、ホストへ書き戻す方法が要素ごとに `getRootNode().host`（壊れている）／`closest('m-material')`
／`this.setAttribute`（`MBusinessBlock`）の**3通りに割れていた**。

### 直したこと

- **基底クラス `MElement` を導入**し、全カスタム要素（`m-tag`・`m-item`・`m-file`・`m-child-list`・
  `m-material`・`m-required-materials`・業務要素4種の基底 `MBusinessBlock`）が継承する形にした。
  各要素に散っていた `connectedCallback`／`attributeChangedCallback` の重複も消えた。
- **描画先を Light DOM に統一**。`<m-child-list>` の `attachShadow` を廃止し、要素内に複製していた
  `<style>` は `assets/components.css` へ移した（クラス `.m-child-list` 系）。
- **ホストへの書き戻しを `data-attr` に一本化**（削除ボタンは `data-remove`）。テンプレートから
  インライン `on*=` を除去し、`render()` の最後の `bindEditFields()` が配線する。配線対象は
  **自分が描いたUIだけ**に限る（入れ子の `<m-item>` も同じ `data-attr` を使うため、素の
  `querySelectorAll` では明細を打つと親ブロックの属性まで書き換わってしまう）。
- **自己更新では再描画しない**（`updateAttr`）。従来は1文字打つごとに `attributeChangedCallback` →
  `render()` で入力欄が作り直され、**フォーカスが飛んで実質1文字しか入力できなかった**
  （`MBusinessBlock` は `getRootNode().host` を使っていないので例外は出ないが、この症状は出ていた）。
- **モード切替時の再描画対象を語彙ベースに**（`assets/index.html` の `applyMode`）。要素名を並べた
  固定リストだったため、あとから増えた業務要素（`m-client-order` 等）が対象から漏れ、編集モードに
  してもフィールドが閲覧用のままだった。

確定仕様は [エディタ仕様.md](エディタ仕様.md) §0.1、プラグイン作者向けの要約は
[【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md) §3 の注記。

### 残したもの

テンプレートの**インライン `style=`** は今回の対象外（[本文サニタイズ設計.md §6](本文サニタイズ設計.md) §4 の
一括移行で扱う）。ただし `m-material-edit` は `on*=` を外すのに伴い、`:focus`／`:hover` の見た目だけ
`components.css` へ引き取った。属性変更ごとの全体 re-render と `window.updateHtmlPreview` への
グローバル結合も残るが、呼び出し口は `MElement` の1箇所に集約された。

## 許可タグ・属性の拡張と、エディタ語彙のサーバー一元化（2026-08-04）

本文で扱えるHTMLの範囲を「**タグは寛容・属性は厳格**」の方針で広げ、あわせて
**エディタとサニタイザが同じ宣言から導かれる**構造にした。決定の経緯は
[本文サニタイズ設計.md §5.0](本文サニタイズ設計.md)、許可・拒否リストと理由の正本は
[本文サニタイズ設計.md](本文サニタイズ設計.md) §5。

**なぜ必要だったか**。棚卸しで、サニタイザが許可しているのにエディタが保存時に捨てる要素が
見つかった。エディタ側に `TEXT_BLOCK_TAGS = ['h1','h2','h3','p']` という手書きの表があり、
`h4`〜`h6`・`ul`・`table`・`blockquote` は**画面に出るのに次の保存で消えていた**。同じ理由で
B/I/U ボタンも事実上機能していなかった（シリアライザが `innerText` しか出さないため）。
許可リストを広げるだけでは「出るのに消える」要素が増えるだけなので、先に語彙を一元化した。

**語彙の一元化**。`GET /api/tag-schema` が構造HTMLとカスタム要素の**両方**を返すようにし
（`elements` / `void` / `block_id`）、エディタはDOMを辿る汎用シリアライザで書き出すようにした。
カスタム要素で既に確立していた「宣言は1つ、両者がそれに従う」形を構造HTMLへも広げた形で、
以後は `structuralElements` を直すだけでエディタが追随する。

**許可リストの拡張**。見出しは `h1`〜`h6`（目次は元から h1〜h6 を拾っていた）、
定義リスト `dl`/`dt`/`dd`、ルビ `ruby`/`rt`/`rp`（日本語の振り仮名）、区分 `section`/`article` 等、
折りたたみ `details`/`summary`、変更履歴 `ins`/`del`、表の完全な一族、`video`/`audio` などを追加。
`div`/`span` と `b`/`i` は**残す**と決めた（前者は構造の境界として意味があり、後者は貼り付けた
表現をそのまま保つため。エディタは常に `strong`/`em` を出すので表現の揺れは生まれない）。

**URLの規則を2種類に分けた**。利用者が自分でクリックする**リンク**（`href`・`cite`）は
外部URL可、閲覧するだけで自動取得される**埋め込み**（`src`・`srcset`・`poster`）は**相対のみ**。
外部の埋め込みは閲覧者のIPと閲覧時刻を第三者へ渡すトラッキングビーコンになるため。
あわせて**プロトコル相対URL `//evil.example/x` が素通りしていた穴を塞いだ**（`safeURL` が
スキーム空を一律「相対」と判定していた）。

**`document.execCommand` を廃止した**。仕様上 deprecated なうえ、生成されるHTMLがブラウザに
よって違う（`<b>` か `<strong>` か、`style="font-weight:bold"` か）。`style` はサニタイザが
落とすので**装飾が保存後に消える**経路でもあった。Range を直接操作して常に
`<strong>`/`<em>`/`<u>` を出す実装に置き換え、付け外しのたびに空要素・入れ子・隣接を整理する
正規化（`tidyInline`）を入れた。入れ子順序も正規化するので、太字→斜体と斜体→太字は同じHTMLになる。

**検証**。サニタイザ側はGoのテストで（新規許可要素・URL方針・危険要素の除去・**エディタ出力が
無変更で通ること**）、エディタ側は `index.html` から関数を抜き出したハーネスを実ブラウザで
動かして確認した（シリアライズ12件・装飾11件）。空要素だけは表記が変わるが
（エディタは `<br>`、Goの描画器は `<br/>`）、比較は描画後の文字列同士なのでエコーバックは起きない。

## 編集中のアンドゥ・リドゥを追加（2026-08-02）

Ctrl+Z / Ctrl+Y（Ctrl+Shift+Z）で編集中の操作を取り消せるようにした。方式は
[【考察】アンドゥ・リドゥ.md](【考察】アンドゥ・リドゥ.md) §3 のスナップショット方式の独自スタック。
ブラウザ標準の undo は `execCommand` とネイティブ入力しか捕捉せず、このエディタが多用する
プログラム的DOM操作（ブロックの挿入・並べ替え・置換、明細追加、カスタム要素の再描画）を
戻せないため、独自に持つ必要があった。キーは `preventDefault` して標準undoとの二重スタックを防ぐ。

粒度は「変更が確定した単位」＝保存が走る単位（既存の1.5秒デバウンス）とし、専用の変更検知は
作らず `saveToServer` の差分判定へ相乗りさせた。復元は既存の `populateEditor` を再利用している。

**設計文書 §7 の未決だった「キャレット復元方式」をここで決定した**。執筆時はブロックに識別子が
無く「全再描画でカーソルが飛ぶ」のが難所だったが、直前に入れたブロック単位保存の
`data-id` により `{ブロックID, 文字オフセット}` で復元できるようになった。アンドゥ時の
キャレットは、戻した先の状態が作られたときの位置ではなく**取り消した編集があった位置**へ置く。

履歴は編集セッションのもので、編集モードの出入りで初期化・破棄する。**編集権を失ったときも
破棄する**——本文がサーバーの最新版に置き換わり手元の編集も失われているため、戻せない状態へ
アンドゥできてしまうのを防ぐ。サニタイズで除去が起きたときは除去後の状態を積み直し、
危険な内容へ戻れないようにしている。

実装中に2件の不具合を踏んで直した。`focus()` をキャレットの範囲設定の後に呼んでいたため位置が
先頭へ上書きされていた件と、復元時に `applyMode()` を呼んでおらずアンドゥ直後にブロックが
`contenteditable` でなくなって文字が打てなくなっていた件。

なお**保存済み文書の版管理（②リビジョン／リバート）は引き続き未実装**。設計文書の
`【考察】` 接頭辞もそのため維持している。

## ブロック単位保存を追加（2026-08-02）

保存のたびに本文全体を送っていたのを、**変わったブロックだけ送る**方式に切り替えた。
`data-id` を**任意の属性**とし、無ければ従来どおり全文保存にフォールバックする設計に
したのが要点で、これにより「正本HTMLは人が読めて手でも書ける」という
[コンセプト](コンセプト.md)を保ったままブロック単位保存の利点を取れる。

属性名は当初 `data-block-id`（12桁の16進）だったが、**`data-id`（4桁の base36）へ短縮**した
（`data-block-id="4d32c9f7c1fa"` の28文字 → `data-id="pj1z"` の14文字）。短くした分の衝突は
**採番時に文書内の重複を検査して振り直す**ことで潰しており、ページ間コピーで生じた重複も
同じ経路で修復される。`id` にしなかったのは意図的で、本文はシェルと同じDOMへ合成されるため
`id` を許すと本文からシェル側の要素（`html-preview` 等）を乗っ取れてしまうから
（詳細は [本文サニタイズ設計.md](本文サニタイズ設計.md) §5.4）。

送信の判定は3通り。**変更が無ければ何も送らない**（従来は `focusout` のたびに、内容が変わって
いなくても全文をPOSTしていた）。1ブロックの内容だけが変わりIDがあればそのブロックだけ、
追加・削除・並べ替え・ID未採番・複数変更なら全文を送る。サーバー側は対象が見つからない・
IDが重複する場合に 409 を返し、クライアントは全文保存へ切り替える。

**効果の範囲は限定的**であることを設計判断として記録しておく。正本はファイル単位で書き直し、
`SyncIndex` もページ単位の洗い替えのままなので、減るのは送信量とエコーバックの粒度だけである。
同時編集の競合はページ単位の悲観ロックが既に防いでいる。実利が大きくなるのは
[タグ設計.md](【考察】語彙モデル.md) §7 の `<m-table>`（行数の多い明細表）や通信記録の長文取り込み、
将来のCRDT化で、その布石として入れた。

実装中に、差し込む断片の前後の空白を落とさないと**保存のたびに空行が1行ずつ増える**不具合が
出たので修正した（`trimEdgeWhitespace`）。回帰テストで冪等性を担保している。

## カスタムタグをプラグイン所有にし、`<m-file>` の責務を分離（2026-08-02）

「属性を読む場所（`plugin_*.go`）と許可する場所（`sanitize.go`）が分かれている」「`<m-file>` が
`tag` の値で意味を変えるのが不健全」という2つの設計指摘への対応。前者は実際に
`item-name` の宣言漏れで**保存のたびに値が消える**不具合を生んでいた。
プラグイン機構の導入（本文書の 2026-06-20 の節）が散弾銃手術アンチパターンとして
名指しし、「コアは無編集」を目標に掲げていた問題そのものである。

**カスタムタグはすべてプラグインが所有する形にした。** `Plugin` に必須メソッド `Tags()` を
追加し（任意インターフェースにしなかったのは、宣言せずに属性を読むプラグインをコンパイラに
書かせないため）、`PluginTags()` の和集合からサニタイズ許可リストを合成する。あわせて
`/api/tag-schema` で語彙をフロントへ配り、エディタのシリアライザを汎用化した。手書きの属性表が
消え、**保存する属性と許可される属性が同じ宣言から導かれる**ので食い違いようがない。
`m-tag` と `page_tags` もコアからプラグインへ移設し、コアテーブルは `pages`・`page_perms` だけ、
`parser.go` はタイトル抽出だけになった。

**`<m-file>` は純粋なファイル容器にした**（[【考察】通信記録処理.md](【考察】通信記録処理.md) §4.5）。
業務上の意味は中身の要素（`m-client-order`/`m-supplier-order`/`m-our-estimate`/
`m-supplier-estimate`）が持ち、プラグインは自分の要素を拾うだけでよくなった。`tag` による分岐は
Go・フロントとも全廃（`MFile.render` の276行の分岐が消えた）。PDFのパスは容器側にあるため
新ヘルパ `ClosestAttr` で親から取る。業務要素は単独でも置ける。

範囲は**構造の分離のみ**。値を属性から要素の中身へ移す転換（`<m-field>`/`<m-table>`、
`<m-tag>` の `value` 廃止、`<m-item>` の `<m-table>` 統合）は
[【考察】タグ設計.md](【考察】語彙モデル.md) の主題で、§2.5 の実装と一括で行う（個別だと二重移行になる）。

副産物として、再描画時に子要素の退避を `this.children` で行っていたため明細 `<m-item>` が
消える不具合を発見・修正した（前回の描画で挟んだクローム `<div>` の中に子が入るため、
子孫を辿って「直近のカスタム要素の祖先が自分」のものを拾う `takeCustomChildren` に置換）。

## 本文のサーバー合成と二層サニタイズ、`/upload` 廃止（2026-08-02）

ページ本文の配信方式を変更した。従来 `GET /{id}` は `assets/index.html`（静的な殻）を返すだけで、
本文はフロントが `/api/load` を叩いて `#editor-content` へ流し込んでいた。これを **サーバーが本文と
タイトルを埋め込んだ完成HTMLを返す方式**（`RenderPageShell`／[shell.go](../internal/cms/shell.go)）へ改めた。
初期表示のチラつきが消え、1往復減り、JSを実行しないクローラでも本文が読め、404・403・
ログイン誘導をサーバーが正しいステータスで返せるようになった。

**この変更にはサニタイズが不可分**だった。本文はそれまで無検査で保存されており、安全だったのは
フロントの `populateEditor()` が `DOMParser` 経由で挿入していた（＝本文中の `<script>` が仕様上
実行されない）ためにすぎない。合成方式では本文が初期HTMLの一部としてパースされるので、
中間版CSPが `script-src 'unsafe-inline'` を許している現状では実行されてしまう。そこで
**許可リスト方式のサニタイザ**（[sanitize.go](../internal/cms/sanitize.go)）を新設し、**保存時と描画時の
二層**で通すようにした。正本は [本文サニタイズ設計.md](本文サニタイズ設計.md)。

保存時サニタイズの「黙って内容が落ちる」難点は、**結果をエディタへ返して画面に反映する**
エコーバック方式で解決した（保存はブロックの編集完了時にも走り、除去が起きたブロックだけ
差し替えて通知する）。編集は必ずロック取得時の生HTMLから始まるため、サニタイズで欠けた内容が
保存されて正本を壊すことはない（「閲覧＝サニタイズ済み／編集＝生」の非対称）。
あわせて `updateHtmlPreview()` の属性値・テキストをエスケープするようにした（値に `"` を
入力しただけで生成HTMLが壊れ、属性注入も成立していた）。

未使用だった `POST /upload`（HTMLファイルを丸ごと取り込むエンドポイント）は削除した。
フロントに呼び出し元が無く docs にも記載の無い初期コンセプトの名残で、認証さえ通れば
任意のHTMLを無検査で正本へ書き込める入口でもあった（`/api/upload-pdf` は別物で現存）。

## `page_tags` の主キーを廃止し同名タグを許可（2026-08-02）

`<m-tag>` の `name` は自由語であり、担当者が2人・関連部品番号が複数といった多値属性は正当な
使い方だが、`page_tags` の `PRIMARY KEY (page_id, name)` がそれを禁じており、同名タグを2つ置くと
`SyncIndex` が UNIQUE 制約違反となって **本文ごと保存できない**（500）状態になっていた。
主キーを廃し、検索用の非一意インデックス `idx_page_tags_page_name` に置き換えた。
`page_tags` はアプリコードから読まれていない検索用インデックスで、タグ値を実際に使う
`plugin_materials.go` は DB ではなく HTML 木から読む `TagValue`（同名なら先頭を採る）を
使っているため影響は無い。`data/master` から再生成できる派生インデックスのため、開発環境では
`data/cms.db` を削除して起動し `RebuildIfEmpty` に作り直させた（本番環境は未稼働）。

## 同時編集の競合対策 Phase 1（悲観ロック・純HTTP）（2026-06-21）

同一ページ同時編集の lost update を防ぐため、ページ単位の悲観ロック（競合トリガー方式）を純HTTPで実装した。合意の経緯は [【考察】同時編集の競合対策.md](【考察】同時編集の競合対策.md)、確定仕様は [エディタ仕様.md](エディタ仕様.md) 10章・[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.3。

*   **堅牢化（ロックと独立）**: `database/sqlite.go` をDSNの `_pragma` で開き、全接続に `busy_timeout`・`foreign_keys`、DBに `journal_mode=WAL` を適用（シナリオD）。`reserveNewPageID` の `INSERT` 自動採番に統一し、非原子的な `GenerateNextID`(MAX+1) を廃止（シナリオE）。`TestReserveNewPageID` で並行一意性を検証。
*   **ロック基盤**（`cms/lock.go`）: プロセス内 mutex 付き map。無競合は無期限、他者要求から2分の猶予で強制明け渡し。待機キューは持たず（busy を返すのみ）、要求者のポーリング途絶（約30秒）で猶予キャンセル、保持者のポーリング途絶（約30秒）で待機者がいれば即解放。判定はアクセス時に遅延評価（常駐ゴルーチン不要）。時刻は引数注入で決定的にテスト可能。
*   **エンドポイント**（`cms/lock_handler.go`）: `POST /api/lock`（取得＝待機リトライ、成功時に最新HTML同梱）・`GET /api/lock-status`（死活更新＋待機者通知）・`POST /api/unlock`（sendBeacon 想定）・`POST /api/lock/force`（admin、`auth.Audit` 記録）。`SaveAPIHandler` がロックトークンを検証し、他者保持/失効は 409、ロック無しは許可。
*   **フロント**（`assets/index.html`）: 編集モード移行でロック取得＋最新版再ロード、busy 時の10秒空き待ち（空き次第で自動編集）、保持中の status 10秒ポーリング、`lost`/409 でクリップボード退避＋閲覧モード復帰。アプリ内通知エリア（トースト）新設、編集トグルが常に見えるようヘッダーを sticky 化。`toggleMode` を `applyMode`＋`onModeToggle` に分離。
*   **検証**: ロックの単体テスト（取得・強制明け渡し・死活奪取・離脱キャンセル・トークン検証・解放/強制解除/待機者通知）。実機（Claude in Chrome）で lock取得→status polling→save(token)→強制解除でlost検知→トースト＋閲覧モード切替まで確認、コンソールエラーなし。
*   **未実装**: Phase 2 の即時通知（SSE/WebSocket）、軽微な競合 B（原子的ファイル書き込み）・C（サイドカー直列化）。

## ページ属性のサイドカー化と独立サイドパネル（2026-06-21）

直前の `<m-page-info>`（HTML本文に属性を埋め込む方式）を見直し、UNIXに倣って
**「内容＝HTML本体／属性＝サイドカー `<id>.meta.json`」** に分離した。あわせてページ情報の
表示・編集を文書から切り離し、クローム側の**独立サイドパネル `<aside class="rail">`** へ集約した（Plan B）。
詳細仕様は [エディタ仕様.md](エディタ仕様.md) 9章・[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 2・4・8章。

*   **動機**: 親ページID・作成日時・作成者・更新日時は文書の「内容」ではなく「属性」であり、
    サイドカー（既に owner/group/mode を持つ正本）へ寄せる方が概念的に整合し、保存APIのHTML属性
    注入・改竄復元（`setPageInfoAttrs`）という一群の処理が不要になる。DB再構築で属性が失われない点は
    HTML埋め込み方式と同等に担保される（サイドカーもファイル＝正本のため）。
*   **サイドカー（`PageMeta`）**: `parent_id` / `created_by` を追加（`created_at` / `updated_at` は既存）。
    `WriteSidecar` は `updated_at` を空のときだけ補完し、本文保存は `BumpUpdatedAt`、親付け替えは
    `SetSidecarParent` が更新日時を進める（所有権の変更は chmod/chown 経由のみ＝自己認可を防止）。
*   **パーサ／同期**: `ParseCore` は属性抽出を廃しタイトル・タグのみ抽出（旧「親ページID」タグはスキップ）。
    `SyncIndex` は親・作成情報・更新日時をサイドカーから読む。
*   **API**: 保存（`SaveAPIHandler`）と新規作成（`NewPageAPIHandler`）を簡素化（HTMLは内容のみ）。

## プラグイン機構の導入（2026-06-20）

ユースケース追加が6ファイル13箇所の協調変更（散弾銃手術）を要していた状態を解消するため、レジストリ＋インターフェース方式のプラグイン機構を導入した。追加手順は [【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md) を参照。

### なぜ導入したか（旧 `【考察】拡張性とプラグイン化.md` の要旨）

「顧客の発注書」1ユースケースを追跡すると、追加には **6ファイル・13箇所**の協調変更が必要だった。
属性名はフロント（`observedAttributes`）・パーサー（`switch attr.Key`）・スキーマ（カラム名）の
**3箇所で一致**していないと動かず、1つのユースケースの知識が複数ファイルに散らばっていた。

**実際に不整合が起きていた**のが決め手。同期処理の「テーブル削除リスト」が2箇所に手書きで存在し、
すでに食い違っていた——`SyncIndex` の `tablesToDelete` には `our_estimates`/`supplier_estimates` が
あったが、`RebuildDatabase` の `tables` には無く、DB再構築時に削除済みページの見積もり行が残存した。
**同じ情報を複数箇所に手書きする設計が必然的に生む不整合**であり、単一の宣言から導出すれば
構造的に消える種類の問題だった。

増える13箇所の大半は機械的なボイラープレートで、本質的に変動するのは「タグ→テーブル→カラム」の
マッピング宣言1つに集約できる。ただし**集計ロジックだけは宣言化できない**（BOM計算や利益率計算は
JOINや乗算を伴う固有のロジック）。そこで2階層に分けた。

- **Tier 1: 宣言的マッピング** — `Plugin` インターフェース＋レジストリ。パース・スキーマ・同期を宣言から導出。
- **Tier 2: コードプラグイン** — `RouteProvider` で集計APIを登録。

Goの `plugin` パッケージによる動的ロード（`.so`）は**採用しなかった**。Windows非対応で、本プロジェクトは
Windows開発＋Linux配備のため。代わりにGoが標準採用している**レジストリ＋インターフェース方式**
（`database/sql` のドライバ登録、`image` のデコーダ登録と同じ流儀）を用いた。これは
[開発方針.md](開発方針.md) の「標準ライブラリ優先・外部依存最小」とも整合する。

結果、ユースケース追加は「**自分自身を登録する1ファイルを足すだけ、コア6ファイルは無編集**」になった。

*   `internal/cms/plugin.go` を新規作成し、`Plugin` インターフェース・レジストリ・`ApplySchema`・`PluginRoutes`・DOMヘルパーを実装。
*   既存の4ユースケースを `plugin_client_order.go` / `plugin_our_order.go` / `plugin_estimates.go` / `plugin_materials.go` に分離（各々が `Schema`/`Tables`/`Sync` を持ち `init()` で自己登録）。
*   `parser.go` をコア抽出（`ParseCore`: タイトル・親ID・タグ）のみに縮小。`ParseHTMLMaster` と各ユースケース構造体は廃止。
*   `sync.go` の `SyncIndex` をコア同期＋プラグイン走査に変更。`RebuildDatabase` は全プラグインの `Tables()` を走査する形にし、削除リストの二重管理を解消。
*   `database/sqlite.go` はコアテーブル（pages / page_tags）のみ作成する `CreateCoreTables` に縮小。ユースケース固有テーブルはプラグインの `Schema()` へ移管。
*   `main.go` で `cms.ApplySchema()`（テーブル作成）と `cms.PluginRoutes()`（集計APIルート登録）を呼ぶよう変更。`/api/required-materials` のハードコード登録を撤去。
*   テストを本番同一スキーマ（`CreateCoreTables` ＋ `ApplySchema`）で動かすよう更新し、テスト内のCREATE TABLE重複を排除。
