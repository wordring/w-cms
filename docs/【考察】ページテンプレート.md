## 1. 目的・背景

新しいページを作るとき、文書の形式によっては**必要な項目があらかじめ決まっています**
（受注ページなら発注書番号・顧客名・明細表、検査記録なら検査項目の並び）。
毎回ゼロから組み立てるのは手間で、しかも人によって項目が揺れます。

一方で**テンプレートの単純なコピーでは足りません**。日付は作成時の日付であるべきですし、
発注書番号のように一意でなければならない値もあります（コピーすると衝突します。§4.1）。

「あらかじめ形の決まった文書を、書き込みを伴って作る」——これが本書の主題です。

## 2. 現状：ブロック単位のテンプレートは既にある

ページ単位の話に入る前に、**同じ問題をブロック単位では既に解いている**ことを確認します。

スラッシュメニューの挿入骨格（[app.js](../assets/app.js) の `buildVocabSkeleton`）は、
語彙レジストリ（[vocab.go](../internal/cms/vocab.go)）の列定義から
`<table data-type>` / `<dl data-type>` / `<section data-type>` の骨格を機械的に生成します。
しかも**動的な書き込みまでやっています**——`defaultFieldValue` が日付列に今日の日付を、
`order-no` に一意な仮番号を埋めます。

つまり本書の主題は「**ブロックで解けたことをページ単位へ持ち上げる**」ことです。
新しい発明はほとんど要りません。

一方、ページ新規作成（[handler_tree.go](../internal/cms/handler_tree.go) の
`NewPageAPIHandler`）は現状、固定の `<h1>新しいページ</h1><p>ここから編集を始めてください。</p>`
をサーバーが書き出すだけです。

## 3. テンプレートの置き場所

### 3.1 検討した3案

| 案 | 内容 | 判定 |
|---|---|---|
| **A: レジストリ宣言** | `VocabDef` と同様、Goコードの宣言テーブルで持つ | **却下**。テンプレートを1つ足すたびにデプロイが要る。テンプレートは現場が育てるものなので硬すぎる |
| **B: テンプレートもWikiページ** | テンプレートを普通のページとして書き、新規作成時に本文をコピーする | **採用** |
| **C: 複製機能として一般化** | 「このページを複製」を作り、テンプレートは複製の起点にすぎないとする | **後回し**。案Bの実装は本質的に「本文コピー＋新規化パス」なので、複製機能は後からボタン1つで落ちてくる |

案Bを採る理由は、**新しい機構がほぼ要らない**ことです。編集はいつものエディタ、権限もいつもの権限、
保存もサニタイズもいつもの経路を通ります。「文書がそのままデータベース」という
[コンセプト.md](コンセプト.md) とも一致し、語彙レジストリの将来像
「(c) 語彙定義ページ」（[vocab.go](../internal/cms/vocab.go) 冒頭のコメント）とも同じ方向を向きます。

### 3.2 見分け方：テンプレートフォルダの葉（決定）

案Bには「どのページがテンプレートか」を見分ける必要があります。
当初は**タイトル接頭辞 `【テンプレート】`**（docs/ の `【考察】` と同じ流儀）を検討しましたが、
**取り下げました**。決定した規則は次のとおりです。

> **テンプレートルートの子孫のうち、子を持たないページ（＝葉）がテンプレートである。
> 子を持つページは分類のためだけに存在する。コピーされるのは常にそのページ1枚だけ。**

```
000000 トップ
└── テンプレート          ← ルート（分類・テンプレートではない）
    ├── 業務              ← 枝＝分類
    │   ├── 受注ページ     ← 葉＝テンプレート
    │   └── 進捗ページ     ← 葉＝テンプレート
    └── 記録              ← 枝＝分類
        └── 検査記録       ← 葉＝テンプレート
```

**接頭辞案より優れている点:**

- **タイトルが汚れない。** 接頭辞案では `【テンプレート】受注ページ` をコピーした結果が
  `【テンプレート】受注ページ` になり、接頭辞を機械的に剥がす（＝魔法）か人が毎回改名するかの
  二択だった。フォルダ方式なら**テンプレートのタイトルがそのままコピー先の正しいタイトル**になる。
- **分類が階層でタダで手に入る。** テンプレート選択メニューの構造は既存の `/api/children` と
  ページ階層レールの描画がそのまま使える。「一覧をどう分類するか」という別問題が消える。
- **権限が既存の継承でそのまま効く。** 新規ページは親から group/mode を継承するので
  （`NewPageAPIHandler`・setgid 相当。[認証認可設計.md](認証認可設計.md) 10.4）、
  テンプレートフォルダを広いグループで作れば配下は自動的に共有される。
- テンプレートは**普通のページなので普通に開いて確認できる**。
- 子を持つページは削除できない規則があるので（`DeletePageAPIHandler`）、
  **分類フォルダを誤って消せない**。

**「葉だけ」とした理由:** 「子孫はすべてテンプレート」だと分類の階層とテンプレートの階層が混ざり、
「受注テンプレートの子に置いた進捗テンプレートは、独立したテンプレートなのか受注の構成要素なのか」が
決まらない。葉だけに限れば**ページは必ず分類かテンプレートのどちらか一方**で、曖昧さが消える。
副次的に、**分類ページは誤ってコピーされ得なくなる**（枝は選択肢に出ないため）。

**分類ページの本文は説明の置き場になる。** 葉だけがテンプレートということは、テンプレートページに
「このテンプレートの使い方」という子ページを付けられない（付けた瞬間に枝へ降格する）。
かわりに**説明は親の分類ページの本文に書く**。分類ページはコピーされないので、そこに何を書いても
増殖しない。むしろ「このカテゴリのテンプレートをいつ使うか」の説明場所として自然。

**位置で決まることの帰結:** テンプレートに子を足すと黙って一覧から消える。ただし
**ページ階層レールに子が見えている**ので原因は目視で辿れる。タイトルの h1 も位置で決めている
（[変更履歴.md](変更履歴.md) 2026-08-20「ページタイトルの h1 に `data-type` を付ける案は見送った」）ので、
方針としては一貫している。

### 3.3 ルート自身の見分け方（決定）

規則が入れ子になるため、**テンプレートルート自身をどう見分けるか**を別に決める必要があります。
現状、設定を置くテーブルはありません（`CoreTables` は `pages` と `page_perms` の2つだけ）。

> **決定: トップページ（`000000`）の子で、タイトルが「テンプレート」であるページをルートとする。**

- スキーマ追加もUI追加も**ゼロ**。HTML本文由来のタイトルなのでDB再構築でも失われない。
- 名前を持つのは**1ページだけ**で、しかもフォルダ名なのでコピー先のタイトルへ漏れない
  （接頭辞案を却下した理由がここでは当てはまらない）。
- 環境ごとに独立したデータ（職場・自宅）でも、それぞれ作れば揃う。

**対案（将来の昇格先）→ 2026-08-21 に不採用**: サイドカー属性 `template_root: true`
（`public` と同じ流儀）。改名に強い代わりに右パネルへのUIが要る。**先祖辿りの実装は両案で同一**
なので、脆いと分かったら判定の述語だけ差し替えれば移行できる——という逃げ道を用意していました。
いったんは「サイドカー属性 `template_root` へ昇格し、右レールにトグルを追加する」と決めましたが、
**2026-08-21 にその決定は取り消され、作業は着手前に中止**になりました。ユーザーの判断は

> 機能が名前で変わるのは目論見通りです。
> 表示されている言葉が機能を表します。

というもので、**h1（ページ名）で機能が決まること自体が意図した挙動**です（§9）。
実装は h1 判定のまま——[template.go](../internal/cms/template.go) の `isTemplateRoot` は
`pageTitleFromDisk(id) == TemplateRootTitle` を見ています（template.go:101-113）。

**受け入れたリスク**: 名前で決まる以上、**トップ直下のページを「テンプレート」に改名すると
その配下は②索引・③計算から外れ**、逆にルートを別名へ改めれば配下は普通のページとして
索引されます（反映は各ページを次に保存したときかDB再構築のとき）。**どちらも告知は出ません**
——保存時のエコーバックは未知の `data-type` と未解決の項目名だけで
（[handler_save.go](../internal/cms/handler_save.go) の `unknown_types` / `unresolved_fields`）、
ルートの改名を見る仕掛けはありません。これは決定と引き換えに**受け入れたリスク**であり、
「ルート名の変更を保存時に知らせる」案は**未検討**です（§8）。

**注意すべき縁の場合:**

- **ルート自身は常にテンプレートではない。** 配下が空のときルートが葉になってしまうため、明示的に除外する。
- **空の分類フォルダは葉になる。** 「業務」を作ってまだ中身を入れていない段階では
  テンプレートとして選べてしまう。実害は「空のページができる」程度で、中身を入れれば自動的に
  解消するので v1 では放置とする。
- ルート候補が複数あるとき（トップの子に「テンプレート」が2つ）はIDの小さい方を採る。

## 4. 「単純なコピーではダメ」——書き込みをどう表すか

### 4.1 第1層：型が知っていることは型に埋めさせる（v1 の範囲）

`defaultFieldValue`（§2）の規則をサーバー側の**新規化パス**へ移植します。規則は1つです。

> **テンプレートの空欄は、列型の既定値で埋める。書いてある値はそのまま保つ。**

| 列型 | 空欄のとき |
|---|---|
| `date` | 今日の日付 |
| `order-no`（機械キー） | 新しい一意番号 `PO-<新ページID>`（同一ページ内の2件目以降は `-2` 連番） |
| `text` / `enum` / `number` / `image` | 空のまま（人が書く） |

番号にページIDを使うのはエディタの `defaultFieldValue`（時刻の下6桁）より衝突しにくく、
**番号から由来ページを辿れる**ためです。

**`order-no` の再採番は必須です。** 同じ番号の発注書が何枚もできると、番号でページを
引いたときに区別がつきません。

> **かつては DB が止めてくれていました**——`client_orders` / `our_orders` の `order_no` に
> **UNIQUE 制約**があり、番号入りのテンプレートをそのままコピーすると2枚目の保存で
> 衝突しました。両テーブルは D-1（2026-08-31）で廃止されたので、**いまは何も止めません**。
> 再採番だけが番号の重複を防いでいます。**テンプレート機能を作るなら新規化パスは省けません。**

新しい構文を発明せず、レジストリが既に持つ型知識だけで動きます。テンプレート作者は
「空欄にしておけば埋まる」と覚えるだけで済みます。

### 4.2 第2層：地の文のプレースホルダ（v1 では入れない・未決）

第1層は型付きブロックの中しか埋められません。`<h1>検査記録 2026-08-20</h1>` のように
**タイトルや段落へ日付を入れたい**場合は、`{{今日}}` のような可視プレースホルダを
**テキストノード置換**で処理する案があります。

- テキストノードに対する置換なのでHTML注入の危険はなく、置換されなかったプレースホルダは
  **そのまま見える**＝壊れ方が自己申告的。「見える文字がすべて」
  （[【考察】語彙モデル.md](【考察】語彙モデル.md) §5.1）とも矛盾しない。
- ただし語彙は最小に絞る（`{{今日}}`・`{{作成者}}` 程度）。増やすとテンプレート言語への坂道を転がる。

**v1 は第1層だけで始めます。** タイトルへの日付挿入の実需が出てから第2層を検討します。

### 4.3 第3層：対話的な入力フォームは作らない

「顧客名を入れてから作成」のようなフォームダイアログは**作りません**。
新規ページは既に `?edit=true` で開くので（`NewPageAPIHandler` の末尾）、
**ページ自体が入力フォーム**です。空欄の骨格へキャレットを置けば足ります。

## 5. コピー時に気をつけるもの

| 対象 | 扱い |
|---|---|
| **`data-src`（配線）** | テンプレートに配線が残っているとコピーが元ページを指してしまう。進捗テンプレートが指すべき受注ページは作成時には決まらないので機械的な解決は無い。**v1 は「テンプレートには `data-src` を書かない」を作法とし**、含まれていたら保存時告知の流儀（`UnknownVocabTypes` と同様）で知らせる程度に留める |
| **`data-id`（ブロックID）** | ページ内で一意なら十分（参照は `ページID#ブロックID`）なので、コピーしてもそのまま衝突しない。**再採番は不要** |
| **計算ビュー** | 空マーカーなのでコピーはそのまま動く（サーバー事前描画が埋める）。むしろテンプレートと相性が良い |
| **サニタイズ・権限** | コピーはサーバー側処理（`/api/new-page?parent=X&template=Y` 等）とし、テンプレート本文は**サニタイザを通してから**書き出す。テンプレートページへの read 権限を要求する |
| **スナップショット意味論** | コピー後にテンプレートを直しても既存ページは変わらない。これが正しい挙動で、追従させる仕組みは要らない |

## 6. ②索引・③計算からの除外（実装の必須事項）

**ここは見落とすと静かに壊れます。**

[sync.go](../internal/cms/sync.go) の `SyncIndex` は保存のたびに本文を回覧させるため、
`client-order` を含むテンプレートページを保存すると、**仮の発注書が②汎用索引に入って
手配集計に出てきます**。

> **除外の規則: テンプレート領域（ルート自身とその配下すべて）は、プラグイン同期を行わない。
> コア（`pages` / `page_perms`）は従来どおり同期する。**

葉か枝かは**問いません**。分類ページに業務データは入らないので、領域ごと一律に除外するのが
単純です。**ルート自身も含めます**——分類ページと同じく業務データを持たないうえ、
「説明のつもりで書いた例の発注書が集計に出る」事故も防げるためです
（判定は `IsTemplateArea`。テンプレートとして選べるかを問う `IsUnderTemplateRoot` は
ルートを含まない、という別物です）。コアを同期し続けるので、テンプレートページは普通に存在し、
閲覧も権限判定もページ階層への表示も従来どおり動きます。

**除外は「プラグインを飛ばす」ではなく「空の本文を渡す」形で実装します。** 全プラグインの
`Sync` は冒頭で当該ページの行を `DELETE` する洗い替えなので、空を渡せば「古い行は消える・
新しい行は入らない」となり、**普通のページをテンプレートフォルダへ移したときに古い行が
残りません**（飛ばすと残ります）。冪等で自己修復もします——`PurgePageIndex` と同じ流儀です。

### 6.1 先祖辿りは必ずサイドカーで行う（罠）

判定は「先祖にテンプレートルートがいるか」の親チェーン辿りになります。
既存の `EffectivePublic`（[perms.go](../internal/cms/page/perms.go)）が同じ形をしていますが、
**あれは `pages` テーブルから `parent_id` を読んでいます。同じやり方を `SyncIndex` の中でやると
DB再構築で壊れます**——`RebuildDatabase` は空のDBへページを1つずつ同期するので、
先祖がまだ `pages` に入っていない順序で子が同期されると「テンプレートではない」と誤判定し、
**静かに索引が汚れます**。

親の正本はサイドカー（`<id>.meta.json`）なので、**先祖辿りは `page.ReadSidecar` で行えば
順序に依存しません**。`EffectivePublic` 自体はリクエスト時にしか呼ばれないため現状は問題ありません。

**ただしサイドカーにタイトルはありません**（`PageMeta` は owner/group/mode/public/parent_id/日時のみ）。
そのため「その先祖が『テンプレート』という名前か」はディスクの本文HTMLを読んで `ParseCore` で
取ります（[template.go](../internal/cms/template.go) の `pageTitleFromDisk`）。
**先に親を見て弾く**ので、1回の親チェーン辿りでファイルを読むのは高々1ページ分です
——「トップの直下」という条件を満たす先祖は鎖の中にただ1つしか無いからです。
ファイルはディスクに常にあるので、順序非依存という性質は保たれます。

### 6.2 葉の判定が要るのはメニューのときだけ

**葉かどうかを問うのはテンプレート選択メニューを出すときだけ**で、それはリクエスト時＝DBが
揃っている場面です。したがって §6.1 の罠は葉の判定には及びません。判定クエリも新規に
考える必要はなく、削除ハンドラが既に持っているもの
（[handler_delete.go](../internal/cms/handler_delete.go) の
`SELECT COUNT(*) FROM pages WHERE parent_id = ?`）がそのまま使えます。

### 6.3 親の付け替え

ページをテンプレートフォルダへ出し入れすると**そのページの性質が変わります**。
親の付け替え（`/api/page-meta`）の後は索引を張り直す必要があります
（テンプレートへ入れたなら `PurgePageIndex` 相当、出したなら `SyncIndex` の再実行）。

## 7. UI

「＋ 子ページを作成」ボタン（[index.html](../assets/index.html) の `w-create-subpage-btn`）を
押したとき:

- テンプレートルートが存在しない、または葉が1つも無ければ**従来どおり即作成**（現在の挙動）。
- あれば小さなメニュー（`#w-template-menu`）を出す。先頭が「空のページ」、以下がテンプレート一覧。
  一覧の構造はルート配下のツリーそのままで、**枝は見出し、葉は選択肢**になる。
  中身は `GET /api/templates`（[handler_template.go](../internal/cms/handler_template.go)）が返す。

階層の字下げは段数が可変なので、CSSクラスではなく描画後に `element.style.paddingLeft` で
当てます（CSP strict のためインラインの `style` 属性は書けない）。

### 7.1 テスト環境の注意（`:memory:` が使えない）

`/api/templates` は `visibleChildren` を使いますが、これは**行を回しながら1件ずつ
`page.GetPerms` を引く**形です。入れ子のクエリはプールの別接続で走り、`:memory:` DBでは
**接続ごとに別の空DB**になるため、権限がフェイルクローズして子ページが1件も見えなくなります。
そのため一覧のテストだけは**ファイルDB**で用意します（`setupTemplateAPITest`）。
本番（`data/cms.db`）はファイルなので同じ問題は起きません。

1. **`data-src` を含むテンプレートの扱い**——作法で済ませるか、保存時告知を実装するか（§5）
2. **第2層のプレースホルダ**——実需が出たときに `{{今日}}` 方式でよいか（§4.2）
3. **複製ボタン**（案Cの副産物）——テンプレートに限定するか、任意のページを複製できるようにするか
4. **テンプレートの公開**——テンプレートフォルダを匿名公開されると配下が公開可能になる。
   ガードを入れるか（`EffectivePublic` は鎖の全段が public を要求するので、
   明示的に公開しない限り露出はしない。リスクは低い）
5. **一式テンプレート**（複数ページのセット）——v1 はスコープ外。必要になったら明示的な仕組みとして足す
6. **ルート名を設定で変えられるようにするか**——ユーザーは B-9 の回答で
   「テンプレートという名前は設定でかえられる方が良いかもしれません。」とも述べている。
   判定を h1 のままとしたうえで、比較先の文字列だけ設定で差し替える形になる
   （現状は定数。[template.go](../internal/cms/template.go) の
   `const TemplateRootTitle = "テンプレート"`）。**未検討**
7. **ルート改名の告知**——トップ直下のページを「テンプレート」に改名した／ルートを別名へ
   改めたときに、保存時のエコーバックで知らせるか（§3.3 の受け入れたリスク）。**未検討**

## 9. 決定ログ

| 日付 | 決定 | 理由 |
|---|---|---|
| 2026-08-20 | テンプレートは**普通のWikiページ**として持つ（案B） | 新しい機構がほぼ要らない。編集・権限・保存が既存経路に乗る |
| 2026-08-20 | 見分け方は**テンプレートフォルダの葉**。枝は分類 | タイトルが汚れない・分類が階層でタダ・権限が継承で効く。ページが必ずどちらか一方になり曖昧さが消える |
| 2026-08-20 | コピーは**常に1ページだけ** | 一式テンプレートは別問題として切り離す |
| 2026-08-20 | ルートは**トップの子でタイトルが「テンプレート」** | スキーマもUIも増やさない。名前を持つのが1ページだけなのでコピー先へ漏れない |
| 2026-08-20 | 書き込みは**型の既定値だけ**（v1） | レジストリが既に持つ知識で足り、新しい構文を発明しない。`order-no` の再採番は UNIQUE 制約のため必須 |
| 2026-08-20 | 対話的な入力フォームは**作らない** | 新規ページは編集モードで開くので、ページ自体が入力フォーム |
| 2026-08-21 | ルートの判定は **h1（ページ名）のまま**とする。サイドカー属性 `template_root` への昇格は**不採用**（同日の「昇格して右レールにトグルを追加する」決定を取り消し。着手前に中止） | ユーザーの判断:「機能が名前で変わるのは目論見通りです。表示されている言葉が機能を表します」。名前が機能を表すのは仕様であって欠陥ではない。改名で配下が②索引・③計算から出入りするリスクは、告知が出ないまま**受け入れる**（§3.3） |
