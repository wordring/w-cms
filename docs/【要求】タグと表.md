# 【要求】タグと表

**本文に書いたタグと表が、DB（データベース）に入る仕組み**の要求仕様です。

- **タグ**は、本文に書く「名前：値」の組です。HTML では `<dl data-type="tags">` と書きます（§2〜§11）。
- **表**は、本文の `<table>` です（§12〜§19）。

**タグと表は、w-cms の土台です。**
w-cms は、「業務データ用のテーブルを作らない」ことにしています。専用テーブルはゼロです。
本文に書いたタグと表が、そのまま DB に入ります。
横断検索・計算ビュー・参照リンクは、そこから読みます。

## 1. 一文でいうと

> **タグと表だけがDBに入る。**

本文には、段落・見出し・画像など、いろいろなものを書けます。
そのうち DB に入るのは、タグと表だけです。

> 2026-09-18 利用者:「素の定義リストはDBから外しましょう」

この決定で、説明が1文で済むようになりました。
それまでは、素の `dl`（`data-type` の付いていない定義リスト）も DB に入っていました。
画面では区別が付かないのに、振る舞いが違いました。そこが混乱の元でした。

| 本文に書いたもの | DBに入るか | 行き先 |
|---|---|---|
| `<dl data-type="tags">` | **入る** | `page_tags`（§2〜§11） |
| `<table>`（`<caption>` のあるもの） | **入る** | 表の写し（`data/tables.db`）。登録された形式なら集計の索引（`vocab_index`）にも（§13） |
| `<caption>` の無い `<table>` | ⚠ **入らない**（古い本文の `data-type` で名乗る表を除く） | — |
| 素の `<dl>`（`data-type` 無し） | ⚠ **入らない**（2026-09-18 から） | — |
| `<p>`・見出し・画像など | 入らない | — |

行き先に出てくる言葉は、次のとおりです。

- **索引**は、検索や集計のために、本文から抜き出して DB に入れたものです。
  タグの索引が `page_tags`、表の集計の索引が `vocab_index` です。
- **表の写し**は、キャプション（`<caption>`。表の題）の付いた表を、DB のテーブルとして写したものです（`data/tables.db`）。
- **登録された形式**は、語彙のレジストリ（登録簿）に載っている、表の種類のことです（§12・§13）。

**表は、`<caption>` で名乗ります。**
節の見出し（`■材料` など）では、表の種類を名乗れません。
見出しで読むと、表を節の外へ動かしただけで、黙って材料表でなくなってしまうからです。

> 利用者:「最終的には節の中のPDFを節の外にも動かせるようにしたい」

## 2. 形

タグは、本文に次の形で書きます。

```html
<dl data-type="tags">
  <dt>仕入先</dt><dd>みなと商店</dd>
  <dt>部材発注日</dt><dd>2026-09-23</dd>
  <dt>部材発注担当</dt><dd>000031-a1b2</dd>
</dl>
```

- **本文に書きます。** 本文が正本（もとになる本物）で、DB は派生（本文から作る写し）です。
- **1ページに何枚でも置けます。同じ名前を何個でも置けます。**
  代表的な例は `メールアドレス` です。1つの連絡先ページに、窓口・担当・共有アドレスが並びます。
- ⚠ **`data-type="tags"` の無い素の `dl` は、索引に入りません。**
  見た目は同じなので、「書いたのに検索に掛からない」という、気づきにくい形になります。

  > 2026-09-18 利用者:「素の定義リストは DBから外しましょう」

- ⚠ **参照として読むのも、このタグの中だけです。**
  参照は、ほかのページやブロックを指す値のことです（§7）。
  素の `dl` まで見ると、発注書番号 `250401-203` が「6桁-英数字」の形に当てはまって、参照に化けます。

### 空欄の形

空欄は、`<dd><br/></dd>` という形で保存されます。
サニタイズ（本文から、許可されていない要素や属性を取り除く処理）が、空の `<dd>` に `<br>` を入れるためです。

**開発者向けの注意**

- `<dd>([^<]*)</dd>` だけで探すと、空欄を素通りします。
  2026-09-11 に、これで `客先` を3枚取りこぼしました。
- 読み書きは `replaceFirstFieldValue` を通すこと（`<br>` も空と扱います）。

## 3. 型は**名前**で決まる

タグの値には、型があります。型は、数・日付・参照のような、値の種類のことです。
その型は、タグの**名前**で決まります。

> 2026-09-06 利用者:「名前が『受信元』であれば値は『参照』」

タグ1つずつに `data-type` の属性で型を明示する案は、採りませんでした。
コピー＆ペーストで型が落ちますし、100ページに同じ属性を書くことになるためです。

名前と型の対応は、設定のファイル [config/settings.json](../config/settings.json) の `vocabulary` が正本です。
`vocabulary`（語彙）は、w-cms に登録した言葉と、その型や選択肢の決まりです。

```json
"vocabulary": {
  "単価":   { "type": "number" },
  "発注日": { "type": "date" },
  "受信元": { "type": "ref" },
  "状態":   { "type": "enum", "values": ["未着手", "納品済", "完了"] }
}
```

- **名前が型を決めるので、型はシステム全体でひとつです。**
  `発注済` を `bool` にしたら、どのページのどのタグも `bool` です。
  揺れないのが利点ですが、場所によって意味を変えることはできません。
- **設定は Git で管理します。** 語を足せば、`git pull` で全部の環境へ届きます。
- ⚠ **語を足したら、DB を再構築します**（`POST /api/rebuild-db`。再起動は要りません）。
  忘れると、索引に載らないままになります。エラーは出ません。
- ⚠ **設定が壊れていると、起動を止めます**（仕様です）。
  Go のコードに、既定値はありません。
  黙って既定値で上書きすると、運用者が足した語が消えてしまうためです。

### 型の一覧（9種）

「畳む」は、表記の揺れ（全角と半角、大文字と小文字など）を、1つの形にそろえることです。正規化とも呼びます。
畳んだ値は、索引の `norm_value` という列に入ります。生の値（書いたままの値）も、別の列に残ります（§4）。

| 型 | 何を表すか | 畳み方（`norm_value`） |
|---|---|---|
| `text` | 自由文 | 全角英数・半角カナ・直径記号を畳む。⚠ **長音には触らない** |
| `code` | 番号・記号（図面番号・品番・発注書番号） | `text` に加えて**空白・ハイフン類・長音・大小**も畳む |
| `number` | 数 | 数として格納（⚠ 文字列にしない。§5） |
| `date` | 日付 | ISO（`2026-09-23`） |
| `datetime` | 日時 | ISO |
| `enum` | 決まった選択肢 | `text` と同じ |
| `image` | 画像 | — |
| `ref` | **他のページ／ブロックを指す**（`ページID-ブロックID`） | — |
| `email` | `名前 <アドレス>` | **アドレスだけ** |

`text` と `code` の違いは、畳む強さだけです。
`レーザー` は、`text` ならそのままです。`code` なら `レ-ザ-` になります。

**開発者向けの注意**

- 機械が書く名前に `NormalizeCode` を使わないこと。上のとおり、長音が `-` に変わります。

### 引き方

タグからページを探す口（プログラムの入口）は、2つです。

| 口 | 何で引くか |
|---|---|
| `PagesByTag` | **生の値**で完全一致 |
| `PagesByTagLoose` | **畳んだ値**で一致（大小・全角・区切りの揺れを越える） |

どちらで引くかは、呼ぶ側（その口を使うプログラム）が選びます。

**開発者向けの注意**

- 2段にはしません。1つの口にまとめて、「生の値で引いて、駄目なら畳んだ値で引く」という形にはしません。
- 畳んだ文字列だけを返す口（`NormalizeForLookup`）は、撤去しました。
  `norm_value` が宣言型を持たなくなってから（§5）、
  文字列で引くと、`number` のタグがエラーにならず0件になるためです。

## 4. 行き先は `page_tags`

タグは、DB の `page_tags` というテーブルに入ります。列は次の5つです。

| 列 | 中身 |
|---|---|
| `page_id` | ページ番号 |
| `seq` | **ページ通し**の連番（`dl` ごとに 0 へ戻さない） |
| `name` | 名前（`<dt>` の表示文字） |
| `value` | 値（生） |
| `norm_value` | 畳んだ値（§5） |

**主鍵は `(page_id, seq)`** です。主鍵は、行を1つに決めるための鍵です。

**業務ブロック（表）は、別のテーブルに入ります**（`vocab_index`。§14）。
タグと表とで、行き先を分けてあります。
分けた経緯は、[【考察】タグ表と業務ブロック表の分離.md](考察/【考察】タグ表と業務ブロック表の分離.md) §8 にあります。

**開発者向けの注意**

- タグと表を書き分けるのは、1か所だけです（`insertVocabEntry`）。
  振り分けをほかの所でやると、片方だけ直した日に、黙ってずれます。
- 主鍵を付けた日に、隠れていた重複が2件出ました。
  洗わずに（古い行を消さずに）書き足していた所と、`dl` ごとに番号を 0 へ戻していた所です。

## 5. ⚠ `norm_value` は宣言型を持たない——型は**値**が持つ

`norm_value`（畳んだ値の列）には、種類の違う値が入ります。

> 2026-09-15 利用者:「norm_value は文字列、数値、時刻のような種類が考えられます」

そこで、この列には型を宣言していません。型は、入れる値のほうが持ちます。
宣言型は、DB のテーブルを作るときに、列ごとに書く型のことです（`TEXT` など）。

理由は、数の並び方です。
SQLite（w-cms が使っている DB）は、宣言の無い列で、値ごとの格納クラスを保ちます。
格納クラスは、SQLite が値ごとに持つ種類のことです（整数・実数・文字など）。
`TEXT` と宣言すると、数まで文字列に化けて、**`"8000" < "900"`** になります（実測）。

| 宣言 | 並び |
|---|---|
| `TEXT` | `12.5, 8000.0, 900.0, abc` ⚠ |
| **宣言なし** | `12.5, 900, 8000, abc` ✓ |

種類の違う値が1つの列に混ざっても平気な理由は、2つです。

1. 並びは格納クラスのグループ順になり、範囲が重なりません。
2. 問いは必ず `name`（タグの名前）で絞ります。そして、名前が型を決めます。

⚠ **代償は「型を取り違えると、エラーにならず0件」です。**

**開発者向けの注意**

- 値を束ねる（SQL へ渡す）形は、`tagNormBind` の1か所に閉じてあります。
  書き手（`insertVocabEntry`）と読み手（`PagesByTagLoose`）が、同じ関数を通ります。
- 範囲で引く口を足すときも、同じ関数を通すこと。
- 整数は、整数の格納クラスへ入れます（`REAL` だと `3` が `3.0` になります）。
- 番人（決まりが破られていないかを見張る試験）は
  [page_tags_norm_type_test.go](../internal/cms/page_tags_norm_type_test.go) です。

### ⚠ 畳めなかったタグは、並べると先頭・絞ると消える

`date` 型のタグに `未定` と書くと、日付としては畳めません。
このとき、`norm_value` は **NULL**（値が無いことを表す印）になります。
生の値は、正本として残ります。

| 書き方 | `未定` の行 |
|---|---|
| `ORDER BY norm_value` | **先頭に来る**（SQLite は NULL を最小として並べる） |
| `WHERE norm_value <= ?` | **黙って消える**（NULL の比較は偽） |

正反対の振る舞いが、同じ列から出ます。

⚠ **日付で並べる・絞るビュー（画面）を作るときは、畳めなかった値を別枠で必ず見せること。**
黙って落とすと、「納期が書いてあるのに一覧に出ない」になります。

**開発者向けの注意**

- SQL では、`norm_value IS NOT NULL` を明示すること。

## 6. 揺れを畳む

同じものが違う字で書かれていても見つかるように、表記の揺れを畳みます。
何を・どこで・どう畳むかは、次のとおりです。

| 何を | どこで | 規則 |
|---|---|---|
| 全角英数・半角カナ | `NormalizeText` | NFKC |
| **直径記号** | 設定 `char_folding` | `Φ ϕ ⌀ Ø ø Ф ф` → `φ`。⚠ **NFKC では畳めません**（別系統の文字）。⚠ **足したらDB再構築** |
| 機械が書き起こす**名前** | `NormalizeNameForIngest` | 書く**時点**で NFKC（どの名前に掛けるかは拡張が決める） |
| 社名の法人格 | `cms.FoldCompanyName` | 設定 `company_forms` |

NFKC は、Unicode（文字の国際規格）が定める、文字の揺れをそろえる方式の1つです。

- **メールの件名には掛けません。** 届いたままが正本です。
- **拡張が名前を書くときの決まりは、拡張の【要求】（[拡張/](拡張/)）に書きます**（[開発方針 §0](開発方針.md)）。
  社名を書く口を揃える、などの決まりです。
  拡張は、w-cms に足す、用途ごとのプログラムのことです。

**開発者向けの注意**

- 機械が書く名前に `NormalizeCode` を使わないこと。`レーザー` が `レ-ザ-` になります。

## 7. 参照タグ（`ref`）

参照タグは、ほかのページやブロックを指すタグです。
値は **`ページID-ブロックID`** の形です（例 `000031-a1b2`）。
ブロックID は、本文のブロック1つ1つに付く印です（`data-id`）。

- **表示のときに、リンクになります。** 本文は書き換えません。
- **宙ぶらりん**（指す先が無い参照）は、**薄赤**で出ます。
- **飛ぶ先は、常に本文のブロックです**（`#<data-id>`）。添付そのものを指す経路は、ありません。
  だから、添付の識別子も、ブロックID と同じ4桁です（ファイル名・URL・`data-id` の3役を兼ねます）。
- ⚠ **指し先は「消えないもの」にすること。**
  人が消せるブロックを指すと、消した日に宙ぶらりんになります（業務での当て方は、拡張の【要求】にあります）。
- **型が `ref` であることが、リンクにする唯一の条件です。**
  値の形だけでは、参照と番号を見分けません（2026-09-04 の事故の教訓です）。
  2026-09-21 に、`資料` の列が `text` のままで押して飛べなかったのは、これを忘れていたためです。
- **表のセルも、列の型が `ref` ならリンクになります。**

実装: `ref_render.go`（表のセルは `linkRefCells`）。

## 8. 書くときの決まり

- **項目の鍵は、見出しの表示文字です**（`<dt>` の文字）。
  機械キー（プログラムが使う、英字の名前）を本文へ書く属性は、ありません。
- **見た目の印は、本文に保存できません。** `class` は、サニタイズで落ちます。
  宙ぶらりんの薄赤のような印は、表示時に付ける鏡型で作ります。
  鏡は、サーバーが表示のときに足すもので、本文には保存されません（§15）。
- ⚠ **空欄の意味を決めつけないこと。**
  出荷済数量・単価の空は、「まだ分からない」という意味です。
  `0` を埋めると、人が入れた `0` と見分けが付きません。

**開発者向けの注意**

- **機械が既存ページのタグを書き換えるときは、`cms.RewriteBody` を通すこと。**
  - `RewriteBody` は、ページごとの書き込みの錠（`LockPageBody`。1回の書き込みのあいだだけの鍵）の中で、読んで・変えて・書きます。
    人の保存（`/api/sync`）と重なっても、片方が黙って消えることはありません。
    人の書きかけとぶつかれば、画面が両方を並べます（[【要求】ページとエディタ.md](【要求】ページとエディタ.md) §3）。
  - ⚠ 本文のファイルへ、直に書かないこと。錠の外で書くと、人の保存と重なって、片方が消えます。
  - ⚠ 錠を取ったまま、同じページの本文を書く関数を呼ばないこと（同じ錠を2度は取れないので、止まります）。
  - 2026-10-12 までの関門（`editlock.RefuseWhileEditing`・`editlock.Locks.EditorOpen`）は、呼び出しが残っています。
    画面が編集権を握らなくなったので、ふだんは素通りします。効くのは、道具が `/api/lock` で一瞬握るときだけです。
- ⚠ **`/api/load` の出力を `/api/save` へ書き戻さないこと。**
  - `/api/load` は、鏡を埋めて返します。それを落とすシリアライザ（保存用に本文を整える処理）は、ブラウザの `app.js` にあります。
  - 外から書き戻すと、鏡が本文に焼き込まれます（2026-09-21 に6枚焼きました）。
  - いまは、`cms.StripChrome` が `Sanitize`／`SanitizeReport` の冒頭で鏡を落とします。
    **順序が、この守りの全部です**（サニタイズは `class` を落とすので、後では印が残っていません）。

## 10. `bool` 型（2026-09-23 決定）

`bool` は、タグの値をチェックボックスで入れられるようにする型です。
型を足すことは、決まっています。

> 2026-09-23 利用者:「発注書ページに『発注済』というタグを足したい…**タグにチェックボックスを
> 使うことは可能ですか？**」「**data-typeがBOOLのタグはチェックボックスを出す**という
> 取り決めはどうですか？」「**BOOL型があると入力が楽です**」

### できること・できないこと

⚠ **チェックボックスは、本文に保存できません。**
サニタイザ（サニタイズを行う部分）が、`input`・`button`・`select` を、部分木ごと（中身ごと）消すためです。
本文に偽のログインフォームを書ける穴を、塞ぐためにそうしています
（[本文サニタイズ設計.md](旧文書/本文サニタイズ設計.md)）。

そこで、実体は次の形になります。すでに3つ動いている形と同じです
（拡張の、案件残表の手続きの印の3列です。拡張の【要求】）。

```
本文に入るもの … 「済」という文字だけ
画面に出るもの … チェックボックス（サーバーが表示のときに足す鏡）
押したとき     … 本文の文字を「済」⇄「空」に書き換える
```

⚠ **いま**: `bool` 型は、まだありません。

- 拡張は、選択肢が1つしかない `enum`（`済` だけ）で偽装しています。
  チェックボックスは、画面の側で手書きしています（拡張の【要求】）。
- `bool` があれば、宣言がそのまま画面になります。
  列を足したときに画面を直し忘れる、という形が、構造として無くなります。

### ⚠ 決めるべきこと——チェックは2状態、データは3状態

チェックボックスが表せるのは、入っているか、外れているかの2つだけです。
ところが、データには3つの状態があります。

```
はい  ／  いいえ  ／  まだ誰も見ていない
              ↑ 外したチェックボックスでは、この2つを見分けられません
```

| タグ | 外れたチェックの意味 | 困るか |
|---|---|---|
| `発注済`・`材料発注` | まだ出していない | 問題なし（同じ意味） |
| `検査合格` | ⚠ **不合格なのか、まだ検査していないのか** | 区別できない |

**提案する取り決め**:

> **`bool` は「印」である。** 値は `済` か**空**の2つで、**空は「まだ」**を意味する。
> ⚠ **「いいえ」を積極的に記録したいときは `bool` を使わず `enum`**（`合格`／`不合格`／空）。

この取り決めでよいかは、まだ決まっていません（§20 の #1）。

### 足すのに要るもの

`bool` を足すには、次の4つが要ります（開発者向けです）。

1. `internal/cms/vocab.go` の `validColumnTypes` に、`bool` を1つ足します。
   ⚠ ここを足さないと、設定に `bool` と書いた瞬間に、起動が止まります。
2. `config/settings.json` の `vocabulary` に、`"発注済": { "type": "bool" }` を書きます。
3. DB を再構築します。
4. **タグの鏡**を作ります（`<dl>` の中に、チェックボックスを出す鏡です）。
   - これは新しい経路です。いまのチェックボックスは全部、計算ビューの中にあります。
     本文のタグの鏡は、まだありません。
   - 閲覧モードと書ける形の両方で、押せる必要があります。

**`bool` を足すことと、「どのページにどのタグを持つか」は、別の話です。**
行から数えれば分かることをタグで二重に持つと、1行取り消したときに、タグが嘘をつきます
（業務での例は、拡張の【要求】にあります）。

## 11. ⚠ タグには「鏡」がありません（2026-09-23）

この節の見出しは、2026-09-23 のままです。
2026-10-09 から、`enum` の候補だけは、タグの値にも出ます。`image` と `bool` の手助けは、いまも出ません。

タグの値には、型に応じた入力の手助けを出す仕組みが、まだそろっていません。
選択肢から選ぶ・チェックを入れる・画像を選ぶ、といった手助けです。
この仕組みを、「タグの鏡」と呼んでいます。タグの値のところに、サーバーが表示のときに足す部品のことです（§10）。

きっかけは、利用者の次の問いでした。

> 利用者:「**ENUM型のタグは、リストで選択できますか？列挙する値は、設定できますか？**」

`enum` は、決まった選択肢から選ぶ型です。いまの答えは、次のとおりです。

| 問い | 答え |
|---|---|
| **値を設定できるか** | ✓ **できます**。`config/settings.json` に `{"type": "enum", "values": [...]}` |
| **リストで選べるか** | ✓ **選べます**。表のセルでも、タグの値でも、選択肢のボタンが出ます（タグの値は書ける形で） |

```json
"在籍":   { "type": "enum", "values": ["在籍", "休職", "出向", "退社"] },
"移行中": { "type": "enum", "values": ["確認待ち"] }
```

### ⚠ いま、タグの値に起きること

⚠ **いま**:

- **印が付きます。**
  値が `values` に在れば `tag-known`、無ければ `tag-unlisted` の印が付きます（色で示します）。
- **書ける形で値を触ると、選択肢のボタンが出ます。**
  - 表のセルと同じ器を使います（`#w-enum-menu`・`updateEnumMenu`）。選択肢は、設定の語彙です。
  - 選ばずに、手で打つこともできます。
  - 閲覧モードでは出ません。
- **空欄には、印を付けません。** 「まだ書いていない」は、間違いではないからです。

選択肢のボタンは、利用者の次の言葉から足しました。

> 2026-10-09 利用者:「タグにはコンボボックスで候補を出す設定が無かったでしょうか？」→「enum のタグ全部に出す」

### ⚠ これは `enum` だけの話ではありません

型に応じた入力の手助けは、表のセルとタグの値とで、出るものが違います。
いまの出方は、次のとおりです。

| | 表のセル | タグの値 |
|---|---|---|
| `enum` の候補 | ✓ ボタンが出る | ✓ ボタンが出る（書ける形） |
| `image` の「画像を選ぶ」 | ✓ 出る | ⚠ **出ない** |
| `bool` のチェックボックス（§10） | （足せる） | ⚠ **出ない** |
| `ref` のリンク | ✓ 出る | ✓ 出る |

**要求: タグの値にも、型に応じた入力補助を出すこと。**
表と同じ理屈です。打つより選ぶほうが速く、速ければ揃います。

タグの鏡を1つ作れば、`enum` の候補・`bool` のチェックボックス・`image` の選択が、まとめて片付きます。

⚠ **いま**: タグの鏡は、まだ作っていません。
`enum` だけは、表のセルの候補の器を、タグの値にも広げて出しました。
`image`・`bool` は、残っています。

### ⚠ 候補は縛りではありません

**候補を採らずに、手で打てること。**
揃うのは、候補を採ったときだけです。手打ちは止められません。
それでも候補を出す意味があるのは、打つより選ぶほうが速いからです。

`tag-unlisted` の印は、「**間違い**」ではなく「**一覧に無い**」を意味します。

## 12. 3層モデル

「語彙を増やす」と「計算を作る」を、別の作業に分けるための形です。

| 層 | 実体 | 変える人 | 担うもの |
|---|---|---|---|
| **① 語彙レジストリ** | **宣言データ** | 運用者（設定ファイル）／拡張（Go） | 形式の定義——名前・表示名・分類・アイコン・要素種別・**列**（機械キー・型・ラベル・許可値） |
| **② 汎用索引** | コアのコード（**1実装**） | — | 形式の解決できる表を `vocab_index` へ同期。検索・単純集計 |
| **③ 計算ビュー** | Goコード（**少数**） | 開発者 | 索引から読んで組み立てる（手配状況・未手配の一覧・案件残・参考単価） |

言葉の説明です。

- **語彙レジストリ**は、語彙の登録簿です。形式（表などの種類）の定義を並べたものです。
- **コア**は、w-cms の土台の部分です。用途ごとに足す部分（拡張）と、分けて呼びます。
- **計算ビュー**は、索引から値を読んで、その場で組み立てて見せる表示です。

**足す手間に段差があるのが、要点です。**

- 記録・表示だけの語彙（100種の大半）は、①の宣言1件で済みます。
  開発者がボトルネック（流れが詰まる所）になりません。
- Go のコードが要るのは、計算を伴う語彙だけです（10個未満に保ちます）。

**安全性は、①に依存しません。**

- サニタイザの許可リスト（本文に書いてよい要素と属性の一覧）は、コードで固定です。
- `data-type` は、属性名だけを、要素を限って許可します（`table`・`dl`・`section`・`th`）。
  値は、不活性な（何も起こさない）文字列として扱い、検査しません。
- レジストリは、編集支援と検証のための語彙です。安全性の門ではありません。
- この分離があるので、将来レジストリを実行時に（動かしたまま）編集できるようにしても、危険な要素は増やせません。

## 13. 形式の解決——表が「自分が何か」を名乗る方法

形式は、表の種類のことです。
表が自分の形式を名乗る方法は、2通りあります。**この順で見て、1回だけ**解決します。

| 順 | 名乗り方 | 例 |
|---|---|---|
| ① | **`data-type` 属性**（古い本文） | `<table data-type="our-order-items">` |
| ② | **`<caption>`** | `<table><caption>部材発注明細表</caption>` |

- ①が優先なので、既存の本文は壊れません。新しく書く表は、キャプションで名乗ります。
- キャプションで名乗る形は、「見た儘が全て」の原則どおりです。利用者の次の言葉から足しました。

  > 利用者:「表のうち、意味の分かるものにキャプションを付けましょう。**キャプションを頼りに集計できるようになるはず**です」

- ⚠ **節の見出し（`<section><h2>材料</h2><table>…`）では、名乗れません**（§1）。

### ⚠ 表の写しにはキャプションだけで入る・集計の索引は登録された形式だけ

表の行き先は2つあり、入る条件が違います。

- **表の写し**（`data/tables.db`）には、`<caption>` のある表なら、**登録が無くても**入ります。
  - キャプションがテーブルの名前に、見出しが列の名前になります。
  - 「🔎 表を探す」と、AI の口から引けます（[【考察】DBの日本語化.md](考察/【考察】DBの日本語化.md)）。
- **集計の索引**（`vocab_index`）には、**レジストリに載っている形式だけ**が入ります（2026-09-20 の利用者の決定です）。

⚠ **裏返すと、キャプションを付けただけでは、集計の索引には入りません。**
形式として登録して初めて、拡張の集計（手配・原価など）が読めます。

## 14. 行き先は `vocab_index`

登録された形式の表は、DB の `vocab_index`（集計の索引）に入ります。

- **索引の `field` は、見出しの表示文字です**（`品番`）。機械キー（`item-id`）ではありません。
- **同じ形式の表が1ページに何枚あっても、行を区別できます。**
  `block_no`（同じ形式の表に、文書の順で振る連番）と `row_no`（表の中の行の番号）で見分けます。
- ⚠ **`section` の素の `dl`（業務ブロックのヘッダ）は、入りません。**
  ヘッダの値は、ページの可変タグ（この文書でいうタグ）に書きます。素の `dl` に書いても、検索に掛かりません。
- ⚠ **読めないページは、混ぜないこと。**
  表には、誰でも行を書けます。絞らないと、読めないページの値が引けてしまいます。

⚠ **いま**（2026-10-04）: 表のセルの式（`=個数*単価`）の扱いは、次のとおりです
（式の決まりは [【要求】ページとエディタ.md](【要求】ページとエディタ.md)「表のセルに式を書く」）。

- 索引（`vocab_index`）と表の写し（`data/tables.db`）には、**計算した値**が入ります。
- 本文に入るのは、式だけです。
  計算は [formula.go](../internal/cms/formula.go) の1か所で行います（閲覧の表示も、同じ関数を通ります）。
- 計算できない式は、**書いたまま**（式の文字）が入ります。
  畳めない値を落とさない、という表の写しの約束と同じです。
- 空のセルを参照した式は、空になります。

**開発者向けの注意**

索引を読む口は、[vocab_query.go](../internal/cms/vocab_query.go) にあります。

| 口 | 何を返すか |
|---|---|
| `VocabTableRowsOf(db, pageID, type)` | **1ページの**その形式の行 |
| `VocabRowsOfType(db, type)` | **全社の**その形式の行（⚠ スコープを越える集計はこちら） |
| `PagesByTag` / `PagesByTagLoose` | タグでページを引く |

`RelatedPages`（深さ1）に頼れない集計があります。

- `RelatedPages` は、集計の範囲（スコープ）を、直接つながったページまで（深さ1）にする口です。
- 置き場の離れたページどうしは、直接つながりません。深さ1では、黙って0件になります。
- そういう集計は、`VocabRowsOfType` で全社を読み、鍵の列で束ねます（業務での例は、拡張の【要求】にあります）。

## 15. 本文の走査は**配送係だけ**

走査は、本文の HTML を、端から順に読んでいくことです。

w-cms では、本文の HTML を処理する仕事を、**1つの走査**に寄せてあります。
その走査をするのが、**配送係**です。
配送係は、本文を文書の順に歩いて、印の付いた要素を、担当の係へ配ります。
実装は [walk.go](../internal/cms/walk.go) です。本文を木の形にしてから、文書の順に歩きます（SAX over DOM）。

配る先の係（段）は、2つです。

| 段 | いつ | 権能 | できること |
|---|---|---|---|
| **観察係** | 保存時 | 書き込みTx | 自分の索引テーブルへ洗い替え。⚠ **`Replace` はありません** |
| **鏡型** | 表示時 | 読み取り専用DB | `Replace`。表示専用のクローム（`.vocab-chrome`）を足す |

- **観察係**は、保存のときに本文を読んで、自分の索引テーブルを入れ直す係です。
  洗い替えは、古い行を消して入れ直すことです。
  書き込みTx は、DB へ書き込むためのひとまとまり（トランザクション）です。
- **鏡型**は、表示のときに、本文の要素を差し替えたり（`Replace`）、表示専用の部品を足したりする係です。
  この部品をクロームと呼びます。クロームは保存されません。
  鏡型が表示のときに作るものを、「鏡」と呼びます。

**開発者向けの注意**

- **観察係に `Replace` が無いのは、行儀ではなく、型の問題です。**
  同じ理由で、鏡型には書き込みTx を渡しません。
  こうすると、「派生→正本の逆流」がコンパイル時に不可能になります（2026-08-21 に一度踏みました）。
  逆流は、派生（DB）の側から、正本（本文）を書き換えてしまうことです。
- **`WalkElements` を自分で回す新しいコードは、たいてい設計を間違えています。**
  除外規則（`.vocab-chrome` の中を読まない・テンプレート領域を索引しない）は、
  配送係がそもそもイベントを発火しない形になっています。規約ではなく、観測できない事実です。
- **鏡は、引き金1つにつき1人です**（重複は起動時に落とします）。「順番」に意味を持たせないためです。
  引き金は、その鏡を呼び出す印のことです。
- ⚠ **観察係の `descend` は、OR で畳まれます。** AND にすると、明細が索引から消えます。
  `descend` は、その要素の中へさらに降りるかどうかの返事です。

### 索引に載らないもの

- **テンプレート領域（ルート含む）**
- **拡張が「DBに入れない」と言ったページ**
  （コアの口は `cms.RegisterTablesExclusion` です。どのページかは、拡張の【要求】にあります）

**開発者向けの注意**

- テンプレート領域かどうかの判定は、サイドカー（ページの属性のファイル）と本文の HTML で行います。
  ⚠ DB を見ると、静かに壊れます。

## 16. 列の宣言

列の宣言は、表の形式ごとに、どんな列があるかをプログラムに書いたものです。
この節は、拡張を書く開発者向けです。

```go
{Field: "item-name", Label: "品名", Type: cms.ColText},
{Field: "status",    Label: "状態", Type: cms.ColEnum, Enum: []string{"未発注", "発注済"}},
```

**`Label` が索引の鍵です**（見出しの表示文字）。`Field` は機械キーで、本文には出ません。

⚠ 次の4つは、知らずに書くと壊れる所です。

- **見出し行は、宣言から組むこと**（`headerRowHTML`）。
  手書きに戻すと、列を足した日に、足した列がどこからも読めません。エラーは出ません。
- **同じ意味の列は、形式を越えて、名前と型を揃えること。**
  `品番` が片方で `code`、片方で `text` だと、畳み方が違って、突き合わせが静かに外れます。
- **列の宣言を共有するときは、毎回作ること。**
  スライス（Go の、並びを持つ値）を共有すると、片方の書き換えがもう片方に及びます。
  `orderItemColumns()` が関数なのは、そのためです。
- **パッケージ変数の初期化は、`init()` より先に走ります。**
  `var x = labelOf(...)` は、`RegisterVocab` の前に引くので、常に空になります。
  すると、比較が素通りして、条件が逆になります。
  レジストリから引くものは、関数にすること。

## 17. スキーマを変えるとき

スキーマは、DB のテーブルと列の形のことです。
この節は、開発者向けです。

**プラグインテーブルに、マイグレーション（古い形から新しい形へ移す手順）はありません。**
起動時に1度だけ、自動で再構築します。

⚠ 次の3つは、知らずに書くと壊れる所です。

- **新しいテーブルを足しても、自動再構築は走りません。**
  - `ApplySchema` は、空の表を作るだけです。
    `page_tags` を足した日に、タグ88行が古い表に取り残されました（画面は無言で空でした）。
  - いまは、`DriftedSchemaTables` が、「**索引に中身があるのに表が無い**」も、ずれとして扱います。
  - `CREATE INDEX` を表と取り違えると、起動のたびに再構築が走ります。
- **スキーマを変えたら、作り直しが `ApplySchema` より先です。**
  逆だと、列を変えた表へ新しい索引を張ろうとして、起動が落ちます（`no such column: name`）。
- **一括置換で SQL を直すときは、UNION を跨がないこと**
  （`page_tags` と `vocab_index` で、列名が違います）。

## 18. 語彙モデルが満たすこと

- **知らないものを消さない。**
  レジストリに登録していない `data-type`・キャプションも、サニタイズは拒否しません。語彙は増えるものだからです。
  表の写しにはキャプションで入り、集計の索引には登録された形式だけが入ります（§13）。
- **見出しの改名を告知する。**
  表は自己記述です（列の意味を、表の見出しそのものが運びます）。
  列の鍵は、見出しの表示文字ただ1つです。だから、見出しを変えると鍵が変わります。
  ⚠ 黙って変えさせないこと。
- **マーカー（印）は、`class` ではなく `data-*`。**
  サニタイザは、`class` を全面的に拒否します。そこに例外を作らないためです。
  だから、見た目の印は本文に保存できません（表示時に付ける鏡で作ります）。
- **レジストリを安全性の門にしない**（§12）。
- **新しいカスタム要素（Web Components・`<m-*>`）は作らない。**

  ⚠ **いま**: カスタム要素は0種です（2026-08-20 に全廃）。

- **写真・画像は、語彙ではなく「内容」です。**
  標準 HTML（`<img>`）だけで完結します（[【要求】添付.md](【要求】添付.md)）。
- **語彙の単一正本を、1つの API で配る。**
  レジストリと拡張の宣言を合成して、`GET /api/tag-schema` で返します。エディタと文書生成が、それを読みます。
  ⚠ エディタ側に、手書きの要素リストを置かないこと。

## 19. レジストリの育て方

レジストリの宣言の置き場は、**段階を踏んで**育てます（2026-08-16 決定）。

| 段 | どこに宣言があるか | 語彙を足すのに |
|---|---|---|
| **v1**（⚠ **いま**） | Goコード内の宣言テーブル＋`config/settings.json` | ⚠ **形式の追加には再ビルドが要る**（下の「⚠ いま」） |
| (b) | 管理コンソールで編集するDB | 再デプロイ不要 |
| (c) | **語彙定義ページ**（w-cms 自身のページで語彙を定義する） | 同上 |

⚠ **いま**（v1）:

- 業務の計算やボタンを伴う形式の追加には、再ビルド（プログラムの組み直し）が要ります。
- 設定で足せるのは、次の3つです（2026-10-14 に、コードで確かめて直しました。それまでは「表の形式は足せません」と書いていました）。
  - 語→型の `vocabulary`
  - 表ごとの列の例外の `table_vocabulary`
  - 表の形式そのものの `vocab_formats`（2026-09-20 から。足したら、DB の再構築が要ります。
    コードの宣言と同じ名前は書けません。いまの設定には、1件もありません）
- ただし、キャプションの付いた表は、**登録なしで**表の写し（`data/tables.db`）に入ります。
  登録が要るのは、`vocab_index` と、それを読む集計です。

先にコード内で始めたのは、定義スキーマが固まる前に DB 化すると、移行が二度手間になるためです。

- 識別子（`data-type` の値と機械キー）は、**kebab-case** にします。
  kebab-case は、小文字の英単語をハイフンでつなぐ書き方です。
- ⚠ **識別子は、レジストリ全体で一意**（重なりなし）にすること。
