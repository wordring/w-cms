# 【考察】エディタの実装方針

> 状態: **検討中**。2026-06-28 の設計議論をまとめた考察。「このエディタはバニラJSで作るのか、フレームワークを導入するのか」という問いへの整理。
> 関連: [エディタ仕様.md](エディタ仕様.md)（§3 Web Components 採用理由）/ [コンセプト.md](コンセプト.md)（§3・既知の課題）/ [開発方針.md](開発方針.md)（§1 外部依存最小）/ [【考察】アンドゥ・リドゥ.md](【考察】アンドゥ・リドゥ.md)

## 0. 結論

**既定はバニラ（Web Components）維持。** 汎用UIフレームワーク（React/Vue）は不向き。検討に値するのは**エディタ専用ライブラリ**（ProseMirror/Lexical 等）だけで、それも「堅牢なアンドゥ・選択範囲・共同編集」が要件化してから。

判断軸は「フレームワークか否か」ではなく、**この系の不変点（保存形式＝DOM／ビルドレス）を壊さない範囲で、どこまで道具を借りるか**。

## 1. 「フレームワーク」を2種類に分ける

- **汎用UIフレームワーク**（React/Vue/Svelte）: 仮想DOM＋ビルド前提。→ このエディタには不向き（§2）。
- **エディタ専用ライブラリ**（ProseMirror/Lexical/TipTap/Slate）: 文書モデル＋選択・undo・コラボ基盤を提供。→ 要件次第で検討対象（§4）。

「contenteditable のエディタにフレームワークを入れる」は、実務上ほぼ後者を意味する（React 直書きで contenteditable を御するのは業界的に難所）。

## 2. なぜバニラがこのプロジェクトに合うか

既存の [エディタ仕様 §3](エディタ仕様.md)・[コンセプト §3](コンセプト.md) の理由は、いずれも**この設計に固有で強い**：

1. **保存形式＝DOM**（決定打）。カスタム要素がそのまま保存HTML（＝正本）になり、Goの `x/net/html` が同じタグを読む（[アーキテクチャ §1](アーキテクチャとDBスキーマ.md)）。仮想DOMを挟むと「コンポーネント木 → 保存用クリーンHTML」への変換層が要り、**HTMLをDBとする設計の最大の利点を失う**。
2. **ビルド工程ゼロ**。`index.html`＋`web-components.js`＋テンプレを**そのまま配信**。多くのフレームワークは npm＋バンドラを連れてきて、[開発方針 §1](開発方針.md) の「単一バイナリ・外部依存最小・ポータビリティ」と衝突。
3. **contenteditable × 仮想DOM は難所**。ブラウザ/ユーザがフレームワーク外でDOMを変えるため相性が悪い。だから本格エディタは専用ライブラリを使う。
4. **規模が小さい**（カスタム要素6種・社内CMS）。汎用フレームワークの学習・依存コストが見合わない。

## 3. いま痛い所は、フレームワーク無しで直せる

[コンセプト 既知の課題](コンセプト.md) の粗さは、リライトでなく**局所改修**で解消できる：

| 課題 | 改修（バニラのまま） |
|---|---|
| テンプレ変数展開の **XSS** | エスケープ処理を入れる／安全なテンプレ方式に |
| 属性変更ごとの **全体再レンダリング** | 差分更新（必要箇所だけDOM更新）へ |
| `window.updateHtmlPreview` 等 **グローバル結合** | CustomEvent で疎結合化 |
| Shadow DOM の不統一（`MChildList` のみ Shadow） | 方針統一（Light DOM 寄せ or 全Shadow） |

## 4. それでも「道具」を入れる場合の段階

1. **`lit`（フレームワーク・ライト・第一候補）**: Web Components ネイティブのライブラリ。**「カスタム要素＝DOM＝保存形式」を保ったまま**、効率的な差分テンプレート＋自動エスケープ（XSS対策）＋リアクティブ更新が得られる。§3 の粗さをまとめて解消できる最小の一歩。buildless（CDN/import map）でも動くので no-build を維持しやすい。代償は依存1つと作法の学習。
2. **エディタ専用ライブラリ（ProseMirror / Lexical）**: **堅牢なアンドゥ・選択範囲管理・将来の共同編集**が必須要件になったときだけ。これらは [【考察】アンドゥ・リドゥ.md](【考察】アンドゥ・リドゥ.md) で「自前は難所」と書いた当のものを提供する。代償は**独自の文書モデルとの相互変換**（カスタムタグHTML ⇄ ライブラリのモデル）と大きめの依存・学習コスト。保存形式＝DOM の利点も一部薄れる。
3. **汎用UIフレームワーク（React/Vue）**: **非推奨**。2大特性（DOM=保存形式／no-build）を壊し、contenteditable と戦う。

## 5. 推奨（まとめ）

- **既定はバニラ（Web Components）維持。** 粗さは §3 の局所改修で潰す。これがこのプロジェクトの ethos（HTML=正本・単一バイナリ・最小依存）に最も忠実。
- 粗さを「道具で一掃したい」なら、**方向を変えずに `lit` を検討**（Web Components の延長で、React/contenteditable 問題に踏み込まない）。
- **ProseMirror/Lexical は「堅牢undo・選択・共同編集」が要件化してから**。先走らない（今のアンドゥは [【考察】アンドゥ・リドゥ.md](【考察】アンドゥ・リドゥ.md) の自前スナップショットで釣り合う）。

## 6. 編集の2面：値（インライン）と属性（インスペクタ）

[【考察】タグ設計](【考察】タグ設計.md) の「役割＝属性／値＝中身」を採ると、**編集対象が2層に分かれる**。両方の編集口を用意する：

| 編集するもの | 例 | 手段 |
|---|---|---|
| **値（中身・表示される）** | セルの値（数量・単価・明細の `status` 等）、`<m-field>` の値、本文プローズ | **インライン（`contenteditable`）** |
| **役割・参照・型（属性・表示されない配線）** | 列の `data-field`/`data-type`、`<m-quote ref>`、`受信元`・`前版` 等の参照、`<m-file>` のファイルメタ（`name`/`ext`） | **属性インスペクタ（設定パネル/ポップオーバ）** |

- `contenteditable` はテキスト（値）しか触れないので、**属性は専用UIで編集**する（例: `<m-table>` の列ヘッダ設定、ブロックのプロパティパネル）。
- これは現状の「テンプレ内 `<input>`＋`oninput→setAttribute`」（§3 のグローバル結合）を、**ブロック共通の属性編集パターン**へ寄せる方向。各ブロックがバラバラに入力欄を持たずに済む。
- 表示ラベルと役割キーは独立（ラベル改名で機械キーが壊れない）。

## 7. 未決・再検討の契機

- ブロック種別が大幅に増える／インタラクションが複雑化したら、`lit` 導入の費用対効果を再評価。
- 共同編集（複数人同時編集の本格対応）が要件化したら、エディタ専用ライブラリ＋CRDT を本格検討（現状は悲観ロックで足りている）。
- `lit` を入れるなら no-build（import map）を維持できるか、配信・キャッシュ方針（[エディタ §8 テンプレ外部化] と整合）を併せて決める。
