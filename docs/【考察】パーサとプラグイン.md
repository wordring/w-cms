# 【考察】パーサとプラグイン

本文HTMLを処理する3つの経路（保存時の索引・表示時の計算ビュー・新規作成時のテンプレート
新規化）を、**1つの回覧機構**へ設計し直します。2026-08-25 のユーザー指示による**委嘱された
設計**であり、状態は**設計済み・未実装**（実装が終わったら【考察】を外す）。

前提の議論は [【考察】語彙モデル.md](【考察】語彙モデル.md) §11（機能見出し・二種類の計算・
可搬性・実行モデルの素描）。**本書はその §11.4 を実装可能な粒度まで詳細化した正本**です。
重要な独立性がひとつ——**機能見出し（§11.1）はまだ未決定だが、本設計はその決定を待たない**。
引き金の解決（何を見て担当を決めるか）を差し替え可能な1点に隔離してあり、いまは `data-type`
属性で動き、機能見出しが採用されたら解決層だけ差し替える。

## 1. いま何が問題か

| 問題 | 現状 |
|---|---|
| **走査が3系統バラバラ** | `SyncIndex`（各プラグインへ木を丸ごと渡し**各自で走査**）・`RenderComputedViews`（自前走査）・`FreshenTemplateBody`（自前走査） |
| **除外規則が散在** | `.vocab-chrome` 除外・テンプレート領域除外を**走査するコードがそれぞれ覚えている**必要がある（作業引き継ぎの勘所に「必ず確かめること」として明文化されるほどの罠） |
| **文字列でHTMLを足す** | サニタイズ後にHTMLを追加する関数が**各自でエスケープ責任**を負う（規律が破れると保存型XSS。実際に一度発火した） |
| **資源の渡し方がアドホック** | 観察は `tx *sql.Tx`、鏡は `*http.Request`、種まきは引数2つ——段ごとの権能の設計がない |

## 2. 全体像

```
保存時:     サニタイズ → [回覧: 観察係] → （プラグインの索引テーブルが洗い替わる）
表示時:     本文読込 →   [回覧: 鏡型]   → アンカー合成 → 殻へ合成
新規作成時: テンプレ読込 → [回覧: 種まき] → 保存経路へ
```

- **パーサは `x/net/html` のまま**（決定・2026-08-25）。木を作ってから、配送係が文書順に
  歩いてイベントを押し込む——SAX over DOM。
- **サニタイザとアンカー合成はコアに残す**。サニタイザはプラグインで拡張できてはいけない
  （安全性の門が破れる）。アンカー合成は「使用済み id 全集合」という全体参照が要るうえ、
  形式に依存しないのでプラグイン化する利益が無い。
- `RouteProvider`（集計APIの口）は本設計の対象外——現行のまま。

## 2.5 いつ動くかの実測根拠（ワンノート運用の時刻分析・2026-08-25）

「集計に関わるプラグインがいつ動くべきか」を、板金部ノート766ページの作成・最終更新時刻で
実測した（生データの取り方は [【考察】ワンノート移行.md](【考察】ワンノート移行.md) §6）:

- **作成は月2〜9ページ・更新は月17〜86ページ**——編集が作成の約10倍。書き込みは高々日に数件。
- **作成から最終更新まで中央値75日・42%が1年超**（最長5年）——リピート発注のたびに同じ
  部品ページへ日付入りの行を追記する運用のため、**古いページが今日変わるのが日常**。
- **手集計は現に腐っている**——「まとめ」ページを持つ67セクションの**半分（34件）で、
  まとめより後に他ページが更新**されていた（遅れの中央値35日・最大495日）。業務はこの
  古さを許容して回っている。

帰結:

1. **3段（保存時・表示時・新規作成時）で実運用の全瞬間を覆う**——夜間バッチ・定期再集計を
   要する兆候は無い。書き込み頻度から索引は保存時で常に追いつき、鮮度要求から鏡型は
   表示時で余裕（公開キャッシュの許容遅延10分は、実測の許容水準35日に対して無限に余裕）。
2. **鏡型の価値は速さではなく「腐らないこと」**——性能のための事前集計は不要（データが小さい）。
   鏡型が消すのは、まとめページを手で更新する仕事と、その半分が古い現状そのもの。
3. **洗い替えの単位は「ページ」で正しい**——追記専用・「最近の分だけ」の仮定は成立しない。
   保存のたびに当該ページ分を DELETE→再挿入する現行方式が編集パターンに合う。
4. **宿題（データモデル側）**——同じ部品ページにロットごとの実績が積もるため、集計には
   時期・ロットの絞り込みがいずれ要る。現状その日付は自由文の行に埋まっている
   （スキーマ設計し直しの入力。タイミングの問題ではない）。

## 3. 配送係（Walker）

コアが1つだけ持つ走査器。責務は4つ:

1. **文書順にイベントを発火する**——要素の開始ごとに担当ハンドラを呼ぶ。
2. **除外領域のイベントを発火しない**——`.vocab-chrome` の中・差し替え済みの部分木。
   除外が「各自が覚える規約」から「観測できない事実」へ変わるのが本設計の最大の利益。
3. **引き金を解決する**——要素から引き金の鍵（いまは `data-type` の値）を求め、
   登録表を引いて担当を決める。**この解決関数だけが将来の機能見出しで差し替わる。**
   **全プラグインへの一斉回覧ではない**（2026-08-26 明確化。「複数のプラグインで
   すべてのタグについて呼び出すのは無駄では」という疑問への答え）——引き金の無い要素
   （`p`・`h2` など大半のタグ）では**誰も呼ばれず**、引き金のある要素でも呼ばれるのは
   **表引きで当たった担当だけ**。関係ないプラグインは「すぐ戻る」のではなく、そもそも
   呼ばれない。各プラグインが木を自前走査する方式（DOM渡し）は、同じ木をプラグイン数だけ
   歩くうえ除外規則の一元化を失うため、性能・安全の両面でこちらが上回る。
   なお `OnElement` が受け取る `el` は生のDOMノードなので、**担当の要素に限ってDOMを渡す**
   方式と言い換えてもよい。
4. **早道**——登録済みの引き金が本文に1つも現れなければ木を歩かない
   （現行 `RenderComputedViews` の `strings.Contains` 早道の一般化）。

**イベントは「要素の開始」1種で足りる**（§11.4 の素描にあった Text／EndElement は落とす）。
根拠は既存3機構の消費形態——索引は表を**部分木ごと**読み（`tableRows`／`rowCells`）、鏡は
セクションを**丸ごと差し替え**、種まきはセルを**部分木の中で**埋める。文字イベントを使う
消費者は1つも無く、木が下にあるのでハンドラは受け取った要素から自由に読める。
イベントを増やすのは必要が出たときでよい。

```go
// Handler は回覧の受け口。el の部分木は自由に読んでよい。
// 戻り値 descend=false で配送係は el の子孫へ降りない（担当済みの意思表示）。
type Handler interface {
    OnElement(ctx *WalkContext, el *html.Node) (descend bool, err error)
}
```

### 登録の口

```go
RegisterObserver(trigger string, h Handler)  // 観察係。trigger="*" で全マーカー要素
RegisterMirror(trigger string, h Handler)    // 鏡型。trigger ごとに一意（重複登録は起動時エラー）
// 種まきは v1 ではコア備え付けの1ハンドラ（レジストリの列型駆動）。口だけ用意する。
```

- **観察係は何人でも**——同じ要素を複数の索引が読んでよい（衝突しない）。
- **鏡型は引き金ごとに1人**——「順番」に意味を持たせない（語彙モデル §11.4 の手すり③）。
- 登録は起動時に確定（現行の `RegisterPlugin` と同じ `init()` 流儀）。

### 差し替えの規律

- 鏡型・種まきの書き換えは **`ctx.Replace(el, nodes...)`／セルへの `SetText`** で行う。
  **文字列APIは存在しない**——`html.Node` を組んで返す（`html.Render` がテキストと属性値を
  自動エスケープすることは 2026-08-25 に検証済み。語彙モデル §11.4）。
- 差し替えた部分木へはイベントを発火しない（再回覧なし・停止性の保証）。

## 4. ライフサイクル——洗い替えの一般化

観察係にはページ単位のフックを足す:

```go
type Observer interface {
    Handler
    Name() string
    Schema() []string   // CREATE TABLE IF NOT EXISTS …（現行 Plugin と同じ）
    Tables() []string
    OnPageStart(ctx *SyncContext) error  // ここで自テーブルの当該ページ分を DELETE
    OnPageEnd(ctx *SyncContext) error    // 必要なら集計の確定
}
```

これで**テンプレート領域の除外が自然な形になる**——現行は「プラグインへ空の本文を渡す」
という工夫で「DELETE だけ走って新規挿入なし」を実現しているが、本設計では
**「OnPageStart と OnPageEnd は呼ぶが、要素イベントを1つも発火しない」**がそのまま同じ意味になる。
仕組みではなく定義から正しい。

## 5. 段別コンテキスト——最小権限（語彙モデル §11.4 の詳細化）

```go
type SyncContext struct {   // 観察係（保存時）
    Tx     *sql.Tx          // 書き込みは自分の索引テーブルへの洗い替えだけに使う
    PageID int
    Meta   func() (PageMeta, error)  // サイドカー由来。読めなければ error（A-7: 自動で治さない）
}

type MirrorContext struct { // 鏡型（表示時）
    DB     ReadOnlyDB       // Query / QueryRow だけを持つインターフェース。Exec は無い
    Viewer *auth.User       // 見せ分け（C案）はここで効かせる
    PageID int
}

type SeedContext struct {   // 種まき（新規作成時）
    DB        ReadOnlyDB
    NewPageID string
    Now       time.Time     // 日付の既定値用。時計もコンテキスト経由（テスト容易性）
}
```

- **鏡型に書く力を型として渡さない**——「派生→正本の逆流」（`bd7ee98` で一度踏んだ）が
  コンパイル時に不可能になる。`ReadOnlyDB` はラッパーではなくインターフェース
  （`Query`/`QueryRow` のみ宣言）で足りる。
- サイドカーは**生のパスを渡さない**。`Meta()` の意味論は A-7 の決定そのもの——
  読めないとき黙って補完せず、エラーで止まる。
- `WalkContext` は歩行状態（祖先スタック・`Replace`・`SkipChildren` 相当の戻り値）を運び、
  段のコンテキストを内包する。

## 5.5 プラグインの信頼境界（2026-08-25 ユーザー質問への答え）

> 「プラグインは運用側が追加するものですから、サニタイズの必要性が減るのでは？」

**半分そのとおり**——プラグインはコンパイル時に組み込まれる Go コードで、運用者が入れるものは
**コア本体と同じ信頼水準**。だから本文用サニタイザをプラグイン出力に通さない（§2）。
サニタイザの守備範囲は昔も今も**本文**（書き手の信頼できないHTML）であり、プラグインの
追加でこの仕事は増えも減りもしない。

**半分は罠**——サニタイズ（信頼できない文書の検査）とエスケープ（データをHTMLへ描くときの
実体参照化）は別物で、**エスケープの必要性は減らない**。プラグインが描くのはページタイトル・
セルの値・仕入先名——全部**本文の書き手が入力したデータ**であり、信頼されたコードが信頼できない
データを素で描けば保存型XSSになる。2026-08-04 の実発火がまさにこの形（テンプレートエンジン
という信頼されたコードが、書き手の値を `String.replace` で流し込んだ）。現行コードの規律
「タイトルは利用者の入力なので必ずエスケープする」（`childListViewHTML`）も同じ認識で、
手すり①（ノード受け渡し）は**プラグイン作者を疑う仕掛けではなく、信頼された作者でも掛け忘れる
エスケープを構造で自動化する仕掛け**である。

**信頼境界は置き場で動く**ことにも注意——レジストリの育成路線（Goコード → 管理DB →
語彙定義ページ。語彙モデル §9）で語彙の定義が**データ**になった段階では、定義を編集できるのは
運用者とは限らなくなる。そこからマークアップを出せる設計にすると注入経路が開き直すため、
**データ定義の語彙がマークアップを運ぶことになった時点で、定義そのものの検査が必要になる**
（そのときまた設計する。いまのコンパイル時プラグインには不要）。

## 6. 既存コードの移行対応表

| いま | あと | 備考 |
|---|---|---|
| `vocabIndexPlugin.Sync`（全文自前走査） | `RegisterObserver("*", …)` | 未知の `data-type` も索引する現行仕様は trigger `"*"` がそのまま表す |
| `clientOrderPlugin.Sync` ほか5つ | `RegisterObserver("client-order", …)` 等 | 各プラグインから **DOM走査コードが消える**。DELETE は `OnPageStart` へ |
| `RenderComputedViews`（child-list / required-materials） | `RegisterMirror("child-list", …)` 等 | エラー時に理由の段落（`view-error`）を描く現行の流儀は**維持**（「無言の空白」を作らない） |
| `FreshenTemplateBody` | 種まき段のコア備え付けハンドラ | レジストリの列型駆動のまま。プラグイン化は将来の口だけ |
| `SyncIndex` のテンプレート領域除外（空の本文を渡す） | 配送係が要素イベントを発火しない | §4 のとおり定義から同じ意味 |
| `.vocab-chrome` 除外（各所） | 配送係の不発火 | 勘所の罠が構造ごと消える |
| `RenderAnchors`・`Sanitize` | **コアのまま** | §2 のとおり |
| `RouteProvider` | 現行のまま | 対象外 |

## 7. エラーの方針

| 段 | エラー時 | 理由 |
|---|---|---|
| 観察係 | **保存失敗**（プラグイン名つき。現行 `SyncIndex` と同じ） | 索引の欠けは「黙って壊れる」の芽。書き手にその場で知らせる |
| 鏡型 | そのビューへ**理由の段落**を描いて続行 | ページ全体を道連れにしない。無言の空白は作らない（現行 `view-error` の一般化） |
| 種まき | 素のコピーで続行＋作成者へ告知 | 新規作成を止めるほどの失敗ではない。書き手が手で直せる |

## 8. 検証戦略

語彙移行（`migrate_vocab`）で使った**同値性テストの流儀**をそのまま使う:

1. **抽出の同値**——現行 `Sync` と新観察係で、同じ本文から**同じ索引行**が得られることを
   全プラグインについてテストで固定（移植は1プラグインずつ・同値を確認して進む）。
2. **描画の同値**——現行 `RenderComputedViews` と新鏡型で、同じページ・同じ閲覧者に対して
   **同じHTML**が出ること（見せ分けC案が壊れていないことを含む）。
3. 既存の固定資産——`go test ./...`・`shell_id_test.go`・`csp_test.go`・
   `route_guard_test.go`・E2E 6本（計128項目）——がすべて通ること。
4. `visibleChildren` を含む鏡型のテストは**ファイルDB**で書く（`:memory:` の罠。勘所）。

## 9. 実装順（各段でテスト全通過を確認して進む）

1. 配送係＋`WalkContext`＋登録の口を追加（**まだ誰も使わない**。挙動変化ゼロ）
2. `vocab_index` を観察係へ移植（同値テストで固定。いちばん消費形態が広い＝APIの試金石）
3. 残る5プラグインを移植し、`SyncIndex` の旧ループを撤去
4. 鏡型2つを移植し、`RenderComputedViews` を配送係経由へ
5. 種まきを配送係経由へ
6. 旧走査コードの残骸を掃除（`WalkElements` の直接利用者を点検して終了）

## 10. 未決（実装前に確認したいこと）

1. **`descend` の既定**——観察係が `false` を返し忘れて入れ子の表を二重に読む事故と、
   `true` を返し忘れて読み漏らす事故のどちらを既定で防ぐか（推奨: 既定 descend=true・
   マーカー要素を担当したハンドラだけ false を返す規約）。
2. **観察係のエラーで保存を止める範囲**——1プラグインの失敗で全体を止める（現行）か、
   失敗したプラグインの索引だけ欠けを許して告知か。現行維持を推奨（欠けは黙って壊れるの芽）。
3. 機能見出し（語彙モデル §11.1）が決まったときの**引き金解決層の差し替え**は本設計の
   範囲外——§3 の解決関数1点に閉じていることだけを保証する。
