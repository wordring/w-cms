# w-cms 開発方針

w-cms プロジェクトにおける、設計、開発、および運用に関する共通の設計思想と開発ルールを定めます。

**本ファイルは、人間の開発者だけでなく、本プロジェクトで作業するAIエージェントが従うべき行動規範でもあります。** エージェントは作業時にこの方針を読み込み、従ってください（旧 `.agents/AGENTS.md` の役割を本ファイルに統合しました）。

---

## 0. コアと拡張の線引き（2026-09-25 ユーザー決定）

> **コアは、「文書を書けばDBに入って検索できる」システムを作るときのベースにできるものにしたい。**
> そのために、いま作っている**特定の業務知識を必要とするものは拡張に分けたい**。
> しかしながら、**共通に使えるものはコアに入れて可用性を高めたい**。
> ——ユーザー（2026-09-25）

何かを作る・直すときは、**どちらに置くか**をまず決めてください。問いは1つです:

> **別の会社・別の業種が、同じ仕組みで「文書を書いて DB に入れて検索する」ときにも要るか？**
> 要るなら**コア**、その業務でしか意味を持たないなら**拡張**（`ext/`）。

| コア（`internal/`）に置く | 拡張（`ext/`）に置く |
|---|---|
| 本文の保存・版・権限・編集ロック・添付・サニタイズ | 受注・発注書・加工製品・材料・必要部材表などの**業務の規則** |
| 表とタグを DB に入れる仕組み・型と正規化・検索 | 業務の計算ビュー・鏡・ボタン（発注書を作る・送る 等） |
| テンプレート（**純粋なコピー**）・置き場・子ページ | 業務の語（`弊社品番`・`取消`・`臨時部材表` …）とその意味 |
| 鏡・計算ビューを**載せる口**（登録の仕組み） | その口に載せる**中身** |

- ⚠ **コアに業務語を書かないこと**（「コアは業務語を知らない」——
  [【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md) §9）。業務の言葉がコアに要るように
  見えたら、**口（登録の仕組み）をコアに作り、言葉は拡張から渡す**形を考えます。
- ⚠ **逆に、共通に使えるものを拡張に閉じ込めないこと**——別の拡張も使える道具（表の読み方・
  正規化・検索など）は、**可用性のためにコアへ**上げます。
- ⚠ **表の種類の登録もコアから無くす方向**です（コアは「キャプションのある表を DB に入れる」
  だけを知る）——[【考察】DBの日本語化.md](【考察】DBの日本語化.md)。
- **迷ったら、置き場所をユーザーに聞くこと。**

## 1. Go言語の設計思想：標準ライブラリの重視と外部依存の最小化

w-cms は、シンプルでメンテナンス性が高く、ポータビリティに優れたGoアプリケーションを目指します。そのため、コードベース全体にわたり以下のポリシーを適用します。

### ① 原則として標準ライブラリを優先する
HTTPルーティング、JSON処理、ファイル操作、DBアクセス、文字列処理など、ほとんどの処理はGoの標準ライブラリ（`net/http`, `encoding/json`, `os`, `database/sql` など）で実現可能です。
既存の処理を実装する、あるいは新規機能を追加する場合は、まず標準ライブラリで完結させる方法を検討してください。

### ② 外部依存パッケージ（3rd-partyライブラリ）の追加制限
外部パッケージはセキュリティリスク（サプライチェーン攻撃）、依存関係のバージョン衝突、ビルドの複雑化を引き起こす原因になります。
以下の例外を除き、原則として外部パッケージを新しく追加することは禁止します。
* **例外が認められるケース**:
  - SQLiteドライバなど、標準ライブラリのみでは物理的に代替不可能なインフラレベルの依存関係（現在はCGO不要のPure Go実装 `modernc.org/sqlite` を使用）。
  - パスワードハッシュ（argon2id）のための `golang.org/x/crypto`。自前実装すべきでない暗号処理であり、Goの準標準（拡張）ライブラリとして承認済み（[認証認可設計.md](認証認可設計.md) 参照）。
  - HTMLパース（`x/net/html`）のための `golang.org/x/net`。標準ライブラリに同等のHTMLツリー解析が無く、`internal/cms/parser.go` 等がDOM走査に使用。Goの準標準（拡張）ライブラリ。
  - PDF/発注書のAI明細抽出のための `github.com/google/generative-ai-go`（Gemini）と、その動作に必要な `google.golang.org/api`。発注書PDFからの明細抽出（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 5章）に使用。
  - **PDFの発行**のための `github.com/signintech/gopdf`（**MIT**）と、その依存
    `github.com/phpdave11/gofpdi`。⚠ **2026-09-21 にユーザー承認**——発注書はPDFで
    送付し7年保存する必要があり、**印刷・メール添付・FAX送信のすべてがPDFを前提**に
    します。ブラウザの「PDFに保存」では人の手が毎回挟まり、自動送信に繋がりません。
    ⚠ **日本語には TTF の埋め込みが要ります**（`.ttc` は読めない）。経緯と罠は
    [【考察】発注書のPDF発行.md](【考察】発注書のPDF発行.md)。
  - 文字コード変換（`x/text/encoding`）のための `golang.org/x/text`。和文メール（ISO-2022-JP / Shift_JIS）のデコード等に使用。既に上記依存の indirect として go.mod に存在し、直接利用してもビルド増分は無い。通信記録の取り込みで直接利用予定（[【考察】通信記録処理.md](【考察】通信記録処理.md)）。Goの準標準（拡張）ライブラリ。
  - その他、プロジェクト内で事前に承認された重大なライブラリ。

  > 上記は実際の `go.mod` の直接依存と対応させて維持すること。新しい直接依存を承認・追加したら、この一覧も同時に更新する（過去にGemini連携追加時に更新が漏れた経緯がある）。

## 2. ドキュメント（Markdown）の命名規則

開発者およびユーザーがドキュメントに直感的にアクセスできるようにするため、ドキュメントの命名規則を以下のように定めます。

* **原則日本語ファイル名**:
  - 設計書、仕様書、運用マニュアル、メモなどの `.md` ファイルは、原則として**わかりやすい日本語のファイル名**にします。
  - 例：
    - `docs/editor_spec.md` ➔ `docs/エディタ仕様.md`
    - `docs/page_creation_mechanism.md` ➔ `docs/ページ作成の仕組み.md`
    - `docs/開発方針.md` （本ファイル）
* **VSCode等のプレビュー前提**:
  - VSCodeのプレビュー環境等において、日本語ファイル名同士の相対リンクはそのまま正常に解釈されるため、URLエンコードされた文字列（`%E3...`）に変換せず、生の日本語でリンクを記述します。
* **文書の種別を `【種別】` の接頭辞で表す**:
  - 探索的な検討・設計判断のメモ → **`【考察】`**（例: `【考察】通信記録処理.md`・`【考察】アンドゥ・リドゥ.md`・`【考察】同時編集の競合対策.md`）。
  - マニュアル・手順ガイド → **`【ガイド】`**（例: `【ガイド】プラグイン開発.md`・`【ガイド】デプロイ・運用.md`）。
  - 業務ユースケースの仕様 → **`【ユースケース】`**（例: `【ユースケース】受注と進捗管理.md`・`【ユースケース】原価と利益.md`）。
  - 参照・一覧（リスト/リファレンス）→ **`【一覧】`**（例: `【一覧】用語集.md`・`【一覧】語彙.md`・`【一覧】API.md`）。
  - **要求仕様** → **`【要求】`**（例: `【要求】発注フォルダ.md`・`【要求】タグ.md`。2026-09-23 追加）。
    ⚠ **これが最新の正本で、他の文書は順次ここへ畳んで廃止していきます**（2026-09-23 ユーザー:
    「**【要求】は要求仕様という意味で、出来るだけ私が書く、あるいは既存文書からClaudeが抽出した
    ものを私が編集するものです。これを最新の文書として、ほかのものは廃止していく方向で**」）。
    - **書くのは利用者。** エージェントは①**散らばった既存文書から抜き出して下書きを置く**
      ②**矛盾を指摘する**——の2つに回ります（ユーザー:「矛盾があれば指摘してくれれば修正します」
      「**実装のもとにしましょう**」）。
    - ⚠ **1つの文書に2種類のことが入ります。混ぜないこと**——**要求**（こうあってほしい・
      利用者が直す）と、⚠ **いま**（実装の現状・エージェントが直す）。
      **「いまこうだから、こうあるべき」ではありません。**
    - ⚠ **廃止には順番が要ります**——**【要求】へ移してから消すこと**。先に消すと正本が失われます。
      ⚠ **そもそも要求仕様ではない文書は廃止しません**——[変更履歴.md](変更履歴.md)（経緯）・
      [作業引き継ぎ.md](作業引き継ぎ.md)（現況）・[コードリファレンス/](コードリファレンス/README.md)
      （実装の写し）・`【考察】`（**なぜそうしたか**の決定ログ）。
  - **`【考察】` は状態（検討中・未実装）マーカー**として、型接頭辞の前に**重ねられます**（例: `【考察】【ユースケース】○○.md` ＝ 検討中の業務ユースケース）。実装が固まったら `【考察】` を外します。
  - 接尾辞（`○○の考察`・`○○マニュアル`・`○○一覧`）でなく**接頭辞**にすることで、一覧で同種が並び、文書の性格が一目で分かります。**ファイル名と本文の見出し（H1）は一致させます。**
  - 実装済みになっても考察メモは記録として接頭辞を維持します。コンセプト・アーキテクチャ・各設計書・変更履歴・開発方針・作業引き継ぎ等の中核文書には付けません。

## 3. コミット・コミュニケーション規約

* **日本語によるコミュニケーション**:
  - ユーザーへの応答・提案、Gitのコミットメッセージ、PRの記述、Issueの記述、およびAIエージェントによる開発報告は、すべて**日本語**で行います。
* **コミットの分割**:
  - 「リネーム」「機能修正」「リファクタリング」など、目的が明確に異なる変更は、1つのコミットに混ぜず、分けてコミットします。

## 4. コード変更時のルール

* **既存コメント・ドキュメントの維持**:
  - コードの書き換えを行う際、既存の無関係なコードコメントやドキュメンテーションは、勝手に削除・上書きせず、可能な限り現状維持します。
* **変更後のテスト実行**:
  - コードを変更したあとは、必ず `go test ./...` などの自動テストを実行し、テストが通ることを確認します。
* **インライン `script`/`style`/`on*=` を書かない**:
  - Content-Security-Policy は **strict 版（`'unsafe-inline'` なし）で運用中**です（2026-08-20 到達）。
    インラインの `<script>`・`<style>`・`style=` 属性・`on*=` 属性ハンドラは**書けません**——
    書くとブラウザが実行を拒否し、画面が壊れます。スクリプト/スタイルは `/assets/` 配下の
    外部ファイル（＝self）へ置き、イベントは `addEventListener`、動的スタイルは描画後に
    `element.style.x = y`（CSSOM経由）で当てます。ヘッダの後戻りは
    [csp_test.go](../internal/auth/csp_test.go) が検出します
    （経緯は [本文サニタイズ設計.md §6](本文サニタイズ設計.md)）。
