# w-cms 開発方針

w-cms プロジェクトにおける、設計、開発、および運用に関する共通の設計思想と開発ルールを定めます。

**本ファイルは、人間の開発者だけでなく、本プロジェクトで作業するAIエージェントが従うべき行動規範でもあります。** エージェントは作業時にこの方針を読み込み、従ってください（旧 `.agents/AGENTS.md` の役割を本ファイルに統合しました）。

---

## 1. Go言語の設計思想：標準ライブラリの重視と外部依存の最小化

w-cms は、シンプルでメンテナンス性が高く、ポータビリティに優れたGoアプリケーションを目指します。そのため、コードベース全体にわたり以下のポリシーを適用します。

### ① 原則として標準ライブラリを優先する
HTTPルーティング、JSON処理、ファイル操作、DBアクセス、文字列処理など、ほとんどの処理はGoの標準ライブラリ（`net/http`, `encoding/json`, `os`, `database/sql` など）で実現可能です。
既存の処理を実装する、あるいは新規機能を追加する場合は、まず標準ライブラリで完結させる方法を検討してください。

### ② 外部依存パッケージ（3rd-partyライブラリ）の追加制限
外部パッケージはセキュリティリスク（サプライチェーン攻撃）、依存関係のバージョン衝突、ビルドの複雑化を引き起こす原因になります。
以下の例外を除き、原則として外部パッケージを新しく追加することは禁止します。
* **例外が認められるケース**:
  - SQLiteドライバなど、標準ライブラリのみでは物理的に代替不可能なインフラレベルの依存関係（現在はCGO不要のPure Go実装 `modernc.org/sqlite` を使用）。
  - パスワードハッシュ（argon2id）のための `golang.org/x/crypto`。自前実装すべきでない暗号処理であり、Goの準標準（拡張）ライブラリとして承認済み（[認証認可設計.md](認証認可設計.md) 参照）。
  - HTMLパース（`x/net/html`）のための `golang.org/x/net`。標準ライブラリに同等のHTMLツリー解析が無く、`internal/cms/parser.go` 等がDOM走査に使用。Goの準標準（拡張）ライブラリ。
  - PDF/発注書のAI明細抽出のための `github.com/google/generative-ai-go`（Gemini）と、その動作に必要な `google.golang.org/api`。発注書PDFからの明細抽出（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 5章）に使用。
  - 文字コード変換（`x/text/encoding`）のための `golang.org/x/text`。和文メール（ISO-2022-JP / Shift_JIS）のデコード等に使用。既に上記依存の indirect として go.mod に存在し、直接利用してもビルド増分は無い。通信記録の取り込みで直接利用予定（[【考察】通信記録処理.md](【考察】通信記録処理.md)）。Goの準標準（拡張）ライブラリ。
  - その他、プロジェクト内で事前に承認された重大なライブラリ。

  > 上記は実際の `go.mod` の直接依存と対応させて維持すること。新しい直接依存を承認・追加したら、この一覧も同時に更新する（過去にGemini連携追加時に更新が漏れた経緯がある）。

## 2. ドキュメント（Markdown）の命名規則

開発者およびユーザーがドキュメントに直感的にアクセスできるようにするため、ドキュメントの命名規則を以下のように定めます。

* **原則日本語ファイル名**:
  - 設計書、仕様書、運用マニュアル、メモなどの `.md` ファイルは、原則として**わかりやすい日本語のファイル名**にします。
  - 例：
    - `docs/editor_spec.md` ➔ `docs/エディタ仕様.md`
    - `docs/page_creation_mechanism.md` ➔ `docs/ページ作成の仕組み.md`
    - `docs/開発方針.md` （本ファイル）
* **VSCode等のプレビュー前提**:
  - VSCodeのプレビュー環境等において、日本語ファイル名同士の相対リンクはそのまま正常に解釈されるため、URLエンコードされた文字列（`%E3...`）に変換せず、生の日本語でリンクを記述します。
* **文書の種別を `【種別】` の接頭辞で表す**:
  - 探索的な検討・設計判断のメモ → **`【考察】`**（例: `【考察】通信記録処理.md`・`【考察】アンドゥ・リドゥ.md`・`【考察】同時編集の競合対策.md`）。
  - マニュアル・手順ガイド → **`【ガイド】`**（例: `【ガイド】プラグイン開発.md`・`【ガイド】デプロイ・運用.md`）。
  - 業務ユースケースの仕様 → **`【ユースケース】`**（例: `【ユースケース】受注と進捗管理.md`・`【ユースケース】原価と利益.md`）。
  - 参照・一覧（リスト/リファレンス）→ **`【一覧】`**（例: `【一覧】用語集.md`・`【一覧】カスタムタグ.md`）。
  - **`【考察】` は状態（検討中・未実装）マーカー**として、型接頭辞の前に**重ねられます**（例: `【考察】【ユースケース】受注処理.md` ＝ 検討中の受注ユースケース）。実装が固まったら `【考察】` を外します。
  - 接尾辞（`○○の考察`・`○○マニュアル`・`○○一覧`）でなく**接頭辞**にすることで、一覧で同種が並び、文書の性格が一目で分かります。**ファイル名と本文の見出し（H1）は一致させます。**
  - 実装済みになっても考察メモは記録として接頭辞を維持します。コンセプト・アーキテクチャ・各設計書・変更履歴・要件定義書・開発方針・作業引き継ぎ等の中核文書には付けません。

## 3. コミット・コミュニケーション規約

* **日本語によるコミュニケーション**:
  - ユーザーへの応答・提案、Gitのコミットメッセージ、PRの記述、Issueの記述、およびAIエージェントによる開発報告は、すべて**日本語**で行います。
* **コミットの分割**:
  - 「リネーム」「機能修正」「リファクタリング」など、目的が明確に異なる変更は、1つのコミットに混ぜず、分けてコミットします。

## 4. コード変更時のルール

* **既存コメント・ドキュメントの維持**:
  - コードの書き換えを行う際、既存の無関係なコードコメントやドキュメンテーションは、勝手に削除・上書きせず、可能な限り現状維持します。
* **変更後のテスト実行**:
  - コードを変更したあとは、必ず `go test ./...` などの自動テストを実行し、テストが通ることを確認します。
* **新規コードでインライン `script`/`style`/`on*=` を書かない**:
  - Content-Security-Policy の strict 化（`'unsafe-inline'` なし）を後戻りさせないため、
    新しく追加するフロントのコードでは、インライン `<script>`・`<style>`・`style=` 属性・
    `on*=` 属性ハンドラを原則使いません。スクリプト/スタイルは `/assets/` 配下の外部ファイル（＝self）へ置き、
    イベントは `addEventListener`、動的スタイルは描画後に `element.style.x = y`（CSSOM経由）で当てます。
    既存のインラインは段階移行の対象です（[【考察】CSP強化.md](【考察】CSP強化.md) 参照）。
