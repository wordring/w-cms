# w-cms 開発方針

w-cms の設計・開発・運用に共通する考え方と、開発の決まりを定めます。

**この文書は、人の開発者だけでなく、このプロジェクトで作業する AI エージェントが従う行動の決まりでもあります。**
エージェントは、作業のときにこの方針を読んで従ってください（旧 `.agents/AGENTS.md` の役割を、この文書にまとめました）。

---

## 0. コアと拡張の線引き（2026-09-25 ユーザー決定）

> **コアは、「文書を書けばDBに入って検索できる」システムを作るときのベースにできるものにしたい。**
> そのために、いま作っている**特定の業務知識を必要とするものは拡張に分けたい**。
> しかしながら、**共通に使えるものはコアに入れて可用性を高めたい**。
> ——ユーザー（2026-09-25）

何かを作る・直すときは、まず**どちらに置くか**を決めてください。問いは1つです。

> **別の会社・別の業種が、同じ仕組みで「文書を書いて DB に入れて検索する」ときにも要るか？**
> 要るなら**コア**、その業務でしか意味を持たないなら**拡張**（`ext/`）。

| コア（`internal/`）に置く | 拡張（`ext/`）に置く |
|---|---|
| 本文の保存・版・権限・同時編集の保護（ブロック単位）・添付・サニタイズ | 受注・発注書・加工製品・材料・必要部材表などの**業務の規則** |
| 表とタグを DB に入れる仕組み・型と正規化・検索 | 業務の計算ビュー・鏡・ボタン（発注書を作る・送る 等） |
| テンプレート（**純粋なコピー**）・置き場・子ページ | 業務の語（`弊社品番`・`取消`・`臨時部材表` …）とその意味 |
| 鏡・計算ビューを**登録する仕組み** | その仕組みに載せる**中身** |

鏡は、表示するときにサーバーが埋める、保存されない部分です。

- ⚠ **コアに業務語を書かないこと。**
  「コアは業務語を知らない」が線です（[【ガイド】プラグイン開発.md](参照/【ガイド】プラグイン開発.md) §9）。
  業務の言葉がコアに要るように見えたら、**登録の仕組みをコアに作り、言葉は拡張から渡す**形を考えます。
- ⚠ **逆に、共通に使えるものを拡張に閉じ込めないこと。**
  別の拡張も使える道具（表の読み方・正規化・検索など）は、**可用性のためにコアへ**上げます。
- **表の種類の登録も、コアから無くす方向**です。
  コアは「キャプションのある表を DB に入れる」ことだけを知る形にします（[【考察】DBの日本語化.md](考察/【考察】DBの日本語化.md)）。
- **迷ったら、置き場所をユーザーに聞くこと。**

### 0.1 境を機械で守る（2026-10-21）

> 2026-10-20 利用者:「コアと拡張を分離することを守らせるために設定に何か書いておくことはできますか？」
> 「両方お願いします。開発方針にも書いたほうが良いと思いうます」

この線は、人の注意だけでなく、試験と Claude Code の設定でも守ります。

- **見張りの試験**は `internal/boundary` です。
  後戻りを見つける試験で、`go test ./...` に入っているので、いつもの試験で一緒に流れます。
  見るのは次の4つです。
  - コアの Go（`internal/`）が、拡張（`w-cms/ext/...`）を import していないこと。
  - コアの Go のコード（文字列と名前。コメントは除く）に、業務の言葉が無いこと。
  - コアの画面（`assets/` 直下の JS・CSS・HTML。コメントは除く）に、業務の言葉が無いこと。
  - コアの `app.css`・`app.js` が、拡張だけが描く class を名指ししていないこと。
- **業務の言葉の表**は、[internal/boundary/rules.json](../internal/boundary/rules.json) の `words` です。
  新しい業務の言葉ができたら、ここへ足します。
- **どうしても要る例外**は、同じ表の `allow` に書きます。
  ファイル・言葉・その行に含まれる文字と、**理由**を必ず書きます。理由の無い例外は効きません。
- **コアが拡張の欄を見分けたいとき**は、拡張の class を名指ししません。
  拡張に、コアの一般の印（`w-` で始まる class。例: `w-no-print`・`w-no-table-menu`・`w-view-empty`）を付けてもらい、それを使います。
  拡張の見た目は、拡張の CSS に書きます。
- **Claude Code の hook**（[.claude/settings.json](../.claude/settings.json)）は、エージェントが次のファイルを書き換えるたびに、この試験を流します（[tools/boundary-hook.js](../tools/boundary-hook.js)）。
  対象は、コアのファイル・拡張の Go・言葉の表です。落ちると、その場でエージェントに知らせます。
- 見張りの試験が落ちたら、言葉を例外にする前に、**登録の仕組みをコアに作り、言葉は拡張から渡す**形を考えます（上の ⚠）。

## 1. Go言語の設計思想：標準ライブラリの重視と外部依存の最小化

w-cms は、シンプルで保守しやすく、どこへでも持っていける Go のアプリケーションを目指します。
そのため、コード全体に次の方針を当てます。

### ① 原則として標準ライブラリを優先する

HTTP のルーティング・JSON・ファイル操作・DB アクセス・文字列の処理など、ほとんどの処理は Go の標準ライブラリ（`net/http`, `encoding/json`, `os`, `database/sql` など）でできます。
処理を書くとき・機能を足すときは、まず標準ライブラリだけで済ませる方法を考えてください。

### ② 外部依存パッケージ（3rd-partyライブラリ）の追加制限

外部のパッケージは、次のことの原因になります。

- セキュリティの危険（サプライチェーン攻撃）
- 依存関係の版の衝突
- ビルドの複雑化

そのため、次の例外を除いて、外部のパッケージを新しく足すことは禁止します。

* **例外が認められるケース**:
  - **SQLite のドライバ**など、標準ライブラリだけではどうしても代わりが無い、土台の依存。
    いまは、CGO の要らない Pure Go の実装 `modernc.org/sqlite` を使っています。
  - **パスワードハッシュ（argon2id）**のための `golang.org/x/crypto`。
    暗号の処理は自前で書くべきではありません。Go の準標準（拡張）ライブラリとして承認済みです（[認証認可設計.md](旧文書/認証認可設計.md) 参照）。
  - **HTML の解析**（`x/net/html`）のための `golang.org/x/net`。
    標準ライブラリには、同じような HTML の木の解析がありません。`internal/cms/parser.go` などが DOM の走査に使います。Go の準標準（拡張）ライブラリです。
  - **PDF・発注書の AI による明細の抽出**のための `github.com/google/generative-ai-go`（Gemini）と、その動作に必要な `google.golang.org/api`。
    発注書の PDF から明細を抜き出すのに使います（[アーキテクチャとDBスキーマ.md](旧文書/アーキテクチャとDBスキーマ.md) 5章）。
  - **PDF の発行**のための `github.com/signintech/gopdf`（**MIT**）と、その依存 `github.com/phpdave11/gofpdi`。
    **2026-09-21 にユーザーが承認しました。**
    - 発注書は PDF で送り、7年保存する必要があります。**印刷・メール添付・FAX 送信のすべてが PDF を前提**にします。
      ブラウザの「PDFに保存」では、毎回人の手が挟まり、自動の送信につながりません。
    - ⚠ **日本語には、フォントの埋め込みが要ります。** gopdf は `.ttc`（フォントコレクション）を読めません。
      そこで、w-cms が `.ttc` から1書体を取り出して渡します（2026-09-23 から）。
      取り出すのは `ext/toho/ttc.go` で、設定は `pdf_font`・`pdf_font_face` です。
      経緯と罠は [【考察】発注書のPDF発行.md](考察/【考察】発注書のPDF発行.md) にあります。
  - **文字コードの変換**（`x/text/encoding`）のための `golang.org/x/text`。
    和文のメール（ISO-2022-JP / Shift_JIS）のデコードなどに使います。
    もともと上の依存の indirect として go.mod にあったので、直接使ってもビルドは増えません。
    いまは、通信記録の取り込み（`ext/comm/intake_eml.go`）や文字の正規化などで直接使っています（[【考察】通信記録処理.md](考察/【考察】通信記録処理.md)）。Go の準標準（拡張）ライブラリです。
  - そのほか、プロジェクトの中で前もって承認された重大なライブラリ。

  > この一覧は、実際の `go.mod` の直接の依存と合わせて保つこと。
  > 新しい直接の依存を承認して足したら、この一覧も同時に直します（以前、Gemini 連携を足したときに直し漏れました）。

## 2. ドキュメント（Markdown）の命名規則

開発者と利用者が文書をすぐ見つけられるように、文書の名前の付け方を次のように決めます。

* **原則日本語ファイル名**:
  - 設計書・仕様書・運用の手引き・メモなどの `.md` ファイルは、原則として**分かりやすい日本語のファイル名**にします。
  - 例：
    - `docs/editor_spec.md` ➔ `docs/旧文書/エディタ仕様.md`
    - `docs/page_creation_mechanism.md` ➔ `docs/ページ作成の仕組み.md`
    - `docs/開発方針.md` （本ファイル）
* **VSCode等のプレビュー前提**:
  - VSCode のプレビューなどでは、日本語のファイル名どうしの相対リンクが、そのまま正しく読まれます。
    だから、リンクは URL エンコードした文字列（`%E3...`）にせず、生の日本語で書きます。
* **文書の種別を `【種別】` の接頭辞で表す**:
  - 探索的な検討・設計判断のメモ → **`【考察】`**（例: `【考察】通信記録処理.md`・`【考察】アンドゥ・リドゥ.md`・`【考察】同時編集の競合対策.md`）。
  - マニュアル・手順ガイド → **`【ガイド】`**（例: `【ガイド】プラグイン開発.md`・`【ガイド】デプロイ・運用.md`）。
  - 業務ユースケースの仕様 → **`【ユースケース】`**（例: `【ユースケース】受注から利益まで.md`）。
  - 参照・一覧（リスト/リファレンス）→ **`【一覧】`**（例: `【一覧】用語集.md`・`【一覧】語彙.md`・`【一覧】API.md`）。
  - **要求仕様** → **`【要求】`**（例: `【要求】タグと表.md`・拡張の `拡張/東邦/【要求】部材発注フォルダ.md`。2026-09-23 追加）。
    ⚠ **【要求】が最新の正本です。ほかの文書は、順にここへまとめて廃止していきます。**

    > 2026-09-23 ユーザー:「**【要求】は要求仕様という意味で、出来るだけ私が書く、あるいは既存文書からClaudeが抽出したものを私が編集するものです。これを最新の文書として、ほかのものは廃止していく方向で**」

    - **書くのは利用者です。** エージェントの役目は2つです。
      ①**散らばった既存の文書から抜き出して、下書きを置く**。②**矛盾を指摘する**。

      > ユーザー:「矛盾があれば指摘してくれれば修正します」「**実装のもとにしましょう**」

    - ⚠ **1つの文書に2種類のことが入ります。混ぜないこと。**
      - **要求**: こうあってほしい。利用者が直します。
      - ⚠ **いま**: 実装の現状。エージェントが直します。

      **「いまこうだから、こうあるべき」ではありません。**
    - ⚠ **廃止には順番が要ります。【要求】へ移してから消すこと。** 先に消すと、正本が失われます。
    - ⚠ **そもそも要求仕様ではない文書は、廃止しません。**
      [変更履歴.md](変更履歴.md)（経緯）・[作業引き継ぎ.md](作業引き継ぎ.md)（現況）・[コードリファレンス/](参照/コードリファレンス/README.md)（実装の写し）・`【考察】`（**なぜそうしたか**の決定ログ）です。
    - **`docs/` のフォルダ分け**（2026-09-27 利用者決定）:

      > 利用者:「【要求】を書いていくことで、【考察】などは古い文書にしていきたい。【要求】以外は別のフォルダに入れるのはどうですか？」

      | 置き場 | 何か |
      |---|---|
      | `docs/` 直下 | **【要求】**（コアの正本）と、進め方の文書（開発方針・作業引き継ぎ・変更履歴・変更履歴アーカイブ）。`CLAUDE.md` が直接読むものは直下に残します |
      | `docs/拡張/<拡張>/` | 拡張の【要求】（下の段） |
      | `docs/考察/` | **【考察】**。「なぜそうしたか」の決定ログです。**廃止しません**。いまの話し合いもここに置きます |
      | `docs/旧文書/` | 設計書（アーキテクチャ・エディタ仕様・コンセプトなど）と【ユースケース】。**【要求】へ移し終えたら消します** |
      | `docs/参照/` | 【ガイド】・【一覧】・コードリファレンス。実装に合わせて保つものです |

      - ⚠ **接頭辞は残します。** フォルダで種類が分かっても、ファイル名だけで性格が分かるようにするためです。
      - ⚠ **文書を動かしたら、変更履歴も含めて、全部のリンクを張り替えること。**
        変更履歴の**文章**は当時のまま残し、**リンク先だけ**を今の場所へ直します。

        > 2026-09-27 利用者:「リンクだけ張り替えてください」

    - **拡張の【要求】は `docs/拡張/<拡張>/` に置きます**（例: `docs/拡張/東邦/【要求】部材発注フォルダ.md`・`docs/拡張/通信/【要求】通信拡張.md`。2026-09-27 利用者決定）。
      - `docs/` 直下の【要求】は**コアの要求**です。⚠ **業務知識を書きません。**
        §0 と同じ線で、業務の決まりは拡張の【要求】へ分けます。

        > 2026-09-27 利用者:「コアの【要求】に入っている業務知識は拡張へ分離していきましょう」

      - コアの【要求】が業務の話に触れるときは、「拡張の【要求】」と案内するだけにします。
      - ⚠ **例に業務の語を使っている所は、まだ残っています**（`発注日` のタグの例など）。例は、一般的なものへ順に替えます。
  - **`【考察】` は、状態（検討中・未実装）の印としても使います。** 型の接頭辞の前に**重ねられます**（例: `【考察】【ユースケース】○○.md` ＝ 検討中の業務ユースケース）。
    実装が固まったら `【考察】` を外します。
  - 接尾辞（`○○の考察`・`○○マニュアル`・`○○一覧`）ではなく**接頭辞**にします。一覧で同じ種類が並び、文書の性格が一目で分かるからです。
  - **ファイル名と本文の見出し（H1）は一致させます。**
  - 実装済みになっても、考察のメモは記録として接頭辞を残します。
  - コンセプト・アーキテクチャ・各設計書・変更履歴・開発方針・作業引き継ぎなどの中核の文書には、接頭辞を付けません。

## 2a. 文書の書き方——人が上から読んで分かるように書く（2026-10-13 利用者決定）

> 2026-10-13 利用者:「順に、文書を人間に読みやすいフレンドリーなものにしてください」
> （1本目の書き直しを見て）「とても良いと思います。考察も読みやすく治してもらえると嬉しいです」

`docs/` の文書は、エージェントの作業メモではなく、**人が読む文書**です。次の決まりで書きます。
見本は [【要求】w-cmsとは.md](【要求】w-cmsとは.md) と [【要求】ページとエディタ.md](【要求】ページとエディタ.md) です。

- **文は短く、です・ます調で書きます。** 1つの文に1つのことを書きます。
- **記号を連ねません。** 「——」でつなぐ文、「⚠」と太字の連続、括弧の中の括弧は避けます。
  「⚠」は、知らないと壊す・失う所だけに使います。
- **専門の言葉は、初めて出る所で一言説明します**（例: インスタンス＝動いている w-cms の1つ1つ）。
- **長い箇条書きは分けます。** 見出しを立てるか、小さな箇条書きにします。
- **意味は変えません。** 文書を読みやすく直すときは、要求の項目・節の番号・小見出しの名前・リンク・識別子を元のままにします。
- **利用者の言葉の引用は、一字も変えません。** 引用は、日付と「利用者:」を付けて、引用の形（`>`）で置きます。
- **「⚠ いま」の印は残します**（§2 の決まり。要求と実装の現状を混ぜません）。
  同じ機能の「⚠ いま」が日付ごとに重なったら、**今の姿1つ**にまとめます。
- **「いつ・なぜその形になったか」の但し書きは、本文に混ぜません。**
  【要求】では、末尾の「この文書の経緯」にまとめます（消しません）。
- **【考察】は決定の記録です。** 決めたこと・日付・利用者の言葉・節の番号はそのままにして、説明の文だけを読みやすくします。
  経緯そのものが中身なので、まとめて消すことはしません。
- **[変更履歴.md](変更履歴.md) は、当時の文章のまま残します**（書き直しません）。

## 4. コード変更時のルール

* **既存コメント・ドキュメントの維持**:
  - コードを書き換えるとき、関係の無いコードのコメントや説明を、勝手に消したり上書きしたりしません。できるだけ今のまま残します。
* **変更後のテスト実行**:
  - コードを変えたあとは、必ず `go test ./...` などの自動の試験を流し、通ることを確かめます。
* **インライン `script`/`style`/`on*=` を書かない**:
  - Content-Security-Policy（CSP）は、**strict 版（`'unsafe-inline'` なし）で運用しています**（2026-08-19 に到達）。
  - だから、次のものは**書けません**。書くとブラウザが実行を拒み、画面が壊れます。
    インラインの `<script>`・`<style>`・`style=` 属性・`on*=` 属性のハンドラ。
  - 代わりに、次のように書きます。
    - スクリプトとスタイルは、`/assets/` 配下の外部のファイル（＝self）に置きます。
    - イベントは `addEventListener` でつなぎます。
    - 動きのあるスタイルは、描いたあとに `element.style.x = y`（CSSOM 経由）で当てます。
  - ヘッダが後戻りしたら、[csp_test.go](../internal/auth/csp_test.go) が見つけます
    （経緯は [本文サニタイズ設計.md §6](旧文書/本文サニタイズ設計.md)）。
