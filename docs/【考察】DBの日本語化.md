## 1. いまの形（測った事実・2026-09-25）

- **表の中身は `vocab_index` に「1セル＝1行」**（縦持ち）で入っています:
  `page_id, data_type, block_no, block_id, row_no, field, value, norm_value, norm_num`。
  - **`field` は見出しの表示文字**（`品番`）——**名前はもう日本語**です。
  - ⚠ **英字なのは `data_type`（形式の機械キー `client-order-items`）と、表・列の識別子だけ**。
  - 見たままの形（1行＝表の1行、列＝見出し）で引くには、縦持ちを**横に並べ直す**必要があります。
- **タグは `page_tags`**（`page_id, seq, name, value, norm_value`）。`name` はタグ名（日本語）。
- **形式の登録は Go のコードの中**（`cms.RegisterVocab`・拡張の `init()`）。
  稼働中のレジストリは **25形式**——データの表 **11**（受注明細・発注明細・発注部材表・
  臨時部材表・材料・購入部品・支給部品・外注加工・見積もり・改訂明細・検査記録）、
  データの節 4、ビュー 9、タグ 1。
  ⚠ **設定ファイル（`config/settings.json`）で足せるのは語→型の辞書 `vocabulary` だけ**
  （いま42語）——形式は足せません。
- **形式の解決**は ①`data-type` 属性 ②節の機能見出し ③`<caption>` の順で1回だけ。
  ⚠ **登録された形式だけが索引に入ります**（2026-09-20 決定——それまでは型の解決しない表も
  **形式名が空のまま**、普通の文章の表まで入っていた）。
- **列の型**は ①見出しセルの `data-type` ②登録の列宣言 ③設定の語彙（`InferColumnType`・

- **値の正規化**は型ごとの `NormalizeValue`——**入れるときも引くときも同じ関数**を通します。

## 3. 案（筆者）

### 3.1 見たままの表

**キャプションのある表は、キャプションの名前の表として DB に入れる。列は見出しの名前。**

```sql
SELECT 品番, 品名, 数量 FROM 受注明細 WHERE 品番 LIKE 'A100%';
```

- ⚠ **キャプションの無い表は入れません**（名前が無い）。09-20 に閉じた「普通の文章の表まで
  入る」は、**キャプションの有無**で線が引けます。
- 行ごとに**どのページの・何番目の表の・何行目か**を持たせます——列の名前は
  **`page_id`・`table_id`・`row_id`**（2026-09-25 利用者:「page_id、table_id などアルファベットで
  良いです」）。`table_id` はそのページの中で同じキャプションの何番目の表か、`row_id` は何行目か。
- ⚠ **見出しが予約語なら警告します**（利用者:「表の見出しに予約語が来たら警告してください」）——
  SQL の予約語（`Order`・`Group`・`Select` など）と、上の3つの列名。入れること自体はできます
  （引用符で囲む）が、SQL を書く人が引用符を要ることに気づけるように。

**置き方: 新しい DB へ移す**（2026-09-25 決定・当初の案B）。利用者:「今あるDBのTableはそのままという
意味であれば、**新しいマナーのDBに移してTableを作ってください**」。

- いまの縦持ち（`vocab_index`・受注明細も発注明細も1つの大きな表に「1セル1行」）を**やめ**、
  **キャプションごとの表だけ**にします。**同じ中身を2か所に持ちません。**
  ⚠ 筆者は当初、縦持ちを残して写しを作る案（A）を推していました——不採用。
- 置き場は**別のファイル**（`data/tables.db`）——中核の表（`pages` など）と名前がぶつからず、
  運用者が開くのもこのファイルだけ（§3.3 の2）。どちらも本文HTMLから作る**派生**なので、
  DB再構築で作り直せます。
- ⚠ **移し終えるまでは両方に書きます**——いまの集計（必要部材表・受注残など）は縦持ちを読んで
  いるので、**読み手を新しい表へ全部移してから縦持ちを消す**（§7 の段取り）。
- ⚠ 見出しが増えたら列を足す（`ALTER TABLE … ADD COLUMN`）。ビュー（`CREATE VIEW`）は使いません
  ——SQLite の TEMP でないビューは同じファイルの中しか参照できないため。

### 3.2 名前にも同じ正規化を（答え4の延長）

値だけでなく**表名・列名にも**正規化を掛けます（2026-09-25 決定）:
**NFKC・前後の空白を落とす・続いた空白は1つにまとめる**。全角半角や前後の空白の違いで
**別の表・別の列**に分かれるのを防ぐためです。
- **既定は「英数字は半角・仮名は全角」**（利用者:「デフォルトで英数字は半角、仮名文字は全角が
  使いやすいです」）——**NFKC がちょうどこの形**です（`ＡＢＣ１２３`→`ABC123`・`ﾌﾟﾚｰﾄ`→`プレート`）。
- ⚠ **中の空白は消しません**——`品 番` と `品番` は別の列になり、§3.4 の一覧に出ます。

⚠ **SQLite は日本語の名前を引用符なしで受けます**（2026-09-25 に実測）——
`SELECT 品番, 数量 FROM 受注明細 WHERE 品名 LIKE '留め%'` がそのまま通ります。
**空白や ASCII の記号を含む名前**は引用符（`"受注 明細"`）が要ります——保存のときに告知します。
⚠ **NFKC は全角の記号も半角にします**——`顧客の発注書（読んだまま）` は `顧客の発注書(読んだまま)` になり、
半角のかっこなので**引用符が要ります**（`SELECT * FROM "顧客の発注書(読んだまま)"`）。全角のままなら
引用符なしで書けますが、`（` と `(` の揺れが別の表・別の列に分かれます——**揃えるほうを採りました**
（変えるなら §3.2 の規則を「英数字と仮名だけ」にする）。

### 3.3 セキュリティ（答え3への返事）

**根本的な問題はありません。守りが4つ要ります。**

1. **表名・列名は必ず引用符で囲む**——名前は利用者が本文に書いた文字で、SQL の `?` では
   渡せません。囲み忘れると**キャプションの文字が SQL として走ります**。
   **囲む関数を1つだけ作り、全部そこを通す**（`tagNormBind` と同じ「判断を1か所に閉じる」）。
2. **別ファイルに置く**（§3.1・`data/tables.db`）——キャプションが `pages` や `page_perms` だと中核の表と
   ぶつかって壊れます。別ファイルなら**壊れても作り直せ**、運用者が開くのも**このファイルだけ**で済みます。
3. **検索画面と AI には自由な SQL を渡さない**——表には**全ページの行**が入るので、
   **読めないページの行も見えます**（見せ分け・C案を素通り）。検索画面と AI は**サーバーの口**を
   通し、**読めるページの行だけ**返します。自由な SQL は **DB を開ける運用者だけ**（答え2）。
   ⚠ **答え1で多いのは検索画面と AI なので、ここがいちばん肝**です。
4. **数の上限**——キャプションを打ち間違えるたびに表が増えます。列は SQLite の既定で
   **2000まで**。上限を越えたら入れずに、運用者へ知らせる。

### 3.4 キャプションが同じで列が違う表（2026-09-25 決定: 列を統合する）

**実例は既にあります**:
- `顧客の発注書（読んだまま）`——**客先ごとに列が違います**（紙の写しなので）。
- `発注明細`——09-22 までの紙は `色`、09-23 からは `表面`（0a9）。

**案: 列の和集合**——

- **名前で合わせる**（列の順番は問わない）。その表に無い列は **NULL**。
- **型は列の名前から語彙で決まる**ので、**表ごとに型が食い違いません**（登録の列宣言が無くなれば、
  型を決めるのは名前だけ——答え6と答え4の帰結）。
- 1つの表の中で見出しが重なったら、**いまの規則（先勝ち）**。
- ⚠ **代償: 打ち間違えた見出しは、黙って新しい列になります。** そこで運用者に
  **「列の揃っていない表」の一覧**を見せる——キャプションごとに、各列を何ページが使っているか。
  **50枚のうち1枚だけの列**は、打ち間違いの疑いが濃い。

**採らない案**:
- **列の組ごとに別の表**（`受注明細_2`）——見たままでなくなり、引く人が**全部の組を知らないと
  漏れます**。
- **列が合わない表を入れない**——黙って消えます（「書いてあるのに出てこない」）。

### 3.5 コアから表の種類の登録を無くす（答え6）

| コアが持つもの | 拡張が持つもの |
|---|---|
| キャプション → 表、見出し → 列、語彙 → 型、型 → 正規化 | 業務のルール（鏡・ボタン・計算ビュー）を**キャプションで**表を見つけて付ける |

影響:

1. **09-20 の「登録された語彙だけDBに入る」を覆します。** 理由だった「普通の文章の表まで
   入る」は、**キャプションの有無**で解けます（§3.1）。原本の写し（`顧客の発注書（読んだまま）`）も
   入りますが、**名前が違うので弊社の明細の集計と混ざりません**。
2. ⚠ **拡張のコードは機械キー（`client-order-items` 等）で表を探しています**
   （`VocabRowsOfType`・`tablesOfType` など）——**キャプションで探す形へ書き換える**のが
   いちばん大きな作業です。
3. **計算ビュー**（必要部材表・受注残・材料を探す など9つ）は**コードそのもの**なので、
   拡張の登録として残ります。**無くすのは「表の種類」の登録**です。
4. **列の型の宣言が無くなる**——型は見出しの名前と語彙だけで決まります。
   ⚠ **同じ名前で表ごとに型を変えることはできなくなります**（それが「一般的なルール」）。
   登録で決めていた型のうち語彙に無いものは、**語彙へ移す**必要があります。
   ⚠ `enum`（`状態` の許可値）は語彙に**許可値の欄が要る**かもしれません。
5. **データの移行は要りません**——索引は本文から作り直せます（DB再構築）。
6. [【一覧】語彙.md](【一覧】語彙.md) の形式の表は、**拡張のビューだけ**になります。

### 3.6 キャプションの無い表——移植のときに人が名前を付ける（2026-09-25 決定）

利用者:「`■材料` のように節の見出しで名乗る表をどう扱うかは**移植の話**だと思いますが、
**まずDBに入れずにページを移植し、表のタイトルなど必要なものをClaudeに指摘して貰い、
私がそれに返答して移植ページを更新しましょう。その後、管理ページでDBを再構築します。**」

**手順**:

1. **DB に入れずに移植する**——いまの `移行中` タグがそのまま使えます（**在るだけで止める**・
   フェイルクローズ）。⚠ **2026-09-25 に配線しました**——`移行中` のページの表は `data/tables.db` に
   入りません（コアの口 `RegisterTablesExclusion` へ板金の拡張が言葉を渡す・開発方針 §0）。
   それまでの `移行中` は**読む側**（集計）で止めるだけで、縦持ちの索引には入っていました。
2. **Claude が指摘する**——キャプションの無い表、表のタイトルにすべき見出し、揃っていない列の名前。
3. **利用者が返答する**。
4. **移植ページを更新する**（キャプションを付け、`移行中` を外す）。
5. **管理ページで DB を再構築する**（`POST /api/rebuild-db`）。

⚠ **コアは「節の見出しで名乗る表」を知らなくてよくなります**——名前はキャプションに
人が付けるので、解決の②をコアに残す理由が移植から消えます。

⚠ **ただし移植ページだけではありません**（2026-09-25 に実データで確かめた）。
**加工製品のテンプレート**（`テンプレート／加工製品`・データの中のページで、コードではない）は、
表を **`data-type` 属性と節の見出し**で名乗っていて、**キャプションがありません**
（`<section><h2>材料</h2><table data-type="part-materials">`）。キャプションで名乗る形へ
切り替えるときは、**テンプレートと、そこから作ったページ**にも同じ手順（指摘 → 返答 → 更新 →
再構築）が要ります。⚠ **テンプレートは環境ごとのデータ**なので、職場と自宅で別々に直します。

### 3.7 値の持ち方（答え4のとおり）

列には**型ごとに正規化した値**を入れます。型は列の名前から設定の語彙で決まり、無ければ文字列。
いまの正規化で実測した例（2026-09-25）:

| 型 | 書いた値 | DB に入る値 |
|---|---|---|
| text | `ﾚｰｻﾞｰ加工 ＡＢＣ１２３` | `レーザー加工 ABC123` |
| code | `a100 b01 001` / `Ａ１００－Ｂ０１` | `A100B01001` / `A100-B01` |
| number | `¥8,000` | `8000`（数として） |
| date | `2026/10/15` | `2026-10-15` |

- ⚠ **畳めない値は、書いたまま入れます**（例: date の列に `最短納期`）——落とすと「書いてあるのに
  出てこない」。代わりに**日付として並べると日付の後ろへ回ります**（文字として比べられる）。
- **見たままの値の正本は本文HTML**です。DB は検索のための写しです。

### 3.8 日本語以外の言語では（利用者の問い・2026-09-25）

**名前はほぼそのまま動きます**——SQLite は ASCII 以外の文字（中国語・韓国語・アクセント付きの
ラテン文字…）を引用符なしで名前に使えます。NFKC も言語を問わない標準の正規化です。
⚠ 気をつけるのは3つ:

1. **英語は予約語と大小に当たりやすい**——`Order`・`Group`・`Index` のような見出しはよくあります
   （→ §3.1 の予約語の警告）。⚠ **SQLite は ASCII の大文字小文字を区別しません**——同じ表に `Qty` と
   `QTY` の見出しがあると**同じ列**になります（統合の規則 §3.4 に乗せる）。
2. ⚠ **数と日付の読み方は国で違います**——ドイツ語では `1.234,56` が 1234.56、米国では
   `10/15/2026` が月/日/年、欧州では `15/10/2026` が日/月/年。**いまの正規化は日本の書き方**
   （`2026/10/15`・`8,000`）を前提にしています。⚠ **他の国で使うなら、読み方を設定で選べる
   必要があります**（言語・地域の設定を1つ持つ）。
3. **画面・エラーの文言は日本語だけ**です——DB とは別の話ですが、コアを他の言語の人が使うなら
   要ります。
