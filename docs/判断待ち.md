## なぜこの文書があるか

2026-08-20〜21 の[設計総点検](【考察】設計総点検.md)で多数の問題が挙がり、そのうち11件を
エージェントが自動で修正しました。**修正が多すぎて追えない**のと、**一部が設計変更に
踏み込んでいる**ため、判断を書き手（あなた）へ戻すのがこの文書の目的です。

**エージェントが代行してはいけない判断の見分け方**は、実例で示すのが早いです。

> エージェントの推奨: 「`tags` に `{Field:"part-id", Label:"部品番号"}` を宣言すれば改名告知が効く」
> あなたの却下: 「`tags` は自由語。列として宣言すると、部品番号を書かない大多数のページで
> 『無い』と鳴って**全ページ誤検知**になる」

技術的には正しいが、**業務を知らないと出せない判断**でした。以下の項目は、
できるかぎり「〜という実装にしますか」ではなく
「**業務上〜ということはありますか／〜されると困りますか**」の形で聞いています。
技術用語のまま残っている問いがあれば、それは翻訳に失敗しているので指摘してください。

### D-3 索引の形は現行の1テーブル縦持ちを維持するか

推奨: **維持＋`norm_value` の日付対応を追加**（時期・ロットで絞る集計の下地）。
行/フィールドの2テーブル分割（§10未決）は利益が具体化していないので今回も見送り。

**あなたの判断**:
「PDFからの取り込み時に正規化します。表の中で認識できる形式は背景色で示します」（2026-08-30）

> **⚠ 推奨の前提が違っていました**（2026-08-30 実測で判明）。「`norm_value` の日付対応を
> **追加**」と書きましたが、**日付の正規化は既に実装済み**です（`normalizeDate`。
> `2026-06-15`・`2026/6/15`・`2026年6月15日` → `2026-06-15`）。実際に足りないのは3つ:
>
> 1. **日付語の辞書が薄い**——型が date になるのは `納期`・`日付`・`検査日`・`発注日`・`納品日` の
>    **5語だけ**（`typeInference`）。「加工日」「出荷日」は素の文字列扱い。
> 2. **単位込みの数量が読めない**——`5個`・`3500円` は数値にならない（`numberRe` は数字のみ）。
>    ワンノートの購入部品表がまさにこの形。
> 3. **自由文の中の日付は拾えない**——「2026-06-15　富士電装　緑　ロット20　3500」のような行。
>
> なお「1テーブル縦持ちのままか、2テーブルに分けるか」は**業務判断が要らない内部の話**
> なので、エージェント判断で**1テーブル維持**とします（分ける利益が具体化していないため）。

**この回答から読み取った方針**（着手前に確認します）:

- **正規化の主戦場は取り込み時**——PDF から取り込む時点で整った形にする。索引側で
  後から推測して直すのではなく、**入り口で揃える**。
- **認識できたことを背景色で見せる**——表のセルのうち、システムが形式を認識できた値に
  背景色を付ける。いまある赤（型不一致の通知）・黄（列型の明示）の**肯定版**にあたり、
  書き手は「これは読まれている」を見て分かる。
- 帰結として、上の 1・2（辞書と単位）は**索引側で頑張る話ではなくなる**——取り込みと
  背景色で「読める形に直す」ほうへ寄せる。ただし手書きのページには依然として辞書が効くので、
  **辞書を増やすかどうかは残る**（着手時に再度うかがいます）。

### D-4 `page_refs`（参照）はスキーマだけ今決めるか

推奨: **設計だけ確定・実装は通信記録と同時**。`(参照元ページ, 参照先ページ, 種類, ブロックID)`。
起動時の自動再構築があるのでテーブルは後から足せます。

**あなたの判断**:
「ある。いまの設計に入れてほしい」（2026-08-30）

→ **決定: `page_refs` は今回のスキーマ設計に含める**（「設計だけ確定・実装は通信記録と同時」から
格上げ）。記録する線は、設計文書にある2種類を出発点とします:

| 線の種類 | 業務での言い方 | 向き |
|---|---|---|
| **由来** | 「この発注書は、どのメールで届いたか」 | 派生ページ → 通信記録ページ |
| **前版** | 「この図面 Rev.C の1つ前は Rev.B」 | **新版 → 旧版**（後ろ向き。旧版には触らない） |

**前版が後ろ向きなのは意図的**です——前向き（旧版に「次はこれ」と書き足す）にすると、
確定済みの旧版を書き換えることになり、帳票としての不変性が壊れます
（[【考察】通信記録処理.md](【考察】通信記録処理.md) §4.6）。「この版を差し替えた新版はどれか」は
逆引きで出せます。

**着手時に確かめること**: 上の2種類以外に辿りたい線はありますか（例:「この見積もりの元に
なった図面」「この発注書とセットの支給品」など）。**種類は後から足せます**が、最初に
2〜3例あると列の設計が固まります。

### D-6 縦持ち表・ヘッダ無し表の受け皿

ワンノートの工程表（第1列が鍵・497件）と購入部品表（ヘッダ無し2列）を受ける語彙2形式。
スキーマはD-1のEAVが吸収するので**索引の書き込み側だけの話**。移行前のどこかで入れれば

**あなたの判断**:
「何を工程表や部品票と認識していますか？」（2026-08-30）

**ご指摘のとおり、呼び名がずれていました。**「部材表」「工程表」は**調査時にエージェントが
付けた仮の呼び名**で、実データにその言葉はありません。実際の見出しはこうです
（`01 資料/事務用` の「コピペ ノート 各製品用」＝手動テンプレートの節構成）:

```
■不具合 ■参考図 ■図面 ■図面番号 ■データ（CADファイル）
■材料  ■外注加工  ■購入品  ■支給品  ■塗装
■見積もり  ■工程  ■完成品
```

仮の呼び名と、実際の場所の対応:

| 仮の呼び名 | 実際はどこの表か | 件数 | いまの w-cms で読めるか |
|---|---|---|---|
| 部材表 | **■材料** の下の表 | 471件 | **読める**（1行目が見出し） |
| 工程表 | **■見積もり** の下の表 | 497件 | **読めない**（鍵が第1列にある） |
| 購入部品表 | **■購入品** の下の表 | — | **読めない**（見出し行が無い2列） |

**「工程表」という呼び名が特に紛らわしい**ので、以後使いません。これは **■見積もり の下の表**で、
第1列に工程名（ブランク・ドリル・ブレーキ・組み立て…）が並ぶために、そう呼んでしまったものです。
**■工程 は別物**——写真主体の作業手順で、表ではありません。

読めない2つの形は具体的にこうです。

**■見積もり の下の表**（第1列が鍵。`工程|工数|備考` 102件、列側にロットを並べる
`工程|ロット6|ロット7|ロット20|備考` などの変種あり）:

```
工程   | 数 | 単位 | 備考          ← 1行目だが、見出しではない
ロット |    | 個   |               ← 鍵は第1列（この行は「ロット」の行）
材料   |    | 円   |
ブランク・ドリル・ブレーキ・組み立て …
```

**■購入品 の下の表**（見出し行そのものが無い2列）:

```
ウェルドナット…M8 | 5個
```

**D-2（機能見出しを採用する）を決めたので、認識は見出しの言葉で行います**——
「■見積もり の下だから見積もりの表」「■購入品 の下だから購入品の表」。形を機械が推測するのでは
なく、**あなたが書いた見出しが形式を宣言する**、という形です。

**残る判断**: この2形式をいつ入れるか（移行前のどこかで足りる、というのが元の見立てです）。
呼び名の訂正が済んだので、改めて優先度をうかがえればと思います。
