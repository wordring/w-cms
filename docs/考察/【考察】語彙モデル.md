## 1. 背景と目的

2026-08-16 に、前提が変わりました。
語彙が100種の規模になること、一般公開のウェブサイトにも使うこと、の2つです。

この前提変更により、「新しいタグ＝新しいGoプラグイン＝新しいテーブル」という増やし方が、成立しなくなりました。

- 開発者がボトルネックになります。
- 公開ページは、カスタム要素の描画に JS を要します。

本書は、2つの問いに答えます。

1. **マークアップをどう書くか**

   どのデータを属性に置き、どれを要素の中身（テキスト）に置くか、という問いです。
   現行実装は、ほぼ全データを属性に持ち、表示文字は、テンプレートが属性から生成しています。
   これが、contenteditable のぎこちなさ・XSS・生HTMLの読みにくさの原因になっています。
   （「現行実装」は、2026-08-16 の時点の実装です。そのあとの移行は、§8 にあります。）
2. **語彙をどう増やすか**

   100種の規模でも、追加コストと保守が破綻しない、拡張の機構です。

## 2. マークアップの原則

> **役割・参照・内部フラグ → 属性。見える値（自由文も数値も）→ 要素の中身（テキスト）。
> 機械可読性は「構造（表の列＝役割）」で担保し、値を属性に隠さない。**

判断の早道は、次の問いです。

**「その値は文書として画面に出るか？」→ 出るなら中身。出ない配線だけ属性。**

「配線」は、表示されない、機械的なつながりのことです（どのページを指すか、など）。

数量・単価も、人が読み書きし、表示されます。だから、中身です。
標準HTMLの表が「列見出しが役割、セルが値」であるのと、同じです。

| 中身（テキスト・人が読み書き・**表示される**） | 属性（**表示されない**機械的な配線） |
|---|---|
| 発注書番号・客先・発注日、品番・品名・数量・単価・納期・状態（表のセル）、タグの名前と値 | ページID参照（`受信元`・`前版`。**のちに D-4 で見える参照タグへ移した**）、役割マーカー（`data-type`）、内部フラグ |

**そのあとの動き（D-2）**

属性の列に残る**役割マーカー（`data-type`）も、セクションの見出しの言葉（見える文字）へ
移す提案は D-2 として決定・実装済み**です（2026-08-30/31・§11）。

- エディタは、見出し形で挿します。
- 属性に残るのは、参照（名前：値の参照タグ）・`file` 容器の `data-src`・可変タグ `tags`・列型の明示だけになりました。
- `data-type` は、明示の正として、引き続き読みます。

**そのあとの動き（2026-09-26〜29）**

表は、見出し形ではなく、キャプション（`<table><caption>表示名</caption>`）で名乗る形になりました。エディタも、キャプションの形で挿します。
節の見出しで形式を決める読み方は、2026-09-29 にやめました（§11 の「この節のその後」）。

さらに一段進めて、**機械属性も「見える文字で足りるなら書かない」**ことにしました。

> **見える文字がすべて（鍵）。機械属性は型の明示だけ。**

- 列の**鍵** ＝ **見出しテキスト**（trim後の textContent）ただ1つです。
  「鍵」は、その列が何の列かを見分けるための名前です。
  - 機械キーを本文へ書き出す `data-field` は、**2026-08-20 に撤去**しました。鍵の例外は、無くなりました。
  - ③計算形式の機械キーは、レジストリ宣言（`Label`→`Field`）が解決します。だから、本文には現れません。
- 列の**型** ＝ `data-type` があれば、その型です。無ければ、見出し語から推論します（`金額`→通貨 等）。
- 残る例外は、型の明示だけです。
  **発動している箇所は、編集モードでハイライト**します。
  見えている文字から推論した型が使われていないことを、示すためです（§5.1）。

鍵が見える文字そのものになった代わりに、**見出しの改名は③計算の読み取りを止めます**。
黙って止まらないよう、解決できなくなった列は、**保存時に告知**します（§9・拒否ではありません）。

この向きの利点は、5つです。

1. **contenteditable と素直に噛み合う**。
   表のセルを直接編集でき、「入力欄→属性へ書き戻し」の配線が消えます。
2. **XSS が構造的に起きにくい**。
   - 表示文字を、属性→`String.replace` でテンプレートに差す経路が、不要になります。
     この経路は、実際に保存型XSSを生みました。2026-08-04 に、`escapeAttr` の徹底で塞いでいます
     （[コンセプト.md](../旧文書/コンセプト.md) 参照）。
   - **テキストノードは DOM が自動エスケープ**します。
     エスケープの掛け忘れ、という失敗の余地が消えます。
3. **生HTML（正本）が自己説明的**。
   数量も、実テキストとして `data/master` に現れます。grep/diff が効きます。
4. **見た目＝文書**。
   発注書の画面表示が、そのまま PDF の表と一致します。
5. **公開ページで閲覧ゼロJS**（§3）。

## 3. 語彙の3分類

| 種類 | 例 | 増やすときのコスト |
|---|---|---|
| **標準HTML** | 見出し・段落・リスト・表・画像… | 増やさない（コアの許可リストで固定） |
| **マーカー付き標準HTML（記録）** | 繰り返し明細＝`<table data-type="…">`、名前:値＝`<dl data-type="…">` | **語彙レジストリへの宣言1件（データ）** |
| **マーカー付き標準HTML（動的）** | 計算ビュー・ファイル容器・ページ参照（マーカーの具体設計の決着は §10） | 計算プラグイン（Goコード＝③） |

**カスタム要素（Web Components・`<m-*>`）は廃止します（2026-08-17 決定・§9）。**

語彙は、標準HTML＋`data-*` に**完全統一**します。
動的な振る舞いは、次の3つが担います。

- **編集モードの画面の部品**（エディタ）
- **閲覧ビューのエンハンサ**（マーカー要素を見つけて振る舞いを付けるバニラJS）
- **サーバー事前描画**

「バニラJS」は、ライブラリを使わない、素の JavaScript のことです。

理由は、4つです。

- ① 公開ページで**閲覧ゼロJS**になります（計算ビューも、サーバー事前描画で、SEOが自然に解けます）。
  SEO は、検索エンジンに見つけてもらいやすくすることです。
- ② 生HTMLの自己説明性。
- ③ 語彙の増加コストの最小化。
- ④ テンプレート機構（`fetch`＋文字列置換＋`innerHTML`）が消えます。
  **`escapeAttr` の規律に頼るXSS経路と、テンプレートの `style=`（CSP strict 化の最後の障害）が、構造的に消えます。**

現行実装のカスタム要素10種は、移行（§8）で撤去します。
**新しいカスタム要素は今後作りません（即時発効）。**

マーカーは、`class` でなく **`data-*`** にします。理由は、3つです。

- ① サニタイザの `class` 全面拒否
  （[本文サニタイズ設計.md](../旧文書/本文サニタイズ設計.md) §5.4。本文はシェルと同一DOMに合成される）に、
  例外を作りません。
  `data-*` には、`data-id` の前例と、`globalAttributes` の仕組みがあります。
  「シェル」は、画面の枠（本文の外側の部分）のことです。
- ② 見た目のフック（class）と、機械可読の役割（data-*）を分けます。
  デザイン都合の改名が、データ破壊になりません。
- ③ シェルの CSS/JS セレクタと衝突しません。

装飾は、`table[data-type="…"]` の属性セレクタで当てられます。

**用途と要素の使い分け:**

| 用途 | 形 | 例 |
|---|---|---|
| 繰り返し明細（行×列） | `<table data-type="…">`（§5.1） | 受注明細・部材リスト・検査記録 |
| 名前:値の組（ブロック内の単一項目・ページ横断メタ） | `<dl>`（§5.3） | 発注書番号・希望納期・顧客名 |
| ファイルの容器 | 標準HTMLの容器マーカー（`section[data-type="file"]`＋`data-src`。§10） | PDF原本＋中身の業務ブロック |
| 他ページへの参照（表示されない配線） | 参照マーカー（例: `<blockquote data-ref="000123">`。設計は決着・§10） | 案件ハブ・受信元・前版 |
| 〃（実装された形） | **「名前：値」の参照タグ**（`ページID-ブロックID`・型 `ref`）。⚠ `data-ref` は**ファイル表示の配線**として 2026-09-15 に `section` へ実装されたが、この行の「参照マーカー」案とは別物（指すのは添付1つ） | 受信元・対応DXF |
| サーバー計算の表示（保存されない派生） | ビューマーカー＋サーバー事前描画／エンハンサ（§10） | 手配状況リスト・進捗ボード |
| 写真・画像 | 標準HTML `<img>`（語彙ではなく内容） | 現場写真・図版 |

「状態」は、2つの概念を区別します。

- **明細の進捗**（行ごと）は、表のセルです（表示される値＝中身）。
- **ページ状態**（`未確認`/`取消`/`廃版` 等）は、ページ横断メタです（`dl` の名前:値）。

## 4. 語彙と拡張の3層モデル

**「語彙を増やす」と「計算を作る」を別の作業に分離します。**

| 層 | 実体 | 変更する人 | 担うもの |
|---|---|---|---|
| **① 語彙レジストリ** | 宣言データ | 管理者（将来は利用者） | `data-type` 形式の定義: 名前・表示名・分類・アイコン・要素種別（table/dl/section）・列（機械キー `Field`・型・ラベル・許可値）・雛形。語→型の推論辞書（§5.1）もここ**だった**——**辞書は 2026-08-30 に `config/settings.json` へ出ました**（運用者がファイルで増やせるように）。さらに 2026-09-07 に**Goコード内の既定値そのものを無くし**、ファイルが唯一の正本になっています（無ければ起動が止まる）。2026-09-14 には語→型と語→選択肢が `vocabulary` の1件（`{"type": …, "values": [...]}`）に畳まれました |
| **② 汎用索引** | コアのコード（1実装） | — | 全 `table[data-type]`/`dl[data-type]` を汎用テーブルへ同期（`page_tags` の一般化・完全正規化の縦持ち）。検索・単純集計 |
| **③ 計算プラグイン** | Goコード（少数） | 開発者 | 型付きテーブル＋計算ロジック（部材手配・利益・進捗・参照追従）・取り込み変換（PDF/画像→表・`.eml`→通信記録）・集計API・外部投入API |

**この節のその後**

- ①: 形式は、設定からも足せます（`config/settings.json` の `vocab_formats`）。
  この仕組みは、2026-09-20 からコードにあります（`internal/cms/settings.go`・`internal/cms/vocab.go` の `SetSettingsVocabFormats`）。
  いまの形式は37（コア5・拡張32）で、全部がコードの宣言です。設定から足した形式は、ありません。
  （2026-10-19 に `RegisterVocab` の宣言の `DisplayName` を数え直すと、42（コア5・拡張37）です。
  見積表・製造明細表・納品明細表・請求明細表・請求書を作る などが増えました。`config/settings.json` には、いまも `vocab_formats` を書いていません。）
  （2026-10-21 に同じ数え方で数えると、43（コア5・拡張38）です。2026-10-20 に、通信の「記録の箱」が増えました。）
- ②: 索引は、2026-09-13 に2つの表に分かれました。タグは `page_tags`、表と業務ブロックは `vocab_index` です
  （[【考察】タグ表と業務ブロック表の分離.md](【考察】タグ表と業務ブロック表の分離.md) §8）。
- ②: 2026-09-25 から、キャプションのある表を、表の写し（`data/tables.db`）にも入れます
  （[【考察】DBの日本語化.md](【考察】DBの日本語化.md) §7）。
  集計の索引（`vocab_index`）に入るのは、登録された形式だけです（2026-09-20）。表の写しには、キャプションのある表が全部入ります。

- **追加コストの段差**
  - 記録・表示だけの語彙（100種の大半）は、①の宣言1件で足せます。
  - 計算が要る語彙だけが、③の開発案件になります。
  - プラグインは、「1**計算**ユースケース＝1プラグイン」へ意味が狭まります。
    語彙の増殖から、切り離されます。
- **語彙の単一正本**
  - ①のレジストリと、③のプラグイン宣言を合成します。
    計算型の列定義は、読み取り（旧 `Sync()`・現在は観察係の `OnElement`）と同じ宣言から導きます。
  - 合成したものを、単一のAPI（`/api/tag-schema` の拡張）で、エディタと、タグ一覧のドキュメント生成へ届けます。
- **安全性の分離（要）**
  - サニタイザの許可リスト（要素・属性名）は、従来どおり**コードで固定**します。
  - `data-type` は、属性**名**だけを、要素限定（`table`・`dl`・`section`・`th`）で許可します。
    **値は不活性な文字列**として、検査しません。
    そのあと `section` には、`data-src` に加えて、ファイル表示の配線 `data-ref` を 2026-09-15 に、鏡の印 `data-mirror` を 2026-09-27 に許しました。
    正本は `internal/cms/htmldoc/sanitize.go` の許可リストです。
  - レジストリは、編集支援と検証の語彙です。**安全性の門ではありません**。
  - この分離があるから、将来レジストリを実行時編集可能（管理UI・語彙定義ページ）にしても、
    危険な要素は増やせません。
- ②の汎用索引にも、「ファイルから再生成できないデータを持たせない」不変条件
  （[アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) §8.1）を適用します。

## 5. 表と定義リストの設計

### 5.1 自己記述テーブル

**列の役割・型は見出し行が運び、セルは値そのものです。**
文書自身が、スキーマ（列の定義）を携帯します。
だから、レジストリが読めなくても、既存文書の閲覧・編集は壊れません（正本＝ファイルの自立性の表版です）。

**この節のその後**: 下の例は、表を `data-type` 属性で名乗っています。
2026-09-26 から、表はキャプションで名乗ります（`<table><caption>受注明細</caption>`）。
属性の形は、古い本文のために、いまも読みます（`internal/cms/walk.go` の `vocabTypeOf`）。

```html
<!-- 記録だけの形式: 機械属性なし。鍵＝見出しテキスト、型＝見出し語から推論 -->
<table data-type="inspection-record">
  <tr><th>品番</th><th>判定</th><th>検査写真</th><th>検査日</th></tr>
  <tr><td>SHAFT-01</td><td>合格</td><td><img src="p1.jpg" alt=""></td><td>2026-08-10</td></tr>
</table>

<!-- 計算形式（③）: 見出しの表示文字がレジストリ宣言の Label と一致し、機械キーへ解決される -->
<table data-type="client-order-items">
  <tr><th>品番</th><th>数量</th><th>単価</th><th>状態</th></tr>
  <tr><td>SHAFT-01</td><td>10</td><td>8000</td><td>未着手</td></tr>
</table>
```

**鍵**

- 鍵は、**見出しテキスト**ただ1つです。
- 同一表内の見出し重複の保存時警告は、**未実装**です（2026-09-02 確認。`vocab_notify.go` に該当なし）。
- ③計算形式では、見出しの表示文字が、レジストリ宣言の `Label` に一致することで、
  機械キー（`Field`）へ解決されます（`columnFor`）。
- **改名すると解決できなくなり、その列は索引（観察係 `vocab_index.go`）・③計算に読まれません。**
  黙って止まらないよう、保存時に告知します（`UnresolvedVocabFields`）。
- 記録だけの形式は、改名しても壊れません。
  ②汎用索引は、固定スキーマを持たず、自由語彙と同じ扱いだからです。
- 2026-08-20 以前は、`data-field` で、表示ラベルと機械キーを分離していました。
  しかし、鍵の解決が元々 `Label` でも引けたため、冗長でした。
  改名耐性を告知へ移して、撤去しました（§9）。

**型**

- 語→型の推論辞書（`金額`/`単価`→通貨、`数量`→数値、`納期`/`検査日`→日付…）が既定です。
- **辞書の正本は `config/settings.json`** です
  （2026-08-30・[アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) §9.4）。
  運用者がファイルへ語を足して、DB再構築すれば効きます。
  DB再構築は、本文から索引を作り直す操作です。
  Goコード内の並びは既定値です。
  （Goコード内の既定値は、そのあと 2026-09-07 に無くなりました。§4 の表の①）
- `th data-type` の明示と、③のレジストリ宣言が、推論に優先します。
- 推論した型で、次の2つを行います。
  - ① エディタが、入力を**検証して通知**します（通貨列に通貨以外→背景を赤く）。
    **拒否はしません**。自由な記述をシステムが認識する、というコア・コンセプトを壊さないためです。
  - ② 汎用索引が、**正規化値を併記**します（`¥8,000`→`8000`）。
    解釈できた値だけです。生テキストが、常に正本です。
    正規化は、表記の揺れをそろえることです。

**機械属性のハイライト**

- `data-type` 付きの `th`（＝列型の明示）は、編集モードで、背景をハイライトします。
  見えている文字から推論した型が使われていないことを、示すためです（型不一致の赤とは別の色です）。
- 実装は、CSS の属性セレクタ（`th[data-type]`）です。
  上書きを起こす属性自体が、印のトリガーになります。だから、表示と実態がずれません。
- 閲覧・公開ページには出しません。
- 鍵を上書きする属性は撤去したので、ハイライトの対象は型だけになりました。

### 5.2 汎用表エディタ

`data-type` 付きの表・定義リストの編集機能は、**型の数に対して不変の汎用実装**とします。
型ごとの JavaScript は書きません。

- セルの直接編集（contenteditable）・行の追加/削除/並べ替え。
- 列型に応じた入力補助（`number`/`date`/`enum` ドロップダウン/`image`＝セル内への添付画像挿入）。
  v1 は、素のテキストセル＋行操作だけでよく、補助は段階的に足します。
- **編集は2面あります**。
  - 値（中身・表示される）は、**インライン**で編集します。
  - 役割・型・参照（属性・表示されない配線）は、**列設定UI（ポップオーバ）**で編集します。
  - contenteditable はテキストしか触れないため、属性を編集する所は別に要ります。
- どの編集も、既存のオートセーブ（差分検出→`/api/save-block`）に乗せます。
  シリアライザは、編集用の画面の部品を剥がし、クリーンな `<table data-type>`（ヘッダ＋データ行）を残します。
  シリアライザは、画面の本文を、保存用の HTML にする処理です。
- 合計・受注残のような**他セルから計算される表示**は、サーバー側の計算ビュー（③）に寄せます。
  エディタ内のリアクティブ計算は、持ちません（道具の追加を避けるためです。必要になったら再検討します）。

**この節のその後**

- 保存の API は、2026-10-12 から `POST /api/sync` です。ブロックの単位で送ります。
  保存するのは、ブロックを去る・タブを隠す・ページを去るときです。
  `/api/save-block` は、道具のために残っています。画面は使いません。
- 「他セルから計算される表示は、サーバー側に寄せる」は、2026-10-04 に、表のセルの式でも同じ形になりました。
  セルに `=個数*単価` と書けます。計算するのは、サーバーの1か所です（`internal/cms/formula.go`）。
  閲覧モードでは結果を、書ける形では式を見せます
  （[【考察】表の集計の一般化.md](【考察】表の集計の一般化.md) §4.5 の追記）。

### 5.3 定義リスト（名前:値）

ページ横断メタと、ブロック内の単一項目は、`<dl>` で表します。

```html
<dl data-type="tags">
  <dt>希望納期</dt><dd>2026-07-10</dd>
  <dt>納入場所</dt><dd>本社工場</dd><dd>第二倉庫</dd>  <!-- 多値 -->
</dl>
```

- 名前も値も、**表示される実テキスト**です。
  - 名前は自由語（スキーマキーではない）なので、`dt` の表示文字＝鍵でよいです。
  - 多値は、`dt` の繰り返し／複数 `dd` で表します（`page_tags` が主キーを持たない現行設計と整合します）。
    主キーは、行を1つに決めるための列です。
  - （可変タグの多値は、そのあと 2026-08-26 に「タグ1つ＝名前1つ＋値1つ」と決まりました。§9 の決定ログの「可変タグは名前：値の1対」の行）
  - （`page_tags` は、2026-09-13 に作り直して、主キー `(page_id, seq)` を持つようになりました。同じ名前のタグを繰り返せることは、変わりません。）
- 素の `<dl>`（用語集など通常の文章）と区別するため、索引へ同期するのは、`data-type` 付きだけです
  （オプトイン。表と同じ規約）。
  オプトインは、書いた人が印を付けたものだけを対象にすることです。
- 役割が固定の dl（受発注ヘッダ等の③計算形式）も、§5.1 と同じ規則です。
  **鍵は `dt` の表示文字**で、レジストリ宣言の `Label` を通じて、機械キーへ解決されます
  （2026-08-20 決定。当初は `<dd data-field="order-no">` の自動付与を見込んでいましたが、撤去しました）。
- **表示されない配線**（`受信元`・`前版` 等）は、dl へ移せない、と当時は考えていました
  （[【考察】通信記録処理.md](【考察】通信記録処理.md) §9.1 と合流）。
  **のちに D-4 で決着**しました。
  名前も値も見える**参照タグ**にして dl へ載せ、描画時にリンクへ合成します。

経路は、プロデューサー（作り手）の違いにすぎません。

## 7. エディタの形式知識の3原則

1. **新規挿入時**: 列定義の全体が要ります。
   レジストリから、API経由で受け取ります（エディタに、手書きの形式リストを置きません）。
   骨格は、列定義から機械的に生成します。
2. **既存ブロックの編集時**: **レジストリ不要**です。
   鍵と型は、文書自身（見出し行・§5.1）が運びます。
   だから、レジストリが読めなくても、既存文書の編集は壊れません。
3. **入力補助・検証**: レジストリがあれば向上します（enum の選択肢・解決できない見出しへの告知）。
   無くても、編集は可能です。

エディタの実装は、汎用表エディタ1つ（§5.2）で、**型の数に対して不変**です。

- 型ごとの JavaScript が要るのは、③の特殊UI（PDFドロップ・集計表示・参照ピッカー）だけです。
  これらも、**カスタム要素ではなくエンハンサ**（マーカー要素に配線するバニラJS）として実装します（§9）。
- DOM生成が要る箇所は、画面の枠に置いた `<template>` ＋ `cloneNode` ＋ `textContent` 代入で行います
  （DOMが自動エスケープします）。
  文字列置換＋`innerHTML` のテンプレート機構は、持ち込みません。
- 実装は、`createElement`＋`textContent` に落ち着きました。
  画面の枠に `<template>` は置いていません（[エディタ仕様.md](../旧文書/エディタ仕様.md) §0）。
- **追加のライブラリは不要**です
  （必要な基盤は `querySelectorAll`・`addEventListener`・既存の `MutationObserver`・`<template>`）。

## 10. 未決事項（全件決着済み）

### 11.1 機能見出し——`data-type` の言葉を見える場所へ

**セクションの最初の見出し（直接の子である最初の h1〜h6）が、そのセクションの機能を表します。**
日付・企業名などのヘッダ項目は、専用の解析をやめ、汎用の「名前：値」タグで持ちます。

```html
<section>
  <h2>受注</h2>                     <!-- 見える言葉が機能 -->
  <dl data-type="tags">
    <dt>受注日</dt><dd>2026-08-25</dd>
    <dt>発注元</dt><dd>南北スポーツ</dd>
  </dl>
  <table>…明細…</table>
</section>
```

これは、コンセプト §1②「ページの役割は置き場所と名前で決まる」の、**ブロックへの再帰**です。

- ページ＝階層とタイトル
- セクション＝入れ子と見出し
- 項目＝th/dt の表示文字

全階層が、同じ規則になります。
本文に残る機械語は、`data-id`（保存の単位）と、タグの容れ物だけに近づきます。

実データとの整合が、強いです。

- ワンノートの加工製品ページは、「`■材料`・`■購入品` という**見出しの下に表**」という構造そのものです
  （[【考察】ワンノート移行.md](【考察】ワンノート移行.md) §2.5）。
- 移行時は、「■見出しから次の■見出しまでをセクションで包む」だけです。
- **現場が既に書いている言葉が、そのまま機能の宣言になります**。

先行した caption 案（`<table><caption>受注</caption>`）は、この案に包含されます。
caption は `<table>` 専用で、`dl`／`section` に付きません。だから、主役にはなれません。
しかし、1セクションに表が複数あるときの**副ラベル**として、残します。

### 11.2 二種類の計算——「種まき」と「鏡」

> ⚠ **2026-09-25: 種まき型の実装（テンプレートの新規化）は撤去しました。**
> テンプレートは、純粋なコピーです（[【考察】ページテンプレート.md](【考察】ページテンプレート.md) §9）。
> 以下は、当時の設計です。

「見出しの言葉が計算を呼ぶ」場所には、**2つの型**があります（2026-08-25 利用者の指摘）。
どちらも、w-cms に**実装済みの先例**があります。
提案は新発明ではなく、既存2機構の一般化になります。

| 型 | ふるまい | 既存の実物 | 正本との関係 |
|---|---|---|---|
| **種まき型** | **最初の一度だけ**データから生成し、以後は人間が書き加える | テンプレート新規化 `FreshenTemplateBody`（[template_new.go](../../internal/cms/template_new.go)。日付・発注書番号を埋める。`FreshenTemplateBody` は 2026-09-25 に消え、いまの template_new.go は写すだけ） | 生成物は**本文として保存され**、人間の持ち物になる |
| **鏡型** | **見るたびに最新**の集計を映す | 計算ビュー `RenderComputedViews`（[view_render.go](../../internal/cms/view_render.go)。子ページ一覧・必要部材） | **正本へ書き戻さない**（`.vocab-chrome`・保存されるのは空マーカー） |

安全規則も、型で分かれます。

- 鏡型は、編集で触れなくします（a案・作業引き継ぎ「自動集計の表を触れなくする」）。
- 種まき型は、生成後、ふつうに編集できます。

語彙の宣言には、**どちらの型か**を書く欄が要ります。

**2026-09-14 の補足: 鏡型は「中身を所有する」ものばかりではありません。**

- 上の行（空マーカー・触れなくする）は、**計算ビュー**（レジストリの `View: true`）の話です。
- 同じ鏡型の段には、**人が書いた中身を残して枠だけ足す**担当も居ます。
  - `section[data-type="file-view"]`（[file_view.go](../../internal/cms/file_view.go)）
  - 図面の赤枠・廃版行（`class` を足すだけ。[drawing_mirror.go](../../ext/toho/drawing_mirror.go)）。
    赤枠は、この補足より前の 2026-09-06 に要らなくなっていました（改定の旧版は、最新版の子ページへ移るため）。いま残るのは、廃版の行を薄く見せる鏡だけです（同じファイルの冒頭の注）。
- こちらは、**中身が正本に保存され、ふつうに編集できます**（足された枠だけが `.vocab-chrome` です）。
- 一覧は、[アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) §4.4 にあります。

**2026-09-15 の補足**

- `file-view` の中身は、**ふつう空**になりました。
  配線が属性 `data-ref` へ移り、中に書くものが無くなったためです。
- 鏡型でいる理由も、入れ替わっています。
  いまは、「計算ビューが**要素を見ずページIDだけで描く**ので、要素ごとに違う参照を読めない」からです。
- 人が説明の段落を添えれば、それは今も消されません。

⚠ **2026-09-27 に変わりました**

- ファイル表示の中には、**短縮ファイル名の名札**を保存します。
  表示では、中身を消して、閉じられる枠で描きます。

  > 利用者:「保存時は `<section data-type="file-view" data-ref="…">短縮ファイル名</section>` としておいて、表示するときに消せば良いのでは？」

- いまは、説明の段落を中に添えても、表示では消えます。添えるなら、印の前後に書きます。

**2つの型は合成できる**（2026-08-26 の問答から）

テンプレート（種まき）に、鏡型のマーカーを置けば、そこから作られる全ページが、
**ボタンなしで常に最新**のビューを持ちます。

- 例: 加工製品ページのテンプレートへ、「最新価格」「価格推移」の鏡を置く。
- かなめ商会の「最新価格を表示」ボタンは、先方の計算コスト対策です。
  データが手元にある w-cms では、**押す操作そのものが不要**です。
- なお、本文へのボタンは置けません。
  サニタイザが、`button`/`form`/`input` を、偽装防止で拒否するためです。

**鏡の引き金も機能見出しで書く**（2026-08-26 利用者の提案。§11.1 の規則を計算ビューへも適用）

```html
<section>
  <h2>最新価格</h2>   <!-- この言葉が鏡を呼ぶ。data-type は書かない -->
</section>
```

- `data-type` の空セクションは、機能が未登録だと、**無の空白**になります。
- 機能見出しなら、**「最新価格」という見出しを持つただのセクション**に留まります。
  壊れ方まで見えます。
  エコーバックの流儀と同じ性質が、マークアップの構造から出ます。
  エコーバックの流儀は、書かれたものを拒否せずに受け入れて、気づいたことを知らせる、という進め方です。
- 見出しを書き換えれば、鏡は止まります。なぜ止まったかも、画面から読めます。
  テンプレート置き場の改名と同じ、受け入れ済みのリスクの形です。
  §11.5 の5は、利用者自身のこの提案により、**受け入れの方向**です。

**2026-09-27 午後の注記**

鏡の引き金は、いま見出しではなく、`<section data-mirror="最新価格"></section>` です。
値は、鏡の表示名です。

> 利用者:「もう少しわかりやすいシングルタグに出来ないでしょうか」「閉じタグがあっても良いです」

登録されていない名前は、描かれません。保存時の告知と、編集モード（いまの書ける形）の薄赤で知らせます。

2026-10-20 からは、拡張の機能も同じ印で描きます。通信記録の本文の `<section data-mirror="記録の箱"></section>` に、サーバーが ✉️ 返信・整理・🤖 解析・前後を描きます（`ext/comm/record_box.go`）。

ボタンが意味を持つのは、「**いまの値を記録として本文へ固定する**」とき（人間の意思による種まき）だけです。
その住処は、本文ではなく、**エディタの画面の部品**です。

**第3の型: 窓型（集計に書き込む）**

> 2026-08-26 利用者:「集計された表にユーザーが書き込む場合もあります。材料を発注した、製造が完了した、納品した、請求したなどの状態です。いつ納品なども個別に書くかもしれません」

まず、動かせない原則があります。
**DBはファイルから作り直せる派生なので、集計表は状態の持ち主になれません。**
書かれた状態は、必ず、どこかの文書に着地する必要があります。
現に、発注明細の `状態` 列は、ソースの表のセルとして、文書に住んでいます。
手配状況リストは、それを映しているだけです。

したがって、「集計表に書く」の実体は、**窓**です。

- 読みは、鏡と同じ集計です。
- 書きは、**由来のソースページの該当セルへの遠隔編集**として、通常の保存経路を通します。
  編集ロック・権限・サニタイズ・索引洗い替え・監査が、全部ただで付きます。
  （2026-10-12 から、画面は編集ロックを取りません。本文はページごとの書き込みのロックの中で書きます。§6 の「この節のその後」。）
  由来は、汎用索引が既に持つ `page_id`/`block_id`/`row_no`/`field` で引けます。

「いつ納品」のような個別の書き込みの置き場は、2案あります。スキーマ設計し直しの論点です。

- ソースの行に、列を足す。
- 納品記録のページに積む。
  こちらは、ワンノート現運用と、通信記録処理の納品レコードの方向です。

段階付けは、次のとおりです。

- v1=現状どおり、ソースページで編集します。鏡は触れません（a案）。
- v2=窓型で、a案が「状態セルだけ触れる」へ精密化します。

**鏡の更新はブラウザの再読み込みで行う**（2026-08-26 確認。現行の割り切りを維持）

- 鏡の古さの上限は、「開きっぱなしの時間」です。
  実測の業務許容（35日遅れ）に対して、十分小さいです。
- 画面の部品に更新ボタンを置くと、描画済みビューを返す新しい取得の API と、部分更新（隣の表は古いまま）を抱え込みます。
  その割に、F5 ひとつ分しか節約しません。
- 再検討の条件は、「**開きっぱなしで参照し続ける画面**」が生まれたときです
  （例: 工場のモニタに手配状況を常時表示）。
  そのときは、人が押さないので、定期リロードが要ります。

### 11.3 語彙の可搬性——「私の使い方」をコアに焼き込まない

> 2026-08-25 利用者:「問題は、ここまでの考察は私の使い方であって、ほかのユーザーはそうとは限らないことです。つまりプラグインのような機構が必要に思います」

ここまでの語彙（材料・購入品・外注加工・受注…）は、**この事業所の使い方**です。
w-cms の一部ではありません。

**2026-08-26 に要件へ格上げされました。**
「プラグインを様々な企業やサイト運営者が自分で設置すること」を、要件に含めます
（[【要求】w-cmsとは.md](../【要求】w-cmsとは.md) §1「特定用途向けに拡張できる」）。

> 利用者:「利用者は私のみではありません」

したがって、次のように分けます。

- **コアが持つのは機構だけ**です。
  - 「機能見出しのあるセクション」「名前：値のタグ」「表の行」を、索引へ写す汎用の仕組み。
  - 見出しの言葉に、（索引の形・種まき/鏡の計算・入力の骨格）を結びつける、**宣言する仕組み**。
- **言葉と結びつきはレジストリ／プラグインの持ち物**です。
  - `Plugin` インターフェース（[plugin.go](../../internal/cms/plugin.go)）と、
    語彙レジストリ（[vocab.go](../../internal/cms/vocab.go)）が、既にこの分担です。
  - §9「レジストリの置き場」の育成路線（Goコード内 → 管理DB → 語彙定義ページ）を、そのまま進めます。
  - 機能見出しの言葉→ふるまいの表は、その段階に応じて、置き場が変わるだけです。
- 板金部の語彙一式は、**既定の同梱セット（またはサイト設定）**になります。

### 11.4 実行モデル——コアが歩き、プラグインに回覧する

> **2026-08-25 に実装可能な粒度の設計へ詳細化しました。正本は
> [パーサとプラグイン.md](../旧文書/パーサとプラグイン.md)** です。
> そちらは、機能見出しの決定を待たずに実装できるよう、引き金の解決を、差し替え可能な1点に隔離してあります。
> 本節は、提案時の記録として残します。

> 2026-08-25 利用者:「パーサーがHTMLを成形するとき、タグを見つけるたびに登録されたプラグインを順番に呼び出すのはどうですか？プラグインは自分に関係あるタグなら書き換えて返します」

**コアが木を1回歩き、ノードごとに登録済みプラグインへ回します。担当なら、書き換えて返します。**

「木」は、HTML を読み込んで、要素の親子関係の形にしたものです。
「歩く」「走査」は、その木の要素を、順にたどることです。

提案した時点の実装は、逆でした。
各プラグインが、`Sync(tx, pageID, root)` で木を丸ごと受け取り、**自前で走査**していました。
走査が方々に散っているから、「新しい走査コードはクローム除外・テンプレート領域除外を忘れるな」という罠が
存在します（[作業引き継ぎ.md](../作業引き継ぎ.md) の勘所）。
**歩く責任をコアの1箇所へ集めれば、除外規則も1箇所で済み、この罠が構造ごと消えます。**

手すり3本を、提案の一部とします。「手すり」は、踏み外さないための決まりのことです。

1. **文字列ではなくノードで受け渡す**
   - プラグインがHTML文字列を返す設計は、「サニタイズ後にHTMLを足す関数が各自エスケープ責任を負う」
     現状の危うさを、プラグインの数だけ増殖させます。
   - `x/net/html` のノードを返す形なら、**`html.Render` がテキストも属性値も自動エスケープします**
     （2026-08-25 に検証済み: テキスト・属性に `<script>…" onmouseover="…` を入れて Render →
     すべて実体参照化された）。
   - クライアントの「`createElement`＋`textContent`」規律のサーバー版が、構造的に成立します。
   - **プラグインAPIに生HTML文字列を入れないこと。**
2. **サニタイザは回覧の鎖に入れない**
   - 安全化は、プラグインで拡張・変更できてはいけません。
   - 順序は、**サニタイズ→回覧**で固定します。
   - 書き換え結果は、**再回覧しません**（元の木だけを歩きます）。
     プラグイン出力が別のプラグインを起動する無限ループも、同時に消えます。
   - サニタイザの冪等性と、同じ流儀です。
3. **「順番」を意味にしない**
   - 登録順の早い者勝ちは、見えない結合を生みます。
   - §9「`data-type` はレジストリ全体で一意」と同じく、
     **機能の言葉→書き換え係は一意**（回覧ではなく表引き）とします。
   - 順番が要らないのは、**観察するだけ**の係（索引・監査）です。
     こちらは、何人購読しても衝突しません。

| 役割 | 多重度 | 例 |
|---|---|---|
| **書き換え係**（言葉ごとに1人・表引き） | 一意 | 鏡型（必要部材を描く）・種まき型（日付・番号を埋める） |
| **観察係**（全ノード回覧） | 何人でも | 汎用索引・タグ索引・（将来）監査 |

**APIの形はイベントハンドラ型（プッシュ型）とします。パーサーは既存の `x/net/html` のまま変えません**
（2026-08-25 利用者の確認）。

つまり、SAX over DOM です。
SAX は、文書を読みながら、出来事（イベント）を順に知らせる方式の名前です。
DOM は、文書を木の形で持つ方式の名前です。

- 木は、今までどおり作ります。
- コアの配送係が、木を文書順に歩きながら、「要素の開始・テキスト・要素の終了」をイベントとして、
  ハンドラへ押し込みます。
- プラグインは、走査コードを一切持ちません。イベントを受けるだけになります。

```go
// 素描（確定形ではない）
type VocabHandler interface {
    StartElement(ctx *WalkContext, el *html.Node) // ctx がセクションのスタックと
    Text(ctx *WalkContext, t *html.Node)          // 「いまの機能の言葉」を運ぶ。
    EndElement(ctx *WalkContext, el *html.Node)   // 差し替えは ctx.Replace(el, nodes...)
}
```

この形の要点は、**除外が「規約」から「観測できない事実」へ変わる**ことです。

- 配送係は、`.vocab-chrome` の中・テンプレート領域・差し替え済みの部分木の
  **イベントをそもそも発火しません**。
- 各プラグインが、除外を「覚えている」必要が消えます。

純粋なストリーミングにしない理由は、2つです。

- アンカー合成のような全体参照と、鏡型の部分木差し替えが、木の上でないと素直に書けないため。
- ページは高々数百KBで、メモリ利益も効かないため。

**コンテキストはサーバー資源の運び手でもあります。**

> 2026-08-25 利用者:「プラグインはデータベースのハンドルを知っている必要がありそうです。サイドカーから情報を引き出すなども必要かもしれません。それらはサーバーがもつ情報なので、プラグインの引数としてコンテキストを渡す必要がある」

「コンテキスト」は、呼び出すときに一緒に渡す、周りの情報のまとまりです。
「サイドカー」は、本文の横に置く、ページの属性のファイルです。

既存3機構が受け取っている資源が、そのまま、最小セットの証拠になっています。

| 段 | いま受け取っている資源 | コンテキストが渡す権能（最小権限） |
|---|---|---|
| 観察係（保存時） | `tx *sql.Tx`・pageID | **書き込みトランザクション**（自分の索引テーブルへの洗い替え）・ページの素性 |
| 鏡型（表示時） | `auth.CurrentUser(r)`・pageID | **読み取り専用のDB**と**閲覧者の身元**（権限での見せ分け＝C案がここで効く）。**書く力は渡さない** |
| 種まき型（新規作成時） | 新ページID・時計 | 読み取り専用のDB・新ページの素性・時計 |

設計の芯は、**1つの太ったコンテキストにしない**ことです。

- 段ごとに型を分ければ、「鏡型が正本やDBへ書く」という事故が、**コンパイル時に不可能**になります。
  この事故は、サイドカー自動修復で、一度踏みました。派生→正本の逆流です
  （[変更履歴アーカイブ.md](../変更履歴アーカイブ.md) 2026-08-22 の2番）。
- サイドカーの読み出しも、生のファイルパスではなく、コンテキストのAPIで渡します。
  読めないときは、黙って補完せず、エラーを返します
  （A-7 の決定「自動で治さない」を、APIの意味論として固定します）。
- このコンテキストの型は、**プラグインとの契約（ABI）そのもの**です。
  §11.3 の可搬性のためにも、最小から始めて、意図的にしか広げないこと。

歩く機会は、3つあります。同じ機構が、段の指定だけ変えて使えます。
**既存3経路の一般化**であって、新発明ではありません。

```
保存時:   サニタイズ → 回覧(観察係)             ← 今の SyncIndex（各自走査を置き換え）
表示時:   本文読込 → 回覧(鏡型) → アンカー合成   ← 今の RenderComputedViews
新規作成: テンプレ読込 → 回覧(種まき型)          ← 今の FreshenTemplateBody
```

（図の「今の」は、2026-08-25 の名前です。保存時と表示時の2つは、いまもあります。
新規作成の種まきは、2026-09-25 に撤去しました。テンプレートは、純粋なコピーです。§11.2 の頭を見てください。）

現在の計算ビューが持つ早道（`strings.Contains` でマーカーが無ければパースしない）は、
「登録済みの言葉が本文に無ければ歩かない」の形で残します。

### 11.5 決めるべきこと（スキーマ設計し直しと一緒に）

   機能見出しの言葉は、レジストリの表示名を正とします
