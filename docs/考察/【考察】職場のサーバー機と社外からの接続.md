職場に w-cms 専用のサーバー機を立て、社外の VPS を通してインターネットから使えるようにする構成を考えた文書です。

>
> 2026-10-15 利用者:「〈会社のドメイン〉の下に作ろうと思います。DNSは〈DNS の会社〉です。VPSは〈VPS の会社〉で借ります。ルーターは〈NTT のホームゲートウェイ〉 の機能を使っています。サーバー機はUbuntuで運用します（まだ入れていません）」

> 2026-10-15 利用者:「WevDAVは続けません。コードも文書も削除します」

2026-10-15 に、WebDAV はやめました。CAD の編集は「📝 ローカル編集」です。
この文書の WebDAV の話は、決めたときの記録として残します。

〈 〉で伏せた名前は、会社を特定できるので、公開のリポジトリに書きません。
実際の名前と、構築の日に確かめることは、デスクトップの `w-cms\サーバー機\構成メモ.txt` にあります。

公開の形そのもの（VPS のリバースプロキシ・WebDAV は出さない・split-horizon DNS）は、2026-09-07 に決まっています。
正本は [【考察】社外公開とHTTPSの構成.md](【考察】社外公開とHTTPSの構成.md) です。

**この文書の結論**（くわしくは各節）

- サーバー機は **Ubuntu** で動かします。
  w-cms は Linux 向けにそのまま組み立てられ、職場のデータもそのまま移せます（2026-10-15 に確かめた・§2）。
- w-cms は **systemd**（Ubuntu で常駐のプログラムを動かす仕組み）で動かします。
  電源を入れれば、誰もサインインしなくても動き、落ちても起こし直されます（§2.2）。
- サーバー機の上に、**本番**と**試験用**の2つの w-cms を動かします。データの場所とポート（待ち受けの番号）を分けます（§4）。
- VPS とサーバー機は **WireGuard** でつなぎます。サーバー機から外へ張るので、職場のルータに受信の穴を開けません（§3）。
- 証明書は、**VPS で取ってサーバー機へ写す**形を勧めます。DNS の会社に書き換えの APIが無くても使えるためです（§3.3）。
- 社内からの繋ぎ方は、ルータの機能しだいで3つの道があります。構築の1日目に、ルータの画面で確かめます（§3.4）。
- 外に出す前に、**`a`/`a` のパスワード**と **Secure Cookie** を必ず直します（§5）。

**先に、言葉の説明**

| 言葉 | 意味 |
|---|---|
| サーバー機 | w-cms を動かし続けるための、専用の機械です |
| Ubuntu | Linux の1つです。サーバーによく使われます |
| systemd | Ubuntu で、常駐のプログラムを起動・見張り・起こし直しする仕組みです |
| VPS | インターネットの上に借りる、自分専用のサーバーです。公開の住所（IP）を持ちます |
| リバースプロキシ | 外から来た要求を受け取り、奥にある本物のサーバーへ中継する役です。VPS がこれをします |
| WireGuard | 2台の機械のあいだに、暗号化した専用の通り道（トンネル）を作る道具です |
| ドメイン・ホスト名 | `wcms.example.jp` のような、インターネットの上の名前です |
| Let's Encrypt | 無料で公的な証明書を出す認証局です。証明書は90日ごとに更新します |

| 本番・試験用 | 本番は実運用のデータで動く w-cms、試験用は E2E や試しに使う、別のデータの w-cms です |

## 1. なぜ方針を変えるか

これまでは、開発用の PC（職場の HP405）の上で、会話の子として w-cms を動かしていました。家では、別のデータで開発していました。
そこから、次の問題が出ていました。

- **サーバーが会話や PC の都合で止まる。** 2026-10-15 夜、会話が作り直されたとき、職場のサーバーが一緒に止まりました。
- **家と職場でデータが違う。** 家で同じことを確かめるのに、サンプルのデータを作る手間がかかります（作り方は【ガイド】家のサンプルデータ）。
- **家から本物を見られない。** 職場のデータを確かめたいとき、家からは届きません。
- **開発と実運用が同じ PC にある。** 試験や入れ替えのたびに、実運用の画面へ影響が出ないか気を配る必要があります。

サーバー機を立てて社外から届くようにすると、**本物は1か所に、どこからでも同じものを見る**形になります。

## 2. サーバー機（Ubuntu）

### 2.1 Ubuntu で動くか（2026-10-15 に確かめたこと）

- **w-cms は Linux 向けにそのまま組み立てられます**（`GOOS=linux go build`）。
  Windows だけの仕組みを使うコードはありません。
- **職場のデータは、そのまま移せます。**
  本文・ページの属性のファイル・添付の目録に、Windows の書き方の道（`\` で区切ったもの）は入っていません。
  ファイル名の日本語は、Linux でもそのまま使えます。
- ⚠ **紙（PDF）の書体の場所だけ、直しが要ります。**
  - 設定 `pdf_font` は `C:/Windows/Fonts/BIZ-UDGothicB.ttc` を指しています。
    設定のファイルは全部の環境で1つなので、Ubuntu の場所を書けません。
  - 候補の場所を並べて「在るものを使う」形に直します（小さな変更・東邦拡張の設定）。
    2026-10-19 に直しました（§5）。
  - 書体は、Windows の `BIZ-UDGothicB.ttc` をサーバー機へ写すか、Ubuntu の BIZ UD ゴシックの包み（`.ttf`）を入れます。
    w-cms は `.ttf` も読めます。
- 試験の `go test -race` も、Ubuntu なら gcc をすぐ入れられます（いまは職場の PC でしか流せません）。

### 2.2 機械の準備

| 項目 | すること | なぜ |
|---|---|---|
| Ubuntu | サーバー版の長期サポート版（LTS）。画面は無くてよい | 更新が長く続く。余計なものが少ない |
| 電源 | 停電から戻ったら自動で電源が入る設定（BIOS）。可能なら UPS（停電のときに数分もたせる電池） | 止まると誰も使えない。停電の瞬断で SQLite が壊れるのを避ける |
| 更新 | 自動の安全更新を入れる。再起動の要る更新は、夜に人が再起動する | 業務中の再起動を避ける |
| 住所 | ルータで、社内の住所（例 `192.168.1.10`）を固定で配る | split-horizon DNS とトンネルが、この住所を指す |
| 利用者 | w-cms を動かす専用の利用者（例 `wcms`）を作る。人は SSH の鍵で入る | w-cms に要らない権限を持たせない |
| ディスク | ディスクの暗号化（入れるときに選べる） | 機械ごと持ち出されても、図面と取引のデータを読ませない |
| 壁 | ufw（Ubuntu の受信の壁）で、社内とトンネルからの 8443・SSH だけを通す | 社内の別の機械からも、要らないポートに触らせない |
| 道具 | Git・Go・Node.js（E2E を流すなら）・mupdf（`mupdf-tools`） | サーバー機の上で、取ってきて組み立てる形にする（§6） |
| 時計 | 時刻を自動で合わせる（入れたときから有効のはず） | 監査記録・版の時刻がずれない |

### 2.3 w-cms をどう動かし続けるか

**systemd に、本番と試験用の2つの単位（サービス）を登録します。**

- 電源を入れれば動きます。誰もサインインしなくてよいです。
- 落ちたら、自動で起こし直します（`Restart=always`）。
- 秘密の設定（Gemini のキー・メールのアプリの登録）は、`/etc/w-cms/w-cms.env` に置きます。
  持ち主だけが読める権限にします（`chmod 600`）。
  中身は、いまの `w-cms.env` と同じです。⚠ チャットやリポジトリには書きません。
- ログは systemd の日誌（`journalctl -u w-cms`）に残ります。大きさは自動で回ります。
- メールのサインインの保管（`data/mail/`）の権限 0600 が、Linux では効きます（Windows では効かなかった）。

⚠ **画面のロック・サインアウト・会話を閉じる、では止まらない**形になります。
止まるのは、サーバー機の電源・再起動・サービスを止めたときだけです。

### 2.4 いまの PC からの引っ越し

本番のデータを、いまの PC（HP405・Windows）からサーバー機へ移します。止める時間は短くできます。

1. サーバー機で、試験用のデータを使って動くところまで確かめる（§7 の1日目）。
2. 業務の止まる時間を決め、利用者に伝える。
3. いまの PC の w-cms を止める。止まったのを確かめる。
4. `data\` のうち、`master\`・`trash\`・`auth.db`・`mail\` を、サーバー機の `data/` へ写す（約5.4GB・約2万ファイル）。
   - `cms.db`・`tables.db` は写さずに、サーバー機で作り直します（DB 再構築）。
     本文から作れるもので、作り直せば確実です。
   - `auth.db` は、止めてから写します。動いているあいだは書かれるためです。
   - メールのサインイン（`mail\`）は、そのまま使えます。
     サインインはアプリの登録に結び付いていて、機械には結び付いていません。
   - 証明書（`tls\`）は写しません。サーバー機は、新しい名前の公的な証明書を使います（§3.3）。
5. サーバー機で本番を起こし、DB を作り直し、職場の PC から開けることを確かめる。
6. いまの PC の w-cms は、起こさないようにしておく（2つの本番が同時に動くと、データが分かれる）。

あわせて、次のものを付け替えます。

- 各 PC とスマホのブックマーク（新しいホスト名へ）。
- 「📝 ローカル編集」のヘルパー（`w-cms-edit.exe -install <新しいアドレス>`）。登録はアドレスごとです。

## 3. VPS と、サーバー機とのつなぎ方

### 3.1 形

```
スマホ・社外のPC ──▶ VPS（公開の住所・証明書・Caddy か nginx）
                         │  WireGuard（サーバー機から張る）
                         ▼
社内のPC ─────────▶ サーバー機（Ubuntu・w-cms 本番 :8443／試験用 :9443）
              （§3.4 の道で、社内は直に）
```

- トンネルは**サーバー機から VPS へ**張ります。職場のルータに、受信の穴を開けません。
  これが、09-07 に決めた理由そのものです。
- VPS は、受け取った要求を、トンネルの中のサーバー機の住所（例 `10.8.0.2:8443`）へ中継するだけです。
  データは VPS に置きません。
- WireGuard の「キープアライブ」を入れます（25秒ごと）。
  サーバー機がルータの内側にいても、トンネルが切れないようにするためです。
- 試験用（:9443）は VPS から中継しません。社内とトンネルの中からだけ使います。

### 3.2 VPS の準備

| 項目 | すること |
|---|---|
| 大きさ | いちばん小さいもので足ります（中継だけ） |
| OS | Ubuntu の長期サポート版（サーバー機と揃える） |
| 入口 | 受けるのは 80・443（HTTPS と証明書の確認）と、WireGuard のポート（UDP）だけ。SSH は鍵だけで入れる。〈VPS の会社〉の画面の「受信の壁」でも同じに絞る |
| 更新 | 自動の安全更新を入れる |
| 中継の道具 | **Caddy** を勧めます。証明書の取得と更新を自分でするので、手が少ない。nginx でもかまいません |

中継の道具に要る設定です。09-07 に決めたものに、2026-10-15 にコードで確かめたことを足しました。

- 09-07 に決めた「`/dav/` は 404」は、要らなくなりました。2026-10-15 に WebDAV をやめ、`/dav/` の入口はもうありません。
- 受け取る大きさの上限を 64MB にします。
  nginx の既定は 1MB で、添付が通りません。w-cms の上限は 32MiB です。Caddy は、既定で上限がありません。
- ログインの画面（`/login`）に、回数制限を付けます（総当たりへの備え）。
- ⚠ **Host の見出しをそのまま渡します**（Caddy は既定でそうする。nginx なら `proxy_set_header Host $host`）。
  w-cms は、書き込みの要求の `Origin` と `Host` が同じかを確かめます（CSRF の守り）。
  中継が Host を書き換えると、**保存も押すボタンも全部断られます**。
- `X-Forwarded-For` を付けます。
  w-cms は、社内の住所から来た中継を信頼して、本当の接続元を監査記録に残します。トンネルの住所は、社内の住所の扱いです。
- ⚠ **長くつなぎっぱなしの要求は、ためずに流します**（nginx なら `proxy_buffering off`。Caddy は既定でそうする）。
  ほかの人の書き込みの通知（`/api/page-events`）は、つなぎっぱなしで届く形（SSE）です。
  2026-10-15 に書いたときは、編集ロックの通知も SSE でした。サーバーの API は残っていますが、2026-10-12 から画面は使っていません（2026-10-21 に `assets/app.js` で確かめました）。
  ためると、通知が遅れたり届かなかったりします。
- 待ち時間を長めにします（例 300秒）。PDF を作る・🤖 解析・メールの読み込みは、数十秒かかることがあります。
- 中継の先（サーバー機の w-cms）は HTTPS です。サーバー機の証明書の名前（公開の名前）で確かめるように設定します。

### 3.3 名前と証明書

名前は〈会社のドメイン〉の下に1つ作ります（例 `wcms.〈会社のドメイン〉`）。
〈DNS の会社〉の画面で、その名前を VPS の住所へ向けます。

証明書は、外の入口（VPS）と、社内からの入口（サーバー機）の両方に要ります。
社内でも同じ名前で繋ぐためです（§3.4）。
取り方は3つあります。

| | A. VPS で取って、サーバー機へ写す（勧め） | B. DNS の書き換えで、それぞれが取る | B'. 確かめの記録だけ別の DNS に預ける |
|---|---|---|---|
| 仕組み | VPS が Let's Encrypt から取り（HTTP の確かめ）、更新のたびにトンネル越しにサーバー機へ写す | サーバー機も VPS も、〈DNS の会社〉の書き換えの APIで、自分で取る | 確かめに使う記録（`_acme-challenge`）だけを、書き換えの APIのある DNS（〈VPS の会社〉の DNS など）へ向ける |
| 要るもの | 写す仕掛け（更新のたびに動く小さな道具・SSH の鍵） | 〈DNS の会社〉に書き換えの APIがあり、証明書の道具がそれを使えること | 書き換えの APIのある DNS を1つ |
| 良い点 | DNS の会社を選ばない | 配る仕掛けが要らない | 〈DNS の会社〉に API が無くても、配る仕掛けが要らない |

**A を勧めます。**
2026-10-15 に調べた範囲では、よく使われる証明書の道具（lego・acme.sh）に、〈DNS の会社〉の API は見当たりませんでした。
A なら、どの DNS の会社でも動きます。
Ubuntu どうしなので、写す仕掛け（`rsync` か `scp` と、更新のときに動く一行）も素直です。

**2026-10-15 の時点の w-cms は、証明書を起動のときに1回だけ読みました。**

- そのままでは、90日ごと（更新は60日ごと）に、写したあとで起こし直すことになります。
- 起こし直しは数秒で済みますが、通知のつなぎ（SSE）は一度切れます（画面は自分で繋ぎ直します）。
- 証明書のファイルが替わったら読み直す形に直すのは、小さな変更です（コアの `cmd/w-cms`）。構築の中で直すことにしました。
- 2026-10-19 に直しました（§5 の「証明書の読み直し」）。

### 3.4 社内からの繋ぎ方

09-07 に決めたのは、split-horizon DNS です（社内で引くとサーバー機の社内の住所、社外で引くと VPS）。
〈NTT のホームゲートウェイ〉に、社内だけの名前を登録する機能があるかは、調べた範囲では分かりませんでした。
構築の1日目に、ルータの画面で確かめます。

確かめた結果で、3つの道に分かれます。

| | 1. ルータに名前を登録 | 2. サーバー機に DNS を立てる | 3. 社内も VPS を通る |
|---|---|---|---|
| 条件 | ルータに静的な名前の登録がある | ルータの DHCP（住所を配る機能）で、配る DNS を指定できる | 何も要らない |
| 仕組み | ルータの名前の表に、`wcms.…` → サーバー機の住所 | サーバー機に小さな DNS（dnsmasq）を立て、`wcms.…` だけ社内の住所を答え、ほかは上へ回す。ルータが配る DNS をサーバー機にする | 社内も公開の名前を引き、VPS を通って入る |
| 速さ | 直に・速い | 直に・速い | インターネットを往復する（添付の上げ下げが少し遅い） |
| 弱い所 | なし | サーバー機が止まると、社内の名前引きが全部止まる（上の DNS へ回す設定を、ルータの側にも残す） | インターネットか VPS が止まると、社内からも使えない |

**1 が使えれば 1、だめなら 2、2 もだめなら 3** の順を勧めます。3 で始めて、あとから 1 か 2 に替えることもできます。

## 4. 本番と試験用を分ける

サーバー機の上に、w-cms を2つ動かします。

| | 本番 | 試験用 |
|---|---|---|
| データの場所 | `data/` | `data-test/`（`WCMS_DATA_DIR`） |
| ポート | 8443 | 例 9443（`WCMS_ADDR`） |
| 外から | VPS 経由で公開 | 公開しない（社内とトンネルの中だけ） |
| 中身 | 実運用 | 本番の写し、またはサンプル（【ガイド】家のサンプルデータ） |
| 使う人 | 利用者 | 開発（E2E・試し・新しいビルドの確かめ） |

- `WCMS_ADDR`・`WCMS_DATA_DIR` は 10-14 から使えます。
  2026-10-15 に、職場の PC で別のポートと別のデータの w-cms を立てて、E2E を流して確かめました。
- ⚠ **E2E は試験用だけに流します。** 本番では流しません（いまの「職場は実運用」の決まりのまま）。
- 試験用の管理者は `a`/`a` のままでよいです（外に出さないので）。本番の `a` は直します（§5）。

## 5. 外に出す前に直すこと

| 項目 | いま | 直すこと |
|---|---|---|
| 管理者 `a` のパスワード | `a`/`a` | 長いものに替えるか、別の管理者を作って `a` を無効にする。⚠ 無効にする前に、別の管理者で入れるのを確かめる（10-02 に誰も入れなくなった） |
| Secure Cookie | なし（`WCMS_SECURE_COOKIES=0`） | あり。HTTPS だけで動かすので、外してよい |
| 利用者ごとのパスワード | 利用者が決めたもの | 外から入れるようになるので、短いものは長くしてもらう |
| 総当たり | 締め出しとバックオフあり | VPS の回数制限を足す。監査記録（ログインの失敗）を見る習慣 |
| 公開ページ | 0件 | そのまま。`public` を立てると本当に世界に見える |
| 証明書の読み直し | ✅ 2026-10-19 から、ファイルが替わったら次の接続から読み直す（`cmd/w-cms/cert_reload.go`・見るのは多くても10秒に1回・組が合わないあいだは古いもの） | 済み |

あわせて、次のことも知っておきます。

- **リポジトリは公開です**（GitHub）。誰でもコードを読めます。
  秘密はリポジトリに入れない決まり（`w-cms.env` はデスクトップ）を守っていれば、困ることはありません。
  公開の名前は、リポジトリに書きません（〈会社のドメイン〉と伏せる）。
- 外から入れるようになると、**スマホを落とした・PC を置き忘れた**が、そのまま入口になります。
  セッションは、最後の操作から8時間で切れます。
- 二段階の確かめ（パスワードのほかにもう1つ）は、いまはありません。要るかは、使い始めてから決めます。

## 6. 開発と入れ替えの流れ

**サーバー機の上で、リポジトリを取ってきて組み立てる**形を勧めます。

```
開発の PC（職場・家）── git push ──▶ GitHub
                                         │ git pull
サーバー機 ── go build ──▶ 試験用で確かめる ──▶ 本番を入れ替える（systemctl restart）
```

- w-cms は、画面のファイル（`assets/` と、拡張の `ext/<拡張>/assets/`）と設定（`config/`）を、動いている場所のディスクから読みます。
  実行ファイルだけを写すと、画面のファイルと食い違います。リポジトリごと持っていれば、取ってくるだけで揃います。
- 入れ替えは、決まった手順を1本の道具（シェルの小さな台本）にします。手順は次のとおりです。
  取ってくる → 組み立てる → 試験用を起こし直して確かめる → 本番を起こし直す → 起動の時刻と実行ファイルの時刻を突き合わせる。
  いまは手で同じことをしていて、取り違えの前例があります（作業引き継ぎの罠）。
- 開発の PC から入れ替えるときは、SSH でサーバー機に入って、その道具を動かします。
  家からは、VPS を通ってサーバー機へ入る道（SSH・鍵だけ・トンネルの中）を足せばできます。
  初めは、職場からだけにすることを勧めます。
- Claude Code の会話は、開発の PC の上で動きます。サーバー機の本番を、会話の子として動かすことはなくなります。

## 7. 構築の順番（案）

1日に1段のつもりで書きました。前の段が確かめられてから、次へ進みます。

| 段 | すること | 確かめること |
|---|---|---|
| 1 | Ubuntu を入れて準備する（§2.2）。ルータの画面で §3.4 と固定の住所を確かめる。リポジトリを取って組み立て、**試験用**（写したデータ）を systemd で動かす（§2.3） | 再起動しても、誰も入らずに w-cms が動く。社内の PC から住所で開ける（このときは自己署名の証明書でよい） |
| 2 | VPS を借りて準備する。WireGuard でつなぐ。名前を VPS へ向け、証明書を取る。中継の設定（§3.2） | 社外（スマホのモバイル回線）から、**試験用**が開ける。保存・ボタン・通知・添付の上げ下げが動く |
| 3 | 証明書をサーバー機へ写す（§3.3）。社内からの繋ぎ方（§3.4）。w-cms の直し（§5） | 社内の PC とスマホ（社内 Wi-Fi）が、名前で繋がる。外からも同じ名前で繋がる |
| 4 | 本番の引っ越し（§2.4）。各 PC の付け替え | 業務の流れ（受注・部材発注・見積）が、社内と社外の両方で通る |
| 5 | 控え（バックアップ）と見張り（§7.1） | 控えから戻せることを、試験用で1回確かめる |

**最初に試験用を外へ出す**のは、本番のデータを外へ出す前に、中継の設定の間違い（Host・大きさ・通知）を見つけるためです。

### 7.1 控えと見張り

- **控え**: 夜に1回、`data/master`（本文・添付・版）と `data/auth.db`（利用者）と `data/mail` を、別のディスクへ写します。
  - `cms.db`・`tables.db` は本文から作り直せるので、控えは要りません（DB 再構築）。
  - ⚠ `auth.db` は、動いているあいだも書かれます。そのまま写すと、壊れた写しになることがあります。
    SQLite の「バックアップ」の形（`sqlite3 … ".backup …"`）で写します。
  - できれば、もう1つ別の場所（社外）にも置きます。
- **見張り**: VPS から1分ごとにログインの画面を見に行き、返ってこなければ知らせます（メールなど）。
  トンネルが切れたときも、ここで分かります。

## 9. いまの仕組みで変わること

- 「職場のサーバーを会話の子として動かす」形は、やめます（§2.3）。会話を閉じても、本番は止まりません。
- 作業引き継ぎの「サーバーを入れ替えるとき」の手順は、§6 の道具に置き換わります。
- 【ガイド】家のサンプルデータは、家の開発用として残します。本番を家から見るだけなら、要りません。
- 自己署名の証明書（`-gencert`）と、各 PC での「信頼する」作業は、公的な証明書に移ると要らなくなります。
- 「📝 ローカル編集」の登録は、新しい名前で付け直します。
- サーバーの OS が Windows から Ubuntu に替わります。
  作業引き継ぎの罠のうち、Windows のもの（PowerShell・`taskkill`・`.ps1` の BOM など）は、サーバー機では当たりません（開発の PC では当たります）。
