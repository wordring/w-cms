# 【考察】職場のサーバー機と社外からの接続

職場に w-cms 専用のサーバー機を立て、社外の VPS を通してインターネットから使えるようにする構成を考えた文書です。
2026-10-16 から構築を始めます。

> 2026-10-15 利用者:「問題が多いようなので方針を変えます
> 職場にサーバー機を立ち上げ、社外のvpsを通してインターネット上からアクセスできる構成にします
> 明日より構築を始めるので考察をお願いします」

公開の形そのもの（VPS のリバースプロキシ・WebDAV は出さない・split-horizon DNS）は、2026-09-07 に決まっています。
正本は [【考察】社外公開とHTTPSの構成.md](【考察】社外公開とHTTPSの構成.md) です。この文書は、その決定を**実際に建てる手順と、決めることの一覧**にします。

**この文書の結論**（くわしくは各節）

- サーバー機は、09-17 に買った HP のワークステーション（Windows 11）を使います（§2）。
- w-cms は**サインインしなくても動く形**（タスク スケジューラの「起動時」）で動かします。会話（Claude Code）や画面のロックに左右されなくなります（§2.2）。
- サーバー機の上に、**本番**と**試験用**の2つの w-cms を動かします。データの場所と口（ポート）を分けます（§4）。
- VPS とサーバー機は **WireGuard** でつなぎます。サーバー機から外へ張るので、職場のルータに受信の穴を開けません（§3）。
- 外に出す前に、**`a`/`a` のパスワード**と **Secure Cookie** を必ず直します（§5）。
- 決めてほしいことは §8 にまとめました。

**先に、言葉の説明**

| 言葉 | 意味 |
|---|---|
| サーバー機 | w-cms を動かし続けるための、専用のパソコンです |
| VPS | インターネットの上に借りる、自分専用のサーバーです。公開の住所（IP）を持ちます |
| リバースプロキシ | 外から来た要求を受け取り、奥にある本物のサーバーへ中継する役です。VPS がこれをします |
| WireGuard | 2台の機械のあいだに、暗号化した専用の通り道（トンネル）を作る道具です |
| ドメイン・ホスト名 | `wcms.example.co.jp` のような、インターネットの上の名前です |
| Let's Encrypt | 無料で公的な証明書を出す認証局です。証明書は90日ごとに更新します |
| split-horizon DNS | 同じ名前を、社内で引くとサーバー機の社内の住所、社外で引くと VPS の住所に答えさせる仕組みです |
| 本番・試験用 | 本番は実運用のデータで動く w-cms、試験用は E2E や試しに使う、別のデータの w-cms です |

## 1. なぜ方針を変えるか

これまでは、開発用の PC（職場の HP405）の上で、会話の子として w-cms を動かしていました。家では、別のデータで開発していました。
そこから、次の問題が出ていました。

- **サーバーが会話や PC の都合で止まる。** 2026-10-15 夜、会話が作り直されたとき、職場のサーバーが一緒に止まりました。
- **家と職場でデータが違う。** 家で同じことを確かめるのに、サンプルのデータを作る手間がかかります（作り方は【ガイド】家のサンプルデータ）。
- **家から本物を見られない。** 職場のデータを確かめたいとき、家からは届きません。
- **開発と実運用が同じ PC にある。** 試験や入れ替えのたびに、実運用の画面へ影響が出ないか気を配る必要があります。

サーバー機を立てて社外から届くようにすると、**本物は1か所に、どこからでも同じものを見る**形になります。

## 2. サーバー機

### 2.1 機械の準備

| 項目 | すること | なぜ |
|---|---|---|
| 電源 | スリープ・休止を「なし」。可能なら UPS（停電のときに数分もたせる電池） | 止まると誰も使えない。停電の瞬断で SQLite が壊れるのを避ける |
| Windows Update | 「アクティブ時間」を業務時間にする。再起動は夜にまとめる | 業務中の自動再起動を避ける |
| 住所 | ルータで、社内の住所（例 `192.168.x.10`）を固定で配る | split-horizon DNS とトンネルが、この住所を指す |
| 名前 | PC の名前を分かりやすく（例 `WCMS-SV`） | 社内で探しやすい |
| 利用者 | w-cms を動かす専用の Windows の利用者を1つ作る | 人の利用者のサインイン・サインアウトに左右されない |
| ディスク | BitLocker（ディスクの暗号化）を入れる | 機械ごと持ち出されても、図面と取引のデータを読ませない |
| ウイルス対策 | Defender はそのまま。速さが気になれば `data\` を除外に足す | 初期化のときに「掴まれていて」失敗した前例がある（作業引き継ぎの罠） |
| 道具 | Git・Go・Node.js（E2E を流すなら）・mupdf | サーバー機の上で、取ってきて組み立てる形にする（§6） |
| 文字 | 紙（PDF）の書体 `BIZ-UDGothicB.ttc` があるか確かめる | 設定 `pdf_font` が `C:/Windows/Fonts/` を指している。Windows 11 には入っているはず |

### 2.2 w-cms をどう動かし続けるか

**タスク スケジューラに登録して、「コンピューターの起動時」に動かす**形を勧めます。

- 「ユーザーがログオンしているかどうかにかかわらず実行する」にします。サインインしなくても動きます。
- 「タスクが失敗した場合の再起動」を入れます（例: 1分おきに3回）。
- 動かす利用者は、§2.1 の専用の利用者です。
- 新しい外部の部品は要りません（Windows のサービスにする方法もありますが、Go の追加の部品か、別の道具が要ります）。

ログは、標準出力と標準エラーをファイルへ流します。大きくなるので、日ごとに切り替えるか、起動のたびに古いものを退けます。

⚠ **画面のロック・サインアウト・会話を閉じる、では止まらない**形になります。止まるのは、サーバー機の電源・再起動・タスクを止めたときだけです。

### 2.3 いまの PC からの引っ越し

本番のデータを、いまの PC（HP405）からサーバー機へ移します。止める時間は短くできます。

1. サーバー機で、試験用のデータを使って動くところまで確かめる（§4・§7 の1日目）。
2. 業務の止まる時間を決め、利用者に伝える。
3. いまの PC の w-cms を止める。止まったのを確かめる。
4. `data\` を丸ごとサーバー機へ写す（約5.4GB・約2万ファイル）。
   - メールのサインイン（`data\mail\`）はそのまま使えます。サインインはアプリの登録に結び付いていて、機械には結び付いていません。
   - 証明書（`data\tls\`）は、§3 で公的な証明書に替えるまでのあいだ、写したものを使います。
5. サーバー機で本番を起こし、職場の PC から開けることを確かめる。
6. いまの PC の w-cms は、起こさないようにしておく（2つの本番が同時に動くと、データが分かれる）。

あわせて、次のものを付け替えます。

- 各 PC のブックマーク（新しいホスト名へ）。
- 「📝 ローカル編集」のヘルパー（`w-cms-edit.exe -install <新しいアドレス>`）。登録はアドレスごとです。
- WebDAV のドライブの割り当て（`Z:`）。

## 3. VPS と、サーバー機とのつなぎ方

### 3.1 形

```
スマホ・社外のPC ──▶ VPS（公開の住所・証明書・nginx か Caddy）
                         │  WireGuard（サーバー機から張る）
                         ▼
社内のPC ─────────▶ サーバー機（w-cms 本番 :8443・WebDAV は社内だけ）
              （split-horizon DNS で、社内は直に）
```

- トンネルは**サーバー機から VPS へ**張ります。職場のルータに、受信の穴を開けません（09-07 に決めた理由そのものです）。
- VPS は、受け取った要求を、トンネルの中のサーバー機の住所（例 `10.8.0.2:8443`）へ中継するだけです。データは VPS に置きません。
- WireGuard の「キープアライブ」を入れます（25秒ごと）。サーバー機がルータの内側にいても、トンネルが切れないようにするためです。

### 3.2 VPS の準備

| 項目 | すること |
|---|---|
| 借りる先 | 国内の VPS（月数百円〜千円台の小さいもので足ります。中継だけなので） |
| OS | Ubuntu の長期サポート版 |
| 入口 | 受けるのは 80・443（HTTPS と証明書の確認）と、WireGuard の口（UDP）だけ。SSH は鍵だけで入れ、できれば決まった場所からだけ |
| 更新 | 自動の安全更新を入れる |
| 中継の道具 | **nginx** か **Caddy**。Caddy は証明書の取得と更新を自分でするので、手が少ない |

中継の道具に要る設定（09-07 に決めたものに、今回分かったことを足しました）:

- `/dav/` は 404（WebDAV は公開しない）。アプリ自身も、中継されてきた `/dav/` を断ります（実装済み）。
- 受け取る大きさの上限を 64MB に（nginx の既定は 1MB で、添付が通らない。w-cms の上限は 32MiB）。
- ログインの口に回数制限（総当たりへの備え）。
- ⚠ **Host の見出しをそのまま渡す**（nginx なら `proxy_set_header Host $host`）。
  w-cms は、書き込みの要求の `Origin` と `Host` が同じかを確かめます（CSRF の守り）。中継が Host を書き換えると、**保存も押すボタンも全部断られます**。
- `X-Forwarded-For` を付ける。w-cms は、社内の住所から来た中継を信頼して、本当の接続元を監査記録に残します（トンネルの住所は社内の住所の扱いです）。
- ⚠ **長くつなぎっぱなしの口は、ためずに流す**（nginx なら `proxy_buffering off`）。
  ほかの人の書き込みの知らせと、編集ロックの知らせは、つなぎっぱなしで届く形（SSE）です。ためると、知らせが遅れたり届かなかったりします。
- 待ち時間を長めに（例 300秒）。PDF を作る・🤖 解析・メールの読み込みは、数十秒かかることがあります。

### 3.3 名前と証明書

**ドメイン**が要ります。会社のドメインの下に名前を1つ作るのが自然です（例 `wcms.<会社のドメイン>`）。

証明書は、外の入口（VPS）と、社内からの入口（サーバー機）の両方に要ります。社内でも同じ名前で繋ぐためです（split-horizon DNS）。
取り方は2つあります。

| | A. VPS で取って、サーバー機へ配る | B. それぞれが DNS で取る（DNS-01） |
|---|---|---|
| 仕組み | VPS が Let's Encrypt から取り、更新のたびにトンネル越しにサーバー機へ写す | サーバー機も VPS も、DNS の設定を書き換える口で、自分で取る |
| 要るもの | 写す仕掛け（更新のたびに動く小さな道具） | DNS を預けている会社が、書き換えの口（API）を持っていること |
| 良い点 | DNS の会社を選ばない | 配る仕掛けが要らない。互いに依存しない |

どちらでも、**w-cms が証明書を読み直す**手当てが要ります。
⚠ いまの w-cms は、証明書を起動のときに1回だけ読みます。90日ごとの更新のたびに、起こし直すことになります。
証明書のファイルが替わったら読み直す形に直すのは、小さな変更です（コアの `cmd/w-cms`）。構築の中で直します。

### 3.4 社内からの接続（split-horizon DNS）

09-07 に決めたとおり、必須です。

- ルータの「ローカル DNS」（社内だけの名前の表）に、`wcms.<会社のドメイン>` → サーバー機の社内の住所、を書きます。
- ルータにこの機能が無ければ、社内の DNS を別に立てることになります（§8 で確かめます）。
- これで、社内の PC とスマホ（社内の Wi-Fi）は直にサーバー機へ、社外は VPS へ繋がります。同じ名前・同じ証明書です。
- WebDAV（CAD の編集）は、社内からだけ使えます。

## 4. 本番と試験用を分ける

サーバー機の上に、w-cms を2つ動かします。

| | 本番 | 試験用 |
|---|---|---|
| データの場所 | `data\` | `data-test\`（`WCMS_DATA_DIR`） |
| 口 | 8443 | 例 9443（`WCMS_ADDR`） |
| 外から | VPS 経由で公開 | 公開しない（社内とトンネルの中だけ） |
| 中身 | 実運用 | 本番の写し、またはサンプル（【ガイド】家のサンプルデータ） |
| 使う人 | 利用者 | 開発（E2E・試し・新しいビルドの確かめ） |

- `WCMS_ADDR`・`WCMS_DATA_DIR` は 10-14 から使えます。2026-10-15 に、職場の PC で別の口と別のデータの w-cms を立てて、E2E を流して確かめました。
- ⚠ **E2E は試験用だけに流します。** 本番では流しません（いまの「職場は実運用」の決まりのまま）。
- 試験用の管理者は `a`/`a` のままでよいです（外に出さないので）。本番の `a` は直します（§5）。

## 5. 外に出す前に w-cms で直すこと

| 項目 | いま | 直すこと |
|---|---|---|
| 管理者 `a` のパスワード | `a`/`a` | 長いものに替えるか、別の管理者を作って `a` を無効にする。⚠ 無効にする前に、別の管理者で入れるのを確かめる（10-02 に誰も入れなくなった） |
| Secure Cookie | なし（`WCMS_SECURE_COOKIES=0`） | あり。HTTPS だけで動かすので、外してよい |
| 利用者ごとのパスワード | 利用者が決めたもの | 外から入れるようになるので、短いものは長くしてもらう |
| 総当たり | 締め出しとバックオフあり | VPS の回数制限を足す。監査記録（ログインの失敗）を見る習慣 |
| 公開ページ | 0件 | そのまま。`public` を立てると本当に世界に見える |
| 証明書の読み直し | 起動のときだけ | ファイルが替わったら読み直す（§3.3） |

あわせて、次のことも知っておきます。

- **リポジトリは公開です**（GitHub）。誰でもコードを読めます。秘密はリポジトリに入れない決まり（`w-cms.env` はデスクトップ）を守っていれば、困ることはありません。
- 外から入れるようになると、**スマホを落とした・PC を置き忘れた**が、そのまま入口になります。セッションは最後の操作から8時間で切れます。
- 二段階の確かめ（パスワードのほかにもう1つ）は、いまはありません。要るかは、使い始めてから決めます。

## 6. 開発と入れ替えの流れ

**サーバー機の上で、リポジトリを取ってきて組み立てる**形を勧めます。

```
開発の PC（職場・家）── git push ──▶ GitHub
                                         │ git pull
サーバー機 ── go build ──▶ 試験用で確かめる ──▶ 本番を入れ替える
```

- w-cms は、画面のファイル（`assets\`）と設定（`config\`）を、動いている場所のディスクから読みます。
  実行ファイルだけを写すと、画面のファイルと食い違います。リポジトリごと持っていれば、取ってくるだけで揃います。
- 入れ替えは、決まった手順を1本の道具にします（取ってくる → 組み立てる → 試験用で確かめる → 本番を止める → 消えたのを待つ → 写す → 起こす → 起動の時刻と実行ファイルの時刻を突き合わせる）。
  いまは手で同じことをしていて、取り違えの前例があります（作業引き継ぎの罠）。
- 家からの入れ替えは、初めは**しない**ことを勧めます。家は開発と、本番を利用者として見ることだけにします。
  家から入れ替えたくなったら、VPS を通ってサーバー機へ入る道（SSH・鍵だけ）を足します。

## 7. 構築の順番（案）

1日に1段のつもりで書きました。前の段が確かめられてから、次へ進みます。

| 段 | すること | 確かめること |
|---|---|---|
| 1 | サーバー機の準備（§2.1）。リポジトリを取って組み立て、**試験用**（写したデータ）で動かす。タスク スケジューラに登録する（§2.2） | 再起動しても、サインインせずに w-cms が動く。社内の PC から開ける |
| 2 | ドメインと VPS を用意する。WireGuard でつなぐ。証明書を取る。中継の設定（§3.2） | 社外（スマホのモバイル回線）から、**試験用**が開ける。保存・ボタン・知らせが動く |
| 3 | split-horizon DNS（§3.4）。証明書をサーバー機へ（§3.3）。w-cms の直し（§5） | 社内の PC とスマホ（社内 Wi-Fi）が、名前で直に繋がる。外からも同じ名前で繋がる |
| 4 | 本番の引っ越し（§2.3）。各 PC の付け替え | 業務の流れ（受注・部材発注・見積）が、社内と社外の両方で通る |
| 5 | 控え（バックアップ）と見張り（§7.1） | 控えから戻せることを、試験用で1回確かめる |

**最初に試験用を外へ出す**のは、本番のデータを外へ出す前に、中継の設定の間違い（Host・大きさ・知らせ）を見つけるためです。

### 7.1 控えと見張り

- **控え**: 夜に1回、`data\master`（本文・添付・版）と `data\auth.db`（利用者）と `data\mail`・`data\tls` を、別のディスクへ写します。
  `cms.db`・`tables.db` は本文から作り直せるので、控えは要りません（DB 再構築）。
  ⚠ `auth.db` は動いているあいだも書かれるので、そのまま写すと壊れた写しになることがあります。SQLite の「バックアップ」の形で写します。
  できれば、もう1つ別の場所（社外）にも置きます。
- **見張り**: VPS から1分ごとにログインの画面を見に行き、返ってこなければ知らせます（メールなど）。

## 8. 決めること・確かめること

構築の前と、段の途中で要るものです。筆者の勧めを添えました。

| # | こと | 勧め |
|---|---|---|
| 1 | **ホスト名**（会社のドメインの下か、新しく取るか）と、DNS を預けている会社 | 会社のドメインの下に `wcms` など。DNS の会社が書き換えの口を持っていれば、証明書は §3.3 の B |
| 2 | **VPS を借りる先**と予算 | 国内の小さい VPS（中継だけ） |
| 3 | 職場のルータの機種（ローカル DNS があるか・社内の住所を固定で配れるか） | 無ければ、社内の DNS をサーバー機に置く |
| 4 | サーバー機の Windows の版（Pro か） | Pro なら BitLocker とリモートデスクトップが使える |
| 5 | 社外から使う人と端末（誰が・スマホか PC か） | 利用者ごとにパスワードを見直してもらう |
| 6 | 本番を止めてよい時間（引っ越しの日） | 業務の後か、休みの日 |
| 7 | 控えを置く場所（別のディスク・社外） | 社内の別のディスクと、社外の1か所 |
| 8 | FAX（モデム）をいつ足すか | 本番が落ち着いてから |
| 9 | 家での開発の形（サンプルのデータで開発するか、本番を見るだけにするか） | 開発はサンプルか試験用、本番は利用者として見るだけ |

## 9. いまの仕組みで変わること

- 「職場のサーバーを会話の子として動かす」形は、やめます（§2.2）。会話を閉じても、本番は止まりません。
- 作業引き継ぎの「サーバーを入れ替えるとき」の手順は、§6 の道具に置き換わります。
- 【ガイド】家のサンプルデータは、家の開発用として残します。本番を家から見るだけなら、要りません。
- 自己署名の証明書（`-gencert`）と、各 PC での「信頼する」作業は、公的な証明書に移ると要らなくなります。
- 「📝 ローカル編集」の登録・WebDAV のドライブは、新しい名前で付け直します。
