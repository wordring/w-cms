## 0. 総評

**壊れているものが1つ、作りの穴が2つ、UXの粗が4つ。安全上の問題は出なかった。**

安全に関わる次の3つは、8観点すべてが「問題なし」で一致しました。

- **エスケープ**（HTML に値を差し込むとき、記号を無害な形に直すこと）。
  `fileViewInnerHTML` が差し込む値の全部と、`analyze_pdf.go` の書き出しを見ました。
- **サニタイザの許可**（サニタイザは、本文から危ない要素や属性を落とす仕組みです）。
  `data-ref` を許すのは `section` だけです。`vocabulary_test.go` がそれを固定しています。
- **匿名経路**（ログインしていない人が通る道）。
  `RenderComputedViews` は、`/api/load` とページ描画の両方で走ります。
  `page.CanView(nil, id)` が `EffectivePublic` へ落ちます。

壊れていたものと穴は、次のような性質のものでした。

- 壊れていたのは、**その日に足した分岐**です。既存の仕組みとの突き合わせを怠っていました。
- 穴は、**同じ壊れ方を別の経路で残した**ものです。

どちらも、試験を通り抜けていました。通り抜けた形は、次の2つです。

- 「試験が HTML の文字列しか見ていない」
- 「E2E が保存APIで正しい形を直接書いていて、人の通る経路を通っていない」

## 1. 教訓

1. **「開ける」と宣言する前に、配信側が何を返すかを見る。**
   - 表示の表（`fileViewKinds`）と配信の表（`setAttachmentHeaders`）は、別々にあります。
   - 片方だけ増やすと、「描けると言って描けない」ができます。
   - **表は配信側に1つ**が筋です。描画は配信の帰結であって、独立した判断ではありません。
2. **届きようのないファイルのための分岐を書かない。**
   - `.txt` は、添付として保存できる拡張子にありません。
   - 「将来のため」の枝は、試験もE2Eも通れません。だから、**壊れていても分かりません**。
3. **同じ壊れ方は経路ごとに潰す。**
   - スラッシュメニューを直しても、見出し形で打つ経路が残っていました。
   - 「気づきにくい壊れ方」と書いた当人が、半分だけ直して満足していました。
4. **試験は「文字列が出た」ではなく「ブラウザで見えた」まで見る。**
   - `TestFileViewOpensAnyKind` は、`<embed` の有無しか見ていませんでした。
   - そのため、配信ヘッダとの矛盾を通しました。
5. **URLを組む場所を増やさない。**
   - 「URLは派生だから本文に書かない」と決めた同じ日に、`page.AttachmentURLFor` を迂回していました。
   - 迂回して書いていたのは `"/" + pageID + "/" + n` です。
6. **浮くパネルは、小さいものに付ける。**
   - section 全体の矩形に付けると、中身が大きい日に、画面外へ開きます。
   - リンクの欄が `<a>` に付いているのは、偶然ではありません。
