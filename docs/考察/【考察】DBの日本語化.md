**この文書でよく使う言葉**

| 言葉 | 意味 |
|---|---|
| キャプション | 表の題です（HTML の `<caption>`） |
| 索引 | 本文のタグと表を、検索と集計のために写した DB の表です。本文が正本で、索引は本文から作り直せます（これを「派生」と呼びます） |
| 縦持ち | 表の1つのセルを、DB の1行として持つ形です（1セル＝1行）。いまの `vocab_index` がこの形です |
| 表の写し | キャプションごとに作る、新しい DB（`data/tables.db`）の表です。本文の表と同じ形（1行＝表の1行）です |
| 形式（表の種類） | 「受注明細」「材料」のような、表やタグの種類です。プログラムの中では、機械キー（`client-order-items` のような英字の名前）で区別してきました |
| 登録（レジストリ） | 形式を、Go のコードで登録しておく仕組みです（`cms.RegisterVocab`） |
| 語彙 | 設定ファイル（`config/settings.json`）に書く、語（列の名前）と型の辞書です |
| 型 | 値の種類です。`text`（文字）・`code`（品番のような番号）・`number`（数）・`date`（日付）・`enum`（決まった選択肢から選ぶ）などがあります |
| 正規化（畳む） | 表記の揺れをそろえることです（全角と半角など）。NFKC は、Unicode（文字の国際規格）が定めた正規化の方式の1つです |
| DB再構築 | 本文から、索引と表の写しを作り直す操作です |
| 鏡・計算ビュー | ページを表示するときに、サーバーが計算して描き足す部分です。本文には保存されません |
| 運用者 | w-cms を設置して、動かしている人です |

## 3. 案（筆者）

### 3.1 見たままの表

**キャプションのある表は、キャプションの名前の表として DB に入れます。列は、見出しの名前です。**

```sql
SELECT 品番, 品名, 数量 FROM 受注明細 WHERE 品番 LIKE 'A100%';
```

- ⚠ **キャプションの無い表は入れません**（名前が無いためです）。
  09-20 に閉じた「普通の文章の表まで入る」は、**キャプションの有無**で線が引けます。
- 行ごとに、**どのページの・何番目の表の・何行目か**を持たせます。
  列の名前は **`page_id`・`table_id`・`row_id`** です。

  > 2026-09-25 利用者:「page_id、table_id などアルファベットで良いです」

  - `table_id` は、そのページの中で、同じキャプションの何番目の表かです。
  - `row_id` は、何行目かです。
- **見出しが予約語なら警告します。**
  予約語は、SQL が自分の命令のために取ってある言葉です。

  > 利用者:「表の見出しに予約語が来たら警告してください」

  - 対象は、SQL の予約語（`Order`・`Group`・`Select` など）と、上の3つの列名です。
  - 入れること自体はできます（引用符で囲みます）。
    警告するのは、SQL を書く人が、引用符の要ることに気づけるようにするためです。
  - **2026-09-28 から、保存の告知（文）ではなく編集画面の薄赤＋⚠**で示します。

    > 利用者:「警告文を出すより、問題個所の背景を薄赤にする方が分かりやすいかもしれませんね」

    範囲は、予約語・予約した列に加えて、空白・記号・数字で始まる名前もです（利用者:「いまのまま」）。
    規則の事実（予約語は SQLite に試した結果）は、`/api/tag-schema` の `sql_names` で配ります。
    印は、エディタの `markSqlNames` が付けます。
- ⚠ **キャプションは「DB に入れる」の宣言です。**
  **証拠の写し**（受注ページの「顧客の発注書（読んだまま）」）には、2026-09-28 から**キャプションを付けません**。
  何の表かは、外側の折りたたみの題が言います（利用者:「入れない」）。
  09-20 の「原本は証拠で、検索したいのは弊社の表」が、表の写し（09-25）で、黙って崩れていました。

**置き方: 新しい DB へ移す**（2026-09-25 決定・当初の案B）

> 2026-09-25 利用者:「今あるDBのTableはそのままという意味であれば、**新しいマナーのDBに移してTableを作ってください**」

- いまの縦持ちを**やめ**、**キャプションごとの表だけ**にします。**同じ中身を2か所に持ちません。**
  - いまの縦持ちは `vocab_index` です。受注明細も発注明細も、1つの大きな表に「1セル1行」で入っています。
  - 筆者は当初、縦持ちを残して写しを作る案（A）を推していました。これは不採用です。
- 置き場は**別のファイル**（`data/tables.db`）です。
  - 中核の表（`pages` など）と、名前がぶつかりません。
  - 運用者が開くのも、このファイルだけです（§3.3 の2）。
  - どちらも本文HTMLから作る**派生**なので、DB再構築で作り直せます。

  いまの集計（必要部材表・受注残など）は、縦持ちを読んでいます。
  だから、**読み手を新しい表へ全部移してから縦持ちを消します**（§7 の段取り）。

### 3.2 名前にも同じ正規化を（答え4の延長）

値だけでなく、**表名・列名にも**正規化を掛けます（2026-09-25 決定）。
規則は、**NFKC・前後の空白を落とす・続いた空白は1つにまとめる**、の3つです。
全角半角や前後の空白の違いで、**別の表・別の列**に分かれるのを防ぐためです。

- **既定は「英数字は半角・仮名は全角」**です。

  > 利用者:「デフォルトで英数字は半角、仮名文字は全角が使いやすいです」

  **NFKC がちょうどこの形**です（`ＡＢＣ１２３`→`ABC123`・`ﾌﾟﾚｰﾄ`→`プレート`）。
- ⚠ **中の空白は消しません。**
  `品 番` と `品番` は別の列になり、§3.4 の一覧に出ます。

**SQLite は日本語の名前を引用符なしで受けます**（2026-09-25 に実測）。
`SELECT 品番, 数量 FROM 受注明細 WHERE 品名 LIKE '留め%'` が、そのまま通ります。

- **空白や ASCII の記号を含む名前**は、引用符（`"受注 明細"`）が要ります。保存のときに告知します。
  （2026-09-28 からは、告知ではなく、編集画面の薄赤＋⚠ です。§3.1）
- ⚠ **NFKC は全角の記号も半角にします。**
  `顧客の発注書（読んだまま）` は `顧客の発注書(読んだまま)` になります。
  半角のかっこなので、**引用符が要ります**（`SELECT * FROM "顧客の発注書(読んだまま)"`）。
- 全角のままなら、引用符なしで書けます。
  しかし、`（` と `(` の揺れが、別の表・別の列に分かれます。
  **揃えるほうを採りました**（変えるなら、§3.2 の規則を「英数字と仮名だけ」にします）。

### 3.3 セキュリティ（答え3への返事）

**根本的な問題はありません。守りが4つ要ります。**

1. **表名・列名は必ず引用符で囲む。**
   名前は、利用者が本文に書いた文字です。SQL の `?` では渡せません。
   囲み忘れると、**キャプションの文字が SQL として走ります**。
   **囲む関数を1つだけ作り、全部そこを通します**（`tagNormBind` と同じ「判断を1か所に閉じる」）。
2. **別ファイルに置く**（§3.1・`data/tables.db`）。
   キャプションが `pages` や `page_perms` だと、中核の表とぶつかって壊れます。
   別ファイルなら、**壊れても作り直せます**。運用者が開くのも、**このファイルだけ**で済みます。
3. **検索画面と AI には自由な SQL を渡さない。**
   表には**全ページの行**が入るので、**読めないページの行も見えます**（見せ分け・C案を素通り）。
   「見せ分け」は、読む権限の無いページの行を、集計に出さない決まりです。
   - 検索画面と AI は、**サーバーの口**を通します。口は、**読めるページの行だけ**を返します。
     「口」は、画面や AI がサーバーへ仕事を頼むときの入口のことです。
   - 自由な SQL は、**DB を開ける運用者だけ**です（答え2）。
   - ⚠ **答え1で多いのは検索画面と AI なので、ここがいちばん肝**です。
4. **数の上限。**
   キャプションを打ち間違えるたびに、表が増えます。
   列は、SQLite の既定で**2000まで**です。
   上限を越えたら、入れずに、運用者へ知らせます。

### 3.4 キャプションが同じで列が違う表（2026-09-25 決定: 列を統合する）

**実例は既にあります。**

- `顧客の発注書（読んだまま）`: **客先ごとに列が違います**（紙の写しなので）。
- `発注明細`: 09-22 までの紙は `色`、09-23 からは `表面` です（0a9）。

**案: 列の和集合**

「和集合」は、どれかの表に出てくる列を、全部合わせたものです。

- **名前で合わせます**（列の順番は問いません）。その表に無い列は **NULL**（値なし）です。
- **型は列の名前から語彙で決まる**ので、**表ごとに型が食い違いません**。
  登録の列宣言が無くなれば、型を決めるのは名前だけです（答え6と答え4の帰結です）。
- 1つの表の中で見出しが重なったら、**いまの規則（先勝ち）**です。
- ⚠ **代償: 打ち間違えた見出しは、黙って新しい列になります。**
  そこで、運用者に**「列の揃っていない表」の一覧**を見せます。
  キャプションごとに、各列を何ページが使っているか、の一覧です。
  **50枚のうち1枚だけの列**は、打ち間違いの疑いが濃いです。

**採らない案**

- **列の組ごとに別の表**（`受注明細_2`）。
  見たままでなくなり、引く人が**全部の組を知らないと漏れます**。
- **列が合わない表を入れない**。
  黙って消えます（「書いてあるのに出てこない」）。

### 3.5 コアから表の種類の登録を無くす（答え6）

| コアが持つもの | 拡張が持つもの |
|---|---|
| キャプション → 表、見出し → 列、語彙 → 型、型 → 正規化 | 業務のルール（鏡・ボタン・計算ビュー）を**キャプションで**表を見つけて付ける |

影響は、次の6つです。

1. **09-20 の「登録された語彙だけDBに入る」を覆します。**
   理由だった「普通の文章の表まで入る」は、**キャプションの有無**で解けます（§3.1）。
   原本の写し（`顧客の発注書（読んだまま）`）も入りますが、**名前が違うので弊社の明細の集計と混ざりません**。
   （2026-09-28 からは、原本の写しにキャプションを付けず、入れません。§3.1）
2. **拡張のコードは機械キー（`client-order-items` 等）で表を探しています**
   （`VocabRowsOfType`・`tablesOfType` など）。
   **キャプションで探す形へ書き換える**のが、いちばん大きな作業です。
3. **計算ビュー**（必要部材表・受注残・材料を探す など9つ）は、**コードそのもの**です。
   だから、拡張の登録として残ります。**無くすのは「表の種類」の登録**です。
4. **列の型の宣言が無くなります。** 型は、見出しの名前と語彙だけで決まります。
   - **同じ名前で表ごとに型を変えることはできなくなります**（それが「一般的なルール」です）。
   - 登録で決めていた型のうち、語彙に無いものは、**語彙へ移す**必要があります。
   - `enum`（`状態` の許可値）は、語彙に**許可値の欄が要る**かもしれません。
     → **2026-09-25 決着（§3.10）**: 列の名前ごとに、型と選択肢を**設定の語彙**に登録します
     （語彙は既に `{"type": "enum", "values": [...]}` を持てます）。
5. **データの移行は要りません。** 索引は、本文から作り直せます（DB再構築）。
6. [【一覧】語彙.md](../参照/【一覧】語彙.md) の形式の表は、**拡張のビューだけ**になります。

### 3.6 キャプションの無い表——移植のときに人が名前を付ける（2026-09-25 決定）

「移植」は、ほかの所にあったページを、w-cms へ移すことです。

> 利用者:「`■材料` のように節の見出しで名乗る表をどう扱うかは**移植の話**だと思いますが、**まずDBに入れずにページを移植し、表のタイトルなど必要なものをClaudeに指摘して貰い、私がそれに返答して移植ページを更新しましょう。その後、管理ページでDBを再構築します。**」

**手順**

1. **DB に入れずに移植します。**
   いまの `移行中` タグが、そのまま使えます（**在るだけで止める**・フェイルクローズ）。
   フェイルクローズは、迷ったら閉じる側に倒す考え方です。
   - **2026-09-25 に配線しました。**
     `移行中` のページの表は、`data/tables.db` に入りません
     （コアの口 `RegisterTablesExclusion` へ、板金の拡張が言葉を渡します。開発方針 §0）。
   - それまでの `移行中` は、**読む側**（集計）で止めるだけでした。縦持ちの索引には、入っていました。
2. **Claude が指摘します。**
   キャプションの無い表、表のタイトルにすべき見出し、揃っていない列の名前です。
3. **利用者が返答します。**
4. **移植ページを更新します**（キャプションを付け、`移行中` を外します）。
5. **管理ページで DB を再構築します**（`POST /api/rebuild-db`）。

**コアは「節の見出しで名乗る表」を知らなくてよくなります。**
名前は、人がキャプションに付けます。
だから、解決の②をコアに残す理由が、移植から消えます。

⚠ **ただし移植ページだけではありません**（2026-09-25 に実データで確かめた）。

- **加工製品のテンプレート**（`テンプレート／加工製品`）は、データの中のページです。コードではありません。
- このテンプレートは、表を **`data-type` 属性と節の見出し**で名乗っていて、**キャプションがありません**
  （`<section><h2>材料</h2><table data-type="part-materials">`）。
- キャプションで名乗る形へ切り替えるときは、**テンプレートと、そこから作ったページ**にも、
  同じ手順（指摘 → 返答 → 更新 → 再構築）が要ります。
- ⚠ **テンプレートは環境ごとのデータ**なので、職場と自宅で、別々に直します。

### 3.7 値の持ち方（答え4のとおり）

列には、**型ごとに正規化した値**を入れます。
型は、列の名前から、設定の語彙で決まります。無ければ、文字列です。

いまの正規化で実測した例です（2026-09-25）。

| 型 | 書いた値 | DB に入る値 |
|---|---|---|
| text | `ﾚｰｻﾞｰ加工 ＡＢＣ１２３` | `レーザー加工 ABC123` |
| code | `a100 b01 001` / `Ａ１００－Ｂ０１` | `A100B01001` / `A100-B01` |
| number | `¥8,000` | `8000`（数として） |
| date | `2026/10/15` | `2026-10-15` |

- ⚠ **畳めない値は、書いたまま入れます**（例: date の列に `最短納期`）。
  落とすと、「書いてあるのに出てこない」になるからです。
  代わりに、**日付として並べると日付の後ろへ回ります**（文字として比べられます）。
- **見たままの値の正本は本文HTML**です。DB は、検索のための写しです。

### 3.10 列の型と選択肢は、設定の語彙に列の名前ごとに（2026-09-25 決定）

> 利用者:「列の名前に対して列の型、enumのような選択肢を持つ型と選択肢を設定に登録できるようにするのはどうでしょう？テーブルが変われば列の名前が同じで違う意味もあるとは思うのですが、そこは勘弁ということで」
>
> 利用者:「まだ開発中でデータも本番用ではないので本文の見出しを書き換えるのは良い」
>
> 利用者:「拡張を導入するなら設定ファイルも拡張に合わせて増えると思います」

- 型と選択肢は、`config/settings.json` の `vocabulary` に、**列の名前ごと**に書きます
  （既に `{"type": "enum", "values": [...]}` の形を持てます）。
  拡張の言葉も、拡張を入れるときに、設定ファイルへ足します。
- **同じ名前で選択肢が違う列が、いま2つあります**（2026-09-25 に登録から数えた）。
  - `状態`: 受注明細は `未着手・加工中・検査中・納品済・完了`、発注明細（と発注部材表）は
    `未発注・発注済・納品済・取消` です。
    → **見出しを改める**（どちらを何と呼ぶかは §4 の未決）。
  - `単位`: 受注明細は `個・セット`、発注明細は `個・セット・本・枚・kg・m` です。
    → 意味は同じなので、**選択肢を合わせる**（多いほうに）。
  - `区分`（現行・廃版）は、4つの表で同じです。
    `材料発注`・`納品書発行`・`請求書発行`（済）も、1つずつで、重なりません。

`状態` は、そのあと §7 の 4-1 で、見出しを改めずに分ける形になりました（例外の `table_vocabulary`）。

### 3.9 SQL の安全の規則（利用者の問い・2026-09-25）

> 2026-09-25 利用者:「SQLのサニタイズ規則を教えてください。それと、SQLiteにはサニタイズ不要の個別に列の値を入力するAPIがあるはずですが、使えませんか？今はSQLの文字列に組み立てて読ませていますか？」

「サニタイズ」は、危ない文字を取り除いて、安全にすることです。

- **値は、個別に渡す仕組み（`?` とバインド）を使っています。**
  - SQL の文には、`?` だけを書きます。値は、別に渡します。
    だから、何が書かれていても、SQL になりません
    （`INSERT … VALUES (?, …)`・`WHERE page_id = ?`・検索の条件の値）。
  - 表の名前を**値として**渡せるところも、そうしています（`pragma_table_info(?)`）。
- **表の名前・列の名前は、SQL の決まりとして `?` で渡せません**（SQLite に限らず）。
  - `CREATE TABLE`・`ALTER TABLE … ADD COLUMN`・`INSERT INTO 表 (列…)`・`DELETE FROM 表`・`DROP TABLE`・
    `SELECT … FROM 表` だけは、文に名前を書きます。
  - そこは、**必ず1つの関数（`quoteIdent`）で囲みます**。
  - SQLite の規則では、`"` で囲んだ名前の中の文字は、**すべてただの文字**です（`;`・`--`・`'`・改行も）。
    特別なのは `"` だけなので、`""` と重ねます。
  - **文字を削るサニタイズではなく、必ず名前として読ませる書き方**です。
- **検索（3段目）はさらに2重**です。
  - 利用者が言った表・列の名前は、**DB に実際にある名前と照らして**、一致したものだけを使います。
  - 条件の種類は、コードが持つ4つから選ぶだけです。
  - 利用者の文字は、SQL の文に入りません。
- 名前の記号は、**ユニコードの正規化規則（NFKC）に準じます**（利用者・2026-09-25）。§3.2 のままです。

### 3.8 日本語以外の言語では（利用者の問い・2026-09-25）

**名前はほぼそのまま動きます。**
SQLite は、ASCII 以外の文字（中国語・韓国語・アクセント付きのラテン文字…）を、引用符なしで名前に使えます。
NFKC も、言語を問わない標準の正規化です。

気をつけるのは、3つです。

1. **英語は予約語と大小に当たりやすい。**
   `Order`・`Group`・`Index` のような見出しは、よくあります（→ §3.1 の予約語の警告）。
   ⚠ **SQLite は ASCII の大文字小文字を区別しません。**
   同じ表に `Qty` と `QTY` の見出しがあると、**同じ列**になります（統合の規則 §3.4 に乗せます）。
2. ⚠ **数と日付の読み方は国で違います。**
   - ドイツ語では、`1.234,56` が 1234.56 です。
   - 米国では、`10/15/2026` が月/日/年です。
   - 欧州では、`15/10/2026` が日/月/年です。

   **いまの正規化は日本の書き方**（`2026/10/15`・`8,000`）を前提にしています。
   **他の国で使うなら、読み方を設定で選べる必要があります**（言語・地域の設定を1つ持ちます）。
3. **画面・エラーの文言は日本語だけ**です。
   DB とは別の話ですが、コアを他の言語の人が使うなら、要ります。
