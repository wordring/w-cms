# 【考察】端末の登録

社外から w-cms にログインできるパソコンとスマホを、あらかじめ登録したものだけに絞る案を考えた文書です。
問いの答えは §7、作ったものは §9 にあります。
いまは §5 の「記録する段階」です。社外の登録のない端末も、まだ断っていません。

> 2026-10-31 利用者:「ログイン元についてはよくわかりません。パソコンやスマホを登録することについてどう思いますか？」
>
> 2026-10-31 利用者:「まとめてください」
>
> 2026-10-31 利用者:「勧めどおりで作る」

**この文書の結論**

- 社外からのログインは、登録した端末だけに許します。パスワードも今までどおり要ります。
- 登録は、社内のネットワークからログインして行います。
- 社外で端末を足すときは、登録済みの端末で出した一回限りの番号を使います。
- 端末の一覧を画面に出し、なくした端末はそこから取り消せるようにします。
- いきなり断る形にはしません。初めは記録するだけにして、全部の端末を登録してから断る形へ切り替えます。

---

## 1. なぜ考えるのか

毎朝のサーバーの監査を読むと、管理者のログインの接続元が並びます。
住所を見ても、本人かどうかはすぐに分かりません。実際、2026-10-31 の監査でも確かめきれない接続元が残りました。

いまのログインは、パスワードだけです。

- 社外からは、公開の名前と VPS（社外に借りたサーバー）を通って、だれでもログインの画面まで来られます。
- 探りの通信は毎日届いています。2026-10-31 に手元のログで数えると、`.env`・`.git` などを探す要求に、中身を返したものはありませんでした。
- 本番で有効なログイン名は3つです（2026-10-31 に数えた）。人の管理者が1人、Claude、機械です。Claude と機械は、Cookie のログインを使いません（§4.5）。
- パスワードが漏れると、世界のどこからでも入れます。

端末を登録すれば、パスワードが漏れただけでは社外から入れなくなります。
監査を読む人も、「登録した端末か、そうでないか」で見分けられます。

---

## 2. どの形にするか

| 案 | 良い所 | 困る所 | 判断 |
|---|---|---|---|
| **端末の登録**（ブラウザに長く残る印） | 利用者の手間が少ない。外部のパッケージが要らない。一覧と取り消しを画面に出せる | ブラウザごとの登録。ブラウザのデータを消すと登録し直し | **勧める** |
| 接続元の住所で絞る | 作るのが簡単 | 家のインターネットの住所は変わることがある。スマホの住所は変わり続ける | 採らない |
| クライアント証明書 | 守りが固い | 端末ごとに入れるのが大変。スマホでは特に難しい。VPS でも扱いが要る | 採らない |
| 認証アプリの6桁の番号（TOTP） | 標準ライブラリだけで作れる。端末を選ばない | ログインのたびに番号を打つ。本物そっくりの偽の画面に打つと盗まれる | 今は採らない |
| パスキー | 偽の画面に強い。いちばん守りが固い | `192.168.1.100` の住所では使えない。公開の名前に統一する必要がある。読み取りの処理が多く、外部のパッケージを足すか自前で書くことになる | 先の話として残す |

端末の登録を勧める理由は、守りと手間の釣り合いです。
いま人のログイン名は1つで、使う端末も限られています。登録の手間は最初の1回で済みます。

パスキーは、あとから足せます。登録の一覧と取り消しの画面は、パスキーでもそのまま使えます。

## 3. 使う人から見た形

### 3.1 社内で登録する

1. 社内のネットワークで、登録したい端末から、**社外で使うのと同じ名前**で w-cms を開いてログインします。
   ⚠ 登録の印は開いた名前ごとに別です。`192.168.1.100` のような数字の住所で開いていると、登録を断ります。
2. 「この端末を登録」を押し、名前を付けます（例: 「事務所のパソコン」「自分のスマホ」）。
3. 以後、その端末は社外からもログインできます。

### 3.2 社外で端末を足す

家のパソコンのように、社内へ持って行けない端末のための道です。

1. 登録済みの端末で「ほかの端末を足す」を押し、番号を出します。番号は1回限りで、10分で切れます。
2. 足したい端末のログインの画面で「番号で登録する」を選びます。
3. 名前・パスワード・番号を入れて、端末に名前を付けます。

### 3.3 登録していない端末で社外から開いたとき

ログインの画面に、次のように出します。

> この端末は登録されていません。社内で登録するか、登録済みの端末で番号を出してください。

公開のページは、今までどおりログインなしで読めます。

### 3.4 端末をなくしたとき

1. 別の端末で「端末の一覧」を開きます。
2. なくした端末を「取り消す」と、その端末のログインもすぐに切れます。

管理者は、ほかの利用者の端末も取り消せます。

### 3.5 通知

新しい端末を登録したら、本人に通知し、監査にも残します。
身に覚えのない通知が来たら、すぐに取り消せます。

## 4. 作り方の案

置き場は**コア**です（`internal/auth`）。
別の会社が同じ仕組みを使うときにも要るもので、業務の知識が要らないからです（[開発方針.md](../開発方針.md) §0）。

### 4.1 持つもの

`data/auth.db` に新しい表 `devices` を足します。

| 列 | 中身 |
|---|---|
| `id` | 端末の番号 |
| `username` | だれの端末か |
| `token_hash` | 印のハッシュ。印そのものは保存しません（セッションと同じ考え方） |
| `name` | 利用者が付けた名前 |
| `created_at` | 登録した時刻 |
| `last_seen` | 最後に使った時刻 |
| `last_ip` | 最後の接続元 |

ブラウザには、セッションとは別の Cookie を置きます。

- `HttpOnly`・`Secure`・`SameSite=Lax` を付けます。
- 寿命はブラウザの上限まで長くし、使うたびに延ばします（Chrome の上限は400日です）。
- 取り消した端末の行は消さず、取り消した時刻を残すか、監査に残すかを作るときに決めます。

`sessions` には、どの端末のログインかを示す列 `device_id` を足します。

### 4.2 社内と社外の見分け

新しい判定は作らず、今ある `IsFromTrustedProxy` を使います。
社外からの要求は VPS のトンネルを通るので、前段のプロキシから来た要求が社外です。
社内からは、公開の名前で開いても業務サーバーへ直に届きます。

監査の接続元と同じ判定なので、規則がずれません。

⚠ `IsFromTrustedProxy` はループバックも信じます。業務サーバーの中から `localhost` で開くと、社外と見なされます。
試験用を SSH の中継で開く E2E も社外に見えます。試験では、これを社外の確かめに使えます。

### 4.3 確かめる順番

社外からのログインは、**パスワードを確かめる前に**端末を見ます。

- 登録のない端末は、パスワードを見ずに断ります。外から総当たりをしても、合っているかどうかが分かりません。
- 重いパスワードの計算（argon2id）を外から何度も走らせられなくなります。
- 番号で登録するときは、番号を先に確かめ、失敗は接続元ごとに数えて止めます。

### 4.4 ログインのあとも確かめる

ログインのときだけ見ると、穴が2つ残ります。

- **社内でログインしたパソコンを、そのまま社外へ持ち出す。** 登録していなくても、セッションの Cookie で入れてしまいます。
- **端末を取り消しても、ログインが残る。**

そこで、次の2つを足します。

- `userFromRequest` で、社外からの要求は、セッションが登録済みの端末に結ばれていることを確かめます。結ばれていなければ、ログインの画面へ戻します。
- 端末を取り消すと、その端末のセッションを消します。

### 4.5 影響を受けないもの

| もの | 理由 |
|---|---|
| 公開のページ | ログインが要りません |
| 機械専用の入口（`/api/machine/`） | Cookie ではなく鍵と接続元で確かめます |
| 業務サーバーの中の入口（Unix ソケット） | ファイルを開けるかで確かめます。Claude の入口も同じです |
| 📝 ローカル編集 | ヘルパーは編集用の鍵を使います。鍵はセッションに結ばれているので、そのセッションが切れれば効かなくなります |

## 5. 切り替えの順番

⚠ いきなり断る形にすると、登録を忘れた端末の人が社外で締め出されます。

1. **記録する段階**: 登録の画面と一覧を入れます。社外から登録のない端末でログインしても入れますが、監査に印を付けて残します。
2. **登録する段階**: 利用者が全部の端末を登録します。監査を見て、登録のない端末からのログインが無くなるのを確かめます。
3. **断る段階**: 環境変数で断る形へ切り替えます。戻すのも環境変数だけで済みます。

## 6. 弱い所と、残る心配

**登録しても防げないもの**

- 登録済みの端末を盗まれた場合。端末の確かめは効かないので、パスワードが最後の守りになります。だからパスワードは省きません。
- 利用者の端末がウイルスに乗っ取られた場合。
- 社内のネットワークにいる人。社内からのログインには、登録を求めないためです。

**使っていて困ること**

- 登録はブラウザごとです。同じパソコンの Chrome と Firefox は、別の端末です。
- ブラウザのデータを消すと、登録し直しになります。
- シークレットモードでは、登録が残りません。
- 1つのブラウザに置ける印は1つです。同じブラウザで別の人が登録すると、前の人の印は置き換わります。

**締め出し**

⚠ 社外で全部の端末を失うと、社内へ行くまで入れません。
これは意図した形です。人の管理者が1人の間は、特に端末を2つ以上登録しておくことを勧めます。
どうしても必要なときは、社内から業務サーバーへ SSH で入り、断る形を切ることができます。

## 7. 利用者に決めてほしいこと

> 2026-10-31 利用者:「勧めどおりで作る」

6つとも、下の筆者の勧めのとおりに決まりました。

**問い1. 社内からのログインにも登録を求めますか？**
求めないことを勧めます。社内の共用のパソコンや試験で手間が増えるわりに、社内の人を止める効果は小さいからです。

**問い2. だれに当てますか？**
全部の利用者を勧めます。いま人のログイン名は管理者の1つだけですが、これから足す人のパスワードでも、業務のデータは読めるからです。

**問い3. 社外で端末を足す番号の道は要りますか？**
要ると勧めます。家のパソコンのように社内へ持って行けない端末があるからです。

**問い4. 登録に管理者の承認を求めますか？**
求めないことを勧めます。本人が登録し、通知と監査で確かめます。人のログイン名が1つなので、承認する人が本人しかいません。

**問い5. 長く使っていない端末を自動で取り消しますか？**
180日で取り消すことを勧めます。忘れた端末が登録のまま残らないようにするためです。

**問い6. 新しい端末を登録したときの通知はどこへ送りますか？**
今あるスマホの通知（Web Push）で本人へ送り、毎朝の監査にも載せることを勧めます。
ほかの管理者にも送るかは、人が増えてから決めます。

## 8. いまの確かめ

作る前に、次のことをコードと本番で確かめました（2026-10-31）。

- ログインはパスワードだけです。`internal/` に、TOTP やパスキーの処理はありません。
- 【要求】権限 §1 には、将来の MFA の「接合点だけ予約」とあります。この案を採るなら、利用者が要求の本文を書き足すことになります。
- 本番の Cookie は `Secure` です（`WCMS_SECURE_COOKIES=0` は書かれていません）。
- 社外の要求の見分けに使える `IsFromTrustedProxy` は、監査の接続元と同じ判定です。

## 9. 作ったもの（2026-10-31）

- **部品**: `internal/auth/device.go`（表 `devices`・`device_codes`、セッションの列 `device_id`）と `device_handlers.go`。
- **断る**: `WCMS_DEVICE_REQUIRED=1` のときだけです。無ければ、ログインは通し、監査に `login.unregistered-device` を残します。
- **ログイン**: `LoginAPIHandler` は、社外の登録のない端末をパスワードの前に断ります。番号があれば、番号 → パスワードの順に確かめて登録します。
- **毎回の確かめ**: `userFromRequest` の `deviceGateOK` です。社外からは、セッションが端末に結ばれ、その端末の印も付いていることを見ます。セッションの Cookie だけでは通りません。
- **API**: `/api/devices`・`/api/devices/register`・`/api/devices/code`・`/api/devices/revoke`。
- **画面**: `assets/devices.html`・`devices.js`。入口は上のメニューの「📱 端末」です。
- **管理の守り**: 社外の登録のない端末は、断らない設定のあいだも、番号を出すこと・取り消すこと・番号なしの登録ができません。パスワードだけを盗んだ人が端末を足せないようにするためです。
- **番号**: 8桁・10分・1回限りで、5回間違えると捨てます。出し直すと前の番号は効きません。
- **180日**: 使っていない端末は、ログインと一覧のときに取り消し、監査に `device.expired` を残します。
- **通知と監査**: 登録するとスマホへ通知します（`internal/cms/device_notice.go`）。監査の `device.*` と `login.unregistered-device` は、毎朝のサーバーの監査にも載ります。

**確かめたこと**

- Go の試験 `internal/auth/device_test.go`。わざと壊して、試験が落ちることも見ました。
- 本物のブラウザの E2E `e2e/verify-devices.js`。自分で一時のデータの w-cms を起こし、同じ名前を社内と社外へ切り替えて確かめます。
- ⚠ 本物の VPS を通した確かめと、本物のスマホの通知は、利用者が登録するときに見ます。
