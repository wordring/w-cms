# 【考察】タグ表と業務ブロック表の分離

> 2026-09-06 利用者:「TAGSと表のTableを分離することについて考察してください」

本文に書いたタグと表は、検索と集計のために、DB の「索引」へ写されます。
この文書は、**タグの索引と、業務ブロックの索引を、別々の表に分けるか**を考えた記録です。

2026-09-06 の時点では、可変タグ（`<dl data-type="tags">`）と業務ブロック（図面・発注書・明細表）は、
**同じ `vocab_index` 1本**に入っていました。
これを2つの表に分けるべきかを、実測した数字と、読み手の一覧から考えました。

そのときの**結論は「分けない。ただし読み手の曖昧さは分けずに直す」**でした（§6）。
未決ではなく、この文書での判断です。蒸し返すのは、§6 の3条件のどれかが崩れたときに、としていました。

> **⚠ この結論は 2026-09-13 に覆りました。**
> 「分けない」と決めましたが、利用者の決定で**分けました**（`page_tags` ＋ `vocab_index`）。理由は §8 です。
> §6 までは、**そのとき何を考えたか**の記録として残します。
> 判断が変わった経緯そのものが次に効くので、消しません。

## 1. いまの形（実測 2026-09-06・118ページ・実メール100通）

`vocab_index` は9列です。
タグも表も **1行＝1セル**で入ります。区別は `data_type` の列だけです。

| data_type | 行数 | `block_id` が入っている行 | `norm_num` | `row_no` の最大 |
|---|---|---|---|---|
| `tags` | **1137** | **0**（全行が空） | 0 | 15 |
| `drawing`（図面ブロックの dl） | 28 | 28（全行） | 0 | 3 |
| `drawing-revision-items`（改訂履歴の表） | 21 | 0 | 0 | 0 |

```sql
-- 数え直すとき
SELECT data_type, COUNT(*), SUM(block_id<>''), SUM(norm_num IS NOT NULL), MAX(row_no)
  FROM vocab_index GROUP BY data_type;
```

- 行の**96%がタグ**です。その大半は、メールの封筒（差出人・宛先・メッセージID…）です。
- タグ行では、`block_id` が**常に空**です。タグの `dl` には `data-id` を振っていないためです。
  `data-id` は、本文のブロックに付く識別子です。

### 1.1 1件（レコード）の単位が違う

同じ表に入っていますが、**何が1件かはタグと表で違います**。

| | 1件の単位 | `row_no` の意味 |
|---|---|---|
| 表（`table`） | `tr` 1行＝1件 | **件を区別する**（行1と行2は別の件） |
| `dl`（タグ・図面ブロックのヘッダ） | ブロック全体で1件 | **並び順**にすぎない |

読み手は、この非対称を `vocabRows(db, pageID, dataType, perBlock)` の `perBlock` で吸収しています
（[vocab_query.go](../../internal/cms/vocab_query.go)）。

- `dl` は、`row_no` を 0 に潰して、1件にまとめます。
- 表は、そのまま使います。

**書き手の作りの違いが、読み手にそのまま出ている**形です。

### 1.2 ブロックの中のタグは、ブロックから切り離されて入る

図面ブロックは `<section><h2>図面</h2><dl>…</dl><dl data-type="tags"><dt>受信元</dt>…</dl></section>`
という形です。
由来の参照タグを、**ブロックの中**に持ちます。
改定で合流させるとき、ブロックごと運べば、出所も付いて行くようにするためです。

ところが、索引では次のようになります。

```
('drawing', 0, '3je2', 0, '図面番号', 'Q130-004')      ← ブロック（block_id あり）
('tags',    0, '',     0, '受信元',   '010173-skr1')   ← 同じ section の中のタグ（block_id 空）
```

- `data-type="tags"` を持つ要素は、本文を配る仕組みが**独立した形式として別に届けます**
  （[vocab_index.go](../../internal/cms/vocab_index.go) `syncVocabSection` の注記）。
  本文を配る仕組み（配送係）は、本文の要素を順に見て、担当の処理へ届けるコアの仕組みです。
- そのため、包んでいる section との対応は、索引に残りません。

図面ブロックが1ページに1つしか無いいま（旧版は子ページへ・2026-09-06）は、実害がありません。
しかし、**「このタグはどのブロックのものか」を索引から引く手は無い**、というのが現状です。

## 2. 読み手の一覧——どちらの読み手も、既に種類で分かれている

索引に触る素の SQL は、**23か所**あります
（テストを除く。`grep -rn "FROM vocab_index"`。うち1つは書き手の `DELETE`）。

| 読み手の種類 | 場所 | `data_type` を絞るか |
|---|---|---|
| **ブロックを読む** | `vocabRows`（`VocabTableRowsOf` / `VocabBlocksOf`） | 絞る（特定の形式名） |
| **タグを読む・入口の関数** | `PagesByTag` / `PagesByTagLoose` / `RelatedPages`（2本） | **`data_type='tags'` で絞る** |
| **タグを読む・素の SQL** | contacts.go ×5・view_unhandled.go ×6・ref_scope・handler_replies ×2・analyzed.go・filing.go ×2・ext/comm/mail/reply.go | **絞らない**——`field` だけで引く |

2つのことが読み取れます。

1. **Go の読む関数は、もう種類で2家族に分かれています。**
   ブロックは `Vocab*Of`、タグは `PagesByTag*` です。
   共有しているのは**保存先**だけで、API は既に分離済みです。
2. **素の SQL の大半は `field` だけで引いています。**
   `WHERE field = '差出人アドレス'` は、「それはタグだ」と**名前で決めつけて**います。
   いまは、業務ブロックの列にその名前が無いので、合っています。
   しかし、誰かが `<th>差出人アドレス</th>` を持つ表を作った瞬間に、
   アドレス帳がその表の値を「未登録の連絡先」として拾います。
   **1つの表であることの、いちばん具体的な危うさ**はここです。

この2つ目を、あとの節では「§2-2」と呼びます。

  「用語：説明」のような普通の定義リストまで DB に入るためです（[walk.go](../../internal/cms/walk.go)）。

  > 利用者:「tags については、データベースに入る汎用的なマークアップとして使いたいので、やはり data-type または似たようなクラス分けが必要」

ここで大事なのは、**過去に消した `page_tags` と、いま考えている分離は別物**ということです。

- 消したのは、「同じ中身を2か所に持つ」重複でした。
- いま考えているのは、「種類で**割る**」分割です。どの行も、1か所にしか入りません。

だから、「D-1 の蒸し返し」にはなりません。
**しかし、D-3 の「分ける利益が具体化していない」は、そのまま当たります**（§5）。

もう一つあります。
2026-08-31 の決定は、**タグが業務ブロックとは違う種類のものだ**と言っています。

- 業務ブロックは、機能見出し（`<h2>図面</h2>`）で形式が決まる、**文書の一部**です。
- タグは、`data-type="tags"` で明示的にオプトインする、**ページの付箋**です。
  オプトインは、書いた人が印を付けたものだけを対象にすることです。

種類が違うものを1つの表に入れている、という指摘は正しいです。
問題は、それを**表を分けて表すか、列で表すか**です（いまは `data_type` 列）。

## 4. 選択肢

A〜D の4つを比べました。2026-09-06 に選んだのは A＋C-1 で、2026-09-13 に B へ改めました。

### A. いまのまま（1表・`data_type` 列で区別）

- 書き手が1つ、再構築が1つ、FK が1つです。
  FK（外部キー）は、ほかの表の行を指す、という列の決まりです。
- `syncVocabDL` は、タグとブロックのヘッダを**同じ関数**で書きます。
- 欠点は、§1.1 の非対称と、§2-2 の曖昧さです。どちらも、**いま壊れてはいません**。

### B. 2表に分ける（`page_tags` ＋ `vocab_index`）

**この節のその後**: 2026-09-13 に、この案で分けました（§8）。実際の `page_tags` は、下の案と3つ違います。
名前の列は `field` ではなく `name` です。`norm_value` は宣言型を持ちません（2026-09-15）。主鍵は `(page_id, seq)` です。
いまの定義は [vocab_index.go](../../internal/cms/vocab_index.go) の `CREATE TABLE IF NOT EXISTS page_tags` にあります。

```sql
CREATE TABLE page_tags (          -- 付箋。1行＝1対
    page_id    INTEGER,
    seq        INTEGER,           -- ページ内の並び（旧 row_no）
    field      TEXT,
    value      TEXT,
    norm_value TEXT,
    FOREIGN KEY (page_id) REFERENCES pages(id) ON DELETE CASCADE
);
-- vocab_index はブロック専用になり、block_no / block_id / row_no / norm_num が
-- **全行で意味を持つ**ようになる
```

**得るもの**

- **スキーマの正直さ**。タグ行に、常に空の `block_id` が無くなります。
- 読み手が、**どちらを読むか書かざるをえなくなります**。§2-2 の曖昧さが、構造的に消えます。
- 検索を速くするための DB の索引（インデックス）を、種類ごとに張れます
  （タグは `(field, value)`・`(field, norm_value)`、ブロックは `(page_id, data_type)`）。

**払うもの**

- 書き手が2つになります（`syncVocabDL` を、タグ用とヘッダ用に割ります）。
- 素の SQL **17か所**の書き換え。
- `DriftedSchemaTables` による、起動時の自動再構築が1回。
- プラグインガイドの更新。
- それと、**§1.2 の帰属問題は解けません**。
  タグを別の表へ出しても、包んでいるブロックとの対応は、同じく残りません。

### C. 分けずに、非対称と曖昧さだけ直す

1. **素の SQL 17か所に `data_type = 'tags'` を足します。** または、`PagesByTag*` を通します。
   §2-2 の危うさは、これだけで消えます。
2. `row_no` の意味の違いは、書き手で揃える手があります
   （`dl` は常に `row_no = 0`、並びは `rowid` で保つ）。
   ただし、読み手の `perBlock` が既に吸収しているので、直す動機が弱いです。

この1つ目を「C-1」と呼びます。

### D. 表は1つのまま、**ビュー**で名前を分ける

ビューは、SQL の問い合わせに名前を付けて、表のように読めるようにしたものです。

```sql
CREATE VIEW page_tags AS
  SELECT page_id, row_no AS seq, field, value, norm_value
    FROM vocab_index WHERE data_type = 'tags';
```

- 書き手はそのままです。読み手は `FROM page_tags` と書けて、意図が見えます。
  B の「正直さ」の半分を、書き換えなしで得ます。
- ただし、SQLite のビューは `DriftedSchemaTables` の対象ではありません（テーブル定義の比較なので）。
  ビューの作り直しを `ApplySchema` に足す手間は要ります。

## 5. 判断の物差し——このプロジェクトが既に決めていること

- **柔軟性 > 速度**（[アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) §9 の原則。方針の行は、同 §8.4 にあります）。
  行数は理由になりません。
  100通で1137行、年435通なら、10年で**5万行前後**です。
  SQLite にとっては、何でもない量です。分けても速くならず、分けなくても遅くなりません。
- **索引は派生**。
  スキーマを変えても、起動時に1度作り直されるだけで、移行は要りません。
  だから、「変えるなら早いうちに」は**成り立ちますが**、「変えないと後で困る」も**成り立ちません**。
  いつでも同じ手間です。
- **読む入口は `vocab_query.go` の3つに閉じる**（引き継ぎ「知らないと踏む罠」）。
  §2 の 17か所は、この決定から**既に漏れている**素の SQL です。
  分離の是非より先に、直すべきものです。

## 6. 結論——分けない。読み手の曖昧さは C-1 で直す

⚠ この節の結論は、2026-09-13 に覆りました（§8）。以下は、2026-09-06 の判断の記録です。

分けない理由は3つです。**この3つのどれかが崩れたら、B を考え直します。**

1. **能力が増えない。**
   いまの読み手に、「2表でないと書けない問い」は1つもありません。
   得られるのは、正直さと見通しです。
   それは、C-1 と D で、**書き換えなしに**大半が手に入ります。
2. **タグの帰属（§1.2）を持ちたくなったとき、同じ表のほうが自然。**
   「この `受信元` はどの図面ブロックのものか」を引きたくなったら、必要なのは `block_id` を**埋める**ことです。
   列は既にあります。
   2表に割っていたら、`page_tags` に列を**足す**ことになり、ブロックと同じ列を2つの表が持つ形へ戻ります。
   §1.1 の非対称は、「タグは付箋であってブロックではない」と読めば、非対称ではありません。
   **種類の違いが列の埋まり方に出ている**だけです。
3. **払うものが具体的で、得るものが抽象的。**
   15か所の書き換えと書き手の分割は、今日やれば1日です。
   しかし、それで直る不具合が、**今日は無い**のです。D-3 と同じ理由です。

この3つを、あとの節では「§6-1」「§6-2」「§6-3」と呼びます。

やることは2つです。

- **C-1（今すぐ・小）**:
  `field` だけで引いている素の SQL に `data_type = 'tags'` を足すか、`PagesByTag*` を通します。
  対象は、次のとおりです。
  - アドレス帳（contacts.go）
  - 未処理一覧（view_unhandled.go）
  - 解析済みの印（analyzed.go）
  - 整理の顧客名推奨（filing.go）
  - 返信（handler_replies.go・ext/comm/mail/reply.go）
  - 参照の集計（ref_scope.go は済み）

  （いまは: 2026-09-13 に表を分けたので、この直しは要らなくなりました。§8。）

  **業務ブロックの列名がタグ名と衝突した日に静かに壊れる**穴です。
  だから、分離の是非とは無関係に塞ぎます。
- **D（任意）**:
  ビュー `page_tags` を足して、以後の素の SQL はそこから読む決まりにします。
  `ApplySchema` に `CREATE VIEW IF NOT EXISTS` を1つ足すだけです。

## 8. 覆した記録（2026-09-13）

> 利用者:「HTMLのTableとタグはDBのTableを分けたいと思います」

**§6 の蒸し返し条件のうち2つが満たされていました**（実測）。

### ① 「タグは付箋であってブロックではない」が崩れた

§6-2 は、タグを「ブロックに貼る付箋」と読んでいました。
ところが、その週のうちに、**アドレス帳がタグになりました**。
連絡先・担当者の実体は、`メールアドレス`・`電話番号`・`役職`・`在籍` のタグです。
**タグが業務データの本体**です。

- 実測でも、索引の**84%がタグ**でした（タグ1172行 / 業務ブロック全部で230行・212ページ）。
- `block_id` が埋まるタグは、**2.5%**だけでした。帰属を心配した §6-2 の前提も、ほぼ当たっていませんでした。

### ② 「C-1 で足りる」が崩れた

§6 は、「読む側で `data_type='tags'` を足せば足りる」としました。**足りませんでした**。

| | |
|---|---|
| 決定から1週間後に残っていた絞り込み無しのSQL | **13箇所** |
| そのうち 2026-09-13 に**増えた**ぶん | **3箇所**（連絡先の実装で、書いた本人が3回忘れた） |
| 実際に起きていた名前の衝突 | 0件（**まだ**運が良かっただけ） |

**規律で守る約束は、守られませんでした。**
表が分かれていれば、間違った問いは、そもそも書けません。

§6-3 の「払うものが具体的で、得るものが抽象的」は、**払うものが思ったより安い**ほうで外れました。

### 実装で踏んだ罠2つ（どちらも試験で固定）

「試験で固定」は、同じ間違いが起きたら、自動の試験が落ちるようにした、という意味です。

- **新しい表は「ずれ」と見なされず、再構築が走りませんでした。**
  「ずれ」は、プログラムが期待する表の定義と、実際の DB の表の定義が食い違っていることです。
  `ApplySchema` は空の表を作るだけなので、**タグ88行が古い表に取り残されました**
  （画面は無言で空になります）。
  そこで、`DriftedSchemaTables` が、「索引に中身があるのに表が無い」をずれとして扱うようにしました。
- **`CREATE INDEX` を表と取り違えていました。**
  直した直後、起動のたびに再構築が走るようになり、ログで気づきました
  （`createdTableName` が、`EXISTS` の次の語を無条件に採っていました）。

分けたあとの決定は、次の2つです。
2行目の「宣言型」は、DB の列に付ける型の宣言（`TEXT` など）のことです。

| 日付 | 決定 | 理由 |
|---|---|---|
| 2026-09-13 | **タグ表と業務ブロック表を分ける**（`page_tags` ＋ `vocab_index`）（ユーザー決定） | §8。タグが業務データの本体になった／C-1 の規律が守られなかった（13箇所・うち3箇所は同日に増えた）／移行が要らず実費が安かった |
| 2026-09-15 | **`page_tags.norm_value` の宣言型を外す**（ユーザー決定） | 分けたことで初めて選べるようになった。**表が分かれる前は選べません**——`vocab_index` の `norm_num` には読み手が実在する（`vocabRows` の集計）ので、1列に混ぜると集計の側を全部書き直すことになる。タグ側には読み手が居らず、しかも「名前が型を決める」ので1つの問いの中では型が揃う。`TEXT` のままだと数が辞書順に並び **`"8000" < "900"`** になる。正本は [【一覧】日付形式と数詞.md](../参照/【一覧】日付形式と数詞.md) §5 |
