# 【考察】社外公開とHTTPSの構成

w-cms を社外からも使えるようにするとき、**どういう形でインターネットへ出すか**と、
**HTTPS の証明書をどうするか**を決めた文書です。

> 2026-09-07。実運用では**社外からも使い、主にスマホから**という前提が出たので、
> 公開の形を決めました。**VPS リバースプロキシ**です（§6）。
> **VPSはまだ建てていません**が、**アプリ側の備えは実装済み**です
> （`/dav/` は転送されてきた要求を断ります）。
>
> 関連: [【考察】添付をローカルアプリで編集する.md](【考察】添付をローカルアプリで編集する.md)
> （WebDAV・HTTPS化の実測）／[認証認可設計.md](../旧文書/認証認可設計.md)（匿名公開の規則）。
> **結論は §6。** どちらを選んでも要ることは §4（split-horizon DNS）。

**決まったこと**（どれも 2026-09-07。理由は §7 の決定ログにあります）

- 証明書は、自己署名から**公的なもの**へ移します（§1）。
- 公開の形は **B（VPS リバースプロキシ）**です（§6）。
- **WebDAV は公開しません**（§3）。アプリ自身も、転送されてきた `/dav/` への要求を断ります（実装済み）。
- **split-horizon DNS は必須**です（§4）。社内でも、ホスト名で繋ぎます。

**残っていること**

- VPS を建てること。建てるときに VPS 側で要る設定は、§6 にあります。
- 外に出す前に確かめること（§5）。

**先に、言葉の説明**

| 言葉 | 意味 |
|---|---|
| HTTPS・証明書 | HTTPS は、通信を暗号化してやり取りする仕組みです。証明書は、「このサーバーは本物です」と相手に示すための電子の書類です |
| 自己署名の証明書 | 自分で作って、自分で署名した証明書です。使う端末ごとに、「これを信頼する」と登録する作業が要ります |
| 公的な証明書 | 認証局（証明書を出す機関）が出した証明書です。Let's Encrypt は、そうした認証局の1つです |
| VPS | インターネットの上に借りる、自分専用のサーバーです |
| リバースプロキシ | 外から来た要求を受け取り、奥にある本物のサーバーへ中継する役のサーバーです |
| WebDAV | サーバーの上のファイルを、パソコンのフォルダのように開いて上書きできる仕組みです。w-cms では、社内の PC から CAD のファイルを編集するのに使います（口は `/dav/`） |
| DNS | ホスト名（`wcms.example.co.jp` のような名前）から、IP アドレス（ネットワークの上の住所）を引く仕組みです |
| split-horizon DNS | 同じホスト名を、社内で引いたときと社外で引いたときとで、別の IP アドレスに答えさせる DNS の構成です（§4） |

## 1. きっかけ——スマホが入ると自己署名は捨てることになる

いまは、**自己署名の証明書＋各PCで1回信頼**という形です（2026-09-07 に実装・2台で確認済み）。

台数が少ないうちは、これは堅い選択でした。
証明書は2年もちますし、更新の自動化が壊れる心配もありません。

**スマホが入ると成り立ちません。**

- iOS では、プロファイル（設定をまとめたファイル）を入れたうえで、「証明書信頼設定」で有効にするところまで要ります。
- この手間が、端末が増えるたびに発生します。

そこで、**公的な証明書（Let's Encrypt 等）へ移ります。**

Let's Encrypt の証明書は、**ISRG Root X1** という大元の証明書（根）から辿れます。
この根は、Windows にも各ブラウザにもスマホにも、最初から入っています。
だから、**信頼させる作業が丸ごと消えます。**

## 2. 選択肢は2つ

社外から w-cms へ届く道の作り方は、2つあります。

### A. 固定IPで社内サーバーに直結

会社のルータが、外から届いた通信（443番＝HTTPS の入口）を、社内の w-cms へそのまま回す形です。

```
スマホ・社外 ──▶ ルータ（443を転送）──▶ 社内 w-cms
社内PC ──────────────────────────▶ 社内 w-cms
```

- 証明書は **HTTP-01 がそのまま使えます**。
  HTTP-01 は、Let's Encrypt が「このホスト名の持ち主か」を、外から繋いで確かめる方式です。
  公開IPに Let's Encrypt が繋がるので、そのまま通ります。
- **部品がいちばん少ない**形です。
  証明書を配る仕掛けが要らないのは、地味に大きな利点です。90日ごとに壊れうる箇所が、1つ減ります。
- **社内に受信ポートを開けます**（受信ポートは、外から入ってくる通信の入口です）。
  図面のある機械が、直接インターネットに面します。

### B. VPS でリバースプロキシ

VPS が外からの通信を受け、トンネル（社内と VPS をつなぐ通り道）を通して、社内の w-cms へ中継する形です。

```
スマホ・社外 ──▶ VPS（公開IP・Let's Encrypt）──トンネル──▶ 社内 w-cms
社内PC ──────────────────────────────────────────────▶ 社内 w-cms（直結）
```

- トンネルは**社内から外向き**に張ります。だから、**ルータの受信ポートは閉じたまま**です。
- **回数制限や遮断をVPS側で**できます。w-cms の本体に触らずに済みます。
- **データは社内に残ります**。VPSは中継するだけです。
- **証明書を社内へ配る仕掛けが要ります**（90日ごと。自動化します）。
- 月額と、もう1台ぶんの運用が掛かります。

### 比べる

| | A. 固定IP直結 | B. VPS |
|---|---|---|
| 証明書 | HTTP-01・本体で取る | HTTP-01・VPSで取って**配る** |
| 社内から | **split-horizon が要る**（§4） | **split-horizon が要る**（§4） |
| 社内の速さ | 直結・最速 | 同（split-horizon 前提） |
| 社内へ開ける穴 | **443の受信** | **不要** |
| 図面のある機械 | 直接インターネットに面する | VPSが前に立つ |
| 回数制限 | サーバー本体でやる | VPS側でやれる |
| 部品の数 | **少ない** | 多い（VPS・トンネル・証明書の配布） |
| 費用 | ルータ設定だけ | 月額＋運用 |

**VPS の値打ちは「社内へ受信ポートを開けないこと」に集約されます。**

アプリへの攻撃そのものは、プロキシがあっても素通りします。
止まるのは、**社内網への到達**と、走査（外から手当たり次第に探りに来る通信）の雑音です。

## 3. WebDAV は外に出さない（決定）

**これがこの文書でいちばん実務に効く判断です。**

| | 誰が・どこから | 経路 |
|---|---|---|
| **画面（ブラウザ）** | スマホ・社外PC・社内PC | 公開する |
| **WebDAV（`/dav/`）** | 社内のPCだけ（CAD編集） | **社内直結。公開しない** |

理由が3つ揃います。

1. **スマホでCADは編集しません。** 外に出す用事がそもそもありません。
2. **Basic 認証を世界に晒さずに済みます。**
   Basic 認証は、要求のたびに合言葉（利用者名とパスワード）が流れる口です。
   締め出しは効きますが、晒さないに越したことはありません。
3. **プロキシ越しWebDAVの落とし穴が丸ごと消えます。** 落とし穴は、次の3つです。
   - `PROPFIND`/`LOCK`（WebDAV が使う要求の種類）を通すかどうか。
   - `client_max_body_size`。nginx（リバースプロキシによく使うソフト）が受け取る大きさの上限で、nginx の既定は**1MB**です。
   - タイムアウト（時間切れ）。

   **どれも「保存できたつもりで届いていない」を作る場所**です。
   2026-09-07 に Windows の無言の失敗を実測した直後なので、なおさら避けたいところです。

塞ぎ方は、公開の形で変わります。
リバースプロキシなら `/dav/` を拒否する一行、直結ならルータかサーバー側で絞ります。

## 4. どちらを選んでも要る——split-horizon DNS

**社内からの接続が、いちばんつまずきます。**

つまずく道筋は、次のとおりです。

1. 社内PCが `wcms.example.co.jp` を引くと、公開DNSは**グローバルIP**（インターネット側の住所）を返します。
2. そこへ社内から繋ぐと、ルータが通信を社内へ折り返す必要があります。これを**ヘアピンNAT**と呼びます。
3. **多くの業務用ルータはこれをしません。**

すると、**社外からは繋がるのに社内からだけ繋がらない**という、いちばん分かりにくい失敗になります。

**IPで逃げることもできません:**

```
https://192.168.1.10:8443/   →   証明書の名前と合わない → 警告
```

**Let's Encrypt はプライベートIPに証明書を出しません。**
プライベートIPは、社内だけで通じる住所のことです。

- 自己署名のときは、証明書にIPを入れられました（`-gencert` はそう作っています）。
- 公的な証明書に移ると、**社内でも必ずホスト名で繋ぐ**ことになります。

答えは **split-horizon DNS** です。
同じ名前を、引く場所によって別の住所に答えさせます。

```
社内で引くと  wcms.example.co.jp → 192.168.1.10   （直結・速い）
社外で引くと  wcms.example.co.jp → グローバルIP（またはVPS）
```

同じ名前・同じ証明書のまま、社内は直結になります。置き場所は3つ:

| | 向き |
|---|---|
| **ルータのローカルDNS機能** | いちばん手軽。台数を問わない |
| 社内DNSサーバー | ちゃんとやるなら |
| 各PCの hosts ファイル | **選べません**——スマホには書けない（社内Wi-Fiでも同じ名前を引く） |

## 5. 外に出す前に確かめること

### 契約と機器

- **プロバイダが 80/443 の受信を許しているか。**
  塞がれていると、HTTP-01 が使えません。
  そのときは、別の確かめ方である TLS-ALPN-01（443のみ）か DNS-01 になります。
- **ルータがローカルDNSを持っているか**（§4）。
  無いと、**スマホが社内Wi-Fiで繋がりません**。

### w-cms 側

- **総当たりへの備え。**
  ログインには、argon2id（パスワードを安全に保管するための方式）と締め出しがあります。
  （→ 2026-10-01 に、バックオフも入りました。続けて失敗すると、次を試せるまでの待ちが、失敗のたびに倍になります。`internal/auth/users.go`）
  それでも、外に出せば世界中から来ます。
  要るのは、プロキシでの回数制限か `fail2ban`（失敗を繰り返す接続元を遮断する道具）、そして**監査記録を見る習慣**です。
- **公開ページ。**
  2026-09-07 時点で**0件**です。
  実効公開は先祖すべての AND です（そのページと、親をたどった先のすべてが公開のときだけ公開になります）。
  だから、うっかり漏れる形にもなっていません。
  ただし、外へ出したあとは、`public` を立てた瞬間に**本当に世界に見えます**。
- **スマホの実機確認2点**（引き継ぎの宿題）。**LANで先にやれます。**
  - リンクのプロパティ欄が、画面右へはみ出さないか。
  - 薄青・薄赤が、小画面で見分けられるか。
- **スマホからの写真アップロード**が、実運用で要るか（現場写真）。要るなら、先に試します。

**この一覧のその後**（2026-10-14 に書き添えました）

- スマホの確認は、[作業引き継ぎ.md](../作業引き継ぎ.md) では済みになっています。
  「スマホ幅」は 2026-09-07 に実測済み（測る道具は `e2e/probe-phone.js`）、「スマホからの実機確認も済み」と書いてあります。
  ただ、上の2点を実機で見た記録そのものは、見つかりませんでした。
- スマホからの写真アップロードは、LAN の中で使えています。2026-10-03 に、利用者がスマホで写真を入れました（作業引き継ぎの「現在の状態（環境）」）。
- VPS は、まだ建てていません（作業引き継ぎの「次にやること」）。

## 6. 結論——**B（VPS リバースプロキシ）**

> 2026-09-07 利用者:「VPSにします」

**図面のある機械へ受信ポートを開けない**ことを採りました。
証明書を配る仕掛けが1つ増えますが、社内網への到達経路を持たせない利点がそれに勝る、という判断です。

**アプリ側の備えは実装済み**（同日）:

- **`/dav/` は転送されてきた要求を断ります。**
  - 判定は、`X-Forwarded-For` 等の有無です。当たれば 404 を返します。
    `X-Forwarded-For` は、プロキシが元の接続元を伝えるために付けるヘッダ（要求に添える情報）です。
  - 「WebDAV は公開しない」はプロキシの設定で実現しますが、**設定だけに頼りません**。
    `location /dav/` を書き忘れた日に、Basic 認証の口が黙って世界に開くからです。
  - 逃げ道は `WCMS_DAV_ALLOW_FORWARDED=1` です（プロキシ経由でしか届かない構成にしたいとき）。
- **`X-Forwarded-For` は元から扱えます**（`clientIP`・`isTrustedProxy`）。
  社内側のトンネル端点は loopback / private（自分自身か、社内の住所）なので、信頼されます。
  だから、**監査記録に本当の接続元が残ります**。

**VPS 側で要ること**（構築時に）:

```nginx
location /dav/ { return 404; }      # WebDAV は公開しない（§3）
client_max_body_size 64m;           # 既定 1MB では添付が通らない
limit_req zone=login burst=5;       # 総当たりへの備え（§5）
```

**先に決まっていること:**

1. **WebDAV は公開しない**（§3）
2. **split-horizon DNS を最初から入れる**（§4）。あとから足すと、構成が二度手間になります。
3. **社内でもホスト名で繋ぐ**（IP直打ちは証明書が合わない）
