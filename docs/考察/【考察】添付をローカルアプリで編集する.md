## 1. 何が欲しいのか

ワンノートの体験を分解すると、**4つの動作が繋がっている**ことが分かります。

```
①クリック → ②ローカルのアプリが開く → ③Ctrl+S → ④サーバー側が新しくなる
```

この①〜④のつながりを、この文書では「輪」と呼びます。

いま w-cms にあるのは、①と、②の半分（ダウンロード）だけです。**③と④が無い**のです。

- ダウンロードしたファイルは、ブラウザの保存先にあります。編集しても、誰も見ていません。
- 人が手で再アップロードすれば繋がります。しかし、それは「Ctrl+S」ではありません。

**AutoCAD・SolidWorks・画像編集ソフトのどれでも**、同じ形で動く必要があります。
拡張子ごとに違う仕掛けを作ると、対応表を永久に育てることになります。

### 1.1 編集するのは**自社のファイル**——メール由来のものではない

> 2026-09-07 利用者:「ワンノートを見てもらえばわかりますが、編集するCADファイルは弊社の物です。
> メール由来のものではありません」

**この区別が、この文書でいちばん大事な線です。** 添付には、出自の違う2種類があります。

| | 出自 | 例 | 書き換えてよいか |
|---|---|---|---|
| **届いたもの** | 通信記録（メール・FAX）の添付 | 客先支給の図面PDF・DXF | **駄目**——届いた事実の証拠。書き換えたら「何を受け取ったか」が消える |
| **自社のもの** | 人が加工製品ページへ置いたファイル | CAM用DXF・自社作図・注記した画像 | **よい**——作った人が直すのが仕事 |

実データが、この2種類をはっきり分けています。

- DXF 911件のうち、**896件は自社のCAM用**（表題欄なし）です。これらは、**取り込み口を通っていません**。
- 客先から届くDXFは、11件です。そちらは、通信記録の添付です
  （[作業引き継ぎ.md](../作業引き継ぎ.md) の「DXFは2種類ある」）。

**線の引き方も、既にある原則そのまま**です。
原則は「**記録は動かしません**」です（[【考察】通信記録処理.md](【考察】通信記録処理.md) §3.2）。

- 通信箱の下にある添付は、記録なので、読み取り専用です。
- 加工製品ページなどに人が置いたファイルは、編集できます。
- **置き場所が権限を決める**ので、ファイルごとの印は要りません。

## 2. 取りうる道は4つ

A〜D の4つを比べました。2026-09-07 は A を選びました（§6）。
2026-09-18 に、本命は B に替わりました（§7）。

### A. WebDAV——サーバーをネットワークドライブとして見せる

Windows のエクスプローラで「ネットワークドライブの割り当て」をすると、
`\\localhost@8080\DavWWWRoot\...` のようなパスでファイルが見えます。
**そこから開いたファイルは、アプリにとって普通のファイル**なので、Ctrl+S が素直に効きます。

⚠ これは、2026-09-07 の見立てです。
実物の CAD で試すと、Ctrl+S はアプリを閉じるまで w-cms に届きませんでした（2026-09-18・§7 の決定ログ）。

- **①②③④が全部つながります。** 特別な仕掛けは、ブラウザ側にも要りません。
- **実装の材料は既にあります**。
  - `golang.org/x/net/webdav` は、**いま使っている依存の中**にあります
    （`x/net` は HTML パースで既に直接依存）。
  - **新しいモジュールはゼロ**です。開発方針の「外部依存の最小化」に抵触しません。
- 認証は、**HTTPの世界の話**です。
  そのため、セッションCookie（ログインしたことを覚えておく印）ではなく、Basic か Digest になります。

**Windows のWebDAVクライアントには既知の癖があります**（実装前に確かめること）:

| 癖 | 影響 | 逃げ道 |
|---|---|---|
| 平文HTTPでの Basic 認証を既定で拒否 | ログインできない | HTTPS にする（本番は要る）／レジストリ `BasicAuthLevel`（＝各PCの設定・避けたい） |
| 既定の最大ファイルサイズが 50MB | 大きなCADが開けない | レジストリ `FileSizeLimitInBytes`（同上） |
| `WebClient` サービスが止まっていることがある | 割り当てできない | サービスを自動起動に |
| 認証が切れると無言で失敗する | 保存できたように見えて消える | **要検証**（いちばん怖い） |

### B. カスタムURLスキーム＋常駐ヘルパー（`w-cms://edit?...`）

各PCに小さなヘルパーを入れ、`w-cms://` を登録します。
`w-cms://` のような、アプリを呼び出すための自前のアドレスの形を、カスタムURLスキームと呼びます。

ブラウザでクリックすると、ヘルパーが起動して、次のことをします。

- ① 一時フォルダへ落とす
- ② 既定のアプリで開く
- ③ ファイルの変更を見張る（`fsnotify` 相当）
- ④ 変わったら、サーバーへ PUT する

Confluence・Nextcloud・Jira の「デスクトップアプリで編集」は、この形です。

- **狙った体験にいちばん近い**。認証も、w-cms のセッションを引き継げます。
- **各PCへインストールが要ります**（レジストリ登録つき）。
  ヘルパーは Go で書けるので、モジュールは増えません。しかし、**配布するものが1つ増えます**。
- ⚠ **攻撃面が増えます**。攻撃面は、外から悪用されうる入口のことです。
  - `w-cms://` は、どのWebページからでも叩けます。
  - だから、ヘルパーは**URLのホストを検証し、使い捨ての鍵を要求する**必要があります。
  - ここを間違えると、「任意のサイトが社内ファイルを書き換えられる口」になります。

> **この節のその後**: B は、2026-09-29 に `cmd/w-cms-edit` として作りました（§7 の決定ログの最後の行）。
> 実際の形は、上の案と少し違います。
>
> - アドレスの形は `w-cms-edit:<w-cms のアドレス>#<鍵>` です（`cmd/w-cms-edit/link.go`）。
> - 鍵は、そのファイル1つに限る使い捨てのものです。ヘルパーは、登録した w-cms にしか繋ぎません。実行できる種類は開きません。
> - 変更の見張りは、`fsnotify` ではなく、ファイルの大きさと時刻を見る形です（`cmd/w-cms-edit/main.go`）。

### C. File System Access API（ブラウザだけで完結）

Chromium 系のブラウザなら、`showSaveFilePicker` でローカルのファイルハンドルを得て、
**ブラウザから書き戻せます**。ファイルハンドルは、手元のファイルを読み書きするための取っ手です。

- **ローカルのアプリを起動できません**。②が無いので、この案だけでは輪が閉じません。
- 「w-cms が保存先を覚えていて、人がアプリで保存したあとブラウザで『取り込む』を押す」
  という**半自動**にはなります。Ctrl+S ではありません。

### D. いまのまま（ダウンロード → 手で再アップロード）

- 追加の仕掛けはゼロです。**回数が少ないうちはこれで足ります**。
- 図面の修正が日常なら、確実に摩耗します。

## 3. w-cms 側で先に決めることが3つある

道を選ぶ前に、**どの道を選んでも必要になる**決定が3つあります。
ここが未決のまま実装すると、静かに壊れる形になります。

この節は、決める前に整理した論点です。決めた結果は、§6e にあります。

### 3.1 添付には版が無い

ページ本文には、版があります（`versions/`・リバートできる）。**添付には版がありません。**

上書き保存を許すと、**前のCADファイルは消えます**。
編集ミスも、間違ったファイルを開いたことも、取り返せません。

既存の決定は「編集結果は**別ファイル保存（原本残置）**が本命」でした
（[【考察】添付ファイルの表示と操作.md](【考察】添付ファイルの表示と操作.md) §3）。

- これは、画像の加工（回転・切り抜き）についての判断です。
  **CADの継続的な修正とは性質が違います**。
- 別ファイルにすると、`Q140-003_v2.dxf` `..._v3.dxf` が増えます。
- すると、**どれが最新か分からなくなる問題**が、添付の側で再発します。
  これは、旧版を子ページへ移した理由そのものです。

なお、**§1.1 の線引きで「原本残置」は別の形で守られます**。

- 届いたファイルは、そもそも書き換えられません。だから、**原本は通信記録の側に必ず残ります**。
- ここで版を積むのは、自社の作業ファイルについてです。失われるのは「自分の前回の作業」です。

選べる形は3つ:

| | 上書き | 版を積む | 別ファイル |
|---|---|---|---|
| 最新がどれか | 明らか | 明らか | **分からなくなる** |
| 前へ戻せる | **戻せない** | 戻せる | 戻せる |
| 置き場 | `files/<ID>.dxf` | `files/versions/<ID>/<時刻>.dxf` | `files/<別ID>.dxf` |

**「上書き＋版を積む」が本文と同じ形**で、いちばん筋が通っています。
ページ本文がそうしているのだから、添付だけ違う原理にする理由がありません。

### 3.2 誰かが同時に開いたら

ページには編集ロックがあります。**添付にはありません。**
2人が同じDXFを開いて、両方が Ctrl+S すると、**後の保存が前を黙って消します**。

- WebDAV には `LOCK` があります（`x/net/webdav` も実装しています）。
  Windows は、Office ファイルでこれを使います。
- **CADアプリが LOCK を送るかは分かりません**。実装前に、実物で確かめる必要があります。
- 送らないなら、w-cms 側で「開いた人・時刻」を記録して、**警告する**（止めない）のが現実的です。

### 3.3 上書きされたあと、派生をどうするか

**§1.1 の線引きで、この心配はほとんど消えます。**

- 解析（図面番号・図面名称の抽出、`✓ 図面` の印）が掛かるのは、**届いたファイル**です。
  そして、届いたファイルは読み取り専用です。
- 自社のCAM用DXFは、取り込み口を通らず、解析もされていません。

残るのは、**更新時刻**です。

- 添付を書き換えても、ページの本文は変わりません。
  いまの仕組みでは、「いつ直したか」がどこにも出ません。
- **「添付が変わったらページを触ったことにする」**（更新時刻を進める）だけは要ります。
- 子ページの並びや「最近の更新」が、実際の作業とずれるためです。

## 4. 名前の問題——`19ux.dxf` が開く

添付の保存名は、**生成ID**です（`19ux.pdf`）。
元の名前は、本文のリンク文字と `download` 属性が運んでいます。

WebDAV でフォルダとして見せるとき、**アプリのタイトルバーに `19ux.dxf` と出ます**。
CADの図面名としては、役に立ちません。

逃げ道は、「WebDAV の見せかけの名前を、元のファイル名にする」ことです。

- `x/net/webdav` の `FileSystem` は、自前で実装できます。
- だから、**`ページID/元の名前.dxf` で見せて、実体は `files/19ux.dxf` へ繋ぐ**ことができます。
- ただし、**元の名前は本文の中にある**ので、
  WebDAV の一覧を出すたびに、本文を読むことになります（重い・要検討）。

**→ 2026-09-17 にそうしました。**

- 元の名前は、本文ではなく、**添付の目録 `files/meta.json`**から取ります。
  目録は、保存時に機械が書く「届いた事実」です。本文は読みません。
- 一覧は、届いたときの名前で出ます。
- 同じ名前が2つあれば、保存名を添えて解きます（`補強ストッパー (a1b2).dxf`）。
- **保存名でも引ける**ので、`19ux.dxf` のショートカットも切れません。
- 目録の無い古い添付は、保存名のままです。

## 5. どこまでを w-cms が持つべきか

**ローカルアプリの起動は、ブラウザにはできません**（できたら攻撃です）。
だから、②を実現する主体は、必ず「OSに登録された何か」です。
ネットワークドライブ（A）か、インストールしたヘルパー（B）です。
**w-cms が単体で完結させる道はありません。**

その前提で、A と B の違いは、**どこに複雑さを置くか**です。

- **A は OS の機能に乗る。**
  w-cms 側は、WebDAV を喋るだけです。癖は、Windows のものです。
  癖が出たときに直せるのは Microsoft だけ、という弱みがあります。
- **B は自分で全部持つ。**
  癖は自分のもので、直せます。
  代わりに、**配る・入れる・更新する**が発生します。攻撃面も、自分で守ることになります。

## 6. 結論——A（WebDAV）から。ただし読み取り専用で試す

⚠ **これは 2026-09-07 の結論です。2026-09-18 に改まりました。**
WebDAV では、Ctrl+S がアプリを閉じるまで届きませんでした。
そのため、本命は B（常駐ヘルパー）に替わっています（§7 の決定ログ）。
以下は、当時の結論の記録です。

**順序が肝**です。いきなり書き込みを許すと、§3 の3つが未決のまま、「消えた」が起きます。

1. **読み取り専用の WebDAV を出す**（`x/net/webdav`・新しい依存ゼロ）。
   - ページの添付フォルダをドライブとして見せ、**CADアプリから開けるか**を実物で確かめます。
   - ここで、Windows の癖（サイズ上限・認証・サービス）が全部出ます。**出させるのが目的**です。
2. 開けたら、**§1.1 の線引きを先に実装する**。
   - 通信箱の下の添付は読み取り専用、それ以外は書き込み可です。
   - **置き場所で決まる**ので、ファイルごとの印は要りません。
3. **§3.1（版）を決めてから**書き込みを許す。「上書き＋版を積む」を推します。
4. §3.2（同時編集）は、まず**警告だけ**。CADアプリが `LOCK` を送るかを見てから決めます。

## 6a. 試用の結果（2026-09-07・実装して測った）

読み取り専用の WebDAV を実装し（`internal/cms/webdav.go`・`WCMS_DAV=1` で開く）、
**実データで試しました**。

**HTTPとしては完全に動いています**（`curl`）:

```
PROPFIND /dav/010256/   → 207 一覧に添付6件
GET      /dav/010256/5jl9.pdf → 200 158,526バイト application/pdf
PUT      （書き込み）    → 403
認証なし                → 401 ＋ WWW-Authenticate: Basic
```

**ところが Windows のエクスプローラからは繋がりません。**
`net use` は、「システムエラー 67（ネットワーク名が見つかりません）」で失敗します。

**サーバー側の記録が原因を1行で示しました**:

```
WebDAV OPTIONS /dav/010256 auth=false     ← 要求はこれ1つきり
```

起きていたことは、次のとおりです。

- Windows は、**認証情報を付けずに1回だけ**問い合わせます。
  401（認証が要る、という応答）を受け取ったところで、**諦めています**。
- `BasicAuthLevel=1`（既定）は、「平文HTTPでは Basic を送らない」という設定です。
- そのため、**送らないまま失敗し、しかも認証の失敗としては報告されません**。
- 「ネットワーク名が見つかりません」と出るので、原因にたどり着きにくい形です。

この機械での実測値:

| | 値 | 意味 |
|---|---|---|
| `WebClient` サービス | Running（スタートアップは手動） | 動いてはいる |
| `BasicAuthLevel` | **1**（＝SSLのみ） | **これが原因**。平文HTTPでは Basic を送らない |
| `FileSizeLimitInBytes` | **50,000,000**（約47.7MB） | 大きなCADはこの先で詰まる |

### 逃げ道は事実上ひとつ——HTTPS

- **Digest 認証は使えません。**
  - Digest は、サーバー側に `MD5(利用者:realm:合言葉)` が必要です。
  - しかし、w-cms が持っているのは、**argon2id のハッシュ**だけです。
    ハッシュは、合言葉を元へ戻せない形に変えた値です。
  - 合言葉から別の形をもう1つ保存しない限り、成立しません。
    **保存すべきではない**ので、この道は塞がっています。
- **レジストリ（`BasicAuthLevel=2`）は各PCの設定**なので、配る運用になります。
  - 「WebDAVはインストール不要」という利点が消えます。
  - そのうえ、**その端末の平文Basicを w-cms 以外に対しても許すこと**になります。勧めません。
- **HTTPS にすれば素直に通ります。**
  もともと本番では要るものです。
  **WebDAV は「HTTPS化の先にある機能」**と位置づけるのが正しい、と分かりました。

## 6b. HTTPS化（2026-09-07・同日に実装）

`-gencert` で自己署名の証明書を作り、`WCMS_TLS_CERT` / `WCMS_TLS_KEY` を置くと、
**:8443 で HTTPS 待ち受け**になります（`cmd/w-cms/tls.go`）。

**HTTPS では全部動きます**（`curl`）:

```
PROPFIND https://localhost:8443/dav/010256/   → 207
GET      …/5jl9.pdf                           → 200（158,526バイト）
ログイン（Secure Cookie を既定の有効のまま）    → 302 ＋ authenticated:true
```

**Windows の壁は、進みましたがまだ残っています。**

| | 平文HTTP | HTTPS（証明書は未信頼） |
|---|---|---|
| `net use` の結果 | エラー **67**（ネットワーク名が見つかりません） | エラー **1244**（認証されていない） |
| サーバーに届いた要求 | `OPTIONS` 1回（認証情報なし） | **ゼロ** |

**エラーの種類が変わったことが手掛かり**です。

- 67 は、「そもそも辿り着けない」です。
- 1244 は、「認証の段で断られた」です。
- つまり、`BasicAuthLevel` の壁は越えました。
  **証明書を信頼していないところで止まっている**と読めます。

残る一手は、**各PCで証明書を信頼させること**です。
これは、**管理者権限とUIの確認**が要ります（自動では通せません）:

```powershell
# PowerShell を「管理者として実行」して、この1行を貼る（改行で分けない）
Import-Certificate -FilePath "C:\...\w-cms\data\tls\cert.pem" -CertStoreLocation Cert:\LocalMachine\Root
```

> **1行で書くこと。**
> バッククォートの継続（PowerShell）も `^`（cmd.exe）も、貼り付け先によっては通りません。
> ここは1回きりの操作なので、長くても1行が確実です。

**`BasicAuthLevel` を変えるのとの違い**は、緩める範囲です。

- レジストリ変更は、**その端末の平文Basicを w-cms 以外に対しても許します**。
- 証明書の信頼は、**その1枚を信じるだけ**です。
- 1台1回で、あとは普通に使えます。

### 6c. 信頼させたら通りました（2026-09-07・実測）

証明書を `LocalMachine\Root` へ入れたあと、**エクスプローラから割り当てられました**。

```
net use * https://localhost:8443/dav/010256 /user:a a
  → Drive Z: is now connected.

Z: の一覧          5jl9.pdf 158,526 / b49d.eml 1,893,152 / hik0.step 481,941 …
Z: の 5jl9.pdf     読める（先頭は %PDF-）
Z: への書き込み     拒否（読み取り専用が効いている）
```

**エラーの道筋は 67 →（HTTPS化）→ 1244 →（証明書の信頼）→ 成功**でした。

`BasicAuthLevel` は、**触っていません**。HTTPS にすれば、当てはまらない設定だからです。
最後まで残った原因は、「証明書を信頼していないこと」1つでした。

⚠ **指紋を照らし合わせること。**
指紋は、証明書を見分けるための短い値です。

- `-gencert` を走らせるたびに、別の証明書ができます。
- **信頼させたものと、サーバーが出しているものが同じか**を、確かめてから試してください。
- 1度、これで食い違わせました。

```powershell
Get-ChildItem Cert:\LocalMachine\Root | Where-Object { $_.Subject -like "*w-cms*" } | Select-Object Thumbprint
```

## 6e. 書き込みを通しました（2026-09-07）——そして無言の失敗を見つけました

§3 の2つを決めて、実装しました（`webdav_write.go`）。

**決定1: 上書きするが、版を積む。**

- 前の中身は、`files/.versions/<名前>/<時刻>.<拡張子>` へ入れます。
- 本文が版を持つのに、添付だけ持たないのは、筋が通りません。
  CADの修正は、取り返せないと重すぎます。
- `.` 始まりなので、WebDAV の一覧にも、素の添付配信にも出ません。

**決定2: 同時編集は止めない。取り返せるようにする。**

- 止める仕掛け（ロック）は、CADアプリが `LOCK` を送るかに懸かっています。
- 送らないアプリでは効きません。それなのに、「守られている」と思わせます。
- **`LOCK` は通す**ので、送るアプリには、本来の守りが効きます。

**書ける範囲は設定が決めます**（`webdav_readonly`・祖先まで効く）。

**新しいファイルは作れません**。
作れるようにすると、拡張子の許可リストと大きさの上限を素通りします。そこは、別に決めます。

> **この節のその後**: 2026-09-18 に、実物の RootPro CAD で保存したとき、`PROPPATCH` を塞いでいたために `PUT` まで届かないことが分かりました。
> `PROPPATCH` を通すようにし、あわせて「一時ファイルが空なら差し替えない」守りを足しました（2つで1組です）。
> 知らないと壊す注意は、[作業引き継ぎ.md](../作業引き継ぎ.md) の罠の節「WebDAV・QR」にあります。

実データでの往復:

```

書き込み（ドライブ越しに追記）
編集後  448バイト
版      .versions/ff4v.dxf/20260907T020358Z.dxf … 416バイト（前の中身）
監査    dav.write 010264/ff4v.dxf
```

### ⚠ Windows は「保存できた」と嘘をつきます

読み取り専用に指定した範囲（`通信箱`）へ、書いてみました。
すると、**PowerShell には成功と返り、サーバーは断っていました**:

```

実ファイル     変わっていない（前日のまま）
```

Windows の WebDAV クライアントが、
**書き込みをローカルに溜めて成功を返し、そのあとの PUT 拒否を呼び出し元へ伝えていません**。

これは、§2 の表で「いちばん怖い」と書いた欄（認証が切れると無言で失敗する）と、同じ質のものです。
**拒否でも起きる**と分かりました。

⚠ **結果として、読み取り専用の範囲は「見せない」ほうが安全です。**

- 見えていると、人は開いて、直して、保存します。
  そして、**保存できたと信じたまま作業を失います**。
- `webdav_readonly` は、権限による拒否（読めるが書けないページ）の守りとして残します。
- しかし、**届いた添付を守るなら `webdav_hidden` で隠すほうが確実**です。
  読むのは、ブラウザで足ります。
