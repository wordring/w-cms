## 0. 何を決めたいか

利用者（2026-09-27 夜）:

> 材料と外注加工、その他では、必要な項目が違うため、発注部材表にうまく入りません

> 外注加工以外に、購入部品、支給部品も必要です。塗装を発注する場合、色も必要です。
> まずどうするか考察が必要です。どの列が必要か設定ファイルに書きましょうか？

> （購入部品の「仕様」、外注加工の「支給」「資料」は）検討が必要です

> 外注加工で図面を添付するような場合、どうしますか？

同じ日の夕方、必要部材表に外注加工を出しました（それまでは材料と購入部品だけ）。ところが運ぶ道が
材料と購入部品の形のままなので、**外注加工の行は品名の欄に「レーザー切断」が入るだけ**になり、
外注先には**どの部品を加工するのか**が伝わりません。

## 1. いま（2026-09-27 夜に調べた事実）

### 1.1 元の表（加工製品ページ）と、発注の表

| 表 | 列 |
|---|---|
| 材料 | 材質・形状・寸法・個数・備考・区分 |
| 外注加工 | 加工内容・支給・個数・推奨業者・資料（ref）・備考・区分 |
| 購入部品 | 品名・仕様・個数・備考・区分 |
| 支給部品 | 品名・仕様・個数・備考・区分 |
| **発注部材表・発注明細**（同じ12列・`orderItemColumns()`） | 弊社品番・品番・品名・材質・形状・寸法・表面・数量・単位・単価・備考・状態 |

- 【要求】発注フォルダ:「部材の種類によって発注明細に必要な項目は変わりますが、**表はすべての項目の集合**
  となります。PDFを作成するときに空の項目を消す」——**実装済み**（`readOrderDoc` が、どの行にも値の無い列を
  刷らない。`金額` だけは計算列なので常に刷る）。
- ⚠ 加工製品ページのテンプレートの外注加工の表には `推奨業者` の列がありません（登録には在る）。

### 1.2 必要部材表 → 発注部材表 → 発注書で運ばれるもの

| 種類 | 運ばれる | 落ちる |
|---|---|---|
| 材料 | 材質・形状・寸法・数量・参考単価 | — |
| 購入部品 | 品名・数量 | 仕様・推奨業者・備考 |
| 外注加工 | 品名＝**加工内容**・数量 | **何の部品か**（品番・図面名称）・支給・**資料**・推奨業者・備考 |
| 支給部品 | —（必要部材表に出していない） | — |

- 運ぶ値は固定です（必要部材表の行の属性 `unorderedRowAttrs`→画面の `lineOf`→`/api/our-order/draft`→
  発注書を作るとき `draftLinesOf`→`ourOrderLine`）。**種類（材料・購入部品・外注加工）も途中で落ちます**——
  発注書の行が外注加工かどうかは、行からは分かりません。
- 手配済みを数える鍵は、材料なら材質・形状・寸法、それ以外は**品名**（`orderedByProduct`・`draftedQty`）。
  外注加工の品名を「図面名称」に変えると、この鍵も変える必要があります。

### 1.3 図面を相手へ渡す部品

- **メールの口**（`/api/mail/send`）は、**複数の添付・別ページのファイル・`.dxf`**（設定 `attachment_extensions`）を
  受け付けます（送る人がそのページを読めること・合計25MB）。控えにも添付へのリンクが残ります。
- ⚠ **発注書の送信画面は、添付を発注書PDF 1本に固定しています**（`order_send.go`・`app.js` の `sendMail`）。
  人が添付を足す欄はありません（通信記録の「✉️ 返信」には、ページの添付を選ぶ欄があります）。
- **FAX・手渡しは印を付けるだけ**です（FAXサーバーはまだ無い）。
- **外注加工の `資料` 列**（ref）は「加工業者に渡す資料」の置き場として宣言済み——**値は添付への参照**
  （`ページID-ブロックID`）で、加工図面を加工製品ページに貼って、ここから指す設計です。**読むコードはまだ無い**。
- **図面ブロック**の `受信元`（顧客から届いた図面PDF）・`対応DXF` はタグで引けます——ただし指す先は
  **通信箱の記録ページ**の添付です（加工製品ページではない）。
- **発注書PDFの後ろに図面PDFを綴じる口**は既にあります——gopdf の `ImportPage`／`ImportPagesFromSource`
  （依存の gofpdi は承認済み・いまは使っていない）。⚠ 読めないPDFで `panic` するので `recover` が要ります。
- ⚠ 参照（`ページID-添付ID`）を保存名（`<ID>.<拡張子>`）へ解く口は、コアの中にあって公開されていません。

### 1.4 ついでに見つけた食い違い（未対応）

- **単価が全部空でも、紙に `金額 0` と `合計金額（税抜） 0 円` が刷られます**——【要求】「単価を書かない発注書が
  あります（実物の材料2枚は単価も合計も空欄）」「0とは別」と食い違い。
- **メールで送るたびにPDFを作り直しています**——【要求】「送るのは表示している最新のPDF（送る直前に作り直さない）」
  と食い違い（作業引き継ぎ 0a10 の「再送とキャンセル」の残りと同じ話）。

## 2. 問題の形——3か所で合っていない

1. **発注の表に列が足りない**——加工内容・仕様・支給・資料（表面は在る）。
2. **元の表に置き場が足りない**——**塗装の色**を加工製品ページのどこに書くか（外注加工の表に色の列が無い）。
   テンプレートの外注加工の表には推奨業者も無い。
3. **運ぶ道が種類を知らない**——種類ごとに運ぶ値が違うのに、道は1本の固定の組で、種類も落ちる。

## 3. 案——「種類ごとに、どの列をどこから運ぶか」を設定に書く（利用者の案）

東邦の設定（`config/settings.json` の `extensions.toho`）に、**種類ごとの運び方**を書きます。

```json
"order_kinds": [
  { "kind": "材料", "from": "材料", "key": ["材質", "形状", "寸法"],
    "columns": { "材質": "材質", "形状": "形状", "寸法": "寸法", "数量": "個数" } },
  { "kind": "外注加工", "from": "外注加工", "key": ["加工内容"],
    "columns": { "品番": "@品番|@図面番号", "品名": "@図面名称", "加工内容": "加工内容",
                 "表面": "表面", "支給": "支給", "資料": "資料", "数量": "個数" } },
  { "kind": "購入部品", "from": "購入部品", "key": ["品名"],
    "columns": { "品名": "品名", "仕様": "仕様", "数量": "個数" } },
  { "kind": "支給部品", "from": "支給部品", "key": ["品名"],
    "columns": { "品名": "品名", "仕様": "仕様", "数量": "個数" } }
]
```

- `columns` の**左が発注部材表・発注明細の見出し**、**右が元の表の見出し**（`@名前` は加工製品ページのタグ・
  `|` は「無ければ次」）。`数量` は元の個数×受注数（いまと同じ）。
- `key` は**手配済みを数える鍵**——同じ値が発注書の行にあれば「もう手配した」。
- **発注の表の列は、全種類の左側の和集合**です——【要求】の「すべての項目の集合」と同じで、紙では空の列が消える
  （実装済み）。発注書はテンプレートの表を埋めるので（テンプレート駆動 D）、**テンプレートに無い列は値があれば
  右端へ足されます**——列の並びはテンプレートで決められます。
- 種類は**どの表から来たか**で決まるので、途中で落とさずに運びます（発注の表に `種類` の列を持つか、
  運ぶ値に添えるか——§6 の問い）。
- **置き場所は拡張**（東邦の業務の規則・開発方針 §0）。コアは「設定から語を読む」口と、表を埋める道具
  （`PageDraft.FillTable`）を貸すだけ。表の種類の登録をコードから出す方向（DBの日本語化 4-5）とも向きが同じ。

**利点**: 種類を足す・列を足すのが**設定の1行**で済む（運用者が足せる——複数運用者の前提）。
**難点**: 設定が「表の見出しの言葉」に依存する——見出しを改名したら設定も直す必要がある（保存のときの
告知で知らせられる）。手配済みの鍵を種類ごとに持つので、**鍵を変えると既存の発注書と結ばれなくなる**。

## 4. 外注加工で図面を添付するとき（利用者の問い）

**おすすめ: 加工製品ページの外注加工の表の `資料` 列に「渡す図面」を書いておき、発注書を送るときにそれを
添付の候補として並べる**（毎回探して選ばなくてよい・人が外せる）。

| 送り方 | 図面の渡し方 |
|---|---|
| メール | 発注書PDF＋`資料` が指すファイル（PDF・DXF）を添付。送信欄に候補を並べ、人が外せる |
| FAX・手渡し | **図面PDFを発注書PDFの後ろのページに綴じる**（gopdf の `ImportPage`）。⚠ DXF は紙にできないので、FAX では渡せないと画面で言う |

- **`資料` が空なら、図面ブロックの `受信元`（顧客の図面PDF）・`対応DXF` を候補に出す**——ただし**顧客の図面を
  そのまま外注先へ渡してよいか**（守秘・版の取り違え）は利用者の判断（§6）。弊社で描き直した加工図（展開DXF など）を
  渡すなら `資料` に書く。
- 運ぶ道: 必要部材表 → 発注部材表 → 発注明細に `資料` の列（ref）を持たせる（§3 の設定で「資料」を運ぶ）。
  発注書ページの送信欄は、発注明細の `資料` を集めて候補にする。
- 足りない部品: ① 参照→保存名の公開の口（コア）② 送信欄の候補の一覧（`order_send.go`・`app.js`）③ PDFの綴じ込み
  （`order_pdf.go`・`recover`）④ 25MB の上限と、図面の置き場の読み権限（通信箱のページを外注担当が読めるか）。

## 5. 段取り（案）

1. §6 の答えで設定の形を決める（まず材料・外注加工・購入部品の3種類）。
2. 設定を読む口（`extensions.toho.order_kinds`）と、必要部材表の集計・運ぶ道を設定から組む形へ（いまの固定の組をやめる）。
3. 発注書テンプレートの発注明細に、決めた列を足す（職場のテンプレート）。
4. 図面の添付（§4）——メールの候補 → PDF の綴じ込み。
5. §1.4 の食い違い（金額0・送るたびの作り直し）は別に直す。

## 6. 聞くこと

1. **支給部品を必要部材表に出す意味**——お客様から支給される部品を「手配する」とは何か（お客様への催促？
   弊社から外注先へ支給する部品？）。発注書（紙）にするのか、別の知らせなのか。
2. **塗装の色の置き場**——外注加工の表に `表面`（色・鍍金・生地）の列を足して、発注明細の `表面` へ運ぶ形でよいか。
   塗装・鍍金は外注加工の表に書くのか、別の表（`塗装`）にするのか。
3. **外注加工の発注明細の品名**——部品（図面名称）にして、加工内容は別の列（`加工内容`）でよいか。品番は加工製品の
   `品番`、無ければ `図面番号` でよいか。
4. **設定の形**（§3 のスケッチ）でよいか。種類を発注の表の列（`種類`）として見せるか。
5. **図面の渡し方**（§4）——`資料` 列で決めておく形でよいか。顧客の図面をそのまま外注先へ渡してよいか。
6. **購入部品の `仕様`・外注加工の `支給`・`推奨業者`・行の `備考`** を紙に出すか（列にするか、落とすか）。
