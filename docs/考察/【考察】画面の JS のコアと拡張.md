## 1. いまの形（2026-10-20 に調べた）

- サーバーは、もう拡張ごとに分かれています。拡張は `init()` で `cms.RegisterExtension` などを呼び、登録の仕組みでコアに載ります。
- 画面の JS は、ほぼ全部が1本の `assets/app.js`（12,884 行）です。東邦と通信の働きも、この中にあります。
  - 東邦の配線は、後ろにまとまっています（10,745 行目から最後まで、約2,100 行）。
  - 整理の欄・メールの飾り・電話・連絡先などは、前半に散らばっています。
  - モードを切り替えるたびに飾りを付け直す一覧（`applyMode` の中）が、業務の飾りを名指しで呼んでいます。
- ファイルどうしは `window.` の名前で呼び合っています。`app.js`（コア）が `mail-compose.js`（通信）の `window.wcmsMailCompose` を呼んでいるのは、向きが逆です。

## 2. 決めたこと

### 2.1 向きは1つ

- 拡張の JS はコアの JS を借りてよい。コアの JS は拡張の JS を借りない（名前も呼ばない）。
- コアが拡張の働きを呼びたい所は、コアが登録の仕組みを用意し、拡張がそこに自分を登録します（サーバーの `RegisterMirror` と同じ形）。

### 2.2 コアが渡すのは `window.wcms` の1つ

- コアの `app.js` は、拡張に渡す道具と登録の仕組みを `window.wcms` にまとめます（凍らせて、拡張が書き換えられないようにする）。
- 拡張の JS は `window.wcms` だけを使います。ここに無いコアの中身には手を出しません。
- 足すときは必要な分だけにします（登録の仕組みが増えすぎると、コアと拡張の約束が太るため）。
- 最初の版の中身は、次のとおりです。
  - 登録の仕組み: `onChrome(fn)`。モードを切り替えるたび（と読み直したとき）に、飾りを付け直します。
    登録が遅れても、もう描いたあとなら、すぐ1度呼びます。拡張の飾りが落ちても、コアは止まりません（呼び出しを包むため）。
  - 道具: 要素を作る（`makeEl`・`makeButton`）・JSON を送る（`jsonPost`・`postJSON`・`readResult`・`failMessage`）・知らせる（`notify`）・ページの番号（`pageId()`）・タグの値（`tagValue`）・拡張が載っているか（`hasExtension`）・本文の欄（`editorContent()`）・読み直す（`reloadContent`・`loadChildNav`）など。

### 2.3 拡張の JS は、拡張の置き場に置き、拡張が登録する

- 拡張の JS は、その拡張のフォルダに置きます（例: `ext/comm/assets/comm.js`）。
- 拡張は `init()` で `cms.RegisterScript` を呼んで、自分の JS を名乗ります。サーバーは `/assets/ext/<拡張>/<ファイル>` として配り、画面の枠（`index.html`）の `<!--WCMS_EXT_SCRIPTS-->` に `<script src>` を差し込みます。
- いまは: この節は §4.4（2026-10-20 夕）で改めました。`cms.RegisterScript` はもうありません。
  拡張は `cms.RegisterExtension` を呼ぶだけで、サーバーが `ext/<名前>/assets/` のファイルを置き場の決まりで拾います（`internal/cms/ext_scripts.go`）。
  CSS は `<!--WCMS_EXT_STYLES-->` に差し込みます。
- ビルドで外した拡張は、登録しないので、その JS も配られません。
- `assets/` と同じく、ディスクから配ります（入れ替えなしで直せる・E2E の写しの道具がそのまま使える）。配り方も `assets/` と同じ `no-cache` です。

### 2.4 モジュール（import／export）は、あとで決める

- いまの `app.js` は地続きで、全部をモジュールにすると書き直しになります。
- 先に `window.wcms` の形で、コアと拡張を別のファイルに分けます。分け方が固まってから、モジュールにするかを決めます（筆者の勧め）。

### 4.5 拡張の機能を本文の印に（2026-10-20 夕・職場）

> 2026-10-20 利用者:「拡張の機能は、出来る限りタグとして実装してほしいです」
>
> 2026-10-20 利用者:「この案で進めてください。既にある通信記録のページにも、保存の口で印を書き足してください。」

「タグとして」は、利用者に聞いて「本文に置く印（鏡の印）」の意味と分かりました。
それまで拡張の JS は、ページを開くたびにタグを探して、画面の部品を自分で組んでいました。
いまは、部品をサーバーが本文の印から描き、拡張の JS は押したときの配線だけを持ちます（document へ委ねる・`delegateClick`）。

- **記録の箱**: 通信記録の本文の印 `<section data-mirror="記録の箱"></section>` に、通信がサーバーで箱を描きます（`ext/comm/record_box.go`）。

- **🤖 解析**は、本文の添付のリンクの横から、記録の箱の「🤖 解析（添付）」の一覧へ移しました（PDF・表計算・中に PDF のある ZIP）。

  - ⚠ 通信記録でないページの添付の横には、もう出ません（ファイルの「⋯」の 🤖 解析と同じく、10-01 に決めた「メールのページだけ」にそろった）。

  - 本文の印はタグそのものです。飾りは `vocab-chrome` で、保存のときに落ちます。
