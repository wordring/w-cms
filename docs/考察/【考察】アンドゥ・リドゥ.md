## 1. 2つの別問題

アンドゥ・リドゥは、性質の異なる2層に分かれます。混同しないこと。

| 層 | 何を戻すか | スコープ |
|---|---|---|
| **① 編集中（セッション内）** | 入力・ブロック操作の取り消し（Ctrl+Z 相当） | エディタ上のDOM／本文HTML |
| **② 保存済み文書** | 保存した過去状態への復元（リビジョン／リバート） | ファイル層の版履歴／本文HTML |

言葉を少し説明します。

- 「DOM」は、ブラウザが持っている、画面の要素の木のことです。
- 「リバート」は、過去の版へ戻すことです。

### 2026-10-12 にコマンドへ作り直した

> 利用者:「アンドゥが効いていないようです。まずアンドゥ・リドゥを本格化しましょう。コマンドパターンを使った実装はどうでしょう？」

「コマンド」は、1つの変更を「前の形」と「後の形」の組として覚えておくものです。
戻すときは前の形へ、やり直すときは後の形へ差し替えます。

#### 効いていなかったもの

職場の本物で、自分で作ったページで再現しました。

- 🗑 で消したブロックを Ctrl+Z で戻すと、画面には戻りますが、**保存されず、4秒後に画面からも消えました**。
  - これはアンドゥではなく、保存の送り方の誤りでした。
  - サーバーが消したブロックの元（`syncBase`）を、手元が覚えたままでした。
    同じ中身で戻ると「変わっていない」と見なして送らず、サーバーは並びの中の知らない ID を捨てていました。
  - 版の「このブロックだけ戻す」も、同じ道でした。
  - → 直し方: サーバーの並びに無いブロックは、足したブロックとして送ります。仕上がりに無いブロックの元は捨てます。
- 帯のボタンや余白を押したあとの Ctrl+Z は、本文の外に届いていました。
  そのため**ブラウザ自身のアンドゥ**が走って、1文字だけ消していました。
  - → 直し方: document で横取りします。

#### コマンドの単位

筆者は初め、「1打鍵ずつのコマンドは日本語入力で壊れやすい（エディタの中身を自前で持つ作りに変わる）」として、
「ブロックの変更を1コマンド」を勧めました。利用者の答えは、次の2つです。

> 利用者:「一文字ずつコマンドを収集し、同じコマンドが来たら結合して圧縮していくのは、ブラウザでは処理が追いつきませんか？」
>
> 利用者:「日本語入力で壊れやすいのであれば、日本語文字列が確定したときにコマンドとして収集すればよいのでは？」

どちらも採りました。

- 処理は追いつきます。
  ブロックごとに書ける欄が分かれているので、1打鍵に書き出すのは、キャレット（文字を打つ位置の印）のある1ブロックだけです。
- 打鍵を自前で書き込むのではなく、**ブラウザが書き込んだあとのブロックの前と後**をコマンドにします。
  だから、日本語の変換はブラウザのままで、壊れません。

#### いまの形

| | いまの形（`assets/app.js`「編集中のアンドゥ・リドゥ（コマンド）」） |
|---|---|
| コマンド | `{label, kind, changes: [{id, before, after}], orderBefore, orderAfter, caretBefore, caretAfter}`——無かった・消えたブロックは null。並びは変わったときだけ |
| 打った文字 | 入力（`input`）ごとに1コマンド。続けて打った同じ種類（打つ・消す）を結合——同じブロック・打つ直前のキャレットが前の打鍵のあとと同じ・1秒以内（`CMD_MERGE_GAP_MS`） |
| 日本語 | 変換中（`compositionstart`〜`compositionend`）は結合し、**確定で閉じる**——確定ごとに1つ |
| 操作 | 本文の外（帯・メニュー・⠿ 🗑 ＋・欄）を押す前に拾い、押した操作のあとに**ボタンの名前**で拾う（`captureAll`）。Enter・Ctrl の組み合わせ・貼り付け・ドラッグも前後で拾う |
| 取りこぼし | 本文が変わって 0.7 秒止まったら、記録（`committed`）といまを比べて「変更」として拾う |
| 戻す | **そのコマンドが変えたブロックだけ**（`applyCommand`）——差し替えは `reconcileBlocks`（2026-10-07 から・サーバーが描いた中身ごと戻る）。いまの中身がコマンドの後と違えば（相手が書き換えた）、自分の版にして相手の版を枠で並べる。消すはずのブロックを相手が書き換えていたら消さない |
| 相手の変更 | コマンドにしない——記録だけをいまに合わせる（`adoptExternal`）。サニタイズのエコーバックと、保存の前に入れ子へ振った ID は、そのブロックを最後に変えたコマンドの「後」（やり直す側はコマンドの「前」）を直す（`adoptMachineEdits`——やり直しで除く前へ戻れない。初めの名前は `adoptSanitized` で、`bb5ef48` で ID も扱う形に改めた） |
| キー | Ctrl+Z・Ctrl+Y・Ctrl+Shift+Z は document で（本文の外の入力欄を除く）。ブラウザのメニューの「元に戻す」（`historyUndo`）も横取り |
| 保管 | 同じタブなら読み直しても残る（`sessionStorage`・形の印 `v: 2`・100件——入りきらなければ減らす） |

#### 作る途中で踏んだもの

- **帯で見出しにする処理の途中で、空の段落が保存された**
  - この処理は、中身を新しい要素へ移してから、古い要素を外します。
  - その途中で、ブラウザが**同期で focusout** を出しました。
  - 受け手の「すぐ保存」が、**空の段落**を記録に積み、サーバーにも一瞬送っていました。
  - → 機械が要素を差し替えている途中（`quietDomChange`）と、戻している途中は、focusout で保存しません。
- **保存のときに記録を積むのもやめた**（区切りはチェックポイントだけです）。
- **サニタイズのエコーバックは、積み増さずに、いちばん新しい記録を置き換える**
  - 積むと、戻すと除く前の危険な中身へ戻れてしまいます。
  - 08-02 の「除去後の状態を積み直す」は、この穴を塞げていませんでした。

### 実装メモ（2026-08-02）

> **実装メモ（2026-08-02）**: 本節の推奨どおり、スナップショット方式で実装しました
> （[app.js](../../assets/app.js)。実装当時は `assets/index.html` 内で、2026-08-06 に外部化されました）。
> 実装上の決定と、設計時には見えていなかった点を、以下に残します。

「スナップショット」は、ある時点の本文をまるごと写したものです。

- **粒度**
  - 「変更が確定した単位」＝**保存が走る単位**（既存の1.5秒デバウンス）としました。
  - 専用の変更検知は作らず、`saveToServer` の差分判定（`decideSaveStrategy`）へ相乗りさせています。
- **キャレット復元（§7 の未決を決定）**
  - **`data-id` ＋ 文字オフセット**方式です。
  - 本メモ執筆時は、ブロックに識別子が無く、「全再描画でカーソルが飛ぶ」のが難所でした。
  - ブロック単位保存の導入で、安定したIDが手に入ったため、解けるようになりました。
- **アンドゥ時のキャレット位置**
  - 「戻した先の状態が作られたときの位置」ではなく、**取り消した編集があった位置**へ置きます（一般的なエディタの挙動）。
  - 前者は、今回の操作と無関係な場所を指すため、使いにくいからです。
- **復元時は `applyMode()` が要る**
  - `populateEditor` は本文を流し込むだけで、編集用の属性を付けません。
  - これを忘れると、アンドゥ直後にブロックが `contenteditable` でなくなり、文字が打てなくなります（実装中に踏みました）。
- **`focus()` の順序**
  - キャレットの範囲を張る**前**に、`focus()` を呼びます。
  - 逆にすると、`focus()` がキャレットを先頭へ動かし、計算した位置が失われます（同上）。
- **セッション境界**
  - `enterEditMode` で初期化、`leaveEditMode` で破棄します。
  - **`handleLockLost` でも破棄します**。
    本文がサーバーの最新版に置き換わり、手元の編集も失われているためです。
    戻せない状態へアンドゥできてしまうのを防ぎます。
  - なお、通常のブロック離脱（`focusout`）は `saveToServer` を呼ぶだけで、履歴は消えません。
- **サニタイズとの関係**
  - 除去が起きたときは、**除去後の状態を積み直します**。
  - 積まないと、「除去された危険な内容」へアンドゥで戻れてしまいます。
- **上限**: 100スナップショット。

### なぜ標準アンドゥでは不十分か

このエディタは、contenteditable に加えて、**大量のプログラム的DOM操作**をします
（[エディタ §1〜§5](../旧文書/エディタ仕様.md)）。たとえば次のものです。

- `wrapInBlock`
- D&Dの `insertBefore/after`
- スラッシュメニューの `replaceBlockWithComponent`
- 表の行・列操作
- dl の項目操作

**ブラウザのネイティブ undo は execCommand/ネイティブ入力しか捕捉しない**ため、これらのDOM操作は記録されません。
その結果、Ctrl+Z は不整合になります（ブロック挿入を戻せない／壊れたDOMに戻る）。

ProseMirror 等が独自 undo を持つ理由そのものです
（[エディタ §3](../旧文書/エディタ仕様.md) も「contenteditable統合は難所」と記載）。

### 推奨：スナップショット方式の独自スタック

重い文書モデルを導入せず、**既存のシリアライズ境界を再利用**します（本プロジェクトの規模に合います）。

- **記録**: `updateHtmlPreview()` が出す**クリーンHTMLをスナップショット**として、スタックに積みます。
- **復元**: `populateEditor()` と同じ「HTMLを `#w-editor-content` に流し込み → `initBlocks()`」で、**まるごと再描画**します
  （アンドゥ＝1つ前のHTML、リドゥ＝逆）。
  この関数は、編集ロック起点の載せ替え（`acquireLock` / `reloadContent`）でも使われている、既存経路です
  （初期表示はサーバー合成に移行済み。[エディタ仕様.md](../旧文書/エディタ仕様.md) 6.4）。
- **粒度**: 1キーストロークでなく、**離散操作（ブロック挿入/削除/移動/置換）＋テキストはデバウンス単位**で1スナップショットとします。
  粗いですが堅牢です。どの形式も本文HTMLに乗るので、**一様に扱える**利点があります。
- **必須**: Ctrl+Z / Ctrl+Y を `preventDefault` し、**独自スタックに一本化**します（ネイティブと二重スタックが衝突するためです）。
- アンドゥ後は、**オートセーブを再発火**して反映します（undo → restore → `updateHtmlPreview` → 保存）。

### トレードオフ

- **キャレット復元**が難所です（全再描画でカーソルが飛びます）。
  各スナップショットにキャレットのマーカー（ノードパス＋offset）を持たせるか、粗いカーソル挙動を許容します。
- スタックは上限を置きます（例 50〜100）。テキストページなので、HTMLスナップショットのメモリは軽いです。

| コアレッシングの契機 | **同じ編集者の連続保存は10分ひとまとめ**。編集者が変わったら必ず切る。加えて**ロック解放時に明示チェックポイント** | オートセーブ（1〜2秒）で版が溢れるのを止めつつ、窓の内側で編集を終えた人の最終形も残すため。編集者を混ぜないのは「あとから編集者を調べたい」という要件そのもの |
| プルーニング | ~~**5年より古い版を消す**~~ ⚠ **2026-09-23 に機構ごと撤去**（末尾の節）。版は消えません | 当時: 2026-08-21 決定「5年は消さない」。⚠ **下限の話だったのに、実装は上限になっていました** |
| 版の実装 | **標準ライブラリ**（`compress/gzip`）。git は使わない | 開発方針 §1。各版が自己完結し、1つ壊れても他へ波及しない |
| リバートUI | **右レールの「🕘 版の履歴」**（編集モードでのみ「この版に戻す」が出る） | 権限カードと同じ場所・同じ流儀。閲覧モードで押せても何も起きないボタンは出さない |
| 5年保持の対象 | **全ページ一律** | 帳票だけに絞るには「どれが帳票か」の判定が要り、その判定がずれると保持義務のほうが破れる。gzip 後は小さいので分ける利得が薄い |

表の言葉を少し説明します。

- 「コアレッシング」は、続けて行った保存を、1つの版にまとめることです。
- 「プルーニング」は、古い版を消すことです。
- 「チェックポイント」は、「ここで版を区切る」という印です。

> **この節のその後**（2026-10-12 に編集モードをやめたあとの形。`assets/app.js` の `loadVersions`・`checkpointVersion` で確かめました）
>
> - **区切りを打つとき**: 「ロック解放時」は、無くなりました。
>   いまは、閲覧モードへ切り替えたときと、ページを離れるときに、画面が `POST /api/version-checkpoint` を呼びます
>   （そのタブで書いていれば）。区切った版は閉じて（`Sealed`）、あとの保存が上書きしないようにします。
> - **リバートUI**: 「この版に戻す」は、書ける形のときに出ます（閲覧モードでは出ません）。

> - 経緯は、[【考察】編集モードの再考.md](【考察】編集モードの再考.md) §6 の問い8 と §7 にあります。

#### コアレッシングを「捨てる」から「置き換える」へ（2026-08-31）

**コアレッシングは 2026-08-31 に「捨てる」から「置き換える」へ改めた**。

- 窓（10分・起点は版ID＝作成時刻）の内側の、同じ編集者の保存は、窓の版を**最新の内容へ置き換える**形にしました。
- 捨てる方式では、1セッションが、ほぼ同じ2版を残していました。
  〈最初の保存≒編集前〉と〈ロック解放時のチェックポイント＝最終形〉の2つです。

  > 利用者:「版の履歴が細かすぎます」

- 置き換えなら、窓の版が常に最新を持ちます。
  チェックポイントは、同内容で自然にスキップされます。その結果、**1セッション＝1版**になります
  （[変更履歴.md](../変更履歴.md)「版のコアレッシングを『捨てる』から『置き換える』へ」）。

#### そのほかの決まり

- **重複した版は作りません**（内容のSHA-256が最新版と同じなら、何もしません）。
  だから、明示チェックポイントが重なっても、無駄には増えません。
- **リバートの前に「いまの内容」を必ず残します**。
  だから、リバートそのものも取り消せます。
- 書き戻す本文は、**いまの許可リストでサニタイズし直します**。
  過去の版は、当時の許可で通ったものです。素通しにはしません。
- 派生索引の再構築（`resyncAllPages`）は、`versions/` へ**降りません**。
  いまの版は `.html.gz` なので、`.html` の判定には掛かりません。
  それでも、手で置かれた `versions/foo.html` が「ページ」として索引に載らないよう、明示的に閉じてあります。

### 2026-08-21 決定：帳票の5年保持は、監査ログでなくこの版管理で満たす

版管理は、この決定で「あると嬉しい」から**要件へ格上げ**されました。
ユーザーの原文と、監査ログでは満たせない理由の実測は、[【要求】運用.md](../【要求】運用.md) §1〜§2 が正本です。

- プルーニングが**年限ベース**（5年は消さない）になったこと。
- 容量見積もりが要ること。
- 対象を、全ページ一律にするか、帳票に絞るか。これは、上の実装表のとおり**全ページ一律**で決着しました。

プルーニングそのものは、のちに 2026-09-23 に機構ごと撤去しました（末尾の節）。

### 既存土台との好相性

- 本システムは、**正本＝ファイル／DBは派生**です（[アーキ §8](../旧文書/アーキテクチャとDBスキーマ.md)）。
  - よって、**履歴はファイル層に置くのが自然**です。
  - **リバート＝「古いHTMLをもう一度保存する」だけ**で済みます。
  - `Sync` がDBを作り直すので、不変条件に乗ります。
- **悲観ロックで1ページ＝単一書き手**（[エディタ §10](../旧文書/エディタ仕様.md)）なので、版履歴は**線形（マージ不要）**です。
  版管理が大幅に単純化します。
  悲観ロックは、先に1人が編集権を握り、ほかの人は待つ守り方です。

> **この節のその後**: 2026-10-12 に、ページ単位の悲観ロックをやめました。1ページを、2人が同時に書けます。
> それでも、版の履歴は線形のままです。
> 本文を書く道はすべて、ページごとの書き込みのロック（`LockPageBody`。`internal/cms/body_lock.go`）を1つずつ通り、その中で版を残すためです
> （`internal/cms/handler_sync.go`・`version.go`）。
> 2人の変更を合わせるのは、保存のときのブロック単位の合わせ方（`/api/sync`）です。版の側では、合わせません。

### 設計案：ページ単位の線形バージョンログ

- 保存時に、旧HTMLを版として残します。置き場は `data/master/<prefix>/<id>/versions/<timestamp>.html` 等。
- **コアレッシング必須**
  - オートセーブは1〜2秒ごとに飛ぶので、**毎回は版を作りません**。
  - 「ロック解放時／一定アイドル時／明示チェックポイント」で版を確定し、連続保存はスカッシュします（1つにまとめます）。
- **リバート**: 選んだ版を現在ファイルとして書き戻し → `Sync` 再生成。UIは「◯時◯分の版に戻す」。
- **依存の判断**
  - git を `data/master` に被せれば、履歴・差分が無料で得られます。しかし、次の2つが引っかかります。
    - (a) 毎オートセーブのコミットは過剰 → コアレッシング前提。
    - (b) go-git は外部依存（[開発方針 §1](../開発方針.md) に抵触）、git バイナリへの shell-out はランタイム依存増。
  - **標準ライブラリでの copy-on-checkpoint リング**が、方針に最も素直です。

### 版の圧縮・保持（2026-06-28 決定：gzip）

**各版は `gzip` でフル圧縮して保存する（`compress/gzip`・標準ライブラリ）。差分チェーンは採らない。**

- **容量の主レバーは圧縮ではなく版数の抑制**
  - ①コアレッシング（連続保存をスカッシュ）＋②**保持のプルーニング**（無限に持たない）を、先に効かせます。
  - 圧縮は、その次の補助です。
  - ※ ②は 2026-08-21 の決定で「**5年は消さない**」という下限を持ちます（上記）。世代数でなく、年限で切る前提になります。
- **gzip（採用）**
  - テキストHTMLで **~70-85%減**。
  - 各版が**自己完結**（復元チェーン不要・破損連鎖なし）です。
  - [開発方針 §1](../開発方針.md) の標準ライブラリ優先に合います。`versions/<timestamp>.html.gz` 等。
- **差分チェーン（不採用）**
  - 最小容量ですが、**Go 標準に diff/patch が無い**ため、自前 Myers 実装 or 外部依存になります。
  - ページが小さい本件では、割に合いません。
  - 復元コスト（キー台座要）・破損連鎖の弱点もあります。
- **表示用 diff は別概念**
  - 「何が変わったか」の表示は、gzip フル版を保存したまま、**必要時に on-demand で diff 計算**すればよいです（保存形式と無関係）。
  - 表示 diff を入れる場合の diff 実装は、別途依存判断です（保存の圧縮目的では不要）。

## 5. スコープの決定（2026-06-28）：版管理は「本文HTMLのみ」

**ページの版管理は本文HTML（`<id>.html`）に限定する。サイドカー・親付け替え・権限・所有者・添付バイナリは対象外。**

「サイドカー」は、ページの属性（親・権限など）を入れたファイル `<id>.meta.json` です。

これは、既存の「内容＝HTML／属性＝サイドカー」分離
（[アーキ §2](../旧文書/アーキテクチャとDBスキーマ.md)・[エディタ §9](../旧文書/エディタ仕様.md)）にそのまま乗る、**ファイル単位の境界**です。

| | 版管理の対象 | 内容 |
|---|---|---|
| ✅ 対象 | **本文HTML** `<id>.html` | テキスト・ブロック・業務データ・**HTML内のタグ**（`状態=未確認/取消`・`受信元`・`版`・受注明細 等すべて） |
| ❌ 対象外 | **サイドカー** `<id>.meta.json` | 親ページID・owner/group/mode・public・作成/更新日時 |
| ❌ 対象外 | 親付け替え・権限・公開・所有者変更 | 専用API＋編集ロック直列化＋`auth.Audit` で別管理 |
| ❌ 対象外 | **添付バイナリ**（PDF等、ページフォルダの `files/` 配下） | HTMLは `src` で参照するだけ。版管理しない（append主体・戻す需要は稀） |

### この限定の利点

- **セキュリティ**
  - リバートで、**過去の権限・親・所有者が復活しません**。
  - 「古い版に戻す」が、権限昇格やページ移動の抜け道になり得ません（構造的に不可能）。
- **整合性**
  - リバート＝内容変更なので、`Sync` が業務行を再生成します。
  - サイドカー由来の列（親・作成者）は**現状維持**、`updated_at` は「今」前進します
    （`Sync` は元々、HTMLとサイドカーを別々に読みます）。
- **統一**
  - 編集中アンドゥ（①）も、本質的に本文HTMLのみを扱います。
  - **①②とも「対象＝本文HTMLのみ」で統一**できます。
- **注意**
  - リバートはテキスト/構造を戻しますが、**参照先のPDF実体は戻しません**
    （後で削除/差し替えされた添付は、復元されません）。
  - ページ間の参照も、同様にソフトです。指す先の存在は読むたびに判定し、無ければ印が付くだけです。
    ページ間の参照は、「名前：値」タグの値 `ページID-ブロックID` のことです
    （2026-08-31 実装・[アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) §9.1）。

## 2026-09-23 決定：5年で消す動作をやめた

> 2026-09-23 利用者:「帳票の保持期限は**企業が過去に問題を起こしていた場合、最大10年**です。
> **個人が5年、法人が7年**です。」「**5年で消す動作をやめましょう**」

**年限を1つに決められないことが分かった**、というのがこの決定の中身です。

| 誰が使うか | 保持年限 |
|---|---|
| 個人 | 5年 |
| 法人 | **7年** |
| 法人（過去に問題を起こしている） | **最大10年** |

**設置した先が個人か法人か、過去に何があったかは w-cms には分かりません。**
w-cms は、**開発元でない企業も設置する**ソフトウェアだからです
（[【要求】w-cmsとは.md](../【要求】w-cmsとは.md) §1「特定用途向けに拡張できる」）。

### ⚠ 既定を「消さない」にした理由——間違えたときの被害が対称ではない

| 間違い | 何が起きるか |
|---|---|
| 短すぎた | ⚠ **保持義務を破る。しかも消えた版は戻らない** |
| 長すぎた | ディスクを使う（gzip 後は小さい） |

⚠ **後から年限を延ばしても、既に消えた版は戻りません。**
だから、**初日から安全な側**に倒しておきます。
**運用者が自分の事情に合わせて短くする**のが、正しい向きです。

**それまでは 5年で消していました。**

- 2026-08-21 の決定は、「5年は消さない」という**下限**の話でした。
- それなのに、実装は**上限**（5年を超えたら消す）になっていました。
- この会社は法人なので、**2年足りませんでした**。

### 何を変えたか——⚠ **機構ごと撤去しました**

> 利用者:「**消さないの意味は、消す機構も持たないで良いです。もしも消す必要が出来たら、エージェントで消します**」

**最初は「設定で年限を指定でき、既定は 0＝消さない」にしました。**
それも撤去し、**`PruneVersions` も設定も消しました**。

- `PruneVersions` を削除（`RecordVersion` の最後の呼び出しも）
- 設定 `version_retention_years` と `VersionRetention()` も削除

これで、**設定の書き間違いでも版が消えません**。
**消してよいと判断できる場所が、コードの中に1つもない**という形です。

#### 試験で踏んだこと

**見張りの試験が1本、最初は何も見張っていませんでした**（10通り目）。
見張りの試験は、後戻りを見つけるための試験です。ここでは、見張っている所をわざと壊しても、試験が落ちませんでした。

- 同じ編集者で続けて保存すると、**コアレッシングの枝へ入って早く戻り**、版を新しく書く道を通りません。
- **掃除が付いていたのはその道の最後**でした。そのため、**掃除を戻しても落ちませんでした**。
- いまは**別の編集者で保存**して、版を新しく書く道を通します。

**わざと壊した所を、試験が実際に通っているかまで確かめること。**
