### 形

組み替えたあとの、拡張のフォルダの形です。

```
ext/
  comm/              通信（通信箱・向き／チャネル・未処理一覧・スレッド・記録する）
    contacts/        アドレス帳 ← toho が import する（別パッケージなので単独で入る）
    mail/            メール（IMAP／SMTP）  -tags nomail
    fax/             FAXサーバー（近日。同じ機械の中の口）
    cti/             着手するときに作る（空の器は作らない）
  toho/            下請け業務（旧 sheetmetal） → import ext/comm/contacts
```

言葉を少し説明します。

- 「通信箱」は、届いた通信と送った通信の記録を入れておくページです。
- IMAP はメールを受け取るための決まり、SMTP はメールを送るための決まりです。
- `-tags nomail` は、組み立てるときにメールの拡張を外す指定です（ビルドタグ）。
- 「import する」は、ほかのパッケージ（プログラムのまとまり）を読み込んで使うことです。

## 1. なぜこの形か

### 1.1 アドレス帳を通信の範疇に入れても、09-11 の判定と矛盾しない

09-11 に、「アドレス帳は**メール**の持ち物ではない」と判定しました。
根拠は4つありました（[【考察】アドレス帳の作り直し.md](【考察】アドレス帳の作り直し.md) §5b）。

この4つは、**相手がメールだったから**成り立っていたものです。
範疇が「通信」に広がると、半分が裏返ります。

- **根拠4「FAXだけ・電話だけの客先にはメールアドレスが無い」**
  通信なら、全部を含みます。むしろ、アドレス帳を入れる理由になります。
- **根拠1「メール拡張は使っていない」**
  FAX 番号も電話番号も、**相手を言い当てる手掛かり**です。3つの通信路が、すべてアドレス帳を引きます。

> ⚠ **下の段落の理由は、2026-09-15 のうちに取り下げました**（§4.3）。
>
> - 「下請けは入れたが通信箱は無い」というビルド（組み立てた実行ファイル）は、**最初から存在しません**。
>   作れるのは、全部入り／`nomail`／`minimal` の3つです。通信箱はコアにありました。
> - つまり、守ろうとした組み合わせが、そもそもありませんでした。
> - アドレス帳は、別パッケージのまま置きます。ただし理由は整理のためで、ビルドタグのためではありません。

**残るのは、根拠3（ビルドタグ）だけです。** これは、**別パッケージにすれば解けます**。

- タグは、`cmd/w-cms/ext_*.go` の import 行に付きます。
- だから、`toho` が直接 import した `ext/comm/contacts` だけが入ります。
  通信箱（`ext/comm` 本体）は連れてこられません。
- **同じパッケージに入れると、`init()` の連鎖で通信箱ごと入ります。「通信を外す」が効かなくなります。**
  注意点は、ここだけです。`init()` は、パッケージが読み込まれたときに自動で走る関数です。

### 1.2 板金拡張は、中身がもう下請け業務だった

`ext/sheetmetal`（5,177行）を調べると、次のとおりでした。

- 板金に寄った語が出るのは、**コード中2行**だけです。
  DXF（CAD の図面のファイル形式）の表題欄の項目名の並びと、部材表の列見出し `材質` です。
- 登録している14形式も、図面を受け取って部品を作る下請けに共通のものです。
- **業種の前提は、整理の木だけです。**
  木は `取引先／社名／段／装置名称／図面名称` で、部品は顧客の装置に属する、という前提です。
  （→ 段のフォルダは、2026-09-29 にやめました。いまの木は `製造／社名／加工製品／装置名称／図面名称` です。`ext/toho/product_tree.go`。根の名前は、2026-10-16 に「取引先」から「製造」へ改めました）
  これは、機械部品の下請け（板金・切削・溶接・塗装）に当てはまります。

範囲は「**製造の下請け**」です。

### 1.3 FAXサーバーと同居すると、機械の口の認証が軽くなる

「機械の口」は、人ではなくプログラム（FAX サーバーなど）が w-cms へ届けるための入口です。
作業引き継ぎでは、**機械の口の認証**を「FAXサーバーと共通の未解決」としていました。

- 同居すれば、ネットワーク越しの認証は要りません。
  「**同じ機械の中からしか届かない口**」で足ります。
  ループバック限定の口（同じ機械の中からだけつながる入口）か、決まったフォルダへの投函です。
- 設計は、`ext/comm/fax` に着手するときに詰めます。
- **人の手ドロップと機械の投函を、同じ口で受けません。** これは、そのまま守ります。
  09-05 の決定です。PDF を `チャネル：FAX` と決めつけた事故がありました。

### 3.5 画面（`assets/`）に居る拡張

**拡張の画面は、ほぼ全部がコアの `assets/app.js` にあります**（合計約1,240行）。
入口は、`applyMode()` の11個の呼び出しです。

- `index.html` に、拡張の部品はありません。拡張の id は、Go のビューが本文に出しています。
- CSS（見た目の決まり）も、全部 `app.css` にあります。
  `.materials-table`・`.chip-btn` は複数の拡張が共用しているので、分けるときに注意が要ります。

**`-tags minimal` で起きること**（コードから読める範囲です。実測はしていません）

`-tags minimal` は、拡張を1つも入れずに組み立てる指定です。

- **押すとエラーの通知が出るもの**
  - 全PDF添付の「🤖 解析」

- **黙ってむだな要求を出すもの**: `/api/analyzed` を、`applyMode` のたびに呼びます（編集モードでも）。
- JS は、応答の `res.ok` を見ずに `res.json()` で読みます。
  そのため、404 の平文が「SyntaxError」の通知になります。

**つまりビルドタグは、サーバーからは拡張を外せますが、画面からは外せていません。**

→ **3c で、下請け・メール・アドレス帳のボタンは出し分けました**（通信の画面は 3d で）。

### 3.6 HTTP ルート・設定・E2E・ビルドタグ

- **ルート表にあるのに、画面が呼んでいないもの**

  - `/api/required-materials`（E2E だけ）

- E2E の既定の固定ID（`010272` ほか）は、職場のデータに合わせてあります。

## 4. 3の前に決めること

§4.1 と §4.2 が論点で、§4.3 がその決定です。§4.4 は、3d-4 のときに測って分かったことです。

### 4.1 拡張の画面をどう持つか

§3.5 のとおり、画面は外れていません。案は2つです。

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| A. **載っている拡張をサーバーが知らせる** | `/api/tag-schema` か `/api/me` に `extensions: ["comm","mail",…]` を足し、`app.js` の各入口が見て出し分ける | 小さい。ファイルは1つのまま | コアの JS が拡張の画面を持ち続ける（語彙がコアに残る） |
| B. **拡張が自分の JS を配る** | `ext/*/assets/*.js` を `embed` し、載っている拡張だけ `<script>` を出す（CSP strict は self なので通る） | 外せば画面ごと消える。コアの JS から業務語が消える | `app.js` の内部関数（`tagValue`・`placeFloating`・`notify` 等）を公開する口が要る |

**推しは、A から B へ進む形です。**

- 3では、A で出し分けだけを直します。
- B は、通信・下請けそれぞれの画面を触る機会に、1つずつ進めます。

### 4.2 拡張の設定をどこに置くか

コアの設定ファイル1本に、次のものが同居しています。

- `machine_stages`（toho だけが使います）
- `vocabulary` の通信の語
- `webdav_readonly` の `通信箱`

`DisallowUnknownFields` があるので、**型をコアから外すだけで、起動が止まります**。
そこで、拡張が自分の設定の節を登録する口が要ります（例 `cms.RegisterSettingsSection("toho", &cfg)`）。

**語彙（`vocabulary`）は分けない**のが自然です。
型は名前で決まります。辞書は1つのほうが、衝突に気づけます。

### 4.3 決定（ユーザー 2026-09-15）

| 論点 | 決定 |
|---|---|
| 拡張の画面（§4.1） | **A→B と段階で**。3段目では A（サーバーが載っている拡張を知らせ、`app.js` が出し分ける）。B（拡張が自分の JS を配る）は画面を触る機会に1つずつ |
| 拡張の設定（§4.2） | **拡張が自分の節を登録する**。`config/settings.json` は1本のまま、語彙（`vocabulary`）は分けない |
| 通信記録の語の参照（3d） | **アドレス帳と下請けは `ext/comm` を import する**（相手のタグ名 `差出人`・`宛先`・`CC`・`返信先` などを定数で通す）。依存は import で表す。`ext/comm` 本体はメールと違いタグを持たず `!minimal`——`nomail` でも通信箱（手で作る記録・電話）は残る。§1.1 の「別パッケージにすれば通信箱を連れてこない」は取り下げ（その組み合わせは作れなかった） |

### 4.4 画面の出し分けが要るのは「JSが自分で作るクローム」だけ（2026-09-16・実測）

「クローム」は、本文以外の画面の部品（ボタンや箱など）のことです。本文には保存されません。

3d-4 の着手時、段取り表は**4つ**（スレッド・未処理一覧・記録する・電話）を出し分ける予定でした。
測ったところ、**実際に要ったのは2つだけ**です。

| 画面 | 出し分け | なぜ |
|---|---|---|
| 通信記録のクローム（`refreshMailChrome`） | **要る**（箱ごと） | 中の「🧵 やりとりの前後」「📨 この記録への返信」が `/api/thread`・`/api/replies` を叩く。通信が無いと**通信記録ページを開くたびに404が2本**（どちらも失敗を黙って飲むので、画面には何も出ないまま要求だけ飛ぶ） |
| 電話の「記録を作る」 | **要る**（チェックだけ） | `/api/intake/memo` を叩く。**既定でオン**なので、掛けるたびに「発信の記録を作れませんでした」の通知が出る。⚠ `tel:` のリンクは残す——**掛けることは通信拡張の持ち物ではない** |
| 未処理一覧（`wireUnhandledActions`・`markHandled`） | **要らない** | 押す相手（`.unhandled-mark`・まとめて片付け）は**サーバーが描いたもの**。通信が無ければ `unhandled-intake` は語彙レジストリに載らず、**鏡の引き金が立たない**——本文に `<section data-type="unhandled-intake">` が書いてあっても空のまま出るので、配線は何も見つけずに帰る |
| 「＋ 記録する」（`wireNewRecord`） | **要らない** | 同じビューが描いているため（上と同じ理由） |
| 機械向けタグを畳む（`foldMachineTags`） | **要らない** | 本文のDOMを畳むだけで、口を叩かない |

**一般則**: 出し分けが要るのは、**JS が自分で作るクローム**だけです。
サーバーが描いたものは、拡張が無ければそもそも描かれません。

**「拡張の画面」を数えるのではなく、「口を叩くところ」を数えること。**
前者で数えると、要らない分岐を4つ足して、次の人がそれを維持することになります。
理由は、`wireUnhandledActions` の直前にコメントとして書き残しました。

番人は `e2e/probe-extension-gating.js` です。

- 期待値を `/api/tag-schema` から導くので、**3つのビルドのどれに当てても通ります**。
- 出し分けを外すと、`-tags minimal` で404が2本出ることを確認済みです。
