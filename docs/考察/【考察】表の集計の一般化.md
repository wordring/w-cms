# 【考察】表の集計の一般化

> 2026-10-01。利用者:「表の集計を一般化できるか考察文書を作りましょう」「確定単価は、塗装のあるなし、ロット数など条件付きで
> 検索して見積もりに入れられると良いですね」。
>
> きっかけは同じ日の見積計算表の依頼です——「加工製品ページの見積もり計算表の下に弊社利益を掛ける項目を作り確定単価と
> したいです。弊社利益はデフォルトで10％なので、単価に1.1をかければ良いのですが、利益率を変更できるようにしたいです。
> 確定単価は目立つように太字です」「単価*10%=○○円と表示したいです。この○○円は見積もりの集計で使うことになるかもしれ
> ません」「見積の時には、色を塗るか塗らないか、ロット数などで価格が変わることがあります。そのため、見積もり計算表は
> 複数ある場合があります」。確定単価は同じ日に**東邦の拡張の Go コード**で作りました（§2・`ext/toho/estimate.go`）。
> この文書は、**次の集計からはコードを書かずに足せるか**を考えます。

## 1. 問い

w-cms の集計は、いま**業務ごとに Go で書いています**。新しい集計が要るたびに開発者がコードを書き、利用者・運用者は足せません
（「語彙とプラグインは運用者が追加できることが要件」——2026-08-26）。

- **何を一般化できるか**——表の中の計算・表の足元の計算・ページをまたぐ集計・条件で探すこと。
- **どこに置くか**（開発方針 §0）——仕組みはコア、業務の式（確定単価＝単価×1.1 など）は拡張か設定。
- **条件で探せるか**——「塗装あり・ロット20 の確定単価」を引いて見積もりへ入れる。

## 2. いまあるもの

### 2.1 表は2つの形がある

| 形 | 例 | 1行は | 読み方 |
|---|---|---|---|
| **1行1件**（横の表） | 受注明細・材料・発注明細・改訂明細 | 1つの品物・1つの注文行 | 列の見出しが項目名 |
| **第1列が鍵**（縦の表） | 見積計算表 | 1つの項目（ロット・材料・板金・単価・総計） | 第1列が項目名、`数` がその値 |

職場の見積計算表は **246ページ**（2026-10-01 に数えた）。見出しは `工程｜数｜単位｜備考` が **226**、残り約20は別の形
——`ロット20｜ロット40` を列にした表（**ロットごとの値を横に並べる**）、`*1.1`・`1.1倍単価` の列を持つ表（**利益の掛け算を
手でしていた**）など。1つのページに2枚以上あるのが **8ページ**（塗装あり・なし、ロットごと）。

⚠ **縦の表は「表の写し」で集計に向きません。** 表の写し（`data/tables.db`）は1行を1件として入れるので、見積計算表1枚は
「工程=ロット・数=20」「工程=材料・数=55」…の**行の束**になり、「ロットが20で塗装がある表の単価」を1つの問い合わせで
引けません。**1枚を1件として読む（縦を横に回す）**読み方が要ります（§4.2）。

### 2.2 集計の置き場

| 集計 | どこで | 何を読む | 形 |
|---|---|---|---|
| 受注残高 | `ext/toho/order_balance.go` | 受注明細（数量×単価−出荷済み） | 表の足元・受注フォルダ |
| 検算 | `ext/toho/checksum.go` | 受注明細と小計・合計のタグ | 表の足元 |
| 必要部材表 | `ext/toho/procurement.go` ほか | 受注明細 → 加工製品 → 材料表 × 数 − 発注明細 | ページをまたぐ・鏡 |
| 最新単価 | `ext/toho/material_price.go` | 発注明細（発注済・納品済） | 材料表の右の列 |
| 確定単価 | `ext/toho/estimate.go`（10-01） | 見積計算表（単価・弊社利益） | 表の足元 |
| 表を探す | コア `tables_query.go` | 表の写し（キャプションのある表） | 画面・AI の口（自由な SQL は受けない） |

どれも **Go で1つずつ**。共通しているのは「表を見出しの言葉で読む」道具（`rowsOf`・`headerIndex`・`cellTexts`）だけで、
**式は全部コードの中**にあります。

### 2.3 写しに入らない表

⚠ **見積計算表の 246 ページは全部「移行中」**（ワンノートから移して、人がまだ確かめていない）。「移行中」のページの表は
**表の写しにも索引の集計にも入れない**決まり（2026-09-21・`RegisterTablesExclusion`）なので、**いまは1枚も探せません**。
条件で探す前に、確かめた表から「移行中」を外していく必要があります（§6 の3）。

## 3. 「集計」を3つの段に分ける

| 段 | 何 | 例 | いま |
|---|---|---|---|
| ① 行の中 | 1行の列どうしの計算 | 金額＝数量×単価 | 紙（PDF）を刷るときに Go で |
| ② 表の中 | 1枚の表の行どうし・足元 | 合計・受注残高・**確定単価＝単価×(1＋率)** | 表の足元の鏡を Go で |
| ③ 表をまたぐ | ページ・表を越えて集める・結ぶ | 受注フォルダの受注残高・必要部材表・**条件で探した確定単価** | Go で（必要部材表は参照を辿る） |

③のうち**「結んで辿る」もの**（受注明細 → 加工製品 → 材料表）は、業務の決まり（どの列が鍵か・何を引くか）が濃く、
一般化しても設定が複雑になるだけです——**Go のままがよい**と考えます。一般化して得をするのは、①②と、③のうちの
**「同じ名前の表を条件で探して並べる・足す」**です。

## 4. 案

### 4.1 式を設定に書く（①②）——コアに小さな式の読み手

表の名前（キャプション）ごとに、**足元に出す計算**を設定に宣言します。式を読む部品はコアに置き、式そのもの（業務の
知識）は設定に置きます（§0 の線どおり——コアは「計算の行を足元に出せる」だけを知る）。

```jsonc
// config/settings.json（案）
"table_formulas": {
  "見積計算表": [
    { "name": "弊社利益", "value": "round(単価 * 率 / 100)", "label": "単価 {単価}円 × {率}% = {値}円",
      "vars": { "率": "行:弊社利益 ?? 設定:estimate_profit_rate" } },
    { "name": "確定単価", "value": "単価 + 弊社利益", "bold": true }
  ],
  "受注明細": [
    { "name": "受注残高", "value": "sum(数量 - 出荷済み) * 単価 where 状態 != 完了" }
  ]
}
```

- **良いところ**: 運用者が足せる（コードを書かない）。式が1か所に見える。鏡なので焼き込まない（人が値を直せば次に開いた
  ときに計算し直す）。同じ式を **③の検索でも使える**（§4.2）。
- **難しいところ**: **小さな言語を作ることになる**——四則・丸め・行の名前の参照（縦の表）・列の参照（横の表）・条件つきの
  合計・空のセル（空は0か「出さない」か）・単位（円と個が混ざる）。⚠ 言語は**小さく閉じる**こと（関数を増やし始めると
  表計算ソフトの再発明になる）。⚠ 式の誤りは**画面に理由を出す**（黙って空欄にしない）。
- **既存の Go の集計は置き換えない**——検算・必要部材表のように業務の決まりが濃いものは Go のまま。新しく足すものから。

### 4.2 縦の表を1件として読む（③の前提）

第1列が鍵の表を、**1枚＝1件**として表の写しに入れる読み方を、表の名前ごとに宣言します（これもコアの仕組み・宣言は設定）。

```jsonc
"table_shapes": {
  "見積計算表": { "key": "工程", "value": "数", "note": "備考" }   // 行の名前を列にする
}
```

見積計算表1枚が `{ロット: 20, 材料: 55, 板金: 310, 塗装: 200, 単価: 565, 弊社利益: 10, 確定単価: 622, 備考: 塗装あり, ページ: 000218}`
の1行になり、**表を探す（`/api/tables/query`）でそのまま条件にできます**——「ロット = 20 かつ 塗装 > 0」。
§4.1 の式で求めた値（確定単価）も、写しに**計算した列**として入れられます（⚠ 写しは派生なので、本文が変われば作り直される
——焼き込みにはならない）。

⚠ 縦の表で**行の名前がぶれる**と列が割れます（`組み立て`／`組立`、`板金材料`／`材料`）。表の写しの「列の揃っていない表の
一覧」と同じく、**ぶれを運用者に見せる一覧**が要ります。

### 4.3 条件を見える言葉で書く

「塗装あり・なし」「ロット」は、いま**表によって書き方が違います**——`ロット` の行の数、`塗装` の行の有無（空なら塗装無し？）、
`備考` に「塗装無し」、列の名前（`ロット6黒塗装`）。条件で探すには、**どの言葉が条件か**を決める必要があります。

- 案 a: **行で書く**——`ロット`（数）・`塗装`（金額。空なら塗装なし）。いまの 226 枚の形のまま読める。
- 案 b: **条件の行を足す**——`条件` の行に「塗装あり」「黒塗装」など自由に書く。
- 案 c: **キャプションに書く**——`見積計算表（塗装あり・ロット20）`。⚠ 表の名前が割れるので、写しで別の表になる（勧めない）。

### 4.4 見積もりに入れる（③の出口）

見積書のページ（【要求】見積 §2——器が要ると決まっている・未実装）の明細に、**加工製品と条件を選ぶと確定単価が入る**形。
入れた値は**その時点の値として本文に書く**（見積書は外に出る紙で、出した後に加工製品の見積計算表が変わっても、出した見積の
値は変わってはいけない——凍結すべき判断・【考察】材料の単価と価格の履歴 §1）。⚠ ここは鏡ではなく**書き込み**。

### 4.5 表の中に式を書く（採らない）

セルに `=単価*1.1` と書いて表計算のように計算する案。**採らない**——本文に式と値の2つが入り（どちらが正本か曖昧）、
サニタイズ・索引・表の写しのすべてが「式のセル」を知る必要があり、人が式を壊したときに黙って間違った値が並ぶため。
式は設定（§4.1）に1か所だけ。

## 5. 進め方（案）

| 段 | 何 | 置き場 |
|---|---|---|
| 0 | ✅ 確定単価を Go で出す（10-01）——`estimateOf` に計算を1つにまとめ、足元の鏡と、将来の検索で同じ関数を使う | 東邦 |
| 1 | 縦の表を1件として写しに入れる（§4.2）——見積計算表を条件で探せるように | コア＋設定 |
| 2 | 条件の書き方を決める（§4.3）・行の名前のぶれの一覧 | 利用者が決める・コア |
| 3 | 表を探す画面で条件をつけて探す（ロット・塗装）・確定単価の列 | コア |
| 4 | 式を設定に書く（§4.1）——確定単価を Go から設定の式へ移し、Go の `estimateOf` を消す | コア＋設定 |
| 5 | 見積書のページから確定単価を引いて入れる（§4.4） | 東邦（見積の器ができてから） |

1 と 4 は独立に進められます。**4 を先にすると、言語の設計に時間が掛かって 1〜3 が遅れる**ので、1〜3 を先に勧めます。

## 6. 聞くこと

1. **条件の書き方**（§4.3）——ロット・塗装の有無を、表の行で読む（案 a）か、`条件` の行を足す（案 b）か。
2. **式を設定に書く形へ進めるか**（§4.1）——運用者が足せる代わりに小さな言語を作ることになる。Go のまま足していくのでもよい。
3. **「移行中」の見積計算表**（§2.3）——246 ページ全部が「移行中」で、いまは探せません。確かめて外していくか、見積計算表だけは
   「移行中」でも写しに入れるか。
4. **確定単価の丸め**——いまは利益を円未満で四捨五入（365円 × 10% = 36.5円 → 37円）。切り上げ・切り捨て・10円単位などの決まりが
   あれば。
