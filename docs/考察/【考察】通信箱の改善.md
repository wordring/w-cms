# 【考察】通信箱の改善

> 状態: **作り始め**（2026-10-21 夜）。§6 の答えから §7 を決め、§7.6 の順に作っています。

通信箱は、メール・電話・FAX・メモの記録を入れる置き場です（トップ直下の「通信箱」。画面では通信フォルダとも呼んでいます）。
本番のサーバーが動き出すと、記録は人がボタンを押さなくても届くようになります。
この文書では、どの入口から届いた記録も、同じように判定して次の工程へ流す形を考えます。

## 1. 話の流れ（利用者の言葉）

> 2026-10-21 利用者:「通信フォルダを改善します。
>
> まず、通信フォルダの記録するボタンですが、本番サーバーが稼働すると電話、FAXは届いた時点で通知されるので、通知を受けて作動するプログラムが必要になります。メールは日中5分間隔、夜間1時間間隔で自動で読み込むと思います。ボタンを押して読み込むのは、メモになると思いますが、どの方法で読み込んだとしてもメールと同じように判定して次の工程に流さないといけません。
>
> したがって、どの方法で作られたとしても解析ボタンが必要です。そしてメモのように人が書き込んで作るものは、人がPDFを挿入する場合があります。それにも解析ボタンが必要になります。
>
> ここで質問ですが　data-mirror="記録の箱"が解析ボタンを出しているでしょうか？」

筆者の答えは「出しているが、本文の中の添付へのリンク（pdf・xlsx・zip）だけを拾う。人が入れた PDF（ファイル表示の印）と画像には出ない」でした（§2.3）。

> 2026-10-21 利用者:「解析ボタンの直しの前に、通信フォルダの改善全体（電話・FAXの通知、メールの自動読み込み、メモ）を【考察】にまとめてください。」

それまでに決めていたことのうち、関わるものです。

> 2026-09-15 利用者:「FAXサーバーは近日作ります。サーバー機として中古のワークステーションを買いました」「FAXサーバーとw－cmsを同居させようと思います」

> 2026-10-09 利用者:「新しいメールの読み込みは、ページを閉じても継続するようにしてください」

> 2026-10-15 利用者:「問題が多いようなので方針を変えます　職場にサーバー機を立ち上げ、社外のvpsを通してインターネット上からアクセスできる構成にします　明日より構築を始めるので考察をお願いします」

## 2. いまの形（2026-10-21）

### 2.1 メール

- 通信箱の「📥 新しいメールを読み込む」を押すと、サーバーの裏で読み込みが始まります（`POST /api/mail/fetch-new`・`ext/comm/mail/fetch_job.go`）。
  - 受信と送信の箱を、新しいメールが尽きるまで 50通ずつ読みます。上限は 30分です。
  - ページを閉じても続きます。様子はサーバーの記憶にしか無いので、サーバーを入れ替えると止まります。
  - 定期的に回す仕組みはありません。
- 読むのに使うのは、**押した w-cms の利用者のメールのサインイン**です（`data/mail/<利用者>.json`・M365 のデバイスコードフロー）。
- 同じメールは、本体を落とす前に Message-ID で弾きます。
- できるページ:
  - テンプレートは「通信記録（受信メール）」と「通信記録（送信メール）」です。置き場は `通信箱／YYYY年／MM月` です。
  - タグは、向き・チャネル（メール）・対応（受信は未処理、送信は不要）・差出人・宛先・受信日時か送信日時・Message-ID・In-Reply-To・親ページID などです。
  - 本文に、記録の箱の印 `<section data-mirror="記録の箱"></section>` があります（テンプレートが持っています）。

### 2.2 手で作る記録（「＋ 記録する」）と電話・FAX

- 「＋ 記録する」は `POST /api/intake/memo` です（`ext/comm/handler_memo.go`）。テンプレートは「通信記録（手入力）」です。
  - チャネルは、電話・FAX・メール・メモの4つです。
  - 向きは受信か送信です（メモには付けません）。
  - 必ず `対応：未処理` を書きます。
- 電話:
  - `電話番号` のタグの横に「☎ かける」（`tel:`）と「☑ 記録を作る」が出ます（`phone_decor.go`）。押すと、チャネル電話・向き送信の記録ができます。
  - 着信を受け取る仕組み（CTI。電話機の装置と w-cms をつなぐこと）は、まだありません。コードは注記だけです。
  - ⚠ 食い違い（直していません）: `ext/comm/assets/comm.js` の注記は「発信の記録は向き：送信なので作業待ちには並びません」と書いていますが、実装（`handler_memo.go`）は、かけた電話の記録も `対応：未処理` で未処理の一覧に並べます。
- FAX:
  - チャネルの値「FAX」があるだけです。FAX サーバーとつなぐ拡張（`ext/comm/fax`）は、まだありません。
  - 2026-09-05 に、PDF を FAX の記録として自動で取り込む仕組みはやめました。「FAX サーバーを繋ぐときは、機械専用の入口を作ること」が残っています（【考察】通信記録処理）。
- 機械が使える入口は `POST /api/intake/eml`（.eml を1通）だけです。
  - 認証は普通のログイン（セッション）で、通信箱に書ける人が使えます。機械専用の認証はありません。
  - 使っているのは道具 `tools/mail/push` です（利用者名とパスワードでログインして呼ぶ）。

### 2.3 判定（🤖 解析）と未処理

- 記録の箱の「🤖 解析（添付）」は、`ext/toho/record_sections.go` の `analyzeSectionHTML` が描きます。
  - 拾うのは、**本文の中の添付へのリンク** `<a href="/<ページ>/<ID>.pdf">` だけです。拡張子は pdf・xlsx・zip です。
  - メールの取り込みは添付を 📎 のリンクで書くので、メールには出ます。
  - 人がエディタで PDF を入れると、**ファイル表示の印**（`<section data-type="file-view" data-ref="…">`）になり、リンクではないので出ません。画像は本文の中の絵（`<img>`）になり、これも出ません。
  - 記録の箱そのものは、`チャネル` のタグのあるページにだけ出ます。
- 解析の口 `/api/analyze-attachment` が受けるのは、PDF と表計算（.xlsx）だけです。
  - Gemini が、客先の発注書・図面・業者の見積の返事・どれでもない、のどれかと答えます。
  - 客先の発注書なら案件ページ、図面なら加工製品ページ、見積の返事なら返事ページを、記録の子に作ります。
  - 押すのは人です（人が押したときだけ Gemini を呼ぶ決まり。「人間ゲート型」）。
- メールの本文から作るページ（作るページの選択肢）もあります。
- 未処理の一覧は、通信箱の子孫で `対応` が無いか `対応：未処理` のページです（上限 100件）。

### 2.4 サーバー機

- 職場に Ubuntu のサーバー機を置き、社外の VPS を通して外からつなぐ構成を作っています（【考察】職場のサーバー機と社外からの接続）。
- FAX のモデムは、本番が落ち着いてから足す予定です（同じ文書の §8 の 10）。
- 2026-09-17 に買った HP のワークステーション（Windows 11）と、この Ubuntu のサーバー機が同じものかは、文書に書いてありません。

## 3. 考え方の芯（筆者の案）

**入口がいくつあっても、記録は同じ形の1枚にし、判定と次の工程は1つにします。**

```
入口                         記録                     判定                 次の工程
メール（自動・5分／1時間） ┐
電話（装置の知らせ）       ├→ 通信記録 1枚 ──→ 🤖 解析（人が押す）──→ 案件ページ・加工製品ページ・
FAX（FAX サーバー）        │   （通信箱／年／月・      作るページ             返事ページ・整理 など
メモ（人が書く・PDF を入れる）┘   記録の箱・対応：未処理）
```

- 記録の形（テンプレート・置き場・タグ・記録の箱の印・`対応：未処理`）は、入口によらず同じにします。違うのは `チャネル` と `向き` と、入口ごとのタグ（電話番号・FAX 番号など）だけです。
- 判定（🤖 解析）は、記録に置いた添付から、入口によらず同じ形で出します（§4.1）。
- 次の工程（整理・作るページ・未処理の一覧）は、いまのままです。

## 4. 入口ごとの案

### 4.1 判定ボタンの直し（どの入口にも要る・最初に作る）

- 「🤖 解析（添付）」は、本文のリンクの形で探すのをやめ、**そのページに置いた添付（`files/`）を全部並べます**。
  リンクでも、ファイル表示の印でも、絵でも、置いた添付なら並びます。
- 並べる種類は、PDF・表計算・ZIP（中に PDF のあるもの）・画像（png・jpg・webp）です。
  - 画像は、いまの解析の口が受けないので、口も画像を受けるようにします（Gemini は画像を読めます）。FAX と写真のためです。
- 記録の箱の印のある記録（通信記録）なら、メール・電話・FAX・メモのどれでも出ます。

⚠ いま（2026-10-21 夜）: 作りました。記録の箱の「🤖 解析（添付）」は、記録に置いた添付（PDF・表計算・ZIP・画像）を全部、置いた順に並べます（`analyzeSectionHTML`）。解析の口は画像も受けます（`judgeOrderImage`・判定の頼み文は PDF と同じ）。E2E `verify-record-analyze.js` で、メモに人が入れた PDF にボタンが出て、押すと口へ送ることを確かめました。

### 4.2 メールの自動読み込み

- サーバーの中で、決まった間隔でメールを読みます。日中は 5分ごと、夜間は 1時間ごとです（利用者の言葉）。
  - 日中と夜間の境、土日・休みの日をどうするかは、問い2です。間隔と時刻は設定（`config/settings.json`）に置く案です。
  - 押して読む「📥 新しいメールを読み込む」は残します（すぐ読みたいとき）。自動の読み込みと重ならないよう、読み込みは同時に1つだけにします。
  - サーバーを入れ替えたら、次の回から続きを読みます（Message-ID で弾くので、二重にはなりません）。
- ⚠ **誰のメールのサインインで読むか**が、いちばん大きな問いです（問い1）。
  いまは押した人のサインインで、その人の受信箱を読んでいます。自動で読むには、決まった1つの口座が要ります。
  - 案A: 会社の代表の受信箱（共有の受信箱）を、自動の読み込み専用の w-cms の利用者でサインインして読む。
  - 案B: いまのように、サインインした人それぞれの受信箱を、全員分順に読む。
  - 筆者の勧めは案Aです。記録は会社の記録で、人ごとにばらばらだと抜けと重なりが出るためです。
- メールの取り込みは、いまの芯（`comm.IntakeFile`・Message-ID の確かめ）をそのまま使います。

### 4.3 FAX

- FAX サーバー（モデムをつないだ機械の上で動く FAX の道具）が受けたら、w-cms の**機械専用の入口**へ渡します。
  - 渡すもの: FAX の画像（PDF。TIFF なら FAX サーバーの側で PDF にする）・送ってきた番号・受けた日時。
  - w-cms は、チャネル FAX・向き受信の通信記録を作り、FAX を添付として置きます。記録の箱と `対応：未処理` も付きます。
  - 送ってきた番号は、連絡帳の FAX 番号から相手を引いて、差出人に入れます（引けなければ番号のまま）。
- 判定は §4.1 の「🤖 解析」で、メールの添付と同じです。
- 同じ機械に w-cms と FAX サーバーを置くなら、入口は外へ出さずに済みます（§4.5）。
- Ubuntu で FAX を扱う道具（HylaFAX+ など）は、モデムを足すときに選びます。
- FAX を送る側（作った PDF をワンタッチで業者へ）は、別の話です（【要求】製造・【要求】通信拡張）。

### 4.4 電話

- 電話の装置（CTI。【要求】通信拡張の言葉では ICT 装置）が着信を知らせたら、w-cms の機械専用の入口へ渡します。
  - 渡すもの: かけてきた番号・日時・（あれば）通話の長さ・出たかどうか。
  - w-cms は、チャネル電話・向き受信の通信記録を作ります。かけてきた番号は、連絡帳の電話番号から相手を引きます。
- それまでの勧めは「着信を知らせて、記録するかは人が押す」でした（無人でページが増えすぎないための歯止め）。
  今回の利用者の言葉は「届いた時点で通知されるので、通知を受けて作動するプログラムが必要」です。
  着信ごとに記録を作るか、知らせるだけにするかは、問い5です。
- 電話の記録には添付が無いのがふつうです。話した中身は人が書きます。人が PDF や写真を足せば、§4.1 で解析できます。
- どの装置で、どう知らせてくるか（HTTP で呼んでくれるのか、別の形か）が分からないと作れません（問い4）。

### 4.5 機械専用の入口と認証

- 電話と FAX のために、機械が呼ぶ入口を作ります（例: `POST /api/intake/fax`・`POST /api/intake/call`）。中では、いまの記録の芯を使います。
- 認証の案:
  - 案A: 同じ機械からだけ受ける（ループバック。`127.0.0.1`）。FAX サーバーと w-cms が同じ機械なら足ります。
  - 案B: 機械用の鍵（設定の外の秘密。`WCMS_` で始まる環境変数）を付けて呼ぶ。別の機械からでも呼べます。
  - 筆者の勧めは、A と B の両方です。⚠ VPS のリバースプロキシが、同じ機械の上から w-cms へつなぐ形になると、外からの要求もループバックに見えます。ループバックだけを頼りにしないためです。
- 機械が作った記録の書き手（ページの持ち主）は、機械用の w-cms の利用者にします（監査に残るように）。

⚠ いま（2026-10-21 夜）: 作りました（`internal/auth/machine.go`）。前置き `/api/machine/` の下の口だけが機械専用で、次の3つがそろったときだけ通します。

- 鍵: `Authorization: Bearer <鍵>` が環境変数 `WCMS_MACHINE_TOKEN`（16文字以上）と一致する。決まっていなければ、入口は閉じています。
- 呼んだ機械のアドレス: 既定は同じ機械だけ。ほかの機械から呼ぶなら `WCMS_MACHINE_ALLOW` に CIDR をカンマ区切りで書く。
- 書き手: 環境変数 `WCMS_MACHINE_USER` の w-cms の利用者。機械が作った記録の持ち主と監査はこの人です。

鍵で通すので、この前置きは Origin の確かめ（CSRF）から外しました。口は2つです。

- `POST /api/machine/call`（`ext/comm/machine_call.go`）: 電話。`answered` で記録を作り、`hangup` で「通話終了」を書く。番号は連絡帳などの `電話番号` と数字だけで比べて相手を引く。
- `POST /api/machine/fax`（`ext/comm/machine_fax.go`）: FAX。PDF か画像を受け、記録を作って添付に置き、本文に表示する。番号は `FAX番号` で相手を引く。TIFF は受けない（FAX サーバーの側で PDF にする）。

どちらも、届いたことを `comm.NotifyArrival` で知らせます（§7.5 のスマホへの知らせが聞き手になる）。

### 4.6 メモ（人が書く記録）

- 「＋ 記録する」は、いまのまま残します。電話を手で記録するときと、メモのときに使います。
- 人が PDF や写真を入れたら、§4.1 で「🤖 解析」が出ます。
- 利用者の言葉「ボタンを押して読み込むのは、メモになると思います」のとおり、人が押して作る記録はメモ（と手で書く電話）が中心になります。

### 4.7 届いたことを知らせる

- 自動で記録が増えるので、届いたことを人が知る道が要ります。
  - 案: 通信箱を開いている画面に「新しい記録が N 件届きました」を出す（いまある、ほかの人の書き込みの知らせと同じ形）。
  - 未処理の一覧は、いまのまま、届いた記録を拾います。
- スマホへの知らせ（プッシュ）までするかは、問い7です。

## 5. 作る順（案）

1. 判定ボタンの直し（§4.1）。どの入口にも要り、いまのメモにもすぐ効きます。
2. メールの自動読み込み（§4.2）。問い1・2の答えが要ります。
3. 機械専用の入口と認証（§4.5）。
4. FAX（§4.3）。モデムと FAX の道具が整ってから。
5. 電話（§4.4）。装置と知らせ方が分かってから。
6. 届いたことを知らせる（§4.7）。

## 6. 問い

1. **自動の読み込みは、どのメールの口座を読みますか**（§4.2）。会社の代表の受信箱を1つ読む（案A・筆者の勧め）か、サインインした人それぞれの受信箱を読む（案B）か。
会社の代表メールとして指定されたアドレス
2. **日中と夜間の境の時刻**と、土日・休みの日の間隔（§4.2）。
8時から20時までが日中。土日は夜間と同じ
3. **判定（🤖 解析）は、いままでどおり人が押しますか**。利用者の言葉は「解析ボタンが必要です」なので、押す形のままと読みました。届いたら自動で解析する（Gemini を自動で呼ぶ）形にはしない、でよいですか。
人が押します。
4. **電話の装置の型と、着信の知らせ方**（§4.4）。HTTP で知らせてくれるか、ほかの形か。
電話装置はアロハND6でパソコンとつなぎます。パソコンとの接続はUSBケーブルとなります。USBの電源断など対策も必要と思います。
このプログラムもお願いします
5. **電話の着信ごとに記録を作りますか**（§4.4）。出られなかった着信も記録にしますか。それとも、知らせるだけにして、記録するかは人が押しますか。
出た着信だけ記録にします。セールスなど不要なものだった場合、人間が消します。電話中に記録するメモともいえるので、電話に出たら素早くメモを作って、しかもユーザーがアクセスする手段を提供して欲しいです。
6. **FAX サーバーは、w-cms と同じ機械に置きますか**（§4.3・§4.5）。Ubuntu のサーバー機と、09-17 に買ったワークステーションは同じものですか。
FAXサーバーはw-cmsと同じ機械に置きます。FAXモデムとして、プラネックスのPL-US56K2（A）を買いました。

### 7.1 メールの自動の読み込み（問い1・2）

### 7.3 電話（問い4・5）——アロハ ND6

製造元の機能仕様書（日辰電機製作所「アロハND6 機能仕様書」）を読みました。要点です。

- USB の仮想 COM ポートです（9600bps・7ビット・偶数パリティ・ストップビット1・RTS/CTS）。Windows では「Prolific USB-to-Serial」、Linux では `/dev/ttyUSB0` のような名前で見えるはずです。
- 送ってくる電文（どれも STX〜ETX で、中は ASCII）:
  - 着信: 着信日時（月日・曜日・時分の9文字）＋発信者の番号（20文字）。番号の代わりに、非通知は「P」、表示圏外は「O」、サービス競合は「S」、公衆電話は「C」、受信の誤りは「E」。
  - 受話器を上げた・置いた: 日時（9文字）＋「OF」（上げた）か「ON」（置いた）。**着信のときだけ**送ります（かけるときは送りません）。
  - 出る前に相手が切った（未応答）: 日時（9文字）＋「UR」。
  - パソコンから「CON」を送ると「ALOHA」が返ります（つながっているかの確かめに使えます）。
- だから、**出た着信だけ記録にする**ことができます。着信の番号を覚えておき、「OF」が来たら、その番号で記録を作ります。「UR」なら作りません。

決めたこと:

- 電話の道具（`w-cms` とは別の小さなプログラム）が ND6 の電文を読み、「OF」で w-cms の機械専用の入口を呼びます。
- w-cms は、チャネル電話・向き受信・`対応：未処理` の記録を作ります。番号から連絡帳の相手を引きます。
- 出たらすぐ書けるように、記録ができたことを知らせます（問い7のスマホへの知らせと、w-cms を開いている画面の知らせ）。押すと、その記録が開きます。
- 「ON」（置いた）で、記録に通話の終わりの時刻を書き足します。
- 要らない電話（セールスなど）の記録は、人が消します（利用者の答え）。
- USB の電源が切れたときの対策:
  - 道具は、ポートが無くなったら開き直し続けます（数秒おき）。1分ごとに「CON」を送り、「ALOHA」が返らなければ開き直します。
  - Linux なら、udev の決まりで決まった名前（例 `/dev/aloha-nd6`）を付け、USB の省電力（オートサスペンド）を切り、systemd で落ちたら起こし直します。
- ⚠ **ND6 をどのパソコンにつなぐかを、利用者に確かめます**（問い8）。電話の線は ND6 を通って電話機へ行くので、ND6 は電話機のそばに置くことになります。

⚠ いま（2026-10-21 夜）: 電話の道具 `cmd/w-cms-phone` を作りました（電文の読み方は機能仕様書のとおりに試験で確かめた・実機ではまだ）。置き方（Ubuntu の udev と systemd・Windows で `-open`）は [deploy/phone/README.md](../../deploy/phone/README.md) です。

### 7.4 FAX（問い6）——プラネックス PL-US56K2（A）・Ubuntu

- FAX サーバーは、w-cms と同じ Ubuntu の機械に置きます。
- FAX の道具は HylaFAX+ を案にします（Ubuntu のパッケージ `hylafax-server`）。受けた FAX を PDF にして、w-cms の機械専用の入口へ渡す小さなスクリプトを、受信のときに動かします。
- ⚠ PL-US56K2（A）が Linux で FAX モデム（Class 1）として使えるかは、実機で確かめます（`lsusb`・`/dev/ttyACM0` が出るか・`AT+FCLASS=?` に 1 が入るか）。調べた範囲では、この型の Linux の情報は見つかりませんでした。
- USB の電源が切れたときの対策は、電話と同じです（udev の決まりで決まった名前・オートサスペンドを切る・systemd で起こし直す）。
- 設定のファイルと手順は、リポジトリの `deploy/` に置きます。

⚠ いま（2026-10-21 夜）: 設定と道具を作りました（[deploy/fax/README.md](../../deploy/fax/README.md)）。HylaFAX の受信のときに `faxrcvd-wcms` が FAX を PDF にして `/api/machine/fax` へ渡し、渡せなければ `w-cms-fax-retry` が5分ごとに送り直します。モデムの USB の番号は、実機をつないで確かめてから udev の決まりに書きます。⚠ 実機ではまだです。

### 7.5 届いたことを知らせる（問い7）

- スマホへの知らせは、Web Push（ブラウザの通知の標準）で作ります。
  - 外のサービスと契約しないで済みます。外部のライブラリも要りません（暗号は Go の標準ライブラリで足ります）。
  - 知らせの中身は暗号にして送ります。届けるのは、スマホのブラウザの会社（Google・Apple）の通知の道です。
  - ⚠ スマホが w-cms を、正しい証明書の HTTPS で開けることが要ります（VPS を通した社外からの入口なら足ります）。iPhone は、w-cms をホーム画面に追加したときだけ受けられます。
- 知らせるのは、電話に出たとき・FAX が届いたとき・メールが届いたとき（自動の読み込みで新しく入ったとき）です。だれに知らせるかは、知らせを受けると決めた人（右のレールなどで「この端末で知らせを受ける」を押した人）です。

⚠ いま（2026-10-21 夜）: 作りました。

- コアの Web Push（`internal/cms/webpush.go`）: 中身の暗号は RFC 8291 の例と1バイトも違わないことを試験で確かめました。送り手の鍵は `data/webpush/vapid.pem`、受け口は `data/webpush/subscriptions.json` です。
- 画面の上の帯の「🔕 知らせを受ける」（`assets/push.js`）で、その端末の受け口を作ります（押すと試しの知らせが届く）。知らせを押すと、その記録が開きます（`assets/sw.js`）。
- 通信の拡張は、電話・FAX・メール（受信の箱に新しく入ったもの。1回に4通以上ならまとめて1つ）が届いたとき、受け口を持つ人のうち、その記録を読める人へ送ります（`ext/comm/push_notify.go`）。
- ⚠ 本物のスマホでは、まだ確かめていません。正しい証明書の HTTPS で開く必要があるので、VPS を通した社外からの入口ができてから確かめます。
