**この文書でよく使う言葉**

| 言葉 | 意味 |
|---|---|
| 添付 | ページに付けたファイルです。ページごとの `files/` フォルダに入ります |
| 配信 | サーバーが添付をブラウザへ送ることです。送るときに付けるヘッダで、ブラウザが開くか保存させるかが決まります |
| 画面の部品（クローム） | サーバーや画面が足した、本文ではない部品です（枠・ボタンなど）。保存しません |
| 鏡 | 本文には印だけを置き、表示のたびにサーバーが中身を描く仕組みです |
| 配線 | 印が「どれを指すか」の指定です。ファイル表示では、どの添付を開くかを属性 `data-ref` に書きます |
| プロパティ欄 | 選んでいるものの設定を、その近くで直せる小さな欄です |
| コンテキストメニュー | 右クリックなどで、その場に出るメニューです |
| OCR | 画像の中の文字を読み取って、文字のデータにすることです |

## 2. 種類別の表示（提案1）

**ファイルは種類に応じた最適な見た目で本文に現れる**、という原則です。

| 種類 | 表示 | 現状 | 埋める距離 |
|---|---|---|---|
| 画像（PNG/JPEG/GIF/SVG） | **そのまま表示**（インライン `<img>`） | **実装済み**（画像アップロード・2026-08-26） | なし |
| PDF | **クリックで展開**（▶を押すと `<embed>`・ビューア内スクロールで多ページも背丈が伸びない） | **実装済み**（2026-09-01・閲覧モードの画面の部品。サムネイル案は取りやめ——生成に外部依存が要る一方、埋め込みはゼロ依存で内部スクロールが場所の問題も解く） | なし |
| ZIP | **クリックで中身の目録**（名前とサイズ。`archive/zip` の目録読みで展開はしない・SJIS名も復号） | **実装済み**（2026-09-01・`GET /api/zip-list`）。**中身の取り出しは取り込みの時点で行う**（2026-09-17・`cms.ExpandZip`。メール添付の ZIP は中のファイルが1つずつ添付になる。人が落とした ZIP は展開しない——原本が無いため） | なし |
| その他のバイナリ（CAD・Office 等） | **アイコン＋クリックでアプリ表示かダウンロード** | 📎 リンク＋`download` 配信（受け皿は 2026-08-31 実装済み） | サムネイル等の飾り |

設計の観察:

- **ワンノート移行の受け皿6条件の1つが、まさに「添付15拡張子」です**
  （[【考察】ワンノート移行.md](【考察】ワンノート移行.md)）。
  この提案は、移行の前提条件を先に一般化した形になっています。
- **添付の置き場は 2026-08-31 に `files/` サブフォルダへ分離済み**です。
  - 添付は、正本（本文と、ページの属性を書いたファイル＝サイドカー）と同じ場所に置かなくなりました。
    そのため、「添付の名前がサイドカーを上書きする」穴は、構造的に消えました。
  - その結果、**拡張子リストは安全の門ではなく運用の方針**になりました。
  - きっかけは利用者の指摘で、そのとおりでした。

    > 利用者:「.json禁止は、アップロードファイルとjsonが同じ
    > フォルダにあることが原因では？」

  - `safeAttachmentName`（いまは `SafeAttachmentName`）の一本化は、引き続き維持します。
    これは、添付の名前の文字種と、トラバーサル（フォルダの外を指す書き方）を正規化する関門です。
- **PDFサムネイルの生成手段**は、当初の論点でした。
  標準ライブラリに PDF を絵にする部品（レンダラ）は無く、外部依存は原則禁止だからです。
  - 候補は3つありました。①`<embed>` の埋め込み／②Gemini で画像化／③アイコンのみ。
  - ①を採用しました。そこから「クリックで展開」へ発展して、決着しました（§5 の 2）。
- バイナリの「クリックでアプリ表示かダウンロード」は、配信側の `Content-Disposition` の仕事です。
  `Content-Disposition` は、ブラウザに「開く」か「保存させる」かを伝えるヘッダです。
  **SVG の sandbox CSP と同じく配信ヘッダが安全の本体**です（作業引き継ぎの罠と同じ）。

### 2.1. 置く場所が増えた——`section[data-type="file-view"]`（2026-09-14 実装）

上の表は、すべて**添付そのものの隣**での見せ方でした。
2026-09-14 に、**添付を別の場所で開く**仕組みができました。きっかけは、利用者の次の言葉です。

> 利用者:「PDFがほかの部品の一部で、部品ページを作らず、ほかのページに
> 埋め込む場合はどうしますか？」「表示するという意図を伝える名前が良いと思います。ほかに
> 編集するという意図も出てくると思います」

本文へマーカー（印）を1つ置き、**開く先は属性に書きます**。
この形にしたのは 2026-09-15 です。それまでは、中に参照タグを1つ書かせていました。
正本は [internal/cms/file_view.go](../../internal/cms/file_view.go) です。

```html
<section data-type="file-view" data-ref="010272-c3p7"></section>
```

#### 中身を描くのはサーバー

- **中身を描くのはサーバー**です（鏡型・`renderFileView`）。
- 描いた中身は `.vocab-chrome`（保存しない部品の印）に包みます。
  そのため、シリアライザ（画面の本文を保存用の HTML にする部品）は保存しません。
  正本に残るのは**マーカー1つだけ**です。
- **計算ビュー（`View: true`）ではなく鏡型**にしました。
  計算ビューは、**要素を見ずページIDだけで描く**ためです。それでは、要素ごとに違う `data-ref` が読めません。
- この理由は、2026-09-15 に入れ替わりました。
  それまでの理由は「全消しすると人が書いた参照タグが消えるから」でした。

#### 開ける形式

**開ける形式は `fileViewKinds` の表**で決まります。

> **この節のその後**（2026-10-14 に [file_view.go](../../internal/cms/file_view.go) の `fileViewKinds` で確かめました）
>
> 下の一覧は、2026-09-15 の途中の形です。いまの表は、次の10個です。
>
> - `.pdf` は `<embed>`
> - `.png` `.jpg` `.jpeg` `.webp` `.gif` `.svg` は `<img>`
> - `.mp4` は `<video>`
> - `.m4a` `.mp3` は `<audio>`
>
> `.webm`・`.wav`・`.txt`・`.csv`・`.log`・`.md` は、表から外しました。
> 添付として保存できる拡張子に無く、配信の側もその場に描ける形で返さないためです
> （2026-09-15・[【考察】ファイル表示のコードレビュー.md](【考察】ファイル表示のコードレビュー.md) の #1）。
> 表は、配信の側（`setAttachmentHeaders`）の帰結です。足すときは、配信の側を先に直します。

- `.pdf` は `<embed>`
- `.png` `.jpg` `.jpeg` `.webp` `.gif` `.svg` は `<img>`
- `.mp4` `.webm` は `<video>`
- `.m4a` `.mp3` `.wav` は `<audio>`
- `.txt` `.csv` `.log` `.md` は `<embed>`

増やす基準は「ブラウザが**素で**描けるか」だけです。
描画ライブラリを連れてくるのは、開発方針 §1（外部依存の最小化）に触れます。

**表に無い形式でも「開くリンク」を出します**（2026-09-15・`kindOther`）。

- CADもOfficeもZIPも、ブラウザは素で描けません。
- しかし、**ファイルは在る**のだから、「見つかりません」は嘘でした。
- 押せば保存でき、手元のアプリで開けます。

#### 配線の書き方

- **配線に名前は要らなくなりました。**
  旧い形では、中のタグ名（`受信元` でも `参考図` でも）に意味がありませんでした。
  どれが配線か、読む人に見分けられませんでした。それが、属性へ移した理由の1つです。
- **いまは中に参照タグを書いても開きません**（`TestFileViewIgnoresInnerTags`）。
- **値を書くための入口が「🔗 参照」**です
  （`makeCopyRefButton`・[エディタ仕様.md](../旧文書/エディタ仕様.md) §7.4）。
  埋め込み自体は前からできました。ただ、`010272-c3p7` は、添付IDを手で調べないと書けませんでした。
- 手順は次のとおりです。
  **添付で「🔗 参照」→ 行き先のページの 📄 ファイル表示 で配線の札を押す → 欄に貼る**。
  札は、編集のときにファイル表示へ付く小さなボタンです。
  札とプロパティ欄のことは [エディタ仕様.md](../旧文書/エディタ仕様.md) §7.5 にあります。

> **この節のその後**（2026-10-01。`assets/app.js` で確かめました）
>
> - ID を写す入口が増えました。
>   ファイル表示と写真には「⋯」が1つ付き、その中に「🔗 ID を写す」があります（`openFileMenu`）。
>   📎 のリンクの横の「🔗 参照」は、PDF・ZIP のほか、STEP・DXF・Excel などの添付にも出ます。
> - スラッシュメニューで空のファイル表示を挿すと、参照の欄がすぐ開きます（`openNewFileViewWire`）。写した ID を貼るだけです。
> - 描けない形式の「開くリンク」は、届いたときの名前で保存されます（リンクに `download` を付けました）。
> - いまの要求は、[【要求】添付.md](../【要求】添付.md) §5 の「形式に合った操作（「⋯」）」にあります。

#### なぜこの形・この名前か

- **なぜ `<embed>` を本文に書かせず、マーカーにしたのか**。
  理由の正本は [セキュリティ設計.md](../旧文書/セキュリティ設計.md) §4 です。
- 名前を `pdf-view` にしなかったのは、**同じ場所に別の意図が並ぶ**からです。
  - 「編集する」という意図が控えています。WebDAV でローカルアプリへ渡す話です
    （§3・[【考察】添付をローカルアプリで編集する.md](【考察】添付をローカルアプリで編集する.md)）。
    （その後: WebDAV は 2026-10-15 にやめ、ローカルアプリへ渡すのは「📝 ローカル編集」になりました。）
  - `pdf-edit` では「PDFを編集する」意味になってしまいます。
  - 対象（file）と意図（view）で名づければ、扱える形式が増えても、名前が変わりません。

## 3. コンテキストメニュー: OCR・編集（提案2）

| 操作 | 中身 | 既存の土台 |
