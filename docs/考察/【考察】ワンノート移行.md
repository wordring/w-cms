# 【考察】ワンノート移行

現在ワンノートで回している業務を w-cms へ移すために、**実物のノートを読み取って
「w-cms 側に必要な受け皿（スキーマ的な条件）」を洗い出した**調査の記録です。
移行スクリプトの設計はまだしません——ここに書くのは**実測値と、そこから決まる条件**だけです。

- 調査日: 2026-08-25。OneNote デスクトップ版の COM（`GetHierarchy` / `GetPageContent`）を
  **読み取り専用**で使用（ワンノート側への書き込み・削除は一切なし）。
- 対象: 全4ノート1,522ページを取得したうえで、**現在運用中の「板金部」ノートに絞って分析**
  （2026-08-25 ユーザー確認:「今運用しているのは板金部というノートのみです」）。
- 実行できること自体は 2026-08 中旬に確認済み（4ノート・当時1,514ページの列挙と本文取得）。
  実施は**運用開始後**の予定（画像アップロードは 2026-08-26 に実装済み）。

## 2. 事実上のスキーマ（発見された定型）

紙の帳票が無いだけで、実質は帳票運用だった。頻度順に:

**① ■材料 の下の表（横持ち・1行目が鍵）——471件**（旧称「部材表」も仮の呼び名）

```
材質 | 形状 | 寸法 | 個数 | 単価（ロット） | 単価（ロット1）甲田 | 単価（ロット1）乙川 | 備考
```

**列名がデータを運んでいる**のが要点——業者名（甲田・乙川）とロット数が列名に埋め込まれ、
ページごとに変わる（ロット1・5・6・7・15・20・40・100 の変種を確認）。

**② ■見積もり の下の表（縦持ち・第1列が鍵）——497件（変種計）**

> ⚠ **この表を「工程表」と呼ぶのはやめました**（2026-08-30・ユーザー指摘）。見出しは **■見積もり**
> であって「工程表」ではなく、**■工程 は別物**（写真主体の作業手順・表ではない）です。第1列に
> 工程名が並ぶために付けた仮の呼び名でしたが、業務の言葉と衝突します。

```
工程   | 数 | 単位 | 備考          ← 1行目
ロット |    | 個   |               ← 鍵は第1列にある
材料   |    | 円   |
ブランク・ドリル・ブレーキ・組み立て …
```

`工程|工数|備考`（102件）や、列側にロットを並べる `工程|ロット6|ロット7|ロット20|備考` の変種もある。

**③ 発注明細表——22件**: `No.|部品番号|品名|サイズ|図面番号|数量|単位|単価|金額`。
w-cms の受注明細（`client-order-items`）とほぼ同型。

**④ 図面番号はハイフン連結の複合キー**: `S130-Q222-97-04`・`T100-02-06（台座）`・
`KHT-NKH-0032-BARI` など。**ワンノートがこれを検索できないことが w-cms の動機の1つ**
（[【要求】運用.md](../【要求】運用.md) §6 の検索）。

**⑤ 手動のテンプレート運用が既にある**——`01 資料/事務用` に「**コピペ ノート 各製品用**」
「**コピペ ノート まとめ用**」というコピー元ページが置かれ、加工製品ページはここから
コピーして作られている。w-cms のページテンプレート機能
（[【考察】ページテンプレート.md](【考察】ページテンプレート.md)・実装済み）の直接の先行事例で、
**移行時はこの雛形がテンプレートページの種になる**。「各製品用」の節構成（＝加工製品ページの
事実上のスキーマ）:

```
■不具合 ■参考図 ■図面 ■図面番号 ■データ（CADファイル）
■材料（部材表）  ■外注加工（表・後述）  ■購入品  ■支給品  ■塗装
■見積もり（工程表）  ■工程（写真主体の作業手順）  ■完成品
```

## 2.5 引き出したい3種と、現状の書かれ方

**各加工製品ページから引き出したいものは「購入部品・購入材料・外注依頼品」の3種**
（2026-08-25 ユーザー要件）。実データでの現れ方は三者三様で、これが移行と語彙設計の
難易度をそのまま決める:

| 引き出したいもの | 現状の書かれ方 | 構造化の度合い |
|---|---|---|
| **購入材料** | `■材料` の部材表（`材質\|形状\|寸法\|個数\|…`）。471件が**記入済み** | ◎ 表として揃っている。ただし仕入先が備考欄（「白石商店」）や列名（甲田・乙川）に散る |
| **購入部品** | `■購入品` の下の**見出し行の無い2列表**（`ウェルドナット…M8 \| 5個`）や箇条書き | △ 表はあるが**ヘッダが無い**。数量は「5個」と単位込みの文字列 |
| **外注依頼品** | `■外注加工` に専用表（`名称\|材質\|加工\|個数\|推奨業者\|備考`）が**設計されたが、確認した21件すべて空**。実データは日付入りの自由文（「2026-06-15　青葉電装　緑　ロット20　3500」）や、まとめページの「○○　外注発注　2026-01-XX（部品リスト）」 | ✗ 様式は現場に定着せず、自由文に散っている |

外注加工の表が埋まらなかった理由は推測になるが、**ワンノートでは表を埋めても何も
起きない**（集計されない）ことが大きいはずで、これは w-cms が変えられる点でもある——
埋めれば手配リストや発注書に載るなら、埋める動機が生まれる。逆に言えば、
**移行時に自由文から外注情報を機械抽出するのは無理筋**で、移行後の運用で埋めていく前提が現実的。

## 3. スキーマ的な条件（w-cms 側に必要な受け皿・重い順）

1. **画像アップロードが移行の絶対前提**——4,825枚・86%のページ。規模が判明したことで、
   [【要求】添付.md](../【要求】添付.md) の優先度の根拠になった（**2026-08-26 実装済み**）。
   印刷イメージ1,120枚は原本PDFが添付されていれば移行対象から外せる（XPSの裏ファイル972個も同様）。
2. **OCRテキストの受け皿**——移行で捨てると、図面画像の中の文字（図面番号など）が
   引けなくなり**「検索を付けたワンノート」なのに検索が後退する**。画像に付随する
   検索可能テキストの置き場（索引に載る形）が要る。形式は未決（`figcaption` か、
   画像コンテナ内の本文テキストか）。**鍵は「見える文字がすべて」との整合**——
   隠しテキストにすると原則が破れる点に注意。
3. **縦持ち表（第1列が鍵）の語彙**——現行の表語彙は**1行目を見出し行として読む**だけ
   （[vocab_index.go](../../internal/cms/vocab_index.go) `syncVocabTable`）。2番目に多い定型
   （工程表497件）が索引に載らない。「鍵は第1列」型を語彙へ足すか、移行時に横持ちへ
   転置するかの決定が要る（3値［数・単位・備考］を持つため `dl`（名前：値）では潰れる）。
4. **添付の許可拡張子**——調査時点は **`.pdf` のみ**（[pdf_handler.go](../../internal/cms/pdf_handler.go)
   `allowedAttachmentExts`。いまも PDF の口だけが使う）。実データは `.dxf`(389)・`.rpcd`(251)・`.xlsx`(175)・`.zip`(54)・
   `.docx`(42)・`.dwg`・`.step`・`.x_t`・`.slddrw`・`.igs`・`.eml`・`.pub`・`.lbx`・`.mp4` の計15種で、
   **約950件のCADデータ等が当時の w-cms には入らなかった**。**2026-08-31 に解消**——汎用アップロード
   `POST /api/upload-file` が設定 `attachment_extensions`（既定はこの15種）を受け、置き場も `files/`
   サブフォルダへ分離した（[【考察】添付ファイルの表示と操作.md](【考察】添付ファイルの表示と操作.md)）。
   拡張子を絞る設計意図（サイドカー `<id>.meta.json` の上書き防止＝権限昇格の遮断）は `files/` 分離で
   構造的に不要になり、`.json` は設定に書けないまま（`settings.go` が拒否する）。
5. **可変列名は汎用索引でしか受からない**——`単価（ロット20）甲田` のような列名は
   硬い列スキーマ（`price INTEGER`）では表現できず、`vocab_index`（ページID・表のID・
   名前・値）なら**そのまま入って、そのまま引ける**。スキーマ設計し直しの「名前：値」汎用索引への
   一本化（D-1・2026-08-31 実装。硬いドメイン表は全廃）を、実データが裏付けた形。業者名もロット数も
   **見えるところに書いてある**——「見える文字がすべて」と同じ向き。
6. **見出し行の無い表**——購入部品の2列表（名前｜数量）にはヘッダが無い。現行の表語彙は
   **1行目を見出し行として食べる**ので、そのまま入れると1行目の部品が鍵に化けて消える。
   移行時にヘッダを補うか、「見出し無し2列＝名前：値の並び」として受ける形式を決める必要がある。

### 追記: 文字数の実測（2026-09-01・表の折り返し制御のため）

| 対象 | 件数 | p50 | p95 | 最大 |
|---|---|---|---|---|
| ページ名（＝品名） | 770 | 8字 | 19字 | 32字 |
| ■図面番号 の下の値 | 260 | 12字 | 18字 | 46字（外れ値1件） |

「上位5%は無視する」方針（ユーザー指示）で、エディタの折り返ししきい値を20字に確定
（app.js の ATOMIC_MAX）。移行時の列幅設計にもそのまま使える。

## 4. 楽観できる材料（「無い」と確認できたもの）

- **ページ間リンクの書き換え問題は実質存在しない**（`onenote:` リンク2件のみ）。
  外部リンクは `a[href]` でそのまま通る。
- **自由配置の線形化はほぼ自明**——1ページ1アウトライン（本文枠）が基本で、
  複数枠のページはごく少数（位置でソートすれば足りる）。サブページも0。
- **階層は `parent_id` ツリーでそのまま受かる**（最大7段）。セクショングループ／
  セクションは本文の無い「分類ページ」になる——**葉だけがテンプレート**という判定
  （[【考察】ページテンプレート.md](【考察】ページテンプレート.md)）とも整合。
- **手書きインク（3ページ）は画像化で足り、ワンノートのタグ機能（6個）は無視できる規模**。
- **「テンプレート」という名前のページは存在しない**——テンプレート置き場の名前駆動判定と
  衝突しない。
- タイトルの重複（全ノート横断で208種。「まとめ」×73・「印刷イメージ」×33 など）は、
  w-cms がページを数字IDで識別するため問題にならない。

## 4.5 実際に3枚移して分かったこと（2026-09-21）

**`【受注】組立補助装置` から3枚**（`軸受ブラケット2`・`昇降駆動
ブラケット`・`調整フランジ`）を w-cms の流儀へ移しました。**想像では出なかったこと**が
並んだので、そのまま残します。

### ⚠ 条件が2つ消えました

| 条件 | 変化 |
|---|---|
| **2. OCRテキストの受け皿** | ⚠ **要件ではありませんでした**。ユーザー（2026-09-21）:「OCRテキストは、ワンノートが画像から取得するものでしょうか？それなら**使ったことが無いので不必要**です」「**ワンノートの検索は本当に使い物にならなかった**のです」 |
| **XPS→PDF の変換** | ⚠ **ほぼ要りません**（下の実測） |

⚠ **「実装が重い条件」が、実は要件ですらなかった**——実物とユーザーに当たらないと
出ない話でした。§3 の重さの見積もりは、**そこだけ過大**でした。

### ⚠ 印刷イメージと原本PDF（実測155ページ）

4セクション（組立補助装置・装置B・装置D・装置C）で数えた結果:

	印刷イメージあり  64ページ
	  ├ 原本PDFもある 39ページ … ⚠ **変換不要**（原本を移せばよい）
	  └ 原本PDFなし   25ページ … ⚠ 全体の16%
	写真 690枚 ／ 添付 379件

ユーザー:「私は普段、**XPSをWindowsに印刷させてPDF**にしています」。

⚠ **その手順を機械にやらせる必要はありません。** 原本PDFが無い25ページにも、
**ワンノートが既に描いた印刷イメージ（PNG）が取り出せます**——それを**PDFに包むだけ**で
済みます（`gopdf` は画像をPDFに置けます）。**XPSにも印刷にも触れません。**
⚠ **画質は「ワンノートが保存した解像度」止まり**ですが、**いま画面で見ているものと
同じ**です。原本が要るなら、そのときは人が元のファイルを探すことになります。

### 取り出し方（実測で通った手順）

- **添付**（PDF・`.rpcd`・`.dxf`）… `InsertedFile` の **`pathCache`** に実体があります。
  ⚠ `pathSource` は**元の置き場**（デスクトップ等）で、**もう無いことがあります**。
- **画像** … `GetBinaryPageContent(pageID, callbackID, ...)`。
  ⚠ **`objectID` では取れません**（`0x8004200E`）——`<Image><CallbackID callbackID="…">` の
  **callbackID** を渡します。
- **印刷イメージと写真の見分け** … `<Image isPrintOut="true">`。
  ⚠ **これがあるので、XPS由来と現物写真を機械的に分けられます**。

### ⚠ 筆者の変換器の誤り（記録）

最初の移植で**表の中身が `<p>` の羅列**になり、ユーザーから「**見出しもただのテキストに
なっていて、構造が崩れています**」と指摘されました。

⚠ **原因はワンノートの `OE`（アウトライン要素）が入れ子であること**——表のセルの中にも
`OE` があり、**表として拾ったあと、セルをもう一度テキストとして拾って**いました。
だから同じ中身が表の外に二度並びます。**`Outline` の直下の `OE` だけを歩く**のが正解。

⚠ **そしてこの誤りは、報告そのものを誤らせました**——`■材料` の表を先にテキストとして
食べてしまい、「**材料の表は空でした**」と報告しました（実際は取れていた）。
**構造を壊す変換は、壊れたことを隠します。**

### 実物の構造（3枚に共通）

	■不具合 ／ ■参考図 ／ ■図面 ／ ■図面番号 ／ ■データ ／ ■材料 ／ ■外注加工
	／ ■購入品 ／ ■支給品 ／ ■塗装 ／ ■見積もり ／ ■工程 ／ ■完成品

- ⚠ **`■外注加工` に `推奨業者` の列があります**（`名称／材質／加工／個数／推奨業者／備考`）。
  **w-cms の語彙のほうが実物より列を落としていました**——2026-09-21 に「外注加工表に
  外注先の鍵が無い」と結論しましたが、**ワンノートには在りました**。
- ⚠ **`■材料` の単価は3列**（`単価（ロット）／単価（ロット1）みなと／単価（ロット1）たちばな`）。
  §3-5 の「可変列名」がそのまま現れており、**汎用索引はそのまま受けました**。
- ⚠ **`■見積もり` は `工程／数／単位／備考` の縦持ち**（`ロット 2 個`・`板金 1330 円`）。
  §2 の「工程表497件」はこれです。**見出し行はあります**が、w-cms の `我々の見積もり`
  （売値）とは**別物**——中身は**原価の内訳**です。
- ⚠ **`■材料` が空のページがあります**（3枚中2枚）。⚠ **移植しても材料発注書は組めません**
  ——これは移行の問題ではなく**運用の問題**で、人が埋めるところから始まります。
- **語彙に無い見出しが5つ**（`■不具合`・`■参考図`・`■図面`・`■データ`・`■完成品`）。
  中身は画像と添付なので、**受け皿を決めないと移せません**。

### 移植の道具立て（実測で通った手順・2026-09-21）

⚠ **3ページぶん24ファイルを実際に入れて確かめました。** 次にやる人が同じ回り道を
しないよう、通った手順だけ残します。

| 中身 | 取り出し方 | ⚠ 罠 |
|---|---|---|
| 添付（PDF・`.rpcd`・`.dxf`） | `InsertedFile` の **`pathCache`** | ⚠ `pathSource` は元の置き場で、**もう無いことがあります** |
| 写真 | `GetBinaryPageContent(pageID, callbackID, …)` | ⚠ **`objectID` では取れません**（`0x8004200E`）——`<CallbackID callbackID="…">` を渡す |
| 印刷イメージ／写真の区別 | `<Image isPrintOut="true">` | — |
| **XPSの原本** | **`XPSFile` 要素**＋`CallbackID` | ⚠ **ベクタのまま**取れます |
| **XPS→PDF** | `mutool convert`（MuPDF 1.28.0・Windows版） | ⚠ 下記 |
| 本文の構造 | `Outline` 直下の `OE` **だけ**を歩く | ⚠ **入れ子へ降りるとセルを二度拾います** |

**w-cms へ入れる口は3つ**——⚠ **拡張子で振り分けます**:

	.pdf            → /api/upload-pdf   （欄名 pdf_file）
	画像            → /api/upload-image （欄名 image_file）
	それ以外        → /api/upload-file  （欄名 file）

⚠ **汎用の口は画像とPDFを受けません**（専用の口の中身検査・EXIF除去を迂回させない
ため）。⚠ **curl では送れません**——Windows の curl が和文のファイル名を壊すので、
**multipart を自分で組んで UTF-8 のまま**送ります（2026-09-18 の罠）。
⚠ **本文を直に書かないこと**——ファイルへ書くと索引が古いままになり、**画面は新しい
のに検索は古い**というずれ方をします。`/api/save` を通します。

#### ⚠ `mutool` について

- **入手先**は `github.com/ArtifexSoftware/mupdf-downloads`。⚠ **最新版に Windows の
  ビルドが無いことがあります**（2026-09-21 時点で 1.28.4 はソースのみ。**1.28.0 に在った**）。
  ⚠ `mupdf.com/downloads/...` は GitHub へリダイレクトします。
- ⚠ **AGPL です。** **w-cms には同梱しません**——**使い捨ての移植作業でだけ使う**ので、
  MIT の配布物には影響しません。**この線引きを崩さないこと。**
- ⚠ **変換で巨大になることがあります**。実測で **5.3MB の XPS が 483MB の PDF** に
  なりました（画像319枚の資料。1枚ものの図面では起きません）。
  **`mutool clean -gggg -z` で 5.3MB に戻ります**——⚠ **入れる前に大きさを見ること**。
- **品質**: 1枚ものの図面は**ベクタのまま**でした（直線10,472本・曲線4,129・画像0）。
  ⚠ 文字が0なのは**CADの印刷で文字がアウトライン化されている**ためで、変換の問題では
  ありません。

### ⚠ 印刷イメージは「束の1枚」です（2026-09-21・移植をやり直した理由）

**最初の移植で入れた図面PDFは、ほぼ全部が誤りでした。** 開くと**別の部品の図面**が
出ます。実物で確かめるまで気づきませんでした。

⚠ **原因は、`XPSFile` が1枚ではなく束だったこと**です。ワンノートへ「印刷」で
取り込んだ資料は、**PDF全体が1つの `XPSFile`** として入り、**ページごとに
`<Image isPrintOut="true">` が1つずつ**並びます。筆者は `Image` を見るたびに
**束ごと**PDFへ変換していました。

	000071 の「図面(印刷)1.pdf」 … 13ページ綴り・1枚目は中間台座（別部品）・4.7MB
	000072 の「図面(印刷)2.pdf」 … 000071 のものと **バイト単位で同一**（5.3MB）

**どの1枚かは `Image` の属性が言っています**（⚠ **`originalPageNumber` は0始まり**）:

	<one:Image xpsFileIndex="0" originalPageNumber="1" isPrintOut="true">
	  → xpsFileIndex 0 の束の **2枚目**

直した手順は「束を1度だけPDFへ変換し、**`mutool clean -gggg -z <束> <出力> <頁>`**
で1枚を切り出す」。**90KB・1ページ**になり、**正しい図面**（`A100-B01-0013`）が
出ました。

⚠ **同じ資料が複数のページへ印刷されています**。束を1枚ずつに割らないと、**加工製品
ページのどれを開いても同じ束**が出ます——`sha256` が一致して初めて気づきました。
**「入った・開けた」では足りません。中身が**その部品のものか**を見ること。**

### 見出しと文章の移植（2026-09-21・ユーザー決定）

ユーザー:「**中身のある見出しだけ移植します。**あとで見出しの書き換えをしてもらう
かもしれません」「（`■工程` の写真と文章は）**並びを保って本文に埋め込む**」。

- **`■見出し` → `<section><h2>見出し</h2>`**。⚠ **`<caption>` は付けません**
  ——形式の解決は ①属性 ②**節の機能見出し** ③caption の順なので②で足り、付けると

### 7.1a 図面——印刷イメージは XPS からベクターの PDF に、Gemini で表題欄を読む（2026-09-28）

利用者:「図面のPNGについてですが、これもGEMINIで解析して、添付されているPDFもGEMINIで解析して、図番や品名などが一致したら、
PDFの方を採用して、PNGは移植しないでください」「PNGの図面はワンノートではXPS形式で記録されています。これをベクターのまま
PDFに変換できませんか？」「すべて、Geminiで図番、装置名称、品名などを確認して入れます」。

- **印刷イメージの元は XPS の束**（`<one:XPSFile xpsFileIndex idDocument>`＋`CallbackID`・`GetBinaryPageContent` で取れる）。
  同じ束を多くのページが共有する（最初の21ページで束は11・うち1つは 5MB で10ページ以上が共有）——吸い出しは `XPS\` に
  **束ごと1回だけ**置く（名前は idDocument）。印刷イメージの `originalPageNumber`（0から）＋1 が束のページ（実物で照合した）。
- **mutool（MuPDF）で束の1ページだけを PDF に**——`mutool convert -o 一時.pdf 束.xps <ページ>` → `mutool clean -gggg -z`
  （450KB → 91KB・画像なし＝ベクター）。`PDF化\` に置いて使い回す。⚠ **mutool は AGPL なので同梱しない**
  （移植の作業でだけ使う・デスクトップの `w-cms\道具\mupdf\mutool.exe`）。JUST PDF 等の仮想プリンタは保存の画面が出るので
  一括には向かない。
- ⚠ **印刷イメージには図面でないものも混ざる**——スキャンした手書きの見積メモ（束の中は画像）。PDF にしても画像のままで、
  束によっては変換に数分・一時ファイル 60MB。だから**先に PNG で図面かを Gemini に読ませ、移す図面だけをベクターに**する。
- **Gemini は表題欄だけを読む**（製造の道具の頼み文・図面番号は書かれているまま）。答えは `Gemini\` にファイルの中身の要約で
  控え、**同じファイルで二度呼ばない**（製造は何度でもやり直すので）。
- **印刷イメージと添付の PDF が同じ図面（図面番号と図面名称が一致）なら、印刷イメージは移さない**（報告に出す）。
- **ページの図面番号・図面名称・装置名称は表題欄から**——■図面 の候補から、ワンノートの図面番号と同じもの → 題と同じ名前 →
  添付の PDF → 印刷イメージ の順で選ぶ。ワンノートと違えば報告（図面番号が違えば「聞きたいこと」）。装置名称は置き場の
  設定が優先（空なら表題欄から）。
- **同じ図面番号のページがあれば作らない**（利用者:「2枚目は作らず、報告に出す」）——この回に先に作ったものと、w-cms の
  索引（`data/cms.db` を読むだけ）。作らなかったページの中身の節は報告に並べる（人が移す）。
- **`-fresh`**: 前に作った「移行中」のページをごみ箱へ移して作り直す（添付には版が無く消せないので、やり直すと前に上げた
  PNG が使われずに残る——それを残さないため。⚠ ページ番号＝弊社品番が変わる）。
