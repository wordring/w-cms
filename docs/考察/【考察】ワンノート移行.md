## 2. 事実上のスキーマ（発見された定型）

紙の帳票が無いだけで、実質は帳票運用でした。
見つかった定型（決まった書き方）を、頻度順に並べます。

**① ■材料 の下の表（横持ち・1行目が鍵）——471件**（旧称「部材表」も仮の呼び名）

横持ちは、1行目に見出しが横に並ぶ表の形です。

```
材質 | 形状 | 寸法 | 個数 | 単価（ロット） | 単価（ロット1）甲田 | 単価（ロット1）乙川 | 備考
```

**列名がデータを運んでいる**のが要点です。
業者名（甲田・乙川）とロット数が列名に埋め込まれ、ページごとに変わります
（ロット1・5・6・7・15・20・40・100 の変種を確認しました）。

**② ■見積もり の下の表（縦持ち・第1列が鍵）——497件（変種計）**

縦持ちは、見出しにあたる言葉が第1列に縦に並ぶ表の形です。

> **この表を「工程表」と呼ぶのはやめました**（2026-08-30・利用者の指摘）。
>
> - 見出しは **■見積もり** であって、「工程表」ではありません。
> - **■工程 は別物**です（写真主体の作業手順で、表ではありません）。
> - 「工程表」は、第1列に工程名が並ぶために付けた仮の呼び名でした。業務の言葉と衝突します。

```
工程   | 数 | 単位 | 備考          ← 1行目
ロット |    | 個   |               ← 鍵は第1列にある
材料   |    | 円   |
ブランク・ドリル・ブレーキ・組み立て …
```

`工程|工数|備考`（102件）や、列側にロットを並べる `工程|ロット6|ロット7|ロット20|備考` の変種もあります。

**③ 発注明細表——22件**: `No.|部品番号|品名|サイズ|図面番号|数量|単位|単価|金額`。
w-cms の受注明細（`client-order-items`）とほぼ同型です。

**④ 図面番号はハイフン連結の複合キー**: `S130-Q222-97-04`・`T100-02-06（台座）`・
`KHT-NKH-0032-BARI` など。
**ワンノートがこれを検索できないことが w-cms の動機の1つ**です
（[【要求】運用.md](../【要求】運用.md) §6 の検索）。

**⑤ 手動のテンプレート運用が既にある**

- `01 資料/事務用` に、「**コピペ ノート 各製品用**」「**コピペ ノート まとめ用**」というコピー元ページが置かれています。
- 加工製品ページは、ここからコピーして作られています。
- w-cms のページテンプレート機能
  （[【考察】ページテンプレート.md](【考察】ページテンプレート.md)・実装済み）の、直接の先行事例です。
- **移行時はこの雛形がテンプレートページの種になります**。

「各製品用」の節構成は次のとおりです。これが、加工製品ページの事実上のスキーマです。

```
■不具合 ■参考図 ■図面 ■図面番号 ■データ（CADファイル）
■材料（部材表）  ■外注加工（表・後述）  ■購入品  ■支給品  ■塗装
■見積もり（工程表）  ■工程（写真主体の作業手順）  ■完成品
```

## 2.5 引き出したい3種と、現状の書かれ方

**各加工製品ページから引き出したいものは「購入部品・購入材料・外注依頼品」の3種**です
（2026-08-25 利用者の要件）。
実データでの現れ方は三者三様です。これが、移行と語彙設計の難易度をそのまま決めます。

| 引き出したいもの | 現状の書かれ方 | 構造化の度合い |
|---|---|---|
| **購入材料** | `■材料` の部材表（`材質\|形状\|寸法\|個数\|…`）。471件が**記入済み** | ◎ 表として揃っている。ただし仕入先が備考欄（「白石商店」）や列名（甲田・乙川）に散る |
| **購入部品** | `■購入品` の下の**見出し行の無い2列表**（`ウェルドナット…M8 \| 5個`）や箇条書き | △ 表はあるが**ヘッダが無い**。数量は「5個」と単位込みの文字列 |
| **外注依頼品** | `■外注加工` に専用表（`名称\|材質\|加工\|個数\|推奨業者\|備考`）が**設計されたが、確認した21件すべて空**。実データは日付入りの自由文（「2026-06-15　青葉電装　緑　ロット20　3500」）や、まとめページの「○○　外注発注　2026-01-XX（部品リスト）」 | ✗ 様式は現場に定着せず、自由文に散っている |

外注加工の表が埋まらなかった理由は、推測になります。

- **ワンノートでは表を埋めても何も起きない**（集計されない）ことが大きいはずです。
- これは、w-cms が変えられる点でもあります。
  埋めれば手配リストや発注書に載るなら、埋める動機が生まれます。
- 逆に言えば、**移行時に自由文から外注情報を機械抽出するのは無理筋**です。
  移行後の運用で埋めていく前提が現実的です。

## 3. スキーマ的な条件（w-cms 側に必要な受け皿・重い順）

w-cms の側に要る受け皿を、重い順に並べます。
このうち 2（OCRテキスト）は、2026-09-21 に要件ではないと分かりました（§4.5）。
4（添付の拡張子）は、2026-08-31 に解消しました。

1. **画像アップロードが移行の絶対前提**

   - 画像は 4,825枚・86%のページにあります。
   - 規模が判明したことで、[【要求】添付.md](../【要求】添付.md) の優先度の根拠になりました
     （**2026-08-26 実装済み**）。
   - 印刷イメージ1,120枚は、原本PDFが添付されていれば移行対象から外せます
     （XPSの裏ファイル972個も同様です）。

2. **OCRテキストの受け皿**

   - 移行で捨てると、図面画像の中の文字（図面番号など）が引けなくなります。
     **「検索を付けたワンノート」なのに検索が後退する**ことになります。
   - 画像に付随する検索可能テキストの置き場（索引に載る形）が要ります。
     索引は、検索や集計のために DB へ入れた写しのことです。
   - 形式は未決です（`figcaption` か、画像コンテナ内の本文テキストか）。
   - **鍵は「見える文字がすべて」との整合**です。
     隠しテキストにすると原則が破れる点に注意します。

3. **縦持ち表（第1列が鍵）の語彙**

   - 現行の表語彙は、**1行目を見出し行として読む**だけです
     （[vocab_index.go](../../internal/cms/vocab_index.go) `syncVocabTable`）。
   - そのため、2番目に多い定型（工程表497件）が索引に載りません。
   - 「鍵は第1列」型を語彙へ足すか、移行時に横持ちへ転置するかの決定が要ります。
   - 3値［数・単位・備考］を持つため、`dl`（名前：値）では潰れます。

4. **添付の許可拡張子**

   - 調査時点は **`.pdf` のみ**でした（[pdf_handler.go](../../internal/cms/pdf_handler.go)
     `allowedAttachmentExts`。いまも PDF の口だけが使います）。
   - 実データは `.dxf`(389)・`.rpcd`(251)・`.xlsx`(175)・`.zip`(54)・
     `.docx`(42)・`.dwg`・`.step`・`.x_t`・`.slddrw`・`.igs`・`.eml`・`.pub`・`.lbx`・`.mp4` の計15種です。
     **約950件のCADデータ等が当時の w-cms には入りませんでした**。
   - **2026-08-31 に解消**しました。
     汎用アップロード `POST /api/upload-file` が、設定 `attachment_extensions`（既定はこの15種）を受けます。
     置き場も `files/` サブフォルダへ分離しました
     （[【考察】添付ファイルの表示と操作.md](【考察】添付ファイルの表示と操作.md)）。
   - 拡張子を絞る設計意図は、サイドカー `<id>.meta.json` の上書き防止（＝権限昇格の遮断）でした。
     これは `files/` 分離で、構造的に不要になりました。
   - `.json` は設定に書けないままです（`settings.go` が拒否します）。

5. **可変列名は汎用索引でしか受からない**

   - `単価（ロット20）甲田` のような列名は、硬い列スキーマ（`price INTEGER`）では表現できません。
   - `vocab_index`（ページID・表のID・名前・値）なら、**そのまま入って、そのまま引けます**。
   - スキーマ設計し直しの「名前：値」汎用索引への一本化（D-1・2026-08-31 実装。硬いドメイン表は全廃）を、
     実データが裏付けた形です。
   - 業者名もロット数も**見えるところに書いてあります**。「見える文字がすべて」と同じ向きです。

6. **見出し行の無い表**

   - 購入部品の2列表（名前｜数量）には、ヘッダがありません。
   - 現行の表語彙は**1行目を見出し行として食べる**ので、そのまま入れると、1行目の部品が鍵に化けて消えます。
   - 移行時にヘッダを補うか、「見出し無し2列＝名前：値の並び」として受ける形式を決める必要があります。

### 追記: 文字数の実測（2026-09-01・表の折り返し制御のため）

| 対象 | 件数 | p50 | p95 | 最大 |
|---|---|---|---|---|
| ページ名（＝品名） | 770 | 8字 | 19字 | 32字 |
| ■図面番号 の下の値 | 260 | 12字 | 18字 | 46字（外れ値1件） |

（→ 2026-09-21 に、字数のしきい値をやめました。`ATOMIC_MAX` は、もうありません。
いまは、折り返してよい列を見出しで決めます。`assets/app.js` の `WRAP_COLUMNS` です。）

## 4. 楽観できる材料（「無い」と確認できたもの）

- **ページ間リンクの書き換え問題は実質存在しません**（`onenote:` リンク2件のみ）。
  外部リンクは `a[href]` でそのまま通ります。
- **自由配置の線形化はほぼ自明**です。
  1ページ1アウトライン（本文枠）が基本で、複数枠のページはごく少数です（位置でソートすれば足ります）。
  サブページも0です。
- **階層は `parent_id` ツリーでそのまま受かります**（最大7段）。
  セクショングループ／セクションは、本文の無い「分類ページ」になります。
  **葉だけがテンプレート**という判定
  （[【考察】ページテンプレート.md](【考察】ページテンプレート.md)）とも整合します。
- **手書きインク（3ページ）は画像化で足り、ワンノートのタグ機能（6個）は無視できる規模**です。
- **「テンプレート」という名前のページは存在しません。**
  テンプレート置き場の名前駆動判定と衝突しません。
- タイトルの重複（全ノート横断で208種。「まとめ」×73・「印刷イメージ」×33 など）は、問題になりません。
  w-cms がページを数字IDで識別するためです。

### ⚠ 印刷イメージと原本PDF（実測155ページ）

4セクション（組立補助装置・装置B・装置D・装置C）で数えた結果です。

```

  ├ 原本PDFもある 39ページ … ⚠ **変換不要**（原本を移せばよい）
  └ 原本PDFなし   25ページ … ⚠ 全体の16%
写真 690枚 ／ 添付 379件
```

> 利用者:「私は普段、**XPSをWindowsに印刷させてPDF**にしています」

XPS は、Windows の印刷用の文書の形式です。

**その手順を機械にやらせる必要はありません。**

- 原本PDFが無い25ページにも、**ワンノートが既に描いた印刷イメージ（PNG）が取り出せます**。
- それを**PDFに包むだけ**で済みます（`gopdf` は画像をPDFに置けます）。
- **XPSにも印刷にも触れません。**
- **画質は「ワンノートが保存した解像度」止まり**ですが、**いま画面で見ているものと同じ**です。
  原本が要るなら、そのときは人が元のファイルを探すことになります。

### 取り出し方（実測で通った手順）

- **添付**（PDF・`.rpcd`・`.dxf`）
  - `InsertedFile` の **`pathCache`** に実体があります。
  - ⚠ `pathSource` は**元の置き場**（デスクトップ等）で、**もう無いことがあります**。
- **画像**
  - `GetBinaryPageContent(pageID, callbackID, ...)` で取ります。
  - ⚠ **`objectID` では取れません**（`0x8004200E`）。
    `<Image><CallbackID callbackID="…">` の **callbackID** を渡します。
- **印刷イメージと写真の見分け**
  - `<Image isPrintOut="true">` で見分けます。
  - **これがあるので、XPS由来と現物写真を機械的に分けられます**。

### ⚠ 筆者の変換器の誤り（記録）

最初の移植で、**表の中身が `<p>` の羅列**になりました。利用者から、次の指摘がありました。

> 利用者:「**見出しもただのテキストに
> なっていて、構造が崩れています**」

**原因は、ワンノートの `OE`（アウトライン要素）が入れ子であること**です。

- 表のセルの中にも `OE` があります。
- **表として拾ったあと、セルをもう一度テキストとして拾って**いました。
  だから、同じ中身が表の外に二度並びます。
- **`Outline` の直下の `OE` だけを歩く**のが正解です。

**そして、この誤りは、報告そのものを誤らせました。**

- `■材料` の表を先にテキストとして食べてしまい、「**材料の表は空でした**」と報告しました
  （実際は取れていました）。
- **構造を壊す変換は、壊れたことを隠します。**

／ ■購入品 ／ ■支給品 ／ ■塗装 ／ ■見積もり ／ ■工程 ／ ■完成品

  - **w-cms の語彙のほうが、実物より列を落としていました。**
  - 2026-09-21 に「外注加工表に外注先の鍵が無い」と結論しましたが、**ワンノートには在りました**。

### 移植の道具立て（実測で通った手順・2026-09-21）

**3ページぶん24ファイルを実際に入れて確かめました。**
次にやる人が同じ回り道をしないよう、通った手順だけ残します。

| 中身 | 取り出し方 | ⚠ 罠 |
|---|---|---|
| 添付（PDF・`.rpcd`・`.dxf`） | `InsertedFile` の **`pathCache`** | ⚠ `pathSource` は元の置き場で、**もう無いことがあります** |
| 写真 | `GetBinaryPageContent(pageID, callbackID, …)` | ⚠ **`objectID` では取れません**（`0x8004200E`）——`<CallbackID callbackID="…">` を渡す |
| 印刷イメージ／写真の区別 | `<Image isPrintOut="true">` | — |
| **XPSの原本** | **`XPSFile` 要素**＋`CallbackID` | ⚠ **ベクタのまま**取れます |
| **XPS→PDF** | `mutool convert`（MuPDF 1.28.0・Windows版） | ⚠ 下記 |
| 本文の構造 | `Outline` 直下の `OE` **だけ**を歩く | ⚠ **入れ子へ降りるとセルを二度拾います** |

**w-cms へ入れる口は3つ**です。**拡張子で振り分けます**。

```
.pdf            → /api/upload-pdf   （欄名 pdf_file）
画像            → /api/upload-image （欄名 image_file）
それ以外        → /api/upload-file  （欄名 file）
```

- ⚠ **汎用の口は画像とPDFを受けません。**
  専用の口の中身検査・EXIF除去を、迂回させないためです。
- ⚠ **curl では送れません。**
  Windows の curl が、和文のファイル名を壊します。
  **multipart を自分で組んで UTF-8 のまま**送ります（2026-09-18 の罠）。
- ⚠ **本文を直に書かないこと。**
  ファイルへ書くと、索引が古いままになります。**画面は新しいのに検索は古い**、というずれ方をします。
  `/api/save` を通します。

#### ⚠ `mutool` について

`mutool` は、MuPDF という PDF の道具に入っているコマンドです。

- **入手先**は `github.com/ArtifexSoftware/mupdf-downloads` です。
  - ⚠ **最新版に Windows のビルドが無いことがあります**
    （2026-09-21 時点で 1.28.4 はソースのみ。**1.28.0 に在った**）。
  - `mupdf.com/downloads/...` は GitHub へリダイレクトします。
- ⚠ **AGPL です。** **w-cms には同梱しません。**
  - AGPL は、配るときの条件が厳しい利用許諾（ライセンス）です。
  - **使い捨ての移植作業でだけ使う**ので、MIT の配布物には影響しません。
  - **この線引きを崩さないこと。**
- ⚠ **変換で巨大になることがあります**。
  - 実測で、**5.3MB の XPS が 483MB の PDF** になりました
    （画像319枚の資料。1枚ものの図面では起きません）。
  - **`mutool clean -gggg -z` で 5.3MB に戻ります**。
  - **入れる前に大きさを見ること**。
- **品質**: 1枚ものの図面は**ベクタのまま**でした（直線10,472本・曲線4,129・画像0）。
  文字が0なのは、**CADの印刷で文字がアウトライン化されている**ためです。変換の問題ではありません。

### ⚠ 印刷イメージは「束の1枚」です（2026-09-21・移植をやり直した理由）

**最初の移植で入れた図面PDFは、ほぼ全部が誤りでした。**
開くと**別の部品の図面**が出ます。実物で確かめるまで気づきませんでした。

**原因は、`XPSFile` が1枚ではなく束だったこと**です。

- ワンノートへ「印刷」で取り込んだ資料は、**PDF全体が1つの `XPSFile`** として入ります。
- **ページごとに `<Image isPrintOut="true">` が1つずつ**並びます。
- 筆者は、`Image` を見るたびに**束ごと**PDFへ変換していました。

```
000071 の「図面(印刷)1.pdf」 … 13ページ綴り・1枚目は中間台座（別部品）・4.7MB
000072 の「図面(印刷)2.pdf」 … 000071 のものと **バイト単位で同一**（5.3MB）
```

**どの1枚かは `Image` の属性が言っています**（⚠ **`originalPageNumber` は0始まり**）:

```
<one:Image xpsFileIndex="0" originalPageNumber="1" isPrintOut="true">
  → xpsFileIndex 0 の束の **2枚目**
```

直した手順は「束を1度だけPDFへ変換し、**`mutool clean -gggg -z <束> <出力> <頁>`**
で1枚を切り出す」です。
**90KB・1ページ**になり、**正しい図面**（`A100-B01-0013`）が出ました。

⚠ **同じ資料が複数のページへ印刷されています**。

- 束を1枚ずつに割らないと、**加工製品ページのどれを開いても同じ束**が出ます。
  `sha256`（ファイルの指紋）が一致して、初めて気づきました。
- **「入った・開けた」では足りません。中身が**その部品のものか**を見ること。**

### 7.1 道具（2段に分ける）

道具は2段です。

**製造**は、そのフォルダから w-cms のページを作る段です。

| 段 | 道具 | 読む・書く |
|---|---|---|
| **吸い出し** | `tools/onenote/extract.ps1`（**32ビットの PowerShell**） | ワンノート → デスクトップの `w-cms\ワンノート\板金部\`。対象は同じ所の `対象.txt`（1行1セクション）。`目録.json` の最終更新時刻で**次からは差分だけ**（新しい・変わった・前回取れなかったページ） |

### 7.1a 図面——印刷イメージは XPS からベクターの PDF に、Gemini で表題欄を読む（2026-09-28）

> 利用者:「図面のPNGについてですが、これもGEMINIで解析して、添付されているPDFもGEMINIで解析して、図番や品名などが一致したら、
> PDFの方を採用して、PNGは移植しないでください」
>
> 利用者:「PNGの図面はワンノートではXPS形式で記録されています。これをベクターのまま
> PDFに変換できませんか？」
>
> 利用者:「すべて、Geminiで図番、装置名称、品名などを確認して入れます」

ベクターは、拡大しても線がぼやけない、図形のままのデータのことです。

- **印刷イメージの元は XPS の束**です
  （`<one:XPSFile xpsFileIndex idDocument>`＋`CallbackID`・`GetBinaryPageContent` で取れる）。
  - 同じ束を、多くのページが共有します
    （最初の21ページで束は11・うち1つは 5MB で10ページ以上が共有）。
  - 吸い出しは、`XPS\` に**束ごと1回だけ**置きます（名前は idDocument）。
  - 印刷イメージの `originalPageNumber`（0から）＋1 が、束のページです（実物で照合しました）。
- **mutool（MuPDF）で束の1ページだけを PDF に**します。
  - `mutool convert -o 一時.pdf 束.xps <ページ>` → `mutool clean -gggg -z`
    （450KB → 91KB・画像なし＝ベクター）。
  - `PDF化\` に置いて、使い回します。
  - ⚠ **mutool は AGPL なので、同梱しません。**
    移植の作業でだけ使います。置き場は、デスクトップの `w-cms\道具\mupdf\mutool.exe` です。
  - JUST PDF 等の仮想プリンタは、保存の画面が出るので、一括には向きません。
- ⚠ **印刷イメージには、図面でないものも混ざります。**
  - スキャンした手書きの見積メモです（束の中は画像）。
  - PDF にしても、画像のままです。束によっては、変換に数分かかり、一時ファイルが 60MB になります。
  - だから、**先に PNG で図面かを Gemini に読ませ、移す図面だけをベクターに**します。
- **Gemini は表題欄だけを読みます**（製造の道具の頼み文・図面番号は書かれているまま）。
  - 答えは、`Gemini\` にファイルの中身の要約で控えます。
  - **同じファイルで二度呼びません**（製造は何度でもやり直すので）。
- **印刷イメージと添付の PDF が同じ図面（図面番号と図面名称が一致）なら、印刷イメージは移しません**（報告に出します）。
- **ページの図面番号・図面名称・装置名称は表題欄から**採ります。
  - ■図面 の候補から、次の順で選びます。
    ワンノートの図面番号と同じもの → 題と同じ名前 → 添付の PDF → 印刷イメージ。
  - ワンノートと違えば、報告します（図面番号が違えば「聞きたいこと」）。
  - 装置名称は、置き場の設定が優先です（空なら表題欄から）。
- **同じ図面番号のページがあれば、作りません。**

  > 利用者:「2枚目は作らず、報告に出す」

  - 比べる相手は、この回に先に作ったものと、w-cms の索引（`data/cms.db` を読むだけ）です。
  - 作らなかったページの中身の節は、報告に並べます（人が移します）。
- **`-fresh`**: 前に作った「移行中」のページをごみ箱へ移して、作り直します。
  - 添付には版が無く、消せません。やり直すと、前に上げた PNG が使われずに残ります。
    それを残さないための引数です。
  - ⚠ **ページ番号＝弊社品番が変わります。**
