# 【考察】キャッシュ制御

w-cms が返す応答を、ブラウザや途中のサーバーにどう取っておかせるか（キャッシュ）を、全体として決め直す考察です。

キャッシュは、一度受け取った応答を取っておいて、次に使い回すことです。使い回し方は、応答に付ける `Cache-Control` という見出しで指示します。

## 1. きっかけ

> 2026-10-27 利用者:「ブラウザで見るとHTTP要求に対して200で応答しているようですが、キャッシュを使うことは無いのですか？」

> 2026-10-27 利用者（開発者ツールの大きさの欄に「(memory cache)」などと出る、という筆者の答えに）:「すべてサイズが出ています」

> 2026-10-27 利用者:「インターネット公開のサイトを作る時に困るので、キャッシュ制御を作り込みましょう」

## 2. いまの形

### 2.1 応答ごとの指示

| 応答 | いまの指示 | 意味 |
|---|---|---|
| ログインした人のページ（`/001351` など） | `no-store` | 取っておかない。毎回まるごと取り直す |
| 要認証の API（`/api/…`） | `no-store` | 同じ |
| 画面のファイル（`/assets/app.js`・CSS・拡張の JS） | `no-cache` | 取っておくが、使う前に毎回「変わったか」をたずねる。変わっていなければ 304（中身は送らない） |
| 添付・写真（住所に版の印 `?v=` があり、今の版と合う） | `private, max-age=31536000, immutable` | その人のブラウザだけが、1年たずねずに使う |
| 添付・写真（印が無い・古い） | `private, no-cache` | その人のブラウザが取っておき、毎回たずねる |
| 匿名に見せる公開ページ・`sitemap.xml`・`robots.txt` | `public, max-age=600`・`Vary: Cookie`・`ETag` | だれでも（途中のサーバーも）10分使ってよい |
| 知らせの流れ（SSE）・ページの更新の通知 | `no-cache` | 溜めない |

- 版の印は、添付を書いた時刻から作ります（`page.AttachmentVersion`）。上書きすると印が変わるので、古い写真を見せ続けることはありません。
- 要認証の `no-store` は、入口で一律に付けます（`internal/auth/middleware.go`）。共用のパソコンで前の人の画面が出ないようにするためです（【要求】運用 §6「キャッシュ」の絶対条件）。
- 途中のサーバー（VPS の Caddy）は、いまは何も貯めません。Caddy には、もとから貯める働きがありません。

### 2.2 測ったこと（2026-10-27・試験用・/001437・写真 10 枚ほど）

| 開き方 | 閲覧モード | 書ける形（パソコンの既定） |
|---|---|---|
| 初めて開く | 写真をまるごと受け取る | 写真をまるごと受け取り、**もう一度まるごと受け取る** |
| 開き直す・F5 | 手元から（送られた量 0） | 1枚ごとにたずねて 304（約 300 バイトずつ） |

## 3. 困ること

### 3.1 書ける形では、写真の印が外れる

パソコンはページを書ける形で開きます。書ける形に入ると、画面は本文を「書くための本文」（素の `/api/load`）で描き直します。この本文の写真には印が付いていません。

- 印の付いた住所と印の無い住所は、ブラウザには別のものです。だから、初めて開いたときに同じ写真を2回受け取ります。
- 印の無い住所は「毎回たずねる」なので、開くたびに写真の数だけ問い合わせが行きます。利用者が開発者ツールで見た「すべてサイズが出ています」は、これです。

書くための本文に印を付けないのは、付けた住所が本文として保存されてしまうからです（`internal/cms/attachment_cache.go` の冒頭）。

### 3.2 画面のファイルを、ページを開くたびにたずねる

ページを開くたびに、画面のファイル（app.js・app.css・boot.js・session.js・push.js・拡張の JS と CSS で十数本）を、1本ずつ「変わったか」とたずねます。

- 変わっていなければ 304 なので、送る量は少ないです。
- ただ、社外から VPS を通して開くと、往復の回数ぶん遅れます。公開サイトでは、訪問者のだれもがこの往復をします。

### 3.3 公開サイトの写真を、途中で貯められない

添付はいつも `private` です。公開ページの写真も、訪問者のブラウザにしか残りません。

- 公開サイトに人が多く来ると、写真は毎回、業務サーバー（か公開用の w-cms）から送ることになります。
- 途中のサーバー（VPS・CDN）に貯めさせるには、公開ページの添付を `public` で配る必要があります。

### 3.4 戻るボタンで、ページを取り直す

ログインした人のページは `no-store` です。ブラウザは `no-store` のページを、戻る・進むの写し（bfcache）に入れません。戻るボタンを押すと、ページを取り直して描き直します。

- 【要求】運用 §6 の「認証済みの応答は no-store」は絶対条件なので、ここは変えない前提で書いています。

## 4. 案

### 案A 書ける形でも写真に印を付ける（§3.1）

- 書くための本文（素の `/api/load` と `/api/sync` の書き出し）でも、写真の住所に印を添えます。
- 保存するときに、サーバーが印を外します。外すのは、自分のサイトの添付の住所に付いた `?v=<印>` だけです。
- 画面のコードも、保存の形にするときに印を外します（サーバーと両方で外す）。
- ⚠ `/api/sync` は、ブロックの中身を比べて「同じブロックを2人が書いた」を見分けます。比べる前に印を外さないと、写真のあるブロックが「変わった」に見えます。比べる所を全部、印を外してから比べる形にします。

### 案B 画面のファイルに版の印を付ける（§3.2）

- サーバーが起動するとき（とファイルが変わったとき）に、画面のファイルごとに中身の指紋を取ります。
- 殻（`assets/index.html`・`public.html`）が読むファイルの住所に、`?v=<指紋>` を添えます。拡張の JS と CSS も同じです。
- 印が今の指紋と合う住所は、`max-age=31536000, immutable` で配ります。合わない・無い住所は、いまと同じ `no-cache` です。
- 入れ替えたあとは、殻が新しい印の住所を指すので、すぐ新しいファイルが届きます。開いたままのタブは古いファイルのままです。読み直せば新しくなります（いまと同じ）。
- 画面のファイルは、だれが読んでも同じ中身なので `public` にしてよいです（ログインの画面も読むため）。

### 案C 公開ページの添付を `public` で配る（§3.3）

- 実効公開のページ（自分と先祖が全部公開）の添付を、ログインしていない訪問者に配るときだけ `public` にします。
- 非公開に戻したとき、すでに貯められた写しは取り消せません（公開ページの HTML と同じ）。そこで、公開の添付は印があっても `max-age=600`（10分）にとどめる案を勧めます。ページの「公開⇄非公開が外から見えるまで10分」と同じ決まりになります。
- ログインした人には、いまと同じ `private` で配ります。

### 案D 公開サイトの前に、貯めるサーバーを置く（§3.3）

- 公開サイトに人が多く来るなら、VPS か CDN に貯めさせます。
- Caddy には、もとから貯める働きがありません。貯めるには、Caddy に別の部品（第三者のもの）を足すか、貯めるサーバーを別に立てるか、CDN を使います。
- 公開サイトをどこに置くか（業務サーバーとは別の w-cms を VPS に、という筆者の勧め）で、形が変わります。案C を入れてから決めれば足ります。

### 勧める順

1. 案A（いま困っている所・業務でも効く）
2. 案B（業務でも公開サイトでも効く）
3. 案C（公開サイトを作るとき）
4. 案D（公開サイトに人が多く来るとわかってから）

## 5. 問い

1. **作る順**は、§4 の勧める順でよいですか。
2. **公開ページの添付の残し方**: 非公開に戻したら10分で見えなくなる決まり（`max-age=600`）を、添付にも当てますか。当てない場合は、印があれば1年残ります（非公開に戻しても、見た人の手元と途中のサーバーに残る）。筆者の勧めは「当てる」です。
3. **公開サイトの置き場**: 別の話で勧めた「VPS に公開用の w-cms を別に立てる」で進めますか。案D の形が、これで決まります。
