# 【考察】テキストの正規化

> 状態: **決定・実装済み（案2・2026-09-04）**。本書は「同じものを同じと認めるために、値をどこまで
> 畳むか」の設計と決定ログです。実装は [normalize_text.go](../../internal/cms/normalize_text.go)、
> 列型 `code` の宣言は [vocab.go](../../internal/cms/vocab.go)。
> 関連の正本は [アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) §9（D-3・D-7）、
> [【一覧】語彙.md](../参照/【一覧】語彙.md)、実装は [vocab.go](../../internal/cms/vocab.go) の `NormalizeValue`。

図面番号や社名のような値は、人が打つたびに書き方が揺れます。
この文書は、揺れた値を「同じもの」と見分けるために、**値をどこまでそろえるか**を決めた記録です。

> **この文書の読み方**
>
> - **決まったこと**: 案2です。新しい型 `code` を足し、その型の値だけを強くそろえます。
>   2026-09-04 に決めて、実装も済んでいます（§8・§9・末尾の決定ログ）。
> - **あとから足した例外**: 機械が本文へ書き起こす名前は、書く時点でそろえます（§3a・2026-09-06）。
> - **まだ決まっていないこと**: §10 の3つです。
> - §1〜§7 は、決める前に考えたことの記録です。考えた順に並んでいます。
> - 表と決定ログに出てくる「ユーザー」は、利用者のことです。

**この文書でよく使う言葉**

| 言葉 | 意味 |
|---|---|
| 正規化（畳む） | 表記の揺れをそろえることです。全角の `Ｋ` と半角の `K` を1つにまとめる、のように使います |
| 生（なま） | 人が書いたままの、そろえる前の値です |
| 索引 | 本文に書いたタグと表を、検索と集計のために写した DB の表です。本文が正本で、索引は本文から作り直せます |
| 型（列型） | 値の種類です。文字（`text`）・数（`number`）・日付（`date`）などがあり、型ごとにそろえ方が決まります |
| NFKC・NFC | Unicode（文字の国際規格）が定めた正規化の方式です。NFKC は全角の英数字を半角に、半角のカナを全角にそろえます。NFC は、濁点の合成のように、同じ字の表し方だけをそろえます |
| コア・拡張 | コアは土台の w-cms です。拡張は、業務ごとに足すプログラムです |
| DB再構築 | 本文から索引を作り直す操作です |

## 1. なぜ要るのか

**w-cms を作る動機そのものです。**

> 利用者:「ワンノートが**ハイフンで区切られた図面名称をうまく検索できない**」

人が打つ値は、必ず揺れます。実データで実際にぶつかったものだけでも、次のとおりです。

| 揺れ | 実例 |
|---|---|
| 空白が混ざる | `P103-227-6_ 台座Assy`（`_` の後ろに空白） |
| アンダースコアがハイフンの位置に来る | `TQ060_284-ソレノイド補助具` |
| 全角と半角 | `Ｋ１２０-Ｗ０１` と `K120-W01` |
| 英字の大小 | `M305-822-07B` と `m305-822-07b` |
| ハイフンの種類 | `-`（半角）・`－`（全角）・`‐`・`−`・`—`・`ー`（長音） |

- **畳まないと、同じ部品の図面が別物として並びます。**
- 逆に畳み過ぎると、**別の部品が1つになります**。

害が大きいのは、後者（畳み過ぎ）のほうです。気づけないためです。

## 2. いま在るもの——正規化が3つ、別々の場所に

この節は、案を決める前に調べた姿です。決めたあとの形は §9 にあります。

調べた時点で、正規化をする所は3つあり、別々の場所に置かれていました。

| どこ | 何を畳む | 対象 |
|---|---|---|
| `cms.NormalizeValue`（コア） | number（通貨記号・桁区切り・単位）／date（`2026/9/4`→`2026-09-04`） | **text は素通し** |
| `toho.normalizeDrawingNo`（拡張） | 空白・`_`→`-`・ハイフン類→`-`・全角→半角・小→大 | PDFとDXFの突き合わせのときだけ（**索引には入らない**） |
| `cms.parseRefValue`（コア） | 参照タグ `ページID-ブロックID` の**構文解析**（ハイフンの種類を吸収） | 参照タグだけ（D-7 決着済み） |

表の言葉を少し説明します。

- 「素通し」は、何も畳まずに、そのまま通すことです。
- 「参照タグ」は、ほかのページやブロックを指すタグです。値は `ページID-ブロックID` の形です。
- 「構文解析」は、値を決まった形として読み解くことです。
- 「D-7」は、アーキテクチャとDBスキーマ §9 にある決定の番号です。

**つまり「図面番号を畳む知恵」は既に在るのに、索引には届いていませんでした。**
`normalizeDrawingNo` は、突き合わせの一瞬だけ使われて、捨てられていました。

## 3. 動かせない前提（既に決まっていること）

- **生が正本です。**
  索引の `value` 列には、**見た目のまま**の値を入れます。
  畳んだ値は、`norm_value` 列に**併記**します
  （[アーキテクチャとDBスキーマ.md](../旧文書/アーキテクチャとDBスキーマ.md) §9.1）。
- **表示は畳みません。**

  > 利用者:「利用者が、『名前：値』のタグは見た目のままにDBに入れられると信じるためには、実際にそうである必要があります」

- **畳むのは、比較のときだけです。**
  **ただし、機械が本文へ書き起こす名前は例外です**（2026-09-06 に追加）。下の §3a に書きます。
- **先頭のゼロは畳めません**（`000002` はページIDのゼロ埋め6桁）。

### 3a. 例外——機械が書き起こす「名前」は、書く時点で NFKC にする（2026-09-06）

「機械が書き起こす」は、人ではなく、プログラムが本文へ値を書くことです。

- 対象は、**顧客名・装置名称・図面名称・図面番号・発注書番号**の5つです（`cms.NormalizeNameForIngest`）。
- 畳むのは、**Unicode の NFKC と空白の詰めだけ**です。
  長音とハイフンには触りません（`NormalizeCode` は使いません）。

**なぜ「比較のときだけ」から外すのか。** 理由は2つあります。

1. **この5つは、そのままページの題になります。そして、題の完全一致が、階層の同一性を決めます**
   （`取引先／社名／段／装置名称／図面名称`）。
   実データは `φ３２０　共通台座` の形で届きました。
   畳まないと、`φ320 共通台座` とは**別の装置ページ**になりました。
2. **揺れは、コピペで増殖します。**

   > 2026-09-06 利用者:「表記の揺れは恐ろしく多く、コピペによって増殖することも多いので、早めに潰した方が良いと思います」

   索引で畳んでも、**人が次にどこへ写すか**は止められません。
   画面に出ている文字が、そのままメール・検索窓・別のページへ運ばれます。

**標準の作法からは外れています。**

- W3C の Character Model（ウェブでの文字の扱いを定めた文書）は、
  「内容は NFC で持ち、NFKC は比較の鍵にする」としています。
- NFKC の互換変換は、元に戻せません（不可逆）。全角だったか半角だったかは、復元できません。
- それでもこちらを採るのは、上の2番目の理由が実務で効くためです。
- **原本との突き合わせは、図面PDFがページに出るので担保されます**
  （加工製品ページのインライン表示・2026-09-06）。

**メールの件名・本文には掛けません。** 届いたままが正本です。
実データ100通のうち、28通の件名が NFKC でずれます。しかし、それは変えるべきものではありません。

正規化を変えたら、**DB再構築**で効きます（再起動は不要です）。
`config/settings.json` の語→型辞書と同じ流儀です。

## 4. 最大の論点——**長音（`ー`）をハイフンにしてよいか**

ここが、この文書の核心です。**同じ関数で両方は扱えません。**

| 値 | `ー`→`-` にすると | 正しいか |
|---|---|---|
| `P103ー227`（図面番号を全角で打った） | `P103-227` | **正しい**（同じ図面番号として引ける） |
| `ひかりレーザー`（会社名） | `ひかりレ-ザ-` | **壊れている** |
| `コンパクト標準２輪`（装置名称） | 影響なし | — |

いまコアの `toHalfWidth` は、**`ー` を無条件で `-` にします**。
この関数は number と date にしか掛からないので、実害は出ていません。
しかし、**これを text へそのまま広げると、日本語が壊れます**。

> **拡張の `normalizeDrawingNo` が `ー`→`-` を畳んでいるのは、対象が図面番号だと分かっているから**です。
> 「どの値なら畳んでよいか」を**型で言い分ける**のが、この問題の本筋だと考えます。

## 5. 何をどこまで畳むか（候補の一覧）

| # | 畳む対象 | 例 | 一般のテキスト | 図面番号・発注書番号 |
|---|---|---|---|---|
| 1 | 前後の空白 | `" A-1 "` → `A-1` | **畳む** | **畳む** |
| 2 | 中間の空白（半角・全角） | `P103-227_ 台座` → `P103-227-台座` | 畳まない | **畳む** |
| 3 | 全角英数 → 半角 | `Ｋ１２０` → `K120` | **畳む** | **畳む** |
| 4 | 英字の大小 | `03a` → `03A` | 畳まない | **畳む** |
| 5 | ハイフン類 → `-` | `－ ‐ − —` | 畳まない | **畳む** |
| 6 | 長音 `ー` → `-` | `P103ー227` | **畳まない**（日本語が壊れる） | **畳む** |
| 7 | `_` → `-` | `TQ060_284` | 畳まない | **畳む** |
| 8 | 区切りの有無 | `R520-M070` と `R520M070` | 畳まない | **畳まない**（別部品を1つにする害） |
| 9 | 半角カナ → 全角 | `ﾊﾟｲﾌﾟ` → `パイプ` | **要判断** | **要判断** |
| 10 | 濁点の分離（NFC） | `ハ`+`゙` → `バ` | **畳む**（同じ字） | **畳む** |

**列3と列4が違うことが、この表の言いたいことのすべてです。**
（`#` の列を除いて数えた3つ目と4つ目、つまり「一般のテキスト」と「図面番号・発注書番号」の列です。）

**Unicode の NFKC を使えば済むのでは？**

答えは「半分だけ」です。

- NFKC は、表の 3・9・10 をまとめて畳んでくれます。
- しかし、**`ー` は触りません**（表の 4〜7 は残ります）。
- 逆に、`㈱`→`(株)`・`①`→`1` のような**行き過ぎた変換**も、一緒に行います。

NFKC を行う Go のライブラリ `golang.org/x/text/unicode/norm` は、**既に承認済みの依存の一部**です。
`go.mod` に直接依存として在るので、追加は要りません。
ただ、**畳む範囲を説明できることのほうが大事**です。

**NFKC を土台に使い、`ー` と大小の扱いだけ自前で足す**のが、現実的な折衷になります。

## 6. 案

3つの案を比べました。○ は良い点、✕ は悪い点です。採ったのは案2です（§8）。

### 案1: text を一律に軽く畳む（1・3・10 だけ）

畳むのは、前後の空白・全角英数・濁点の合成だけです。**日本語が壊れない範囲**にとどめます。

- ○ コアの1関数で済みます。既存の呼び出し（`insertVocabEntry`）に何も足しません。
- ✕ **図面番号の揺れ（4〜7）が残ります。** 動機そのものが解決しません。

### 案2: 新しい列型 `code` を足し、そこだけ強く畳む（**推奨**）

語彙レジストリに、`code` 型を1つ足します。
語彙レジストリは、表やタグの種類と、その列の型を登録しておく登録簿です。

- `text` は、案1の軽い正規化です。
- `code` は、1〜7 を全部畳みます。

```
図面番号 / 発注書番号 / 品番 / 部品番号 …… code（強く畳む）
図面名称 / 装置名称 / 客先 / 備考       …… text（軽く畳む）
```

どの語が `code` かは、**`config/settings.json` の `vocabulary` に書きます**
（2026-09-14 までは `type_inference` という名前でした）。
ここには、既に「語→型」の辞書が在ります。運用者が編集できて、DB再構築で効きます。
**新しい仕組みを1つも増やしません。**

- ○ 「どの値なら畳んでよいか」を**型で言い分けます**。長音の罠を、構造的に避けられます。
- ○ 拡張の `normalizeDrawingNo` の知恵をコアへ引き上げて、**索引に届きます**（`norm_value` に入ります）。
- ○ 運用者が語を足せます（運用者が複数いる、という前提と合います）。
- ✕ 列型が1つ増えます（エディタの列設定・`validColumnTypes`・`/api/tag-schema` に波及します）。
- ✕ **既存データは DB再構築が要ります**（無害ですが、知らないと「効かない」と見えます）。

### 案3: 索引は畳まず、検索するときだけ畳む

- ○ 索引が単純なままです。
- ✕ **毎回の全走査**になります（`norm_value` の索引が効きません）。
  全走査は、行を1つ残らず読んで探すことです。
  いまの規模なら動きますが、ワンノートの766ページが入ると効かなくなります。

## 7. 引く側をどうするか（案2を採ったとして）

「引く」は、索引から値を探すことです。「逆引き」は、タグの値から、それを持つページを探すことです。

| 用途 | 引く列 | 理由 |
|---|---|---|
| 参照タグの解決（`受信元` 等） | 現状のまま**構文解析** | D-7 決着済み。触らない |
| ページの逆引き（`PagesByTag`） | `value`（生）→ 見つからなければ `norm_value` | **打った通りに引けたら、それが正しい**。畳んだ一致は次善 |
| サイト内検索（未実装） | `norm_value` | 人は揺れた形で打つ。**畳んだ側で引くのが本筋** |
| PDF↔DXF の突き合わせ | `norm_value` | 拡張の自前実装を捨てて、索引に寄せられる |

> **`PagesByTag` を「生 → 畳んだ値」の2段にすると、静かに別のページを引き当てる危険が
> 出ます**（`R520-M070` と `R520_M070` が別部品だったとき）。
> **2段にせず、呼ぶ側がどちらで引くか選ぶ**ほうが、安全かもしれません。ここは未決です（§9）。

上の囲みは、この節を書いた時点の考えです。
この問いは、そのあと §8 で「2段にしない」と決まりました。

## 8. 決定（2026-09-04）

| 問い | 決定 | 誰が |
|---|---|---|
| 案1／案2／案3 | **案2**（列型 `code` を足し、そこだけ強く畳む） | ユーザー |
| `code` にする語 | **いまは決めない**。「いずれ出てくると思いますが、**運用前のいまはわかりません**」。既定は `図面番号`・`発注書番号` の2語だけ——出てきたら `config/settings.json` へ足してDB再構築 | ユーザー |
| 半角カナ（表の9） | **畳む**（`ﾊﾟｲﾌﾟ`＝`パイプ`）。NFKC が text / code の両方で行う | ユーザー |
| `PagesByTag` を2段にするか | **2段にしない**。生の完全一致は `PagesByTag` のまま据え置き、畳んだ一致は **`PagesByTagLoose` という別の関数**にした | 実装判断 |

**`PagesByTagLoose` を分けた理由**

2段にする、というのは、まず生で引いて、駄目なら畳んで引く形です。
そうすると、**打った通りに在るのに別のページも一緒に返る**ことが起きます
（`R520-M070` と `R520_M070` が別の部品だったとき）。

**探す**（多めに出して人が選ぶ）のと、**突き合わせる**（1つに決める）のは、別の仕事です。
だから、どちらで引くかは、呼ぶ側が選びます。

## 10. 未決（着手時に確かめる）

まだ決まっていないことは、次の3つです。

- **区切りの有無（表の8）を、将来も畳まないでよいか。**
  「畳み過ぎて別の部品を1つにするほうが、取りこぼしより害が大きい」という拡張側の判断を、
  コアでも踏襲する前提で書いています。
- **`norm_value` は、既に number と date で使われている列です。そこへ text の畳んだ値を入れてよいか。**
  **型が違う値が、同じ列に入ります。**
  いまも `value` は全部の型で共用なので、筋は通ります。
  ただ、`norm_num` のように分けるべきかは、確かめが要ります。
- **エディタ側の見え方。**
  `code` 型の列に、何か表示上の合図が要るか（薄青の見出し語と同じ系統）。
