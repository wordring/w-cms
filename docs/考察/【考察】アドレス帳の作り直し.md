**先に、言葉の説明**

| 言葉 | 意味 |
|---|---|
| アドレス帳 | 取引の相手（会社・個人）と、その連絡先を持つ仕組みです |
| タグ | ページに書く「名前：値」の組です（例: `メールアドレス`）。保存すると DB の索引に入り、検索に使えます |
| 索引 | 検索や集計のために、本文のタグや表から作る DB の表です |
| 解析 | AI が PDF を読んで、値を取り出すことです |
| 整理 | 解析でできたページを、製造の下の置き場へ片付ける操作です。片付け先の会社のページが無ければ、このとき作ります |
| 照合 | メールの差出人のアドレスから、相手のページを探すことです |
| 作業面 | 人が片付けるものを並べて見せる一覧です（未登録の連絡先の一覧 など） |
| 計算ビュー | 索引から値を読んで、その場で組み立てて見せる表示です |
| コアと拡張 | コアは w-cms の土台（`internal/`）、拡張は用途ごとに足す部分（`ext/`）です |
| CTI | 電話の着信を、コンピュータへ知らせる仕組みです |

## 0. 言葉の決め（2026-09-15 ユーザー決定）

この文書でいちばん使う2語を、先に分けておきます。

| 語 | 指すもの | 実体 |
|---|---|---|
| **連絡先** | **相手を言い当てる手掛かり**。同じ相手に何個でも付き、増えるし移る | いまは `メールアドレス` タグ（`EmailTag`）。`電話番号`（CTI）・FAX番号が同じ口に並ぶ前提 |
| **相手** / **取引先ページ** | **相手そのもの**（同一性の持ち主）。1社1枚 | ページ。同一性を担うのは常にページID |

「同一性」は、「どの相手か」が1つに決まることです。

**この表のその後**: 2026-09-16 に、木を2つに分けました。
連絡先を持つのは、`連絡帳／組織／人` のページです。`製造／社名` のページは、`連絡帳` のタグで、その組織を指します。
組織の連絡先として、`ドメイン` のタグも加わりました（`DomainTag`）。

**もとは、連絡先のほうを「識別子」と呼んでいました。**

> 2026-09-12 利用者:「識別子とは何でしょう？」

こう問われて、**コードのどこにも無い概念語**だったことが分かりました（文書と説明の中だけで使っていました）。
利用者の決定で、「連絡先」に改めています。

日本語の「連絡先」は、第一義が「連絡する先＝アドレス・電話番号」です。
だから、この割り当ては自然です。
`contacts.go` は、既にその意味で使っていました（「連絡先そのもの（メールアドレス・電話番号）は」）。

**実体のほうを「連絡先」と呼ばないこと。**
「連絡先の無い連絡先」という、書けない文になります。相手・取引先ページと呼びます。

## 1. 何が起きたか（実データ）

2026-09-10、整理を実データで通したときに、**顧客名の推奨値が空振り**しました。

- 解析が読んだ生の値が、そのまま出ました（誤記入りの「株式会社南北ス**ス**ポーツマシーン」）。
- 既にある取引先ページの題には、解決されませんでした。

原因は単純です。**取引先ページ `010264` にタグが1つもありませんでした。**

- そのページは**整理が作った**もので、アドレス帳を通っていません。
- 照合（`PartnerTitleForAddress`）は `メールアドレス` タグを引くので、空振りします。

100通を取り込んだあとの状態を測ると、もっとはっきりします。

| | 数 |
|---|---|
| 索引に出てくるメールドメイン | **11** |
| 取引先ページ | **1**（南北スポーツ機械） |
| そのページが連絡先を持った経緯 | 2026-09-10 に**人が手で足した**（アドレス帳の「既にある相手へ足す」） |

`example-works.co.jp`（自社・**104回**）も `example-kanagata.co.jp`（こだま金型製作所・3回）も、
ページになっていません。
**アドレス帳は、実質からっぽのまま動いていました。**

## 2. なぜそうなったか

**取引先ページを作る道が2本あります。**

| 作る道 | 何を書くか | 結果 |
|---|---|---|
| アドレス帳の登録（`RegisterContactAPIHandler`） | 題＋`メールアドレス`＋`取引` | **照合できる** |
| 整理（`filing.go` の `ensureChildPage`） | 題だけ | **照合できない** |

2本目は、「会社のフォルダを作る」つもりの操作です。
ところが w-cms では、**会社のフォルダと連絡先は同じ1枚**です
（2026-09-05 の決定「相手のページは1枚・箱も1枚」）。
だから、**フォルダを作ると、連絡先の無い相手ページが黙って生まれます**。

見た目は同じページです。
違いは「タグが在るか」だけで、**無いことは誰にも知らされません**。
次のメールが来たときに、静かに空振りするだけです。

さらに、アドレス帳の作業面（未登録の連絡先の一覧）は、**出てくるだけで、放っておけます**。
誰にも催促されないので、11ドメイン中10が未登録のまま、100通が過ぎました。

## 2b. もっと単純な原因もありました——**作業面が存在していなかった**

§2 を書いたあとに `取引先` ページの本文を見たら、こうでした:

```html
<h1>取引先</h1><p><br/></p>
```

**未登録の連絡先の一覧が、どこにも載っていません。**

- この一覧は、計算ビュー（`unknown-contacts`）です。
  計算ビューは、**本文にブロックを置いて初めて描かれます**。
- 通信箱には `<section data-type="unhandled-intake">` が入っていますが、それは**人が置いた**ものです。
- 取引先ページは、`EnsurePartnerBox` が**機械で作る**ものです。見出しだけを書いていました。

`EnsurePartnerBox` は、当時の名前です。
2026-09-16 の木の分割で、取引先の箱は `toho.EnsureCustomerBox`、連絡帳は `contacts.EnsureContactsBox` に分かれました。

つまり、**100通のあいだ、誰も一覧を見たことがなかった**のです。
「催促されないから登録されない」どころか、**催促する画面が無かった**わけです。
実際にブロックを置いたら、その場で**9件**が並びました。

ここから引ける規律が1つあります:

> **機械が作るページは、行き止まりにしない。**
> 人が意図して置くページ（通信箱）と、機械が都合で作るページ（取引先）では、
> **中身を用意する責任の所在が違う**。

**これは作り直しを待たずに直せる**ので、2026-09-11 に直しました（`partnerBoxBody`）。

- 既にある職場のページにも、作業面を入れました。
- 自社（`example-works.co.jp`・4アドレス）も登録して、未登録の一覧から外しました。

`partnerBoxBody` の、その後の移り変わりです。

- のちに `customerBoxBody`（[customer_box.go](../../ext/toho/customer_box.go)）になりました。
  載る作業面は「連絡帳と未接続の相手」です。
- 2026-09-27 に、コードから消えました。いまは、**テンプレート／東邦／製造**が本文を持ちます（2026-10-16 までの名前は「取引先」）。

## 3. なぜ他所のシステムではアドレス帳が独立しているのか

利用者の見立ては当たっていると思います。
理由を分けると4つあり、**w-cms に効くのは後ろの2つ**です。

| 理由 | 内容 | w-cms に効くか |
|---|---|---|
| ① 保管の都合 | 連絡先は構造が決まっていて、専用の表が素直 | **効かない**。w-cms は `vocab_index` 1本と決めた（D-1）。タグで足りている |
| ② 画面の都合 | 一覧・検索・重複統合の専用UIが要る | 弱い。作業面は既にある |
| ③ **同一性の解決が「機能」だから** | 「この差出人は誰か」は、メール取り込み・整理・CTI・見積……**多くの機能が呼ぶ**。だから1か所に置く | **効く**。いまは `PartnerTitleForAddress` が1本あるだけで、**書く側が通らない** |
| ④ **連絡先が開いていて、変わるから** | 1社にアドレスが何個も、ドメインが2つ、電話番号、旧社名。増えるし移る | **効く**。だから「連絡先が付いているか」を**誰かが保証しないと壊れる** |

つまり、独立しているのは**保管**ではなく、**同一性を決める仕事**です。

w-cms は、保管の答えを先に出していました（ページ1枚・タグ）。
しかし、**仕事の側を作っていなかった**のです。

## 4. 作り直しの原則

**この節のその後**: 「取引先ページ1枚のまま」は、2026-09-16 に変わりました。

> 2026-09-16 利用者:「両方を別の木にする」

1つの箱が、部品の階層（下請けの業務）とアドレス帳（通信）の2つの役目を兼ねていたので、分けました。
いまは、`連絡帳／組織／人` と `製造／社名／…` の2つの木です。2つを、`連絡帳` のタグが結びます。
専用テーブルを作らないことは、いまも同じです。

**保管は変えません。**

- 取引先ページ1枚のままです。
- `vocab_index` のままで、専用テーブルは作りません。
- 利用者の「顧客であり、仕入れ先である場合もあります」も、加工製品の階層と同じページに置く決定も、
  どれも有効なままです。

変えるのは**入口**です。

> **取引先ページは、アドレス帳を通してしか生まれない。**
> **「この相手は誰か」を答えるのも、アドレス帳だけ。**

## 5. 具体案

### 5.1 作る口を1つにする

```go
// EnsurePartner は取引先ページを返し、無ければ作ります。**連絡先も一緒に受け取ります**。
func EnsurePartner(user *auth.User, name string, ids Identifiers) (string, error)
```

- 整理（`fileOneDrawing`）は、`ensureChildPage(boxID, customer)` をやめて、これを呼びます。
- 整理の時点で分かる連絡先も、一緒に渡します。
  **その加工製品ページの `受信元` から辿れる差出人アドレス**のことです。
  そうすれば、**作った瞬間から照合できる**ページになります。
- 連絡先が何も無いときは、**そのまま作ります**（FAXしか来ない客先は実在します）。
  ただし、「連絡先なし」は**見える**ようにします（§5.3）。

### 5.2 答える口を1つにする

```go
// ResolvePartner は連絡先から取引先ページを探します（見つからなければ ok=false）。
func ResolvePartner(user *auth.User, id Identifier) (pageID string, ok bool)
```

いまの `PartnerTitleForAddress` は、**題しか返しません**。
整理はページが欲しいので、題で引き直しています（完全一致の二度手間）。
そこで、**ページIDを返す**形に改めます。

優先順位は、現行のままです（**完全一致 → ドメイン**）。理由も変わりません。

- 自社の工場長だけ別プロバイダのアドレスを使っている、という実例があります。
- だから、ドメインは手掛かりであって、決定ではありません。

将来は、`電話番号`（CTI）・FAX番号が、同じ口に並びます。
**着信から相手を名指しする**のは、この関数の仕事です。
`PagesByTag` の逆引きをあちこちに書かないためにも、1本にします。

### 5.3 「連絡先の無い相手」を見えるようにする

いまの作業面は、「**まだページになっていないアドレス**」を並べます。

裏返しが抜けています。**ページになっているが、連絡先が無い相手**です。
これが、今回の事故そのものです。

取引先の作業面に1行足します:

```
⚠ 南北スポーツ機械 — メールで結びつきません（メールアドレスが未登録）
```

押すと、索引にあるアドレスから候補を出して、足せます。

これは、**「未登録の連絡先」と対になる**2つ目の作業です。
どちらも、「見つかっているものを並べ、決めるのは人」という同じ形です。

#### 出すのは「メールは来ているのに結びついていない相手」だけ（2026-09-15 ユーザー決定）

**全部を警告にすると狼少年になります。**

- FAXしか来ない客先・電話だけの客先は、**正当に連絡先ゼロ**です。それは異常ではありません。
- 実データでも、取引先ページの大半は、いつかそうなります。

絞り込みの条件は1つです:

> **その相手の題が、索引のどこかのメールアドレスから引ける形で現れているのに、
> その相手のページに `メールアドレス` タグが無い。**

言い換えると、「**メールは届いているのに、届いた先が結びついていない**」です。

2026-09-10 の事故が、まさにこの形でした。
`example-sports.co.jp` からメールが来ていて、`南北スポーツ機械` のページもありました。
それなのに、両者がつながっていませんでした。

**FAXだけの客先は静かなまま**です。メールが1通も来ていないので、条件に当たりません。

**つまり「直せるのに直っていないもの」だけが光ります。**
直しようのないものを並べても、人は一覧ごと信用しなくなります（未処理一覧で一度学んだことです）。

⚠ **判定の材料はメール由来のアドレスです。**

- 実装は、「索引にあるアドレスのドメインや表示名から、その相手の題に解決できるか」を見る形になります。
- このとき、**解決の規則は `PartnerTitleForAddress` と同じものを使うこと**。
- ここを別に持つと、「警告は出ているのに、押しても候補が出ない」が起きます。

### 5.4 自社を登録する

`example-works.co.jp` は**104回**出てくるのに、ページがありません。

登録して `取引：自社` を付けると、**未登録の一覧から自社の4アドレスが消え**、照合も自社を飛ばせます
（`isSelfPartner` は既にあります）。
**作り直しの前でもできる、いちばん効く1手**です。

その後のことです。
2026-09-18 に、`取引` タグの全廃とともに、`isSelfPartner` は削除されました。
いま、自社を見分ける手掛かりはありません
（[変更履歴.md](../変更履歴.md) の「`取引`（顧客・仕入先・自社）を全廃（2026-09-18）」と、`ext/comm/contacts/contacts.go` の `EmailTag` のコメント。
もとは「作業引き継ぎ 0a0」を指していましたが、その項目は、いまの作業引き継ぎにありません）。

## 5b. どこの持ち物か——**メールではなく業務側**

> 2026-09-11 利用者:「アドレス帳はメールプラグインの持ち物か業務プラグインの持ち物か
> 考えましょう」

**測った結果、メールではありません。** 好みではなく、構造の話です。

この節に出てくる `ext/mail`・`ext/sheetmetal`・`ext/contacts` は、当時の名前です
（いまの名前は、下の小見出し「ただし、いまはコアに在る」の注記にあります）。

### メールの持ち物ではない（4つの根拠）

1. **メールプラグインは使っていません。**
   - `ext/mail` から `contacts.go` への参照は、**ゼロ**です。
   - 使っているのは、`ext/sheetmetal/filing.go` の4箇所と、`main.go` のルート登録だけです。
2. **拡張どうしは import しません**（実測: `ext/` 間の import はゼロ）。
   import は、プログラムの部品が、別の部品を取り込んで呼ぶことです。
   アドレス帳が `ext/mail` に居ると、**業務側から呼べません**。
3. **`-tags nomail` で整理が壊れます。**
   `-tags nomail` は、メールの拡張を外して組むときの指定です。
   - `ext/sheetmetal` は `!minimal` なので、**nomail でも入ります**。
   - 加工製品の階層は `取引先／社名／段／装置名称／図面名称` で、**取引先の下に生えます**。
   - メールを外したら階層ごと消える、というのは筋が通りません。
4. **同一性は情報源より長生きします。**
   - FAXしか来ない客先・電話だけの客先には、メールアドレスがありません。
   - CTI が来れば、**電話番号から同じ相手**を引きます。
   - **メールは連絡先の供給元の1つ**であって、同一性の持ち主ではありません。
