> **検討中・未実装**（2026-09-20）。**決定は済んでいます**。
> この文書は着手前の設計メモです。実装したら `【考察】` を外し、確定した仕様は各設計書へ移します。
>
> 一言でいうと: **各社ばらばらの発注書を、弊社の1つの様式へ落とし込む。落とし込み方は
> 取引先ごとに覚える。同一性はページ番号で持つ。**
>
> **この文書を書いた同じ日に、土台が2つ入りました**（§3 の ③ と ②）。

**この文書の読み方**

顧客から届く発注書を、弊社の受注明細（受注ページに載せる、弊社の項目の表）へ写す方法を決めた記録です。

- **決まったこと**は §2（2.1〜2.12）にあります。日付ごとの一覧は §5 の決定ログです。
- **作るもの**は §3 の表です。残っているのは 6（様式ページ）と 7（整理のフォーム）です。
- **まだ決まっていないこと**は §6 にあります。
- 知らずに書くと壊れるものは、§4 にまとめてあります。

## 0. 何の話か

> 利用者:「弊社が必要なのは、**品番、品名、単価、数量、納期**などです。顧客の発注書から
> いかにココへ落とし込むかということになります」

発注書には、会社ごとに様式があります。列の名前も並びも違います（`員数`／`数量`、`納入日`／`納期`）。
それを弊社の1つの表へ写すのが本題です。

そして、**もっと難しい問題**がその下にあります。

> 2026-09-20 利用者:「顧客の発注には図面番号や品名が同じで別の品物の場合があります。これは**文脈から担当者が
> 糸をくみ取る**ので自動化は無理です。そこで**弊社の加工製品番号としてページ番号を使っては
> どうでしょうか？** 加工製品番号を頼りに製造を進めるのです。」

**後半は新しい話ではありません。** 2026-09-03 に同じ結論が出ています。

- 「別の製品の図面番号が一致してしまう場合もあり…**社内で識別番号を割り当てるしかありません**」
- →「同一性は常にページID、図面番号は探すためのタグ。w-cms は6桁を必ず振るので
  『社内で識別番号』は構造として既に満たされている」

**今回はそれを使う話**です。

## 2. 決めたこと

受注ページの形と、発注書の読み取り方について決めたことを、2.1〜2.12 に並べます。
どれも決定済みです。まだ作っていないのは、様式ページ（§2.7）と、整理のフォームの欄（§2.8・§2.2）です。
作ったものと残りの一覧は §3 にあります。

### 2.1 受注ページには表が2つ載る

> 利用者:「Geminiに単なるOCRをしてもらうとともに、**どの顧客項目が弊社項目に結びつくか
> 教えてもらう**のが良いのでは？すると、**顧客の表と弊社の表の二つを表示**して頂けると
> 比較しやすいです」

OCR は、紙や PDF の字を機械が読み取ることです。

```
受注 250715-304
  （タグ: 発注書番号 / 発注元 / 発注日 / 受信元）

  ▼ 顧客の発注書（PDF）                   ← <details>（原本そのもの・通常は畳む）
  ▼ 顧客の発注書（読んだまま）            ← <details> で畳める
  | 図面No. | 品名           | 員数 | 単価 | 納入日     | 備考       |
  |  K120-1 | ｳｹﾌﾞﾗｹｯﾄ  | 100  | 390  | 2026-10-15 | 材質変更   |

  ■ 受注明細（弊社の項目）
  | 加工製品番号 | 品番 | 品名 | 単価 | 数量 | 納期 | 備考 | 状態 |
```

**原本の写しを残す理由**は、目で確かめられることです。

- 項目の対応が合っているか。
- **OCR が7行全部読めたか・数字を取り違えていないか。**

対応表だけ見せる形では、後のほうが分かりません。

**整理したあとも残します**（利用者の決定）。長くなるので、`<details>` で畳めるようにします。
`<details>` は、押すと開く、畳める囲みです。

- `details`／`summary` は**サニタイズを通ります**
  （[htmldoc/sanitize.go:174](../../internal/cms/htmldoc/sanitize.go#L174)）。
  サニタイズは、本文から危ない HTML を取り除く処理です。
- **素のHTMLだけで畳めるので、JS も `on*=` も要りません。**
  CSP strict（インラインのスクリプトを禁じる、ブラウザの決まり）の下で動きます。
- **公開ページのゼロJS（JavaScript なしの表示）でも畳めます。**

### 2.2 弊社品番はページ番号

**名前は `弊社品番` になりました。**
この文書の初稿では `加工製品番号` と書いていました。現場で使う言葉に揃えます。

> 2026-09-20 利用者:「**加工中に番号を使うので**、受注の表に**弊社品番として製造製品のページIDを入れたい**です」

`弊社品番` の列を弊社の表に置き、**加工製品ページのページ番号**を入れます。
型は `ref` です（ほかのページを指す参照の型。`cms.ColRef`。既にあります）。

**`品番` とは別の列にします。**

| 列 | 誰の言葉か |
|---|---|
| `品番` | **顧客の言葉**。先方の発注書に書いてあるもの |
| `弊社品番` | **弊社の識別**。ページ番号。⚠ **加工中に使う番号** |

同じ列に混ぜると、顧客の品番で問い合わせが来たときに引けません。

**これは 0c（受注明細の見出しが `品番` に化ける件）への答えでもあります。**
`図面番号` が `品番` に置き換わるのが気持ち悪かったのは、
**顧客の言葉と弊社の識別が1つの列に混ざっていた**からでした。

**結ぶのは人です。**

> 利用者:「文脈から担当者が糸をくみ取るので自動化は無理」

機械の仕事は、**候補を狭めるところまで**です。

- `受信元`（どの通信記録から届いたかを指すタグ）が同じ通信記録ページを指す加工製品ページを並べます。
- 発注書と図面は同じメールで届くことが多いので、たいていその中にあります。
- **新しいデータは要りません**（`受信元` は全ページが既に持っています）。

### 2.3 列（`備考` を含む）

```
| 弊社品番 | 品番 | 品名 | 単価 | 数量 | 納期 | 備考 | 状態 |
|   ref    | code | text | number | number | date | text | enum |
```

**2026-09-20 に実装済み**（`c0cdb22`）です。

⚠ **見出しは宣言から組みます**（`headerRowHTML`。2026-09-21 に改訂履歴の見出しも同じ口へ通しました）。

- 列を足したのに本文の `<th>` が古いままだと、**宣言と本文が黙ってずれます**。
- 索引は、見出しの表示文字で引きます。そのため、**足した列がどこからも読めません**。
  索引は、検索や集計のために DB へ入れた写しのことです。

> 利用者:「表には**「備考」欄**が必要です」

**並びは既存4表に揃えました。**

- `構成部品`・`加工工程`・`購入部品`・`支給部品` は、
  どれも `{Field: "note", Label: "備考", Type: cms.ColText}` を持っています。
- **`備考` は `区分`（状態）の手前**にあります（[ext/toho/vocab.go](../../ext/toho/vocab.go)）。
- 受注明細だけが持っていませんでした。

**備考はたぶんこの設計の要です。**
§0 の「文脈から担当者が汲み取る」の中身は、多くの場合、備考欄に書いてあります。
たとえば「材質変更」「前回と同じ」「至急」「改訂あり」です。

```
| 加工製品番号 | 品名           | 備考         |
|  000047      | ｳｹﾌﾞﾗｹｯﾄ  | 材質SUS304へ |   ← これを読んで人が結ぶ
|  000063      | ｳｹﾌﾞﾗｹｯﾄ  | 従来品       |   ← 同じ品名・別の物
```

**加工製品番号を選ぶ画面では、備考を並べて見せること。** 見えていないと判断できません。

**顧客の備考と弊社の備考は別物です**（利用者の決定）。

- 先方が書いたもの（「材質変更」）と、こちらの申し送り（「在庫から手配」）は別です。
- **初期値として写し、人が直せる**ようにします。他の欄と同じ扱いです。

### 2.4 形式の宣言は、見える文字（`<caption>`）へ

> 利用者:「**見た儘が全ての原則**から言って、`data-type` より表の見出し（caption）で
> 検索できるのが筋では？」

言葉の説明です。

- 形式は、表の種類のことです（受注明細・材料 など）。
- `<caption>` は、HTML の「表の題」の要素です。画面に見えます。
- `data-type` は、HTML の属性です。画面には見えません。

いまの決め方はこうです（[walk.go:316](../../internal/cms/walk.go#L316)）。

```
① data-type 属性          （見えない）
② section の機能見出し    （見える・ただし節で包む必要がある）
```

この「いま」は、この決定の前の姿です。caption の枝は 2026-09-20 に入りました（§3 の 2）。

**`data-type` へ寄ったのは意図した判断ではなく、副作用でした。**

- 受注ページは、もともと②でした。
- 2026-09-18 に「1文書1ページ」で節をやめたとき、**見える印が消え、`data-type` が肩代わり**しました
  （変更履歴「節をやめたので表が自分で名乗ります」）。

`<caption>` はその穴をふさぎます。**節で包まずに、表自身が見える名前を持てる**からです。
HTML でも、`caption` は「表の名前」そのものの要素です。

**費用はほぼゼロ**です:

- **`<caption>` は既にサニタイズを通ります**（[htmldoc/sanitize.go:190](../../internal/cms/htmldoc/sanitize.go#L190)）
- **表示文字→形式を引く関数も既にあります**（`VocabDefByHeading`。②が使っているものです）

```go
if el.Data == "table" {
    if def, ok := VocabDefByHeading(tableCaption(el)); ok {
        return def.Type   //  <caption>受注明細</caption> → client-order-items
    }
}
```

**①が優先のままなので、既存の本文は1枚も壊れません。**
ただし、**2つの書き方が併存**します。そこで、こう決めます。

- **新しく書くものは caption。**
- **`data-type` は、古い本文のための互換。**

**改名すると形式が変わります**が、これは受け入れ済みの性質です。
テンプレート置き場が h1（ページの題）で決まるのと同じです
（「機能が名前で変わるのは目論見通りです。表示されている言葉が機能を表します」）。

**`dl`（タグ）は `data-type="tags"` のまま**です。`caption` は表の要素なので、使えません。

- **表は見える印・タグは見えない印**という非対称が残ります。
- 2026-08-31 に一度「セクション外の素の `dl`＝タグ」を試しました。
  すると**「用語：説明」のような普通の定義リストまでDBに入った**ので、撤回した経緯があります。
- **表には caption という自然な名前の置き場があるが、定義リストには無い**。その差です。

### 2.5 登録済みの語彙だけDBに入る

> 利用者:「事前に登録されている語彙だけＤＢに入れましょう。**すべての表をＤＢに入れる必要は
> ない**と思います」

**いまは型が決まらない表も索引に入っています。**

- `VocabDefByType` が「未定義でもゼロ値の def で続行」するためです
  （[vocab_index.go:206](../../internal/cms/vocab_index.go#L206)）。
- **普通の文章の中の表まで、形式名が空のまま入ります**。
- これは意図した設計ではなく、気づかれていなかった振る舞いです。

ここの「いま」と下の表の「いま」は、この決定の前の姿です。
決定は 2026-09-20 に実装しました（§3 の 3）。

| 表 | いま | 決定後 |
|---|---|---|
| `受注明細`（登録済み） | 入る | 入る |
| **発注書の様式**（対応表） | — | ⚠ **登録が要ります**（機械が引くため） |
| **顧客の発注書**（原本の写し） | 入る | **入らない**——見せるだけ |
| 型が解決しない素の表 | ⚠ 空の形式名で入る | **入らない** |

**顧客の表が入らないのは正しい**です。
あれは**原本の証拠**であって、検索したいのは弊社の表です。
二重計上の心配も、最初から起きません。

**ワンノート移行とは衝突しません。**

- 受け皿（`■材料` の下の表）は `VocabDefByHeading` を通るので、**もともと登録を前提**にしていました。
- 移行文書にも「残るのは **■材料 等の言葉を
  レジストリの表示名として宣言すること**」とあります。レジストリは、語彙の登録簿のことです。
- `材料`・`外注加工`・`購入部品`・`支給部品` は**既に登録済み**です。

### 2.6 表の形式も `settings.json` から足せるようにする

利用者の決定です（2026-09-20）。§2.5 と対になる決定です。

**これが無いと、要件を1つ落とします。**
「運用者が語彙を足せること」は 2026-08-26 の要件ですが、調べると次のとおりでした。

- **タグの語**（`図面番号` の型など）→ `config/settings.json` の `vocabulary` で**足せる**
- **表の形式**（列を持つ `VocabDef`）→ **Go のコードにしかない**
  （`RegisterVocab` を呼ぶのはプラグインだけ）

いままでは「登録されていなくても索引に載る」が抜け道になっていました。
§2.5 でそれを塞ぐので、**正面の道を開けます**。
タグの語と同じく、`git pull` で全環境へ届くのも利点です。

設定の扱いは `vocabulary` と同じです。

- ⚠ **設定が壊れていたら起動を止めます。** これは既存の規律のままです。
  黙って既定値で上書きすると、運用者の語が消えるためです。
- **足したらDB再構築**が要ります。

**2026-09-20 に実装しました**（`vocab_formats`）。書き方はこれだけです。

```json
"vocab_formats": [
  {
    "type": "shop-log",
    "display_name": "作業日誌",
    "category": "記録",
    "icon": "📝",
    "element": "table",
    "columns": [
      { "label": "日",   "type": "date" },
      { "label": "作業", "type": "text" },
      { "label": "時間", "type": "number" }
    ]
  }
]
```

本文では、`<table data-type="shop-log">` でも `<caption>作業日誌</caption>` でも名乗れます
（§2.4 と同じ規則）。

⚠ **コードが宣言している形式名は使えません。**
どちらが効いているのか画面から分からず、列の型だけが静かに変わるためです。

**読み直しで落ちないこと**が、思ったより厄介でした。

- 設定は、DB再構築のたびに読まれます。
- 検査が素朴に「もう登録されているか」を見ると、**前回の自分と衝突して HTTP 500** になります。
- **実データで踏みました**（単体の試験はまっさらな設定を見ていたので、出ませんでした）。
- 見るのは**コードが宣言した形式だけ**です。

### 2.7 対応表は `取引先／社名／発注書の様式` ページ

> 利用者:「対応表の置き場は 取引先／社名以下に**ページを作って**はどうでしょう？」

```
取引先／南北スポーツ機械／発注書の様式

  <table><caption>発注書の様式</caption>
  | 顧客の見出し | 弊社の項目 |
  |   図面No.    |            |   ← 空 ＝ 対応なし
  |   品名       |   品名     |
  |   員数       |   数量     |
  |   納入日     |   納期     |
```

**表ではなくページにする利点が2つ**あります。

1. **ページには版がある。**
   対応表は「決定」なので、**間違えたときに戻せる**のは大きいです。
2. **機械の書き込み先が分かれる。**
   社名ページは人も書きます。そこへ機械が書くと、オートセーブ（自動保存）と上書きし合います。
   様式ページを分ければ、触る範囲が閉じます。

**社名ページに子を1枚足しても壊れません。**
`machineNames` は `stage.title IN (…)` で段を名指しするので、別の題の子は自然に外れます
（[ext/toho/filing.go](../../ext/toho/filing.go)・確認済み）。

**1社に様式が複数あることはあります**（利用者）。そのときは、**1ページに表を複数**置きます。

**どれを使うかは caption では決めません。**
人が付けた名前（「発注書の様式」「注文請書の様式」）では、届いたPDFがどちらかを機械は判断できません。
**顧客の見出しの組み合わせで選びます**。

```
届いた発注書の見出し:  図面No. / 品名 / 員数 / 納入日
                          ↓ 一致する表を探す
様式①（発注書）        図面No. / 品名 / 員数 / 納入日   ← これ
様式②（注文請書）      受注No. / 品名 / 数量 / 回答納期
```

一致が無ければ、Gemini に聞きます。人が確定したとき、**3つ目の表として足ります**。
**caption は人が読むためのもの**、という役割分担です。

**空欄＝対応なし**（利用者の決定）です。

- 空欄は、「Gemini が弊社項目に対応する顧客項目を見出せなかった
  場合」を表します。
- **それ以前に人が見て書き込めば済みます。**

### 2.8 ⚠ Gemini はページに書かない

> 利用者:「**Geminiが書き込むというのが分かりませんが**、Geminiの返答を基に、整理の時に
> 出てくるようなフォームで人間が修正すればよいと思います」

**筆者（AI）の設計が間違っていたところです。**
機械がページを書く形を提案しましたが、正しくはこうです。

- **Gemini の返りは、フォームの初期値にすぎません。**
- **書くのは、人が実行したときです。**

そしてこれは、**このプロジェクトで既に4回繰り返されている形**でした。

| | 機械が出すもの | 人が決める場 |
|---|---|---|
| 加工製品の整理 | 顧客名・装置名称の推奨値 | 整理のフォーム |
| 連絡帳の登録 | 組織の候補 | 行のコンボボックス |
| 受注の整理 | 発注元の候補 | 整理のフォーム |
| **発注書の様式** | **対応の推測** | **整理のフォーム** |

**この形なら「承認前に間違った対応が定着する」が構造的に起きません。**
書く瞬間が人の操作だけになるからです。機構も1つ減ります。

```
🤖 解析   …… 顧客の表（読んだまま）＋ Gemini の推測で組んだ弊社の表
📁 整理   …… 対応のフォームが出る → 人が直す
              ├─ 弊社の表を組み直す
              └─ 様式ページに覚える
2通目以降 …… 覚えた様式で組むので、フォームは確認だけ（たいてい素通り）
```

整理が**直した値を索引にも書き戻す**のは、既にやっていることです（2026-09-11）。
置き場所としても自然です。

### 2.9 検算——数どうしの辻褄で読み取りを確かめる（2026-09-20 夜）

> 利用者:「顧客の発注書に数量と単価があって、金額や総額もあるなら、**検算が出来ると
> 思います**」

**これが、外の正解なしに OCR を確かめられる、たぶん唯一の手段です。**
§2.1 で原本の写しを残すことにしたのも「人が見比べられるように」でした。
**数どうしの辻褄なら、機械が自分で見られます。**

| 検算 | 式 | これだけが捕まえるもの |
|---|---|---|
| 行 | 数量 × 単価 = 金額 | その行の数の読み違い |
| 小計 | Σ金額 = **小計** | ⚠ **行の落丁** |
| 合計 | 小計 + 消費税 = 合計 | 小計・消費税そのものの読み違い |

**行の検算だけでは落丁に気づけません。** 落丁は、行が抜けることです。
1行まるごと落ちても、**残った行は互いに辻褄が合ったまま**だからです。
**小計との突き合わせが唯一の手段**になります。

**3本目に税率を使いません。**
`小計 × 税率 = 消費税` と書くと、10%／8%（軽減）を当てにいくことになります。
`小計 + 消費税 = 合計` なら、税率を知らずに済みます。

**⚠ 検算を Gemini にやらせない。**

- 自分の読みを自分で検算させると、**数字を合うように書き直します**。
- 誤りが消えるのではなく、**見えなくなります**。
- これは §2.8 の「機械は候補まで、決めるのは人」と同じ形の誤りです。
  **機械に自分の答え合わせをさせない**という、一段手前の線引きです。

**小計・消費税・合計金額はページのタグ**にします。

> 利用者:「変形した表になっていて、**表の
> 右下の方に、小計、消費税、合計金額が飛び出しています**」

- 書面のヘッダにある値なので、納期と同じ扱いです。
- **飛び出しているので、Gemini は明細の行としても返してきます。**
  3つの数が揃う行だけ足して、二重計上を避けます。

**見せ方は鏡型**です（弊社の明細の足元・`<tfoot>`）。
鏡型は、表示のたびにサーバーが描いて、本文には保存しない出し方です。

- **本文には焼き込みません。** 本文に焼き込むと、人が数字を直しても ⚠ が残ります。
- **原本側には出しません。** `<details>` で畳まれていて、「開くまで読まれない警告」になるためです。
- **合っているときも黙りません。**
  黙ると、「検算して合った」と「そもそも検算していない」が見分けられません。
- ただし、**辻褄が合うことは正しいことを意味しません**。合わないときに疑える、それだけです。

**見出しが見つからなければ検算しません。**

- 当て推量で別の列を掛け算すると、**正しい発注書に ⚠ を出します**。
- 狼少年になると、本物の ⚠ も読まれなくなります。
- §2.7 の**様式ページ**が入ったら、そちらが見出しの対応の正本になります。

### 2.10 原本のPDFを、写しの上に畳んで置く（2026-09-21）

> 利用者:「顧客の発注書（読んだまま）の上にPDFを表示できるようにします（通常は

並びは **原本（PDF）→ 読んだまま（機械の読み取り）→ 弊社の明細**、つまり**確かさの順**です。

⚠ **入れ替えてはいけません。**
人は、上にあるものを原本だと思って読みます。
読み取りの結果が原本の顔をすると、間違いはそこで止まります。

- **畳んだ状態で始めます**（`open` を付けない）。
  毎日見るのは弊社の明細で、PDFは**食い違いを疑ったときに開くもの**です。
- 書くのは**ファイル表示のマーカー1つだけ**です（`section[data-type="file-view" data-ref]`）。
  開くのはコアの機能で、**この拡張はPDFの出し方を知りません**。
- **写しが読めなくてもPDFは出します。**
  写しは機械の読み取りなので失敗しえますが、PDFは在ります。
  **読めなかったときこそ人は原本を開きたい**からです。
- ⚠ **番人はコア側にも1本**あります（`TestFileViewOpensInsideDetails`）。
  番人は、後戻りを見張る試験のことです。
  - 配送係が `<details>` の中へ降りなくなった日に、**PDFが黙って出なくなります**。
    配送係は、本文の要素を各機能へ配る、コアの仕組みです。
  - 畳んであるので、人は「閉じているだけ」と思って開き、空を見ます。

### 2.11 弊社の表は正規形、原本の写しは読んだまま（2026-09-21）

> 利用者:「品名が半角カナになっているので、正規化します。半角カナ以外も正規化します」

§6 に「`ｳｹﾌﾞﾗｹｯﾄ` の半角カナ——未確認」と書いていたものが、実データで出ました。

正規化は、表記の揺れをそろえることです。この文書では「畳む」とも書きます。

**半角カナのままだと、同じ品物が2つの綴りで並びます。**

- 索引の畳んだ値（`norm_value`）は NFKC を通るので、**引くほうは当たります**。
  NFKC は、文字の揺れをそろえる Unicode の決まりの1つです。
- しかし、**人が読む値**（`value`・表の見た目）は半角のまま残ります。
- `ブラケット` と `ﾌﾞﾗｹｯﾄ` は、**画面では似て見えるのに、目で見比べる人が揺れます**。

決めたのは次の4つです。

- 通すのは `NormalizeNameForIngest`（NFKC＋空白の詰め）です。
  ⚠ **`NormalizeCode` ではありません。** 長音を潰すと、`レーザー` が `レ-ザ-` になります。
- 畳むのは**品番・品名・単位**です。
  **単位を落とすと**、`ｾｯﾄ` が選択肢（`個`／`セット`）のどちらにも当たらず、
  画面が「見慣れない単位」として色を付けます。
  **まれにしか出ない単位ほど、揺れたまま気づかれません**。
- **行の納期もページのタグと同じ作法**で書きます（`CanonicalForIngest`）。
  それまでは、ここだけ生で書いていました。
  そのため、先方が `2026/10/15` と書くと、**タグは `2026-10-15`、行は `2026/10/15`** と食い違いました。
- **原本の写しは畳みません。** 畳むと、「読んだまま」が名前どおりでなくなります。

**これは「機械は text を書き換えない」の例外です。**
根拠は図面名称のときと同じで、**原本がページに出ているから**です。
すぐ上の「読んだまま」の表と、その上のPDFで見比べられます。
**§2.10 を入れた日に §2.11 が成り立つ**、という順番でした。

### 2.12 品番に何を入れるかは、Gemini に選ばせる（2026-09-21）

> 利用者:「品番には入りそうなものを入れます。…図番が多いですが、そうとも限りません。
> これはGeminiに尋ねてはどうでしょう？」

§1 で見たとおり、実データは**品番が7行とも空**でした。
先方の表に「品番」という見出しの列が無かったためです。

- **品番を持たず図番を品番として送ってくる客先**があります。
- 一方で、**図番とは別に品番を持つ客先**もあります。

**どの列が品番なのかは、表を見ないと決まりません。**
固定の規則では書けない、というのがこの決定の理由です。

決めたのは次の4つです。

- **頼み文の規則**（頼み文は、Gemini へ渡す指示の文です）
  - 「品番」の列があれば、それを入れます。
  - 無ければ、**図番・図面番号・部品番号・型式**など、**その品物を一意に指している列**を入れます。
  - 番号にあたる列が無ければ、空にします。
  - ⚠ **品名を入れさせません。** 同じ名前の別の品物がありえます。
- **選んだ根拠も返させます**（`item_no_source`）。
  - **これが 0c の積み残しでした。**
    それまで**元の見出しは返り値のどこにも残らず**、原本と見比べない限り気づけませんでした。
  - 言い換えたときだけ、本文に1行残します。
  - **言い換えていなければ黙ります**（毎回出る注意書きは読まれなくなります）。
  - **行ごとに違う列から採っていたら黙ります**。
    様式を読めていない印で、**1行で言えないことを1行で言うと嘘になります**。
- **鏡型ではなく本文に書きます。**
  - 検算の ⚠（§2.9）は、**いまの数字**についての判断です。人が直したら消えねばなりません。
  - こちらは、**解析がそのとき何をしたか**という出来事です。あとから品番を打ち直しても、真のままです。
- **頼み文を関数の外の定数へ出しました**（`orderJudgePrompt`）。
  - ⚠ `TestPromptMentionsEveryJSONKey` が、頼み文とGoの構造体のずれを見ます。
  - **片方だけ直すと、その項目はエラーにならず常に空**になります。
    応答に入っていないだけなので、`json.Unmarshal` は何も言いません。

**様式ページ（§2.7）が入れば、そちらが正本になります。**
それまでの繋ぎとして、機械に選ばせて根拠を残す形にしてあります。
