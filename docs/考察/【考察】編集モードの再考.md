## 1. 発端

メールのページの「対応: 未処理・済・不要」の札をきっかけに、利用者から2つの問いが出た。

> 「メールページには、「対応」未処理、済、不要というタグ風のものがあるのですが、これもタグそのものにしては」
> 「タグにはコンボボックスで候補を出す設定が無かったでしょうか？」——利用者（2026-10-09）

決まったことは2つ（【要求】通信拡張 §4 の下書き）:

- タグの値の候補を、編集モードで enum のタグ全部に出す。同じ日に作った（【要求】タグと表 §11）。
- `対応` のタグが無い記録に `対応：未処理` を書き足す。

未決は**値の替え方**。筆者は次の3つを挙げた。

- 閲覧モードでも押して替える。
- 編集モードだけで替える。
- いまの札も残す。

利用者の答えはこうだった。

> 「せっかくですから、編集モードについて再考察しましょう」——利用者（2026-10-09）

いまの札は閲覧モードで1回押せば替わり、編集権も要らない。札を本物のタグにすると、タグの値を替えるには編集モードに入ることになる。
問いは「対応」1つでは終わらない。**値を1つ替えるために、モードを替えて編集権を取るのが正しいのか**、という問いになる。

## 2. いまの形（2026-10-09 の実装・事実だけ）

**モードは2つ**です。閲覧が既定で、右上のトグルで編集へ入ります（`assets/app.js` の `onModeToggle`・`enterEditMode`・`applyMode`）。

- **編集に入ると**、ページ単位の編集権を取ります（`POST /api/lock`）。
  - 本文は最新に載せ直し、保持者として SSE をつなぎます。
  - 誰かが持っていれば 423 になり、「空き次第このまま自動で編集を開始します」と待ちます。
  - 待っている人が来ると、2分の猶予で持ち主から明け渡されます。持ち主の接続が切れていれば、すぐに明け渡されます。
  - 待つ人がいなければ、編集権に期限はありません（`internal/cms/editlock/lock.go`）。
- **編集から出ると**、書きかけの保存を流し切ってから編集権を返します。
- **保存**:
  - 1.5秒止まったときと、本文から出たときに保存します。
  - ブロック1つだけが変わったときは `/api/save-block`、それ以外は `/api/save` で全体を保存します。
  - どちらも編集権のしるし（トークン）が要ります。ロックの無いページはしるし無しでも通ります。
- **閲覧モードのまま本文を書く口が多くあります**（14種ほど）。たとえば次のものです。
  - 対応の札
  - 発注部材表・発注書を作る
  - 整理
  - 見積依頼書を作る
  - 連絡帳の登録
  - 図面の改定
  - 行の状態
  - 表に行を足す
  - メールの下書き

  関門はどれも「**誰かがエディタを開いていれば断る**」です（`editlock.RefuseWhileEditing`・`Locks.EditorOpen`）。
  ⚠ **自分が開いていても断ります**。そのため業務のボタンの多くは、閲覧モードでだけ押せます。
- **編集モードだけにあるもの**:
  - 書けること（contenteditable）
  - スラッシュメニュー
  - ブロックの ⠿・🗑・＋
  - 帯（B I U・¶ H1 H2 H3・＋・↶ ↷）
  - 選択肢のメニュー（表のセル・10-09 からタグの値も）
  - アンドゥ・リドゥ（編集モードのあいだだけ）
  - 子ページを作る・このページを削除
- **閲覧モードだけにあるもの**:
  - 表の並べ替え
  - 見出しで畳む
  - カルーセルを1枚ずつ見せる
  - 画像の拡大表示
  - 機械向けのタグを「▸ 詳細」へ畳む
  - ほかの人の書き込みの知らせ
  - 業務のボタンの多く（解析・整理・対応・返信・印刷 など）

  ⚠ **編集に入ると見た目が変わります**——並べ替えと畳みが外れ、カルーセルは枠になり、タグは全部出ます。
- ⚠ コードのコメントの食い違い（直していない）: `app.js` の `onModeToggle` の上のコメントには「status を10秒ポーリング」とありますが、
  実装は SSE です。

## 3. いまの形で起きていること

| | 何が起きるか | 例 |
|---|---|---|
| a | **値を1つ替えるのに、モードを替えて編集権を取る**——その手間を避けるために、場面ごとに専用の札やボタンを作ってきた（タグに似た別物が増える） | 対応の札・行の状態のボタン（発注明細）・「✓ 回答を記録」 |
| b | 業務のボタンは閲覧モードにしか無く、編集モードでは自分の編集権で断られる——**直してはボタンを押す作業で、モードを行き来する** | 発注部材表を直して「発注書を作る」 |
| c | 編集権は**ページに1人**——2人が同じページの別の場所を直せない（片方が待つ） | 受注フォルダ・発注のページ |
| d | **閲覧と編集で見た目が変わる**——並べ替えた表・畳んだ見出しが編集に入ると元に戻る | 長い加工製品ページ |
| e | スマホでは、帯とキーボードで書く場所が狭い（10-07 に帯を上へ移した） | — |

## 4. 案

### A. モードは残し、閲覧モードの「小さな書き込み」を型で一般化する（筆者の推し）

閲覧モードで、**選択肢の決まった値**（enum のタグ・表のセル。のちに bool・日付も）を押すと、選択肢が出て1回で替わる。

- サーバーには「1つの値を書く」口を1つ置く（コア・設定の語彙の選択肢に無い値は断る）。
- 関門は業務のボタンと同じ「誰かが開いていれば断る」。
- 値の変更は版に残す。
- **対応の札はこれに置き換わる**（`対応：未処理` を押すと3つ出る）。
  発注明細の状態・見積依頼明細の状態のような、場面ごとの札も同じ道に寄せられる。
- モードは「**文章と形を書く**」ためのものになる。値を替えるだけならモードに入らない。
- 良いところ:
  - 発端の問い（a）がいちばん小さい変更で片付く。
  - 業務の札の作り方が1つになる（語彙に選択肢を書けば、どのタグ・どの列でも押せる——コアと拡張の線にも合う）。
  - ロック・保存の仕組みは今のまま。
- 弱いところ:
  - b・c・d は残る。
  - 「閲覧モードでも書ける所がある」ので、何が押せるかを見た目で示す必要がある。
  - 1回押すたびに版が1つ増える。

### B. モードを無くす（いつでも書ける）

読んでいるページにそのまま書ける。打ち始めたときに編集権を取り、しばらく止まれば放す。

- 良いところ: a・b・d がまとめて消える（行き来が無い・見た目は1つ）。
- 弱いところ:
  - **読んでいるだけの人が誤って書き換える**——通信記録（届いたときのまま不変）・受注ページ（原本の写し）など、
    触ってほしくないページが多い。
  - 編集権を取るのが打ち始めなので、取れなかったとき（誰かが書いている）に、打った字をどうするかを決める必要がある。
  - 並べ替え・畳み・カルーセルと書くことの両立（並べ替えた表に書くと、本文のどの行か）。
  - スマホで読むたびにキーボードが出る。
  - 作り直しが大きい（編集権・保存・アンドゥの前提が全部変わる）。

### C. B に加えて、編集権をブロックごとにする

打っているブロックだけを握る。別の人は同じページの別のブロックを書ける。

- 下地はある——ブロックごとの保存（`/api/save-block`）と、変わったブロックだけを読み直す知らせ（10-07）。
- 良いところ: c まで消える。
- 弱いところ:
  - ブロックを足す・消す・並べ替えるといった形の変更は、ページの編集権が要る（2つの粒度が混ざる）。
  - 機械が本文を書く口（14種）の関門も、ブロックごとに考え直す必要がある。
  - 3案の中で最も大きい。

### 筆者の見立て

**A から始めるのがよい**と考えます。

- 発端（対応）を片付けつつ、業務の札をコアの仕組み1つに寄せられます。
- B・C へ進むときも、A の「1つの値を書く口」は使えます。B・C の弱いところ（誤って書き換える・形の変更）は、実際に困ってから
  測ったほうがよいと考えます。
- ただ、利用者がいちばん困っているのが b・c・d なら、話は B・C からです。

## 5. 聞くこと

1. **いちばん困っていることはどれか**——次の4つのうちどれでしょうか（§3）。
   - a: 値を1つ替えるのにモードを替える。
   - b: 直してからボタンを押すたびにモードを行き来する。
   - c: 2人が同じページを直せない。
   - d: 編集に入ると見た目が変わる。
2. **閲覧モードで押して替えてよいものの範囲**——次のどこまでにするか。
   - enum のタグだけ
   - 表のセルの enum も
   - 日付・数も（数は打つことになる）
3. **閲覧で書けてはいけないページ**があるか——通信記録（届いたまま不変）・受注ページの原本の写しなど。
   - 対応のように、通信記録にも「人の印」は書く。そのため、ページ単位ではなく**タグ・列ごと**に決める形もある。
4. **対応の札**——A なら、`対応：未処理` のタグの値を押すと3つ出る形に置き換えてよいか（札は無くす）。
5. B・C を考えるなら: 読んでいるだけで書ける状態をどう見分けるか（例: 字の上に乗ると枠が出る・長押し・ダブルクリック）。

→ 2026-10-12 に利用者が上の問いを飛ばして**方針そのもの**を決めた（§6）。問い2〜5 は §6 の「このあと聞くこと」へ組み直した。

## 6. 決めたこと（2026-10-12 利用者）

> 「排他のために編集モードを設けたが、今後は編集モードの代わりに、閲覧に邪魔なものを表示しない目的で、閲覧モードを設けることに
> します。そして、ブロック単位の保護に変更し、保護の内容は編集中の同ブロックを同時に編集したものが居たら、警告してマージできるように
> 両方表示します。」——利用者（2026-10-12）

筆者の読み:

- **モードの意味が入れ替わる。** いまの編集モードは「編集権を取る」ためのもの（排他）。これからは**ページはふだん書ける**形で、
  モードは**見た目だけ**——「閲覧モード」は読むのに邪魔なもの（⠿ 🗑 ＋・帯・機械向けのタグなど）を出さないためのもの。
  モードを替えても編集権は取らない。
- **ページ単位の悲観ロック（編集権）をやめる。** 守りは**ブロック単位**で、しかも**先に握る形ではない**——同じブロックを同時に
  書いた人がいたら**警告し、両方の版を並べてマージできるようにする**（楽観的な守り）。§4 の案C（ブロックごとの編集権）とも違う
  ——握らないので、待つ人が出ない（§3 の c が消える）。
- これで §3 の a〜d は次のようになる見込み:
  - a: 値を替えるのにモードを替えない（ふだん書けるので）。
  - b: 業務のボタンの「誰かが開いていれば断る」が意味を失う（開いている＝書いている、ではなくなる）——関門の作り直しが要る。
  - c: 2人が同じページの別のブロックを同時に書ける。同じブロックだけが警告とマージになる。
  - d: 見た目は閲覧モードと書く形の2つのまま——並べ替え・畳みをどちらに置くかは詰める。

下地（10-12 に確かめた事実）:

- ブロックごとの保存 `/api/save-block`（`internal/cms/handler_save.go`）は `page_id`・`block_id`・`html`・`token` だけを送る——
  **どの版から書き始めたか（元の版）を送っていない**ので、いまは同時の書き込みを見分けられない。元の版（ブロックの中身の指紋など）を
  足し、サーバーで「いまのブロックが元の版のままか」を比べるのが芯になる。
- ほかの人の書き込みの知らせ（`internal/cms/page_events.go`・SSE・10-07）は、本文が変わると知らせ、画面が**変わったブロックだけ**を
  差し替える——ぶつかったことを書いている最中に知らせる道はこれに乗る。
- 編集権を前提にした口: 編集権の口（`internal/cms/editlock/`）のほかに、「誰かが開いていれば断る」関門を使う口が 22 ファイル
  （`RefuseWhileEditing`・`Locks.EditorOpen`・`RequireEditLock`——業務のボタン・権限・親の付け替え・添付・削除・版を戻す・整理など。
  `editlock` を使うファイルは全部で 25）。どれも考え直しが要る。

このあと聞くこと（1つずつ・答えで次が変わる順）:

1. **ページを開いたときの形と、閲覧モードで字を打てるか**——書ける形で開くか閲覧モードで開くか（端末ごと・スマホは別か）。
   閲覧モードは読むだけ（打てない）か、飾りが消えるだけ（打てる）か。
   → ✅ **2026-10-12 決まった**（利用者:「お勧め通りで」）——**閲覧モードは読むだけ（打てない）**。表の並べ替え・見出しで畳む・
   カルーセル・画像の拡大は閲覧モードに置く。書ける形との切り替えに編集権は要らない（一瞬で替わる）。**開いたときの形はその端末に
   憶える**（最後に使った形）——初めて開くときは、パソコンは書ける形・スマホは閲覧モード（読むたびにキーボードと帯が出ないように）。
2. **誤って書き換えてほしくないページ**——通信記録（届いたまま不変）・受注ページの原本の写しなど。ふだん書ける形になると、
   読んでいるだけの人が触れてしまう。
   → ✅ **2026-10-12 決まった**（利用者:「Aで良いです。その分、アンドゥ・リドゥが重要になると思う」）——**何もしない**（閲覧モードで
   読めばよい・触っても戻せる）。置き場ごとに閲覧で開く（B）・ブロックごとに書けない（C）は作らない。そのかわり**戻す道が守りになる**。
   筆者が書き留めたこと（10-12 に今の作りを見て）:
   - いまのアンドゥは**ページ全体の写し**（上の段のブロックの並び）を積み、戻すときにそれへ差し替える（`assets/app.js`「区切り
     （チェックポイント）」・`pushState`）。履歴は編集モードのあいだだけ。**ほかの人が同じページの別のブロックを書く形では、
     このままだと戻したときに相手の書き込みまで巻き戻す**——アンドゥは**自分の変更だけ**（自分が変えたブロックの前と後）を
     積み、戻すときに相手がそのブロックを書き換えていたら、ぶつかったときと同じく両方を並べる形にする必要がある。
   - 版の「この版に戻す」もページ全体を戻す——同じ理由で、相手の書き込みを消す。「このブロックだけ戻す」が要るかもしれない。
   - 後で気づいた誤り（翌日など）は、アンドゥの履歴ではなく版で戻すことになる。→ 問い8。
3. **警告の時機**——同じブロックに別の人が書き始めた時点で知らせるか、両方が書き終えて**ぶつかったときだけ**か。
   → ✅ **2026-10-12 決まった**（利用者:「勧め通りで」）——**相手の保存が届いた時点**（ウ）＋**保存のときにぶつかったら**（ア）。
   自分が書いている最中（まだ保存していない変更がある）のブロックを、ほかの人の保存が書き換えたら、書き換わりの知らせ
   （`page_events`）を受けたその場で警告して両方を並べる（相手が打って約2秒——保存の間隔）。知らせを取りこぼしても、自分の保存で
   サーバーが「書き始めたあとに変わった」と見つけたら同じ形にする（最後の守り）。相手がカーソルを置いただけでは出さない
   （誰がどこにいるかのやり取り〔イ〕は、困ってから足す）。
4. **両方を並べたあとのマージの仕方**——どちらかを採る・両方を残して人が直す・ブロックの中で差分を見せる、など。
   → ✅ **2026-10-12 決まった**（利用者:「勧め通りで」）——**イ＋エ**:
   - **イ**: そのブロックの上に**相手の版を読むだけで**（色の枠で）出し、下の**自分の版はそのまま書ける**。相手の書いたことを取り込んで
     「これで決める」。急ぐときのボタン「相手の版にする」「自分の版にする」も付ける。
   - **エ**: **表は、違うセルの変更なら自動で合わせる**——書き始めたときの表・自分の表・相手の表の3つを比べ、違うセルを直しただけなら
     黙って両方を入れる。同じセルを違う値にしたとき、または行・列を足した・消したときだけイの形で並べる。
   - 違うところに色を付ける（ウ）は、使ってみて読みにくければ足す。
   - 前提（10-12 に確かめた事実）: ブロックは本文のいちばん上の段の単位——表は1つの表がまるごと1ブロック、見出しと表を節で包んだもの
     （加工製品ページの「材料」など）は節ごと1ブロック。だから2人が同じ表の別の行を直してもぶつかる——エはそのため。
5. **業務のボタン（機械の書き込み）と人の書きかけがぶつかったとき**——どちらを先にするか。
   - 作るときの必須（10-12 に確かめた事実・利用者の判断は要らない）: 業務のボタンは本文のファイルを**読んで・変えて・書き戻す**
     （`cms.RewriteBody`→`rewritePageBody`・`internal/cms/append_page.go`・呼び手 30 か所）。ブロックの保存も同じく読んで書く。いまは
     「誰かが開いていれば断る」関門があるので重ならないが、関門を外すと**同じページへの書き込みが重なって片方が消える**——サーバーで
     **ページごとに書き込みを1つずつ通す**（ページ ID ごとの錠・人の保存も機械の書き換えも同じ錠を通る）。これは編集権（人が握る）
     ではなく、1回の書き込みのあいだだけの錠。
   → ✅ **2026-10-12 決まった**（利用者:「勧め通りで」）——**機械も「ほかの書き手の1人」として扱う**（ア）。業務のボタンはいつでも
   動いて本文を書き換え、同じブロックを書いている人がいれば問い3・4の形（その場で警告・相手の版を上に・表は違うセルなら自動で合わせる）。
   相手の名前は「○○さんが押した『発注書を作る』」のように出す。**自分が押すボタンは、押す前に自分の書きかけを保存してから動く**
   （直してすぐ押せる——いまの「一度閲覧へ戻る」は要らなくなる）。ボタンごとの「誰かが開いていれば断る」関門（22 ファイル）は外す。
6. **形の変更とぶつかったとき**——あるブロックを書いている間に、別の人がそのブロックを消す・動かす。

### 試験の約束（2026-10-12 利用者:「込み入ってるのでテストは十分にお願いします」）

作り直しは、次の試験が揃って緑になるまで「できた」と言わない。

- **サーバーの合わせ方（Go）**——書き始めたときの本文・自分の変更・相手の変更の組を表にして全部の組み合わせを試す:
  違うブロックを変えた／同じブロックを変えた（ぶつかる）／表の違うセル・同じセル・行や列を足した消した／足した・消した・動かした・
  並べ替えた の組み合わせ／消したブロックを書いていた。期待する結果（合わさる・両方を返す）を1行ずつ書く。
- **重なり（Go・`-race`）**——人の保存と業務のボタン（`RewriteBody`）を同じページへ同時に何十回も流し、**どの書き込みも消えない**
  （ページごとの書き込みの錠）。
- **画面（E2E）**——ブラウザを2つ（2人）立ち上げ、同じページで: 別のブロックを同時に書く（両方残る）／同じブロックを書く（その場で
  警告・相手の版が上に出る・「これで決める」「相手の版にする」「自分の版にする」）／表の違うセル（黙って合わさる）・同じセル（並ぶ）／
  書いているブロックを相手が消す（「残す」「消す」）／業務のボタンを押す（書きかけを保存してから動く・相手には警告）／
  アンドゥが自分の変更だけを戻す（相手の書き込みは残る）／閲覧モードでは打てない・開いたときの形を端末に憶える。
- **変異試験**——合わせ方の要所（元の版との比較・セルの比べ方・錠）をわざと壊し、上の試験が落ちることを確かめる
  （空振りの罠は引き継ぎの「罠」——当たったか・振る舞いが変わったかまで見る）。
- 今ある E2E（編集モードの出入り・ロックを前提にしたもの）は、作り直しに合わせて書き直す——消して済ませない。
