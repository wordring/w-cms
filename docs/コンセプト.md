# w-cms ソフトウェアコンセプト・設計仕様書

このドキュメントでは、**w-cms** の基本コンセプトである「自由なファイルベース保存と、タグ（名前：値）による意味付けをベースとした双方向データ連携」の仕様について定義します。

---

## 1. コア・コンセプト：自由な記述と「タグ」によるデータの意味付け

w-cms は、入力項目が固定された硬直的な入力フォーム（帳票システム）を排除します。**「Notionのように、テキストや見出しを自由なブロックレイアウトでフラットなページに記述し、PDF等の原本ファイルを好きな場所に配置し、タグを付与することでその情報の意味（親ページ、発注書、部材など）をデータベースに自律的に認識させる」**というデータ連携を採用しています。

```mermaid
graph TD
    subgraph Browser [ブラウザ / Notion風エディタ]
        UI[ブロックベースの自由なレイアウト]
        FBlock[m-file / m-material タグブロック<br>PDFファイル + 意味タグ]
    end

    subgraph Storage [ファイルシステム (物理ストレージ)]
        F1["data/master/xx/xxxxx/xxxxx.html (ID名のHTML本体)"]
    end

    subgraph DB [SQLite データベース]
        T1["pages / page_tags テーブル"]
        T2["各種取引インデックス (発注書/部材/PDFパス)"]
    end

    UI -- "1. 編集・自動保存" --> F1
    FBlock -- "2. Web Componentsによる入力" --> F1
    F1 -- "3. HTML解析・抽出 (Sync)" --> DB
    DB -- "4. API経由での動的集計ロード" --> UI
```

### ① すべてがフラットな「ただのメモ（ページ）」
システム上には「顧客管理画面」「製品管理画面」といった特有のページ種別は存在しません。すべてのページはフラットな数字IDのフォルダに格納された、同一の構造を持つHTMLファイルです。
*   **自動採番**: ページID（ファイル名）は、新規作成時に連番の10進数で付与されます（例: `00001`）。
*   **物理分離**: ファイルはディレクトリ階層に分散して格納されます（例: `data/master/00/00001/00001.html`）。

### ② 記述内容によって「役割」が動的に決まる
白紙のメモに、ユーザーが「どのWeb Componentsブロックを配置するか」によってページの役割が決まります。
*   `<m-tag name="顧客名" value="〇〇">` を埋め込めば、そのページは「顧客のページ」として機能します。
*   `<m-client-order>` を配置すれば、そのページは「受注記録」としての役割を持ちます。

### ③ タグによる「仮想的な親子関係（階層）」の表現
「顧客 ＞ 完成品機種 ＞ 部品」のような階層構造も、データベースの固定設計ではなく、ページ内に記述する「親ページを示すタグ」によって表現します。
これにより、複雑なディレクトリ構造を気にせず、タグ一つで仮想的なツリーを表現できます。

### ④ データベースによる一元集計と非同期レンダリング
データベースにはすべてのドキュメントから抽出されたデータがフラットに集約されます。
エディタ上に `<m-required-materials>` のような集計コンポーネントを配置すると、バックエンドのAPIを呼び出して「必要な部材の総数と手配状況」などを動的に計算し、テーブルとして画面にレンダリングします。

## 2. Web Components と HTMLブロック構造

HTML内には独自定義のカスタム要素がシリアライズされて保存されます。これがバックエンドのパーサーと連携し、DBへのインデックス化を実現します。

### マークアップ例
```html
<div class="editor-block">
    <div class="block-controls">...</div>
    <div class="block-content" contenteditable="false">
        <m-file src="PO-2026-001.pdf" name="発注書.pdf">
            <m-client-order order-no="PO-2026-001" client-name="テスト株式会社" ordered-at="2026-06-18">
                <m-item item-id="ITEM-A" item-name="特殊シャフト" price="5000" quantity="10" status="未着手"></m-item>
            </m-client-order>
        </m-file>
    </div>
</div>
```
このように、業務要素（`m-client-order` ＝発注書ヘッダ）の中に複数の `m-item`（明細）がネストされる構造となっており、これをGoのパーサーが読み取ってリレーショナルデータベースに登録します。

`<m-file>` は「ここにファイルがある」ことだけを表す**容器**で、業務上の意味は中身の要素が持ちます。
ファイルの無い受注なら業務要素だけを置けばよく、新しい文書種別は要素とプラグインを足すだけで増やせます。

（※データベースの詳細なスキーマについては `アーキテクチャとDBスキーマ.md` を、エディタのUI技術仕様については `エディタ仕様.md` を参照してください。）

## 3. UI実装方式：Web Componentsの採用理由

`assets/web-components.js` で定義されているカスタム要素（`m-tag`, `m-item`, `m-file`, `m-child-list`, `m-material`, `m-required-materials`）によるUI実装は、本プロジェクトの要件に対して妥当な選択である。この判断根拠は恒久的な設計記録として残す。

*   **保存形式とDOMの一致**: カスタム要素はDOM自体がそのまま保存対象のHTMLになるため、React等の仮想DOM系フレームワークのような「HTML文字列への変換層」が不要。
*   **バックエンド連携の単純さ**: Goバックエンド（`internal/cms/parser.go`）は標準の `golang.org/x/net/html` パーサーでタグ名・属性をそのまま再帰トラバースするだけでデータ抽出が完結する。
*   **contenteditableとの共存**: リッチな`contenteditable`領域とカスタム要素を同一DOM上で自然に共存させられる。Reactなどを併用する場合、contenteditableとの統合は業界的にも難所であり（多くのリッチエディタはProseMirror等の専用ライブラリに依存する）、本プロジェクトの規模（カスタム要素10種類程度の社内CMS）にはフレームワーク導入はオーバーエンジニアリングと判断。

## 既知の課題（未修正・解消後に本項目は削除）

2026-06-20時点でのWeb Components実装に残るプロトタイプ的な粗さ。修正が完了したらこの項目ごと削除する。

*   **高い結合度**: CustomEvent/dispatchEventを使わず、`window.updateHtmlPreview` 等のグローバル関数に依存している。呼び出し口は基底クラス `MElement`（`updateAttr` / `bindEditFields`）に集約されたので、置き換えるならそこ1箇所で済む。

> **解消済み — Shadow DOM方針の不統一（2026-08-05）**: 10要素中 `MChildList` だけが Shadow DOM で
> 描画しており、その名残の Shadow 前提API `getRootNode().host` が Light DOM のテンプレートに
> 残っていた。Light DOM では `getRootNode()` が `document` を返し `.host` は `undefined` なので、
> **`<m-tag>` の値編集・`<m-tag>`/`<m-item>` の項目編集・`<m-item>` の削除ボタンは
> `TypeError` で動いていなかった**（方針の不統一にとどまらず実害があった）。
> **Light DOM に統一**し、ホストへの書き戻しは `data-attr` へ一本化（基底クラス `MElement`）。
> 判断根拠は [エディタ仕様.md](エディタ仕様.md) §0.1。

> **解消済み — 非効率な再描画（2026-08-05・部分）**: 属性変更ごとの全体 re-render 自体は残るが、
> **自分のUI操作による属性変更では再描画しない**ようにした（`MElement.updateAttr`）。
> 従来は1文字打つたびに入力欄が作り直され、フォーカスが飛んで実質1文字しか入力できなかった。
> 外から属性が変わったとき（読み込み・PDF解析の反映など）は従来どおり描き直す。

> **解消済み — XSSリスク（2026-08-04）**: テンプレート変数の展開（`/assets/templates/*.html` を
> `fetch` し `String.replace` で変数展開する自作エンジン）にエスケープが無く、**実際に発火する
> 保存型XSS**だった（`<m-tag value='" onmouseover="…'>` で属性を注入でき、`value` に
> `<img onerror=…>` を入れればスクリプトが走った）。**サーバーのサニタイザでは止まらない**——
> `value` はURL属性ではないので中身を検査せず、`&lt;img…&gt;` として保存された値を
> `getAttribute()` が生の文字列へ戻すため。中間版CSPの `script-src 'unsafe-inline'` も
> インラインイベントハンドラを許すので防げなかった。`escapeText`/`escapeAttr` を
> 全コンポーネント（`m-tag`・`m-item`・`m-material`・`m-child-list`・`m-required-materials`）へ
> 適用して修正済み。**新しいテンプレート差し込みを書くときは必ず通すこと。**
