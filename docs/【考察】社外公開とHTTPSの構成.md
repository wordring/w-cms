# 【考察】社外公開とHTTPSの構成

> 2026-09-07。実運用では**社外からも使い、主にスマホから**という前提が出たので、
> 公開の形を先に決めておきます。**まだ実装していません**——選ぶための材料と、
> どちらを選んでも要ることを書き残すのが目的です。
>
> 関連: [【考察】添付をローカルアプリで編集する.md](【考察】添付をローカルアプリで編集する.md)
> （WebDAV・HTTPS化の実測）／[認証認可設計.md](認証認可設計.md)（匿名公開の規則）。
> **結論は §6。** どちらを選んでも要ることは §4（split-horizon DNS）。

## 1. きっかけ——スマホが入ると自己署名は捨てることになる

いまは**自己署名の証明書＋各PCで1回信頼**という形です（2026-09-07 に実装・2台で確認済み）。
これは台数が少ないうちは堅い選択でした——2年もち、更新の自動化が壊れる心配もありません。

**スマホが入ると成り立ちません。** iOS はプロファイルを入れたうえで
「証明書信頼設定」で有効化まで要り、端末が増えるたびに発生します。
**公的な証明書（Let's Encrypt 等）へ移ります。**

Let's Encrypt の証明書は **ISRG Root X1** から辿れ、この根は Windows にも各ブラウザにも
スマホにも最初から入っています。**信頼させる作業が丸ごと消えます。**

## 2. 選択肢は2つ

### A. 固定IPで社内サーバーに直結

```
スマホ・社外 ──▶ ルータ（443を転送）──▶ 社内 w-cms
社内PC ──────────────────────────▶ 社内 w-cms
```

- 証明書は **HTTP-01 がそのまま使えます**（公開IPに Let's Encrypt が繋がるため）
- **部品がいちばん少ない**。証明書を配る仕掛けが要らないのは地味に大きい
  ——90日ごとに壊れうる箇所が1つ減ります
- **社内に受信ポートを開けます**。図面のある機械が直接インターネットに面します

### B. VPS でリバースプロキシ

```
スマホ・社外 ──▶ VPS（公開IP・Let's Encrypt）──トンネル──▶ 社内 w-cms
社内PC ──────────────────────────────────────────────▶ 社内 w-cms（直結）
```

- トンネルは**社内から外向き**に張るので、**ルータの受信ポートは閉じたまま**
- **回数制限や遮断をVPS側で**できます（本体に触らずに済む）
- **データは社内に残ります**。VPSは中継するだけ
- **証明書を社内へ配る仕掛けが要ります**（90日ごと・自動化する）
- 月額と、もう1台ぶんの運用

### 比べる

| | A. 固定IP直結 | B. VPS |
|---|---|---|
| 証明書 | HTTP-01・本体で取る | HTTP-01・VPSで取って**配る** |
| 社内から | **split-horizon が要る**（§4） | **split-horizon が要る**（§4） |
| 社内の速さ | 直結・最速 | 同（split-horizon 前提） |
| 社内へ開ける穴 | **443の受信** | **不要** |
| 図面のある機械 | 直接インターネットに面する | VPSが前に立つ |
| 回数制限 | サーバー本体でやる | VPS側でやれる |
| 部品の数 | **少ない** | 多い（VPS・トンネル・証明書の配布） |
| 費用 | ルータ設定だけ | 月額＋運用 |

**VPS の値打ちは「社内へ受信ポートを開けないこと」に集約されます。** アプリへの
攻撃そのものは、プロキシがあっても素通りします——止まるのは**社内網への到達**と、
走査の雑音です。

## 3. WebDAV は外に出さない（決定）

**これがこの文書でいちばん実務に効く判断です。**

| | 誰が・どこから | 経路 |
|---|---|---|
| **画面（ブラウザ）** | スマホ・社外PC・社内PC | 公開する |
| **WebDAV（`/dav/`）** | 社内のPCだけ（CAD編集） | **社内直結。公開しない** |

理由が3つ揃います。

1. **スマホでCADは編集しません。** 外に出す用事がそもそもありません
2. **Basic 認証を世界に晒さずに済みます**——要求のたびに合言葉が流れる口です
   （締め出しは効きますが、晒さないに越したことはない）
3. **プロキシ越しWebDAVの落とし穴が丸ごと消えます**——`PROPFIND`/`LOCK` を
   通すか、`client_max_body_size`（nginx の既定は**1MB**）、タイムアウト。
   **どれも「保存できたつもりで届いていない」を作る場所**です
   （2026-09-07 に Windows の無言の失敗を実測した直後なので、なおさら避けたい）

リバースプロキシなら `/dav/` を拒否する一行、直結ならルータかサーバー側で絞ります。

## 4. どちらを選んでも要る——split-horizon DNS

**社内からの接続が、いちばんつまずきます。**

社内PCが `wcms.example.co.jp` を引くと、公開DNSは**グローバルIP**を返します。
そこへ社内から繋ぐと、ルータが折り返す必要があります（**ヘアピンNAT**）。
**多くの業務用ルータはこれをしません**——すると
**社外からは繋がるのに社内からだけ繋がらない**、いちばん分かりにくい失敗になります。

**IPで逃げることもできません:**

```
https://192.168.1.10:8443/   →   証明書の名前と合わない → 警告
```

**Let's Encrypt はプライベートIPに証明書を出しません。** 自己署名のときは証明書に
IPを入れられましたが（`-gencert` はそう作っています）、公的な証明書に移ると
**社内でも必ずホスト名で繋ぐ**ことになります。

答えは **split-horizon DNS** です。

```
社内で引くと  wcms.example.co.jp → 192.168.1.10   （直結・速い）
社外で引くと  wcms.example.co.jp → グローバルIP（またはVPS）
```

同じ名前・同じ証明書のまま、社内は直結になります。置き場所は3つ:

| | 向き |
|---|---|
| **ルータのローカルDNS機能** | いちばん手軽。台数を問わない |
| 社内DNSサーバー | ちゃんとやるなら |
| 各PCの hosts ファイル | **選べません**——スマホには書けない（社内Wi-Fiでも同じ名前を引く） |

## 5. 外に出す前に確かめること

### 契約と機器

- **プロバイダが 80/443 の受信を許しているか。** 塞がれていると HTTP-01 が使えず、
  TLS-ALPN-01（443のみ）か DNS-01 になります
- **ルータがローカルDNSを持っているか**（§4）。無いと**スマホが社内Wi-Fiで繋がりません**

### w-cms 側

- **総当たりへの備え**——ログインは argon2id ＋締め出しがありますが、世界中から来ます。
  プロキシでの回数制限か `fail2ban`、そして**監査記録を見る習慣**
- **公開ページ**——2026-09-07 時点で**0件**（実効公開は先祖すべての AND なので、
  うっかり漏れる形にもなっていません）。外へ出したあとは、`public` を立てた瞬間に
  **本当に世界に見えます**
- **スマホの実機確認2点**（引き継ぎの宿題）——リンクのプロパティ欄が画面右へ
  はみ出さないか、薄青・薄赤が小画面で見分けられるか。**LANで先にやれます**
- **スマホからの写真アップロード**が実運用で要るか（現場写真）。要るなら先に試す

## 6. 結論——**B（VPS リバースプロキシ）**

ユーザー決定（2026-09-07）:「VPSにします」。**図面のある機械へ受信ポートを開けない**
ことを採りました。証明書を配る仕掛けが1つ増えますが、社内網への到達経路を持たせない
利点がそれに勝る、という判断です。

**アプリ側の備えは実装済み**（同日）:

- **`/dav/` は転送されてきた要求を断ります**（`X-Forwarded-For` 等の有無で判定・404）。
  「WebDAV は公開しない」はプロキシの設定で実現しますが、**設定だけに頼りません**
  ——`location /dav/` を書き忘れた日に、Basic 認証の口が黙って世界に開きます。
  逃げ道は `WCMS_DAV_ALLOW_FORWARDED=1`（プロキシ経由でしか届かない構成にしたいとき）
- **`X-Forwarded-For` は元から扱えます**（`clientIP`・`isTrustedProxy`）。社内側の
  トンネル端点は loopback / private なので信頼され、**監査記録に本当の接続元が残ります**

**VPS 側で要ること**（構築時に）:

```nginx
location /dav/ { return 404; }      # WebDAV は公開しない（§3）
client_max_body_size 64m;           # 既定 1MB では添付が通らない
limit_req zone=login burst=5;       # 総当たりへの備え（§5）
```

**先に決まっていること:**

1. **WebDAV は公開しない**（§3）
2. **split-horizon DNS を最初から入れる**（§4）——あとから足すと構成が二度手間になります
3. **社内でもホスト名で繋ぐ**（IP直打ちは証明書が合わない）
