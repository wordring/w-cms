## 1. 背景と目的

2026-08-16 の前提変更——語彙100種規模・一般公開ウェブサイト用途——により、
「新しいタグ＝新しいGoプラグイン＝新しいテーブル」という現行の増やし方が成立しなくなった
（開発者がボトルネックになり、公開ページはカスタム要素の描画にJSを要する）。
本書は**語彙の増やし方と拡張機構**を再設計する。

## 2. 3層モデル

**「語彙を増やす」と「計算を作る」を別の作業に分離する。**

| 層 | 実体 | 変更する人 | 担うもの |
|---|---|---|---|
| **① 語彙レジストリ** | 宣言データ | 管理者（将来は利用者） | `data-type` 形式の定義: 名前・表示名・分類・アイコン・要素種別（table/dl）・列（`data-field`・型・ラベル・許可値）・雛形 |
| **② 汎用索引** | コアのコード（1実装） | — | 全 `table[data-type]`/`dl[data-type]` を汎用テーブルへ同期（`page_tags` の一般化）。検索・単純集計 |
| **③ 計算プラグイン** | Goコード（少数） | 開発者 | 型付きテーブル＋計算ロジック（部材手配・利益・進捗・参照追従）・取り込み変換（PDF/画像→表・`.eml`→通信記録）・集計API・外部投入API |

- **追加コストの段差**: 記録・表示だけの語彙（100種の大半）＝①の宣言1件。
  計算が要る語彙だけが③の開発案件。プラグインは「1**計算**ユースケース＝1プラグイン」へ
  意味が狭まり、語彙の増殖から切り離される。
- **語彙の単一正本の拡張**: ①のレジストリと③のプラグイン宣言（計算型の列定義は `Sync()` と
  同じ宣言から導く）を合成し、単一のAPI（`/api/tag-schema` の拡張）でエディタ・
  タグ一覧のドキュメント生成へ届ける。
- **安全性の分離（要）**: サニタイザの許可リスト（要素・属性名）は従来どおり**コードで固定**し、
  `data-type`/`data-field` は属性**名**だけを許可して**値は不活性な文字列**として扱う。
  レジストリは編集支援と検証の語彙であって**安全性の門ではない**。この分離があるから、
  将来レジストリを実行時編集可能（管理UI・語彙定義ページ）にしても危険な要素は増やせない。
- ②の汎用索引にも「ファイルから再生成できないデータを持たせない」不変条件
  （[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §8.1）を適用する。

## 3. 挿入経路と不変条件

構造化ブロックが本文へ入る経路の全体像。**不変条件: どの経路から入っても出口は同じ**——
同じ語彙・同じ保存時サニタイズと検証・同じ編集ロックを通る。経路はプロデューサーの違いに
すぎず、語彙の単一正本を迂回する経路を作らない。

| 経路 | 例 | 状態 |
|---|---|---|
| 明示挿入 | スラッシュメニュー → レジストリの列定義から骨格生成 | 実装済み（現行9種・レジストリ駆動化は未実装） |
| 貼り付け変換 | Excel/TSV → 表、他アプリHTML → サニタイズ受け入れ | HTML貼り付けは実装済み・表変換は検討中 |
| ファイル取り込み変換 | 発注書PDF → 明細表（**実装済み**・Gemini）、撮影画像 → 表・`.eml` → 通信記録（構想） | 一部実装済み |
| デバイス起点 | カメラ写真の挿入（要件定義書 §2.6）、バーコード/QR → 品番セル（構想） | 未実装 |
| 他ページ参照 | 子ページ一覧（実装済み）、`<m-quote ref>`（構想） | 一部実装済み |
| 計算ビュー | `<m-required-materials>`——内容は閲覧時にAPIから取得し**保存されない**派生表示 | 実装済み |
| 雛形・複製 | ページ雛形・ブロック雛形（製品マスタの `必須項目` 規約の一般化） | 構想 |
| エディタ外生成 | 受信箱 fan-out・外部投入API・一括移行 | 構想 |

経路ごとに③プラグインが宣言しうる能力が対応する（明示挿入＝メニュー項目と骨格／
取り込み変換＝ファイル種→変換／計算ビュー＝集計API…）。①②で賄えない経路能力だけが
③のインターフェースに載る。

## 4. エディタの形式知識の3原則

1. **新規挿入時**——列定義の全体が要る。レジストリからAPI経由で受け取る
   （エディタに手書きの形式リストを置かない）。骨格（ヘッダ行つきの表）は列定義から
   機械的に生成する。
2. **既存ブロックの編集時**——**レジストリ不要**。表の鍵は見出し行が運ぶ
   （**`data-field` があればその値、無ければ見出しテキスト**——§5「列の鍵」）ため、
   文書自身が運ぶスキーマだけで編集が成立する。レジストリが読めなくても
   既存文書の編集は壊れない（正本＝ファイルの自立性の表版）。
3. **入力補助・検証**——レジストリがあれば向上する（enum の選択肢・未知の `data-field` への
   警告）。無くても編集は可能。

エディタの実装は**汎用表エディタ1つ**（セル編集・行操作・列設定UI・列型
`text`/`number`/`date`/`enum`/`image` に応じた入力補助）で、**型の数に対して不変**。
型ごとの JavaScript が要るのは③の特殊UI（PDFドロップ・集計表示・参照ピッカー）だけ。

## 5. 決定ログ（2026-08-16）

| 判断 | 決定 | 理由 |
|---|---|---|
| マーカーの属性 | `class` でなく **`data-*`** | サニタイザの `class` 全面拒否に例外を作らない（`data-id` の前例あり）・見た目と役割の分離・シェルDOMと衝突しない（[【考察】タグ設計.md](【考察】タグ設計.md) §7） |
| レジストリの置き場（v1） | **Goコード内の宣言テーブル**から始める | 定義スキーマが固まる前にDB化すると移行が二度手間。データ構造はそのままに (b)管理UIのDB → (c)語彙定義ページへ段階的に育てる。**v1の間は語彙追加に再ビルドが要る**（「再デプロイ不要」は(b)以降の目標） |
| 未知の `data-type` | **通す**（＋保存時に「未定義の種別」と通知） | 値は不活性で害がなく、②の索引に載るだけ。落とす方式はレジストリを安全性の門に変質させ、(b)(c)への発展を塞ぐ。通知は拒否でなく告知（エコーバックの流儀） |
| 移行の段取り | **まず標準HTMLへの移行の検討から始める**（§6が本体） | 移行マップと外形の論点を先に固めてから、実装順を決める |
| レジストリの定義スキーマ | **サンプルスキーマで実装を先行**し、ある程度動いてから実運用スキーマを確定する | 机上で確定させるより、汎用表エディタ・②索引・骨格生成を実際に駆動して過不足を知るほうが早い。v1がコード内宣言（上記）なのでスキーマ変更のコストが最小のうちに試せる |
| 識別子の文字種 | `data-type`・`data-field` の値は **kebab-case**（小文字英数とハイフン。例: `client-order-items`・`item-id`） | HTML属性値・URL・Goの文字列リテラルのどこでも引用符や変換が要らない。既存の `data-field` 案（タグ設計 §7）とも一致 |
| 識別子の一意性 | **`data-type` はレジストリ全体で一意**。`data-field` は **（`data-type`, `data-field`）のセットで一意**——形式内で重複しなければ、形式間の同名再利用（`item-id` 等）は可 | 形式の識別は `data-type` が担うため、そこが一意でないと成立しない。フィールドは形式が名前空間になる。②汎用索引のキーも（page_id, `data-type`, 行, `data-field`）で引く。**同名 `data-field` を形式間で同じ意味に揃える（`item-id`＝品番）のは推奨規約であり機械は強制しない**——形式横断の名寄せ（原価と利益の `item-id` 横串など）はこの規約に依る |
| DBの設計姿勢（方針・詳細は後日検討） | **完全な正規化と考える**——②汎用索引は縦持ち（1フィールド＝1行）とし、**検索の速さより定義変更への強さを優先**する | 小規模事業者用のシステムでデータ総数は少なく、性能は問題にならない。縦持ちなら形式の定義変更（列の追加・削除・改名）が **DBスキーマ変更を一切要求しない**（`ALTER TABLE` 不要・再構築も不要）。定義変更の影響は文書とレジストリの側だけに閉じる |
| 列の鍵 | **`data-field` があればその値、無ければ見出しテキスト（trim後の textContent）**。`data-field` を付けるのは**③計算形式だけ**（レジストリからの骨格生成時にエディタが自動付与。人は書かない・見ない）。同一表内の見出し重複は保存時に警告 | 見出しに `金額` と書いてあるのに `data-field="amount"` を重ねる必要はない（ユーザー指摘）。②汎用索引は固定スキーマを持たないので、記録だけの形式は改名しても壊れない——`<m-tag>`／`dl` の「表示文字＝鍵（自由語彙）」と同じ扱いに統一。機械キーが要るのは `Sync()` というプログラム契約がある③のみ。kebab-case・一意性の決定は `data-field` を使う場面に限定適用。タグ設計 §7 の「見出しテキストを役割キーにしない」は**③限定**に狭める |
| 列の型と正規化 | **列型も見出しテキストから推論する**——語→型の辞書（`金額`/`単価`/`原価`→通貨、`数量`/`個数`→数値、`納期`/`発注日`→日付…）をレジストリの一部として持つ。推論した型で ①エディタが入力を検証し**通知**する（例: 通貨列に通貨以外の文字→背景を赤く。**拒否はしない**）②汎用索引が**正規化値を併記**する（解釈できた値だけ。**生テキストが常に正本**）。特別な場合は少数への例外対応で: 辞書に無い語→text 扱い（検証しない）／推論を外したい列→`th data-type` の明示で上書き／③計算形式→レジストリ宣言の型が優先 | 見出しに `金額` とあれば通貨であることは自明（ユーザー）。鍵と同じく**「見える文字が既定・機械属性は例外」**の原理に統一。検証を通知に留めるのは、自由な記述をシステムが**認識する**（強制しない）というコア・コンセプトを壊さないため |
| 機械属性の可視化 | **属性値が見出しテキストに優先している箇所は、編集モードで背景をハイライトする**（`data-field`/`data-type` 付きの `th`・`dd`）。列設定UIを開けば実際の鍵・型が見える。値の型不一致の通知（赤）とは**別の色**にする | 見えている文字が鍵・型として無視されていることは、印が無いとユーザーに分からない（ユーザー指摘）——「見える文字が既定」の原理を守るには、**例外の発動も見える**必要がある。実装は CSS の属性セレクタ（`th[data-field]` 等）で済み、**上書きを起こす属性自体が印のトリガー**になるため表示と実態がずれない。ハイライトはエディタのクローム（編集モード限定・保存HTMLには載らない） |

## 6. 標準HTMLへの移行の検討（初版・たたき台）

### 6.1 現行9要素の移行マップ

| 現行 | 移行先 | 層 | 備考 |
|---|---|---|---|
| `<m-tag>`（可視メタ） | `<dl data-type="tags">`（`<dt>名前</dt><dd>値</dd>`） | ①＋② | 多値は `dt` 繰り返し／複数 `dd`。`部品番号`・`必須項目` 等の特別扱いは `page_tags`（または汎用索引）経由で不変 |
| `<m-tag>`（配線: `受信元`・`前版`） | **参照専用要素**（`<m-quote ref>` 系・未設計） | ③ | 表示されない配線は dl へ移せない。[【考察】通信記録処理.md](【考察】通信記録処理.md) §9.1 と合流 |
| `<m-item>` | 親に応じた表の行（`client-order-items`／`our-order-items`） | ③ | 列＝ `item-id`・`item-name`・`price`/`cost`・`quantity`・`status`。`status` は enum 列 |
| `<m-client-order>` | 業務文書ブロック（**§6.2 論点A**）: ヘッダ＝`<dl>`＋明細＝`<table data-type>` | ③ | 発注書番号・客先・発注日はヘッダ側 |
| `<m-supplier-order>`・`<m-our-estimate>`・`<m-supplier-estimate>` | 同上パターン | ③ | 見積2種は明細が無ければ dl のみでも成立 |
| `<m-material>` | `<table data-type="part-materials">` の行 | ③ | 部材手配計算（`/api/required-materials`）が読む |
| `<m-file>` | **カスタム要素のまま残す**（容器＋PDFプレビュー） | ③ | `<embed>` は本文で禁止（削除要素）のため、プレビュー描画にJSが要る。ファイルメタ（`src`/`name`/`ext`）は配線＝属性のまま |
| `<m-child-list>` | 残す（計算ビュー） | ③ | 公開ページでのSEOはサーバー側展開の検討対象（要件定義書 §4.4） |
| `<m-required-materials>` | 残す（計算ビュー・保存されない派生表示） | ③ | 同上 |

移行後にカスタム要素として残るのは **容器・参照・計算ビュー**の3系統だけになる。

### 6.2 論点A: 業務文書ブロックの外形

ヘッダ（1回きりの項目）＋明細（繰り返し）の束をどう包むか。

- **案1（傾き）: `<section data-type="client-order">` で包む**——完全に標準HTML・閲覧ゼロJS。
  ```html
  <section data-type="client-order">
    <dl><dt>発注書番号</dt><dd>PO-A100</dd><dt>発注元</dt><dd>トーア</dd><dt>発注日</dt><dd>2026-06-18</dd></dl>
    <table data-type="client-order-items">
      <tr><th data-field="item-id">品番</th><th data-field="item-name">品名</th>
          <th data-field="quantity">数量</th><th data-field="price">単価</th><th data-field="status">状態</th></tr>
      <tr><td>SHAFT-01</td><td>シャフトA</td><td>10</td><td>8000</td><td>未着手</td></tr>
    </table>
  </section>
  ```
  パーサは `section[data-type]` を1文書ブロックとして読み、直下の `dl` をヘッダ項目、
  `table` を明細として対応付ける（`x/net/html` の走査は現行と同じ要領）。
  `section` はサニタイザで許可済み。
- **案2: 薄いカスタム容器 `<m-order>` で包む**——未定義のカスタム要素でも子は表示される
  ため閲覧JSはほぼ不要だが、標準HTML路線の徹底からは一歩劣り、語彙がコード側に残る。
- 案1を採る場合、[【考察】タグ設計.md](【考察】タグ設計.md) §6 の `<m-field>`（単一項目）は
  **`<dl>` の `dt`/`dd` で代替され、導入不要になる可能性が高い**（タグ設計 §6 の再考点）。

### 6.3 移行の機構

- **一度きり変換ツールを基本**とする: サーバー側で全ページを走査し、`m-*` → 新形式へ
  テキスト変換 → `SyncIndex` 再同期（DB再構築と同じ流儀・実行前にバックアップ）。
  正本がファイルなので、変換の検証は「**変換前後で `Sync()` の抽出結果が一致する**」ことを
  テストで固定できる。
- 読み取りの両対応（旧 `m-item` と新形式を同時に受けるパーサ）は、変換ツールが安定するまでの
  **短期の保険**に留める（恒久両対応は語彙の単一正本に反する）。

### 6.4 実装順（縦切り案）

1. **新語彙だけで新機構を稼働**——①コード内レジストリ＋②汎用索引＋汎用表エディタv1
   （セル編集・行操作）を、既存9要素に**一切触れず**新形式（例: 検査記録）で end-to-end 動作。
   サニタイザは `data-type`/`data-field` の属性名許可のみ追加。
2. **計算に絡まないものから移行**——`<m-tag>`→`<dl>`（`page_tags` の同期元切り替え）、
   `<m-material>`→表（部材手配計算の読み先を切り替え）。
3. **受発注4種＋参照追従を一括**——論点A確定後、`<m-item>` 統合・`<m-quote>`・参照追従JOINと
   まとめて（[【考察】タグ設計.md](【考察】タグ設計.md) §8 の方針どおり）。

### 6.5 未決事項

- **論点A**（§6.2: `section` か薄い容器か）と、ヘッダ `<dl>` に `data-type` を付けるか
  （親 `section` が意味を与えるなら不要か）。
- **型付き dl の項目キー**——§5「列の鍵」の規則を dl にも延長すれば
  「`data-field` があればその値、無ければ `dt` の表示文字」となり、受発注ヘッダ（③計算形式）
  だけ `<dd data-field="order-no">` を自動付与、自由語彙の `tags` は表示文字のまま、で
  解ける見込み。論点Aの確定時に最終決定する。
- 表の**行識別とブロック単位保存**の関係（表全体が1ブロック＝`data-id` 1つでよいか、
  セル編集の差分送信粒度）。
- **②汎用索引の詳細設計**——縦持ち・完全正規化と、正規化値の併記（見出し語からの型推論で
  解釈できた値だけ・生テキスト正本）は方針決定済み（§5）。残る詳細: 語→型辞書の初期内容と
  パース規則（`¥8,000`・`8,000円`・全角数字・日付表記のゆれ）、テーブル分割
  （行/フィールドの2テーブルか1テーブルか）。**後日検討**（2026-08-16 ユーザー指示）。
- レジストリの定義スキーマの詳細（**サンプルスキーマで実装先行と決定済み**・§5）。
  実運用スキーマ確定時に決める残り: 改名の扱い（別名リストを持つか改名禁止か）・
  列型 `enum` の閉/開・`required` 等の付加属性。
- 変換ツールの適用範囲（ローカル `data/` のみか、実環境の既存データがあるか）。
