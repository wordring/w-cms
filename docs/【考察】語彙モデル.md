# 【考察】語彙モデル

> 状態: **実装中（縦切り第1段まで実装済み・2026-08-17）**。本書は語彙（文書の意味づけ）の設計の正本——

> 決定ログを扱う。要件レベルの要約は [要件定義書.md](要件定義書.md) §2.5、現行実装の語彙は
> [【一覧】カスタムタグ.md](【一覧】カスタムタグ.md)。

## 1. 背景と目的

2026-08-16 の前提変更——語彙100種規模・一般公開ウェブサイト用途——により、
「新しいタグ＝新しいGoプラグイン＝新しいテーブル」という増やし方が成立しなくなった
（開発者がボトルネックになり、公開ページはカスタム要素の描画にJSを要する）。

本書は2つの問いに答える。

1. **マークアップをどう書くか**——どのデータを属性に置き、どれを要素の中身（テキスト）に
   置くか。現行実装はほぼ全データを属性に持ち、表示文字はテンプレートが属性から生成して
   いるが、これが contenteditable のぎこちなさ・XSS・生HTMLの読みにくさの原因になっている。
2. **語彙をどう増やすか**——100種規模でも追加コストと保守が破綻しない拡張機構。

## 2. マークアップの原則

> **役割・参照・内部フラグ → 属性。見える値（自由文も数値も）→ 要素の中身（テキスト）。
> 機械可読性は「構造（表の列＝役割）」で担保し、値を属性に隠さない。**

判断の早道: **「その値は文書として画面に出るか？」→ 出るなら中身。出ない配線だけ属性。**
数量・単価も人が読み書きし表示されるので中身（標準HTMLの表＝列見出しが役割、セルが値、と同じ）。

| 中身（テキスト・人が読み書き・**表示される**） | 属性（**表示されない**機械的な配線） |
|---|---|
| 発注書番号・客先・発注日、品番・品名・数量・単価・納期・状態（表のセル）、タグの名前と値 | ページID参照（`<m-quote ref>`・`受信元`・`前版`）、役割マーカー（`data-type`/`data-field`）、内部フラグ |

さらに一段進めて、**機械属性も「見える文字で足りるなら書かない」**:

> **見える文字が既定、機械属性は例外。**
> 列の**鍵** ＝ `data-field` があればその値、無ければ見出しテキスト（trim後の textContent）。
> 列の**型** ＝ `data-type` があればその型、無ければ見出し語から推論（`金額`→通貨 等）。
> 機械属性を書くのは③計算形式（§4）だけで、レジストリからの骨格生成時にエディタが
> 自動付与する。人は書かない・見ない。**例外が発動している箇所は編集モードで
> ハイátハイライトし、見えている文字が鍵・型として使われていないことを示す**（§5.1）。

この向きの利点:

1. **contenteditable と素直に噛み合う**。表のセルを直接編集でき、「入力欄→属性へ書き戻し」の
   配線が消える。
2. **XSS が構造的に起きにくい**。表示文字を属性→`String.replace` でテンプレートに差す経路
   （実際に保存型XSSを生み、2026-08-04 に `escapeAttr` の徹底で塞いだ。[コンセプト.md](コンセプト.md)
   参照）が不要になり、**テキストノードは DOM が自動エスケープ**するため、エスケープの
   掛け忘れという失敗の余地が消える。
3. **生HTML（正本）が自己説明的**。数量も実テキストとして `data/master` に現れ、grep/diff が効く。
4. **見た目＝文書**。発注書の画面表示がそのまま PDF の表と一致する。
5. **公開ページで閲覧ゼロJS**（§3）。

## 3. 語彙の3分類

| 種類 | 例 | 増やすときのコスト |
|---|---|---|
| **標準HTML** | 見出し・段落・リスト・表・画像… | 増やさない（コアの許可リストで固定） |
| **マーカー付き標準HTML（記録）** | 繰り返し明細＝`<table data-type="…">`、名前:値＝`<dl data-type="…">` | **語彙レジストリへの宣言1件（データ）** |
| **マーカー付き標準HTML（動的）** | 計算ビュー・ファイル容器・ページ参照（マーカーの具体設計は §10 未決） | 計算プラグイン（Goコード＝③） |

**カスタム要素（Web Components・`<m-*>`）は廃止する（2026-08-17 決定・§9）。**
語彙は標準HTML＋`data-*` に**完全統一**し、動的な振る舞いは**編集モードのクローム**（エディタ）と
**閲覧ビューのエンハンサ**（マーカー要素を見つけて振る舞いを付けるバニラJS）／
**サーバー事前描画**が担う。理由: ①公開ページで**閲覧ゼロJS**（計算ビューもサーバー事前描画で
SEOが自然に解ける）②生HTMLの自己説明性 ③語彙の増加コストの最小化
④テンプレート機構（`fetch`＋文字列置換＋`innerHTML`）が消え、**`escapeAttr` の規律に頼る
XSS経路と、テンプレートの `style=`（CSP strict 化の最後の障害）が構造的に消える。
現行実装のカスタム要素10種は移行（§8）で撤去する。**新しいカスタム要素は今後作らない（即時発効）。**

マーカーは `class` でなく **`data-*`**: ①サニタイザの `class` 全面拒否
（[本文サニタイズ設計.md](本文サニタイズ設計.md) §5.4。本文はシェルと同一DOMに合成される）に
例外を作らない——`data-*` には `data-id` の前例と `globalAttributes` の仕組みがある
②見た目のフック（class）と機械可読の役割（data-*）の分離——デザイン都合の改名がデータ破壊に
ならない ③シェルの CSS/JS セレクタと衝突しない。装飾は `table[data-type="…"]` の
属性セレクタで当てられる。

**用途と要素の使い分け:**

| 用途 | 形 | 例 |
|---|---|---|
| 繰り返し明細（行×列） | `<table data-type="…">`（§5.1） | 受注明細・部材リスト・検査記録 |
| 名前:値の組（ブロック内の単一項目・ページ横断メタ） | `<dl>`（§5.3） | 発注書番号・希望納期・顧客名 |
| ファイルの容器 | 標準HTMLの容器マーカー（現行 `<m-file>` から移行。設計未決・§10） | PDF原本＋中身の業務ブロック |
| 他ページへの参照（表示されない配線） | 参照マーカー（例: `<blockquote data-ref="000123">`。設計未決・§10） | 案件ハブ・受信元・前版 |
| サーバー計算の表示（保存されない派生） | ビューマーカー＋サーバー事前描画／エンハンサ（現行 `m-child-list`・`m-required-materials` から移行。設計未決・§10） | 手配状況リスト・進捗ボード |
| 写真・画像 | 標準HTML `<img>`（語彙ではなく内容） | 現場写真・図版 |

「状態」は2概念を区別する: **明細の進捗**（行ごと）は表のセル（表示される値＝中身）、
**ページ状態**（`未確認`/`取消`/`廃版` 等）はページ横断メタ（`dl` の名前:値）。

## 4. 語彙と拡張の3層モデル

**「語彙を増やす」と「計算を作る」を別の作業に分離する。**

| 層 | 実体 | 変更する人 | 担うもの |
|---|---|---|---|
| **① 語彙レジストリ** | 宣言データ | 管理者（将来は利用者） | `data-type` 形式の定義: 名前・表示名・分類・アイコン・要素種別（table/dl）・列（`data-field`・型・ラベル・許可値）・雛形。語→型の推論辞書（§5.1）もここ |
| **② 汎用索引** | コアのコード（1実装） | — | 全 `table[data-type]`/`dl[data-type]` を汎用テーブルへ同期（`page_tags` の一般化・完全正規化の縦持ち）。検索・単純集計 |
| **③ 計算プラグイン** | Goコード（少数） | 開発者 | 型付きテーブル＋計算ロジック（部材手配・利益・進捗・参照追従）・取り込み変換（PDF/画像→表・`.eml`→通信記録）・集計API・外部投入API |

- **追加コストの段差**: 記録・表示だけの語彙（100種の大半）＝①の宣言1件。
  計算が要る語彙だけが③の開発案件。プラグインは「1**計算**ユースケース＝1プラグイン」へ
  意味が狭まり、語彙の増殖から切り離される。
- **語彙の単一正本**: ①のレジストリと③のプラグイン宣言（計算型の列定義は `Sync()` と同じ
  宣言から導く）を合成し、単一のAPI（`/api/tag-schema` の拡張）でエディタ・タグ一覧の
  ドキュメント生成へ届ける。
- **安全性の分離（要）**: サニタイザの許可リスト（要素・属性名）は従来どおり**コードで固定**し、
  `data-type`/`data-field` は属性**名**だけを要素限定（`table`・`dl`・`th`／`th`・`dd`）で許可、
  **値は不活性な文字列**として検査しない。レジストリは編集支援と検証の語彙であって
  **安全性の門ではない**。この分離があるから、将来レジストリを実行時編集可能（管理UI・
  語彙定義ページ）にしても危険な要素は増やせない。
- ②の汎用索引にも「ファイルから再生成できないデータを持たせない」不変条件
  （[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §8.1）を適用する。

## 5. 表と定義リストの設計

### 5.1 自己記述テーブル

**列の役割・型は見出し行が運び、セルは値そのもの。** 文書自身がスキーマを携帯するため、
レジストリが読めなくても既存文書の閲覧・編集は壊れない（正本＝ファイルの自立性の表版）。

```html
<!-- 記録だけの形式: 機械属性なし。鍵＝見出しテキスト、型＝見出し語から推論 -->
<table data-type="inspection-record">
  <tr><th>品番</th><th>判定</th><th>検査写真</th><th>検査日</th></tr>
  <tr><td>SHAFT-01</td><td>合格</td><td><img src="p1.jpg" alt=""></td><td>2026-08-10</td></tr>
</table>

<!-- 計算形式（③）: エディタが骨格生成時に data-field を自動付与 -->
<table data-type="client-order-items">
  <tr><th data-field="item-id">品番</th><th data-field="quantity">数量</th>
      <th data-field="price">単価</th><th data-field="status">状態</th></tr>
  <tr><td>SHAFT-01</td><td>10</td><td>8000</td><td>未着手</td></tr>
</table>
```

- **鍵**: `data-field` があればその値、無ければ見出しテキスト。同一表内の見出し重複は
  保存時に警告。表示ラベルと機械キーの分離が要るのは③だけ（`単価`→`単価（税抜）` と
  改名しても `Sync()` が壊れない）。記録だけの形式は改名しても壊れない——②汎用索引は
  固定スキーマを持たず、`<m-tag>` の自由語彙と同じ扱い。
- **型**: 語→型の推論辞書（`金額`/`単価`→通貨、`数量`→数値、`納期`/`検査日`→日付…）が既定。
  `th data-type` の明示と③のレジストリ宣言が推論に優先する。推論した型で
  ①エディタが入力を**検証して通知**する（通貨列に通貨以外→背景を赤く。**拒否はしない**——
  自由な記述をシステムが認識する、というコア・コンセプトを壊さないため）
  ②汎用索引が**正規化値を併記**する（`¥8,000`→`8000`。解釈できた値だけ。生テキストが常に正本）。
- **機械属性のハイライト**: `data-field`/`data-type` 付きの `th`・`dd` は編集モードで背景を
  ハイライトし、見えている文字が鍵・型として使われていないことを示す（型不一致の赤とは別の色）。
  実装は CSS の属性セレクタ（`th[data-field]` 等）——上書きを起こす属性自体が印のトリガーに
  なるため、表示と実態がずれない。閲覧・公開ページには出さない。

### 5.2 汎用表エディタ

`data-type` 付きの表・定義リストの編集機能は、**型の数に対して不変の汎用実装**とする。
型ごとの JavaScript は書かない。

- セルの直接編集（contenteditable）・行の追加/削除/並べ替え。
- 列型に応じた入力補助（`number`/`date`/`enum` ドロップダウン/`image`＝セル内への添付画像挿入）。
  v1 は素のテキストセル＋行操作だけでよく、補助は段階的に足す。
- **編集は2面ある**: 値（中身・表示される）は**インライン**で、役割・型・参照（属性・
  表示されない配線）は**列設定UI（ポップオーバ）**で編集する。contenteditable はテキストしか
  触れないため、属性の編集口は別に要る。
- どの編集も既存のオートセーブ（差分検出→`/api/save-block`）に乗せる。シリアライザは
  編集クロームを剥がし、クリーンな `<table data-type>`（ヘッダ＋データ行）を残す。
- 合計・受注残のような**他セルから計算される表示**はサーバー側の計算ビュー（③）に寄せ、
  エディタ内のリアクティブ計算は持たない（道具の追加を避ける。必要になったら再検討）。

### 5.3 定義リスト（名前:値）

ページ横断メタ（現 `<m-tag>` の後継）とブロック内の単一項目は `<dl>` で表す。

```html
<dl data-type="tags">
  <dt>希望納期</dt><dd>2026-07-10</dd>
  <dt>納入場所</dt><dd>本社工場</dd><dd>第二倉庫</dd>  <!-- 多値 -->
</dl>
```

- 名前も値も**表示される実テキスト**。名前は自由語（スキーマキーではない）なので
  `dt` の表示文字＝鍵でよい。多値は `dt` の繰り返し／複数 `dd`（`page_tags` が主キーを
  持たない現行設計と整合）。
- 素の `<dl>`（用語集など通常の文章）と区別するため、索引へ同期するのは `data-type` 付き
  だけ（オプトイン。表と同じ規約）。
- 役割が固定の dl（受発注ヘッダ等の③計算形式）は §5.1 と同じ規則——
  `<dd data-field="order-no">` を骨格生成時に自動付与する見込み（論点Aとあわせて最終決定）。
- **表示されない配線**（`受信元`・`前版` 等）は dl へ移せない。参照専用要素
  （`<m-quote ref>` 系）として分離する（[【考察】通信記録処理.md](【考察】通信記録処理.md) §9.1 と合流）。

## 6. 挿入経路と不変条件

構造化ブロックが本文へ入る経路の全体像。**不変条件: どの経路から入っても出口は同じ**——
同じ語彙・同じ保存時サニタイズと検証・同じ編集ロックを通る。経路はプロデューサーの違いに
すぎず、語彙の単一正本を迂回する経路を作らない。

| 経路 | 例 | 状態 |
|---|---|---|
| 明示挿入 | スラッシュメニュー → レジストリの列定義から骨格生成 | 実装済み（現行9種＝手書き項目、レジストリの語彙＝動的生成・骨格生成とも実装済み。メニュー全体の再設計は別課題） |
| 貼り付け変換 | Excel/TSV → 表、他アプリHTML → サニタイズ受け入れ | HTML貼り付けは実装済み・表変換は検討中 |
| ファイル取り込み変換 | 発注書PDF → 明細表（**実装済み**・Gemini）、撮影画像 → 表・`.eml` → 通信記録（構想） | 一部実装済み |
| デバイス起点 | カメラ写真の挿入（[要件定義書.md](要件定義書.md) §2.6）、バーコード/QR → 品番セル（構想） | 未実装 |
| 他ページ参照 | 子ページ一覧（実装済み）、`<m-quote ref>`（構想） | 一部実装済み |
| 計算ビュー | `<m-required-materials>`——内容は閲覧時にAPIから取得し**保存されない**派生表示 | 実装済み |
| 雛形・複製 | ページ雛形・ブロック雛形（製品マスタの `必須項目` 規約の一般化） | 構想 |
| エディタ外生成 | 受信箱 fan-out・外部投入API・一括移行 | 構想 |

経路ごとに③プラグインが宣言しうる能力が対応する（明示挿入＝メニュー項目と骨格／
取り込み変換＝ファイル種→変換／計算ビュー＝集計API…）。①②で賄えない経路能力だけが
③のインターフェースに載る。

## 7. エディタの形式知識の3原則

1. **新規挿入時**——列定義の全体が要る。レジストリからAPI経由で受け取る
   （エディタに手書きの形式リストを置かない）。骨格は列定義から機械的に生成する。
2. **既存ブロックの編集時**——**レジストリ不要**。鍵と型は文書自身（見出し行・§5.1）が
   運ぶため、レジストリが読めなくても既存文書の編集は壊れない。
3. **入力補助・検証**——レジストリがあれば向上する（enum の選択肢・未知の `data-field` への
   警告）。無くても編集は可能。

エディタの実装は汎用表エディタ1つ（§5.2）で、**型の数に対して不変**。型ごとの JavaScript が
要るのは③の特殊UI（PDFドロップ・集計表示・参照ピッカー）だけ——これらも**カスタム要素では
なくエンハンサ**（マーカー要素に配線するバニラJS）として実装する（§9）。DOM生成が要る箇所は
殻に置いた `<template>` ＋ `cloneNode` ＋ `textContent` 代入で行い（DOMが自動エスケープする）、
文字列置換＋`innerHTML` のテンプレート機構は持ち込まない。**追加のライブラリは不要**
（必要な基盤は `querySelectorAll`・`addEventListener`・既存の `MutationObserver`・`<template>`）。

## 8. 標準HTMLへの移行

### 8.1 現行9要素の移行マップ

| 現行 | 移行先 | 層 | 備考 |
|---|---|---|---|
| `<m-tag>`（可視メタ） | `<dl data-type="tags">` | ①＋② | 多値は `dt` 繰り返し／複数 `dd`。`部品番号`・`必須項目` 等の特別扱いは `page_tags`（または汎用索引）経由で不変 |
| `<m-tag>`（配線: `受信元`・`前版`） | **参照マーカー**（例: `<blockquote data-ref>`。設計未決・§10） | ③ | 表示されない配線は dl へ移せない |
| `<m-item>` | 親に応じた表の行（`client-order-items`／`our-order-items`） | ③ | `status` は enum 列 |
| `<m-client-order>` | 業務文書ブロック（**§8.2 論点A**）: ヘッダ＝`<dl>`＋明細＝`<table data-type>` | ③ | 発注書番号・客先・発注日はヘッダ側 |
| `<m-supplier-order>`・`<m-our-estimate>`・`<m-supplier-estimate>` | 同上パターン | ③ | 見積2種は明細が無ければ dl のみでも成立 |
| `<m-material>` | `<table data-type="part-materials">` の行 | ③ | 部材手配計算（`/api/required-materials`）が読む |
| `<m-file>` | 標準HTMLの**容器マーカー**＋編集クローム（設計未決・§10） | ③ | `<embed>` は本文で禁止（削除要素）のため、PDFプレビューは**サーバー合成時の埋め込み**かエンハンサ描画（設計未決）。ファイルメタ（`src`/`name`/`ext`）は配線＝属性のまま |
| `<m-child-list>` | **ビューマーカー**＋サーバー事前描画／エンハンサ（設計未決・§10） | ③ | 公開ページはサーバー事前描画で閲覧ゼロJS（要件定義書 §4.4 のSEO検討の解） |
| `<m-required-materials>` | 同上（保存されない派生表示） | ③ | 同上 |

**移行の到達点はカスタム要素ゼロ**（§9）。最後まで残る動的3系統（容器・参照・計算ビュー）も
標準HTML＋マーカーへ置き換え、`web-components.js`・`assets/templates/` を**撤去**する。

### 8.2 論点A: 業務文書ブロックの外形（未決）

ヘッダ（1回きりの項目）＋明細（繰り返し）の束をどう包むか。

- **案1（傾き）: `<section data-type="client-order">` で包む**——完全に標準HTML・閲覧ゼロJS。
  ```html
  <section data-type="client-order">
    <dl><dt>発注書番号</dt><dd>PO-A100</dd><dt>発注元</dt><dd>トーア</dd><dt>発注日</dt><dd>2026-06-18</dd></dl>
    <table data-type="client-order-items">
      <tr><th data-field="item-id">品番</th><th data-field="item-name">品名</th>
          <th data-field="quantity">数量</th><th data-field="price">単価</th><th data-field="status">状態</th></tr>
      <tr><td>SHAFT-01</td><td>シャフトA</td><td>10</td><td>8000</td><td>未着手</td></tr>
    </table>
  </section>
  ```
  パーサは `section[data-type]` を1文書ブロックとして読み、直下の `dl` をヘッダ項目、
  `table` を明細として対応付ける。`section` はサニタイザで許可済み（`data-type` の許可追加は
  この案の採用時）。
- **案2: 薄いカスタム容器で包む**——未定義のカスタム要素でも子は表示されるため閲覧JSは
  ほぼ不要だが、標準HTML路線の徹底からは一歩劣り、語彙がコード側に残る。

### 8.3 移行の機構

- **一度きり変換ツールを基本**とする: サーバー側で全ページを走査し、`m-*` → 新形式へ
  変換 → `SyncIndex` 再同期（DB再構築と同じ流儀・実行前にバックアップ）。
  検証は「**変換前後で `Sync()` の抽出結果が一致する**」ことをテストで固定できる
  （正本がファイルであることの利点）。
- 読み取りの両対応（旧 `m-item` と新形式を同時に受けるパーサ）は、変換ツールが安定するまでの
  短期の保険に留める（恒久両対応は語彙の単一正本に反する）。

### 8.4 実装順（縦切り）

1. **新語彙だけで新機構を稼働**——①コード内レジストリ＋②汎用索引＋汎用表エディタv1
   （セル編集・行操作）を、既存9要素に**一切触れず**新形式（例: 検査記録）で end-to-end 動作。
   サニタイザは `data-type`/`data-field` の属性名許可（要素限定）のみ追加。
   → **実装済み（2026-08-17）**。①＝[vocab.go](../internal/cms/vocab.go)、
   ②＝[vocab_index.go](../internal/cms/vocab_index.go)（縦持ち `vocab_index` テーブル）、
   エディタ＝スラッシュメニューのレジストリ駆動項目・骨格生成・行操作ツールバー・
   機械属性ハイライト（[app.js](../assets/app.js)）。未知 data-type の保存時告知
   （`unknown_types`）と正規化値の併記も実装。詳細は [変更履歴.md](変更履歴.md)
   2026-08-17 の節。
   → **§5.2 の段階的追加も実施（2026-08-19）**: 列操作・列設定ポップオーバ
   （列型の明示＝属性側の編集口）・dl の項目操作・型不一致の赤印（推論辞書は
   `/api/tag-schema` の `type_inference` で配布）・enum の選択肢メニュー。
   残りは date/image の入力補助のみ（image は画像アップロードの実装待ち）。
   詳細は [変更履歴.md](変更履歴.md) 2026-08-19 の節。
2. **計算に絡まないものから移行**——`<m-tag>`→`<dl>`（`page_tags` の同期元切り替え）、
   `<m-material>`→表（部材手配計算の読み先切り替え）。
3. **受発注4種＋参照追従を一括**——論点A確定後、`<m-item>` 統合・参照マーカー・
   参照追従JOIN・[【考察】通信記録処理.md](【考察】通信記録処理.md) §2.5 とまとめて。
4. **動的3系統の置換と Web Components 機構の撤去**——容器・参照・計算ビューを
   マーカー＋エンハンサ／サーバー事前描画へ置き換え、`web-components.js` と
   `assets/templates/` を削除する。**CSP strict 化（`'unsafe-inline'` の除去）はここで完了**
   （インライン `style=` の発生源が消えるため。[【考察】CSP強化.md](【考察】CSP強化.md) §4）。
   `m-file` は受発注と絡むため 3 と一括にしてもよい。

## 9. 決定ログ（2026-08-16）

| 判断 | 決定 | 理由 |
|---|---|---|
| マーカーの属性 | `class` でなく **`data-*`** | `class` 全面拒否に例外を作らない・見た目と役割の分離・シェルDOMと衝突しない（§3） |
| レジストリの置き場（v1） | **Goコード内の宣言テーブル**から始める | 定義スキーマが固まる前にDB化すると移行が二度手間。(b)管理UIのDB → (c)語彙定義ページへ段階的に育てる。v1の間は語彙追加に再ビルドが要る（「再デプロイ不要」は(b)以降の目標） |
| 未知の `data-type` | **通す**（＋保存時に「未定義の種別」と通知） | 値は不活性で害がなく、②の索引に載るだけ。落とす方式はレジストリを安全性の門に変質させる。通知は拒否でなく告知（エコーバックの流儀） |
| 移行の段取り | **まず標準HTMLへの移行の検討から始める**（§8） | 移行マップと外形の論点を先に固めてから実装順を決める |
| レジストリの定義スキーマ | **サンプルスキーマで実装を先行**し、動いてから実運用スキーマを確定 | 汎用表エディタ・②索引・骨格生成を実際に駆動して過不足を知るほうが早い。v1がコード内宣言なのでスキーマ変更コストが最小のうちに試せる |
| 識別子の文字種 | `data-type`・`data-field` の値は **kebab-case** | HTML属性値・URL・Goの文字列リテラルのどこでも引用符や変換が要らない |
| 識別子の一意性 | **`data-type` はレジストリ全体で一意**。`data-field` は**（`data-type`, `data-field`）のセットで一意** | 形式の識別は `data-type` が担う。フィールドは形式が名前空間。同名 `data-field` の形式間再利用（`item-id`＝品番）は**推奨規約**で機械は強制しない——形式横断の名寄せはこの規約に依る |
| DBの設計姿勢 | **完全な正規化**——②汎用索引は縦持ちとし、検索の速さより**定義変更への強さ**を優先（詳細は後日検討） | 小規模事業者用でデータ総数は少なく性能は問題にならない。縦持ちなら形式の定義変更が DBスキーマ変更を一切要求しない |
| 列の鍵 | **`data-field` があればその値、無ければ見出しテキスト**。`data-field` は③計算形式だけ（エディタが自動付与） | 見出しに `金額` とあるのに `data-field="amount"` を重ねる必要はない。機械キーが要るのは `Sync()` というプログラム契約がある③のみ |
| 列の型と正規化 | **見出し語から型を推論**（語→型辞書はレジストリの一部）。検証は**通知**・正規化値は**併記**（生テキスト正本）。`th data-type` と③宣言が推論に優先 | 鍵と同じく「見える文字が既定・機械属性は例外」に統一。検証を通知に留めるのは自由な記述の原則を壊さないため |
| 機械属性の可視化 | 属性が見出しに優先する箇所は**編集モードで背景ハイライト**（型不一致の赤とは別色） | 「見える文字が既定」を守るには例外の発動も見える必要がある。CSS属性セレクタで実装し表示と実態がずれない |
| `data-type`/`data-field` の許可範囲 | **要素限定**: `data-type`→`table`・`dl`・`th`、`data-field`→`th`・`dd`（`section` は論点A採用時） | 必要外の要素に許す理由がない。「属性は厳格」の維持。全要素共通の例外は `data-id` のみ |
| **Web Components（カスタム要素）の廃止**（2026-08-17） | `<m-*>` を**全廃**し、語彙を標準HTML＋`data-*` に完全統一する。動的な振る舞いは編集モードのクローム（エディタ）＋閲覧ビューのエンハンサ（バニラJS）＋サーバー事前描画。DOM生成は殻の `<template>`＋`cloneNode`＋`textContent` 代入（自動エスケープ）。**新しいカスタム要素は作らない（即時発効）**。`lit` の再評価は打ち切り。**追加ライブラリは不要**（将来の例外候補はバーコード読取の Safari 対応のみ・その機能の判断時に別途） | 採用理由の3本柱（保存形式＝DOM・連携の単純さ・contenteditable共存）は**バニラJS＋素のDOMの性質**であり、`customElements` 固有ではない。残る価値は自動ライフサイクルだけで、既存の `MutationObserver`・初期化パスで代替可。廃止で消えるもの: `escapeAttr` 規律頼みのXSS経路（実際に発火した）・テンプレートの `style=`（CSP strict の最後の障害）・グローバル結合と全体再描画（コンセプト既知の課題）・`lit` 問題。計算ビューのSEOはサーバー事前描画（Goの得意技）で自然に解ける |

## 11. 経緯

2026-08-16 のユーザー提案「受注表は HTML の `table`＋class で用途を決めては」を起点に、
マーカーを `data-*` へ修正して標準HTML路線を採用。続く検討（`<m-tag>` の定義リスト化 →
挿入経路の列挙 → プラグインの要不要 → エディタの形式知識 → カメラ写真の位置づけ →
鍵・型の既定）で3層モデルと「見える文字が既定・機械属性は例外」の原理に到達した。
旧 `【考察】タグ設計.md`（2026-06〜08。値を中身へ移す原則を `<m-field>`/`<m-table>` という
カスタム要素で実現する案）は、原則部分（§2）を本書が引き継ぎ、実現手段を標準HTMLへ
差し替えたうえで廃止した。2026-08-17 には Web Components の採用妥当性を再検討し、
採用理由がカスタム要素固有ではないことの確認と代替（エンハンサ・`<template>` 方式・
追加ライブラリ不要）の検討を経て、**全廃を決定**した（§9）。
各決定の日付と経緯は [変更履歴.md](変更履歴.md) 2026-08-16〜17 の各節。
