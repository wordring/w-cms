# 【考察】発注書から受注明細へ

> **検討中・未実装**（2026-09-20）。**決定は済んでいます**——この文書は着手前の設計メモで、
> 実装したら `【考察】` を外し、確定した仕様は各設計書へ移します。
>
> 一言でいうと: **各社ばらばらの発注書を、弊社の1つの様式へ落とし込む。落とし込み方は
> 取引先ごとに覚える。同一性はページ番号で持つ。**
>
> ⚠ **この文書を書いた同じ日に、土台が2つ入りました**（§3 の ③ と ②）——
> **登録された語彙だけDBに入る**（`87ff0f4`）と、**表は `<caption>` で形式を名乗れる**

## 0. 何の話か

ユーザー:「弊社が必要なのは、**品番、品名、単価、数量、納期**などです。顧客の発注書から
いかにココへ落とし込むかということになります」。

発注書は各社に様式があります。列の名前も並びも違う（`員数`／`数量`、`納入日`／`納期`）。
それを弊社の1つの表へ写すのが本題です。

そして**もっと難しい問題**がその下にあります。

> 顧客の発注には図面番号や品名が同じで別の品物の場合があります。これは**文脈から担当者が
> 糸をくみ取る**ので自動化は無理です。そこで**弊社の加工製品番号としてページ番号を使っては
> どうでしょうか？** 加工製品番号を頼りに製造を進めるのです。（ユーザー・2026-09-20）

⚠ **後半は新しい話ではありません**——2026-09-03 に同じ結論が出ています
（「別の製品の図面番号が一致してしまう場合もあり…**社内で識別番号を割り当てるしかありません**」
→「同一性は常にページID、図面番号は探すためのタグ。w-cms は6桁を必ず振るので
『社内で識別番号』は構造として既に満たされている」）。**今回はそれを使う話**です。

## 2. 決めたこと

### 2.1 受注ページには表が2つ載る

ユーザー:「Geminiに単なるOCRをしてもらうとともに、**どの顧客項目が弊社項目に結びつくか
教えてもらう**のが良いのでは？すると、**顧客の表と弊社の表の二つを表示**して頂けると
比較しやすいです」。

```
受注 250715-304
  （タグ: 発注書番号 / 発注元 / 発注日 / 受信元）

  ▼ 顧客の発注書（読んだまま）            ← <details> で畳める
  | 図面No. | 品名           | 員数 | 単価 | 納入日     | 備考       |
  |  K120-1 | ｳｹﾌﾞﾗｹｯﾄ  | 100  | 390  | 2026-10-15 | 材質変更   |

  ■ 受注明細（弊社の項目）
  | 加工製品番号 | 品番 | 品名 | 単価 | 数量 | 納期 | 備考 | 状態 |
```

**原本の写しを残す理由**は、対応が合っているかだけでなく、**OCR が7行全部読めたか・数字を
取り違えていないか**を目で確かめられることです。対応表だけ見せる形ではそこが分かりません。

⚠ **整理したあとも残します**（ユーザー決定）。長くなるので `<details>` で畳めるようにします。
`details`／`summary` は**サニタイズを通ります**
（[htmldoc/sanitize.go:174](../internal/cms/htmldoc/sanitize.go#L174)）——⚠ **素のHTMLだけで
畳めるので、JS も `on*=` も要りません**（CSP strict の下で動き、**公開ページのゼロJSでも畳めます**）。

### 2.2 弊社品番はページ番号

> ⚠ **名前は `弊社品番` になりました**（2026-09-20 ユーザー:「**加工中に番号を使うので**、
> 受注の表に**弊社品番として製造製品のページIDを入れたい**です」）。この文書の初稿では
> `加工製品番号` と書いていました。現場で使う言葉に揃えます。

`弊社品番` の列を弊社の表に置き、**加工製品ページのページ番号**を入れます。型は `ref`
（`cms.ColRef`。既にあります）。

⚠ **`品番` とは別の列にします。**

| 列 | 誰の言葉か |
|---|---|
| `品番` | **顧客の言葉**。先方の発注書に書いてあるもの |
| `弊社品番` | **弊社の識別**。ページ番号。⚠ **加工中に使う番号** |

同じ列に混ぜると、顧客の品番で問い合わせが来たときに引けません。

⚠ **これは 0c（受注明細の見出しが `品番` に化ける件）への答えでもあります**——`図面番号` が
`品番` に置き換わるのが気持ち悪かったのは、**顧客の言葉と弊社の識別が1つの列に混ざっていた**
からでした。

**結ぶのは人です。** ユーザー:「文脈から担当者が糸をくみ取るので自動化は無理」。機械の仕事は
**候補を狭めるところまで**——`受信元` が同じ通信記録ページを指す加工製品ページを並べれば、
発注書と図面は同じメールで届くことが多いので、たいていその中にあります。
**新しいデータは要りません**（`受信元` は全ページが既に持っています）。

### 2.3 列（`備考` を含む）

```
| 弊社品番 | 品番 | 品名 | 単価 | 数量 | 納期 | 備考 | 状態 |
|   ref    | code | text | number | number | date | text | enum |
```

**2026-09-20 に実装済み**（`bdf48d1`）。⚠ **見出しは宣言から組みます**
（`clientOrderItemColumns`）——列を足したのに本文の `<th>` が古いままだと
**宣言と本文が黙ってずれ**、索引は見出しの表示文字で引くので**足した列がどこからも
読めません**。

ユーザー:「表には**「備考」欄**が必要です」。

⚠ **並びは既存4表に揃えました**——`構成部品`・`加工工程`・`購入部品`・`支給部品` は
どれも `{Field: "note", Label: "備考", Type: cms.ColText}` を持ち、**`備考` は `区分`（状態）の
手前**にあります（[ext/subcon/vocab.go](../ext/subcon/vocab.go)）。受注明細だけが持っていませんでした。

⚠ **備考はたぶんこの設計の要です。** §0 の「文脈から担当者が汲み取る」の中身は、多くの場合
備考欄に書いてあります——「材質変更」「前回と同じ」「至急」「改訂あり」。

```
| 加工製品番号 | 品名           | 備考         |
|  000047      | ｳｹﾌﾞﾗｹｯﾄ  | 材質SUS304へ |   ← これを読んで人が結ぶ
|  000063      | ｳｹﾌﾞﾗｹｯﾄ  | 従来品       |   ← 同じ品名・別の物
```

**加工製品番号を選ぶ画面では、備考を並べて見せること。** 見えていないと判断できません。

⚠ **顧客の備考と弊社の備考は別物です**（ユーザー決定）。先方が書いたもの（「材質変更」）と、
こちらの申し送り（「在庫から手配」）は別。**初期値として写し、人が直せる**——他の欄と同じ扱い。

### 2.4 形式の宣言は、見える文字（`<caption>`）へ

ユーザー:「**見た儘が全ての原則**から言って、`data-type` より表の見出し（caption）で
検索できるのが筋では？」。

いまの決め方はこうです（[walk.go:316](../internal/cms/walk.go#L316)）。

```
① data-type 属性          （見えない）
② section の機能見出し    （見える・ただし節で包む必要がある）
```

⚠ **`data-type` へ寄ったのは意図した判断ではなく、副作用でした。** 受注ページはもともと②
でしたが、2026-09-18 に「1文書1ページ」で節をやめたとき**見える印が消え、`data-type` が
肩代わり**しました（変更履歴「節をやめたので表が自分で名乗ります」）。

`<caption>` はその穴をふさぎます——**節で包まずに、表自身が見える名前を持てる**。HTML でも
`caption` は「表の名前」そのものの要素です。

**費用はほぼゼロ**です:

- ⚠ **`<caption>` は既にサニタイズを通ります**（[htmldoc/sanitize.go:190](../internal/cms/htmldoc/sanitize.go#L190)）
- **表示文字→形式を引く関数も既にあります**（`VocabDefByHeading`——②が使っているもの）

```go
if el.Data == "table" {
    if def, ok := VocabDefByHeading(tableCaption(el)); ok {
        return def.Type   //  <caption>受注明細</caption> → client-order-items
    }
}
```

⚠ **①が優先のままなので、既存の本文は1枚も壊れません。** ただし**2つの書き方が併存**します
——**新しく書くものは caption、`data-type` は古い本文のための互換**、と決めます。

⚠ **改名すると形式が変わります**が、これは受け入れ済みの性質です——テンプレート置き場が h1 で
決まるのと同じ（「機能が名前で変わるのは目論見通りです。表示されている言葉が機能を表します」）。

⚠ **`dl`（タグ）は `data-type="tags"` のまま**です。`caption` は表の要素なので使えません。
**表は見える印・タグは見えない印**という非対称が残りますが、2026-08-31 に一度
「セクション外の素の `dl`＝タグ」を試して**「用語：説明」のような普通の定義リストまでDBに
入った**ので撤回した経緯があります。**表には caption という自然な名前の置き場があるが、
定義リストには無い**——その差です。

### 2.5 登録済みの語彙だけDBに入る

ユーザー:「事前に登録されている語彙だけＤＢに入れましょう。**すべての表をＤＢに入れる必要は
ない**と思います」。

⚠ **いまは型が決まらない表も索引に入っています**——`VocabDefByType` が
「未定義でもゼロ値の def で続行」するため（[vocab_index.go:206](../internal/cms/vocab_index.go#L206)）。
**普通の文章の中の表まで、形式名が空のまま入ります**。これは意図した設計ではなく、
気づかれていなかった振る舞いです。

| 表 | いま | 決定後 |
|---|---|---|
| `受注明細`（登録済み） | 入る | 入る |
| **発注書の様式**（対応表） | — | ⚠ **登録が要ります**（機械が引くため） |
| **顧客の発注書**（原本の写し） | 入る | **入らない**——見せるだけ |
| 型が解決しない素の表 | ⚠ 空の形式名で入る | **入らない** |

**顧客の表が入らないのは正しい**——あれは**原本の証拠**であって、検索したいのは弊社の表です。
二重計上の心配も最初から起きません。

⚠ **ワンノート移行とは衝突しません。** 受け皿（`■材料` の下の表）は `VocabDefByHeading` を
通るので**もともと登録を前提**にしていました。移行文書にも「残るのは **■材料 等の言葉を
レジストリの表示名として宣言すること**」とあり、`材料`・`外注加工`・`購入部品`・`支給部品` は
**既に登録済み**です。

### 2.6 表の形式も `settings.json` から足せるようにする

ユーザー決定（2026-09-20）。§2.5 と対になる決定です。

⚠ **これが無いと、要件を1つ落とします**——「運用者が語彙を足せること」は 2026-08-26 の要件
ですが、調べると:

- **タグの語**（`図面番号` の型など）→ `config/settings.json` の `vocabulary` で**足せる**
- **表の形式**（列を持つ `VocabDef`）→ ⚠ **Go のコードにしかない**（`RegisterVocab` を
  呼ぶのはプラグインだけ）

いままでは「登録されていなくても索引に載る」が抜け道になっていましたが、§2.5 でそれを塞ぐので、
**正面の道を開けます**。タグの語と同じく `git pull` で全環境へ届くのも利点です。

⚠ **設定が壊れていたら起動を止める**規律は既存のまま（黙って既定値で上書きすると運用者の語が
消える）。**足したらDB再構築**が要るのも `vocabulary` と同じです。

### 2.7 対応表は `取引先／社名／発注書の様式` ページ

ユーザー:「対応表の置き場は 取引先／社名以下に**ページを作って**はどうでしょう？」。

```
取引先／南北スポーツ機械／発注書の様式

  <table><caption>発注書の様式</caption>
  | 顧客の見出し | 弊社の項目 |
  |   図面No.    |            |   ← 空 ＝ 対応なし
  |   品名       |   品名     |
  |   員数       |   数量     |
  |   納入日     |   納期     |
```

**表ではなくページにする利点が2つ**あります。

1. **ページには版がある。** 対応表は「決定」なので、⚠ **間違えたときに戻せる**のは大きい。
2. **機械の書き込み先が分かれる。** 社名ページは人も書きます。そこへ機械が書くと
   オートセーブと上書きし合います。様式ページを分ければ、触る範囲が閉じます。

⚠ **社名ページに子を1枚足しても壊れません**——`machineNames` は `stage.title IN (…)` で段を
名指しするので、別の題の子は自然に外れます（[ext/subcon/filing.go](../ext/subcon/filing.go)・確認済み）。

**1社に様式が複数あることはあります**（ユーザー）。**1ページに表を複数**置きます。

⚠ **どれを使うかは caption では決めません。** 人が付けた名前（「発注書の様式」「注文請書の
様式」）では、届いたPDFがどちらかを機械は判断できません。**顧客の見出しの組み合わせで選びます**。

```
届いた発注書の見出し:  図面No. / 品名 / 員数 / 納入日
                          ↓ 一致する表を探す
様式①（発注書）        図面No. / 品名 / 員数 / 納入日   ← これ
様式②（注文請書）      受注No. / 品名 / 数量 / 回答納期
```

一致が無ければ Gemini に聞き、人が確定したとき**3つ目の表として足ります**。
**caption は人が読むためのもの**、という役割分担です。

**空欄＝対応なし**（ユーザー決定）。「Gemini が弊社項目に対応する顧客項目を見出せなかった
場合」を空欄が表し、**それ以前に人が見て書き込めば済む**。

### 2.8 ⚠ Gemini はページに書かない

ユーザー:「**Geminiが書き込むというのが分かりませんが**、Geminiの返答を基に、整理の時に
出てくるようなフォームで人間が修正すればよいと思います」。

⚠ **筆者（AI）の設計が間違っていたところです。** 機械がページを書く形を提案しましたが、
正しくは**Gemini の返りはフォームの初期値にすぎず、書くのは人が実行したとき**です。

そしてこれは**このプロジェクトで既に4回繰り返されている形**でした。

| | 機械が出すもの | 人が決める場 |
|---|---|---|
| 加工製品の整理 | 顧客名・装置名称の推奨値 | 整理のフォーム |
| 連絡帳の登録 | 組織の候補 | 行のコンボボックス |
| 受注の整理 | 発注元の候補 | 整理のフォーム |
| **発注書の様式** | **対応の推測** | **整理のフォーム** |

⚠ **この形なら「承認前に間違った対応が定着する」が構造的に起きません**——書く瞬間が人の操作
だけになるからです。機構も1つ減ります。

```
🤖 解析   …… 顧客の表（読んだまま）＋ Gemini の推測で組んだ弊社の表
📁 整理   …… 対応のフォームが出る → 人が直す
              ├─ 弊社の表を組み直す
              └─ 様式ページに覚える
2通目以降 …… 覚えた様式で組むので、フォームは確認だけ（たいてい素通り）
```

整理が**直した値を索引にも書き戻す**のは既にやっていることなので（2026-09-11）、
置き場所としても自然です。
