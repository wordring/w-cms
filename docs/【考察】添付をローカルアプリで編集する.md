# 【考察】添付をローカルアプリで編集する

> 2026-09-07。ユーザー:「サーバー上のCADファイルや画像ファイルなどをローカルのアプリで
> 編集する方法を考察してください。ブラウザでファイルをクリックするとローカルのアプリが
> 立ち上がり、Ctrl＋Sで上書き保存されるような使い方をワンノートでしています」。
>
> 関連: [【考察】添付ファイルの表示と操作.md](【考察】添付ファイルの表示と操作.md)（表示・
> コンテキストメニュー）／[要件定義書.md](要件定義書.md) §5（保存した画像の編集）。
> **結論は §6**——WebDAV を第一候補とし、まず読み取り専用で試す。

## 1. 何が欲しいのか

ワンノートの体験を分解すると、**4つの動作が繋がっている**ことが分かります。

```
①クリック → ②ローカルのアプリが開く → ③Ctrl+S → ④サーバー側が新しくなる
```

いま w-cms にあるのは①と、②の半分（ダウンロード）だけです。**③と④が無い**——
ダウンロードしたファイルはブラウザの保存先にあり、編集しても誰も見ていません。
人が手で再アップロードすれば繋がりますが、それは「Ctrl+S」ではありません。

**AutoCAD・SolidWorks・画像編集ソフトのどれでも**同じ形で動く必要があります。
拡張子ごとに違う仕掛けを作ると、対応表を永久に育てることになります。

## 2. 取りうる道は4つ

### A. WebDAV——サーバーをネットワークドライブとして見せる

Windows のエクスプローラで「ネットワークドライブの割り当て」をすると、
`\\localhost@8080\DavWWWRoot\...` のようなパスでファイルが見えます。**そこから開いた
ファイルは、アプリにとって普通のファイル**なので、Ctrl+S が素直に効きます。

- **①②③④が全部つながります。** 特別な仕掛けはブラウザ側にも要りません。
- **実装の材料は既にあります**——`golang.org/x/net/webdav` は**いま使っている依存の中**
  （`x/net` は HTML パースで既に直接依存）。**新しいモジュールはゼロ**で、開発方針の
  「外部依存の最小化」に抵触しません。
- 認証は**HTTPの世界の話**なので、セッションCookieではなく Basic か Digest になります。

**Windows のWebDAVクライアントには既知の癖があります**（実装前に確かめること）:

| 癖 | 影響 | 逃げ道 |
|---|---|---|
| 平文HTTPでの Basic 認証を既定で拒否 | ログインできない | HTTPS にする（本番は要る）／レジストリ `BasicAuthLevel`（＝各PCの設定・避けたい） |
| 既定の最大ファイルサイズが 50MB | 大きなCADが開けない | レジストリ `FileSizeLimitInBytes`（同上） |
| `WebClient` サービスが止まっていることがある | 割り当てできない | サービスを自動起動に |
| 認証が切れると無言で失敗する | 保存できたように見えて消える | **要検証**（いちばん怖い） |

### B. カスタムURLスキーム＋常駐ヘルパー（`w-cms://edit?...`）

各PCに小さなヘルパーを入れ、`w-cms://` を登録します。ブラウザでクリックすると
ヘルパーが起動し、①一時フォルダへ落とし、②既定のアプリで開き、③ファイルの変更を
見張って（`fsnotify` 相当）、④変わったらサーバーへ PUT する。

Confluence・Nextcloud・Jira の「デスクトップアプリで編集」はこの形です。

- **狙った体験にいちばん近い**。認証も w-cms のセッションを引き継げます。
- **各PCへインストールが要ります**（レジストリ登録つき）。ヘルパーは Go で書けるので
  モジュールは増えませんが、**配布するものが1つ増えます**。
- **攻撃面が増えます**——`w-cms://` はどのWebページからでも叩けるので、ヘルパーは
  **URLのホストを検証し、使い捨ての鍵を要求する**必要があります。ここを間違えると
  「任意のサイトが社内ファイルを書き換えられる口」になります。

### C. File System Access API（ブラウザだけで完結）

Chromium 系なら `showSaveFilePicker` でローカルのファイルハンドルを得て、
**ブラウザから書き戻せます**。

- **ローカルのアプリを起動できません**。②が無いので、この案だけでは輪が閉じません。
- 「w-cms が保存先を覚えていて、人がアプリで保存したあとブラウザで『取り込む』を押す」
  という**半自動**にはなります。Ctrl+S ではない。

### D. いまのまま（ダウンロード → 手で再アップロード）

- 追加の仕掛けはゼロ。**回数が少ないうちはこれで足ります**。
- 図面の修正が日常なら、確実に摩耗します。

## 3. w-cms 側で先に決めることが3つある

道を選ぶ前に、**どの道を選んでも必要になる**決定が3つあります。ここが未決のまま
実装すると、静かに壊れる形になります。

### 3.1 添付には版が無い

ページ本文には版があります（`versions/`・リバートできる）。**添付には版がありません。**
上書き保存を許すと、**前のCADファイルは消えます**——編集ミスも、間違ったファイルを
開いたことも、取り返せません。

既存の決定は「編集結果は**別ファイル保存（原本残置）**が本命」（
[【考察】添付ファイルの表示と操作.md](【考察】添付ファイルの表示と操作.md) §3）でした。
これは画像の加工（回転・切り抜き）についての判断で、**CADの継続的な修正とは性質が違います**
——別ファイルにすると `X026-001_v2.dxf` `..._v3.dxf` が増え、**どれが最新か分からなく
なる問題**（旧版を子ページへ移した理由そのもの）が添付の側で再発します。

選べる形は3つ:

| | 上書き | 版を積む | 別ファイル |
|---|---|---|---|
| 最新がどれか | 明らか | 明らか | **分からなくなる** |
| 前へ戻せる | **戻せない** | 戻せる | 戻せる |
| 置き場 | `files/<ID>.dxf` | `files/versions/<ID>/<時刻>.dxf` | `files/<別ID>.dxf` |

**「上書き＋版を積む」が本文と同じ形**で、いちばん筋が通っています。ページ本文が
そうしているのだから、添付だけ違う原理にする理由がありません。

### 3.2 誰かが同時に開いたら

ページには編集ロックがあります。**添付にはありません。** 2人が同じDXFを開いて
両方が Ctrl+S すると、**後の保存が前を黙って消します**。

WebDAV には `LOCK` があり（`x/net/webdav` も実装しています）、Windows は
Office ファイルでこれを使います。**CADアプリが LOCK を送るかは分かりません**——
実装前に実物で確かめる必要があります。送らないなら、w-cms 側で
「開いた人・時刻」を記録して**警告する**（止めない）のが現実的です。

### 3.3 上書きされたあと、派生をどうするか

DXFは解析されて索引に入ります（図面番号・図面名称）。**中身が変わっても索引は
古いまま**です。上書き後に、

- 索引の再同期（ページの本文は変わらないので、いまの仕組みでは走りません）
- 「🤖 解析」の印（`受信元` の逆引き）は残ったまま——**古い解析結果が最新の顔をします**

の2つが起きます。**「添付が変わったらページを触ったことにする」**（更新時刻を進め、
索引を作り直す）という決まりが要ります。

## 4. 名前の問題——`19ux.dxf` が開く

添付の保存名は**生成ID**です（`19ux.pdf`）。元の名前は本文のリンク文字と
`download` 属性が運んでいます。

WebDAV でフォルダとして見せるとき、**アプリのタイトルバーに `19ux.dxf` と出ます**。
CADの図面名としては役に立ちません。

逃げ道は「WebDAV の見せかけの名前を、元のファイル名にする」——`x/net/webdav` の
`FileSystem` は自前で実装できるので、**`ページID/元の名前.dxf` で見せて、実体は
`files/19ux.dxf` へ繋ぐ**ことができます。ただし**元の名前は本文の中にある**ので、
WebDAV の一覧を出すたびに本文を読むことになります（重い・要検討）。

## 5. どこまでを w-cms が持つべきか

**ローカルアプリの起動は、ブラウザにはできません**（できたら攻撃です）。だから
②を実現する主体は必ず「OSに登録された何か」——ネットワークドライブ（A）か、
インストールしたヘルパー（B）です。**w-cms が単体で完結させる道はありません。**

その前提で、A と B の違いは**どこに複雑さを置くか**です。

- **A は OS の機能に乗る。** w-cms 側は WebDAV を喋るだけで、癖は Windows のもの。
  癖が出たときに直せるのは Microsoft だけ、という弱みがあります。
- **B は自分で全部持つ。** 癖は自分のもので、直せます。代わりに**配る・入れる・
  更新する**が発生し、攻撃面も自分で守ることになります。

## 6. 結論——A（WebDAV）から。ただし読み取り専用で試す

**順序が肝**です。いきなり書き込みを許すと、§3 の3つが未決のまま「消えた」が起きます。

1. **読み取り専用の WebDAV を出す**（`x/net/webdav`・新しい依存ゼロ）。
   ページの添付フォルダをドライブとして見せ、**CADアプリから開けるか**を実物で確かめる。
   ここで Windows の癖（サイズ上限・認証・サービス）が全部出ます。**出させるのが目的**です。
2. 開けたら、**§3.1（版）を決めてから**書き込みを許す。「上書き＋版を積む」を推す。
3. §3.2（同時編集）は、まず**警告だけ**。CADアプリが `LOCK` を送るかを見てから決める。
4. §3.3（派生の作り直し）は書き込みと**同時に**入れる。あとからでは、古い索引を
   信じた集計が既に出回っています。

**Bは、Aが Windows の癖で使い物にならなかったときの控え**にします。先に作らないのは、
配布物が増える判断を「Aが駄目だった」と確かめる前にしたくないためです。

**Cは採りません**——②が無いので、この話の要求を満たしません。

### まだ確かめていないこと

- **CADアプリがネットワークドライブ上のファイルを直接編集できるか**（一時ファイルを
  同じフォルダに作る作りのアプリは、WebDAV上で遅い・失敗することがある）
- **`WCMS_SECURE_COOKIES=0` の平文HTTP運用と、Windows の Basic 認証拒否の衝突**
  ——本番のHTTPS化が前提条件になる可能性が高い
- 認証の切れ方（§2 の表のいちばん怖い行）
