# 【考察】テキストの正規化

> 状態: **検討中（未実装）**。本書は「同じものを同じと認めるために、値をどこまで畳むか」の
> 設計メモです。決めるのはユーザー——**論点と選択肢を並べて、推奨を添える**ところまでが本書の役割。
> 関連の正本は [アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §9（D-3・D-7）、
> [【一覧】語彙.md](【一覧】語彙.md)、実装は [vocab.go](../internal/cms/vocab.go) の `NormalizeValue`。

---

## 1. なぜ要るのか

**w-cms を作る動機そのものです。** ユーザー:「ワンノートが**ハイフンで区切られた図面名称を
うまく検索できない**」。人が打つ値は必ず揺れます——実データで実際にぶつかったものだけでも:

| 揺れ | 実例 |
|---|---|
| 空白が混ざる | `X008-135-4_ 架台Assy`（`_` の後ろに空白） |
| アンダースコアがハイフンの位置に来る | `PW050_167-ソレノイド補助具` |
| 全角と半角 | `Ｙ０５０-Ｗ０１` と `Y050-W01` |
| 英字の大小 | `P200-911-03A` と `p200-911-03a` |
| ハイフンの種類 | `-`（半角）・`－`（全角）・`‐`・`−`・`—`・`ー`（長音） |

**畳まないと、同じ部品の図面が別物として並びます。** 逆に畳み過ぎると、**別の部品が1つに
なります**——後者のほうが害が大きい（気づけないため）。

## 2. いま在るもの——正規化が3つ、別々の場所に

| どこ | 何を畳む | 対象 |
|---|---|---|
| `cms.NormalizeValue`（コア） | number（通貨記号・桁区切り・単位）／date（`2026/9/4`→`2026-09-04`） | **text は素通し** |
| `sheetmetal.normalizeDrawingNo`（拡張） | 空白・`_`→`-`・ハイフン類→`-`・全角→半角・小→大 | PDFとDXFの突き合わせのときだけ（**索引には入らない**） |
| `cms.parseRefValue`（コア） | 参照タグ `ページID-ブロックID` の**構文解析**（ハイフンの種類を吸収） | 参照タグだけ（D-7 決着済み） |

**つまり「図面番号を畳む知恵」は既に在るのに、索引には届いていません。**
`normalizeDrawingNo` は突き合わせの一瞬だけ使われて捨てられます。

## 3. 動かせない前提（既に決まっていること）

- **生が正本**。索引の `value` 列は**見た目のまま**入れる。畳んだ値は `norm_value` に**併記**する
  （[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §9.1）。
- **表示は畳まない**。ユーザー:「利用者が、『名前：値』のタグは見た目のままにDBに入れられると
  信じるためには、実際にそうである必要があります」。
- **畳むのは比較のときだけ**。
- **先頭のゼロは畳めない**（`000002` はページIDのゼロ埋め6桁）。
- 正規化を変えたら **DB再構築**で効く（再起動は不要）。`data/settings.json` の語→型辞書と同じ流儀。

---

## 4. 最大の論点——**長音（`ー`）をハイフンにしてよいか**

ここが本書の核心です。**同じ関数で両方は扱えません。**

| 値 | `ー`→`-` にすると | 正しいか |
|---|---|---|
| `X008ー135`（図面番号を全角で打った） | `X008-135` | **正しい**（同じ図面番号として引ける） |
| `レーザーマックス`（会社名） | `レ-ザ-マックス` | **壊れている** |
| `コンパクトオールラウンド２輪`（装置名称） | 影響なし | — |

いまコアの `toHalfWidth` は **`ー` を無条件で `-` にします**。number と date にしか掛からないので
実害は出ていませんが、**これを text へそのまま広げると日本語が壊れます**。

> **拡張の `normalizeDrawingNo` が `ー`→`-` を畳んでいるのは、対象が図面番号だと分かっているから**です。
> 「どの値なら畳んでよいか」を**型で言い分ける**のが、この問題の本筋だと考えます。

---

## 5. 何をどこまで畳むか（候補の一覧）

| # | 畳む対象 | 例 | 一般のテキスト | 図面番号・発注書番号 |
|---|---|---|---|---|
| 1 | 前後の空白 | `" A-1 "` → `A-1` | **畳む** | **畳む** |
| 2 | 中間の空白（半角・全角） | `X008-135_ 架台` → `X008-135-架台` | 畳まない | **畳む** |
| 3 | 全角英数 → 半角 | `Ｙ０５０` → `Y050` | **畳む** | **畳む** |
| 4 | 英字の大小 | `03a` → `03A` | 畳まない | **畳む** |
| 5 | ハイフン類 → `-` | `－ ‐ − —` | 畳まない | **畳む** |
| 6 | 長音 `ー` → `-` | `X008ー135` | **畳まない**（日本語が壊れる） | **畳む** |
| 7 | `_` → `-` | `PW050_167` | 畳まない | **畳む** |
| 8 | 区切りの有無 | `W470-L090` と `W470L090` | 畳まない | **畳まない**（別部品を1つにする害） |
| 9 | 半角カナ → 全角 | `ﾊﾟｲﾌﾟ` → `パイプ` | **要判断** | **要判断** |
| 10 | 濁点の分離（NFC） | `ハ`+`゙` → `バ` | **畳む**（同じ字） | **畳む** |

**列3と列4が違うことが、この表の言いたいことのすべてです。**

> **Unicode の NFKC を使えば済むのでは？** ——半分だけ。NFKC は 3・9・10 をまとめて畳んでくれますが、
> **`ー` は触らず**（＝4〜7は残る）、逆に `㈱`→`(株)`・`①`→`1` のような**行き過ぎた変換**も
> 一緒に行います。`golang.org/x/text/unicode/norm` は**既に承認済みの依存の一部**なので追加は
> 不要ですが（`go.mod` に直接依存として在る）、**畳む範囲を説明できることのほうが大事**です。
> **NFKC を土台に使い、`ー` と大小の扱いだけ自前で足す**のが現実的な折衷になります。

## 6. 案

### 案1: text を一律に軽く畳む（1・3・10 だけ）

前後空白・全角英数・濁点の合成だけ。**日本語が壊れない範囲**にとどめる。

- ○ コアの1関数で済む。既存の呼び出し（`insertVocabEntry`）に何も足さない
- ✕ **図面番号の揺れ（4〜7）が残る**——動機そのものが解決しない

### 案2: 新しい列型 `code` を足し、そこだけ強く畳む（**推奨**）

語彙レジストリに `code` 型を1つ足す。`text` は案1の軽い正規化、`code` は 1〜7 を全部畳む。

```
図面番号 / 発注書番号 / 品番 / 部品番号 …… code（強く畳む）
図面名称 / 装置名称 / 客先 / 備考       …… text（軽く畳む）
```

どの語が `code` かは **`data/settings.json` の `type_inference` に書く**——既に「語→型」の辞書が
在り、運用者が編集できて、DB再構築で効きます。**新しい仕組みを1つも増やしません。**

- ○ 「どの値なら畳んでよいか」を**型で言い分ける**——長音の罠を構造的に避けられる
- ○ 拡張の `normalizeDrawingNo` の知恵をコアへ引き上げ、**索引に届く**（`norm_value` に入る）
- ○ 運用者が語を足せる（複数運用者の前提と整合）
- ✕ 列型が1つ増える（エディタの列設定・`validColumnTypes`・`/api/tag-schema` に波及）
- ✕ **既存データは DB再構築が要る**（無害だが、知らないと「効かない」と見える）

### 案3: 索引は畳まず、検索するときだけ畳む

- ○ 索引が単純なまま
- ✕ **毎回の全走査**になる（`norm_value` の索引が効かない）。いまの規模なら動くが、
  ワンノートの766ページが入ると効かなくなる

## 7. 引く側をどうするか（案2を採ったとして）

| 用途 | 引く列 | 理由 |
|---|---|---|
| 参照タグの解決（`受信元` 等） | 現状のまま**構文解析** | D-7 決着済み。触らない |
| ページの逆引き（`PagesByTag`） | `value`（生）→ 見つからなければ `norm_value` | **打った通りに引けたら、それが正しい**。畳んだ一致は次善 |
| サイト内検索（未実装） | `norm_value` | 人は揺れた形で打つ。**畳んだ側で引くのが本筋** |
| PDF↔DXF の突き合わせ | `norm_value` | 拡張の自前実装を捨てて、索引に寄せられる |

> **`PagesByTag` を「生 → 畳んだ値」の2段にすると、静かに別のページを引き当てる危険が
> 出ます**（`W470-L090` と `W470_L090` が別部品だったとき）。**2段にせず、
> 呼ぶ側がどちらで引くか選ぶ**ほうが安全かもしれません——ここは未決（§9）。

## 8. 決めるべきこと（ユーザーへ）

1. **案1／案2／案3 のどれか**（推奨は案2）
2. **`code` にする語**——図面番号・発注書番号・品番・部品番号のほかに何があるか
3. **半角カナ（表の9）を畳むか**——`ﾊﾟｲﾌﾟ` と `パイプ` を同じとみなすか。
   実データに半角カナがどれだけ在るかは**未測定**（メールの取り込みで出てくる可能性はある）
4. **`PagesByTag` を2段にするか**（§7 の注記）

## 9. 未決（着手時に確かめる）

- 区切りの有無（表の8）を**将来も畳まない**でよいか。「畳み過ぎて別の部品を1つにするほうが、
  取りこぼしより害が大きい」という拡張側の判断を、コアでも踏襲する前提で書いている
- `norm_value` が既に number/date で使われている列に text の畳んだ値を入れてよいか
  （**型が違う値が同じ列に入る**——いまも `value` は全型で共用なので筋は通るが、
  `norm_num` のように分けるべきかは要確認）
- エディタ側の見え方——`code` 型の列に何か表示上の合図が要るか（薄青の見出し語と同じ系統）
