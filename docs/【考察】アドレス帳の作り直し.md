> 関連: [ext/contacts/](../ext/contacts/)（現行の正本。**2026-09-15 に `internal/cms` から

## 0. 言葉の決め（2026-09-15 ユーザー決定）

この文書でいちばん使う2語を、先に分けておきます。**もとは前者を「識別子」と
呼んでいました**が、2026-09-12 にユーザーから「識別子とは何でしょう？」と問われ、
**コードのどこにも無い概念語**だったことが分かりました（文書と説明の中だけで
使っていた）。ユーザー決定で「連絡先」に改めています。

| 語 | 指すもの | 実体 |
|---|---|---|
| **連絡先** | **相手を言い当てる手掛かり**。同じ相手に何個でも付き、増えるし移る | いまは `メールアドレス` タグ（`EmailTag`）。`電話番号`（CTI）・FAX番号が同じ口に並ぶ前提 |
| **相手** / **取引先ページ** | **相手そのもの**（同一性の持ち主）。1社1枚 | ページ。同一性を担うのは常にページID |

日本語の「連絡先」は第一義が「連絡する先＝アドレス・電話番号」なので、この割り当ては
自然です（`contacts.go` は既にその意味で使っていました——「連絡先そのもの
（メールアドレス・電話番号）は」）。**実体のほうを「連絡先」と呼ばないこと**
——「連絡先の無い連絡先」という書けない文になります。相手・取引先ページと呼びます。

## 1. 何が起きたか（実データ）

2026-09-10、整理を実データで通したときに**顧客名の推奨値が空振り**しました。
解析が読んだ生の値（誤記入りの「株式会社トーアス**ス**ポーツマシーン」）がそのまま出て、
既にある取引先ページの題に解決されなかった。

原因は単純です。**取引先ページ `010264` にタグが1つもありませんでした。**
そのページは**整理が作った**もので、アドレス帳を通っていません。照合
（`PartnerTitleForAddress`）は `メールアドレス` タグを引くので、空振りします。

100通を取り込んだあとの状態を測ると、もっとはっきりします。

| | 数 |
|---|---|
| 索引に出てくるメールドメイン | **11** |
| 取引先ページ | **1**（トーアスポーツマシーン） |
| そのページが連絡先を持った経緯 | 2026-09-10 に**人が手で足した**（アドレス帳の「既にある相手へ足す」） |

`i-toho.co.jp`（自社・**104回**）も `conic.co.jp`（コニック金型センター・3回）も、
ページになっていません。**アドレス帳は、実質からっぽのまま動いていました。**

## 2. なぜそうなったか

**取引先ページを作る道が2本あります。**

| 作る道 | 何を書くか | 結果 |
|---|---|---|
| アドレス帳の登録（`RegisterContactAPIHandler`） | 題＋`メールアドレス`＋`取引` | **照合できる** |
| 整理（`filing.go` の `ensureChildPage`） | 題だけ | **照合できない** |

2本目は「会社のフォルダを作る」つもりの操作です。ところが w-cms では
**会社のフォルダと連絡先は同じ1枚**（2026-09-05 の決定「相手のページは1枚・箱も1枚」）
なので、**フォルダを作ると、連絡先の無い相手ページが黙って生まれます**。

見た目は同じページです。違いは「タグが在るか」だけで、**無いことは誰にも知らされません**。
次のメールが来たときに、静かに空振りするだけです。

さらに、アドレス帳の作業面（未登録の連絡先の一覧）は**出てくるだけで、放っておける**。
誰にも催促されないので、11ドメイン中10が未登録のまま100通が過ぎました。

## 2b. もっと単純な原因もありました——**作業面が存在していなかった**

§2 を書いたあとに `取引先` ページの本文を見たら、こうでした:

```html
<h1>取引先</h1><p><br/></p>
```

**未登録の連絡先の一覧が、どこにも載っていません。** この一覧は計算ビュー
（`unknown-contacts`）で、**本文にブロックを置いて初めて描かれます**。通信箱には
`<section data-type="unhandled-intake">` が入っていますが、それは**人が置いた**ものです。
取引先ページは `EnsurePartnerBox` が**機械で作る**もので、見出しだけを書いていました。

つまり **100通のあいだ、誰も一覧を見たことがなかった**。「催促されないから登録されない」
どころか、**催促する画面が無かった**わけです。実際にブロックを置いたら、その場で
**9件**が並びました。

ここから引ける規律が1つあります:

> **機械が作るページは、行き止まりにしない。**
> 人が意図して置くページ（通信箱）と、機械が都合で作るページ（取引先）では、
> **中身を用意する責任の所在が違う**。

**これは作り直しを待たずに直せる**ので、2026-09-11 に直しました（`partnerBoxBody`）。
既にある職場のページにも作業面を入れ、自社（`i-toho.co.jp`・4アドレス）も登録して
未登録の一覧から外しました。

## 3. なぜ他所のシステムではアドレス帳が独立しているのか

ユーザーの見立ては当たっていると思います。理由を分けると4つあり、
**w-cms に効くのは後ろの2つ**です。

| 理由 | 内容 | w-cms に効くか |
|---|---|---|
| ① 保管の都合 | 連絡先は構造が決まっていて、専用の表が素直 | **効かない**。w-cms は `vocab_index` 1本と決めた（D-1）。タグで足りている |
| ② 画面の都合 | 一覧・検索・重複統合の専用UIが要る | 弱い。作業面は既にある |
| ③ **同一性の解決が「機能」だから** | 「この差出人は誰か」は、メール取り込み・整理・CTI・見積……**多くの機能が呼ぶ**。だから1か所に置く | **効く**。いまは `PartnerTitleForAddress` が1本あるだけで、**書く側が通らない** |
| ④ **連絡先が開いていて、変わるから** | 1社にアドレスが何個も、ドメインが2つ、電話番号、旧社名。増えるし移る | **効く**。だから「連絡先が付いているか」を**誰かが保証しないと壊れる** |

つまり独立しているのは**保管**ではなく、**同一性を決める仕事**です。
w-cms は保管の答えを先に出していて（ページ1枚・タグ）、**仕事の側を作っていなかった**。

## 4. 作り直しの原則

**保管は変えません。**取引先ページ1枚のまま、`vocab_index` のまま、専用テーブルは作りません。
ユーザーの「顧客であり、仕入れ先である場合もあります」も、部品階層と同じページに置く決定も、
どれも有効なままです。

変えるのは**入口**です。

> **取引先ページは、アドレス帳を通してしか生まれない。**
> **「この相手は誰か」を答えるのも、アドレス帳だけ。**

## 5. 具体案

### 5.1 作る口を1つにする

```go
// EnsurePartner は取引先ページを返し、無ければ作ります。**連絡先も一緒に受け取ります**。
func EnsurePartner(user *auth.User, name string, ids Identifiers) (string, error)
```

- 整理（`fileOneDrawing`）は `ensureChildPage(boxID, customer)` をやめ、これを呼びます。
  整理の時点で分かる連絡先——**その部品ページの `受信元` から辿れる差出人アドレス**——を
  一緒に渡せば、**作った瞬間から照合できる**ページになります。
- 連絡先が何も無いときは**そのまま作ります**（FAXしか来ない客先は実在する）。
  ただし「連絡先なし」は**見える**ようにします（§5.3）。

### 5.2 答える口を1つにする

```go
// ResolvePartner は連絡先から取引先ページを探します（見つからなければ ok=false）。
func ResolvePartner(user *auth.User, id Identifier) (pageID string, ok bool)
```

いまの `PartnerTitleForAddress` は**題しか返しません**。整理はページが欲しいので、
題で引き直しています（完全一致の二度手間）。**ページIDを返す**形に改めます。

優先順位は現行のまま（**完全一致 → ドメイン**）。理由も変わりません——自社の工場長だけ
別プロバイダのアドレスを使っている実例があるので、ドメインは手掛かりであって決定ではない。

将来 `電話番号`（CTI）・FAX番号が同じ口に並びます。**着信から相手を名指しする**のは
この関数の仕事で、`PagesByTag` の逆引きをあちこちに書かないためにも1本にします。

### 5.3 「連絡先の無い相手」を見えるようにする

いまの作業面は「**まだページになっていないアドレス**」を並べます。裏返しが抜けています
——**ページになっているが、連絡先が無い相手**。これが今回の事故そのものです。

取引先の作業面に1行足します:

```
⚠ トーアスポーツマシーン — メールで結びつきません（メールアドレスが未登録）
```

押すと、索引にあるアドレスから候補を出して足せる。**「未登録の連絡先」と対になる**
2つ目の作業で、どちらも「見つかっているものを並べ、決めるのは人」の同じ形です。

#### 出すのは「メールは来ているのに結びついていない相手」だけ（2026-09-15 ユーザー決定）

**全部を警告にすると狼少年になります**——FAXしか来ない客先・電話だけの客先は
**正当に連絡先ゼロ**で、それは異常ではないからです。実データでも取引先ページの
大半は、いつかそうなります。

絞り込みの条件は1つです:

> **その相手の題が、索引のどこかのメールアドレスから引ける形で現れているのに、
> その相手のページに `メールアドレス` タグが無い。**

言い換えると「**メールは届いているのに、届いた先が結びついていない**」。
2026-09-10 の事故がまさにこの形でした——`toa-sports-machine.co.jp` から
メールが来ていて、`トーアスポーツマシーン` のページもあったのに、
両者がつながっていなかった。

**FAXだけの客先は静かなまま**です。メールが1通も来ていないので条件に当たりません。
**つまり「直せるのに直っていないもの」だけが光ります**——直しようのないものを
並べても、人は一覧ごと信用しなくなります（未処理一覧で一度学んだことです）。

⚠ **判定の材料はメール由来のアドレスです**。実装は「索引にあるアドレスのドメインや
表示名から、その相手の題に解決できるか」を見る形になりますが、**解決の規則は
`PartnerTitleForAddress` と同じものを使うこと**——ここを別に持つと、
「警告は出ているのに、押しても候補が出ない」が起きます。

### 5.4 自社を登録する

`i-toho.co.jp` は**104回**出てくるのに、ページがありません。登録して `取引：自社` を
付けると、**未登録の一覧から自社の4アドレスが消え**、照合も自社を飛ばせます
（`isSelfPartner` は既にある）。**作り直しの前でもできる、いちばん効く1手**です。

## 5b. どこの持ち物か——**メールではなく業務側**

2026-09-11 ユーザー:「アドレス帳はメールプラグインの持ち物か業務プラグインの持ち物か
考えましょう」。**測った結果、メールではありません。** 好みではなく構造の話です。

### メールの持ち物ではない（4つの根拠）

1. **メールプラグインは使っていません。** `ext/mail` から `contacts.go` への参照は**ゼロ**。
   使っているのは `ext/subcon/filing.go` の4箇所と `main.go` のルート登録だけです。
2. **拡張どうしは import しません**（実測: `ext/` 間の import はゼロ）。アドレス帳が
   `ext/mail` に居ると、**業務側から呼べません**。
3. **`-tags nomail` で整理が壊れます。** `ext/subcon` は `!minimal` なので **nomail でも入り**、
   部品階層は `取引先／社名／段／装置名称／図面名称` と**取引先の下に生えます**。
   メールを外したら階層ごと消える、というのは筋が通りません。
4. **同一性は情報源より長生きします。** FAXしか来ない客先・電話だけの客先には
   メールアドレスがありません。CTI が来れば**電話番号から同じ相手**を引きます。
   **メールは連絡先の供給元の1つ**であって、同一性の持ち主ではない。

> **メールが供給するのは連絡先。アドレス帳が持つのは同一性。使うのは業務側。**

### ~~ただし、いまはコアに在る~~ → **2026-09-15 に `ext/contacts` へ出しました**

> 以下は移設前の記述です（そのまま残します——なぜ出したかの説明なので）。
> **済んだあとの実測**: `go build -tags minimal` の実行ファイルに `取引先`・
> `未登録の連絡先`・`仕入先`・`api/contacts` は**1つも入っていません**（移設前は
> 全部入っていた）。通常ビルドには入り、起動ログに `拡張セット: contacts（アドレス帳）`
> が出ます。

`contacts.go` は `internal/cms/` です。プラグイン開発ガイド §9 の「**業務に固有のものは
`ext/` の別パッケージへ出す**」に照らすと、ここは外れています——実際、
`go build -tags minimal`（**他社へ配る素の w-cms**）にも `取引先`・`顧客`・`仕入先`・
`自社`・`/api/contacts/register` が入ります。

同じ外れ方をしているものが、この機会に洗い出しただけで他にもあります:

| コアに在る業務語彙 | 場所 |
|---|---|
| `通信箱` | `intake.go` |
| `取引先`・`担当者`・`メールアドレス`・`取引` | `contacts.go` |
| `unknown-contacts`・`unhandled-intake`・`inspection-record` | `vocab.go`（①語彙レジストリ） |
| `.eml` の解析 | `intake_eml.go` |

**アドレス帳だけ動かしても、隣が残ります。** どこまで動かすかは別の判断です。

### 移すとして、行き先は3つ

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| **A. `ext/subcon` へ** | 唯一の使い手のところへ置く | いちばん小さい。ガイドの規則どおり | **名前が嘘になる**。アドレス帳は板金固有ではない |
| **B. `ext/contacts` を作る** | 独立した拡張。`ext/subcon` が import する | 粒度が正しい。他社配布でも選べる | **拡張どうしの import を解禁**することになる（いまはゼロ） |
| **C. コアに残す** | 仕組みはコア、語は `config/settings.json` へ | 移設コストなし。型推論辞書と同じ形 | 素の w-cms が `顧客／仕入先` を知ったままになる |

**移設の実費は小さいです**（実測）。`contacts.go` は699行で、コアの非公開ヘルパは
**3つしか使っていません**——`topLevelPageByTitle`・`insertAfterH1`・`endOfFirstTagList`。
どれも業務の匂いがしない汎用の道具で、**公開して困らないもの**です。
語彙とビューとルートは既に外から足せます（`RegisterVocab`・`RegisterView`・`Routes()`）。

> **やってみて分かったこと**（2026-09-15）。数は合っていましたが**中身が1つ違い**、
> **本体は別のところ**にありました。
>
> 非公開ヘルパは**コンパイラに数えさせて**3つ——`topLevelPageByTitle`・
> `pageTitleByID`・`endOfFirstTagList`（`insertAfterH1` は既に公開済みで、
> 代わりに `pageTitleByID` が要りました。分割で増えたぶんです）。ほかに**公開済みの
> 8つ**があり、そちらは `cms.` を付けるだけでした。
>
> **本当の作業は、コアからアドレス帳への名指し2本を裏返すこと**でした
> ——`view_render.go` の表の `unknown-contacts` と、`ref_render.go` が直接呼んでいた
> `ContactPageForAddress`。前者は `RegisterView` で済みましたが、後者には
> **新しいフック（`RegisterContactResolver`）が要りました**。ここが済むまで
> ファイルは動かせません（動かした瞬間にコアが `ext/` を import することになる）。
> **だから2つのコミットに分けました**——先に依存を裏返し、次にファイルを移す。
>
> 試験は**パッケージ境界を越えられません**。コアの `newPage`・`setupTemplateAPITest`
> を `ext/contacts/setup_test.go` へ持ちました（`ext/subcon` と同じ割り切り）。
> ⚠ ただし**ファイルDBにすること**——アドレス帳は `visibleChildren`・`page.CanView` を
> 通るので `:memory:` では静かに空を返します。`ext/subcon` がインメモリなのは、
> あちらがその経路を通らないからです。

**推すのは B** です。アドレス帳は「取引の相手を1枚のページで持つ」という、板金にも
メールにも依らない仕組みで、他社へ配る形でも**欲しがられる側**だからです。
拡張どうしの import は、ビルドタグを増やさない限り複雑さも増えません
（`ext/contacts` にタグを付けず、使う側が連れてくる形にする）。

## 6. 決めていただきたいこと

> **全部決まりました**（§8 の決定ログ）——0: **B（`ext/contacts`）**・
> 1: **ドメインは独立させない**・2: **整理パネルで提案し、人が確かめる**・
> 3: **メールは来ているのに結びついていない相手だけ警告**（2026-09-15）。
> **判断待ちはゼロで、着手できます**（順序は §5.4 の自社登録が先）。

0. **行き先（§5b の A / B / C）**。**推すのは B（`ext/contacts`）**ですが、
   拡張どうしの import を解禁してよいかはプロジェクトの方針の話なので、ここで伺います。
1. **`ドメイン` を独立したタグにするか。**
   いまはドメインを `メールアドレス` の後ろから切り出しています。`ドメイン：toa-sports-machine.co.jp`
   というタグを持てると、**具体的なアドレスを1つも知らなくても**「この会社だ」と言えます
   （新しい担当者からの初メールが、いきなり正しい相手に結びつく）。
   反面、**タグが2種類になり、どちらが正かを人が意識することになります**。
2. **整理が連絡先まで書いてよいか。**
   §5.1 は「整理が会社ページを作るとき、`受信元` から辿った差出人アドレスも一緒に書く」案です。
   **機械が連絡先を書く**ことになるので、「人が確認してから」にする選択もあります
   （PDF解析を人間ゲート型にしたのと同じ考え方）。
3. ~~**「連絡先の無い相手」を警告にするか、ただ並べるだけにするか。**~~
   **→ 「メールは来ているのに結びついていない相手」だけ警告する**（2026-09-15 ユーザー決定）。
   絞り込みの条件と理由は §5.3。

## 7. やらないこと（確認）

- **専用テーブルは作りません**（D-1・[【考察】タグ表と業務ブロック表の分離.md](【考察】タグ表と業務ブロック表の分離.md) の結論と同じ理由）。
- **会社ページを2枚に割りません**（連絡先用と部品階層用に分けない。2026-09-05 決定）。
- **名寄せを機械にやらせません**。題の完全一致が階層の同一性という根っこは動かしません
  ——揺れを機械が吸収すると、別の顧客が1つに潰れます。候補を出すところまでが機械の仕事。

| 2026-09-11 | **アドレス帳を作り直す**（ユーザー決定） | 取引先ページを作る道が2本あり、整理で作った側は連絡先を持たないので照合が静かに空振りする。実データで11ドメイン中1件しか登録されていなかった |
| 2026-09-11 | **機械が作るページには作業面を載せる**（実装済み） | `EnsurePartnerBox` が見出しだけのページを作っていたため、アドレス帳の一覧がどこにも存在しなかった。人が置くページ（通信箱）と機械が作るページでは責任の所在が違う |
| 2026-09-11 | **メールプラグインの持ち物ではない**（判定） | `ext/mail` からの参照はゼロ・拡張どうしは import しない・`-tags nomail` で部品階層が壊れる・FAXと電話だけの相手にはアドレスが無い |
| 2026-09-11 | **独立させるのは入口であって保管ではない**（提案・未承認） | 他システムでアドレス帳が独立している理由のうち w-cms に効くのは「同一性の解決が機能だから」「連絡先が開いていて変わるから」の2つ。どちらも保管の話ではない |
| 2026-09-12 | **行き先は B: `ext/contacts` を新設**（ユーザー決定） | §5b の3案のうち推奨。アドレス帳は業務側の持ち物で、メールの持ち物ではない（上の判定）。**これで拡張どうしの import が解禁される**（いまはゼロ）——`ext/subcon` の整理が `ext/contacts` の口を呼ぶ形になる |
| 2026-09-12 | **`ドメイン` を独立したタグにしない**（ユーザー決定） | ドメインはこれまでどおり `メールアドレス` の後ろから切り出す。タグが2種類になると、どちらが正かを人が意識することになる |
| 2026-09-12 | **整理は連絡先を「提案」し、書くのは人が確かめてから**（ユーザー決定・案 b） | 整理が辿れる差出人（`受信元` → 通信記録 → `差出人アドレス`）は、**その部品の客先とは限らない**——社内からの転送では差出人が社員になる。自動で書くと社員のアドレスが客先のページに入り、以後その社員のメールが全部その客先に結びつく。**連絡先が「無い」より「間違っている」ほうが悪い**——無ければ照合が空振りして §5.3 で見えるが、間違っていれば自信を持って間違い、何も知らせない。整理パネルはもともと「機械が出して人が直す」場所（顧客名・装置名称）なので、アドレスを1行足すだけで新しい画面も手順も要らない。PDF解析を人間ゲート型にしたのと同じ考え方 |
| 2026-09-15 | **「連絡先の無い相手」の警告は、メールが来ている相手だけに絞る**（ユーザー決定・§6-3） | FAXだけ・電話だけの客先は**正当に連絡先ゼロ**で、全部を警告にすると狼少年になる。条件は「索引のアドレスから題に解決できるのに、そのページに `メールアドレス` タグが無い」——**直せるのに直っていないものだけが光る**。2026-09-10 の事故がまさにこの形だった。直しようのないものを並べると、人は一覧ごと信用しなくなる（未処理一覧で学んだこと）。⚠ 解決の規則は `PartnerTitleForAddress` と同じものを使うこと——別に持つと「警告は出るが押しても候補が出ない」が起きる |
| 2026-09-15 | **`ext/contacts` へ移設（実装済み）** | 案Bの実装。**拡張どうしの import を解禁**（`ext/subcon` → `ext/contacts` が最初の1本）。`ext/contacts` に**ビルドタグは付けません**——付けると「板金は入れたがアドレス帳は外した」という組み合わせが作れてしまい、整理が取引先ページを作れずに黙って壊れる。依存は import で表す。`cmd/w-cms/ext_contacts.go` は**表示だけ**（`loadedExtensions` が `package main` の変数で拡張から名乗れないため。消しても機能は消えない）。コアとの境目はフック3つ（`RegisterVocab`・`RegisterView`・`RegisterContactResolver`）で、**どれも任意**——積まなければ `email` 型のタグが素のテキストで出るだけ |
| 2026-09-15 | **「識別子」を「連絡先」と呼ぶ**（ユーザー決定） | コードのどこにも無い概念語で、文書と説明の中だけで使っていた（2026-09-12「識別子とは何でしょう？」）。語の割り当ては §0 が正本——**連絡先＝相手を言い当てる手掛かり／相手・取引先ページ＝相手そのもの**。⚠ 実体のほうを「連絡先」と呼ばないこと（「連絡先の無い連絡先」という書けない文になる） |
