# 【考察】タグ表と業務ブロック表の分離

> 2026-09-06。ユーザー:「TAGSと表のTableを分離することについて考察してください」。
> いま可変タグ（`<dl data-type="tags">`）と業務ブロック（図面・発注書・明細表）は
> **同じ `vocab_index` 1本**に入っています。これを2つの表に分けるべきかを、
> 実測した数字と読み手の一覧から考えます。**結論は「分けない。ただし読み手の曖昧さは
> 分けずに直す」**（§6）。未決ではなく、この文書での判断です——蒸し返すときは
> §6 の3条件のどれかが崩れたときに。

## 1. いまの形（実測 2026-09-06・118ページ・実メール100通）

`vocab_index` は9列。タグも表も **1行＝1セル**で入り、区別は `data_type` だけです。

| data_type | 行数 | `block_id` が入っている行 | `norm_num` | `row_no` の最大 |
|---|---|---|---|---|
| `tags` | **1137** | **0**（全行が空） | 0 | 15 |
| `drawing`（図面ブロックの dl） | 28 | 28（全行） | 0 | 3 |
| `drawing-revision-items`（改訂履歴の表） | 21 | 0 | 0 | 0 |

```sql
-- 数え直すとき
SELECT data_type, COUNT(*), SUM(block_id<>''), SUM(norm_num IS NOT NULL), MAX(row_no)
  FROM vocab_index GROUP BY data_type;
```

行の**96%がタグ**で、その大半はメールの封筒（差出人・宛先・メッセージID…）です。
タグ行では `block_id` が**常に空**——タグの `dl` には `data-id` を振っていないためです。

### 1.1 1件（レコード）の単位が違う

同じ表に入っていますが、**何が1件かはタグと表で違います**。

| | 1件の単位 | `row_no` の意味 |
|---|---|---|
| 表（`table`） | `tr` 1行＝1件 | **件を区別する**（行1と行2は別の件） |
| `dl`（タグ・図面ブロックのヘッダ） | ブロック全体で1件 | **並び順**にすぎない |

読み手はこの非対称を `vocabRows(db, pageID, dataType, perBlock)` の `perBlock` で吸収しています
（[vocab_query.go](../internal/cms/vocab_query.go)）。`dl` は `row_no` を 0 に潰して1件にまとめ、
表はそのまま使う。**書き手の作りの違いが、読み手にそのまま出ている**形です。

### 1.2 ブロックの中のタグは、ブロックから切り離されて入る

図面ブロックは `<section><h2>図面</h2><dl>…</dl><dl data-type="tags"><dt>受信元</dt>…</dl></section>`
という形で、由来の参照タグを**ブロックの中**に持ちます（改定で合流させるとき、ブロックごと
運べば出所も付いて行くように）。ところが索引では:

```
('drawing', 0, '3je2', 0, '図面番号', 'X011-002')      ← ブロック（block_id あり）
('tags',    0, '',     0, '受信元',   '010173-skr1')   ← 同じ section の中のタグ（block_id 空）
```

`data-type="tags"` を持つ要素は配送係が**独立した形式として別に届ける**ので
（[vocab_index.go](../internal/cms/vocab_index.go) `syncVocabSection` の注記）、
包んでいる section との対応は索引に残りません。図面ブロックが1ページに1つしか無い
いま（旧版は子ページへ・2026-09-06）は実害がありませんが、**「このタグはどのブロックの
ものか」を索引から引く手は無い**、というのが現状です。

## 2. 読み手の一覧——どちらの読み手も、既に種類で分かれている

索引に触る素の SQL は**23か所**（テストを除く。`grep -rn "FROM vocab_index"`。うち1つは書き手の `DELETE`）。

| 読み手の種類 | 場所 | `data_type` を絞るか |
|---|---|---|
| **ブロックを読む** | `vocabRows`（`VocabTableRowsOf` / `VocabBlocksOf`） | 絞る（特定の形式名） |
| **タグを読む・入口** | `PagesByTag` / `PagesByTagLoose` / `RelatedPages`（2本） | **`data_type='tags'` で絞る** |
| **タグを読む・素の SQL** | contacts.go ×5・view_unhandled.go ×6・ref_scope・handler_replies ×2・analyzed.go・filing.go ×2・ext/mail/reply.go | **絞らない**——`field` だけで引く |

2つのことが読み取れます。

1. **Go の読み口は、もう種類で2家族に分かれています。** ブロックは `Vocab*Of`、タグは
   `PagesByTag*`。共有しているのは**保存先**だけで、API は既に分離済みです。
2. **素の SQL の大半は `field` だけで引いています。** `WHERE field = '差出人アドレス'` は
   「それはタグだ」と**名前で決めつけて**います。いまは業務ブロックの列にその名前が無いので
   合っていますが、誰かが `<th>差出人アドレス</th>` を持つ表を作った瞬間に、
   アドレス帳がその表の値を「未登録の連絡先」として拾います。**1つの表であることの、
   いちばん具体的な危うさ**はここです。

## 3. 経緯——`page_tags` は一度あって、消した

- 2026-08-17: 汎用索引を **1テーブル縦持ち** `vocab_index` と決定
  （[【考察】語彙モデル.md](【考察】語彙モデル.md) §10）。
- 〜2026-08-30: `page_tags` テーブルが**並走**していた。中身が `vocab_index` の `tags` 行と
  完全に重複し、**読む者が1人もいなかった**ため、D-1 の第一歩で吸収
  （[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §9・`vocab_index.go` の注記）。
- 2026-08-30: 「行/フィールドの2テーブル分割」を D-3 で見送り——分ける利益が具体化して
  いない、業務判断の要らない内部の話なのでエージェント判断（同 §9）。
- 2026-08-31: タグは `data-type="tags"` の**明示が正**と決定。「セクション外の素の dl＝タグ」
  という位置の規則は、「用語：説明」のような普通の定義リストまでDBに入るため撤回
  （ユーザー:「tags については、データベースに入る汎用的なマークアップとして使いたいので、
  やはり data-type または似たようなクラス分けが必要」・[walk.go](../internal/cms/walk.go)）。

ここで大事なのは、**過去に消した `page_tags` と、いま考えている分離は別物**ということです。
消したのは「同じ中身を2か所に持つ」重複でした。いま考えているのは「種類で**割る**」分割で、
どの行も1か所にしか入りません。だから「D-1 の蒸し返し」にはなりません——**が、
D-3 の「分ける利益が具体化していない」はそのまま当たります**（§5）。

もう一つ。2026-08-31 の決定は、**タグが業務ブロックとは違う種類のものだ**と言っています。
業務ブロックは機能見出し（`<h2>図面</h2>`）で形式が決まる**文書の一部**、タグは
`data-type="tags"` で明示的にオプトインする**ページの付箋**です。種類が違うものを
1つの表に入れている、という指摘は正しい。問題は、それを**表を分けて表すか、
列で表すか**（いまは `data_type` 列）です。

## 4. 選択肢

### A. いまのまま（1表・`data_type` 列で区別）

- 書き手1つ・再構築1つ・FK 1つ。`syncVocabDL` はタグとブロックのヘッダを**同じ関数**で書く。
- 欠点は §1.1 の非対称と §2-2 の曖昧さ。どちらも**いま壊れてはいない**。

### B. 2表に分ける（`page_tags` ＋ `vocab_index`）

```sql
CREATE TABLE page_tags (          -- 付箋。1行＝1対
    page_id    INTEGER,
    seq        INTEGER,           -- ページ内の並び（旧 row_no）
    field      TEXT,
    value      TEXT,
    norm_value TEXT,
    FOREIGN KEY (page_id) REFERENCES pages(id) ON DELETE CASCADE
);
-- vocab_index はブロック専用になり、block_no / block_id / row_no / norm_num が
-- **全行で意味を持つ**ようになる
```

- 得るもの: **スキーマの正直さ**（タグ行に常に空の `block_id` が無くなる）、読み手が
  **どちらを読むか書かざるをえない**（§2-2 の曖昧さが構造的に消える）、索引を種類ごとに
  張れる（タグは `(field, value)`・`(field, norm_value)`、ブロックは `(page_id, data_type)`）。
- 払うもの: 書き手が2つ（`syncVocabDL` をタグ用とヘッダ用に割る）、素の SQL **17か所**の
  書き換え、`DriftedSchemaTables` による起動時の自動再構築1回、プラグインガイドの更新。
  それと**§1.2 の帰属問題は解けない**——タグを別の表へ出しても、包んでいるブロックとの
  対応は同じく残らない。

### C. 分けずに、非対称と曖昧さだけ直す

1. **素の SQL 17か所に `data_type = 'tags'` を足す**——または `PagesByTag*` を通す。
   §2-2 の危うさはこれだけで消える。
2. `row_no` の意味の違いは、書き手で揃える手がある（`dl` は常に `row_no = 0`、並びは
   `rowid` で保つ）。ただし読み手の `perBlock` が既に吸収していて、直す動機が弱い。

### D. 表は1つのまま、**ビュー**で名前を分ける

```sql
CREATE VIEW page_tags AS
  SELECT page_id, row_no AS seq, field, value, norm_value
    FROM vocab_index WHERE data_type = 'tags';
```

- 書き手はそのまま、読み手は `FROM page_tags` と書けて意図が見える。B の「正直さ」の
  半分を、書き換えなしで得る。
- ただし SQLite のビューは `DriftedSchemaTables` の対象ではない（テーブル定義の比較なので）。
  ビューの作り直しを `ApplySchema` に足す手間は要る。

## 5. 判断の物差し——このプロジェクトが既に決めていること

- **柔軟性 > 速度**（§9 の原則）。行数は理由になりません——100通で1137行、年435通なら
  10年で**5万行前後**。SQLite にとって何でもない量で、分けても速くならず、分けなくても
  遅くなりません。
- **索引は派生**。スキーマを変えても起動時に1度作り直されるだけで、移行は要りません。
  だから「変えるなら早いうちに」は**成り立ちますが**、「変えないと後で困る」も
  **成り立ちません**——いつでも同じ手間です。
- **読む口は `vocab_query.go` の3つに閉じる**（引き継ぎ「知らないと踏む罠」）。
  §2 の 17か所はこの決定から**既に漏れている**素の SQL で、分離の是非より先に
  直すべきものです。

## 6. 結論——分けない。読み手の曖昧さは C-1 で直す

分けない理由は3つ。**この3つのどれかが崩れたら、B を考え直します。**

1. **能力が増えない。** いまの読み手に「2表でないと書けない問い」は1つもありません。
   得られるのは正直さと見通しで、それは C-1 と D で**書き換えなしに**大半が手に入ります。
2. **タグの帰属（§1.2）を持ちたくなったとき、同じ表のほうが自然。** 「この `受信元` は
   どの図面ブロックのものか」を引きたくなったら、必要なのは `block_id` を**埋める**こと
   ——列は既にあります。2表に割っていたら、`page_tags` に列を**足す**ことになり、
   ブロックと同じ列を2つの表が持つ形へ戻ります。§1.1 の非対称は「タグは付箋であって
   ブロックではない」と読めば、非対称ではなく**種類の違いが列の埋まり方に出ている**だけです。
3. **払うものが具体的で、得るものが抽象的。** 15か所の書き換えと書き手の分割は今日やれば
   1日ですが、それで直る不具合が**今日は無い**。D-3 と同じ理由です。

やることは2つ。

- **C-1（今すぐ・小）**: `field` だけで引いている素の SQL に `data_type = 'tags'` を足す
  か、`PagesByTag*` を通す。アドレス帳（contacts.go）・未処理一覧（view_unhandled.go）・
  解析済みの印（analyzed.go）・整理の顧客名推奨（filing.go）・返信（handler_replies.go・
  ext/mail/reply.go）・参照の集計（ref_scope.go は済み）。**業務ブロックの列名がタグ名と
  衝突した日に静かに壊れる**穴なので、分離の是非とは無関係に塞ぐ。
- **D（任意）**: ビュー `page_tags` を足して、以後の素の SQL はそこから読む決まりにする。
  `ApplySchema` に `CREATE VIEW IF NOT EXISTS` を1つ足すだけ。
