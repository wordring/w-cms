# ユースケース拡張とプラグイン化の考察

ユースケース（受注管理・原価管理・製品マスタなど）を追加していくと、フロントのカスタムタグ・DBスキーマ・集計プログラムが増えていく。本ドキュメントは「1ユースケースを足すと実際に何が増えるか」を実コードに基づいて棚卸しし、それをプラグイン化（拡張容易化）できるかを考察する設計検討メモである。2026-06-20時点の調査。

> [!NOTE]
> **本考察は2026-06-20に実装済みです。** Tier 1（宣言的同期＝レジストリ＋`Plugin`インターフェース）とTier 2（集計API＝`RouteProvider`）の両方を導入し、既存の4ユースケース（顧客発注・自社発注・見積もり・部材）をプラグインへ移行しました。新しいプラグインの追加手順は [プラグイン開発ガイド.md](プラグイン開発ガイド.md) を参照してください。以下は導入時の検討経緯の記録です。

---

## 1. ユースケース追加時に増えるもの（現状の実態）

「顧客の発注書」ユースケースを例に追跡すると、1つのユースケースの追加は **6ファイル・13箇所** の協調した変更を要する。

| 層 | ファイル | 増えるもの |
|---|---|---|
| フロント要素 | `assets/web-components.js` | カスタム要素クラス1つ + `customElements.define` + `observedAttributes` |
| フロント表示 | `assets/templates/` | view用・edit用のHTMLテンプレート2ファイル |
| パース構造体 | `internal/cms/parser.go` | 新しい構造体（`ClientOrder`等）+ `ParsedPage` へのフィールド追加 |
| パース処理 | `internal/cms/parser.go` | `traverse` 内の `switch`/`if` 分岐 + 子要素用サブ関数 |
| スキーマ | `internal/database/sqlite.go` | `CREATE TABLE` 文 |
| 同期(削除) | `internal/cms/sync.go` | `tablesToDelete` への追記 **＋** `RebuildDatabase` の `tables` への追記（**2箇所**） |
| 同期(挿入) | `internal/cms/sync.go` | INSERTループのブロック |
| 集計API | `internal/cms/handler.go` | ハンドラ関数 |
| ルーティング | `cmd/w-cms/main.go` | `mux.HandleFunc` 1行 |
| 集計表示 | `assets/web-components.js` | 集計用カスタム要素（`MRequiredMaterials`等） |

### これは「散弾銃手術（shotgun surgery）」アンチパターン
属性名はフロント（`observedAttributes`）・パーサー（`switch attr.Key`）・スキーマ（カラム名）の **3箇所で一致** していなければ動作しない。1つのユースケースの知識が複数ファイルに散らばっているため、変更が常に協調作業になり、不整合が混入しやすい。

#### 実際に発生していた不整合（2026-06-20に発見・修正済み）
同期処理の「テーブル削除リスト」が2箇所に手書きで存在し、すでに食い違っていた。
*   `SyncIndex` の `tablesToDelete` には `our_estimates` / `supplier_estimates` が **あった**。
*   `RebuildDatabase` の `tables` には **なかった**。

このため、DB再構築時に削除済みページに紐づく見積もりの古い行がクリアされず残存する不具合があった（修正済み）。これは「同じ情報を複数箇所に手書きする設計」が必然的に生む不整合であり、プラグイン化を検討すべき最大の根拠である。

## 2. 変動部分と不変部分の分離

増える13箇所のうち、大半は **機械的なボイラープレート** である。本質的に変動するのは「タグ→テーブル→カラム」のマッピング宣言1つに集約できる。

```
タグ  m-file[tag="顧客の発注書"]  →  テーブル client_orders
  属性  order-no    → order_no    (TEXT, unique)
  属性  client-name → client_name (TEXT)
  属性  ordered-at  → ordered_at  (DATE)
  子要素 m-item → client_order_items (FK: order_no)
      item-id  → item_id
      price    → price (INTEGER)
      ...
```

このマッピングを宣言すれば、`CREATE TABLE`・パース（DOM走査して属性読み取り）・同期（page_id でDELETE → INSERT）は **すべて自動生成可能** である。属性名の3重一致や削除リストの二重管理といった脆さも、単一の宣言から導出すれば構造的に消える。

ただし **集計ロジックだけは宣言化できない**。BOM計算（受注数 × 部材必要数 − 発注済数）や利益率計算は、JOINや乗算を伴う固有のビジネスロジックであり、コードとして書く必要が残る。

## 3. プラグイン化の方針

**結論: 2階層のプラグイン化が妥当。** ただしGoの `plugin` パッケージによる動的ロード（`.so`）は採用すべきでない（Windows非対応で、本プロジェクトはWindows開発＋Linux配備）。代わりに、Goが標準採用している **レジストリ＋インターフェース方式**（`database/sql` のドライバ登録、`image` のデコーダ登録と同じ流儀）を用いる。これは [開発方針.md](開発方針.md) の「標準ライブラリ優先・外部依存最小」とも完全に整合する。

### Tier 1: 宣言的マッピング（ボイラープレートを消す）
*   `cms.RegisterTagMapping(mapping)` を各機能ファイルの `init()` で呼び、タグ→テーブル→カラムのマッピングを登録する。
*   汎用パーサーが、ハードコードの `switch` の代わりに登録済みマッピングを走査して属性を抽出する。
*   汎用同期が、登録済みマッピングから DELETE 対象リストと INSERT 文を生成する（→ 削除リスト二重管理の不整合が構造的に発生しなくなる）。
*   スキーマも各機能が自分の `CREATE TABLE`（またはマッピングから生成）を登録する。

### Tier 2: コードプラグイン（集計ロジック用）
*   `Feature` インターフェースに、集計APIの `http.HandlerFunc` とパスを登録させる。
*   `main.go` はハードコードの代わりにレジストリをループしてルートを登録する。

### 結果
ユースケース追加が「**自分自身を登録する1ファイルを足すだけ、コア6ファイルは無編集**」になる。フロント側も同様に、新コンポーネントを1ファイル追加して自己登録し、スラッシュメニューがレジストリから読む形にできる（テンプレートはすでに外部化済みで、下地は半分できている）。

## 4. トレードオフと判断材料

*   **メリット**: 追加コストが13箇所→1〜2ファイルに激減。属性名の3重一致バグと削除リスト二重管理バグが構造的に消滅する。
*   **デメリット**: 汎用エンジンの初期実装コスト。リフレクションや `interface{}` の多用による静的型安全性の低下。

### 導入是非の分かれ目
現状のユースケースは6種類程度。**「今後あと何種類増える見込みか」** が判断の核心となる。
*   3〜4種で頭打ちなら、汎用エンジンの初期コストが見合わず **現状維持** が妥当。
*   十数種に育つ計画なら、まず **Tier 1（宣言的マッピング）だけでも早期導入** する価値が高い。集計ロジック（Tier 2）は固有性が高いので、必要になった時点で後追い導入でよい。
