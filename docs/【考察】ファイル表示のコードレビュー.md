## 0. 総評

**壊れているものが1つ、作りの穴が2つ、UXの粗が4つ。安全上の問題は出なかった。**
エスケープ（`fileViewInnerHTML` の全補間値・`analyze_pdf.go` の書き出し）、サニタイザの許可
（`data-ref` は `section` 限定・`vocabulary_test.go` が固定）、匿名経路（`RenderComputedViews` は
`/api/load` とページ描画の両方で走り `page.CanView(nil, id)` が `EffectivePublic` へ落ちる）は、
8観点すべてが「問題なし」で一致した。

壊れていたのは**その日に足した分岐**で、既存の仕組みとの突き合わせを怠ったもの。穴は
**同じ壊れ方を別の経路で残した**もの。どちらも「試験が HTML の文字列しか見ていない」
「E2E が保存APIで正しい形を直接書いていて、人の通る経路を通っていない」という形で、
試験を通り抜けている。

## 1. 教訓

1. **「開ける」と宣言する前に、配信側が何を返すかを見る。** 表示（`fileViewKinds`）と配信
   （`setAttachmentHeaders`）は別々の表で、片方だけ増やすと「描けると言って描けない」が
   できる。**表は配信側に1つ**が筋——描画は配信の帰結であって、独立した判断ではない。
2. **届きようのないファイルのための分岐を書かない。** `.txt` は添付として保存できる拡張子に
   無い。「将来のため」の枝は、試験もE2Eも通れないので**壊れていても分からない**。
3. **同じ壊れ方は経路ごとに潰す。** スラッシュメニューを直しても、見出し形で打つ経路が
   残っていた。「気づきにくい壊れ方」と書いた当人が、半分だけ直して満足していた。
4. **試験は「文字列が出た」ではなく「ブラウザで見えた」まで見る。** `TestFileViewOpensAnyKind`
   は `<embed` の有無しか見ておらず、配信ヘッダとの矛盾を通した。
5. **URLを組む場所を増やさない。** 「URLは派生だから本文に書かない」と決めた同じ日に、
   `page.AttachmentURLFor` を迂回して `"/" + pageID + "/" + n` を書いていた。
6. **浮くパネルは、小さいものに付ける。** section 全体の矩形に付けると、中身が大きい日に
   画面外へ開く。リンクの欄が `<a>` に付いているのは偶然ではない。

### 2.6 確かめて「問題なし」だったもの

- `refreshDrawingPreviews` は `.file-view-plain` に憶えた高さを当てない（`.file-view-body` が無いので飛ばす）
- 旧形（中に `受信元` タグ）の本文は、この環境では**検証用の4枚だけ**で、移行済み。解析が作った本物の
  部品ページに旧形は無かった。ただし **`page_tags` に旧形の `受信元` 行が残る**ので、DB再構築を1回
- `.mp4`（`attachment_extensions` に在る）の `<video>` は**未確認**——09-14 から在る分岐で、
  #1 と同じ配信ヘッダの縁に居る。メディア要素は `Content-Disposition` を無視するので鳴る見込みだが、
  実測していない
- シグネチャを変えた `attachmentURLFor`・`fileViewInnerHTML` の呼び手は `renderFileView` 1か所だけ
- E2E のセレクタ（`.fv-wire`・`#w-fv-popover`・`.slash-menu-item[data-type="vocab:file-view"]` ほか）は
  すべて現行コードに実在
