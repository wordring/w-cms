# 本文サニタイズ設計

ページ本文（HTML）を許可リスト方式で安全化する仕組みの設計書。実装は
[internal/cms/htmldoc/sanitize.go](../internal/cms/htmldoc/sanitize.go)（純粋なHTML部品）で、
**本文で扱えるHTMLの語彙はここが唯一の正本**（`structuralElements` ＋ `data-*` マーカー）。
[internal/cms/sanitize.go](../internal/cms/sanitize.go) は薄いラッパで、
`htmldoc.New()` を呼んでパッケージ変数を1本持つだけ（2026-08-17 に切り出し）。

> 最終更新: 2026-08-20（語彙モデルへの移行完了に追随）。サーバー合成
> （[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md)）の導入と同時に実装。
> 許可リストを増減したら [【一覧】語彙.md](【一覧】語彙.md) §1 も同期させること。

---

## 1. なぜ必要か

ページ本文はユーザー入力由来のHTMLであり、`data/master/<xx>/<id>/<id>.html` が正本。
サーバーはこれをシェル `assets/index.html` へ埋め込んだ完成HTMLを返す（サーバー合成）。

**合成方式では本文が初期HTMLの一部としてパースされる**ため、本文中に `<script>` や
`on*=` があれば**そのまま実行される**。

CSP は strict 化済み（`script-src 'self'; style-src 'self'`。`'unsafe-inline'` なし・2026-08-19）なので、
いまは本文中のインラインスクリプトはCSPでも止まる。ただし**サニタイズはCSPの代わりにならない**——
CSPが見ていない攻撃が残る（`<form>`／`<input>` による偽ログイン欄の設置は `form-action` を
指定していないので素通り、`<dialog>` で画面を覆う妨害、`id` によるシェル要素の乗っ取り、
同一オリジンの `<iframe src="/…">` など）。役割の違いは §6。

> 合成方式にする前は、フロントの `populateEditor()` が `DOMParser` 経由で本文を挿入していた。
> DOMParser で生成した `<script>` は仕様上実行されないため、結果的に守られていた。
> つまり**合成方式への移行とサニタイズはセットで初めて成立する**。

## 2. 二層構成

サニタイザ本体（`Sanitize` / `SanitizeReport`）は1つで、通す場所が2つある。

| 層 | 実装箇所 | 目的 | カバーする経路 |
|---|---|---|---|
| **保存時** | `SaveAPIHandler`（[handler_save.go](../internal/cms/handler_save.go)） | 正本を清書された状態に保つ＋編集者へのフィードバック | エディタからの保存（＝唯一の書き込みAPI） |
| **描画時** | `RootHandler` の合成（[handler_view.go](../internal/cms/handler_view.go)） | 最後の防壁 | 既存の保存済みデータ、バックアップからのファイル復元、`data/master` への手動配置 |

描画時サニタイズは冪等なので、保存時に清められた本文は素通り（差分ゼロ）でコストも小さい。

> かつて存在した `/upload`（HTMLファイルを丸ごと取り込むエンドポイント）は、無検査で正本へ
> 書き込める入口だったため削除済み。呼び出し元が無い死んだ経路でもあった。

> **サニタイザの外側にある経路（2026-08-05 に塞いだ）**: 本文でない**添付ファイル**は、この二層の
> どちらも通らない。`POST /api/upload-pdf` が任意の名前・種類を受け付けていたため、`.html` を
> ページのディレクトリへ置き `/data/master/...` から**同一オリジンのHTMLとして**配信させれば、
> サニタイズを丸ごと迂回した保存型XSSが成立した（中間版CSPの `script-src 'unsafe-inline'` は
> インラインを許す）。対策は入口（`.pdf` のみ・先頭 `%PDF-` 必須）と出口（`DataFileHandler` が
> `nosniff` ＋ PDF以外は `application/octet-stream` でダウンロード扱い、本文とサイドカーは配信しない）の
> 両方。**「本文HTMLを清める」だけでは足りず、同一オリジンから配るものすべてが対象**という例。

## 3. 保存時エコーバック（編集者へのフィードバック）

保存時サニタイズには「黙って内容が落ちる」という難点がある。本設計はこれを
**結果を編集者へ返して画面に反映する**ことで解決している。

1. エディタはブロックの編集が終わった時点（`focusout`）で保存する。
2. サーバーはサニタイズ後の本文を保存し、レスポンスに `html`（サニタイズ済み本文）と
   `sanitized`（除去が起きたか）を載せる。
3. クライアントは `sanitized` が真のときだけ、**差分のあったトップレベルのブロックを差し替え**、
   「安全でない記述を除去しました」と通知する。
   **フォーカス中のブロックは差し替えない**（キャレットが飛ぶため。離脱時の保存で反映される）。

**冪等性が前提条件**: `Sanitize(Sanitize(x)) == Sanitize(x)` でなければ、返した内容を保存し直す
たびに本文が変化して収束しない。`sanitize_test.go` で検証している。

**通常の編集では発火しない**。エディタのシリアライザ `updateHtmlPreview()`
（[assets/app.js](../assets/app.js)。2026-08-06 の殻の外部化で `index.html` から移動）は
既に許可リスト相当の語彙しか出力しないため、
実際に除去が起きるのは異物が混入した時だけ。なお同シリアライザは属性値・テキストを
`esc()` でエスケープする（これが無いとタグの値に `"` を入力しただけで生成HTMLが壊れ、
値が欠けたり意図しない属性が生まれてサニタイザに除去される）。

## 4. 「閲覧＝サニタイズ済み／編集＝生」の非対称

- **閲覧**: サーバー合成でサニタイズ済みの本文が入る。
- **編集**: 編集モードへ入るときに `acquireLock()` が `POST /api/lock` の応答（生HTML）で
  載せ替える。編集権を失ったときの `reloadContent()` も `/api/load`（生）から取り直す。

**この非対称が安全な理由**: 編集は必ずロック取得時の生HTMLから始まるため、
サニタイズで欠けた内容が保存されて正本を壊すことがない。
なお保存時サニタイズにより正本自体が清書済みになるので、実際に返る内容は
サニタイズ済みと一致する（冪等のため差は出ない）。

## 5. 許可リスト（2026-08-04 決定・実装済み）

正本は [internal/cms/htmldoc/sanitize.go](../internal/cms/htmldoc/sanitize.go) の `structuralElements`。
エディタは同じ内容を `GET /api/tag-schema` から受け取る（§7）。

### 5.0 方針：**タグは寛容・属性は厳格**

| 対象 | 方針 | 理由 |
|---|---|---|
| **要素（タグ）** | **危険でなければ許可する** | 本文は文書であり、意味を持つ標準HTMLを禁じる理由がない。落とすと貼り付けた資料の構造が壊れる |
| **属性** | **必要なものだけ許可する** | 属性は挙動・見た目・DOM上の同一性に効く。ここが緩いとUIの乗っ取りやCSP方針の破綻に直結する |

**要素は3通りに分かれる。**

1. **許可**（5.2）— そのまま通す。属性は要素ごとの許可リストで絞る
2. **削除**（5.1）— 危険なので**部分木ごと**捨てる（中のテキストも残さない）
3. **アンラップ** — 上のどちらでもない未知の要素。要素は捨てるが**子とテキストは残す**ので、
   知らないタグが混ざっても本文が消えない

> **重要な前提**: 許可リストを広げるときは、**エディタのシリアライザも同じ語彙を扱えること**を
> 確認する。片方だけ広げると「画面には出るが保存すると消える」要素が増える。
> 両者は `/api/tag-schema` を通じて同じ宣言から導かれる（5.3・§7）。

### 5.1 削除する要素（部分木ごと）

| 要素 | 落とす理由 |
|---|---|
| `script` `noscript` | スクリプト実行そのもの。本文からのコード実行を許さない |
| `style` | 任意CSSの注入。クロームの見た目を書き換えられ、CSP strict 化の方針にも反する |
| `iframe` `frame` `frameset` `object` `embed` `applet` | 外部文書・プラグインの埋め込み。実行と外部通信の経路になる |
| `base` | **相対URLの解決先を書き換えられる**。本文中の全リンク・画像の宛先を乗っ取れる |
| `link` `meta` | 外部リソース読み込み・リダイレクト（`http-equiv="refresh"`）の経路 |
| `svg` `math` | 内部にスクリプトやイベント属性を書ける。XML名前空間なのでHTMLの属性フィルタが素通りしうる |
| `form` `input` `button` `textarea` `select` `option` | 入力欄の偽装。本文から偽のログインフォーム等を作れる |
| `template` | 中身がパース済みDOMとして保持され、サニタイズの走査から外れる |
| `dialog` | モーダルで画面を覆い、操作を妨げられる |

### 5.3 語彙は htmldoc の1箇所（注入は移行完了で不要になった）

**本文で扱えるHTMLの語彙は `htmldoc/sanitize.go` の `structuralElements` ＋ `data-*` マーカーだけ**です。
`internal/cms/sanitize.go` は `htmldoc.New()` を呼んでパッケージ変数を1本持つだけの薄いラッパで、
語彙の合成はしません。

> **かつての形（撤去済み・2026-08-20）**: 各プラグインが必須メソッド `Tags() []TagSpec` で
> カスタム要素 `<m-*>` の語彙（要素と属性）を宣言し、cms 側のラッパが `PluginTags()` で集めて
> `htmldoc.New(custom)` へ**注入**していた（`cms → htmldoc → cms` の循環を解くための依存反転。
> [変更履歴.md](変更履歴.md) 2026-08-06 の選択肢(b)）。**語彙モデルへの移行完了でカスタム要素が
> ゼロになり、受け皿が「常に空」になったため機構ごと外した。**
> 副産物として、プラグインの `init()` 登録を待つ遅延初期化（`sync.Once`）と、
> そこにあった**暗黙の初期化順序への依存も消えている**。

依存は `cms → htmldoc` の一方向のままで、**htmldoc から cms を import しません**。
htmldoc はアプリのドメイン（プラグイン・語彙レジストリ）を一切知らず、
「どの `data-type` がどんな形式か」は知らないまま**マーカー属性を不活性な値として通す**ところまでを受け持ちます。

**カスタム要素はゼロ**です。到達状態は `vocabulary_test.go` の `TestNoCustomElementVocabulary` が
固定していて、`AllowedVocabulary()` にハイフンを含む要素名が現れたら落ちます。

**旧要素（`<m-tag>`・`<m-file>` 等）は「許可リストに無い未知の要素」として扱われ、アンラップされます**
（5.0 の3分類のうち 3.。要素は捨てるが**子とテキストは残る**ので、文章そのものは失われません）。
属性は要素ごと消えるため、旧要素に属性として持たせていた値（`order-no` 等）は失われます。
一括変換ツールも撤去済みなので、未変換のデータが後から出てきた場合は
この版より前のバイナリで変換するか手作業で書き換えます（[変更履歴.md](変更履歴.md) 2026-08-20）。

**形式（`data-type`）の宣言はサニタイザに関与しません。** 語彙レジストリ
（`cms/vocab.go` の `vocabRegistry`）は編集支援と索引の語彙であって安全性の門ではなく、
`data-type` の**値**は検査対象外の不活性な文字列です（5.4）。未知の値も保存を通り、
保存応答の `unknown_types` で告知されるだけです。

エディタへ届く語彙（`GET /api/tag-schema`）は次の合成です（§7 に応答の全キー）。

```
htmldoc の structuralElements ＋ data-* マーカー ──► サニタイズ許可リスト
                                                 └─► /api/tag-schema の elements / void / block_id
cms/vocab.go の vocabRegistry ────────────────────► /api/tag-schema の vocab / type_inference
                                                     （サニタイズ許可リストには**関与しない**）
```

形式ごとの一覧は [【一覧】語彙.md](【一覧】語彙.md)、全体像は [【考察】語彙モデル.md](【考察】語彙モデル.md) §4。

### 5.4 属性の規則（全要素に共通）

**属性は「必要なものだけ許可」**。5.2 の表に無い属性はすべて落とす。加えて、以下は
**どの要素でも常に拒否**する。

| 拒否する属性 | 理由 |
|---|---|
| **`on*`**（`onclick` `onload` 等） | 本文からのスクリプト実行そのもの。`innerHTML` 経由でも属性ハンドラは動く |
| **`style`** | 任意CSSの注入。要素を画面全体に広げてUIを覆うなどの妨害ができ、CSP strict 化（`'unsafe-inline'` 除去）の方針にも反する |
| **`id`** | **シェルの要素を乗っ取れる**（下記） |
| **`class`** | クローム側のCSS（`.editor-block` `.rail` `.m-block` 等）と衝突し、レイアウトを壊せる |
| `srcdoc` `formaction` `xlink:href` 等 | そもそも許可要素の属性リストに無いので通らない（許可リスト方式の効用） |

> **`id` を許さないのは意図的**（2026-08-02 決定）。本文はシェル `assets/index.html` と
> **同じDOMへ合成される**ため、`id` を通すと本文からシェル側の要素を乗っ取れる。
> `getElementById` は文書順で最初の要素を返し、シェルの62個の `id` のうち**23個は
> `#editor-content` より後ろ**に定義されている（2026-08-20 に測り直した数。2026-08-06 の
> 殻の外部化直後は41個で、増えた21個は語彙モデルの編集クローム——行/列ツールバー・
> dl項目ツールバー・列設定ポップオーバ・enum メニュー——ですべて `#editor-content` より前。
> **後ろの23個は変わっていない**）。とくに `html-preview` を奪われると
> 保存経路（`getElementById('html-preview').value`）が壊れる。`pp-mode`（権限）や
> `pi-parent-input`（親ページ）も同様。ブロック識別子に `data-*` を使えばこの経路は
> 構造的に塞がれ、CSSセレクタの制約（数字始まりのIDが不正セレクタになる問題）も回避できる。

#### ページ内アンカーをどう実現するか（2026-08-20 再考察）

`id` を落とすと**ページ内リンク（`#fragment`）が成立しない**。ブラウザの `#` ジャンプは `id` を
探し、`data-id` は見ないためである。実際、目次のページ内移動も `id` を使わず
JSの `scrollIntoView` で実装されている（[app.js](../assets/app.js) の `buildToc`）ので、
**公開ページ（閲覧ゼロJS）ではアンカーが効かない**。

**`id` を許可リストへ戻す案は採らない。** 乗っ取りは理論上の話ではなく、この画面構成そのものが
持つ性質である——本文の挿入点は `assets/index.html` の
`<div id="editor-content"><!--WCMS_CONTENT--></div>`（151行目）で、権限UIの入力欄は
その**後ろ**（`pi-parent-input` 173／`pp-owner-input` 197／`pp-group` 202／`pp-mode` 203／
`pp-public` 215）にある。`getElementById` は文書順で最初の要素を返すので、本文に
`<input id="pp-mode" value="777">` を仕込むと、**そのページを開いた人の権限パネルが
攻撃者の値を読む**。管理者がそのページを開いて「保存」を押せば、意図しない mode／所有者／
親ページ／公開フラグが送信される。攻撃者は自分のページに書くだけでよい。

**採る案: `id` は保存形式に入れず、描画時にサーバーが合成する。**

| 保存形式（正本ファイル） | 描画結果（ブラウザが受け取るHTML） |
|---|---|
| `<h2>発注書A</h2>` | `<h2 id="h-発注書A">発注書A</h2>` |
| `<section data-id="a7k2m9">` | `<section data-id="a7k2m9" id="b-a7k2m9">` |
| `<a href="#発注書A">` | `<a href="#h-発注書A">` |

- **接頭辞の名前空間をサーバーが独占する**。`h-`／`b-` で始まる `id` はシェルに1つも無いので、
  衝突は原理的に起きない。ブロックIDは base36 の英数字だけ（`newBlockId`）なので `id` 値として安全
- **保存形式に `id` が入らないので、5.3 の拒否リストは変えない**——安全性の門は不変のまま
- 付ける場所はサニタイズ**後**の合成段（`RenderComputedViews` と同じ段階）。サニタイザは触らない
- 書き手は `id` を管理しない。**見出しの表示文字がそのままアンカー名**になる
  （「見える文字が鍵」＝[【考察】語彙モデル.md](【考察】語彙モデル.md) §5.1 と同じ思想）
- 既存の全ページが**遡って**アンカーを持つ。目次も `scrollIntoView` から標準リンクへ
  乗り換えられ、公開ページで目次が機能するようになる
- `data-src="000200#a7k2m9"`（[【考察】通信記録処理.md](【考察】通信記録処理.md) §2.7⑤）の
  URL 変換も、この合成と同じ規則に乗る

**未決**: 見出しテキストのスラッグ化規則（空白・記号の扱い、重複見出しの連番）。
見出しを改名するとリンクが切れる点（`data-field` 撤去と同じトレードオフ。告知の仕組みに乗せられる）。
書き手が `#発注書A` と手で書くのか、UIで「この見出しへのリンクをコピー」を出すのか。

**例外（全要素で通す唯一の属性）**

- **`data-id`** … ブロック単位保存の識別子。落とすとブロックの同一性が静かに失われ、
  以後ずっと全文保存に戻ってしまう（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.1.0）。
  文書構造の都合であってドメインの語彙ではないので、プラグインではなくコアが持つ。

**例外（要素限定で通す語彙マーカー・実装済み）**

| 属性 | 許可される要素 | 役割 | 値の検査 |
|---|---|---|---|
| `data-type` | `table` `dl` `section` `th` | 形式名（table/dl/section）・列型の明示（th） | **しない**（不活性な文字列） |
| `data-src` | `section` | **出所アドレス**（型ごとに解釈が変わる。ファイル／出所ページ／集計対象ページ） | **する**（埋め込みと同じ相対URL限定・5.5） |

語彙モデル（標準HTML＋`data-*` マーカー）の役割マーカーで、許可するのは**属性名だけ**。
`data-type` の**値は不活性な文字列として検査しない**——語彙レジストリは
編集支援・検証の語彙であって安全性の門ではなく、未知の値も通す（保存時に `unknown_types` で通知のみ）。
`data-src` だけは**URLとして使われる**ので例外で、埋め込みと同じ相対URL限定にしている（多層防御）。
2026-08-20 に意味を一般化し、ファイルパス専用ではなく**その要素の出所を指す論理アドレス**とした
（`000200` ／ `000200#<ブロックID>` ／ `000200/<ファイル名>`。解釈は `data-type`＝型が決める。
[【考察】通信記録処理.md](【考察】通信記録処理.md) §2.7⑤）。**値は常に参照先に限り、状態値は入れない**
——`data-src` は `embed.src` へ流れる経路があるため、参照先と状態値が混在すると
サニタイザが「URLとして使われる値か」を判定できなくなる（`isRelativeURL("終了")` は true を返す）。

`globalAttributes` には入れず**要素限定**とする（「属性は厳格」の維持）。
`data-type`→`table`・`dl`・`th` は決定ログ（[【考察】語彙モデル.md](【考察】語彙モデル.md) §9）どおりで、
**機能を足すときにその要素へ `data-type` を都度許可していく**（同 §9「`data-type` は型名」・2026-08-20）。
機械キーの属性（`data-field`）は同日に撤去した——項目の鍵は見出し（`th`／`dt`）の表示文字が運び、
レジストリ宣言の `Label` を通じて機械キーへ解決される。改名で解決できなくなった列は
保存時に `unresolved_fields` で告知する（拒否はしない）。
`section` への `data-type`／`data-src` は業務文書ブロックの外形（論点A・案1）を採用した
移行第3段（2026-08-19）で追加した。正本は同書 §4・§9、形式ごとの一覧は
[【一覧】語彙.md](【一覧】語彙.md) §1.1。

### 5.5 URLの規則（`href` / `src` / `srcset` / `poster` / `cite` / `data-src`）

| 用途 | 対象の属性 | 許可するスキーム | 理由 |
|---|---|---|---|
| **リンク** | `href`（`a`）・`cite`（`blockquote` `q` `ins` `del`） | 相対URL・`http`・`https`・`mailto`・`tel` | 外部サイトへのリンクは文書として正当。**利用者が自分でクリックする**ので、勝手な通信は起きない |
| **埋め込み** | `src`・`srcset`・`poster`（`img` `video` `audio` `source` `track`）と **`data-src`**（`section`） | **相対URLのみ** | 外部URLは**閲覧するだけで自動的に取得され、閲覧者のIPと閲覧時刻を第三者へ渡す**（トラッキングビーコン）。しかも CSP `default-src 'self'` が実行時に遮断するので、許可しても壊れた表示になるだけで利益がない |

`data-src` は属性名としては不活性だが、**ファイル容器のエンハンサがPDFプレビューのURLに使う**ため、
埋め込みと同じ基準を掛けている（多層防御）。判定は `embedURLAttributes` の一員として行われる。

**共通の拒否**

- `javascript:` `data:` `vbscript:` などは**属性ごと除去**する。
  `data:` は `data:image/svg+xml` の形でスクリプトを持ち込めるため、画像でも許可しない。
- **プロトコル相対URL（`//host/path`）を拒否する**。スキームが空でも**別ホストを指す**ため、
  「相対URL」として通してはいけない（2026-08-04 に穴として発見・修正）。
- 判定前にタブ・改行を取り除く（`java&#9;script:` のような回避を防ぐ）。

### 5.6 その他

- 可変タグの `親ページID`（`<dl data-type="tags">` の `dt` にこの名前が書かれた項目）を
  取り込まない規則は、その語彙を所有する `plugin_page_tags.go`（`legacyParentTagName`）が持つ。
  サニタイザは**通す**——HTMLの安全性だけを見て、形式の**意味**には立ち入らないため。
  ページ属性の正本はサイドカー `<id>.meta.json`（[エディタ仕様.md](エディタ仕様.md) 9章）。
- コメント・DOCTYPE は落とす。
- **空要素の表記差は無視される**。エディタは `<br>`、Goの描画器は `<br/>` と書くが、
  比較は描画後の文字列同士で行うため `sanitized` は立たず、エコーバックも起きない
  （正本ファイルには `<br/>` の形で残るが、読み込めば同じDOMになる）。

## 6. CSPとの関係

サニタイズとCSPは**役割が違う多層防御**であり、どちらか一方では足りない。

- **サニタイズ**: 本文という「データ」から危険な構造を除く。CSPが見ていない攻撃
  （偽ログイン欄の設置・`<dialog>` による画面の占拠・`id` によるシェル要素の乗っ取り・
  同一オリジンの `<iframe>`）を止めるのはこちらだけ。
- **CSP**: 万一の漏れや将来の別経路に対する網。**strict 化は完了済み**
  （`script-src 'self'; style-src 'self'`。`'unsafe-inline'` なし・2026-08-19 の移行第4段）なので、
  インラインスクリプトはCSPでも止まる。正本は [【考察】CSP強化.md](【考察】CSP強化.md)。

`on*` と `style` をどの要素でも常に落とす方針は、strict CSP と同じ方向を向いている
（そもそもインラインを増やさない）。逆に言えば、本文に `style=` を通す例外を作ると
`style-src 'self'` を緩めることになるので、この2つはセットで維持する。

## 7. 保守

- **新しい「形式」を足すだけなら、サニタイザは変更不要。** `data-type` は許可済みの属性名で
  **値は検査されない**ので、[vocab.go](../internal/cms/vocab.go) の `vocabRegistry` へ宣言を1件足すだけでよい
  （[【一覧】語彙.md](【一覧】語彙.md) §5、[【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md)）。
- **新しい「要素・属性」が要るときだけ `structuralElements` を直す。** 直す場所は1箇所で、
  エディタは `GET /api/tag-schema` から語彙を受け取ってシリアライズするので自動的に追随する。
  あわせて 5.2 の表と [【一覧】語彙.md](【一覧】語彙.md) §1.1 も更新すること。
  応答は次の5つ:

  | キー | 内容 | エディタでの用途 |
  |---|---|---|
  | `elements` | 要素名 → 許可属性（構造HTML＋`data-*` マーカー） | 保存する要素・属性の判断 |
  | `void` | 子を持てない要素（`br` `img` `hr` …） | 終了タグを書かない |
  | `block_id` | `data-id` | ブロック単位保存の識別子 |
  | `vocab` | 語彙レジストリ（①）の形式定義 | スラッシュメニューの項目と挿入骨格の生成（サニタイズ許可リストには**関与しない**。5.3） |
  | `type_inference` | 語→型の推論辞書 | 型不一致の通知（赤印）。サーバーの索引と同じ辞書で判定が食い違わない |

- **新しいマーカー属性を要素へ許可するときは、要素限定を崩さない**（`globalAttributes` へ
  入れない）。値がURLとして使われるなら 5.5 の埋め込み扱いにする（`data-src` がその例）。

  かつてエディタ側に `TEXT_BLOCK_TAGS = ['h1','h2','h3','p']` という手書きの表があり、
  許可されている `h4`〜`h6`・`ul`・`table` が**画面には出るが保存すると消えていた**。
  手書きの要素リストをエディタ側に置かないこと。
- **URLを取る属性を追加したら、リンク（外部可）と埋め込み（相対のみ）のどちらかを判断する**（5.5）。
  埋め込み扱いの属性を外部可にすると、トラッキングビーコンの経路が開く。

  アンラップ・冪等性・属性注入耐性・URL方針・**エディタ出力の無変更通過**・
  **旧カスタム要素のアンラップ**＝`TestSanitizeDropsLegacyCustomElements`）と
  [save_sanitize_test.go](../internal/cms/save_sanitize_test.go)（保存経路のエコーバック、
  通常本文が変化しないこと）、[shell_test.go](../internal/cms/shell_test.go)（描画時サニタイズ）、
  [vocabulary_test.go](../internal/cms/vocabulary_test.go)（**到達状態**＝カスタム要素ゼロと
  マーカー属性の維持。5.3）。
