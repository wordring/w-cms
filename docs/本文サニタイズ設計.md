# 本文サニタイズ設計

ページ本文（HTML）を許可リスト方式で安全化する仕組みの設計書。実装は
[internal/cms/sanitize.go](../internal/cms/sanitize.go)。

> 最終更新: 2026-08-02。サーバー合成（[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md)）の
> 導入と同時に実装。許可リストは [【一覧】カスタムタグ.md](【一覧】カスタムタグ.md) と同期させること。

---

## 1. なぜ必要か

ページ本文はユーザー入力由来のHTMLであり、`data/master/<xx>/<id>/<id>.html` が正本。
サーバーはこれをシェル `assets/index.html` へ埋め込んだ完成HTMLを返す（サーバー合成）。

**合成方式では本文が初期HTMLの一部としてパースされる**ため、本文中に `<script>` や
`on*=` があれば**そのまま実行される**。現行のCSPは中間版で `script-src 'self' 'unsafe-inline'` を
許しているため、CSPでは止まらない（[【考察】CSP強化.md](【考察】CSP強化.md)）。

> 合成方式にする前は、フロントの `populateEditor()` が `DOMParser` 経由で本文を挿入していた。
> DOMParser で生成した `<script>` は仕様上実行されないため、結果的に守られていた。
> つまり**合成方式への移行とサニタイズはセットで初めて成立する**。

## 2. 二層構成

サニタイザ本体（`Sanitize` / `SanitizeReport`）は1つで、通す場所が2つある。

| 層 | 実装箇所 | 目的 | カバーする経路 |
|---|---|---|---|
| **保存時** | `SaveAPIHandler`（[handler.go](../internal/cms/handler.go)） | 正本を清書された状態に保つ＋編集者へのフィードバック | エディタからの保存（＝唯一の書き込みAPI） |
| **描画時** | `RootHandler` の合成（[handler.go](../internal/cms/handler.go)） | 最後の防壁 | 既存の保存済みデータ、バックアップからのファイル復元、`data/master` への手動配置 |

描画時サニタイズは冪等なので、保存時に清められた本文は素通り（差分ゼロ）でコストも小さい。

> かつて存在した `/upload`（HTMLファイルを丸ごと取り込むエンドポイント）は、無検査で正本へ
> 書き込める入口だったため削除済み。呼び出し元が無い死んだ経路でもあった。

## 3. 保存時エコーバック（編集者へのフィードバック）

保存時サニタイズには「黙って内容が落ちる」という難点がある。本設計はこれを
**結果を編集者へ返して画面に反映する**ことで解決している。

1. エディタはブロックの編集が終わった時点（`focusout`）で保存する。
2. サーバーはサニタイズ後の本文を保存し、レスポンスに `html`（サニタイズ済み本文）と
   `sanitized`（除去が起きたか）を載せる。
3. クライアントは `sanitized` が真のときだけ、**差分のあったトップレベルのブロックを差し替え**、
   「安全でない記述を除去しました」と通知する。
   **フォーカス中のブロックは差し替えない**（キャレットが飛ぶため。離脱時の保存で反映される）。

**冪等性が前提条件**: `Sanitize(Sanitize(x)) == Sanitize(x)` でなければ、返した内容を保存し直す
たびに本文が変化して収束しない。`sanitize_test.go` で検証している。

**通常の編集では発火しない**。エディタのシリアライザ `updateHtmlPreview()`
（[assets/index.html](../assets/index.html)）は既に許可リスト相当の語彙しか出力しないため、
実際に除去が起きるのは異物が混入した時だけ。なお同シリアライザは属性値・テキストを
`esc()` でエスケープする（これが無いとタグの値に `"` を入力しただけで生成HTMLが壊れ、
値が欠けたり意図しない属性が生まれてサニタイザに除去される）。

## 4. 「閲覧＝サニタイズ済み／編集＝生」の非対称

- **閲覧**: サーバー合成でサニタイズ済みの本文が入る。
- **編集**: 編集モードへ入るときに `acquireLock()` が `POST /api/lock` の応答（生HTML）で
  載せ替える。編集権を失ったときの `reloadContent()` も `/api/load`（生）から取り直す。

**この非対称が安全な理由**: 編集は必ずロック取得時の生HTMLから始まるため、
サニタイズで欠けた内容が保存されて正本を壊すことがない。
なお保存時サニタイズにより正本自体が清書済みになるので、実際に返る内容は
サニタイズ済みと一致する（冪等のため差は出ない）。

## 5. 許可リスト

**方針**: 許可したものだけを通す。危険な要素は部分木ごと削除、許可リストに無い要素は
**アンラップ**（要素は捨てるが子・テキストは残す）してレガシー本文が消えないようにする。

### 5.1 部分木ごと削除する要素

`script` `style` `iframe` `object` `embed` `form` `input` `button` `textarea` `select`
`option` `link` `meta` `base` `svg` `math` `template` `noscript` `frame` `frameset` `applet`

### 5.2 許可する要素と属性

| 分類 | 要素 | 許可属性 |
|---|---|---|
| 見出し | `h1`〜`h6` | なし |
| テキスト | `p` `br` `hr` `div` `span` `blockquote` `pre` `code` `strong` `em` `b` `i` `u` `s` | なし |
| リスト | `ul` `li` | なし |
| 〃 | `ol` | `start` |
| リンク・画像 | `a` | `href` `title` |
| 〃 | `img` | `src` `alt` `title` `width` `height` |
| 表 | `table` `thead` `tbody` `tr` | なし |
| 〃 | `th` `td` | `colspan` `rowspan` |

### 5.3 カスタム要素（**プラグインが宣言する**。サニタイザは持たない）

**サニタイザはカスタム要素の語彙を一切持ちません。** 許可リストは
「構造HTML ∪ 全プラグインの `Tags()`」を合成して作られます（`allowedElements()`）。

```
各プラグインの Tags() ──► PluginTags()（要素ごとの和集合）─┬─► サニタイズ許可リスト
                                                          ├─► /api/tag-schema（エディタ）
                                                          └─► ドキュメント
```

属性を「読む側」が「許可」も宣言するので、**読むのに許可し忘れる不整合が構造的に起きません**
（過去に `m-file` の `item-name` が漏れ、保存のたびに値が消えて原価集計が壊れていた）。
現在の要素と所有プラグインの一覧は [【一覧】カスタムタグ.md](【一覧】カスタムタグ.md) §1 が正本です。

属性を増減するときは**プラグインの `Tags()` を直すだけ**でよく、サニタイザもエディタも追随します。

### 5.4 全要素に共通の規則

- **`on*` 属性と `style` 属性は常に除去**する（CSP strict 化の方針とも一致。
  [開発方針.md](開発方針.md) §4）。
- **`href` / `src` は相対URLか `http` / `https` / `mailto` のみ許可**。`javascript:` や
  `data:` は属性ごと除去する。判定前にタブ・改行を取り除く（`java\tscript:` 等の回避を防ぐ）。
- 許可リストに無い属性（`class` `id` `data-*` 等）は落とす。
  ただし **`data-block-id` だけは全要素で通す**（`globalAttributes`）。ブロック単位保存の
  識別子で、落ちるとブロックの同一性が静かに失われ全文保存に戻ってしまうため
  （[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) 4.1.0）。文書構造の都合であって
  ドメインの語彙ではないので、プラグインではなくコアが持つ。
- 旧形式の `<m-tag name="親ページID">` を取り込まない規則は、`m-tag` を所有する
  `plugin_page_tags.go` が持つ（サニタイザはカスタム要素の**意味**には立ち入らない）。
- コメント・DOCTYPE は落とす。

## 6. CSPとの関係

サニタイズとCSPは**役割が違う多層防御**であり、どちらか一方では足りない。

- **サニタイズ**: 本文という「データ」から危険な構造を除く。中間版CSPが
  `'unsafe-inline'` を許している現状では、これが実質の主防御。
- **CSP**: 万一の漏れや将来の別経路に対する網。strict 化（`'unsafe-inline'` 除去）が
  完了すれば、インラインスクリプトはCSPでも止まるようになる。

`on*` と `style` を常に落とす方針は、CSP strict 化の前提（インラインを増やさない）とも
一致している。

## 7. 保守

- **カスタム要素・属性を増減したら、所有プラグインの `Tags()` を直す**（サニタイザと
  エディタは自動で追随する）。あわせて [【一覧】カスタムタグ.md](【一覧】カスタムタグ.md) §1 の
  表も更新すること。`Tags()` に載せ忘れた属性は保存のたびに黙って消える
  （エコーバックで編集者には見えるが、原因が分かりにくい）。
- テストは [internal/cms/sanitize_test.go](../internal/cms/sanitize_test.go)（除去・保持・
  アンラップ・冪等性・属性注入耐性）と
  [save_sanitize_test.go](../internal/cms/save_sanitize_test.go)（保存経路のエコーバック、
  通常本文が変化しないこと）、[shell_test.go](../internal/cms/shell_test.go)（描画時サニタイズ）。
