**未実装**・**検討中**を明記し、第5章に集約します。仕様変更の際は正本を先に直し、本書は追随させます
（語彙モデルの設計の正本は [【考察】語彙モデル.md](【考察】語彙モデル.md)。本書 §2.5 は**要件だけ**）。

## 1. システムの目的と対象

### 1.1 目的と用途

- 入力項目が固定された帳票システムを排し、**Notion のように自由なブロックレイアウトで書いたページ＋
  PDF 原本**から、**見える文字（階層・ページ名・見出し・タグ）を手掛かりに**データベースが集計する
  CMS を提供する（[コンセプト.md](コンセプト.md) §1・§2）。
- 「顧客管理画面」「製品管理画面」のような固定のページ種別は持たない。すべてのページは同一構造の
  HTML であり、**ページの役割は階層とページ名でだいたい決まる**こと。集計に載せるかどうかは
  ブロック単位の印で決まる（[コンセプト.md](コンセプト.md) §1②）。
- **用途は2つあり、同じソフトウェアを別サーバー・別ドメインの2インスタンスとして運用する**
  （2026-08-16 決定）。

  | インスタンス | 用途 | 主な利用者 | 中心となる要件 |
  |---|---|---|---|
  | **業務インスタンス** | 社内の業務システム | 認証済みユーザーのみ | 受発注・進捗・原価/利益の記録と集計（§2.5） |
  | **サイトインスタンス** | 一般公開のウェブサイト | 匿名の訪問者＋編集者 | 公開ページの読み取り専用配信（§4.4） |

  - **データは完全に独立**する。`data/master`・`cms.db`・`auth.db` はインスタンスごとに別で、両者は
    ページを共有しない。したがって**業務データが公開面へ出る事故は、権限設定ではなく構成そのもので
    防がれる**（業務ページと公開ページが同じツリーに同居しない）。
  - **ソフトウェアは同一**（同じ単一バイナリ）。用途の差は**データと運用**で吸収し、インスタンスごとに機能を
    分岐させる作りは持たない。語彙（§2.5 のレジストリ）はデータなので異なってよい。**運用は2セットになる**
    （デプロイ・バックアップ・更新・初期管理者。§4.3）。

- **設置者は開発元に限らない**（2026-08-26 要件化。ユーザー:「プラグインを様々な企業やサイト
  運営者が自分で設置することは要件に含まれていますか？含まれていない場合、含めてください。
  **利用者は私のみではありません**」）。w-cms は複数の企業・サイト運営者がそれぞれの環境に
  設置して使うソフトウェアであり、**語彙とプラグイン（計算を含む）は設置した運用者が自分で
  追加できること**。開発元の業務語彙（受発注・部材など）は**同梱の既定セット**であって、
  コアの一部ではない（§4.5・[【考察】語彙モデル.md](【考察】語彙モデル.md) §11.3）。

### 1.2 業務ドメインと規模

- 業務システムとしての対象領域は、製造・加工業（部品加工／材料調達）の**受発注業務**。用語は視点に
  依らない役割語（受注／発注・販売見積／購入見積）で統一する
  （[【一覧】用語集.md](【一覧】用語集.md) §1）。
- **語彙（文書の種類・意味づけ）は最終的に100種規模を予定する**（現行実装は語彙レジストリの12形式。
  **カスタム要素は0種**＝2026-08-20 に全廃）。§2.5 の語彙モデルにより、語彙は**レジストリの宣言
  データとして増える**（現行の形式名は `data-type` 値。**見出しの言葉へ移す提案が検討中**——
  [【考察】語彙モデル.md](【考察】語彙モデル.md) §11・未決定）。「語彙を増やす／一覧を保守する／エディタから選ぶ」経路は、
  数十〜百のオーダーで破綻しない仕組みであることを要件とする（§2.2・§2.5・§4.5）。
- ウェブサイトとしては、公開ページが検索エンジンと一般の訪問者に晒されることを前提とする（§4.4）。

### 1.3 利用者

| 利用者 | できること |
|---|---|
| 認証済みユーザー | ページ権限（Unix風 read/write）の範囲で閲覧・編集 |
| グループ | ページの group クラス権限の単位（フラット・入れ子なし） |
| admin | root 相当。全権限バイパス・ユーザー/グループ管理・DB再構築・ロック強制解除 |
| 匿名の訪問者 | **実効公開ページのみ** read 専用で閲覧（＝一般公開サイトの読者） |

### 1.4 公開範囲と脅威モデル

- **どちらのインスタンスもインターネット公開を前提**とする。したがって強固な認証・HTTPS・レート制限・
  CSRF 対策を必須とする（[認証認可設計.md](認証認可設計.md) §0）。
- **業務インスタンスは匿名に対して何も見せない**。全ページ非公開（`public` を使わない運用）とし、匿名
  には存在情報も返さない（§2.1 の404統一）。業務データの露出は、権限設定ではなく**インスタンス分離と
  いう構成**で防ぐ（§1.1）。
- **サイトインスタンスでは匿名アクセスが常時の主要動線**である。未認証で到達できる面（公開ページの
  本文・子ページ一覧・親リンク・添付配信）は、**既定非公開＋明示的な公開操作**というフェイルクローズの
  原則で保護すること（§2.3）。下書き（非公開ページ）の存在も匿名には漏らさない（§2.1）。

## 2. 機能要件

### 2.1 ページ管理

- ページIDは**6桁ゼロ埋めの連番**とし、DBの `INSERT` 自動採番で原子的に確定すること（同時作成でも
  衝突しない）。
- 保存先は `data/master/{ID先頭2桁}/{ID}/` に分散配置し、1ページ＝1ディレクトリに本文 `<id>.html`・
  属性サイドカー `<id>.meta.json`・添付ファイルを格納すること。
- ページは**必ず親を持つ**。親なし（トップレベル）にできるのはトップページ `000000` のみ（admin でも
  例外なし）。子ページの作成は単一リクエストで採番→ファイル生成→DB同期→編集画面へのリダイレクトまで
  完結すること。親の付け替えは専用APIで行い、実在・自己参照/循環の防止・新しい親への write 権限を
  検証すること。
- 初期表示は**サーバー合成**とする（殻 `index.html` に本文とタイトルを埋め込んだ完成HTMLを返す）。
  チラつきが無く、JSを実行しないクローラでも本文が読めること。
  > **2026-08-20 に完全達成**——かつてはカスタム要素の中身がクライアント描画で、この要件は構造HTMLの本文に
  > 限って成立していた。移行で本文がすべて標準HTMLになり、最後まで残った動的部分（計算ビュー＝子ページ一覧・
  > 手配集計）も**サーバー事前描画**へ移したため、**閲覧はゼロJSで完結する**
  > （[アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §4.4）。
- 認可に応じた応答: 認証済み×read不可＝403、不存在＝404。
- **匿名に対しては「読めないページ」と「存在しないページ」の応答を区別しない**（どちらも 404。
  2026-08-16 決定・**2026-08-22 実装**。狙いは列挙対策ではなく、権限の無いアドレスを開いた
  社員が迷わないこと。404画面は**ログインへの戻り先つきリンク**を持ち、ログインしたその足で
  目的のページへ着く——これが無いと社員どうしのアドレス共有が行き止まりになる）。ページIDが連番であるため、応答が 302/401 と 404 で分かれると非公開ページ
  の存在・総数・作成ペースを外部から列挙できてしまう。画面・API（`/api/load`・`/api/page-meta`・
  `/api/children`・`/data/` 配信）のすべての匿名経路で揃えること。
  > 例外: 入口が失われないよう、トップ経由（`/` → `/000000`）のアクセスに限り従来どおり `/login` へ
  > 誘導してよい。ログイン画面自体は `/login` で常に到達可能。

正本: [アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §4〜§6・§8

### 2.2 エディタ

- **Notion風ブロックエディタ**を提供する: ドラッグ&ドロップによるブロック並べ替え、スラッシュメニュー
  （`/`）によるブロック挿入、ブロック単位のコンテキストツールバー。
- **ブロック挿入UIは100種規模に耐えること**（§1.2）。全件を並べた固定リストでは選べないため、**絞り込み
  入力・分類（カテゴリ）・使用頻度順**などで目的の形式に到達できる必要がある。選択肢と挿入される骨格は
  **語彙レジストリ（§2.5）から生成**し、語彙を増やすたびにフロントの markup やコードを手で足す運用に
  しないこと。形式を選ぶと列定義からヘッダ行つきの骨格を**機械的に生成**して挿入する（見出しの表示文字が
  鍵になるので、骨格が入れるのはレジストリ宣言のラベルそのもの。§2.5）。
  > **2026-08-26 に完成**（絞り込み・分類・頻度順。エディタ仕様 §3.1）。動的生成は 2026-08-17 実装（`populateSlashMenuVocab` が `/api/tag-schema` の
  > `vocab` から項目と骨格を生成し、殻に残る手書き項目は `h1`・`p` の2つだけ）。残っていた絞り込み
  > 入力・分類・使用頻度順による到達性も入り、全項目を1列に並べる形は解消した。
- **汎用表エディタ**（2026-08-16 要件化 → **2026-08-17 v1・2026-08-19 拡張を実装済み**。残りは
  date/image の入力補助のみ——image は §2.6 の画像アップロード実装待ち。仕様の正本は
  [エディタ仕様.md](エディタ仕様.md) §3.2）: `data-type` 付きの表・定義リストの編集（セルの直接編集・
  行の追加/削除/並べ替え・列設定UI・列型に応じた入力補助）は、**型の数に対して不変の汎用実装**とすること。
  型ごとの JavaScript を書かない。列型は当面 `text`／`number`／`date`／`enum`（ドロップダウン）／`image`
  （セル内への添付画像挿入。§2.6 と接続）を想定し、原則**見出し語から推論**する（`金額`→通貨、`数量`→数値
  など、語→型の辞書はレジストリの一部）。`th data-type` の明示と
  ③計算形式のレジストリ宣言が推論に優先し、型に合わない入力は**通知**（背景色など）に留めて拒否しない。
  **機械属性（`th` の `data-type`＝列型の明示）が見出しからの型推論に優先している箇所は、編集モードで
  背景をハイライト**し、見えている文字が型として使われていないことを利用者に示すこと（型不一致の通知＝
  赤とは別の色。閲覧・公開ページには出さない）。
- **レジストリが無くても既存文書の編集が壊れないこと**（2026-08-16 整理）。レジストリが要るのは新規挿入
  （列定義の全体から骨格を生成）と入力補助・検証（enum の選択肢・解決できない見出しへの告知）だけで、
  既存ブロックの編集には要らない——表の鍵と型は見出し行が運ぶ（鍵は**見出しテキスト**、型は
  `th data-type` があればその値・無ければ**型推論**。§2.5）ため、文書自身が運ぶ情報だけで編集が成立する
  （3原則の整理は [【考察】語彙モデル.md](【考察】語彙モデル.md) §7）。
- **オートセーブ**を提供する: 入力のデバウンス（1〜2秒）とブロックの `focusout` で自動保存。変更が無ければ
  何も送らず、1ブロックのみの変更はブロック単位（`/api/save-block`）、それ以外は全文保存（`/api/save`）へ
  自動で振り分けること。保存状況（未保存／保存中／保存済）を常時表示すること。
- **編集中のアンドゥ・リドゥ**を提供する（Ctrl+Z / Ctrl+Y、スナップショット上限100、キャレット位置も
  復元）。履歴は編集モードのセッション限りとする。
- インライン装飾（太字・斜体・下線）は `document.execCommand` を使わず自前の Range 操作で実装し、出力は
  常に `<strong>`/`<em>`/`<u>` に正規化すること。
- **エディタが扱える語彙（要素・属性）はサーバーの1箇所を正本**とし、`GET /api/tag-schema` で受け取る
  こと。エディタ側に手書きの要素リストを置かない（許可済み要素が保存時に黙って消える不具合の再発防止）。
  同APIは語彙レジストリの形式定義（`vocab`）と語→型の推論辞書（`type_inference`）も返す（§2.5。
  2026-08-17／08-19 実装済み）。
- 実装は**バニラJS・ビルド工程ゼロ・追加ライブラリなし**とし（§4.5）、**新規カスタム要素は作らない**
  （§2.5。`web-components.js`・`assets/templates/`・`components.css` は撤去済み）。新規コードでインライン
  `script`/`style`/`on*=` を書かないこと（[開発方針.md](開発方針.md) §4）。
- 画面は4カラム（左レール＝階層／目次レール／文書／右レール＝ページ情報・権限）＋ヘッダー・フッター帯。
  狭幅（≤760px）ではレールをドロワー化すること。保存されるのは本文（`#w-editor-content`）のみで、
  クロームは保存しない（**殻の `id` は接頭辞 `w-` を独占する**。本文側の `w-` 付き `id` は剥がされ、
  後戻りは [shell_id_test.go](../internal/cms/shell_id_test.go) が検出する）。

正本: [エディタ仕様.md](エディタ仕様.md)、[【一覧】用語集.md](【一覧】用語集.md) §2（画面各部の呼び名）

### 2.3 認証・認可

- 認証は**アプリ単体管理**（SSOへ委譲しない）。パスワードは argon2id でハッシュし、総当たり対策
  （バックオフ／ロックアウト）とユーザー列挙対策（存在しないユーザーでも同じ計算量を消費）を備えること。
- セッションは 256bit トークン（DB側はハッシュ保存）、Cookie は `HttpOnly`/`Secure`/`SameSite=Lax`、
  **「最後の操作から8時間」で失効**すること（アイドル基準へ一本化。失効の数分前に画面で告知する）。
  **2026-08-21 決定・未実装**——2026-06-20 の「絶対8時間／アイドル30分」を上書き。経緯とトレードオフは
  [認証認可設計.md](認証認可設計.md) §2.2a。
- 初期管理者は環境変数（`WCMS_ADMIN_USER`/`WCMS_ADMIN_PASSWORD`）で、ユーザーが空のときのみ作成すること。
- 認可は**ページ単位の Unix 風モデル**: read/write の2ビット × owner/group/other の3クラス（mode は
  `"330"` のような3桁文字列）。子ページ作成には親ページの write を要求する（ディレクトリ書き込み相当）。
  chmod/chgrp は owner または admin、chown は admin のみ。
- 権限の正本は**サイドカー `<id>.meta.json`** とし、書き込めるのは権限変更APIとページ新規作成のみ。
  本文保存APIは権限に一切触れないこと（自己認可の構造的防止）。
- **匿名公開**は mode と独立した `public` フラグで制御する。実効公開＝自分の public ∧ 全先祖の public
  （パスゲート）とし、ルート `000000` の非公開化がサイト全体のキルスイッチになること。新規ページの
  `public` は常に false（フェイルクローズ）。匿名は read 専用。
- 書き込み・権限変更の**監査ログ**を記録し、admin が閲覧できること。**認証イベント（ログインの成功・
  失敗・ログアウト）も記録対象に含める**（2026-08-21 決定・**2026-08-25 実装**）。
  ユーザーの言葉:「**誰が事務所の外から入ってきたか知る必要があると思います。**」——「どこから」を
  満たすため、認証イベントには**接続元アドレス**も残す。本番はリバースプロキシの背後で動くので
  `X-Forwarded-For` を見るが、**詐称できないよう、前段がプロキシ（ループバック／私設アドレス）の
  ときだけ採用し、末尾＝直近のプロキシが足した値**を使う。ページの新規作成（`new-page`）・添付の
  保存と上書き（`attach` / `attach.overwrite` と区別する。添付は上書きが復元できないため）・索引の
  全再構築（`rebuild-db`。取り込み件数つき）も同時に記録対象へ入れた。なお**「5年遡れること」は
  監査ログでは満たさない**——§3 の保持年限を参照。

正本: [認証認可設計.md](認証認可設計.md)

### 2.4 同時編集の直列化

- **ページ単位の悲観ロック＋SSE** により、複数人（同一ユーザーの別タブを含む）が同時に開いても
  lost update が起きないこと。保持者はエディタ個体（トークン）で識別する。
- 本文保存だけでなく、権限変更・所有者変更・親付け替え・公開切替・**添付のアップロード**・**ページ削除**
  も同じロックで直列化すること（共通ゲート `RequireEditLock`／フロント共通ラッパ `lockedFetch`）。添付は
  2026-08-21 に追加——他人が編集中のページへ第三者が添付を足せていた。
- ロック取得成功時は**最新の生HTMLを同梱**し、古い版からの編集開始を防ぐこと。他者保持中は 423 を返し、
  待機者はSSE通知で解放を検知して自動的に編集モードへ移行すること。無競合なら無期限、待機者が現れたら
  2分の猶予で強制明け渡し。admin は強制解除できる（監査記録あり）。ロックは単一プロセス内の揮発的状態で
  よい（再起動での消失は許容）。

### 2.5 語彙モデルと業務機能（プラグイン）

> **設計の正本は [【考察】語彙モデル.md](【考察】語彙モデル.md)**——語彙の3分類は同 §3、
> 語彙と拡張の3層モデル（①語彙レジストリ ②汎用索引 ③計算プラグイン）は同 §4、表と定義リストの

> **本節は「要件として何を満たすか」だけを書き、分類表・例・経緯は正本に預ける。**
> **2026-08-20 に移行完了**——本文の語彙は「標準HTML＋`data-*` マーカー」に完全統一され、
> カスタム要素は0種、形式の宣言は語彙レジストリ（[vocab.go](../internal/cms/vocab.go)・12形式）が
> 持つ。**残る未実装は参照系だけ**（受信元・前版の参照マーカーと参照追従JOIN。
> [【考察】通信記録処理.md](【考察】通信記録処理.md) §2.5 の設計待ち）。

#### (1) 語彙モデルが満たすこと

- **追加コストに段差を付ける**——記録・表示だけの語彙（100種の大半・§1.2）は**①語彙レジストリへの
  宣言1件（データ）**で完結し、**開発者がボトルネックにならない**こと。②汎用索引（全
  `table[data-type]`／`dl[data-type]` を汎用テーブルへ同期）はコアに一度だけ実装する。③計算
  プラグイン（Goコード）が要るのは計算・取り込み変換を伴う語彙だけで、数は10個未満に保つ（§4.5）。
- **未知の `data-type` を通す**（2026-08-16 決定）——レジストリ未登録の種別もサニタイズは拒否せず、②の汎用索引にも
  載せる。保存時に「未定義の種別です」と**通知**する（エコーバックの流儀——拒否でなく告知）。落とす方式はレジストリを
  安全性の門に変質させ、レジストリを実行時編集可能にする道（下の (4)）を塞ぐため採らない。
- **見出しの改名を告知する**——表は**自己記述**とし、**列の鍵は見出しの表示文字**（`th`／`dt`）ただ1つと
  する（2026-08-20 改定。当初の「`data-field` があればその値」は、鍵の解決が元々レジストリのラベル経由で
  成立しており冗長だったため属性ごと撤去した）。③計算形式では見出しの表示文字がレジストリ宣言のラベルに
  一致して機械キーへ解決されるので、**改名するとその列は計算に読まれなくなる**——黙って止まらないよう、
  解決できなくなった列を**保存時に告知**すること（拒否はしない）。
- **レジストリを安全性の門にしない**——サニタイザの許可リスト（要素・属性名）は従来どおりコード側で
  固定し、`data-type` は属性**名**を許可して**値は不活性な文字列**として扱う。**w-cms がその要素を
  見て何かする（DB保存・描画・配線・入力補助）要素にだけ `data-type` を許可していく**（型名としての
  `data-type`・2026-08-20 決定）。この分離があるから、レジストリを将来実行時編集可能にしても危険な
  要素は増やせない。
- **マーカーは `class` でなく `data-*`** とする（サニタイザの `class` 全面拒否に例外を作らない・
  見た目のフックと機械可読の役割の分離・殻のDOMのセレクタと衝突しない）。
- **語彙の単一正本を1つのAPIで配る**——①のレジストリと③のプラグイン宣言（計算型の列定義は `Sync()`
  と同じ宣言から導く。エディタが書く見出しラベルと同期が読む機械キーのずれを構造的に防ぐため）を
  合成し、**単一のAPI**（`/api/tag-schema`）としてエディタ・語彙一覧の生成へ届けること。
- **新しいカスタム要素（Web Components・`<m-*>`）は作らない**（2026-08-17 決定・2026-08-20 に移行完了で
  0種）。動的な振る舞いは編集モードのクローム（エディタ）・閲覧ビューのエンハンサ（バニラJS）・サーバー事前
  描画が担う。理由（閲覧ゼロJS・生HTMLの自己説明性・語彙の増加コスト最小化・テンプレート機構由来のXSS経路と
  インライン `style=` の消滅）は [【考察】語彙モデル.md](【考察】語彙モデル.md) §9 の決定ログ。最後の理由の
  帰結として **CSP strict 化も完了した**（§4.1）。
- **写真・画像は語彙ではなく内容**であり、標準HTML（`<img>`）だけで完結する（§2.6）。意味を持たせたい
  ときに初めて語彙側と接続する（例: 表の `image` 列＝レジストリのデータ、撮影画像→明細表の変換＝
  計算プラグイン）。
- ②の汎用索引にも「ファイルから再生成できないデータを持たせない」不変条件（§3）を適用する。

#### (2) 挿入経路の不変条件

貼り付け変換・ファイル取り込み変換・デバイス起点・他ページ参照・計算ビュー・雛形/複製・エディタ外生成）はプロデューサー
の違いにすぎず、**語彙の単一正本を迂回する経路を作らないこと**。経路ごとの例と位置づけは [【考察】語彙モデル.md](【考察】語彙モデル.md) §6、未実装の経路は §5 に集約する。

### 2.6 添付ファイル

- ページへ PDF を添付できること。受け入れはサーバーで強制する: リクエスト32MiB上限・中身の先頭
  `%PDF-` 必須・ファイル名の正規化（パス要素や制御文字の拒否、本文・サイドカーと同名の拒否）。
- **ページへ画像を添付できること（2026-08-16 要件化・2026-08-26 実装）**。ウェブサイト用途（§4.4）で本文に
  画像を表示するため。PDF と同じ入口・出口の二層で守る。
  - **許可する種類は `png`・`jpeg`・`webp`・`gif`・`svg`**。ラスタ画像は拡張子だけでなく**中身のマジックナンバーを
    検証**する（PDF の `%PDF-` 検査と同じ考え方）。サイズ・名前の規則は PDF と共通（32MiB・ファイル名正規化・
    本文/サイドカー名の拒否）。必要なら画像固有の上限（ピクセル数等）を実装時に追加してよい。
  - **配信はインライン表示を許可**する: 検証済みの画像種別に限り、実際の種別に対応する `Content-Type`（`image/png` 等）を
    明示して返す（`nosniff` は維持）。それ以外の種別が「PDF以外はダウンロード扱い」のままであることは変えない。本文からは
    **絶対パス**（`<img src="/data/master/00/000012/写真.png">`）で参照する——ページのアドレス（`/000012`）からの
    相対名はページの隣ではなくサイトのルートを指してしまうため。サニタイザは埋め込みの絶対パスを `/data/` 配下に
    限って許可しており（2026-08-21 決定）、この形はその許可範囲そのもの。URLの組み立ては `page.DataURLFor` が担う。
  - **SVG は「不活性な画像」として許可する**。スクリプトを内包できる文書形式なので中身の完全なサニタイズは行わず、
    **埋め込み方と配信の二層で無害化**する: ①本文からの表示は `<img src="x.svg">` 経由のみ（**画像コンテキストでは
    ブラウザ仕様としてスクリプトが実行されない**。外部取得・対話も不可。インライン `<svg>` は従来どおりサニタイザが
    部分木ごと削除する）②配信（`DataFileHandler`）は `Content-Type: image/svg+xml` ＋ `Content-Disposition: attachment`
    （**直接開くと描画せずダウンロード**。`<img>` のサブリソース読み込みはこのヘッダを無視するので表示は影響を受けない）
    ＋このレスポンス限定の `Content-Security-Policy: sandbox; default-src 'none'`（万一描画されても別オリジン扱い・全実行
    禁止）③入口では well-formed XML でルートが `<svg>` であることを検査し、`<script>`・`<foreignObject>`・`on*=`・
    `javascript:` を含むファイルを拒否する（安全性の本体は②の配信側で、こちらは多層防御の網。Go の XML パーサは外部
    実体を解決しないため XXE の心配は無い）。代償として SVG 内の対話性は動かない（ロゴ・図版用途を想定）。
  - **将来: SVG 編集アプリ（構想・§5）**。SVG が「閲覧する画像」から「編集対象の文書」になった時点で、扱いを
    不活性画像から**編集器の語彙への許可リストサニタイズ**へ拡張する（本文HTMLと同じ流儀——語彙はサーバーの
    1箇所が正本で、編集器が知らない要素は取り込み時に落ちる。「任意のSVGの完全な保全」は目標にしない）。
    語彙が確定すればインライン `<svg>` の解禁も同じ許可リストで判断できる。
  - **エディタに画像の挿入手段を用意する**: ドロップ／ファイル選択に加え、**モバイル端末ではカメラで
    撮影してその場で挿入できること**。実現はOS標準のカメラUI（`<input type="file" accept="image/*">`
    ＋ `capture`）でよく、独自のカメラ画面（`getUserMedia`）は要件としない。挿入後は本文に `<img>` が
    入り、通常のオートセーブに乗る。表の `image` 列（§2.2）のセル内挿入も同じ機構を使う。
  - **EXIFメタデータは保存時にサーバーで除去する**。カメラ写真には撮影位置（GPS）・撮影日時・機材情報が埋まって
    おり、公開サイトに載ると撮影者の所在が漏れる。除去はアップロード経路の一律処理とする（公開時に選別する
    方式にしない——フェイルクローズ）。回転情報（orientation）を捨てる場合は画素の向きを補正してから保存し、
    表示が横倒しにならないこと。**帰結**——撮影日時・撮影場所を業務データとして使う場合、EXIF から拾う設計に
    はできない。必要ならアップロード受付時刻をサーバーが記録するか、利用者が表の `date` 列へ入力する
    （検査記録など「いつ撮ったか」が意味を持つ用途で意識すること）。
  - iOS のカメラ写真は HEIC 形式の場合がある（file input 経由では通常 JPEG に変換されて届く）。
    **HEIC が届いた場合は許可リスト外として拒否し、理由を利用者へ表示する**（サーバーでの変換は
    要件としない）。
  > **実装メモ（2026-08-26）**——入口は `POST /api/upload-image`（`internal/cms/upload_image.go`）、
  > 検査と無害化は `internal/cms/image.go`、配信は `page.DataFileHandler`。外部パッケージは使っていない
  > （開発方針 §1）——JPEG は標準の `image/jpeg` で復号→向き補正→再符号化するため、その過程で EXIF・XMP・ICC が
  > すべて落ちる。PNG と WebP は容器の塊（チャンク）を歩いて `tEXt`/`zTXt`/`iTXt`/`eXIf`/`tIME`・`EXIF`/`XMP ` だけ
  > 落とす（`gAMA` など見え方に関わる塊は残す）。GIF は EXIF を持たない。**画素数の上限は設けていない**
  > （32MiB のサイズ上限のみ）——必要になったら足す。**HEIC/AVIF/TIFF/BMP は拒否の理由を形式ごとに返す**
  > （「許可リスト外です」だけでは、写真が入らない人が次に何をすればよいか分からないため）。
  > 挿入は3つの入口（スラッシュメニューの「🖼 画像」・本文へのドロップ・`image` 列のセル）が同じ関数を通る。
  > 検証は Go テスト（`image_test.go`・`upload_image_test.go`）と E2E（`e2e/verify-image.js`）。
- 添付の配信（`GET /data/...`）は静的配信ではなく**ページの read 権限を要求する保護ハンドラ**とし、
  `nosniff` 付与・許可種別以外はダウンロード扱い・本文とサイドカーは配信しないこと（権限昇格・
  保存型XSSの防止。経緯は [変更履歴.md](変更履歴.md) 2026-08-05）。

## 3. データ要件

- **正本はファイル、DBは派生インデックス**。`data/master/` 配下が唯一の正データであり、`data/cms.db`
  は検索・集計のための使い捨てキャッシュとする。**DBにはファイルから再生成できないデータを一切
  持たせない**（不変条件。プラグイン追加時も、§2.5 の汎用索引にも適用する）。
- 内容と属性を分離する: HTML本体 `<id>.html`＝内容、サイドカー `<id>.meta.json`＝属性
  （owner・group・mode・public・parent_id・作成/更新情報）。
- 認証情報 `data/auth.db` だけは**再生成不可**であり、DB再構築の対象外とする。
- **バックアップ対象は `data/master/` 全体＋ `data/auth.db`**。`cms.db` は対象外（復元時に再生成）。
- SQLite は Pure Go ドライバ（CGO不要）を用い、`journal_mode=WAL`・`busy_timeout`・`foreign_keys`
  を適用すること。
- **日時の表記は ISO 8601 を w-cms 全域の正とする**（2026-08-30 決定。ユーザー:「時刻は
  ISO-8601とします。w-cms全域で使用しますが、**利用者がプラグインなどで別表記に対応するのを
  妨げるものではありません**」）。日付のみは `YYYY-MM-DD`（ゼロ詰め）、時刻付きは **`T` 区切り**
  （空白区切りは ISO 8601 ではない——SQL リテラルの流儀）。ゼロ詰めISOは文字列比較＝時系列順に
  なり SQLite の日付関数にもそのまま通る（実測は [【一覧】日付形式と数詞.md](【一覧】日付形式と数詞.md)）。
  別表記（和暦・スラッシュ等）は**入り口（取り込み・正規化）で受けて ISO へ揃える**ものであり、
  内部表現としては使わない。プラグインによる別表記の入出力対応は運用者の自由。
- **帳票の保持年限は5年**とし、これは監査ログではなく**保存済み文書の版管理（リビジョン／リバート）で満たす**
  （2026-08-21 決定・**2026-08-26 実装**）。保持は**全ページ一律**——帳票だけに絞るには「どれが帳票か」の
  判定が要り、その判定がずれると保持義務のほうが破れるため。年限で切る際、うるう年で目減りしないよう
  366日で数え、端数は必ず**長い側**へ倒す。ユーザーの言葉:「**あとから編集者を調べたくなる場面はあります。日本は
  5年間の帳票保持義務があるので、5年保存できるとありがたい。しかし、監査記録に残すというより、文書のアンドゥ―
  リドゥ―で残すほうが良いと思います。これは今すぐ実現しなくても良いです。**」監査ログで満たさない理由は、記録の
  性質の違いに加えて**実測**にもある——手元の実データでは監査記録 587件中 529件（90%）が編集中の自動保存で、
  管理コンソールの「最近200件」は**約4時間分しか遡れていなかった**。設計は
  [【考察】アンドゥ・リドゥ.md](【考察】アンドゥ・リドゥ.md) §4・§5。

## 4. 非機能要件

### 4.1 セキュリティ

- **本文サニタイズは二層**（保存時＋描画時）の許可リスト方式とし、サニタイザは冪等であること
  （`Sanitize(Sanitize(x)) == Sanitize(x)`）。保存時は除去結果をエディタへエコーバックして
  利用者に通知すること。
- 方針は「**タグは寛容・属性は厳格**」: 構造HTMLは h1〜h6・リスト・ルビ・表・`details`・
  `video`/`audio` まで広く許可する一方、`script`/`style`/`iframe`/`form` 系は部分木ごと削除、
  `on*`・`style`・`id`・`class` 属性は常に拒否（例外は `data-id`。§2.5 の語彙モデルでは
  `data-type` の属性**名**が加わるが、**値は不活性**でありレジストリは安全性の判断に関与しない）。
  > **検討項目（2026-08-16）→ 決定済み（2026-08-21・§5）**: この規則のもとでは本文にレイアウト・装飾を書く手段が無い。
  > 公開サイト（§4.4）でのデザイン表現について、**決定（2026-08-21・ユーザー）: 3案から1つを選ぶのではなく、複数を
  > 併用する。**「テンプレートHTMLの編集と、テーマCSS、classの許可リストがいずれ必要と思います。」——2026-08-16 に立てた
  > 「①表示専用の `data-type` 形式（レジストリへ宣言を足し、装飾はテーマCSS側で当てる。当初案の『表示専用カスタムタグ』は
  > カスタム要素廃止により読み替え）／②`class` の**許可リスト**（任意クラスではなく、定義済みユーティリティ名だけ通す）／
  > ③サイト全体のテーマCSS（本文は構造のみ、装飾は殻側で完結）のどれか1つを選ぶ」という**立て方そのものが誤りだった**
  > （①②③の内容自体は生きているので記録として残す）。必要な手段はこの3つに**④テンプレートHTMLの編集**（ユーザーが
  > 新たに挙げた4つ目）を加えた4つで、**いずれも未実装**。評価軸は変わらない——サニタイズの「属性は厳格」原則を壊さずに
  > 実現できるか。加えて④だけは**本文サニタイズの外側＝殻**を触るため、誰が編集できるか（admin 限定か）・保存時に何を
  > 検証するかという論点が新たに要る。現状の殻は `assets/index.html` の1ファイル固定で、サーバーは本文とタイトルを文字列
  > 置換で差し込むだけ（[shell.go](../internal/cms/shell.go) の `shellPath`・`contentPlaceholder`・`titlePlaceholder`）
  > ——**差し替える／編集する手段は無い**。殻も CSP strict の下にあり、テンプレートへインライン `script`/`style` は
  > 書けない。
- URL規則は2種類: リンク（`href`・`cite`）は相対・http・https・mailto・tel を許可、
  **埋め込み（`src`・`srcset`・`poster` 等）は相対のみ**。`javascript:` 等のスキームと
  プロトコル相対URL（`//host/…`）は拒否。
- **CSP を全レスポンスへ付与**する。**2026-08-19 に strict 版へ到達**
  （`default-src 'self'; script-src 'self'; style-src 'self'; object-src 'self'; base-uri 'self'; frame-ancestors 'self'`。
  `'unsafe-inline'` を含まない）。インラインの `script`/`style`/`on*=` はリポジトリ全体でゼロで、
  後戻りは [csp_test.go](../internal/auth/csp_test.go) が検出する
  （ポリシーと理由は [本文サニタイズ設計.md](本文サニタイズ設計.md) §6）。
- **CSRF は Origin/Referer とリクエストホストの一致検証**（GET/HEAD/OPTIONS 以外に適用、ヘッダが
  無ければ安全側で拒否）＋ `SameSite=Lax` の併用。あわせて、**状態を変えるエンドポイントは GET を
  受け付けないこと**——Origin 検証は GET に掛からないので、GET で状態が変わる口が1つでもあれば本文に
  `<img src="…">` を1つ保存するだけで発火する（**保存型CSRF**。実際に `/api/logout` で「そのページを
  開いた全員を無音でログアウト」が成立していた）。2026-08-21 に `/api/new-page`・`/api/logout` を
  POST 限定へ移し、固定は [method_guard_test.go](../internal/cms/method_guard_test.go)。
- フロントでテンプレートへ値を差すときは必ず `escapeAttr` を通すこと（サニタイザでもCSPでも止まらない保存型
  XSS経路。経緯は [変更履歴.md](変更履歴.md) 2026-08-04）。§2.5 の語彙モデル（値を属性でなく中身に置く＝
  テキストノードはDOMが自動エスケープ）は、この失敗の余地そのものを構造的に減らす。
- 本番は**TLS/HTTPS 必須**（リバースプロキシで終端）。Secure Cookie の無効化
  （`WCMS_SECURE_COOKIES=0`）はローカル検証専用とする。

正本: [本文サニタイズ設計.md](本文サニタイズ設計.md)、[認証認可設計.md](認証認可設計.md) §0.1・§2.3

### 4.3 デプロイ・運用

- **単一バイナリ**で配布・起動できること（`go build`、クロスビルド可）。待受は `:8080`。
- 本番想定は VPS（2 CPU / 2GB RAM / Linux・systemd）＋リバースプロキシ（Caddy/nginx）。
  argon2id のピークメモリはログインの同時実行制限（セマフォ4件）で約256MiBに抑える。
- **設定の受け渡しは環境変数のみとする**（2026-08-16 決定）。アプリは設定ファイルを読まず、コマンドライン
  フラグも持たない。インスタンスごとの設定一覧は、アプリではなく**運用側**が systemd の `EnvironmentFile=`
  （`KEY=VALUE` を並べた1ファイル。例 `/etc/w-cms/site.env`）で持つ。理由: アプリ実装が最小で済む・秘密情報が
  リポジトリやバックアップへ紛れる事故が構造的に起きにくい・2インスタンス運用と素直に噛み合う。
- **設定項目の一覧（本表が正本）**。追加するときは `WCMS_` 接頭辞で命名し、本表を更新する:

  | 環境変数 | 意味 | 既定値 | 状態 |
  |---|---|---|---|
  | `WCMS_ADMIN_USER` / `WCMS_ADMIN_PASSWORD` | 初期管理者（`users` が空のときのみ。作成後は外す） | なし | 実装済み |
  | `WCMS_SECURE_COOKIES` | `0` で Secure Cookie を無効化（ローカル検証専用・本番禁止） | 有効 | 実装済み |
  | `GEMINI_API_KEY` | PDF明細抽出（§2.5）のAPIキー。未設定なら当該機能はエラー | なし | 実装済み（業界慣行名のため `WCMS_` 接頭辞の例外） |
  | `WCMS_BASE_URL` | サイトの基底URL（`https://example.com`）。canonical と `sitemap.xml` の絶対URLに使う。**未設定ならリクエストから組み立てる**（`X-Forwarded-Proto`/`-Host` は前段がプロキシのときだけ採用）。正規表記を1つに固定したい運用（www 有無・http/https の揺れを避けたい）で設定する | なし（リクエストから導出） | 実装済み（2026-08-26・§4.4） |
  | `WCMS_ADDR` | 待受アドレス（`host:port`）。リバースプロキシと同居するなら `127.0.0.1:8081` のようにローカルへ束縛できる | `:8080` | **未実装（§5）** |
  | `WCMS_DATA_DIR` | `data/` の場所 | 実行時カレントディレクトリ直下の `./data` | **未実装（§5）** |

- 環境変数方式は「いま何が効いているか」が見えにくいため、**起動時に有効な設定を1行ログへ出す**こと。
  ただし**秘密情報は値を出さない**（アドレス・データディレクトリ・Secure Cookie の有無・Gemini キーの
  **有無**のみ）。
- `data/` は既定で実行時カレントディレクトリ直下に自動生成される（systemd では `WorkingDirectory=`
  を明示）。
- **2インスタンス運用**（§1.1）: 業務用とサイト用を**別サーバー・別ドメイン**で動かし、バックアップ・初期
  管理者・更新もインスタンスごとに行う。**Cookie・セッションはドメイン単位で自然に分離**されるので、編集者が
  両方を使う場合はアカウントをそれぞれで作成する。同一ホストに同居させる場合は `WCMS_ADDR`・`WCMS_DATA_DIR`
  で分離する（どちらも未実装・§5）。

### 4.4 公開ウェブサイトとしての要件

**サイトインスタンス**（§1.1）に効く要件群。社内システムとしては不要だったが、一般公開サイトとして使う以上は
必要になる。現状はいずれも未達（§5 に再掲）。ソフトウェアは業務インスタンスと同一なので、ここでの改善は
業務側にも入るが害はない。

- **公開ページの見え方**: 公開ページは編集用クロームを含まない体裁で届くこと（**2026-08-26 実装**）。
  匿名の要求には**公開専用の殻**（`assets/public.html` ＋ `assets/public.css`）を返し、認証済みには
  従来どおり編集できる殻（`assets/index.html`）を返す。分岐は認証済みかどうかの1点だけで、
  実効公開の判定は手前の認可（`requirePageViewable`）が済ませている。
  公開専用の殻は**スクリプトを一切読み込まない**——閲覧はゼロJSで完結する（§2.1）ので、
  訪問者へ配る理由が無い。後戻りは `TestPublicShellShipsNoScript` が検出する。
  - **開いた瞬間のちらつきを消すこと**（2026-08-21 決定・**2026-08-25 実装**）。未ログインで公開ページを開くと、
    ログアウトボタン・編集スイッチ・「保存されるHTML」の欄が**一瞬映ってから消えて**いた——隠す手順が
    `/api/me` の応答後にあったため（`body.anonymous` が付いて初めてCSSが隠す）。**情報は漏れていない**
    （中身は空で、見た目だけの問題）。ユーザーの言葉:「**治しておいてください**」。
    直し方は、**印をサーバーが刻む**こと——`RenderPageShell` が匿名の要求に対して
    `<body class="anonymous">` を返すので、最初の描画からCSSが効く（JS側も従来どおり付ける。冪等）。
    ただしこれは応急処置であり、**本筋は本節の公開専用ビュー**（クローム自体を配信しない）のほう。
- **SEO・SNS共有**: ページごとの `<title>` に加え、`description`・OGP・正規URL（canonical）・
  `sitemap.xml`・`robots.txt` を提供できること。**非公開ページをクロールさせない**ことも同じ要件に含む。
  **2026-08-26 実装**。
  - `description` は**本文の最初の段落**から作る（120字で切る）。人が別途書かなくても成立させるため。
    見出しは題名と重複するので使わない。段落が無いページでは `description` を出さない
    （中身の無いタグを出すより良い）。
  - `sitemap.xml` に載るのは**実効公開のページだけ**で、判定は認可と同じ `page.EffectivePublic` を通す。
    ここに独自の判定を書くと、認可とずれた瞬間に**非公開ページのアドレスを sitemap が外へ配る**。
  - `robots.txt` は**サイト全体が非公開なら全面拒否**（`Disallow: /`）を返す。業務インスタンスは匿名に
    何も見せない運用（§1.4）なので、クローラにも入らせない。判定はトップページの実効公開で行う
    ——トップが非公開ならパスゲートで配下も全部非公開になるため、これが「サイトが閉じているか」と同義。
    索引が使えないときも閉じている扱いにする（フェイルクローズ）。
  - 絶対URLの基底は `WCMS_BASE_URL`（§4.3）を最優先し、無ければリクエストから組み立てる。
- **キャッシュ**: 公開ページは匿名向けにキャッシュ可能な応答（`ETag` を含む）を返せること。ただし
  **非公開ページや認証済み応答をキャッシュさせない**ことが絶対条件。**2026-08-26 実装**。
  - キャッシュ可能にするのは**匿名 × 実効公開のページ応答だけ**（`public, max-age=600` ＋ `Vary: Cookie`
    ＋ `ETag`。`If-None-Match` が一致すれば 304）。それ以外は `no-store` のまま——認証済みのページ応答・
    匿名が読めないページの 404・要認証API（`RequireAuth` の入口で一律に付与）・`/api/me`。
    **API ごとに付けるとどれか1本が漏れる**ので、入口でまとめて付けている。
  - **公開／非公開の切り替えが外から見えるまでの許容遅延は10分**とする（2026-08-21 ユーザー決定。**従来の
    「即座に反映されること」を上書きする**——即座を要件にするとキャッシュが一切効かないため）。ユーザーの言葉:
    「キャッシュにとって必要な時間を知りませんが、10分程度でどうでしょう？」——**技術的な検討の裏付けを
    持たない暫定値**。値は `publicCacheSeconds`（[handler_sitemap.go](../internal/cms/handler_sitemap.go)）の1箇所。
  - この10分は**非公開へ切り替えた側にも同じだけ効く**（いったん公開したページは、非公開へ戻してから
    最大10分は外から見えうる）。「公開→非公開だけは即時失効させる」という非対称な設計を採るか、という
    実装時の判断は——**採れない**。いったん配った応答は取り消せないので、原理的に作れない仕組みです。
    即時性が要るなら `publicCacheSeconds` を 0 にして毎回再検証（ETag で 304）へ倒すのが現実的な選択肢で、
    それでも帯域は節約できます。**サーバー側の状態は即時**なので、キャッシュを持たない相手（初回訪問者・
    クローラ・`sitemap.xml`）には非公開化がその場で効きます。
- **公開面の負荷とレート制限**: 匿名アクセスは不特定多数から来る。リバースプロキシ側のレート制限
  （[【ガイド】デプロイ・運用.md](【ガイド】デプロイ・運用.md) §6.2）を前提としつつ、1リクエストあたりの
  サーバー処理（サーバー合成・描画時サニタイズ）が公開ページで過大にならないこと。
- **エラー画面**: 404・403 が一般の訪問者にも意味の分かる体裁であること（**2026-08-26 実装**。
  404 は 2026-08-22 に入れた「ログインへの戻り先つき」画面、403 は同じ体裁で理由と次の手を出す。
  なお **403 を見るのはログイン済みの利用者だけ**で、匿名には 404 へ統一されている＝§2.1）。
- **アクセシビリティ・サイト内検索**: どちらも「**出来る限りやる程度の要件とします**」（2026-08-21 ユーザー
  決定・原文のまま）。＝**努力目標**として要件に含め、達成しなければ公開できない類の必達要件としては扱わ
  ない。現状——**サイト内検索は未実装**（検索のエンドポイントも画面も存在しない）。画面読み上げ対応は殻に
  `aria-*` が散発的にあるだけで、体系的な対応は**未着手**。
- **運用要件（アクセス記録・可用性目標・バックアップの RPO/RTO）**: 「**定めるが、いまではない**」（2026-08-21 ユーザー
  決定・原文のまま）。要件として持つこと自体は確定で、**値を決めるのは公開サイトの運用設計に入る時点**とする。現状——
  サーバーが出すログは起動・エラーの通知だけで、**リクエスト単位のアクセスログは無い**（書き込みと権限変更の監査記録は
  auth.db の `audit_log` にあるが（§2.3）、閲覧アクセスの記録ではない）。バックアップの**対象**は §3 で確定済みだが、
  **どこまで戻せるべきか（RPO）・どれだけで復旧すべきか（RTO）・止まってよい時間（可用性目標）は未定義**。

### 4.5 拡張性（100種規模の語彙）

- **語彙の追加コストに正しい段差を付けること**——要件の本文は §2.5 (1)（記録・表示だけの語彙＝①レジ
  ストリへの宣言1件・再デプロイ不要が目標／計算が要る語彙＝③プラグイン1ファイル）。最終的には利用者・
  管理者が語彙を増やせる形（語彙定義ページ・§2.5 (4)）を目指す。
- **語彙とプラグインは運用者のもの**（2026-08-26 要件化・§1.1）——開発元でない企業・サイト運営者が、
  自分の設置環境へ自分の語彙・計算プラグインを追加できること。現行の追加手段は Go コード＋再ビルド
  （[【ガイド】プラグイン開発.md](【ガイド】プラグイン開発.md)）であり、この要件の完全な充足は
  レジストリの育成路線（§2.5 (4): コード → 管理DB → 語彙定義ページ）の後段を要する。
  **語彙の定義がデータになった段階では信頼境界が動く**（定義の検査が必要になる。
  [パーサとプラグイン.md](パーサとプラグイン.md) §5.5）。
- **実装量が語彙数に対して不変であること**: エディタは汎用表エディタ＋定義駆動の骨格生成（§2.2）で型
  ごとの JavaScript を書かない。サーバーの同期は汎用索引（§2.5）で、型ごとの `Sync()` は計算プラグイン
  だけが持つ。カスタム要素のテンプレート資産（1要素＝閲覧/編集2テンプレートで増えていた）は
  **2026-08-20 に撤去済み**で、語彙が増えてもフロントのファイルは増えない。
- `/api/tag-schema`（レジストリ込み）の応答サイズ・許可リスト検索・DBスキーマ数が実用上の問題に
  ならないこと。
- **フロントエンドの実装方式**: **バニラJS・ビルド工程ゼロ・追加ライブラリなし**で確定（2026-08-17）。動的な
  振る舞いはエンハンサ方式、DOM生成は殻の `<template>`＋`cloneNode`＋`textContent` 代入（自動エスケープ）で
  行う。`lit` の再評価は打ち切り。**React/Vue の採用は引き続き非推奨**（保存形式＝DOM・ビルド工程ゼロの2特性を
  壊すため）。将来ライブラリを検討しうる唯一の候補はバーコード読取（`BarcodeDetector` API の Safari 非対応）で、
  その機能の判断時に [開発方針.md](開発方針.md) §1 の承認手続きに載せる。
