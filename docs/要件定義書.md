# 要件定義書

w-cms がアプリケーションとして満たすべき要件を一覧化した文書です。

**本書は要件の「目次・逆引き」であり、各要件の詳細仕様の正本は末尾リンク先の設計文書です。**
現行実装から起こした要件（原則実装済み）と、2026-08-16 の方針転換——一般公開ウェブサイト用途・
語彙100種規模・標準HTML＋`data-*` マーカーの語彙モデル——で加わった将来要件が混在するため、
後者には**未実装**・**検討中**を明記し、第5章に集約します。仕様変更の際は正本を先に直し、
本書は追随させます（語彙モデル・3層モデルの設計の正本は
[【考察】語彙モデル.md](【考察】語彙モデル.md)。本書 §2.5 はその要約です）。

## 1. システムの目的と対象

### 1.1 目的と用途

- 入力項目が固定された帳票システムを排し、**Notion のように自由なブロックレイアウトで書いた
  ページ＋PDF 原本＋タグ（名前:値）**から、データベースが自律的に意味を認識して集計する
  CMS を提供する（[コンセプト.md](コンセプト.md) §1）。
- 「顧客管理画面」「製品管理画面」のような固定のページ種別は持たない。すべてのページは同一構造の
  HTML であり、ユーザーが配置したブロックによってページの役割が動的に決まること。
- **用途は2つあり、同じソフトウェアを別サーバー・別ドメインの2インスタンスとして運用する**
  （2026-08-16 決定）。

  | インスタンス | 用途 | 主な利用者 | 中心となる要件 |
  |---|---|---|---|
  | **業務インスタンス** | 社内の業務システム | 認証済みユーザーのみ | 受発注・進捗・原価/利益の記録と集計（§2.5） |
  | **サイトインスタンス** | 一般公開のウェブサイト | 匿名の訪問者＋編集者 | 公開ページの読み取り専用配信（§4.4） |

  - **データは完全に独立**する。`data/master`・`cms.db`・`auth.db` はインスタンスごとに別で、
    両者はページを共有しない。したがって**業務データが公開面へ出る事故は、権限設定ではなく
    構成そのもので防がれる**（業務ページと公開ページが同じツリーに同居しない）。
  - **ソフトウェアは同一**（同じ単一バイナリ）。用途の差は**データと運用**で吸収し、
    インスタンスごとに機能を分岐させる作りは持たない。語彙（§2.5 のレジストリ）は
    データなのでインスタンスごとに異なってよい。
  - **運用は2セットになる**（デプロイ・バックアップ・更新・初期管理者）。§4.3 参照。

### 1.2 業務ドメインと規模

- 業務システムとしての対象領域は、製造・加工業（部品加工／材料調達）の**受発注業務**。
  用語は視点に依らない役割語（受注／発注・販売見積／購入見積）で統一する
  （[【一覧】用語集.md](【一覧】用語集.md) §1）。
- **語彙（文書の種類・意味づけ）は最終的に100種規模を予定する**（現行実装は語彙レジストリの
  12形式。**カスタム要素は0種**＝2026-08-20 に全廃）。§2.5 の語彙モデルにより、語彙は
  **`data-type` 値（レジストリの宣言データ）として増える**。「語彙を増やす／一覧を保守する／
  エディタから選ぶ」経路は、数十〜百のオーダーで破綻しない仕組みであることを要件とする
  （§2.2・§2.5・§4.5）。
- ウェブサイトとしては、公開ページが検索エンジンと一般の訪問者に晒されることを前提とする
  （§4.4）。

### 1.3 利用者

| 利用者 | できること |
|---|---|
| 認証済みユーザー | ページ権限（Unix風 read/write）の範囲で閲覧・編集 |
| グループ | ページの group クラス権限の単位（フラット・入れ子なし） |
| admin | root 相当。全権限バイパス・ユーザー/グループ管理・DB再構築・ロック強制解除 |
| 匿名の訪問者 | **実効公開ページのみ** read 専用で閲覧（＝一般公開サイトの読者） |

### 1.4 公開範囲と脅威モデル

- **どちらのインスタンスもインターネット公開を前提**とする。したがって強固な認証・HTTPS・
  レート制限・CSRF 対策を必須とする（[認証認可設計.md](認証認可設計.md) §0）。
- **業務インスタンスは匿名に対して何も見せない**。全ページ非公開（`public` を使わない運用）とし、
  匿名には存在情報も返さない（§2.1 の404統一）。業務データの露出は、権限設定ではなく
  **インスタンス分離という構成**で防ぐ（§1.1）。
- **サイトインスタンスでは匿名アクセスが常時の主要動線**である。未認証で到達できる面
  （公開ページの本文・子ページ一覧・親リンク・添付配信）は、
  **既定非公開＋明示的な公開操作**というフェイルクローズの原則で保護すること（§2.3）。
  下書き（非公開ページ）の存在も匿名には漏らさない（§2.1）。

## 2. 機能要件

### 2.1 ページ管理

- ページIDは**6桁ゼロ埋めの連番**とし、DBの `INSERT` 自動採番で原子的に確定すること
  （同時作成でも衝突しない）。
- 保存先は `data/master/{ID先頭2桁}/{ID}/` に分散配置し、1ページ＝1ディレクトリに
  本文 `<id>.html`・属性サイドカー `<id>.meta.json`・添付ファイルを格納すること。
- ページは**必ず親を持つ**。親なし（トップレベル）にできるのはトップページ `000000` のみ
  （admin でも例外なし）。子ページの作成は単一リクエストで採番→ファイル生成→DB同期→
  編集画面へのリダイレクトまで完結すること。
- 親の付け替えは専用APIで行い、実在・自己参照/循環の防止・新しい親への write 権限を
  検証すること。
- 初期表示は**サーバー合成**とする（殻 `index.html` に本文とタイトルを埋め込んだ完成HTMLを
  返す）。チラつきが無く、JSを実行しないクローラでも本文が読めること。
  > **2026-08-20 に完全達成**。かつてはカスタム要素の中身がクライアント描画だったため、
  > この要件は構造HTMLの本文に限って成立していた。語彙モデルの移行で本文がすべて標準HTMLに
  > なり、最後まで残った動的部分（計算ビュー＝子ページ一覧・手配集計）も**サーバー事前描画**
  > （[view_render.go](../internal/cms/view_render.go)）へ移したため、**閲覧はゼロJSで完結する**。
- 認可に応じた応答: 認証済み×read不可＝403、不存在＝404。
- **匿名に対しては「読めないページ」と「存在しないページ」の応答を区別しない**
  （どちらも 404。2026-08-16 決定・未実装）。ページIDが連番であるため、応答が
  302/401 と 404 で分かれると非公開ページの存在・総数・作成ペースを外部から列挙できて
  しまう。画面・API（`/api/load`・`/api/page-meta`・`/api/children`・`/data/` 配信）の
  すべての匿名経路で揃えること。
  > 例外: 入口が失われないよう、トップ経由（`/` → `/000000`）のアクセスに限り従来どおり
  > `/login` へ誘導してよい。ログイン画面自体は `/login` で常に到達可能。

正本: [アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §4〜§6・§8

### 2.2 エディタ

- **Notion風ブロックエディタ**を提供する: ドラッグ&ドロップによるブロック並べ替え、
  スラッシュメニュー（`/`）によるブロック挿入、ブロック単位のコンテキストツールバー。
- **ブロック挿入UIは100種規模に耐えること**（§1.2）。全件を並べた固定リストでは選べないため、
  **絞り込み入力・分類（カテゴリ）・使用頻度順**などで目的の形式に到達できる必要がある。
  選択肢と挿入される骨格は**語彙レジストリ（§2.5）から生成**し、語彙を増やすたびに
  フロントの markup やコードを手で足す運用にしないこと。形式を選ぶと、列定義から
  ヘッダ行つきの骨格を**機械的に生成**して挿入する（見出しの表示文字が鍵になるので、
  骨格が入れるのはレジストリ宣言のラベルそのもの。§2.5）。
  > **レジストリからの動的生成は実装済み**（2026-08-17。`populateSlashMenuVocab` が
  > `/api/tag-schema` の `vocab` から項目と骨格を生成する）。カスタム要素の手書き項目は
  > 移行完了（2026-08-20）で**消滅し、殻に残る `.slash-menu-item` は `h1`・`p` の2つだけ**
  > になった。**未達**なのは絞り込み入力・分類（カテゴリ）・使用頻度順による到達性で、
  > 現状は全項目を1列に並べているだけ。再設計は §5 の課題として扱う。
- **汎用表エディタ**（2026-08-16 要件化 → **2026-08-17 v1・2026-08-19 拡張を実装済み**。
  残りは date/image の入力補助のみ——image は §2.6 の画像アップロード実装待ち。
  仕様の正本は [エディタ仕様.md](エディタ仕様.md) §3.2）:
  `data-type` 付きの表・定義リストの編集
  （セルの直接編集・行の追加/削除/並べ替え・列設定UI・列型に応じた入力補助）は、
  **型の数に対して不変の汎用実装**とすること。型ごとの JavaScript を書かない。
  列型は当面 `text`／`number`／`date`／`enum`（ドロップダウン）／`image`
  （セル内への添付画像挿入。§2.6 と接続——検査写真の列などに使う）を想定する。
  列型は原則**見出し語から推論**する（`金額`→通貨、`数量`→数値など、語→型の辞書は
  レジストリの一部）。`th data-type` の明示と③計算形式のレジストリ宣言が推論に優先し、
  型に合わない入力は**通知**（背景色など）に留めて拒否しない。
  **機械属性（`th` の `data-type`＝列型の明示）が見出しからの型推論に優先している箇所は、
  編集モードで背景をハイライト**し、見えている文字が型として使われていないことを利用者に示すこと
  （型不一致の通知＝赤とは別の色。閲覧・公開ページには出さない）。
- **エディタの形式知識は3場面で扱いが異なる**（2026-08-16 整理）:
  1. **新規挿入時**——列定義の全体が要る。語彙レジストリから API 経由で受け取る
     （エディタに手書きの形式リストを置かない）。
  2. **既存ブロックの編集時**——**レジストリ不要**。表の鍵と型は見出し行が運ぶ
     （鍵は**見出しテキスト**、型は `data-type` があればその値・無ければ**型推論**——§2.5）
     ため、文書自身が運ぶ情報だけで編集が成立する（レジストリが読めなくても
     既存文書の編集は壊れない）。
  3. **入力補助・検証**——レジストリがあれば向上する（enum の選択肢・解決できない見出しへの
     告知）。無くても編集は可能。
- **オートセーブ**を提供する: 入力のデバウンス（1〜2秒）とブロックの `focusout` で自動保存。
  変更が無ければ何も送らず、1ブロックのみの変更はブロック単位（`/api/save-block`）、
  それ以外は全文保存（`/api/save`）へ自動で振り分けること。保存状況（未保存／保存中／保存済）を
  常時表示すること。
- **編集中のアンドゥ・リドゥ**を提供する（Ctrl+Z / Ctrl+Y、スナップショット上限100、
  キャレット位置も復元）。履歴は編集モードのセッション限りとする。
- インライン装飾（太字・斜体・下線）は `document.execCommand` を使わず自前の Range 操作で
  実装し、出力は常に `<strong>`/`<em>`/`<u>` に正規化すること。
- **エディタが扱える語彙（要素・属性）はサーバーの1箇所を正本**とし、`GET /api/tag-schema` で
  受け取ること。エディタ側に手書きの要素リストを置かない（許可済み要素が保存時に黙って
  消える不具合の再発防止）。同APIは語彙レジストリの形式定義（`vocab`）と語→型の推論辞書
  （`type_inference`）も返す（§2.5。2026-08-17／08-19 実装済み）。
- 実装は**バニラJS・ビルド工程ゼロ・追加ライブラリなし**とする（§4.5）。
  **Web Components（カスタム要素）は廃止**（2026-08-17 決定・**2026-08-20 に移行完了で0種**。§2.5）。
  `web-components.js`・`assets/templates/`・`components.css` は撤去済みで、
  **新規カスタム要素は作らない**。
  新規コードでインライン `script`/`style`/`on*=` を書かないこと（[開発方針.md](開発方針.md) §4）。
- 画面は4カラム（左レール＝階層／目次レール／文書／右レール＝ページ情報・権限）＋
  ヘッダー・フッター帯。狭幅（≤760px）ではレールをドロワー化すること。
  保存されるのは本文（`#editor-content`）のみで、クロームは保存しない。

正本: [エディタ仕様.md](エディタ仕様.md)、[画面構成と用語.md](画面構成と用語.md)

### 2.3 認証・認可

- 認証は**アプリ単体管理**（SSOへ委譲しない）。パスワードは argon2id でハッシュし、
  総当たり対策（バックオフ／ロックアウト）とユーザー列挙対策（存在しないユーザーでも同じ
  計算量を消費）を備えること。
- セッションは 256bit トークン（DB側はハッシュ保存）、Cookie は `HttpOnly`/`Secure`/
  `SameSite=Lax`、**絶対8時間／アイドル30分**で失効すること。
- 初期管理者は環境変数（`WCMS_ADMIN_USER`/`WCMS_ADMIN_PASSWORD`）で、ユーザーが空のときのみ
  作成すること。
- 認可は**ページ単位の Unix 風モデル**: read/write の2ビット × owner/group/other の3クラス
  （mode は `"330"` のような3桁文字列）。子ページ作成には親ページの write を要求する
  （ディレクトリ書き込み相当）。chmod/chgrp は owner または admin、chown は admin のみ。
- 権限の正本は**サイドカー `<id>.meta.json`** とし、書き込めるのは権限変更APIとページ新規作成
  のみ。本文保存APIは権限に一切触れないこと（自己認可の構造的防止）。
- **匿名公開**は mode と独立した `public` フラグで制御する。実効公開＝自分の public ∧
  全先祖の public（パスゲート）とし、ルート `000000` の非公開化がサイト全体のキルスイッチに
  なること。新規ページの `public` は常に false（フェイルクローズ）。匿名は read 専用。
- 書き込み・権限変更の**監査ログ**を記録し、admin が閲覧できること。

正本: [認証認可設計.md](認証認可設計.md)

### 2.4 同時編集の直列化

- **ページ単位の悲観ロック＋SSE** により、複数人（同一ユーザーの別タブを含む）が同時に
  開いても lost update が起きないこと。保持者はエディタ個体（トークン）で識別する。
- 本文保存だけでなく、権限変更・所有者変更・親付け替え・公開切替も同じロックで直列化すること
  （共通ゲート `RequireEditLock`／フロント共通ラッパ `lockedFetch`）。
- ロック取得成功時は**最新の生HTMLを同梱**し、古い版からの編集開始を防ぐこと。他者保持中は
  423 を返し、待機者はSSE通知で解放を検知して自動的に編集モードへ移行すること。
  無競合なら無期限、待機者が現れたら2分の猶予で強制明け渡し。admin は強制解除できる
  （監査記録あり）。
- ロックは単一プロセス内の揮発的状態でよい（再起動での消失は許容）。

正本: [アーキテクチャとDBスキーマ.md](アーキテクチャとDBスキーマ.md) §4.3、
[【考察】同時編集の競合対策.md](【考察】同時編集の競合対策.md)

### 2.5 語彙モデルと業務機能（プラグイン）

> 本節の (1)〜(3) は 2026-08-16 の方針で、**設計の正本は
> [【考察】語彙モデル.md](【考察】語彙モデル.md)**（マークアップの原則・3層モデル・
> 表と定義リストの設計・挿入経路・移行・決定ログ）。
> **2026-08-20 に移行完了**——本文の語彙は「標準HTML＋`data-*` マーカー」に完全統一され、
> カスタム要素は0種、形式の宣言は語彙レジストリ（`internal/cms/vocab.go`・12形式）が持つ。
> **残る未実装は参照系だけ**（受信元・前版の参照マーカーと参照追従JOIN。
> [【考察】通信記録処理.md](【考察】通信記録処理.md) §2.5 の設計待ち）。

#### (1) 本文の語彙は3種類

| 種類 | 例 | 増やすときのコスト |
|---|---|---|
| **標準HTML** | 見出し・段落・リスト・表・画像… | 増やさない（コアの許可リストで固定） |
| **マーカー付き標準HTML（記録）** | 繰り返し明細＝`<table data-type="…">`（列役割はヘッダ行の見出し）、名前:値メタ＝`<dl data-type="tags">`、業務文書ブロック＝`<section data-type="…">`（ヘッダ dl ＋明細 table を包む） | **語彙レジストリへの宣言1件（データ）** |
| **マーカー付き標準HTML（動的）** | 計算ビュー＝`<section data-type="child-list"\|"required-materials">`（実装済み・サーバー事前描画）、ファイル容器＝`<section data-type="file" data-src>`（実装済み・エンハンサ）、ページ参照（**未実装**・設計待ち） | 計算プラグイン（Goコード） |

- **カスタム要素（Web Components・`<m-*>`）は廃止する**（2026-08-17 決定・**2026-08-20 完了**）。語彙は
  標準HTML＋`data-*` に**完全統一**し、動的な振る舞いは編集モードのクローム（エディタ）と
  閲覧ビューのエンハンサ（バニラJS）／サーバー事前描画が担う。**新しいカスタム要素は
  作らない（即時発効）**。理由: ①公開ページで**閲覧ゼロJS**（計算ビューもサーバー事前描画で
  SEOが解ける）②値が実テキストになり生HTML（正本）が自己説明的・grep/diff が効く
  ③語彙の増加コストが最小になる ④テンプレート機構由来のXSS経路とインライン `style=`
  （CSP strict 化の障害）が構造的に消える。**カスタム要素10種は移行で撤去済み（0種）**で、
  ④の帰結として **CSP strict 化も完了した**（§4.2）。
- マーカーは `class` でなく **`data-*`**（サニタイザの `class` 全面拒否に例外を作らない・
  見た目のフックと機械可読の役割の分離・シェルDOMのセレクタと衝突しない）。
- 表は**自己記述**とする: 列の鍵は見出し行が運ぶ——**見出しテキストそのもの**
  （2026-08-20 改定。当初は「`data-field` があればその値、無ければ見出しテキスト」だったが、
  鍵の解決が元々レジストリのラベル経由で成立していたため属性ごと撤去した）。
  ③計算形式では、見出しの表示文字がレジストリ宣言のラベルに一致することで機械キーへ解決される。
  **見出しを改名すると解決できなくなり、その列は計算に読まれない**——黙って止まらないよう、
  解決できなくなった列を**保存時に告知**すること（拒否はしない）。
- 写真・画像は語彙ではなく**内容**であり、標準HTML（`<img>`）だけで完結する（§2.6）。
  意味を持たせたいときに初めて語彙側と接続する（例: 表の `image` 列＝レジストリのデータ、
  撮影画像→明細表の変換＝計算プラグイン）。

#### (2) 語彙と拡張の3層モデル

| 層 | 実体 | 追加・変更のコスト | 担うもの |
|---|---|---|---|
| **① 語彙レジストリ** | 宣言データ（コードでない） | **再デプロイ不要が目標** | `data-type` の定義: 表示名・分類・アイコン・列（機械キー・型・ラベル・許可値）・雛形骨格 |
| **② 汎用索引** | コアに一度だけ実装 | — | すべての `table[data-type]`/`dl[data-type]` を汎用テーブル（page_id・種別・行・フィールド・値）へ同期。`page_tags` の一般化。検索・単純集計 |
| **③ 計算プラグイン** | Goコード（現行プラグインの後継・少数） | 開発者の仕事 | 型付きテーブル＋計算ロジック（部材手配・利益・進捗・参照追従）、取り込み変換（PDF/画像→表・.eml→通信記録）、集計API、外部投入API |

- **追加コストの段差を正しく付ける**: 記録・表示だけの語彙（100種の大半）は①のデータ1件で
  完結し、**開発者がボトルネックにならない**。計算が要る語彙だけが③の開発案件になる。
- **語彙の単一正本の拡張**: ①のレジストリと③のプラグイン宣言（計算型の列定義は `Sync()` と
  同じ宣言から導く——エディタが書く見出しラベルと同期が読む機械キーのずれを構造的に
  防ぐ）を合成し、**単一のAPI**（`/api/tag-schema` の拡張）としてエディタ・タグ一覧の
  ドキュメント生成へ届けること。
- **サニタイザの許可リスト（要素・属性名）は従来どおりコード側で固定**し、レジストリを
  安全性の門にしない。`data-type` は属性**名**を許可し、**値は不活性な文字列**
  として扱う。**w-cms がその要素を見て何かする（DB保存・描画・配線・入力補助）要素にだけ
  `data-type` を許可していく**（型名としての `data-type`・2026-08-20 決定）。この分離により、レジストリを将来実行時編集可能にしても危険な要素は増やせない。
- ②の汎用索引にも「ファイルから再生成できないデータを持たせない」不変条件（§3）を適用する。

#### (3) 挿入経路

同じ語彙・同じ保存時サニタイズと検証・同じ編集ロックを通る。経路はプロデューサーの違いに
すぎず、語彙の単一正本を迂回する経路を作らないこと。

### 2.6 添付ファイル

- ページへ PDF を添付できること。受け入れはサーバーで強制する: リクエスト32MiB上限・
  中身の先頭 `%PDF-` 必須・ファイル名の正規化（パス要素や制御文字の拒否、
  本文・サイドカーと同名の拒否）。
- **ページへ画像を添付できること（2026-08-16 要件化・未実装）**。ウェブサイト用途（§4.4）で
  本文に画像を表示するため。PDF と同じ入口・出口の二層で守る。
  - **許可する種類は `png`・`jpeg`・`webp`・`gif`・`svg`**。ラスタ画像は拡張子だけでなく
    **中身のマジックナンバーを検証**する（PDF の `%PDF-` 検査と同じ考え方）。
  - **SVG は「不活性な画像」として許可する**。SVG はスクリプトを内包できる文書形式なので、
    中身の完全なサニタイズは行わず、**埋め込み方と配信の二層で無害化**する:
    - 本文からの表示は `<img src="x.svg">` 経由のみ（**画像コンテキストではブラウザ仕様として
      スクリプトが実行されない**。外部取得・対話も不可）。インライン `<svg>` は従来どおり
      サニタイザが部分木ごと削除する。
    - 配信（`DataFileHandler`）は `Content-Type: image/svg+xml` ＋
      `Content-Disposition: attachment`（**直接開くと描画せずダウンロード**。`<img>` の
      サブリソース読み込みはこのヘッダを無視するため表示は影響を受けない）＋
      このレスポンス限定の `Content-Security-Policy: sandbox; default-src 'none'`
      （万一描画されても別オリジン扱い・全実行禁止）。
    - 入口では well-formed XML でルートが `<svg>` であることを検査し、`<script>`・
      `<foreignObject>`・`on*=`・`javascript:` を含むファイルは拒否する
      （安全性の本体は配信側であり、こちらは多層防御の網。Go の XML パーサは
      外部実体を解決しないため XXE の心配は無い）。
    - 代償として SVG 内のリンク・ホバー等の**対話性は動かない**（ロゴ・図版用途を想定）。
  - **将来: SVG 編集アプリ（構想・§5）**。SVG が「閲覧する画像」から「編集対象の文書」に
    なった時点で、扱いを不活性画像から**編集器の語彙への許可リストサニタイズ**へ拡張する。
    本文HTMLと同じ流儀——語彙はサーバーの1箇所を正本とし、編集器が知らない要素は取り込み時に
    落ちる——であり、「任意のSVGの完全な保全」は目標にしない。語彙が確定すれば
    インライン `<svg>` の解禁（＝対話性の復活）も同じ許可リストで判断できる。
  - サイズ・名前の規則は PDF と共通（32MiB・ファイル名正規化・本文/サイドカー名の拒否）。
    必要なら画像固有の上限（ピクセル数等）を実装時に追加してよい。
  - **配信はインライン表示を許可**する: 検証済みの画像種別に限り、実際の種別に対応する
    `Content-Type`（`image/png` 等）を明示して返す（`nosniff` は維持）。
    それ以外の種別が「PDF以外はダウンロード扱い」のままであることは変えない。
  - 本文からは相対URL（`<img src="ファイル名">`）で参照する。サニタイザは
    `img`（`src`・`alt`・`title`・`width`・`height`）と相対URLを既に許可しており変更不要。
  - **エディタに画像の挿入手段を用意する**: ドロップ／ファイル選択に加え、
    **モバイル端末ではカメラで撮影してその場で挿入できること**。
    実現はOS標準のカメラUI（`<input type="file" accept="image/*">` ＋ `capture`）でよく、
    独自のカメラ画面（`getUserMedia`）は要件としない。挿入後は本文に `<img>` が入り、
    通常のオートセーブに乗る。表の `image` 列（§2.2）のセル内挿入も同じ機構を使う。
  - **EXIFメタデータは保存時にサーバーで除去する**。カメラ写真には撮影位置（GPS）・
    撮影日時・機材情報が埋まっており、公開サイトに載ると撮影者の所在が漏れる。
    除去はアップロード経路の一律処理とする（公開時に選別する方式にしない——
    フェイルクローズ）。EXIFの回転情報（orientation）を捨てる場合は、
    画素の向きを補正してから保存し、表示が横倒しにならないこと。
  - **EXIF除去の帰結**: 撮影日時・撮影場所を業務データとして使う場合、EXIF から拾う設計には
    できない。必要ならアップロード受付時刻をサーバーが記録するか、利用者が表の `date` 列へ
    入力する（検査記録など「いつ撮ったか」が意味を持つ用途では要件として意識すること）。
  - iOS のカメラ写真は HEIC 形式の場合がある（file input 経由では通常 JPEG に変換されて
    届く）。**HEIC が届いた場合は許可リスト外として拒否し、理由を利用者へ表示する**
    （サーバーでの変換は要件としない）。
- 添付の配信（`GET /data/...`）は静的配信ではなく**ページの read 権限を要求する保護ハンドラ**
  とし、`nosniff` 付与・許可種別以外はダウンロード扱い・本文とサイドカーは配信しないこと
  （権限昇格・保存型XSSの防止。経緯は [変更履歴.md](変更履歴.md) 2026-08-05）。

## 3. データ要件

- **正本はファイル、DBは派生インデックス**。`data/master/` 配下が唯一の正データであり、
  `data/cms.db` は検索・集計のための使い捨てキャッシュとする。**DBにはファイルから再生成できない
  データを一切持たせない**（不変条件。プラグイン追加時も、§2.5 の汎用索引にも適用する）。
- 内容と属性を分離する: HTML本体 `<id>.html`＝内容、サイドカー `<id>.meta.json`＝属性
  （owner・group・mode・public・parent_id・作成/更新情報）。
- 認証情報 `data/auth.db` だけは**再生成不可**であり、DB再構築の対象外とする。
- **バックアップ対象は `data/master/` 全体＋ `data/auth.db`**。`cms.db` は対象外
  （復元時に再生成）。
- SQLite は Pure Go ドライバ（CGO不要）を用い、`journal_mode=WAL`・`busy_timeout`・
  `foreign_keys` を適用すること。

## 4. 非機能要件

### 4.1 セキュリティ

- **本文サニタイズは二層**（保存時＋描画時）の許可リスト方式とし、サニタイザは冪等である
  こと（`Sanitize(Sanitize(x)) == Sanitize(x)`）。保存時は除去結果をエディタへエコーバック
  して利用者に通知すること。
- 方針は「**タグは寛容・属性は厳格**」: 構造HTMLは h1〜h6・リスト・ルビ・表・`details`・
  `video`/`audio` まで広く許可する一方、`script`/`style`/`iframe`/`form` 系は部分木ごと削除、
  `on*`・`style`・`id`・`class` 属性は常に拒否（例外は `data-id`。§2.5 の語彙モデルでは
  `data-type` の属性**名**が加わるが、**値は不活性**でありレジストリは
  安全性の判断に関与しない）。
  > **検討項目（2026-08-16・§5）**: この規則のもとでは本文にレイアウト・装飾を書く手段が
  > 無い。公開サイト（§4.4）でデザイン表現をどう与えるかは未決——候補は
  > ①表示専用の `data-type` 形式（レジストリへ宣言を足し、装飾はテーマCSS側で当てる。
  > **当初案の「表示専用カスタムタグ」はカスタム要素廃止により読み替え**）
  > ②`class` の**許可リスト**（任意クラスではなく、定義済みユーティリティ名だけ通す）
  > ③サイト全体のテーマCSS（本文は構造のみ、装飾は殻側で完結）。
  > いずれもサニタイズの「属性は厳格」原則を壊さずに実現できるかで評価する。
- URL規則は2種類: リンク（`href`・`cite`）は相対・http・https・mailto・tel を許可、
  **埋め込み（`src`・`srcset`・`poster` 等）は相対のみ**。`javascript:` 等のスキームと
  プロトコル相対URL（`//host/…`）は拒否。
- **CSP を全レスポンスへ付与**する。**2026-08-19 に strict 版へ到達**
  （`default-src 'self'; script-src 'self'; style-src 'self'; object-src 'self'; base-uri 'self'; frame-ancestors 'self'`。
  `'unsafe-inline'` を含まない）。インラインの `script`/`style`/`on*=` はリポジトリ全体でゼロで、
  後戻りは [csp_test.go](../internal/auth/csp_test.go) が検出する
  （[【考察】CSP強化.md](【考察】CSP強化.md)）。
- **CSRF は Origin/Referer とリクエストホストの一致検証**（GET/HEAD/OPTIONS 以外に適用、
  ヘッダが無ければ安全側で拒否）＋ `SameSite=Lax` の併用。
- フロントでテンプレートへ値を差すときは必ず `escapeAttr` を通すこと
  （サニタイザでもCSPでも止まらない保存型XSS経路。経緯は [変更履歴.md](変更履歴.md) 2026-08-04）。
  ※ §2.5 の語彙モデル（値を属性でなく中身に置く＝テキストノードはDOMが自動エスケープ）は、
  この失敗の余地そのものを構造的に減らす。
- 本番は**TLS/HTTPS 必須**（リバースプロキシで終端）。Secure Cookie の無効化
  （`WCMS_SECURE_COOKIES=0`）はローカル検証専用とする。

正本: [本文サニタイズ設計.md](本文サニタイズ設計.md)、[認証認可設計.md](認証認可設計.md) §0.1・§2.3

### 4.2 依存最小化・ポータビリティ

- **標準ライブラリ優先**。外部パッケージの新規追加は原則禁止・事前承認制とする。
  承認済みの直接依存は [開発方針.md](開発方針.md) §1 の一覧が正本（Pure Go SQLite・
  `x/crypto`・`x/net`・Gemini SDK・`x/text`）。
- **CGO 不要**でビルドできること（Windows でも C コンパイラなしで動作）。
- フロントエンドは**ビルド工程ゼロ**（npm・バンドラ不使用）。

### 4.3 デプロイ・運用

- **単一バイナリ**で配布・起動できること（`go build`、クロスビルド可）。待受は `:8080`。
- 本番想定は VPS（2 CPU / 2GB RAM / Linux・systemd）＋リバースプロキシ（Caddy/nginx）。
  argon2id のピークメモリはログインの同時実行制限（セマフォ4件）で約256MiBに抑える。
- **設定の受け渡しは環境変数のみとする**（2026-08-16 決定）。アプリは設定ファイルを読まず、
  コマンドラインフラグも持たない。インスタンスごとの設定一覧は、アプリではなく**運用側**が
  systemd の `EnvironmentFile=`（`KEY=VALUE` を並べた1ファイル。例 `/etc/w-cms/site.env`）で
  持つ。理由: アプリ実装が最小で済む・秘密情報がリポジトリやバックアップへ紛れる事故が
  構造的に起きにくい・2インスタンス運用（1インスタンス＝1環境ファイル）と素直に噛み合う。
- **設定項目の一覧（本表が正本）**。追加するときは `WCMS_` 接頭辞で命名し、本表を更新する:

  | 環境変数 | 意味 | 既定値 | 状態 |
  |---|---|---|---|
  | `WCMS_ADMIN_USER` / `WCMS_ADMIN_PASSWORD` | 初期管理者（`users` が空のときのみ。作成後は外す） | なし | 実装済み |
  | `WCMS_SECURE_COOKIES` | `0` で Secure Cookie を無効化（ローカル検証専用・本番禁止） | 有効 | 実装済み |
  | `GEMINI_API_KEY` | PDF明細抽出（§2.5）のAPIキー。未設定なら当該機能はエラー | なし | 実装済み（業界慣行名のため `WCMS_` 接頭辞の例外） |
  | `WCMS_ADDR` | 待受アドレス（`host:port`）。リバースプロキシと同居するなら `127.0.0.1:8081` のようにローカルへ束縛できる | `:8080` | **未実装（§5）** |
  | `WCMS_DATA_DIR` | `data/` の場所 | 実行時カレントディレクトリ直下の `./data` | **未実装（§5）** |

- 環境変数方式は「いま何が効いているか」が見えにくいため、**起動時に有効な設定を1行ログへ
  出す**こと。ただし**秘密情報は値を出さない**（アドレス・データディレクトリ・Secure Cookie
  の有無・Gemini キーの**有無**のみ）。
- `data/` は既定で実行時カレントディレクトリ直下に自動生成される（systemd では
  `WorkingDirectory=` を明示）。
- **2インスタンス運用**（§1.1）: 業務用とサイト用を**別サーバー・別ドメイン**で動かす。
  - 各インスタンスは独立した `data/`（`master`・`cms.db`・`auth.db`）を持ち、
    バックアップ・初期管理者・更新もインスタンスごとに行う。
  - **Cookie・セッションはドメイン単位で自然に分離**される（相互に影響しない）。
    編集者が両方を使う場合、アカウントはそれぞれで作成する。
  - 同一ホストに同居させる場合は `WCMS_ADDR`・`WCMS_DATA_DIR` で分離する
    （どちらも未実装・§5）。

正本: [【ガイド】デプロイ・運用.md](【ガイド】デプロイ・運用.md)

### 4.4 公開ウェブサイトとしての要件

**サイトインスタンス**（§1.1）に効く要件群。社内システムとしては不要だったが、
一般公開サイトとして使う以上は必要になる。現状はいずれも未達で、詳細は §5 に再掲する。
（ソフトウェアは業務インスタンスと同一なので、ここでの改善は業務側にも入るが、害はない。）

- **公開ページの見え方**: 公開ページは編集用クロームを含まない体裁で届くこと。現状は編集用の
  殻をCSSで隠す方式のため、匿名にも不要なマークアップと `/assets/` の資産が配信される。
- **SEO・SNS共有**: ページごとの `<title>`（実装済み）に加え、`description`・OGP・正規URL
  （canonical）・`sitemap.xml`・`robots.txt` を提供できること。**非公開ページを
  クロールさせない**ことも同じ要件に含む。
  > **前提はそろった（2026-08-20）**: §2.5 の語彙モデル移行完了により本文は標準HTMLになり、
  > 計算ビュー（手配状況・子ページ一覧）も**サーバー事前描画**（マーカー容器へGoが中身を埋める）
  > へ移ったので、**閲覧はゼロJSで完結する**。残るのは本項の `description`・OGP・canonical・
  > `sitemap.xml`・`robots.txt` の実装で、**いずれも未実装**。
- **キャッシュ**: 現状すべての画面応答が `Cache-Control: no-store`。公開ページは匿名向けに
  キャッシュ可能な応答（`ETag`／`Last-Modified` を含む）を返せること。ただし
  **非公開ページや認証済み応答をキャッシュさせない**ことが絶対条件で、公開／非公開の切り替えが
  即座に反映されること。
- **公開面の負荷とレート制限**: 匿名アクセスは不特定多数から来る。リバースプロキシ側の
  レート制限（[【ガイド】デプロイ・運用.md](【ガイド】デプロイ・運用.md) §6.2）を前提としつつ、
  1リクエストあたりのサーバー処理（サーバー合成・描画時サニタイズ）が公開ページで
  過大にならないこと。
- **エラー画面**: 404・403 が一般の訪問者にも意味の分かる体裁であること。

### 4.5 拡張性（100種規模の語彙）

- **語彙の追加コストに正しい段差を付けること**（§2.5 の3層モデル）:
  - 記録・表示だけの語彙（100種の大半）＝**レジストリへの宣言1件**。再デプロイ不要が目標で、
    最終的には利用者・管理者が増やせる形（語彙定義ページ）を目指す。
  - 計算が要る語彙＝**プラグイン1ファイル**（開発者の仕事）。数は10個未満のオーダーに保つ。
- **実装量が語彙数に対して不変であること**:
  - エディタは汎用表エディタ＋定義駆動の骨格生成（§2.2）で、型ごとの JavaScript を書かない。
  - サーバーの同期は汎用索引（§2.5）で、型ごとの `Sync()` は計算プラグインだけが持つ。
  - カスタム要素のテンプレート資産（1要素＝閲覧/編集2テンプレートで増えていた）は、
    Web Components の廃止・移行完了とともに **2026-08-20 に撤去済み**（`assets/templates/`
    12ファイル・`web-components.js`・`components.css`）。語彙が増えてもフロントの
    ファイルは増えない。
- `/api/tag-schema`（レジストリ込み）の応答サイズ・許可リスト検索・DBスキーマ数が
  実用上の問題にならないこと。
- **フロントエンドの実装方式**: **バニラJS・ビルド工程ゼロ・追加ライブラリなし**で確定
  （2026-08-17）。Web Components は廃止し、動的な振る舞いはエンハンサ方式、DOM生成は
  殻の `<template>`＋`cloneNode`＋`textContent` 代入（自動エスケープ）で行う。
  `lit` の再評価は打ち切り。**React/Vue の採用は引き続き非推奨**（保存形式＝DOM・
  ビルド工程ゼロの2特性を壊すため）。将来ライブラリを検討しうる唯一の候補は
  バーコード読取（`BarcodeDetector` API の Safari 非対応）で、その機能の判断時に
  [開発方針.md](開発方針.md) §1 の承認手続きに載せる。
