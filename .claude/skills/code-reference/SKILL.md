# コードリファレンスの作成・更新

`docs/コードリファレンス/` は**実装の現状を写した文書群**です。設計の「なぜ」は各設計書が持ち、
ここは「いま何がどうなっているか」だけを扱います。

**役割分担**: このスキルは**書く**（新規作成・測り直し）。既にある記述が実装と合っているかを
確かめて直すのは **`/doc-audit`**。書き終えたら最後に `/doc-audit` を通します（手順7）。

## 鉄則

1. **推測を書かない。** 行数・箇所数・呼び出し関係は、必ずコマンドで数える。
   目視の見積もりは外れる（このプロジェクトで実際に2回外した記録がある）。
2. **数えた結果を疑う。** 識別子の単純な検索は偽陽性を含む（後述）。おかしい数字は個別に確認する。
3. **古い記述は直すか消す。** 実装と食い違った文書は、コードより有害。
4. **文書の編集は Edit ツールで行う。** 一括の正規表現置換は使わない（後述の事故）。

## 手順

### 1. 対象を確定する

```bash
git log --oneline -1
git status --short
```

作業ツリーがクリーンな状態で行う。文書の冒頭に書く「対象コミット」はこのハッシュ。

### 2. ファイルの棚卸し

```bash
# Go のファイル一覧と行数
find internal cmd -name '*.go' -not -name '*_test.go' | xargs wc -l | sort -rn
# フロント
wc -l assets/*.js assets/*.css assets/*.html
ls assets/templates/
```

### 3. ルーティング表を作る（シナリオ文書の背骨）

```bash
grep -nE 'Handle(Func)?\("' cmd/w-cms/main.go
```

ミドルウェアの入れ子（`CSPProtect(CSRFProtect(root))` など）と、`RequireAuth` / `OptionalAuth` の
どちらに載っているかを必ず確認する。**認可の話はここが起点**。

### 4. 依存関係を測る

パッケージ間:

```bash
grep -rn 'w-cms/internal' --include='*.go' internal cmd | grep -v '_test.go'
```

パッケージ内のファイル間（識別子の宣言元 → 参照元）は、宣言を集めてから参照を数える。
**次の3つは必ず偽陽性になるので、数える前に除外するか、後で個別に確認する**:

- **メソッド名**: `Name` / `Schema` / `Tables` / `Tags` / `Sync` は全プラグインが実装するため、
  「最初に宣言したファイルへの依存」に見えてしまう。
- **構造体フィールド名**: `Attr:` のようなフィールド指定が、同名の関数 `Attr()` の呼び出しに見える。
  関数呼び出しだけを数えたいときは `識別子\(` で絞る。
- **コメント内の言及**: `grep -v '^\s*//'` で落とす。件数だけ見て内訳を見ないと足をすくわれる
  ——「DOMヘルパーを使うのは `plugin_*.go` 6本」と書いた実績があるが、6本目のヒットは
  `plugin_file.go` の**コメント**で、実際は5本だった（総数49箇所の方は正しかった）。

### 5. 未読のファイルを読む

**「grep で見た」は「読んだ」ではない。** 文書に書く対象のファイルは通読する。
読んでいないファイルがあるなら、文書にそう書くか、読んでから書く。

### 6. 文書を書く

`docs/コードリファレンス/` の3本を更新する（構成を変えるなら README も）。

| 文書 | 内容 | 更新の目安 |
|---|---|---|
| `全体地図.md` | パッケージ構成・依存の向き・ファイルの役割・正本性・不変条件・既知のねじれ | 構造が変わったら必ず |
| `【一覧】関数リファレンス.md` | 主要関数と呼び出し元の対応表 | 関数の追加・移動・改名のたび |
| `シナリオ別の呼び出し追跡.md` | 操作ごとの呼び出しの連鎖 | 経路が変わったら（新API・ミドルウェア変更など） |

書き方の指針:

- シナリオは**実際に追える形**にする。関数名は実在するものだけを書き、
  分岐（403/409/423 になる条件）も併記する。
- 表の「主な呼び出し元」は、grep の結果から書く。記憶で書かない。
- **不変条件**（何が正本か・どちら向きに依存しているか・破ると何が起きるか）を必ず残す。
  これは他の文書から集めにくく、この文書群の一番の価値になる。

### 7. 検証

```bash
# リンク切れの確認（相対リンク先が実在するか）
(cd docs/コードリファレンス && for l in $(grep -ohE '\]\(([^)#]+\.md)' *.md | sed 's/^](//'); do
   [ -e "$l" ] || echo "MISSING: $l"; done)
# コードは変えていないはずなので、念のため
go build ./... && go test ./...
```

文書に書いた**行数・箇所数は、書いた後にもう一度数え直す**（編集中にずれるため）。

そのうえで **`/doc-audit` を自分の書いた文書に対して通す**。書いた直後は「そう書いたのだから
正しい」という思い込みが働くので、検証は別の観点（doc-audit の型別チェック）で行う。

### 8. コミット

`docs:` で1コミット。対象コミットのハッシュと更新日を文書冒頭に残すこと。

## この環境での落とし穴（実際に踏んだもの）

- **PowerShell の .NET ファイルI/Oは既定でUTF-8ではない。**
  `[System.IO.File]::ReadAllText($p)` / `WriteAllText($p, $t)` をそのまま使うと、
  日本語のコメント・文字列がすべて文字化けする。必ず
  `$utf8 = New-Object System.Text.UTF8Encoding($false)` を第2引数に渡す。
- **PowerShell は要素1つの配列を潰す。** `@(@('a','b'))` は `@('a','b')` になり、
  `$pair[0]` が文字列ではなく1文字を指す。文字単位の破壊的置換になった事故がある。
  → **ファイル書き換えは Edit ツールで行う。**
- **`gofmt -l` はこのリポジトリでは全ファイルを挙げる**（CRLF のため）。整形の判断材料にしない。
  `go build` / `go vet` / `go test` を使う。
- **`Measure-Object -Line` は空行を数えない。** 行数は `wc -l` か `(Get-Content).Count` を使う。
- **Go の `(?m)^package cms$` は CRLF ではマッチしない**（`\r` が残るため）。`\r?$` を付ける。
- **フロントの「読み込み順」は「実行順」ではない。** `<head>` の `defer` 付きスクリプトは
  解析完了後に走るため、`</body>` 直前の `defer` 無しスクリプトの方が**先に**実行される。
  シナリオ文書に読み込み順をそのまま書いて逆にした実績がある。`defer`/`async` の有無を見ること。

## 完了の条件

- 3本の文書の「対象コミット」が現在の HEAD と一致している
- 文書中の関数名がすべて実在する（少なくとも grep で1件は当たる）
- 「未確認」と書いた箇所以外に、読まずに書いた記述が無い
