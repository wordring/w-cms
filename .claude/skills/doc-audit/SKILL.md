# 文書の検証と修正

`docs/` 配下の文書は**実装より先に古くなる**。古い記述はコードより有害で、読む人は
確かめずに信じてしまう。このスキルは「書いてあることが本当か」を機械的に確かめ、
違っていたら直すための手順。

新しく文書を書き起こすときは `/code-reference`（コードリファレンスの作成・更新）を使う。

## 鉄則

1. **1文ずつ検証可能な主張に割る。** 「〜を4分割し、行数は211行」は2つの主張。まとめて
   ○×を付けない。
2. **根拠のコマンドを必ず走らせる。** 「たぶん合っている」は不一致と同じ扱い。
   確かめずに残した記述は、次に読む人に対する嘘になる。
3. **直す対象は文書。コードは直さない。** コード側のコメントが間違っていた場合は
   修正せず**報告する**（開発方針 4「既存コメント・ドキュメントの維持」）。
4. **消すより直す。** 記述が古いだけなら現状に合わせる。設計の「なぜ」や決定の経緯は
   実装と食い違って見えても消さない（それは変更履歴・考察文書の役割）。
5. **編集は Edit ツールで。** 一括の正規表現置換は使わない（`/code-reference` の
   「この環境での落とし穴」に事故の記録がある）。

## 手順

### 1. 基準を固定する

```bash
git log --oneline -1
git status --short
```

作業ツリーがクリーンな状態で始める。文書に「対象コミット」が書いてあるなら、それが
現在の HEAD と一致しているかをまず見る（ずれていれば全体が疑わしい）。

### 2. 主張を抜き出す

文書を**通読**して、検証可能な主張を型ごとに拾う。grep で拾えるのは一部だけなので、
必ず目で読む。型は次の8つでほぼ尽きる。

| 型 | 例 | 危険度 |
|---|---|---|
| 数値 | 「`handler_save.go` は211行」「75箇所」 | 中（編集のたびにずれる） |
| 実在 | 「`RequireEditLock` が…」 | 低（grep で一発） |
| 呼び出し関係 | 「呼び出し元は A・B・C」 | **高**（漏れと偽陽性の両方が起きる） |
| 手順・順序 | 「認可 → ロック検証 → サニタイズ」 | **高**（読まないと分からない） |
| 認可・エラー | 「admin 限定」「他者保持なら409」 | **高**（間違うと誤解が実害になる） |
| 全称・唯一 | 「〜だけ」「すべて」「リポジトリ全体でゼロ」 | **高**（反例1つで崩れる） |
| 構成・命名 | ファイル名・パッケージ名・依存の向き | 低〜中 |
| リンク | 相対リンク先の実在 | 低 |

### 3. 型ごとに検証する

```bash
# 数値（行数）。Measure-Object -Line は空行を数えないので使わない
wc -l internal/cms/*.go assets/*.js assets/*.css assets/*.html

# 実在（宣言があるか）
grep -rn 'func RequireEditLock(' --include='*.go' .

# 呼び出し関係。宣言行とテストを除く。**コメント内の言及が混じる**
grep -rn 'GetPerms(' --include='*.go' internal cmd | grep -v '_test.go'

# 相対リンクの実在
(cd docs && for l in $(grep -ohE '\]\(([^)#]+\.md)' *.md | sed 's/^](//'); do
   [ -e "$l" ] || echo "MISSING: $l"; done)
```

**呼び出し関係と全称主張は、数えた結果をそのまま信じない。**

- **コメントは偽陽性になる。** 実例: 「DOMヘルパーを使うのは `plugin_*.go` 6本」と
  書かれていたが、6本目のヒットは `plugin_file.go` の**コメント内の言及**で、実際は5本だった。
  件数が合うのに内訳が違うことがあるので、ヒット行は必ず目で見る。
- **メソッド名・構造体フィールド名も偽陽性になる**（`Name`/`Tags`/`Sync`、`Attr:` と `Attr(`）。
  詳細は `/code-reference` の「4. 依存関係を測る」。
- **全称主張は反例を探す向きで検証する。** 「〜だけ」を確かめるには、その1件を確認するのでは
  なく、**他に無いこと**を grep で示す。

**手順・順序と認可は grep では検証できない。** 対象のハンドラ・関数を**冒頭から通読**し、
文書の箇条書きと実際の行順を並べて突き合わせる。特に:

- 認可ゲートは何を要求しているか（`RequirePageWrite` か `RequireAdmin` か、認証だけか）。
  実例: 「`/api/lock` ほか3本 = 要＋write」と1行にまとめられていたが、`/api/unlock` は
  認証のみ、`/api/lock/force` は admin だった。**まとめた行は中身がばらけている**と疑う。
- ステータスコードの分岐条件（403/409/423 がどの条件で出るか）。
- フロントの実行順序は `defer` の有無と配置で決まる。実例: `<head>` の `defer` 付き
  スクリプトより、`</body>` 直前の `defer` 無しスクリプトの方が**先に走る**（文書は逆に
  書いていた）。読み込み順＝実行順ではない。

### 4. 判定を3つに分ける

| 判定 | どうするか |
|---|---|
| 一致 | 何もしない。**「確認した」と報告に残す**（次に読む人の手間を減らす） |
| 文書が誤り | 直す（手順5） |
| **コードが誤り** | 直さずに報告する。コード内の古いコメント・実態と合わない定数名など |

3つ目を潰さないこと。文書だけ実装に合わせると、間違ったコメントが正しいものとして
固定されてしまう。

### 5. 直す

- Edit ツールで最小差分。周辺の文・書式・見出し構造には触らない。
- **なぜ間違いだったかが再発防止になるなら、直した先に一言残す**
  （例: 「`defer` 付きは解析完了後に走るため app.js が先」）。
- 曖昧でどちらとも読める記述は、**具体的な数字・関数名に置き換える**。曖昧なままだと
  次の検証でまた判定に迷う。
- 検証できなかった主張は消さずに「未確認」と明記する。

### 6. 再検証

```bash
go build ./... && go test ./...   # 文書だけの変更でも念のため
```

文書に書いた数値は**直したあとにもう一度数える**（編集中にずれる）。リンクの実在チェックも
もう一度走らせる。

### 7. 報告

表で出す。読む人が追試できるよう、実際の値まで書く。

| 文書 | 箇所 | 誤り | 実際 |
|---|---|---|---|
| 全体地図.md | `storage.go` の役割 | 「`GetPageDir` だけ」 | 定数 `IDLength`・`MasterDir` もある |

最後に **「確認して正しかった主な記述」** を1段落で添える。これが無いと、報告に出ていない
箇所が「未確認」なのか「確認済みで正しい」のか読む人に分からない。
コード側の誤り（判定3）は**別の節**にして、文書の修正と混ぜない。

## やらないこと

- 推測での書き換え。確かめられないなら「未確認」と書く。
- 文体・語尾・見出しの趣味的な整形。差分が膨らんで、意味のある修正が埋もれる。
- 設計判断そのものの変更提案。それは考察文書と変更履歴の仕事。
- コード内コメントの修正（報告に留める）。

## 完了の条件

- 抜き出した主張がすべて「一致 / 修正済み / 未確認と明記」のいずれかになっている
- 直した数値をもう一度数え直した
- リンク切れゼロ、`go build` / `go test ./...` が通る
- コード側の誤りを別節で報告した
